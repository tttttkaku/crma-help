数式項目の追加

Data 360 でスキーマを作成したら、数式フィールドを追加できます。

必要なエディション

使用可能なインターフェース: Lightning Experience
  1. [データストリーム] タブに移動して、データストリームを選択します。
  2. データストリームの [詳細] ページで、[新規数式項目] を選択します。
  3. 数式を入力して、[保存] をクリックします。
    メモ データストリームの設定後に数式項目を追加する場合は、フル更新を実行して既存のレコードの項目を入力します。新規レコードの場合、数式項目は自動的に入力されます。

データレークオブジェクトへの検索条件の追加

データレークオブジェクト (DLO) 項目属性の検索条件を使用して、地域固有またはブランド固有のデータを表示します。異なる検索条件を使用して同じ DLO を複数のデータスペースに追加し、データを分離します。

必要なエディション

使用可能なエディション: Data 360 でサポートされるすべてのエディション。 「Data 360 Edition の可用性」を参照してください。
必要なユーザー権限
データレークオブジェクトに検索条件を追加する

権限セット

  • Data Cloud アーキテクト
  1. Data 360 で、[データスペース] タブに移動します。
  2. データスペースを選択します。
  3. DLO の横にあるドロップダウンから、[Set Filters (フィルタを設定)] を選択します。
  4. [検索条件を追加] をクリックします。
  5. オブジェクト、列、演算子を選択し、絞り込む値を入力します。ネストされた演算子はサポートされません。検索条件はキー修飾子以外のテキスト項目にのみ追加します。
    使用可能な演算子は、データ型によって異なります。
    • テキスト: 次の文字列と一致する、次の文字列と一致しない、次の文字列と一致しない、次の文字列を含む
    • 数値: 次の文字列と一致する、次の文字列と一致しない、次の文字列と一致しない、次の文字列と一致しない、次の文字列より大きい、次の文字列より小さい
    • 日付/日時: 次の値より大きい、次の値より小さい、最後の日数
    • Boolean: 次の文字列と等しくない
    メモ CONTAINS ANY 演算子では、部分一致または複数一致を識別するために複数のカンマ区切り値を使用できます。結果のデータには、項目が完全な値と一致するレコード、または入力をカンマで分割した後に取得した個々のトークンのみが含まれます。スペースはリテラルとして扱われます。たとえば、Biohealth, Systems の検索条件では、先頭または末尾のスペースを含め、完全に一致する文字列が特に検索されます。
    メモ DateTime 項目の値を選択すると、値は GMT に変換されず、Salesforce 組織のタイムゾーンで保存されます。たとえば、GMT-7:30 タイムゾーンで「2025-09-09 7:30 PM」を選択すると、「2025-09-10 03:00」(GMT) ではなく「2025-09-09 19:30」として保存されます。
    条件が DLO とデータストリームの合計レコード数に影響することはありません。
  6. [追加] をクリックし、次に [保存] をクリックします。
例

Data 360 に接続されているさまざまな地域の取引先責任者がセールス組織に存在し、取引先責任者 DLO がすべての取引先責任者と共に取り込まれているとします。取引先責任者を分離するには、地域 1 や地域 2 などの地域固有のデータスペースを作成し、2 つの異なる検索条件を追加して取引先責任者 DLO をこれらのデータスペースに関連付けます。両方の検索条件で、列に [Region (地域)]、演算子に [次の文字列と一致する] を選択します。最初の検索条件の値として「Region 1」、2 番目の検索条件の値として「Region 2」と入力します。

DMO メタデータのルート重要指標の追加または削除

ルートキーは、データグラフのプライマリデータモデルオブジェクト (DMO) のプライマリキーです。データグラフでは、ルートキーがメイン識別子です。また、データを取得するための初期アクセスポイントでもあります。これはプライマリ DMO のプライマリキーです。

必要なエディション

使用可能なエディション: Data 360 でサポートされるすべてのエディション。 「Data 360 Edition の可用性」を参照してください。
必要なユーザー権限セット
DMO メタデータのルート重要指標を追加または削除する

権限セット

  • Data Cloud アーキテクト

ルートキーを持つオブジェクトのメタデータインジケーターを追加すると、受信データでルートキーが識別されて使用され、計算プロセスが簡略化されます。これにより、更新実行時に不要なルックアップが排除されます。

メタデータインジケーターを使用できない場合、更新プロセスはデフォルトで従来の計算方法になります。たとえば、データグラフ構造では、主 DMO は顧客 DMO で、Web サイトエンゲージメントとケースの詳細が子 DMO です。Web サイトエンゲージメントデータモデルオブジェクト (DMO) には、ルートキーとなる顧客 ID が含まれます。この顧客 ID をルートキーとしてタグ付けできます。Web サイトエンゲージメント DMO では、データグラフの計算を合理化するためにメタデータ (具体的には組み込みルートキー) を直接使用します。ただし、ケースの詳細 DMO はクエリに従来の計算プロセスを使用します。

データグラフを作成または編集するときに、項目をルートキーとして指定できます。DMO のメタデータのルート重要指標を管理する手順は、次のとおりです。

  1. プライマリ DMO に直接関連しないオブジェクトに移動し、項目を選択します。
  2. [Select as Root Key (ルートキーとして選択)] をクリックします。後でメタデータインジケータを削除するには、フィールドを選択して [Remove as Root Key (ルートキーとして削除)] をクリックします。

データグラフでの検索条件の適用

検索条件は、新しいデータグラフを作成するときや既存のデータグラフを編集するときに適用できます。

必要なエディション

使用可能なエディション: Data 360 でサポートされるすべてのエディション。 「Data 360 Edition の可用性」を参照してください。
必要なユーザー権限セット
データグラフを編集する

権限セット

  • Data Cloud アーキテクト

検索条件を適用する

  1. データグラフから、［New］ をクリックしてデータグラフを作成するか、既存のデータグラフの横にある ［Edit］ をクリックします。
  2. データグラフエディターページで、含める DMO と項目を選択します。
  3. 検索条件を追加する
    1. [条件] セクションで、テキストボックスに検索条件を入力または更新します。
      メモ データグラフの検索条件は AND ロジックだけを使用して評価されます。
    2. サポートされている演算子を使用して、[条件を追加] をクリックします。
    構文は自動的に検証されます。
  4. 並び替えと制限を適用する
    1. [並び替えと制限] セクションで、並び替えの基準となる項目を選択します。
    2. 並び替え順 (昇順または降順) を選択します。
    3. 関連レコードの最大数と時間制限を設定します。
  5. 変更を確認し、[保存して構築] をクリックします。

ショートカットを使用したセグメント検索条件の簡略化

よく使用するセグメント検索条件属性をデータモデルパスと共にショートカットとして保存し、セグメントや有効化で再利用します。毎回属性ライブラリ内を移動して適切なデータモデルオブジェクト (DMO)、パス、属性を検索する代わりに、必要な設定を含む保存済みショートカットを選択できます。

必要なエディション

メモ

2025 年 10 月 14 日以降、Data Cloud は Data 360 にブランド変更されました。この移行中、アプリケーションやドキュメントでは「Data Cloud」と表示されている場合があります。名前は新しくなりますが、機能やコンテンツに変更はありません。

使用可能なエディション: Data 360 でサポートされるすべてのエディション。 「Data 360 Edition の可用性」を参照してください。

セグメントを作成する場合、適切な属性を見つけるには、使用する DMO やそれらを接続するパスなど、組織のデータモデルに関するKnowledgeが必要になることがよくあります。属性ショートカットでは、セグメント化オブジェクト、パス、対象属性を再利用可能な検索条件として保存することで、その複雑さを軽減します。ショートカットを 1 回作成すると、セグメント作成権限を持つすべてのユーザーがセグメント全体で使用できます。同じ検索条件を一貫して適用できます。

属性ショートカットは、属性ライブラリパネルの専用の [ショートカット] タブに既存のデータモデルタブと共に表示されます。[ショートカット] タブは、最初のショートカットを保存した後にのみ表示されます。

属性ショートカットのしくみ

各属性ショートカットには、次のコンポーネントが保存されます。

  • セグメントが構築されるセグメント追加オブジェクト
  • セグメント化オブジェクトから対象 DMO へのオブジェクトパス
  • パスの最終 DMO の対象属性

セグメントにショートカットを追加すると、Data 360 は保存したパスと属性設定を自動的に適用します。次に、検索条件の演算子と値のみを設定します。

属性ショートカットは、コンテナレベルではなく検索条件レベルで動作します。ショートカットには属性自体とそのパスが保存されますが、同じコンテナ内の集計設定や他の検索条件など、コンテナレベルのコンテキストは取得されません。

考慮事項

属性ショートカットを使用するときは、次の点に留意してください。

  • すべてのショートカットに一意の名前を使用します。使用中の名前でショートカットを保存しようとすると、別の名前を選択するように求められます。
  • 各属性パスには 1 つのショートカットのみを設定できます。特定のパスにショートカットが存在する場合は、既存のショートカットを使用するか、一意のパスを指定して作成できます。
  • ショートカットの範囲は、ショートカットが作成されたデータスペースになります。
  • ショートカットは組織レベルで保存されます。
  • ショートカットは DataKit でパッケージ化できるため、組織全体でリリースでき、Sandbox と互換性があります。
  • 属性ショートカットは、ガードレールとしてテナントあたり 500 個に制限されます。
例

小売企業のデータスペシャリストは、顧客が購入した商品に基づいてセグメントを作成することが多いです。統合個人プロファイルからメールを経て商品までのパスには、複数の DMO が含まれます。スペシャリストは、このパスを毎回移動する代わりに、「統合 → メール → 商品」というパスで「Product Drill Up (商品のドリルアップ)」という属性ショートカットとして保存します。セグメントを作成するチームメンバーは、基盤となるデータモデル構造を知らなくても、[Product Drill Up (商品のドリルアップ)] ショートカットをキャンバスにドラッグして、検索条件値の設定をすぐに開始できるようになりました。

  • 属性ショートカットの作成
    頻繁に使用する属性とそのデータモデルパスをショートカットとして保存して、自分と他のセグメントビルダーが毎回完全な属性ライブラリを移動せずに再利用できるようにします。
  • 属性ショートカットを使用したセグメントの作成
    事前設定されたデータモデルパスを使用して検索条件属性を保存する属性ショートカットを使用して、セグメントの作成を高速化します。完全な属性ライブラリを参照する代わりに、チームが設定したショートカットから選択します。

カテゴリ

データストリームを作成するときに、そのデータストリームで見つかったデータのカテゴリまたはタイプを選択します。

3 つのデータカテゴリは [プロファイル]、[エンゲージメント]、[その他] です。

警告 データストリームの保存後にカテゴリを変更することはできません。選択する前に、種別を慎重に確認します。

プロファイル

データセットが次に対応する場合は、[プロファイル] を選択します。

  • コンシューマー ID、メールアドレス、電話番号などの識別子を持つ個人のリスト
  • 取引先 ID を含むビジネスまたは取引先のリスト
  • セグメントの基準とするか、セグメントの開始母集団として使用する、従業員または他の母集団のリスト

セグメント化、統合、強化するエンティティに関するデータには、プロファイルデータストリームを使用します。エンティティには、人 (消費者や従業員) や人間以外のもの (車両、デバイス、ロイヤルティカード) が主な対象である場合が含まれます。

エンゲージメント

データセットが時間系列に基づいている場合は、[エンゲージメント] カテゴリを選択します。データストリームカテゴリを [エンゲージメント] に設定する場合、ソーススキーマの日付または日時型付け項目を使用してイベント時刻を定義します。エンゲージメントカテゴリを選択すると、UI に [イベント時刻項目] ドロップダウンが表示されます。

重要 [イベント時刻項目] は、最初に設定した後に編集することはできません。データレコードで定義された後に変更されない日付または日時型の項目を選択します。変更可能な日付項目を使用するとレコードの重複が発生し、同じプライマリキーを持つ複数のレコードがデータレークオブジェクト (DLO) に追加されます。たとえば、頻繁に変更される項目 (更新日など) を選択すると、重複レコードが作成される可能性が高くなります。同じファイルのすべてのレコードのファイル抽出日が同じであるため、ファイルの抽出日など、他の種別の日付でもレコードが重複する可能性があります。
例 保険請求が作成された日付と保険請求の状況が変更された日付の 2 つの日付の保険請求データを取り込んでいます。[イベント時刻項目] には、請求が更新された日付ではなく請求が作成された日付を使用します。請求が作成された日付は、請求の作成後に変更されません。ただし、請求が更新された日付は、請求ステップのレビュープロセスによって変更されます。

Other

データセットがプロファイルとエンゲージメントに関連しているが、セグメンテーションと統合の主エンティティになる予定がない場合は、[その他] カテゴリを選択します。このカテゴリは通常、プロファイルレコードまたはエンゲージメントレコードの説明属性を提供する参照データに使用されます。

ヒント 時系列データセットがあり、不変の日付項目がない場合、[その他] カテゴリを選択します。
例 自動車ディーラーは、商品カタログ (説明、色、価格)、店舗の所在地 (住所と時間)、静的車種 (メーカー、年式、エンジン種別) などの参照データに Other データストリームを使用します。プロファイルデータストリームには、個々の顧客レコードが含まれます。また、エンゲージメントデータストリームには、販売トランザクションの時系列レコードが含まれます。

データモデルオブジェクトのカテゴリ

Data Cloud の [データモデル] タブでデータモデルオブジェクト (DMO) のカテゴリを表示します。

DMO にはカテゴリの概念は組み込まれていません。代わりに、DMO はそのカテゴリをマッピングされた最初のデータレイクオブジェクト (DLO) から継承します。これらのカテゴリ間の後続の対応付けを作成できます。

  • プロファイル DLO はプロファイル DMO または他の DMO に対応付けることができますが、エンゲージメント DMO に対応付けることはできません。
  • エンゲージメント DLO はエンゲージメント DMO にのみ対応付けることができます。
  • 他の DLO はプロファイル DMO または他の DMO に対応付けることができますが、エンゲージメント DMO に対応付けることはできません。
例 Sales Order (販売注文) は、エンゲージメントカテゴリの Order-Headers (注文ヘッダー) という DLO に最初にマッピングされます。この DLO により、Sales Order (販売注文) がエンゲージメントカテゴリに割り当てられます。その後、Sales Order (販売注文) にマッピングできるのはエンゲージメントカテゴリの DLO のみです。

項目マッピングキャンバスでは、DLO カテゴリと互換性のある DMO のみを選択できます。

属性ショートカットの作成

頻繁に使用する属性とそのデータモデルパスをショートカットとして保存して、自分と他のセグメントビルダーが毎回完全な属性ライブラリを移動せずに再利用できるようにします。

必要なエディション

使用可能なエディション: Data 360 でサポートされるすべてのエディション。 「Data 360 Edition の可用性」を参照してください。
必要な権限セット
属性ショートカットを作成する

次の権限セットのいずれか:

  • Data Cloud アーキテクト
  • Data Cloud 有効化マネージャー
  • Data Cloud 有効化スペシャリスト

属性ショートカットを作成する前に、データモデルを設定し、セグメント化オブジェクトから対象属性へのパスを理解していることを確認します。

属性ショートカットは、属性ライブラリの操作中にセグメントビルダー内から作成します。セグメント間で再利用する属性が見つかったら、わかりやすい名前を付けてショートカットとして保存します。このショートカットでは、セグメント化オブジェクト、関連 DMO のパス、対象属性を取得します。これにより、他のセグメント・ビルダーは、基盤となるデータ・モデル構成に関する幅広いKnowledgeがなくてもショートカットを使用できます。

  1. Data 360 で、[セグメント] をクリックします。
  2. 既存のセグメントを開いて [Edit Rules (ルールの編集)] をクリックするか、新しいセグメントを作成してセグメントビルダーのキャンバスに移動します。
  3. 属性ライブラリパネルで、ショートカットとして保存する属性を検索します。直接属性または関連属性セクションのいずれかを使用できます。
    メモ 複数のデータモデルオブジェクトに表示される直接属性の場合、左ペインに属性を選択するときのパスが表示されます。ショートカットとして保存する前に、目的のオブジェクトから取得していることを確認します。属性ライブラリの移動方法によって、関連属性のパスが決まります。
  4. 属性を選択してセグメントキャンバスに追加します。
  5. [ショートカットとして保存] をクリックします。
    [属性のショートカットを保存] ウィンドウが開き、属性のオブジェクトパスが表示されます。
  6. ショートカットの名前を入力します。
    属性の意味とセグメント化オブジェクトとの関係を明確に説明する簡潔な名前を選択します。たとえば、「unified_email_product_path」ではなく「Product Drill Up」を使用します。
  7. (省略可能) ショートカットが何を表すかを説明する説明を入力します。
  8. ショートカットを保存します。
    Data 360 によって属性ショートカットが保存され、属性ライブラリパネルの [ショートカット] タブに表示されます。
  9. [完了] をクリックして、セグメントキャンバスの検索条件を確認します。

    4. [次へ] をクリックします。
  8. (省略可能) 有効化メンバーシップに検索条件を追加して、イベントとの関連性を高めます。絞り込みに使用できる DMO は、有効化でデータグラフが使用されているかどうかによって異なります。
    1. データグラフがない場合、有効化された DMO の属性のみを有効化メンバーシップの絞り込みに使用できます。
    2. 有効化でデータグラフが使用されている場合、有効化された DMO から最大 2 ホップ離れたそのデータグラフに含まれる DMO の属性で絞り込むことができます。これにより、データグラフですでにモデル化した関連 DMO を使用して、より正確な利用者条件を適用できます。
  9. (省略可能) キャンペーンに関連する同意とその他の連絡先検索条件を追加します。
    1. レコードごとに送信される連絡先の最大数を選択します。
    2. 連絡先を並び替えてランク付けする属性を選択します。[次へ] をクリックします。
  10. 名前、説明 (省略可能)、有効化の開始日と終了日を入力します。

Data 360 でデータ削除要求を送信する方法について説明します。

Data 360 で個々のデータプロファイルのデータ削除要求を送信できます。同意 API を使用して、すべての要求を送信する必要があります。

データ削除要求により、指定された個人レコードが個人 DMO および関連 DMO から削除されます。

警告 削除に含めるには、データが個人 DMO に関連付けられている必要があります。関連のない DMO に保存されているデータは削除されません。

すぐには処理されないデータ削除は、通常数時間以内に実行されます。この時間は、削除する必要があるレコードの数に応じて長くなる可能性があります。

削除要求は、30 日、60 日、90 日後に再処理され、追加されたデータが削除され、完全削除が確認されます。

すべての接続システムと Salesforce クラウドでデータ削除要求を送信する必要があります。

完全修飾キーを使用したデータ解釈

完全修飾キーは、さまざまなソースから取り込まれたデータを正確に解釈するのに役立ちます。各データストリームは、その特定のキーと属性と共に Data 360 に取り込まれます。複数のデータストリームが 1 つのデータモデルオブジェクト (DMO) にハーモナイズされると、さまざまなキーが競合し、複数のレコードが同じキー値を持つ状態になる可能性があります。完全修飾キーを使用すると、キー修飾子項目を追加してデータを正確に解釈できるため、競合を回避できます。

完全修飾キーは、ソースキー (CRM の取引先責任者 ID や Marketing Cloud Engagement の購読者キーなど) とキー修飾子で構成されます。

たとえば、Salesforce CRM の取引先責任者 DLO とエンゲージメントの購読者 DLO の 2 つのデータストリームに、プロファイルデータの関連データレイクオブジェクト (DLO) があるとします。この DLO のレコードが個人 DMO にマッピングされます。ここで、個人 DMO をエンゲージメント DMO と結合して 2 クリック以上の個人を特定しようとしています。完全修飾キーを使用して 2 つの異なるソースから取り込まれたデータを正確に解釈できるしくみを次に示します。

2 つのデータストリームは、Data 360 の個人 DMO にマッピングされます。取引先責任者 DLO には 3 件のレコード、購読者 DLO には 2 件のレコードがあります。この場合、個人 DMO にはマッピングされたすべてのデータストリームからのレコードがすべて含まれるため、5 件のレコードがあります。

Engagement では CRM 組織の取引先責任者 ID をプライマリキー (購読者キー) として使用します。そのため、個人 DMO の複数のレコードでプライマリキー項目である個人 ID の値が同じになります。

次に、エンゲージメントから取り込まれたメールエンゲージメントデータが含まれるメールエンゲージメント DMO について考えます。個人 DMO とメールエンゲージメント DMO には個人 ID を介した 1:N リレーションがあります。

個人 DMO とメールエンゲージメント DMO を結合すると、Data 360 は結合されたデータセットを、個人 2 の最初の行が 1 回のクリック、個人 2 の 2 番目の行が 1 回のクリックと解釈します。つまり、個人 2 は 2 メールクリックと想定されます。けれども、Data Cloud では個人 2 は 2 クリックアクションと解釈されますが、実際には 1 クリックアクションのみです。

この誤解釈により、セグメンテーション、計算済みインサイト、クエリ API など、このデータが照会されたときに問題が発生することがあります。クエリを実行して、クリックアクションが 2 以上の個人を照会すると、応答で個人 2 が返されます。この問題は、プロファイルの統合がリリースされていても発生します。エンゲージメントデータは常に個人 DMO と結合されるからです。

この問題は、完全修飾キーを使用することで回避できます。キー修飾子フィールドを、プライマリキーまたは外部キーのいずれかのキー値を含むすべての DLO フィールドに追加すると、Data 360 は異なるデータソースから取り込まれたデータを正しく解釈します。次の例では、キー修飾子が Salesforce CRM と Engagement からの DLO に追加されています。個人 DMO にはレコードのソースを示すキー修飾子項目が追加されています。

個人 DMO とメールエンゲージメント DMO を結合する場合、テーブル結合では外部キー フィールド (個人 ID) とキー修飾子フィールド (KQ_ID) の両方が使用されます。これにより、Data 360 はデータを正確に解釈できます。

同じクエリを実行して、クリックアクションが 2 以上の個人を照会すると、個人 2 のデータはクエリ条件を満たさないため、クエリ応答では返されません。

データレンズを使用したデータの視覚化

Data Lens では、直観的でインタラクティブな環境で詳細なデータの探索と視覚化を行うことができます。静的レポートだけでなく、データを直接操作して、隠れた価値のあるインサイトとパターンを明らかにすることができます。

データレンズを使用すると、次のことができます。

  • 分布の分析: 値の広がりを理解してパターンと異常値を特定します。
  • リレーションの探索: 関連するデータポイント間の接続を検出します。
  • 行の詳細を検査: 個々の行を確認して集計データを検証します。
  • Pinpoint Nulls (Null を特定): データセット内の欠損値を特定します。
  • 一意の値を分類: 個別のエントリを認識してデータを分類します。
  • データ型の理解: 各項目に割り当てられるデータ型を決定します。
  • ビューの合理化: 項目を表示または非表示にして、データパースペクティブを最適化します。

データレンズでは、[セグメント]、[データレークオブジェクト]、[データモデルオブジェクト] タブ内で次のユーザーインターフェース機能が提供されます。

  • Profile View (プロファイルビュー): データ列を色の付いた棒として表示し、データの分布、値、null を集計します。値をクリックして、リレーションを含めたり除外したり強調表示したりできます。
  • データグリッドビュー: 行レベルの詳細を表示するスプレッドシートのようなビュー。一貫性を確保するためにプロファイルペインと同期されます。
  • リストビュー: ビューを合理化するために項目を表示または非表示にします。

Data Lens は、既存のクエリレイヤーを活用してデータをプレビューし、確立されたセキュリティプロトコルに準拠して動作します。Data Lens では、クエリ時に適用される動的 PII マスキングなどのポリシーが適用されます。つまり、Data Lens プレビューにはマスクされたデータのみが表示され、マスクされていない未加工データは元の場所では安全なままです。このアプローチにより、データの探索やプレビュー中に機密情報が不正に表示されないように保護され、厳格なデータガバナンスとコンプライアンスの要件に対応できます。

警告

ソースデータの少量のサンプルに基づいて日付形式または日時形式が提案されます。提案の確認は各自の責任で行ってください。誤った推奨形式をレビューせずに受け入れると、データが破損する可能性があります。

たとえば、ソースデータで MM/DD/YYYYY が使用されていて、システムで DD/MM/YYYY が推奨されている場合、03/07/2024 のような日付は 2024 年 3 月 7 日ではなく 2024 年 7 月 3 日と解釈されます。

データの破損を回避するには、続行する前に推奨形式がソースデータに完全に一致することを手動で確認します。ソースファイルまたはデータストリームの複数行を確認して、正しい形式を確認します。システムの提案がデータと一致しない場合は、形式を手動で編集します。

Data 360 は、受信した未加工データを確認して、該当するデータ型を推奨します。形式の提案も行います。日付種別から日時へ、または日時から日付種別へ上書きする場合は、形式を同じままにして未加工データの形式が反映されるようにしてください。

Marketing Cloud Next について

Marketing Cloud Next は、プラットフォームの機能をチームのマーケティング活動に提供します。複数のデータ ソースをData 360と統合し、Experience Cloudでコンテンツを作成し、Flow Builderで複雑なカスタマー ジャーニーを強化し、その過程でAgentforceで最適化できます。

連携

Marketing Cloud Next は、セグメンテーションなどの特定の機能に Data 360 を使用します。マーケティング担当者はマーケティングアプリケーションで ToDo を実行できますが、一部のシステム管理者 ToDo とデータ ToDo を完了するには Data 360 アプリケーションにアクセスする必要があります。

デフォルトでは、マーケティング アプリケーションには次のData 360タブが含まれます。

  • ID 解決 – システム管理者は ID 解決を使用して、マーケティングで使用する受信データの統合方法を決定するルールセットを作成します。
  • セグメント – マーケティング担当者はセグメントを使用して、マーケティングキャンペーンの対象オーディエンスを特定します。
  • プロファイルエクスプローラー – マーケティング担当者は、プロファイルエクスプローラーを使用して、データが統合取引先および統合個人レコードにどのように関連するかを確認します。

その他のデータ タスクについては、Data 360アプリケーションにアクセスするか、システム管理者にタブをマーケティング アプリケーションに追加するよう依頼してください。次の Data 360 タブは、マーケティング管理者に役立ちます。

  • データストリーム – システム管理者は、設定時に Marketing Cloud Next を Salesforce CRM や他の接続アプリケーションに接続するデータストリームをリリースします。
  • データグラフ – システム管理者は、基本的なコンテンツのパーソナライズで使用される顧客データと商品データを提供するデータグラフを設定できます。
  • データレイクオブジェクトとデータモデルオブジェクト – データアナリストは、取り込まれたデータを保存するオブジェクト項目と対応付けを確認して設定します。
  • データモデル – データアナリストがカスタムオブジェクトを作成し、オブジェクトリレーションを構築または確認します。

考慮事項

Marketing Cloud Next を有効化または使用する前に、次の考慮事項を確認してください。

  • データの取り込み、セグメンテーション、テストメールの送信などの一部のマーケティングタスクでは、使用量ベースの価格設定が使用されます。Agentforce 機能もクレジットを消費します。
  • Marketing Cloud Next を初めて有効にすると、デフォルトのデータスペースが作成されます。ほとんどのマーケティング機能は、このデータスペースと連携するように事前設定されています。カスタムデータスペースを使用する場合、マーケティングユーザーは特定のタスク中に正しいデータスペースを選択する必要があります。
  • Marketing Cloud Next のデータを取り込んでマッピングするには、各 DMO またはソーステーブルのプライマリキーに関連する一意の識別子を使用します。たとえば、CRM から人データを対応付けるには、リード ID を個人 ID に対応付けます。
  • Marketing Cloud Engagement で Data 360 を使用する場合、人データのプライマリキーとして [登録者 ID] を選択することをお勧めします。

Better Together: データと AI

信頼できる正確で関連性の高いデータに基づく AI ソリューションが最も役立つエージェントです。Data 360を使用すると、さまざまなデータ ソースを顧客または取引先の統合プロファイルに統合できるため、AIとAgentforceの機能が向上します。

AI ソリューション

プロンプト駆動型 Salesforce AI ソリューションは、データ型に関係なく YOUR データに基づきます。グラウンディングにより、より適切で信頼性の高い応答が日々のワークフローに組み込まれます。初回に正確な回答をすることで、チームの時間を節約し、不正確な懸念を軽減します。

また、Salesforce AI ソリューションは、予測機能から現在の生成 AI への拡張へと進化しました。AI プラットフォームでは、ビジネス要件と AI の専門知識に合わせてモデルを選択できます。新規ユーザー向けには、OpenAI、Azure、Anthropic などのプロバイダーが提供するさまざまなモデルが用意されています。エキスパートの場合は、AIモデル(旧称Einstein Studio)を使用して独自のモデルを統合できます。Salesforce の柔軟なプラットフォーム上に構築すると、すべてのユーザーが AI にアクセスできるようになります。

Agentforceでは、組み込みソリューションやエージェント主導のエクスペリエンスを通じて、新しい方法で作業フローにAIを使用できるようになりました。

Data 360 を選択する理由

Data 360は、堅牢で拡張性が高く安全なデータ基盤を提供するため、AgentforceなどのAIソリューションを強化します。既存のAI機能の中にはこの機能を必要としないものもありますが、Data 360は、次のような重要な方法ですべてのデータ ソースにグラウンディングされた高速で信頼できるAIをサポートするために必要です。

  • すべてのデータタイプ: 音声、サポートチャット、PDFなど、構造化データや非構造化データをData 360に取り込みます。
  • リアルタイムデータ: Data 360 を使用して、数秒でデータを処理して反応します。
  • ゼロ コピー:ゼロ コピー データ統合を使用してSalesforceの外部にデータを接続することで、データの範囲を拡張します。
  • Trusted Data:Trust Layerと呼ばれる安全なAIアーキテクチャにより、安心してAI環境を利用できます。
  • マルチモデルのサポート: AIモデルでモデルを作成するか、独自のモデルを使用します。

高頻度データグラフ更新のデータドリフト

データグラフを 1 日に 1 回以上更新するようにスケジュールすると、データドリフトが発生する可能性があります。データドリフトは、高速更新サイクルでソースシステムからの更新を完全に取得または調整できず、データグラフに一時的な矛盾が生じる場合に発生します。

必要なエディション

使用可能なエディション: Data 360 でサポートされるすべてのエディション。 「Data 360 Edition の可用性」を参照してください。

フル更新は 24 時間に 1 回自動的に実行され、より頻繁な更新サイクル中にドリフトがあれば修正されます。

データドリフトの原因

フル更新が完了する前にデータグラフが複数回更新されると、データドリフトが発生する可能性があります。一般的な原因は次のとおりです。

  • 部分的な更新: ソースシステムのレコードが 1 日に数回変更されると、フル更新が実行されるまで、すべての更新がデータグラフに表示されるわけではありません。

  • Deleted or Modified Records (削除または変更済みレコード): ソースで削除または変更されたレコードは、次のフル更新で調整されるまでデータグラフに残ります。

  • 複雑なリレーション: 関連データまたは結合キーが更新されると、フル更新ですべてのデータが再処理されるまで、不一致または重複するノードがグラフに表示される可能性があります。

  • 階層連動関係: 親ノードがシステムに存在する前に、より深いレベルのノードに更新が到着した場合にもドリフトが発生する可能性があります。このような場合、フル更新時に親ノードが処理されるまで、子レコードは一時的に不一致または欠落したリレーションとして表示されます。

データドリフトの修正方法

スケジュールされた毎日のフル更新では、取得元からのすべてのデータが再処理され、グラフがデータの最新の状態に再調整されます。このプロセスにより、頻繁な更新サイクル中に表示される矛盾、重複、古いレコードが削除されます。ベストプラクティスとして、ほぼリアルタイムのデータが必要で一時的な矛盾が許容される場合にのみ、より高い頻度での更新を使用してください。

データグラフでの DMO リレーションの特殊な処理

データモデルオブジェクト (DMO) リレーションは、データの処理方法とデータグラフ (特にリアルタイムデータグラフ) への反映方法に影響する可能性があります。データグラフを設計するときに DMO リレーション種別を確認し、処理の動作が想定された更新パターンに従っていることを確認します。

必要なエディション

使用可能なエディション: Data 360 でサポートされるすべてのエディション。 「Data 360 Edition の可用性」を参照してください。

リアルタイムデータグラフでは、1 対 1 および 1 対 N の DMO リレーションがサポートされます。N:1 リレーションは、複数の子レコードが 1 つの親レコードを参照する場合に発生します。たとえば、販売注文商品と商品カテゴリ間のリレーションについて考えてみます。販売注文には複数の商品を含めることができ、注文の各商品は販売注文商品レコードとして表されます。各販売注文商品は、[エレクトロニクス] や [ファッション] などの商品カテゴリに関連付けられます。1 つの注文に、どちらも [エレクトロニクス] カテゴリに属する iPhone と ProgID、および [ファッション] カテゴリに属する T シャツが含まれる場合があります。

このシナリオでは、複数の販売注文商品レコードが同じ商品カテゴリレコードを参照します。たとえば、iPhone と ProgID の両方の販売注文商品レコードでエレクトロニクス商品カテゴリが参照されます。このリレーションは、多くの子レコードが 1 つの親レコードに対応付けられる N:1 リレーションを表します。子レコードの外部キー (商品カテゴリ ID) は親レコードの主キーを参照するため、複数の子レコードが同じ親レコードを参照できます。

リアルタイムデータグラフが作成されたタイミングに基づく N:1 リレーションのサポートの次の 2 つのシナリオについて考えてみます。

  • 新しいリアルタイムデータグラフの動作: 新規作成または編集されたリアルタイムデータグラフでは、N:1 リレーションはサポートされません。DMO を追加すると N:1 リレーションが導入されるため、作成中または編集中に選択がブロックされます。
  • 既存のリアルタイムデータグラフの動作: この制限が導入される前に作成されたリアルタイムデータグラフには、すでに N:1 リレーションが含まれている場合があります。これらのグラフは、下位互換性のために引き続き実行されます。ただし、N:1 リレーションの親 DMO への変更は、リアルタイムデータグラフ内の関連レコードにすぐには反映されません。更新された値は、その設定に従ってデータグラフが再構築または更新された後にのみ使用可能になります。

この制限は、新しく作成されたリアルタイムデータグラフにのみ適用されます。標準データグラフでは、引き続き N:1 リレーションがサポートされます。

Docling Parser

Docling パーサーは、レイアウトの理解とテーブルの抽出のために複数のオープンソースモデルをまとめたサードパーティのインテリジェントなドキュメント解析フレームワークです。画像や複雑なテーブルで使用可能な情報からの回答を強化するには、大規模言語モデル (LLM) を使用して Docling パーサーを画像処理と組み合わせます。

メモ LLM を使用して画像を解析すると、クレジット消費に影響し、インテリジェント処理の利用状況種別に対して請求されます。詳細は、「非構造化データの請求に関する考慮事項」を参照してください。

LLMベースの画像処理により、Data 360はロゴなどの不要な画像を除外し、複雑なインフォグラフィックのみをルーティングします。Data 360 は、特定のしきい値を超える画像を含むページをキャプチャして、キャプション用の 1 つのページ全体の画像として送信します。これにより、複数の画像間のリレーションが取得され、品質が維持され、遅延が軽減されます。

LLMベースの画像処理では、Data 360は複雑なテーブルのみを評価してLLMに転送します。これには、ネストされたヘッダーを持つテーブルや、複数のページにまたがる長い形式のマージ列が含まれます。

詳細は、「Docling パーサー」を参照してください。

この機能強化により、LLM はフローチャートを構造化プロセスとして解釈し、ノード、コネクタ、矢印、ステップの順序を認識できます。LLM では、表示ラベルのフラットなリストではなく、ロールおよび部門全体のアクションの連続したフローが再構築されます。その結果、責任や一連のステップに関連する項目の質問への回答の精度が高まります。

完全修飾キー

Data 360 データモデルでさまざまなソースからのデータがハーモナイズされるときに、完全修飾キー (FQK) を使用してキーの競合を回避します。

キー値が含まれるすべてのデータレークオブジェクト (DLO) 項目にキー修飾子項目を設定して FQK を使用します。この項目はプライマリキー項目または外部キー項目にできます。

  • 完全修飾キーを使用したデータ解釈
    完全修飾キーは、さまざまなソースから取り込まれたデータを正確に解釈するのに役立ちます。各データストリームは、その特定のキーと属性と共に Data 360 に取り込まれます。複数のデータストリームが 1 つのデータモデルオブジェクト (DMO) にハーモナイズされると、さまざまなキーが競合し、複数のレコードが同じキー値を持つ状態になる可能性があります。完全修飾キーを使用すると、キー修飾子項目を追加してデータを正確に解釈できるため、競合を回避できます。
  • 完全修飾キーのベストプラクティス
    完全修飾キー (FQK) を使用して、さまざまなデータソースから取り込まれたデータを Data 360 で正確に解釈できるようにします。
  • データオブジェクトの完全修飾キー
    Data 360では、キー修飾子フィールドがDLO(データ レイク オブジェクト)とDMO(データ モデル オブジェクト)に追加されます。キー修飾子項目は、DLO と DMO 間のオブジェクトリレーションとオブジェクトマッピングを作成するときにも追加できます。
  • クエリ API の完全修飾キー
    クエリ API を使用して、Data 360 のデータを照会します。Data 360メタデータAPIを使用してデータ レイク オブジェクトのキー修飾子フィールドを識別し、すべてのテーブル結合にキー修飾子フィールドを含めて正確な結果を取得します。
  • キー修飾子項目の設定
    データストリームを作成したら、データレークオブジェクト (DLO) 項目にキー修飾子を追加して、完全修飾キー (FQK) を作成します。プライマリキーまたは外部キーのいずれかが含まれるすべての DLO 項目にキー修飾子を設定します。最大 20 個の有効なキー修飾子を追加できます。キー修飾子は、DLO 項目で使用される場合に有効になります。Data 360 では、データモデルオブジェクト (DMO) 項目に対してキー修飾子が自動的に追加および削除されます。これらのシステム項目は編集できません。
  • キー修飾子の削除
    乱雑さを軽減し、組織のキー修飾子の制限に達しないようにするには、システムから不要なキー修飾子を削除して削除します。キー修飾子を削除するには、まず、キー修飾子が関連付けられているすべてのデータレイクオブジェクト (DLO) 項目から削除してから削除します。DLO 項目からキー修飾子を削除するだけで、システムから削除することはできません。DLO 項目からキー修飾子を削除すると、計算済みインサイト、セグメント、有効化、API クエリの精度に影響する可能性があります。

データストリーム、インサイト、およびその他のソースから作成された (属性で構成される) データのグルーピング。DMO はビジネスニーズに基づいて標準 DMO にすることもカスタム DMO にすることもできます。一般的な標準 DMO には、販売注文、取引先、関係者 ID、メールエンゲージメントなどがあります。次のような DMO があります。
  • 仮想: データレークオブジェクトのビュー。
  • 物理: Data 360 にある実際のデータのグルーピング。
データ共有
Data 360からデータを移動せずにクエリを実行できるようにするDLO(データ レイク オブジェクト)、DMO(データ モデル オブジェクト)、CIO(計算済みインサイト オブジェクト)のコレクション。

データを交換できるシステム。
データスペース

データストリーム

データ変換
Data 360 でデータを直接結合、形成、クリーンアップ、準備する機能。
データ型

データベース
構造化情報 (データ) の整理されたコレクション。通常はコンピューターシステムに保存されます。永続的なデータベースでは、データは長期にわたって保存されます。たとえば、顧客の購入データは複数年保存されます。

ディメンション
基準を分類するために使用する定性的な値。たとえば、すべての顧客の総支出額を表示する場合は、顧客 ID が総支出額の基準に関連付けられたディメンションになる可能性があります。

ハッシュされた電話
「SHA」またはセキュアハッシュアルゴリズムによって匿名化するための一意の鍵を含む匿名電話番号の一種。
ハイブリッド検索
キーワード検索とベクトル検索の結果をマージしてランク付けし、最も関連性の高い応答を生成するプロセス。ハイブリッド検索では、2 つの結果セットが生成されます。1 つはキーワードの一致に基づく結果セット、もう 1 つは意味の類似性に基づく結果セットです。ハイブリッド検索フュージョンランカーモデルでは、この結果を 1 つのランキングに再ランク付けして、取得拡張生成 (RAG) で使用します。
ハイブリッド検索の自動ドロップ
ハイブリッド検索の自動ドロップでは、検索クエリの関連性スコアが急激に減少している結果が動的に除外されます。これにより、プロンプトと RAG の使用事例の検索結果の精度が向上します。
ハイブリッド検索フュージョンランカー
Data 360ハイブリッド検索から取得したマージ結果をランク付けし、検索クエリに最も関連性の高い結果を表示するフュージョンランキングモデル。

リレーション
2 つのオブジェクトまたはデータのセット間の接続。次のようなリレーションがあります。
  • 1 対 1 (1:1): 2 つのテーブルの情報間のリンク。各テーブルの各レコードは 1 回のみ表示されます。たとえば、従業員と従業員が運転する車の 1 対 1 のリレーションなどです。「直接属性」を参照してください。
  • 1 対多 (1:N): テーブルの 1 つのレコードが別のテーブルの 1 つ以上のレコードに関連付けられる場合があるレコード間のリレーション。たとえば、顧客ごとに多数の販売注文がある可能性があります。「関連属性」を参照してください。

一連の特性を共有するオブジェクトのセット (B2C の個人など)。オーディエンスと同様に、この内部リソースでも相違点の詳細を確認できます。オーディエンスと母集団数に関連します。
セグメント
マーケティング担当者が有効化対象に送信するセグメントを作成できる Data 360 のタブ。
セグメント基準
セグメンテーション内のセグメント基準は、セグメントを構築するために使用される対象オブジェクトを定義します。
セグメンテーション
データを照会して、さまざまな属性または特性に基づいてグループに分割する機能。たとえば、過去 30 日間に靴を購入した顧客などです。
ストリーミングインサイト
ほぼリアルタイムのデータに基づく計算およびクエリ。ストリーミングインサイトを使用してデータアクションを作成できます。
構造クエリ言語 (SQL)
SQL は、「sequel」または「S-Q-L」で発音されるクエリ言語で、データベースの情報へのアクセスや変更に使用されます。インサイトは、Data 360 で SQL を使用して作成されます。
構造オブジェクトクエリ言語 (SOQL)
標準の構造化クエリ言語 (SQL) と同様に、SOQL を使用して Salesforce データモデルを照会します。データインサイトは、Data 360 の SOQL を使用して作成されます。 SOQL の発音は「ソーケル」または「エスオーキュール」です。
構造化データ
スキーマに準拠した特定の一貫した形式の情報。このデータは定義済みのテーブル、行、列に整理されているため、リレーショナルデータベースでの保存、クエリ、分析が容易です。一般的な例として、CRM レコード (取引先、取引先責任者、リード)、E コマーストランザクション、その他の顧客プロファイルデータなどがあります。
主題領域
データモデリングに役立つ類似する DMO をグループ化するために使用される用語。Data 360 の主題領域には、関係者、エンゲージメント、ロイヤルティなどが含まれます。

特定の一貫した形式がなく、一般的なリレーショナルデータベースに簡単に保存できないデータ。一般的な非構造化データには、チャットトランスクリプト、音声ファイル、Web サイト、法的文書、その他の大きなテキスト (書籍など) があります。

デルタ抽出

Marketing Cloud Engagement では、2 種類の増分抽出 ([日付でデルタ抽出] と [数値でデルタ抽出]) がサポートされています。

数値でデルタ抽出

[数値でデルタ抽出] を選択すると、数値データ型のデータエクステンションの項目のカスケードリストが作成されます。連続する抽出間のハイウォーターマークのベースとして数値項目を選択します。

この抽出方法では、選択した [数値] 項目に従ってデータエクステンションデータが昇順に並び替えられます。最初の抽出では、並び替えられた最も高い数値 (最大値) の次にハイウォーターマークがトリガーされ、そのマーク以下のデータが送信されます。2 番目の抽出までに、他のデータが蓄積され、最大値が更新される可能性があります。2 番目の抽出には、最初の最大値と更新された最大値間のすべてのデータ行が反映されます。新しい抽出ごとに、最後から 2 番目の最大値 (最後から 2 番目に識別された最大値) と最後に識別された最大値間のすべての新しいデータ行が送信されます。

日付でデルタ抽出

[日付でデルタ抽出] を選択すると、日時データ型のデータエクステンションの項目のカスケードリストが作成されます。連続する抽出間のハイウォーターマークのベースとして日時項目を選択するように求められます。

この抽出方法では、選択した [日時] 項目に従ってデータエクステンションデータが昇順に並び替えられます。最初の抽出では、並び替えられた最も新しい日時の次にハイウォーターマークがトリガーされ、そのマーク以下のデータが送信されます。2 番目の抽出までに、他のデータが蓄積され、最も新しい日時または最大値が更新される可能性があります。2 番目の抽出には、最初の最大値と更新された最大値間のすべてのデータ行が反映されます。新しい抽出ごとに、最後から 2 番目の最大値 (最後から 2 番目に識別された最大値) と最後に識別された最大値間のすべての新しいデータ行が送信されます。

強固なデータ基盤: Data 360 と Informatica IDMC

Salesforce は、Data 360 と Informatica のインテリジェントデータマネージメントクラウド (IDMC) を使用して、基本的なデータ管理機能を提供します。IDMC は、高度なデータ品質、系統、ガバナンス、マスターデータ管理 (MDM) 機能を提供します。Data 360 は、データを統合プロファイルに接続、ハーモナイズ、統合し、安全で信頼できるデータ基盤を提供します。Data 360 と IDMC は、プロジェクトのさまざまなフェーズで並列または個別に使用できます。

連携

IDMC と Data 360 を使用して、メタデータ管理、ビジネス用語集の作成、ルールベースのポリシーなど、補完的なデータガバナンスイニシアチブを実現します。アプリケーションは連携して、種別に関係なくすべてのデータソースに接続し、データからアクション可能な情報を抽出します。AgentforceまたはMCP(モデル コンテキスト プロトコル)サーバーを使用して、Data 360でのAIの使用事例を強化します。IDMC では、分析の実行、データのおすすめの提供、データタスクの自動化が可能な AI ツールである CLAIRE GPT を使用します。

IDMC は、データインテグレーション、分類、ガバナンス、データ品質、継続的なデータメンテナンスに使用します。IDMC は、Data 360 がさまざまな使用事例で有効化できる信頼性の高いクリーンアップ済みデータを提供します。

MDM と統合プロファイル

IDMC は MDM を使用してゴールデンレコードを作成するのに対して、Data 360 は ID 解決を使用して統合プロファイルを作成するという重要な概念の違いがあります。

  • MDM。IDMC を使用して、クリーンで強化され、重複排除されたマスターレコードを作成および管理します。マスターレコードは、組織の一元化された情報源として機能します。MDM は柔軟性が高く、サプライヤー、ロケーションから国、コストセンターに至るまで、さまざまなデータセットを処理できます。
  • 統合プロファイル。Data 360 の ID 解決ルールセットを使用して、データをリンクする統合プロファイルを作成します。統合プロファイルでは、すべてのソースからの連絡先値が保持されるため、基礎となるデータを損失、統合、上書きすることなく、総合的なビューを作成できます。

Data 360 は MDM システムではないため、ID 解決機能は IDMC MDM 機能に代わるものではありません。代わりに、既存の MDM ソリューションを補完する役割を果たします。MDM はマスターデータを管理し、統合プロファイルはそのデータをアクション可能にする有効化レイヤーとして機能します。

Data 360 と IDMC は、個別に使用する方法に関係なく、データ管理のあらゆる側面に対応する完全なツールセットを作成します。
