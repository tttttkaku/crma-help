Data Cloud でのオーディエンスセグメントの作成

カリフォルニアを拠点とする顧客に今後のポリシー変更について通知する SMS メッセージを作成するには、Data Cloud で次の手順に従ってオーディエンスセグメントを作成します。

  1. Data 360 の [セグメント] タブで、[新規] をクリックします。
    1. [データスペース] で、[デフォルト] を選択します。
    2. [セグメント対象] で、統合個人データモデルオブジェクト (DMO) を選択します。
    3. セグメントに「Terms of Service Changes - CA」 (サービス規約の変更 - CA) という名前を付け、説明を追加します。
    4. [次へ] をクリックします。
  2. [公開種別] で、[公開スケジュールが 24 時間の標準公開] を選択します。
    この種別によって、セグメントで使用するエンゲージメントデータの量が決まります。スケジュールによって、データを更新する頻度が決まります。
  3. [Publish Schedule (公開スケジュール)] に、開始日時と有効期限を入力し、[保存] をクリックします。
  4. 直接属性リストで、[統合個人] を選択します。
  5. [State of Residence (居住都道府県)] をセグメントキャンバスにドラッグします。
    1. 演算子を [次の値と等しい] に設定し、カリフォルニアの値 CA を入力します。
  6. [完了] をクリックして [保存] をクリックします。

セグメントの絞り込みと Marketing Cloud Engagement への公開

セグメントを作成したら、検索条件を追加して利用者を絞り込むことができます。この使用事例では、同意状況と、ユーザーが電話番号を提供したかどうかで絞り込みます。

  1. Data 360 の [セグメント] タブで、[Terms of Service Changes - CA (サービス利用規約の変更 - CA)] セグメントを選択します。
  2. セグメントレコードの [有効化] セクションで、[新規] をクリックします。
  3. Marketing Cloud Engagement 有効化対象 (セグメントデータの有効化先) を選択します。
    1. 有効化メンバーシップで、[Individual] を選択します。
    2. [続行] をクリックします。
  4. 連絡先(チャネル)として [+ Select for Phone (SMS)] をクリックします。
    1. 電話パスと発信元の優先順序を確認し、[次へ(Next)] をクリックします。
  5. メンバーに選択される連絡先を決定するには、[連絡先] で [検索条件を追加] をクリックします。
  6. 同意を管理するには、連絡先同意 DMO (L3) に移動します。
    1. [データ使用目的] 属性をセグメントキャンバスにドラッグし、[次の値と等しい] 演算子を選択して、値「Services」を入力します。
    2. [同意状況] 属性をセグメントキャンバスにドラッグし、[次の値と等しい] 演算子を選択して、[オプトイン] の値を入力します。
    3. [完了] をクリックします。
  7. コミュニケーション登録の同意 DMO (L4) に移動します。
    1. [コミュニケーション登録] 属性をドラッグし、[次の値と等しい] 演算子を選択して、値に [サービス利用規約] を入力します。
    2. [同意状況] 属性をドラッグし、[次の値と等しい] 演算子を選択して、[オプトイン] の値を入力します。
    3. 属性に AND 演算子があることを確認し、[完了] をクリックします。
  8. 2 つの DMO の AND 演算子を確認します。
  9. [保存] をクリックします。
  10. [連絡先] では、連絡先チャネルごとに 1 つの値のみが送信されるため、[属性値の最大数] の値は 1 になります。[並び替え] で、[最終更新日] 属性と [降順] 演算子を選択してデータを整理します。
  11. このキャンペーンには、顧客の名と姓を含めるためのパーソナライズ用のプレースホルダーがあります。この情報が Marketing Cloud Engagement に送信されるようにするには、有効化に属性を追加します。
    1. 画面の上部にある [Add Attributes (属性を追加)] をクリックします。
    2. 個人 ID に加えて、直接属性リストから [名] と [姓] を選択してキャンバスにドラッグします。
    3. パスが正しいことを確認し、[保存] をクリックします。
    4. [次へ] をクリックします。
  12. 有効化に「Terms of Service Changes - CA」 (サービス規約の変更 - CA) という名前を付けて、説明を追加します。
    1. [増分更新] を選択します。
    2. [保存] をクリックします。

有効化が Marketing Cloud Engagement に送信されます。

ポリシー変更 SMS 通知 (B2C) の使用事例のテキスト送信

Cumulus Bank は、カリフォルニアに住む顧客に今後の保険契約の変更についてアカウントを確認するように SMS メッセージを送信したいと考えています。顧客が同意したすべての電話連絡先を含めることを希望している。

要件の特定

  • 目標
    • カリフォルニアに住むすべての顧客に今後の保険契約の変更に関する SMS 通知を送信します。
  • パーソナライズコンポーネント
    • SMS メッセージには、顧客の名と姓が含まれます。
  • 利用者とデータソース
    • 同意を提供したカリフォルニア州に住む顧客とその電話番号。
    • 関連する DMO: 統合個人、個人、連絡先電話、連絡先登録に関する同意、コミュニケーション登録に関する同意
  • Data Cloud でのオーディエンスセグメントの作成
    カリフォルニアを拠点とする顧客に今後のポリシー変更について通知する SMS メッセージを作成するには、Data Cloud で次の手順に従ってオーディエンスセグメントを作成します。
  • セグメントの絞り込みと Marketing Cloud Engagement への公開
    セグメントを作成したら、検索条件を追加して利用者を絞り込むことができます。この使用事例では、同意状況と、ユーザーが電話番号を提供したかどうかで絞り込みます。

IP ネットワーキングポリシーの追加

Snowflake データ共有対象の設定時に認証エラーが発生した場合は、必ず Snowflake に Data Cloud IP アドレスを含めてください。Snowflake で、許可される Data Cloud IP アドレスをリストする IP ネットワークポリシーを作成します。

必要なエディション

使用可能なエディション: Data 360 でサポートされるすべてのエディション。 「Data 360 Edition の可用性」を参照してください。
  1. Data Cloud で、[設定] をクリックして、[Data Cloud 設定] を選択します。
  2. インスタンスを見つけます。たとえば、「CDP2-AWS-PROD1-USEAST1」のように入力します。
  3. 地域に基づいて、[IP Addresses Used by Data Cloud Services (Data Cloud サービスで使用される IP アドレス)] テーブルで VPCE ID とソース IP アドレスを特定します。たとえば、CDP2-AWS-PROD1-USEAST1 の場合、クラウドは AWS、リージョンは US-EAST-1、VPCE ID は CDP2 です。
  4. Snowflake で、IP アドレスを含むネットワークポリシーを作成します。 
    CREATE OR REPLACE NETWORK POLICY <name> -- Example: SFDC_NW_POLICY
    ALLOWED_IP_LIST = ('ip1 from step 3', 'ipN from step 3')
    COMMENT = 'Policy for SFDC Auth';
  5. セキュリティインテグレーションにネットワークポリシーを添付します。 
    CREATE OR REPLACE SECURITY INTEGRATION oauth_kp_int
    TYPE = oauth
    ENABLED = true
    OAUTH_CLIENT = custom
    OAUTH_CLIENT_TYPE = 'CONFIDENTIAL'
    OAUTH_REDIRECT_URI = '<SFDC_Callback_URL>'
    NETWORK_POLICY = SFDC_NW_POLICY;

データマスキング

Salesforce 組織とモデル Playground のデータマスキング設定によって、機密情報のプライバシーと、そのデータが応答でどのように表示されるかが決まります。組織レベルの設定はデフォルトで有効になっています。

モデル設定を作成または更新するときに、モデル Playground プロンプト設定でデータマスキングを有効にします。データ マスキングを有効にすると、テスト中にデータがサードパーティの大規模言語モデルに Einstein Trust Layer から送信されないようにし、プロンプト応答ですべての機密データをマスキングします。この設定を無効にすると、テスト中に名前、誕生日、メールアドレスなどの機密データがマスクされなくなります。

組織レベルでは、Einstein Trust Layerによって、本番にリリースされたモデル用に選択された機密データが検出され、マスクされます。

AI モデルのモデル系統

モデルの系統により、トレーニングデータ、バージョン管理、リリース、ライブデータでの使用に至るまで、AI モデルのライフサイクルの追跡可能な履歴が提供されます。Data 360は、この機能をAIモデル(旧Einstein Studio)とガバナンスに統合しています。

AI モデルでは、詳細ページと [インテグレーション] タブで予測モデルの下流の表示を確認できます。このビューは、モデルの利用状況、連動関係、インテグレーションを明確に示すため、監査可能、再現可能、信頼できるアセットを作成するために不可欠です。モデルの詳細にはページ上部にメタデータが表示されますが、インテグレーションはモデルがライフサイクル全体を通じて使用する推測チャネルです。

メタデータ

各インテグレーションには、モデルの状況 (有効または無効)、種別、最終実行日、実行状況、データモデルオブジェクト (DMO) が表示されます。

これらの推測チャネルは [インテグレーション] タブで表示できます。

  • 一括処理データ変換: 推測に AI ノードを使用するデータ変換。
  • フロー: Data 360 アクションを使用してモデルを参照するフロー。
  • 予測ジョブ: 推測に使用されるストリーミングジョブまたは一括処理ジョブ。
  • Personalization Maps (パーソナライズマップ): パーソナライズの決定を絞り込むために Salesforce Personalization ターゲティングルールで使用されるモデルからの予測。

これらのインテグレーションからのインサイトは、次の機能を提供します。

運用効率

リストビューでは、この情報が 1 か所に統合され、調査時間が大幅に短縮されます。

影響分析

モデルを再トレーニングまたは削除する前に、変更がどのビジネスプロセス (特定のフローや変換など) に影響するかをすぐに確認できます。

オブジェクトまたは項目へのタグの手動適用

必要なエディション

使用可能なエディション: Data 360 でサポートされるすべてのエディション。 「Data 360 Edition の可用性」を参照してください。
ユーザー権限が必要です  
タグを適用する 「Data Cloud アーキテクト」権限セット
  1. Data Cloud で、[データガバナンス] タブに移動します。
  2. [タグマネージャー] をクリックします。
  3. 左ペインで、オブジェクトを選択します。
  4. データモデルオブジェクトまたは計算済みインサイトオブジェクトを選択する場合、関連付けられているデータスペースを選択します。
  5. [タグを添付] をクリックし、タグを検索します。
  6. タグをオブジェクト全体に割り当てるには、[次のタグを <オブジェクト名> に追加] を選択します。
  7. オブジェクトの特定の項目にタグを適用するには、項目を選択します。
  8. [保存] をクリックします。

Data 360 の分類タグ

分類により、分類内で追加のコンテキストと意味が提供されます。機密性や使用目的などの定義済みの条件に基づいてデータを分類できるため、データの適切な管理、保護、使用が容易になります。

たとえば、HIPAA 規制の対象となるヘルスケアデータを [PII 機密] として分類し、特別な処理が必要であることを示すことができます。分類者は、一般的なポリシーアクションを必要とするタグをグループ化することもできます。この方法では、同じ分類を共有するすべてのオブジェクトに一貫してポリシーを適用できます。たとえば、[機密] として分類されたデータのマスキングポリシーを定義する場合、ポリシーの設定は 1 回のみです。新しいデータオブジェクトが作成されたときに、必要に応じて機密分類を割り当てるだけで、ポリシーを再作成または変更することなく自動的に適用されます。

データガバナンスに関する考慮事項

開始する前に、Data 360でデータ ガバナンス機能を使用する場合にサポートされる機能と考慮事項を確認することが重要です。

サポートされる機能

データガバナンスタグとポリシーは、次の Data 360 機能でサポートされています。

  • Data Cloud One: データガバナンスでは、自宅組織とコンパニオン組織の両方で一貫したタグ付けとポリシー管理がサポートされます。「Data Cloud One でのタグ付けとポリシー管理」を参照してください。
  • DevOps データキット: DevOps データキットにタグを含めて、関連付けられた標準およびカスタムデータモデルオブジェクト (DMO) と共にパッケージ化し、Sandbox から本番組織にマージできます。これにより、開発環境と本番環境で一貫したタグ付けが実現します。「データキットと Data 360 in a Sandbox」を参照してください。
  • Data 360 Sandbox: Sandbox 環境にタグを含めて本番組織にマージできるため、開発組織と本番組織で一貫したタグ付けを実現できます。

一般的な考慮事項

  • 権限セットを使用してデータスペースを割り当てても、自動的にユーザーにデータへのアクセス権は付与されません。
  • Data 360 では、既存の組織と新しい組織の両方に [すべて許可] ポリシー (Day Zero ポリシーとも呼ばれる) が標準で用意されています。
  • システム管理者は、特定のアクセス要件に基づく詳細なアクセス制御を有効にするには、デフォルトの [すべて許可] ポリシーを削除する必要があります。
  • ポリシーで明示的に許可されている場合を除き、データスペースのデータへのアクセスは制限されます。
  • 行レベルセキュリティポリシーはクエリに適用されます。クエリがアクセスするオブジェクトと項目のセキュリティチェックに合格すると、行レベルポリシーが適用されてアクセス権が決定されます。
  • オブジェクトに対して行レベルの許可ポリシーが作成された場合、データへのアクセスは行レベルの許可ポリシーを持つユーザーのみに制限されます。

データアクセスポリシーの作成

これらのガイドラインにより、定義されたポリシーに基づいて Data 360 のデータアクセスを制御できます。

  • 許可ポリシー:
    • ログインユーザーに、オブジェクトや項目などのリソースのデータへの参照アクセス権とメタデータへの編集アクセス権を付与します。
    • 助成金で指定されたオブジェクトのすべての項目とレコードへのアクセス権を付与します。
  • 拒否ポリシー:
    • 「すべてのレコードの参照 (VAR) すべてのレコードの編集 (MAR)」権限を持つユーザーがこれらの制限をスキップできる場合を除き、すべてのアクセス権を上書きします。
    • リソースへのログインユーザーアクセスを拒否します。
  • 複数のポリシーが同じユーザー、リソース、およびアクションに適用される場合、拒否ポリシーが優先され、許可ポリシーと競合する場合はアクセスが拒否されます。
  • [主キー] 項目と [完全修飾キー] 項目に影響する項目レベルの拒否ポリシーを記述すると、予期しない結果になる可能性があるためお勧めしません。
  • ポリシーに対するカスタム権限の影響
    Data 360 のカスタム権限は、ポリシーの適用方法を決定する上で重要な役割を果たします。カスタム権限セットまたはプロファイルを使用してユーザーに割り当て、ポリシービルダー内でユーザー属性として機能させることができます。

  • 明確な目的と範囲を定義する: まず、分類でサポートされる特定の目的 (顧客データ、営業情報、業務評価指標のタグ付けなど) を特定します。範囲を絞り込むことで、構造を管理しやすく関連性を維持できます。

  • 複雑さよりも明確さを優先する: 技術的な用語やあいまいな用語よりもシンプルで明確なビジネス用語を優先します。分類は、技術者以外のユーザーでも直感的で容易に正しく適用できる必要があります。

    • 親タグ: 目的に関連する広範で論理的なグルーピングを確立します。たとえば、顧客データ、商品情報、運用評価指標などです。

  • 一貫性の維持:
    • 標準化された命名規則を使用します。たとえば、Cust_ID や CustomerID などのバリエーションではなく、常に顧客 ID を使用します)。
    • タグ名は明確かつ明確にしてください。一貫した命名により、提案タグなどの LLM 機能を備えた機能を使用する場合の使いやすさが向上し、結果が向上します。
  • 小さく開始して反復する:
    • 最初は、親タグと子タグのセットをいくつか使用します。
    • Data 360 オブジェクトのサンプルセットにタグを付けて分類をテストします。
    • さらに拡張する前にユーザーからフィードバックを収集し、構造を調整します。

自動コンテンツタグ付けの設定 (ベータ)

非構造化ファイルの自動コンテンツタグ付けを設定し、信頼性しきい値を定義します。Data 360 はしきい値以上であるタグを承認しますが、その他のタグは手動で確認する必要があります。

必要なエディション

コンテンツのタグ付けは構造化されていないコンテンツに適用され、最初に検索インデックスを入力する必要があります。自動タギングを有効にすると、選択したオブジェクトのすべての新しい非構造化データに適用されます。

使用可能なエディション: Data 360 でサポートされるすべてのエディション。 「Data 360 Edition の可用性」を参照してください。

自動コンテンツタギングを使用するには、組織に動的データマスキング SKU をプロビジョニングします。このライセンスにより、Data 360 で機密データを分類およびマスキングできるセキュリティポリシーとガバナンスポリシーが有効になります。「Data 360 Editions and Licenses」を参照してください。

メモ コンテンツのタギングと非構造化データのマスキングは、パイロットまたはベータ サービスであり、お客様が実行した場合は Agreements - Salesforce.com のベータ サービス条件、書面の場合は統合パイロット契約、および製品条件ディレクトリの適用条件が適用されます。このパイロットサービスまたはベータサービスは、お客様ご自身の裁量でご利用ください。

自動コンテンツタグ付けを設定する

  1. Data Cloud で、[データガバナンス] タブに移動します。
  2. 左側のナビゲーションから、[Tag Assignments (タグ割り当て)]> [Content Tagging (コンテンツタグ付け)] に移動し、[Objects Selected for Automatic Content Tagging (自動コンテンツタグ付けに選択されたオブジェクト)] ドロップダウンを選択します。
  3. コンテンツのタギング設定を編集するには、[編集] をクリックします。
    コンテンツのタグ付けは構造化されていないコンテンツに適用され、最初に検索インデックスを入力する必要があります。自動タギングを有効にすると、選択したオブジェクトのすべての新しい非構造化データに適用されます。
    UDLO にはオブジェクトあたり最大 5 GB のタグを付けることができます。データが大きい場合は、複数の UDLO に分割し、個別の検索インデックスを作成します。合計サイズが5 GBを超えると、検索インデックスを再構築すると既存のタグがすべて削除され、以前に保護されていたデータは保護されなくなります。
  4. 自動タギングを有効にするには、[Enable Automatic Content Tagging (自動コンテンツタギングを有効化)] を選択します。
  5. [Automatic Content Tagging Threshold (自動コンテンツタギングしきい値)] ドロップダウンから、タグを自動的に承認する信頼性しきい値を選択します。信頼性しきい値は、タグの自動承認の厳格度を制御します。
    • Low (低): タグは、精度に関係なくすべてのデータに適用されます。
    • Medium (中): タグは、中～高精度のデータにのみ適用されます。
    • 高: タグは高精度のデータにのみ適用されるため、エラーは減りますが、自動タグ付けは制限されます。
  6. [設定を保存] をクリックします。
  7. 検出されたコンテンツ タグを確認し、タギングしきい値に基づいて適用された数を確認するには、[タグ]> [タグ マネージャ] に移動して、UDLO の検索インデックスを選択します。

Data 360 での外部ユーザーアクセスの制御

データガバナンスポリシーを使用して、Data 360 対応アプリケーションで外部ユーザーがアクセスできる内容を制御します。明確なポリシーベースのアクセスを定義することで、身元不明外部ユーザーと認証済み外部ユーザーに目的のデータのみが表示されるようにします。

必要なエディション

Data 360 では、Trust とアクセスのレベルが異なる次のユーザー タイプがサポートされます。内部ユーザーの Trust レベルは最も高く、身元不明外部ユーザーの Trust レベルは最も低くなります。

  • Unidentified External User (身元不明外部ユーザー): サインインせずに Data 360 を使用するアプリケーションにアクセスする認証されていないユーザー。このユーザーには Data 360 ユーザー権限は必要ありません。身元不明外部ユーザーのポリシーによってアクセスが制御されます。
  • 認証済み外部ユーザー: 対外アプリケーションから Salesforce にアクセスする認証済みユーザー (顧客やパートナーなど)。これらのユーザーには Data 360 ユーザー権限は必要ありません。認証済み外部ユーザーのポリシーによってアクセスが制御されます。
  • 内部ユーザー: 従業員やコントラクターなど、Salesforce 組織の認証済みユーザー。割り当てられた権限、データスペースアクセス、および適用されるガバナンスポリシーによって、Data 360 データへのアクセスが制御されます。外部ユーザーのアクセスポリシーでは、内部ユーザーは制御されません。
必要なユーザー権限
外部ユーザーのデータアクセスポリシーを作成する

権限セット

  • Data Cloud アーキテクト

Data 360 を利用する多くのアプリケーションには、顧客やパートナーなどの外部ユーザーが関与します。機密情報が誤って漏洩しないように、Data 360 にはデフォルトでアクセスを制限するガードレールが組み込まれています。

Data 360 では、分類とポリシーで明示的にアクセスを許可しない限り、すべてのデータへの外部ユーザーのアクセスが拒否されます。分類によってオブジェクトが外部アクセスの対象であるかどうかが決まり、ポリシーによってオブジェクトにアクセスできるユーザーが決まります。

  • Unidentified external users: Data 360 は、標準 ExternalData.Visibility.Public タグを適用してオブジェクトを公開として分類しない限り、すべてのオブジェクトへのアクセスを拒否します。
  • 認証済み外部ユーザー: Data 360 は、標準ExternalData.Visibility.Portalまたは ExternalData.Visibility.Public タグを適用してオブジェクトをポータルまたは公開として分類しない限り、すべてのオブジェクトへのアクセスを拒否します。
  • 内部ユーザー: Data 360では、外部表示タグを必要とせずに、内部ポリシーと分類に基づいてアクセスできます。

外部ユーザーにアクセス権を付与するには、分類、ポリシーの作成、および認証済み外部ユーザーの場合は権限セットを使用したデータスペースアクセス権が必要です。詳細は、「Data 360 のデータタギングと分類」および「Create a Object or Field-Level Access Policy in Data 360 (Data 360 でのオブジェクトまたは項目レベルのアクセスポリシーの作成)」を参照してください。

ポリシー承認レベル

ポリシーには、ユーザー種別を定義する認証レベル ([内部]、[認証済み外部]、または [識別されていない外部]) が含まれます。ポリシーを作成するときにこのレベルを設定します。この選択により、選択した認証レベルに基づいて編集できないデフォルト条件がポリシーに追加されます。ポリシーの保存後に認証レベルを変更することはできません。

ポリシーは、ユーザーの認証レベルに基づいてカスケードロジックに従います。

  • Allow policies cascade up (ポリシーのカスケードを許可): 身元不明外部ユーザーにアクセス権を付与すると、認証済み外部ユーザーと内部ユーザーにもそのアクセス権が付与されます。
  • ポリシーを拒否: 内部ユーザーへのアクセスを拒否した場合、これは認証済みおよび身元不明外部ユーザーにも適用されます。

既存のすべてのポリシーは、自動的に内部ユーザーのみに適用されます。

外部アクセスの保護とガバナンスに関する考慮事項

外部アクセスを設定する前に、次の考慮事項を確認してください。

  • 自動ガードレール: オブジェクトレベルの外部ユーザーに対する許可ポリシーを作成すると、システムによって自動的にデフォルト条件が追加されます。
    • リソースセクションでは、条件でオブジェクトをData Categorization.Access Level.PortalまたはData Categorization.Access Level.Publicとして分類する必要があります。
    • プリンシパルセクションでは、選択した認証レベル (身元不明外部ユーザーや認証済み外部ユーザーなど) にのみアクセス権を付与することが条件となります。この条件により、広範な [許可] ポリシーで内部データが誤って公開されたり、意図しないユーザー種別にアクセスが許可されることを防ぎます。
  • セキュリティアクセス制御: 認証された外部ユーザーと共有されるオブジェクトに対してオブジェクトレベルセキュリティ (OLS)、項目レベルセキュリティ (FLS)、または行レベルセキュリティ (RLS) ポリシーを作成し、ユーザーが目的のデータにのみアクセスできるようにします。
  • 従来のポリシー保護:セキュリティを維持するために、Data 360は認証レベルの導入前に作成されたすべてのポリシーを内部ユーザーに自動的に制限します。
  • 権限セットおよびデータスペース割り当て: 認証済み外部ユーザーまたは身元不明外部ユーザーに「Data 360 ユーザー」権限セットまたは明示的なデータスペース割り当てを割り当てないでください。「Data 360 ユーザー」権限セットは、内部 Salesforce ユーザー専用です。外部ユーザーは、DMO/DLO オブジェクトタギングと明示的なデータガバナンスの許可ポリシーを介してのみ Data 360 データにアクセスできます。

AI エージェントを介した身元不明外部ユーザーアクセス

Data 360 でのオブジェクトまたは項目レベルのアクセスポリシーの作成

データガバナンスでは、ユーザーおよびデータ属性に基づいて特定のデータオブジェクトまたは項目にアクセスできるユーザーを定義します。ユーザーへのオブジェクトレベルまたは項目レベルのアクセス権を作成します。

必要なエディション

このタスクを完了する前に、次のガイドラインと制限事項を考慮してください。

  • Data 360 では、オブジェクトレベルセキュリティ (OLS) および項目レベルセキュリティ (FLS) ポリシーにサービス保護の制限を適用して、複雑なポリシーがシステムパフォーマンスに影響しないようにします。影響は、ルールの数と条件の複雑さによって異なります。ポリシーがより複雑になると、影響が大きくなります。ポリシーを作成、編集、または削除するときに、これらの制限が確認されます。制限を超えるポリシーは保存できません。ポリシーを簡略化するか、既存のポリシーを統合します。
  • データグラフ内のオブジェクトに OLS または FLS の制限が適用されると、不正アクセスを防ぐためにグラフがリストビューに非表示になります。ただし、ドラフト データグラフの基礎となるオブジェクト (ID や値 DMO など) はまだ作成されていないため、このフィルタリングは適用されません。そのため、ドラフトデータグラフがリストビューに引き続き表示される可能性がありますが、そのグラフを開くとエラーが表示されます。
  • Data Cloud アーキテクトまたは「すべてのレコードの参照 (VAR) すべてのレコードの編集 (MAR)」権限を持つユーザーは、拒否ポリシーが設定されている場合でも、すべてのオブジェクトのメタデータを表示できます。ポリシーで制限されている項目を含め、レポートの作成中または編集中に項目をレポートに追加できます。ただし、アクセスポリシーは実行時に適用されます。Data 360 管理者またはユーザーがレポートに含まれる項目へのアクセス権を持っていない場合、レポートの実行に失敗し、エラーが表示されます。
使用可能なエディション: Data 360 でサポートされるすべてのエディション。 「Data 360 Edition の可用性」を参照してください。
必要なユーザー権限

Data 360 でのレコードレベルポリシーの作成

ユーザー属性とデータ属性に基づいて、オブジェクト内の特定のレコードにアクセスできるユーザーを定義します。

必要なエディション

このタスクを完了する前に、次の考慮事項を確認してください。

  • DMO または計算済みインサイトオブジェクトでレコードレベルセキュリティポリシー (RLS) を作成すると、そのポリシーはオブジェクトが使用可能なデータスペースにのみ適用されます。これは、API 参照名にデータスペースプレフィックスが含まれており、ポリシーがこの API 参照名に基づいて作成されているためです。
  • RLS と結合ポリシーでマスクされた項目を結合キーとして使用している場合、結合はマスクされた値に基づいて実行されるため、結果が不正確になる可能性があります。RLS での結合クエリでのマスクされた項目の使用は避けてください。
  • 正確なオブジェクトリレーションと効果的なデータ結合を維持するために、主キー項目と外部キー項目をマスク解除します。
  • RLS ポリシーは、セグメントおよび計算済みインサイトの作成時に適用されません。これらの操作はシステムコンテキストで実行されるためです。
  • 現在、RLS ポリシーでは、ポリシー条件を満たすユーザーのレコードのみが絞り込まれます。デフォルトの Day 0 Allow All オブジェクトレベルセキュリティ (OLS) ポリシーは引き続き有効なため、他のユーザーにはすべてのレコードが表示されます。今後の変更では、RLS 許可ポリシーによって [0 日目にすべてを許可] ポリシーが無効になります。RLS 条件を満たさないユーザーは、RLS ポリシーで管理されているすべてのレコードにアクセスできなくなります。たとえば、RLS ポリシーで米国の商談レコードにのみアクセス権が付与されている場合、必要な権限のないユーザーには、この変更後に商談レコードが表示されなくなります。
  • 階層データは定期的に同期されます。ソースシステムの変更が Data 360 に反映されるには、最大 15 分かかります。

動的データマスキングポリシーを作成する

  1. Data Cloud で、[データガバナンス] タブに移動します。
  2. 左ペインで、［Policies］ をクリックします。
  3. [新規] をクリックし、[動的データマスキング] を選択して、[次へ] をクリックします。
  4. Policy Builder で、一意のポリシー名と必要に応じて説明を入力します。ポリシー API 参照名はポリシー名に基づいて自動的に入力されますが、変更できます。
  5. [次へ] をクリックします。
  6. [ルール] を選択し、保護するリソースを選択します。[Resource (リソース)] ドロップダウンで、[String in Unstructured Data (非構造化データの文字列)] を選択します。
    デフォルトでは、ルールはすべてのデータスペースに適用されます。新しいデータスペースが追加されると、システムルールがそのリソースに適用されます。
  7. ポリシーを特定のデータスペース範囲に制限するには、[Customize Scope (範囲のカスタマイズ)] をクリックし、[Apply to the resources in all Data Spaces in Data Cloud (Data Cloud のすべてのデータスペースのリソースに適用)] を選択解除して、目的のデータスペースを選択します。
  8. [保存] をクリックします。
  9. リソースに対して実行するアクションを選択します。[アクション] ドロップダウンから、[マスク] を選択します。
  10. 次のいずれかのマスキング方法を選択します。
    • Redaction (縮小) - マスクされた文字を X に置き換えます。縮小する文字数を選択します。
    • Nullification - データを NULL に置き換えます。
  11. このアクションを実行する条件を定義します。
    たとえば、オブジェクトに Financial Data.Account Info タグが存在する場合にルールをトリガーする条件を設定します。または、オブジェクトに Personal Data.Digital Identifier.Browsing History タグが存在しない場合の条件を設定します。
  12. ポリシーをユーザーに適用するには、[ユーザー] を選択します。
  13. すべてのユーザーまたは特定の AND および OR 条件を満たすユーザーにポリシーを適用します。条件は、ユーザーに割り当てられたカスタム権限に基づきます。
  14. さらに条件を追加するには、[条件を追加] をクリックします。
  15. 条件を異なるセットにグループ化し、OR 演算子を使用して、グループがルール条件を満たしたときにアクションを実行することもできます。グループを追加するには、[Add Group (グループを追加)] をクリックします。
  16. [保存して有効化] をクリックします。

Salesforce ユーザーの Data Cloud データアクセスレベルの管理

Data Cloud へのアクセス権や他のコンテキストで Data Cloud を表示する権限を付与せずに、Data Cloud データへの関連リスト強化やその他の SOQL クエリへの参照アクセス権を Salesforce ユーザーに付与するように権限セットを設定できます。

データアクセスレベルを更新するには、[設定] で権限セットを選択し、Data Cloud データスペース管理に移動して、データスペースを選択します。

Data Cloud データへの親アクセス権による権限の付与

あるオブジェクト (親オブジェクト) に別のオブジェクト (子オブジェクト) が使用する値が含まれている場合、オブジェクト間のリレーションは「親子」リレーションと呼ばれます。

データスペースに対する「親による制御」アクセス権を付与すると、関連する親オブジェクトのデータを参照するアクセス権がある限り、子オブジェクトのデータを表示できます。Data Cloud データへの「親による制御」アクセス権を付与すると、Salesforce ユーザーは、データに関連するレコードを参照する権限を持っている限り、関連リストまたは SOQL クエリ結果で Data Cloud データを表示できます。

例 たとえば、Data Cloud が Salesforce 組織の取引先責任者オブジェクトから取引先責任者に関する情報を取り込むとします。その後、取引先責任者レコードと関連レコード (エンゲージメントレコードなど) が ID 解決によって処理され、統合プロファイルに含まれます。システム管理者は、取引先責任者オブジェクトで、各取引先責任者の統合プロファイルのすべてのエンゲージメントデータを表示する充実した関連リストを作成します。システム管理者は、ユーザーが Data Cloud にアクセスしたり、統合プロファイルを直接表示したりせずに、強化された関連リストデータを表示できるようにしたいと考えています。この場合、システム管理者は取引先責任者オブジェクトレコードを参照する権限を持つユーザーに「親による管理」アクセス権を付与し、強化された関連リストも表示できるようにします。

オブジェクト、項目、およびレコードレベルセキュリティ

Data 360 のデータガバナンスポリシーは、ユーザーロール、属性、リレーションに基づいて、オブジェクト、項目、行などのさまざまなレベルでデータへのアクセスを制御します。

例

制御できるさまざまなアクセスレベルの例を次に示します。

  • オブジェクトレベルセキュリティ (OLS): Customer_Orders オブジェクトには、適切なデータスペースに割り当てられた営業部門のユーザーがアクセスできます。
  • 項目レベルセキュリティ (FLS): 財務チーム外のユーザーに対して [クレジットカード番号] 項目を非表示にします。
  • レコードレベルセキュリティ (RLS): 特定の地域の顧客レコードをユーザーに表示したり、保護されたオブジェクトのデータとログインユーザーの属性を比較して、顧客が所有するレコードのみを表示したりします。サポートされるすべての属性は、18 文字形式で保存された Salesforce ID です。
    • ユーザー ID – ログインユーザーの一意の ID
    • ロール ID – ユーザーの Salesforce ロール
    • 組織 ID – ユーザーの Salesforce 組織
  • RLS with Joins: アクセスルールで外部対応付けテーブルまたはルックアップテーブルを参照できるようにすることでレコードレベルセキュリティを拡張し、より動的でコンテキストを認識するアクセス条件を可能にします。たとえば、マネージャー階層に基づいて、商談レコードが自分またはレポートチェーンの他のユーザーによって所有されている場合に、そのレコードへのアクセスをユーザーに許可するアクセスポリシーを作成できます。
  • 階層付き RLS: マネージャー階層やロール階層など、Salesforce CRM のレポート構造に基づいてアクセスルールを設定できます。ポリシールールを作成すると、マネージャーには自分とチームが所有するレコードが自動的に表示され、チームメンバーは自分のレコードのみを表示できます。
  • Data 360 でのオブジェクトまたは項目レベルのアクセスポリシーの作成
    データガバナンスでは、ユーザーおよびデータ属性に基づいて特定のデータオブジェクトまたは項目にアクセスできるユーザーを定義します。ユーザーへのオブジェクトレベルまたは項目レベルのアクセス権を作成します。
  • Data 360 でのレコードレベルポリシーの作成
    ユーザー属性とデータ属性に基づいて、オブジェクト内の特定のレコードにアクセスできるユーザーを定義します。
  • 階層データの取り込み
    Salesforce CRM の組織階層 (ロール、マネージャー、テリトリーなど) を Data 360 に取り込みます。 取り込み後、階層ベースのレコードレベルセキュリティ (RLS) ポリシーでこれらの階層を参照できます。

Data 360 のデータガバナンス

データガバナンスは、タグ、分類、ユーザー属性、ポリシーベースのガバナンスを組み合わせて使用することで、データを保護および管理するための堅牢なフレームワークを提供します。ポリシーやその他のガバナンス機能を有効にすると、制御が改善され、ユーザーは適切なデータに大規模にアクセスできます。

Data 360 ガバナンスについて

データガバナンスは、データを安全で整理された状態に保つための一連のルールです。複数のツールを組み合わせて使用し、適切なユーザーが適切なデータにアクセスできるようにします。

データタギングは、ラベルまたはメタデータをデータに添付して識別および整理し、簡単に検索、絞り込み、管理できるようにするプロセスです。タグは機密性またはビジネスの関連性に基づいてデータを分類し、ポリシーを適用するための基礎となります。

データ分類では、値、機密性、規制要件に基づいてタグがカテゴリにグループ化されます。たとえば、データは公開、内部、社外秘、制限付きに分類できます。

Data 360 のオブジェクトレベルセキュリティ (OLS) および項目レベルセキュリティ (FLS) ポリシーは、タグと分類に基づいており、多数のオブジェクトと項目にわたる拡張性の高いガバナンスを実現します。

データガバナンスは拡張性が高く、自動的に行われます。新しいデータを Data 360 に取り込むときは、正しいタグを付けるだけで済みます。既存のルールは追加作業なしで自動的に適用されます。これにより、特に大量の情報を扱う場合に、データセキュリティの管理がより効率的になります。

  • データガバナンスの使用開始
    データガバナンス機能を使用する前に、組織のデータ全体のガバナンスを有効にするために必要な前提条件と手順を確認することが重要です。
  • Data 360 のポリシーベースのガバナンス
    データガバナンスポリシーは、データへのアクセス、使用、保護、管理方法を定義するルールとガイドラインです。これらのポリシーは、データ処理をセキュリティ要件、コンプライアンス基準、ビジネス目標に合わせるのに役立ちます。
  • Data 360 のデータタギングと分類
    データタギングは、オブジェクト、項目、レコードなどのデータアセットに表示ラベルやメタデータを付加して、コンテンツ、機密性、目的を説明するプロセスです。タグは、データの識別と整理に役立つため、簡単に検索、絞り込み、管理できます。
  • Unified Lineage を使用したデータリレーションの表示
    統合系統により、データオブジェクトがどのように接続されているかの全体像を把握できます。これを使用して、データジャーニー、連動関係、変更による下流への影響 (タグの適用やオブジェクトの更新など) を把握します。
  • Data 360 での外部ユーザーアクセスの制御
    データガバナンスポリシーを使用して、Data 360 対応アプリケーションで外部ユーザーがアクセスできる内容を制御します。明確なポリシーベースのアクセスを定義することで、身元不明外部ユーザーと認証済み外部ユーザーに目的のデータのみが表示されるようにします。
  • DevOps データキットを使用した Data 360 Governance マージバック
    Sandbox を使用してデータガバナンス戦略を開発および検証し、マージバックで本番にリリースします。マージバックは、検証済みのメタデータを Sandbox 組織からリンクされた本番組織または別のリンクされた Sandbox 組織に戻すプロセスです。DevOps データキットは、ガバナンスメタデータを環境間で移動し、一貫したセキュリティ体制を維持します。

データグラフタグの伝達

データグラフでは、計算済みインサイトオブジェクト (CIO) の管理方法と同様に、タグベースの制御でアクセスとセキュリティの管理がサポートされます。参加 DMO で定義された行レベル セキュリティ（RLS）は、データグラフで自動的に適用されません。必要なデータ保護のレベルに応じて、管理者はタグの伝達を使用してアクセス権を適用できます。

データグラフを作成すると、さまざまなデータモデルオブジェクト (DMO) と CIO から項目が取り込まれます。データグラフに明示的に投影された項目のみが具体化され、クエリ時に使用可能になります。アクセス制御を適用するために、予測される項目、参加 DMO、CIO に関連付けられたタグに基づいてユーザー権限が評価されます。すべての項目、ソース DMO および CIO のタグがデータグラフレコードにコピーされます。ただし、データグラフの作成後に新しいタグが DMO に追加された場合、そのタグは自動的にデータグラフに反映されません。このような場合、更新されたタギングがデータグラフに反映されるように手動で反映する必要があります。

重要

ユーザーが参加 DMO または CIO の必須タグにアクセスできない場合、そのユーザーはデータグラフ全体にアクセスできません。

DMO レベルの RLS ポリシーはデータグラフに適用されません。データグラフは、投影された項目に対するタグベースの制御を介してのみアクセスを適用します。

  • 系統の精度を定期的に検証します。グラフが予想されるフローと一致しない場合は、Salesforce サポートに連絡してグラフを再構築してください。
  • タグは一貫して使用します。機密性や分類などの重要なガバナンスタグがオブジェクトレベルと項目レベルの両方に適用されるようにします。
  • 系統とポリシーを関連付けます。タグベースのポリシーをクロスチェックして、アクセスルールが系統パスに従っていることを確認します。
  • 重要な連動関係を文書化します。トラブルシューティングに役立つ、影響の大きいオブジェクトの主要な上流と下流のリレーションを記録します。
  • レビューでリネージュを活用します。データモデルとポリシー変更レビュー中に系統インサイトを取り込んでリスクを軽減します。

データ系統項目

Data 360 は、データオブジェクトに項目を追加して、データソースの詳細を取得します。

  • データソース — レコードソースを参照する論理名の参照 ID。外部ソース ID とも識別されます。 たとえば、SFMC_1487860 は、Salesforce Marketing Cloud Engagement (SFMC) のレコードと内部組織 ID を示します。
  • データソースオブジェクト — レコードの提供元であるオブジェクトの論理名 (クラウドストレージファイルの名前や、別のコネクタの外部オブジェクトの名前など) の参照 ID。たとえば、SFMC_1487860_Campaign は、Marketing Cloud Engagement のレコードであること、内部組織 ID、オブジェクトのキャンペーンを示します。
  • 内部組織 — データレコードを所有するビジネスユニットやその他の内部組織の参照 ID。たとえば、Marketing Cloud Engagement からインポートされたデータレコードには、データレコードの取得元であるビジネスユニットの ID が示されます。CRM ソースの内部組織 ID は自動的に対応付けられません。
