Data 360 セグメントでのベクトル検索条件の使用 (ベータ)

ベクトル検索条件により、キーワードの完全一致や手動のデータ整理への依存が軽減され、正確なセグメントを効率的に作成できます。この機能では、セグメント作成で NLP アルゴリズムを使用して非構造化データを並び替えます。1 つのインターフェースとセグメント内で構造化データと非構造化データの両方を絞り込むことができます。

必要なエディション

メモ セグメントのベクトル検索条件はベータサービスであり、顧客が実行した場合は Agreements - Salesforce.com のベータサービス条件、書面で締結した場合は統合パイロット契約、および商品条件ディレクトリの適用条件が適用されます。このベータサービスは、お客様独自の裁量で使用するものとします。
使用可能なエディション: Data 360 でサポートされるすべてのエディション。 「Data 360 Edition の可用性」を参照してください。
必要な権限セット
ベクトル検索条件を使用する

次の権限セットのいずれか:

  • Data Cloud アーキテクト
  • Data Cloud 有効化マネージャー
  • Data Cloud 有効化スペシャリスト
  1. Data Cloud で [セグメント] をクリックします。
  2. リストからセグメントを選択します。
  3. [ルールを編集] をクリックします。
  4. [Include (包含)] または [Exclude (除外)] タブをクリックします。各タブに最大 50 個の検索条件を追加できます。
  5. 条件を追加できるのは、次のとおりです。
    • 直接属性 — 郵便番号、名、誕生日など、セグメント化されるエンティティに関する 1 つのデータポイントまたは情報。直接属性は、多くの場合デモグラフィック属性です。
    • 関連属性 — セグメント化されるエンティティに関連付けられた複数のデータポイントまたは情報 (購入履歴、商品番号、メールのやり取りなど) のコレクション。多くの場合、関連属性は行動またはエンゲージメントイベントです。
    • Calculated Insights (計算済みインサイト) — 名前で計算済みインサイトを検索するか、SQL で参照されるオブジェクトで計算済みインサイトを見つけます。処理済みの計算済みインサイトはセグメントでのみ使用できます。
  6. [Is Similar To (類似する)] 演算子を選択します。
  7. 必要な値を入力します。たとえば、バックパックなどです。
  8. スライダーを使用して類似性レベルを選択します。デフォルトでは、100 に設定されています。
  9. [Compute Results (結果を計算)] をクリックします。
  10. [View Results (結果の表示)] をクリックします。次の詳細が表示されます。
    • 検索語と選択した類似性レベルに基づいて返される類似語の数。
    • 最も類似する 5 つの用語のサンプル。
    • 類似度の低い 5 つの語のサンプル。

    必要に応じて、類似性レベルや値の異なる結果を計算できます。

  11. ［Done］ をクリックしてフィルタを保存します。

検索条件は定義された範囲内で動作し、収集するデータが関連していて、探しているコンテキストに適合することを確認し、セグメントデータの精度を向上させます。

取得者の引用による信頼できるAI応答の取得

引用は、AI で生成された回答を各回答に関連するソースコンテンツにリンクします。引用により、ユーザーは LLM 応答をソースデータと比較して応答の有効性を検証し、潜在的な不正確さや幻覚を特定できます。AI モデル (旧 Einstein Studio) の引用を個々の取得者レベルで有効にして、取得者をコールするソリューションコンポーネント (プロンプトテンプレートなど) への引用へのアクセス権を付与します。

標準引用では、ソース URL とヘッダーテキストを含む引用が自動的に生成されます。カスタム引用では、ソースデータモデルオブジェクト (DMO) 項目のベース URL、URL パス、表示ラベルを定義できます。Agentforce エージェントやプロンプト テンプレートなどのダウンストリーム アプリケーションでは、引用ヘッダーとリンクがエンドユーザに表示されることがあります。これらの項目が適切に入力され、エンドユーザーがソースリンクにアクセスできることを確認します。

Einstein Platform でカスタム アクションと [Knowledge を使用した質問への回答] 標準アクションを使用して引用を設定することもできます。詳細については、「Build Trust in AI Responses with Citations」を参照してください。

使用事例: 画像ソースへの引用を使用したエージェントの応答のグラウンディング

ファイナンシャルプランナーが顧客とのミーティングの準備をしていて、投資のおすすめを提供するシナリオを考えてみます。クライアントの財務計画ドキュメントには、ポートフォリオ総額のグラフなど、さまざまなグラフが含まれています。

高度な検索インデックス設定により、計画ドキュメントのテキストと画像の両方を処理し、クライアントのポートフォリオに関する質問をすることができます。グラフとグラフは、LLM を使用して画像の構造化された説明を生成し、画像への URL リンクを提供することで処理されます。次の一般的なフローを使用してドキュメントを処理します。

  • 画像やグラフなどのビジュアルを含むドキュメントを接続して取り込みます。
  • Data 360 検索の高度な設定を使用して、ドキュメントの変換とインデックス付けを行います。画像処理を有効にし、チャンク戦略の一環として画像を処理する適切な埋め込みモデルを選択します。
    メモ 画像ファイルでは、拡張インデックスはサポートされていません。
  • 検索インデックスの個別のリトリーバを作成します。
  • 取得元をテストするには、プロンプトテンプレートに埋め込みます。
  • 取得元は、カスタムエージェントまたは他のクライアントアプリケーションで使用します。

そのため、ファイナンシャルプランナーがポートフォリオの割り当てについてエージェントに質問すると、LLM は画像へのリンクを含むグラフのテキスト説明を取得します。エージェント応答には、ソース引用を含む回答が含まれます。画像の引用は外部リンクとして表示されます。

データの取得

取得機能を使用して、検索インデックスから関連データを検索して返します。Data 360でのRAG(拡張生成の取得)のためのAIモデル(旧Einstein Studio)での取得者の作成とカスタマイズ。取得者は、プロンプトに関連する特殊なグラウンディング情報を提供して、プロンプトテンプレートを増強します。

必要なエディション

使用可能なエディション: Data 360 でサポートされるすべてのエディション。 「Data 360 Edition の可用性」を参照してください。

検索インデックスから取得するためのデータの準備には、検索に最適化された方法でのコンテンツの読み込み、チャンク化、ベクトル化、保存が含まれます。Data 360 では、ドキュメントや会話履歴などの非構造化データにベクトルデータストアを使用します。検索インデックスには、他のアプリケーションから検索および取得できるチャンク化されたベクトル化されたデータが保存されます。Data 360 で検索インデックスを作成および管理できます。これらはデータスペースで定義され、データモデルオブジェクト (DMO) に関連付けられます。

Data 360の高度なドキュメント処理機能とインデックス機能により、取得者はテキストと画像の両方を処理してエージェント応答を取得してグラウンディングできます。非構造化データモデルオブジェクト検索インデックスの画像処理を有効にして、画像や、テーブルやフローチャートなどのビジュアルを含むドキュメントを処理します。検索インデックスの高度な設定の詳細については、「AI、自動化、および分析の検索の使用」を参照してください。

検索インデックスは、Knowledgeベース全体のインデックス付けなど、一般的な使用を目的として設計されていることが多いです。取得機能を使用して、検索インデックスで特殊な検索を実行し、関連する結果をエージェント、プロンプトテンプレート、フロー、その他の機能に提供します。検索インデックスの個々の取得者は、多目的検索インデックスを特定の使用事例に適用します。たとえば、取得者は記事のカテゴリや最新情報 (過去 90 日間など)、地域に基づいて絞り込まれたコンテンツを返すことができます。

AIモデルで取得者を作成し、有効化してプロンプトビルダー ユーザーが使用できるようにします。プロンプトビルダーで、取得機能を挿入して設定することで、Knowledge を使用してプロンプトテンプレートをグラウンディングします。実行時に、取得者は LLM に正確で最新の関連情報を提供し、LLM 応答の関連性、正確性、価値を向上させます。

取得者は、データに設定されたデータガバナンスポリシーに従います。行レベルのアクセス チェックでは、取得者によって返されたデータとKnowledgeへのアクセス権をユーザーが持っていることを確認します。

Data 360 ホーム組織で取得者を作成すると、コンパニオン組織で表示し、プロンプトビルダーおよびフローで使用できます。コンパニオン組織でローカルに取得者を作成して管理することもできます。詳細は、「Retriever Support in Data Cloud One and Data Cloud One Companion Connections」を参照してください。

個人取得者

個々の取得者を使用して、検索インデックスからデータを取得します。AIモデルで個々の取得者を作成するには、その検索インデックスを選択し、検索条件を定義して、返される情報を指定します。検索条件により、より関連性の高いデータに絞り込まれます。検索インデックスでは、 絞り込みに使用できるフィールドを定義します 。プロンプトに返されるデータ (返されるデータの項目や結果の数など) を設定することもできます。個々の取得者を編集して保存するたびに、AI モデルは別のバージョンを作成します。1 つのバージョンの取得者のみを有効にできます。

メモ 検索インデックスの作成時に Data 360 でデフォルトの取得者が自動的に作成されなくなりました。以前は、Data 360 で検索インデックスを作成すると、デフォルトの取得者が自動的に作成されていました。プロンプトビルダーやフローなどのアプリケーションでは、既存のデフォルトの取得機能を使用できます。

アンサンブルレトリーバー

アンサンブル取得者は、個々の取得者のコレクションです。アンサンブル取得を実行すると、個々の取得者が実行され、その結果が 1 つのリストに結合され、検索要求との関連性に従ってリストが再ランク付けされ、プロンプトビルダーやフローなどのアプリケーションに最も関連性の高い情報のみが返されます。

動的取得

動的取得では、プロンプトテンプレートの実行時値を受け入れるプレースホルダーを使用します。動的取得には、プロンプトテンプレートのニーズに基づいて実行時に指定された値のプレースホルダーがあります。

  • 取得者の引用による信頼できるAI応答の取得
    引用は、AI で生成された回答を各回答に関連するソースコンテンツにリンクします。引用により、ユーザーは LLM 応答をソースデータと比較して応答の有効性を検証し、潜在的な不正確さや幻覚を特定できます。AI モデル (旧 Einstein Studio) の引用を個々の取得者レベルで有効にして、取得者をコールするソリューションコンポーネント (プロンプトテンプレートなど) への引用へのアクセス権を付与します。
  • 取得者の管理
    Data 360 で RAG (Retrieval Augmented Generation: 拡張取得生成) の取得者を作成してカスタマイズします。取得者のリストを表示するには、AIモデル(旧称Einstein Studio)の[Retrievers (取得者)]タブに移動します。取得者については、ドロップダウンメニューから [詳細を表示] を選択します。カスタム取得者を編集して変更を保存するたびに、新しいバージョンが作成されます。複数のバージョンを作成できますが、一度に有効にできるバージョンは 1 つのみです。
  • Retriever Playground を使用した取得者のカスタマイズ、テスト、検証
    retriever playground を使用して取得拡張生成 (RAG) システムの取得ロジックを微調整および検証し、リリースリスクを軽減し、AI の正確な出力を検証します。AIモデル(旧称Einstein Studio)の取得遊び場を使用して、事前検索条件を設定し、テスト データを選択し、結果パラメーターを調整して、苦情ドキュメントやKnowledge記事の取得など、ドメイン固有の使用事例に合わせて取得ロジックをカスタマイズします。
  • Retriever Filters Reference (取得者検索条件のリファレンス)
    AIモデル(旧称Einstein Studio)で取得者を作成またはテストするときに、取得精度の検索条件を設定します。検索条件を使用して、検索クエリで取得したレコードを絞り込みます。個々の取得者には最大 10 個の検索条件を設定できます。
  • Data Cloud One での取得者のサポート
    Data Cloud One ホームおよびコンパニオン組織を使用する場合の取得機能および制限事項について説明します。

個人取得者の作成

特定の使用事例のプロンプトに返されるコンテンツの関連性を向上させるには、AIモデル(旧称Einstein Studio)でカスタムの個人取得機能を作成します。取得者をカスタマイズするには、検索インデックスを選択し、フィルタを定義して、返される情報を指定します。

必要なエディション

使用可能なエディション: Data 360 でサポートされるすべてのエディション。 「Data 360 Edition の可用性」を参照してください。
必要なユーザー権限
AI モデルで取得者またはバージョンを管理する (作成、編集、削除)

ユーザーが AI モデルでモデルを管理できるようにする

または

「Data Cloud アーキテクト」権限セット
取得者を使用してデータにアクセスする

Knowledgeオブジェクトの場合、ユーザーにKnowledgeオブジェクトへの参照アクセス権があり、「Allow View Knowledge」アプリケーション権限があることを確認します。

その他のすべての標準オブジェクトについては、ユーザーにオブジェクトへの参照アクセス権と適切な共有ルールがあることを確認します。詳細については、「内部組織の共有設定」を参照してください。
  1. [Retrievers (取得者)] タブの [AI Models (AI モデル)] で、[New Retriever (新規取得者)] をクリックします。
  2. 取得者種別として [Individual Retriever (個人の取得者)] を選択します。[次へ] をクリックします。
  3. 取得者のデータソースとして [Data Cloud] を選択します。
    1. 検索インデックスが存在する Data Cloud のデータスペースを選択します。
    2. 検索インデックスに関連付けられたデータモデルオブジェクト (DMO) を選択します。
    3. 検索インデックスを選択します。
    4. [次へ] をクリックします。
  4. (省略可能) 検索条件を定義して、検索結果を絞り込みます。
    取得フィルタは、選択した検索インデックスにフィルタフィールドが定義されている場合にのみ使用できます。
    1. [Filter Documents to Return (返すドキュメントの絞り込み)] を選択し、適用する条件を 10 個まで指定します。
    2. [条件の要件] を選択します。
      たとえば、特定のサブセット (カテゴリ = ハードウェア AND 言語 = ドイツ語など) を定義するには、[すべての条件に一致] を選択します。異なる条件が同じ目標をサポートする場合 (優先度 = 高 OR エスカレーション済み = True など)、[いずれかの条件に一致] を選択します。

      番号付き条件 (1. Car Make = Honda、2. Car Model = Civic、3. CarYear greater than 2000 など) を使用してカスタムロジックを作成するには、[Custom Condition is Met (カスタム条件に一致)] を選択します。 1 AND (2 OR 3) などのカスタム条件を作成します。

    3. 条件ごとに、[条件を追加] をクリックし、検索インデックスの項目、演算子、値を選択します。項目のデータ型 (テキストや数値など) によって、使用可能な演算子が決まります。
    4. [次へ] をクリックします。
  5. どの情報をどの程度返すかを設定します。
    1. 返される結果の最大数を指定します。
    2. プロンプトをグラウンディングする 1 つ以上の項目を指定します。選択した項目ごとに、取得した情報を説明する一意の表示ラベルを入力し、検索インデックスで項目を選択します。
      使用事例に合わせてプロンプトを補足し、プロンプトへの応答をより正確で関連性の高いものにする項目のみを選択します。
    3. [次へ] をクリックします。
  6. (省略可能) この取得者の引用を有効にします。

Data Cloud One での取得者のサポート

Data Cloud One ホームおよびコンパニオン組織を使用する場合の取得機能および制限事項について説明します。

Data Cloud One 環境での取得者の動作を理解するには、2 つの基本的なルールに基づきます。

  • 取得者は、自分が作成した組織でのみ編集または削除できます。
  • Data Cloud One メタデータの同期は、ホーム組織からコンパニオン組織への一方向のみで実行され、その逆方向やコンパニオン組織間では実行されません。

制約と影響

これらの制約は、Data Cloud One で取得者を作成および管理する方法に影響します。

  • 取得者は、基幹業務 (LOB) 組織からホーム組織、または LOB 組織間で同期されません。各 LOB 組織は、ローカルで作成された取得者用に分離されています。
  • ホーム組織で作成されたアンサンブル取得者は、コンパニオン組織に表示されます。ホーム組織でアンサンブル取得者を作成すると、コンパニオン組織に同期されます。同じデータスペースに取得者があるローカル LOB 組織でアンサンブル取得者を作成できます。
  • エージェントアクションでリモート取得者を参照することはできません。LOB エージェントはアクションにローカルで作成された取得者を使用する必要があります。
  • 編集は所有組織でのみ可能です。自宅組織と LOB 組織を切り替えて、取得元を調整およびテストします。

取得者の管理

Data 360 で RAG (Retrieval Augmented Generation: 拡張取得生成) の取得者を作成してカスタマイズします。取得者のリストを表示するには、AIモデル(旧称Einstein Studio)の[Retrievers (取得者)]タブに移動します。取得者については、ドロップダウンメニューから [詳細を表示] を選択します。カスタム取得者を編集して変更を保存するたびに、新しいバージョンが作成されます。複数のバージョンを作成できますが、一度に有効にできるバージョンは 1 つのみです。

取得者は、データに設定されたデータガバナンスポリシーに従います。結果に対するアクセスチェックでは、ユーザーが標準オブジェクトとレコードに安全にアクセスできることを確認します。取得者をコールしている AI エージェントまたはユーザーに取得元レコードへのアクセス権がない場合、取得者の結果には表示されません。詳細については、「Best Practices for Agent User Permissions (エージェントユーザー権限のベストプラクティス)」を参照してください。

  • 個人取得者の作成
    特定の使用事例のプロンプトに返されるコンテンツの関連性を向上させるには、AIモデル(旧称Einstein Studio)でカスタムの個人取得機能を作成します。取得者をカスタマイズするには、検索インデックスを選択し、フィルタを定義して、返される情報を指定します。
  • アンサンブル取得者の作成
    アンサンブル取得を使用して、複数の検索またはデータソースから最も関連性の高い情報を取得します。AIモデル(旧Einstein Studio)では、アンサンブル レトリーバーは個々のレトリーバーのコレクションです。アンサンブル取得を実行すると、すべての個々の取得者が実行され、結果が 1 つのリストに結合され、検索要求との関連性に従ってリストが再ランク付けされ、最も関連性の高い情報のみがプロンプトまたはエージェントに返されます。

  1. [有効化対象] タブに移動し、[新規] をクリックします。
  2. [File Storage]で、有効化プラットフォームを選択し、[Next]をクリックします。
    注意: ファイルストレージ対象は、それぞれの対象接続が設定されている場合にのみ存在します。詳細は、「Data 360 のデータターゲットの設定」を参照してください。
  3. 一意の名前と説明 (省略可能) を入力します。
  4. 有効化対象プラットフォーム固有の設定を定義します。
    • S3 (従来)
      1. S3 バケットとフォルダーの詳細を入力します。
      2. S3 アクセスキーと秘密鍵を指定します。
      3. 変換先ファイル形式を選択します。
      4. 有効化対象を関連付けるデータスペースを選択し、[保存] をクリックします。
    • Amazon S3、SFTP、GCS、Microsoft Azure Blob Storage
      1. コネクタとデータスペースを選択し、[次へ] をクリックします。
      2. 親ディレクトリ: 対象接続設定から継承されます。ルート以外の親ディレクトリが必要です。詳細は、「Data 360 のデータターゲットの設定」を参照してください。
      3. 子ディレクトリ: ディレクトリ名は大文字と小文字が区別されます。SFTP、GCS、および Azure ターゲットの場合、指定した子ディレクトリが対象ロケーションにすでに存在している必要があります。これは、ディレクトリがない場合、Data 360 によってディレクトリが作成されないためです。Amazon S3 ターゲットの場合、子ディレクトリに任意の値を入力できます。この値がない場合、Data 360 は有効化プロセス中にフォルダーを作成します。
        • 子ディレクトリ内にフォルダーを作成: 選択すると、有効化されたファイルが別のフォルダーに追加されます。フォルダ名では、セグメントベースの有効化には <SegmentName_ActivationName> が使用され、セグメント以外の有効化には <ActivationName> が使用されます。選択しない場合、ファイルは子ディレクトリに残ります。英数字とアンダースコアを除くすべての文字を含むフォルダー名は、ハイフン (-) に自動的に置き換えられます。<SegmentName_ActivationName> が 200 文字を超える場合、フォルダー名は 200 文字に制限され、それ以上の文字は自動的に切り捨てられます。
      4. ファイル形式: CSV ファイルの有効化されたファイル形式と区切り文字を選択します。
      5. 圧縮形式: 有効化されたファイルの圧縮形式を選択します。PGP 暗号化は CSV と JSON でのみサポートされますが、Parquet ではサポートされません。
      6. ファイル名の種類: [事前決定済み] または [カスタムファイル名] を選択します。事前に決定されたファイル名の場合、SegmentName と ActivationName の文字 (英数字とアンダースコアを除く) はハイフン (-) に置き換えられます。
        • [<ActivationName>] を選択した場合、ファイル名ではすべての有効化種別に <ActivationName> が使用されます。
        • [<SegmentName>] を選択した場合、セグメント以外の有効化ではファイル名として <ActivationName> が使用されます。
        • [<SegmentName_ActivationName>] を選択した場合、セグメント以外の有効化ではファイル名として <ActivationName> が使用されます。
      7. データ/タイムサフィックス: ファイル名のサフィックス形式を選択します。これはセグメント更新タイムスタンプを UTC 形式で表します。タイムスタンプの範囲は、特定の日付からミリ秒です。
      8. 制限種別: ファイルあたりの最大レコード数 (デフォルト: 100,000) や最大ファイルサイズ (デフォルト: 500 MB) など、設定された制限に達すると、有効化されたデータは自動的に複数のファイルに分割されます。

        たとえば、

        • 有効化ペイロードのレコード数が 45 万件で、レコード制限が 100,000 件の場合、ペイロードは複数のファイルに分割され、1 つのファイルが 100,000 件のレコードを超えないようにします。
        • 有効化ペイロードの合計が 3 GB で 500 MB の制限がある場合、ペイロードは複数のファイルに分割され、1 つのファイルが 500 MB のサイズ制限を超えないようにします。
        メモ ファイル分割は非確定的であり、出力ファイルの最終的な数とサイズは、データの特性、ファイル形式、圧縮、暗号化、処理動作に応じて実行ごとに異なる場合があります。

  • 有効化されたデータファイルと同じディレクトリにあるセグメントメタデータ JSON ファイル。
    • Amazon S3 ターゲットの場合、このメタデータ JSON ファイルは、対象への書き込み操作が完了し、データを消費する準備が整っていることを確認する役割を果たします。
    • SFTP、GCS、Azure ターゲットの場合、メタデータファイルと有効化されたデータファイルは任意の順序で到着できます。そのため、メタデータファイルがあっても、有効化が完了したことを示すものではありません。

    • セグメント ID と名前
    • データスペース ID と名前
    • レコード件数
    • 更新 ID と公開更新種別
    • 属性名と対応するデータ型

  • 項目にカンマまたは改行文字が含まれている場合、値全体が引用符で囲まれます。例: value1,value2 → "value1,value2"。
  • 項目に二重引用符が含まれている場合、各引用符はバックスラッシュ (\) でエスケープされます。例: "value1","value2" → "\"value1\",\"value2\""

ハイブリッド検索の自動ドロップの結果

関連性スコアの急減を示す結果を動的に除外して、プロンプトと RAG の使用事例の検索結果の精度を高めます。Data 360ハイブリッド検索の自動ドロップは、プロンプトビルダーなどのアップストリームアプリケーションがそれらの結果を使用して誤解を招く可能性がある無関係な検索結果を除外する方法です。

検索クエリを開始すると、ハイブリッド検索フュージョンランキングモデルでは、取得する検索結果ごとに最適なランキングスコアが導出されます。ハイブリッド検索の自動ドロップオプションを使用すると、スコアが大幅に低下する 1 つ以上のスコアカットオフポイントから結果をドロップできます。このカットオフポイントを超える結果は、クエリとの関連性が低いと見なすことができます。

自動ドロップは、ハイブリッド検索でのみ使用できます。ハイブリッド検索はベクトル検索とキーワード検索の両方を兼ね備えているため、クエリ API を使用して、ベクトル検索結果、キーワード検索結果、融合ハイブリッド検索結果など、ハイブリッド検索の各検索種別の結果の自動ドロップを設定できます。ハイブリッド検索では、検索結果スコアを分析し、無関係な結果を絞り込みます。ハイブリッド検索の自動ドロップはデフォルトで無効になっています。Data Cloud クエリ API を使用して自動ドロップを有効にします。

ハイブリッド検索自動ドロップのベストプラクティス

次のベストプラクティスを使用して、Data 360 ハイブリッド検索結果の自動ドロップを設定します。

  • 自動ドロップでは次の推奨値を使用し、キーワード検索結果では 2、ベクトル検索結果では 5 を使用します。 これらの設定をテストし、使用事例とクエリに応じて調整します。
    • キーワード検索結果では自動ドロップ値を 2、ベクトル検索結果では自動ドロップ値を 5 にすることをお勧めします。 
      { "autodrop_keyword": {"num_drops": 2},  "autodrop_vector":{"num_drops": 5 }}
    • デフォルトの自動ドロップ値は、キーワード検索結果に対して攻撃的ではありません。
      { "autodrop_keyword": {"num_drops": 5},  "autodrop_vector":{"num_drops": 5 }}
  • ハイブリッド検索結果配信の性質上、自動ドロップによって予期しない動作が発生する可能性があります。「autodrop_hybrid」パラメーターの代わりに「autodrop_vector」パラメーターと「autodrop_keyword」パラメーターを使用することをお勧めします。
    select * from hybrid_search(
    table(<Search_index_DMO>), 
    ‘<Search String>’,
    '<PreFilteringColumn><Operator><Value>', 
    '<Limit Results>', 
    ‘{ "autodrop_keyword": {"num_drops": 2},  "autodrop_vector":{"num_drops": 5 }}’
);
  • 検索結果に最も関連性の高い結果が表示されるようにするには、一連のテストクエリを使用して自動ドロップの数を調整し、関連する結果が結果セットに表示されるまで値を徐々に変更します。

    ハイブリッド検索の自動ドロップをあまり積極的にせず、より多くの結果を保持するには、num_drops 値を大きくすることを検討してください。特に、スコアドロップがデータセットで発音されない場合や、関連する結果の定義が広い場合は、過度に積極的な自動ドロップによって重要な文書が切り捨てられる可能性があります。関連する結果の消失に気付いた場所に基づいて、「autodrop_keyword」、「autodrop_vector」、「autodrop_hybrid」を調整できます。

    ハイブリッド検索の自動ドロップをより積極的にして、最も関連性の高い結果を保持するには、num_drops の値を減らします。たとえば、最初の自動削除後も検索結果に無関係のドキュメントが多数含まれ、デフォルトの num_drops でノイズを効果的に除去できない場合は、num_drops 値を減らす必要があります。

  • autodrop の値がリスト内の実際のスコアドロップ数を超える場合、切り捨てが適用されません。
  • ドキュメントに類似する用語が多数含まれている場合、キーワード結果に自動ドロップを適用すると、最も関連性の高い結果のみを保持できます。
  • または、クエリで返される結果数の制限を設定することで、結果セットを減らすこともできます。詳細については、「Run Hybrid Search Queries with Query API」を参照してください。この例では、制限はクエリの 2 つの結果に設定されています。
    select * from hybrid_search(
       table(Knowledge_full_index__dlm),
       'How to input special mark/character when using keyboard input data field','', 2)

適切な項目を分割し、事前絞り込み項目を選択し、ランキング要素を追加して、ハイブリッド検索の取得と検索の関連性を強化します。

ハイブリッド検索フュージョンランキング

ランキングでは、ユーザークエリに最も関連性の高い結果が先頭に表示されるように検索結果が並び替えられます。Data 360ハイブリッド検索では、クエリとの類似性に基づいてキーワードとベクトルの2つのインデックスから結果を取得し、結果をマージ(融合)します。その後、ランキングモデルはマージされた結果をランク付けします。

設定時に、レコードの最新性や人気度など、ランキングに影響する追加のランキング要素を設定できます。ランキング要素は、検索インデックスオブジェクト項目または関連オブジェクト項目に基づきます。たとえば、インデックス付き DMO の LastModifiedDate 項目を使用して、レコードの最近度を定義できます。

Salesforce フュージョンランカーモデルは、さまざまな検索ベースのタスクの内部ベンチマークに基づいて最適化されています。ベンチマークでは、精度、堅牢性、感度のパフォーマンスを測定し、高品質のモデルを生成します。評価の基準は、検索応答とアノテーションに関するユーザーインタラクションの組み合わせから選定されます。トレーニング データと評価データは、Salesforce Einstein SearchとRAGアプリケーション(Einstein Search Answerなど)の両方から取得したクエリに基づいています。

ベクトル検索とキーワード検索の類似性スコアに影響する要素は多数あります。たとえば、キーワード類似性スコアは、クエリ テキストと検索インデックス DMO のコンテンツによって異なります。ベクトル類似性スコアは、クエリテキストと検索インデックスの特定の埋め込みモデルによって異なります。フュージョンランカーモデルでは、キーワードとベクトルの類似性スコアをランキング要素と共に線形に組み合わせたハイブリッド検索スコアが返されます。

一般的なハイブリッド検索の使用事例で最良の結果を提供するために、モデルは、各スコアの正規化戦略と各スコアの加重を含む最適な組み合わせになるように微調整されます。フュージョンランキングモデルでは、派生したハイブリッド検索スコアに基づいて結果の最終ランクを決定します。モデルでは、いずれかの検索類似性スコアが 0 であっても、ハイブリッド検索スコアが高い結果をランク付けできます。たとえば、キーワードスコアが 0 の結果のベクトルスコアが同じ検索クエリの代替結果のベクトルスコアと比較して十分高い場合、ハイブリッド検索スコアが高くなる可能性があります。

ハイブリッド検索

gen AI アプリケーションを使用して LLM に関連情報を提供し、正しい応答を生成するには、ベクトル検索とキーワード検索の両方が必要です。ベクトル検索ではセマンティックの類似点とコンテキストは理解されますが、特定のドメインの語彙はありません。キーワード検索は語彙的類似性では優れていますが、意味的類似性では優れていません。Data 360 では、ハイブリッド検索はセマンティックアウェアなベクトル検索の強みとキーワード検索の精度と速度を兼ね備えています。

必要なエディション

使用可能なエディション: Data 360 でサポートされるすべてのエディション。 「Data 360 Edition の可用性」を参照してください。

たとえば、ベクトル検索では「アカウントへのログイン方法」が理解されます。「How can I sign on? (サインオン方法は?)」は同様のクエリです。ただし、ベクトル検索では、「LaserPrinter TX 400」と「LaserPrinter TX 440」の検索も、数値や LaserPrinter などの特定のドメイン用語にうまく一致せず、キーワード検索で類似していることが理解できない場合があります。

ハイブリッド検索では、DMO または UDMO の情報がインデックス付けされ、関連する結果が取得されます。ハイブリッド検索インデックスを作成する前に、DMO と UDMO に保存されている非構造化データがチャンクされます。チャンクにより、DMO と UDMO が管理可能で意味的な単位に分割されます。

次に、データインデックス付けによって、ベクトル検索インデックスと DMO および UDMO のキーワード検索インデックスのベクトル埋め込みが生成されます。検索インデックスの作成、削除、ハイドレーションは、Data 360 検索インデックス UI インターフェースと API を使用して管理します。

ハイブリッド検索では、ベクトル検索インデックスは意味的な類似性に基づいて情報を取得するために照会され、キーワード検索インデックスは語彙的な類似性に基づいて情報を取得するために照会されます。ハイブリッド検索では、両方の種別の検索で提供された結果がマージされてランク付けされ、最適な応答が生成されます。また、返される検索結果に影響を与えるために、レコードの最近性や人気度などの追加のランキング要素を設定することもできます。

Data 360 で検索インデックスを作成したら、プロンプトビルダー、AI エージェント、Tableau などのアプリケーションからそのデータに対して検索を実行できます。

  • 高度な設定を使用したハイブリッド検索インデックスの作成
    DMO(データ モデル オブジェクト)またはUDMO(非構造化データ モデル オブジェクト)のハイブリッド検索インデックスを設定して、生成AIアプリケーションに関連情報を提供します。Data 360 は、参照されるデータをセマンティックに関連するチャンクに分割して検索可能なベクトルを生成し、ベクトルインデックスとキーワードインデックスを生成します。
  • クエリ API を使用したハイブリッド検索クエリの実行
    Data 360 でハイブリッド検索を実行するには、クエリ API を使用します。 次の例を出発点として使用します。
  • ハイブリッド検索クエリ式
    事前絞り込み項目と結合式を使用してハイブリッド検索クエリを強化し、項目にアクセスします。
  • ハイブリッド検索フュージョンランキング
    ランキングでは、ユーザークエリに最も関連性の高い結果が先頭に表示されるように検索結果が並び替えられます。Data 360ハイブリッド検索では、クエリとの類似性に基づいてキーワードとベクトルの2つのインデックスから結果を取得し、結果をマージ(融合)します。その後、ランキングモデルはマージされた結果をランク付けします。
  • 影響ハイブリッド検索の関連性ランキング
    関連性固有のパラメーターを送信することで、検索インデックススクエリ結果の精度を高め、RAG アプリケーションの品質を向上させます。SQL を使用して、サポートされるフュージョンランカーモデルの関連性設定を送信し、特定の使用事例の結果の関連性を改善できます。
  • ハイブリッド検索の自動ドロップの結果
    関連性スコアの急減を示す結果を動的に除外して、プロンプトと RAG の使用事例の検索結果の精度を高めます。Data 360ハイブリッド検索の自動ドロップは、プロンプトビルダーなどのアップストリームアプリケーションがそれらの結果を使用して誤解を招く可能性がある無関係な検索結果を除外する方法です。
  • ハイブリッド検索のベストプラクティス
    適切な項目を分割し、事前絞り込み項目を選択し、ランキング要素を追加して、ハイブリッド検索の取得と検索の関連性を強化します。
  • ハイブリッド検索自動ドロップのベストプラクティス
    次のベストプラクティスを使用して、Data 360 ハイブリッド検索結果の自動ドロップを設定します。

絞り込み要素とランキング要素の項目の設定

検索結果の精度と関連性を高めるために、ユーザーが検索を絞り込むために使用できる項目を指定します。

  1. [絞り込みの項目] ページで、必要に応じてソースオブジェクトまたは関連オブジェクトの項目を追加して、検索を絞り込む方法を増やします。最大 10 個の検索条件項目を選択できます。

    Data 360 では、ベクトル埋め込みを生成するときに事前検索条件項目が選択されます。これらの事前絞り込み項目の値を変更すると、ベクトル埋め込みを生成または更新するときに Data 360 によって値が選択されます。取得元オブジェクトと関連オブジェクト間のオブジェクトリレーションのカーディナリティは、1:1 または N:1 である必要があります。

    たとえば、インデックス付けされた非構造化データにケースの会話トランスクリプトが含まれている場合、ケースオブジェクトの [状況] 項目で絞り込むと、会話トランスクリプトを検索するときのセマンティック検索結果の関連性を改善できます。

影響ハイブリッド検索の関連性ランキング

関連性固有のパラメーターを送信することで、検索インデックススクエリ結果の精度を高め、RAG アプリケーションの品質を向上させます。SQL を使用して、サポートされるフュージョンランカーモデルの関連性設定を送信し、特定の使用事例の結果の関連性を改善できます。

ハイブリッド検索では、業界標準の相互関係ランクフュージョン (RRF) モデル、カスタマイズ可能な線形フュージョンランカー (LFR) モデル、より堅牢なディープフュージョンランカー (DFR) モデルの 3 つのフュージョンランキングモデルがサポートされます。

ハイブリッド検索クエリでは、関連性設定を表す JSON 文字列を使用できます。

select * from hybrid_search(
    table(<Search_index_DMO>),
    ‘<Search_string>’,
    '<PreFilteringColumn><Operator><Value>', 
    '<Limit_results>', 
    ‘<”Relevance Ranking Configuration” (JSON)>’
);

相互ランクフュージョンモデル

相互ランクフュージョン (RRF) モデルでは、最も関連性の高い結果を得るために各検索種別の加重が考慮された相互ランクフュージョン数式が使用されます。

往復順位フュージョン数式は、デフォルトの減衰が k=60 のキーワード検索 (スパース) とベクトル検索 (デンス) の両方の往復順位スコアの合計です。 また、2 つのスコアの凸の組み合わせでスパース加重を制御するアルファパラメーターも提供します。検索結果は、RRF ランクフュージョン数式から派生した合計を使用してランク付けされます。

たとえば、次のハイブリッド検索クエリ式は、RRF モデルのキーワード検索 (スパース) 加重パラメーターを渡します。

select * from hybrid_search(
    table(<Search_index_DMO>), 
    ‘<Search String>’,
    '<PreFilteringColumn><Operator><Value>', 
    '<Limit Results>', 
    ‘{ "rrf": { "keyword_weight": 0.4 } }’
);

関連性設定の入力パラメーター:

  • rrf: Enable Reciprocal Ranking Fusion model (相互関係ランキングフュージョンモデルの有効化)
  • keyword_weight: ハイブリッド検索でのキーワード検索コンポーネントの重要性または加重。範囲は 0 ～ 1 です。ベクトル検索の重要度は、1.0 からキーワードの加重を差し引いて自動的に計算されます。

RRF モデルでは、検索インデックスの作成時に設定するランキング要素に影響する高度な数式もサポートされています。ランキング要素についての詳細は、「ハイブリッド Search Fusion ランキング」を参照してください。

高度な RRF 数式の関連性設定の入力パラメーター:

  • アルファ (a): キーワード検索に与えられた重要度を表します。デフォルトは 0.5f
  • ベータ (B): ベクトル検索に与えられた重要度を表し、キーワード検索に与えられた重要度 (1-alpha) に基づいて計算されます。
  • Gamma (Y):ランキング要素の人気度の重要性を表します。デフォルトは 0.00074478f です。最大値は 1 です。
  • Delta (D):ランキング要素の最新性に付与される重要度を表します。デフォルトは 0.00028472f です。最大値は 1 です。

クエリの加重の重要度を指定します。結果に対する適切な関連性が得られるように、値を小さい単位で調整および調整します。

線形核融合ランキングモデル

線形フュージョンランキング (LFR) モデルは、ベクトル検索 (稠密) とキーワード検索 (疎) の両方から変換されたスコアの加重合計を計算するデフォルトのフュージョンランカーモデルのカスタマイズ可能な形式です。検索結果は、LFR 数式から派生した合計を使用してランク付けされます。

デフォルトでは、ハイブリッド検索では、内部実験とベンチマークに基づく変換と加重を使用して、最適な線形フュージョンランカー設定が提供されます。LFR では、キーワード検索 (スパース) スコアとベクトル検索 (デンス) スコア、およびそれらの加重の変換関数を使用して、ランキングをさらに設定できます。

LFR モデルでは、DMO のハイブリッド検索の設定時に設定できる最新および人気のあるランキング要素を使用することもできます。追加のランキング要素は、変換関数と加重を使用して設定できます。

たとえば、次のハイブリッド検索クエリ式は LFR モデルの関連性パラメーターを渡します。


select * from hybrid_search (
    table(<Search_index_DMO>), 
    ‘<Search String>’,
    '<PreFilteringColumn><Operator><Value>', 
    '<Limit Results>',                          
‘{
  "lfr": {
    "vector": {
      "score_transform": {
        "type": "reciprocal_rank",
        "decay": 60
      },
      "weight": 0.66913
    },
    "keyword": {
      "score_transform": {
        "type": "query_min_max",
        "theoretical_min": 0.1
      },
      "weight": 4.0343633
    }
  }
}’);

関連性設定の入力パラメーター:

  • lfr - 線形フュージョンランキングモデルを有効化
  • vector: ベクトル検索のランキングを設定します。
  • keyword: キーワード検索のランキングを設定します。

ベクトル検索とキーワード検索の各ランキング設定では、次のパラメーターを使用できます。

  • score_transform: 検索コンポーネントのスコア変換の設定
  • type: score 変換の種別
    • reciprocal_rank
    • query_min_max
  • decay: 相互関係ランク変換でのみサポートされ、decay パラメータで結果ランク間の勾配を制御します。たとえば、ランク 1 の結果とランク 2 の結果の相互順位スコアは、減衰が 10 なのに対し、減衰が 20 と大きく離れています。
    • クエリに減衰パラメーターが含まれている場合、スコア = 1/(rank+decay) になります。
  • theoretical_min: 理論最小/最大変換でのみサポートされ、基盤となる検索機能の理論上の最小スコアを表します。このパラメーターを使用して、[0,1] の範囲で特徴分布を拡大または縮小します。そのため、最適な結果を得るには、機能の最小値を選択します。キーワード検索スコアの場合、0 が適切な値です。値が大きいほど関連性が高いことを示すデータがない限り、この値は調整しないでください。
  • weight: ハイブリッド検索のこのコンポーネントに与える重要度

Deep Fusion ランカーモデル

Deep Fusion Ranker (DFR) モデルでは、ベクトルの類似性、キーワードの一致、人気、最新性などの従来のシグナルとクエリテキストの深い理解を統合することで、検索の関連性を高めます。このモデルでは、ディープラーニングの手法とトランスフォーマーアーキテクチャを活用して、複雑な特徴のインタラクションを取得し、レコードを共同でスコアリングします。検索結果が正確で、絞り込まれ、コンテキストに関連する。このモデルでは、欠損データやノイズの多いデータを効果的に処理できるため、さまざまな検索シナリオで信頼性の高いパフォーマンスが保証されます。

dfr 関連性設定を使用して、Deep Fusion Ranker モデルを有効にします。このモデルに使用できる他のカスタマイズはありません。

たとえば、次のハイブリッド検索クエリ式は、Deep Fusion Ranker モデルの関連性パラメーターを渡します。

select * from hybrid_search (
    table(<Search_index_DMO>), 
    ‘<Search String>’,
    '<PreFilteringColumn><Operator><Value>', 
    '<Limit Results>)', 
    ‘{  "dfr": {}}’
);

関連性設定の入力パラメーター:

  • dfr: ディープフュージョンランカーモデルの有効化

ノートブック AI を使用したコンテンツの探索と調査

Data 360 Notebook AIは、個人、エンタープライズ、公開コンテンツのアップロード、調査、インサイトの生成を行うための生成AIノートブックです。

ノートブック AI は、営業、サポート、マーケティングなどの個人ビジネスユーザーやチーム向けです。質問してコンテンツを探索したり、ソースコンテンツを選択して概要を生成したりするための個人用の専用ワークスペースを作成します。

ユーザーは、ノートブックに非公開リソースライブラリを作成し、企業全体のコンテンツと組み合わせて、信頼できるコンテンツを 1 つのスペースで生成します。

ノートブック AI は、短期の期限付きのプロジェクトや長期の研究およびコンテンツ作成用であり、AI を駆使した研究に柔軟性、制御性、コラボレーションをもたらします。

Notebook AI は、Data 360 または Web アプリケーションとして使用できます。

使用事例: 繰り返されるカスタマーサポートの問題を調査するためのノートブック AI

カスタマーサポート担当者は、商品や設定の根本的なギャップに起因する顧客の反復的な問題に対処することがよくあります。

サポートケース、JIRA チケット、Slack スレッド、商品に関連するエラーログなど、複数のシステムとソースで顧客の問題が記録されます。個人メモ、製品マニュアル、コミュニティ記事など、さまざまな方法で問題の解決方法を見つけて文書化できます。

サポート担当者が使用、再利用、共有できる明確なKnowledgeが1か所にない場合、対応やエスカレーションが異なる場合があります。サポートエンジニアは、次の一般的なフローを使用して Notebook AI を操作します。

  • 研究ノートを作成する
  • すべてのソースをリソースライブラリにアップロードする
  • 質問、回答の確認、ソース引用の検証によるソースの探索

分析をコピーまたはダウンロードして、解決を検証し、信頼できる記事を作成します。新しいコンテンツをKnowledgeベース記事として共有してエンタープライズリソースに追加し、他のユーザーが調査からメリットを得られるようにします。

使用事例: 提案依頼 (RFP) 商談を調査するためのノートブック AI

営業担当は Notebook AI を使用して、新しい商談の販売提案を調査できます。

営業担当は、AI で生成されたノートブックを使用して、さまざまなドキュメントをリソースライブラリにアップロードできます。これらのドキュメントには、顧客とのミーティングメモ、市場トレンドの詳細が記載された Web ページ、競合他社の分析レポート、RFP が含まれます。

質問、回答の確認、引用元の検証を行ってソースを探索します。調査を使用してレポートを生成し、チームと共有して確認します。

  • データスペースとユーザーのノートブック AI の有効化
    Data 360 Notebook AIにデータスペースのデータへのアクセス権を付与し、カスタム権限セットを使用してエンタープライズユーザーにNotebook AIへのアクセス権を付与します。マルチ組織アーキテクチャでは、ホーム組織とコンパニオン組織の両方でノートブック AI を有効にします。
  • ノートブック AI Web アクセスの有効化
    エンタープライズユーザーに Data 360 Notebook AI Web アプリケーションへのアクセス権を付与します。Notebook AI Web アプリケーションが Salesforce 組織に接続することを承認し、ユーザーが Web からアプリケーションにログインできるようにします。
  • AI ノートブックの管理
    Data 360 Notebook AIで生成AIノートブックを管理します。デフォルトでは、ノートブックは作成者のユーザーに非公開です。
  • ノートブック AI の請求に関する考慮事項
    Notebook AIを使用してコンテンツのアップロード、質問、インサイトの保存を行うと、データはData 360とAgentforceで処理されます。Data 360を使用したデータの処理、コンテンツ ソースのインデックス付け、データの照会には、請求処理が含まれます。
  • ノートブック AI エラーのトラブルシューティング
    ノートブック AI を設定するときに、最も一般的な問題を診断して修正します。
