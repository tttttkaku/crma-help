Data 360 でのセグメント名の使用

セグメント名は Salesforce Platform に保存されます。これらをクリーンルームクエリ結果に含めるには、CRM コネクタを使用してマーケットセグメントデータに接続し、Data 360 で使用できるようにします。セグメント名を Data 360 に取り込まない場合、クエリレポートにはセグメント ID のみが含まれます。

必要なエディション

使用可能なエディション: Data 360 でサポートされるすべてのエディション。 「Data 360 Edition の可用性」を参照してください。

Data 360 へのセグメント名の取り込み

Salesforce に保存されているセグメント名を Data 360 に取り込むデータストリームと数式を作成します。 数式は、データモデルリレーションで使用できるようにセグメント ID を 15 文字に切り捨てます。

必要なエディション

必要なユーザー権限
データストリームを作成する 「Data Cloud アーキテクト」権限セット

Data 360 を CRM 組織に接続します。Data Cloud の [設定] で CRM コネクタを設定します。

  1. Data Cloud の [データストリーム] タブで、[新規] をクリックします。
    1. [Salesforce CRM] を選択し、[次へ] をクリックします。
    2. クリーンルームの Salesforce 組織を選択します。 
    3. [View Objects (オブジェクトの表示)] を選択します。
    4. セグメント・オブジェクトを検索して選択します。
    5. [次へ] をクリックします。
  2. [標準項目] タブで、[ セグメント名]、[ 母集団]、およびセグメントを識別するその他の項目を選択します。 
    必須項目は自動選択されます。
  3. DLO の項目をマーケットセグメント DMO に対応付けます。［Population］ フィールドを ［Last Segment Member Count］ フィールドにマッピングします。
  4. [数式項目] タブで、[新規数式項目] をクリックし、次の詳細を入力します。
    1. 項目の表示ラベルを入力します。項目表示ラベルは、データストリーム項目の表示名として機能します。
    2. 項目の API 参照名を、指定された形式の項目の表示ラベルと一致するように更新します。項目 API 参照名は、データストリーム項目のプログラムによる参照として機能します。
    3. [数式の戻り値のデータ型] で [テキスト] を選択します。
  5. [検索機能] ウィンドウの [テキスト] で、[サブ文字列] 関数を見つけて選択します。
  6. [関数を適用] をクリックします。
    1. この数式例では、「text」を削除し、「Attributes」タブから「Segment ID」を選択して置き換えます。
    2. 「beginindex」を 0 に、「endindex」を 15 に置き換えます。
      この関数は SUBSTRING(sourceField[‘Id’],0,15) として表示されます。
    3. [テスト対象値] で、15 文字を超えるセグメント ID を入力し、[テスト] をクリックします。
      出力では、セグメント ID が 15 文字に切り捨てられます。
    4. [保存] をクリックします。
  7. [数式項目] タブで、新しい項目を選択し、[次へ] をクリックします。
  8. データスペースを選択します。
  9. [リリース] をクリックします。
  10. (省略可能) 複数のデータスペースでクリーンルームを使用するには、必要なすべてのデータスペースのセグメントオブジェクトを取り込みます。
    1. [データストリーム] タブで、追加するデータスペースを選択します。
    2. [スペース メンバーを追加] をクリックします。
    3. 取り込んだ DLO を選択します。 

マーケットセグメント DMO へのリレーションの作成

個人 - 最新 DMO とマーケットセグメント DMO 間のリレーションを作成して、セグメント名を個人 - 最新 DMO の関連項目に対応付けます。

必要なエディション

必要なユーザー権限
DMO リレーションを作成する 「Data Cloud アーキテクト」権限セット
  1. Data Cloud で、[データモデル] タブに移動します。
  2. [Individual - Latest DMO (個人 - 最新 DMO)] を検索して選択します。DMO が見つからない場合は、[リストビュー] を [対応付け済み] から [すべて] に変更します。
  3. [リレーション] タブで、[編集] をクリックします。
  4. [新規リレーション] をクリックし、次の情報を入力します。 
    1. [項目] で、[セグメント ID] を選択します。
    2. [カーディナリティ] で、[1:1] を選択します。
    3. [関連オブジェクト] に「Market Segment」と入力します。
    4. [関連項目] で、作成した数式項目を選択します。
  5. [保存] をクリックします。 
  6. 該当する場合は、統合個人 - 最新の DMO に対してこの手順を繰り返します。
    セグメント名が [Individual - Latest DMO (個人 - 最新 DMO)] に接続され、クリーンルームクエリ結果に含まれるようになりました。

クリーンルームプロバイダー

プロバイダーとは、プラットフォームを所有し、データまたは広告スペースへのアクセス権を他の会社に提供できるパブリッシャーまたは企業です。Data 360 クリーンルームを使用すると、プロバイダーは Salesforce Data 360 クリーンルームまたは AWS クリーンルームを使用してコラボレーションできます。 

  • Data 360 クリーンルームを使用するプロバイダーは、Salesforce が提供するコラボレーションテンプレートまたはカスタムコラボレーションテンプレートを使用して、コンシューマーに使用事例を提供します。 
  • AWS クリーンルームを使用するプロバイダーの場合、Data 360 開発者組織を使用して、提供する使用事例をサポートするカスタムコラボレーションテンプレートを作成します。コンシューマーがコラボレーションを招待すると、AWS クリーンルームでコラボレーションできます。

プロバイダーは、複数の方法で使用事例を提供できます。 

  • 潜在的なコラボレーターが公開検出できるクリーンルームの使用事例を提供するには、クリーンルームパッケージを AppExchange で公開します。AWS クリーンルームを使用しているプロバイダーの場合、この方法を使用します。
  • コラボレーションテンプレートを概念実証として特定のコラボレーターに配布するには、クリーンルームパッケージを未管理パッケージとして作成します。ただし、この方法では、アップグレードまたは改訂されたバージョンのパッケージを提供することはできません。
  • 特定のコンシューマーとコラボレーションするには、コンシューマーがData Cloud組織の許可リストに組織を追加し、コラボレーションにSalesforceが提供するコラボレーション テンプレートを使用する必要があります。

AppExchange へのクリーンルームパッケージの公開

Data Cloud の [設定] でクリーンルームパッケージを作成したら、データキットを使用してパッケージ化します。次に、パッケージマネージャーを使用して管理パッケージを作成し、AppExchange で公開します。管理パッケージは AppExchange でのみ公開できます。

必要なエディション

使用可能なエディション: Developer Edition
必要なユーザー権限
クリーン ルーム パッケージを AppExchange に公開する AppExchangeパートナー
メモ AppExchange パートナーのみが AppExchange にパッケージを公開できます。
  1. データキットを作成します。
  2. データキットを保存したら、[Clean Room Providers (クリーンルームプロバイダー)] でプロバイダー名を選択します。
  3. データキットの公開順序が表示され、同期されていることを確認します。
  4. データキットを公開します。
  5. パッケージマネージャーにデータキットを追加します。
重要 パッケージの作成時に必ず [管理] チェックボックスをオンにします。

Salesforce パートナーになるための要件と手順については、「AppExchange ISV オンボーディングガイド」を参照してください。

Salesforceパートナー コンソールを使用するには、「AppExchangeパートナー コンソール ガイド」を参照してください。

Sandbox 組織のクリーンルームの検証

クエリ結果を検証するには、Developer Sandbox または Developer Pro Data 360 Sandbox でクリーンルームパッケージ、設定、データマッピングをテストします。クエリの実行で期待される結果が得られたら、対応付けられたテンプレートを Sandbox 組織から本番組織にリリースします。

必要なエディション

使用可能:

本番でクリーンルームを設定した後に Data 360 Sandbox を作成すると、クリーンルームパッケージと対応付けられたテンプレートが Sandbox に複製されます。ただし、クリーンルームのコラボレーションは Sandbox では複製されません。 

Sandbox でクリーンルーム設定を開始するには、クリーンルームパッケージをリリースします。

メモ Sandbox 組織に Clean Room パッケージをインストールする場合、認証の失敗を回避するために、パッケージのインストールリンクで login.salesforce.com を test.salesforce.com に置き換えます。

既知のパートナーとコラボレーションしている場合は、Sandbox 組織 ID を許可リストに登録します。 クリーンルームパッケージがなくても、許可リストに登録された組織とコラボレーションできます。Sandbox から本番組織へのコラボレーションを開始することはできません。その逆も同様です。コラボレーションを設定する前に、両方の組織が同じ種別 (両方の Sandbox または両方の本番) であることを確認します。プロバイダーの場合、2 つの Sandbox 組織を使用してクリーンルーム設定を検証します。

セグメント重複の使用事例テンプレート

セグメント重複の使用事例は、提供者と消費者が共有オーディエンスセグメントを理解するのに役立ちます。消費者は、提供者データベースの特定のオーディエンスセグメントとの重複を特定できます。提供者はオーディエンスデータの価値を示すことができます。双方は未加工データを公開することなく、共同マーケティング活動を計画し、ターゲティング戦略を調整できます。

セグメント重複の使用事例テンプレートには、次のパラメーターが含まれます。

パラメーター 値
関係者寄稿データ 両方
必須属性 セグメント名、個人 ID、ハッシュされたメールアドレス、連絡先
省略可能な属性 セグメントの親カテゴリ
Query Type (クエリ種別) Count Overlap by Segment (セグメント別の重複の件数)
Query Run By (クエリ実行者) コンシューマー
結果の型 集計済み件数
集計しきい値 一致する個人は 100 人以上
Result Received By コンシューマー
Results Stored In (保存される結果) コンシューマー側での出力 DMO
プライバシー対策 非公開結合、クエリ制限、集計しきい値

クリーンルームの有効化の設定

クリーンルーム有効化コラボレーションが有効になると、プロバイダーは Amazon S3 バケットで一致するオーディエンスデータを直接受信します。提供者はこのデータを使用して、広告プラットフォームまたは下流のメディアシステムで対象を絞ったキャンペーンを実行できます。

必要なエディション

使用可能なエディション: Data 360 でサポートされるすべてのエディション。 「Data 360 Edition の可用性」を参照してください。
必要なユーザー権限
クリーンルームの有効化を設定する

次のいずれかの権限セット:

  • Data Cloud アーキテクト
  • Data Cloud 有効化マネージャー
  • Data Cloud 有効化スペシャリスト

プロバイダーは、クリーン ルーム プラットフォームとして Data 360 または AWS を使用できます。Data 360 をクリーンルームプラットフォームとして使用している提供者は、Salesforce が提供するコラボレーションテンプレートまたはカスタムテンプレートを選択できます。AWS をクリーンルームプラットフォームとして使用するプロバイダーは、カスタムコラボレーションテンプレートを使用する必要があります。

メモ クリーンルームパッケージを作成またはリリースするには、Data 360 開発者組織が必要です。
  1. 提供者: 有効化の使用事例をサポートするクリーンルームパッケージを作成します。Data 360 開発者組織の場合。
    「Create a Clean Room Package」を参照してください。
  2. 提供者: AppExchange でクリーンルームパッケージを公開します。
  3. コンシューマー: AppExchange からパッケージをリリースします。プロバイダーが信頼できるパートナーの場合、パッケージをリリースせずに、サポートされている使用事例へのアクセスを許可リストに登録できます。
    「Deploy a Clean Room from an AppExchange Package」または「Allowlist a Clean Room Provider」を参照してください。
  4. コンシューマーとプロバイダー: マッピングされたテンプレートを作成して、各関係者のデータをコラボレーションの必須項目に対応付けます。
    事前に対応付けられたテンプレートを作成したり、コラボレーションの作成時および招待の受け入れ時にデータを対応付けたりできます。コラボレーションを有効にする前に、双方が必要な対応付けを完了する必要があります。「クリーンルームの使用事例のデータの対応付け」を参照してください。
  5. コンシューマー: コラボレーションを作成し、招待を提供者に送信します。
    「Create a Clean Room Collaboration and Invite a Provider」を参照してください。
  6. 提供者: コラボレーション招待を受け入れます。

    招待の受け入れウィザードで、Data 360がコラボレーション結果をAmazon S3バケットに書き込めるように、AWSアカウントへのIDプロバイダー ベースの認証を設定します。既存のバケットを使用するか、バケットを作成できます。

    「クリーンルームへの招待の受け入れまたは却下」を参照してください。
  7. 消費者: 提供者が受け入れてコラボレーションが有効になったら、クリーンルームでクエリを実行します。
    詳細は、「クリーンルームでコラボレーション」を参照してください。
    クエリ結果は、プロバイダーの S3 バケットに Parquet ファイルとして書き込まれます。クエリを実行するたびに、s3://[your-bucket]/[Collaboration Name]/[Query Name]_[Timestamp]/時に新しいタイムスタンプ付きフォルダが作成されます。
  8. 提供者: 広告プラットフォームまたは下流のメディアシステムで出力を使用します。
    出力を Data 360 に取り込んで有効化するには、まず外部ツールで Parquet ファイルを変換してから、再度取り込みます。

Salesforce が提供するコラボレーションテンプレート

Data 360 には、重複するセグメントを識別するための定義済みテンプレートが用意されています。信頼できるプロバイダーを許可リストに登録してコラボレーションを開始する場合は、Salesforce が提供するコラボレーションテンプレートを使用します。

  • セグメント重複の使用事例テンプレート
    セグメント重複の使用事例は、提供者と消費者が共有オーディエンスセグメントを理解するのに役立ちます。消費者は、提供者データベースの特定のオーディエンスセグメントとの重複を特定できます。提供者はオーディエンスデータの価値を示すことができます。双方は未加工データを公開することなく、共同マーケティング活動を計画し、ターゲティング戦略を調整できます。
  • 有効化の使用事例テンプレート
    有効化の使用事例では、プロバイダーのメディアまたは広告プラットフォームを介してファーストパーティオーディエンスデータを有効化するプライバシー優先の方法を消費者に提供します。セグメントリスト全体を転送するのではなく、コンシューマーはクリーンルーム内で一致するオーディエンスを特定します。Data 360は、キャンペーンの有効化で使用するために、一致したレコードをプロバイダーのAmazon S3バケットに直接書き込みます。

SQL を使用したインサイトの作成

SQL を記述して、Data 360 の計算済みインサイトとストリーミングインサイトを定義します。各クエリは特定の構造に従い、サポートされる関数、演算子、データ型を使用する必要があります。

必要なエディション

使用可能なエディション: Data 360 でサポートされるすべてのエディション。 「Data 360 Edition の可用性」を参照してください。

計算済みインサイトクエリは次の構造に従います。

SELECT <attributes>, <aggregation(measures)>
FROM <data_model_object>
JOIN [INNER | LEFT | RIGHT | FULL] <data_model_object> -- optional
WHERE <row_filter>                                     -- optional
GROUP BY <dimensions>
指標
集計関数によって生成される定量的な値 (総額やレコード件数など)。すべてのクエリに少なくとも 1 つの基準を含める必要があります。
ディメンション
商品名、日付、プロファイル ID など、基準を分類およびグループ化するために使用する定性的な項目。 SELECT 句内の項目のうち、集計関数内にない項目はディメンションとして扱われ、GROUP BY 句にも含める必要があります。
メモ 計算済みインサイトをセグメントに含めるには、セグメント化されたテーブルをJOINとして追加し、その主キーをクエリのディメンションとして含めます。

サポートされる構文ルール、関数、演算子の完全なリストについては、このセクションの参照トピックを参照してください。

  • SQL を使用した計算済みインサイトの作成
    マッピングされたオブジェクトおよび項目から評価指標とディメンションを作成する SQL 式を記述します。SQL を使用して Data 360 で計算済みインサイトを作成できます。
  • SQL を使用したストリーミングインサイトの作成
    SQL 式を記述して、ほぼリアルタイムのデータソースからディメンション全体のストリーミング評価指標を計算します。ストリーミングインサイトでは、特定の時点のデータが分析されます。ストリーミング インサイトは、ほぼリアルタイムで時系列集計を作成し、Data 360内のデータをオーケストレーションして最適化するのに役立ちます。
  • インサイトの SQL ルール
    Data 360 で計算済みインサイトまたはストリーミングインサイトの SQL を記述する場合、ルールによって各条項の解釈方法と適用される制約が決まります。WHERE または JOIN 句にネストされたサブクエリを埋め込み、外部クエリで返される行を制限することもできます。
  • インサイト SQL のデータ型
    Data 360 で SQL を使用して計算済みインサイトまたはストリーミングインサイトを定義する場合、基準とディメンションでサポートされているデータ型を使用します。基準は集計する数値で、ディメンションはグループ化する定性的な項目です。
  • インサイトの SQL 関数
    Data 360 で計算済みインサイトを作成する場合、次の集計、日時、分析、書式設定、算術および統計、Boolean 関数を使用します。[集計可能] 列は、セグメントまたは有効化で照会されたときに、関数の出力をより少ないディメンションで積み上げ集計できるかどうかを示します。
  • インサイトの SQL 演算子
    Data 360 で計算済みインサイトを作成するときは、SQL 式で次の算術演算子、通貨演算子、論理演算子を使用します。
  • 数式、演算子、計算済みインサイト
    Data 360の数式、演算子、計算済みインサイトを使用して、ワークフローの異なる方法とフェーズで利用者を作成します。取り込み時に、数式を使用して、下流で使用される行ベースのデータの操作を実行できます。セグメンテーションでは、セグメント演算子を使用してオーディエンスが作成されます。

    • 毎日
    • 毎週

Data 360 プロファイルライセンス請求可能プロファイルの計算

Data 360 Profiles ライセンスがある組織では、請求可能なプロファイル数は有効な ID 解決ルールセットがあるかどうかに基づきます。請求可能なプロファイル数がエンタイトルメントを超えた場合、追加のプロファイルの超過料金で請求されます。

有効な ID 解決ルールセットを使用したデータスペースのプロファイルの計数

ID 解決を使用してソースプロファイルを統合プロファイルにリンクしている場合、請求可能な統合プロファイル数は、既知の統合プロファイルの合計、匿名プロファイルの 4%、および ID 解決で使用されていないプロファイルとして分類された DMO にマッピングされたすべての DLO のレコード数の合計です。

  • Known Unified Profiles: 有効な ID 解決ルールセットによって出力される既知の統合プロファイルレコードの数。既知の統合プロファイルレコードの数を確認するには、有効なルールセットごとに ID 解決の概要を表示します。すべての有効なルールセットで既知の統合プロファイルの数を追加します。
  • 匿名統合プロファイル: 有効な ID 解決ルールセットによって出力される匿名統合プロファイルレコード数の 4%。この数を計算するには、有効な各ルールセットの ID 解決概要を表示します。匿名プロファイルの数に 0.04 を乗算します。 すべての有効なルールセットで匿名統合プロファイルの数を追加します。
  • 統合ソースプロファイル: ID 解決ルールセットによって出力された統合データモデルオブジェクト (Unified DMO) を除き、プロファイルとして分類された DMO にマッピングされている、カテゴリに関係なくすべての DLO のすべてのレコードの数。

有効な ID 解決ルールセットのないデータスペースでのプロファイルの計数

ID 解決を使用していないデータスペースでは、請求可能なプロファイル数は、カテゴリに関係なく、プロファイル種別として分類されたデータモデルオブジェクト (DMO) に対応付けられたすべてのデータレイクオブジェクト (DLO) のすべてのレコードの合計です。既知のプロファイルレコードと不明なプロファイルレコードの両方が計数されます。

次の DMO にのみマッピングされている DLO は、この数から除外されます。

  • Account Contact (取引先責任者)
  • 連絡先住所
  • 連絡先アプリケーション
  • 連絡先の同意
  • 連絡先メール
  • 連絡先 OTT サービス
  • 連絡先電話
  • 連絡先ソーシャル
  • デバイス
  • 関係者 ID
例

組織に 2 つの ID 解決ルールセット (10,000 件のレコードがある統合個人.1 と 8,000 件のレコードがある統合個人.2) があるとします。また、[プロファイル] に分類され、[プロファイル] に分類された他の DMO に対応付けられる 2 つの DLO もあります。取引先 DLO には 2,000 件のレコードがあり、カスタム DLO には 5,000 件のレコードがあります。この顧客の場合、請求可能な統合プロファイルの合計は 10,000 + 8,000 + 2,000 + 5,000 = 25,000 です。

統合プロファイル数に影響する要素

プロファイル数がビジネスニーズを正確に反映するように、これらの要素に対処します。

複数の ID 解決ルールセット

すべての有効な ID 解決ルールセットの統合プロファイル数を使用して、請求可能な既知のプロファイルと匿名プロファイルの合計を計算します。有効な ID 解決ルールセットの数を検証します。複数の有効なビジネス目的にすべてが必要かどうかを判断します。

データストリームの増加

異なるソースシステムを Data Cloud に接続し、新しいデータストリームを介して取り込まれるデータ量が増加すると、ソースプロファイルの数も増えます。プロファイルとして分類されたすべてのデータストリームとソースを確認します。重複するソース、開発ソース、テストソース、ステージングソースが接続されているかどうかと、それらがまだ必要かどうかを判断します。

データモデルオブジェクトカテゴリ

プロファイルとして分類されるデータモデルオブジェクト (DMO) に対応付けられたデータレイクオブジェクト (DLO) はセグメント化でき、統合プロファイル数に含まれます。DLO から DMO へのすべてのマッピングを確認します。[プロファイル] に分類された DMO にマッピングされたすべてのデータストリームに、セグメント化の基準となる母集団が含まれているか、セグメントの開始母集団として使用する母集団が含まれているかを判断します。DMO がプロファイルとして誤って分類されていないかどうかを確認します。

DMO がプロファイルとして誤って分類されている場合、そのカテゴリを [その他] に変更できます。DMO のカテゴリは、セグメンテーションまたは有効化で使用されていない場合にのみ変更できます。カテゴリを [プロファイル] から [その他] に変更する前に、DMO を使用するすべてのセグメントと有効化を削除します。「データモデルオブジェクトのカテゴリの変更」を参照してください。

統合プロファイル数に関するその他の考慮事項

  • 複数のデータスペースに含まれる DLO のレコードは 1 回のみ計数されます。ソース DLO のレコード数は、DLO のデータスペース固有のビューに含まれるレコード数に関係なく計数されます。
  • マッピングされていない DMO として出力された変換から作成されたデータは、請求可能な統合プロファイルには含まれません。DLO がマッピングされていない場合、DLO は計数されません。
  • 個人 DMO にマッピングされ、[プロファイル] 種別の DMO にもマッピングされている DLO は 2 回計数されません。
  • プロファイル種別が DMO にマッピングされているすべての DLO は、請求可能な統合プロファイルに含まれます。この数には、次のシナリオが含まれます。
    • ID 解決数外のデータストリーム
    • ID 解決の範囲外の同意 DMO の数
    • ID 解決数外のプロファイル タイプの DMO にマッピングされたデータ変換またはストリーム変換 DLO

データグラフデータ構造

データグラフの基盤となるコンポーネントを理解して、データグラフを効果的に作成および使用できるようにします。

Data 360 では、データグラフはデータスペース内に作成され、1 つのプライマリデータモデルオブジェクト (DMO) が必要です。データグラフの基盤として使用するデータスペースの DMO を選択します。基盤 DMO はプライマリ DMO です。プライマリ DMO (関連オブジェクトと呼ばれる) に関連する DMO や、関連する計算済みインサイトからデータを追加することもできます。計算済みインサイトとストリーミングインサイトは、データグラフにも含まれる DMO に基づいている限り、データグラフに含めることができます。

プライマリ DMO はエンゲージメント以外のカテゴリに属することができ、最も一般的なカテゴリはプロファイルカテゴリです。関連オブジェクト DMO は、[プロファイル]、[その他]、または [エンゲージメント] カテゴリに属することができます。データグラフに含める項目をプライマリ DMO とその関連オブジェクトから選択します。

データグラフを作成すると、選択したオブジェクトと項目が元の階層リレーションから 1 つのフラット化された参照のみのデータグラフレコードに変換されます。データグラフレコードには、データスペースやデータグラフ名などのメタデータが含まれます。また、プライマリ DMO と関連オブジェクトのデータもクエリ可能な JSON Blob として含まれます。

メモ 新しいリアルタイムデータグラフでは、DMO 間の N:1 リレーションはサポートされません。N:1 リレーションを作成する DMO を追加しようとすると、選択できなくなります。すでに N:1 リレーションが含まれている既存のリアルタイムデータグラフは引き続き実行されます。ただし、N:1 リレーションの親 DMO への変更は、リアルタイムデータグラフにすぐには反映されません。

データグラフ

データグラフでは、Data 360 のデータモデルオブジェクト (DMO) の構造化データがまとめられます。このデータを組み合わせて、情報の使いやすいビューを作成します。

データグラフのデータは事前に用意されているため、より少ない手順で必要な情報を取得できます。つまり、データ要求とクエリでほぼ即座に結果が表示されます。リアルタイムデータグラフは、次のような強力な機能にとって重要です。

  • リアルタイムの ID 解決
  • リアルタイムの計算済みインサイト
  • リアルタイムセグメンテーション

データグラフを作成するには、既存の DMO から組み合わせる特定の項目を選択します。次に、Data 360 はこれらの選択されたフィールドを収集して、参照のみの 1 つのデータグラフレコードに変更します。このレコードでは、結合されたすべてのデータが 1 つの JSON Blob に配置されます。

Salesforce Lightning Experience では、データ エクスプローラーとクエリ エディタを使用してデータグラフを表示できます。Data 360 メタデータ API およびクエリ API を使用して、データグラフを直接照会できます。この組み合わせたデータを他の Salesforce アプリケーションや操作で使用することもできます。

  • データグラフデータ構造
    データグラフの基盤となるコンポーネントを理解して、データグラフを効果的に作成および使用できるようにします。
  • データグラフの請求に関する考慮事項
    データグラフの使用は、次の使用量タイプのクレジットの消費に影響します。Digital Walletを使用して、組織で有効な消費カードを確認し、各カードで使用可能なクレジット数を確認し、各使用量種別で消費されたクレジット数を確認します。Data 360 ProfilesライセンスやAgentforce 1 Editionなど、特定のライセンスまたはエディションでは測定されない使用量タイプもあります。詳細は、ライセンスとライセンスドキュメントを参照してください。
  • データグラフの状況
    古いデータグラフの ［Last Run Status］ 列を使用して、進行状況を追跡し、問題を特定して、対応策を実行します。
  • データグラフの作成および管理
    Data 360 でデータグラフを作成および管理します。データグラフは、Data 360 ユーザーインターフェースまたは API を使用して表示できます。
  • データグラフの高度な設定
    Data 360 では、データグラフの高度な設定により、デフォルト設定以外のデータグラフをカスタマイズできます。

データエクスプローラーの列と検索条件

データエクスプローラーのデータビューをパーソナライズして、Data 360 で選択したオブジェクトに最も関連するデータのみを表示できます。最大 10 列を表示できます。デフォルトではアルファベット順で表示されます。列データを昇順または降順に並び替えることができます。

オブジェクト種別とオブジェクトを選択すると、データエクスプローラーダッシュボードにデータが表示されます。列を編集して、そのオブジェクトで表示されるデータを変更できます。計算済みインサイトオブジェクトの場合、列に対して少なくとも 1 つのディメンションと 1 つの基準を含めます。

値を表示または除外するための検索条件をデータに追加することができます。検索条件アイコンを選択して、検索条件を追加します。検索条件ロジックの作成時に次の演算子を使用できます。[値] 項目の数値にカンマは使用しないでください。たとえば、1,000 ではなく 1000 を使用します。 [値] 項目の文字列では、大文字と小文字が区別されます。

演算子 説明
次の値と一致する 選択した項目の値が指定した入力値と等しいかどうかを評価する場合は、「次の値と一致する」演算子を使用します。たとえば、取引先が 100001 であるすべてのレコードを選択する場合は、「次の値と一致する」演算子を使用して、入力値に 100001 を指定します。
次の値と一致しない 選択した項目の値が指定した入力値と一致しないかどうかを評価する場合は、「次の値と一致しない」演算子を使用します。たとえば、取引先が 100001 と一致しないすべてのレコードを選択する場合は、「次の値と一致しない」演算子を使用し、入力値に 100001 を指定します。
次の値より大きい 選択した項目の値が指定した入力値より大きいかどうかを評価する場合は、「次の値より大きい」演算子を使用します。たとえば、取引先が 100001 より大きいすべてのレコードを選択する場合は、「次の値より大きい」演算子を使用し、入力値に 100001 を指定します。
次の値以上 選択した項目の値が指定した入力値以上であるかどうかを評価する場合は、「次の値以上」演算子を使用します。たとえば、取引先が 100001 以上のすべてのレコードを選択する場合は、「次の値以上」演算子を使用し、入力値に 100001 を指定します。
次の値未満 選択した項目の値が指定した入力値より小さいかどうかを評価する場合は、「次の値未満」演算子を使用します。たとえば、取引先が 100001 より小さいすべてのレコードを選択する場合は、「次の値未満」演算子を使用し、入力値に 100001 を指定します。
次の値以下 選択した項目の値が指定した入力値以下かどうかを評価する場合は、「次の値以下」演算子を使用します。たとえば、取引先が 100001 以下のすべてのレコードを選択する場合は、「次の値以下」演算子を使用し、入力値に 100001 を指定します。
次に部分一致する 選択した項目の値が指定した入力値のテキスト文字列の文字と一致するかどうかを評価する場合は、「次に部分一致する」演算子を使用します。「次に部分一致する」演算子はテキストデータ型のみをサポートします。

この演算子はテキスト文字列を部分的に照合するメカニズムを備え、ワイルドカードの使用がサポートされます。たとえば、「appl%」は appleton、apple、appl と一致しますが、Bappl とは一致しません。
次に含まれる 「in」演算子を使用して、選択したフィールドの値がカンマ区切りリストにあるかどうかを評価します。「次に含まれる」演算子は、日付および日時データ型をサポートしません。たとえば、APAC 地域の特定の国のすべてのレコードを選択する場合は、「次に含まれる」演算子を使用し、日本、台湾、韓国などの国のリストを指定することが考えられます。
次に含まれない 選択した項目の値が複数値のカンマ区切りリストに含まれないかどうかを評価する場合は、「次に含まれない」演算子を使用します。「次に含まれない」演算子は、日付および日時データ型をサポートしません。たとえば、APAC 地域の特定の国のすべてのレコードを除外する場合は、「次に含まれない」演算子を使用し、日本、台湾、韓国などの国のリストを指定することが考えられます。

360 データとインサイトによる組織の強化

Data 360 強化を使用して、組織全体のクリーンアップおよびハーモナイズされたデータを組織に追加します。Data 360 のデータを使用して、レコードページの関連リストとコピー項目の強化を作成します。

必要なエディション

使用可能なエディション: Data 360 でサポートされるすべてのエディション。 「Data 360 Edition の可用性」を参照してください。

強化を使用して、Data 360 からの情報を Salesforce CRM レコードページに追加できます。強化には 3 つの種類があります。

  • 関連リスト — 関連リストには、DMO オブジェクトの情報が表示されます。DMO オブジェクトには、Data 360 個人オブジェクトまたは統合個人オブジェクトとの 1 対多のリレーションがあります。たとえば、1 人の取引先責任者が多くのメールエンゲージメントを担当することがあります。関連リストを使用すれば、取引先責任者のエンゲージメントを会社全体で確認できます。
  • 直接 DMO 関連リスト — 直接リレーションを介して Salesforce オブジェクトに接続されている DMO からの情報が表示されます。直接リレーションでは、DMO の ID 解決が完了している必要はありません。たとえば、Automotive Cloud の車両オブジェクトには、Data 360 の車両テレマティクスイベント DMO レコードの関連リストを含めることができます。
  • 項目をコピー — [項目をコピー] には、1 対 1 のリレーションを持つオブジェクトから Data 360 個人、統合個人、Data 360 取引先、または統合取引先 DMO にコピーされた項目データが表示されます。CIO オブジェクトには、ディメンションとして 1 つの個人 ID を使用するか、複数ディメンションの集計可能な CIO である必要があります。

    Data Cloud Sandbox で、新しい関連リストの強化を作成するか、自動生成された既存の関連リストを変更します。強化のテストが完了したら、データキットにパッケージ化して、変更セットを使用して本番にリリースします。

ステップ 1: データスペースを作成する

強化を作成するにはデータスペースへのアクセス権が必要です。データスペースにアクセスする必要がある場合や、データスペースを作成する必要がある場合は、Data 360 管理者が対応します。複数のデータスペースがある場合、取引先責任者レコードとリードレコードで共有する情報が含まれるデータスペースを理解することが重要です。たとえば、各データスペースが異なるビジネスユニットに割り当てられている場合、ビジネスユニットに一致するデータスペースを選択します。

  2. Data Cloud アーキテクト — 計算済みインサイトの作成 (インサイトあたり 5 分)

数式、演算子、計算済みインサイト

Data 360の数式、演算子、計算済みインサイトを使用して、ワークフローの異なる方法とフェーズで利用者を作成します。取り込み時に、数式を使用して、下流で使用される行ベースのデータの操作を実行できます。セグメンテーションでは、セグメント演算子を使用してオーディエンスが作成されます。

計算済みインサイトでは、ビューを使用して大規模な行動データを理解し、ビューを再利用してセグメンテーションを強化できます。また、ビジネスインテリジェンスツールでインサイトを検索することもできます。データ変換を実行するために使用するオプションは、使用事例とデータ型によって異なります。

数式

数式はさまざまなデータ型の計算に適していますが、高度な知識を必要とします。数式は他のソース項目から取得されますが、ハードコード化された値を使用することもできます。

ユーザーがセグメンテーション時に消費および使用できるロジックの抽出に単純な行ベースの操作が使用される場合、数式を使用することをお勧めします。行ベースの計算では、行全体の集計ではなく、自己完結行にロジックを適用します。たとえば、「Shoe」を「Shoes」に変更する IF 数式は、結果が静的であるため機能します。ただし、1 月 1 日以降の日数の確認は、日数が時間の経過と共に変化するため機能しません。計算は取り込み時にのみ実行されるため、実行時の計算ではなく保存されている計算になります。数式は自動的に更新されません。

セグメンテーション演算子

演算子を使用して、データアナリストの助けを借りずにセルフサービスの絞り込み使用事例を完了します。セグメンテーション演算子は次の用途に最適です。

  • 1 つのオブジェクトの単純な集計 (件数など)
  • 条件が単純であり、頻繁に再利用される可能性が低い場合の数値の最大、最小、平均、合計集計
  • 2 年以下の集計データでの絞り込み

セグメンテーション演算子で使用事例が完全にサポートされていない場合は、代わりに計算済みインサイトを使用します。たとえば、日付に対する最大演算子は、計算済みインサイトでのみ使用できます。たとえば、これを使用して靴の最終購入日を見つけます。セグメント間で再利用される数値では、または数値に検索条件コンテナの一部としてその他の属性の長いリストがある場合、最大、最小、平均、合計集計には計算済みインサイトを使用します。

計算済みインサイトの機能

顧客の行動を理解するために、複数のディメンション (顧客属性、チャネル属性、商品属性など) を使用して、顧客レベルまたは母集団全体レベルで計算済みインサイトを使用します。リーセンシー、頻度、金額値 (RFM)、顧客生涯価値 (CLV) など、複数ディメンションの評価指標を定義および計算します。評価指標の計算後、評価指標は毎日自動的に更新できるため、チャネル、顧客、または商品の最新情報に基づいて操作できます。

計算済みインサイトを使用すると、ユーザーは、評価指標、ディメンション、検索条件を使用して有効化のセグメント条件とパーソナライズ属性を簡単に定義できます。計算済みインサイトは次の目的に最適です。

  • ネットプロモータースコアのパーセント値の計算など、非自明な計算
  • 複数のオブジェクトにまたがる複雑なクエリ
  • 再利用性。異なる値でビューを複数回使用することが予想される場合や、同じビューで関連属性を組み合わせた場合など

たとえば、同じビューに属する Web ページビュー数とページクリック数、およびディメンションとして変更された商品カテゴリを確認する必要があるとします。セグメンテーションを使用して実装した場合、変更があるたびに条件を再定義する必要があります。計算済みインサイトでは、ビューにディメンションが設定された後、必要に応じてディメンションを再利用できます。基準は 50 個以下、ディメンションは 10 個以下に制限されているため、ビューを整理して異なるビューを作成したり、関連するオブジェクトの評価指標をグループ化したりします。可能な限り、ビューにさまざまチャネルを含めてすべてのエンゲージメントが 1 つのクロスチャネルビューに含まれるようにすることは避けます。

有効化での Google オーディエンスインサイト

Data Cloud 内の Google オーディエンスレポートからのインサイトを使用して、顧客固有の特性、関心、行動を掘り下げます。Google に対してセグメントを有効化すると、5 ～ 7 日でオーディエンスレポートが生成されます。レポートでは、デモグラフィック、商品を積極的に調べている顧客、その顧客のアフィニティグループに関するインサイトがライフスタイル、長期の購入習慣、関心に基づいて提供されます。

レポートスコア

レポートでは、有効化されたセグメントメンバーシップの母集団 (カスタマーマッチオーディエンスとも呼ばれる) を特定の国における平均 Google ユーザーの母集団と比較してスコアが生成されます。スコアは、カスタマーマッチオーディエンス内のメンバーが特定のデモグラフィックまたは行動カテゴリに属している可能性を表します。

デモグラフィックでは、メンバーは年齢と性別に基づいて分類されます。[In-Market (購買意向の強い)] カテゴリには、商品を積極的に調べているため、特定のサービスや商品を購入する可能性のある顧客が表示されます。アフィニティでは、特定の特性を有する顧客が分類されます。

[In-Market (購買意向の強い)] カテゴリと [アフィニティ] カテゴリの場合、レポートには最大 20 個のスコアが含まれます。選択されたインサイトは、上位 20 個のスコアに基づいています。

考慮事項とプライバシー

オーディエンスインサイトレポートの対象になるには、有効化されたセグメントの母集団が 1,000 ユーザーを超える必要があります。レポートは、セグメントメンバーシップに大幅な変更がある場合に更新されます。

インサイトが匿名性を確保し、個人に紐付けられないようにするために、Google はプライバシー保護を実装しています。プライバシー対策の一部を次に示します。

  • カテゴリの編集 — 特定のケースでは、ユーザーの母集団が小さすぎると判断されると、高インデックスカテゴリがレポートから除外されます。この除外により、ユーザーのプライバシーが保護されます。
  • 差分プライバシー — レポート結果に大きな影響を及ぼすことなく、個人のメンバーシップレコードを保護するために、Google はランダム化されたノイズをレポートに追加するアルゴリズムを採用しています。そのため、インサイトスコアは近似値とみなされ、経時的に若干の変動が生じる可能性があります。

自動ドロップのハイブリッド検索クエリ式

Data 360 クエリ API を使用して、ハイブリッド検索結果の自動ドロップを設定します。

必要なエディション

使用可能なエディション: Data 360 でサポートされるすべてのエディション。 「Data 360 Edition の可用性」を参照してください。

キーワード検索結果、ベクトル検索結果、ハイブリッド検索結果の自動ドロップを設定できます。最良の結果を得るには、キーワード検索とベクトル検索に自動ドロップを使用するか、ハイブリッド検索結果のみを使用します。1 つのクエリですべての検索種別に対して自動ドロップを使用しないでください。

「autodrop_keyword」、「autodrop_vector」、および「autodrop_hybrid」に渡される num_drops 整数パラメーターは、ハイブリッド検索機能で結果を切り捨てるために対応するスコア リストで検出する必要がある重要なスコア ドロップの数を定義します。

キーワード検索とベクトル検索結果での自動ドロップには、次の構文を使用します。

select * from hybrid_search(
    table(<Search_index_DMO>), 
    ‘<Search String>’,
    '<PreFilteringColumn><Operator><Value>', 
    '<Limit Results>', 
    ‘{ "autodrop_keyword": {"num_drops": 2},  "autodrop_vector":{"num_drops": 5 }}’
);

)

この場合、次のようになります。

"autodrop_keyword": {"num_drops": 2}
取得したキーワード検索結果を 2 番目の重要なスコアのカットオフポイントにドロップします。
"autodrop_vector":{"num_drops": 5 }
取得したベクトル検索結果を 5 番目の重要なカットオフポイントでドロップします。

ハイブリッド検索結果での自動ドロップには、次の構文を使用します。

select * from hybrid_search(
    table(<Search_index_DMO>), 
    ‘<Search String>’,
    '<PreFilteringColumn><Operator><Value>', 
    '<Limit Results>', 
    ‘{{ "autodrop_hybrid": {"num_drops": 1}}’
);

この場合、次のようになります。

{ "autodrop_hybrid": {"num_drops": 1}
最初の重要なスコアのカットオフポイントで結合されたハイブリッド検索結果をドロップします。

ベクトル検索クエリで品質検索条件を適用しない場合、検索では常に要求された結果 (topK 結果) の数が返されます。キーワード検索では、ドキュメントに含まれるクエリの用語のみに一致する結果が返されます。

例

たとえば、2 つのスコアドロップを含むキーワード検索結果スコアのシナリオを考えてみます。

  1. 結果 A: スコア 0.95
  2. 結果 B: スコア 0.92
  3. 結果 C: スコア 0.88
  4. 結果 D: スコア 0.40 - スコアの急減
  5. 結果 E: スコア 0.38
  6. 結果 F: スコア 0.35
  7. 結果 G: スコア 0.10 - スコアの急減
  8. 結果 H: スコア 0.80
  9. 結果 I: スコア 0.05

num-drops = 1 で「autodrop_keyword」を設定すると、ハイブリッド検索では結果 C の後の最初の重要なドロップ (0.88 ～ 0.40) が検出されます。ハイブリッド検索では、結果 D、E、F、G、H、I が最終検索結果から削除されます。検索クエリでは、結果 A、結果 B、結果 C が返されます。

「autodrop_keyword」を num_drops = 2 に設定した場合、ハイブリッド検索では結果 C の後の最初のドロップ (0.88 ～ 0.40) と結果 F の後の最初のドロップ (0.35 ～ 0.10) が検出されます。検索クエリでは、結果 G、H、I が削除され、結果 A ～ F が返されます。
