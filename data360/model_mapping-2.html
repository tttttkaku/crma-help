データモデルオブジェクト (DMO)

データモデルオブジェクト (DMO) を作成、表示、管理します。DMO は Data 360 の基本です。 DMO を作成または操作する前に、DMO に関連する定義、概念、リソースについてよく理解してください。

  • データモデルオブジェクトの表示
    Data 360 データモデルオブジェクトは、リストビューまたはグラフビューで表示できます。
  • カスタムデータモデルオブジェクトの作成
    標準データモデルオブジェクトがビジネスニーズを満たさない場合、カスタムデータモデルオブジェクト (DMO) を作成して、各自のビジネスに固有の情報を保存できます。カスタムデータモデルオブジェクトの作成は、既存の DMO、ファイル、またはゼロから行えます。
  • 既存のデータモデルオブジェクトからのカスタムデータモデルオブジェクトの作成
    カスタムデータモデルオブジェクト (DMO) を使用して、各自のビジネスに固有の情報を保存します。既存の標準またはカスタム DMO をコピーして、DMO を作成できます。
  • CSV ファイルからのカスタムデータモデルオブジェクトの作成
    カスタムデータモデルオブジェクト (DMO) を使用して、各自のビジネスに固有の情報を保存します。CSV ファイルをアップロードして、カスタム DMO を追加できます。
  • データモデルオブジェクトのプロパティの編集
    データモデルオブジェクト (DMO) のプロパティは、[データモデル] タブまたはデータマッピングページで編集できます。
  • データモデルオブジェクトのカテゴリの変更
    ほとんどの場合、データモデルオブジェクトのカテゴリはオブジェクトの作成後に変更できません。カテゴリは、セグメンテーションまたは有効化で使用されていないオブジェクトの [プロファイル] から [その他] または [その他] から [プロファイル] に変更している場合にのみ変更できます。
  • データモデルオブジェクトリレーション
    Data 360 データモデルオブジェクト (DMO) には、他の DMO との標準リレーションまたはカスタムリレーションを設定できます。リレーションは一対一リレーションまたは多対一リレーションとして構成できます。リレーションとその状況は DMO レコードの [リレーション] タブで表示できます。

Data 360 オブジェクトと項目の対応付けの管理

データモデルオブジェクト (DMO) またはデータレークオブジェクト (DLO) に関連付けられたオブジェクトと項目の対応付けを編集または削除します。マッピングとオブジェクトを管理して、データの正確性を確保し、データモデルの整合性を維持します。

必要なエディション

使用可能なエディション: Data 360 でサポートされるすべてのエディション。 「Data 360 Edition の可用性」を参照してください。
メモ DMO は、カスタムオブジェクトの場合にのみ削除できます。標準オブジェクトは削除できません。ごみ箱アイコンを使用して、DMO へのすべての項目のマッピングを削除したり、DMO を削除したりします。

次のシナリオでは、対応付けを削除できません。

  • 項目のマッピングの参照整合性チェックに失敗した場合。項目の対応付けを削除しようとすると、Data 360 で参照整合性チェックが実行されます。これにより、ID 解決、計算済みインサイト、セグメントなどの下流の連動関係が影響を受けなくなります。現在マッピングされている DMO 項目のいずれかで参照整合性チェックに失敗すると、その項目のマッピングを削除できません。
  • DMO 項目は 1 つの DLO ソースにのみ対応付けられます。最後の対応付けを削除すると、項目は空のままになります。カスタム DMO には少なくとも 1 つの有効な対応付けが必要なため、DMO 全体を削除する必要があります。
  • DLO は ID 解決調整ルールのソース優先度で使用されます。これらの調整ルールの連動関係を削除するまで、項目の対応付けを削除することはできません。
    重要 この連動関係は、エラーダイアログには表示されません。ID 解決調整ルール設定ページから手動で確認する必要があります。
  • 削除しようとしているマッピングに対応するフィールドが Data 360 Lightning ページで使用されています。まず、 Data 360 ページから項目を削除します。
    重要 この連動関係は、エラーダイアログには表示されません。Lightning ページ設定ツールを使用して手動で確認する必要があります。

オブジェクトの削除

[オブジェクトを削除(Delete Object)] オプションを選択すると、DMO にマッピングされているすべての DLO からフィールドのマッピングが削除され、DMO が削除されます。カスタムオブジェクトは完全に削除されますが、標準オブジェクトは無効状態になります。無効な標準オブジェクトは、引き続きシステムに存在し、項目が再度対応付けられると自動的に再有効化されます。

DMO に ID 解決、セグメント、計算済みインサイト、有効化などの下流連動関係がある場合、このオプションは使用できません。オブジェクトを削除する前に、すべての連動関係を削除する必要があります。

1 つの DLO から少なくとも 1 つの DMO フィールドがマッピングされている場合、[マッピングを削除] ボタンは使用できません。この場合、オブジェクトを完全に削除できます。

連動関係のあるオブジェクトの削除

連動関係のある DMO を削除しようとすると、Data 360 には最初に削除する必要がある連動関係が表示されます。この整合性チェックは、DMO だけでなく、DMO 項目ごとに実行されます。DMO を使用するデータストリームを表示することもできますが、データストリームによってオブジェクトの削除が妨げられるわけではありません。連動関係リストを確認した後、DMO へのマッピングから現在の DLO の関連付けを解除し、オブジェクトは削除しない場合は、[オブジェクトを削除] ではなく [マッピングを削除] をクリックします。

  1. プロファイル DMO を削除するには、DMO に関連するすべてのセグメントを削除します。
  2. Data 360 によって作成された、関連付けられたセグメントメンバーシップ DMO を削除します。 [データモデル] タブに移動し、[リストビュー] を [対応付け済み] から [すべて] に変更します。
  3. 削除するプロファイル DMO の名前を検索します。次に、関連付けられた両方のセグメントメンバーシップ DMO を削除します。
  4. プロファイル DMO を削除します。

項目の対応付けの置換

DMO 項目と同じデータ型の別の DLO 項目に対応付けることができます。

メモ Developer Edition または Sandbox 組織では、項目の対応付けを置き換えることはできません。
  1. マッピングする新しい DLO 項目と DMO 項目を選択します。新しい対応付けで古い対応付けが上書きされます。たとえば、誤ってマッピングされた DLO 項目「姓」を「名」に置き換えて、同じ DMO 項目にすることができます。
  2. 連動機能を確認して、DMO 項目が正しいデータを受信することを確認します。

データオブジェクトの完全修飾キー

Data 360では、キー修飾子フィールドがDLO(データ レイク オブジェクト)とDMO(データ モデル オブジェクト)に追加されます。キー修飾子項目は、DLO と DMO 間のオブジェクトリレーションとオブジェクトマッピングを作成するときにも追加できます。

DLO のキー修飾子項目

Data 360 では、プライマリキーまたは外部キーのいずれかを含む DLO フィールドにキー修飾子フィールドが追加されます。キー修飾子項目に保存されるデフォルト値は null です。プライマリキーまたは外部キーのいずれかが含まれる各 DLO 項目にキー修飾子を作成、設定する必要があります。

DLO のプライマリキー項目は、DLO が作成されたときに決定されます。Data 360 は、DLO フィールドが DMO フィールドにマッピングされ、DMO フィールドがオブジェクトリレーションに含まれる場合に、DLO フィールドが外部キーフィールドであると判断します。

Data 360 では、DLO と DMO キー修飾子項目間の項目マッピングも追加されます。このマッピングは内部的に管理され、項目マッピングページには表示されません。

DMO のキー修飾子項目

Data 360 は、DMO の各プライマリ キー フィールドとオブジェクト リレーションに関与する各 DMO フィールドにキー修飾子フィールドを追加します。ただし、特定の DMO 項目が含まれているリレーションの数に関係なく、その項目に設定されるキー修飾子項目は 1 つのみです。

新しい DMO が作成されると、キー修飾子項目が DMO のプライマリキー項目に自動的に追加されます。新しいオブジェクトリレーションが有効化されるときに、オブジェクトリレーションでリンクされている DMO 項目に対応するキー修飾子項目がない場合、その DMO にキー修飾子項目を追加できます。キー修飾子項目とその関連付けられた DMO 項目は、DMO レコードホームページの [キー修飾子] 列に表示されます。

完全修飾キーはソース提供キーとキー修飾子で構成されるため、DMO リレーションではキー項目とキー修飾子項目で構成される複合キーも使用されます。DMO レコードホームページのオブジェクトリレーション概要ビューには、各オブジェクトリレーションに含まれるキー修飾子項目が表示されます。

Data 360 データモデルオブジェクトの有効化

データモデルオブジェクト (DMO) を有効化して、さまざまなソースのデータを使用して完全な顧客プロファイルを作成します。この機能は、すぐにアクション可能な形式でデータを表示し、パーソナライズされたカスタマーエクスペリエンスを促進します。Data 360 では、ストリーミングとバッチの 2 つの方法で DMO を有効化できます。それぞれは、さまざまな使用事例や対象に合わせて設計されています。

ストリーミング DMO の有効化

ストリーミングの有効化は、ほぼリアルタイムの使用事例に合わせて設計されており、イベントが発生したときにデータを宛先に送信します。

標準イベントとカスタムイベント

ストリーミング有効化を作成するときに、標準またはカスタムイベントを使用できます。

  • 標準イベント — これらは対象プラットフォーム (Meta CAPI など) によって事前定義されます。必要なすべての属性と値が自動的に含まれます。これは、初めて使用するユーザーに推奨される方法です。
  • カスタムイベント — カスタムイベントを作成し、よりカスタマイズされた有効化環境を提供する属性のみを追加します。

データグラフを使用したアクティベーション メンバーシップのフィルタリング

ストリーミング DMO 有効化で有効化メンバーシップに検索条件を追加する場合、絞り込みに使用できる DMO は、有効化でデータグラフが使用されているかどうかによって異なります。

  • データグラフがない場合、有効化された DMO の属性のみを有効化メンバーシップの絞り込みに使用できます。
  • 有効化でデータグラフが使用されている場合、有効化された DMO から最大 2 ホップ離れたそのデータグラフに含まれる DMO の属性で絞り込むことができます。
メモ

既存の DMO 有効化はコピーできません。ただし、有効化の終了日は編集および更新できます。

一括 DMO の有効化

分析、アーカイブ、または大規模なマーケティングキャンペーンで完全なデータセットを送信する必要がある場合は、一括有効化を使用します。一般的なシナリオは次のとおりです。

  • ビジネスインテリジェンスのために完全な顧客プロファイルテーブルをデータウェアハウスにエクスポートする。
  • 商品のおすすめやパーソナライズされた属性の大規模で包括的なリストを Marketing Cloud Engagement に送信する。
  • コンプライアンスまたはレコード管理のために、DMO の完全なスナップショットを安全な SFTP 場所にアーカイブする。

考慮事項

  • 外部 DMO が高速化されている場合は有効化できます。Bring Your Own Lake (BYOL) シナリオでは、加速 DMO のみがサポートされます。非加速外部 DMO はサポートされません。
  • 一括 DMO 有効化では、プロファイル、エンゲージメント、その他の DMO 種別がサポートされます。オーディエンス DMO と特定のシステム生成 DMO には使用できません。
  • 一括セグメント有効化とは異なり、現時点では UI で一括 DMO 有効化のカスタムスケジュールを設定するオプションはありません。
  • エンゲージメント DMO を有効化する場合、有効化ペイロードには過去 90 日間のレコードのみが含まれます。エンゲージメントレコードの履歴全体が送信されるわけではありません。
  • 標準イベントを使用した DMO の有効化の作成
    標準イベントを使用して Data Cloud で有効化を作成すると、データモデルオブジェクト (DMO) の必須属性が自動的に追加されます。DMOS の有効化は、Meta Conversion API プラットフォームでサポートされています。
  • カスタムイベントを使用した DMO の有効化の作成
    カスタムイベントを使用して Data 360 で DMO アクティベーションを作成する場合、カスタマイズされたアクティベーション環境に必要な属性を追加します。DMO の有効化は、Meta Conversion API プラットフォームでサポートされています。
  • Data 360 での一括 DMO 有効化の作成
    一括 DMO 有効化を作成して、データモデルオブジェクト (DMO) 全体をエクスポートします。公開前にレコードの絞り込み、属性の追加、利用者のランク付けを行って有効化を設定する方法について説明します。

既存のデータレークオブジェクトを使用したデータストリームの作成

S3、Google Cloud Storage、または SFTP データストリームを作成するときに、既存のデータレークオブジェクト (DLO) を使用できます。DLO を最初に作成したデータストリームによって、プライマリキー、行動日時、レコード変更済み項目などの特性が定義されます。新しいデータストリームの項目を既存の DLO 項目にどのように適合させるかを伝えることができます。

既存の DLO を使用してデータストリームを作成するときは、次の点に留意してください。

  • 他のソースですでに使用されている DLO は使用できません。
  • すべてのデータストリーム項目を取り込みます。各自のデータストリーム項目に対応する項目が DLO にない場合、[データレークオブジェクト] タブで DLO を拡張できます。
  • データストリーム項目のデータ型が DLO の取得先項目と同じでなければなりません。ドロップダウンに DLO 項目が見つからない場合、データ型が一致していないか DLO 項目が別のデータストリーム項目で使用されています。
  • データストリーム項目を DLO のプライマリキーに割り当てます。
  • DLO がエンゲージメントカテゴリに該当する場合は、データストリーム項目を DLO の行動日時に割り当てる必要があります。
  • DLO がプロファイルカテゴリに該当し、DLO で以前にレコード変更済み項目が宣言されている場合は、データストリーム項目を割り当てる必要があります。レコード変更済み項目が割り当てられたことがない場合は、データストリームの設定中にレコード変更済み項目を設定できます。
  • DLO で以前に組織単位識別子が宣言されている場合は、データストリーム項目を割り当てます。割り当てられたことがない場合は、データストリームの設定中に設定できます。

コンテンツとKnowledgeのハーモナイゼーション

ハーモナイゼーションを使用して、取り込まれたKnowledge記事と非構造化コンテンツを Data 360 に変換します。 ハーモナイゼーションにより、コンテンツが正規化および強化され、コンテンツビューアーでの一貫した表示に適した 1 つのハーモナイゼーションスキーマが作成されます。ビューアには、Data 360 のデータエクスプローラーまたは Service Cloud の Enterprise Knowledge コンポーネントからアクセスします。

必要なエディション

使用可能なエディション: Data 360 でサポートされるすべてのエディション。 「Data 360 Edition の可用性」を参照してください。

ハーモナイゼーション ダッシュボードには、ハーモナイゼーションされたすべてのコンテンツのレコードが含まれます。各レコードから、コンテンツビューアーでハーモナイズされたコンテンツを表示できます。次の 2 つの方法で閲覧者にアクセスします。

  • Data 360 から: Data 360 の [データエクスプローラー] タブのコンテンツビューアでハーモナイズされたファイルを表示します。

  • サービスコンソールから:<サービスコンソールのEnterprise KnowledgeコンポーネントでSalesforce Knowledgeを表示します。一貫したハーモナイズコンテンツにより、サービス担当者はサービスコンソールから離れることなく、関連する完全なドキュメントを確認し、より多くのコンテンツを探索できます。「Get Started with Enterprise Knowledge (Enterprise Knowledge の使用開始) (ベータ)」を参照してください。

請求に関する考慮事項

データハーモナイゼーションと表示は、次の領域でのクレジット消費に影響する可能性があります。

  • データパイプラインと取り込み: Data 360 は、すべての取り込み中に処理されたレコード数に基づいて使用量を計算します。増分取り込みの場合、Data 360 は新規または更新されたファイルのみを処理します。コンテンツ閲覧者エンゲージメントテレメトリの場合、イベントは別のデータストリームとして処理行として計数されます。

  • データのハーモナイゼーションと処理: 検索インデックスを作成または更新すると、Data 360 は処理されたデータ量 (MB) に基づいて使用量を計算します。

  • データクエリ: インデックスに対するすべての検索アクションでデータクエリがトリガーされ、消費として計数されます。検索をトリガーする Agentforce 会話のすべての質問がデータクエリとして計数されます。ページを表示するすべての要求は消費とみなされます。

  • データストレージ: これらの操作はストレージに含まれます。

    • ファイルの取り込み

    • データレイクオブジェクト (DLO)、データモデルオブジェクト (DMO)、ハーモナイズ DLO、ハーモナイズ DMO、エンゲージメントテレメトリ DLO などのテーブルの作成。

    • チャンク生成とインデックス DMO。これは、非構造化データを使用してベクトルインデックスまたはハイブリッドインデックスを作成するときに発生します。

    • 文字起こし DMO (Data 360 で音声ファイルと動画ファイルが処理される場合)。

  • LLM ゲートウェイは、要求と応答のトークン数に基づいて AI 強化を要求します。Salesforce では、これらのコールを標準 Flex クレジットまたは標準 Einstein 要求として数えます。この要求は、ハーモナイズ DMO (HDMO) が AI 強化 (特に Q&A 概要と FAQ の生成) のためにファイルを LLM に送信するときに発生します。

完全修飾キーのベストプラクティス

完全修飾キー (FQK) を使用して、さまざまなデータソースから取り込まれたデータを Data 360 で正確に解釈できるようにします。

FQK を使用する場合は、次のベストプラクティスに従ってください。

  • キー修飾子項目を設定します。
    • キー値 (プライマリまたは外部) が含まれるすべてのデータレークオブジェクト (DLO) 項目のキー修飾子項目を設定します。
    • 同じデータモデルオブジェクト (DMO) 項目にマッピングされている複数の DLO の項目の場合、すべての DLO 項目にキー修飾子項目が必要です。
  • null セーフ結合を使用します。
    • Data Cloud クエリ SQL では、null 値を処理してデータの損失を防ぐために、すべてのテーブル結合のキー修飾子項目で COALESCE() を使用します。
    • Tableau では、テーブル結合およびアドホックテーブル結合のキー修飾子項目で IFNULL() を使用します。
  • 既存の組織で FQK を有効にする場合、既存の計算済みインサイトを更新して、キー修飾子項目をテーブル結合とディメンションに追加します。
  • 計算済みインサイトを作成するときに、テーブル結合およびディメンションでキー修飾子項目を使用してデータの精度を確保します。キー修飾子フィールドを使用すると、セグメントおよびアクティベーションで他の DMO と組み合わせると、Data 360 でインサイトが正しく解釈されます。

この例では、取引先責任者および SFMC 登録者 DLO のプライマリキー項目が同じ DMO 項目 Individual.Id にマッピングされています。そのため、両方の DLO 項目でキー修飾子項目が設定されている必要があります。

データモデルオブジェクトのマッピング

データマッピングにより、データレークオブジェクト (DLO) 項目がデータモデルオブジェクト (DMO) 項目に関連付けられ、ソースデータを 1 つの標準化された Customer 360 データモデルに統合できます。

必要なエディション

使用可能なインターフェース: Lightning Experience
メモ
  • DLO は 1 つ以上の DMO にマッピングできます。
  • DMO 項目にマッピングできる DLO 項目は 1 つのみです。1 つの DMO 項目に複数のソース DLO 項目を設定することはできません。
  • DLO 項目は同じ DMO の複数の DMO 項目にマッピングできます。
警告 カスタム DMO のオブジェクト API 参照名が標準 DMO と同じ場合:
  • 標準 DMO に項目の対応付けがある場合も、既存の対応付けを編集できます。ただし、すべてのマッピングが削除されて DMO を保存すると、DLO をこの標準 DMO にマッピングできなくなります。
  • 標準 DMO に項目の対応付けがない場合、DLO をこの標準 DMO に対応付けることはできません。

組織 ID の対応付け

内部組織 ID は、一般に Salesforce.com 組織 ID または単に組織 ID と呼ばれます。これは、データレコードを所有するビジネスユニットまたはその他の内部組織への参照 ID であり、すべての標準 DMO の標準監査項目です。ただし、この参照 ID 値は CRM コネクタによって入力されません。

  • CRM ソースの内部組織 ID は自動的に対応付けられません。
    • また、CRM 接続組織またはリモート組織にもマッピングされません。
    • 他のソースの場合は、サブ範囲またはテナント ID であり、照会または検索できます。
  • [データソース] と [データソースオブジェクト] はシステム項目であり、対応付けはシステムで管理されます。
    • ホーム組織の場合:
      • データソースの静的値は「Salesforce_Home」で、クエリや検索ができます。
      • データソースオブジェクトは、取得元オブジェクト名の値を取得し、照会または検索できます。
    • 接続組織またはリモート組織の場合:
      • データソースは「Salesforce_{OrgId}」の静的値を取得し、クエリまたは検索できます。
      • データソースオブジェクトには取得元オブジェクト名の値があり、クエリまたは検索できます。

ロイヤルティ状況の SMS キャンペーンのオーディエンスセグメントを作成して有効化します。

オーディエンスセグメントの作成

  1. Data 360 にログインします。
  2. [セグメント] タブで [新規] をクリックします。
  3. 新しいオーディエンスセグメントを基盤にするには、統合個人 DMO を選択します。
  4. セグメントに「SMS Loyalty Campaign」(SMS ロイヤルティキャンペーン) という名前を付けて説明を追加し、24 時間の公開スケジュールを選択します。
  5. 開始日時と有効期限を追加して、[保存] をクリックします。
  6. 関連属性リストから、[ロイヤルティプログラムメンバー] を選択し、[ロイヤルティプログラムランク] を選択します。
  7. [Loyalty Member Tier Change (ロイヤルティメンバーランク変更)] 属性をキャンバスにドラッグします。
  8. [集計] を [件数]、[演算子] を [以上]、[値] を [1] に設定します。 
  9. [属性] で、[演算子] を [次の値と等しい] に設定し、[値] を true の [T] に設定します。
  10. [完了] をクリックして、[保存] をクリックします。

Data 360 のデータマッピング要件

マッピングとリレーションは、標準データバンドルを使用してリリースされるデータストリームに対してのみ自動的に設定されます。一方、カスタムデータストリームの場合は必要なマッピングとリレーションが適切に設定されるようにする必要があります。

  • [プロファイル] または [その他] カテゴリでデータモデルオブジェクト (DMO) をマッピングする場合、主キー項目をマッピングする必要があります。データマッピングは、主キーをマッピングした後にのみ保存できます。
  • [エンゲージメント] カテゴリで DMO をマッピングする場合、主キー項目とイベントの dateTime 項目をマッピングする必要があります。両方の項目をマッピングした後にのみマッピングを保存できます。
  • ID 解決、セグメンテーション、有効化を使用するには、関係者領域データの必須の項目とリレーションをマッピングします。関係者領域のエンティティリレーションダイアグラム (ERD) を使用して、マッピングを計画できます。データストリームで個人オブジェクトと連絡先または関係者 ID オブジェクトのいずれかをマッピングする必要もあります。
  • データモデル内の他のオブジェクトの個人オブジェクトへの参照は、関係者属性を通じて行われます。これを Individual.Id 属性にリンクする外部キーリレーションと考えてください。関係者エンティティリレーションダイアグラムでは、各連絡先 <チャネル> オブジェクトと並んでいる関係者 ID にその参照があります。属性に関しては、関係者 = Individual.Id の場合、紛らわしくなることがあります。
  • 統合および有効化プロセスを機能させるには、少なくとも 1 つの連絡先 <チャネル> 属性をマッピングします。

    連絡先 <チャネル> オブジェクトには、メールアドレスや電話番号など、個人に関する詳細が含まれます。連絡先がない場合、顧客にエンゲージするための連絡先の詳細がないため、有効化を実行できません。

  • 関係者 ID オブジェクトは、多くの顧客レコードを一緒に関連付けることができるサードパーティ識別子のセット (ロイヤルティカード番号、運転免許証番号など) を表します。同じ関係者 ID 種別と ID 名の値の場合、Data 360 は同じ ID 番号のレコードに一致します。
  • 有効化ツールキットを使用する JSON ベースの外部有効化プラットフォームにデジタル識別子を有効化するには、連絡先デジタル ID オブジェクトを対応付けます。この対応付けは、有効化プラットフォームが UID2 や RampID などの特定のデジタル識別子に依存している場合に必須です。有効化の対象がメールまたは電話ベースの通知先 (連絡先メールまたは連絡先電話を使用) のみの場合、この対応付けは省略可能です。詳細は、「JSON ベースの外部有効化対象の取り込みおよびモデルデジタル識別子」を参照してください。

セマンティックモデル内のデータの構造化

Tableau Semantics では、Data 360 または Tableau Next のセマンティックモデルビルダーを使用してセマンティックモデルを作成および変更できます。

  • Tableau セマンティックでのデータオブジェクトの管理
    データオブジェクトには属性と項目が含まれます。セマンティックモデルのデータオブジェクトを追加、編集、削除できます。
  • Tableau Next での意味モデル内のリレーションの作成
    人工知能 (AI) を使用して、Tableau Semantics でリレーションの提案を取得してリレーションを作成できます。提案は、モデルに追加されたセマンティックオブジェクトとサンプルデータに基づきます。

セマンティックモデルの作成

セマンティックモデルは、Data 360、Tableau Next、およびインテリジェントアプリケーション全体で統合され、分析とデータ主導のエクスペリエンスを強化する、最初の Salesforce メタデータです。セマンティックモデルには、特定の分析使用事例に合わせて調整された定義が含まれます。モデルには 1 つ以上のデータオブジェクトを含めることができます。オブジェクト間で柔軟な結合と結合を作成し、計算されたディメンションと基準を使用して分析を強化できます。

  • Data 360 での意味モデルの作成
    セマンティックモデルを作成して、Data 360 から直接特定のビジネスニーズに対応します。セマンティックモデルを作成するには、最初から作成する、既存のセマンティックモデルを拡張する、Data 360 データキットを使用して作成するの 3 つの方法があります。
  • Tableau Next での意味モデルの作成
    Tableau Next 内の Tableau Semantics では、セマンティックモデルを作成し、そのモデルに基づいて評価指標を作成できます。セマンティックモデルを使用して、視覚化の計算項目を作成することもできます。
  • Open Semantic Interchange (OSI) からの意味モデルの作成
    Tableau Semantics は、さまざまなプラットフォームやツールでセマンティックモデルを共有するためのオープンソース標準である Open Semantic Interchange (OSI) をサポートしています。

Tableau セマンティックでの意味モデルへのアクセスの管理

セマンティックモデルを特定のユーザーまたは組織全体と共有して、参照または編集できるユーザーを制御します。セマンティックモデルはデフォルトで非公開ですが、[共有] オプションを使用してアクセス権を管理し、閲覧者やエディターなどのアクセスロールを割り当てることができます。

セマンティックモデルで使用できるアクセスロールは 3 つあります。

  • 閲覧者: ユーザーはモデルを開いて操作できますが、変更はできません。
  • エディター: ユーザーにはモデルを変更する権限があります。
  • Owner (所有者): セマンティックモデルを最初に作成したユーザーがフルコントロールできます。所有者は、他のユーザーと共有することで、モデルを編集し、アクセス権を管理できます。閲覧者またはエディターのアクセスロールを他のユーザーに割り当てることはできますが、所有権を移行することはできません。

セマンティックモデルは組織内の任意のユーザーと共有できますが、モデルが存在するデータスペースにアクセスできるユーザーにのみ表示されます。これらのユーザーには、オブジェクトレベルのセマンティックモデル権限を含め、セマンティックモデルを表示するための適切な権限も必要です。

モデルを共有しても、ユーザーの既存の権限は上書きされません。たとえば、ユーザーにセマンティックモデルを編集する権限がない場合、ユーザーにエディターロールを割り当てても、共有モデルは編集できません。同様に、ユーザーにグローバル編集権限があり、そのユーザーにモデルの閲覧者ロールを割り当てた場合、ユーザーは参照のみが可能です。

基礎となるデータへのアクセス権がない場合、ユーザーはモデルを開いて表示または拡張できますが、編集はできません。

唯一の例外は、「すべて変更」または「すべて表示」権限を持つユーザー (通常はシステム管理者) に適用されます。これらのユーザーはモデルを開いて、制限されたオブジェクトを含む完全なメタデータにアクセスできます。また、所有者でなくても、「すべてのレコードの編集」権限がある場合は、セマンティックモデルを共有できます。ただし、アクセス権のない項目やエンティティを使用してモデルをプレビューまたはテストしようとすると、クエリが失敗する可能性があります。

  • Tableau セマンティックでの意味モデルの共有
    Tableau Semantics で他のユーザーとセマンティックモデルを共有してアクセス権を付与します。モデルを個々のユーザーと共有することも、組織のすべてのユーザーが使用できるように一般的なアクセス権を設定することもできます。
  • Tableau セマンティックでのセマンティックモデルへのアクセスの削除
    ユーザーが Tableau Semantics でセマンティックモデルを表示または編集できないように、セマンティックモデルへのアクセス権を削除します。個々のユーザーのアクセス権を削除し、個別に追加されたユーザーのみがアクセスできるようにモデルの一般的なアクセス権を制限できます。
  • Tableau セマンティックでの意味モデルへのリンクのコピー
    セマンティックモデルへのリンクを取得し、モデルを表示または編集するアクセス権を持つユーザーと共有します。

    構成モデルを作成すると、構成モデルは参照されるモデルからすべてのプロパティ定義を継承します。プロパティ定義を変更すると、新しい定義が上書きとして定義されます。上書きされたプロパティ定義は、参照されるモデルに接続されません。そのため、参照されるモデルが更新されても、上書きされたプロパティ定義は変更されません。一方、上書きのないプロパティは、参照されるモデルデータソースに接続したままで、データソースから更新を受信し、データソースとして保持します。元の値に戻す場合は、いつでも上書きを元に戻して自動更新を再開できます。
