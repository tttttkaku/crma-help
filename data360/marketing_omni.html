使用可能なエディション: Data 360 でサポートされるすべてのエディション。 「Data 360 Edition の可用性」を参照してください。

ソースの優先順序

ソースの優先順序を使用して、複数の値を使用可能な場合に有効化で選択される連絡先値を決定します。また、複数のソースのデータがあるセグメントメンバーに選択される連絡先値を並び替えます。ソースを追加、並び替え、削除して、優先度を変更できます。

ID 解決でソースデータを統合した後、すべての連絡先は統合個人 DMO の一部のままです。ID 解決の調整ルールでは、統合連絡先オブジェクトではなく統合個人オブジェクトの項目のみが調整されます。ソースの優先度を使用して、調整ルールに関係なく、目的のデータソースの連絡先を有効化対象に確実に提供します。[メール種別] で [いずれか] を選択していない場合、連絡先が一致するには、対応する連絡先 DMO で [主フラグ] がマッピングされている必要があります。

値 説明
主 データストリームで [主フラグ] 項目がマッピングされている場合、[主] がオプションとして表示されます。
いずれか [主フラグ] 項目がマッピングされていない場合、有効化では使用可能ないずれかのソースから連絡先値が取得されます。
個人 データストリームで [個人用途] 項目がマッピングされている場合、[個人] がオプションとして表示されます。[個人用途] 項目の値は 1 である必要があります。
ビジネス データストリームで [ビジネス用途] 項目がマッピングされている場合、[ビジネス] がオプションとして表示されます。[ビジネス用途] 項目の値は 1 である必要があります。

有効化で特定のソースの値のみを使用するには、ソースの優先順序のいずれかのソースといずれかの種別を削除します。値を選択するデータソースが少なくなるため、有効化の母集団数も少なくなることが期待されます。

プラットフォームごとにデフォルトのソースの優先順序があります。外部プラットフォームの場合、プラットフォームの作成者がデフォルトのソースの優先順序を決定します。B2C Commerce Cloud と MobilePush では、デフォルトのソースの優先順序は常に同じままであり、変更できません。

Marketing Cloud Engagement 更新モード

Marketing Cloud EngagementからData 360にデータを取り込む場合、更新モードは更新/挿入またはフル更新のいずれかになります。それぞれのモードでデータの処理方法が異なります。

更新/挿入モード

データストリームが更新/挿入モードで作成されている場合、更新ごとに新しい情報が追加され、古い情報は維持されます。

フル更新

データストリームがフル更新モードで作成されている場合、データは更新サイクルごとに新しいインポートデータと置き換えられます。取引先責任者が新しい取り込みのリストに含まれていない場合は削除できます。Data 360 データから削除する連絡先のみをソースから削除することをお勧めします。

データ基盤に関する考慮事項とベストプラクティス

一般に、データ基盤の個人部分はできるだけ使用することをお勧めします。データ基盤の統合個人部分からのコンテンツのパーソナライズまたは判断属性を使用するジャーニーを実行する場合は、次の考慮事項とベストプラクティスに留意してください。

人に関する誤ったコンテキストの使用

統合個人は、さまざまな外部データソースからインポートされた別々の個人を関連付けることで作成されます。インポートプロセスの一部として、名などのインポート済み項目によっては、各データソースから異なる値を使用できます。顧客は ID 解決の一環として調整ルールを定義し、Marketing Cloud Engagement に対して利用者を有効化するときに使用するデータソース値に優先順位を付けます。

調整ルールによって、誤ったコンテキストを使用してメッセージが送信されることがあります。たとえば、ある人が自宅用にギフトを購入し、その人の個人用メールに確認メールが送信されるとします。ただし、メールコンテンツは、誤った納入先住所でパーソナライズされています (自宅住所ではなく、勤務先の納入先住所が使用されている)。

  • Cumulus内の各ブランドには異なる外部システムがあり、それぞれがData 360にデータをインポートします。John Smith という人物が同社のブランド A の Cumulus メールニュースレターにサインアップしました。それとは別に、その後 John Smith はブランド B にサインアップし、最終的にモバイルアプリケーションでブランド C にもサインアップしました。
  • John Smith の統合個人には、3 つの異なるシステムから「John.Smith.1」(ブランド A のシステム A)、「John.Smith.2」(ブランド B のシステム B)、および「John.Smith.3」(ブランド C のシステム C) という 3 つの別々の個人が含まれることになります。各システムによって、John Smith の氏名、連絡先、連絡先設定、生涯価値、ロイヤルティレベルの異なる値がインポートされます。
  • 有効化の一環として使用される値に優先順位を付けるために、Cumulus は調整ルールを作成して、Data 360 が共有フィールドから値を選択する方法を定義する必要があります。この例では、Cumulus は、システム A (ブランド A) からのメールアドレス、システム C (ブランド C) からの氏名値、システム A (ブランド A) からの連絡先設定、生涯価値とロイヤルティレベルの最近更新されたシステム値 (システム A、B または C) を優先することを選択します。

人に関するデータの欠落

Data 360 は、個人レベルと統合個人レベルの両方で有効化できます。個人レベルでは、人の各インスタンスは各データソースから有効化されます。これに対し、統合個人レベルでは複数のデータソースの情報が使用されます。統合個人を使用している場合、Data 360 は関連する個人の 1 つから 1 つの識別子を選択します。ただし、データ基盤内で人を表すために使用される識別子は、後続のジャーニーでその人に使用される識別子とは異なる場合があります。結果として、判断分割などのジャーニーのルックアップでは、データ基盤の統合個人部分の人に関するデータを検索できない可能性があります。このシナリオは、サードパーティからトリガーされるイベントベースのジャーニーでよく発生し、多くの場合、データ基盤で統合個人を表すためにどの識別子が使用されるのかを示すコンテキストがありません。ただし、このシナリオは利用者ベースのジャーニーでも発生することがあります。

Data 360 のデータを使用した Marketing Cloud Engagement でのデータ基盤の実装

外部システムのデータを Marketing Cloud Engagement に対して有効化し、エンゲージメント連絡先モデルにリンクすることで、データ基盤を確立できます。さらに、このデータを Journey Builder 全体で更新して再利用し、ジャーニーの判断、待機活動、終了を行うことができます。イベントトリガーキャンペーンのコンテンツパーソナライズにデータを使用することもできます。このソリューション キットでは、Data 360を使用してデータ基盤を設定する方法に関する一般的なブループリントを提供します。

このソリューションキットを使用することで、マーケット担当者の効率とエンドツーエンドのスケールパフォーマンスの両方が最大化され、意図しない請求消費が発生する可能性を低減できます。

すべてのキャンペーンでデータ基盤を実装する必要があるわけではありません。一括送信、Transactional メッセージ、判断分岐に Engagement 連絡先モデルを使用しないジャーニーなどでは必要ありません。

キャンペーンでジャーニーをトリガーする場合は、これらの設定を考慮します。Engagement でデータエクステンションを作成するときは、種別としてメールを使用します。Data Cloud では、メール種別が存在しないため、項目はテキストです。Engagement にない連絡先にジャーニーで送信する場合は、Journey Builder 設定を使用して任意のソースのメールを使用します。

Data 360とMarketing Cloud Engagementを統合する場合、各製品の役割と責任を明確に示します。Data 360は、データの取り込み、解決、変換、セグメント化、強化を目的として設計されています。Marketing Cloud Engagement は、パーソナライズされたメッセージングキャンペーンを調整するエンゲージメント製品です。

Engagement 連絡先モデルで作成するデータ基盤を詳しく確認することをお勧めします。Engagement でデータが無秩序に増えないようにしながら、マーケット担当者の効率をバランスよく高めるには、一般的な共有データセットを選択的に統合する初期データ基盤をお勧めします。この基盤を使用して、さまざまな Journey Builder の使用事例でコンテンツのパーソナライズや判断を行うことができます。

Marketing Cloud Engagement データ基盤に必要なデータについて

Engagement のデータ基盤には、ジャーニー全体で使用する更新されたデータが保存されます。利用者ベースのジャーニーでは、データ基盤を高速判断に使用しますが、通常はコンテンツのパーソナライズには使用しません。ただし、イベントトリガージャーニーでは、データ基盤を高速判断とコンテンツのパーソナライズの両方に使用できます。

メモ デフォルトでは、イベントトリガージャーニーではコンテンツのパーソナライズにジャーニーデータを使用します。多くの場合、これでトランザクションジャーニーや短期間のジャーニーの使用事例に十分に対応できます。より複雑なキャンペーンや複数日数のキャンペーンにイベントトリガージャーニーを使用する場合、コンテンツのパーソナライズには更新されたデータを使用します。このようなジャーニーでは、データ基盤の連絡先データを使用することをお勧めします。

Marketing Cloud データ基礎で組織に必要なパーソナライズ属性を判断するには、データスペシャリストとマーケット担当者が参加して、このような担当者が実行したいキャンペーンやジャーニーを自ら確認する必要があります。まずは、コンテンツのパーソナライゼーションによく使用される属性の初期セットから始めます。この属性セットはイベントトリガージャーニー専用です。次に、すべてのジャーニーの判断でよく使用される属性の初期セットをお勧めします。始めるにあたり、属性の包括的なリストは必要ありません。より多くのキャンペーンを立ち上げて実装を進めていく中で、データ基盤を調整して、さらに属性を追加することができます。

メモ パフォーマンス上と機能上の両方の理由で、ジャーニーの判断、待機、終了のために関連属性を有効化してデータ基盤に保存することはお勧めしません。代わりに、関連属性を計算済みインサイトに変換することをお勧めします。

個人属性と統合個人属性

ジャーニーの判断に使用されるメッセージや同意属性をパーソナライズするための個人を特定できる情報などの機密情報については、個人レベルで属性を有効化することをお勧めします。このアクションにより、特定の個人の有効化された連絡先に関するデータの正しいコンテキストがデータ基盤に常に含まれるようなります。

例: John Smith には、John.Smith.1、John.Smith.2、John.Smith.3 の 3 つの個人プロファイルがあります。各プロファイルは、氏名が少し異なる John Smith、John Smith Jr.、John Smith の Data 360 にインポートされ、それぞれに一意のメールアドレス (js@example1.com、js@example2.com、js@example3.com) があります。生涯価値はそれぞれ $20、$30、$50、ロイヤルティレベルはブロンズ、シルバー、ゴールドです。

John Smith の 3 つの表現をすべて 1 つのデータエクステンションに追加するには、Data 360 を使用して個人レベルでセグメント化および有効化します。結果データエクステンションは 3 行になり、各属性がそれぞれの個人プロファイルから直接選択されます。

ジャーニーの判断に使用される集計情報の場合、統合個人レベルで属性を有効化します。この有効化では、より大きな統合個人プロファイル全体で収集されたデータに基づいて、人を再対象設定できます。

例: John Smith には、John.Smith.1、John.Smith.2、John.Smith.3 の 3 つの個別のプロファイルがあります。各プロファイルは、氏名が少し異なる John Smith、John Smith Jr.、John Smith の Data 360 にインポートされ、それぞれに一意のメールアドレス (js@example1.com、js@example2.com、js@example3.com) があります。生涯価値はそれぞれ $20、$30、$50、ロイヤルティレベルはブロンズ、シルバー、ゴールドです。

John Smith の 3 つの表現の一部を 1 つのデータエクステンションに追加するには、Data 360 を使用して統合個人レベルでセグメント化および有効化します。結果データエクステンションは 1 行になり、各属性が 3 つの個人プロファイルのいずれかから選択されるか、またはこのプロファイル全体で集計されます。たとえば、個人 ID: John.Smith.1、氏名: John Smith Jr.、メールアドレス: js@example1.com、生涯価値: $100、ロイヤルティレベル: ゴールドとなります。

データ基盤の関連用語

データ基盤を作成するときに知っておく必要がある用語を説明します。

Data 360 の用語

  • 有効化: セグメントを有効化プラットフォーム (対象) に公開するプロセス。
  • 有効化対象: 有効化中にセグメントのデータが送信される場所 (認証および承認情報を含む) (広告プラットフォームや Marketing Cloud Engagement など)。
  • 属性: データモデルオブジェクト (DMO) などのオブジェクトにある情報またはデータ。Data 360 のセグメンテーションには、次の 2 種類の属性があります。
    • 直接属性 (1:1): データモデルオブジェクトの直接リレーションを持つ属性。つまり、ユーザーに 1 つの値のみが設定されます (郵便番号や名など)。 
    • 関連属性 (1:N): 1 対多 (1:N) リレーションを持つ属性。つまり、特定のユーザーの属性ごとに複数の値が設定される可能性があります (購入、メールイベントなど)。
  • 個人: 個人プロファイルは、Marketing Cloud Engagement の SubscriberKey など、外部システムの個人のインスタンスを表します。人物の各インスタンスをデータエクステンションに取り込むには、個人レベルでオーディエンスをセグメント化して有効化します。
  • セグメント: 一連の特性を共有するデータがグループ化されたもの (たとえば、誕生日が同じ顧客)。
  • 統合個人: 1 つの統合個人プロファイルに関連する別個の個人プロファイルがグループ化されたもの。このリレーションは、ID 解決と調整ルールに基づきます。複数の個人の属性を 1 つのデータエクステンション行に含めるには、統合個人レベルでオーディエンスをセグメント化して有効化します。

Marketing Cloud Engagement の用語

  • 属性: Data 360 の有効化の一環として作成されたデータエクステンションで見つかった取引先責任者に関する情報またはデータ。Engagement 全体で属性を使用して、コンテンツのパーソナライズ、オムニチャネルのメッセージング、ジャーニーの決定を行えます。たとえば、連絡先の性別などを使用できます。
  • 属性グループ: エンゲージメント内の取引先責任者モデルを構成するデータエクステンションの論理グループ。データスペシャリストは、Contact Builder 内で、属性グループとそれに関連付けられたデータエクステンションを管理できます。
  • 取引先責任者モデル: エンゲージメント内の個人を定義する属性グループのコレクション。Engagement 全体 (Journey Builder など) で、連絡先モデルに関連するデータをより幅広く使用できます。
  • データエクステンション: Engagement にデータを保存するテーブル。データエクステンションは、データストレージや顧客へのメッセージ送信に使用できます。Data 360 を有効化するたびに、エンゲージメントのデータエクステンションが作成され、入力されます。
  • Data Foundation: Data 360 からエンゲージメント連絡先モデルにデータを有効化する実装。Journey Builder 全体でこのデータを簡単に更新、再利用して、ジャーニーの決定、「次まで待機」および「終了」活動、イベントトリガージャーニーのコンテンツパーソナライズを行えます。
  • ジャーニー: 一連のパーソナライズされたメッセージ、判断分岐、その他の活動をオーケストレーションするマーケティングワークフロー。マーケティング担当者は Journey Builder でジャーニーを作成します。

データ基盤用語

  • コア利用者モデル: 2 つのコアデータエクステンションがエンゲージメント連絡先モデルに接続され、Journey Builder のさまざまな使用事例でコンテンツのパーソナライズと意思決定を行います。
    • 個人データエクステンションには、全オーディエンスおよびその一般的に使用される属性 (名、姓、住所、性別、オプトイン状況、ロイヤルティ状況、個人レベルの生涯価値など) が含まれます。
    • 統合個人データエクステンションには、統合レベルの全オーディエンスおよび集計データまたは計算済みインサイト (ロイヤルティランク、生涯価値など) が含まれます。
  • 包括的コア利用者モデル: 複数の個人データエクステンションと 1 つ以上の統合個人データエクステンションがエンゲージメント連絡先モデルに接続されています。このコアデータエクステンションを使用して、Journey Builder のさまざまな使用事例でコンテンツのパーソナライズや意思決定を行えます。たとえば、デモグラフィック (性別、年齢、国の属性) で個人をグループ化したものを 1 つ作成し、e コマース (ロイヤルティランクと生涯価値) で個人をグループ化したものを 1 つ作成します。次に、集計データまたは計算済みインサイト (ロイヤルティランク、生涯価値など) が含まれる統合個人データエクステンションを 1 つ作成します。

オムニチャネルに関する考慮事項とベストプラクティス

このソリューションを実装する前に考慮すべき重要な側面とトレードオフがあります。このガイドは、顧客向けのオムニチャネル環境を有効にする方法の一例にすぎません。たとえば、独立したシングルチャネルジャーニーの代わりに、ユーザーは Data Cloud を使用して、1 つのジャーニーをメール、SMS、MobilePush のすべての活動と一緒にオーケストレーションすることで、シームレスなカスタマーエクスペリエンスを作成できます。

このソリューションで統合個人を使用する場合の潜在的なリスク

このソリューションでは、メール、SMS、MobilePush のすべてのチャネルで使用するオムニチャネル連絡先を Engagement に作成するために Marketing Cloud Engagement を実装していないことを前提としています。このガイドでは、Data Cloud で ID 解決ルールを作成して、別々の個人 (メール、SMS、MobilePush の各 SubscriberKey) を統合個人 (人を示す単一の表現) に関連付ける方法について説明します。

通常は、個人プロファイルをできるだけ使用することをお勧めします。キャンペーンでの統合個人の使用は、トランザクションまたはイベントトリガーの使用事例ではなく、プロモーションの使用事例に限定することをお勧めします。

誤った人へのメッセージ送信

統合個人は動的として検討し、変更される可能性があるため慎重に扱ってください。統合個人は、ID 解決内で設定したルールと、Data Cloud インスタンス内に保存されているデータに基づいています。ID 解決プロセスでは、外部データソースから新しくインポートされたデータまたは ID 解決ルールセットで行った変更に基づいて、個人プロファイルとそれに関連付けられた連絡先住所を特定の統合個人に追加したり、特定の統合個人から削除したりすることができます。そのため、誤った人にメッセージを送信する可能性があります。

例: Data Cloud には、John Smith という人物の統合個人を含めることができます。ID 解決ルールに基づいて、John Smith の統合プロファイルは最初に John.Smith.Email、John.Smith.SMS、John.Smith.MobilePush の 3 つの異なる個人 (Marketing Cloud Engagement の SubscriberKey) で構成されます。Cumulus は、John Smith の統合個人を有効化して Journey Builder で使用します。

オプトアウトした個人または連絡先の選択

Data Cloud では、統合個人でセグメント化する場合、条件を満たす個人が少なくとも 1 つ設定されている統合個人が対象になります。

統合個人で有効化する場合、Data Cloud でソース注文の優先度とエンゲージメント履歴を使用して、同意または設定種別に関係なく、有効化する連絡先を選択します。連絡先の有効化およびすべての連絡先にメッセージを送信することに対する同意の取得についての責任は、お客様が単独で負うものとします。

たとえば、John Smith の統合個人に 2 つの個人 (システム A の John.Smith.1 とシステム B の John.Smith.2) を関連付けることができ、それぞれが別々のデータソースからインポートされ、それぞれに独自の関連付けられた SMS 電話番号が設定されているとします。Cumulus が、SMS メッセージを統合個人がオプトインしたかどうかという条件で統合個人をセグメント化した場合、John.Smith.A が SMS メッセージにオプトインし、John.Smith.B がオプトアウトしたとしても、John Smith の統合個人は利用者の対象となります。有効化の一環として、Cumulus がソースシステムであるシステム B から取得された SMS 連絡先を優先するように選択している場合、Data Cloud でオプトアウト済みの電話番号を John.Smith.B から選択できます。

人に関する誤ったコンテキストの使用

Data Cloud では、統合個人でセグメント化する場合、条件を満たす個人が少なくとも 1 つ設定されている統合個人が対象になります。

統合個人で有効化すると、Data Cloud により、統合個人のプロファイル内のいずれかの個人からチャネルの連絡先が選択されます。この連絡先は、会社のさまざまなシステム、ブランド、部署、または関連子会社から取得される可能性があります。そのため、Data Cloud で、会社に設定された調整ルールによって決定されたソースシステムに基づいて、属性値が選択されます。

このアクションは、誤った顧客コンテキストが使用されて、カスタマーエクスペリエンスがパーソナライズされる原因になる可能性があります。顧客が望まない連絡先で対象を絞ったコンテンツやプロモーションを受信することになるかもしれないためです。

例 Cumulus は、各ブランドの連絡先を 1 つの一元化されたソースシステム内に保存しています。John Smith という人物が、john.smith@example1.com を使用して会社のブランド A (保険ブランド) で Cumulus のメールニュースレターにサインアップしました。これとは別に、その後 John Smith は john.smith@example2.com を使用してブランド B (クレジットカードブランド) にサインアップしました。最終的に、John Smith は john.smith@example3.com を使用して、モバイルアプリケーションでブランド C (株取引ブランド) にもサインアップしました。

ブランド A を担当するマーケティングチームは、住宅保険をアップグレードする可能性のある統合個人を検索するセグメントを作成します。有効化の一環として、Data Cloud により、最もエンゲージメントの高いメールアドレスである john.smith@example3.com が選択されます。

ただし、このようなブランドと住所にはコンテキスト上の関連性はありません。Cumulus が既存の住宅ローンを顧客がアップグレードするためのプロモーションを送信すると、顧客の保険に関連付けられているメールアドレスではなく、株取引アプリケーションで使用されるメールアドレスに送信されます。

例

Cumulus 内の各ブランドには異なるソースデータシステムがあり、それぞれがデータを Data Cloud にインポートしています。John Smith という人物が、会社のブランド A (保険ブランド) で Cumulus のメールニュースレターにサインアップしました。これとは別に、その後 John Smith はブランド B (クレジットカードブランド) にサインアップしました。最終的に、John Smith はモバイルアプリケーションでブランド C (株取引ブランド) にもサインアップしました。

ブランド A を担当するマーケティングチームは、住宅保険をアップグレードする可能性のある統合個人を検索するセグメントを作成します。この有効化の一環として、チームはメール、SMS、MobilePush の各連絡先を優先順位の取得元として選択し、最初にシステム A、次にシステム B、最後にシステム C から取得するようにします。

結果データエクステンションには、John のシステム A (保険ブランド) からのメール、システム B (クレジットカードブランド) からの電話番号、システム C (株取引アプリケーション) からの MobilePush キーが含まれます。

ただし、このようなブランドと住所にはコンテキスト上の関連性はありません。Cumulus が既存の住宅ローンを顧客がアップグレードするためのプロモーションを送信する場合に、保険ブランドで使用されるメールアドレスを使用することは理にかなっています。ただし、クレジットカードブランドに関連付けられている電話番号や、株取引ブランドに関連付けられているアプリケーションを使用することは適切ではありません。

チャネルごとの同意動作

Marketing Cloud Engagement には、顧客の同意と設定の管理に使用できるさまざまな機能があります。

このソリューションでは、SubscriberKey として MobilePush キーを使用してジャーニーが編成されているため、メールアドレス john.smith@example.com の同意状況が John.Smith.MobilePush のレコードに対して確認されます。

SMS メッセージ: SMS 送信の Marketing Cloud Engagement のネイティブ同意状況は、電話番号レベル (およびキーワード) で保存され、SubscriberKey レベル (メールとは異なり) では保存されません。このソリューションでは、調整する SubscriberKey に関係なく、電話 555-123-1234 の同意状況が確認されます。注意: SMS 活動を [すべての連絡先をキーワードに登録] に設定すると、ネイティブの同意が上書きされ、連絡先がオプトインされます。

メール活動のみ

  • ジャーニーのメール活動ごとに、特定のメールアドレスに送信されないようにする連絡禁止リストを関連付けます。このオプションは、メンバーが 200,000 人未満のジャーニーまたはリストのみにお勧めします。メールを送信する前に、Journey Builder で、リストに関連付けられているメールアドレスの連絡禁止状況が確認されます。
  • ジャーニーのメール活動ごとに、パブリケーションリストを関連付けます。Journey Builder では、メールを送信する前に、連絡先に関連付けられた公開状況をチェックし、連絡先が登録されているかどうか確認します。

メール、SMS、MobilePush 活動

  • ジャーニーで終了条件を使用して、人物の同意や設定を表す、最新であることがわかっている連絡先モデルの属性を監視します。ジャーニーの期間中、この値は Journey Builder で監視されます。
  • ジャーニーエントリに有効化されたデータエクステンションを使用する前に、Automation Studio でオートメーションを実行して、別データエクステンションに対して各連絡先の同意や設定の状況を検証します。無効な連絡先は、ジャーニーにエントリされる前に削除されます。
  • ジャーニーエントリソースの一部として、連絡先をジャーニーへのエントリから除外するように検索条件を設定します。無効な連絡先は、ジャーニーにエントリされる前に削除されます。

代替のオムニチャネルオーケストレーションアプローチ

メール、SMS、MobilePush のすべての活動をまとめて一緒に使用するジャーニーの代わりに、Data Cloud を使用して、独立したシングルチャネルから成る一連のジャーニーを絞り込み、オーケストレーションすることで、同様のカスタマーエクスペリエンスを作成します。

デフォルトのアドレス動作

このソリューションキットでは、Journey Builder 設定内のデフォルト送信アドレスを更新し、MobilePush キーのデフォルトのメールアドレスと SMS アドレスを上書きして、代わりに有効化されたデータエクステンションに保存されている EmailAddres と PhoneNumber に送信することをお勧めします。この方法によって、Marketing Cloud Engagement と Data Cloud のシステムで下流の更新が行われることがあります。

MobilePush キー (MobilePush SubscriberKey) 連絡先レコードの更新

送信で使用されるメールアドレスと SMS アドレスが Engagement の MobilePush キー (MobilePush SubscriberKey) 連絡先レコードに追加されるため、SubscriberKey にメールアドレスと SMS 連絡先アドレスの両方が含まれるようになります。その後、この情報は Data Cloud に同期され、MobilePush SubscriberKey の個人レコードに反映され、メールと SMS の両方の連絡先アドレスが個人に含まれるようになります。

このアクションによって更新が競合する可能性があります。Engagement では、新しいデフォルトのメールと SMS の連絡先アドレスで連絡先レコードが更新される可能性があります。一方、Data Cloud では、同じ連絡先に対して異なるメールと SMS の連絡先アドレスを使用して新しい利用者が有効化されます。

レポートとトラブルシューティング

  • すべての送信とジャーニーのレポートは、ジャーニーに使用されている SubscriberKey に基づいています。このソリューションキットの場合、MobilePush キーの値はジャーニーの SubscriberKey として機能します。
  • レポート戦略によっては、ジャーニーの送信の基準となったメールまたは SMS の SubscriberKey、または連絡先にこの値をハーモナイズするための追加プロセスが必要になる場合があります。
  • このソリューションを使用するジャーニーでは、スケジュールに基づいて更新される有効化を使用することはできません。更新により、MobilePush キー属性を購読者キーに関連付ける必須の送信リレーション設定が上書きされます。そのため、Journey Builder では MobilePush キー (MobilePush SubscriberKey を表す) の値に基づいて、オーケストレーション、パーソナライズ、送信ルックアップがすべてデフォルトに設定されます。

MobilePush SubscriberKey を選択するための計算済みインサイトの作成

Data 360 には、チャネル連絡先を選択および有効化するための多数のコントロールがあります。ただし、一部のシナリオでは、特定のチャネル連絡先を絞り込む、または選択するために計算済みインサイトを作成する必要があります。たとえば、Data 360 では、メール、SMS、MobilePush チャネルを一緒に有効化することはできません。

メモ オムニチャネルジャーニーにメールと SMS が含まれ、MobilePush が含まれていない場合、このステップをスキップできます。

計算済みインサイトの出力には MobilePush キー属性が含まれており、統合個人を有効化するときに直接属性として追加できます。このアクションにより、Marketing Cloud Engagement で有効化されたデータエクステンションにメール、SMS、および MobilePush の各チャネルの連絡先値が確実に設定されます。Journey Builder では、次の連絡先を使用してオムニチャネルジャーニーを編成できます。

Data 360 を使用したオムニチャネルジャーニーの関連用語

データ基盤を作成するときに知っておく必要がある用語を説明します。

Data 360 の用語

  • 有効化: セグメントを有効化プラットフォーム (対象) に公開するプロセス。
  • 有効化対象: 有効化中にセグメントのデータが送信される場所 (広告プラットフォームや Marketing Cloud Engagement など)。認証および承認情報が含まれます。
  • 属性: データモデルオブジェクト (DMO) などのオブジェクトにある情報またはデータ。Data 360 のセグメンテーションには、次の 2 種類の属性があります。
    • 直接属性 (1:1): データモデルオブジェクトで直接リレーションを持つ属性。つまり、郵便番号や名など、ユーザーが持つ値は 1 つのみです。
    • 関連属性 (1:N): 1 対多 (1:N) リレーションを持つ属性。つまり、特定のユーザーの属性ごとに複数の値を持つことができます (購入やメールイベントなど)。
  • 個人: 個人プロファイルは、エンゲージメントの SubscriberKey など、外部システムの個人のインスタンスを表します。人物の各インスタンスをデータエクステンションに取り込むには、個人レベルでオーディエンスをセグメント化して有効化します。
  • Segment (セグメント): 同じ誕生日の顧客など、いくつかの特性を共有するデータのグループ。
  • 統合個人: 統合個人は、1 つの統合個人プロファイルに関連する個別の個人プロファイルのグループです。このリレーションは、ID 解決と調整ルールに基づきます。複数の個人の属性を 1 つのデータエクステンション行に含めるには、統合個人レベルでオーディエンスをセグメント化して有効化します。

Marketing Cloud Engagement の用語

  • 属性: Data 360 の有効化の一環として作成されたデータエクステンションで見つかった取引先責任者に関する情報またはデータ。Engagement 全体で属性を使用して、コンテンツのパーソナライズ、オムニチャネルのメッセージング、ジャーニーの決定を行えます。たとえば、連絡先の性別などを使用できます。
  • 属性グループ: エンゲージメント内の取引先責任者モデルを構成するデータエクステンションの論理グループ。データスペシャリストは、Contact Builder アプリケーション内で、属性グループとそれに関連付けられたデータエクステンションを管理できます。
  • Channel Address (チャネルアドレス): メッセージが配信されるアドレス。メールチャネルの場合は EmailAddress です。SMS チャネルの場合は PhoneNumber です。MobilePush チャネルの場合は SubcriberKey で、対応するすべてのデバイスに自動送信します。
  • 取引先責任者: 取引先責任者は、メッセージを送信できるユーザーのインスタンスを表します。連絡先は、1 つ以上のチャネルに関連付けることができます。連絡先の概念は、Data 360 の個人や Engagement の SubscriberKey に似ています。
  • 取引先責任者モデル: エンゲージメント内の個人を定義する属性グループのコレクション。Engagement 全体 (Journey Builder など) で、連絡先モデルに関連するデータをより幅広く使用できます。
  • データエクステンション: Engagement にデータを保存するテーブル。データエクステンションは、データストレージや顧客へのメッセージ送信に使用できます。Data 360 を有効化するたびに、エンゲージメントのデータエクステンションが作成され、入力されます。
  • Data Foundation: Data 360 からエンゲージメント連絡先モデルにデータを有効化する実装。Journey Builder 全体でこのデータを簡単に更新、再利用して、ジャーニーの決定、「次まで待機」および「終了」活動、イベントトリガージャーニーのコンテンツパーソナライズを行えます。
  • ジャーニー: 一連のパーソナライズされたメッセージ、意思決定の分岐、その他の活動を調整するマーケティングワークフロー。マーケティング担当者は Journey Builder でジャーニーを作成します。
  • オムニチャネル取引先責任者: このソリューションキットのコンテキストでは、エンゲージメントの 1 つの SubscriberKey で表される個人。この SubscriberKey には、各チャネル (メール、SMS、MobilePush) に関連付けられたアドレスが含まれます。オムニチャネル連絡先は、オムニチャネルジャーニー内の各チャネルを実行できます。
  • シングルチャネル取引先責任者: このソリューションキットのコンテキストでは、エンゲージメントの 3 つの異なる SubscriberKey で表される個人。各 SubscriberKey に関連付けられるチャネルアドレスは 1 つのみです (メール、SMS、または MobilePush)。
  • SubscriberKey: SubscriberKey は、メッセージを送信できる個人または取引先責任者のインスタンスを表す識別子です。SubscriberKey は 1 つ以上のチャネルに関連付けることができます。SubscriberKey の概念は、Data 360 の個人やエンゲージメントの連絡先の概念に似ています。

Data Cloud Sandbox からの関連リスト強化の構築とリリース

Data Cloud Sandbox で、新しい関連リストの強化を作成するか、自動生成された既存の関連リストを変更します。強化のテストが完了したら、データキットにパッケージ化して、変更セットを使用して本番にリリースします。

必要なエディション

メモ Sandbox での関連リスト強化の使用とリリースは、ID 解決に基づく関連リスト強化にのみ適用されます。
使用可能なエディション: Enterprise Edition および Unlimited Edition

Data Cloud Sandbox で関連リスト強化を構築、テスト、リリースする手順は、次のとおりです。

  1. Sandbox 組織で、関連リスト強化を作成するか、既存のリスト強化を変更します。
  2. Sandbox で関連リストの強化をテストします。
  3. テストが完了したら、強化をパッケージ化する DevOps データキットを作成します。標準データキットはまだサポートされていません。一般的なプロセスは「Deploy Data Cloud Changes from a Sandbox (Sandbox からの Data Cloud の変更のリリース)」で説明していますが、関連リスト強化をパッケージ化する場合は、さらに次の手順を実行する必要があります。
    1. 新しいデータキットの [データキットコンテンツ] ページで、[関連リストの強化] セクションまでスクロールし、[追加] をクリックします。次に、リリースする関連リスト強化を選択します。
    2. データキットを送信変更セットにリンクしたら、関連リスト強化の連動コンポーネントもすべて変更セットに追加します。2 つ目の変更セットの一部としてページレイアウトの更新をリリースする必要もあります。

受信変更セットを本番組織にリリースしたら、オブジェクトマネージャーで、サポートされるオブジェクトの Data Cloud 関連リスト強化のリストの下に関連リスト強化が表示されます。

リリースに関する考慮事項

  • 対象組織に強化がすでに存在し、すべてのコンポーネントが一致しない場合、関連リスト強化のリリースが失敗する可能性があります。ソース組織と対象組織で次の関連リスト強化コンポーネントが検証され、一致していることが確認されます。
    • 取得元および子データモデルオブジェクト (DMO)
    • DMO リレーション
    • 統合個人またはアカウント
    • 親オブジェクト
    • 子リレーション名
  • まったく同じ定義の強化がすでに存在する対象組織に関連リストの強化をリリースすると、リリースは成功しますが、組織に変更は加えられません。

リリースに関する考慮事項

DMO をリリースするには、データキットにデータレイクオブジェクト (DLO) マッピングまたは関連付けられたデータストリームが含まれている必要があります。2 つの DMO 間のリレーションをマージバックするには、両方の DMO がこの要件を満たし、[項目取得元リレーション] が送信変更セットに追加されていることを確認します。

制限事項

  • 更新された関連リスト強化のリリースはサポートされていません。
  • リリースの取り消しはまだサポートされていません。
  • Connect REST API ベースのリリースはまだサポートされていません。
