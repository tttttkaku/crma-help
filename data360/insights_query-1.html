計算済みインサイトオブジェクトからの CRM Analytics へのアクセス

CRM Analytics には、Data 360 の [計算済みインサイト] タブからアクセスできます。

  1. Data 360 で、[計算済みインサイト] タブに移動し、分析する計算済みインサイトオブジェクトを選択します。
  2. [計算済みインサイト] で、[Analytics 内を探索] をクリックし、[Analytics] タブのデータを表示して作業します。

広告オーディエンスパートナープラットフォームからのオーディエンスインサイト

Data 360 の外部プラットフォームから詳細な顧客インサイトを取得します。この機能では、有効化されたセグメントに基づいてデモグラフィックデータとアフィニティグループが提供されます。インサイトはインサイト DMO に保存され、48 時間ごとにオーディエンスの一致数と更新も追跡されます。

「Audience Match Count for Advertising Activations」を参照してください。

Data 360 では、次のプラットフォームで利用者インサイトがサポートされています。

  • Google 広告インサイト
  • LinkedIn インサイト
  • Amazon インサイト

考慮事項

  • オーディエンスインサイトは、サポートされているプラットフォームに対してセグメントを有効化すると自動的に生成されます。インサイトを取得するために個別の有効化ステップは必要ありません。
  • インサイトはオーディエンスインサイト DMO に保存され、48 時間ごとに更新され、過去 90 日間のレコードが保持されます。
  • プラットフォームでインサイトデータを生成するには、オーディエンスサイズの最小しきい値を満たしている必要があります。しきい値より低いセグメントでは、レポートは生成されません。
  • サポートされるプラットフォームごとに異なるディメンションがレポートされます。各レポートについての詳細は、プラットフォーム固有のドキュメントを参照してください。
  • オーディエンスインサイト DMO は、データエクスプローラー、クエリエディター、SOQL、ANSI SQL、または Tableau などの接続済みレポートツールを使用して照会できます。
  • Amazon 広告と Amazon Marketing Cloud 有効化でのインサイト
    Amazon Marketing Cloud (AMC) オーディエンスインサイトレポートを使用して、顧客固有の特性、関心、行動を掘り下げます。Amazon 広告 AMC に対してセグメントを有効化すると、オーディエンスレポートが生成されます。このレポートでは、ライフスタイル、長期の購入習慣、関心に基づいて、商品を積極的に調べている顧客とそのアフィニティグループに関するデモグラフィックインサイトが提供されます。
  • 有効化での Google オーディエンスインサイト
    Data Cloud 内の Google オーディエンスレポートからのインサイトを使用して、顧客固有の特性、関心、行動を掘り下げます。Google に対してセグメントを有効化すると、5 ～ 7 日でオーディエンスレポートが生成されます。レポートでは、デモグラフィック、商品を積極的に調べている顧客、その顧客のアフィニティグループに関するインサイトがライフスタイル、長期の購入習慣、関心に基づいて提供されます。
  • Data Cloud のオーディエンスインサイトデータモデルオブジェクト
    Audience Insights データモデルオブジェクト (DMO) は、Google 広告プラットフォームで Ad Audiences コネクタを使用して有効化したオーディエンスに関するインサイトを提供します。複数の有効化された利用者からレコードを取得し、類似点と相違点を掘り下げることができます。DMO は 48 時間ごとに更新され、過去 90 日間のオーディエンスインサイトレコードが保存されるため、キャンペーンの長期的な影響とオーディエンスの進化を追跡できます。

Amazon 広告と Amazon Marketing Cloud 有効化でのインサイト

Amazon Marketing Cloud (AMC) オーディエンスインサイトレポートを使用して、顧客固有の特性、関心、行動を掘り下げます。Amazon 広告 AMC に対してセグメントを有効化すると、オーディエンスレポートが生成されます。このレポートでは、ライフスタイル、長期の購入習慣、関心に基づいて、商品を積極的に調べている顧客とそのアフィニティグループに関するデモグラフィックインサイトが提供されます。

レポート

このレポートでは、セグメント内の対象ユーザー (広告主オーディエンス) と、より広範な対象ユーザー母集団を比較してスコアが生成されます。スコアは、広告主オーディエンス内のメンバーが特定のデモグラフィックまたは行動カテゴリに属している可能性を表します。  インサイトの幅と深さは、最近の広告キャンペーンの一意のユーザーインプレッションリーチに基づいて変化する可能性があります。  広告を閲覧するユーザーが多いほど、得られるインサイトが増え、統計的に有意になります。

母集団分布 (傾向スコアへの入力) を計算するときに含めるには、ユーザーが Amazon で少なくとも 1 つの広告にさらされている必要があります。  たとえば、過去 90 年間に 1,000 万人のユニークユーザーに広告を提供した場合、レポートを実行するときに 1,000 万人のプロファイルを使用できます。

インサイトの作成方法

ビジュアル作成ツールまたはダイレクト SQL 構文を使用して、特定の分析要件を満たすインサイトを設計および実装します。作成者は、ノードベースのワークフローやストリーミング機能を使用してデータセットを結合、集計、または絞り込むことで、未加工データを変換できます。これらの方法では、既存のロジックをコピーし、ドラフトを保存し、複雑な SQL 演算子を適用して、リアルタイムまたは計算済み評価指標を生成できます。高度なデータモデルをゼロから構築したり、事前設定済みのパッケージを使用して迅速にリリースしたりできます。

  • テンプレートからのインサイトの作成
    テンプレートを使用して、Data 360 インサイトを効率的に作成します。インサイトの作成を簡略化するために、テンプレートで必要な Data 360 DMO を検証し、簡単な設定の質問をして、新しいインサイトを設定します。
  • ユーザーインターフェースを使用したデータインサイトの構築
    Visual Insight Builder を使用して Data 360 で総計値を作成します。インサイトビルダーは、Data 360の[計算済みインサイト]タブにある、ビジネスアナリストに焦点を絞った使いやすい評価指標作成ツールです。
  • パッケージからの計算済みインサイトの作成
    Data 360 にインストールされている Salesforce パッケージから計算済みインサイトを作成します。
  • SQL を使用したインサイトの作成
    SQL を記述して、Data 360 の計算済みインサイトとストリーミングインサイトを定義します。各クエリは特定の構造に従い、サポートされる関数、演算子、データ型を使用する必要があります。
  • インサイトをドラフトとして保存
    インサイトビルダーまたは SQL 式ビルダーを使用して計算済みインサイトを作成するときに、計算済みインサイトをドラフトとして保存でき、公開するまで継続的に更新することができます。計算済みインサイトをリリースする準備が整ったときに検証できます。ただし、既存の計算済みインサイトを編集中にドラフトとして保存することはできません。
  • インサイトのコピー
    既存のインサイトからの評価指標を使用して計算済みインサイトを作成します。Data 360 の計算済みインサイトレコードから SQL 関数を複製し、ディメンションや検索条件などの属性を編集できます。

データグラフの作成および管理

Data 360 でデータグラフを作成および管理します。データグラフは、Data 360 ユーザーインターフェースまたは API を使用して表示できます。

データグラフデータにアクセスするには、Data 360 メタデータまたはクエリ API を使用します。

  • データグラフの作成
    Data 360 でデータグラフを作成する前に、プライマリ DMO として使用する既存のデータモデルオブジェクト (DMO) を決定します。プライマリ DMO によって、データグラフに含めることができる関連オブジェクトが決まります。
  • データキットからのデータグラフの作成
    公開済みデータキットのデータグラフを使用することで、データグラフを手動で作成する手間を省きます。管理パッケージと未管理パッケージの両方を使用して、データグラフを含むデータキットをリリースできます。元のデータグラフを変更しても、データキットのデータグラフには影響しません。
  • データグラフへの計算済みインサイトの追加
    Data 360では、計算済みインサイトがデータグラフにも含まれるデータモデルオブジェクト(DMO)に基づいている限り、計算済みインサイトをデータグラフに含めることができます。DMO の主キー項目は、計算済みインサイトオブジェクト (CIO) のディメンションとして設定する必要があります。データグラフのルートにのみ CIO を追加できます。CIO を別のオブジェクトの子ノードとして追加することはできません。
  • データグラフのプロパティと JSON 構造の表示
    リストビューを使用して、プライマリデータモデルオブジェクト (DMO)、データグラフの状況、構造などのデータグラフのプロパティを確認します。また、レコードホームページからデータグラフの JSON 構造をコピーできます。
  • データグラフの編集
    データグラフの名前と説明を変更したり、新しいデータモデルオブジェクト (DMO) を関連付けたり、既存のプライマリ DMO および関連付けられた DMO を追加で変更したりできます。
  • データグラフのコピー
    データグラフをコピーすると、コピー元のデータグラフからデータスペースとプライマリデータモデルオブジェクト (DMO) が継承されます。データスペースまたは主 DMO は変更できませんが、異なる関連オブジェクトと項目を選択できます。コピーしたデータグラフの名前、API 参照名、検索条件設定、説明を変更することもできます。
  • データグラフの削除
    Data 360 では、データグラフを削除すると、レコードの DMO スキーマ構造と照会可能な JSON Blob も削除されます。データグラフを削除すると、そのデータグラフとすべての関連データが削除されます。このアクションを元に戻したり、削除されたデータグラフを取得したりすることはできません。
  • データグラフの更新
    Data 360 では、最初にデータグラフを作成したときに更新スケジュールを設定し、後でスケジュールを更新できます。データグラフを更新すると、前回の更新以降の変更で基礎となるデータが更新されます。必要に応じて、データグラフを手動で更新することもできます。
  • ストリーミングデータグラフ
    ストリーミングデータグラフを使用して、基盤となるデータが変更されたときにデータを自動的に更新します。ストリーミング更新により、遅延が短縮され、スケジュールする必要がなくなり、より予測可能な更新動作が提供されます。
  • データグラフで返されるデータの管理
    条件と並び替えおよび制限を使用して、データグラフに含まれるデータを管理します。条件は条件に基づいて含まれるレコードを制御し、子レコード制限は返される関連子レコードの数を制御します。これらの機能を組み合わせることで、ストレージの削減、パフォーマンスの向上、最も関連性の高いデータのみの追加が可能になります。並び替えと制限、条件の検索条件を一緒に適用して、パフォーマンスを向上させることができます。
  • リアルタイムデータグラフでのレコードのキャッシュとユーザーセッションの長さ
    キャッシュに保持されるレコード数とユーザーセッションの長さを管理するようにリアルタイムデータグラフを設定します。
  • リアルタイムデータグラフのセッション延長
    リアルタイムデータグラフと標準データグラフの一貫性を維持するために、セッション拡張では標準グラフが更新されている間、データが長期間保持されます。
  • データグラフの更新履歴
    [更新履歴] を使用して、特定のデータグラフに関連付けられた最近の更新イベントのリストを表示します。更新情報は、データグラフで選択された更新スケジュールによって異なります。[更新履歴] タブには、最新の更新実行が含まれます。

インサイトの SQL 関数

Data 360 で計算済みインサイトを作成する場合、次の集計、日時、分析、書式設定、算術および統計、Boolean 関数を使用します。[集計可能] 列は、セグメントまたは有効化で照会されたときに、関数の出力をより少ないディメンションで積み上げ集計できるかどうかを示します。

必要なエディション

メモ ストリーミングインサイトとリアルタイムインサイトでは、集計関数 SUM と COUNT のみがサポートされます。
使用可能なエディション: Data 360 でサポートされるすべてのエディション。 「Data 360 Edition の可用性」を参照してください。

集計可能な評価指標と集計不可能な評価指標

一部の関数は、ディメンション間で積み上げ集計または折りたたみ可能な総計値を生成します。これらは、集計可能メトリックと呼ばれます。集計可能な総計値の例として、SUM、COUNT、AVG などがあります。インサイトの作成時に定義したディメンションのサブセットについて結果を照会できます。

その他の関数では、集計不可能なメトリックが生成されます。RANK、NTILE、CASE などの関数は、集計不可能な総計値の例です。結果は一度にすべてのディメンションに依存するため、総計値をより小さいディメンションセットに削減または折りたたむことはできません。集計不可能な指標を照会する場合、インサイトの作成時に定義されたすべてのディメンションの値を指定する必要があります。

たとえば、RANK 関数を使用して「Rank customers by total spend by product category and location (商品カテゴリとロケーション別の総支出額で顧客をランク付け)」という指標を作成した場合、後でそのランクを商品カテゴリのみで照会することはできません。総計値を照会する場合、常に「商品カテゴリ」と「場所」の両方を指定する必要があります。

SELECT
  ssot__SalesOrder__dlm.ssot__SalesChannelId__c AS channel__c,
  RANK() OVER (ORDER BY SUM(ssot__SalesOrder__dlm.ssot__GrandTotalAmount__c) ASC) AS spend_rank__c,
  UnifiedIndividual__dlm.ssot__Id__c AS unified_individual__c
FROM
  ssot__SalesOrder__dlm
  JOIN IndividualIdentityLink__dlm
    ON ssot__SalesOrder__dlm.ssot__SoldToCustomerId__c = IndividualIdentityLink__dlm.SourceRecordId__c
  JOIN UnifiedIndividual__dlm
    ON IndividualIdentityLink__dlm.UnifiedRecordId__c = UnifiedIndividual__dlm.ssot__Id__c
GROUP BY
  unified_individual__c,
  channel__c

関数で集計不可能な総計値が生成されるかどうかは、計算済みインサイトのオブジェクトホーム画面で確認できます。

インサイトの SQL ルール

Data 360 で計算済みインサイトまたはストリーミングインサイトの SQL を記述する場合、ルールによって各条項の解釈方法と適用される制約が決まります。WHERE または JOIN 句にネストされたサブクエリを埋め込み、外部クエリで返される行を制限することもできます。

必要なエディション

使用可能なエディション: Data 360 でサポートされるすべてのエディション。 「Data 360 Edition の可用性」を参照してください。

句によるルールの照会

条項 ルール
全般 DMO 名では、大文字と小文字が区別されます。SQL の DMO 参照が、[データモデル] タブの [オブジェクト API 参照名] 列に表示されている大文字小文字に一致することを確認します。
クエリには少なくとも 1 つの基準が含まれている必要があります。基準とは、集計関数でラップされた項目です。
SELECT 句の属性のうち、集計関数内にないものはディメンションとして扱われ、GROUP BY 句に記述する必要があります。

トップレベルのクエリでは DISTINCT を使用できません。
複数行コメント (/* */) を使用できます。
SELECT ディメンションの別名は、項目の元の名前と一致できません。たとえば、UnifiedIndividual__dlm.Id__c as customer_id__c は有効ですが、UnifiedIndividual__dlm.Id__c as Id__c ではエラーが発生します。

ネストされたサブクエリ

サブクエリは、別のクエリ (通常は WHERE または JOIN 句) 内に埋め込まれたクエリです。サブクエリを使用して、外部クエリで取得する行を制限するデータを返します。

たとえば、次のクエリは、1980 年以降に生まれた顧客の販売注文の合計を平均します。

SELECT
  avg(SalesOrder__dlm.GrandTotalAmount__c) as avg__c,
  SubQuery1.Id as customer_id__c
FROM SalesOrder__dlm
JOIN (
  SELECT Individual__dlm.Id__c as Id
  FROM Individual__dlm
  WHERE year(Individual__dlm.BirthDate__c) > 1980
) as SubQuery1
ON SalesOrder__dlm.SoldToCustomerId__c = SubQuery1.Id
GROUP BY customer_id__c;

有効化の計算済みインサイト

Data 360の計算済みインサイトを使用して、有効化ジャーニーの意思決定とメッセージのパーソナライズを可能にします。

計算済みインサイト評価指標は、Marketing Cloud Engagement のコンテンツパーソナライズを促進するために役立ちます。

完了した計算済みインサイト評価指標を新規または既存の有効化にドラッグします。有効化に関するより詳細なインサイトを得るには、計算済みインサイトにディメンション検索条件を追加します。

計算済みインサイトには、評価指標を作成するときの 2 つの異なるカテゴリである集計可能な評価指標と集計不可能な評価指標が含まれます。

集計可能な評価指標

集計可能な評価指標ではディメンション検索条件は省略可能であり、引き続きインサイトに基づいて集計できます。

評価指標 基準 例
DateTime 購入総額 最小 = 最初に行われた購入、最大 = 最後に行われた購入
数値 購入総額 合計 = 行われた購入総額の回数

集計不可能な評価指標

属性を 1 つの特定の値に絞り込むには、集計不可能な評価指標に少なくとも 1 つのディメンション検索条件が必要です。

  • テキスト
  • 数値
例

「購入ランク」基準 = 1、「商品」ディメンション = Pizza、「日付」ディメンション = 1 月の場合、ディメンションを属性に追加してからの特定の 1 つの値を見つけることができます。「購入ランク」基準しかない場合、それ自体は集計不可能であり、値はありません。

メモ

ディメンション検索条件が集計不可能な評価指標の Date または DateTime である場合、インサイトは表示されますが集計不可能な評価指標は非表示になります。集計可能な評価指標はすべて引き続き属性として追加できます。

セグメンテーションの計算済みインサイト

計算済みインサイトを使用して、セグメンテーションでデータ主導のインサイトを制御します。セグメンテーション検索条件で計算済みインサイトの総計値とディメンションを記述することもできます。

セグメントで計算済みインサイトを使用する場合、選択するセグメント対象データモデルオブジェクト (DMO) はプロファイル種別である必要があります。

セグメントで計算済みインサイトを使用するには、Data 360 の [セグメント] タブに移動します。 更新するセグメントを選択し、[ルールを編集] をクリックします。計算済みインサイトは、インサイトの SQL 式で参照される DMO の下にある直接属性および関連属性ライブラリで見つけることができます。インサイトをクリックして総計値のリストを表示し、追加する総計値をセグメンテーションキャンバスにドラッグします。演算子を更新し、値を追加します。必要に応じて、[ディメンションを追加] をクリックしてセグメントにディメンションを追加することで、データを集計することもできます。

メトリクス

  • コンテナには 1 つの評価指標のみを含めることができます。
  • 複数の評価指標間の AND/OR 演算子を定義するには、異なるコンテナに評価指標を追加してから、を定義します。

ディメンション

  • コンテナには、評価指標の検索条件として複数のディメンションを含めることができます。
  • 複数のディメンションが追加された場合は、ディメンション間の AND/OR 演算子を定義します。
  • 計算済みインサイトに複数のディメンションがあり、そのすべてのディメンションが選択されていない場合、計算済みインサイトは選択したディメンションの 1 つの出力に積み上げ集計されます。

計算済みインサイトをセグメントに表示するには、セグメント化の基準となるテーブルをインサイトクエリ定義の結合として追加します。計算済みインサイトは、直接属性または関連属性の DMO に関連付けられており、セグメントとのリレーションがある必要もあります。2 つの DMO (Individual と SalesOrder など) がある場合、SalesOrder DMO の下に表示されるには、計算済みインサイトに個人 DMO のプライマリキーを 1 つのディメンションとして含め、SalesOrder 属性から直接派生するディメンションを少なくとも 1 つ含める必要があります。セグメント化されたテーブルの主キーは、計算済みインサイトのディメンションである必要もあります。Github リポジトリでクエリ例を参照してください。

メモ

セグメントでストリーミングインサイトを使用することはできません。

セグメントの集計不可能な総計値

集計不可能な総計値はセグメンテーションでサポートされます。Data 360 で複数ディメンション評価指標を作成する場合、一部の計算済みインサイト関数または評価指標は、1 つ以上のディメンションでさらに集計したり、折りたたんだりできません。これらの基準は、集計不可能な評価指標と呼ばれます。

計算済みインサイトがセグメントの複雑な関数を使用して定義されている場合、ディメンションで使用できる唯一の検索条件は [次の文字列と一致する] です。計算済みインサイトに日時ディメンションまたは日付ディメンションが含まれ、集計不可能な基準が 1 つのみ含まれている場合、計算済みインサイトは非表示になります。同様に、日付型ディメンションが含まれている場合、セグメントビルダーの属性ライブラリで集計不可能な基準が非表示になります。日時ディメンションがあると複数の可能性があるレコードに基づいて集計が行われることになり、集計不可能なメカニズムと矛盾します。

インサイトでの Join 句の使用

計算済みインサイトでは、同時に複数のデータモデルオブジェクト (DMO) にアクセスできます。異なる DMO の複数の行に一度にアクセスする計算済みインサイトクエリは、結合クエリと呼ばれます。Data 360 では、計算済みインサイトの 4 種類の結合 (内部、左、右、完全) がサポートされます。

必要なエディション

使用可能なエディション: Data 360 でサポートされるすべてのエディション。 「Data 360 Edition の可用性」を参照してください。

内部結合

内部結合では、2 つの DMO の値が一致するすべてのレコードが返されます。

例 
SELECT 
SUM(SALESORDER__dlm.grand_total_amount__c) as TotalOrderAmount__c, 
Individual__dlm.Id__c as CustomerId__c
FROM  SALESORDER__dlm
INNER JOIN Individual__dlm ON SALESORDER__dlm.partyid__c = Individual__dlm.Id__c 
GROUP BY CustomerId__c

左結合

左結合では、左側のテーブルのすべてのレコードと右側の DMO の一致レコードが返されます。

例 
SELECT 
SUM(SALESORDER__dlm.grand_total_amount__c) as TotalOrderAmount__c, 
Individual__dlm.Id__c as CustomerId__c
FROM  SALESORDER__dlm
LEFT JOIN Individual__dlm ON SALESORDER__dlm.partyid__c = Individual__dlm.Id__c 
GROUP BY CustomerId__c

右結合

右結合では、右側のテーブルのすべてのレコードと左側の DMO の一致レコードが返されます。

例 
SELECT 
SUM(SALESORDER__dlm.grand_total_amount__c) as TotalOrderAmount__c, 
Individual__dlm.Id__c as CustomerId__c
FROM  SALESORDER__dlm
RIGHT JOIN Individual__dlm ON SALESORDER__dlm.partyid__c = Individual__dlm.Id__c 
GROUP BY CustomerId__c

完全結合

完全結合では、左側または右側のいずれかの DMO に一致がある場合にすべてのレコードが返されます。

例 
SELECT 
SUM(SALESORDER__dlm.grand_total_amount__c) as TotalOrderAmount__c, 
Individual__dlm.Id__c as CustomerId__c
FROM  SALESORDER__dlm
FULL JOIN Individual__dlm ON SALESORDER__dlm.partyid__c = Individual__dlm.Id__c 
GROUP BY CustomerId__c
  • Data 360 の自動入力結合キー
    インサイトビルダーで 2 つ以上のオブジェクトを結合すると、結合ノードと結合キーは Data 360 のリレーションに基づいて自動入力されます。キー結合は、リンクテーブルを結合する簡単な手段です。結合ノードが自動入力されれば、エンゲージメントデータを統合プロファイルに簡単に接続して、自動推奨された結合を上書きできます。

有効化の使用事例では、プロバイダーのメディアまたは広告プラットフォームを介してファーストパーティオーディエンスデータを有効化するプライバシー優先の方法を消費者に提供します。セグメントリスト全体を転送するのではなく、コンシューマーはクリーンルーム内で一致するオーディエンスを特定します。Data 360は、キャンペーンの有効化で使用するために、一致したレコードをプロバイダーのAmazon S3バケットに直接書き込みます。

関係者寄稿データ 両方

省略可能な属性 (プロバイダー) セグメント名、カテゴリ、親カテゴリ
省略可能な属性 (コンシューマー) セグメント名、エンゲージメント同意、登録同意

例を見てみましょう。コンシューマー A (小売業者) とプロバイダー B (メディアネットワーク) は、有効化の使用事例でコラボレーションしています。コラボレーションを有効にする前に、双方で同じ 3 つの必須属性を対応付ける必要があります。

  • セグメント ID は、有効化する消費者 A のオーディエンスセグメント (ロイヤルティプログラムセグメントなど) を識別します。
  • メンバー ID は、各オーディエンスメンバーのコンシューマーの内部識別子です。プロバイダーが一致するレコードを参照できるように、出力に表示されます。
  • ハッシュされたメールアドレスが一致キーです。双方がメールアドレスをハッシュしてからクリーンルームに投稿するため、照合時に未加工の連絡先データが公開されることはありません。

消費者 A は、エンゲージメント同意とサブスクリプション同意の 2 つの省略可能な属性を対応付けることもできます。対応付けられている場合、コンシューマー A は関連する同意種別を付与したメンバーのみが含まれるようにクエリを絞り込むことができます。

提供者 B は、セグメント名、カテゴリ、親カテゴリの 3 つの省略可能な属性を対応付けることができます。マッピングされている場合、これらは一致するレコードと共に出力に表示され、一致したメンバーが属するプロバイダーセグメントに関するより豊富なメタデータがコンシューマー A に提供されます。

クリーンルームの有効化

クリーンルーム有効化の使用事例では、プロバイダーのメディアまたは広告プラットフォームを介してファーストパーティデータを有効化するプライバシー優先の方法を消費者に提供します。コンシューマーは、オーディエンスセグメント全体を転送するのではなく、クリーンルーム内の共有オーディエンスを特定します。Data 360 は、デマンドサイドプラットフォーム (DSP)、メディアシステム、または広告プラットフォーム内でキャンペーンを有効化するために、共有利用者リストを提供者に直接提供します。

小売業者 (消費者) は、メディアネットワーク (プロバイダー) プラットフォームで対象を絞った広告をロイヤルティプログラムの顧客に提供したいと考えています。小売業者がメディアネットワーク (プロバイダー) とクリーンルームコラボレーションを開始します。小売業者は有効化クエリを実行し、Data 360 は小売業者の顧客リストをメディアネットワークの利用者データと照合し、一致したレコードをメディアネットワークの S3 バケットに直接書き込みます。メディアネットワークは、一致したオーディエンスに対する小売業者の広告キャンペーンを有効化します。小売業者は、一致する個人を確認できません。Clean_Room_Audit_Log DMO で処理された行数のみが表示されます。この使用事例の条件については、「有効化使用事例テンプレート」を参照してください。

プライバシーとデータ所有権

クリーンルームの有効化により、提供者はファーストパーティデータを消費者が制御することなく、一致するオーディエンスデータを受信できます。

  • 一致するオーディエンスリストは、プロバイダーの Amazon S3 バケットにのみ存在します。
  • Data 360 には、プロバイダーが設定した特定の S3 パスへの書き込みのみのアクセス権があります。コンシューマーの組織は、プロバイダーの S3 バケットにアクセスできません。
  • コンシューマーの組織では、Clean_Room_Audit_Log DMO のクエリ実行ごとに処理された行数のみが記録されます。
  • 範囲設定済みTrustポリシーを使用するAWS IAM(Identity and Access Management)ロールでは、プロバイダーのS3バケットへの書き込みがこの特定のコラボレーションのみに制限されます。
  • クリーンルームの有効化の設定
    クリーンルーム有効化コラボレーションが有効になると、プロバイダーは Amazon S3 バケットで一致するオーディエンスデータを直接受信します。提供者はこのデータを使用して、広告プラットフォームまたは下流のメディアシステムで対象を絞ったキャンペーンを実行できます。
  • クリーンルームの有効化のための AWS ID プロバイダーの設定
    クリーン ルーム アクティベーションのコラボレーション招待ごとに、Data 360がクエリ結果をS3バケットに安全に書き込めるようにAWSアカウントを設定し、Data 360で招待を受け入れます。

    「Creating a role using custom Trust policies (console)」を参照してください。

      "Principal": {
        "Federated": "arn:aws:iam::[YOUR_ACCOUNT_ID]:oidc-provider/[SALESFORCE_CONSUMER_URL]/services/connectors"
      },
      "Action": "sts:AssumeRoleWithWebIdentity",
      "Condition": {
        "StringEquals": {
          "[SALESFORCE_CONSUMER_URL]/services/connectors:sub": "[EXTERNAL_ID]"
        }
      }
    }
  ]
}

クリーンルームコンシューマー

消費者は、商品に適したオーディエンスを見つけるために提供者のデータからのインサイトを求める広告主です。コンシューマーは、AppExchange からクリーンルームパッケージをリリースするか、プロバイダーを許可リストに登録することで、クリーンルームを開始できます。パートナーを許可リストに登録する場合、クリーンルームコラボレーションを開始するためにクリーンルームパッケージは必要ありません。Salesforce が提供するコラボレーションテンプレートを使用して、コラボレーションを開始します。

提供者をコラボレーションに招待するには、提供者とコラボレーションを作成します。コラボレーションを保存すると、提供者にコラボレーションへの招待が自動的に送信されます。提供者が招待を受け入れたら、結合されたデータセットで許可されたクエリを実行できます。クエリの結果は DMO に保存されます。

カスタムコラボレーションテンプレート

カスタムコラボレーションテンプレートは、必要なメタデータ属性とコラボレーションの条件を指定するためにプロバイダーが作成できる JSON ファイルです。カスタムテンプレートでは、各使用事例で複数の使用事例と複数のクエリをサポートできます。カスタムテンプレートを作成するには、サンプル JSON をコピーして項目値を指定し、パッケージの作成時にテンプレートをアップロードします。クリーンルームパッケージの作成時に Data 360 の [設定] からサンプル JSON をダウンロードすることもできます。 

テンプレートの概要

カスタムテンプレートを提供するプロバイダーの場合は、クリーンルームプラットフォームの仕様に従います。AWS と Data 360 には、カスタムテンプレートの成功に影響する小さな違いがあります。大きな違いの 1 つは、見積識別子です。

Data 360 クリーンルームのしくみ

クリーンルームは、個人情報を公開することなく、関係者がデータに関してコラボレーションするための安全な環境を提供します。共有するデータと条件を指定します。すべてのデータは暗号化され、クリーンルームから出ることはありません。Data 360では、厳格なプライバシーとセキュリティ対策を使用してコラボレーターが機密データを表示できないようにするとともに、メタデータへのアクセスとクエリ方法を完全に透過的に行うことができます。

提供者として、または消費者として、クリーンルームでコラボレーションできます。コラボレーションするには、コラボレーションテンプレートを使用して、双方がデータをクリーンルームに対応付けます。必須および省略可能なデータ項目は、コラボレーション条件 (許可されているクエリ、クエリを実行する関係者、クエリ結果を受信する関係者など) と共にテンプレートで事前定義されています。

Data 360 クリーンルームでは、Data 360 組織間のデータ共有を使用して、メタデータを安全に関連付け、設定されたデータセットの統合クエリを許可します。Data 360 にデータがない場合は、データを取り込むか、ゼロコピーを使用してメタデータをクリーンルームに関連付けることができます。クエリがクリーンルームで実行されると、Data 360 は必要なプライバシー保護措置をデータに適用します。プライバシーを保護するために集計されたクエリ結果はデータモデルオブジェクト (DMO) に保存され、そこからレポートを作成できます。

クリーンルームでのコラボレーション

クリーンルームコラボレーションの一連のイベントを次に示します。

メモ クリーンルームパッケージを作成またはリリースするには、Data 360 開発者組織が必要です。
  • Data Cloud の [設定] でクリーンルームを設定する手順は、次のとおりです。
    • 提供者: クリーンルームパッケージを作成します。パッケージには、カスタムまたは Salesforce 提供のコラボレーションテンプレートを含めることができます。カスタムテンプレートでは、複数の使用事例をサポートできます。
    • 提供者: AppExchange でクリーンルームパッケージを公開します。
    • コンシューマー: AppExchange からパッケージをリリースします。プロバイダーが信頼できるパートナーの場合、パッケージをリリースせずに、サポートされている使用事例へのアクセスを許可リストに登録できます。
  • Data 360 の [クリーンルーム] タブでのクリーンルームの使用方法を次に示します。
    • コンシューマーとプロバイダー: 使用事例に必要な属性と各関係者のデータセットの対応する属性間の対応付けを作成します。事前に対応付けられたテンプレートを作成したり、コラボレーションの作成時および招待の受け入れ時にデータを対応付けたりできます。コラボレーションを有効にする前に、双方が必要な対応付けを完了する必要があります。
    • コンシューマー: 特定の使用事例とコラボレーションクエリのコラボレーションを作成し、コラボレーションを保存します。コラボレーションを保存すると、提供者に自動的に招待が送信されます。
    • 提供者: コラボレーション招待を受け入れます。受け入れると、コラボレーションの状況が [有効] に変更されます。
    • 提供者またはコンシューマー: コラボレーションテンプレートの使用事例で定義されたロールと権限に従って、結合されたデータセットに対してクエリを実行します。コラボレーション結果は DMO に保存されるか、コラボレーションテンプレートの定義に従って処理されます。許可されたユーザーは結果を表示し、結果からレポートを作成できます。
  • クリーンルームプロバイダー
    プロバイダーとは、プラットフォームを所有し、データまたは広告スペースへのアクセス権を他の会社に提供できるパブリッシャーまたは企業です。Data 360 クリーンルームを使用すると、プロバイダーは Salesforce Data 360 クリーンルームまたは AWS クリーンルームを使用してコラボレーションできます。 
  • クリーンルームコンシューマー
    消費者は、商品に適したオーディエンスを見つけるために提供者のデータからのインサイトを求める広告主です。コンシューマーは、AppExchange からクリーンルームパッケージをリリースするか、プロバイダーを許可リストに登録することで、クリーンルームを開始できます。パートナーを許可リストに登録する場合、クリーンルームコラボレーションを開始するためにクリーンルームパッケージは必要ありません。Salesforce が提供するコラボレーションテンプレートを使用して、コラボレーションを開始します。
