広告有効化のオーディエンス一致数

[Match Count (一致数)] は、外部広告パートナープラットフォーム (Facebook、Google 広告、TikTok など) で正常にマッチングされたオーディエンスセグメントのおおよそのユーザー数です。セグメントリストの有効化の一致数を監視して、有効化するオーディエンスのリーチと規模を把握します。

必要なエディション

使用可能なエディション: Data 360 でサポートされるすべてのエディション。 「Data 360 Edition の可用性」を参照してください。
アドオンライセンスで使用可能: Ad Audiences

一致数の値は、これらの広告プラットフォームの有効化の [インサイト] タブに表示されます。 

  • Amazon
  • Meta (Facebook)
  • Google 広告
  • Google アドマネージャー
  • Google DV360
  • LinkedIn
  • Pinterest
  • Snapchat
  • TikTok
メモ Conversion API (CAPI) 目標の一致数値は表示されません。

特定のパートナーの一致数の解釈

  • Google DV360 および  Google 広告: 一致数の値は、Google 検索数に基づきます。
  • Amazon: 一致数の値は Amazon Marketing Cloud に基づきます。
  • Meta (Facebook): 一致数の値はおおよその上限です。
  • LinkedIn: 会社リストの有効化の一致数は、一致する会社リストに関連付けられた一致する個人の数を示します。 

一致数を最適化するための推奨事項 

  • 有効化するデータをマッピングする場合、該当するすべての属性を一致キーとして使用します。
  • メールアドレスや電話番号などの属性に複数の値がある場合、有効化時に追加します。各項目には、プロファイルごとに最大 5 個の値を含めることができます。
  • 広告プラットフォームの要件に基づいて同意値を適切に書式設定します。

ID 解決について

ID 解決は、Data 360 に保存されているソースプロファイルデータから統合プロファイルを生成する処理エンジンです。統合プロファイルは、ソースデータをロック解除するための参照システムとして機能します。ソースプロファイルの処理方法とタイミング、および統合プロファイル出力でできることを理解します。

統合プロファイルキーリング

統合プロファイルはデータのロックを解除する鍵ですが、ゴールデンレコードではありません。統合プロファイルにより、個人または取引先に関するすべてのソースプロファイルデータから作成された各顧客の最も完全で正確、かつ堅牢な把握が可能になります。ID 解決では、プロファイルの統合中に成立値が選択されたり、既存のデータが上書きされることはありません。

各統合プロファイルを鍵の輪のように考えます。各リングには、同じ個人または会社に属する 1 つ以上の鍵が含まれます。キーリングの各キーは、異なるロックに適合します。このたとえでは、統合プロファイルはソースレコードのキーを含むキーリングです。キーを使用して、1 つのレコードまたは複数のレコードのロックを解除し、レコードに含まれるデータを使用することができます。

統合プロファイルキーリングを使用すると、個人または会社に属するすべてのレコードを識別し、それらに関するデータにアクセスできるキーを見つけることができます。統合プロファイルキーリングを使用すると、データを 1 つの「最適な」レコードにマージすることなく、顧客の全体像を構築できます。この参照システムを使用して、特定の目的で最も重要となるデータを決定できます。また、使用事例ごとに異なる顧客のビューを選択することもできます。

  • ID 解決の処理頻度
    ID 解決では、データソースに応じて 60 分～ 24 時間ごとにルールセットが処理されます。各データソースは、データが受信されたタイミングと蓄積された変更の数に応じて、独自のタイムラインで処理されます。
  • リアルタイム ID 解決

Data 360 でのリアルタイムマッチングの設定

ルールセットの出力統合プロファイルデータモデルオブジェクトに基づいてリアルタイムデータグラフを作成することで、最初のルールセットの実行が完了した後にリアルタイム照合を行うようにルールセットを設定できます。

必要なエディション

使用可能なエディション: Data 360 でサポートされるすべてのエディション。 「Data 360 Edition の可用性」を参照してください。
必要なユーザー権限
ID 解決ルールセットを作成または編集する

権限セット

  • Data Cloud アーキテクト
  1. 必要な対応付けを設定します。
  2. ID 解決ルールセットを作成します。
  3. ID 解決を実行します。
  4. 実行が完了したら、ルールセットによって作成された統合プロファイルに基づいてリアルタイムデータグラフを設定します。
  5. リアルタイムデータグラフは、パイロット期間中に統合個人 DMO から 24 時間ごとに更新されます。
  6. リアルタイム照合では、ID 解決によって特定の顧客プロファイルがデータグラフの統合プロファイルと照合され、リアルタイムのプロファイルデータが返されます。

ID 解決ルールセットの削除

ルールセットを削除すると、統合されたすべての顧客データが完全に削除され、データモデルオブジェクトの連動関係が排除され、ルールセットのすべての処理が停止し、以前の実行の履歴が削除されます。場合によっては、ルールセットを削除するのではなく、一致ルールや調整ルールを更新することをお勧めします。

[ID 解決] タブまたはルールセットのレコードホームからルールセットを削除します。削除は、完了するまで最大 24 時間かかります。

警告 ルールセットを削除した後は、以前の統合データを復元することはできません。

同じルールセット名とルールセット ID を保持し、既存のデータを上書きするには、ルールセットを削除するのではなく更新します。

クエリエディターでの取引先の一致の評価

クエリエディターで統合取引先プロファイルを確認して、取引先統合一致ルールの有効性を確認します。

次のクエリは、ルールセットの出力をルールセット ID 001、ルールセットの出力をルールセット ID 002と比較します。このクエリでは、電話番号 555-234-5678 にリンクされたプロファイルが各ルールセットでどのように統合されているかが比較されます。

組織のクエリエディターでこのクエリを実行するには、組織のデータのクエリをカスタマイズします。

  1. 指定された UnifiedLinkssotAccount オブジェクトの取引先 ID を組織で有効なルールセット ID に置き換えます。たとえば、ID が ABC および XYZ のルールセットを比較するには、UnifiedLinkssotAccount001__dlm and を UnifiedLinkssotAccount002__dlm UnifiedLinkssotAccountABC__dlm and に UnifiedLinkssotAccountXYZ__dlm.置き換えます。

  2. サンプル電話番号の (555) 234-5678 を、確認する特定のレコードの電話番号に置き換えます。または、異なる条件で WHERE 句を更新します。

重要 クエリから LIMIT 句を削除しないでください。無制限のクエリ応答では、返されたレコードが多すぎて役に立たない可能性があります。

クエリを実行したら、出力を確認して、一致ルールによって作成された一致がビジネス要件を満たしているかどうかを判断します。一致していない場合は、一致条件と照合方法を調整して一致を最適化します。

SELECT
	"ssot__Account__dlm"."ssot__Id__c",
	"UnifiedLinkssotAccount001__dlm"."UnifiedRecordId__c" as Med_UUID,
	"UnifiedLinkssotAccount002__dlm"."UnifiedRecordId__c" as LOW_UUID,
	"ssot__Account__dlm"."ssot__Name__c",
	"ssot__ContactPointAddress__dlm"."ssot__AddressLine1__c",
	"ssot__ContactPointAddress__dlm"."ssot__AddressLine2__c",	
	"ssot__ContactPointAddress__dlm"."ssot__CityId__c",
	"ssot__ContactPointAddress__dlm"."ssot__CountryId__c",
	"ssot__PartyIdentification__dlm"."ssot__PartyIdentificationTypeId__c",
	"ssot__PartyIdentification__dlm"."ssot__Name__c" AS "Party_Name",
	"ssot__PartyIdentification__dlm"."ssot__IdentificationNumber__c",
	"ssot__ContactPointPhone__dlm"."ssot__FormattedE164PhoneNumber__c"	
FROM "ssot__Account__dlm" 
	LEFT JOIN "UnifiedLinkssotAccount001__dlm" ON "UnifiedLinkssotAccount001__dlm"."SourceRecordId__c" = "ssot__Account__dlm"."ssot__Id__c"
	LEFT JOIN "UnifiedLinkssotAccount002__dlm" ON "UnifiedLinkssotAccount002__dlm"."SourceRecordId__c" = "ssot__Account__dlm"."ssot__Id__c"
	LEFT JOIN "ssot__ContactPointAddress__dlm" ON "ssot__ContactPointAddress__dlm"."ssot__PartyId__c" = "ssot__Account__dlm"."ssot__Id__c"
	LEFT JOIN "ssot__PartyIdentification__dlm" ON "ssot__PartyIdentification__dlm"."ssot__PartyId__c" = "ssot__Account__dlm"."ssot__Id__c"
	LEFT JOIN "ssot__ContactPointPhone__dlm" ON "ssot__ContactPointPhone__dlm"."ssot__PartyId__c" = "ssot__Account__dlm"."ssot__Id__c"
WHERE "ssot__ContactPointPhone__dlm"."ssot__FormattedE164PhoneNumber__c" = '(555) 234-5678'
ORDER BY 
	"ssot__ContactPointPhone__dlm"."ssot__FormattedE164PhoneNumber__c",
	"ssot__Account__dlm"."ssot__Id__c"
LIMIT 100

ID 解決からのソースレコードの絞り込み

ルールセットのプライマリデータモデルオブジェクトで検索条件を定義して、ID 解決処理パイプラインに入るソースレコードを制御します。検索条件は前処理ゲートとして機能するため、除外条件に一致するレコードが統合パイプラインに入ることはありません。検索条件を使用すると、統合プロファイルをクリーンな状態に保ち、クレジット消費を削減できます。

検索条件は、広範なパーティションレベルの分離を目的としています。ルールセットのプライマリデータモデルオブジェクトに適用され、ID などのカーディナリティの高い項目に対するレコードレベルの制御には適していません。

使用事例

  • Separate B2B and B2C accounts (B2B および B2C アカウントの分離) — データスペースに同じアカウント DMO の法人取引先と個人取引先の両方が含まれている場合、RecordType = "B2B" などの検索条件を B2B ルールセットに追加します。法人取引先はコンシューマー統合から、コンシューマー取引先は B2B 統合から除外されます。
  • 一致ルールをテストするためのサンプルデータセットの実行 — データセット全体で ID 解決を実行する前に、データソースで絞り込んで代表的なサンプルのみを処理します。一致ルールと調整ルールの結果を評価し、設定を絞り込み、検索条件を削除してデータセット全体を処理します。
  • 検証済みデータソースの分離 — 検証済みのCRMデータと共に処理速度が高いまたは品質が低いデータソースがある場合、検索条件を使用して検証済みのソースのみを特定のルールセットに含めます。

制限および考慮事項

各ルールセットは最大 3 つの検索条件グループをサポートし、グループごとに最大 3 つの項目条件を設定できます。各検索条件グループは、ルールセットのプライマリデータモデルオブジェクトに適用されます。

AND/OR ロジックを使用して、グループ内およびグループ間で条件を組み合わせます。標準演算子は建物の条件で使用できます。

有効なルールセットで検索条件を追加または変更すると、ルールセットの完全な再処理がトリガーされます。完全な再実行の回数を最小限に抑えるには、ルールセットの自動スケジュールを一時停止し、検索条件の変更を含むすべての設定変更を一度に行ってからスケジュールを再開します。

セグメント内の複数の ID 解決ルールセット

同じエンティティに対して、異なる ID 解決ルールセットを適用した場合にセグメント母集団の件数に与える影響を比較します。ID 解決を使用して同じエンティティに対して別のルールセットを作成すると、両方のルールセットで作成されたエンティティと属性をセグメンテーションで使用できます。両方のルールセットの属性を使用して、異なる母集団を検証するか、A/B テストを行います。セグメント対象とするエンティティを選択しているか、属性を属性ライブラリに追加している場合、エンティティおよび属性名の末尾にはルールセット ID が含まれます。

ID 解決を使用して、個人エンティティ用の 2 つの異なるルールセットを作成します。1 番目のルールセットには、厳格な一致ルールを使用します。2 番目のルールセットには、より一般的な一致ルールを使用し、ルールセット ID に「fzzy」を付け加えます。fzzy ルールセットに基づいて新しいセグメントを作成するために、[セグメント対象] を「Unified Individual fzzy」とします。

ヒント 2 番目のルールセットを一時的な方法として使用して、データに最適なルールセットを作成し、その後に 2 番目のルールセットを削除します。すべてのルールセットの統合プロファイルがエンタイトルメントの制限に含まれます。

ID 解決一致ルールの用語

ID 解決ルールセットでの一致ルール、一致条件、一致方法の役割を理解します。一致ルール、一致条件、一致方法を追加、調整、および削除すると、ルールセット全体の統合率が変わる可能性があります。

一致ルール

各一致ルールは、レコードが一致する機会です。レコードがルールセットに一致するには、1 つの一致ルールの条件にのみ一致する必要があります。作成する一致ルールが多いほど、照合するレコードの商談が増えます。ルールセットにルールを追加すると、ルールセットの統合率が向上します。

一致条件

各一致ルール内で、条件によって特定の一致ルールの精度が決まります。2 つのレコードは、一致ルール内のすべての条件に一致する必要があります。含める条件が多いほど、2 つのレコードの一致が難しくなります。一致ルールに条件を追加すると、ルールセットの統合率が低下します。

照合方法
照合方法は、ID 解決で照合する前にデータを変換するためのさまざまな方法です。最大 5 個の照合方法から選択できますが、すべてのオブジェクトと項目ですべての方法を使用できるわけではありません。[完全] や [完全 (標準化)] など、条件をより厳しくする一致方法では統合率が低下し、[あいまい一致 - 精度低] など、より限定的な一致方法では統合率が増加する可能性があります。

ルールセットをリアルタイム一致で実行している場合、ルールセットの設定時に選択したスケジュール済み一致方法に関係なく、電話番号とメールアドレスを除くすべての一致条件が完全一致方式で実行されます。リアルタイム一致では、スケジュール済み一致方法として完全一致を指定していない限り、電話番号とメールアドレスは完全正規化一致を使用して実行されます。

ID 解決でのスケジュール済み一致とリアルタイム一致

ID 解決では、スケジュール済みとリアルタイムの 2 種類のルールセットを実行できます。2 つの種別のルールセットの実行方法と実行タイミング、および他の機能とのインタラクションが異なります。

スケジュール済み一致

スケジュール済み照合では、選択した照合方法を使用して、新規および更新されたソースデータが 1 日に数回確認されます。更新された統合プロファイル情報は、統合取引先または統合個人データモデルオブジェクトに保存されます。

スケジュール済み一致は、ID 解決ルールセットを初めて実行したときに使用されます。最初の実行が成功した後、プライマリデータモデルオブジェクトのデータが変更されたときに、スケジュール済み一致を使用して ID 解決ルールセットが増分更新されます。

スケジュール済み照合のタイミングは変更または制御できませんが、スケジュールを無効にすれば無効にできます。

スケジュール済み一致が実行されると、より多くの照合方法を使用できます。スケジュール済み照合では、データの徹底的なレビューを調整できます。

リアルタイム照合

リアルタイム照合では、有効なエンドユーザーに関する情報を統合プロファイルと照合するため、ミリ秒以内にアプリケーションまたは Web サイトをパーソナライズできます。リアルタイムマッチングは、リアルタイムパーソナライズプロセスから顧客 ID 情報を受信するたびに使用されます。

ルールセットの出力オブジェクトがリアルタイムデータグラフの主オブジェクトである場合、ルールセットはリアルタイム一致を使用して実行されます。リアルタイム照合では、特定の一致ルールで選択されたスケジュール済み一致に関係なく、照合方法は [完全] または [完全 (標準化)] 照合のみに制限されます。メールアドレスと電話番号は完全正規化一致で照合できますが、その他の項目は完全一致でのみ照合されます。

1 日に 1 回、リアルタイムのデータグラフは、スケジュール済みルールセットの実行によって生成された統合プロファイルで更新されます。リアルタイム照合で迅速な結果が返されるように、統合プロファイルに含まれるソースプロファイルとエンゲージメントイベントの数は制限されます。詳細は、Data 360 の制限とガイドラインを参照してください。ソースプロファイルは、リアルタイム一致の値に基づいて含めるように優先順位が付けられます。たとえば、最近の活動、頻繁な活動、ユーザー認証のあるプロファイルは、使用頻度の低いプロファイルよりも優先されます。

リアルタイム照合は高速で、ID 解決をミリ秒単位で有効な顧客と統合プロファイルと照合できます。顧客 ID 情報が既存の統合プロファイルと完全一致しない場合、一致するプロファイルは返されません。リアルタイム一致を使用して一致しなかったデータは、スケジュールされた一致中にレビューされ、そのときに照合される可能性があります。

リアルタイム照合の調整ルール

ID 解決では、一致ルールがスケジュール済みかリアルタイムかに関係なく、すべてのモードで同じ調整ルールが使用されます。

ID 解決のデータ前処理

一括処理ソースおよび統合ソースからのデータは、ソースレコードが ID 解決に送信される前に一致させる必要がないレコードを削除するために前処理されます。これにより、ID 解決では新規または変更されたレコードのみが処理され、変更されていないソースレコードは再実行されません。前処理は、増分処理を実現するために ID 解決をより迅速に実行し、現在の形式ですでに統合されているレコードに対して ID 解決を実行することでクレジットが消費されないようにします。

レコードが新規または変更されたかどうかを判断するために、ソースレコードは MD5 ハッシュ値に変換されます。各レコードのハッシュ値は、ID 解決によって以前に実行されたレコードのハッシュ値と比較されます。ID 解決による処理では、一意のハッシュ値を持つレコードのみが送信されます。

レコードの前処理により、データソースでフル更新が実行されても、ID 解決で変更のないレコードが実行されなくなります。

リアルタイム ID 解決

リアルタイムの ID 解決により、ミリ秒で顧客を識別できるため、エンゲージメント中にサイトやコミュニケーションをパーソナライズできます。

リアルタイム ID 解決は、既存のルールセットのルールを使用して、有効なユーザーのプロファイル情報を既存のプロファイルと比較することで実行されます。リアルタイム ID 解決のルールセットを指定するには、その出力をリアルタイムデータグラフの入力として使用します。

リアルタイム ID 解決にルールセットを使用する場合、ルールセットの設定時に別の照合方法を選択しても、すべての一致ルール条件は完全または完全正規化された照合方法を使用して実行されます。リアルタイム実行では、[空白の一致] は無視されます。

リアルタイム ID 解決のために受信されたプロファイル情報も保存され、選択した照合方法を使用して次回のスケジュール済みルールセットの実行中にプロファイルに統合されます。スケジュール済みルールセットの実行でリアルタイムの ID 情報を統合することで、統合プロファイルに顧客に関する最新かつ完全な情報を含めることができます。

ID 解決ルールセット

ルールセットには、複数のデータソースを統合プロファイルにリンクする方法を Customer Data Platform に指示する一致ルールと調整ルールが含まれます。統合プロファイル情報は、ルールセットによって作成されたデータモデルオブジェクトに保存されます。

  • ID 解決ルールセットの作成
    ID 解決を開始するには、取引先、個人、リード、世帯を統合するルールセットを設定します。ルールセットの主データモデルオブジェクトによって、統合されるレコードが決まります。ルールセットを作成した後にルールセットに追加する一致ルールと調整ルールでは、レコードの照合方法をガイドします。
  • ID 解決一致ルール
    一致ルールは、ID解決プロセス中にどのプロファイルを統合するかをData 360に指示します。各一致ルールに 1 つ以上の条件が含まれています。一致ルールのすべての条件を満たすと、プロファイルが一致します。
  • ID 解決調整ルール
    調整ルールでは、ID 解決プロセス中に、複数の値を含めることができない統合項目 (個人の名前など) に保存する 1 つの値を選択する方法を指定します。調整ルールはオブジェクトレベルで設定され、項目固有の調整ルールで上書きできます。調整プロセスでは、ソースプロファイルデータの削除や変更、接続済みソースシステムの更新、顧客との作業時に使用するソースデータの通知は行われません。
  • ID 解決でのスケジュール済み一致とリアルタイム一致
    ID 解決では、スケジュール済みとリアルタイムの 2 種類のルールセットを実行できます。2 つの種別のルールセットの実行方法と実行タイミング、および他の機能とのインタラクションが異なります。
  • ID 解決ルールセット処理結果
    ルールセットジョブが初めて実行された後に、概要統計を使用できるようになります。最新の実行の結果は [解決の概要] に表示されます。前の日の結果は処理履歴テーブルにリストされます。ルールセットが 1 日に複数回処理された場合、処理履歴テーブルの結果にはその日に完了した最後の実行が反映されます。

ID 解決の用語

ID 解決のコンテキストで使用されるルールセットや統合オブジェクトなどの用語の意味を理解します。

ルールセット
ID 解決ルールセットは、複数のデータソースを統合プロファイルにリンクする方法を指定する一致ルールと調整ルールで構成されます。一致ルールでは、項目値を比較して一致レコードを特定する方法を指定します。調整ルールでは、統合プロファイルでサマリーデータとして使用する複数のデータソースから値を選択する方法を指定します。

一致ルールについての詳細は、「ID 解決一致ルールの用語」を参照してください。

調整ルールについての詳細は、「ID 解決調整ルール」を参照してください。

ルールセットジョブ
ルールセットジョブは、ソースデータのマッピング方法、一致、および設定した調整ルールに従ってソースプロファイルを処理します。ソースデータやルールセットの設定に変更が検出された場合を除き、ジョブは各ルールセットで 1 日に 1 回以上実行されます。何も変更されていなければ、ルールセットジョブは省略されます。
統合プロファイルオブジェクト
ID 解決では、ソースプロファイルと、セグメンテーションや有効化、計算済みインサイト、レポートなどのプロセスで使用できる統合プロファイル情報がリンクされます。統合は、作成するデータマッピングと、ルールセットで指定された一致ルールと調整ルールに基づいて決定されます。

ルールセットが個人 DMO に基づいている場合、複数のデータソースからの名と姓などの情報が統合個人オブジェクトに統合されます。ルールセットが取引先 DMO に基づいている場合、会社名、場所、種別などの情報が統合取引先オブジェクトに統合されます。各統合プロファイルオブジェクトには、ソースデータを参照する調整ルールと ID を使用して選択されたプロファイルに関する概要情報が含まれており、特定の使用事例に最適なデータソースを決定できます。

統合連絡先オブジェクト
個人または取引先には、統合個人または統合取引先ごとに保持する必要がある複数の有効な連絡先を設定できます。たとえば、個人には自宅電話番号と携帯電話番号の両方を設定できます。Data 360 では、各ルールセットの対応付けとルールに基づいて、さまざまなデータソースからの連絡先を集計する統合連絡先オブジェクトが作成されます。統合連絡先オブジェクトには、統合プロファイルの一意の連絡先がすべて保持されます。

調整時に、ソース間で競合がある場合、連絡先を説明する属性のみが調整されます。たとえば、電話番号が一部のソースでは個人番号としてリストされ、他のソースでは法人番号としてリストされる場合、調整ルールによって電話番号が個人番号と法人番号のどちらとしてリストされるかが決定されます。

統合リンクオブジェクト
統合リンクオブジェクトはソースデータと統合オブジェクト間のリンクとして機能します。統合リンクオブジェクトでは、各統合プロファイルのソースデータを参照できます。統合プロファイルの計算済みインサイトを作成する場合にこのオブジェクトが必要になります。
  • 統合リンクオブジェクトと統合オブジェクトへのリレーション
    ID 解決では、ソースオブジェクトと統合プロファイルオブジェクト間のブリッジとして次のリンクテーブルが作成されます。

Data 360 の ID 解決では、レコードを統合するいくつかの異なる方法が提供されます。選択した統合種別によって、統合プロファイルのベースとなるオブジェクトの種別、ルールセットによって作成される出力オブジェクト、レコードの統合速度が決まります。

外部リンクを使用した個人または取引先の統合

外部リンクの一致により、外部データソースで一致として識別されたプロファイルを統合できます。ソースデータには、一致するレコードを識別する ID が含まれている必要があります。

外部リンクに基づく照合では、属性データが変更されてもレコードが確実にリンクされるため、複雑な状況でのプロファイルの照合が改善されます。たとえば、ブラウザーセッション中にリンクを寄稿して、匿名ユーザープロファイルをログインユーザープロファイルと照合します。または、ソースプロファイルに識別子を追加して、通常のルールでは一致しないプロファイルを統合します。

世帯への個人のグループ化

世帯照合では、統合個人を世帯と呼ばれる個人のグループに統合できます。世帯では、ルールセットの主データモデルオブジェクトとして統合個人オブジェクトが使用され、統合世帯オブジェクトに出力されます。

世帯を作成するには、まず個人オブジェクトに基づいてルールセットを設定し、それを実行して統合個人プロファイルを生成する必要があります。次に、個人ルールセットの出力に基づいてルールセットを設定します。

各世帯グループは個別の UUID で指定されます。ルールセットからの出力は統合世帯オブジェクトに保存されます。
