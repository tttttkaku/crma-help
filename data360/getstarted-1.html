Data 360 のデータに対するアクション

有効化を使用して、有効化対象のセグメント化されたデータ (Meta や Marketing Clound Engagement など) に対してアクションを実行します。データ共有を使用して、Data 360 オブジェクトをサードパーティパートナーと共有します。データアクションを使用して、Data 360 のデータイベントをほぼリアルタイムで監視します。

メモ

2025 年 10 月 14 日以降、Data Cloud は Data 360 にブランド変更されました。 この移行中に、アプリケーションやドキュメントで Data Cloud への参照が見られることがあります。名前は新しくなりますが、機能とコンテンツに変更はありません。

  • 有効化と有効化対象
    有効化は、セグメントを有効化プラットフォームに公開するプロセスで、そのデータに対してアクションを実行できます。有効化対象は、Marketing Cloud Engagement や Meta などの特定の有効化プラットフォームの認証および承認情報を保存するために使用されます。
  • クリーンルーム
    クリーンルームを使用して、未加工データを公開したり、機密性を損なうことなく、利用者データについて他の関係者と安全にコラボレーションします。提供者はそのデータを使用して、会社が商品やサービスに適した利用者を見つけるのに役立ちます。消費者はインサイトを使用してターゲティング戦略を調整できます。使用事例テンプレートでは、入力データ、サポートされるクエリ、プライバシー規制に関するルールが適用されます。
  • データ共有
    データ共有により、外部システムで Data 360 のデータに簡単にアクセスできます。データレークオブジェクト (DLO)、データモデルオブジェクト (DMO)、計算済みインサイトオブジェクト (CIO) へのアクセス権を使用して、強力な分析インサイトと機械学習モデルを作成できます。データ共有を使用したゼロ コピー データ共有により、データを外部システムに読み込むことなくData 360オブジェクトを共有でき、ほぼリアルタイムでデータにアクセスできます。
  • Data 360 のデータアクション
    Data 360 のデータモデルオブジェクトと計算済みインサイトオブジェクトのデータ変更を監視し、変更データイベントを Salesforce Platform イベント、Marketing Cloud Engagement、または Web フックに送信します。
  • 360 データとインサイトによる組織の強化
    Data 360 強化を使用して、組織全体のクリーンアップおよびハーモナイズされたデータを組織に追加します。Data 360 のデータを使用して、レコードページの関連リストとコピー項目の強化を作成します。
  • Data 360 でのフローの自動化
    自動化を定義し、取り込み(Salesforce CRMおよびAmazon S3データストリーム)、セグメンテーションと有効化、ID解決、計算済みインサイトを含むData 360プロセスをチェーニングします。スケジュールした時刻にプロセスが実行されるのを待つのではなく、必要に応じてを順番に実行できます。たとえば、プロセスをチェーニングして、データの取り込みが完了した場合に計算済みインサイトを更新したり、セグメンテーションを実行したりできます。自動化を定義して、フローの実行を監視したり、進行状況を確認したりできます。Flow Builder を使用して、Data 360 フローを作成します。Flow Builder では、自動化されたトリガー、再利用可能なビルディングブロック、事前作成済みソリューションを使用して、複雑なエンタープライズ規模のオートメーションを作成できます。

Data 360 を使用した広告

Data 360 を使用して、ファーストパーティデータを使用した広告戦略を実装します。Data 360で信頼できる情報源を確立し、外部広告プラットフォームに接続して、すべてのチャネルで高度に対象を絞ったパーソナライズされた環境を提供します。

Data 360 では、Google や Meta などの広告プラットフォームとのインテグレーションがサポートされています。これらのプラットフォームでの広告には Ad Audiences ライセンスが必要です。このライセンスを使用して、セグメントと DMO を広告プラットフォームに対して有効化し、有効化からインサイトを取得します。

AppExchange 広告パートナー プラットフォームでアドバタイズすることもできます。Data 360AppExchangeパートナーに対して利用者セグメントを有効化するには、Data Cloudライセンスのみが必要です。「 Create an Activation for an External Platform (外部プラットフォームの有効化の作成) 」の手順に従って AppExchange 有効化を作成します。

  • 広告オーディエンスパートナープラットフォームへのセグメント有効化
    Ad Audiences (広告オーディエンス) パートナープラットフォームに対してオーディエンスセグメントを有効化し、既知の顧客への広告キャンペーンをターゲティングします。
  • 広告オーディエンスパートナープラットフォームへの有効化の作成
    広告プラットフォームに対してオーディエンスセグメントと会社リストを有効化します。
  • Conversion API (CAPI) による広告オーディエンスパートナープラットフォームへの有効化
    オンラインおよびオフラインのコンバージョンイベントとデータを広告プラットフォームに直接送信します。CAPI インテグレーションは、セグメントの作成をスキップし、イベントシグナルをほぼリアルタイムで配信して、優れたキャンペーンの最適化とより明確な属性分析を実現します。
  • 広告オーディエンスパートナープラットフォームからのオーディエンスインサイト
    Data 360 の外部プラットフォームから詳細な顧客インサイトを取得します。この機能では、有効化されたセグメントに基づいてデモグラフィックデータとアフィニティグループが提供されます。インサイトはインサイト DMO に保存され、48 時間ごとにオーディエンスの一致数と更新も追跡されます。
  • 広告有効化のオーディエンス一致数
    [Match Count (一致数)] は、外部広告パートナープラットフォーム (Facebook、Google 広告、TikTok など) で正常にマッチングされたオーディエンスセグメントのおおよそのユーザー数です。セグメントリストの有効化の一致数を監視して、有効化するオーディエンスのリーチと規模を把握します。

結合を使用する場合の考慮事項

参照関係とは異なり、結合では複数行が一致している場合、一致ごとに個別のレコードが出力データに作成されます。結合を使用する前に、重複行の影響を理解していることを確認してください。

結合のレコードを集計する場合、基準が二重に計数されないようにします。

この例では、両方の入力データソースオブジェクトに重複するキー値があります。

左オブジェクトは右オブジェクトの複数件と一致しているため、左結合では左オブジェクトの Opp_ID の 1 レコードが重複します。

重複レコードでは、Alice の商談金額が繰り返されています。合計を取得するためにすべての商談金額を加算すると、Alice の金額が二重に計数されます。重複レコードを回避するには、結合ではなく参照関係を使用します。

結合キーに多対多リレーションがある場合、結合を使用しないようにします。

結合キーに多対多リレーションがあると、出力データが入力データソースよりも非常に大きくなる可能性があります。たとえば、左側の 4 件のレコードと右側の 5 件のレコードに同じキー値がある場合、結合で 20 (4*5) 件のレコードが出力に追加されます。より極端な例として、左側の 10,000 件のレコードと右側の 5,000 件のレコードが同じキー値を共有している場合、結合で 5,000 万件のレコードが出力に作成されます。

これが発生する理由を示すため、重複するキー値を持つ次の入力データソースを考えてみます。

左オブジェクトは右オブジェクトの 5 件と一致しているため、左結合では左オブジェクトの各レコードが 5 回重複します。

重複レコードを回避するには、結合ではなく参照関係を使用します。結合を使用する必要がある場合、キー項目を追加してキー値の一意性を高めます。

完全修飾キー (FQK) を作成するには、必ずキー修飾子項目を結合に追加します。また、キー修飾子項目の null 値を置き換えます。「一括処理データ変換のオブジェクトの結合」を参照してください。

一括処理データ変換でのノードの操作

一括処理データ変換には、データを取り込み、変換して、結果を対象に書き込めるノードがあります。キャンバスでノードを追加します。複数のノードを連続化して、データのフローを順次変更します。一括処理データ変換には、複数の入力ノードと出力ノードに加えて複数の追加ノード、結合ノード、集計ノード、検索条件ノード、変換ノード、更新ノードを含めることができます。

  • 入力ノードと出力ノード: 一括処理データ変換へのデータの追加および書き込み
    入力ノードを使用して、データを一括処理データ変換に追加します。一括処理データ変換の出力を保存するには、データを 1 つ以上の出力ノードに書き込みます。入力ノードと出力ノードには、データレークオブジェクト、またはプロファイル型またはその他型のデータモデルオブジェクトを使用できます。データレークオブジェクトの入力ノードとデータモデルオブジェクトの出力ノードを使用することはできません。その逆も同様です。通常、データアウェアスペシャリストとエンジニアはデータレークオブジェクトとデータモデルオブジェクトにアクセスできますが、マーケティング担当者とアナリストはデータモデルオブジェクトにしかアクセスできません。
  • 追加ノードを使用した異なるデータソースの行の統合
    追加ノードを使用して、複数の入力データソースの行を 1 つの結果に結合します。
  • 集計ノード
    集計ノードを使用して、データを積み上げ集計します。より高いレベルの粒度に集計したり、階層データを積み上げ集計したりできます。
  • 検索条件ノード
    検索条件ノードを使用して、対象内で必要のない行を削除します。たとえば、ケースレコードを絞り込んでエスカレーション済みのケースのみに焦点を絞ることができます。検索条件値では、大文字と小文字が区別されます。
  • 一括処理データ変換のオブジェクトの結合
    一括処理データ変換キャンバスで、ノードを使用してデータオブジェクト間の結合を作成します。複数のデータオブジェクトのデータを正確に結合し、重複しないようにするには、必ずキー修飾子項目を追加して、結合に完全修飾キー (FQK) を作成します。キー修飾子項目の null 値が正しく一致するようにするには、null 値を null 文字列または空の文字列に置き換えて、null セーフ結合を使用します。
  • 結合操作
    一括処理データ変換では、次の結合操作がサポートされています。
  • 変換ノード: 出力に読み込む前のデータの変換
    変換ノードを使用して、ノードに追加した変換に基づいてデータを操作します。各変換ノードに 1 つ以上の変換を追加できます。たとえば、2 つの列を連結し、日付列の形式を標準化し、フィードバック列でコメントのセンチメントを検出する変換を追加できます。各変換で独自の方法でデータが変更されます。データ変換の複数のフェーズでデータを操作するには、各フェーズで個別の変換ノードを追加します。
  • 一括処理データ変換の変換
    変換を使用して、データで計算を実行してデータを操作できます。たとえば、変換を使用して、数式に基づいて計算済み項目を作成できます。変換は変換ノード内に追加します。複数の変換をつなぎ合わせてデータを順次操作できます。
  • [更新] ノード: 列値のスワップ
    [更新] ノードでキーペアが一致した場合、列値を別のデータソースのデータに置き換えます。たとえば、最近の一連の買収や合併後に、選択した取引先名を更新するには、アップロードしたスプレッドシートからの名前を、一致する取引先 ID に基づいて置き換えます。処理時間を最短にするには、列のすべての値ではなく、キーペアが一致する列の値のみを変更します。
  • 一括処理データ変換のコピーと貼り付け
    CRM Analytics では、ツールバーまたはキーボードショートカットを使用して、1 つの一括処理データ変換内で、または複数の一括処理データ変換の間でノードをコピーして貼り付けます。この機能を使用するには、ブラウザーでクリップボードアクセス権限を有効にします。
  • 一括処理データ変換のノードまたは分岐の接続と再編成
    一括処理データ変換で、切断されたノードまたは分岐を接続して、任意のノードから他のノードにデータを追加します。中間ノードに分岐を作成し、一括処理データ変換の別のパスにその分岐を追加することもできます。

一括処理データ変換

一括処理データ変換を使用すると、ID 解決、セグメンテーション、計算済みインサイトなど、データをさらに活用できるように変換したり、Salesforce レポートからインサイトを引き出したりできます。一括処理変換は、データの更新時に実行できる反復可能な一連の操作です。一括処理データ変換を初めて実行すると、手順に従ってデータが取り込まれ、定義されます。次に、変換を手動で実行するか、スケジュールされた間隔で実行するかを設定できます。

メモ 「Salesforce ヘルプ: 一括処理データ変換」では、「項目」と「列」は同じ意味で使用されます。

一括処理データ変換では、キャンバスにノードを表示することで、データフローの概要を表します。キャンバスでは、すべてのデータオブジェクトを使用できます。たとえば、データの追加、操作、データオブジェクトへの書き込みを行うことができます。

キャンバスには、データに対する操作の完全なシーケンスが表示されます。この例では、追加ノード、集計ノード、検索条件ノード、変換ノード、結合ノードでデータレークオブジェクトの入力を変更します。結果が対象データレークオブジェクトに書き込まれます。変換ノードには一連の変換 (順番に組み合わせ可能な数式) が含まれます。組み込み変換には、連結や列の型変換も含まれます。カスタム数式は、日付、文字列、数値演算、ウィンドウ関数、case ステートメントを組み合わせるために使用します。

キャンバスには個々のデータ変換は表示されませんが、変換ノード (1) を選択して、その変換の詳細を確認できます (2)。

左パネルで変換ステップを選択すると、[プレビュー] タブでその変換の結果をプレビューできます。同様に、キャンバスで任意のノードを選択して、そのノードの結果をプレビューできます。

一括処理データ変換を実行すると、入力データに各ノードの機能が適用され、指定したデータオブジェクトに結果が出力されます。その後、このデータオブジェクトを他の一括処理データ変換やダウンストリームプロセスへの入力として使用できます。

各一括処理変換には、変換名と定義名の両方が割り当てられます。定義名を使用して、特定の変換定義を識別したり、複数の定義を 1 つの変換に結合したりできます。

  • 一括処理データ変換へのアクセス
    ビジュアルアプリケーションビルダーまたはカスタムコードを使用して、一括処理データ変換を作成してアクセスします。
  • 一括処理データ変換の通貨の設定
    データ変換で通貨値を使用するには、通貨を設定します。それ以外の場合、データは変更されません。この設定では、マルチ通貨のデータを 1 つの値に変換します。たとえば、データに GBP と USD が含まれており、通貨を USD に設定した場合、GBP 値は変換で使用するために自動的に USD に変換されます。
  • 一括処理データ変換の作成
    アプリケーション内ビルダーを使用して、データレークオブジェクトまたはデータモデルオブジェクトを使用して一括処理データ変換を作成します。
  • 一括処理データ変換でのノードの操作
    一括処理データ変換には、データを取り込み、変換して、結果を対象に書き込めるノードがあります。キャンバスでノードを追加します。複数のノードを連続化して、データのフローを順次変更します。一括処理データ変換には、複数の入力ノードと出力ノードに加えて複数の追加ノード、結合ノード、集計ノード、検索条件ノード、変換ノード、更新ノードを含めることができます。
  • 一括処理データ変換の作成
    次のガイドラインと推奨事項に留意して、一括処理データ変換を最大限に活用してください。
  • 一括処理データ変換の実行
    一括処理データ変換を初めて実行すると、データが作成されます。再度実行すると、最新のデータで更新されます。
  • 一括処理データ変換状況の確認
    少なくとも 1 つの一括処理データ変換を作成した後、[データ変換] タブをクリックすると、[最近参照したデータ] 画面に移動し、データ変換の状況を確認できます。
  • キーボードショートカット
    キーボードから基本アクションを実行します。

一括処理データ変換の変換

変換を使用して、データで計算を実行してデータを操作できます。たとえば、変換を使用して、数式に基づいて計算済み項目を作成できます。変換は変換ノード内に追加します。複数の変換をつなぎ合わせてデータを順次操作できます。

  • バケット変換: 項目値の分類
    数値、テキスト、Boolean 項目をバケット化して、データをグループ化および整理します。
  • データ型変換: 列の型の変換
    列のデータ型によって、その列のデータを照会できる方法が決まります。たとえば、テキストまたは日付列で絞り込みやグループ化を行ったり、数値列で計算を実行したりできます。項目のタグ付けが正しくないことがあります。必要に応じて、列の型変換を使用して、列を正しい型に変換します。
  • 日時変換: 日付項目の計算
    日付項目は、時間の経過に伴うトレンドを把握したり、今後のマイルストーンと期限をチームに知らせたりするための重要な項目です。日付に基づいて計算したり、分析で日付がより役立つようにしたりするには、日時変換を使用します。[現在] オプションを使用して、指定された形式の現在日時を含む列を挿入します。[日付の差] を使用して、選択した 2 つの日付列間の期間を日数、月数、年数として計算します。また、[日数や月数を加算または減算] 関数を使用して、日付列から日数または月数を加算または減算します。
  • [列を削除] 変換
    一括処理データ変換から不要な列を削除します。たとえば、数式変換の後に [列を削除] 変換を追加して、計算列で使用された入力列を削除できます。
  • 抽出変換: 日付コンポーネントの取得
    抽出変換を使用して、選択したコンポーネントを日付項目から新しい項目に取り込みます。たとえば、[ケースの作成日] 項目から時間コンポーネントを抽出して、時間別にケースの作成を分析します。
  • [属性を編集] 変換: 列名と値の形式の変更
    [属性を編集] 変換を使用して、列名をわかりやすくしたり、列値に一貫した形式を適用したりします。すべての列の表示ラベルと API 参照名を設定できます。数値列の精度とスケール、テキスト列の文字数、日付列の日付形式を設定することもできます。
  • JSON データのフラット化
    JSON 文字列として取り込まれたデータを一括変換で表形式データに変換します。ID 解決やセグメンテーションなどの下流機能でデータを使用するには、データをデータレイクオブジェクトまたはデータモデルオブジェクトの行および列として保存する必要があります。フラット化できる JSON データには、単一オブジェクト、オブジェクトの配列、リテラル (スカラー値) の配列として保存されたものがあります。
  • 階層データのフラット化
    flatten 変換を使用すると、ネストされた階層データをリストに変換して簡略化できます。このリストでは、各ノードとその前に存在するノード (上位ノード) が階層内で表示される場所を追跡します。データをフラット化するには、階層内のすべてのノードが含まれる項目と、それぞれに対応する親が含まれる項目を指定します。変換を実行すると、各レコードには親レコードのリストが含まれます。
  • [日付を書式設定] 変換: 列の日付形式の標準化
    [日付を書式設定] 変換を使用して、テキスト列内のすべての日付の形式を標準化します。一貫した形式により、月などの特定の日付部分による絞り込みを含め、レコードを日付で正しく絞り込み、グループ化できます。また、一貫した形式により、テキストから日付に列の型を確実に変換することができます。
  • 数式変換: 式に基づく計算列の作成
    数式計算に基づいて値を表示する列を作成します。計算には、同じ行や他の行の他の列からの入力を含めることができます。たとえば、[Revenue (収益)] 列と [Cost (コスト)] 列からの入力に基づいて [Profit (利益)] 列を作成できます。SQL で数式を入力します。Data 360 の SQL は、数値、文字列、日付データの標準関数とカスタム関数のコレクションです。
  • 分割変換: 列値の分割
    区切り文字を指定して、テキスト列の文字列を 2 つの値に分割します。列値を 2 個以上の部分に分割するには、複数の分割変換インスタンスを追加します。たとえば、3 個の分割変換を使用して、住所を町名・番地、市区郡、都道府県、郵便番号に分割できます。

請求に対するサイズの影響の計算

カスタムコードリリースで選択した計算サイズは、クレジット消費に直接影響します。

使用可能な計算サイズオプションは次のとおりです。

  • 標準 - 大規模 - 1時間あたり4コンピューティングユニット
  • 標準 - X-Large - 1 時間あたり 8 コンピューティングユニット
  • 標準 - 2X - 大 - 1 時間あたり 16 コンピューティングユニット
  • 標準 - 4X - 大 - 32 コンピューティングユニット/時
重要 計算サイズが大きいほど処理能力は高くなりますが、消費するクレジットは増えます。パフォーマンス要件とコストの考慮事項のバランスを取る計算サイズを選択します。

単位消費量の計算

計算単位の消費量は、コード実行で選択した計算サイズと合計計算時間によって異なります。合計計算時間は、基礎となるすべてのコンポーネントの実行時間の合計です。ジョブでは基盤となるコンポーネントの並列処理が使用されるため、合計計算時間が開始から終了までの期間よりも長くなる可能性があります。

メモ コードエクステンションチャンク関数は、実行完了後の 1 時間の待機時間を含め、関数が有効である間は計算料金が発生します。スタンバイ期間中に新しい要求が到着すると、1 時間タイマーがリセットされます。このリセットにより、関数が受信要求に対応できるようにして、検索インデックス処理を高速化し、信頼性を高めます。

計算単位消費量は次の数式を使用して計算されます。

単位消費量の計算 = 合計計算時間 (時間) x 計算サイズに対する 1 時間あたりの計算単位レート

計算単位の消費の場合、合計計算時間値は次のように適用されます。

  • 合計計算時間が 1 分未満の場合は、60 秒に切り上げられます。
  • 合計計算時間が 1 分を超える場合、請求では 1 秒単位が使用されます。たとえば、合計計算時間が 5 分 1 秒の場合、5 分 1 秒として請求されます (6 分ではない)。

例: 標準 - 大規模コンピューティングサイズ用に設定されたコード拡張スクリプトを実行するとします。合計計算時間は 1.5 時間です。[標準 - 大] の計算サイズを使用するように設定した場合、コードは 1 時間ごとに 4 つの計算単位を使用します。

  • 計算サイズ: 標準 - 大 - 1 時間あたり 4 計算ユニット
  • 合計計算時間: 1.5時間(説明)
  • Compute Unit Rate Per Hour for the Compute Size: 4 Compute Units/hour (計算サイズの 1 時間あたりの単位レートの計算: 4 計算単位/時間)
  • コンピューティング ユニット消費:1.5時間 x 4コンピューティング ユニット/時間 = 6コンピューティング ユニット

コードは 6 個の計算ユニットを消費します。

より大きな計算サイズを選択した場合、コードの実行時間が短くなる可能性がありますが、計算サイズが大きいほど 1 時間あたりの消費量が多くなります。

ライブクエリとクエリ消費の高速化

データ統合の使用方法によっては、ライブクエリまたは加速クエリの方が状況に適したコスト効率になる可能性があります。

例

通常、データへのアクセス頻度は高くても、変更の量と頻度が少ない場合、高速化によるデータ統合が適しています。

たとえば、ネットワーク内の各店舗の昨年の商品カテゴリの売上トレンドを表示するダッシュボードを作成するとします。データは毎日更新され、ダッシュボードは 1 日あたり平均 20 回参照されます。ダッシュボードは、読み込まれるたびにクエリ結果から作成されます。

外部データレイクに保存されている 1,000,000 件のレコードのデータを使用してダッシュボードが作成されたとします。毎日約 10,000 件のレコードが追加または更新されます。

このシナリオでは、高速化を有効にするとコストが低くなります。下の計算をやりましょう。

ライブクエリを介したクエリ統合で消費されたクレジット
ダッシュボードは 1 日あたり約 20 回読み込まれるため、ライブクエリを使用して 1 日あたり約 20 回データを照会します。各クエリは約 100,000 件のレコードにアクセスします。100 万行にアクセスするごとに消費されたクレジットのレートが 70 クレジットであるとします。
  • クエリあたりのアクセスレコード数 100,000 件 x 1 日あたりのクエリ数 20 件 = 1 日あたりのアクセス行数 200 万件
  • 毎日アクセスされる 200 万行 x 30 日 = 1 か月間アクセスされる 60 万行
  • 60 万 x 70 クレジット/月 = 4,200 クレジット消費
Credits Consumed by Query Federation with Acceleration (高速化を使用したクエリ統合で消費されたクレジット)
データフェデレーションクエリでアクセラレーションを有効にして、ローカルデータキャッシュに増分入力するとします。新規または変更されたレコードのみがキャッシュに追加されます。ソースデータの新規または変更された行 100 万行あたり 2,000 クレジットの割合でクレジットを消費しているとします。

初期設定時に、外部データレイクオブジェクトのすべてのレコードをキャッシュに入力します。

  • 100 万件のレコード x 2,000 クレジット/100 万 = 2,000 クレジット (キャッシュ初期化の場合)

また、フル更新を実行するたびに 2,000 クレジットを使用します。

キャッシュは毎日更新され、1 日あたり 10,000 件の新規レコードと変更されたレコードがあるとします。

  • 毎日更新される 10,000 行 x 30 日 = 1 か月で返される 300,000 行
  • 100 万あたり 0.3 万 x 2000 クレジット = 1 か月あたり 600 クレジット

キャッシュを初期化した月に 1 回フル更新を実行した月は、2,000 クレジットを使用します。キャッシュが確立されてからフル更新を実行しない月は、600 クレジットを使用します。

このシナリオでは、高速化を使用して 1 か月あたり 1,600 ～ 3,600 クレジットを節約できます。

例

データが頻繁に変更され、最新のデータを使用する必要がある場合は、ライブクエリを使用したデータ統合が最適です。

たとえば、セグメントを 1 日に 20 回公開するとします。セグメントは、外部データレイクに保存されている約 1,000,000 件のレコードから作成します。約 10,000 件のレコードが 30 分ごとに追加または更新されます。

このシナリオでは、ライブクエリを使用するとコストが低くなります。下の計算を順に見ていきましょう。

セグメントは 1 日あたり約 20 回公開されるため、ライブクエリを使用してデータを照会するのは 1 日あたり約 20 回です。各クエリは約 100,000 件のレコードにアクセスします。100 万行にアクセスするごとに消費されたクレジットのレートが 70 クレジットであるとします。

  • ファイル設定--フル更新モードで実行されているコネクタの場合、[Refresh initial file immediately] を選択しないでください。余分な消費サイクルを回避するには、コネクタで定期的にデータを更新できるようにします。
  • スケジュール頻度--フル更新モードで実行されているコネクタの使用頻度を減らすには、データの取り込み頻度を低くします。

セグメンテーションコストの削減

いくつかの方法で、セグメンテーションのクレジット消費レートを下げることができます。

  • セグメントを公開する前に、サンプルデータセットでプレビューして結果の品質を確認します。
  • 公開前にセグメントメンバーシップを検証して、セグメントの品質チェックを実行します。
  • 再利用してコストを削減するために、最後のメンバーシップモードで共通の検索条件を複数のセグメントにネストします。

消費を最小限に抑えるには、セグメントでこれらの設定を更新します。

  • 実行モード--使用事例で許可されている場合は、セグメントの公開をスケジュールしないでください。たとえば、セグメントをテストおよび調整するときに、準備ができたときにのみ実行することでコストを削減できます。
  • 頻度、実行間隔、開始日 -- スケジュールされた公開の頻度を減らすことで、クレジット消費を削減します。
  • 終了--セグメントの実行を停止するように設定して、セグメントの実行期間を制限します。
  • ルックバックウィンドウ--ルックバックウィンドウを、使用事例に必要な時間のみに絞り込むことで、処理されるレコード数を減らします。

Customer Data Platform ライセンスの請求と制限

このライセンスを持つユーザーは、Salesforce 組織で Data 360 にアクセスできます。このライセンスは購入できなくなり、更新できなくなります。このライセンスを持つ組織は、組織のプロファイル、エンゲージメント、およびその他のレコードの数に基づいて請求されます。その他の機能には制限があります。このライセンスを持つ Data 360 組織では、すべての Data 360 機能を使用できるわけではありません。

  • Customer Data Platform ライセンスから Data Cloud ライセンスへのユーザーの移行
    以前に Customer Data Platform ライセンスで Data 360 を運用していた組織に Data Cloud ライセンスを追加すると、Customer Data Platform ライセンスで付与された権限セットによって Data 360 へのアクセスは許可されなくなります。ユーザーに Data 360 への継続的なアクセスを提供するには、Data Cloud ライセンスに関連付けられた権限セットをユーザーに割り当てる必要があります。
  • Customer Data Platform の請求可能な使用量の計算
    旧 Customer Data Platform 組織への請求は、契約上のエンタイトルメントに基づいて行われます。請求の対象となる使用量を理解しておくと、データ管理に関する決定を下しやすくなります。
  • Customer Data Platform の制限とガイドライン
    ガイドラインでは、Customer Data Platform のお客様が Data 360 を最適に採用して最高のパフォーマンスを得るためのベストプラクティスの推奨事項を定義します。制限は、それを超えると機能が利用不可になったり、パフォーマンスが調整されたり、使用量の請求料金が適用されたりする境界線です。この記事では、購入できなくなった従来の Customer Data Platform ライセンスについて説明します。

Data 360 有効化での関連属性の選択に関する考慮事項

関連属性は、プライマリ DMO または有効化 DMO に接続されているデータモデルオブジェクト (DMO) に属するデータ項目です。これらの属性は、定義されたリレーションパスを介してリンクされている他のオブジェクトの情報にアクセスするのに役立ちます。DMO、関連属性、適用可能な検索条件との直接リレーションがあります。

メモ エンゲージメントデータの場合、有効化で 90 日間のルックバック期間がサポートされています。高速セグメント公開を使用する有効化で関連属性が選択されている場合、ルックバック期間は 7 日です。有効化ではこの期間内のエンゲージメントデータが考慮され、出力値を選択するときにこの期間外のレコードは考慮されません。エンゲージメント日がセグメントの 24 か月の期間内にある場合、プロファイルが有効化に含まれることがあります。特定のエンゲージメントレコードが 90 日のルックバック期間外の場合、有効化に含まれない可能性があります。

関連属性を選択するときは、次のガイドラインに従ってください。

  • 関連属性ごとに最大 25 個の値を有効化できます。 
  • 有効化ごとに最大 300 個の関連属性を選択できます。 
  • 有効化ごとに最大 8 個の DMO を使用できます。
  • 関連属性で最大 10,000 件の有効化を使用できます。この制限に達したら、既存の有効化から関連属性を削除するか、未使用の有効化を削除するか、直接属性のみの有効化を作成することができます。
  • セグメントのサイズは、有効化時にチェックされます。公開時にセグメントに 1 億 5,000 万件を超えるレコードがあり、関連属性が含まれている場合、セグメントは有効化されません。
  • 1 人の顧客 (または個人) が複数の販売注文を持つことができ、それぞれがさまざまな注文の詳細に関連付けられます。有効化 DMO の複数のパスで異なる DMO の属性を選択できます。次に例を示します。
    • 個人 → エンゲージメント (メール、Web サイト)
    • 個人 → 販売注文 → 注文の詳細
  • DMO に検索条件を適用する場合、絞り込まれた DMO 自体または関連する子 DMO の属性を使用できます。未選択または無効な DMO の属性も絞り込みに使用できます。検索条件は省略可能です。検索条件が適用されていない場合、有効化では選択した DMO のすべてのデータが考慮されます。
  • セグメンテーションと有効化の属性ライブラリは、達成する目的が異なるため、動作も異なります。セグメンテーションでは、DMO 階層全体が表示されます。有効化では、オブジェクトに至近の DMO が表示されます。他の DMO にアクセスするには、階層内をクリックして移動します。
  • 有効化によってセグメンテーション検索条件が自動的に取得されるわけではありません。属性の特定の値を有効にするには、検索条件を有効化に適用します。セグメンテーション検索条件は、セグメントの対象となるユーザーの検索に使用します。有効化検索条件は、メッセージをパーソナライズする属性の検索に使用します。

関連属性の絞り込み

関連属性の絞り込みでは、特定の検索条件を適用して、ユーザーが有効化ペイロードに関連データのみを含めることができます。これにより、有効化されたデータがキャンペーンのインテントと一致するようになります。 

たとえば、マーケティング担当者は、現在配送処理中状態の注文に関するEメールを顧客に送信したいと考えています。有効化する属性として[Order ID]や[Order Details]を選択し、[Order Status]が[Shipping In Progress]の検索条件を適用します。これにより、この状況に一致する注文のみが出力に含まれます。

  • 上流で適用される検索条件は下流で継承されるため、有効化全体で一貫した絞り込みが保証されます。 
  • 子 DMO の検索条件ビューがロックまたはグレー表示になっている場合は、継承された検索条件を示します。
  • 異なるパスの同じレベルの DMO は、互いの検索条件を継承しません。

Data 360 の数式項目に関する考慮事項

Data 360 で数式項目を作成するときは、次の考慮事項を参照してください。

未加工データ項目

数式で未加工データの項目を参照する場合は、sourceField['Header Label'] の構文を使用します。ここで、「Header Label」 (ヘッダーの表示ラベル) は未加工データの列名に対応します。構文 sourceField['Header Label'] は、大文字と小文字を区別します。

  • sourceField はプレフィックスです。sourcefield が正しくありません。
  • Header Label (ヘッダーの表示ラベル) の大文字小文字は未加工データに対応します。たとえば、ファイルで「address」と入力されている場合、参照は「address」である必要があります。ファイルで「Address」と入力されている場合、参照は「Address」である必要があります。
  • Header Label (ヘッダーの表示ラベル) への参照は一重引用符で囲む必要があります。ファイルに「address」という列が含まれる場合、構文は、sourceField['Address'] ではなく sourceField['address'] である必要があります。

自由形式テキスト

数式の文字列を参照するには、単一引用符または二重引用符を使用します。たとえば、未加工データ項目内の値が何らかの文字列と一致しているかどうかを確認する場合、どちらの式も有効です。

  • sourceField[‘Eye Color’] == “blue”
  • sourceField[‘Eye Color’] == ‘blue’

特定の用語では、単一引用符と二重引用符の参照を混在させないでください。たとえば、次の式は無効です。

  • sourceField[‘Eye Color’] == ‘blue”
  • sourceField[‘Eye Color’] == “blue’

区切り文字

有効な正規表現文字を数式の区切り文字として使用している場合は、その区切り文字を「\\」でエスケープする必要があります。

REPLACE('dd.mm.yy','\\.','_')
Output
dd_mm_yy

数値データ型

数値データ型を使用する数式項目の出力は、入力によって異なります。たとえば、次の 2 つの数式では、sourceField['ColumnX'] が 1.54 の場合に異なる結果となります。

数式結果

0.0 - sourceField['ColumnX'] -1.54

クリーンルームの請求に関する考慮事項

クリーンルームでは、Data 360 を使用してクリーンルームのコラボレーションにデータを安全に取り込みます。クリーンルームの使用は、次の使用量種別のクレジットの消費に影響します。

Digital Walletを使用して、組織で有効な消費カードを確認し、各カードで使用可能なクレジット数を確認し、各使用量種別で消費されたクレジット数を確認します。

プロバイダー組織で使用される利用状況の種別

プロバイダー組織は、クリーンルームにデータを送信して照会する Data 360 組織です。

Data 360 の利用状況

データの収集と処理にData 360を使用する場合、組織はData Services消費カードまたはFlex Credits消費カードからクレジットを消費します。有効なデータサービスクレジットがある場合、それらのクレジットが最初に消費されます。データ サービス クレジットが不足していたり、まったくクレジットがなかったりした場合、組織は Flex Credits for Data 360 サービスを消費します。詳細は、「Data Services Billable Usage Types for Data 360」および「Flex Credits Usage Types for Data 360」を参照してください。

使用量種別ごとの乗数を確認するには、「Multipliers for Data Services Rate Card」または「Agentforce & Data 360 Flex Credits Rate Card」を参照してください。各クレジットのコストは契約によって決まります。

Digital Wallet消費カード 利用状況の種別 利用状況種別の説明 備考
データサービス データ共有行の共有 (データ出力)

使用量は、最初にデータ共有を作成してデータ共有対象にリンクしたときに処理されたレコードの合計数に基づいて計算されます。これは、最初のフルバッチのデータにのみ適用されます。それ以降の増分変更は、この使用量種別には含まれません。

Data 360 組織間のデータ共有の場合、この利用状況種別はソース組織には適用されません。

  
データサービス アクセスされたデータ統合または共有行

データ統合の場合、使用量はソースから取得したレコード数に基づいて計算されます。データ共有の場合、使用量は外部データレイクの要求を満たすために返された行数に基づいて計算されます。

Data 360 組織間のデータ共有の場合、この利用状況種別はすべてのクエリの対象組織に適用されます。

Data 360 プロファイルのライセンス請求に関する考慮事項

Data 360 組織に Data 360 Profile または Data 360 Enterprise Profile ライセンスを追加すると、消費請求が変更され、特定の機能の制限が追加されます。

Data 360 Profiles ライセンスに関連付けられたすべての制限は、本番 Data 360 ホーム組織とその接続された Data Cloud One コンパニオン組織に一括して適用されます。Data 360 ホーム組織から作成された Sandbox 組織は、ホーム組織の制限を継承します。この制限は、Sandbox 組織とその接続済みコンパニオン組織に一括して適用されます。Data 360 Profiles ライセンスを持つ組織の制限を確認するには、「Data 360 Profiles ライセンス基本ライセンスの制限」を参照してください。

プロファイル

Data 360 組織クラスターに含まれるプロファイルの数は、購入した Data 360 Profile ライセンスの数に基づきます。プロファイルエンタイトルメントを超えた場合、超過料金で請求されます。

本番組織の場合、データスペースで ID 解決が有効であれば、各データスペースのプロファイル数は、既知の統合プロファイル、匿名プロファイルの 4%、および ID 解決で使用されていないプロファイルとして分類された DMO にマッピングされたすべての DLO のレコード数の合計になります。

ID 解決が有効でない場合、請求可能なプロファイル数は、カテゴリに関係なく、特定の DMO を除き、プロファイル種別として分類されたデータモデルオブジェクト (DMO) に対応付けられたすべてのデータレイクオブジェクト (DLO) のすべてのレコードの合計です。

Sandbox 組織の場合、同じ計数ロジックが適用されますが、制限の対象となるプロファイルの合計数は、Sandbox 組織のすべてのデータスペースのすべてのプロファイルの合計の 80% です。

プロファイルの計数方法についての詳細は、「Data 360 Profiles License Billable Profiles Calculations (Data 360 プロファイルライセンスの請求可能プロファイルの計算)」を参照してください。

ID 解決ルールセット

ID 解決の実行時に、バッチプロファイル統合または Data 360 統合の使用種別でクレジットは消費されません。

データ変換

クレジットは一括処理データ変換または Data 360 Prep 利用状況種別では消費されませんが、Data 360 組織クラスターの有効な一括処理データ変換の合計数は制限されます。

本番組織の場合、制限の対象となる一括処理データ変換の数は、ホーム本番組織のすべてのデータスペースのすべてのデータ変換の合計です。

Sandbox 組織の場合、制限の対象となる一括処理データ変換の数は、Sandbox 組織のすべてのデータスペースのすべてのデータ変換の合計です。

計算済みインサイト

クレジットは一括計算インサイトまたは Data 360 Prepusage 種別では消費されませんが、Data 360 組織クラスターの有効な一括計算インサイトの合計数は制限されます。

本番組織の場合、制限に計数される一括計算済みインサイトの数は、ホーム本番組織のすべてのデータスペースのすべての計算済みインサイトの合計です。

Sandbox 組織の場合、制限に計数される一括計算済みインサイトの数は、Sandbox 組織のすべてのデータスペースのすべての計算済みインサイトの合計です。

セグメンテーション

クレジットはセグメンテーションまたは Data 360 セグメンテーションの利用状況種別では消費されませんが、Data 360 組織クラスターの有効なセグメント (標準、ウォーターフォール、リアルタイム種別を含む) の合計数は制限されます。

本番組織の場合、制限の対象となるセグメント数は、ホームの本番組織のすべてのデータスペースのすべてのセグメントと、すべての接続された Data Cloud One Companion 組織のすべてのデータスペースのすべてのセグメントの合計です。

Sandbox 組織の場合、制限の対象となるセグメント数は、Sandbox 組織のすべてのデータスペースのすべてのセグメントの合計です。

Data 360 アーキテクチャ戦略

マルチ組織アーキテクチャを計画するときは、次のデータテナント、レジデンシーの詳細、管理の詳細を考慮してください。場合によっては、法的要件またはビジネス要件を満たすために複数の Data 360 インスタンスが必要です。

既存の Salesforce 組織で Data 360 を有効にするか、新しい Data 360 ハブを Data 360 ハブとして設定して、Data 360 機能を既存の Salesforce エコシステムから分離できます。

Data 360 データレジデンシーに関する考慮事項

Data 360 組織は、他の Salesforce クラウドや外部ソースシステムとは異なる領域でホストできます。Data 360 では複数の地域のデータを取り込むことができますが、取り込む前に弁護士に相談し、組織のデータレジデンシーに関するポリシーを確認してください。地域ごとに 1 つの Data 360 を作成し、Data 360 を使用してその地域の複数の組織のデータを統合および強化することもできます。Salesforce のデータ転送メカニズムと関連トピックについての詳細は、Salesforce のプライバシーリソースを参照してください。

データ処理に関する考慮事項

データは、ユーザーがレコードを表示および更新したり、組織間で共有されるオブジェクトを作成したり、レポートを生成したりするときに処理されます。組織を標準 CRM 組織または Data Cloud One コンパニオン接続に接続すると、データが処理される場所が変更され、法的に影響する可能性があります。すべての適用法を弁護士に確認し、データレジデンシー要件についてビジネスポリシーを相談します。

ホーム組織とコンパニオン組織のデータスペース間の接続を確立すると、すべての接続組織でデータが処理されます。これらの組織は、異なるテリトリーにある場合があります。自宅組織とコンパニオン組織に適用される処理場所については、インフラストラクチャとサブプロセスのドキュメントを参照してください。新しいコンパニオン組織を設定しても、ホーム組織のデータの保存場所は変更されません。

請求およびクレジット消費に関する考慮事項

Salesforce 組織からデータを取り込むと、請求に影響する可能性があります。クレジットは引き続きホーム組織で消費されます。

管理に関する考慮事項

Salesforce 組織で有効にすると、Data 360 は複数のソースからのデータに接続して統合できます。エンタープライズレベルのデータモデラーとデータアーキテクトは、Data 360 を使用して、1 つ以上の Salesforce 組織のすべてのビジネスユニットの一元化された情報源を確立できます。Data 360 を設定する場所と Data 360 のインスタンス数は、データアーキテクチャとデータレジデンシーの要件によって異なります。

Data 360 アーキテクチャに関する考慮事項

データニーズ — データモデリング、テスト、個別の環境の必要性など、組織のデータ要件にアクセスします。

ヒント データ使用の準備と計画については、「Build a Data Strategy for Data 360 (データ 360 のデータ戦略の構築)」 Trailhead モジュールを参照してください。

将来の成長 — 長期的な成長目標を特定し、1 つの Data 360 インスタンスを実装する決定を確認します。

制御と集中管理 — すべての組織でデータと Data 360 設定を完全に制御する必要があるかどうかを評価します。その場合、複数の Data 360 組織を作成することをお勧めします。ただし、組織全体の制御を一元化する場合は、複数の組織を 1 つの Data 360 に接続します。

機能の分離 — 新しい Salesforce 組織で Data 360 を有効にすると、その組織を Data 360 タスク専用に使用できます。たとえば、個別の管理チームを設定するには、新しい組織で Data 360 を設定します。

共有機能 — 既存の Salesforce 組織で Data 360 を有効にすると、既存の組織のユーザーはすべての Data 360 機能を使用できます。既存の組織のシステム管理者は、Data Cloud の [設定] にアクセスできます。

  • Data 360 でのマルチブランド管理
    複数のブランドを管理するには、さまざまなロケーション テナントにData 360を設定します。
  • Data 360 への Salesforce CRM 組織の接続
    Salesforce 組織を Data 360 に接続して、Data 360 で処理と統合するために Salesforce オブジェクトからデータを取り込みます。選択した接続の種別に応じて、データアクションまたはハーモナイズされた Data 360 データのみを送信できます。Salesforce CRM 組織の Data 360 のデータと機能にアクセスするには、Salesforce コンパニオン接続を設定します。フロー、Apex、CRM、データ強化などのプラットフォーム コンポーネントも、コンパニオン組織全体のData 360データにアクセスできます。

Data 360 のデータキットに関する考慮事項

データキットの作成、公開、リリースに関する次の考慮事項を確認して、実装を正常に行い、一般的な問題を回避します。

  • 標準データキットは Developer Edition 組織からのみ作成します。
  • データコネクタフレームワーク (DCF) データストリーム: データコネクタフレームワーク (DCF) は、Data 360 でコネクタを設定および管理する方法を制御します。 DCF ベースのデータストリームを標準データキットにリリースする場合、パッケージ化されたコネクタを使用するか、リリース時に対象組織で事前設定されたコネクタを選択できます。
  • 非 DCF データストリーム: 非 DCF データストリームをリリースするときに、対象組織で事前設定されたコネクタを選択します。コネクタの詳細はリリースプロセスに含まれません。
  • DevOps データキット: DevOps データキットを使用してデータストリームをリリースすると、Data 360 によって自動的にコネクタ情報が対象組織に追加されます。
  • データモデルオブジェクト (DMO): Sandbox から標準およびカスタムデータモデルオブジェクト (DMO) をリリースすると、関連付けられたリレーションとタグがリリースプロセス中に自動的に追加されます。ただし、派生 DMO や選定された DMO など、他の DMO 種別に明示的に割り当てられたタグはリリースに含まれません。
  • データモデルオブジェクトを標準データキットに追加すると、カスタムデータモデルはそのまま追加されます。標準データモデルを選択した場合、データモデル上に追加されたカスタムマッピングとカスタム項目のみがパッケージ化されます。
  • ゼロコピーデータストリーム: Google BigQuery、Snowflake、Databricks、または Redshift 接続を使用するゼロコピーデータストリームの場合、データベース、スキーマ、およびテーブル名がパブリッシャー組織と対象組織間で一致していることを確認します。
  • データレークオブジェクト (DLO): [データキット] タブの [追加] オプションを使用してデータキットに DLO を追加すると、スタンドアロン DLO のみがページに表示されます。
  • DLO-to-DMO マッピング: リリース時に出力 DLO-to-DMO マッピングが継承されるようにするには、出力 DLO 自体をデータキット設定に明示的に追加する必要があります。
  • 非構造化データレークオブジェクト (UDLO): UDLO をデータキットに追加すると、マッピングされた非構造化データモデルオブジェクト (UDMO) が自動的にデータキットに含まれます。
  • 計算済みインサイト:データ キットにインサイトを追加する場合、手動でインサイトの連動関係を追加します。連動関係には、子計算済みインサイト、データモデルオブジェクト、データレークオブジェクト、データグラフなどがあります。連動関係がない場合、インサイトのリリースが失敗する可能性があります。
  • 有効化: データキットを作成するときに、有効化を少量ずつ追加して保存します。多数の有効化を同時に保存しようとすると、操作がタイムアウトして失敗する可能性があります。
  • 一括データ変換:データ キットで一括データ変換をリリースすると、リリースに変換のスケジュールが含まれます。スケジュールはインストール後に対象組織で有効になります。

Data Cloud ライセンスの請求と制限

Data Cloud ライセンスを追加すると、Salesforce 組織で Data 360 が有効になります。このライセンスを持つ組織は、Data 360サービスの使用によって消費された消費クレジットを購入します。

Data Cloud ライセンスを購入または更新した時期に応じて、組織は Data Services クレジットまたは Flex Credits for Data 360 サービスのいずれかを消費します。Digital Walletを確認して、自分に適用されるクレジットのタイプを判断します。

  • Data 360 の Flex Credits の請求可能使用量種別
    特定の Data 360 機能の使用は、クレジット消費に影響します。Flex Credits使用量カテゴリの使用量を監視するには、組織のDigital Walletにアクセスします。組織に Data 360 Profiles タイプのライセンスがある場合、一部の使用量種別は消費されません。使用量の請求方法についての詳細は、契約書を参照いただくか、アカウントエグゼクティブにお問い合わせください。
  • Data 360 のデータサービス請求可能利用状況種別
    特定の Data 360 機能の使用は、クレジット消費に影響します。2026 年 2 月 24 日より前にクレジットを購入した場合、組織は Data 360 サービスのデータサービスクレジットを消費します。2026 年 2 月 24 日以降に購入または更新する組織には、データサービスまたは Flex Credit のいずれかを使用できます。これらのデータ サービス使用状況カテゴリの使用状況を監視するには、組織の Digital Wallet にアクセスします。組織に Data 360 Profiles タイプのライセンスがある場合、一部の使用量種別は消費されません。使用量の請求方法についての詳細は、契約書を参照いただくか、アカウントエグゼクティブにお問い合わせください。
  • Data 360 の制限およびガイドライン
    ガイドラインでは、Data 360 の採用を最適化して最高のパフォーマンスを実現するためのベストプラクティスの推奨事項を定義します。制限は、それを超えると機能が利用不可になったり、パフォーマンスが調整されたり、使用量の請求料金が適用されたりする境界線です。Data 360 は拡張性を備えているため、ビジネスニーズに合わせていくつかの制限を調整できます。アカウントエグゼクティブと協力して目標を満たすソリューションを見つけてください。
