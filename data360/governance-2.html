データ主体の権利の要求に対するデータモデリングの影響

データモデリングが Data 360 のデータ主体の権利の要求に与える影響について説明します。

Data 360に保存されているすべての個人データを個人エンティティに対応付けて、データ主体の権利の要求の一部として処理されるようにします。

個人データが含まれるフィールドは、Data 360 の標準属性またはカスタム属性を使用して個人エンティティに対応付けることができます。別の標準エンティティまたはカスタムエンティティに個人データを保存する場合、そのエンティティの顧客識別子にマッピングされている項目と個人 ID 項目間のオブジェクトデータモデルのリレーションを作成します。

例 Northern Trail Outfitters は Sales Cloud から販売注文データを取り込み、Data 360 の販売注文エンティティに保存します。この販売注文データには、個人データとみなされる顧客のメールアドレスの項目が含まれます。Northern Trail Outfitters は、販売注文エンティティのカスタム顧客 ID 属性と個人 ID 項目間のオブジェクトデータモデルのリレーションを作成します。
例 Northern Trail Outfitters は、Samantha Smith から個人データの削除要求を受信します。Northern Trail Outfitters は、Data 360 で個人 ID 1234 に関する Samantha の個人データを検索し、その個人 ID を使用して同意 API にデータ削除要求を送信します。販売注文エンティティのカスタム顧客 ID 属性と個人 ID 項目間のリレーションが定義されているため、データ削除要求の一部として両方のエンティティが削除されます。

データ主体の権利

欧州連合の一般データ保護規則 (GDPR) によって付与される権利など、顧客のデータ主体の権利は、個人データの保管と使用に関連します。Data 360は、データ保護とプライバシーのさまざまな規制に従って、消費者のデータ主体の権利をサポートするツールを提供します。

Data 360 では、次の規制が適用されます。Salesforce 同意 API を使用して、すべてのデータ主体の権利の要求を送信します。

  • データの削除または忘れられる権利 (RTBF)
  • 処理の制限 (RofP)
  • データのアクセスおよびエクスポート

データ主体の権利の要求

Data 360 でデータ主体の権利の要求を送信する方法について説明します。

個人 ID を識別パラメーターとして使用して、データ主体の権利の要求を送信します。要求は、Commerce Cloud を含むすべての接続済み Salesforce クラウドで個別に送信して処理する必要があります。

DevOps データキットを使用した Data 360 ガバナンスポリシーのリリース

DevOps データキットを使用して、Sandbox から本番組織にデータガバナンスポリシーを移行します。この方法では、一貫性が維持され、手動エラーが減少します。

使用可能なエディション: Data 360 でサポートされるすべてのエディション。 「Data 360 Edition の可用性」を参照してください。

Data 360 の変更をリリースする Data Cloud アーキテクト

マージバックを開始する前に、リリースが次の前提条件を満たしていることを確認します。

  • Sandbox 組織でガバナンスポリシーを作成してテストします。次のドキュメントを参照してください。
    • Data 360 でのオブジェクトまたは項目レベルのアクセスポリシーの作成
    • Data 360 でのレコードレベルポリシーの作成
    • Data 360 の動的データマスキングポリシー
  • 対象組織には、必要なデータモデルオブジェクト (DMO) とデータレイクオブジェクト (DLO) が含まれます。
  • すべてのポリシーとそれに関連付けられた保護オブジェクトを 1 つのデータキットにバンドルして、ポリシーの漏洩や意図しないデータの漏洩を防止します。
  • 結合で参照されるオブジェクトを含め、レコードレベルセキュリティ (RLS) ポリシーの連動関係が対象環境に存在することを確認します。
重要 ガバナンスポリシーは、Salesforce 変更セットを使用してのみリリースします。Salesforce CLI では、ガバナンス ポリシーの導入はサポートされていません。

ガバナンスポリシーを移動する

  1. Sandbox 組織で DevOps データキットを作成します。「Create a Data 360 Sandbox」を参照してください。
    1. 移行するデータストリームバンドルや DLO などのデータアセットを選択します。
    2. データキットウィザードで、関連付けられた RLS、OLS、FLS ポリシーとタグ割り当てを選択します。
    3. 実装に結合を含む RLS ポリシーが含まれている場合は、2 つ目の DevOps データキットを作成します。RLS ポリシーと関連タグの割り当てが含まれるデータストリームバンドルを追加します。
  2. データキットとそのタグの割り当てを送信変更セットに追加します。
    1. [設定] から、[クイック検索] ボックスに「送信変更セット」と入力し、[送信変更セット] を選択します。
    2. 新しい送信変更セットを作成します。
    3. すべての連動関係を含むデータキットを変更セットに追加します。「連動コンポーネントの表示と変更セットへの追加」を参照してください。
    4. 公開順序を確認します。連動する DLO または DMO がリリース順序の上位か、それより前にリリースされていることを確認します。
  3. 変更セットを本番組織にアップロードします。「送信変更セットのアップロード」を参照してください。
  4. 本番組織で、変更セットをリリースします。

    変更セットをリリースすると、DevOps データキットがインストールされ、関連するガバナンスポリシーが対象組織に適用されます。「変更セットのリリース」を参照してください。

  5. リリース状況を確認します。
    1. 対象組織で、[データキット] に移動し、[リリース履歴] をクリックしてリリースが成功することを確認します。
    2. 対象組織で、[Data Governance]に移動し、[Policies]をクリックして、マージされたRLS、FLS、OLSポリシーがダッシュボードに表示され、有効であることを確認します。

Data 360 での「共有不可」および「販売不可」要求の尊重

本人のデータのサードパーティへの共有または販売を禁じる権利を消費者に付与するカリフォルニア州プライバシー権法などの法律に準拠する方法を理解します。

「共有不可」および「販売不可」データの取り込み

データストリームの一環として、「共有不可」および「販売不可」に関する個人のデータも取り込まれます。データが Data 360 で適切に処理されるように、調整して統合個人データモデルオブジェクト (DMO) に保存します。

  1. 個人 DMO に、「共有不可」または「販売不可」要求データを保存するカスタム項目を作成します。
  2. 「共有不可」または「販売不可」要求データをその項目にマッピングします。
  3. ID 解決ルールセットの調整ルールを使用して、統合個人のデータをどのように処理して保存するかを決定します。

「共有不可」および「販売不可」要求の絞り込み

セグメンテーション中のデータの共有を禁じている統合個人を除外します。

セグメントを設定するときに、「共有不可」または「販売不可」データを保存する統合個人 DMO 項目に基づいて直接属性を作成します。データをサードパーティに引き渡す前に、個人に関するすべてのデータにこの検索条件を適用します。

Data 360 の動的データマスキングポリシー

動的データマスキングでは、機密データの使いやすさ、正確性、リレーションを変更せずに非表示にします。アクセス方法に関係なく、すべての Data 360 オブジェクトと項目に適用されます。

Data 360 では、機密データを保存時に暗号化して保護するため、データベースが侵害された場合でも不正アクセスを防止できます。動的データマスキングを使用すると、承認されたユーザーはデータを表示できますが、機密データはプレーンテキストで表示されないようにマスキングされます。

マスキングは他のセキュリティ機能と連動します。まず、アクセスポリシーによってユーザーがデータを表示できるかどうかが決まります。次に、マスキングポリシーによって、ユーザーに表示されるデータがマスクされるか、マスク解除されるかが決まります。これは、動的マスキングまたはクエリ時マスキングとも呼ばれます。

サポートされるマスキング方法には、構造化データの赤化 (選択的な赤化)、null化、日時または数値の丸めなどがあります。

  • Data 360 の動的マスキング種別
    動的データマスキングポリシーでは、機密データを照会するときに値を変更または非表示にすることで、機密データを保護します。これはユーザー情報、ロール、またはポリシールールに基づいて行われますが、データ自体は変更されません。
  • Data 360 での構造化データの動的データマスキングポリシーの作成
    ユーザーロールと権限に基づいてデータの表示を制限することで、機密情報を保護します。
  • Data 360 での非構造化データのマスキング (ベータ)
    PDF やテキストドキュメントなどの非構造化ファイルの機密情報をマスキングして、承認されたユーザーのみが参照できるようにします。マスキングポリシーは、自動的にタグ付けまたは識別される機密データに対して機能します。
  • 非構造化データの動的データマスキングポリシーの作成 (ベータ)
    PDF やテキストドキュメントなどの非構造化ファイルの機密情報を保護するために、マスキングポリシーを定義します。
  • 動的データマスキングのベストプラクティス
    Data Cloud で動的データマスキングを実装するためのベストプラクティスを次に示します。

動的データマスキングポリシーを作成する

権限セット

  • Data Cloud アーキテクト
  1. Data Cloud で、[データガバナンス] タブに移動します。
  2. 左ペインで、［Policies］ をクリックします。
  3. [新規] をクリックし、[動的データマスキング] を選択して、[次へ] をクリックします。
  4. Policy Builder で、一意のポリシー名と必要に応じて説明を入力します。
    ポリシー API 参照名はポリシー名に基づいて自動入力されますが、変更できます。
  5. [次へ] をクリックします。
  6. [Rules (ルール)] を選択し、保護するリソースを選択します。[リソース] ドロップダウンで、[Field in Structured Data (構造化データの項目)] を選択します。

    デフォルトでは、ルールはすべてのデータスペースに適用されます。新しいデータスペースが追加されると、次のルールがそのリソースに適用されます。

  7. ポリシーを特定のデータスペース範囲に制限するには、[Customize Scope (範囲のカスタマイズ)] をクリックし、[Apply to the resources in all Data Spaces in Data Cloud (Data Cloud のすべてのデータスペースのリソースに適用)] を選択解除して、目的のデータスペースを選択します。
  8. [保存] をクリックします。
  9. リソースに対して実行するアクションを選択します。[アクション] ドロップダウンから、[マスク] を選択します。
  10. 次のいずれかのマスキング方法を選択します。
    • Redaction (縮小) - マスクされた文字を X に置き換えます。縮小する文字数を選択します。
    • Nullification - データを NULL に置き換えます。
    • Datetime Rounding (日時丸め) - 年のみまたは年と月のみを表示することで、日時の表示を簡略化します。
    • Numeric Rounding (数値丸め) - 数値を最も近い整数または指定された小数点以下の桁数に丸めます。
  11. このアクションを実行する必要がある条件を定義します。たとえば、オブジェクトに Financial Data.Account Info タグが存在する場合にルールをトリガーする条件を設定します。または、オブジェクトに Personal Data.Digital Identifier.Browsing History タグが存在しない場合。
  12. さらに条件を追加するには、[条件を追加] をクリックします。
  13. 条件を異なるセットにグループ化するには、[グループを追加] をクリックします。OR 演算子を使用して、いずれかのグループがルール条件を満たしたときにアクションを実行できます。
  14. [保存して有効化] をクリックします。

動的データマスキングのベストプラクティス

Data Cloud で動的データマスキングを実装するためのベストプラクティスを次に示します。

  • 機密データの特定: マスキングを適用する前に、機密とみなされて保護が必要なデータ項目を特定します。たとえば、PII、財務レコード、医療データを保護します。
  • ロールベースのマスキング: ロールベースのアクセス制御を使用して、誰がどのデータを表示するかを決定します。たとえば、上級マネージャーは完全なデータにアクセスでき、他のユーザーには項目が縮小または部分的にマスクされます。
  • 使いやすさとセキュリティのバランス: マスキングによって機密データが保護されると同時に、ユーザーはタスクを効果的に実行できます。データ保護と使いやすさのバランスを目指します。
  • 結合およびクエリで使用されるキー項目をマスキングしない: 結合キーまたはクエリ検索条件で使用される項目をマスキングすると、結果セットが不正確または不完全になる可能性があります。クエリの精度を維持するために、データリレーションや絞り込みに重要な項目にマスキングを適用しないでください。マスクされたキー値に対する結合ポリシーがある行レベルセキュリティ (RLS) では、結果が返されません。同様に、マスクされた項目に基づく関連リストにはデータは表示されません。

データ倫理

Customer Trustを獲得して維持することは、Data 360を使用するときにデータ倫理のベスト プラクティスを採用することを意味します。

データ倫理とは、個人識別情報の収集、保護、使用とそれが個人に与える影響に関する道徳的な指標です。

個人情報を適切に収集して使用する

顧客が自分の情報に関する設定をコントロールできるようにします。顧客には自分のデータの使用について発言する権利があります。最も重要なのは、顧客が設定を指定したら、必ずその設定を尊重することです。Data 360は、オムニチャネルのすべてのマーケティング実践で顧客の設定を追跡および尊重するのに役立つ、顧客の統合プロファイルの作成に役立ちます。

メモ カスタムプリファレンスセンターの構築方法を参照してください。

データと引き換えに明確な価値を提供する

データと引き換えに明確な利点を提供します。見返りに顧客は何を得られるのでしょうか?顧客は、カスタマーエクスペリエンスが改善され、自分が大切な存在と感じられるようにするためにデータを提供します。

例 頻繁に購入する品目についてのおすすめを提供して利便性を高めます。特別なオファーを送ってコミュニティへの参加に感謝します。または、関心のある新商品や補完商品を提案して提供して認識を促進します。

機密データを慎重に扱う

他のデータよりも機密性の高いデータの種類があります。何を機密データポイントとするか決まりがあるわけではありませんが、年齢、性別、民族などのデータを求めるかどうかは慎重に検討することをお勧めします。最終的に、機密データとは何かを定義し、それを求める理由を決めるのは管理者と組織です。除外を検討すべきその他の機密データとして、保護されている属性 (人種、健康、退役軍人、障害など)、性自認、性的指向、宗教、民族、市民権、所属政党などがあります。

必要なデータのみを収集して使用する

データの使用は、よりパーソナライズされたカスタマーエクスペリエンスを作るために必要な用途に限定します。少なめにします (特に人口統計、社会経済、行動、取引のデータ)。

パートナーは慎重に選ぶ

ファーストパーティデータとサードパーティデータの選択と取り込みには細心の注意を払い、そのデータをさまざまな広告プラットフォームを通じて有効化する場合は慎重に行ってください。有効化パートナーが関わる場合は、パートナーに提供するデータの管理の連鎖 (Chain of Custody) を必ず理解しておきます。有効化パートナーがデータをキャンペーンに使用した後、どうなるのか?削除するのか?再利用するのか?有効化パートナーとの各契約を精査し、パートナーに送信されるデータの処理、保管、管理に関する明確な義務が定められていることを確認します。

メモ 「 Data 360: Guide to the Value of Ethical Data Partnerships (Data 360: 倫理的なデータパートナーシップの価値へのガイド)」ガイドを参照してください。

Data 360 での手動および自動タギング

データにタグを適用するには、手動タギングと自動タギングの 2 つの方法があります。

手動タギング

手動タギングを使用すると、ユーザーはデータオブジェクトと項目にタグを直接割り当てることができます。この方法は正確であり、ユーザーはドメインKnowledgeを適用できるため、コンテキストが重要な機密データやビジネス・クリティカルなデータにタグ付けする場合に最適です。

自動タギング

自動タギングでは、AI を使用してタグの提案を生成することで、このプロセスを大規模なデータセット全体に拡張します。Data 360 の [タグの提案] 機能では、大規模言語モデル (LLM) を使用してオブジェクト名や項目名などの情報を確認し、定義された分類に基づいてタグを提案します。プライバシーを確保するため、顧客データへのアクセスや分析は行いません。代わりに、メタデータを分析して、オブジェクトおよび項目レベルで関連するタグを提案します。これらのタグは自動的に適用されません。データスチュワードまたはシステム管理者は、ビジネスコンテキストを理解しているユーザーに最終的な制御が委ねられるように、これらの情報を確認して承認します。このプロセスをさらに絞り込むには、自動提案の上に手動タグを追加します。

  • オブジェクトまたは項目へのタグの手動適用
    Data 360 では、定義済みのタグをデータオブジェクトまたは項目に追加して、機密性、利用状況、またはカテゴリに基づいて分類します。
  • Data 360 での自動タグの提案の使用
    Data 360 は、オブジェクトや項目の名前や型などのメタデータを分析してタグを提案します。これにより、実際のデータをスキャンすることなく、インテリジェントなコンテキスト対応の提案が提供され、タグ付けが合理化されます。

Data 360 のオブジェクトレベルおよび項目レベルのタグ

データガバナンスでは、オブジェクトレベルのタグと項目レベルのタグを使用して、さまざまなレベルの粒度でデータの表示ラベル付けと管理を行うことができます。

Data 360 のタグは、データレイクオブジェクト (DLO)、データモデルオブジェクト (DMO)、計算済みインサイトオブジェクト (CIO) などのデータオブジェクト全体に適用されます。これらのタグは、オブジェクトの全体的な性質や機密性を表します。たとえば、社外秘タグまたは顧客データタグをセールスデータセット全体に適用できます。

項目レベルのタグを使用して、メール、社会保障番号、誕生日など、オブジェクトの個々の部分を識別できます。これらのタグは、マスキング、アクセス制限、または特別な処理が必要な機密項目を識別します。

両方のレベルのタギングを使用すると、組織は機密項目を保護しながら、オブジェクトレベルでより広範なアクセスと制御が可能になります。

  • Data 360 でのタグの作成
    タグは、大規模なデータの整理、分類、管理に不可欠です。これらは、データオブジェクトまたは項目の内容、機密性、利用状況、目的を説明するメタデータの表示ラベルとして機能します。タグには 1 つの親タグと複数の子タグを含めることができますが、複数のレベルの階層はサポートされません。
  • Data 360 でのタグの編集または削除
    タグを削除したり、タグ名、API 参照名、分類を編集したりできます。ポリシーで使用されているタグは削除できません。これには、Data Cloud によって提供されるデフォルトタグが含まれます。

オムニチャネルジャーニーへの同意および設定検索条件の追加

メールチャネルの場合、Marketing Cloud Engagement ではメールアドレスレベルではなく SubscriberKey レベルで同意が保存されます。Cumulus は、データエクステンションに保存されているメールアドレスにメール送信するときに MobilePush キーを使用することで、自社の同意戦略に違反した可能性があります。

たとえば、Cumulus は Marketing Cloud Engagement で SubscriberKey John.Smith.Email に関するメール同意を保存していますが、これはデータエクステンションの EmailAddress john.smith@example.com に関連付けられています。ところが Cumulus は、MobilePush Key John.Smith.MobilePush を使用して EmailAddress john.smith@example.com を送信しました。この場合、John.Smith.MobilePush のレコードに対して john.smith@example.com に関するメール同意はチェックされません。

メモ 各自の会社のニーズは異なる場合があります。詳細は、「Data 360 の同意管理と考慮事項およびベストプラクティス」を参照してください。

  2. 活動を設定するには、キャンバス上の最初のメール活動をクリックします。
  3. [メッセージ定義] ステップと [メッセージ設定] ステップを完了します。
  4. [送信オプション] タブをクリックします。
  5. [連絡禁止リスト] で [選択] をクリックします。
  6. [共有連絡禁止リスト] フォルダーをクリックします。
  7. [登録解除済み] リストを見つけ、[選択] をクリックします。
  8. [概要] をクリックします。
  9. [完了] をクリックします。
  10. 残りのジャーニー設定を完了し、[有効化] をクリックします。

ルート鍵はサブセカンドリアルタイム機能と互換性があります。ただし、Data 360 の有効な Salesforce ルート鍵がある組織でサブセカンドリアルタイムを有効にすると、ルート鍵は 24 時間以内に使用可能になります。

Data 360 のポリシーベースのガバナンス

データガバナンスポリシーは、データへのアクセス、使用、保護、管理方法を定義するルールとガイドラインです。これらのポリシーは、データ処理をセキュリティ要件、コンプライアンス基準、ビジネス目標に合わせるのに役立ちます。

Data 360 では、ポリシーベースのガバナンスを簡素化し、タグとメタデータを使用してデータ環境全体で拡張できます。

  • タグの適用: データオブジェクトと項目にタグを適用して、機密性、ビジネス目的、またはコンプライアンスのニーズに基づいて分類します。タグを使用すると、1 つのメタデータ属性に基づいて複数のオブジェクトが保護されるため、データガバナンスポリシーを拡張できます。
  • Assign custom permissions: カスタム権限を割り当てて、ポリシーを適切なユーザーに適用します。
  • ポリシー条件を定義します。タグと分類を使用してデータアクセスポリシーまたはマスキングポリシーを作成し、カスタム権限に基づいてユーザーに割り当てます。たとえば、「Non-Sensitive」 (機密なし) というタグが付けられたすべてのデータへのアクセス権を付与したり、「PII」というタグが付けられたすべての項目をマスクしたりするポリシーを定義します。
メモ ポリシーを作成または変更したら、ポリシーが有効になるまで 2 ～ 3 分待ちます。この間、ポリシーのアクセス制御は有効になりません。

主要コンポーネント

Data 360 のポリシーベースのガバナンスは、連携してデータアクセスを制御する方法を決定するいくつかのコアコンポーネントで構成されます。

  • メタデータ: データを分類および管理するオブジェクト名、データ型、タグなど、データの構造を記述します。
  • リソース: 管理されている実際のデータオブジェクトまたは項目を参照します。たとえば、顧客テーブルやメール項目などです。
  • 件名: ポリシーが適用されるユーザーまたはグループを識別します。これは、カスタム権限またはユーザー属性で定義されます。
  • ポリシー定義: 誰がどの条件でどのデータにアクセスできるかを決定する規則が含まれます。
  • ポリシー適用: 実行時にポリシーを適用し、ユーザーが参照および変更が承認されたデータにのみアクセスできるようにする実行レイヤー。

アクセス

アクセスポリシーによって、ユーザーが特定のデータを表示または操作できるかどうかが決まります。通常、これらのポリシーはアクションを許可または拒否します。

許可ポリシーでは、特定の条件を満たした場合にデータへのアクセスを明示的に許可します。たとえば、「ユーザーの地域がレコードの地域と一致するセールスレコードへのアクセスを許可」などです。許可ポリシーは通常、データにアクセスできるユーザーを定義するために使用されます。

拒否ポリシーは、他のポリシーで許可されている場合でも、データへのアクセスを明示的にブロックします。たとえば、「ユーザーがコンプライアンスチームにいない場合、社外秘としてマークされたレコードへのアクセスを拒否します。」などです。[拒否] ポリシーは [許可] ポリシーよりも優先され、より厳格な制御または例外を適用する場合に便利です。

  • Data 360 の保険契約の種類
    Data 360 では、データガバナンスで 2 つのポリシーカテゴリ (ロールベースのアクセス制御 (RBAC) と属性ベースのアクセス制御 (ABAC)) が提供されます。
  • オブジェクト、項目、およびレコードレベルセキュリティ
    Data 360 のデータガバナンスポリシーは、ユーザーロール、属性、リレーションに基づいて、オブジェクト、項目、行などのさまざまなレベルでデータへのアクセスを制御します。
  • Data 360 の動的データマスキングポリシー
    動的データマスキングでは、機密データの使いやすさ、正確性、リレーションを変更せずに非表示にします。アクセス方法に関係なく、すべての Data 360 オブジェクトと項目に適用されます。
  • Data 360 でのポリシーの適用
    ポリシーは、ユーザーがデータを作成しているか消費しているかに応じて、Data 360 のさまざまな機能領域で適用されます。ポリシーの適用は、ダッシュボードではすぐには有効になりません。

DLO
  • ユーザーは、ポリシーで許可されている DLO のみを使用できます。

  • ユーザーは、アクセスポリシーで許可されている DMO を使用できます。

データオブジェクトを使用する場合の主要な適用コールアウト

Data 360 での管理データの動作に関する主要なコールアウトを次に示します。これには、独自のポリシールールや例外も含まれます。

オブジェクト種別 ユーザーができること
DLO
  • DLO で「すべて表示」および「すべて変更」権限を持つユーザーは、すべてのメタデータを表示できます。データスペースの割り当てとポリシー制御クエリアクセス。
  • ユーザーは、アクセス権に応じて、データエクスプローラー、プロファイルエクスプローラー、クエリエディターなどのオブジェクトレベルのページでマスクされた項目を表示できます。

  • CIO には専用のタブがないため、UI での適用は CIO と共に CI プロセス定義に依存します。
  • FLS ポリシーでディメンションへのアクセスが制限されていて、集計可能な評価指標を照会すると、評価指標値によって制限されたディメンションが自動的に除外され、定義されたディメンションレベルに積み上げ集計されます。
  • FLS ポリシーでディメンションへのアクセスを制限すると、タグや明示的なポリシーが定義されていない場合でも、集計不可能な総計値は自動的に制限されます。
  • CIO をセマンティックデータモデルに追加し、ディメンションへのアクセスを制限する FLS ポリシーを適用すると、同じ集計関数を使用する総計値の表示も制限されます。
  • マスキングポリシーを適用すると、セマンティックデータモデルクエリの総計値の結果は、ポリシーで定義された丸め動作によって異なる可能性があります。
DMO
  • DMO に対する「すべて表示」および「すべて変更」権限を持つユーザーは DMO メタデータにアクセスできますが、クエリを許可するかどうかはポリシーによって決まります。
  • マスキングされた項目は、ユーザーアクセス権に応じて、データエクスプローラー、プロファイルエクスプローラー、クエリエディターなどのオブジェクトレベルのページで引き続き表示できます。マスキングが適用されるユーザーの場合、これらの項目はマスク済みとして表示されます。
検索インデックス 検索インデックスを作成すると、チャンクやベクトル DMO などの派生オブジェクトが自動的に生成され、検索可能なデータが保存されます。これらの派生オブジェクトは、ソース DMO に適用されたセキュリティポリシー (オブジェクトレベル、項目レベル、レコードレベルセキュリティなど) を継承します。これにより、検索結果と取得拡張生成 (RAG) 駆動型インサイトで元のデータのガバナンスルールが一貫して尊重されます。
データグラフ
  • ユーザーがデータグラフを使用してデータにアクセスすると、ポリシーが詳細レベルで適用されます。ユーザーはデータグラフのうち、アクセス権限のある部分のみを参照でき、制限されたデータモデルオブジェクト (DMO) と項目は結果から除外されます。
  • データグラフのタグはソース DMO から継承され、直接割り当てられません。現在、伝播されたタグはデータグラフ UI に表示されません。

データストリームおよびデータオブジェクト作成時のポリシーの動作

データストリーム、データレークオブジェクト (DLO)、またはデータモデルオブジェクト (DMO) を作成すると、Data 360 はアクセスポリシーを適用して、使用が許可されているオブジェクトと項目のみを操作できるようにします。

オブジェクト種別 ユーザーができること
データストリーム
  • データレイクオブジェクトを作成する権限を持つユーザーは、バンドルをリリースできます。
  • リリースが成功すると、結果のデータストリーム、DLO、および DMO にポリシーが適用されます。リリースを開始したユーザーにバンドルの出力へのアクセス権がない場合、それ以降は出力を表示できません。
DLO
  • ユーザーは既存の DLO から新しい DLO を作成できます。選択できる DLO は、アクセスポリシーで許可されている DLO です。
  • DLO を作成した後も、「すべて表示」権限と「すべて変更」権限がない限り、ユーザーにはその DLO をリストビューに表示する権限が必要です。
DMO
  • ユーザーは既存の DMO から新しい DMO を作成できます。選択できる DMO は、アクセスポリシーで許可されている DMO です。

  • CIO を作成したら、ユーザーはタグを適用してポリシーを定義し、CIO データへのアクセスをさらに保護できます。
  • CIO ディメンション項目が対応する DMO 項目と完全に一致する場合、タグは DMO から CIO に自動的に伝播されます。CIO ディメンションが数式から取得された場合、タグは自動的に反映されません。

プロセス定義に対するポリシーの動作

Data 360 プロセス定義は、データストリーム、変換、計算済みインサイト、セグメント、ID 解決などのデータを管理するために使用するワークフローと ToDo を記述します。これらの定義は、データ操作の作成方法と実行方法を標準化するのに役立ちます。データガバナンスポリシーは、ユーザーがこれらの定義を作成または消費したときに適用されます。

Data Data 360 でプロセス定義を作成するための主要な適用コールアウト

プロセス定義を作成するときのポリシー適用のしくみを次に示します。

  • 選択できるオブジェクトは、ユーザーのコンテキストとポリシーに従って絞り込まれます。
    • データグラフは、定義で使用される基盤となる DMO と CIO に加えて、ID、値、フラグメントの DMO へのアクセス権がユーザーにある場合に使用できます。
    • 計算済みインサイトは、定義で使用される基盤となる DMO と CIO へのアクセス権がユーザーにある場合に使用できます。計算済みインサイト出力オブジェクトへのアクセス権も必要です。
  • データオブジェクトに対する「すべて表示」および「すべて変更」権限を持つユーザーは、すべてのメタデータを表示でき、プロセス定義を作成できます。

機能領域 ポリシーの適用方法
有効化
  • データオブジェクトに対する「すべて表示」および「すべて変更」権限を持つユーザーは有効化を保存できますが、属性ライブラリマップ (ALM) の読み込みに必要な基礎となるエンティティに直接アクセスできないため、有効化定義を作成できません。

データを照会するときのポリシーの動作

データエクスプローラー、プロファイルエクスプローラー、Tableau のいずれを使用しても、Data 360 のデータを照会する場合、ガバナンスポリシーによって取得可能なデータが制御されます。メタデータが UI に表示されている場合でも、機密データを保護するためにクエリ時に実際のアクセスが適用されます。

クエリ API を使用する場合のキー適用コールアウト

独自のポリシールールや例外など、Data 360 での管理データの動作を次に示します。

一般に、データを照会する場合、次のようになります。

  • ユーザーは、ポリシーで定義されたアクセス権があればオブジェクトを照会できます。
    • ユーザーは、アクセス権があれば DMO を照会できます。DLO に対する基本的なアクセスチェックはありません。
    • ユーザーは、ID および値の DMO とそのすべての項目へのアクセス権があれば、データグラフを照会できます。データグラフ内で使用される DMO または CIO に対する基本的なアクセスチェックはありません。
    • ユーザーは、基盤となる計算済みインサイトオブジェクトへのアクセス権がある場合、計算済みインサイトを照会できます。
  • 項目適用はクエリレイヤーで適用されます。ユーザーは、ポリシーで定義されたアクセス権がある場合にのみ項目を照会できます。
  • データを照会する場合、「すべて表示」および「すべて変更」データオブジェクト権限は適用されません。
  • ユーザーは、基盤となるオブジェクトと項目へのアクセス権があれば、マスクされた項目を作成または編集できます。マスキングはクエリレイヤーで適用され、データの入力や更新を妨げることはありません。

Data 360 でのポリシーの適用

ポリシーは、ユーザーがデータを作成しているか消費しているかに応じて、Data 360 のさまざまな機能領域で適用されます。ポリシーの適用は、ダッシュボードではすぐには有効になりません。

ポリシーが正しく適用されるようにするには、ダッシュボードを更新するか、キャッシュをクリアします。

  • データストリームおよびデータオブジェクト作成時のポリシーの動作
    データストリーム、データレークオブジェクト (DLO)、またはデータモデルオブジェクト (DMO) を作成すると、Data 360 はアクセスポリシーを適用して、使用が許可されているオブジェクトと項目のみを操作できるようにします。
  • データストリームおよびデータオブジェクトを使用する場合のポリシーの動作
    Data 360 でデータオブジェクトを表示または操作する場合、アクセスポリシーによって何を表示および使用できるかが決まります。
  • データを照会するときのポリシーの動作
    データエクスプローラー、プロファイルエクスプローラー、Tableau のいずれを使用しても、Data 360 のデータを照会する場合、ガバナンスポリシーによって取得可能なデータが制御されます。メタデータが UI に表示されている場合でも、機密データを保護するためにクエリ時に実際のアクセスが適用されます。
  • プロセス定義に対するポリシーの動作
    Data 360 プロセス定義は、データストリーム、変換、計算済みインサイト、セグメント、ID 解決などのデータを管理するために使用するワークフローと ToDo を記述します。これらの定義は、データ操作の作成方法と実行方法を標準化するのに役立ちます。データガバナンスポリシーは、ユーザーがこれらの定義を作成または消費したときに適用されます。
  • Data 360 のコアアプリケーションでのポリシーの動作
    関連リストやコピー項目強化などのコアアプリケーションは、特定のポリシー動作に従います。ユーザーレベルのアクセス制御が適用される機能もあれば、システムモードで実行され、CRM レベルで追加のセキュリティ対策が必要な機能もあります。

Data 360 の保険契約の種類

Data 360 では、データガバナンスで 2 つのポリシーカテゴリ (ロールベースのアクセス制御 (RBAC) と属性ベースのアクセス制御 (ABAC)) が提供されます。

ロールベースのアクセス制御

ロールベースのアクセス制御 (RBAC) では、ロールに基づいてユーザーに権限を割り当てることで、データアクセスを管理できます。

RBAC を使用して、データレイクオブジェクト (DLO)、データモデルオブジェクト (DMO)、計算済みインサイトオブジェクト (CIO) など、データスペース内の特定のデータオブジェクトへのアクセス権を権限セットで付与します。RBAC は個々のオブジェクトに割り当てられます。

属性ベースのアクセス制御

属性ベースのアクセス制御 (ABAC) は、属性の組み合わせに基づいてデータへのアクセスを許可または拒否するデータアクセス制御モデルです。これらの属性は、ユーザー、データ、または環境に属することができます。

  • ユーザー属性: カスタム権限
  • データ属性: タグ、機密レベル、所有者、分類

ABAC では、ポリシーは実行時に属性を評価する論理条件を使用します。パフォーマンスを維持するために、ABAC ポリシーの作成にはリソースの使用状況に基づく組み込みの制限が含まれます。各ポリシーの使用方法は、ルールの数とその条件の複雑さによって異なります。より複雑なポリシーでは、データアクセス時により多くのリソースが使用されます。ポリシーを作成、更新、または削除すると、Data 360 はこの使用状況を条件要素の最大しきい値と比較します。ほとんどのユーザーはこの制限に達しませんが、複雑なポリシーがパフォーマンスに影響するのを防ぐのに役立ちます。

タグと分類

ABAC では、タグと分類を意思決定属性として追加して、アクセスを許可するかどうかを決定できます。たとえば、オブジェクトまたは項目が「社外秘」としてタグ付けされている場合や、「PII」 (個人識別情報) として分類されている場合、これらのタグを参照するアクセスポリシーを作成できます。次に、サンプルポリシーを示します。

「データが社外秘として分類されている場合、コンプライアンスチームのユーザーにアクセス権を付与します。」または、「サポートチーム外のユーザーに対して PII としてタグ付けされたデータへのアクセスを拒否」します。

この方法でタグと分類を使用すると、データの機密性とユーザーの属性の両方に適応する動的なコンテキスト対応コントロールが可能になります。これにより、ポリシー管理が簡素化され、データエコシステム全体で一貫した適用が保証されます。

  • Data 360 でのロールベースのアクセス制御ポリシーの作成
    データスペースに割り当てられたユーザーのオブジェクト権限を管理します。
  • Data 360 での「すべての許可」ポリシーの作成
    制限を適用せずに広範なユーザーアクセスを維持するには、Data 360 で [すべて許可] ポリシーを作成します。 このポリシーでは、権限セットを使用してユーザーに割り当てられたデータスペース内のオブジェクトへのアクセス権が付与されます。

Data 360 での保険契約セグメントの作成

自動車保険契約の Welcome ジャーニーのオーディエンスセグメントを作成します。

  1. Data 360 にログインします。
  2. [セグメント] タブで [新規] をクリックします。
  3. 新しいオーディエンスセグメントの基盤となる統合個人 DMO を選択します。
  4. セグメントに「New Auto Policy Holders」(新規自動保険契約者) という名前を付けて説明を追加し、公開スケジュールに 24 時間を選択します。
  5. 開始日時と有効期限を追加して、[保存] をクリックします。
  6. セグメントを作成するには、[ルールを編集] をクリックします。
  7. 属性リストから [RA_PolicyInformation_02] を選択し、[Starting Date (開始日)] を選択します。
  8. [Starting Date (開始日)] 属性をキャンバスにドラッグします。
  9. [演算子] を [最後の日数] に設定し、[日数] 項目に「30」を追加します。

  11. 属性リストから、[Has a Policy (保険契約がある)] を選択して、属性をキャンバスにドラッグします。

Tableau セマンティクスのデータガバナンス

Tableau Semantics のデータガバナンスにより、承認されたデータのみを表示および操作できます。ガバナンスは、データスペース権限と Data 360 セキュリティポリシーを組み合わせます。これらのポリシーにより、モデル設計時および Tableau でのクエリ実行時に、セマンティックモデルを表示できるユーザーと使用可能なデータが決まります。

データスペース権限

セマンティックモデルが存在するデータスペースにアクセスする権限が必要です。このアクセス権がないと、モデルは表示されません。データスペース権限は Tableau セマンティックのガバナンスの基盤を形成し、追加のセキュリティポリシーを適用する前にどのモデルが表示されるかを確立します。

ポリシーレイヤー: ABAC、OLS、FLS、RLS

モデルが表示されると、Data 360 セキュリティポリシーによって基礎となるデータへのアクセスが制御されます。これらのポリシーには、属性ベースのアクセス制御 (ABAC)、オブジェクトレベルセキュリティ (OLS)、項目レベルセキュリティ (FLS)、レコードレベルセキュリティ (RLS) が含まれます。

  • ABAC によって、セマンティックモデルへのアクセスが決まります。セマンティックモデルの項目またはオブジェクトへのアクセス権がない場合は、セマンティックモデルを表示または拡張できます。
  • OLS によって、データスペース内のどのオブジェクトにアクセスできるかが決まります。必須オブジェクトへのアクセスが拒否された場合、そのオブジェクトは非表示になり、セマンティックモデルは表示または拡張できます (ただし編集はできません)。モデル名の横にある錠アイコンで示されます。制限されたオブジェクトは、表示、編集、照会できません。
  • FLS は、オブジェクト内の個々の項目に対して同様に動作します。必須項目が制限されていると、ビューから完全に削除され、設計やクエリで使用できません。OLS と同様に、必須項目にアクセスできない場合、セマンティックモデルは参照または拡張のみ可能です。制限された項目は、表示、編集、照会できません。
  • RLS はレコードレベルで動作し、組織階層、ロール、テリトリーなどの条件に基づいてデータを動的に絞り込みます。

拒否ポリシーは、常に許可ポリシーを上書きします。OLS または FLS のために必須のオブジェクトまたは項目へのアクセス権がない場合、ABAC ではセマンティックモデルを直接編集できません。この動作により、設計フェーズとクエリフェーズの両方で機密データが保護されます。

管理アクセス

「すべてのレコードの参照」や「すべてのレコードの編集」など、上位レベルの権限を持つシステム管理者は、より広い視野を持つことができます。セマンティックモデルを開き、通常は制限されているオブジェクトや項目を含む完全なメタデータを表示できます。システム管理者は、所有者でなくてもモデルを共有できます。

システム管理者にも「すべてのレコードの編集」権限がある場合、通常のポリシーで編集がブロックされている場合でもモデルを管理できます。ただし、要求されたデータがアクセス権のない項目やオブジェクトを使用していたり、RLS で絞り込まれたり、拒否ポリシーでブロックされたりすると、クエリで返される結果が制限されたり、失敗したりします。

共有とコラボレーション

セマンティックモデルは、閲覧者、エディター、所有者のアクセスロールを介して他のユーザーと共有できます。

  • 閲覧者はモデルを開いて操作できますが、変更はできません。
  • エディターはモデルを変更できます。
  • 所有者は、モデルの編集、他のユーザーとの共有によるアクセス権の管理、セマンティックモデルの削除など、すべての操作を実行できます。所有権は移行できません。

共有を使用すると、カタログに表示されなくてもモデルを開くことができますが、Data 360 セキュリティポリシーが上書きされることはありません。モデルを開くことはできますが、引き続き ABAC、OLS、FLS、RLS によってアクセスできるオブジェクト、項目、レコードが決まります。たとえば、エディターの場合、OLS ポリシーで必須オブジェクトへのアクセスがブロックされていると、モデルを拡張できますが編集できません。拡張モデルでは、OLS または FLS によってブロックされたオブジェクトまたは項目へのアクセス権がありません。制限されたオブジェクトへのリレーションの作成など、セマンティックモデルの特定の機能がブロックされる場合があります。

Tableau Semantics では、共有は主にコラボレーション機能です。実際のデータガバナンスは、データスペース権限とセキュリティポリシーによって引き続き厳格に適用されます。

エンドツーエンドの保護

データスペース権限、ABAC、OLS、FLS、RLS を組み合わせることで、セマンティックモデルの階層的な保護が提供されます。この構造により、アクセスの管理に共有機能やコラボレーション機能に依存することなく、モデルの作成からクエリの実行までのライフサイクル全体で機密データのセキュリティを確保できます。
