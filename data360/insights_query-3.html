クエリ API を使用したハイブリッド検索クエリの実行

Data 360 でハイブリッド検索を実行するには、クエリ API を使用します。 次の例を出発点として使用します。

例

この構文は、クエリエディターでハイブリッド検索を実行します。

select * from hybrid_search(
    table(<Search_Index_DMO>),
    '<Search String>',
    '<PreFilteringColumn><Operator><Value>',
    '<Limit Results>)';

入力パラメーター

  • <Search_Index_DMO> は、インデックス DMO の API 参照名です。
  • <Search String>  はハイブリッド検索の検索テキストです。
  • <PreFilteringColumn> は事前検索条件です。
  • <結果の制限> は、返される結果の数です。

結果パラメーター

  • RecordId__c は結果の一意の識別子です。このパラメーターの値は SourceRecordId__c 項目と同じです。
  • SourceRecordId__c  は、この結果に関連付けられているソース (チャンク DMO) レコードの識別子です。チャンク DMO テーブルとの結合式で使用できます。
  • vector_score__c は、基盤となるベクトル検索インデックスによって返される類似性スコアです。
  • keyword_score__c は、基盤となるキーワード検索インデックスによって返される類似性スコアです。
  • hybrid_score__c は、キーワードスコアとベクトルスコアを組み合わせたスコアです。このスコアでは、人気や最新性などのランキング要素が考慮され、結果のランクに影響します。

この構文では、事前検索条件なしでハイブリッド検索が実行されます。

select * from hybrid_search(
       table(Knowledge_full_index__dlm),
       'How to input special mark/character when using keyboard input data field','', 2)

クエリ結果

この構文は、事前検索条件を使用してハイブリッド検索を実行します。

select * from hybrid_search(
         table(Knowledge_full_index__dlm),
         'How to input special mark/character when using keyboard input data field',
         'RecordId__c=''b7e66a34-15e3-43c6-8d84-9af80cd121d6''', 5);

select * from

LIKE 演算子は、末尾にワイルドカード文字 (%) が 1 つだけある値で使用する必要があります。無効な LIKE 検索条件の例を次に示します。

'StrField LIKE ''%prefix%'''
'StrField LIKE ''%prefix'''
'StrField LIKE ''prefix%suffix'''

LIKE 演算子では、 次の文字はサポートされていません。 たとえば、 : ^ { } [ ] ( ). 

Field__c LIKE 'https:%'

, はコロン (:) が含まれているため無効です。

事前絞り込み項目の大文字と小文字

事前絞り込み項目の名前は、大文字と小文字を区別しません。たとえば、項目の名前が My_Column_c の場合、my_column_c の filter 式はその項目を正しく参照します。ただし、検索条件内で使用される値では大文字と小文字が関係します。項目に値 SomeValue, がある場合、filter 式 My_Column_c='somevalue' または My_Column_c='SOMEVALUE' は一致せず、式 My_Column_c='SomeValue' のみがそのレコードに一致します。

デフォルトの事前絞り込み項目

チャンクデータモデルオブジェクト (CDMO) の DataSource__c 項目は、デフォルトの事前絞り込み項目です。これは、事前絞り込みクエリで常に使用できます。

1:N リレーションのオブジェクトの値の事前絞り込み

検索インデックスを作成する場合、インデックスを作成できる事前フィルタリング値は 1 つのみです。

次の例を考えてみます。インデックス付けされたチャンク データ モデル オブジェクト (CDMO) が関連レコードと 1 対 N の関係にあり、そこから事前フィルタリング値が抽出される検索インデックスを作成します。リレーションでは、CDMO {"chunkId":"1"} は {"filterRecordId"="123": "filterValue": "tag1"} と {"filterRecordId"="123": "filterValue": "tag2”} の両方に一致します。

Data 360 では、これらの絞り込まれた値の 1 つのみが取得用にインデックス付けされ、どれがインデックス付けされるかは保証されません。たとえば、Data 360 ではインデックス付け{"chunkId":"1", "filterValue":"tag1"}や{"chunkId":"1", "filterValue":"tag2"}はできますが、{"chunkId":"1", "filterValue":["tag1", "tag2”]}はできません。

ハイブリッド検索での式の結合

インデックスに関連付けられたチャンク DMO と検索インデックス DMO の両方のフィールドにアクセスするには、結合を含めます。

SELECT
  src.ArticleNumber__c,
  hsearch.hybrid_score__c
FROM
  hybrid_search(	
    TABLE(Knowledge_index__dlm),
    'DataWedge Decode Volume',
    '',
    10
  ) hsearch
  join Knowledge_chunk__dlm chnk 
on hsearch.SourceRecordId__c = chnk.RecordId__c
  join Knowledge_kav_Home__dlm src 
on chnk.SourceRecordId__c = src.Id__c

計算済みインサイト履歴の追跡

計算済みインサイトで履歴管理を開始すると、Data 360 によって計算済み履歴インサイトが作成されます。

必要なエディション

使用可能なエディション: Data 360 でサポートされるすべてのエディション。 「Data 360 Edition の可用性」を参照してください。
  1. [Calculated Insights]リスト ビューに移動します。
  2. 有効な計算済みインサイトを選択します。
    1. ドロップダウン矢印から、[Track History (追跡履歴)] を選択します。
    2. 計算済みインサイトをクリックしてレコードページに移動し、ドロップダウン矢印から [履歴を追跡] を選択します。
  3. ［Track history］ チェックボックスをオンにします。
  4. 計算済みインサイトのスケジュールと時間を選択します。
  5. [保存] をクリックします。

リストビューには、元のソース名にHistoryが付加された新しい計算済み履歴インサイトが表示されます。

履歴追跡インサイトの出力には、history_capture_ts timestamp フィールドが含まれます。

ユーザーインターフェースを使用したデータインサイトの構築

Visual Insight Builder を使用して Data 360 で総計値を作成します。インサイトビルダーは、Data 360の[計算済みインサイト]タブにある、ビジネスアナリストに焦点を絞った使いやすい評価指標作成ツールです。

次の動画で、SQL の知識を必要とせずにインサイトを作成する方法をご覧ください。

  • ビジュアルインサイトビルダーでのノードの操作
    ビジュアルインサイトビルダーでは、ローコードのドラッグアンドドロップインターフェースを使用して、ストリーミングインサイト、計算済みインサイト、リアルタイムインサイトの作成を簡略化します。ビジュアルコンポーネントは複雑なコードを置き換えるため、技術的な専門知識がなくても評価指標や式を開発できます。
  • ビルダーを使用したストリーミングインサイトの作成
    ストリーミングインサイトを作成して、Data 360 でほぼリアルタイムのデータを使用します。ストリーミングインサイトは、特定の時点のデータに焦点を絞ります。SQL 式を記述して、リアルタイムデータソースからディメンション全体のストリーミング総計値を計算できます。ストリーミングインサイトを使用して、部門間オーケストレーションを実行し、Data 360 のデータを最適化します。
  • ビルダーを使用した計算済みインサイトの作成
    Data 360 のビルダーツールを使用して、SQL を使用せずに計算済みインサイトを作成します。
  • ビルダーを使用したリアルタイムインサイトの作成
    リアルタイムデータグラフと関連データモデルオブジェクト (DMO) を使用して、リアルタイムインサイトを作成できます。関連 DMO は、リアルタイムデータグラフで定義されていない DMO ですが、リアルタイムディメンションとして使用できます。

ショッピングカートインサイトの作成

ショッピングカートインサイトを作成して、顧客とのやりとりを理解し、ジャーニーを最適化します。このプロセスには、個々のデータモデルの選択、リアルタイム処理または一括処理の選択、イベント値の定義が含まれます。ショッピングトレンドに関する貴重なインサイトを取得し、取引開始率を向上させます。

必要なエディション

使用可能なインターフェース: Lightning Experience
使用可能なエディション: Data Cloud でサポートされるすべてのエディション。Data Cloud エディションの使用可能状況を参照してください。
必要なユーザー権限
ショッピングカートインサイトを作成する Data Cloud アーキテクト

また、それらを参照するインサイトを作成するには、関連するすべての DMO およびデータグラフへの参照アクセス権も必要です。

  1. Data Cloud で、[計算済みインサイト] タブに移動し、[新規] をクリックします。
  2. データスペースを選択します。
  3. ［Create from Template］ をクリックします。
  4. [ショッピングカート] をクリックします。
  5. 顧客のモデルとして使用する個々のデータモデルオブジェクトの種別を選択します。
    統合個人を選択した場合は、ID 解決ルールセットを選択します。
  6. インサイトでデータを処理する方法を選択します。
    [Real-Time] を選択した場合は、データグラフを選択します。
  7. 前提条件ページを確認し、不完全な前提条件を修正します。このショッピングカートインサイトを作成するには、接続されたデータグラフとデータモデルオブジェクト (DMO) に特定の項目とリレーションが含まれている必要があります。
  8. [詳細] ショッピングカートインサイトの詳細を定義します。
    1. ショッピングカートインサイト名を入力します。API 参照名は自動的に入力されます。
    2. 説明を入力します。
    3. エンゲージメントイベントのアクションのイベント値を指定します。この値は一致する必要があり、大文字と小文字が区別されます。

相対期間評価指標の定義

ローリングタイムウィンドウに基づく総計値を使用して、Data Cloud のインサイトをリアルタイムで取得します。指定された過去の秒数、分数、日数など、相対的な期間を使用して総計値を決定します。

計算済みインサイト期間総計値

計算済みインサイトの場合、NOW関数を使用して動的または相対的な時間枠を確立します。SECOND_ADD 関数と SECOND_SUB 関数は、メトリックの正確な時間枠を定義するためのより正確な制御を提供します。

  • 可用性:
    • NOW、SECOND_ADD、およびSECOND_SUB機能は、ビジュアルインサイトビルダーの変換ノードで使用できます。
    • これらの関数は、SQL Functions for Insightsに含まれます。
  • フィルタリング: ビジュアルビルダーのフィルタノード「相対日時演算子」オプションを使用して、相対時間フィルタを定義できます。
  • 柔軟性: 秒単位から年単位 (365 日以上) まで、設定可能な期間で動的な評価指標を定義および計算できます。

リアルタイム時間枠評価指標

動的期間総計値を使用して、特定の期間の総計値をリアルタイムで計算します。これらの総計値は、最近の活動によって通知されるパーソナライズされた商品のおすすめに使用します。たとえば、次のことができます。

  • 過去 10 分間の Web サイトインタラクションを数えて、最近の参照数に似た商品をおすすめします。
  • 過去 10 分間に表示されなかった商品を削除します。

リアルタイムインサイトによる評価指標の更新方法

データイベントが処理されると、リアルタイムインサイトで総計値が更新されます。

  • Calculation at query time (クエリ時の計算): この指標の値はグラフクエリ時に計算されます。
  • イベントを処理しない: イベントが処理されない場合、指標値は定義された相対時間枠に基づいて計算されます。たとえば、総計値が「過去 10 分間の商品クリック数」で、この間にクリックがない場合、総計値は 0 になります。
  • クライアント側の処理: グラフクエリ時に真の指標を取得するには、リアルタイムグラフクライアントがクライアント側のリアルタイムインサイトデータを処理する必要があります。

サブ指標と時間バケットを使用したデータ集計の合理化

リアルタイムグラフ内のデータ集計を合理化し、ストレージを最小限に抑えるために、時間枠プロセスではユーザー定義の期間内のサブ指標と時間バケットが使用されます。このプロセスにより、すべてのイベントをリアルタイムグラフに保存する必要がなくなります。

  • 仕組み:リアルタイム イベントを処理するときに、NOW 関数は 5 分のサブタイム ウィンドウ内の各イベントのイベント時間を比較して、適切なウィンドウ サイズを決定します。この関数は、5 つの異なるウィンドウ種別を階層順で適用し、各種別は計算時間に関連する特定の時間範囲を対象とします。
  • 自動ディメンション作成: 動的時間枠が定義されている場合、ディメンションwindow_start__cとwindow_end__cがリアルタイムインサイトディメンションとして作成されます。
  • ストレージコストの改善: 時間枠プロセスでは、イベントの正確な数ではなく、おおよその評価指標が使用される場合があります。このプロセスは、最新のデータを小さくて正確なバケットに保存するように最適化され、古いデータを大きなバケットにグループ化して、精度とストレージコストのバランスを取ります。

ウィンドウの種類とロジック:

  • 5 分ウィンドウ (最新データ)

  • 1 時間枠 (最近のデータ)
    • 対象: 1 時間前から 1 日前まで
    • 最大バケット数: 23

    • 対象: 1 日前から 1 か月前まで
    • バケットの例: [2025-03-19 00:00 - 23:59]、[2025-03-20 00:00 - 23:59]

    • 対象期間: 1 か月前から 1 年前
    • バケットの例: [2025-02-01 00:00 - 2025-02-28 23:59]、[2025-03-01 00:00 - 2025-03-31 23:59]
    • 最大バケット数: 11
  • Yearly Windows (Oldest Data) (年間ウィンドウ (最も古いデータ))
    • 対象: 計算時間から 1 年以上経過したすべてのデータ
    • バケットの例: [2024-01-01 00:00 - 2024-12-31 23:59]、[2023-01-01 00:00 - 2023-12-31 23:59]

ショッピングカートインサイトテンプレート

Data 360 ショッピングカートインサイトテンプレートでは、顧客のショッピングカートのアクションに基づいて計算済みインサイトまたはリアルタイムインサイトが作成されます。品目の追加から購入の完了または破棄まで、ショッピングカートでの顧客とのやりとりを分析できます。Shopping cart Insightsでは、Checkout プロセスを通じた顧客のジャーニーを把握できます。

必要なエディション

使用可能なエディション: Data 360 でサポートされるすべてのエディション。 「Data 360 Edition の可用性」を参照してください。

このインサイトは、次の作業に役立ちます。

  • 人気のある商品の組み合わせを特定します。
  • カート破棄の一般的なポイントを特定します。
  • カートの完了に対するプロモーションまたは割引の影響を理解します。
  • Checkout フローを最適化して摩擦を軽減します。
  • 商品のおすすめとマーチャンダイジング戦略を改善します。

顧客のモデル化

ショッピングカートインサイトは、個人データモデルまたは統合個人データモデルでモデル化されます。このモデルは、顧客とそのショッピングカート環境を表します。

  • 個人: 顧客のショッピングカートは、顧客が使用するデバイスまたはブラウザーごとに異なります。
  • 統合個人: 顧客のショッピングカートはすべてのデバイスとブラウザーで共有されます。

    統合個人を使用するには、関連する ID 解決ルールセットを選択します。ルールセットでは、複数のショッピングセッションで顧客を識別する方法を定義します。Salesforce ヘルプの「ID 解決ルールセット」を参照してください。

ショッピングカートデータの処理

ショッピングカートインサイトを作成するには、計算済みインサイトとリアルタイムインサイトのいずれかを選択します。

計算済みインサイト
計算済みインサイトは、通常スケジュールに従ってデータをバッチで処理します。この方法は、すぐに更新する必要のない分析に適しています。履歴データは、トレンド分析や、より長期間にわたる顧客の行動を掘り下げるために使用します。
リアルタイムインサイト
リアルタイムのインサイトでは、継続的に更新されるデータが提供され、顧客のアクションが発生したときに反映されます。リアルタイムインサイトにはリアルタイムのデータグラフが必要であり、現在のカートの内容に基づいてパーソナライズされたオファーをトリガーしたり、即時放棄のリスクを特定したりするなど、即時対応に不可欠です。Salesforce ヘルプの「データグラフ」を参照してください。

イベント追跡は、顧客がショッピングカートに関連するアクションを取得するために不可欠です。これには、品目の追加、品目の削除、数量の更新、Checkout の開始、購入の完了に関するイベントが含まれます。

  • Purchase event (購入イベント): Successful order completion (成功した注文完了)。

評価指標には、顧客生涯価値 (LTV)、参照回数の多いカテゴリ、顧客満足度スコア (CSAT)、その他の評価指標を含めることができます。

インサイトを作成したら、データアクションが含まれるストリーミングインサイトで有効にします。

計算済みインサイト

計算済みインサイトを使用して、Data 360のデジタル状態全体に関する複数ディメンションの評価指標を定義して計算します。評価指標はプロファイル、セグメント、母集団レベルで作成できます。たとえば、チャネルレベルでパフォーマンスを評価したり、商品評価指標を使用して購入行動や閲覧行動を把握したりできます。

マーケティング担当者は、評価指標、ディメンション、および検索条件を使用して、有効化のセグメント条件とパーソナライズ属性を定義できます。データアナリストは、CRM Analytics でインサイトを視覚化して、データパターンを把握することもできます。

計算済みインサイトは、さまざまな評価指標を分析することで、カスタマージャーニーの各フェーズを理解するのに役立ちます。次のような利点があります。

  • 詳細な分析を行うための分析関数を使用して、Data 360 の大規模なデータに関する総計値を作成します。たとえば、顧客を支出またはエンゲージメントスコアでランク付けします。

  • ロジック、数学、統計、時系列関数、複雑なワークフローを使用してカスタム評価指標を計算します。

  • ベースデータが変更されたときに計算済みインサイトを自動的に再計算します。計算済みインサイトにより、増分データの変更が自動的に追加されます。

  • ポイント & クリックインサイトを作成するには、ビジュアルインサイトビルダーにアクセスします。SQL ベースのインサイトの作成環境では、データエンジニアにロールと経験に応じて適切なツールが提供されます。

  • セグメンテーションと有効化に統合されているインサイトをアクションに変換します。

ストリーミングインサイト

ストリーミングデータの評価指標を作成して、インサイトをよりすばやく取得します。ストリーミングインサイトは、直近の期間のリアルタイムエンゲージメントデータに基づく集計クエリです。インサイトは、Web SDK や Mobile SDK などのストリーミングデータソースのデータを処理します。ストリーミングインサイトを使用して、ほぼリアルタイムで時系列集計を作成し、Data 360 でオーケストレーションやデータアクションを促進できます。

注意: セグメントと有効化では、ストリーミングインサイトはサポートされていません。

ストリーミングインサイトとデータアクションを使用して、さまざまな使用事例をサポートできます。次の例を参照して、この機能を適用する方法を確認してください。

  • サービスとサポート: 顧客がサポートに電話する前にトラブルシューティングページにアクセスした。この情報があれば、サポートは顧客が試行した不要なトラブルシューティング手順をスキップできます。
  • インテリジェントルーティング: Service Cloud で使用すると、顧客がケースをエスカレーションした場合に PagerDuty に通知を送信します。
  • 顧客のフィードバック: ほぼリアルタイムの顧客レビューを傍受し、ケースの作成など、満足度向上アクションを促進します。
  • Account Engagement (取引先エンゲージメント): 顧客エンゲージメントシグナルの無効な取引先をほぼリアルタイムで代行受信して、再エンゲージメントを促進します。
  • ポイント残高: 注文トランザクションとソーシャルシェアに基づいて Salesforce CRM のポイント残高を更新します。
  • ログスキャン: エラーコードに基づいてストリーミングデバイスのログデータを絞り込み、最も頻繁に発生するエラーを見つけて、デバイスの保守が必要かどうかを判断します。
  • リードスコアリング: ほぼリアルタイムのユーザーアクション (顧客がフォーラムで商品機能を要求した場合など) に基づいてリードスコアリングを実行します。

リアルタイムインサイト

リアルタイムインサイトを使用して、Web サイトのより複雑なパーソナライズロジックを作成します。リアルタイムインサイトを使用して、Web サイトの累積活動を追跡し、ユーザーの活動が定義されたしきい値を満たしているかどうかを確認できます。

たとえば、顧客の有効な閲覧行動を使用して次のことを行います。

  • 顧客が最も関心を持っている商品を計算し、パーソナライズされたおすすめを提供します。
  • 顧客のカート内の品目の金額を計算して、割引の対象となるかどうかを確認します。
  • 顧客が商品をクリックした回数を取得して、商品カテゴリの設定を追跡します。

リアルタイムデータグラフと関連データモデルオブジェクト (DMO) を使用して、リアルタイムインサイトを作成できます。Data 360 は、インサイトを計算してデータグラフに保存します。セグメンテーションと有効化を含むリアルタイムインサイトをリアルタイムデータグラフの一部として使用できます。

データグラフノードの検索条件の設定

親ごとに子レコードの設定可能な制限を適用することで、安定した予測可能なデータグラフを確保します。子レコードの制限を設定すると、制御とカスタマイズが強化され、項目に基づいて選択順序 (昇順または降順) を指定できます。子レコードの最大数を 1000 個まで設定することも、デフォルト値の 100 個を使用することもできます。 この機能強化により、複雑なデータグラフ環境でカーディナリティを管理し、パフォーマンスを維持するためのスケーラブルで使いやすいソリューションが提供されます。さらに、エンゲージメントカテゴリデータモデルオブジェクト (DMO) の場合、[最近] 検索条件オプションを使用して、期限に基づいてレコードを並び替えます。

データグラフの計算済みインサイト (CI) ノードの並び替えと制限の検索条件を設定することもできます。この設定により、最終的な JSON 出力に含まれる CI レコードの数を制限し、並び替え項目と並び替え順を指定して、優先されるレコードを制御できます。

CI ノードと DMO ノードの動作の違いは次のとおりです。

  • CI ノードの並び替えと制限の検索条件はオプトインです。DMO とは異なり、CI ノードではデフォルトのレコード制限や並び替え順が適用されません。CI ノードごとに並び替え検索条件と制限検索条件を明示的に設定する必要があります。
  • CI ノードの並び替えと制限の検索条件設定は、Connect API を介してのみ使用できます。UI はサポートされていません。
  • CI ノードで並び替えと制限の検索条件を設定したら、設定を更新できますが、完全に削除することはできません。

Data 360 でのデータのクエリ

クエリは、Data 360 からの特定の情報に対する構造化された要求です。これは、データの正確な質問に似ています。Data 360 では、データを照会する方法が複数用意されています。

  • 統合アプリケーション: クエリエディターやDBeaverなどの統合アプリケーションを使用して、データを視覚的に探索および照会します。

  • Data 360 Connect API: Connect REST API を使用して、モバイルアプリケーション、Web サイト、およびサードパーティアプリケーションを接続し、絞り込まれたローカライズされたデータを取得します。

  • Data 360 SQL: Data 360 SQLを使用して、正確なクエリを記述し、データに関する非常に具体的な情報を取得します。クエリの記述についての詳細は、「 Data 360 でのデータのクエリ」を参照してください。

  • クエリ統合: クエリ統合を使用して、データを Data 360 に複製することなく、パートナーが管理するコンピューティングを照会します。「クエリ統合」を参照してください。

セカンダリインデックスを使用したクエリの最適化

データレークオブジェクト (DLO) またはマテリアライズドデータモデルオブジェクト (DMO) でセカンダリインデックスを作成すると、Data 360 は定義されたセカンダリ項目値に基づいてデータをすばやく検索して返します。セカンダリインデックスを使用すると、パフォーマンスが向上し、クレジット使用量が減少します。

Data 360 では、オブジェクトに自動的にインデックスが付けられます。[プロファイル] カテゴリと [その他] カテゴリでは、インデックスが主キーになります。[エンゲージメント] カテゴリの場合、インデックスは [イベント時刻項目] です。セカンダリインデックスを使用して、プライマリキー以外の項目を使用してデータを絞り込み、結合できるため、クエリのパフォーマンスが向上します。

Data 360 では、セカンダリ インデックスは、指定されたフィールドを新しいインデックスとして追加する、提供された DLO またはマテリアライズド DMO での一括処理データ変換です。

使用事例とベストプラクティス

セカンダリインデックスを作成するときは、次の指針を考慮してください。

  • セカンダリインデックスを使用すると、プライマリ以外の項目で頻繁に絞り込む大規模な DLO やマテリアライズド DMO のクエリ速度を改善できます。
  • セカンダリインデックスは、多くの異なる値を持つ項目で絞り込むクエリで最適に機能します。クエリで返されるオブジェクトはほぼ一意です。たとえば、customer-id、phone number、email、または「Global ID」項目です。
  • セカンダリインデックスを使用して、大きなオブジェクトのデータの範囲をすばやく検索します。たとえば、セカンダリインデックスを使用して、定義された郵便番号範囲内の顧客を検索します。
  • セカンダリインデックスを使用すると、顧客セグメントや集計された総計値などの具体化された DMO のクエリを高速化できます。
  • クエリで最も効率的なインデックスが使用されるように、1 つの DLO または DMO に複数のセカンダリインデックスを作成できます。
  • 共有が容易で一貫性のある設定になるように、セカンダリインデックス設定を標準データキットにパッケージ化することを検討してください。

クレジット使用量についての詳細は、「セカンダリインデックスの請求に関する考慮事項」を参照してください。

セカンダリインデックスと SQL

  • DLO または DMO セカンダリインデックス項目に対応付けられた項目で絞り込むデータモデルオブジェクト (DMO) クエリでは、セカンダリインデックスを使用してクエリのパフォーマンスを向上させます。
  • WHERE句 （フィルタ） では、 セカンダリインデックスは、 インデックス付けされた項目の直接一致でのみ機能します 。インデックス付き項目は、計算、関数、あいまいなパターンに基づくことはできません。
  • 主項目以外の項目で 2 つの大きなオブジェクトを結合する場合、一方のオブジェクトの行数が少ないほど結果が改善されます。
  • セカンダリインデックスと別のフィールドで絞り込む場合は、AND 句を使用します。セカンダリインデックスでは、他の項目が評価される前に結果セットが絞り込まれます。

制限事項

セカンダリインデックスを定義するときは、次の制限事項を考慮してください。

  • セカンダリ インデックスでは、ゼロコピー Data 360 オブジェクトまたは非構造化 DLO はサポートされません。
  • セカンダリインデックスでは、DevOps データキットや管理パッケージはサポートされません。
  • セカンダリインデックスは、マテリアライズド DMO (派生、ブリッジ、または変換種別) でのみサポートされます。非マテリアライズド DMO (基礎となる物理テーブルのないシンプルなビュー) はインデックス付けできません。
  • コンパニオン組織ではセカンダリインデックスを作成できません。ただし、コンパニオン組織からホーム組織の共有データスペースの DLO へのクエリでは、定義されたセカンダリインデックスが使用されます。
  • Data 360 では、セカンダリインデックスが毎日更新されます。オブジェクトが更新された場合、クエリは最初にセカンダリインデックスをスキャンしてから、ベースオブジェクトの新しい値をスキャンします。セカンダリインデックスは、エンゲージメント DLO、最大 24 時間ごとに更新される DLO、または最大 24 時間ごとに更新されるマテリアライズド DMO に最適です。

次のステップ

  • セカンダリインデックスの請求に関する考慮事項
    セカンダリインデックスを使用すると、データサービスクレジットが消費されます。セカンダリインデックスの使用は、次の使用量種別の請求に使用されるクレジットの消費に影響します。
  • セカンダリインデックスの作成
    Data 360でセカンダリ インデックスを作成し、プライマリ キー フィールド以外のデータ取得を最適化することで、クエリのパフォーマンスを向上させ、DLO(データ レイク オブジェクト)またはDMO(マテリアライズド データ モデル オブジェクト)のクレジット使用量を削減します。

リアルタイムデータグラフでのレコードのキャッシュとユーザーセッションの長さ

キャッシュに保持されるレコード数とユーザーセッションの長さを管理するようにリアルタイムデータグラフを設定します。

レコードキャッシュ

レコードキャッシュでは、最近アクティブになった訪問者のレコードがリアルタイムレイヤーに保持され、Web サイトまたはアプリケーションの最初のページですぐにパーソナライズできます。レコードキャッシュが有効になっている場合、最近有効になった既知の訪問者のプロファイルおよびエンティティデータはリアルタイムレイヤーで引き続き使用でき、ライブセッション中に Data360 Lake House レイヤーから取得する必要はありません。

レコードキャッシュが無効になっている場合、プロファイルデータは最初に Data360 Lake House レイヤーから取得する必要があるため、既知の訪問者が最初にアクセスしたページにすぐにパーソナライズが表示されない可能性があります。システム条件によっては、パーソナライズが表示されるまでこの取得に時間がかかる場合があります。

レコードキャッシュが無効になっている場合、キャッシュが無効のままになっている月は、1 秒未満のリアルタイムプロファイルとエンティティエンタイトルメントは消費されません。

ユーザーセッションの長さ

セッションの長さでは、ユーザーが Web サイトとのエンゲージメントを停止してからセッションが有効とみなされる時間を定義します。タイムアウト期間を 30 分に設定すると、ユーザーからの最新のエンゲージメントから 30 分後にユーザーのセッションが無効になります。31 分以降に発生するエンゲージメントは新しいセッションになります。

Data 360 では、通常の状態で必要なセッションの長さが維持されます。ただし、Web トラフィックが急増すると、セッションが予想より早く終了することがあります。

セッションの有効期限の業界標準は、無操作状態が 30 分間です。サポートされるセッションの最大期間は 48 時間です。

基本ベクトル検索

この構文では、インデックスデータモデルオブジェクト (DMO) 全体でベクトル検索を実行し、定義された文字列を検索します。

    
SELECT * 
FROM vector_search(TABLE(<Your_Vector_Embedding DMO>), 
  '<Search_String>', 
  '<PreFilteringColumn><Operator>"<Value>"', 
  '<k=topK results>'
)

この場合、次のようになります。

<Your_Vector_Embedding>
インデックス DMO の API 参照名。
Search_String
ベクトル検索の検索文字列。
PrefilteringColumn

主キー項目のスカラー項目を絞り込んで検索を制限する Boolean 式。事前フィルタリングについての詳細は、「ベクトル検索クエリ式と事前フィルタリング」を参照してください。

k=topK_results

インデックスおよびチャンク DMO を使用したベクトル検索

この構文は、インデックス DMO とチャンク DMO でベクトル検索を実行します。


SELECT
  v.score__c AS Score__c,
  c.chunk__c AS Chunk__c
FROM
  vector_search(
    TABLE(<Your_Vector_Embedding_DMO>),
    '<Search_String>',
    'language = \'English\' AND status = \'active\'',
    10
    ) v
JOIN
  <Your Chunk DMO> c ON v.RecordId__c = c.RecordId__c
  AND c.KQ_RecordId__c IS NOT DISTINCT FROM v.KQ_RecordId__c
ORDER BY 1
LIMIT 10

この場合、次のようになります。

Score__c
入力検索文字列に対する各ベクトルの類似性スコア。
Chunk__c
ベクトル埋め込みの生成に使用されたチャンク。
language=\'English\' AND status=\'active\'
2 つの検索条件を使用した事前絞り込みの例。これらの検索条件は、論理AND演算子を使用して結合されます。
10
上位 10 件の結果を返します。
<チャンク DMO>
チャンク DMO の API 参照名。
RecordId__c and KQ_RecordId__c
NULL 値を回避しながら、RecordID とキー修飾レコード ID の両方で join ステートメントが一致します。DMO と DLO を結合するときは、ID が重複しないようにキー修飾子を使用します。

DMO と非構造化データモデルオブジェクト (UDMO) を使用したベクトル検索

この例では、ベクトル検索を実行し、関連するテキストチャンクとそのスコアを取得して、チャンクのソースドキュメントのファイルパスを指定し、上位 10 件の結果を返します。


SELECT
  v.score__c AS Score__c,
  c.chunk__c AS Chunk__c,
  u.FilePath__c AS FilePath__c
FROM
  vector_search(TABLE(<Your Vector_Embedding DMO>), '<Search String>', '', 10) v
JOIN
  <Your_Chunk_DMO> c ON v.RecordId__c = c.RecordId__c
  AND c.KQ_RecordId__c IS NOT DISTINCT FROM v.KQ_RecordId__c
JOIN
  <Your_UDMO> u ON c.SourceRecordId__c = u.FilePath__c
ORDER BY 1 DESC
LIMIT 10;

この場合、次のようになります。

Your_UDMO
チャンクの作成に使用される UDMO の API 参照名。
FilePath__c
チャンクとベクトル埋め込みの作成に使用された各ファイルの相対パス。

事前絞り込み項目の大文字と小文字

事前絞り込み項目の名前は、大文字と小文字を区別しません。たとえば、項目の名前が My_Column_c の場合、my_column_c の filter 式はその項目を正しく参照します。ただし、検索条件内で使用される値では大文字と小文字が関係します。項目に値 SomeValue, がある場合、filter 式 My_Column_c='somevalue' または My_Column_c='SOMEVALUE' は一致せず、式 My_Column_c='SomeValue' のみがそのレコードに一致します。

デフォルトの事前絞り込み項目

チャンクデータモデルオブジェクト (CDMO) の DataSource__c 項目は、デフォルトの事前絞り込み項目です。これは、事前絞り込みクエリで常に使用できます。

1:N リレーションのオブジェクトの値の事前絞り込み

検索インデックスを作成する場合、インデックスを作成できる事前フィルタリング値は 1 つのみです。

次の例を考えてみます。インデックス付けされたチャンク データ モデル オブジェクト (CDMO) が関連レコードと 1 対 N の関係にあり、そこから事前フィルタリング値が抽出される検索インデックスを作成します。リレーションでは、CDMO {"chunkId":"1"} は {"filterRecordId"="123": "filterValue": "tag1"} と {"filterRecordId"="123": "filterValue": "tag2”} の両方に一致します。

Data 360 では、これらの絞り込まれた値の 1 つのみが取得用にインデックス付けされ、どれがインデックス付けされるかは保証されません。たとえば、Data 360 ではインデックス付け{"chunkId":"1", "filterValue":"tag1"}や{"chunkId":"1", "filterValue":"tag2"}はできますが、{"chunkId":"1", "filterValue":["tag1", "tag2”]}はできません。

リアルタイムデータグラフのセッション延長

リアルタイムデータグラフと標準データグラフの一貫性を維持するために、セッション拡張では標準グラフが更新されている間、データが長期間保持されます。
