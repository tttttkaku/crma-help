Data 360 プロファイル関連レコード Lightning アプリケーションの設定

Lightning アプリケーションビルダーを使用して、統合プロファイルに関連するレコードを表示するように Data 360 Profile Related Records アプリケーションを設定します。

必要なユーザー権限  
Lightning アプリケーションビルダーで Lightning ページを作成および保存する 「アプリケーションのカスタマイズ」

このアプリケーションは、デフォルトでプロファイルエクスプローラーのプロファイル詳細ページに追加されます。接続されている Salesforce 組織の取引先責任者レコードホームページにこのアプリケーションを追加することもできます。

  1. Data Cloud Lightning アプリケーションを設定する Lightning ページに移動します。
  2. ページの [設定] メニューから、[編集ページ] をクリックして Lightning アプリケーションビルダーにアクセスします。
  3. Data Cloud プロファイルの関連レコードアプリケーションをレコードホームページに追加します。すでに追加されている場合は、アプリケーションをクリックして選択します。
  4. データスペースを選択します。[デフォルト] が唯一のデータスペースオプションの場合、[デフォルト] を選択します。
  5. プライマリデータモデルオブジェクト (DMO) を選択します。
    プロファイルデータはこのオブジェクトから取得されます。
  6. 統合個人リンクオブジェクトが入力されている間、待機します。
  7. 関連するデータモデルオブジェクトを選択します。選択したオブジェクトの項目のレコードがアプリケーションに表示されます。
    統合個人 DMO に直接関連するオブジェクトのみを使用できます。
  8. [選択] をクリックして、[項目を選択] ウィンドウを開きます。最大 10 個の項目を [選択可能] から [選択済み] に移動し、[OK] をクリックします。選択した項目のデータがアプリケーションに表示されます。
  9. プロファイル関連レコードアプリケーションに表示するアイコンを選択します。
  10. コンポーネントを保存して有効化します。

Data Cloud One

Data Cloud One を使用して、マルチ組織アーキテクチャを合理化し、Data 360 へのアクセスを簡素化します。Data Cloud One では、接続されたコンパニオン組織のユーザーが 1 つの統合 Data 360 ホーム組織からデータと Data 360 機能にアクセスできます。

    Data 360 コンパニオン接続では、1 つの Data 360 と 1 つ以上の Salesforce 組織間の双方向接続を作成できます。コンパニオン接続は標準接続の機能に基づいて構築され、統合データをコンパニオン Salesforce 組織に同期します。コンパニオン接続を使用すると、Salesforce 組織は、会社のすべてのデータのデータを使用して構築された顧客の全体像を把握できます。

コンパニオン組織からの Data Cloud One へのアクセス

コンパニオン組織では、Data 360 アプリケーションの代わりに Data Cloud One アプリケーションを使用できます。これを使用して、プロファイルエクスプローラーなどの Data 360 機能にアクセスします。

必要なエディション

必要なユーザー権限
Data Cloud One にアクセスする 「Data Cloud One ユーザー」権限セット
  1. コンパニオン組織で、アプリケーションピッカーで Data Cloud One を検索します。
  2. [Data Cloud One] を選択します。

一部の Data 360 機能はコンパニオン組織では使用できません。

  • コンパニオン組織の Data 360 機能
    Data Cloud One アプリケーションを使用して、Data 360 ホーム組織から共有される Data 360 機能にアクセスします。フルアクセスとは、適切な権限セットを持つユーザーが、ログインしている組織の機能の設定を作成、更新、削除できることを意味します。
  • コンパニオン組織の Data 360 接続の詳細
    コンパニオン組織では、[設定] でホーム組織を特定し、組織と共有されているデータスペースを確認し、コンパニオン組織の接続状態を確認できます。接続済み組織名とインスタンスの詳細を使用して、組織が接続されている Data 360 と、組織が配置されている地域を特定します。
  • ユーザーへの Data Cloud One アクセス権の付与
    コンパニオン組織のユーザーが組織の Data Cloud One にアクセスするには、「Data Cloud One ユーザー」権限セットが割り当てられている必要があります。共有データスペースのデータを表示するには、ユーザーに必要なデータスペースが関連付けられた権限セットが割り当てられている必要があります。

Data Cloud One でのタギング、ポリシー、およびアクセス

Data Cloud One では、Data 360 の他のバージョンと同じタギング、ポリシー作成、アクセス管理が使用されますが、仕様が追加されています。Data Cloud One では、タギングとポリシー作成の両方で、ホーム組織は、さらに同期を実行できるスタンドアロン組織として機能します。

タグ管理

Data Cloud One では、タグ、分類、分類はホーム組織でのみ作成できます。Data Cloud One の初期設定時に、「0 日目」同期によって、既存のすべてのガバナンスアーティファクトがホームからコンパニオン組織に転送されます。最初の同期後は、自動的な増分更新によって両方の組織の整合性が維持されます。これらの同期は、Data Cloud One 機能を有効にする前でも後にでも、タグが最初に作成されたタイミングに関係なく実行できます。

タグの割り当て

コンパニオン組織でのタグの割り当てには次の制限があります。

  • ユーザーはコンパニオン組織内でタグを割り当てることができますが、その特定のコンパニオン組織内でローカルに作成されたオブジェクトにのみ割り当てることができます。
  • ホーム組織で作成されたオブジェクトのオブジェクトタグは、自動的にコンパニオン組織に同期されます。これらのオブジェクトのタグ割り当ては、コンパニオン組織では変更できません。

タグ伝達

ホーム組織では、組織で作成された親オブジェクトと子オブジェクト間でタグを伝達できます。

コンパニオン組織では、ホーム組織オブジェクトの更新は、オブジェクトの同期対象に自動的に同期されます。変更は、そのオブジェクト上に作成されたローカルのオブジェクトには自動的に反映されません。反映するには、ホーム組織で同期されたオブジェクトをローカルオブジェクトに手動で同期します。

同期済みオブジェクト間でタグを伝達することはできません。

ライセンス制御はホーム組織にあります。コンパニオン組織は、対応するアドオンがホーム組織から購入された場合にのみ機能にアクセスできます。

接続組織のメタデータ所有権

オブジェクトは、Data 360 と共有されている場合や、Data 360 から他の接続済み組織と共有されている場合でも、そのオブジェクトが元の組織によって所有されます。編集または削除できるのは、そのデータを所有する組織のデータのみです。

[接続で所有] 項目は、組織の接続名を使用して、レコードを所有する組織を識別します。レコードは、共有データスペースで共有されている場合でも、そのレコードを所有する組織でのみ変更できます。

ホーム組織が所有するレコードは、データスペースにアクセスできるコンパニオン組織から参照できます。ただし、コンパニオン組織が所有するレコードはコピーできますが、共有データスペース内にある場合でも、他の組織から参照することはできません。

Sandbox 組織の Data 360 One に関する考慮事項

Data 360 One クラスタを設定する前に次の考慮事項を確認して、よくある間違いを回避します。Data 360 One 接続を確立する前に本番組織から Sandbox 組織を作成するか、Data 360 One クラスタを再作成する前に Data 360 メタデータをクリーンアップします。Data 360 One を使用して Sandbox 組織を本番組織に接続することはできません。

警告

まず本番組織から Sandbox 組織を作成し、次に Data 360 One 接続を作成することをお勧めします。接続は Sandbox 組織にコピーされません。Sandbox コンパニオン組織からコピーした Data 360 メタデータをクリーンアップするまで、Data 360 One 接続を再確立することはできません。

メモ

Data 360 One Sandbox を作成するには、取り込み API コネクタを有効化し、remote_connection_full-sync_feed および remote_connection_incremental-sync_feed データストリームが有効であることを確認します。

Sandbox にコピーするものとコピーされないもの

これらの項目は Sandbox 組織にコピーされます。

  • Data 360 および Data 360 One Companion 組織ライセンス
  • Data 360 メタデータ

これらの項目は Sandbox 組織にコピーされません。手動で追加または作成します。

  • Data 360 データ
  • Data 360 One コンパニオン接続

Data 360 データは Sandbox 組織にコピーされないため、Sandbox 組織にサンプルデータを入力することをお勧めします。少数の代表的なデータを使用すると、設定をテストしながらデータ処理コストを節約できます。

設定とメンテナンスのベストプラクティス

  • Data 360 One 接続を確立する前に Sandbox 組織を設定します。

    コンパニオン接続を確立する前に、本番組織から Sandbox 組織を作成することをお勧めします。

  • Sandbox 組織から Data 360 メタデータをクリーンアップします。

    既存の Data 360 データが含まれる組織を Data 360 One コンパニオンとして接続することはできません。本番 Data 360 One クラスタを作成した後に Sandbox 組織を作成する場合、Data 360 クリーンアップおよびリセット機能を使用してコピーしたメタデータを削除し、コンパニオン接続を手動で再確立します。

  • ホーム組織の Sandbox で Data 360 を手動で有効化します。

    Sandbox 組織では、Data 360 は自動的に有効になりません。有効にするには、Data Cloud の [設定] ホームに移動します。

  • 更新する前に、コンパニオン Sandbox 組織を自宅から切断します。

    Sandbox を更新すると、既存の組織が完全に破壊され、新しい組織 ID が生成されるため、Data 360 One 接続は切断されますが、削除されません。ホーム組織にログインし、Data 360 設定に移動してコンパニオン組織を切断し、接続を再確立します。

  • 本番組織のライセンスを照合します。

    Sandboxの設定後にData 360 Oneコンパニオン組織にライセンス供与する場合は、一致する本番ライセンスを使用してData 360 One Companion OrgライセンスをSandboxに追加します。

Data 360 One Sandbox 組織のコストに関する考慮事項

クレジットを消費する Data 360 データサービスまたはその他のサービスを使用する場合、クレジットは本番ホーム組織の消費カードから減算されます。Sandbox 組織では使用量が割引されます。

Data Cloud One 組織のバージョン不一致エラー

Data Cloud One では、自宅組織とコンパニオン組織の間で混在バージョンがサポートされますが、バージョンの不一致により、状況によっては一時的なメタデータ同期の遅延が発生する可能性があります。Salesforce のマイナーバージョン間でオブジェクトのスキーマが変更されると、ホーム組織とそのコンパニオン組織間のメタデータ同期が遅延する可能性があります。同期が一時的なエラー状態であっても、以前に同期されたすべてのメタデータを引き続き使用できます。バージョンの不一致エラーは、両方の組織が同じバージョンにアップグレードされるとすぐに解決されます。

重要 バージョンの不一致が原因で同期が遅延したりエラー状態になったりしても、以前に同期されたすべてのメタデータを引き続き使用できます。組織のバージョンを確認して不一致を確認し、同期エラーが自動的に解決するまで 24 ～ 72 時間待ちます。

Data Cloud One ホーム組織とコンパニオン組織間でバージョンの不一致が発生することがあります。マイナーアップグレードは、2 週間に 1 回程度頻繁に発生します。通常、メジャーリリース中の更新には下位互換性がありますが、マイナーバージョンによってはスキーマが変更されます。新しいバージョンの Salesforce は、24 ～ 72 時間にわたってさまざまなデータセンターに異なるタイミングでロールアウトされます。ホーム組織とコンパニオン組織が異なるデータセンターでプロビジョニングされている場合 (特に異なるリージョンにある場合)、ロールアウト期間中にバージョンが一致しない可能性があります。

バージョンの不一致の影響

  • 新しいコンパニオン接続を確立できますが、ホーム組織とコンパニオン組織のバージョンが一致するまで、最初のメタデータ同期の状況が待機中またはエラーになる可能性があります。
  • バージョンの不一致によってオブジェクトのスキーマが 2 つの組織で異なっていて、その特定のオブジェクトが使用されている場合、同期は一時停止します。たとえば、Salesforce リリースでデータモデルオブジェクト (DMO) の新しいプロパティが導入され、その DMO を使用している場合、ホーム組織とコンパニオン組織が同じバージョンになるまで新しいメタデータは同期されません。
  • 以前に同期されたすべての Data 360 メタデータは、不一致のコンパニオン組織で引き続き使用できます。ただし、新規または変更されたメタデータは、同期が再開されるまで使用できません。

バージョンの不一致のチェック

Data Cloud One 組織クラスターの各組織で使用しているリリースバージョンを確認してから、新しいコンパニオン接続を確立するか、メタデータの同期に遅延があることを確認することをお勧めします。Salesforce の更新のタイミングを変更することはできませんが、各組織の現在のバージョンを把握することで、事前に計画を立てることができます。

バージョンを確認するには、各 Salesforce 組織にログインします。ドメイン URL に/releaseVersion.jspを追加します。たとえば、https://yourdomain.lightning.force.com/releaseVersion.jsp です。ページにReleaseName=[Your Precise Version]が表示されます。たとえば、ReleaseName=[111.22.33] です。

ホーム組織とコンパニオン組織の両方のバージョンを比較します。組織のマイナーバージョン番号は、2 番目の数値セットで示されます。たとえば、バージョン番号が の場合 111.22.33、22 はマイナーバージョンを示します。メタデータ同期エラーは通常、マイナーバージョンの不一致によって発生します。

バージョンの一致の処理

バージョンの不一致を解決するためにアクションを実行する必要はありません。バージョンの不一致は 24 ～ 72 時間以内に解決されます。ホーム組織とコンパニオン組織のバージョンが一致し、スキーマの不一致が解消されると、メタデータ同期が自動的に再開されます。

Sandbox での Data 360

Data 360 Sandbox を使用して、ライブの顧客プロファイルに影響を与えることなく、データの取り込み、モデリング、ID 解決をテストします。Sandbox では、本番 Data 360 組織からメタデータをコピーすることで、安全なテスト環境が提供されます。Sandbox の使用では、本番組織のクレジットを消費します。

Sandbox 環境の利点

Sandbox とリリースツールを使用すると、次のことができます。

  • 本番データおよびユーザーのコピーに対して変更をテストする。
  • トレーニング環境を提供する。
  • AppExchange パッケージまたはインテグレーションをテストします。
  • 変更をリリースする準備が整うまでカスタマイズおよび開発作業を本番環境から分離する。

Sandbox の種別

Data 360 では、すべての Sandbox 種別 (Developer、Developer Pro、Partial Copy、Full Copy) がサポートされます。Sandbox で Data 360 をプロビジョニングする場合、メタデータのみが含まれます。Partial Copy Sandbox と Full Copy Sandbox でもデータを複製することはできません。

Data 360 Sandbox のストレージと制限

Data 360 Sandbox は、本番環境の制限とガイドラインに従います。Developer Sandbox の 200 MB の制限など、Salesforce Sandbox のストレージ制限をスキップします。

Data 360 ライセンスと設定の要件

Sandbox で Data 360 を使用するには、Data Cloud ライセンスをプロビジョニングし、本番組織で有効な Data 360 テナントを維持します。Sandbox は、この本番設定によって異なります。Sandbox で Data 360 を有効化するには、まず本番で有効化して設定します。

Data 360 Sandbox の請求に関する考慮事項

Data 360 Sandbox の使用でフレックスクレジットがどのように消費されるかを理解し、Sandbox のコストを削減する戦略を確認します。

Sandbox での Data 360 の利用状況の種別は、本番の利用状況の種別と同じです。Data 360 Sandbox 組織で生成された使用量では、Sandbox の作成元の組織の本番クレジットが消費されます。Sandbox 組織で Data 360 を有効化すると、一部の機能でクレジットの消費が開始されます。

Digital Walletを使用して、組織で有効な消費カードを確認し、各カードで使用可能なクレジット数を確認し、各使用量種別で消費されたクレジット数を確認します。

Data 360 ProfilesライセンスやAgentforce 1 Editionなど、特定のライセンスまたはエディションでは測定されない使用量タイプもあります。詳細は、ライセンスとライセンスドキュメントを参照してください。

Digital Wallet での Data 360 Sandbox の消費

Sandbox と本番の使用量の両方が Digital Wallet の本番カードに表示されます。使用量を生成した組織を確認するには、使用量種別を表示して組織で絞り込みます。

詳細は、「Data 360 Sandbox Credit Merge」を参照してください。

Data 360 Sandbox 消費の乗数

Data 360 Sandbox 組織の使用量乗数は、Data 360 本番組織の使用量乗数から割引されます。各利用状況種別の特定の本番および Sandbox の乗数については、「Data Cloud 乗数」を参照してください。

どの使用量がどの Data 360 使用量タイプに分類されるかを理解するには、「Data 360 Billable Usage Types for Data 360 and Flex Credits Usage Types for Data 360」を参照してください。

Sandbox コストの削減

Sandbox 組織で Data 360 を有効化するとすぐにクレジットを消費し始める機能もあります。不要な機能を無効にすると、クレジットの消費が減少します。

たとえば、本番組織から複製されたデータストリームは、データの取り込みとクレジットの消費をすぐに開始します。クレジット使用量を減らすには、不要なデータストリームを無効にします。

Data 360 の Sandbox に関する考慮事項

Sandbox を作成し、Data 360 で Sandbox から変更をリリースするときは、次の考慮事項を参照してください。

ライセンスと設定の要件

Sandbox で Data 360 を使用するには、本番で Data Cloud ライセンスをプロビジョニングし、Data 360 テナントを作成します。テナントを作成するには、[設定] から [Data Cloud 設定] を見つけて選択し、[設定] をクリックします。Sandbox で Data 360 を使用できるようにする前に、テナントの設定を完了します。本番が Salesforce Data Cloud ライセンスで Data 360 を操作していない場合、Sandbox で Data 360 を有効にすることはできません。

Sandbox での Data 360 のプロビジョニング

Data 360 が本番組織にプロビジョニングされる前に作成された Sandbox で Data 360 を設定するには、ライセンスの一致機能を使用できます。この機能により、Sandbox を更新せずに本番組織から Data Cloud ライセンスを継承できます。ただし、いくつかの重要な考慮事項があります。

  • ライセンスの一致が機能するには、本番組織に Data 360 がプロビジョニングされている必要があります。
  • ライセンスの一致プロセスでは、Data Cloud ライセンスのみがコピーされます。ライセンスの一致では、組織の設定、値、メタデータ、権限はコピーされません。Sandbox でカスタム設定、インテグレーション、その他のメタデータを手動で設定する必要があります。
  • まず Sandbox で Data 360 プロビジョニングを完了します。Agentforce または Einstein 機能を有効化する前に、プロビジョニングが有効であることを確認します。

Sandbox 組織で Data 360 を有効にするには、Sandbox の作成元の本番組織が Data Cloud ライセンスで Data Cloud を運用している必要があります。ソース本番組織が Salesforce Data Cloud ライセンスで Data Cloud を運用している場合、Sandbox 組織で Data 360 を有効にすることはできません。

Data 360 Sandbox のストレージと制限

  • Data 360 Sandbox は、本番環境の制限とガイドラインに従います。Developer Sandbox の 200 MB の制限など、Salesforce Sandbox のストレージ制限はありません。Data 360 に関連する制限については、「Data 360 の制限とガイドライン」を参照してください。

Sandbox を作成するときの考慮事項

  • 開発者が管理する管理パッケージから追加された Data 360 コンポーネントが本番組織にある場合、そのコンポーネントは Sandbox にコピーされますが、編集や状況の変更はできません。この場合、Sandbox でそのコンポーネントを再作成します。
  • データの取り込みに依存する一部の Data 360 コンポーネントが Sandbox にコピーされると、レコード件数項目と日付項目に本番環境の値が反映されます。Sandbox にデータが取り込まれるまで、これらの本番値が表示されます。この動作は、データストリーム、データレイクオブジェクト、セグメント、ID 解決で確認できます。
  • Data 360 Sandbox を作成するときに Sandbox テンプレートを使用することはできません。
  • Sandbox でデータレイクオブジェクト (DLO) が複製されると、そこで削除することはできません。DLO は本番環境からのみ削除できます。
  • 統合メッセージングは、2025 年 5 月 9 日以降に作成された Sandbox でサポートされます。
  • Einstein 会話インサイト機能の Data 360 コネクタは、Sandbox 組織ではサポートされていません。Sales Signalsなど、Data 360に依存するEinstein会話インサイトの機能は、Sandboxではテストできません。
  • コピーした Sandbox から Data 360 Sandbox を作成することはできません。
  • Digital Wallet 請求ストリームは Sandbox 組織に複製されます。ストリームは本番組織でのみ参照され、Sandbox 組織でのみ参照されます。

Sandbox から変更をリリースする場合の考慮事項

Sandbox 組織から別の Sandbox 組織または本番組織に変更を移行する準備ができたら、次の点に留意してください。

  • 変更セット、Salesforce コマンドラインインターフェース、またはメタデータ API を使用して、Sandbox 間で変更をリリースします。
  • 本番組織に存在しない Sandbox にデータスペースを作成し、そのデータスペースからコンポーネントをリリースする場合、最初に本番でデータスペースを手動で作成する必要があります。データキットをリリースするときにデータスペースは作成されません。
  • デフォルトのデータスペースとカスタムデータスペースから計算済みインサイトをリリースできます。
  • Sandbox から標準およびカスタムデータモデルオブジェクト (DMO) をリリースすると、関連付けられたリレーションとタグがリリースプロセス中に自動的に追加されます。ただし、派生 DMO や選定された DMO など、他の DMO 種別に明示的に割り当てられたタグはリリースに含まれません。
  • DMO の関連リストを含む Lightning ページをリリースするときに、リストがリレーション参照項目を参照している場合、リリースは失敗します。リレーション参照の API 参照名は各環境に固有であり、ソース組織と対象組織では一致しないため、検証に失敗します。
  • Marketing Cloud Engagement (MCE) 接続、取り込み用のビジネスユニット、またはデータスペースへのビジネスユニットの対応付けを作成または変更する場合、データキットに含めてソース組織にリリースすることはできません。この場合、ソース組織で次の機能を作成または変更します。
  • Sandbox の Marketing Cloud Engagement Enterprise Attributes バンドルデータストリームでは、次のアクションを実行できますが、結果の変更は本番にリリースされません。
    • 項目の無効化
    • 数式項目の変更
    • 数式項目の追加
  • ホーム組織接続があるデータアクションターゲットのみを本番にリリースできます。組織間接続はサポートされていません。
  • Sandbox で Einstein Studio モデルを作成する場合、そこでトレーニング評価指標を確認できます。モデルをリリースすると、本番で使用できますが、評価指標は表示されません。
  • サポートされるデータストリームを追加すると、Data 360 にコネクタメタデータが含まれます。データストリームを初めてリリースするときに、Data 360 はコネクタを無効な状態でリリースします。データの取り込みを開始するには、対象組織でログイン情報を設定し、接続を有効化します。後続のリリースでは、対象組織に有効なコネクタが存在する場合、リリースで属性への変更が無視されます。この変更は、すべてのデータストリームコネクタに適用されます。
  • データストリームを削除する場合は、DevOps データキットからコネクタメタデータを削除する必要があります。

組織間で変更をリリースする場合の考慮事項

  • 本番組織間でメタデータを移動するには、本番組織から Sandbox 組織にデータをリリースします。次に、本番組織 2 に最終的なプッシュを行う前に、Sandbox 1 から本番組織 2 にリンクされている Sandbox にこれらの変更をリリースします。

Sandbox でセグメントを使用する場合の考慮事項

  • Sandbox で [暫定的なオーディエンス制限] または [静的属性] のオーディエンスセグメントを作成した場合、そのセグメントを本番にリリースすることはできません。本番でセグメントを手動で再作成する必要があります。
  • Sandbox から本番へのリレーションがないセグメントメンバーシップ DMO をリリースできます。ただし、リレーションを使用したセグメントメンバーシップ DMO のリリースはサポートされていません。
  • 新しいセグメントをリリースすると、その公開スケジュールはデフォルトで [公開しない] になります。セグメントがすでに本番に存在する場合、そのスケジュールは影響を受けません。

Sandbox でデータグラフを使用する場合の考慮事項

  • データグラフは本番から Sandbox に複製されますが、状況は [処理中] です。関連付けられた変換が正常に実行されると、データグラフの状況が [有効] に変更されます。データグラフを手動で有効化するには、データグラフページで更新します。
  • Sandbox からデータ変換またはデータグラフをリリースし、本番にリリースされた後に自動的に実行されない場合は、リストビューからその状況を更新します。

Sandbox で有効化と有効化対象を使用する場合の考慮事項

  • Sandbox で有効化を作成し、Amazon S3、Marketing Cloud Engagement、SFTP、GCS、または Microsoft Azure の有効化を Sandbox から本番にリリースできます。
  • Sandbox から本番に有効化対象をリリースする前に、本番環境で有効化対象の対応する接続を有効にする必要があります。
  • 有効化と有効化対象は本番から Sandbox にコピーされますが、基盤となるコネクタが有効になるまで Sandbox で有効化することはできません。
    メモ Sandbox にコピーされた有効化では、本番セグメントと有効化 ID が保持されます。その結果、Marketing Cloud Engagement (MCE) 有効化対象では、同じ共有データエクステンションキーが参照されます。本番データのクリアや上書きを防止するには、Sandbox 有効化対象を無効にしておくか、認証プロセス中に完全に分離されたエンタープライズ ID (EID) または対象を使用します。
  • データアクションターゲット、ストリーミングデータ変換、一括処理データ変換は本番から Sandbox に複製されますが、明示的に有効化する必要があります。
  • [エコシステム有効化対象] で公開スケジュールを有効にするには、プラットフォームを無効にしてから再度有効にします。
  • 本番から Sandbox にコピーされたロイヤルティ有効化対象は機能しません。また、[Data Cloud 有効化対象] ページで目標の状況を手動で更新することはできません。
  • Marketing Cloud Engagement 有効化対象のタイトルを編集すると、既存の有効化対象を編集する代わりに新しい有効化対象が作成されます。
  • データキットを作成するときに、有効化を少量ずつ追加して保存します。多数の有効化を同時に保存しようとすると、操作がタイムアウトして失敗する可能性があります。

Sandbox でデータストリームと接続を使用する場合の考慮事項

  • Sandbox で接続を作成し、その接続を本番組織にリリースする場合、本番組織で再認証する必要があります。接続を設定すると、データが Sandbox に取り込まれます。
  • S3 接続に基づくデータストリームがあり、その接続のパスに組織 ID が含まれている場合、Sandbox の作成時に組織 ID が本番組織 ID から Sandbox 組織 ID に変更されます。接続パス名が変更された場合、それらの Sandbox データストリームのデータは更新されません。たとえば、S3 ストリームパスが parentpath/productionOrgID/fileName.csv の場合、Sandbox S3 ストリームパスは parentpath/sandboxOrgID/fileName.csv です。Sandbox ストリームパスを編集し、組織 ID を本番組織 ID に変更するか、ファイルを新しいパスに追加する必要があります。
  • Sandbox で接続を設定し、その接続に基づくデータストリームの状況が NEEDS_ACTIVATION のままになっている場合は、Salesforce カスタマーサポートにお問い合わせください。
  • Sandbox を作成したら、Amazon Kinesis コネクタに基づいて接続を再作成する必要があります。

Sandbox で Zero Copy データストリームを使用する場合の考慮事項

  • Google BigQuery、Snowflake、Databricks、Redshift、または Zero Copy 接続をサポートする新しく起動されたコネクタを使用する Zero Copy データストリームの場合、本番環境と Sandbox 環境で異なるデータベース、スキーマ、テーブル名を使用できます。
  • Sandbox 組織で Google BigQuery 接続を有効化すると、Sandbox 組織に合わせて Google BQ プロジェクト ID、サービスアカウントのメール、非公開鍵を変更できます。Sandbox で異なるデータベース名、スキーマ名、またはテーブル名を使用している場合、有効化後にこれらの値を更新できます。
  • Sandbox 組織で Snowflake 接続を有効化するときに、Sandbox のアカウント URL、ユーザー名、非公開鍵を更新できます。Sandbox 環境でデータベース名、スキーマ名、テーブル名が異なる場合は、有効化後にこれらの値を更新できます。
  • Sandbox の Databricks 接続の場合、認証の詳細、接続 URL、HTTP パスを変更できます。Sandbox で異なるデータベース名、スキーマ名、またはテーブル名を使用している場合、有効化後にこれらの値を更新できます。
  • Redshift 接続の Sandbox 設定で、認証の詳細、接続 URL、データベースを変更できます。Sandbox 環境で異なるデータベース名、スキーマ名、またはテーブル名を使用している場合は、有効化後にこれらの値を更新できます。

Sandbox で非構造化データと検索インデックスを使用する場合の考慮事項

  • 検索インデックスに使用されるデータソースが CRM オブジェクト (DMO) の場合:
    • DLO(データ レイク オブジェクト)、DMO(データ モデル オブジェクト)、検索インデックスが本番組織からSandboxにコピーされます。
    • Sandbox 組織では、CRM ホーム組織接続を有効化し、CRM データストリームを有効化する必要があります。検索インデックスは、データが DLO に取り込まれた後に自動的に実行されます。
  • Agentforce データライブラリ (ADL) を使用して検索インデックスを作成すると、次のようになります。
    • UDLO、UDMO、DLO、DMO、CRM データストリーム、検索インデックスは本番組織で自動的に作成されます。
    • UDLO、UDMO、DLO、DMO、CRMデータ ストリーム、検索インデックスが本番組織からSandboxにコピーされます。
    • Sandbox 組織では、CRM ホーム組織接続を有効化し、CRM データストリームを有効化する必要があります。UDLO と UDMO には何もする必要はありません。検索インデックスは、Knowledge データが DLO に取り込まれた後に自動的に実行されます。Sandbox 組織の ADL にアップロードされたファイルには、自動的にインデックスが付けられます。
  • 検索インデックスのデータソースが外部 Blob ストア (S3、GCS、Azure など) の場合:
    • UDLO、UDMO、検索インデックスが本番組織から Sandbox にコピーされます。
    • Sandbox 組織で、外部クライアントアプリケーションまたは接続アプリケーションを作成し、Blob ストアでファイル通知を設定して、これらのファイル通知を Sandbox 組織に向ける必要があります。
    • Sandbox 組織で、UDLO を再作成して UDMO に再マッピングする必要があります。検索インデックスは、データが UDLO に取り込まれた後に自動的に実行されます。

Data 360 Sandbox の作成

本番組織に影響を与えることなく、Data 360 で開発、テスト、トレーニングを行います。Data 360 では、すべての Sandbox 種別 (Developer、Developer Pro、Partial Copy、Full Copy) がサポートされますが、プロビジョニングされるのはメタデータのみです。Partial Copy Sandbox または Full Copy Sandbox を作成しても、本番データは保護されます。データは Data 360 Sandbox に複製されません。

ステップ 2: 既存の Sandbox での Data 360 の有効化

  • ライセンスの一致が機能するように本番組織に Data 360 がプロビジョニングされていることを確認します。
  • ライセンス照合プロセスでは、Data 360 ライセンスのみがコピーされます。ライセンスの一致では、組織の設定、値、メタデータ、権限はコピーされません。Sandbox でカスタム設定、インテグレーション、その他のメタデータを手動で設定できます。

  3. [Match Production Licenses (本番ライセンスを照合)] をクリックします。

    ライセンスの同期が完了するまで最大 24 時間かかります。ライセンス同期が完了する前に Data Cloud 設定にアクセスしようとすると、[Data Cloud 設定] メニューは使用できません。

  2. Data Cloud の [設定] で、[使用開始] をクリックします。

ステップ 4: 接続の設定

Data 360 Sandbox を作成すると、接続は複製されますが、認証データは複製されないため、Sandbox 組織の接続の状況は無効になります。各 Sandbox 接続を有効化し、データを Sandbox に取り込むための認証情報を入力します。

Data 360 を有効にしたら、バックグラウンド処理を完了できるように、約 1 時間待ってからこのステップを実行します。

  1. Sandbox 組織で、[Data Cloud 設定] を選択します。
  2. [クイック検索] ボックスに、有効化するコネクタの種類を入力します。

    CRM 以外のコネクタの場合は、「Other Connectors」 (他のコネクタ) と入力します。リストからコネクタを選択します。ドロップダウンリストから、[有効化] を選択します。

    Salesforce CRM ホーム組織コネクタの場合、「Salesforce CRM」と入力します。リストからコネクタを選択します。ドロップダウンメニューから、[有効化] を選択します。CRM 接続が本番組織 ID から Sandbox 組織 ID に変更されます。

    他の Salesforce CRM コネクタの場合は、CRM ホーム組織接続の手順に従います。任意の本番組織または Sandbox 組織への接続を有効化できます。接続の組織のログイン情報を入力し、[ログイン] をクリックします。Data 360 組織識別子を入力して、接続を確認します。この ID は、モーダルの [Data 360 Org Details (Data 360 組織の詳細)] にあります。この識別子は、ソース組織からデータを取得する Data 360 組織を指定します。

  3. チェックボックスをオンにして接続の作成に同意し、［Activate］ をクリックします。

接続を有効化すると、その接続を使用するデータストリームまたはその他のコンポーネントが有効になります。

ステップ 1: リリース接続の作成

本番組織で、本番 (対象) 組織と Sandbox (ソース) 組織間のリリース接続をまだ作成していない場合は作成します。「リリース接続の承認」および「変更セットの設定」を参照してください。
Sandbox から本番組織にリリースするため、本番組織でリリース接続を作成します。このリリース接続により、受信変更セットを本番組織にインストールできます。

ステップ 2: DevOps データキットの作成

  1. Sandbox 組織で、Data Cloud の [設定] から DevOps データキットを作成します。「データキットの作成」を参照してください。
  2. [Data Kit Type (データキットタイプ)] で、[DevOps] を選択します。
  3. データスペースを選択します。
    Sandbox 組織と本番組織の両方に同じプレフィックス名のデータスペースが存在することを確認します。
  4. リリースする Data 360 コンポーネントを DevOps データキットに追加します。
  5. 対象組織のデータキットコンポーネントの自動公開順序を確認するには、[Publishing Sequence (公開順序)] をクリックします。

    公開順序を編集した場合、データキットコンポーネントを追加または変更しても Data 360 によって順序が自動的に更新されません。編集後、データキットの変更ごとに公開順序を手動で更新します。

    コンポーネントは作成日に基づいて公開されます。次のコンポーネントの公開順序を確認します。

  6. [保存] をクリックします。

本番組織に存在しない Sandbox にデータスペースを作成し、そのデータスペースからコンポーネントをリリースする場合、最初に本番でデータスペースを手動で作成する必要があります。データキットをリリースするときにデータスペースは作成されません。

ステップ 3: 送信変更セットの作成とアップロード

  1. Sandbox 組織で、[設定] から送信変更セットを作成します。「送信変更セットの作成」を参照してください。

ドキュメントAIは、Data 360を使用して非構造化ドキュメントから構造化データを抽出し、Flex Creditsを使用して生成AIをコールします。ドキュメント AI の使用は、次の利用状況種別のクレジットの消費に影響します。

Data 360 の利用状況

データの収集と処理にData 360を使用する場合、組織はData Services消費カードまたはFlex Credits消費カードからクレジットを消費します。有効なデータサービスクレジットがある場合、それらのクレジットが最初に消費されます。データ サービス クレジットが不足していたり、まったくクレジットがなかったりした場合、組織は Flex Credits for Data 360 サービスを消費します。詳細については、「Data Services Billable Usage Types for Data 360」および「Flex Credits Usage Types for Data 360」を参照してください。

使用量種別ごとの乗数を確認するには、「Multipliers for Data Services Rate Card」または「Agentforce & Data 360 Flex Credits Rate Card」を参照してください。各クレジットのコストは契約によって決まります。

ドキュメント AI コストの削減

ドキュメント AI の消費レートは、いくつかの方法で低下させることができます。

  • 対象通話の請求を回避するために、生成 AI アクションが測定されていないヒューマンコンテキスト使用状況に該当するかどうかを確認します。
  • データ処理メーターはデータ MB あたりの料金であるため、アップロードする前に高品質の画像と画像コンテンツを PDF で圧縮します。
  • Digital Walletを定期的にチェックして、消費トレンドを監視し、予期しない急増を早期にキャッチします。
  • 予期しないクレジット消費を避けるために、更新は慎重に計画してください。ドキュメント AI 設定を変更する必要がある場合は、すべての変更をまとめてから公開します。
  • [再構築] アクションは、設定を編集し、その変更でコンテンツを再処理する必要がある場合にのみ使用します。再構築すると、以前に処理されたすべてのコンテンツが再処理され、大量のクレジットが消費される可能性があります。処理の問題のトラブルシューティングに [再構築] を使用しないでください。

強化されたインデックスコストの理解

強化されたインデックス付けにより、エンティティ、概要、トピック、回答可能な質問などの生成されたインテリジェンスでチャンクが強化され、インテント駆動型検索が改善されます。このプロセスにより、AI アシスタントの検出可能性とグラウンディングが向上しますが、すべてのチャンクで追加の埋め込みとメタデータチャンクが生成されるため、インデックス作成コストが増加します。

データセットから生成されるチャンクの数は、チャンク戦略 (パッセージ抽出、セクション対応) やチャンクサイズなどの要素によって異なります。これらの変数を合わせると、コンテンツがどの程度効率的にチャンクされるかと、強化されたインデックス付けのコストが決まります。

例: クレジット消費量の計算

商品カタログやテクニカルガイドなどの PDF ドキュメントで構成される 5 MB のサンプルデータがあるとします。最大チャンクサイズが 512 トークンの構造対応チャンク戦略を使用して、Data 360 検索チャンクで MB あたり約 16 チャンクが生成されると仮定します。強化チャンクを生成するために実行された LLM 要求の合計と、消費されたフレックスクレジットを計算してみましょう。

合計チャンク数 = MBあたり5 MB x 16チャンク = 80チャンク

各 LLM 要求で 4 つのチャンクが処理されます。

LLM 要求の合計 = 80 チャンク ÷ LLM 要求あたり 4 チャンク = 20 要求

各 LLM 要求にはトークンの使用状況が含まれます。要求ごとに使用されるトークンの合計を計算してみましょう。

- プロンプト命令には 2,100 トークンが必要です。

- 処理されたチャンクのトークン = 4 チャンク x 512 トークン = 2,048 トークン

- 出力トークンの合計 = 1,500 トークン

Total Tokens Used per Request (要求あたりの使用トークン総数) = 2,100 + 2,048 + 1,500 = 5,648 トークン

2000 トークンを Salesforce Flex Credit の 1 単位とし、請求は最も近い単位に切り上げられます。5 MB データセットに必要な請求単位数は次のとおりです。

- 5,648 トークン ÷ 2,000 トークン/単位 = 2.824 請求単位

- 2.824 請求単位は 3 請求単位に切り上げられます。

各請求単位が標準プロンプトで 4 つのフレックスクレジットを消費したとします。この場合、各 LLM 要求は次のものを消費します。

単位あたり 3 請求単位 x 4 フレックスクレジット = LLM 要求あたり 12 フレックスクレジット

したがって、20 LLM 要求の場合: 使用された Flex Credit の合計 = 20 要求 x 12 Flex Credits per request = 240 Flex Credits

または、データセットが MB あたりのチャンク数の多いファイルで構成されていた場合、強化作業負荷が大幅に増加します。同じ 5 MB のデータセットで、構造認識チャンクによって MB あたり 121 個のチャンクが生成されるとします。

合計チャンク数 = MB あたり 5 MB x 121 チャンク = 605 チャンク

各 LLM 要求で 4 つのチャンクが処理されます。

LLM 要求の合計 = 605 チャンク ÷ LLM 要求あたり 4 チャンク = 152 要求

要求ごとに使用されたトークンの合計、合計請求単位、および請求単位ごとに使用された Flex Credit の計算方法に基づいて、152 LLM 要求で消費された Flex Credit の合計を計算してみましょう。

Total Tokens Used per Request (要求あたりの使用トークン総数) = 2,100 + 2,048 + 1,500 = 5,648 トークン

合計請求単位 = 5,648 トークン ÷ 2,000 トークン/単位 = 2.824 単位

2.824 請求単位は 3 請求単位に切り上げられます。

3 つの請求単位で使用された Flex Credit の合計 = 単位あたり 3 x 4 クレジット = LLM 要求あたり 12 Flex Credit

152 LLM 要求で消費された Flex Credit の合計 = 152 要求 x 12 Flex Credits per request = 1,824 Flex Credits

次のサンプル計算は、生成されたチャンク数が、実行された LLM 要求の数にどのように影響し、最終的に消費されたフレックスクレジットに影響するかを示しています。

セキュリティ

組織の親オブジェクト (取引先責任者、リード、または個人取引先) に設定された権限で、レコードホームページの関連リストまたはコピー項目へのアクセスを制限します。

関連リストを参照できるユーザーを制限すると、次のようになります。

  • オブジェクトレコードホームページにアクセスできるすべてのユーザーが関連リストを表示できます。
  • オブジェクトレコードホームページにアクセスできるユーザーは関連リストを表示できません。
  • 組織でその親オブジェクトを表示する権限を持つユーザーのみが関連リストを表示できます。
  • 各データスペース範囲の特定の権限を持つユーザーのみが関連リストを表示できます。

オブジェクトレコードホームページへのアクセス権を持つユーザーが関連リストデータにアクセスできないようにアクセス権を制限すると、関連リストは空白で表示されます。

データスペースの場合、Salesforce の標準の「最も厳しい制限のあるアクセスを優先する」というセキュリティポリシーは、関連リストの強化に表示されるデータには適用されません。Data Cloud 内にある追加のデータ制限に関係なく、選択したデータスペース内のすべての情報にアクセスできます。表示できるデータを制限するには、動的関連リストを作成してデータスペースで絞り込みます。

ユーザーの権限セットでオブジェクト権限と機能権限を設定することで、データスペース対応オブジェクトおよび機能へのユーザーアクセスを制御できます。詳細は、「データスペース対応オブジェクトおよび機能」を参照してください。

データ損失

項目の強化を組織の既存の項目に対応付けると、項目のデータが Data Cloud のデータで上書きされます。Data Cloud に設定された取り込みと同期のオプションによっては、データが Data Cloud に取り込まれる前に組織の項目で変更されたデータが上書きされ、データ損失が発生する可能性があります。

データの損失を回避するために、次のオプションを検討してください。

  • コピー項目を、データが入力される Salesforce オブジェクトの既存の項目ではなく、Data Cloud のデータのみを含む新しい項目に対応付けます。たとえば、取引先責任者にニックネームを入力できる [ニックネーム] 項目がある場合、Data Cloud のデータ用に新しい [優先ニックネーム] 項目を作成します。Data Cloud のデータはハーモナイズされており、クリーンで正確なデータが表示される可能性が高くなります。Data Cloud で異なる値を解決する際には、最後に入力されたニックネームと最も頻繁に使用されるニックネームのどちらを使用するかを制御できます。
  • 組織からのデータストリームにはスケジュールされた取り込みは使用しないでください。代わりに、データのコピー先の項目のデータ変更によって取り込みがトリガーされるようにワークフローを作成します。

たとえば、顧客が姓を変更するためにサービスセンターに電話をかけてきた場合、どのビジネスユニットで働いているかに関係なく、すべてのサービス担当者が最新のデータを使用できるようにする必要があります。

そこで、組織から Data Cloud へのデータストリームを設定し、15 分ごとに実行するようにスケジュールします。そして、Data Cloud から組織の [姓] 項目にデータをコピーする強化を作成します。サービス担当は、コピー項目である [姓] 項目で顧客の姓を [Alders] から [Mayfair] に変更します。しかし、Salesforce は、スケジュールされたデータ取り込みの前にコピー項目のデータを同期して、Mayfair を元の値 Alders で上書きしてしまいます。新しい値であった Mayfair は復元できず、失われてしまうのです。

データが上書きされないようにするには、[姓] 項目の変更が検出されたときに取り込みをトリガーできるフローを作成します。

データアクションとデータ対象

項目の強化は、使用可能なデータアクションとデータ対象の合計数に影響します。各コピー項目強化では、Data Cloud ライセンスで使用可能な 1 つのデータアクションと 1 つのデータ対象が使用されます。使用可能なデータアクションとデータ対象の数は、オブジェクトの強化のリストで確認できます。

データ遅延

関連リストでクリック操作によって詳細情報を表示すると、リストで Data Cloud に対して詳細情報が照会されます。コンポーネントのデータはほぼリアルタイムで表示されます。ただし、デフォルトである 7 日間のデータ範囲を超える日付を指定した場合、取得されたデータ量によっては関連リストで大幅な遅延が発生する可能性があります。日付範囲を減らすか、関連リスト強化の一環として検索条件を追加して、遅延を改善できます。

コピー項目強化では、一括処理ジョブを使用して Data Cloud と組織レコード間で情報を同期します。処理中のレコード数によっては、データ遅延が発生することがあります。データの初期読み込みには、レコード数に応じて数時間または日かかることがありますが、その後の同期では変更されたレコードのみが更新されるため、短時間で完了します。

動的関連リスト

関連リスト強化によって作成された関連リストから動的関連リストを作成できます。動的関連リストを使用すると、関連リストの強化のために返されるデータのデフォルトの 7 日間の制限を上書きして、リストに表示されるデータを制限できます。

Lightning と Lightning アプリケーションビルダー

Lightning アプリケーションビルダーおよび Lightning レコードページの関連リストコンポーネントには、関連リストの強化に関するいくつかの制限事項があります。

  • [関連リスト - 1 つ] コンポーネントと [関連リスト] コンポーネントでは、Lightning アプリケーションビルダーに Data Cloud 関連リストのプレビューは表示されません。
  • Lightning アプリケーションビルダーでは、関連リストのクイックリンクコンポーネントに Data Cloud 関連リストのレコード件数は表示されません。ユーザーがレコードページでコンポーネントの Data Cloud 関連リストにマウスポインターを置いたときに、リストのフロート表示に関連レコードは表示されません。

関連リスト強化の制限

  • 関連リスト強化の場合、関連リストの最大数は、Data Cloud 組織で作成できる参照関係の最大数によって異なります。組織の上限は 10,000 件です。
  • フロート配列データ型を除くすべてのデータ型の関連リストを作成できます。

エンゲージメントデータの関連リストの日付範囲

デフォルトでは、エンゲージメントデータを含む関連リスト強化では、過去 7 日間のデータが返されます。デフォルトの日付範囲を変更するには、強化を作成または編集するときに日付検索条件を使用するか、動的リストを作成します。日付範囲を長くすると、表示するデータ量が多くなるため、関連リストの表示速度が大幅に低下する可能性があります。

Direct-DMO 関連リストの強化とマージされた Salesforce レコードに関する考慮事項

Salesforce レコードをマージすると、Salesforce レコード ID を参照している場合に、直接 DMO 関連リストの強化で問題が発生する可能性があります。 重複する取引先、取引先責任者、またはリードレコードが重複ルールを使用してマージされると、いずれかのレコードが削除され、その ID は、そのレコードが存在しないため有効ではなくなります。関連リスト強化で ID に基づいてレコードを照合する DMO リレーションが使用され、削除された Salesforce レコード ID を参照している場合、関連リスト強化ではすべての関連データが表示されません。

ソリューションは、使用するコネクタの種類によって異なります。

  • Salesforce CRM コネクタが設定されている場合は、データストリームを更新します。この更新により、Data Cloud DMO レコードのレコード ID が更新されます。
  • コネクタが S3 などの外部データソースで使用されている場合は、外部データソースの ID を更新します。外部接続では、次のいずれかの Data Cloud コネクタを使用します。

レコードのマージシナリオの例を次に示します。たとえば、Salesforce システム管理者が取引先責任者 Salesforce オブジェクトとメールエンゲージメント DMO 間のリレーションを設定し、Contact.Id 項目と EmailEngagement.ssot__IndividualId__c 項目に基づいてレコードを関連付けます。ID が 2 の取引先責任者レコードが ID が 1 の取引先責任者とマージされると、ID が 2 の取引先責任者が削除されます。 そのため、マージ後、IndividualId__c 項目が 2 のメールエンゲージメントレコードは、ID が 1 の強化取引先責任者に表示されません。この問題を修正するには、2 の IndividualId__c に関連付けられているメールエンゲージメントが 1 の IndividualId__c に関連付けられているように DMO データを更新します。

この考慮事項は、Salesforce オブジェクトの ID 項目を使用する直接 DMO 関連リストの強化にのみ影響します。CRM オブジェクト ID 項目に基づいていない他の種別の強化や直接 DMO 強化には影響しません。

コピー項目強化の制限

コピー項目強化の最大数は、組織のデータアクションとデータアクション対象の最大数によって制限されます。

パフォーマンスに影響を与えずに 1 つの強化でコピーできる項目の最大数は、エンティティのカスタム項目の最大数です。ただし、必要に応じて同じオブジェクトに複数の強化を作成できます。

コピー項目強化の除外項目

コピー項目強化でサポートされていない項目は除外されます。除外された項目は、コピー項目強化の対象項目として使用できません。これらは、互換性のない項目とは異なります。

コピー項目強化に関する技術的な考慮事項

コピー項目強化の実装を成功させるには、次の技術的な考慮事項が不可欠です。

  • データキットの互換性: データキットは多くのユーザーにとって重要な機能です。ただし、強化とデータキットの現在の互換性は不明です。シームレスなインテグレーションを確保するために、さらに調査することをお勧めします。
  • 既存のワークフローへの影響: 強化を実装すると、既存のデータ処理ワークフローに影響する可能性があります。潜在的な中断を徹底的に評価し、必要に応じて緩和戦略を策定します。

完全同期の制限

完全同期ジョブは、最大 24 時間実行できます。処理できるレコード数は、 の環境に応じて 6 ～ 1 億です。本番環境では、通常、この数より多くのレコードを処理できます。

強化のトラブルシューティング

組織のデータは、データスペース、オブジェクト、対応付け、Data Cloud のデータ取り込みによって異なります。

強化が期待どおりに動作しない場合は、次の点を確認してください。

  • オブジェクトとオブジェクトに対して設定されているデータスペースが変更されていない。
  • オブジェクトのデータストリームが正常に接続され、データが取り込まれている。
  • 正しいキー修飾子を指定した。通常、キー修飾子は必要ありません。ただし、誤ったキー修飾子を指定すると、誤ったデータがコピーされる可能性があります。キー修飾子が必要になるのは、CRM コネクタを使用して組織から直接データを取り込むのではなく、別のシステムまたはサービスを介して取り込むまれなケースのみです。
  • ユーザーが関連リストが空白であることに気付いた場合は、割り当てられた権限セットのデータスペースアクセス権があることを確認してください。

計算済み履歴インサイトを使用した指標の追跡

評価指標の経時的な変化を追跡して、データに基づく意思決定を行います。

必要なエディション

使用可能なエディション: Data 360 でサポートされるすべてのエディション。 「Data 360 Edition の可用性」を参照してください。

ビジネス評価指標は、成功を測定するために不可欠です。ただし、セールスパイプライン、サービスコール統計、ブランド認知スコアなどの重要な評価指標は、長期間にわたって追跡することが困難な場合があります。Data 360 の計算済みインサイト履歴では、これらの総計値とディメンションの経時的な変化を確認できます。

履歴管理を使用して評価指標とディメンションを保存すると、十分な情報に基づいた意思決定が可能になる例を次に示します。この例では、Sales Pipeline のソース定義は次のようになります。

SELECT Region, Territory, Deal Stage, SUM(Opp Value) AS Pipeline Value
      FROM Opportunity
      GROUP BY Region, Territory, Deal Stage

計算済みインサイトで履歴管理を有効にすると、Data 360 によって新しい計算済み履歴インサイトが作成されます。計算済み履歴インサイトは、特定の時点でデータを取得し、計算済みインサイトオブジェクト値を計算済み履歴インサイトオブジェクトに追加します。

取得元の計算済みインサイトのデータが変更されると、計算済み履歴インサイトによってその変更が追跡および記録されます。データエクスプローラーを使用して、計算履歴インサイトと会社のデータの経時的な変化を確認できます。履歴管理は、次のような使用事例で使用します。

  • 最も多くのパイプライン金額を失った商談フェーズの進行状況を確認する
  • 値のトレンドに基づいてテリトリーを分割または組み合わせる
  • MoM、QoQ、前年同期比に基づく将来の価値のトレンド分析
  • 売上予測と実際の売上の比較

履歴管理の使用開始

  • 履歴管理に関する考慮事項

  • 計算済みインサイト履歴の追跡

履歴管理に関する考慮事項

履歴管理を使用するときは、次の考慮事項に留意してください。

  • 履歴管理は、計算済みインサイトでのみ使用できます。履歴管理は、ストリーミングやリアルタイム調査では使用できません。

  • ソース計算済みインサイトオブジェクト (CIO) のスキーマに影響する変更 (新しい基準の追加など) では、履歴 CIO データが切り捨てられ、既存の履歴が削除されます。履歴管理は、次の履歴ジョブの実行時に新しいスキーマで再開されます。

    履歴データを保持するには、新しいソース計算済みインサイトを作成し、その履歴管理を有効にします。

  • 履歴管理は、取得元の計算済みインサイトの請求には影響しません。履歴管理 CIO の請求は、[データクエリ] 利用状況種別にあります。「インサイトの請求に関する考慮事項」を参照してください。

インサイトの作成に関する考慮事項

戦略的計画により、Data 360 インサイトはビジネスユーザーに正確かつハイパフォーマンスなデータを視覚化します。複雑な結合、相対期間、高度な評価指標の階層化を使用して、データ処理を最適化できます。

これらの考慮事項は、セグメント内で信頼できる情報源を維持するために適切な集計方法と日時ディメンションを選択するのに役立ちます。このセクションのガイドラインを使用して、アクション可能な顧客インテリジェンスを促進する拡張性の高い複数ディメンションのインサイトを構築します。

  • 相対期間評価指標の定義
    ローリングタイムウィンドウに基づく総計値を使用して、Data Cloud のインサイトをリアルタイムで取得します。指定された過去の秒数、分数、日数など、相対的な期間を使用して総計値を決定します。
  • セグメンテーションの計算済みインサイト
    計算済みインサイトを使用して、セグメンテーションでデータ主導のインサイトを制御します。セグメンテーション検索条件で計算済みインサイトの総計値とディメンションを記述することもできます。
  • インサイトでの Join 句の使用
    計算済みインサイトでは、同時に複数のデータモデルオブジェクト (DMO) にアクセスできます。異なる DMO の複数の行に一度にアクセスする計算済みインサイトクエリは、結合クエリと呼ばれます。Data 360 では、計算済みインサイトの 4 種類の結合 (内部、左、右、完全) がサポートされます。
  • Metrics on Metrics
    複雑な計算済みインサイト (CI) SQL データを論理ステップに整理して、強力なワークフローを作成します。Metrics on Metrics を使用すると、複数のシナリオで評価指標を改善して再利用できます。

Customer Data Platform (CDP) ライセンス

  • ライセンス: このライセンスは購入または更新できなくなりました。
  • 請求: Customer Data Platform ライセンスを使用している組織は、組織で完了したプロファイル、セグメントの公開、エンゲージメントイベントの数に基づいて請求されます。請求計算については、「Customer Data Platform Billable Usage Calculations」を参照してください。
  • 制限: Customer Data Platform 組織は、ほとんどの機能について特定の制限に準拠する必要があります。一部の Data 360 機能は、このライセンスタイプの組織では使用できません。制限を確認するには、「Customer Data Platform の制限とガイドライン」を参照してください。
  • Data 360 のエディションとライセンス
    Data 360 は、サポートされている複数の Salesforce エディションで使用できます。一部の Data 360 機能では、追加のライセンスも必要です。
  • Data 360 レポート可能リソース参照
    リソース参照は、使用量を生成した機能別にクレジット消費量を表示するための標準使用量タグです。リソース種別に関するカスタム Data 360 レポートを作成し、そのソースで使用量を表示、絞り込み、並び替えることができます。
  • 標準消費タグのデータスペース参照
    Data 360 の消費利用状況に関するレポートをデータスペースで絞り込んでグループ化します。
  • Data 360 でのクレジット消費の削減
    データストリーム、データ変換、ID 解決などの機能の設定を更新することで、Data 360 データサービスで消費されるクレジット数を削減できます。ほとんどの機能では、処理するデータの量や処理頻度を減らすとコストが削減されます。
  • Data 360 を利用した機能の請求への影響
    Salesforce CRM の一部の機能は、Data 360 データに基づいています。これらの機能は、Data 360の関連プロセス(クエリ、ストレージ、処理、分析など)の使用量を増やすことで、データ サービスのクレジット消費に影響します。Data 360 の機能を設定する前に、機能と使用に関するドキュメントを確認してください。機能が Data 360 のデータサービスクレジット消費にどのように影響するかについては、アカウントエグゼクティブにお問い合わせください。
  • Data Cloud ライセンスの請求と制限
    Data Cloud ライセンスを追加すると、Salesforce 組織で Data 360 が有効になります。このライセンスを持つ組織は、Data 360サービスの使用によって消費された消費クレジットを購入します。
  • Data 360 プロファイルライセンスの請求と制限
    Data 360 Profiles および Data 360 Enterprise Profiles ライセンスを Data Cloud ライセンスに追加して、Data 360 組織の請求方法と制限を変更できます。Data 360 組織にこのライセンスがある場合、統合プロファイル、セグメント、データ変換、インサイトが制限されますが、クレジットは消費されません。
  • Customer Data Platform ライセンスの請求と制限
    このライセンスを持つユーザーは、Salesforce 組織で Data 360 にアクセスできます。このライセンスは購入できなくなり、更新できなくなります。このライセンスを持つ組織は、組織のプロファイル、エンゲージメント、およびその他のレコードの数に基づいて請求されます。その他の機能には制限があります。このライセンスを持つ Data 360 組織では、すべての Data 360 機能を使用できるわけではありません。

制限事項と主要な考慮事項

シンプルスタートを使用する前に、次の制限事項を確認してください。

  • 可用性制限:Data 360では、Simple Startは2026年7月以降にプロビジョニングされた新しい組織にのみ制限されます。既存の組織は、この自動設定ツールにアクセスできません。
  • 接続制限: 自動セットアップは、ホーム組織の接続からのみ動作します。コンパニオン組織はサポートされません。
  • データスペース制限: Simple Start では、データレークオブジェクト (DLO)、データストリーム、マッピングなどのすべての自動同期コンポーネントがデフォルトのデータスペースにのみ作成されます。
  • オブジェクトのサポート: Data 360 は、AccountやContactなど、ホーム組織からの標準 CRM オブジェクトの指定リストの設定を自動化します。すべての標準オブジェクト、カスタムオブジェクト、または CRM 以外のオブジェクトがサポートされているわけではありません。『Data 360 Simple Start Guide』を参照してください。
  • バンドル項目の除外: [Simple Start (簡易開始)] では、CreatedBy、Created Date、Last Modified Date のマッピングが省略される標準データバンドルがプロビジョニングされます。

Data Cloud での複数通貨の使用に関する考慮事項

Data Cloud でマルチ通貨を使用するときは、次の考慮事項に留意してください。

  • Data Cloud では静的換算レートのみがサポートされ、Salesforce CRM 組織で有効になっている期間指定換算レートは無視されます。
  • Salesforce 組織で通貨の換算レートが指定されていない場合、Data Cloud は通貨項目に null 値を返します。この問題を回避するには、Salesforce 組織で通貨換算レートを追加するか、独自の換算レート DMO を使用します。

    クエリエディターの Data Cloud クエリサービス変換関数を使用して、変換率をテストできます。 

    select Order_ID__c, Sales__c, try_convert_currency(Sales__c, 'USD', 'EUR') as Sales_EUR, Profit__c, cdp_sys_record_currency__c from orders_same_currency__dll limit 10
  • 複数の CRM 組織を Data Cloud に接続する場合、各組織で同じ通貨と換算レートのリストを使用します。
  • Data Cloud では、接続されているさまざまな CRM 組織間での通貨換算はサポートされません。たとえば、Data Cloud で CRM 組織 1 の米ドル (USD) とユーロ (EUR)、CRM 組織 2 の日本円 (JPY) とインドルピー (INR) の換算レートが同期されているとします。 このシナリオでは、米ドルから日本円、米ドルから日本円、ユーロから日本円、ユーロからインドルピーの換算はサポートされていません。変換で null 値を回避するには、USD および EUR の通貨レートを組織 2 に追加し、JPY および INR の通貨レートを組織 1 に追加します。
  • DMO の通貨項目では、異なる通貨をサポートできます。たとえば、販売注文 DMO の [金額] 項目は、ある注文では米ドル、別の注文ではユーロにすることができます。このような場合の通貨変換を支援するために、ISO 通貨コード値が含まれる cdp_sys_record_currency フィールドがデフォルトで含まれています。
  • Sandbox 組織では単一通貨組織を使用できません。

計算済みインサイトでマルチ通貨を使用するときは、次の追加考慮事項に留意してください。

  • 計算済みインサイトのすべての通貨項目は同じ通貨である必要があります。たとえば、計算済みインサイトに通貨値を含む 2 つの基準が含まれる場合、両方の基準のすべての項目が同じ通貨である必要があります。
  • 計算済みインサイトを使用して通貨値を集計する場合、通貨値を 1 つの通貨に変換する必要があります。
  • ビルダーを使用して計算済みインサイトを作成すると、ビルダーによって変換ロジックが自動的に管理されます。ただし、ユーザーはインサイト出力の通貨を選択する必要があります。
  • SQL を使用して通貨項目を使用して計算済みインサイトを作成する場合、構文標準に準拠するために、次の構文を使用して try_convert_currency 関数を含めます。 
    try_convert_currency(Source Currency Field, Source Currency ISO, Target Currency ISO)
  • ビルダーを使用して通貨データ型を含む計算済みインサイトを作成すると、ビルダーは自動的に [currency_type_c] 項目を追加します。SQL を使用して通貨項目を使用して計算済みインサイトを作成する場合、ユーザーはこの項目を手動で追加する必要があります。

プライベートコネクトに関する考慮事項

Private Connect for Data 360 は、仮想プライベートクラウド (VPC) 間の安全な接続を確立し、公開インターネットを迂回してセキュリティを強化します。

VPC の非公開接続

VPC は、パブリッククラウド内のプライベートネットワークです。これにより、Amazon などのクラウドプロバイダーはデータとアプリケーション用の安全で隔離されたスペースを作成できます。一般に、データレイクでは、公開インターネットアクセスを防止するために VPC などの安全な手段が使用されます。ただし、この対策では Data 360 へのアクセスも制限されます。 Data 360 のプライベートコネクトでは、プライベートネットワークアクセスを確立して、トラフィックがパブリックインターネットから切断されないようにすることで解決策が提供されます。

Private Connect for Data 360 は現在、Amazon Web Services (AWS) PrivateLink をサポートしており、Data 360 AWS VPC と AWS VPC 間の安全なポイントツーポイント接続を作成できます。この非公開接続は個々のテナント専用であり、インターネット制限を維持しながら Data 360 にのみアクセス権を付与できます。

Data 360 のプライベートコネクトアーキテクチャ

Private Connect for Data 360 は、パフォーマンスと拡張性に優れたアーキテクチャを使用して、各テナントに専用の容量とセキュリティを提供します。このアーキテクチャでは、非構造化データの大量初期取り込みや分析のための低レイテンシのクエリなど、さまざまな使用事例がサポートされます。

Private Connect for Data 360 と Private Connect for Data 360 は異なる製品

Salesforce Private Connect と Private Connect for Data 360 は、機能や価格体系が異なる個別の製品です。Salesforce プライベートコネクトは Data 360 と互換性がありません。 ただし、Data 360 のプライベートコネクトでは Data 360 がサポートされます。

プライベートコネクトのデータキットサポート

現在、データキットではプライベートコネクトはサポートされていませんが、Snowflake と Redshift の両方で使用可能な手動の回避策があります。この手動回避策では、他の使用事例でデータキットを使用することはブロックされません。

Snowflake のソリューション

この回避策では、対象組織で PNR を作成し、次のように有効化する必要があります。

  • DevOps データキットを対象組織にリリースします。リリースは失敗しますが、問題ではありません。
  • 対象組織でプライベートコネクトプライベートネットワークルート (PNR) を作成します。
  • Data Cloud 設定に移動し、Snowflake 接続を見つけます。無効な状態です。次のように有効化します。
    • [プライベートコネクト] の切り替えを有効にします。
    • 作成した PNR を選択します。
    • URL、キー、その他の詳細を指示に従って入力します。
    • 設定接続に [有効] 状態が表示されます。
  • アプリケーションランチャーに移動し、[Data Cloud]、[Data Streams] の順に選択します。データストリームにエラー状態が表示されている。
  • エラー記号をクリックし、ストリームの作成を再試行します。接続が成功し、データストリームが ACTIVE 状態に移行します。

Redshift のソリューション

この回避策では、PNR を作成する必要がありますが、コネクタやデータストリームなど、他のコンポーネントの転送のブロックが解除されます。必要なデータキットをダウンロードしたら、データキットを開いて DataKitObject テンプレートを開き、outboundnetworkconnection 値を更新します。

  • 対象組織でプライベートコネクトプライベートネットワークルート (PNR) を作成します。PNR を作成するときに、プライベート ネットワーク ルート ID をコピーして保存します。ステップ 4 で必要です。
  • 対象組織で、Salesforce コマンドラインインターフェース (CLI) を使用してデータキットを取得します。
  • 取得したパッケージで、DataKitObjectTemplate を開きます。
  • [ outboundnetworkconnection.] という名前のパラメータを見つけます。 値をステップ 1 で収集したプライベート ネットワーク ルート ID に置き換えます (例: {"paramName":"outboundnetworkconnection","value":"<PNR-ID>"})。
  • UI/変更セットを使用してデータキットリリースを投稿します。接続に成功し、[無効] 状態に移行します。次のように有効化します。
    • [プライベートコネクト] の切り替えを有効にします。
    • 作成した PNR を選択します。
    • URL、キー、その他の詳細を指示に従って入力します。
    • 設定接続に [有効] 状態が表示されます。
  • アプリケーションランチャーに移動し、[Data Cloud]、[Data Streams] の順に選択します。データストリームにエラー状態が表示されます。
  • エラー記号をクリックし、ストリームの作成を再試行します。接続が成功し、データストリームが ACTIVE 状態に移行します。

Amazon Simple Storage Service (S3)

Data 360は、Data 360のプライベート コネクトを使用しないS3とのプライベート ネットワーク接続をサポートします。ネットワーク トラフィックはパブリックIPを介して発生しますが、AWSバックボーンに留まり、パブリック インターネットを経由しないことが保証されています。

  • プライベート IP アドレスを使用して、同じ AWS リージョン内の S3 バケットと Data 360 インスタンスを接続します。その地域の Data 360 の AWS VPC エンドポイントを非公開 S3 アクセスの許可リストに含めるようにバケットポリシーを更新します。

  • Data 360 テナントとは異なるリージョンのバケットへのアクセスは、パブリック IP を介して行われます。

詳細は、「AWS PrivateLink for Amazon S3 and IP Addresses Used by Data 360 Services」を参照してください。

プライベート IP アドレスと公開 IP アドレスの違い

公開 IP アドレスはインターネットに表示されます。ただし、プライベート IP アドレスは、通常は内部ネットワーク用に予約されているインターネットに対応していない IP アドレスの範囲を使用するため、表示されません。Data 360 のプライベートコネクトを使用する場合、公開 IP の許可リスト登録は省略可能です。プライベートコネクトでは、プライベート IP アドレスが使用され、公開 IP アドレスは使用されません。

Data 360 クレジット消費のプライベートコネクト

一般に、レート カードに表示されるように、クレジット消費はすべての種別で独立しています。たとえば、ゼロコピー統合では、アクセス 100 万行ごとに消費レートが 70 クレジットになります。非公開接続を使用して Zero Copy 統合を取り込む場合、転送される 1 GB あたり 500 クレジットに加えて、アクセス 100 万行あたり 70 クレジットのレートが適用されます。

Snowflake の IP 許可リスト

多くの組織は、Snowflake ネットワークポリシーを使用して Snowflake インスタンスへのアクセスを禁止しています。また、選択した IP セットやその他の一意に識別できるソースからのアクセスも許可します。プライベートコネクトを使用して Snowflake への Data 360 接続を作成する場合、トラフィックは 1 つの AWS PrivateLink VPC エンドポイントから発信されます。このエンドポイントには、広範な Data 360 IP アドレスの配列のいずれかがあります。Data 360 が Snowflake に接続するように、VPC エンドポイントからのトラフィックを許可リストに登録します。Data 360 VPC エンドポイント ID または IP 範囲 10.0.0.0/8 を使用します。 VPC エンドポイントの ID を許可リストに登録することをお勧めします。既存のプライベートネットワークルートの詳細ページから ID を取得します。

IP 範囲を使用している場合は、10.0.0.0/8 の全範囲を許可リストに追加することをお勧めします。この範囲により、継続的なメンテナンスや、ネットワークの中断による停止を回避できます。Data 360 では、内部非公開 IP アドレスは予告なく変更される可能性があるため、特定の IP アドレスによる許可リスト登録はサポートされていません。

接続の問題をトラブルシューティングするには、ネットワークルートの詳細ページで使用可能な Data 360 VPC エンドポイントの Domain Name System (DNS) の dig または nslookup を使用して、関連付けられた IP アドレスを検索します。

Snowflake データ共有

Snowflake フェデレーション接続と Snowflake プライベートネットワークルートの関係は、接続を作成するときに発生します。データ共有ではプライベートコネクトの動作が異なります。Snowflake プライベートネットワークルートとデータ共有対象が同じ URL を使用している場合、対象の作成プロセスではプライベートコネクトが使用されます。その他の URL 種別の場合、Data 360 は最初に公開インターネットを使用して対象を作成します。

Data 360 Snowflake データ共有機能では、非公開 Snowflake インスタンスに Snowflake のセキュアデータ共有 (SDS) が使用されます。データ共有対象を作成するときに、OAuth サインインを使用して共有アカウントの所有権を確認します。検証が完了すると、Data 360 は OAuth トークンを含むすべてのサインインデータを削除できます。

データ共有対象の作成を正常に行うには、元のコンピューターに、許可されたネットワークの場所から Snowflake へのネットワークアクセス権が必要です。通常の設定では、ユーザーは企業 VPN に接続し、Snowflake はそのネットワークからの要求を許可するよう設定されます。他の要求では、このアカウントを使用してログインしません。通常、このステップでは、Salesforce Private Connect を使用するか、Data 360 が OAuth API エンドポイントに到達できるように Data 360 の公開 IP アドレスを一時的に許可リストに登録する必要があります。

Redshift および Snowflake データ共有の実装

データ共有の実装は、Redshift と Snowflake で異なります。Redshift の実装にはプライベートコネクトは必要ありません。Snowflake では、データ共有対象の初期作成時にプライベートコネクトが必要です。この違いは、クレジット消費が作成時にのみ発生し、約 1 クレジットが必要であることを意味します。共有またはアクセスされるデータ量に関係なく、Snowflake データ共有のプライベートコネクトでは追加のクレジット消費は発生しません。

詳細は、「Salesforce Data CloudからAmazon Redshift for Unified AnalyticsへのHarness Zero Copyデータ共有 – パート2」を参照してください。

複数の Redshift インスタンスのサポート

1 つの VPC 上の複数の Redshift インスタンスは、アクセスに 1 つの Redshift プライベートネットワークルートを使用できません。さらに、プライベートネットワークルート (PNR) と Redshift インスタンス間には 1 対 1 の対応付けが存在します。

プロファイルエクスプローラーに関する考慮事項

プロファイル エクスプローラーまたは Data 360 統合プロファイル Lightning アプリケーションを使用するときは、次の考慮事項に留意してください。

  • Profile Explorer の個人ビューと Data 360 の統合プロファイル Lightning アプリケーションでは、データスペースから統合個人レコードを表示する場合、および設定時に選択した統合個人データモデルオブジェクトのプロファイルデータのみが表示されます。
  • Data 360 プロファイルインサイトアプリケーションには、設定された計算済みインサイトに 1 つのディメンションがあり、選択された統合プロファイルに関連付けられている場合にのみ結果が表示されます。

  • Data 360 Profile Insights アプリケーションでは、グラフを使用して数値指標が表示されます。数値以外の評価指標 (テキストまたは日付の評価指標など) を表示するようにアプリケーションが設定されている場合、それらの値はグラフ形式では表示できないため、エラーが返されます。

取得拡張生成の使用

Data 360 の取得拡張生成 (RAG) は、大規模言語モデル (LLM) プロンプトをグラウンディングするためのフレームワークです。RAG は、プロンプトに正確で最新の関連情報を追加することで、ユーザーにとっての LLM 応答の関連性と価値を向上させます。

LLM プロンプトを送信すると、Data 360 で RAG を実行します。

  1. Data Cloud のベクトルデータベースでインデックス付けされた構造化データと非構造化データから関連情報を取得します。
  2. この情報を元のプロンプトと組み合わせることで、プロンプトを増強します。
  3. プロンプト応答を生成する

RAG は、オフラインでの準備とオンラインでの使用の 2 つの主要な部分に分けて考えることをお勧めします。

オフライン準備

RAG を実装するには、まず RAG で使用する構造化データと非構造化データをグラウンディング LLM プロンプトに接続します。

Data 360 では、ベクトルデータベースを使用して非構造化データを管理します。ベクトル・データベースには、検索に最適化された方法でインデックス付けされた構造化コンテンツと非構造化コンテンツのコレクション（検索インデックス）が含まれます。コンテンツは、さまざまなソースやファイル形式から取り込むことができます。RAGで使用される非構造化コンテンツの例として、サービス返信、ケース、RFP応答、Knowledge記事、メール、ミーティングメモなどがあります。

オフライン準備の手順は次のとおりです。

  1. 非構造化データを接続します。
  2. コンテンツをチャンク化してベクトル化する検索インデックス設定を作成します。

    チャンクはテキストを意味的に意味のある小さな単位に分割し、ベクトル化はチャンクをテキストの数値表現に変換して意味的な類似性を取得します。

  3. Data 360 で検索インデックスを保存および管理します。

    取得者は、検索インデックスとプロンプトテンプレート間のブリッジとして機能します。取得者は検索条件をさらに絞り込み、プロンプトの増強に使用される最も関連性の高い情報を取得します。さまざまな使用事例をサポートするために、AIモデル(旧称Einstein Studio)でカスタム リトリーバーを作成します。詳細は、「データの取得」を参照してください。

オンライン利用状況

RAG実装の最後の要素は、プロンプトテンプレートで取得者をコールすることです。プロンプトデザイナーは、特定のプロンプトテンプレートで、取得クエリと結果の設定をカスタマイズして、プロンプトに最も関連性の高い情報を入力できます。

オンライン使用には、次の手順が含まれます。

  1. 取得者は、プロンプトテンプレートから開始された動的クエリで呼び出されます。
  2. クエリはベクトル化されます (数値表現に変換されます)。ベクトル化により、検索インデックスでセマンティック一致を検索できます。
  3. このクエリは、Data 360 のベクトルデータベースから関連するコンテキストを取得します。
  4. 元のプロンプトには、検索インデックスから取得した情報が入力されます。
  5. プロンプトが LLM に送信され、LLM がプロンプト応答を生成して返します。

多くの LLM は、一般的に古いコンテンツについてインターネットでトレーニングされていました。RAG を使用すると、プロンプトテンプレートユーザーは LLM に最も正確な最新情報を提供するだけでなく、モデルを再トレーニングして微調整することなく独自のデータを LLM に取り込むことができるため、状況と使用事例により関連性の高い応答を生成できます。

C360 セマンティックモデルについて

Data 360 を搭載した C360 セマンティックモデルは、データの「プライマリマップ」として機能する 1 つのモデルを提供することで、断片化されたデータと総計値の問題を解決します。

必要なエディション

使用可能なエディション: Data 360 でサポートされるすべてのエディション。 「Data 360 Edition の可用性」を参照してください。

C360 セマンティックモデル

このモデルでは、セールス、サービス、マーケティング、コマースなど、さまざまな Salesforce クラウドの統合ビューが提供されます。SDM も拡張可能です。これにより、コア構造を把握しながら、特定の業種やドメインのニーズに合わせてコアモデルを拡張できます。

主なメリット

主なメリット:

  • 一貫性のある統合評価指標: Sales、Service、Marketing、Commerce の各クラウドの重要業績評価指標を 1 つの信頼できるビューで確認できます。
  • 迅速なインサイト: ユーザーがモデルをゼロから再構築することなく、クラウド全体でデータをすばやく分析できるようにします。
  • インテリジェントなワークフローを有効化: 一貫したデータを使用して、よりスマートな自動化プロセスとアクションを促進します。
  • 拡張性: SDM では、コア構造との整合性を維持しながら、特定の業種またはドメインのニーズに合わせてコアモデルを拡張できます。

C360 セマンティックモデルのコンポーネント

C360 セマンティックモデルでは、Salesforce クラウド標準 DMO を統合モデルに統合し、一元的な場所で一貫したクロスクラウド評価指標を提供します。Data 360 を搭載しており、統合アクセスを提供し、市場投入までの時間を短縮します。

モデルのコアコンポーネントは、標準テーブル、共有テーブル、論理ビューの 3 つの主要な機能を活用します。

  • 標準結果テーブル: これらのテーブルでは、キャンペーン、リード、商談、注文、収益、ケースなどの評価指標と基準を取得します。日次、月次、トランザクションレベルのデータなど、さまざまな粒度がサポートされます。
  • 標準ディメンションテーブル: これらのテーブルでは、顧客、商品、ユーザー、地域などのビジネスエンティティを定義し、階層リレーションを含めます。たとえば、商品はカテゴリとブランドの一部です。
  • 共有テーブルまたは共有ディメンション: クロスクラウドインサイトをサポートする例として、取引先、個人、またはユーザーがあります。セールス、サービス、マーケティング、コマースなど、さまざまなビジネス領域の指標を次の共通のディメンションを使用して分析できます。一般的なテーブルの例として、取引先、取引先責任者、商品と商品階層、個人、ユーザー、日付などがあります。
  • 論理ビュー: これらのビューは、重複するオブジェクト、共用体、結合、またはカスタム SQL を管理します。

C360 セマンティックモデルの具体的な DMO には、Sales Cloud、Service Cloud、Marketing Cloud、Commerce Cloud のオブジェクトの選択と、これらのクラウドで共有される一般的なテーブル/ディメンションが含まれます。総計値は計算項目 (計算ディメンションと基準) として作成されます。
