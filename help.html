CRM Analytics 総合ヘルプ

概念の全体像から、データ連携・ダッシュボード作成・共有設定、エンドユーザー操作、そしてイベントモニタリングのログ分析までを1ページに。自分の理解と、顧客への手順説明の両方に使えます。

最終更新: 2026-07-11 ／ 対象: Salesforce CRM Analytics（旧 Tableau CRM / Einstein Analytics / Wave）

1. CRM Analytics とは

CRM Analytics（CRMA）は、Salesforce に組み込まれた BI（ビジネスインテリジェンス）プラットフォームです。Salesforce のデータや外部データを取り込み、対話的なダッシュボードで「集計・可視化・深掘り」を行います。過去に Wave Analytics → Einstein Analytics → Tableau CRM と改称され、現在の名称が CRM Analytics です。

レポート/ダッシュボード（標準）との違い

標準レポートは「1オブジェクト＋関連」中心でリアルタイム。CRMA は大量データを事前に取り込んだ独自データセット上で動くため、数千万行でも高速に、複数ソース横断で分析できます。

Tableau との違い

Tableau は独立した汎用 BI。CRMA は Salesforce ネイティブで、権限・レコードへのリンク・Flow/Apex 連携が強み。Salesforce 中心の分析なら CRMA が親和的です。

💡 ひとことで言うと 「Salesforce の中に住んでいる、超高速で対話的な分析ダッシュボード基盤」。データを取り込み（レシピ）→データセット化→ダッシュボードで見せる、が基本の流れです。

2. 基本用語（まずこれだけ）

用語意味たとえ
データセット (Dataset)CRMA 用に最適化された分析専用のデータの塊。ダッシュボードの元データ。分析用に整えた「表」
レシピ (Recipe)データを取り込み・結合・加工してデータセットを作る処理。Data Prep の中心。料理の「調理手順」
データフロー (Dataflow)レシピの前世代のETL。今は原則レシピを使う。旧式の調理手順
コネクタ (Connector)Salesforce や外部DB等からデータを引き込む接続設定。食材の「仕入れ先」
アプリ (App)ダッシュボード・レンズ・データセットをまとめるフォルダ。共有の単位。作品を入れる「フォルダ」
ダッシュボード (Dashboard)複数のチャート/表/フィルタを配置した対話画面。完成した「料理の盛り付け」
レンズ (Lens)1つの探索的なチャート。アドホック分析の起点。味見の一皿
SAQL / SOQLSAQL は CRMA 独自のクエリ言語。SOQL は Salesforce 標準クエリ。専用の「レシピ言語」

3. 全体アーキテクチャ（データの流れ）

CRMA は左から右へデータが流れます。まずこの1本の流れを頭に入れると全体が理解できます。

①ソース          ②取り込み/加工        ③保管            ④可視化           ⑤利用
┌──────────┐    ┌──────────────┐    ┌──────────┐    ┌──────────────┐   ┌────────┐
│Salesforce│    │  コネクタ     │    │          │    │ ダッシュボード │   │ 閲覧    │
│オブジェクト│──▶│    ＋        │──▶│ データセット│──▶│    ＋       │──▶│ フィルタ │
│外部DB/CSV │    │  レシピ(ETL) │    │          │    │  レンズ      │   │ 深掘り  │
└──────────┘    └──────────────┘    └──────────┘    └──────────────┘   └────────┘
                       │                                    │
                   スケジュール実行                    Salesforceレコードへリンク
✅ 覚え方 仕入れ（コネクタ）→ 調理（レシピ）→ 盛り付け（ダッシュボード）→ 提供（共有）。管理者は①〜④、エンドユーザーは主に⑤を触ります。

4. 初期セットアップ 管理者

CRMA を使い始めるまでの一度きりの準備です。

1

CRM Analytics を有効化 / ライセンス確認

設定 → クイック検索で「Analytics」→ 「CRM Analytics を有効化」をオン。ユーザーには CRM Analytics Plus などの権限セットライセンスが必要です。

2

権限セットを割り当て

標準権限セット（例：CRM Analytics Plus Admin / CRM Analytics Plus User）を、管理者と閲覧者にそれぞれ割り当てます。管理者＝作成・データ管理、ユーザー＝閲覧・探索。

3

Analytics スタジオを開く

アプリランチャー（⠿）→「Analytics スタジオ」。ここが CRMA の作業拠点です。

4

データ同期（レプリケーション）を有効化

データマネージャの設定で「データ同期を有効化」をオン。ソースを一度キャッシュし、レシピ実行を高速化します。

⚠️ よくあるつまずき 「Analytics スタジオが見えない」の大半は権限セットライセンスの未割り当てです。ユーザーの詳細ページで PSL が付いているか確認してください。

5. データ連携（レシピ / Data Prep） 管理者

分析の質は「どんなデータセットを作るか」で決まります。中心となるのがレシピです。

レシピの基本ノード

ノード役割
入力 (Input)同期済みデータやCSV、他データセットを読み込む
結合 (Join)複数ソースをキーで突き合わせる（例：商談＋取引先）
変換 (Transform)列の追加・計算式・型変換・日付処理
集計 (Aggregate)グループごとの合計・件数・平均を作る
フィルタ (Filter)不要な行を除外
出力 (Output)加工結果をデータセットとして保存

レシピ作成の手順

1

データマネージャ → レシピ → 新規

Analytics スタジオ左下の歯車、または「データマネージャ」から入ります。

2

入力ノードでソースを選択

同期済みの Salesforce オブジェクト（例：Opportunity）を追加。

3

加工ノードをつなぐ

結合・変換・集計・フィルタを目的に応じて追加。プレビューで結果を随時確認。

4

出力ノードでデータセット名を指定

保存先アプリと API 名を決めて保存。

5

スケジュール実行を設定

毎日/毎時など。ソース同期→レシピの順で最新化されます。

✅ 設計のコツ「1ダッシュボード＝1〜数データセット」を意識。粒度（行の単位）を揃え、表示に使う項目はあらかじめ整形しておくとダッシュボードが軽く・作りやすくなります。

6. アプリ / ダッシュボード作成 管理者/作成者

アプリを作る

Analytics スタジオ →「作成」→「アプリ」。空アプリ、またはテンプレートから開始できます。ダッシュボード・レンズ・データセットの入れ物です。

ダッシュボードを作る（ダッシュボードビルダー）

1

「作成 → ダッシュボード」

空のキャンバスかテンプレートを選択。

2

ウィジェットを配置

チャート・表・数値・フィルタ・トグル・画像・テキストをドラッグで配置。

3

クエリ（ステップ）を割り当て

各ウィジェットに「どのデータセットを、どう集計して見せるか」を設定。GUI で作れます（内部は SAQL）。

4

フィルタ連動 / ファセットを設定

フィルタを操作すると全チャートが連動して絞り込まれるように。

5

プレビュー → 保存 → 実行

右上「プレビュー」で利用者目線を確認して保存。

💡 テンプレートを活用「Sales Analytics」「Service Analytics」など業務別テンプレートアプリを入れると、データセット・ダッシュボードが自動生成され、ゼロから作るより圧倒的に速いです。

7. 共有とセキュリティ 管理者

共有の2層構造

層制御対象設定場所
アプリ共有誰がアプリ（＝中のダッシュボード）を見られるか。表示のみ / 編集 / 管理。アプリの「共有」ダイアログ
行レベルセキュリティ (Security Predicate)同じダッシュボードでもユーザーごとに見える行を制限（例：自分の担当商談だけ）。データセットの編集 → セキュリティ述語
継承共有 (Sharing Inheritance)Salesforce 本体の共有ルールをデータセットに継承。データセット設定
🔒 重要データセットは取り込み時点でレコード共有から切り離されます。「担当者しか見えないはず」の情報が全員に見える事故を防ぐため、機密データには必ずセキュリティ述語 or 継承共有を設定してください。

セキュリティ述語の例

// 「自分が担当（OwnerId）の行だけ見せる」
'OwnerId' == "$User.Id"

// 「自分または同じ部署（Region）の行を見せる」
'OwnerId' == "$User.Id" || 'Region' == "$User.Region__c"

8. エンドユーザー操作 閲覧者

閲覧者は「作る」ことは不要です。見る・絞り込む・深掘りする・共有するの4動作だけ覚えれば使えます。

ダッシュボードを開く

アプリランチャー →「Analytics スタジオ」または、Salesforce のレコードページやタブに埋め込まれたダッシュボードから開きます。

① 見る

数値・グラフをそのまま確認。凡例やタイトルで何の指標かを把握します。

② 絞り込む（フィルタ）

上部のフィルタやトグルで、期間・地域・担当などを選ぶと全チャートが連動して変わります。

③ 深掘り（ドリル）

グラフの棒や扇をクリック →「深掘り」で内訳へ。別項目でグルーピングし直すこともできます。

④ レコードへ移動

明細をクリックすると元の Salesforce レコード（商談・取引先等）へジャンプできる場合があります。

結果を活用する

  • 共有 / スナップショット：右上メニューから、現在のフィルタ状態のリンクや画像を共有。
  • ダウンロード：チャートのデータを CSV/画像でエクスポート（権限による）。
  • サブスクリプション（通知）：条件を満たしたら通知を受け取る設定（Smart Notification）。
✅ 迷ったら「フィルタをいったん全部クリア」→「見たい期間を選ぶ」→「気になる棒をクリックして深掘り」。この3ステップでほぼ目的に届きます。

9. イベントモニタリング概要 管理者/監査

イベントモニタリング (Event Monitoring) は、「誰が・いつ・どこから・何をしたか」を記録する Salesforce の監査ログ機能です。ログイン、レポート出力、API 呼び出し、ダウンロード、Apex 実行などの操作がイベント種別ごとに記録されます。CRMA と組み合わせると、これらの膨大なログをダッシュボードで可視化できます。

⚠️ 前提（ライセンス）イベントモニタリングは Salesforce Shield または Event Monitoring アドオンが必要です。標準組織には Event Log File（ELF）が含まれないことが多く、まず有効化されているか確認してください。

3つの取得手段

手段内容特徴
Event Log File (ELF)EventLogFile オブジェクトに1日/1時間単位で生成されるログファイル（CSV）。過去ログの一括取得。生成に遅延あり。
Real-Time Event Monitoring◯◯EventStore オブジェクト等にほぼリアルタイムで保存。ログインやレポート閲覧等。直近の監視・ポリシー連動（Transaction Security）。
Event Monitoring Analytics AppELF を取り込んだCRMA テンプレートアプリ。ダッシュボードで即分析。ノーコードで可視化。本ページの主役。

代表的なイベント種別（EventType）

EventType記録される内容主な用途
Login / LoginAsログイン成否・IP・ブラウザ・代理ログイン不正アクセス・代理ログインの監査
ReportExportレポートのエクスポート操作情報持ち出しの検知
API / RestApi / BulkApiAPI 経由のデータアクセス大量抽出・連携の監視
URIUI ページ表示（画面遷移）利用状況・アクセス経路の分析
ApexExecution / ApexCalloutApex 実行・外部コールアウト性能・エラー分析
ContentDocumentLink / Downloadファイルのダウンロード機密ファイル持ち出しの検知

10. Event Monitoring Analytics App でログを分析 管理者

最短で「ログを見える化」する王道は、Event Monitoring Analytics テンプレートアプリを作成することです。ELF を自動で取り込み、ログイン・API・ページ表示などのダッシュボードが一式生成されます。

導入手順

1

前提を確認

Shield / Event Monitoring 有効、CRMA 有効、EventLogFile にデータが生成されていること。

2

Analytics スタジオ →「作成 → アプリ」

テンプレートから 「Event Monitoring Analytics」 を選択。

3

ウィザードで設定

取り込むイベント種別・保持期間・（あれば）Setup Audit Trail 連携などを選択。

4

アプリ作成 → データ更新（レシピ実行）

初回のデータフロー/レシピが走り、データセットが生成されます。完了まで数分〜。

5

スケジュール設定

毎日実行にして、ELF を継続的に取り込むようにします。

主なダッシュボードと読み方

ダッシュボード見るもの気づけること
User Activity / Overviewログイン数、アクティブユーザー、地域別アクセス普段と違う時間帯・国からのログイン
Report / Data Export誰がどのレポートを何件出力したか退職直前の大量エクスポート等の異常
API UsageAPI 呼び出し量、呼び出し元、種別特定ユーザー/連携の急増、上限逼迫
Page Views (URI)よく見られる画面、遷移傾向使われていない機能／過剰アクセス
Performanceページ/Apex/DB の処理時間遅い画面・重い処理の特定
🔒 監査での典型的な使い方「ReportExport が普段0の人が急に大量出力」「深夜・海外IPからの Login」「API が特定ユーザーだけ桁違い」——これらをダッシュボードのフィルタ（ユーザー/日付/IP）で切り分けるのが基本動作です。
✅ 覚えておくと便利ELF は過去分の一括ログなので「昨日までの傾向分析」に強い一方、リアルタイム検知には Real-Time Event Monitoring + Transaction Security ポリシーを併用します（例：条件に合致したら即ブロック/通知）。

11. ログを直接取得する（API / SOQL） 管理者/開発

CRMA アプリを使わず、ログファイルを直接落として調べたい場合の手順です。ELF は「メタ情報を SOQL で引く → 実体の CSV を取得」の2段構えです。

① EventLogFile を SOQL で検索

-- 昨日以降の ReportExport / Login ログの一覧を取得
SELECT Id, EventType, LogDate, LogFileLength, LogFileFieldNames
FROM EventLogFile
WHERE EventType IN ('ReportExport','Login')
  AND LogDate = LAST_N_DAYS:7
ORDER BY LogDate DESC

LogFile 項目に CSV 本体が Base64 で入っています。件数が多い場合は上記でIDを絞ってから本体を取得します。

② Salesforce CLI でログ本体を取得

# 一覧を確認（sf CLI / SOQL）
sf data query --query "SELECT Id, EventType, LogDate FROM EventLogFile WHERE LogDate = LAST_N_DAYS:1" --target-org trueagent

# 個別ログの CSV 本体を REST で取得（{ID} は上のクエリ結果）
sf api request rest "/services/data/v60.0/sobjects/EventLogFile/{ID}/LogFile" --target-org trueagent > event_log.csv
💡 ヒントELF は組織設定により1日1回 or 1時間ごとに生成され、直近のイベントは反映に遅延があります。「今この瞬間」を見たい場合は Real-Time Event Monitoring 側（◯◯EventStore）を参照してください。
⚠️ 保持期間ELF の保持はライセンスにより1日〜30日など上限があります。長期保管したい場合は CRMA データセットに取り込む／外部にエクスポートして蓄積する運用が必要です。

12. よくある質問

Q. 標準レポートで足りるのに、なぜ CRMA？

A. データ量が大きい／複数ソース横断／対話的な深掘りが要る場合に効きます。単一オブジェクトの定型集計なら標準レポートで十分です。

Q. データはリアルタイムで反映される？

A. 基本はスケジュール実行時点のスナップショットです。同期＋レシピの実行間隔がそのまま鮮度になります（例：毎朝1回なら前日分）。

Q. Analytics スタジオが見えない

A. ほぼ権限セットライセンス未割り当てが原因。CRMA の有効化とユーザーへの PSL 付与を確認してください。

Q. イベントモニタリングは追加費用？

A. はい、Shield または Event Monitoring アドオンが必要です。含まれているかは組織の契約次第です。

Q. ログを1年分ためて分析したい

A. ELF の保持は短いため、CRMA データセットに継続取り込みして蓄積するのが定石です。
