EventLogFile 早わかりガイド

Salesforce の「誰が・いつ・何をしたか」を記録するイベントモニタリングログの読み方 / ベンダー作業を追うコツ

0. このページの目的

EventLogFile（イベントログファイル）は、組織の中で起きた操作を 1時間ごと / 1日ごとの CSV ファイル にまとめてくれるオブジェクトです。ログイン・レポート出力・API 呼び出し・ページ表示などが記録され、「誰がいつ何をしたか」を後から追えます。

ひとことで： 設定変更履歴（監査証跡）とは別物で、こちらは「日々の操作の生ログ」。外部ベンダーが API で大量データを抜いた / 深夜に大量ログインした といった調査に使います。
※ 利用には Event Monitoring（Shield または Event Monitoring アドオン） のライセンスが必要です。

1. EventLogFile とは

EventLogFile は「1本のログファイル」を表すレコードです。1レコード ＝ 「あるイベント種別（例: Login）× ある日 × ある集計間隔」の CSV ファイル1つ、と考えると分かりやすいです。

  • 読み取り専用。 API/レポートから照会するだけで、作成・編集はできません。
  • 1レコードの中に、その日の同種イベントが何百〜何万行まとめて入っています（＝ CSV 本体）。
  • Salesforce が自動生成します。ログイン画面で操作した瞬間に出るのではなく、少し遅れてファイル化されます（後述）。
2段階で使う： ① まず EventLogFile を SOQL で検索して「どんなログファイルがあるか」の一覧を取る → ② 目的のレコードの LogFile フィールド（CSV 本体）をダウンロードして中身を見る。この2ステップが基本です。

2. ログの構造（ここが肝）

EventLogFile の分かりにくさは、ほぼ全部「構造」に集約されます。ここだけ押さえれば読めます。

タイミング（いつログができるか）

種類Interval 値生成タイミング用途
1日ログDailyイベント発生の翌日にその日ぶんをまとめて生成通常の日次監査。デフォルト
1時間ログHourlyおおむね数時間以内に1時間ぶんを生成（準リアルタイム）インシデント調査・当日中に見たい時
要注意： リアルタイムではありません。「今さっきの操作」はまだログに出ていないのが普通です。特に Daily は翌日になるまで出ません。「ログが無い＝操作が無い」ではないので注意。
頻度と保持は別物： Daily / Hourly は「どのくらいの間隔でファイル化するか」という生成頻度の話です。「何日残るか」（保持期間）は別軸で、Edition・ライセンスに依存します（無償ぶんは約1日、有償の Event Monitoring は最大1年）。詳細は §8。

1レコードを分解すると

1つの EventLogFile レコードは、下の要素で「どの CSV か」が決まります。

  • EventType … 何のログか（Login / API / Report …）
  • LogDate … 何日ぶんか
  • Interval … Daily か Hourly か
  • Sequence … 同じ日・同じ種別で複数ファイルに分かれた時の連番
  • LogFile … CSV 本体（これをダウンロードして中身を読む）

CSV の中身の見方

CSV には共通の先頭列があり、ここを見れば「誰が・いつ・どこから」が分かります。

列名意味調査での使いどころ
EVENT_TYPEイベント種別ファイル種別と一致
TIMESTAMP / TIMESTAMP_DERIVED発生時刻（UTC）時刻は UTC。日本時間は +9時間して読む
USER_ID / USER_ID_DERIVED実行ユーザーの18桁ID「誰が」を特定する主キー
CLIENT_IP接続元IPアドレス社外/海外IP、見慣れないIPの検知
SESSION_KEY / LOGIN_KEYセッション/ログインの識別子一連の操作を1本につなげて追跡
REQUEST_IDリクエスト識別子種別をまたいで同じ操作を突き合わせ
RUN_TIME / CPU_TIME処理時間(ms)重い処理・パフォーマンス調査
コツ： どの列が入っているかは LogFileFieldNames（列名一覧）と LogFileFieldTypes（型一覧）フィールドで事前に確認できます。EventType ごとに列は違います。

種別は数十あります。調査でよく使う代表を用途別に。

5. ログを見るときのポイント（実務チェックリスト）

  1. 時刻は必ず UTC。 TIMESTAMP は協定世界時。日本の出来事と突き合わせる時は +9時間。「深夜3時のアクセス」が実は日本の正午だった、という読み違いに注意。
  2. 「誰が」は USER_ID で。 名前ではなく18桁ID。別途 User をクエリして氏名に変換すると読みやすい。
  3. 「どこから」は CLIENT_IP。 普段と違うIP・海外IP・データセンターIPは要チェック。ベンダーは固定IPのことが多いので、そのIP一覧を先に控えておくと判別が速い。
  4. 一連の操作は SESSION_KEY / LOGIN_KEY で束ねる。 「ログイン→レポート出力→ログアウト」を1本の線として追える。
  5. 量の異常を見る。 ReportExport / BulkApi の急増、普段0が突然数千行、は持ち出しのサイン。LogFileLength の急な増加も目印。
  6. ログの欠損＝安全ではない。 Daily は翌日まで出ない／保持期間を過ぎると消える。「無いこと」を無罪の証拠にしない。
  7. 種別をまたぐ時は REQUEST_ID。 同じ操作が API と Apex 両方に記録されることがあり、REQUEST_ID で名寄せできる。

6. ベンダー作業で出てくるログの例

外部ベンダーが開発・保守作業をすると、典型的に下記のようなログが並びます。「これは何の作業か」を読めるようにしておくのがこのセクションの狙いです。

① 開発ツール（VS Code / sfdx CLI）で接続して作業

EVENT_TYPE  TIMESTAMP(UTC)        USER_ID            CLIENT_IP       (概要)
Login       2026-07-11T23:40:12Z  0055i0000…VendorA  203.0.113.10    APIログイン(OAuth)
API         2026-07-11T23:41:02Z  0055i0000…VendorA  203.0.113.10    Metadata取得(retrieve)
MetadataApiOperation 2026-07-11T23:55:20Z 0055i0000…VendorA 203.0.113.10  deploy 実行
ApexExecution 2026-07-12T00:03:11Z 0055i0000…VendorA 203.0.113.10   テスト実行

→ OAuth/API 経由のログイン＋MetadataApiOperationが並んだら「ベンダーがコードを配備した」合図。deploy の直後に ApexTrigger/Flow が動き出したら実装が有効化されたということ。

② Bulk / API で大量データを投入・抽出

BulkApi   2026-07-12T01:10:00Z  0055i0000…VendorA  203.0.113.10   job投入(insert 5万件)
BulkApi   2026-07-12T01:12:30Z  0055i0000…VendorA  203.0.113.10   batch処理
RestApi   2026-07-12T01:20:00Z  0055i0000…VendorA  203.0.113.10   query(件数確認)

→ データ移行/一括更新の典型。件数と時間帯を控えておくと「予定外の抽出」との区別がつく。ROWS_PROCESSED 列で処理件数が見える。

③ 管理者に代理ログインして画面操作（LoginAs）

LoginAs   2026-07-12T02:00:00Z  管理者ID → 対象ユーザーID           ベンダーが代理ログイン
URI       2026-07-12T02:01:15Z  対象ユーザーID  203.0.113.10          設定画面を表示
URI       2026-07-12T02:03:40Z  対象ユーザーID  203.0.113.10          レコード確認

→ LoginAs が出たら「誰かが別ユーザーになりすまして操作」。正規のサポート作業か、要確認の対象か切り分ける。DELEGATED_USER 列で「元の人／なりすまし先」が分かる。

④ 外部システム連携（ApexCallout）を仕込んだ

ApexCallout 2026-07-12T03:00:00Z  自動プロセス/連携ユーザー  —   外部APIへ送信(URL, ステータス)

→ 送信先URL・HTTPステータス・応答時間が記録される。連携先が意図通りか、エラー(4xx/5xx)が出ていないかを確認。

調査の型： ①ベンダーの接続元IPとユーザーIDを先に確定 → ②その条件で Login / MetadataApiOperation / BulkApi を時系列に並べる → ③「作業予定表」と突き合わせる。この3手で「予定通りの作業か／想定外か」がほぼ判別できます。

7. 取得手順（SOQL / CLI）

① まず一覧を取る（SOQL）

SELECT Id, EventType, LogDate, Interval, Sequence, LogFileLength
FROM EventLogFile
WHERE EventType = 'Login' AND LogDate = LAST_N_DAYS:7
ORDER BY LogDate DESC

② CSV 本体をダウンロード（Salesforce CLI）

# 一覧を取得
sf data query --query "SELECT Id, EventType, LogDate FROM EventLogFile WHERE EventType='API' AND LogDate=LAST_N_DAYS:1" --target-org ORG

# LogFile(CSV本体) を REST で取得して保存
sf api request rest "/services/data/v60.0/sobjects/EventLogFile/<取得したId>/LogFile" \
  --target-org ORG > login_log.csv
GUI 派なら： AppExchange の無料アプリ「Event Log File Browser」や、Setup > Event Monitoring Analytics を使うと、クエリを書かずにダウンロード/可視化できます。

8. つまずきポイント / 制限

ハマりどころ実態
ライセンスEvent Monitoring / Shield が必要。無いと EventType の多くが生成されない
リアルタイムでないDaily=翌日、Hourly=数時間遅れ。今の操作はまだ出ない
保持期間生成頻度（Daily/Hourly）と保持期間は別軸。 保持は Edition・ライセンス依存で、無償ぶんは 約1日、有償 Event Monitoring は 最大1年。長期保存は外部エクスポートが前提
時刻がUTC日本時間へ +9h 変換を忘れると読み違える
列がEventTypeごとに違う共通列以外は種別依存。LogFileFieldNames で毎回確認
LogFileはbase64/大容量数十MBになることも。SOQLで LogFile を直接SELECTせず、REST でファイル取得する
設定変更は別物「誰が項目を消したか」等の設定変更は Setup Audit Trail 側。EventLogFile には出ない
まとめの一言： EventLogFile は「操作の生ログ」。UTC・翌日反映・保持はライセンス依存（放置すると消える）・種別ごとに列が違う の4点だけ先に頭に入れておけば、あとは EventType で絞って CSV を開くだけです。
