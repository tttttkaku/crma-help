画面フローを起動するボタンの作成

取引先オブジェクトにアクションボタンを作成します。営業担当は取引先レコードページのボタンをクリックして画面フローを開始し、その取引先から科目の被招集者を登録します。

必要なエディション

使用可能なインターフェース: Salesforce Classic および Lightning Experience の両方

使用可能なエディション: Contact Manager Edition、Group Edition、Professional Edition、Enterprise Edition、Performance Edition、Unlimited Edition、Developer Edition、および Database.com Edition

管理パッケージは Database.com Edition では使用できません。
必要なユーザー権限
クイックアクションを作成および編集する 「アプリケーションのカスタマイズ」

このサンプルクイックアクションボタンは、Automate a Course Management Process Project (コース管理プロセスプロジェクトの自動化) と連動します。

クイックアクションボタンを作成すると、ユーザーは必要な場所 (取引先レコードページ) から画面フローに簡単にアクセスできます。取引先ページレイアウトに「被招集者の登録」という表示ラベルのボタンを追加することで、担当者はその取引先に関連付けられた取引先責任者の登録フローをすぐに起動できます。フローを移動したり、検索したりする必要はありません。このボタンは、取引先のレコード ID をフローに渡します。この ID を使用して、新しく作成された取引先責任者を正しい取引先に関連付けます。このコンテキストアクセスにより、営業担当はすでに表示している取引先から 1 回のクリックで出席者を登録できるため、ユーザーの採用が向上します。自動化は、個別に検索して起動する必要がある個別のツールではなく、ワークフローの自然な一部のように感じられます。

メモ 画面フローを配布するその他の方法については、「フローの配布」を参照してください。
  1. [設定] で [オブジェクトマネージャー] をクリックします。
  2. [取引先] を選択します。
  3. [ボタン、リンク、およびアクション] をクリックします。
  4. [新規アクション] をクリックします。
  5. [アクション種別] で、[フロー] を選択します。
  6. [フロー] で、[Register New Attendee for a Course (コースの新規出席者の登録)] を選択します。
  7. [表示ラベル] に「Register Attendee」 (出席者の登録) と入力します。
    API 参照名を自動入力します。
  8. [保存] をクリックします。
  9. [ページレイアウト] をクリックし、[アカウントレイアウト] を選択します。
  10. [モバイルおよび Lightning のアクション] をクリックします。
  11. [被招集者の登録] アクションを [Salesforce モバイルおよび Lightning Experience アクション] セクションにドラッグします。
  12. [保存] をクリックします。
  13. 取引先レコードを開き、[出席者を登録] ボタンがあることを確認します。
  14. [被招集者を登録] をクリックし、サンプルデータを使用してフローを再度テストします。
    営業担当は、取引先ページから直接コースの被招集者を登録できるようになりました。

コースの被招集者を登録する画面フローの作成

画面フローを使用して登録プロセスを合理化します。営業担当は画面フローを使用して、コース被招集者とコース提供に関するすべての関連情報を取得し、被招集者にサインアップすることができます。

必要なエディション

サポートされているエディションを表示する。
必要なユーザー権限
Einstein for Flow や Agentforce for Flow など、Flow Builder で使用できるすべてのフロー タイプ、要素、機能を使用してフローを開く、編集、作成、有効化、または無効化する 「フローの管理」
メモ 「フローの管理」権限を持つ管理者である必要はありません。プロファイルまたは権限セットに追加するようにシステム管理者に依頼してください。

このサンプルフローは、「コース管理プロセスプロジェクトの自動化」の他のサンプルフローと連動します。

この画面フローでは、営業担当がコースの被招集者を登録するためのガイド付きユーザーインターフェースが提供され、必要な情報をステップバイステップで収集し、エラーを適切に処理します。このフローでは、まず入力コンポーネントを使用して被招集者の詳細を収集し、重複する取引先責任者をチェックして重複するレコードが作成されないようにします。次に、被招集者の地域で絞り込まれ、今後スケジュールされている受講可能なコース提供が表示されるため、営業担当は適切なコースを選択できます。営業担当が登録を送信すると、フローによってコース被招集者レコードが作成され、保存前フローがトリガーされてデータが検証され、登録状況が設定されます。この画面フローには、問題が発生した場合 (同じ科目に同じ人を 2 回登録しようとした場合など) にわかりやすいエラーメッセージをキャッチして表示するための障害パス処理が含まれています。最後に、被招集者が登録されたか待機リストに登録されたかを示す確認画面がフローに表示されます。このアプローチにより、営業担当は常に完全で有効な情報を収集し、自動化フローでバックグラウンドでビジネスロジックを処理できます。

コース登録画面フローの作成

担当者がコースの受講生を登録するための画面フローとフローリソースを作成します。

  1. [フロー] リストビューを開きます。
    • Automation アプリケーションから、[フロー] タブを選択します。
    • 任意の Lightning アプリケーションの [フロー] タブで、アクション メニューをクリックし、[フローを開く] を選択します。
    • [設定] で、[クイック検索] ボックスに「フロー」と入力して、[フロー] を選択します。
    [オートメーションアプリケーション] および [フロー] タブのオプションには、[設定] アクセス権は必要ありません。
  2. 画面フローを作成します。
    • Automation アプリケーションで、[新規] をクリックします。[画面の自動化] を選択し、[画面フロー] を選択します。
    • [設定] から、[新規フロー] をクリックします。[画面の自動化] を選択し、[画面フロー] を選択します。
  3. 画面で使用する被招集者の地域を保持する選択リスト選択肢セットを作成します。
    被招集者の地域は、被招集者のロケーションに近いコースの配送を検索するために使用されます。
    1. ツールボックスを開くには、[] をクリックします。
    2. [新規リソース] をクリックし、[選択リスト選択セット] を選択します。
    3. [API 参照名] に「RegionPicklistChoiceSet」と入力します。
    4. [説明] に「被招集者の地域を保存します」と入力すると、被招集者の地域で使用可能なコースのみを表示できます。
    5. [オブジェクト] で、[コース配信] を選択します。
    6. [データ型] で [選択リスト] を選択します。
    7. [項目] で、[Region__c] を選択します。
    8. [完了] をクリックします。
  4. 担当者がボタンをクリックしてフローを開始する取引先レコードの ID を保存する変数を作成します。
    1. ツールボックスを開くには、[] をクリックします。
    2. [新規リソース] をクリックし、[変数] を選択します。
    3. [API 参照名] に「recordId」と入力します。
    4. 説明に営業担当がフローを開始するアカウントレコードのIDを保存しますと入力します。この ID は、アカウントに関連するレコードを作成するために使用され、フローに渡されます。
    5. [データ型] で [テキスト] を選択します。
    6. [フロー外部での可用性] で、[入力で使用可能] を選択します。
    7. [完了] をクリックします。

  1. 画面要素を使用して被招集者情報を収集します。
    1. [] をクリックし、[画面] を選択します。
    2. [表示ラベル] に「Collect Attendee Details」 (出席者の詳細の収集) と入力します。
    3. [API 参照名] に「CollectAttendeeDetailsScreen」と入力します。

    1. [Components (コンポーネント)] メニューで、[Name (名前)] コンポーネントをクリックします。
      [Collect Attendee Details (被招集者の詳細を収集)] 画面に名前コンポーネントが追加されます。
    2. [名前] プロパティパネルで、[API 参照名] に「AttendeeNameComponent」と入力します。
  3. メールコンポーネントを使用して、画面上の被招集者のメールを取得します。
    1. [コンポーネント] メニューで、[メール] コンポーネントをクリックします。
      [Collect Attendee Details (被招集者の詳細を収集)] 画面にメールコンポーネントが追加されます。
    2. [メール] プロパティパネルで、[API 参照名] に「AttendeeEmailComponent」と入力します。
  4. 選択リストコンポーネントを使用して、画面から被招集者の地域を取得します。
    1. [コンポーネント] メニューで、[選択リスト] コンポーネントをクリックします。
      [Collect Attendee Details (被招集者の詳細を収集)] 画面に選択リストコンポーネントが追加されます。
    2. [選択リスト] プロパティパネルで、[表示ラベル] に「出席者リージョン」と入力します。
    3. [API 参照名] に「AttendeeRegionPicklistComponent」と入力します。
    4. [必要] を選択します。
    5. [データ型] で [テキスト] を選択し、[コンポーネント種別] で [選択リスト] を選択します。
    6. [選択肢] で、[RegionPicklistChoiceSet] を選択します。
      選択リストコンポーネントの値は RegionPicklistChoiceSet によって指定されます。
    7. [完了] をクリックします。
  5. 同じ姓の取引先責任者を取得し、[レコードを取得] 要素でメールを送信します。
    1. 画面要素の後に [] をクリックし、[レコードを取得] を選択します。
    2. [表示ラベル] に「Get Duplicate Contact」と入力します。
      API 参照名を自動入力します。
    3. [説明] に、「CollectAttendeeDetailsScreen で AttendeeNameComponent および AttendeeEmailComponent と同じ姓とメールを持つ取引先責任者レコードを取得します。」と入力します。結果を Get Duplicate Contact レコード変数に保存します。
    4. [オブジェクト] で [取引先責任者] を選択します。
    5. [Filter Contact Records (取引先責任者レコードの絞り込み)] セクションの [条件の要件] で、[すべての条件に一致 (AND)] を選択します。
    6. [項目] で、[姓] を選択します。
    7. [演算子] で [次の文字列と一致する] を選択します。
    8. [値] で、[Collect Attendee Details]> [AttendeeNameComponent]> [姓] を選択します。
    9. [+ 条件を追加] をクリックします。
      [取引先責任者レコードを絞り込む] の下に 2 つ目の条件が追加されます。
    10. [項目] で、[メール] を選択します。
    11. [演算子] で [次の文字列と一致する] を選択します。
    12. [値] で、[Collect Attendee Details]> [AttendeeEmailComponent]> [Value] を選択します。
  6. 新しいコース出席者レコードの取引先責任者 ID を保存する変数を追加します。
    1. ツールボックスを開くには、[] をクリックします。
    2. [新規リソース] をクリックし、[変数] を選択します。
    3. [API 参照名] に「AttendeeContactId」と入力します。
    4. [説明] に「 コース被招集者の取引先責任者 ID を保存」と入力します。
    5. [データ型] で [テキスト] を選択します。
    6. [完了] をクリックします。
  7. [レコードを取得] 要素で [決定] 要素の重複する取引先責任者が見つかったかどうかを判断します。

    4. [Select Decision Logic (決定ロジックを選択)] で、[Define Manually (Default) (手動で定義 (デフォルト))] を選択します。

    3. [説明] に、「Get Duplicate Contact によって返されたレコードの取引先責任者 ID に AttendeeContactId 変数の値を設定します」と入力します。
    4. [変数] で、[AttendeeContactId] を選択します。
    5. [演算子] で [次の文字列と一致する] を選択します。
    6. [値] で、[Get Duplicate Contact]> [Contact ID] を選択します。
  9. [レコードを作成] 要素で重複する取引先責任者が見つからない場合は、取引先責任者レコードを作成します。取引先責任者のアカウントは、営業担当が画面フローを開始したレコードの ID です。
    1. [いいえ] パスで [] をクリックし、[レコードを作成] を選択します。

    4. [レコードフィールド値の設定方法] で、[手動] を選択します。
    5. [オブジェクト] で [取引先責任者] を選択します。
      [姓] 項目が最初の項目として自動的に選択されます。

コース提供のコース被招集者を登録するフローの設定

画面要素を追加してコース提供を選択し、レコード作成要素を追加してコース被招集者レコードを作成します。被招集者レコードの作成に問題がある場合、このフローでエラーが処理され、フローが正しいパスに設定されます。

  1. [レコードを取得] 要素を使用して、コース被招集者の地域での今後のコース提供を取得します。
    1. 終了要素の前にある をクリックし、[レコードを取得] を選択します。

重要

外部システム変更トリガーフローでは、ポーリング機能を使用して、選択したスケジュールでレコードを取得します。

ポーリング動作と無効化

  • 再試行: ポーリングが失敗すると、フローは最大 3 回連続して再試行します。
  • 自動無効化: ポーラーが 3 回連続して失敗した後に実行されます。この動作は、ポーラーレベルの失敗 (認証や接続など) に適用されますが、個々のレコードレベルの失敗には適用されません。
  • 再有効化: ポーラーの失敗によってフローが無効化された場合は、原因となっている問題を解決して、フローを手動で再有効化します。

ポーラーの制限と例外

  • Pre-execution Failures: 実行の開始前にポーラーが失敗した場合、開始要素で障害パスを使用できなくなります。
  • ペイロード制限: 128,000 文字を超えるポーリング応答 (データとメタデータを含む) がペイロード制限を超えている。

詳細と制限については、「MuleSoft for Flow: Integration Limits & Considerations (フロー用 MuleSoft: インテグレーションの制限と考慮事項)」を参照してください。

5. 接続を作成してから、自分でまたは Agentforce を使用してフローを作成する

接続を作成してシステムに接続します。Flow Builder またはオートメーションアプリケーションで接続を作成できますが、接続を編集または削除できるのはオートメーションアプリケーションのみです。接続を変更すると、すべての有効なフローにすぐに影響します。そのフローで使用されている接続は削除できません。

Flow Builder のサイドパネルで Agentforce を使用して、フローを自分で作成したり、自然言語を使用して新しい AI を駆使したフローを生成したり、既存のフローを変更したりできます。フローで Agentforce を使用するには、[設定] で生成 AI を有効にして、Data 360 をプロビジョニングします。フローを作成するには、オートメーション アプリケーションに移動し、[フロー] タブを選択して、[使用開始] をクリックします[Agentforce による構築のサポート] セクションを参照してください。次に、プロンプトを入力します。既存のフローを進化させるには、Flow Builder で開き、Agentforce サイドパネルを使用してプロンプトを入力します。

詳細は、外部システムと接続の作成に関する制限事項のページを参照してください。

6. MuleSoft for Flow の拡張機能の実装: インテグレーション

次の拡張機能を使用して、条件の追加、データ処理のカスタマイズ、フロー実行の制御を行い、より高度で効率的なインテグレーションフローを構築します。

  • コネクタバージョンの管理: マイナーアップデートを自動的に実行してセキュリティを確保しながら、メジャーアップグレードを手動で管理して安定性を高めます。
  • 条件付きロジックによるトリガーの絞り込み: トリガーフィールドで AND/OR ロジックを定義することで、効率を高め、API コールを削減します。
  • 入力値の合理化: Apex 項目および外部 API の動的型プロバイダと判読可能な表示ラベルを使用して、データ入力を合理化します。
  • 外部システムからレコードを返す: [レコードを取得] や [問題を取得] などのアクションを使用して、カスタム検索条件ロジックと並び替えに基づいてデータを取得します。
  • カスタムフィールドの対応付け: 割り当て要素内でカスタムフィールドを対応付けて、インテグレーションロジックに一意のサードパーティデータを含めます。
  • Trigger flows from file events: 条件に一致するファイル (種別や拡張子など) がレコードに添付されたときにフローを自動的に開始します。
  • ファイルの添付および転送: アクションを使用して、Salesforce と外部システム間で最大 15 MB のバイナリファイルとドキュメントを転送します。
  • Control polling frequency: 外部システム変更トリガーフローで更新をチェックする頻度を調整して、応答速度を向上させます。
  • カスタムフローコネクタを使用: コネクタビルダーを使用してカスタムフローコネクタを作成およびリリースします。

リリース固有の機能強化についての詳細は、『MuleSoft for Flow: Integration Release Notes』を参照してください。

比較するフローバージョンの選択

  2. [フロー] リストビュー、フローの詳細ページ、またはバージョンページから、フローのアクションをクリックし、[バージョンの比較] を選択します。

  3. 比較する 2 つのフローバージョンを選択します。
    一方のフローバージョンがベースフローバージョンで、他方が対象フローバージョンです。たとえば、バージョン 2 がベースフローバージョンで、バージョン 3 (最新) が対象フローバージョンです。[フロー] リストビューからフローバージョンを比較すると、デフォルトの対象フローバージョンは有効なバージョンになります。有効なバージョンがない場合、デフォルトの対象フローバージョンは最新バージョンになります。

比較結果の確認

  1. 比較結果を表示します。
    2 つのフローバージョンが同じ場合、表示する変更がないため、比較結果は表示されません。ヘッダーには、対象フローバージョンの変更日、変更を行ったユーザー、およびすべての変更の概要が表示されます。テーブルビューの各行には、要素の表示ラベル、API 参照名、変更の種別が表示されます。
    デフォルトでは、比較結果には変更された項目のみが表示されます。変更されたかどうかに関係なくすべての項目を表示するには、[変更済み項目のみを表示] を選択解除します。
  2. 結果のさまざまな変更種別を理解します。
    比較結果には、対象フローバージョンに対するフロー、要素、およびリソースの変更が表示されます。
    • 追加：項目の API 参照名と種別 ([レコードを取得] 要素など) がベースフローバージョンに存在しない。
    • 削除: 項目の API 参照名と種別 ([レコードを取得] 要素など) が対象フローバージョンに存在しません。
    • 更新: 対象フローバージョンで項目のプロパティが変更されました。
    • Connector Changed (コネクタの変更): 対象フローバージョンで次の要素または前の要素への要素のコネクタが変更された。この要素は対象フローバージョンでは変更されません。
    • 要素の API 参照名とデータ型は、フロー全体で一意に識別されます。たとえば、ベースフローバージョンに要素種別と API 参照名が含まれ、対象フローバージョンに異なる要素種別と API 参照名が含まれている場合、同じ API 参照名を持つ要素がベースフローバージョンから削除され、対象フローバージョンに追加されます。同様に、対象フローバージョンで要素の API 参照名が変更された場合、その要素はベースフローバージョンでは削除され、対象フローバージョンでは追加されて表示されます。
    • 比較結果には、コンポーネントのプロパティの変更は表示されますが、画面要素内の順序の変更は表示されません。たとえば、[表示テキスト] コンポーネントを別の位置に移動すると、比較結果に表示されません。フローの変更がコンポーネントの順序のみの場合、比較結果は空です。
  3. [詳細を表示] をクリックすると、項目の変更に関する詳細情報が表示されます。
    • 詳細には、[レコードを取得] 要素または [決定] 要素の AI の関連レコードに関する情報は含まれません。
    • 詳細では、次の変更がサポートされます。
      • [フロー API 参照名]、[フローの表示ラベル]、[説明]、[フローの実行方法]、[ソーステンプレート]、[上書き可能]、[元のフロー]、[トリガー順序]、[このフローの永続的ログを有効化] のフロープロパティ。
      • データ型: String、Number、Date、Date/Time、Time、Boolean、値を参照する差し込み項目、数式、Salesforce レコード ID。 サポートされていないデータ型は、「参照不可値」として表示されます。
    • 要素の [結果を実行する条件の要件] 項目が [カスタム条件ロジックに一致] に変更された場合、変更には条件の数が表示されます。たとえば、1 AND 2 などです。

共有比較の結果

フローの比較結果への直接リンクを共有したり、特定の比較にアクセスしたりできます。比較結果 URL には、特定のフローと、比較中の 2 つのバージョンを識別するクエリパラメーターが含まれます。

メモ 比較結果ページからフローを編集すると、クエリパラメーターがクリアされます。
  • flowId: 一意のフローバージョン ID を指定します。 このクエリパラメーターが存在しない場合、[新規自動化] ウィンドウが表示されます。
  • compareBaseFlowId: フローのベースフローバージョンの ID を指定します。
  • compareTargetFlowId: フローの対象フローバージョンの ID を指定します。

完全な URL 形式を使用して比較結果を共有します。

完全な URL の例を次に示します。

https://yourDomain.my.salesforce.com/flowBuilder.app?flowId=301YT0000000000000&compareBaseFlowId=301YT0000000000001&compareTargetFlowId=301YT0000000000002を参照してください。

URL にベースフローバージョン、対象フローバージョンが含まれていない場合、またはバージョン ID が無効である場合、比較ページは開きますが、ベースフローバージョンは空です。フローバージョンを比較するには、有効なフローバージョンを選択します。

出力変数 フローからフローをコールした外部システムまたはフローに値を渡すことができる変数。出力変数を使用すると、フローはデータを起動元に戻すことができます。

画面コンポーネント 画面コンポーネントは、情報を収集または表示するために画面フローの画面要素に配置される項目です。たとえば、実行時にユーザーから名と姓を収集する [名前] 画面コンポーネントを追加します。標準画面コンポーネントのリストについては、「標準画面コンポーネント」を参照してください。

サードパーティコネクタ サードパーティコネクタでは、外部システムへのコードなしの接続が提供されます。Flow Builder に接続する各外部システムの動作は、取得および操作する情報を外部システムにどのように保存しているかによって異なります。
トランザクション トランザクションは、1 つの単位として実行される一連の操作を表します。フローインタビューは、フロー以外の操作を実行するトランザクションに含めることができます。たとえば、スプレッドシートから 100 件のレコードを Salesforce 組織にアップロードすると、トランザクションが開始されます。これらのレコードを作成すると、新しいレコードごとにフローが実行されます。レコードの作成とすべてのフローの実行は 1 つのトランザクション内で行われます。
トリガー トリガーは、フローを起動するイベントです。たとえば、ケースに関連するエンタイトルメントを検索して割り当てるフローがあります。ケースの作成時には常にこのフローを起動するフロートリガーを作成します。これにより、すべての新しいケースにデフォルトのエンタイトルメントが自動的に設定されます。
変数 フロー全体で使用または変更できる値を保存するリソース。変数にはさまざまなデータ型 (テキスト、数値、レコード、Boolean など) を保存でき、複数の値を保存するコレクションとして設定できます。

Salesforce フローを使用したビジネスプロセスの自動化

Salesforce フローを使用して、手動の ToDo を不要にし、業務を効率化します。自動化を使用して手動プロセスと反復作業の数を減らすことで、所要時間が短縮され、精度とユーザーの生産性が向上し、コストが削減されます。Salesforce フローには、ガイド付きビジュアルエクスペリエンス、バックグラウンドの自動化、承認の自動化の作成に役立つ、Flow Builder や Flow Orchestration などのポイント & クリックなしのツールが用意されています。

この動画では、Flow Builder を使用してコードなしで強力な自動化を作成する方法をいくつか紹介します。

この動画は別のタブでご覧ください。

  • Salesforce フローを使用した自動化について
    Flow Builder、フローオーケストレーション、MuleSoft for Flow などの Salesforce フローツールを使用すると、ビジネスニーズに合わせて自動化ソリューションをすばやく設定および変更できます。これらのツールは ToDo とプロセスの自動化を簡単なインテグレーションソリューションと組み合わせることで、コードを記述することなく、あらゆるシステムのデータ変更をまとめてアクションを実行できます。
  • フローを使用した ToDo の自動化
    自動化により、反復作業が減り、チームがより迅速かつ正確に ToDo を完了できるようになります。Flow Builder では、コードなしで簡単な自動化や複雑な自動化、フォーム、ガイド付き環境を作成できます。Salesforce ページとエクスペリエンスサイトにフォームを追加し、ボタン、レコードトリガー、またはスケジュールを使用してフローを起動できます。
  • オーケストレーションを使用した複雑なプロセスの自動化
    会社の成長に伴い、ワークフローの複雑さも増します。プロセスでは、複数のタイムゾーンにまたがる複数の部門の複数のユーザーからの入力が必要になることがよくあります。この複雑さの増加により、各ユーザーが適切な順序でタスクを完了するまでの待機時間が長くなります。フローオーケストレーションは、オーケストレーション (複数のユーザーやシステムを操作する複数ステップのプロセス) を使用してこのプロセスを合理化するのに役立ちます。
  • フロー承認プロセスを使用した承認の自動化
    会社の成長に伴い、承認の複雑さも増し、多くの場合、異なるタイムゾーンの異なる部門の複数の担当者からの入力が必要になります。この複雑さにより、各ユーザーが適切な順序でレビューを完了するまでの待ち時間が長くなります。フロー承認プロセスは、ユーザー、システム、条件付きパスを含む複数ステップのレビューを調整するのに役立ちます。
  • 自動化アプリケーション
    オートメーション Lightning アプリケーションから既存のフローとオーケストレーションを監視および管理します。
  • おすすめ戦略を使用したオプションの提案
    Einstein Next Best Actionを使用して、カスタマイズされたおすすめを適切なタイミングで提供します。ビジネスロジックを適用して、修理、割引、アドオンサービスなど、いくつかの高価値の提案を提示する戦略を定義します。最終的なおすすめを自動化 Lightning アプリケーションまたは Experience Builder サイトに表示します。
  • 自動アクション
    自動アクションは、項目の更新やメールの送信などのアクションをバックグラウンドで実行する再利用可能なコンポーネントです。自動アクションを作成したら、プロセス、マイルストーン、その他の自動プロセスに追加します。
  • 従来の Salesforce フロー機能
    従来の Salesforce フロー機能には、プロセスビルダーとワークフロールールが含まれます。

ワークフロールールは、組織内のレコードの条件とアクションを定義できる従来の自動化機能です。サポートは 2025 年 12 月 31 日に終了しました。 新しい自動化には Flow Builder を使用し、必要に応じて既存のルールを移行します。

使用可能なインターフェース: Lightning Experience および Salesforce Classic
使用可能なエディション: Enterprise Edition、Performance Edition、Unlimited Edition、および Developer Edition
重要 ワークフロールールのサポートと更新は 2025 年 12 月 31 日で終了しました。 つまり、ワークフロールールのサポートは提供されず、ワークフロールール製品のバグは修正されません。「Workflow Rules & Process Builder End of Support (ワークフロールールとプロセスビルダーのサポート終了)」を参照してください。

2025 年 12 月 31 日以降、既存のワークフロールールは引き続き実行され、有効化、無効化、編集ができますが、Flow Builder を使用することをお勧めします。既存のワークフロールールを移行するには、Flow Builder への切り替えを計画し、フローに移行ツールを使用します。新しい自動化の場合は、Flow Builder でフローを作成します。

例: (if) 雨が降っていたら、(then) 傘を持っていく。

ワークフロールールは 2 つの主要コンポーネントに分解できます。

  • 条件: 「if/then」ステートメントの「if」部分。つまり、ワークフローが関連アクションを実行するためには、true でなければならない条件です。
  • アクション: 「if/then」ステートメントの「then」部分。つまり、レコードが条件を満たしたときに実行されるものです。

雨の例では、条件は「雨が降っている場合」で、アクションが「傘を持っていく」です。条件が満たされない場合 (「雨が降っていない」)、アクションは実行されません (「傘を持ってきていません」)。

おすすめ戦略を使用したオプションの提案

Einstein Next Best Actionを使用して、カスタマイズされたおすすめを適切なタイミングで提供します。ビジネスロジックを適用して、修理、割引、アドオンサービスなど、いくつかの高価値の提案を提示する戦略を定義します。最終的なおすすめを自動化 Lightning アプリケーションまたは Experience Builder サイトに表示します。

必要なエディション

Next Best Action でサポートされるエディションを表示します。
メモ 可能な場合は、[おすすめ戦略] フロー種別を使用して Flow Builder で戦略を作成することをお勧めしますが、Strategy Builder で戦略を作成することもできます。
  • Next Best Action について
    一意の条件に合わせて調整した、ユーザーへの提案とアクションを作成して表示します。ビジネスロジックを適用する戦略を作成し、おすすめを絞り込みます。戦略により、おすすめが洗練され、修正、割引、またはアドオンサービスのようないくつかの主要な提案に変換されます。最終的なおすすめを Lightning アプリケーションまたは Experience Builder サイトに表示します。
  • おすすめの作成
    Einstein Next Best Action を使用して、ユーザーに推奨する提案またはアクションを作成します。おすすめとは、取引先や取引先責任者と同様の標準 Salesforce レコードであり、戦略によって処理され、フローに関連付けられます。戦略では、ビジネスルール、予測モデル、他のデータソースを使用して、表示されるおすすめレコードを決定します。このプロセスの結果は、ユーザーに表示するコンテキスト固有のおすすめです。
  • 戦略の作成
    戦略によって、Salesforce Lightning レコードページに Einstein Next Best Action のおすすめを表示するタイミングと方法が決まります。たとえば、一部の顧客に割引を提供する場合、適切な顧客レコードを収集し、提示する割引オプションを特定する戦略を作成します。戦略を作成するには、Flow Builder (推奨) または Strategy Builder を使用できます。
  • おすすめの表示
    戦略を作成したら、戦略を実行しておすすめを表示するページを選択します。おすすめを表示する場所に応じて、Lightning レコードページ、アプリケーションのホームページ、Experience Cloud サイトページ、Visualforce ページ、または外部サイトを使用できます。

Apex クラスによるモデル JSON オブジェクト

Apex クラスで複雑なデータオブジェクトを定義します。たとえば、JSON オブジェクトに対応した Apex クラスを作成できます。このクラスは、テンプレートとして機能し、JSON をフローで使用できるオブジェクトに変換します。

Web 製品の Apex クラスを定義すると、REST コールを使用して Web サービスからデータを取得する Apex アクションを作成できます。Apex で定義されたデータ型を使用するフロー変数に、返されたデータを保存します。その後、フロー、Apex、および Lightning コンポーネントのデータを操作します。

例

WebProduct Apex テンプレートの例を次に示します。これには、メインの WebProduct クラスと、Price および Identifiers 用のクラスが含まれます。WebProduct には 3 種類のデータ型があります。

  • model 項目と brand 項目は、プリミティブ String データ型を使用します。
  • price 項目は、Price クラスを参照します。フロー用の Apex で定義されたデータ型では、内部クラスがサポートされません。このため、各クラスが別々のクラスファイルに保存されていることを確認してください。
  • identifiers 項目は、price に類似していますが、リストとして表現されます。Identifiers クラスでは、フローが JSON 配列にアクセスして 3 つの特定の SKU 番号のリストを表現できます。
  • parse メソッドは、JSON をフローがアクセスできる Apex オブジェクトに変換します。
  • フロー用の Apex クラスの項目には、@AuraEnabled アノテーションが必要です。
public class WebProduct {

@AuraEnabled
public String model;

@AuraEnabled
public String brand;

//Because the identifiers information is an array in the JSON schema, we create a separate class called Identifiers and define a property that contains a List.
@AuraEnabled
public List<Identifiers> identifiers;

//This field has an Apex-defined data type in the Price Apex class.
@AuraEnabled
public Price price;

//This method is used as part of the Create Apex Action section.
public static WebProduct parse(String json) {
return (WebProduct) System.JSON.deserialize(json, WebProduct.class);
}

Apex アクションの作成

JSON データをフローリソースに変換するメカニズムを作成すると、JSON データを取得する Apex クラスを作成できます。@InvocableMethod アノテーションを使用して、クラスをフローの Apex アクションとして定義できます。

GetWebProduct Apex クラスには、Apex アクションが定義されています。このアクションにより、REST エンドポイントから製品データが取得され、JSON 応答が解析されて WebProduct Apex オブジェクトが作成されます。

API バージョン 66.0 以降、呼び出し可能なアクション パラメータとして使用されるカスタム Apex クラスには、アクセス可能な引数なしコンストラクタが必要です。この例では、Requests および Results 内部クラスでコンストラクタが定義されていないため、Apex は暗黙的に引数なしのコンストラクタを提供します。これらのクラスに他のコンストラクターを追加する場合、クラスには適切なアクセス修飾子 (public または global) が含まれる明示的な引数なしコンストラクターが必要です。

開発者は、InvocableActionExtension メタデータ・ファイルを作成して、Flow Builder でのこの Apex アクションの表示方法をカスタマイズできます。このメタデータにより、入力順序とグルーピングの制御、カスタムヘッダーの追加、入力パラメーターの選択リストの定義、特定の入力のカスタムプロパティエディターの作成を行うことができます。詳細は、『メタデータ API 開発者ガイド』の「InvocableActionExtension」を参照してください。

例 
global with sharing class GetWebProduct {
 
    @InvocableMethod
    public static List<Results> GetWebProduct(List<Requests> requests)
       {
            Http http = new Http();
            HttpRequest request = new HttpRequest();
            String endpoint = requests[0].endpoint;
            String submittedId = requests[0].submittedId;
            request.setEndpoint(endpoint + submittedId );
            request.setMethod('GET');
            HttpResponse response = http.send(request);
           
            Results curResult = new Results();
            String responseJSON = response.getBody();
           
            WebProduct curProduct = WebProduct.parse(responseJSON);        
            curResult.WebProduct = curProduct;
           
            List<Results> resultsList = new List<Results>();
            resultsList.add(curResult);
            return resultsList;
       }
    
    global class Requests {
        @InvocableVariable
        global String submittedId;
        
        @InvocableVariable
        global String endpoint;       
    }
    
    global class Results {
        @InvocableVariable
        global WebProduct WebProduct;
    }

}
メモ

この例では、グローバルアクセス修飾子を使用します。これは、グローバルアクセス修飾子が管理パッケージシナリオ用に設計されているためです。組織内でのみ使用する Apex アクションを作成する場合は、global ではなく public を使用できます。

フローのビルディングブロック

フローは、要素、コネクタ、リソースの 3 つのコアコンポーネントから構築されます。要素は、Salesforce データの読み取りや書き込みなど、フローで実行されるアクションを表します。コネクタは、実行時にフローがたどるパスを定義します。リソースは、フロー全体で参照できる値を表します。

必要なエディション

サポートされているエディションを表示する。
  • 各要素 (1) は、フローで実行できるアクションを表します。たとえば、Salesforce データの読み取りまたは書き込み、フローユーザーへの情報の表示、フローユーザーからのデータの収集、ロジックの実行、データの操作などです。
  • 各コネクタ (2) は、実行時にフローで使用できるパスを定義します。
  • 各リソース (3) は、フロー全体で参照できる値を表します。

Flow Builder でフローを作成する場合、3 つの主要なビルディングブロックを使用して自動化を作成します。

要素

要素は、フローで実行するアクションです。これらはフローの「実行」部分と考えてください。各要素は、フローで実行される特定の ToDo を表します。最も一般的な要素は次のとおりです。

画面
ユーザーに情報を表示し、その入力を収集します。
レコードの作成
Salesforce に新しいレコードを追加します。
レコードを更新
既存の Salesforce レコードを変更する。
レコードを取得
Salesforce からレコードを取得してフローで使用します。

コネクタ

コネクタは、要素をリンクする線です。実行時にフローがたどるパスを定義し、アクションの実行順序を示します。最も一般的なコネクタの種類は次のとおりです。

標準コネクタ
要素を順番に次の要素にリンクします。
決定結果コネクタ
条件を満たしているかどうかに基づいてフローを転送します。例: True と False のパス。
障害コネクタ
要素に障害が発生した後にフローを指示してエラーを処理します。
スケジュール済みパスコネクタ
指定された時間遅延の後、またはスケジュールされた日にアクションをトリガーします。

すべてのコネクタの種類についての詳細は、「フロー要素コネクタ」を参照してください。

リソース

リソースには、フロー全体で使用できる情報が保存されます。これらは、参照する値、計算する値、要素間で渡す値のコンテナとして機能します。一般的なリソース種別は次のとおりです。

変数
フローの実行時に変更される可能性のある 1 つの値を保存します。
Formula
他のデータに基づいて値を計算します。
テキストテンプレート
メールまたはメッセージの書式設定されたテキストを作成します。
定数
変更されない値を保存する。
選択肢
画面の選択リストまたはラジオボタンのオプションを定義します。
レコードコレクション変数
複数の Salesforce レコードを保存します。

すべてのリソース種別についての詳細は、「フローのリソース」を参照してください。

トランザクションでのフローの一括処理

フローが複数のレコードに対して同時に実行される場合、Salesforce はレコードごとに 1 つのフローインタビューを作成します。一括処理では、同じフローのインタビューが同じ要素に到達したときに類似する操作がグループ化されるため、トランザクションで使用するクエリやステートメントが少なくて済みます。

必要なエディション

サポートされているエディションを表示する。

一括処理を使用しない場合、100 のインタビューがそれぞれ独自の Salesforce Object Query Language (SOQL) クエリとデータ操作言語 (DML) ステートメントを実行すると、すぐにガバナ制限を超える可能性があります。Salesforce は、操作を自動的にグループ化することでガバナ制限の失敗を防ぎます。複数のインタビューが同じ要素に到達すると、Salesforce はそれらの操作 (100 ではなく 1 つの SOQL クエリまたは 100 ではなく 1 つの DML ステートメント) を一括処理します。

複数のインタビューが同じ要素に到達すると、Salesforce は自動的に操作をグループ化します。ただし、Salesforce は 1 つのフローのロジック内で操作を自動的に統合しません。たとえば、ループ内の [レコードを作成] 要素では、反復ごとに 1 つの DML 操作が実行されます。

  • フローの一括処理のしくみ

  • 一括処理可能なフロー要素

フローの一括処理のしくみ

Salesforce では、同じフローのインタビューが同じ要素に到達したときに操作を一括処理します。

1 つのトランザクションで同じフローの複数のインタビューが実行される場合、インタビューはそれぞれ一括処理可能な要素に達するまで実行されます。Salesforce は、同じ要素で停止したすべてのインタビューを対象に、これらの操作をインテリジェントにまとめて実行します。他のインタビューが別の要素にあれば、Salesforce はその後、これらの操作をインテリジェントにまとめて実行します。Salesforce は、すべてのインタビューが終了するまでこのプロセスを繰り返します。

一括処理であるにもかかわらず、いずれかのインタビューがガバナ制限に達した場合は、トランザクションのすべてのインタビューが失敗します。インタビューがトランザクション内で実行した操作がすべてロールバックされ、トランザクションの操作が再試行されることはありません。外部データにアクセスする操作はロールバックされません。

次のいずれかの要素の実行中にガバナ制限によるものではないエラーが発生した場合、Salesforce は一括操作で成功したすべてのレコード変更について、保存を 3 回まで試みます。

  • サブフロー ([レコードの作成] 要素と [レコードを更新] 要素のみ)
  • レコードの作成
  • レコードを更新
例 100 件のケースをアップロードする場合、MyFlow_2 というフローがケースごとに 1 つのインタビューをトリガーします。
  • 50 のインタビューがレコードの作成要素 Create_Task_1 で停止します。
  • 残りの 50 のインタビューはレコードの作成要素 Create_Task_2 で停止します。

その結果、少なくとも 2 つの一括操作グループが実行されます。

  • 1 つは Create_Task_1 を実行する 50 のインタビュー用
  • 1 つは 50 のインタビューに対して Create_Task_2 を実行する操作です。

フローの一括処理の例

次の例では、データローダーで 100 件のケースが更新されるときに、フローの操作がどのように一括処理されるかを示します。

関連付けられたフロー

理解しやすくするために、関連付けられたフローの設計を次に示します。このフローでは、親取引先のオープン ケースの数に基づいて各ケースがチェックされ、Chatterに投稿されます。

フロー:

  • ケースの親取引先と、その取引先が有するオープンケースの件数を検索します。
  • 取引先のオープンケースが 6 件以上かどうかを確認します。
  • 取引先のオープンケースが 6 件以上の場合:
    • 取引先のディビジョンマネージャーを検索します。
    • 取引先の Chatter フィードに投稿して、ディビジョンマネージャーと取引先所有者に通知します。
  • 取引先のオープンケースが 5 件以下の場合は、取引先の Chatter フィードに投稿して、取引先所有者のみに通知します。

一括処理されるインタビュー

レコードの更新時に、各ケースのフローインタビューが同時に作成されます。インタビューがすべて同じフローに関連付けられます。インタビューはそれぞれ一括処理可能な要素に達するまで実行されます。

最初のインタビューがレコードを取得要素 (1) を処理します。[レコードを取得] は一括処理が可能なため、インタビューは他のすべてのインタビューが同じ処理を終了するまでこの時点で待機します。その後、Salesforce はすべての [レコードを取得] 操作をまとめて実行します (すべて同じフローの同じ要素に対する操作であるため)。トランザクションで、100 件の SOQL クエリではなく、1 件の SOQL クエリが実行されます。

決定要素 (2) で最初のインタビューが評価されます。取引先にケースが 6 件あるため、インタビューが「6 件以上」のパスに転送されます。インタビューが 2 つ目のレコードを取得要素 (3a) に進みます。この要素も一括処理が可能なため、インタビューがこの時点で待機します。

決定要素 (2) で 2 番目のインタビューが評価されます。この取引先はケースが 1 件のため、インタビューが「5 件以下」のパスに転送されます。インタビューは [Chatter に投稿] コアアクション (4) に進みます。この要素も一括処理が可能なため、インタビューがこの時点で待機します。

すべてのインタビューが処理された後、30 は 2 つ目のレコードを取得要素 (3a) の実行を待機し、残りの 70 は [Chatter に投稿] コアアクション (4) の実行を待機します。

Salesforce は、最初の 30 のインタビューに対してすべての [レコードを取得] (3a) 操作を実行します。トランザクションで、30 件の個々の SOQL クエリではなく、1 件のクエリが実行されます。

次に、トランザクションが [Chatter に投稿] コア アクション (4) に戻ります。このコア アクションでは、70 のインタビューが Chatter に投稿操作を実行する準備が整っています。これらのインタビューの取引先は、ケースが 5 件以下しかありません。Salesforce が、Chatter への投稿操作をまとめて実行します。トランザクションで、各 Chatter 投稿を作成する 100 件の個別の DML ステートメントではなく、100 の投稿をすべて一度に作成する 1 件の DML ステートメントが実行されます。[Chatter に投稿] コアアクションは後続の要素に結び付けられていないため、この 70 のインタビューは終了します。

関連するディビジョンマネージャーを検索した 30 のインタビューは、最後の [Chatter に投稿] コアアクション (3b) に進みます。30 のすべてのインタビューの準備が整ったら、Salesforce が 30 の [Chatter に投稿] 操作をまとめて実行します。Chatter 投稿ごとの 30 件の個々の DML ステートメントではなく、1 件の DML ステートメントが実行されます。[Chatter に投稿] コアアクションは別の要素に結び付けられていないため、この 30 のインタビューは終了します。

アクションを使用した Slack への画面フローの送信

有効な画面フローを Slack に送信するこの方法は、公式の Salesforce Slack アプリケーションのみで使用できます。この方法は、入力変数を使用し、詳細設定で [Slack で使用できるようにする] が選択されている有効な画面フローを実行するための唯一の方法です。

詳細設定で [Slack で使用できるようにする] が選択されている有効な画面フローは、フローのデフォルト環境で実行することができます。Slack 環境で実行するフローを送信するには、[フローを起動するための Slack 送信メッセージ] アクションのバージョンをコールする別のフローを使用します。

[フローを起動するための Slack 送信メッセージ] アクションには、詳細設定の [Slack で使用できるようにする] が選択されている有効な画面フローごとにバージョンがあります。たとえば、Get Pet Name という有効な画面フローがあります。この有効な画面フローを Slack に送信する新しいフローにアクション要素を追加する場合、API 参照名が slackSendMessageToLaunchFlow - Get_Pet_Name で、表示ラベルが Get Pet Name というアクションを選択します。

このアクションを含むフローが実行されると、メッセージが Slack チャンネルまたはダイレクトメッセージグループに送信されます。Slack チャンネルまたはグループメンバーがボタンをクリックすると、関連付けられた画面フローが起動します。

CMS Orchestrator、EvaluationFlow、Journey、Orchestrator、Survey、SurveyEnrich、TransactionSecurityFlow の各フロー種別では [フローを起動するための Slack 送信メッセージ] アクションはサポートされていません。

フローを実行するための API バージョン

一部の実行時動作の改善はバージョン管理された更新として提供されるため、フローごとにこれらの更新を採用するタイミングを制御できます。各自のペースでフローを 1 つずつテストしてアップグレードします。1 つまたはすべてのフローでバージョン管理された更新を採用しないこともできます。

トランザクションでのフローの実行方法

フローは、操作を 1 つの単位としてグループ化するトランザクション内で実行されます。操作が失敗すると、トランザクション全体がロールバックされ、データの整合性が維持されます。これには、Apexトリガー、エスカレーション ルール、トランザクションのすべてのフロー インタビューが含まれます。

各トランザクションで、Salesforce は、共有リソースが枯渇することがないようにガバナ制限を適用します。複数の Salesforce 組織がリソースを共有するため、Salesforce は 1 つの組織がすべてのリソースを独占し、他の組織がリソース不足に陥らないようにします。アパートで 1 つの貯水槽から各世帯に配水するしくみと似ています。隣人が水を使い切ってしまったら、シャワーを浴びられなくなります。(陳腐なたとえですが、お分かりいただけるのではないでしょうか)。トランザクション単位のガバナ制限によって、こうしたリソース不足が阻止されます。

Winter '26 以降、すべてのフロー種別を設定して、アクションを正常に実行するために新しいトランザクションが必要かどうかを判断できます。以前は、画面フローのみでトランザクションを制御していました。レコードトリガーフローの場合、非同期またはスケジュール済みパスのアクションにトランザクションコントロールを適用できますが、すぐに実行するパスには適用できません。

ヒント すべてのフローで、トランザクションを制御する最適な方法はフローに任せることをお勧めします。Summer '25 より前に設定されたアクションの場合、トランザクションコントロールを [フローの決定に任せる (推奨)] に変更します。

トランザクションの終了方法

トランザクションの終了時点は、フローに特定の要素が含まれているかどうか、および元々の開始理由がレコードの変更かどうかによって異なります。

トランザクションの終了時点:

  • 画面要素、ローカルアクション要素、待機要素が実行されたとき
  • アクションの実行が完了した順序 (レコードが作成または更新されたときにフローがトリガーされた場合)
  • トランザクションのすべてのインタビューが終了したとき
ヒント フローのインタビューがトランザクション内のガバナ制限に達する可能性があると思われる場合は、画面要素、ローカルアクション要素、待機要素を追加することを検討します。

必要なエディション

サポートされているエディションを表示する。

Flow Builder

  • クラウドフローデザイナーは、サポートされません。
  • 値を表示するカスタムコンポーネント、たとえば表示テキスト画面コンポーネントには、Apex で定義された変数からのすべての項目を表示できます。たとえば、{!Car} 変数は、Car Apex クラスで定義されたすべての項目値を保存します。表示テキスト画面コンポーネントに、Apex で定義された変数 {!Car} が入力属性としてある場合、画面には、Car Apex クラスからのすべての項目が表示されます。Apex クラスが管理パッケージに含まれているものである場合は、Apex クラス ID のみが表示されます。
  • @AuraEnabled アノテーションが付与された Apex クラスが 200 個を超える組織で、要素またはリソースウィンドウを初めて開くと、ウィンドウの読み込みに時間がかかることがあります。
  • Flow Builder には、管理パッケージ内の非推奨の Apex クラスが表示されます。
  • フローが Apex を呼び出す場合、実行ユーザーのプロファイルまたは権限セットに対応する Apex クラスの割り当てがある必要があります。
  • Apex で定義されたデータ型であるフロー変数のフィールドの場合、フローでは list データ型はサポートされません。

Apex

  • Apex クラスでサポートされているデータ型は、Boolean、Integer、Long、Decimal、Double、Date、DateTime、String です。各データ型で単一値およびリストがサポートされています。複数の Apex クラスを組み合わせて複雑な Web オブジェクトを表すことができます。
  • 項目ごとに @AuraEnabled アノテーションが必要です。
  • 引数が指定されていないコンストラクターが必要です。
  • クラスメソッドはサポートされません。
  • 項目の getter メソッドはサポートされません。
  • 内部クラスはサポートされません。
  • 内部クラスと同じ名前の外部クラスは、サポートされません。
  • Apex クラスの項目では、参照整合性はサポートされません。たとえば、Car Apex クラスのモデル項目を表現する Apex で定義された変数がフローにあります。このクラスのモデル項目が変更または削除されると、フローが失敗します。

入力値および出力値

  • Apex で定義された変数値をフローの外部で設定したり、保存したりすることはできません。この値は、サブフロー要素に渡すことができません。

ローカルアクション

  • ローカルアクションとして使用される Aura コンポーネントが Apex で定義された属性を設定することはできません。

フローの変更セットの考慮事項

変更セットを使用してフローをリリースする前に、コンポーネントの連動関係、リリース、フロートリガーに関連する制限と動作を理解しておく必要があります。

必要なエディション

サポートされているエディションを表示する。

変更セットの作成

  • 変更セットを使用してフローをリリースする場合、変更セットにはフローが参照するコンポーネントが含まれている必要があります。
  • 変更セットの連動コンポーネントを参照するとき、[コンポーネントの連動関係] ページに、フローのすべてのバージョンの連動関係が一覧表示されます。関連するフローバージョンのすべての相互連動関係コンポーネントを送信変更セットに追加します。
  • フロー要素が次のコンポーネントを参照している場合、これらのコンポーネントは [コンポーネントの連動関係] ページに表示されません。フローを正常にリリースするには、参照される次のコンポーネントを変更セットに手動で追加します。
    • Chatter に投稿
    • メールを送信
    • 承認申請
    たとえば、承認申請要素を含むフローをリリースする場合、参照される承認プロセスを手動で追加します。
  • フローで CSP 信頼済みサイトに依存する Lightning コンポーネントを参照している場合、その信頼済みサイトはパッケージまたは変更セットに追加されません。

変更セットのリリース

  • 変更セットには 1 つのバージョンフローのみを含むことができます。
  • 変更セットの有効なフローは、対象に無効としてリリースされます。リリース後にフローを手動で有効化してください。
  • 送信変更セットをアップロードするときに有効なバージョンがない場合、最新の無効なバージョンが使用されます。
  • 変更セットを使用してフローをリリースまたは再リリースすると、対象の Salesforce 組織にフローのバージョンが作成されます。
  • 本番組織では、変更セットまたはメタデータ API を使用して、プロセスまたはフローの新しい有効なバージョンをリリースする設定を有効にできます。スクラッチ組織、Sandbox 組織、開発者組織などの非本番組織では、新しい有効なバージョンを常にデプロイできるため、この設定は表示されません。

フロートリガー

  • フロートリガーは、変更セット内では使用できません。

デフォルト値を含むフロー選択肢コンポーネントの考慮事項

画面フローで選択肢コンポーネントのデフォルト値を設定するときに理解すべき重要な動作と制限事項。

必要なエディション

サポートされているエディションを表示する。

少なくとも 1 つの選択肢を追加すると、選択肢オプションリストの下に [デフォルト値] 項目が表示されます。[デフォルト値] 項目で、選択リスト値または別のフローリソース (変数、レコード変数の項目、手動で入力した値など) を指定します。フローの互換性のある型参照を選択できます。レコードの値をデフォルト値として使用できます。この値は選択リスト選択肢またはレコード選択肢に適用されます。

フローを保存して実行すると、デフォルト値に基づいてオプションが事前選択されます。選択肢オプションは重複せず、選択肢の順序は保持されます。

デフォルトの選択肢オプションのフロー実行時の動作

実行時に、[選択肢値] がコンポーネントのデフォルト値と一致すると、Salesforce は選択肢を事前に選択します。デフォルト値がフローのリソースを参照する場合は、照合の前にその参照が解決されます。フローを保存して実行すると、選択肢に表示されるリストでデフォルト値が事前選択されます。

デフォルト値 実行時に Salesforce が選択肢オプションを事前選択する基準
コンポーネントの選択肢オプションのリストに含まれている選択肢リソース 選択された選択肢の API 参照名との一致。
コンポーネントの選択肢オプションのリストに含まれない選択肢リソース 選択肢リソースの解決された値。特定の選択肢の値が解決済みのデフォルト値と一致する場合、その選択肢が選択されます。
フロー内の別のリソース (レコード取得要素からのレコード変数への参照など) フローリソースの解決された値。特定の選択肢の値が解決済みのデフォルト値と一致する場合、その選択肢が選択されます。
手動で入力された値 手動で入力された値。特定の選択肢の値が手動で入力した値と一致する場合、その選択肢が選択されます。

ユーザーが 1 つのオプションを選択する選択肢コンポーネント (選択リストやラジオボタンなど) では、最初に一致した選択肢が事前選択されます。

ユーザーが複数のオプションを選択する選択肢コンポーネント (複数選択リストやチェックボックスグループなど) では、一致するすべての選択肢を Salesforce が事前に選択します。

メモ コンポーネントの選択肢オプションに選択肢値を指定せず、デフォルト値がいずれかの選択肢の場合、実行時にすべての選択肢が事前選択されます。これは、入力した選択肢のデフォルト値が null であり、その値がコンポーネントのすべての選択肢オプションの null 値と一致するためです。

選択肢コンポーネントの複数のデフォルト値

ユーザーが複数のオプションを選択する選択肢コンポーネントで複数のデフォルト値を指定するには、値をセミコロンで区切ります。解決されたデフォルト値に Red;Blue などのセミコロンが含まれている場合、Salesforce は各値を個別のデフォルトとして扱います。

例 実行時にユーザーが色を選択できるようにする画面フローについて考えてみます。画面フローの画面要素にチェックボックスグループコンポーネントが含まれています。チェックボックスグループコンポーネントでは、ユーザーが複数のオプションを選択でき、3 つの選択肢リソースがあります。
  • 選択肢 1
    • API Name: Choice_Red
    • 選択肢の表示ラベル: Red
    • 選択肢値: 赤
  • 選択肢 2
    • API 参照名: Choice_Blue
    • 選択肢の表示ラベル: Blue
    • 選択肢値: 青
  • 選択肢 3
    • API 参照名: Choice_Green
    • 選択肢の表示ラベル: Green
    • 選択肢値: 緑

[デフォルト値] フィールドは Red;Blue に設定されているため、実行時に Salesforce は Red または Blue の値を持つすべての選択肢を事前に選択します。

セミコロンを含む選択肢値を設定すると、複数選択値の一致動作で問題が発生する可能性があります。選択肢の値が完全一致 (Red;Blue など) の場合、Salesforce は事前選択しません。たとえば、[Red (赤)] 選択肢の選択肢の値を Red;Blue に変更し、チェックボックスグループコンポーネントの [デフォルト値] 項目に「Red;Blue」と入力すると、実行時に [Red (赤)] と [Blue (青)] の両方の色オプションが期待どおりに事前選択されません。

複数のレコードを含む選択肢コンポーネントを設定する場合、値が各レコードのレコード ID に解決される変数を使用し、ID をセミコロンで区切ります。

コレクション選択肢セットのデフォルト値

フローでは、画面が最初に表示されるときにコレクション選択肢セットが入力されません。選択肢コンポーネントのデフォルト値としてコレクション選択肢セットの値を参照する場合、画面の読み込み時のデフォルト値は null です。実行時に画面を再読み込みしてデフォルト値を表示するには、同じ画面で値を参照するか、数式で値をラップします。

コレクションのデフォルト値を保持する変数を使用する場合、その変数が選択肢を使用するコンポーネントと同じ画面で使用されていることを確認します。

値を数式でラップするには、フローで数式リソースを作成します。この数式では、値を操作または組み合わせてデフォルト値を生成できます。たとえば、var1 と var2 の 2 つの変数があり、コレクション選択肢のデフォルト値を両方に設定する場合は、{!var1} & ";" & {!var2} という数式を作成します。この数式は、var1 と var2 をセミコロンで連結します。詳細は、「コンテキスト別の数式の演算子と関数」を参照してください。

例 複数選択リストで組織のすべてのアカウントを表示し、Acmeアカウントと業種がテクノロジーの取引先を事前に選択する画面フローについて考えてみます。

このフローでは、[レコードを取得] 要素を使用してすべてのアカウントを取得し、取得したアカウントを varAllAccounts という変数に保存します。その後、フローはこれらの各取引先をループ処理し、取引先の業種が [テクノロジー] かどうかを確認します。業種が [テクノロジー] の取引先の場合、フローは取引先名を varTechnologyAccounts という別の変数に追加します。

このフローには Test という数式リソースがあり、数式 SUBSTITUTE({!varTechnologyAccounts}, 2, LEN({!varTechnologyAccounts}) - 2),",", ";" ) を使用して、テクノロジー取引先のカンマ区切りリストをセミコロン区切りリストに分割します。

このフローには、テクノロジー取引先のセミコロン区切りリストを Acme に連結する varPreselectDefaults という 2 番目の数式リソースがあります。数式 {!Test} & ";" & "Acme" を次に示します。

このフローでは、次の項目値を持つ AccountChoices というコレクション選択肢セットリソースを使用します。

項目 value
コレクション {!varAllAccounts}
選択肢表示ラベル 取引先名
選択肢の値 取引先名
データ型 Text

フローの最後の要素は画面要素です。この画面要素に追加される複数選択リストコンポーネントには、次の項目値があります。

項目 value
選択肢 {!AccountChoices}
デフォルト値 {!varPreselectDefaults}

実行時に、フローでは Acme アカウントと、業種が [テクノロジー] である他のすべてのアカウントが事前に選択されます。

フローの条件付き表示に関する考慮事項

画面コンポーネントの表示を設定する前に、フローの条件付き表示の動作を理解してください。

必要なエディション

サポートされているエディションを表示する。

null および空の文字列

null 値は、{!$GlobalConstant.EmptyString} と同じように評価されます。

サポートされないデータ型および演算子

  • 条件付き表示では、これらの演算子はサポートされません。
    • アクセス済み
    • 設定済み
  • 条件付き表示では、これらのデータ型はサポートされませんが、属性と項目を参照することは可能です。
    • Apex で定義されたデータ型
    • レコード変数
  • 条件付き表示では、この結果を参照できません。
    • Apex で定義された呼び出し可能なアクションの結果
    • サブフロー要素を使用して現在のフローが参照するフローの結果
  • [Manually assign variables (advanced) (変数の手動割り当て (上級))] が選択されている画面入力コンポーネントは、同じフロー画面の条件付き表示のリソースとして使用できません。
  • 差し込み項目が含まれているテキストは、値ではサポートされません。差し込み項目は、単独でサポートされます。
  • Is Null 演算子は、チェックボックスや切り替えなどの Boolean 画面コンポーネントで API バージョン 64.0 以降で実行されるフローでのみサポートされます。

テキストテンプレートおよび数式

  • テキストテンプレートおよび数式では、初期値が評価されます。
  • ユーザー入力に基づく変更は評価されません。

非表示の画面入力コンポーネント

  • ユーザーがフローを実行する場合、Required が {!$GlobalConstant.True} に設定されていても、条件付き表示で非表示にされている画面入力コンポーネントは不要です。コンポーネントがユーザーに表示される場合、必須として扱われます。
  • 画面入力コンポーネントが条件付き表示の要件を満たさないために非表示である場合、その値は null に設定されます。ただし、連動選択リストコンポーネント全体が非表示になっていない限り、連動選択リストコンポーネントの非表示の選択リストは null に設定されません。
  • [レコードを更新] 要素で、非表示の画面コンポーネントの値を使用して項目を更新すると、項目値は空白に設定されます。代わりに、項目値を設定する前に項目が空白かどうかを確認する数式リソースを使用して項目を更新します。たとえば、次の数式を使用します。 
    IF( ISBLANK( {!myTextField} ), {!myOriginalFieldValue}, {!myTextField})
  • コンポーネントの表示を設定する条件を定義するときに、リソース値として変数を指定できます。この変数は、Contact.Account.Owner など、最大 3 つのオブジェクト項目をトラバースできます。
  • 非表示のコンポーネントが画面の再アクセス後に表示可能になった場合や、入力規則エラーがある場合、コンポーネントのデフォルトテキストは表示されません。

セクションおよび条件付き項目の表示

セクションの表示条件でセクション内に含まれるコンポーネントが参照されている場合、セクション全体が非表示になります。セクションの表示条件でコンポーネントの表示条件が参照され、表示条件が true と評価された場合、セクションが表示されます。

焦点

画面が最初に表示された後に画面のコンポーネントやその一部が表示された場合は、それらにフォーカスを設定することはできません。たとえば、コンポーネントが非同期で ToDo リストを取得して表示した場合は、フォーカスをどの ToDo にも設定できません。画面コンポーネントで条件付き表示が使用されていて、ユーザー入力の後でなければ表示されない場合、その画面コンポーネントのどの部分にもフォーカスを設定することはできません。

循環ロジック

循環ロジックを条件内で使用しないでください。フローの実行時にパフォーマンスが低下し、動作が異常になり、エラーが発生する可能性があります。

関連レコード項目

項目の表示条件の関連レコード項目は、画面表示時に値が設定される参照項目のみで機能します。

条件値のカンマ

条件値にカンマが含まれている場合は、値の先頭と末尾に引用符を追加します。例: 「Email, Phone, and Social Media」。

Performance

最高のパフォーマンスを得るには、画面コンポーネントとレコード項目の条件付き表示条件の数と複雑さを最小限に抑えます。画面フローユーザーが参照または更新できる画面コンポーネントとレコード項目を制御する方法は他にもあります。

  • セクションコンポーネントを使用します。同じロジックを使用して複数の画面コンポーネントまたはレコード項目を表示する必要がある場合は、[セクション] コンポーネントに配置します。次に、各コンポーネントまたは項目ではなく、セクションコンポーネントで条件付き表示を設定します。
  • 条件付き表示ではなく、コンポーネントの [無効] 属性を使用します。画面フローユーザーが画面コンポーネントの入力項目を入力したくないが、項目が表示されても問題ない場合は、コンポーネント入力項目を無効にできます。Boolean 値を持つリソースを選択して、画面コンポーネントの [無効] 属性を設定します。たとえば、別の画面コンポーネントが空の場合に true と評価される数式リソースに [無効] 属性を設定します。
  • 反応型の数式または画面アクションを使用します。別の画面コンポーネントの値に応じて、画面コンポーネントのデフォルト値を条件付きで動的に非表示にして設定する場合、値ごとに画面コンポーネントを追加しません。代わりに、条件に応じて表示される 1 つの画面コンポーネントと反応型の数式または画面アクションを使用してデフォルト値を入力します。「反応型画面フローの数式演算子」を参照してください。
