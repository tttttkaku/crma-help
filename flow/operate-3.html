画面フローの配布方法の決定

画面フローにアクセスするユーザーと操作方法に基づいて、画面フローを配置する場所を選択します。

必要なエディション

サポートされているエディションを表示する。

画面フローを作成して有効化したら、ユーザーと共有する方法を決定します。判断に役立つ次の質問を考慮してください。

  • ユーザーは組織の内部ユーザーですか、それとも組織外の外部ユーザーですか?
  • ユーザーがフローのどこにアクセスできるようにするか?

画面フローを配布する方法はいくつかあります。画面フローは Salesforce 組織で実行されるため、ほとんどが内部ユーザー向けです。Experience Cloud サイトにフローを埋め込むことで、フローを外部ユーザーと共有できます。ユーザーがログインしてフローを使用しない場合は、Experience Cloud ライセンスを購入する必要はありません。ユーザーがログインしてフローを使用するには、Experience Cloud ライセンスを購入します。

フローを実行するためのユーザーアクセスの制限

ユーザーレコード、プロファイル、または権限セットに基づいて、フローを実行できるユーザーを制限します。より詳細なセキュリティを個々のフローに適用するには、デフォルトの動作を上書きし、ユーザープロファイルまたは権限セットに基づいて特定のフローへのアクセスを許可します。

  • ユーザーへの「フローを実行」権限の付与
    「フローを実行」権限を割り当てて、UIからの画面フローやユーザー コンテキストで実行される自動起動フロー(Apex、Lightningページ、APIから起動されるフローなど)など、フローを直接実行できるユーザーを制御します。システムトリガーフロー (レコードトリガーフロー、プラットフォームイベントトリガーフロー、スケジュールトリガーフロー) は自動的に実行され、開始ユーザーに「フローを実行」権限は必要ありません。フロー種別に関係なく、フローを正常に完了するには、実行コンテキストに適切なオブジェクト、項目、およびレコード権限が必要です。
  • ユーザープロファイルまたは権限セットによるフローへのアクセス権の設定
    作成またはコピーする各フローに対して、デフォルトの動作を上書きし、フローへのアクセスを、有効なプロファイルまたは権限セットを持つ本ユーザのみに限定できます。
  • フローインタビューの共有ルールを使用した、フローへのゲストユーザープロファイルアクセスの設定
    デフォルトでは、フローインタビューを開始したユーザーのみがフローインタビューを再開できます。フローを起動したユーザー以外のユーザーがフローインタビューにアクセスできるようにするには、インタビューの共有ルールを使用してください。ゲストユーザープロファイルの特定のフローへのアクセス権は、プロファイルページでのみ制御できます。

ユーザーへの「フローを実行」権限の付与

「フローを実行」権限を割り当てて、UIからの画面フローやユーザー コンテキストで実行される自動起動フロー(Apex、Lightningページ、APIから起動されるフローなど)など、フローを直接実行できるユーザーを制御します。システムトリガーフロー (レコードトリガーフロー、プラットフォームイベントトリガーフロー、スケジュールトリガーフロー) は自動的に実行され、開始ユーザーに「フローを実行」権限は必要ありません。フロー種別に関係なく、フローを正常に完了するには、実行コンテキストに適切なオブジェクト、項目、およびレコード権限が必要です。

ユーザーには次の「フローを実行」権限が必要です。

  • 画面フローの実行
  • ユーザーコンテキストで実行される自動起動フローを実行する
  • フローインタビューの一時停止または再開
  • オーケストレーションと承認の作業項目を完了
メモ [設定] の「フローを実行」権限はアプリケーション権限であり、システム権限ではありません。

    2. 更新するプロファイルを選択します。

    2. 更新する権限セットを選択します。
    3. [アプリケーション権限] をクリックします。
    4. [フローおよびフローオーケストレーション] で、[フローを実行] を選択します。
    5. [保存] をクリックします。

自動システムへのフローの配布

一部のフローは、ユーザー操作なしで開始できます。システムでフローを自動的に起動できるようにするには、start Apex メソッドを使用できます。

これらのメソッドのほとんどは、自動起動フローでのみ使用できます。フローは、Apex interview.startメソッドなどからユーザー操作なしで起動できます。自動起動フローは、ユーザー操作なしで一括で実行されます。有効なフローバージョンまたは最新のフローバージョンに、ステップ、画面、選択肢、動的選択肢を含めることはできません。フローユーザーが自動起動フローを呼び出すと、有効なフローバージョンが実行されます。有効なバージョンがない場合は、最新バージョンが実行されます。フロー管理者がフローを呼び出すと、常に最新のバージョンが実行されます。

  • REST API からのフローの開始
    REST コールを使用して、呼び出し可能なアクションエンドポイントを使用し、フローへのパスを設定して自動起動フローを実行します。たとえば、Salesforce 以外のアプリケーションやコードからフローを実行できます。フローでは、Salesforce からデータを取得し、REST コールの出力変数として返します。
  • Apex からのフローの開始
    Apexから開始するフローには、複雑なビジネス・ロジックや高度なエラー処理を含めることができ、より効果的に外部システムと統合できます。このアプローチでは、必要に応じてコールできるフロー内にロジックをカプセル化することで、再利用を促進します。また、実行コンテキストと操作の順序をより詳細に制御できます。Apexとフローを組み合わせることで、より強力で柔軟性の高いアプリケーションをより容易に作成して管理できるようになります。

Apex からのフローの開始

Apexから開始するフローには、複雑なビジネス・ロジックや高度なエラー処理を含めることができ、より効果的に外部システムと統合できます。このアプローチでは、必要に応じてコールできるフロー内にロジックをカプセル化することで、再利用を促進します。また、実行コンテキストと操作の順序をより詳細に制御できます。Apexとフローを組み合わせることで、より強力で柔軟性の高いアプリケーションをより容易に作成して管理できるようになります。

メモ Apex からフロー管理者としてフローを開始すると、有効化状況に関係なく、最新バージョンのフローが使用されます。

Invocable.Action クラスまたは Flow.Interview クラスを使用して、Apex からフローを開始できます。2 つのクラスの違いを考慮してください。

  • Invocable.Action クラスを使用してフローを実行する場合、フローは一括処理で一括実行されますが、動的に参照できるのはフローのみです。参照整合性を提供しないフロー名の文字列値を指定します。この方法は、任意のフローを実行する場合に適していますが、特定のフローをコールする場合は適しません。
  • 参照整合性を取得するには、Flow.Interview クラスを使用してフローを静的に参照します。対象組織、リリース、またはパッケージにフローが存在しない場合、Apex をパッケージ化またはリリースできません。ただし、一括処理を使用して Flow.Interview クラスを一括で実行することはできません。

フローの実行時に、Salesforce Object Query Language (SOQL) と Data Manipulation Language (DML) の制限が適用されます。Salesforce ヘルプの「トランザクション単位のフローの制限」を参照してください。

例の次のサンプルフローについて考えてみます。

  • フロー API 参照名: MyFunFlow
  • フローには、入力に使用できる 2 つのテキスト変数があります。
    • inputA
    • inputB
  • フローには、出力に使用できる 1 つのテキスト変数があります。
    • outputVariable
  • フローには、inputA と inputB の値を連結して結果を outputVariable に割り当てる割り当て要素があります。

Invocable.Action クラスを使用した Apex からの 1 つの自動起動フローの実行

Invocable.Action を使用してフローを実行するには、createCustomAction() メソッドを使用してInvocable.Actionクラスのインスタンスを作成します。実行するフローの 1 つ以上のインスタンスの入力変数値を設定し、invoke() メソッドを実行します。invoke() メソッドは、エラーを読み取ることができるオブジェクト、またはフローが提供する出力を返します。

この方法では、異なる入力セットに対して同じフローの複数のインスタンスを実行できます。

/* Set the input variable values into a Map<String,Object> with each input as a key, and the input value you want to set as the value */
Map<String,Object> flowInputVariables = new Map<String,Object>();
flowInputVariables.put('inputA','hello');
flowInputVariables.put('inputB','world');

/* Put the input map(s) into a List. Each item in this list represents a flow interview that's invoked together in a single batch run that uses flow bulkification. You must use a list, even if you want to run just one instance of the flow. */
List<Map<String,Object>> flowInputs = new List<Map<String,Object>>{ flowInputVariables };

/* Initialize the flow as an action with the Action Type 'flow' and the API name of the flow */
Invocable.Action flowAction = Invocable.Action.createCustomAction('flow','MyFunFlow');

/* Use the input parameters to prepare the invocations that will be invoked */
flowAction.setInvocations(flowInputVariables);

/* Invoke the flow, assigning the results to a list of Invocable.Action.Result */
List<Invocable.Action.Result> flowResults = flowAction.invoke();

/* Read the results and outputs of the invocation */
for (Invocable.Action.Result result : flowResults) {
	if (result.isSuccess() == false) {

REST API からのフローの開始

REST コールを使用して、呼び出し可能なアクションエンドポイントを使用し、フローへのパスを設定して自動起動フローを実行します。たとえば、Salesforce 以外のアプリケーションやコードからフローを実行できます。フローでは、Salesforce からデータを取得し、REST コールの出力変数として返します。

REST API から開始するフローには、より効果的に外部システムと統合できるように、複雑なビジネスロジックや強化されたエラー処理を含めることができます。このアプローチでは、必要に応じてコールできるフロー内にロジックをカプセル化することで、再利用を促進します。また、実行コンテキストと操作の順序をより詳細に制御できます。REST API とフローの組み合わせにより、より強力で柔軟なアプリケーションを作成でき、管理が容易になります。

フローの実行時に、Salesforce Object Query Language (SOQL) と Data Manipulation Language (DML) の制限が適用されます。Salesforce ヘルプの「トランザクション単位のフローの制限」を参照してください。

注: REST API コールで開始できるのは自動起動フローのみです。REST API コールでフローの有効なバージョンが実行されます。

フローメタデータの取得

フローを実行する前に、REST コールを使用してフローの説明を取得し、フローで使用可能な入力を確認します。このアプローチは、フローで想定される入力変数とそのデータ型を理解するのに役立ちます。

フローの説明とフローの入力を取得するには、GET 要求を使用します。

GET /services/data/v65.0/actions/custom/flow/FLOW_API_NAME

FLOW_API_NAME をフローの API 参照名に置き換えます。応答には、フローの入力変数と出力変数に関するメタデータが含まれます。

エラーハンドリング

REST API を使用してフローを実行する場合、潜在的なエラーを処理します。

  • 認証エラー: アクセストークンが有効であり、フローを実行するために必要な権限があることを確認します。

Flow Builder への切り替えを計画するときには、いくつかの作業に集中する必要があります。

オートメーションを分析する

移行ジャーニーを開始するには、既存のオートメーションを分析します。

  • 最も使用頻度が高い自動化タイプを分類します。
  • 総エラー数や開始した自動化の総数など、組織のフロー活動をレポートとダッシュボードで確認します。
  • フローインタビューログとフローインタビューログエントリを参照します。
  • [サンプルフローレポート: 画面フロー] レポートを実行します。レポートを使用して画面フローに関する実行時の詳細を調べます。
  • 総計値を使用して使用パターンを発見することで、ユーザー向けの画面フローを最適化できます。

最初に Sandbox で移行する

変更を行う前に既存のデータの安全を確保することが重要です。Sandbox で作業すれば、Flow Builder に移行したときにデータを損なうことはありません。

現在のオートメーションのカタログを作成する

カタログの作成には、さまざまな方法があります。スプレッドシートを作成できます。オブジェクト別にオートメーションを整理します。カタログを作成するときに、カテゴリ、開始条件、関連アクションを含めます。視覚化に役立つダイアグラムを作成できます。

重複するプロセスを特定して削除する

プロセスが引き続き必要かどうか、または改善できるかどうかを評価します。重複には一般的に次の原因があります。

重複 例
1 つのオブジェクトに複数のエントリポイント 1 つの取引先更新に複数のプロセスとワークフロールールがあり、重複するビジネスケースが実行される。
再帰的な更新
  • プロセスビルダー 1 の更新によってプロセスビルダー 2 がトリガーされる。
  • プロセスビルダー 2 によってプロセスビルダー 3 がトリガーされる。
  • プロセスビルダー 3 によってプロセスビルダー 1 が再トリガーされる。
競合するアクション ワークフロールールによって項目値が上書きされている間に、高速項目更新フローによって同じ項目が更新される。

最初に移行するプロセスに優先順位を付ける

レコードの更新を高速化し、移行にかかる時間と労力を軽減するプロセスを移行します。単一オブジェクトから始めます。関連付けられているワークフロールールとプロセスの数が最も少ないオブジェクトを選択します。最初に移行するオブジェクトとして適しているのは、メールアラートを送信するプロセスや、同じレコードの項目自動更新を実行するプロセスです。

オートメーションを構造化する

ビジネスニーズについて考えるときには、一般的に次のような考慮事項があります。

  • パフォーマンス: エントリ条件や他の最適化を使用して不要な操作を削減できますか?
  • メンテナンスと変更管理: このビジネスプロセスの責任者は誰ですか?変更または反復の可能性は?
  • ワークフロールールおよびプロセスからフローへの移行は 1 対 1 ではありません。移行するプロセスごとにフローを作成する必要がない場合があります。
  • 既存のフローを分析して、更新できる対応する要素があるかどうかを確認したり、既存のフローに新しいアクションを組み込んだりします。
  • より複雑な自動化プロセスを再利用してサブフローとして実装できるかどうかを検討します。
  • 自動化を必要としない、より適切なソリューションがあるかどうかを確認します。

    例: ワークフロールールまたはプロセスによって、ケースオブジェクトの項目が作成された後にのみ更新される。代わりに数式項目に置き換えます。

1 つのオブジェクトに 1 つのフローという観念にとらわれない

1 つのオブジェクトに複数のフローがあるようにオートメーションを設計できます。将来の拡張性を高めるために、トリガー順序オプションを使用してフローを並び替えます。フロートリガーエクスプローラーを使用して、優先度値をフローに割り当てます。このツールを使用すると、オブジェクトごとに複数のフローを管理できます。

効率的なレコードトリガーフローを作成すると、フローの制限を最小限に抑えることができます。フローを作成するときに、効率を高めるために次のオプションを選択できます。

エントリ条件を最適化する

パフォーマンスへの影響を軽減するようにエントリ条件を設定します。効果的にエントリ条件を使用すると、オートメーションが不要に実行されるのを防ぎ、パフォーマンスを向上させます。フローを実行するエントリ条件を、レコードが作成または編集された場合と、項目に特定の値がある場合に設定します。またはエントリ条件を、レコードが作成または編集された場合と、項目が特定の値に「変更済み」の場合に設定します。レコードが作成または編集されたときに項目値を確認するだけの場合、エントリ条件の作成以外に追加するステップはありません。レコードが作成または編集された場合に項目値が何に変更されたかを確認するエントリ条件を作成するには、[Run When Conditions Met (条件に一致した場合に実行)] 設定を有効にします。この設定を有効にすると、操作の繰り返しを防ぎ、一貫性が維持されます。

時間ベースのワークフロールールをスケジュール済みパスに置き換える

スケジュール済みパスをレコードトリガーフローに追加します。スケジュール済みパスは、トリガーが起動された後で、日付と時間に基づいて将来に発生します。オートメーションをトリガーしたレコードの日付 (完了予定日など) に基づいて、アラームやフォローアップなどのアクションをスケジュールできます。この機能ではエントリ条件も再確認されます。

例: 入力条件を [状況] = [エスカレーション済み] に設定し、完了の 2 日前にリマインダーを送信する自動化を使用します。アラームは、状況が [エスカレーション済み] のままである場合にのみ送信されます。

オートメーションを並び替える

フロートリガーエクスプローラーを使用して、オートメーションの実行順序を表示したり、フローを並び替えたりできます。フローは、他の自動化、管理パッケージ、または組織間の移動による中断を最小限に抑えるために、説明されている順序で実行されます。フロートリガーの並び替えを使用して、フローに優先度値を割り当てることができます。レコードが作成、更新、または削除されたときに実行される、関連付けられたフローがすべて表示されます。このアクションで、同じ環境下で実行されるフロー間を簡単に移動できます。

説明を使用してフローを文書化します。

要素、リソース、スケジュール済みパス、フローバージョンで [説明] 項目を使用して、フローの背後にあるインテントを文書化します。説明によって混乱が減り、今後の更新が容易になります。

説明が欠落しているリソースを検索および更新するには、[ツールボックス] パネルを開き、[検索条件] を開いて、[欠落している説明] を選択します。結果には説明のない要素とリソースが表示されるため、フローをすばやく文書化できます。

Sandbox でテストする

組織のデータを保護するために、変更を本番に移行する前に必ず Sandbox でテストしてください。

再構築時に古いオートメーションを無効化する

デフォルトでは、有効なプロセスとフローは無効としてリリースされます。リリース後、手動で新しいバージョンを再有効化し、古いバージョンを無効化します。

このセクション

  • トランザクションでのフローの実行方法
    フローは、操作を 1 つの単位としてグループ化するトランザクション内で実行されます。操作が失敗すると、トランザクション全体がロールバックされ、データの整合性が維持されます。これには、Apexトリガー、エスカレーション ルール、トランザクションのすべてのフロー インタビューが含まれます。
  • トランザクションでのフローの一括処理
    フローが複数のレコードに対して同時に実行される場合、Salesforce はレコードごとに 1 つのフローインタビューを作成します。一括処理では、同じフローのインタビューが同じ要素に到達したときに類似する操作がグループ化されるため、トランザクションで使用するクエリやステートメントが少なくて済みます。
  • フローインタビュー
    フローインタビューは、フローの実行中のインスタンスです。フローは、システム管理者が作成するアプリケーションです。ユーザーに入力を求め、その入力に基づいて Salesforce で処理を行います。
  • フロー、一時停止中のインタビュー、およびスケジュール済みアクションの表示の制御
    プロセスからのフロー、一時停止中のフローインタビュー、およびスケジュール済みアクションを表示するには、2 つのオプションがあります。デフォルトで選択される拡張オプションを使用することをお勧めします。ただし、もう一方のオプションに切り替えて、たとえば、拡張オプションで再作成していないカスタムリストビューを使用することもできます。
  • フローの要素エラー率
    いくつかの種類のフローでバックグラウンドで ToDo が自動化されます。そのため、エラーが発生しても、ビジネスプロセスに問題があることに気付くまでしばらくかかることがあります。[要素エラー率] 項目を使用して、注意が必要なフローを一目で確認できます。この項目には、正常なフローの場合は緑の成功アイコン、正常なフローの場合は黄色の警告アイコンが表示されます。Salesforce でエラー率を計算する方法と、計算で使用する総計値について説明します。
  • 組み込み要素分析と詳細なインサイトの表示
    有効なフローと以前に実行されたオートメーションイベントトリガーフロー、有効化トリガーフロー、セグメントフローの場合、要素実行データがフローキャンバスに表示されます。要素の [分析] タブでより詳細なパフォーマンス評価指標にアクセスできます。これには、メール、SMS、WhatsApp、RCS のメッセージングフロー要素のエンゲージメント評価指標が含まれます。
  • 個人のフロー実行の表示
    完了したフローの実行を通じて個人の実際の実行パスを追跡し、問題のトラブルシューティング、パーソナライズの結果の理解、特定のカスタマーエクスペリエンスの調査を行います。
  • フローバージョン分析の表示
    実行状況、個人の進行状況、詳細な実行データがサマリーダッシュボードに表示される包括的な分析を使用して、フローバージョンの全体的なパフォーマンスを監視します。
  • 画面フローレポート
    作成した画面フローを実行しているユーザーを確認します。[レポート] タブから、[サンプルフローレポート: 画面フロー] を使用して、フローインタビューの実行数と画面所要時間を検出し、フローインタビューの状況を確認します。
  • Data 360 へのフローデータの永続的な記録
    フローの実行総計値を Data 360 に永続的に記録し、信頼性と拡張性のあるデータ管理を実現します。レコードトリガーフロー、プラットフォームイベントトリガーフロー、スケジュールトリガーフロー、自動起動フローの永続的なログ記録を設定します。
  • 自動化アプリケーションでフローの連動関係を表示します。
    フローバージョンでは、サブフロー要素から他のフローをコールでき、アクション要素からフローとフロー承認プロセスをコールできます。フロー承認プロセスバージョンとオーケストレーションバージョンでは、フローを使用してステップを実行し、複雑な条件を評価します。フローと、フローがコールするオートメーションおよびフローがコールするオートメーション間のリレーションを理解するには、オートメーションアプリケーションの [フローバージョン] ページまたは [フロー] ページの [利用状況] タブを表示します。
  • フローバージョンの比較による変更の追跡
    Flow Builder またはオートメーションアプリケーションから直接、同じフローの 2 つのフローバージョンの違いをすばやく特定できます。複雑なフローを変更するときに問題を把握し、より効率的に変更を確認し、変更を明確に把握できます。自動起動フロー、画面フロー、スケジュールトリガーフロー、プラットフォームイベントトリガーフロー、レコードトリガーフローのバージョンを比較できます。同じフローバージョン内の保存を確認するには、代わりに [フローの編集履歴] を使用します。
  • フローバージョンの編集履歴の表示と復元
    現在のフローバージョンの保存履歴を確認し、フローを以前の保存に復元します。フローを保存するたびに、保存インスタンスがバージョン編集履歴に追加されます。保存インスタンスには、日付、フローを保存したユーザー、追加、編集、削除された要素の概要が表示されます。
  • キャンバス上の要素実行データの表示
    有効なフローと以前に実行されたフローの集計された要素実行データをキャンバスで直接表示できます。日付範囲検索条件を適用して、指定した期間の指標を表示します。要素の [分析] タブと要素レコードの [分析] タブで、より詳細なパフォーマンス総計値にアクセスできます。組み込み Analytics は、画面フローまたはオーケストレーションでは使用できません。

  • 実行状況の追跡: 完了、処理中、停止、エラー、一時停止中のフロー実行の分布を把握する
  • 実行パターンの分析: すべての個人および実行で要素ごとの詳細な実行データを確認する
  • パフォーマンスの問題の特定: 複数のユーザーに影響するエラー率、処理の遅延、ボトルネックのトレンドを特定する
  • 関係者とのインサイトの共有: 技術系以外のチームメンバーに包括的なフローパフォーマンスデータを提供する

バージョン分析では、すべてのフロー活動の全体像を把握し、概要評価指標と詳細な実行データを組み合わせて、包括的なフローの監視と最適化を行います。

  4. 詳細な Analytics ダッシュボードで完全なフロー分析を確認します。このダッシュボードには、サマリー総計値と、個人の詳細、要素情報、実行状況、タイムスタンプ、パスの割り当て、エラーの説明の列を含む、各個人の実行のすべての要素を示す包括的なデータテーブルが含まれます。

フロー実行時エラーのトラブルシューティング

有効化後に発生するフローのエラーや予期しない動作をトラブルシューティングして解決する方法について説明します。エラーメールを解釈し、ベストプラクティスを使用して問題をすばやく特定して解決します。

フローエラーメールについて

フローの実行が失敗した場合、関連付けられたフローを最後に変更したシステム管理者、または Apex 例外メールの受信者にメールが送信されます。このメールには、エラーメッセージ、フローで実行された各フロー要素の詳細、失敗したフローを Flow Builder で表示するためのリンクが含まれます。

メモ フローの実行が複数の要素で失敗した場合、またはフローインタビューのバッチで失敗が発生した場合、受信者は各失敗についてのエラーメッセージが記載された 1 つまたは複数のメールを受信します。
  • エラーメッセージ: 問題の原因を説明します。「未対応の例外」、「要素に失敗しました」、または特定の検証エラーなどのキーワードを探します。
  • フロー名とバージョン: 失敗したフローとバージョンを示します。
  • 要素の詳細: フローのどの要素がエラーの原因かを示します。通常、要素の API 参照名または表示ラベルが含まれます。
  • Stack Trace: 高度なトラブルシューティングでは、スタックトレースを使用してエラーの原因を特定できます。特に、複雑なフローや Apex アクションに役立ちます。
例

エラー: Send_Email_to_Contact 要素でエラーが発生しました。必須入力パラメーター: RecipientId がありません。

意味: [受信者 ID] 項目に値がないため、フローは Send_Email_to_Contact 要素で設定されたメールを送信できませんでした。

フローエラーのトラブルシューティングのヒント

  • まず、エラーメールを注意深く読みます。問題要素とエラーメッセージを特定します。
  • Flow Builder でフローを開き、メールに記載されている要素を見つけます。
  • Flow Builder のデバッグ機能を使用して、サンプルデータでフローを実行し、リアルタイムで失敗を監視します。フローエラーのメールで、[Flow Error: Click here to debug the error in Flow Builder (フローエラー: Flow Builder でエラーをデバッグするにはこちらをクリックしてください)] をクリックします。デバッガについての詳細は、「Flow Builder デバッガを使用したフローのテストまたはトラブルシューティング」を参照してください。
  • 特に必須項目や変数の入力値に欠落や誤りがないか確認します。
  • 障害コネクタとエラー処理パスが正しく設定されていることを確認します。
  • 異なるユーザーとしてフローをテストし、権限またはアクセスの問題を確認します。
  • レコードトリガーフローの場合、トリガーレコードがすべてのエントリ条件を満たしていることを確認します。

トラブルシューティングを容易にするベストプラクティス

  • エラーメールを解釈しやすくするために、フロー要素とリソースに説明ラベルと API 参照名を追加します。たとえば、[レコードを取得 1] は、[関連取引先責任者を取得] ほどエラーメールでは役立ちません。
  • 重要な要素で障害コネクタを使用して、わかりやすいエラーメッセージと代替パスを提供します。フローの実行でエラーが発生して障害パスが発生すると、フローは障害パスの要素を実行してエラーを処理します。場合によっては、エラーメールも送信される可能性があります。
  • 通知を送信して追跡と解決を容易にします。
  • 一般的なエラーとチームの解決策を文書化します。
  • エラーを修正したら、Flow Builder デバッガーを使用してフローを再テストします。
  • 詳細: エラーの詳細を表示するには、カスタムオブジェクトにエラーを記録します。
メモ Salesforce レコードとして保存されているインタビューに関する詳細情報を保存するには、インタビューの GUID を参照するカスタムオブジェクトを構築します。Salesforce レコードとして保存されている一時停止中のインタビューにのみ 18 文字の Salesforce ID が割り当てられます。処理中でも一時停止中でも、各インタビューには GUID が割り当てられます。
  • フローでの REQUIRED_FIELD_MISSING エラーのトラブルシューティング
    フローですべての必須項目が入力されていない状態でレコードを作成または更新しようとすると、REQUIRED_FIELD_MISSING エラーが表示されます。
  • フローでの APEX_CPU_TIME_LIMIT_EXCEEDED エラーのトラブルシューティング
    トランザクションで CPU 時間が過度に消費されると、Salesforce は Apex＿CPU＿TIME＿LIMIT＿EXCEEDED エラーをスローします。フローでは、この制限を同じトランザクションの他のすべての自動化 (Apex トリガーを含む) と共有します。
  • フロー URL のトラブルシューティング
    フローを配布しており、カスタムボタン、カスタムリンク、または直接フロー URL が期待どおりに機能していない場合は、参照されるフローを確認します。さらに、値を URL からフローに渡している場合は、その変数も確認します。
  • フローの再試行のトラブルシューティング
    フローが正常に終了しなかった場合にフローがどのように再度実行されるかについて説明します。フローの再試行とは、保存に失敗したレコードを処理するためにフローが再度実行されることです。

[フローに移行] ツールの考慮事項とサポートされるプロセスビルダープロセスについて説明します。

考慮事項

再帰を含むプロセスは完全にはサポートされていません。再帰を含むプロセスが移行されると、レコードは 1 回だけ評価されます。移行後に再帰を含むプロセスをテストして、意図したとおりに動作することを確認します。

プロセスは、[アクションと関連レコード] で最適化された (保存後) フローとして移行されます。必要に応じて、フローが移行された後に [高速項目更新] (保存前) のフローを編集して最適化できます。

フローの呼び出しアクションは、呼び出し可能なフローアクションではなくサブフロー要素として移行されます。サブフローは、親フローと同じトランザクションで実行されます。プロセスで、外部コールアウト、外部アクション、一時停止などを伴うフローの呼び出しアクションが使用されている場合は、非同期パスを使用して再設計する必要があります。

スケジュール済みアクションに関連付けられている条件を 1 つだけ選択した場合にのみ、プロセスビルダーのスケジュール済みアクションを移行できます。複数の条件が選択されている場合は、スケジュール済みアクションは移行されません。移行されたスケジュール済みアクションは、Flow Builder のスケジュール済みパスになります。フローでは、移行後のスケジュール済みアクションは命名規則 ScheduledPath__# に従います。実行時に、新しいフローは、移行元のプロセスに待機中のアクションがあるかどうかを確認し、あれば削除します。レコードが更新されると、待機中のスケジュール済みアクションは適切なスケジュール済みパスに移動するか、レコードが条件を満たさなくなった場合はキャンセルされます。スケジュール済みアクションの実行時にレコードが更新されない場合、プロセスのスケジュール済みアクションが実行されます。「プロセスの待機中のスケジュール済みアクションの監視」を参照してください。

数式のクロスオブジェクト参照は移行できません。

数式でカスタムメタデータ参照を使用するプロセスは移行できます。 移行後、カスタムメタデータ参照はフロー数式で使用されますが、リソースピッカーを使用して設定することはできません。

時間ベースのプロセスを移行する場合、各結果を独自のスケジュール済みアクションフローに移行します。次に、新しいフローを有効化し、プロセスを無効化します。

プロセスを元のプロセスビルダーと同じ組織内のフローに移行します。中間組織に移行してから対象組織にリリースしないでください。プロセスを同じ組織のフローに移行すると、フローでプロセス先行のキューにあるスケジュール済みアクションを処理できます。フローを新しい組織にリリースすると、新しいフローとして扱われ、スケジュール済みパスは新しいスケジュール済みアクションに移行されません。

サポートされるプロセス

[フローに移行] ツールでは、レコードトリガープロセスのみがサポートされています。カスタムイベント種別およびカスタム呼び出し可能種別のプロセスはサポートされていません。またこのツールでは、カスタムメタデータ型を含むプロセスや関連オブジェクトからの項目 (項目のトラバース) を含む条件もサポートされていません。サポートされているプロセスでは、追加の設定なしで次のアクション種別を移行できます。

  • レコードの更新
  • レコード作成
  • フローの呼び出し
  • Apex の呼び出し
  • メールアラート

移行後、これらのアクション種別はフロー内の元の位置を保持しますが、期待どおりに機能するには追加の設定が必要です。

  • Chatter に投稿
  • クイックアクション
  • 承認申請
  • カスタム通知を送信
  • Live Message Notification (ライブメッセージ通知)
  • アンケートを送信
  • Quip 関連のアクション種別

ワークフローからフローへの移行に関する考慮事項

[フローに移行] ツールの考慮事項とサポートされるワークフロールールについて説明します。特定のワークフロールールの手動での変換方法についても説明します。

考慮事項

ワークフロールールに項目自動更新のみが含まれている場合は、[フローに移行] ツールによって迅速な項目自動更新 (保存前) フローに変換されます。

実行順序での位置により、レコードトリガーフローは同様のワークフロールールとは異なる動作をする場合があります。

保存されている待機中の時間ベースのアクションは、関連するレコードが変更された場合に、スケジュール済みパスに移行されます。

サポートされるワークフロールール

[フローに移行] ツールは、次の項目が含まれるワークフロールールをサポートします。

  • 項目ベースの条件
  • 項目自動更新
  • メールアラート
  • 送信メッセージ
  • 時間ベースのワークフローアクション
  • true に設定されたルール条件の数式 (評価条件が [作成されたとき、およびその後基準を満たすように編集されたとき] に設定されていない場合)
  • Equal to null
  • Not equal to null
  • ルール条件の数式

以下を含むワークフロールールは、[フローに移行] ツールでは移行できません。

  • ワークフローアクションが定義されていない条件
  • グローバル変数項目
  • 関連レコードの項目
  • レコードタイプ
  • does not contain、includes、excludes、または within 演算子
  • 選択リスト項目の greater than、greater or equal、less than、less or equal 演算子
  • Hour、Minute、Second、TimeNow、TimeValue、IsClone、または $RecordType を使用する数式
  • ToDo
  • 日付項目の相対日付値
  • マルチ通貨

手動変換方法

[フローに移行] ツールではサポートされない一部の機能は、手動で変換できます。

サポートされていない使用事例が開始条件に含まれるワークフロールールを手動で変換するには、フロー内で決定要素を作成します。次に、条件ビルダーを使用してワークフロールールステップを再作成します。

メモ この方法を使用すると、フローは常に実行開始直後に決定要素を確認します。この方法では、パフォーマンスが低下したり、時間ベースのワークフロートリガーが移行されなくなったりすることがあります。

does not contain 演算子を使用するワークフロールールを手動で変換するには、カスタム条件ロジックを使用します。たとえば、最初の条件で Contains 演算子を使用する条件を作成し、条件ロジックで「NOT 1」と入力します。

ToDo を使用するワークフロールールを手動で変換するには、[レコードを作成] オプションを使用して ToDo オブジェクトのレコードを作成します。

フローでは、メールアラートと送信メッセージのワークフローアクションがサポートされます。これらのワークフローアクションをフローに追加するには、[アクション] 要素を使用します。

TODAY や NEXT WEEK などの相対日付値を複製するには、決定要素を使用します。
