一時停止中のフローインタビューと失敗したフローインタビューのモニタリングと管理

オートメーション Lightning アプリケーションで、失敗したフローインタビューと一時停止中のフローインタビューを簡単に追跡して管理できます。[監視] タブには、すべての失敗したフローインタビューと一時停止中のフローインタビュー、および失敗したか一時停止した理由が表示されます。

必要なエディション

使用可能なインターフェース: Lightning Experience
サポートされているエディションを表示する。
必要なユーザー権限
オートメーションアプリケーションで [監視] タブを表示する 「フローの管理」権限セット
メモ Apex アクションを含む一括トランザクションの場合、失敗したフローインタビューには、失敗の原因となったレコードの詳細ではなく、最初のレコードの詳細が表示されます。

失敗したフローインタビューと一時停止中のフローインタビューの管理

オートメーションアプリケーション内からの失敗したフローインタビューと一時停止中のフローインタビューをすべて表示します。そこから、失敗したフローインタビューをデバッグし、一時停止中のフローインタビューを再開できます。

自動化アプリケーションにアクセスするには、プロセスの自動化設定の[Enable the Automation Lightning App (自動化 Lightning アプリケーションを有効化)]が選択されていることを確認します。

失敗したフローと一時停止中のフローの表示

  1. Automation アプリケーションで、［Monitor］ タブを選択します。
  2. 失敗したフローインタビューと一時停止中のフローインタビューを表示するには、[フロー] サブタブの [すべてのフローインタビュー] リストを参照してください。
    [エラーの詳細] 列には、失敗したフローインタビューの理由が表示されます。

カスタマイズ後に [すべてのフローインタビュー] リストビューに結果が表示されない場合は、[現在のフロー API 参照名] 項目が含まれているかどうかを確認します。この 項目は動的であり、サポート項目と組み合わせる必要があります。この問題を解決するには、[現在のフロー API 名前] 項目を削除するか、次の項目の少なくとも 1 つを含めます。

  • 現在のフロー種別
  • 現在のフローバージョン
  • 現在のフロー バージョンの表示ラベル

失敗したフローのデバッグ

  1. Automation アプリケーションで、［Monitor］ タブを選択します。
  2. [フロー] サブタブで、失敗したフロー名をクリックします。
    失敗したフローインタビューの詳細タブには、フローインタビューの失敗の原因となったエラーの説明が表示されます。
  3. フローの詳細タブで、Open をクリックします。
    Flow Builder に、失敗したフローの実行のデバッグの詳細が表示されます。

一時停止中のフローの再開

  1. Automation アプリケーションで、［Monitor］ タブを選択します。
  2. [フロー] サブタブで、一時停止中のフロー名をクリックします。
  3. フローインタビューを再度実行する準備ができたら、フローの [詳細] タブで [再開] をクリックします。

ボタンを使用したフローの開始

レコードページへのフローリンクの追加

有効な画面フローまたは自動起動フローを開始するカスタムリンクをレコードページに追加します。フローの Web アドレス (URL) を使用してリンクを設定します。

必要なエディション

サポートされているエディションを表示する。
必要なユーザー権限
Einstein for Flow や Agentforce for Flow など、Flow Builder で使用できるすべてのフロー タイプ、要素、機能を使用してフローを開く、編集、作成、有効化、または無効化する 「フローの管理」
メモ 「フローの管理」権限を持つ管理者である必要はありません。プロファイルまたは権限セットに追加するようにシステム管理者に依頼してください。

フローの作成

リンクから起動する自動起動フローまたは画面フローを作成します。必要に応じて、リンクをクリックしたレコードの ID をフローに送信できます。レコード ID をフローに送信して、フローが作業するレコードを把握できるようにするには、ID を保持する recordId というフロー変数を作成します。

  1. [フロー] リストビューを開きます。
    • Automation アプリケーションから、[フロー] タブを選択します。
    • 任意の Lightning アプリケーションの [フロー] タブで、アクション メニューをクリックし、[フローを開く] を選択します。
    • [設定] で、[クイック検索] ボックスに「フロー」と入力して、[フロー] を選択します。
    [オートメーションアプリケーション] および [フロー] タブのオプションには、[設定] アクセス権は必要ありません。
  2. 自動起動フローまたは画面フローを作成します。
    1. Automation アプリケーションで、[新規] をクリックします。次に、[Autolaunch Flow (No Trigger) (自動起動フロー (トリガーなし))] タイルまたは [Screen Flow (画面フロー)] タイルを選択します。
    2. [設定] から、[新規フロー] をクリックします。次に、[Autolaunch Flow (No Trigger) (自動起動フロー (トリガーなし))] タイルまたは [画面フロー] タイルを選択します。
    Flow Builder が開きます。
  3. 必要に応じて、レコード ID を保存するテキスト変数を追加します。
    1. ツールボックスを開くには、[] をクリックします。
    2. [新規リソース] をクリックし、[変数] を選択します。
    3. [API 参照名] に「recordId」と入力します。
    4. [説明] に「Stores the ID of the record that is located in the link. (リンクがあるレコードの ID を保存します)」と入力します。この値はフローに渡されます。
    5. [データ型] で [テキスト] を選択します。
    6. [入力で使用可能] を選択します。
    7. [完了] をクリックします。
  4. 必要に応じて、実行時にフローに送信される追加の入力値を保存する変数を追加します。レコード ID に加えて入力値を URL に追加する方法については、「フローの URL を使用した変数値の送信」を参照してください。
  5. 必要なアクションを実行する要素をフローに追加します。
    たとえば、フローに送信された取引先責任者の ID がフローにある場合、[メールを送信] アクションを使用して、レコード ID を recordId 変数に設定することで取引先責任者にメールを送信できます。
  6. フローを保存します。
  7. [Debug (デバッグ)] をクリックし、テストデータを使用してフローをテストします。
  8. [有効化] をクリックします。

フローの URL の取得

  1. [設定] の [クイック検索] ボックスに「フロー」と入力し、[フロー] を選択します。
  2. 実行するフローで をクリックし、[詳細とバージョンの表示] を選択します。
  3. フローの URL をコピーします。
    URL の形式は /flow/My_Flow です。

カスタムリンクの作成

  1. [Setup (設定)] で [Object Manager (オブジェクトマネージャー)] をクリックします。
  2. レコードページリンクを追加するオブジェクトをクリックします。例: 取引先責任者。
    オブジェクトウィンドウが開きます。
  3. [ボタン、リンク、およびアクション] をクリックします。
  4. [New Button or Link (新規ボタンまたはリンク)] をクリックします。
  5. リンクの表示ラベルと名前を付けます。
  6. [表示種別] で、[詳細ページリンク] を選択します。
  7. 残りの項目はデフォルト値のままにします。
  8. 大きなテキストボックスにフローの URL を入力し、URL の先頭に /Lightning を追加します。
    全文は /lightning/flow/My_Flow のようになります。
  9. ボタンが配置されているレコードの ID を渡す場合は、URL に recordId 入力変数の値を追加します。たとえば、ボタンが取引先レコードにある場合は、?flow__recordId={Account.Id} と入力します。そのため、完全な URL は /lightning/flow/My_Flow?flow__recordId={Account.Id} です。
  10. 作業内容を保存します。
メモ Lightning Experience を使用し、フロー URL の先頭に /Lightning を追加することをお勧めします。ただし、フロー URL に /Lightning を追加しなくても機能します。Lightning で実行する新しい利点は得られません。詳細は、「Choosing Between Lightning and Non-Lightning Flow URL Formats」を参照してください。
メモ 必要に応じて、フローの終了時の動作をカスタマイズできます。詳細は、「フロー終了動作のカスタマイズ」を参照してください。

ページレイアウトへのカスタムリンクの追加

  1. [ページレイアウト] をクリックします。
  2. リンクを追加するページレイアウトをクリックします。
  3. [カスタムリンク] をクリックします。
  4. リンクをカスタムリンクリストから [カスタムリンク] セクションにドラッグアンドドロップします。
  5. 作業内容を保存します。

これで、ユーザーはレコードに移動し、作成したリンクをクリックして、画面または自動起動フローを開始できます。入力変数を設定している場合、ユーザーが画面フローの [次へ] ボタンをクリックしたとき、または自動起動フローが開始されたときに、これらの値がフローに送信されます。

  8. フローを有効化します。
    1. [有効化] をクリックします。

コース管理システムの各フローをテストして、正しく動作することを確認します。フローを有効化します。

フローのテストと有効化は、実際のユーザーがフローを操作する前に自動化が正しく機能することを確認する重要なステップです。このテストプロセスでは、実際のシナリオ (コース提供の作成、参加者の登録、待機リストの管理、キャンセルの処理) をシミュレーションし、すべてのフローが正常に機能することを確認します。テストデータを作成し、登録ワークフローを完了することで、保存前フローでデータが正しく検証され、保存後フローで適切なメールが送信されて状況が更新されること、画面フローでスムーズなユーザーエクスペリエンスが提供されることを確認します。テストが完了し、すべてが正常に機能することを確認したら、フローを有効化して本番で使用できるようにすることで、組織で自動化された科目管理システムのメリットを活用できるようになります。この段階的なテストアプローチにより、問題を早期に発見し、稼働中のビジネスプロセスをスムーズに実行できます。

制限事項

[画面フロー] カスタムレポートの制限について説明します。

制限

  • フローインタビューログエントリオブジェクトは、過去 31 日間に有効だった各画面フローのログレコードを生成します。
  • フローインタビューログエントリオブジェクトの制限は、過去 31 日間の 1 か月あたり 700 万件のログレコードです。
    メモ 組織で 1 か月あたりの制限に達することはほとんどありません。その場合、Salesforce は新しいフローの評価指標の記録を停止します。ただし、制限に達したときにフローインタビューが行われている場合、Salesforce はフローインタビューの評価指標を追跡します。制限に達していない組織でも、31 日を経過したログはすべて自動的に削除されます。

制限事項

  • デフォルトでは、[サンプルフローレポート: 画面フロー] レポートはすべてのユーザーに表示されます。ただし、各ユーザーは実行ユーザーであるフローに関する情報のみを表示できます。「すべてのデータの参照」権限を持つユーザーのみが他のユーザーのフローログデータを表示できます。このレポートでは、新しいフローインタビューログとフローインタビューログエントリの主オブジェクトのデータが使用されます。他のユーザーが実行したフローに関する情報を表示する権限をユーザーに付与するには、共有設定を使用してフローインタビューログオブジェクトへのアクセス権を付与します。詳細は、「共有設定の定義」を参照してください。
  • 同じ API 参照名のカスタムレポートタイプまたは同じレポートタイプ名のレポートを持つ組織は、画面フローカスタムレポートタイプを受け取りません。組織がレポートを受信しない場合は、フローインタビューログオブジェクトとフローインタビューログエントリオブジェクトを使用してカスタムレポートタイプを作成します。その後、ユーザーはカスタムレポートタイプを使用してカスタムレポートを作成できます。

Agentforce を使用したフローのテストシナリオの生成

手動設定をスキップし、Agentforce を使用して、Flow Builder を開かずにコマンドラインからテストシナリオのドラフトを作成します。レコードトリガーフロー、自動起動フロー、または Data Cloud トリガーフロー (成功、障害、エッジケースパスなど) の包括的なテストシナリオを生成します。

必要なエディション

サポートされているエディションを表示する。
必要なユーザー権限
Einstein for Flow や Agentforce for Flow など、Flow Builder で使用できるすべてのフロー タイプ、要素、機能を使用してフローを開く、編集、作成、有効化、または無効化する 「フローの管理」

Agentforce VibesでフローのAgentforceを使用するには、「Agentforce Platform Developer and Admin(Agentforceプラットフォーム開発者および管理者)」権限セットライセンスと、「Agentforce Developer and Admin Tools(Agentforce開発者および管理ツール)」権限セットがユーザーに割り当てられている必要があります。

開始する前に、AI 端末を Salesforce 組織に接続します。

複雑なフローの包括的なテストシナリオを手動で作成すると、時間がかかり、エラーが発生しやすくなります。Agentforce for Flow Headlessは、フローの構造、意思決定結果、必須項目を自動的に分析し、包括的なテストシナリオのドラフトを作成します。Agentforce for Flow Headless でテストシナリオを生成できるようにすることで、次のことが可能になります。

  • 成功、障害、エッジケースの各パスで包括的にカバーします。

  • AI で生成されたテストシナリオを CI/CD パイプラインに直接統合することで、テスト戦略を拡張します。

分離されたテストデータを使用したフローのテスト

テスト設定メソッドを含むApexクラスからの専用の再利用可能なテスト・データを使用して、レコード・トリガー・フローと自動起動フローをテストします。テスト シナリオの実行後、分離されたテスト データはApex単体テストのようにロールバックされるため、組織のライブ データはそのまま維持されます。

必要なエディション

サポートされているエディションを表示する。
必要なユーザー権限
Einstein for Flow や Agentforce for Flow など、Flow Builder で使用できるすべてのフロー タイプ、要素、機能を使用してフローを開く、編集、作成、有効化、または無効化する 「フローの管理」

組織データをテストに使用すると、誰でもそのデータを変更し、テストが失敗する可能性があります。Sandbox と本番ではレコード ID が異なるため、ある環境で合格したテストを別の環境にリリースすると失敗する可能性があります。Apex テストの設定で実行時にデータを作成するのと同じように、テストシナリオの実行時に分離されたテストデータを作成します。テストデータの一貫性が維持されるため、複数の環境にリリースできます。

フローをテストモードで開くには、「テストシナリオの設定および実行 (ベータ)」を参照してください。

  1. @isTest アノテーションと、テストシナリオで使用できるようにするレコードを挿入する @testSetup メソッドを使用して、Apex クラスを作成します。

    たとえば、次の Apex クラスはテストアカウントを作成します。「Using Apex Test Setup Methods」を参照してください。

    @isTest
global class CommonTestSetup {
  @testSetup
  global static void setup() {
    List<Account> accts = new List<Account>();
    for (Integer i = 1; i <= 2; i++) {
      accts.add(new Account(Name = 'Test Account ' + i));
    }
    insert accts;
  }
}

    データサイロ内の分離されたテストデータを使用する場合、入力レコードは分離されたテストデータで作成したレコードを参照する必要があります。そのデータにレコードが存在しない場合、エラーが発生します。組織データを使用するテストシナリオとは異なり、Flow Builder から分離されたテストデータの入力レコードの項目値はカスタマイズできません。分離されたテストデータでは、そのレコードが主要な項目によって選択され、そのまま使用されます。Apex @testSetupメソッドで、すべての主要なフィールドに入力します。重要な項目は、後の手順で選択します。

  2. レコードトリガーフローまたは自動起動フローを開きます。
  3. [Test (テスト)] をクリックしてテストモード (ベータ) に入ります。
  4. [Scenario Testing Automation (シナリオテストの自動化)] を有効にし、[Select Data Source (データソースを選択)] で [Run from Data Silo (データサイロから実行)] を選択します。
    必須の Apex テスト設定フィールドが表示されます。作成した Apex @testSetup クラスを選択します。このテストシナリオでは、組織のデータが変更されないように、ロールバックを含む Apex クラスをデータソースとして使用します。
  5. テストシナリオで使用する各オブジェクトの主要な項目を選択します。
    分離されたオブジェクトの外部キー項目は、分離されたテストデータの一意のレコードを識別します。テストレコード ID は実行ごとに変更されるため、これらの主要な項目は実行時に入力レコードを分離されたテストデータと一致させます。たとえば、Phone フィールドを取引先レコードを識別するキーフィールドとして使用します。
  6. 分離されたテストデータのレコードと一致するようにトリガーレコードまたは入力値を設定します。
  7. [予測される結果 (アサーション)] で、アサーションを設定し、[シナリオを保存して実行] をクリックします。
    テストシナリオは、ライブ組織データではなく、データサイロ内の分離されたテストデータに対して実行されます。

モック出力を使用したフローのテスト (ベータ)

疑似出力を使用して、外部システムに依存することなく自動起動フローとレコードトリガーフローをテストします。アクション要素とサブフロー要素の予測可能な出力値を定義し、ライブコールアウトやサブフロー実行ではなくフローロジックをテストシナリオで検証できるようにします。

必要なエディション

必要なユーザー権限
Einstein for Flow や Agentforce for Flow など、Flow Builder で使用できるすべてのフロー タイプ、要素、機能を使用してフローを開く、編集、作成、有効化、または無効化する 「フローの管理」
メモ モック出力は、Salesforce.com の契約に関するページのベータサービス規約またはお客様が署名された Unified Pilot Agreement、および製品規約ディレクトリの該当する条件が適用されるパイロットまたはベータサービスです。このパイロットサービスまたはベータサービスは、お客様ご自身の裁量でご利用ください。

テストシナリオの疑似出力を設定する前に、次の点を確認してください。

  • フローが自動起動フローまたはレコードトリガーフローである。
  • フローに 1 つ以上のアクション要素またはサブフロー要素が含まれている。

疑似出力を使用すると、外部コールアウトを実際に送信したり、参照されるフローを実行したりすることなく、アクションまたはサブフロー要素がテスト実行中に返すデータを定義できます。この分離により、テストシナリオは外部連動関係ではなく、検証するフローロジックに集中できます。テストシナリオとアサーションについての詳細は、「自動フローテスト」を参照してください。

疑似出力を使用するケースの例:

  • 処理速度が制限されているか使用できない外部 API への HTTP コールアウトを含むアクション要素を含むフロー
  • 複雑な連動関係を持つ Apex メソッドを呼び出すアクション要素を含むフロー
  • テストシナリオで実行しないサブフロー要素を含むフロー。

疑似出力を使用するには、次の手順に従います。

  1. Flow Builder で、テストするフローを開きます。
  2. [Test (テスト)] をクリックしてテストモードを開きます。
  3. キャンバスで、疑似出力を使用するアクション要素またはサブフロー要素をクリックします。
    要素のプロパティパネルが開きます。
  4. [Scenario Output (シナリオ出力)] タブをクリックします。
  5. [Use Mock Output (モック出力を使用)] をクリックして、この要素のモック出力を有効にします。
  6. この要素の疑似出力の使用を停止するには、［Using Mock Output］ をクリックします。
  7. 出力ごとに、疑似値を入力するか、デバッグ履歴の以前のデバッグ実行の値をコピーします。
  8. (省略可能) 障害パスまたは代替パスをテストするには、[模擬出力後のパス] をこの要素の実行後にフローで実行するパスに設定します。
  9. このテストシナリオで非同期に実行されるアクション要素またはサブフロー要素ごとに上記の手順を繰り返します。
  10. [シナリオを保存] をクリックして、テストシナリオを保存します。
  11. [シナリオを実行] をクリックして、シナリオを実行します。

テストシナリオは、疑似出力を有効にした各要素の疑似出力を使用して実行されます。フローは要素の通常の実行をスキップし、指定した値を使用します。キャンバスでは、モックされた要素に [出力モック] バッジが表示されます。

テストを自動化する理由

自動テストにより、時間が節約され、フローの信頼性が向上します。テストシナリオを 1 回設定すると、各自動実行で同じ入力とアサーションが再利用されます。フローごとに 1 つのテストシナリオに制限されません。さまざまなパスと条件に対応するテストシナリオを必要なだけ作成します。

自動テストシナリオは、Sandbox から本番にフローをリリースする場合に特に有用です。テストシナリオが特定の組織のレコードに結び付けられず、環境全体で一貫して実行されるように、分離されたテストデータを使用します。

フローで実行できるすべてのパスのテストシナリオを作成することをお勧めします。

自動起動フローとレコードトリガーフローでは、テストモードで自動テストが 1 つの機能になります。テストシナリオを設定するときに [シナリオテストの自動化] を有効にします。「テストモードでのフローのテスト (ベータ)」を参照してください。Data Cloud トリガーフローについては、「Data Cloud トリガーフローのテスト」を参照してください。

アサーションのしくみ

アサーションでは、[次の文字列と一致する] などの演算子を使用して、リソースの値が期待値と一致することを確認します。テストシナリオの実行後、実際の値が設定した条件に一致するかどうかに基づいて、各アサーションが合格または不合格として評価されます。テストシナリオは、そのすべてのアサーションに合格した場合にのみ合格します。

テスト結果の解釈

テストシナリオが実行されると、各アサーションの状況と 2 つの値 (設定した式である条件と実際のランタイム値である条件評価) が表示されます。アサーションを展開すると、両方の値が表示されます。

アサーションが失敗した場合、その条件と条件評価を比較して不一致を見つけます。フロー内の担当要素を修正し、テストシナリオを再実行して修正を確認します。

詳細は、「テストモードでのテストシナリオ結果の解釈 (ベータ)」または「Data Cloud トリガーフローテスト結果の解釈」を参照してください。

テストするフローバージョンの選択

テストシナリオを実行するフローバージョンを選択できます。デフォルトの選択内容は、テストシナリオを設定する場所によって異なります。

Data Cloud トリガーフローの場合、デフォルトでフローの有効なバージョンに対してテストシナリオが実行され、有効なバージョンがない場合は最新バージョンに対して実行されます。

テストモードでは、テストシナリオでデフォルトですべてのフローバージョンが選択されます。1 つのバージョンまで含め、テストするバージョンのみが残るまで削除します。たとえば、新しいバージョンに新しいロジックを追加する場合、そのロジックを含むバージョンに対してのみテストシナリオを実行します。

テスト実行によるデータへの影響

ロールバックの動作は、テスト環境とシナリオ設定によって異なります。テストモードでは、ロールバックはデフォルトで有効になっています。これは、アサーションを使用するシナリオや、期待される結果を手動で評価するレコードトリガーシナリオで必要です。Data Cloud トリガーフローテストでは、トリガーレコードの一時的なコピーが作成され、そのコピーはデータベースに保存されません。

テストモードでのみ、分離されたテストデータがサポートされます。レコード トリガー フローおよび自動起動フローの場合、@testSetupメソッドを使用するApexクラスを使用して、データ サイロに専用のテスト レコードを作成できます。

  • Data Cloud トリガーフローのテスト

  • エラー処理のためのフローのテスト

次の表に、CPU 制限エラーのトラブルシューティングのリファレンスを示します。各行には、一般的な問題、それを解決するソリューション、および今後のフローでそれを回避するための技術が記載されています。まず、これらの問題がフローに適用されるかどうかを判断します。該当するものがない場合は、同じトランザクション内の別の自動化 (Apex トリガー、別のフロー、ワークフロー ルールなど) が同じ CPU バジェットから取得され、実行犯になる可能性があります。トランザクション全体で何が CPU を消費しているかを特定するには、Apex デバッグログを確認します。詳細は、「デバッグログ」を参照してください。

問題 解決方法 予防技術

ループ内のデータ操作言語 (DML) の操作

ループパス内で [レコードを作成]、[レコードを更新]、または [レコードを削除] 操作を実行すると、反復ごとに CPU 時間が消費されます。複数のレコードを一度に 1 つずつ処理すると、すぐに制限を使い切ってしまう可能性があります。

例: フローは 100 件の商談をループし、ループ内で [レコードを作成] 要素を使用して商談ごとに ToDo を作成すると、100 件の個別の DML 操作が作成されます。

コレクションベースのデータ操作言語 (DML) 操作の使用

ループ内で、割り当て要素を使用してレコードをレコードコレクション変数に追加します。ループが完了したら、1 つの [レコードを作成]、[レコードを更新]、または [レコードを削除] 要素を使用してコレクション全体を一度に処理します。このアプローチは一括処理と呼ばれます。

例: 商談をループし、割り当て要素を使用して各商談の ToDo を作成します。次に、別の割り当て要素を使用して、各 ToDo をコレクション変数に追加します。ループ後、[レコードを作成] 要素を使用してすべての ToDo を一度に作成します。

詳細は、「トランザクションでのフローの一括処理」を参照してください。

ループ内に DML 操作を配置しないでください。ループ中にコレクション変数のレコードを収集するフローを常に設計し、ループの完了後に DML を実行します。

ループ内の複数のクエリ

ループ内の [レコードを取得] 要素では、特に大きなオブジェクトを照会する場合や複雑な検索条件を使用する場合に CPU 時間が大幅に消費されます。

例: フローは取引先をループし、ループ内で [レコードを取得] を使用して各取引先の関連取引先責任者を取得するため、取引先ごとに 1 つのクエリが生成されます。

Query Data Before Loops (ループ前のデータの照会)

ループの前に、1 つの [レコードを取得] 要素と [関連レコードを取得] 機能を使用して、適切な検索条件で必要なすべてのデータを取得します。ループ中は、反復ごとに照会するのではなく、収集したデータを使用します。1 つの [レコードを取得] 要素を使用できない場合は、[レコードを取得] 要素を使用してプライマリレコードを取得します。次に、別の [レコードを取得] 要素を使用してセカンダリレコードを取得します。レコード項目、[対象] 演算子、および最初の [レコードを取得] コレクションを使用して、セカンダリレコードを絞り込みます。たとえば、[取引先 ID] > [入力] > [取引先] の [取引先を取得] を選択します。

例:最初に取引先 ID で絞り込む [レコードを取得] 要素を使用してすべての関連取引先責任者を取得し、ループ中に取引先責任者コレクションを参照します。

ループ内でのクエリは避けてください。ループに入る前に、必要なすべてのデータを取得します。

ループ内の複雑な数式

ループの反復ごとに複雑な数式計算を実行する割り当て要素では、特に文字列操作、日付計算、ネストされた関数で CPU 時間が累積されます。

例: フローが 500 件のレコードをループ処理し、各反復処理で複数の数式計算を実行して項目値を派生します。

数式の簡略化

複雑な数式を簡単なステップに分割します。ループ外で変更されない値を計算します。可能な場合は、ネストされた関数は避けてください。フロー数式の代わりにオブジェクトで数式項目を使用することを検討してください。

コレクション全体に対する操作 (絞り込み、対応付け、並び替えなど) の場合、変換要素はループよりも効率的に実行されます。ループの反復ごとに 1 つのクエリではなく、1 つのクエリですべての関連レコードを取得するには、レコードを取得要素と IN 演算子を使用します。

詳細は、「変換要素」を参照してください。

数式を簡略化し、変更されない計算をループ外に移動します。現実的なデータ量で数式のパフォーマンスをテストします。

大規模なレコードコレクションの処理

1 つのトランザクションで数千件のレコードを処理するスケジュール済みフローまたは一括処理は、適切な一括処理であっても、CPU 時間を消費する可能性があります。

例:スケジュール済みフローで 5,000 件のアカウントレコードを取得し、各レコードのデータに対して複雑な変換を実行してから更新します。

代替アプローチの使用

データ量が多い場合は、次の点を考慮してください。

  • 作業を複数のスケジュール済みフローに分割し、各フローでレコードのサブセットを処理する
  • 大量のデータに対する Apex 一括処理の使用
  • 経時的なレコードの増分処理
  • プラットフォームイベントを使用した複数のトランザクションへの処理の分散

早い段階でデータを絞り込んで、処理するレコード数を減らします。[レコードを取得] 検索条件を使用して、必要なレコードのみを取得します。本番にリリースする前に、現実的なデータ量でテストします。

トランザクションの複数のフロー

1 つのフローが (レコード変更またはサブフローを介して) 他のフローをトリガーすると、トランザクションのすべてのフローの累積 CPU 時間が制限に含まれます。

例: アカウント更新時のレコードトリガーフローで複数のサブフローが実行され、関連オブジェクトで他のレコードトリガーフローもトリガーされます。

フローチェーンの削減

関連する自動化をより少ないフローに統合します。フロートリガー条件を確認して、必要な場合にのみフローが実行されるようにします。エントリ条件を使用して、レコードトリガーフローを実行するタイミングを制限することを検討してください。

同じトランザクションで実行できるすべての自動化 (フロー、プロセス、ワークフロー、トリガー) の累積影響を確認します。自動化チェーン全体を監視および最適化します。

一括データ読み込み

一括データインポートまたは一括更新中に実行されるレコードトリガーフローでは、すべてのレコードを効率的に処理する必要があります。非効率的なフローは、個々のレコードで正常に機能していても、一括処理中に CPU 制限に達します。

例: ユーザーが 200 件のアカウントレコードをインポートするとします。保存前レコードトリガーフローでは、取引先ごとに複数のルックアップと計算が実行されます。

一括処理の最適化

  • コレクションベースの DML とクエリを使用
  • 重要でない操作の保存後フローを考慮する (非同期で実行され、CPU 制限が高くなる)
  • ループよりも効率的にコレクション全体を操作する変換要素 (条件、対応付け、並び替え) を使用する

詳細は、「変換要素」を参照してください。

レコードトリガーフローでは、常に複数のレコードを同時に処理することを前提としてください。本番にリリースする前に、一括データ読み込みを使用して (データローダーまたは一括更新を使用して) テストします。適切に設計されていない場合、個々のレコードで完全に機能するフローは、適切に設計されていない場合、一括操作中に失敗する可能性があります。

一般的な予防ガイドライン

  • フローパフォーマンスの監視: Apex デバッグログを定期的に確認し、CPU 制限に近づいているフロー (まだ失敗していない場合も含む) を特定します。定期的な監視により、本番で問題が発生する前にフローを最適化できます。
  • Test with realistic data: 現実的なデータ量を使用してフローをテストし、有効化する前にパフォーマンスの問題を明らかにします。通常、デバッグモードでは 1 つのレコードでテストされるため、一括操作の問題は発生しません。
  • ドキュメントの最適化の決定: 要素の説明を使用して、一括処理やその他の最適化を適用した場所をメモします。このドキュメントは、将来のメンテナが設計を理解し、パフォーマンスの問題を誤って導入しないようにするのに役立ちます。
  • Start simple and optimize: フローを小単位で作成し、各ステップでパフォーマンスをテストします。作業フローの最適化は、複雑に壊れたフローを修正するよりも簡単です。

フローでの CPU 負荷の高い要素の識別

Apex デバッグ ログを使用して、フロー内で CPU 時間を最も消費している要素を特定します。

  1. [設定] に移動して、[クイック検索] ボックスに「デバッグログ」と入力します。
  2. エラーが発生したユーザーのデバッグログを設定するか、フローをデバッグモードで実行します。
  3. フローを実行してエラーを再現します。
  4. 生成されたデバッグログを開きます。
  5. デバッグログで次の主要なイベントを検索します。
    • FLOW_CREATE_INTERVIEW_BEGIN - 各フローの開始日時を表示します。
    • FLOW_ELEMENT_LIMIT_USAGE - 各フロー要素の CPU 消費時間を表示します。
    • CUMULATIVE_LIMIT_USAGE - CPU時間の合計を表示します。
  6. CPU 時間値が高い要素を特定します。
    一般的な原因は次のとおりです。
    • 大きなコレクションがあるループ要素。
    • 複雑な検索条件を使用してレコード要素を取得します。
    • 複数のレコードを含む DML 操作 (レコードの作成、レコードの更新、レコードの削除)。
    • 複雑な数式を含む割り当て要素。

CPU 時間を最も消費している要素がわかりました。この情報を使用して、対象を絞った最適化を適用します。

デバッグログについての詳細は、「Working with Logs in the Developer Console (開発者コンソールでのログの操作)」を参照してください。

一般的な必須項目の問題を特定し、解決策を適用して、REQUIRED_FIELD_MISSING エラーを回避するための予防方法に従います。

次の表は、必須項目のエラーのトラブルシューティングのリファレンスです。各行には、一般的な問題、それを解決するソリューション、および今後のフローでそれを回避するための技術が記載されています。

問題 解決方法 予防技術

すべての必須フィールドを使用しないレコードの作成

[レコードを作成] 要素を使用する場合、Flow Builder ではオブジェクトでどの項目が必須かは示されません。すべての必須項目を手動で設定しないと、実行時にフローが失敗します。

例: フローは取引先責任者レコードを作成しますが、必須の [姓] 項目には入力しません。

構築前の必須項目の確認

[レコードを作成] 要素または [レコードを更新] 要素を設定する前に、オブジェクトマネージャーでオブジェクトの必須項目を確認します。要素で直接、割り当て要素を介して、または画面入力から、すべての必須項目を入力します。

または、[作成] 種別のクイックアクション要素には、アクションレイアウトで必要な項目が表示されます。ただし、クイックアクション要素では使用可能な項目がアクションレイアウトに制限され、作成されたレコードの ID は保存されません。

フロー内で別の方法で入力しない場合は、必須項目のデフォルト値を設定します。

フローでよく使用されるオブジェクトの必須項目のチェックリストを管理します。レコードを作成または更新するフローを作成する前に、オブジェクトマネージャーまたはオブジェクトのページレイアウトに相談してください。

必須フィールドに入力されない画面フロー

画面フローで情報を収集してレコードを作成するときに、必須項目が画面に含まれておらず、フローで別の方法で設定されていない場合、必須項目が入力されないことがあります。

例: ケースを作成する画面フローには [件名] と [説明] の項目がありますが、画面には必須の [状況] 項目が含まれておらず、[レコードを作成] 要素で設定されていません。

画面への必須フィールドの追加またはフローでの項目の入力

レコード項目をオブジェクトから直接画面に追加します。レコード項目は、オブジェクト定義からその必須性を自動的に継承します。ユーザーが設定しない必須項目については、[レコードを作成] 要素で直接入力するか、フローの前半で割り当て要素を入力します。

画面フローを設計するときは、オブジェクトマネージャーでオブジェクト定義を確認し、すべての必須項目を特定します。必須項目を画面に追加するか、フローでユーザーが設定しない項目のデフォルト値を指定します。

画面フローの更新 必須項目のクリア

画面フローでは、ユーザーが項目を空白のままにし、フローがその空白値を使用してレコードを更新すると、更新によって既存の値が空白で上書きされます。その項目が必須の場合、更新は失敗します。

例: 画面フローでは、ユーザーが Account 項目を編集できます。ユーザーは [会社] 項目を空白のままにします。[レコードを更新] 要素では、空白の画面値を使用して [会社] 項目を更新します。これは [会社] が必須であるため失敗します。

画面項目を必須にするか、決定を使用

必須項目の画面コンポーネントを必須としてマークし、ユーザーが空白のままにできないようにします。必須レコード項目を更新する省略可能な画面項目の場合、決定要素を使用して値が空白かどうかを確認します。空白の場合、他の項目のみを更新する別の [レコードを更新] 要素に転送します。

さまざまなレコード状態で更新操作をテストし、必須項目が入力されていることを確認します。どの画面項目を必須レコード項目に対応付けて、画面で必須としてマークするかを指定します。

レコードタイプと入力規則の要件

レコードタイプごとに異なる必須項目を設定できます。入力規則によって、項目を条件付きで必須にすることもできます。フローは、あるレコードタイプでは機能しますが、別のレコードタイプでは機能しません。

例: フローで「エンタープライズ」レコードタイプを使用して商談を作成すると、「標準」レコードタイプでは不要なカスタム項目が増えます。

複数のレコードタイプを使用したテスト

オブジェクトにレコードタイプがあり、フローで複数のレコードタイプのレコードを作成する場合は、各レコードタイプでフローをテストして、フローですべての種別固有の必須項目が入力されていることを確認します。必要に応じて、決定要素を使用して、ロジックパスの異なるさまざまなレコードタイプを処理します。

フローに影響するレコードタイプと入力規則を文書化します。フロー設計時に各レコードタイプの項目の必須性を確認します。フローテストチェックリストにレコードタイプテストを含めます。

一般的な予防ガイドライン

  • 障害パスの実装: [レコードを作成] 要素と [レコードを更新] 要素に障害パスを追加します。障害パスを使用して、役に立つエラーメッセージをユーザーに表示したり、Salesforce システム管理者が確認できるようにエラーを記録したりします。
  • 有効化前に徹底的にテスト: デバッグモードを使用して、一部のフィールドが空になるエッジケースなど、さまざまなデータシナリオでフローをテストします。
  • 説明フィールドを使用: フローに入力される必須フィールドと値の取得元を記録する説明をフロー要素に追加します。
  • フローエラーの監視: フローエラーメールとログを定期的に確認し、問題を早期に発見します。

欠落している項目の特定

REQUIRED_FIELD_MISSING エラーを受け取ったら、次の手法を使用してエラーの原因となった項目を特定します。

  1. エラーメッセージを確認します。
    REQUIRED_FIELD_MISSING エラーは、通常、欠落していた項目を示します。エラーの詳細で項目の API 参照名を探します。
  2. デバッグモードを使用します。
    デバッグモードでフローを実行し、エラーが発生したときにデバッグの詳細を確認します。デバッグログには、失敗した要素と特定の項目名が表示されます。詳細は、「Flow Builder デバッガを使用したフローのテストまたはトラブルシューティング」を参照してください。
  3. Apex デバッグログを確認します。
    レコードトリガーフローの場合は、Apex デバッグログを確認します。「REQUIRED_FIELD_MISSING」を検索して、失敗の原因となった正確な項目を見つけます。
  4. メール通知を確認します。

レコードを保存する前に実行されるレコードトリガーフローでは、挿入できない項目の内部の書き込み可能状況が考慮されるようになりました。既存のフローで編集できない項目を更新しようとすると、「項目自動更新の対象項目が無効です。」というエラーメッセージが表示されます。
