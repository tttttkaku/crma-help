買い物客通知のメールドメインの設定

通知を使用するには、通知の送信元を示す有効な電子メール アドレスが必要です。Salesforce が提供するデフォルトのアドレスを使用するか、認証済みのサイトドメインを使用してアドレスを作成し、ブランド設定されたエクスペリエンスを提供できます。

デフォルトでは、通知メールはno-reply@101.mx.salesforce.comまたはno-reply@201.mx.salesforce.comから送信されます。サイトのドメインがアクティブな認証済みドメインと一致しない場合は、代わりにデフォルトの Salesforce アドレスのいずれかからメールが送信されます。

  1. メールアドレスから独自のドメインを作成するには、Salesforce 組織で、[設定] から [ ユニファイドメッセージングメール | 認証済みドメイン] | を選択します。
  2. [ ドメインの追加]をクリックし、指示に従ってドメインをアクティブ化します。
  3. [設定(Setup)] から、[ ユニファイド メッセージング | Eメール | 認証元アドレス(Unified Messaging Email Authenticated From Addresses )] を選択します。
  4. [差出人住所を追加 ] をクリックし、住所の情報を追加します。ユーザー名はno-replyである必要があります。
  5. 保存をクリックします。

B2C Commerce の買い物客通知の設定

放棄された買い物カゴのリマインダーや注文後のマーケティング通知など、買い物客に通知を送信します。通知には、Salesforce Flow、Agentforce Marketing、Data 360 が必要です。Data 360 クレジットは、送信される通知ごとに消費されます。クレジットの使用状況については、アカウントエグゼクティブにお問い合わせください。また、パーソナル化を有効にして、特定の買い物客のニーズや好みに合わせてマーケティングコミュニケーションをカスタマイズすることもできます。

同意を設定する前に、前提条件を満たしていることを確認してください。「B2C Commerce と Agentforce Marketing の前提条件」を参照してください。

  1. Salesforce 組織で拡張 CMS ワークスペースを設定します。

    「CMSワークスペース」を参照してください。

  2. エンゲージメントイベントデータキットをインストールし、表にリストされているDMOを手動でマッピングします。

    「エンゲージメントイベント」を参照してください。

    パーソナライゼーションを使用すると、買い物客の通知で関連性の高いパーソナライズされた体験を提供できます。買い物客への通知を使用するためにパーソナル化は必要ありません。

    Business Manager の通知ページから通知テンプレートとフローにアクセスしてカスタマイズします。
  • 買い物客通知チャネルフローとテンプレートのインストール

B2C Commerce サイトの Data 360 データスペースへのマッピング

データスペースは、Data 360 でのプロファイルの統合、インサイト、マーケティングのためにデータを分割します。Data 360 で、B2C Commerce サイトごとに個別のデータスペースを作成します。次に、B2C Commerce で、各サイトを対応する Data 360 データスペースにマッピングします。

Data 360 で、データスペースを作成します。「データ・スペースについて」を参照してください。

  1. アプリケーションランチャーの順にクリックし、マーチャントツール | サイト | サイト環境設定 | Salesforce Data Cloud | 機能設定データ | スペースマッピングの順に選択します。
  2. ドロップダウンで、現在選択されているサイトに対応するデータスペースを選択します。
    警告 データ・スペース・マッピングは、保存後に変更することはできません。
  3. 保存をクリックします。

B2C Commerce と Agentforce Marketing 機能を使用するその他のサイトについては、このプロセスを完了してください。

PWA ストアフロントで買い物客の同意を得るための SLAS クライアントの設定

PWA ストアフロントがある場合は、B2C Commerce インスタンスに Shopper Login and API Access Service (SLAS) クライアントを設定してアクセストークンをリクエストします。

Shopper Consents APIのアクセストークンをリクエストするように SLAS クライアントを設定する方法については、「Shopper API の承認」を参照してください。クライアントを設定する際には、クライアントのsfcc.shopper-consentsと、カスタム買い物客の範囲で定義されたsfcc.shopper-consents.rwがあることを確認してください。

PWA または SFRA ストアフロントでの買い物客の同意の表示

買い物客の同意は、Progressive Web App (PWA) サイトのマーケティング同意フッターコンポーネント、またはStorefront Reference Architecture (SFRA) サイトのフッターと登録コンポーネントに表示できます。

マーケティング同意フッターコンポーネントは、Shopper Consents API フックをサポートします。PWA ストアの詳細については、「PWA Kit の概要」を参照し、GitHub でホストされている PWA Kit オープンソース プロジェクトを参照してください。SFRA ストアの詳細については、SFRA GitHub同意リポジトリを参照してください。

同じ B2C Commerce 注文での複数クーポンの使用制限

買い物客は 1 回の B2C Commerce 注文で複数のクーポンコードを適用できます。

たとえば、教師が複数の学生のために書籍を注文できるようにする場合などです。この場合、それぞれの学生が 1 冊または複数冊の書籍を選択して、次に無料の書籍 用のクーポンを使用できます。このプロモーションのクーポンコードは同じクーポンに属しており、クーポンはチラシまたは電子メールで学生に送信されます。教師は、書籍の注文とクーポンコードを生徒のサイトに入力します。クーポンを提示した各生徒は、無料で本を受け取ります。

買い物客が買い物カゴに複数のクーポンを追加すると、各コードがクーポンの品目に関連付けられます。

クーポンの構成の全般タブで、注文ごとの使用制限を構成します。

クーポンの検証は、使用制限の構成によって異なります。

  • クーポンコードごとの使用 - 制限は他のプロモーションと同じ方法で検証されます。設定された制限数に達している場合は、クーポンコードは買い物カゴに追加できません。
  • 顧客ごとの使用 — 検証は、過去の注文と現在買い物カゴに入っているクーポンコードによって異なります。たとえば、買い物客 1 人につき 3 回使用できるクーポンを構成するとします。顧客は以前の注文でクーポンコードを使用しましたが、買い物カゴにはクーポンコードが 2 つ入っています。顧客は同じクーポンの別のコードを買い物カゴに追加することはできません。
  • 期間ごとの使用 - 検証は、過去の注文と現在買い物カゴに入っているクーポンコードによって異なります。たとえば、クーポンが 1 週間に 3 回しか使用できず、顧客が 6 日前の注文でそのクーポンを 1 回使用しているとします。買い物カゴにはまだ 2 つのクーポンコードがありますが、顧客は同じクーポンの別のコードを買い物カゴに追加することはできません。

買い物カゴに適用されるプロモーションが複数のクーポンコードで修飾されている場合、プロモーションの適用回数を増やせます。

  • 複数のクーポンコードの適用に対応していないプロモーションタイプの場合は、動作は変化しません。
  • プロモーションタイプが複数の適用に対応していて、プロモーションの最大適用数フィールドが空白に構成されている場合は、制限はありません。
  • プロモーションタイプは複数の適用に対応しており、最大適用数に有限数が設定されいる場合は、プロモーションはクーポンコードあたりの最大適用数まで適用されます。つまり、有効な最大適用数 は、許可されている最大適用数にクーポンコードの数を掛けた値と同じです。

このクーポン設定では、プロモーションが適用される回数を超えることはまずありません。それ以外の場合は、標準の動作が適用されます。購入条件が設定されているプロモーションでは、その購入条件を複数回満たす必要はありません。商品は複数回割引されることはなく、除外ルールは同じままです。

例外は、「対象商品の金額に基づく」と「対象商品を含まない」の商品プロモーションタイプです。この 2 つのプロモーションでは、「ボーナス商品の選択」割引を受けることができます。このプロモーションタイプでは最大適用数フィールドが表示されますが、これは使用されません。たとえば、顧客が 15,000 円分の対象商品を買い物カゴに入れた場合です。「対象商品を 7,500 円以上購入してボーナス商品をゲット」というプロモーションの場合、このクーポンで 2 つのボーナス商品はもらえません。このプロモーションでは、買い物カゴに入っているそれぞれ個別のクーポンコードに対してボーナス商品が提示されます。金額はトリガー要因ではありません。

この機能は、B2C Commerce API を使用して実装します。

B2C Commerce の Promotion_Campaign_Assignent 要素

<promotion-campaign-assignment> 要素は、キャンペーンにプロモーションを割り当てるための XML のトップレベルにある要素です。このトピックは、B2C Commerce に該当します。

<promotion-campaign-assignment> 要素を使用する際には、以下を念頭に置いてください。

  • 各 <promotion-campaign-assignment> 要素には、有効なプロモーションおよびキャンペーンに一致する <promotion-id> と <campaign-id> が必要です。プロモーションまたはキャンペーンが見つからない場合、エラーメッセージがログされ、要素はスキップされます。
  • 含まれる要素はすべて任意です。マージモードまたは更新モードの既存の割り当てで任意の要素が指定されていない場合、対応する値は変更されません。マージモードまたは置換モードの新規の割り当てで任意の要素が指定されていない場合は、デフォルト値が使用されます。
  • 削除は、<promotion-campaign-assignment> 要素で mode="delete" を使用して行います。
  • 削除で <promotion-id> または <campaign-id> のみが指定された場合は、ワイルドカードで削除する処理が行われます。削除は、特定のプロモーションのすべてのキャンペーンへの割り当て、またはすべてのプロモーションの特定のキャンペーンへの割り当てに対して実行できます。
  • <promotion-id> と <campaign-id> の両方が指定されている場合は、特定のプロモーションから特定のキャンペーンへの割り当てが削除されます。
  • 条件を満たす割り当てがないためワイルドカードによる削除が実行できない場合は、警告メッセージがログされます。

B2C Commerce のプロモーション互換性

互換性ルールを使用して、プロモーションの適用をコントロールします。互換性ルールでは、買い物客が可能なすべてのプロモーションの対象となることを防止できます。ランクおよび除外のシステム属性を使用して、プロモーションの互換性を管理します。

たとえば、買い物客全員向けの 10% グローバル商品プロモーションと、登録買い物客向けの 20% 特別商品プロモーションがサイトにあるとします。登録済みの買い物客が両方の割引の対象とならないようにするには、プロモーションにクラス除外を追加します。

ランク

優先するプロモーションを定義します。たとえば、10 を最高、100 を最低として、プロモーションランクを指定できます。Business Manager のプロモーション編集ページで、プロモーションのランクを (任意で) 設定します。デフォルトでは、プロモーションにランクは設定されていません。

  • ランクが定義されていないプロモーションは、ランクが定義されているプロモーションより低いランクになります。
  • ランクシステムでは、プロモーションはランクの順に (最高ランクから最低ランクに) 適用されます。結果が予測可能になるように、同じランクのプロモーションは、さらにデフォルトの並べ替えメカニズムによって並べ替えられます (プロモーションの処理のデフォルトの並べ替えセクションを参照してください)。
  • ランク値をカスタマイズするには、システムオブジェクト Promotion (プロモーション) のランク属性を編集します。

除外

除外属性を使用して、プロモーションを相互に除外するかどうかを指定します。除外は全般的に、またはプロモーションのクラスに対して相対的に行えます。この設定は必須ですが、任意の時点で変更できます。

除外 定義
なし どのプロモーションとも組み合わせることができます (デフォルト)
クラス 同じクラスのプロモーションと組み合わせることはできません
グローバル いずれのプロモーションとも組み合わせることができません
メモ グローバル除外プロモーションは、組み合わせの構成を使用してのみ組み合わせることができます。グローバル除外をもつプロモーションを組み合わせた場合、買い物カゴでプロモーションを適用する際に他のプロモーションよりも優先されます。どのプロモーションが適用されるかについては、Salesforce B2C Commerce の優先度ルールを参照してください。

Promotion Conversions ダッシュボード

B2C Commerce Reports & Dashboards の Promotion Conversions (プロモーションコンバージョン) ダッシュボードは、ストアフロントに表示するプロモーションのパフォーマンスに関するインサイトを提供します。このダッシュボードを使用して、プロモーション戦略の効果を評価できます。また、サイトのトラフィックを収益に変換しているプロモーションと、パフォーマンスが思わしくないプロモーションを特定できます。

ダッシュボードのデータは 3 つのチャートとテーブルで示されています。

  • プロモーションのコンバージョン率
  • プロモーションのコンバージョンの概要
  • プロモーションのコンバージョンの詳細

コンバージョン率

コンバージョン率は、サイトの訪問のうち、プロモーションを含む注文を行ったものの割合です。たとえば、11 月 15 日にサイト X には 10,000 件の訪問があったとします。これらの訪問のうち、買い物客はプロモーションを含む注文を 300 件行っています。この場合、サイト X のコンバージョン率は 3% (300/10,000) となります。

コンバージョン率のグラフは、合計の訪問数と各プロモーションクラスのコンバージョン率が経時的に表示されます。チャートの表示を合計からプロモーションクラスの 1 つに変更するには、チャートキーからクラスを選択します。

  • Total (合計): プロモーションを含む注文の合計数を訪問の合計数で割ったもの。
  • Order (注文): 注文クラスプロモーションの注文数を注文クラスプロモーションの訪問数で割ったもの。
  • Product (商品): 商品クラスプロモーションの注文数を商品プロモーションクラスのプロモーションの訪問数で割ったもの。
  • Shipping (配送): 配送クラスプロモーションの注文数を配送クラスプロモーションの訪問数で割ったもの。

プロモーションの訪問

サイトの訪問は、買い物客がプロモーションをトリガーした場合にプロモーションのサイト訪問とみなされます。買い物客はプロモーションの限定子を満たした場合にプロモーションをトリガーします。

以下に例を示します:

  • 注文の訪問: 買い物客は、1 個購入で 1 個無料 (BOGO) プロモーションの一部である商品を 2 つの商品を買い物カゴに入れると、注文プロモーションの訪問をトリガーします。
  • 配送の訪問: 買い物客は、買い物カゴに $50 以上の商品を入れることで配送プロモーションをトリガーします。
  • 商品の訪問: 買い物客は、買い物カゴにプロモーション商品を入れることで、商品プロモーションをトリガーします。

割引が適用された場合、システムはプロモーションの設定と限定子に基づいてプロモーションの訪問を追跡します。たとえば、Everyone (すべての顧客) 顧客グループに割り当てられたプロモーションでは、買い物客が必要な品目を買い物カゴに追加した時点で訪問が追跡されます。クーポン駆動型プロモーションでは、買い物客がクーポンを買い物カゴに正常に適用した時点で訪問が追跡されます。サイトにデフォルトの配送方法が設定されていない場合、買い物客が注文手続きの配送ページで配送方法を選択するまで、配送プロモーションの訪問は配送の訪問として追跡されません。

Promotion Conversion ダッシュボードでは、すべてのプロモーションとプロモーションクラスごとにプロモーションの訪問が追跡されます。

プロモーションのコンバージョンの概要

Conversion Summary (コンバージョンの概要) テーブルは、プロモーション戦略がサイトの訪問から注文のコンバージョンにどのように影響を与えているかに関する分析情報を提供します。このチャートには、以下のサイトの訪問タイプに対するプロモーションのコンバージョンメトリクスの概要がリストされます。

  • All Visits (すべての訪問): すべてのサイトの訪問
  • Promo Visit (プロモーションの訪問): 任意のクラスのプロモーションが少なくとも 1 つ適用されている
  • Product Promo Visit (商品プロモーションの訪問): 商品プロモーションが適用されている
  • Shipping Promo Visit (配送プロモーションの訪問): 配送プロモーションが適用されている
  • Order Promo Visit (注文プロモーションの訪問): 注文プロモーションが適用されている

買い物客は、割引で設定されている最大許容数よりも多くのボーナス商品を追加することはできません。ストアフロントアプリケーションは API メソッド LineItem.setQuantityValue() を呼び出して数量を任意の値に設定できますが、次に割引が適用されると値が調整されます。ボーナス商品割引では、数量が 1 にリセットされます。

「価格表からの価格」の割引

スケジュールおよび限定子機能を使用しているときに価格表内の価格を管理する場合は、価格表からの価格を使用します。この割引では、価格表が定額商品プロモーションに割り当てられ、割り当てられた価格表から割引商品の定額が取得されます。この割引は定額割引と似ていますが、特定の定額が保管されるのではなく、セール価格表への参照が保持されます。

たとえば、シャツを 3 枚以上購入すると、SalesPriceBook の価格が適用され、シャツを 5 枚以上購入すると、ClearancePriceBook の価格が適用されるようにできます。

また、キャンペーンは顧客グループとも関連付けられます。顧客グループはプロモーションのインポート/エクスポートファイル内にあるものとして、または customergroup.xsd を使用して別に指定します。次に示すのは、promotion.xsd の内部の例です: 

<xsd:complexType name="CustomerGroups" mixed="false">
    <xsd:sequence>
     <xsd:element name="customer-group" type="CustomerGroup" minOccurs="0" maxOccurs="unbounded" />
    </xsd:sequence>
</xsd:complexType>
<xsd:complexType name="CustomerGroup" mixed="false">
    <xsd:attribute name="group-id" type="Generic.NonEmptyString.256" use="required" />
</xsd:complexType>

B2C Commerce のプロモーションクラス

すべてのプロモーションクラス (商品、注文、配送、ボーナス) で、プロモーション XML 要素のレベルで定義され、promotion.xsd で指定される特定の要素が共有されます。このトピックは、B2C Commerce に該当します。

主要なプロモーションクラス (商品、注文、配送) 間の違いは、プロモーションクラスの特定のルール要素のオプション選択として表されます。

<xsd:choice minOccurs="0" maxOccurs="1">
  <xsd:element name="product-promotion-rule" type="ProductPromotionRule" />
  <xsd:element name="shipping-promotion-rule" type="ShippingPromotionRule" />
  <xsd:element name="order-promotion-rule" type="OrderPromotionRule" />
</xsd:choice>

excluded-products要素を使用して、注文プロモーションを含む除外商品ルールをインポートおよびエクスポートします。

<!-- 注文プロモーション -->
<xsd:complexType name="OrderPromotionRule" mixed="false">
  <xsd:sequence>
   <!-- 新規要素-->
    <xsd:element name="excluded-products" type="ProductSpecification" minOccurs="0" maxOccurs="1" />
    <!-- 新規要素終了-->
 ...
    </xsd:sequence>
</xsd:complexType>

qualifying-products (対象商品) 要素は配送プロモーションと注文プロモーションでサポートされています。

    <order-promotion-rule>

      <excluded-products>

            <condition-group>
              <category-condition catalog-id="mainproduct-catalog">
                <category-id>GiftCerts</category-id>

個別プロモーションのエクスポート

Business Manager 内では、個別のプロモーションをインポートおよびエクスポートできます。このトピックは、B2C Commerce に該当します。

必要なエディション

使用可能なソリューション: B2C Commerce

エクスポート内では、キャンペーンのセット、プロモーションキャンペーンの割り当て、およびプロモーションは、指定した要素内の選択した値に限られます。

  1. サイト名 | マーチャントツール | オンラインマーケティング | インポート & エクスポートの順に選択します。
  2. インポート & エクスポートページのプロモーションセクションで、エクスポートをクリックします。
  3. プロモーションのエクスポート - プロモーションの選択ページで、プロモーションを ID、名前、またはクラスで検索します。
  4. プロモーションを 1 つまたは複数選択してから、次へ >> をクリックします。
  5. プロモーションのエクスポート - ステップ 2 で、エクスポートの設定ページから、検索結果をエクスポートするまたは選択項目のみをエクスポートするを選択します。
  6. エクスポートファイル名を指定します。
  7. 完了をクリックします。インポート & エクスポートページで、ファイルのエクスポートが処理されます。
  8. エクスポートされたファイルをクリックして表示します。

B2C Commerce のプロモーション商品ルールの属性条件

カタログをインポートする場合は、商品の属性を考慮する必要があります。このトピックは、B2C Commerce に該当します。

商品の属性には数値が使用できますが、商品の属性の値に使用できるのは文字列のみです。文字列は、サポートされているすべての属性タイプの最低の一般基準となります。インポートのロジックでは、メタデータ定義に基づいて演算子と属性の値が検証されます。これらの定義は、カタログのインポートにおけるカスタム商品属性のものと似ています。

検証ルールは以下のとおりです:

  • インポートロジックでは、XML スキーマ検証を使用して属性 ID、演算子、および値がチェックされます。空の文字列であってはなりません。
  • attribute-id の値は、Product (商品) システムオブジェクトタイプから属性定義を取得するために使用されます。そのような属性定義がない場合、条件はスキップされます。
  • 属性条件のタイプがサポートされていない場合、その条件はスキップされます。
  • 属性条件で値が 1 つだけサポートされている場合に複数の値が XML にある場合、警告がログされ、最初の値が使用されます。
  • サポートされている演算子のみが許可されます (値タイプ)。サポートされていない演算子が検出されると、属性条件はスキップされます。
  • 複数の値のうちのひとつが無効である場合、属性条件全体がスキップされます。

B2C Commerce での注文プロモーションのインポート/エクスポート

注文プロモーションは商品プロモーションより単純で、その XML スキーマは、記述済みの商品プロモーションスキーマのサブセットです。このトピックは、B2C Commerce に該当します。

B2C Commerce での配送プロモーションのインポート/エクスポート

配送プロモーションのインポート/エクスポート形式は注文プロモーションと似ています。大きな違いは、配送プロモーションでは割引配送方法を定義できることです。このトピックは、B2C Commerce に該当します。

次のサンプル XML は、対象商品の合計金額がそれぞれ $50、$100 を超える場合に、選択した配送方法が 50%、100% 割引になる階層化された配送プロモーションを示しています。

<promotion promotion-id="tiered-shipping-promo" campaign-id="c1">
  <enabled-flag>true</enabled-flag>
  <name xml:lang="x-default">Tiered ShippingPromotion</name>
  <shipping-promotion-rule>
    <shipping-methods>
      <method-id>ups-ground</method-id>
      <method-id>ups-air</method-id>
    </shipping-methods>
    <discounts condition-type="shipment-total">
      <discount>
       <threshold>50</threshold>
       <percentage>50</percentage>
      </discount>
      <discount>
       <threshold>100</threshold>
       <fixed-price>0</fixed-price>
      </discount>
    </discounts>
  </shipping-promotion-rule>
</promotion>

上記のプロモーションの例では、condition-type (条件タイプ) に "shipment-total" (配送合計) が指定されています。また、配送プロモーションで condition-type に "product-quantity" を指定することもできます。このようなプロモーションでは、特定数の対象商品が配送に含まれることが、割引適用の条件になります。このタイプのプロモーションの XML では、<discounted-methods>の前に<qualifying-products>セクションがあります。

B2C Commerce のプロモーション優先度ルール

買い物カゴに複数のプロモーションが適用される際に予想外の結果または希望しない結果が発生するのを防ぐために、プロモーション優先度ルールを使用します。これらのルールはハードコードされていますが、除外やランクなどの特定のプロモーション属性を調整して、プロモーションの適用を操作することができます。B2C Commerce で評価されないプロモーションの順序もあります。優先順位付けから生じた順序では、買い物客にとって最大の割引が常に提供されるわけではありません。このトピックは、B2C Commerce に該当します。

外部

B2C Commerce では、API を通じてプログラムによって入力され、システムでプロモーションによって表現されていないプロモーションは、Business Manager を通じて入力されたプロモーションの前に適用されます。

デフォルトの優先順序

プロモーションは、除外によって分類されます。除外のカテゴリは、以下の順序で処理されます。

  1. グローバル除外
  2. クラス除外の商品
  3. 除外なしの商品
  4. クラス除外の注文
  5. 除外なしの注文
    メモ 注文プロモーションは、商品合計に基づいて計算されます。注文プロモーションの適用後、注文レベルの割引は注文内のすべての商品で比例配分されます。
  6. クラス除外の配送
  7. 除外なしの配送

各カテゴリ内では、プロモーションは次の順番に優先順位付けされます。

  1. A/B テストの一部であるプロモーション (最下位のランクから開始)
  2. キャンペーンの一部であるプロモーション (最下位のランクから開始)
    メモ ランクは、オプションの数値属性です。この属性を指定して適用の優先順位を指定します。ランク付けされたプロモーションは、ランク付けされていないプロモーションの前に計算されます。ランクが指定されているプロモーションが 2 つある場合、ランクが低い方のプロモーションが先に計算されます。
  3. 割引タイプ
  4. 割引額
  5. ID のアルファベット順

割引のタイプと値

一般的に、プロモーションは以下の順番で割引タイプによって並べ替えられます。

  1. 定額
  2. 合計定額
  3. 無料
  4. 価格表の価格
  5. 割引金額
  6. 割引率
  7. ボーナス商品
  8. ボーナス商品の選択
  9. 無料商品配送
  10. 定額商品配送

同じ割引タイプのプロモーションが複数ある場合は、買い物客にとって割引額が最大になるプロモーションから順に評価されるように並べ替えられます。プロモーションは階層化して、複数の割引を提供できます。B2C Commerce で 2 つのプロモーションの優先度が割引によって決められる際には、各プロモーションの割引階層が事前評価され、(階層がある場合は) それぞれのプロモーションにどの階層が適用されるかが判断されます。たとえば、プロモーションに商品 PX を 3 点以上購入すると $5 割引、Product X を 5 点以上購入すると 30% 割引 という 2 つの階層があるとします。

買い物カゴには商品 X が 4 点入っています。低い方の割引階層 ($5 割引) は事前評価され、割引タイプは割引金額です。この事前評価処理の後、各プロモーションは 0 または 1 つの割引と関連付けられます。

次に、プロモーションは割引タイプごとに並べ替えられます。単純な割引は、定額、割引金額、割引率の順序で適用されます。2 つのプロモーションに同じ事前評価済み割引タイプが設定されている場合、買い物客にとってもっとも割引金額が大きくなるプロモーションの優先度が最も高くなります。たとえば、20% 割引のプロモーションは、10% 割引のプロモーションよりも優先度が高くなります。

メモ 定額 (または合計定額、または無料) プロモーションが複数ある場合、定額プロモーションは併用できないため、適用される順序を考慮する必要がなくなります。B2C Commerce には、対象となる定額プロモーションが複数ある場合、割引金額が最大になるプロモーションだけを適用する特別なロジックがあります。

最大適用数

最大適用数を設定すると、商品プロモーションが適用される順序と割引計算が行われるタイミングに影響します。最大適用数でプロモーションが適用される場合、最も金額の高い商品に最初に割引が適用され、続いて次に金額の高い商品に適用され、最大適用数の制限に達するまでこれが繰り返されます。

たとえば、以下の 2 つのプロモーションがあります。

  • プロモーション 1 - シャツを 3 枚購入するとシルクネクタイが無料 - 最大適用数 2
  • プロモーション 2 - シャツを 3 枚購入すると 20% オフ - 最大適用数 1

顧客が 1 枚 $100 のシャツ A を 2 枚、1 枚 $75 のシャツ B を 2 枚、1 枚 $50 のシャツ C を 2 枚、合計 6 枚のシャツを購入するとします。

プロモーション優先度ルールによって、割引率が最初に適用され、ボーナスが次に適用されるため、プロモーション 2 が最初に適用されます。この場合、買い物客にとって割引が最大になるようにもっとも高額のシャツから割引が行われます。

シャツ 3 枚 ($100 が 2 枚、$75 が 1 枚) が 20% オフで 1 回適用。
$275 - $55 (割引額) = $220

除外が「なし」の場合は、プロモーション 1 に基づいて、顧客はシルクネクタイも 2 本もらえます。除外が「クラス」または「グローバル」の場合は、プロモーション 1 は適用されません。

割引率は「X の購入で Y をゲット」の割引と対照的です。「X の購入で Y をゲット」の割引では、同じ商品が対象商品にも条件商品にもなれる場合、プロモーションでは価格に基いて商品が並べ替えられます。このプロモーションでは、価格が 1 番高い商品を使用して、条件を満たします。割引は、サイトのプロモーション環境設定に基づき、条件商品と価格が同じかそれより低いリスト内の次の商品に適用されます。「X の購入で Y をゲット」プロモーションを参照してください。

B2C Commerce のプロモーションの処理

プロモーションを処理する際、B2C Commerce では、顧客、ソースコード、クーポンコード商品などのパラメーターに基づいて、アクティブなプロモーションのリストが生成されます。このリストは、プロモーションを買い物カゴに適用するためだけに使用されるのではありません。対象となる可能性のあるプロモーションを商品詳細ページなどで買い物客に提示する目的でも使用されます。

B2C Commerce ではその後、買い物カゴの中身と優先度のルールに基づいて、適用されるプロモーションが識別されます。最後に、買い物カゴにプロモーションが適用されます。

メモ 買い物客の買い物カゴ内で何らかの情報が変更されるたびに、プロモーションが再計算されます。

デフォルトの並べ替え

デフォルトでは、プロモーションは割引タイプ別に並べ替えられます。複数のプロモーションが同じ割引タイプである場合は、割引金額によってランク順が決まり、金額が最も高いものが上になります。

B2C Commerce では複数階層プロモーションのどの割引が使用されたかを特定できません。このため、割引が適用されていない状態で、割引プランに基づいてすべてのプロモーションが事前に評価されます。これは近似的なアプローチですが、予測可能な並べ替え順序を提供します。ただし、最高位のプロモーションクラス/タイプの優先度ルールや割引タイプで並べ替えたからといって、ルールや割引階層が常に適用されるとは限りません。

B2C Commerce でのプロモーションのトラブルシューティング

プロモーションで問題が発生した場合、基本的なトラブルシューティングのヒントに従って、正しい仕様を満たしているかどうかを判断します。

ルールと買い物カゴの間を行き来するには、ストアフロントを 1 つのブラウザーウィンドウで開き、Business Manager を別のブラウザーウィンドウで開きます。

プロモーションを正しくテストするには、以下を確認します。

  • プロモーションの上位キャンペーンが現在の日付で有効になっている。
  • プロモーションが現在の日付で有効になっている。
  • プロモーションの対象となるための以下の条件を少なくとも 1 つ満たしている:
    • ターゲット顧客グループに属している。
    • プロモーションに関連付けられている有効なクーポンを提示している。
    • プロモーションに関連付けられている有効なソースコードを提示していて、かつ、そのソースコードがプロモーションに割り当てられており、有効になっている。
  • 商品プロモーションの場合:
    • 対象商品ルールの適切な数量または金額 (該当する場合) に一致する商品が選択されている。
    • 割引の対象となる商品が選択されている (該当する場合)。
  • 注文プロモーションの場合、買い物カゴの中にある商品が、商品割引適用後に、指定されているしきい値を超えている。ギフト券は商品合計に加算されません。
  • 配送プロモーションの場合は、以下を確認します:
    • 買い物カゴの中にある商品が、商品レベルおよび注文レベルの割引適用後に、指定されている商品しきい値を超えている。ギフト券は商品合計に加算されません。
    • 配送料の計算が行えるように、地域情報が指定されている。
    • 割引の対象となる配送方法が選択されている。
メモ 配送プロモーションは、(買い物カゴの商品合計金額ではなく) 配送商品合計金額に対して評価されます。

注

  • Everyone (すべての顧客) 以外の顧客グループに基いてテストしている場合は、使用している顧客ログインがターゲットグループのメンバーのものであることを確認します。
  • 1 回のみ使用できるクーポンを使ってテストしている場合は、テストに使用しているのと同じインスタンスでクーポンを作成します。
  • ソースコードを使用してテストしている場合は、プロモーション限定子リストでソースコードグループを検索します。使用している値が、選択したソースコードで有効であることを確認するには、文字列をソースコードテスト一致ボックスに入力します。サイト名 | マーチャントツール | オンラインマーケティング | ソースコード | コードの順に選択します。
  • 互換性とランキングの設定をテストしている場合は、ルールがどのように動作するかをチェックして意図する結果を確認します。

B2C Commerce プロモーションのプロモーションと課税

プロモーションを作成する場合は、税金の計算の影響を考慮します。このトピックは、B2C Commerce に該当します。

税率は次のように決定されます:

プロモーションクラス 税金
商品

関連する商品品目の税率を使用します。

たとえば、商品品目の税率が 5% の場合は、価格調整にも同じ税率が使用されます。
注文

買い物カゴ内のすべての商品品目からの、混在する税率を計算します。

たとえば、商品の最初の価格が $105 で、商品の割引価格が $100 だとします。すべての注文レベルの価格調整に対して設定される税率は (105 / 100) - 1 = 5% です。
配送

配送で標準の配送品目の税率を使用します。

たとえば、配送品目の標準税率が 3% に設定されている場合は、配送価格の調整にも同じ税率が使用されます。
メモ B2C Commerce では、これらのルールが CalculateCart.ds で実装されます。貴社固有のビジネス要件を満たすように、これらのルールをカスタマイズします。

たとえば、バックエンドシステムで注文レベルの割引を処理できない場合など、注文の品目に対して代替の税金計算方法が必要な場合は、品目の課税基準を参照してください。

  • 品目の課税基準
    B2C Commerce API (LineItem.updateTax ()) と Business Manager を使用して、注文内の品目に対する代替の税計算を構成します。この機能は、バックエンドシステムでは商品レベルの割引しか処理できないが、注文全体に税金を比例配分する必要がある品目を処理する場合に便利です。
  • プロモーションの比例配分
    プロモーションの割引は、実際の買い物プロセス中には各品目ごとに比例配分されることはありません。ただし B2C Commerce では、メモリ内で比例配分された値を計算し、リクエストに応じて呼び出し元に返す API が提供されています。比例配分された価格の情報は、通常すべての割引を品目として計上することを要求するバックエンドの注文管理や会計のシステムとの統合で使用されます。
  • プロモーションの比例配分のロジック
    比例配分を使用しない場合は、プロモーションは最後に 1 回計算されます。比例配分を使用すると、プロモーションは各品目に対して比例的に計算されます。比例配分は、商品の返品など、すでに完了した注文を処理する際に便利です。
  • B2C Commerce での税金の管理
    サイト課税方針は、サイト内で商品およびその他の価格をグロス価格で扱うか、ネット価格で扱うかを規定するものです。このトピックは、B2C Commerce に該当します。

Promotions ダッシュボード

B2C Commerce Reports & Dashboards の Promotions (プロモーション) ダッシュボードを使用して、プロモーションのパフォーマンスや個々のプロモーションの結果を評価します。

Promotions ダッシュボードには、もっともよく使用されたプロモーション、プロモーションの合計割引金額、プロモーションの組み合わせ、平均注文割引、プロモーションクラス別の使用、およびプロモーション割引による収益への影響に関するレポートが表示されます。

Most Used Promotions (もっともよく使用されたプロモーション)

このレポートでは、選択した日付範囲内に買い物客がプロモーションを使用した回数に基づいてプロモーションがランク付けされます。もっともよく使用されたプロモーションは、使用頻度が高い順にレポートにランキングされます。各項目には、プロモーションクラス、使用回数、およびプロモーションによって与えられた割引金額が含まれます。参考までに、注文プロモーションは顧客の注文に適用されます。商品プロモーションは個々の商品に適用されます。配送割引は注文の配送に適用されます。レポートを使用して、プロモーションの成功を評価します。たとえば、このレポートを使用して、レポート期間の初めに開始したプロモーションがもっともよく使用されたプロモーションに含まれているかどうかを確認します。

また、デバイス、顧客登録 (登録済みまたは未登録)、顧客タイプ (新規または再訪問)、チャネル、またはサイトごとに、上位 3 位にランキングされているプロモーションを確認できます。ランキングの表示を変更するには、ドロップダウンを使用します。

Most Used Coupons (もっともよく使用されたクーポン)

このレポートには、選択した日付範囲内でもっとも使用されたクーポンがリストされます。各項目には、関連付けられたプロモーション ID と使用回数が含まれます。

Total Promotion Discount (プロモーションの合計割引金額)

プロモーションの合計割引金額のグラフには、選択した期間におけるすべてのプロモーション割引の合計金額がプロットされます。また、各プロモーションクラスの割引金額もプロットされます。グラフの凡例の要素をクリックすると、個々の要素の表示/非表示を切り替えることができます。このグラフを使用して、プロモーション中に割引金額がどのように変化しているかを追跡します。

Promotion Combination (プロモーションの組み合わせ)

プロモーションの組み合わせレポートでは、顧客が 1 回の注文で 2 つのプロモーションを同時に使用した頻度がランキングされます。ランキングは、合計注文数に対する割合に基づいています。このレポートを使用して、顧客がプロモーションの組み合わせをどのように使用しているかを評価します。たとえば、顧客がすべての注文の 10% でプロモーション 1 とプロモーション 2 を一緒に使用しているとします。顧客はプロモーション 1 とプロモーション 3 をすべての注文の 5% で同時に使用しています。また、プロモーション 1 はもっともよく使用されたプロモーションでトップにランキングされています。

Average Order Discount (平均注文割引)

このレポートには、注文あたりの平均のプロモーション割引金額が表示されます。グラフには、選択した期間の各日付における金額が表示されます。

Uses by Promotion Class (プロモーションクラス別の使用)

このレポートには、プロモーションクラス、商品、注文、または配送別のプロモーションの割合が表示されます。このレポートを使用して、クラスタイプ別にプロモーションを分析します。

Revenue Impact by Promotion Discount (プロモーション割引による収益への影響)

このレポートには、各プロモーションの合計収益と合計割引金額が表示されます。グラフ上の点は、ダッシュボード期間中に使用されたプロモーションを表しています。このグラフを使用して、関連収益の創出につながった割引を評価します。

Promotions Detail ダッシュボード

B2C Commerce Reports & Dashboards の Promotion Detail (プロモーションの詳細) ダッシュボードには、個々のプロモーションのデータとレポートが表示されます。

このダッシュボードは、Promotions (プロモーション) ダッシュボードで行ったフィルター設定を継承します。必要に応じて、Promotion Detail ダッシュボードのフィルターを変更します。選択したプロモーションと日付範囲に応じてダッシュボードに次が表示されます。

Total Promotion Discount (プロモーションの合計割引金額)

このレポートには、プロモーション期間中の合計割引金額と平均割引金額が表示されます。毎日の割引金額の合計を表示するには、グラフでプロットされている特定の日の点にマウスを合わせます。

Top Product using the Promotion (プロモーションを使用した売れ筋商品)

このレポートでは、プロモーションを使用して購入された商品がランキングされます。たとえば、いくつかの異なる商品に適用されるプロモーションを実行しているとします。このレポートのランキングを使用して、プロモーションからもっとも恩恵を受けた商品の売上を決定できます。

このレポートでは、顧客が詳細プロモーションと別のプロモーションを同じ注文内で組み合わせた頻度がランキングされます。ランキングは、合計の注文数に対する割合で決定されます。たとえば、顧客が詳細プロモーションとプロモーション 2 をすべての注文の 8% で同時に使用しているとします。顧客はすべての注文の 5% で詳細プロモーションとプロモーション 3 を一緒に使用しています。プロモーション 2 は詳細プロモーションとより頻繁に組み合わせて使用されているため、プロモーション 3 よりも上位にランキングされます。

Average Promotion Discount (平均プロモーション割引)

このグラフには、レポート期間において 1 日あたり販売 1 件ごとに適用された、詳細プロモーションによる平均割引額がプロットされます。このデータを使用して、詳細プロモーションが販売あたりの収益に与えた影響を追跡します。

Revenue Impact (収益への影響)

このグラフには、レポート期間において、プロモーションを含む販売によって生み出された合計収益がプロットされます。このデータを使用して、プロモーションによって生じた売上収益を追跡します。

  • アクティブなソースコードを使用した合計注文数: アクティブなソースコードを少なくとも 1 つ使用して行われた注文数。
  • 非アクティブなソースコードを使用した合計注文数: 非アクティブなソースコードを少なくとも 1 つ使用して行われた注文数。

Order Conversion Results (注文コンバージョン結果)

このレポートには、注文コンバージョンがソースコードの分類ごとに表示されます。注文コンバージョンとは、少なくとも 1 つの注文を作成したソースコード訪問の割合です。

このレポートでは、セッション内のすべてのソースコードに対する注文が関連付けられます。アフィリエイトリンクには複数のソースコードが関連付けられている場合があるため、注文合計の総計が実際の合計よりも大きくなる可能性があります。たとえば、1 回の訪問に 2 つのソースコードと 1 つの注文がある場合、各ソースコードの注文がソースコードコンバージョンとして追跡されます。

1 つのセッションに、無効や非アクティブなどの異なるステータスをもつソースコードが複数存在する場合、システムはこれらのステータスそれぞれについて 1 回の訪問を報告します。

アクティブなソースコードを使用した注文コンバージョン: アクティブなソースコードのセッション中に行われた注文。このデータを使用して、アクティブなソースコードのコンバージョンが成功しているかどうかを確認します。

非アクティブなソースコードを使用した注文コンバージョン: 非アクティブなソースコードのセッション中に行われた注文。このカテゴリの結果が大きい場合は、非アクティブなソースコードが引き続き使用されていることを示します。

無効なソースコードを使用した注文コンバージョン: 無効なソースコードのセッション中に行われた注文。このカテゴリの値が大きい場合は、意図しないソースコードがアクティブ化されたことを示します。たとえば、無効なソースコードのアクティブ化が注文につながっていることが多い場合は、更新または削除が必要な古いソースコードがあることが考えられます。

Conversion of Source Codes (ソースコードのコンバージョン)

ソースコードのコンバージョンレポートは、少なくとも 1 つの注文を作成したソースコードのアクティブ化に関するメトリクスを提供します。レポートを「アクティブ」、「非アクティブ」、または「無効」のソースコードでフィルタリングします。このレポートは、ソースコードグループを注文と関連付けて、以下のメトリクスをレポートします。

  • グループ: 注文に関連付けられているソースコードが属する、ソースコードグループ。
  • サイト: リダイレクトリンクのサイト。たとえば、サイトのプロモーションページです。
  • アクティブ化: グループに割り当てられているソースコードがアクティブ化された回数。
  • Orders (注文数): すべてのソースコードセッションで作成された注文の数。
  • 商品合計額: すべてのソースコードセッションで注文された商品の数。
  • 平均使用あたりの商品合計額: ソースコードセッションあたりの平均売上額。
  • 平均注文ごとの平均商品額: ソースコードのセッション中に行われた各注文の平均金額。
  • 注文あたりの商品数: 各ソースコードセッションで注文された商品の数。
  • 注文コンバージョン率: 少なくとも 1 つの注文につながったソースコードセッションの割合。

プロモーションの比例配分

プロモーションの割引は、実際の買い物プロセス中には各品目ごとに比例配分されることはありません。ただし B2C Commerce では、メモリ内で比例配分された値を計算し、リクエストに応じて呼び出し元に返す API が提供されています。比例配分された価格の情報は、通常すべての割引を品目として計上することを要求するバックエンドの注文管理や会計のシステムとの統合で使用されます。

商品プロモーション

商品プロモーションは 2 つの方法で比例配分できます。

金額と割引率による商品プロモーションを比例配分できます。プロモーションを作成する際にオプションを選択するだけです。選択しないと、商品のプロモーションは、複数の品目の合計に割引が不均等に適用される場合にのみ比例配分されます。たとえば、SKU1 と SKU2 を合計 20 ドルで購入する場合です。品目に個々に影響する割引は比例配分されません。たとえば、注文内のすべてのシャツが 10% 引きなどの場合です。

注文プロモーション

API は、商品割引と前の注文割引の後の調整済みのユニット価格に基づいて、各対象ユニットに対する比例配分された値を計算します。注文プロモーションで除外されていない各品目に対し、1 つの商品レベルの価格調整が計算されます。

税金

商品品目の税金を計算する場合、API では、商品プロモーションと比例配分された注文プロモーションが適用された後の調整済みの価格に、商品の税率が適用されます。注文プロモーションが比例配分されているかどうかにかかわらず、注文の合計は同じです。ただし、API では各品目に税率が適用されるため、丸めの誤差により、注文プロモーションを比例配分した場合に税金がやや高くなることがあります。

品目の課税基準機能を使用して、注文全体で税金を比例配分し、丸めによる誤差を排除します。

配送プロモーション

配送プロモーションの対象を決定するために使用される商品合計金額は、商品プロモーションと比例配分された注文プロモーションが適用された後の、配送内のすべての商品品目の合計です。比例配分の順序は、特に分割配送の注文に影響を与えます。たとえば、注文が配送プロモーションをトリガーするために必要な金額に達しても、比例配分を適用した後に個々の配送が対象とならない場合があります。

Promotions ダッシュボードのメトリクスの定義

B2C Commerce Reports & Dashboards の Promotions (プロモーション) ダッシュボードを使用して、プロモーションのパフォーマンスや個々のプロモーションの結果を評価します。Promotions ダッシュボードには、もっともよく使用されたプロモーション、プロモーションの合計割引金額、プロモーションの組み合わせ、平均注文割引、プロモーションクラス別の使用、およびプロモーション割引による収益への影響に関するレポートが表示されます。

ビジネスメトリクス

Promosions ダッシュボードの各セクションは、さまざまなビジネス指標を追跡し、ダッシュボード属性として表示します。

B2C Commerce でのプロモーションの追跡ツールを使用したプロモーションのテスト

プロモーション追跡ツールを使用して、プロモーションをストアフロントに公開する前にテストします。特定の買い物カゴにどのプロモーションを適用できるかを確認できます。プロモーションが買い物カゴに適用されない場合は、その理由を参照してください。

必要なエディション

使用可能なソリューション: B2C Commerce

Storefront Toolkit は Staging (ステージング) 環境と Development (開発) 環境でのみ使用できるため、Production (本番) 環境でプロモーションをテストすることはできません。追跡ツールは買い物カゴの評価にのみ機能します。商品詳細ページや商品一覧ページでは機能しません。

  1. テストしたいプロモーションを有効にして、アクティブなキャンペーンに割り当ててください。
    たとえば、メンズ衣料品を少なくとも 200 ドル購入した場合に、注文を 20% 割引するプロモーションがあるとします。
  2. ストアフロントを起動します。
  3. 買い物カゴに商品を追加して、買い物カゴを開きます。
  4. プロモーションの追跡を有効にします。
    1. プレビュー設定ツールアイコンをクリックします。
    2. プロモーションの追跡を有効にするを選択して、プロモーション追跡 ID を入力します。
      プロモーション追跡 ID を使用して、リクエストログのプロモーションログメッセージを追跡します。
    3. プレビューをクリックします。
      ログメッセージがリクエストログに保存されます。メッセージは、買い物カゴに適用されたプロモーションと、評価されたが適用されなかったプロモーションを示します。
  5. リクエストログを開くには、リクエストログアイコンをクリックします。
  6. リクエストログでプロモーション追跡 ID を探します。
    多くのプロモーションがある環境では、リクエストログウィンドウにリクエストログ全体が表示されない場合があります。ログをテキストエディターにコピーして、エディターでプロモーション追跡 ID を検索することをお勧めします。
    たとえば、プロモーションテスト ID に TraceTest と入力した場合は、TraceTest を検索します。
  7. 結果を読み取り可能な形式に変換するには、プロモーションテスト情報を含むブロックを任意の JSON パーサーにコピーします。
    プロモーションは次のようにレポートされます。
    • applicablePromotions: たとえば、時刻、顧客グループの割り当て、またはソースコードのエントリなど、コンテキストと買い物カゴ内の商品に基づいて買い物客が対象となるプロモーション。
    • qualifiedPromotions: プロモーションがランキングと除外のアルゴリズムで処理される前に、買い物カゴ内の対象商品に基づいて買い物客が対象となるプロモーション。
    • appliedPromotions: プロモーションがランキングと除外のアルゴリズムで処理された後に、買い物カゴに適用されたプロモーション。
    たとえば、このログメッセージを JSON パーサーで開くと、200 ドルのしいき値が満たされなかったために、20 パーセント引きの注文プロモーションが適用されなかったことが明らかになります。

    プロモーションの条件が満たされた場合は、JSON パーサーに割引が適用されたことを示すメッセージが表示されます。

B2C Commerce の配送プロモーション

配送プロモーションでは、注文の配送料に割引が適用されます。配送プロモーションは、プロモーションの最大適用数を指定しない限り、通常注文内のすべての配送に適用されます。このトピックは、B2C Commerce に該当します。

最大適用数を設定すると、金額が最も大きいものから順に、指定した数の配送にプロモーションが適用されます。すべての配送注文は、設定した特定の配送方法にのみ適用されます。

カテゴリ、ブランド、ID、価格、在庫、およびその他の属性に基づいて配送プロモーションを指定します。

商品に関連する配送割引は、商品プロモーションと見なされます。また、商品固有の配送料 (定額または追加料金) も構成できます。

プロモーションタイプ 説明 利用可能な割引
配送対象商品の金額に基づく

このプロモーションは、顧客が 1 つの配送で指定した金額を購入した場合にトリガーされます。たとえば、顧客が $100 の買い物をした場合に、翌日配送を 10% 割引にすることができます。

購入金額は、商品と注文のプロモーションを適用した後に、各配送に対して計算されます。ギフト券、税金、配送料は、配送の合計金額に含められません。

  • 割引金額

  • 無料
配送対象商品の数に基づく

このプロモーションは、顧客が 1 つの配送で指定した数の商品を購入した場合にトリガーされます。たとえば、顧客がシャツを 3 枚購入した場合に、翌日配送を $10 割引することができます。

この割引は、指定した数の対象商品が配送に含まれている場合にのみ適用されます。

  • 定額
  • 無料

配送プロモーションルール

  • 商品が、複数の配送料グループのメンバーの場合、配送料が最も低いものが優先されます。
  • 定額配送料および追加配送料の両方が商品に定義されている場合、定額配送料が優先されます。
  • マスター商品に定義されている配送料は、このマスター商品のすべてのバリエーション商品にも定義されています。
  • 配送料は、バンドルされた商品品目またはオプション品目には適用されません。
  • 別のプロモーションから与えられたボーナス商品の金額は、配送の対象や割引を計算する際には考慮されません。ボーナス商品の配送料は引き続き適用されます。買い物カゴの残りには、適切な配送割引が適用されます。
メモ 品目レベルの定額配送料をもつ品目だけが買い物カゴに入っている場合、最下層の標準配送料も注文に適用されます。これを回避するため、各配送料テーブルに、"0 ～ 0.01" の注文金額階層を作成し、配送料 $0.00 を指定します。

ソースコードパターンの使用

ソースコードはパターンに従っていますか? 1 つのソースコードグループに 100 以上のソースコードが必要な場合は、個別のソースコードの代わりに、ソースコードパターンを使用することをお勧めします。

ソースコードグループはパターンによって定義されるグループです。システムがソースコードを処理する際にパターンが一致すれば、ソースコードグループは認識され、アクティブになります。すべてのソースコードを明示的に追加する必要はありません。コードの追加はルールというより例外であり、数百件のソースコードに限定されます。ソースコードグループのパターンは認識目的で使用されますが、実際のコードはセッションとともに保持および保管されます。

メモ ソースコードがパターンに従っていない場合は、ソースコードソリューションを再実装することを考慮してください。

たとえば、複数のソースコードと一連のセールカタログがあるとします。各セールカタログに対し 1 つのソースコードが指定されています。ストアフロントにはこれらのセールカタログがすべて含まれており、すべてのソースコードをストアフロントの 1 つのアウトレットエリアに誘導したいとします。以下の操作を行うことができます:

  1. たとえば、すべてのカタログを含む SALE というソースコードグループを作成して、SPRING* から始まるソースコード仕様を作成します。
  2. SPRING* の仕様を使用して、すべての春物セールカタログを表す「SPRING」を名前に含むソースコード (SPRINGOUTDOOR、SPRINGHOME、SPRINGWOMENS など) をすべて含めます。
  3. リダイレクト タブで、ソースコードグループ「SALE」をストアフロントの「アウトレット」セクションのカテゴリ ID と関連付けます。

別の方法として、同じソースコードグループ「SALE」を作成し、その中に個別のソースコードを含んだ一連のソースコード仕様を作成することもできます。以下がその例です:

  • ソースコードグループ: SALE
  • ソースコード仕様: 
    OUTDOOR[N1..1000], HOME[N1..1000] and WOMENS[N1..1000]
    この仕様には、ソースコード OUTDOOR1 ～ OUTDOOR1000 などが含まれます。

すべてのサイトのクーポンコードの合計数が 100 万を超えると、Staging (ステージング) から Production (本番) へのコードのレプリケーション速度が大幅に低下します。システムにより生成されたクーポンコードでは、クーポンコードが多くなってもレプリケーションにかかる時間が長くなることはありません。10,000 のコードをもつクーポンは、システムにより生成されたコードよりも良い結果をもたらします。

Business Manager で新しいクーポンコードを設定します。既存のクーポンコードは、最初に生成した後は変更されません。既存のクーポンコードグループに対して追加のコードを生成すると、そのコードがグループに追加されます。したがって、グループに 100 万個のコードがあり、さらに 100,000 個生成された場合、グループには合計 110 万個のコードがあります。

システム生成コードを増やすためのガイドライン

システム生成コードは、何十億もの一意の組み合わせをもたらす可能性があります。これらのコードが最初に登録される際には、各クーポン ID には一定の制限があります。コードの長さを長くしたり、既存のクーポン ID の接頭辞を変更したりしても、この制限がリセットされたり、新しいコードプールが提供されたりすることはありません。システムで生成されるクーポンコードの数を増やすには、以下のガイドラインを確認してください。

  • (推奨)新しいクーポン ID を指定して、既存のキャンペーンまたはプロモーションに割り当てます。新しい内部カウンタが、新しいコード プールとともに開始されます。
  • 既存のクーポン ID を使用して、クーポンコードの数を増やします。
  • クーポンの接頭辞を変更したり、コードに数字を追加したりしないでください。これらの操作を行うと、既存のクーポンコードが無効になります。
  • B2C Commerce のシステム生成クーポンコードの構成
    コードを自動生成するには、まずクーポンコードの環境設定を行い、次にコード設定を構成します。コードを生成したら、クーポンの使用条件を指定します。

B2C Commerce のプロモーション限定子としてのクーポン

B2C Commerce ストアフロントプロモーションの対象となるユーザーを決定するために、クーポンを使用できます。クーポンは、B2C Commerce、B2C Commerce の外部のソース、カスタム定義されたクーポンを使用して生成できます。また、外部の Eメールマーケティングシステムとの間でクーポンコードをインポートまたはエクスポートできます。

クーポンの作成は、プロモーションやキャンペーンとは無関係です。クーポンをキャンペーンまたはプロモーションに割り当て、プロモーションまたはキャンペーンの構成に基づいてクーポンの有効期間と有効期限を管理します。

クーポンをキャンペーンに割り当てると、そのキャンペーン内のすべてのプロモーションでそのクーポンが継承されます。クーポンの継承を停止したり、クーポンの仕様をプロモーションレベルで拡張したりできます。

B2C Commerce には、次の 3 種類のクーポンがあります。

クーポンタイプ 定義 ソース
マーチャントが定義した単一コード 1つのクーポンにつき1つのクーポンコードを複数回使用できます。 これは Business Manager で管理します。
マーチャントが定義した複数コード クーポンごとのコードリストで、通常は外部のシステムからインポートされます。各コードを複数回使用できます。 これは Business Manager で管理します。
システムにより生成 B2C Commerce によってコードが自動的に生成されます。 エクスポートまたはスクリプティング API によって発行されます。形式は Business Manager で管理します。

1 つのクーポンに対して、複数のクーポンコードが存在する可能性があります。買い物客は注文手続き時にクーポンコードを入力すると、プロモーションの対象となります。そのコードが認証済みコードのリストと照合され、適切な場合は、プロモーションと割引が有効になります。1 つのクーポンが 1 つまたは複数のプロモーションの対象になることがあります。

単一コードのクーポン

単一コードのクーポンは、以下の目的で構成します。

  • 1 つのクーポンにコードを 1 つだけ割り当て、使用回数の制限を 1 に指定して発行する。

    たとえば、店舗を頻繁に利用する顧客へのお礼として発行します。

  • 1 つのクーポンにコードを 1 つだけ割り当て、使用回数を特定数または無制限に指定して発行する (使用数を空白にすると無制限に使用可)。

    たとえば、Eメールプロモーションでは、使用回数を指定する代わりに、クーポンがアクティブである期間を制限します。

複数コードのクーポン

複数コードのクーポンは、以下の目的で構成します:

  • 1 つのクーポンに複数のコードを割り当て、使用回数の制限を 1 に指定して発行する。

    たとえば、ロイヤル顧客のグループにクーポンコードを 1 つ送信し、各顧客が 1 回使用できるようにする場合などです。

  • 1 つのクーポンに複数のコードを割り当て、使用回数を特定数または無制限に指定して発行する (使用数を空白にすると無制限に使用可)。

    たとえば、"友人と家族" キャンペーンで、使用制限のないコードを各従業員に 1 つ送信するとします。従業員はそのコードを家族や友人に転送でき、どの従業員がサイトに最も多くの収益をもたらしたかを確認できます。

システムにより生成されるクーポン

買い物客は必ずしも利用可能なすべてのクーポンを利用するわけではないため、事前にすべてのコードを生成するのは非効率的です。単一コードまたは複数コードのクーポンを使用して、必要に応じてコードを生成できます。多数のコードを公開するには、システムにより生成されたクーポンを使用して生成を自動化します。

システムにより生成されるクーポンコードは、AFDR-3FE3-6HUJ-45ERなどの形式に従います

必要に応じて、SUMMER などの接頭辞を指定します。たとえば、SUMMER-AFDR-3FE3-6HUJ-45ERです。

B2C Commerce では、顧客が送信したコードが有効かどうかを判断するためにアルゴリズムが使用されます。B2C Commerce がシステム生成コードを発行すると、単一のクーポンコードが返され、使用可能なコードのセットから削除されます。コードが発行されても、特定の買い物客用にそのコードが予約されたり、今後のコードの使用が制限されたりするわけではありません。

B2C Commerce のプロモーション限定子としてのソースコード

B2C Commerce を使用して、顧客が有効なソースコードを提供したときに価格表をアクティブにし、ストアフロントリダイレクトを実装し、プロモーションを有効にするルールを作成します。

ソースコードを使用して、顧客を特別なページにリダイレクトするカスタム URL を作成します。ソースコードは一般的に、顧客がアフィリエイト Web サイトのリダイレクトリンクをクリックするか、印刷されたカタログに掲載されている値を使用して手動でソースコードを入力することによって渡されます。ソースコードを使用して、特別なランディングページ、特集商品の詳細ページ、カテゴリリスト、および URL に顧客をダイレクトできます。

ソースコードグループには、ストアフロントで一般的な方法で処理されるコードを 1 つまたは複数含めることができます。ソースコードグループを構成して、1 つまたは複数のソースコード、または複数のコードに一致するパターンを含めます。複数のルールを同じセットのルールにマッピングします。ソースコードごとに結果を追跡しながら、ソースコードグループの一部としてルールを定義します。1 つまたは複数のソースコードをキャンペーンに割り当てると、そのキャンペーン内のすべてのプロモーションでこれらのソースコードが使用されます。

顧客は、アフィリエイトによって提供されたソースコード URL を使用して、マーチャントのサイトにアクセスできます。その場合、アフィリエイトのソースコードが有効になります。この顧客がサイトを去り、別のソースコード URL からサイトに戻ってきた場合、前のソースコードは新しいソースコードで置き換えられます。ソースコードを置換することで、マーチャントは、提供する割引とアフィリエイトへの支払いの両方について、全体的な金銭的負担を制限できます。

メモ ソースコードグループはそれぞれ独自の有効期間と有効フラグをもちます。ソースコードグループを限定子として使用する場合は、グループを有効にし、グループの日付範囲がプロモーションスケジュールに含まれていることを確認してください。

顧客は、アクティブなソースコードグループの一部である個別のソースコードを提示できます。この場合、その顧客はこのソースコードグループに関連付けられているすべてのアクティブなプロモーションの対象になります。セッション中に一度にアクティブにできるソースコードは 1 つのみです。ソースコードを使用して、顧客が一度にアクセスできるプロモーションの数およびグループ化を管理できます。

URL のソースコードの処理

B2C Commerce でソースコードが URL パラメーターとして受け取られると、コードが検証されます。そのコードが存在するかどうか、また、上位ソースコードグループの有効ステータス、開始日、終了日が検証されます。

  • ソースコードがアクティブかつ有効な場合、現在のユーザーセッションと Cookie 内のソースコードが B2C Commerce に保管されます。
  • ソースコードがアクティブではなく有効でもない場合、ソースコードは無視され、通常のランディングページが表示されます。

URL 内でソースコードが渡されなかった場合で、Cookie が有効になっている場合は、ストアフロントは保管された Cookie からソースコードを読み込もうとします。Cookie からソースコードを読み込める場合、そのソースコードは検証されます。B2C Commerce でソースコード Cookie が保存される期間は、特定のソースコードグループに設定された Cookie 期間によって異なります。ソースコードグループに Cookie 継続期間が設定されていない場合は、Business Manager のサイト環境設定で設定された Cookie 継続期間が使用されます。

複数のアクティブソースコードグループにソースコードが含まれている場合は、作成日が最も新しいグループが使用されます。

顧客が入力するソースコードの処理

商品ページまたは買い物カゴに顧客がソースコードを入力できるようにするには、B2C Commerce API を使用してソースコードを検証します。有効なソースコードがある場合、B2C Commerce では以下の処理が行われます:

  • そのソースコードグループを限定子として使用するすべてのプロモーションを有効にする
  • または、選択された価格表を有効にする
  • または、商品、カテゴリ、ページ、または URL に顧客をリダイレクトする

同じソースコードグループに含まれるソースコードは同様に処理されます。URL に 2 つ目のソースコードパラメーターが含まれる場合は、最初のパラメーターのみが評価され、2 つ目は無視されます。以下に、2 つ目のソースコードパラメーターの例を示します。

http://user.dw.demandware.net/on/demandware.store/Sites-YourShopHere-Site/​default/​SourceCodeRedirect-Start?src=ACME&src=KATJA

1 度にアクティブにできるソースコードグループは 1 つのみであるため、別のソースコードグループに属するソースコードは非アクティブと見なされます。これらのソースコードは同様にマッピングできますが、マッピング先は異なる商品、カテゴリ、ページ、URL になります。

  • B2C Commerce のソースコードグループの定義
    ソースコードグループは、Business Manager で、またはインポートによって定義します。Business Manager では、ソースコードグループは 1 つまたは複数のソースコードやソースコード仕様を表わすことができます。
  • B2C Commerce でのソースコードをもつ 2 つ目の URL の追加
    B2C ストアフロントの 2 つのセットの受信 URL を同じターゲットにマッピングします。
  • B2C Commerce のソースコードの例
    一般的にソースコードは、顧客によってアフィリエイト Web サイト上のリダイレクトリンクを通じて提供されます。
  • B2C Commerce のソースコードのベストプラクティス
    B2C Commerce のストアフロントでソースコードを使用する場合は、以下のベストプラクティスに従ってください。
  • B2C Commerce のソースコード対象プロモーションレポート
    Promotions Source Code (プロモーションソースコード) ダッシュボードは、ソースコードによって対象となるユーザーが決定されるプロモーションの効果を理解するうえで役に立ちます。このトピックは、B2C Commerce に該当します。
  • B2C Commerce での URL からのソースコードを使用したパイプライン開始ノードの呼び出し
    B2C Commerce ストアフロントでプロセスを開始するには、URL からパイプライン開始ノードを呼び出します。ソースコードが有効な場合、この URL は顧客を 2 つの目的地のいずれかにナビゲートします。有効なソースコードを有効にする必要があります。この機能は、B2C Commerce に該当します。
  • B2C Commerce のソースコードをもつ URL の動的マッピング
    受信 URL を動的にマッピングして、特定のページに移動します。

B2C ストアフロントのクーポン使用の追跡と管理

クーポンの使用データを表示して、誰がいつクーポンを使用するかを追跡および管理します。すべてのクーポンの使用データを検索および分析したり、クーポン固有の使用データを表示したりできます。また、使用されたクーポンから買い物客の Eメールアドレスを削除できます。使用は注文に関連付けられています。買い物客が注文を削除すると、使用済みクーポンは削除されます。クーポンとコードを削除しても、使用済みのクーポンには影響しません。

Staging (ステージング) と Production (本番) の間でクーポンの使用データをレプリケートすることはできません。B2C Commerce では、使用データは本番データとして扱われます。Staging (ステージング) でクーポンの動作をテストできますが、制限と追跡に関して実際に強制力のある使用レコードが作成されるのは Production (本番) のみです。

メモ クーポンの使用は Staging (ステージング) インスタンスでテストし、リアルタイムクーポンは Production (本番) インスタンスで管理します。
  1. サイト名 | マーチャントツール | オンラインマーケティング | クーポンを選択します。
  2. 使用済みクーポンの表示をクリックします。
  3. [使用] ページで、次のタスクを実行します。
    • すべてのクーポンの使用データを表示し、ヘッダーでエントリを並べ替えます。
    • クーポン ID をクリックすると、特定のクーポンの使用データが表示されます。
    • 使用をコード、注文番号、時刻、または顧客 (Eメールアドレスで表される) 別に表示します。
    クーポンの合計使用回数が更新されるまでに、最大 1 時間の遅延が生じる場合があります。
  4. 過去の使用データから買い物客の Eメールアドレスを削除するには、「Eメールを破棄する」をクリックします。
    すべてのクーポンの使用で Eメールアドレスがマスクされ、削除した Eメールアドレスに関連付けられている使用済みクーポンを検索できなくなります。
