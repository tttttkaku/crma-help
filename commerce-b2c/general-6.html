Log Center 表示の変更

デフォルトでは、検索を実行すると Log Center に詳細ビューで問題のリストが表示されます。また、リストをコンパクトビューで表示することもできます。

ヒストグラムには、一定の時間間隔で記録された問題の数がグラフで表示されます。初期の時間間隔は 15 分です。この間隔は時間フィルターに応じて変わります。集計間隔の最小値は 1 分です。「All」(すべて) は、すべてのログの合計数を表します。「hits」(ヒット数) は、フィルターとキーワード検索の結果の集計数です。

  1. 詳細ビューとコンパクトビューを切り替えるには、表示オプションの横にある適切なアイコンをクリックします。
  2. 各ページに表示される問題の数を表示するには、「ヒット数/ページ」の横の数字をクリックします。
  3. 問題のページをさらに表示するには、Older (古い) およびNewer (新しい) をクリックします。
  4. 表示するカウント数を変更するには、All (すべて) またはHits (ヒット数) をクリックします。
  5. フィルターを再適用するには、必要な値を選択してShow filtered results (フィルターされた結果を表示) をクリックします。

製品の準備状況の監視

マーチャントツールのホームページまたは商品リストから、カタログ内の商品の準備状況に関するインサイトを表示します。

必要なエディション

使用可能なソリューション: B2C Commerce

製品名や説明などのローカライズされた属性の場合、準備状況の分析情報では既定のサイト地域情報が考慮されます。

Business Manager でアプリケーションランチャーをクリックし、マーチャントツール | ホームを選択します。[Product Readiness (商品の準備状況)] で、ストアフロント対応になっていないカタログ内の商品、またはカテゴリが割り当てられていない商品を表示します。ストアフロント対応でない商品の絞り込まれたリストに移動するには、[ 詳細を表示 ] をクリックします。

または、ストアフロント対応でない商品のリストを表示するには、マーチャントツール | ホームに移動し、商品フィールドで「準備完了」でフィルターして、「false」を選択します。次に、適用をクリックします。ストアフロント対応でない商品が表示されます。

商品リストの「準備完了」列には、カタログ内の各商品の準備状況が表示されます。

システムは、サイトカタログの各商品に対して以下のチェックを実行します。

  • 名前。商品名が追加されます。
  • 画像。少なくとも 1 つの商品画像が割り当てられています。
  • オンラインステータス。商品がストアフロントに表示されます。
  • 在庫ステータス。商品は在庫で入手可能です。
  • 価格の入手可能性。価格は商品に指定されています。
  • 検索ステータス。商品が検索インデックスに含められます。
  • 簡単な説明。製品の簡単な説明が利用可能です。
  • 商品詳細。詳細な説明が利用可能です。

準備スコアにカーソルを合わせると、準備チェックの詳細が表示されます。欠落しているデータがある場合は、「商品詳細の編集」を参照して、対応するフィールドを追加または更新します。

デフォルトでは、準備完了列は B2C Commerce 26.4 リリース以降で作成された商品リストに含まれています。古い製品リストを使用していて、準備完了列を含める場合は、列ピッカーを使用して追加します。B2C Commerce の商品リストを参照してください。

製品の準備状況を分析するためのジョブは、アプリケーションランチャー | の管理ジョブ | から表示します。ジョブの実行時間は、カタログのサイズと店舗数によって異なります。

  • sfcc-calculate-product-readinessです。価格フィルターと在庫フィルターのデータを計算します。
  • sfcc-calculate-product-insight です。[準備完了] フィルターのデータを計算します。

B2C Commerce における PayPal での Venmo の使用

Salesforce Payments は、エクスプレスおよび複数ステップチェックアウト方法として、Venmo をサポートします。Venmo では、クレジットカード、デビットカード、銀行振替、または Venmo の資金銀行にリンクしたデジタルウォレットの支払オプションを買い物客に提供できます。Salesforce Reference Architecture (SFRA) ストアフロントで Venmo を使用するには、Salesforce Payments で PayPal インテグレーションが行わていることが必要です。この機能は、B2C Commerce に該当します。

Venmo のアクティブ化

Venmo は、米国の通貨を使用する米国拠点のマーチャントと買い物客のみが使用できます。Venmo は、米国を拠点とする買い物客と米国の通貨を受け付ける任意の支払ゾーンで使用できます。支払ゾーンで米国以外を本拠とする買い物客と米国以外の通貨を受け入れている場合は、Venmo はこれらの買い物客に対して支払サービスのオプションとして提供されません。

支払ゾーンですでに PayPal がアクティブな場合、選択した PayPal 注文手続き方法 (エクスプレスまたは複数ステップ) に対し Venmo はデフォルトで選択されています。支払オプションとして Venmo を提供したくない場合は、支払ゾーンの注文手続き構成で Venmo の選択を解除します。

購入者の体験

Venmo の購入者体験は、モバイルとデスクトップの買い物客で異なります。

デスクトップ ⁻ 買い物客が支払オプションとして Venmo を選択すると、QR コードが表示されます。購入者は QR コードをスキャンし、Venmo アプリを使用して支払を承認し、完了します。買い物客は Venmo アプリでトランザクションを完了し、ストアフロントの注文の確認ページに戻ります。

モバイル ⁻ 買い物客が支払オプションとして Venmo を選択すると、Venmo アプリがモバイルデバイスで開きます。買い物客は Venmo アプリで支払を完了し、ストアフロントの注文の確認ページに戻ります。モバイルデバイスの買い物客は、iOS では Safari、Android では Chrome を使用する必要があります。また、Venmo アプリがインストールされていることが必要です。

B2C Commerce でのオープンリダイレクト攻撃

Web アプリケーションがユーザー入力をリダイレクト先として信頼すると、攻撃者はこの入力を使用してユーザーを自分がコントロールする Web サイトにリダイレクトし、ユーザーの情報を盗むことができます。

オープンリダイレクト攻撃の仕組み

攻撃は以下のように行われます。

  1. 攻撃者は買い物客が、myshop.com/?next=evil.com などのように、信頼できそうに見えるリダイレクトパラメーターをもつリンクを訪問するように仕向けます。
  2. myshop.com サイトはユーザーにログインページを返します。
  3. ユーザーが myshop.com のユーザー名とパスワードを入力します。
  4. ユーザーが sometrustedshop.com にログインします。
  5. ブラウザーがユーザーを evil.com に転送およびリダイレクトします。
  6. 攻撃者がユーザーの認証情報を盗みます。

オープンリダイレクト攻撃の緩和方法

Internet Store Markup Language (ISML) テンプレート <isredirect> 要素を使用する場合、またはユーザーが入力したデータを直接的または間接的にdw.system.Response.redirectに提供する場合は、この脆弱性を考慮してください。

以下のベストプラクティスに従ってください。

  • リダイレクトを避けます。
  • ローカルリダイレクトを強制します。
  • ユーザーが URL を移動先として入力できないようにします。
  • ユーザー入力を避けられない場合は、URL を検証します。
  • すべての移動先の入力を、実際の URL ではなく、値にマッピングします。
  • 入力をサニタイズするために、信頼できる URL のリストを作成します。
  • ユーザーにリダイレクトについて通知し、リンクをクリックして確認するように求めます。

B2C Commerce のページのメタタグルール

ページのメタタグは、HTML ドキュメントで使用され、Web ページに関する構造化されたデータを提供します。一般的なタグとしては、タイトル、ロボット、説明、Open Graph のタグなどのソーシャルタグがあります。このトピックは、B2C Commerce に該当します。

メタタグはページ自体には表示されませんが、ページのコンテンツを記述するページのコードに含まれます。ページのメタタグルールをカテゴリに設定できます。ページのメタタグルールの検索は継承スキームに従っており、ルール構成の作業を最小限に抑えることができます。ルートカテゴリのルールは、すべての下位カテゴリおよび割り当てられている商品内に表示されます。ルールはまず、地域情報フォールバックの前に、言語設定の定義に従って現在の地域情報コンテキスト内で継承されます。

PayPal 資金の支払

PayPal が実装された Salesforce Payments では、キャプチャと資金の支払が即時に行われます。たとえば、買い物客が買い物カゴの注文手続きを完了し、注文が承認されると、その買い物客の支払は即時にキャプチャされ、マーチャントに支払われます。

PayPal による即時のキャプチャと支払のプロセスは、次のフローに従います。

  1. 買い物客が買い物カゴの注文手続きを完了する。
  2. 注文ステータスが承認済みに設定される。
  3. PayPal が注文をキャプチャします。
  4. PayPal は、購入者のアカウントから販売者の PayPal アカウントに資金を送金します。

Page Designer ビジュアルエディターのヒント

以下のヒントは顧客のフィードバックから集められたもので、ビジュアルエディターを使用して Page Designer ページを作成する場合に知っておくと便利です。このトピックは、B2C Commerce に該当します。

  • Page Designer コンポーネントに含めることのできるコンポーネントの最大数

    ページとコンポーネントは、コンテンツアセットにも適用されるコンテンツクォータに数えられます。ページでは最大 5 レベルまでのネスト深度が許可されます。最大ネスト深度の他には、制限はありません。メンテナンスを容易にするために、ページはあまり大きくしないでください。

  • コンポーネントのドラッグアンドドロップ

    一部の領域とレイアウトは、特定のコンポーネントのみを受け入れます。コンポーネントが動かない場合は、ターゲットの領域がそのタイプのコンポーネントをサポートしていないことが考えられます。詳細については、デベロッパーに問い合わせてください。

  • 同じページを複数のサイトに一度に公開する

    ページを作成すると、ページは共有ライブラリを通じて非公開モードですべてのサイトと自動的に共有されます。公開済みまたは非公開のステータスはサイトごとに独立しており、手動で調整する必要があります。

  • 商品タイルでのバリエーション商品の使用

    バリエーション商品を商品タイルに表示することができます。Site Genesis と Salesforce Reference Architecture (SFRA) のマスター、バリアント、および商品グループは、Page Designer 内で基本的に同じです。

  • 特定の地域情報でコンポーネントを非表示にする

    顧客グループでは、特定のユーザーに対してコンポーネントを勧めることができます。どの顧客グループがコンポーネントを表示できるかを決定するには、ページまたはコンポーネントのターゲット設定を使用します。顧客グループを作成して、特定の地域を含めたり除外したりします。また、顧客グループのバインドをサポートするプロモーションなど、その他の機能でも顧客グループによるルールを使用します。

  • Page Designer と Einstein Product Recommendations

    SFRA には、Einstein による推奨項目を提供する Page Designer コンポーネントが含まれており、希望する Recommender を選択することもできます。

    メモ この特定の機能の Business Manager カートリッジリストで、正しい Business Manager カートリッジを割り当ててください。
  • コンポーネントでのコンテンツアセットの使用

    コンポーネントはコンテンツアセットのバインドをサポートします。コンテンツを直接入力する代わりに、コンポーネント属性をコンテンツアセット属性にバインドします。このアプローチは、複数のページでコンテンツを再利用し、1 か所から更新する場合に使用します。詳細については、コンテンツアセットへのコンポーネントのバインドを参照してください。

これらの B2C Commerce プレイブックは、幅広いトピックをカバーし、買い物客の体験を向上させるための出発点としてデータと事実を活用するのに役立ちます。

  • Improve Average Order Value (AOV) (平均注文価格 (AOV) の向上)

    平均注文価格 (AOV) を、販売の傾向を評価し、マーチャンダイジングとプロモーションの戦略を測定するためのメトリクスとして使用する方法を学習します。

  • Buy Online Pick up In Store (BOPIS) (オンライン購入、店舗受け取り (BOPIS))

    買い物客がオンラインで購入し、最寄りの店舗で受け取ることのできる機能を有効にします。

  • Improve the Checkout Experience (注文手続きの体験の改善)

    注文手続きの体験をレビューおよび最適化するための戦略とツールについて理解します。

  • Improve Conversion Rate (コンバージョン率の向上)

    コンバージョンの傾向の分析方法を理解し、この鍵となるメトリクスを増加させる戦略を決定します。

  • Improve Product Discovery (商品発見の向上)

    コンバージョンと収益を促進し、サイト訪問者が探しているものを見つけられるようにする戦略について学びます。

  • Increase Site Traffic (サイトトラフィックの増加)

    良質のトラフィックを引きつけ、サイトのスピードを最適化するために重要な要素について学習します。

eコマースの不正行為の防止

eコマースの不正行為は、増加しつつあるセキュリティ上の課題です。サイバー攻撃者は盗んだ認証情報のリストを使用して、ユーザーアカウントにアクセスし、承認されていないトランザクションを行うために総当たり攻撃を行います。

ほとんどの攻撃はシンプルで、自動化されています。攻撃者は悪意をもつボットを使用して、盗んだクレジットカードデータをマーチャントのストアフロントでテストします。Web スクレーパーは自動化されたソフトウェアを使用して、ターゲットの Web サイトから情報を収集します。スクレーパーはコンテンツを盗み、Web インフラストラクチャに負荷をかけます。これによって Web サイトの検索エンジン最適化 (SEO) ランキングが下がることがあります。

パスワードの使い回しによるアカウントの乗っ取り、消費者がフィッシング攻撃に引っかかってしまった場合、なりすまし犯罪、トライアンギュレーションスキームなど、多くのタイプの不正行為があるため、不正注文への対応は困難です。不正行為と不正な注文を低減するには、不正行為防止サービスを利用するか、LINK テクノロジーパートナープログラムのパートナーに問い合わせてください。

買い物客が不正行為や不正な注文について報告した場合は、まず必ず不正行為対策プロバイダーに確認してください。不正行為を効果的に防止するには、総合的なリスク管理プロセスの実装が必要になります。

B2C Commerce では、顧客は以下の 3 種類の方法でプロモーションの資格を獲得します:

限定子 使用法
顧客グループ 割り当てられた顧客グループのメンバーは、特定のキャンペーンに含まれるすべてのプロモーションの対象になります。例外は、プロモーションの構成時に、顧客グループを限定子への割り当てから解除した場合です。
ソースコード

ソースコードを使用して、特定の期間に顧客がどのプロモーションを利用できるかを管理します。顧客は、アフィリエイト Web サイトのリダイレクトリンクから、または印刷されたカタログに掲載されている値を手動で入力して、ソースコードを提供できます。B2C Commerce では、そのソースコードに関連付けられている特別価格とプロモーションがトリガーされます。

単回使用クーポンと複数回使用クーポンを使用して、通常 Eメールによるマーケティングキャンペーンの一環としてクーポンを受け取る顧客向けに特別プロモーションをアクティブにします。

  • 単回使用クーポンは一度しか使用できず、顧客はそのクーポンを誰かに渡したり、インターネットに投稿したりすることはできません。このため、クーポン使用者をより厳格に管理できます。
  • 複数回使用クーポンは、合計使用回数に制限して、特定のキャンペーンのマーケティング予算を超えないようにします。一般的な例は、在庫一掃セール などのキャンペーンを行う場合です。

キャンペーン内に、スケジュールおよび限定子を構成します。すべての体験はデフォルトで、構成されている限定子を継承します。この継承は非アクティブにできますが、上書きはできません。体験条件を拡大するには、体験が含まれているキャンペーン内で使用できない限定子を割り当てます。たとえば、キャンペーンにソースコードグループ A と B が限定子として含まれており、そのキャンペーンに割り当てられたプロモーションに、ソースコードグループ A と B が限定子として継承されるとします。これらのソースコードを使用する場合は、他のソースコードも選択してください。これらのソースコードを使用しない場合は、ソースコードを限定子として使用することはできません。

プロモーション体験では、デフォルトで「クーポンをプロモーション限定子として使用しますか? 」が選択されています。この設定は、プロモーションが上位キャンペーンからクーポンを継承することを示します。

  • 有効になっている場合、プロモーションでクーポン限定子が使用されます。キャンペーンから継承されたクーポンの選択を解除することはできません。追加のみ可能です。
  • 無効になっている場合、クーポンは限定子として使用されません。

限定子は暗黙の OR ステートメントです。限定子のうち 1 つだけを満たしていれば、顧客が割引対象になります。たとえば、ソースコードと顧客グループを限定子として設定すると、そのソースコードを持っているか、またはその顧客グループのメンバーであれば、顧客は割引を受けることができます。

B2C Commerce でのリカバリおよびロールバック

インポートおよびエクスポート処理中に問題を検出し、エラーから復旧します。このトピックは、B2C Commerce に該当します。

ジョブの問題の検出

Business Manager を使用して、ジョブが指定時間を超えて実行された場合に管理者に Eメールが送信されるように構成します。

ジョブに問題が発生し、ログエントリが作成されることがありますが、問題が発生した場合でもインポートは停止しません。これらのエラーが重大な場合は、インポートを検出して停止する処理をインポートパイプラインに追加します。インポートログを定期的に確認して問題を特定することは、一般的に推奨される方法です。

ジョブの問題からのリカバリ

ジョブを再度実行する前に、ジョブロックを解除してください。ロックを解除するには、インスタンスを停止して再起動します。詳細については、Control Center ドキュメンテーションを参照してください。

ネットワークの問題からのリカバリ

インスタンスがダウンしたことが原因でジョブが中断された場合は、フィードを再度インポートします。標準のインポート機能ではオブジェクトごとにコミットが行われるため、データベースが破損することはありません。

インポートの途中でジョブが中断された場合は、正常にインポートされたデータ、および変更または削除されなかった古いデータがデータベースに含まれた状態になります。カタログインポートが完了しなかった場合は、検索インデックスとカタログとの同期がとれなくなってしまうため、検索機能が期待どおりに動作しなくなります。

フィードデータに問題があると思われる場合は、以下のいずれかの方法を使用します:

リカバリの方法 説明
別のインスタンスからデータをレプリケートする Production (本番) へのインポートに問題があり、ロールバックできる正しいデータが Staging (ステージング) にある場合は、この方法が最も便利です。
バックエンドシステムで生成された新しいフィードをインポートする これはリカバリのための最も一般的な方法です。通常はバックエンドシステムでデータを修正し、新しいフィードを生成します。

Production (本番) インスタンスフィードのロールバックのカスタマイズ

Production (本番) インスタンスでは、データレプリケーションによってほとんどのデータが Staging (ステージング) からインスタンスに転送されます。ただし、在庫データや価格データなど、頻繁にインポートするデータは、Production (本番) に直接インポートすることもあります。ステージングと同様、ジョブが何らかの理由で中断された場合、カタログは不完全なインポートデータと従来からあるデータが含まれる状態になっていることがあります。たとえば、在庫のインポートが完了しなかった場合、現在は入手できなくなっている商品が販売されてしまう可能性があります。

フィード全体をインポートするか何もインポートしないようにするには、カスタムパイプラインを作成します。このパイプラインは、オブジェクトをカプセル化して 1 回のトランザクションでインポートし、一度にコミットします。ただし、コードの作成とデバッグが難しくなる可能性があるため、このアプローチは不要であり、お勧めできません。

コミットのサイズの制約により、作成するカスタムパイプラインが制限されます。1 度に 1,000 個を超えるオブジェクトをコミットすることはできません。B2C Commerce のトランザクションでは 1 度に 1,000 個を超えるオブジェクトを変更することはできません。また、これらのオブジェクトをすべて変更しているときに他のユーザーがそのうちの 1 つを手作業で変更すると、コミットに失敗することがあります。1 回のコミットでこれより多い数のオブジェクトを処理しようとすると、コミットに失敗する可能性が高くなります。

B2C Commerce での古くなったオブジェクトの削除

古くなったオブジェクトを削除する方法は、バックエンドシステムのデータに Business Manager の属性を追加してエンリッチ化するかどうかによって異なります。また、削除するビジネスオブジェクトのタイプによっても異なります。B2C Commerce では一般的に、データがエンリッチ化されているかどうかにかかわらず、削除するオブジェクトのフィードを作成し、削除モードを使用してインポートすることによって、すべてのタイプのオブジェクトを安全に削除することをお勧めします。

カタログオブジェクトの削除

ほとんどのマーチャントは商品オブジェクトをバックエンドフィードからインポートし、次に Business Manager で URL やその他の Web 固有の属性をそのオブジェクトに追加してエンリッチ化します。この場合、通常のインポートモードはマージです。ただし、このモードでは、データベースからオブジェクトを削除することはできません。このため、商品は削除するまでデータベースに残ります。

不要なカタログオブジェクトの削除には、次のオプションがあります:

  • DELETE フィード - 削除するオブジェクトを含むフィードを作成し、削除モードを使用してインポートします。このメカニズムは、すべてのタイプのオブジェクトで使用でき、エンリッチデータには影響を与えないので、推奨される方法です。
  • カタログフィードの削除の構文 - カタログフィードの場合のみ、バックエンドシステムで必要な構文を作成できる場合は、フィード自体で削除するオブジェクトを指定します。この構文は他のタイプのフィードでは使用できません。
  • パイプレットのカタログ削除 - ImportCatalog パイプレットでは、ImportConfiguration パラメーターで以下の構成オプションがサポートされています。
    オプション 説明 
    key=deleteCatalog; value=true | false
    		 インポート前にカタログを削除します。このメカニズムは、カタログを空にするための高パフォーマンスの方法として使用します。ただしこのオプションを使用すると Business Manager でエンリッチ化された属性が削除されるため、エンリッチ化されていないオブジェクトに対してのみ使用してください。 
    key=replaceCustomAttributes; value=true| false
    		更新モードまたはマージモードを使用した場合に、インポート前にカスタム属性を削除します。このメカニズムを使用して古いカスタム属性を自動的に削除しますが、置換モードよりも高速です。 
    key=replaceCustomAttributesExclusions; value=attrID1, attrID2, ...
    		 置換、マージ、および更新モードで商品カスタム属性をインポートしても、リストされている属性は置換されません。このアプローチは、replaceCustomAttributes オプションとともに使用されます。
  • Business Manager オブジェクトの削除 - Business Manager でオブジェクトを削除します。このアプローチは、少数のオブジェクトを削除する場合以外はお勧めしません。

インポートの前に、カタログ全体を削除するか、すべてのカスタム属性を削除するかを選択します。ただし、フィードのインポート中はインスタンスには完全なデータが含まれません。フィードのインポートが正常に完了しなかった場合には、正常にインポートされたデータのみがインスタンスのデータベースに含まれます。このアプローチは、Production (本番) システムではお勧めしません。ただし、シーズンごとに異なるカタログがあり、すべての商品を入れ替える場合は、この方法が便利なこともあります。また、Staging (ステージング) に複数のカタログがある場合もこの戦略を利用できます。たとえば、外部ベンダーからのデータのみを読み込んだカタログ 1 つを削除するとします。また、保存したいカスタムストアフロントカタログがもう 1 つあるとします。2 つ目のカタログについては、更新を実行することで、Staging (ステージング) ですでに行われた変更を保持できます。

ジョブフローの範囲

各フローは範囲をもっています。範囲は、組織全体、すべてのストアフロントサイト、特定のストアフロントサイト、または Open Commerce API (OCAPI) Data API を使用して実行時にジョブに渡すサイトのいずれかになります。CreateSitemap などの一部のジョブステップは、サイトのコンテキストでのみ実行できます。また、ExecuteDataReplication などのジョブステップは、組織のコンテキストでのみ実行できます。ステップでサポートされていない範囲をもつフローにジョブステップを割り当てようとすると、ステップにエラーが表示されます。このトピックは、B2C Commerce に該当します。

ジョブフローを作成する際には、次の範囲オプションのいずれかを選択します。

  • 組織: フローはインスタンスに対して実行されます。
  • すべてのストアフロントサイト: フローは、ジョブの実行時に使用可能なすべてのストアフロントサイトで実行されます。フローは、Business Manager サイト、またはステータスが削除対象となっているサイトでは実行されません。
  • 特定のサイト: フローは選択したストアフロントサイトでのみ実行されます。
  • サイトパラメーター: フローは OCAPI Data API を使用して渡すサイトで実行されます。ジョブは Business Manager から実行することはできず、ジョブを自動的に実行するようにスケジュールすることはできません。Business Manager で「ただちに実行」ボタンとスケジュールのオプションは無効になります。このオプションを選択すると、SiteScope パラメーターが空の値でジョブに追加されます。OCAPI Data API を使用して、SiteScope に 1 つまたは複数の特定のサイト、あるいはすべてのストアフロントサイトを指定します。

複数のサイトに対して順次実行するフローを構成すると、並列実行を行う十分なシステムリソースがあれば、B2C Commerce は異なるサイトに対してフローを並列で実行します。

B2C Commerce での機密事項の保存

機密事項の保存と使用は、買い物客の情報のセキュリティを万全にするために、デベロッパーが行うもっとも重要なアクションの 1 つです。機密事項には以下のものがあり、また、これには限られません。

  • リモートサービスへの認証に使用される認証情報。たとえば、ユーザー名とパスワード、API トークン、アクセストークン、セッション ID など。
  • 機密データの暗号化と復号化に使用される秘密の鍵。たとえば、秘密鍵や対称鍵など。

さまざまな方法でデータの漏洩を防止します。まず、どうしても必要な場合を除き、フォームの機密データをログに記録したり、その他の方法で保存したりしないようにします。データを維持しなければ、盗難されることはありません。機密データを保存する必要がある場合は、できるだけ早く破棄し、必ず暗号化します。クレジットカードデータの場合は、必ず PCI データセキュリティ基準 (DSS) に準拠したトークナイゼーションまたは切り捨てを使用してください。

Salesforce B2C Commerce に機密事項を安全に保存するには、以下の API を使用します。

  • サービス認証情報
  • 秘密鍵
  • カスタムオブジェクト属性

サービス認証情報

各 Web サービスに対し、フレームワークではサービスの構成、サービスプロフィールの構成、およびサービス認証情報の構成が必要です。これらの構成は Business Manager で作成および管理します。

サービス認証情報は B2C Commerce API から dw.svc.ServiceCredential オブジェクトとしてアクセス可能です。これらは読み取り専用です。ストアフロントリクエストに返したり、ログに書き込んだりしないでください。

秘密鍵

暗号化鍵と証明書は、暗号化と復号化、認証、署名などの重要なリソースです。これらの鍵と証明書を管理するには、専用の Business Manager ウィザードを使用します。これらは、スクリプト API で CertificateRef クラスと KeyRef クラスを使用してアクセスできます。

カスタムオブジェクト属性

B2C Commerce のオブジェクトモデルを拡張するには、カスタムオブジェクトを使用します。属性、各属性のフィールド、およびカスタムオブジェクトタイプのプロパティをカスタマイズします。

機密情報を処理するカスタムオブジェクト属性では、PASSWORD タイプを使用します。

B2C Commerce のセキュアなログ

Salesforce B2C Commerce のログは安全に保存されており、site_admin 役割または developer 役割のユーザーのみがアクセスできます。ログは Web インターフェイスまたは WebDAV を通じてアクセスできます。ログに記録する情報のタイプを決定する際には、これらを考慮してください。

B2C Commerce のセキュアなストレージ

Salesforce B2C Commerce は多くのタイプの機密情報を保存しており、もっとも重要なものとしてはクレジットカード情報があります。

  • B2C Commerce でのクレジットカードの暗号化
    B2C Commerce では、クレジットカード暗号化、鍵の生成、および再暗号化が自動化されています。B2C Commerce は、PCI 監査を受けているマーチャントのために、このプロセスをモニターする機能を提供しています。
  • B2C Commerce の秘密鍵と証明書
    さまざまなシナリオで、サードパーティの証明書と秘密鍵をインスタンスの鍵ストアにインポートする必要が生じます。鍵ストアは複数のエントリを保存できます。各エントリはタイプ PrivateKeyEntry または TrustedCertificateEntry とすることができます。これは java.security.KeyStore で使用される用語と同様です。

  • サーバーでレンダリングされる HTML にキー コンテンツが存在することを確認します。AI クローラーと一部の従来の検索エンジン クローラーは JavaScript を実行しないため、クライアント側でのみ読み込まれるコンテンツは表示されません。商品名、説明、および価格が最初の HTML 応答に表示されることを確認します。
  • HTML タグを正しく使用する。Google でも他の検索エンジンでも、スタイル効果を作成するためのコードではなく、重要な情報を表示するために使用される h1 や見出しタグなど、意味のあるコードの使用が好まれます。見出しやリスト、その他の HTML タグを使用してテキストの重要性を伝えたり CSS に沿ったスタイルにしたりすると、コードが読みやすくなり、SEO ランキングの上昇につながります。
  • 全般的に短く、意味のある URL を構築する。
  • 正規 URL の追加を考慮する。

SEO でありがちな落とし穴を参照してください。

コンテンツ作成に関するベストプラクティス

CSS ファイルを使用すると、一貫性のある洗練されたルック アンド フィールが得られます。CSS とクリーンなタグ付けには、以下で説明する SEO の利点もあります。ツールバーでは span style を使用して書式が設定されますが、これは SEO には最適ではありません。コンテンツのタグ付け方法に関する次の推奨事項は、SEO 結果を改善し、よりクリーンで管理しやすいコードを作成するのに役立ちます。

コンテンツのコーディングには、次の推奨事項を使用してください。

  • コンテンツの概観は、HTML タグを選択するのではなく CSS を使用して設定します。HTML タグには、コンテンツの概観よりも、その重要性が反映されているべきです。外部検索エンジンはタグを使用してページにとって最も重要であるコンテンツを判断するため、意味が伝わる方法でタグを使用していれば、SEO 結果が改善されます。
  • タグは以下のように使用します:
    タグ 使用法
    b 強調するテキスト。しかしその重要性は他のテキストとさほど変わりません。
    cite 書籍のタイトルまたはその他の公開メディア。
    em 異なる口調やニュアンスを表すテキスト。スクリーンリーダーやその他の解説デバイスで強調されます。これにより、目の不自由な方々や、ストアフロントへアクセスするためにスクリーンリーダーが必要な方々の満足度が改善されます。
    i 異なる口調やニュアンスを表すテキスト。しかしその重要性は他のテキストとさほど変わりません。たとえば、外国語のフレーズ、植物や動物の学名など。
    strong 強調するテキスト。他のテキストと比べて重要性が高い。たとえば、セール名、商品名、ブランド名、ページのキーワードなど。

AI 検出可能性のベスト プラクティス

AI を活用した検索および応答エンジンがストアフロントをクロールして、買い物客への応答を生成します。次のプラクティスは、これらのシステムによってコンテンツが正確に解釈され、引用されるようにするのに役立ちます。

  • 関連ページ間の内部クロスリンク (たとえば、商品ページからそのカテゴリ、関連商品、購入ガイドへのリンク) を使用して、クローラーがコンテンツを見つけ、コンテキスト化できるようにします。
  • FAQやQ&Aのセクションを商品ページやカテゴリページに追加することを検討してください。AI モデルは、ユーザーのクエリに自然にマッピングされるため、直接的な質問と回答のペアとして構造化されたコンテンツを好みます。

  • robots.txt構成を見直して、検出可能にしたいコンテンツに AI クローラーがアクセスできることを確認します。「Business Manager を使用した Robots.txt ファイルの生成」を参照してください。

B2C Commerce サイトの favicon.ico の設定

B2C Commerce の favicon.ico は、ショートカットアイコン、Web サイトアイコン、タブアイコン、URL アイコン、またはブックマークアイコンとも呼ばれ、特定の Web サイトまたは Web ページに関連付けられた 1 つ以上の小さなアイコンを含むファイルです。favicon.icoを使用して、ブラウザーのアドレスバー、ブックマークリスト内のサイト名の横、およびブラウザーのタブにサイトを表示します。

サイトは 2 つの場所でfavicon.icoを提供し、クライアントはどちらを使用するかを決定できます。

  • HTML 内の <head> タグ内の <link> タグで指定された URL - 複数の可能性あり (2010 年以降)
  • ルートディレクトリから提供。たとえば、https://www.site.com/favicon.ico など (1999 年以降)

B2C Commerce では、ルートディレクトリからのカスタムファイルはサポートされていません。サイトでfavicon.icoを使用するために、B2C Commerce は指定したファイルをカートリッジのディレクトリに配置します。そのファイルがデフォルトの favicon.ico になります。

  1. B2C Commerce で favicon.ico を設定するには、favicon.ico ファイルをカートリッジ内のこの場所に配置します: */cartridge/static/default/images/favicon.ico
  2. ファイルがサイトのカートリッジパスにあることを確認し、コードバージョンをアクティブ化します。
    これで、ファイルはサイトのルートディレクトリでデフォルトのアイコンとして提供されるようになります。

Salesforce Reference Architecture (SFRA) (Storefront Reference Architecture) リファレンスサイトでは <head> メタタグが実装されていますが、ルートから提供されるよく知られたfavicon.icoは実装していません。カスタム実装は両方を行います。

Log Center での異常検出機能の設定

異常なログパターンを特定し、必要に応じて、異常がアラートのしきい値に達したときにアラートを送信します。Log Center は受信したログデータを継続的に分析し、学習したベースライン動作と比較します。データがベースラインから逸脱し、しきい値に達すると、Log Center は異常にフラグを立てます。このトピックは、B2C Commerce に該当します。

  1. Business Manager でLog Centerを開きます。
  2. [Anomaly Detection (異常検出)] タブ (1) で、[ Anomaly Detector Configurations (異常検出器の構成 )] をクリックします。
  3. 異常検出機能を構成します。
    1. [Anomaly Detector Configurations ] プラスアイコンをクリックします。
    2. 名前と説明を入力します。
    3. ディテクタを実行するレルムを選択します。
    4. Log Center で異常をチェックする頻度を指定するには、検出時間間隔を設定します。
      モニターの種類 分
      重要な監視 5 分または 10 分
      一般的な監視 15 分または 20 分
      トレンド 30 分
    5. 検出器が異常にフラグを立てる易度を制御するには、検出感度スケールを設定します。不要なアラートを減らして強力な検出を行うには、5 から 8 までの値から始めます。値が小さいほど、大きな偏差のみが検出されます。値を大きくすると、より微妙なパターンを検出できますが、より多くの調整が必要になる場合があります。
  4. 検出を開始するには、[リアルタイムの異常検出を有効にする]を選択します。ディテクタを停止するには、このオプションの選択を解除します。
  5. (オプション)異常通知を受信するには、[アラートを有効にする]を選択し、しきい値、間隔、電子メール アドレスを設定します。異常が条件を満たすと、Log Center から受信者に Eメール通知が送信されます。
  6. (オプション)関連するログに検出を集中させるには、フィルターを構成します。変更内容を保存します。

店舗ショッピング

「店舗ショッピング」機能では、B2C 店舗の所在地と店舗レベルの在庫に基づいて検索結果が絞り込まれます。買い物客は、店舗を選択して、その店舗で購入可能な商品を見つけたり、商品を検索してから、その店舗の所在地を使用して検索を絞り込んだりできます。買い物客は商品一覧ページをフィルターし、「店舗ショッピング」機能を使用して特定の店舗の商品を検索できます。

たとえば、熱心なゲーマーである Adam は、最新の Call of Duty をプレイしたいと思っています。オンラインゲームを販売している B2C ストアをチェックし、最寄りの実店舗を見つけてゲームを検索し、買い物カゴに追加します。その後、店舗での受け取りを選択し、すぐにゲームを始めることができます。

「店舗ショッピング」では、買い物客は店舗の在庫リストに基づいて検索結果を取得します。「店舗ショッピング」では、最大 5,000 万件の在庫レコードにインデックスを付けることができます。在庫レコードの正確な数は、店舗数と各店舗の SKU 数によって異なります。たとえば、マーチャントは、各店舗に 50,000 SKU を持つ 1,000 店舗、または各店舗に 500,000 SKU を持つ 100 店舗をインデックス化できます。

API リクエストで、ilids URL パラメーターを使用して、最大 10 個の店舗在庫リスト ID を取得します。

  • URL パラメーターに複数の店舗在庫リスト ID が含まれている場合、商品の表示は OR 条件で決定されます。たとえば、「店舗 A または 店舗 B または 店舗 C」で購入可能なすべての商品を表示します。
  • URL パラメーターに有効な店舗在庫リスト ID と無効な店舗在庫リスト ID が含まれている場合、B2C Commerce は無効な在庫リスト ID を無視し、有効な在庫リストを使用して検索結果をフィルターします。たとえば、検索パラメーターがilids=valid1|valid2|invalidの場合、B2C Commerce は valid1 と valid2 の店舗在庫リストで検索またはカテゴリをフィルターします。
  • URL パラメーターに無効な店舗在庫リスト ID が含まれている場合は、サイトの在庫リストが取得されるか、空の検索結果が表示されます。たとえば、検索パラメーターが&ilids=invalidの場合、B2C Commerce はサイトの在庫リストで検索またはカテゴリをフィルターするか、空の検索結果を表示します。
  • 管理者は、「店舗ショッピング」の在庫のフォールバック機能スイッチを使用して、店舗の在庫リストがない場合のフォールバック動作を制御できます。
    • このスイッチを有効にすると、システムはサイトの在庫を取得します。
    • このスイッチを無効にすると、サイトには空の検索結果が表示されます。B2C Commerce での機能スイッチ (トグル) の設定を参照してください。

「店舗ショッピング」の制限事項

  • インスタンスごとに最大 10 個のサイトストアで Shop the Store を有効にします。
  • 買い物客は在庫データに基づいて商品を並べ替えることはできません。たとえば、買い物客は売れ行きの速い商品順に検索結果を並べ替えることはできません。ただし、買い物客は価格やブランドに基づいて商品を並べ替えることができます。買い物客に最高のショッピング体験を提供するには、入手可能性に関連しない属性を使って並べ替えルールを作成します。B2C Commerce の並べ替えルールを参照してください。
  • Einstein の商品の推奨と検索の提案は、選択した店舗の入手可能性ステータスでフィルターされません。買い物客が店舗検索から店舗を選択すると、一部の推奨商品はオンラインで購入できますが、その店舗では購入できません。
  • 「注文可能商品のみ表示」の検索環境設定では、入手できない商品をサイトレベルの検索結果に表示するかどうかを制御します。ただし、「店舗ショッピング」が有効になっている場合、検索結果ではサイトと店舗の両方の在庫が考慮されます。

    たとえば、買い物客が 2 つの商品バリエーションがあるメンズレザージャケットを検索するとします。ブラックはオンラインで入手可能で、ブラウンはオンラインでは在庫切れですが XYZ 店舗では入手可能です。

    「店舗ショッピング」機能が有効になっていて、XYZ 店舗の在庫をチェックするように構成されている場合、検索結果には、オンラインで入手可能なブラックと、XYZ 店舗で入手可能なブラウンの両方の商品バリエーションが表示されます。

SKU カバレッジ

SKU カバレッジは、マスター商品の販売可能なバリアントの合計数とバリアント数との正規化された比率です。SKU カバレッジは、在庫リストを共有するすべてのサイトで同じです。つまり、これはサイト固有の値です。このトピックは、B2C Commerce に該当します。

SKU カバレッジは:

  • 比率値は 0.0 ～ 1.0 です。
  • Salesforce B2C Commerce では、この値がリアルタイムで計算されます
  • インポートまたはエクスポートできません。
  • ステージングされていないため、値はインスタンスに固有です。

標準商品

  • 商品の在庫がある場合は、SKUCoverage (SKU カバレッジ) = 1.0
  • 商品の在庫がない場合は、SKUCoverage (SKU カバレッジ) = 0.0

マスター商品

マスター商品の SKU カバレッジは、表示されているすべての商品バリエーションの平均と同じです。SKU カバレッジは売上数の影響を受けるため、シンプルな商品の販売可能数量 (ATS) の計算が 100 で、売上数が 10 の場合、skuCoverage = 0.9 になります。

SKUCoverage(mp) = SUM(SKUCoverage(vpX)) / X

この場合:

  • mp がマスター商品
  • vpX がマスター商品のオンラインバリエーション
  • X がオンラインバリエーション商品の数

B2C Commerce の明細書記述子の設定

明細書記述子は、クレジットカードトランザクションの課金の説明を銀行やクレジットカードのネットワークに提供します。Salesforce Payments によって、買い物客の銀行またはカードの明細書に説明が追加され、課金の発生元が特定されます。買い物客が課金の発生元を知ることで、支払の異議申し立てや支払拒否のリクエストを減らすことができます。Salesforce Payments では次の 3 つの明細書記述子の設定がサポートされています。

Stripe の短縮形の記述子

Salesforce Payments Stripe アカウントは、Stripe の短縮形の記述子をサポートしています。短縮形の記述子の値は Stripe ダッシュボードで入力します。Salesforce Payments は、短縮形の記述子を Stripe Payment Intents API の statement_descriptor の値として使用します。買い物客がクレジットカードのトランザクションを完了すると、Commerce Payments は明細書記述子の値を買い物客の銀行またはカードのネットワークに渡します。この方法では、レルムで同じ Stripe マーチャントアカウント ID を使用するサイトに対し、サイト固有の記述子を指定することはできません。

メモ Stripe の一部のアプリケーションでは、Stripe の短縮形 (接頭辞) の値と動的 (接尾辞) の値を使用して、動的な明細書記述子が生成されます。Salesforce Payments では、サイトレベルの記述子としての Stripe 動的 (接尾辞) 値はサポートされていません。

サイト固有の記述子

サイト固有の顧客明細書の記述子を使用して、課金が発生したサイトを識別します。Business Manager では、レルム内の各サイトで異なる記述子を設定できます。Business Manager の記述子は Stripe の statement_descriptor の値を上書きします。サイト固有の記述子の値は Stripe Payment Intents API で使用され、買い物客の銀行またはカードのネットワークに渡されます。

トランザクションごとの記述子

さらに細かい情報を説明に追加したい場合などには、Script API を使用して支払アプリケーションごとに明細書記述子を設定します。Script API で設定した明細書記述子の値は、Stripe ダッシュボードと Business Manager で設定した記述子の値を上書きします。
