B2C Commerce の動的マッピング

パターンを使用する動的マッピングルールを設定して、レガシーサイトの URL を識別し、自動的に B2C Commerce URL にリダイレクトします。マッピングルールを使用して、既存の B2C Commerce URL または古い形式の B2C Commerce URL を、別の B2C Commerce URL にリダイレクトすることや、画像などの静的リソースのリダイレクトを作成することはできません。

マッピングルールは、リダイレクトを必要とする類似した URL が多数ある場合に使用します。たとえば、特定カテゴリ内のすべての URL をリダイレクトする必要がある場合などです。特定の URL を 1 つリダイレクトする場合は、静的マッピングを使用するのが一般的です。エイリアス、マッピングルール、および静的マッピングを使用するタイミングの詳細については、URL リダイレクトを参照してください。Business Manager の構成のファイルサイズは 2MB に制限されています。この制限を超えた場合は、サイトのインポートとエクスポートの機能を使用して動的マッピングを更新します。

メモ SEO サポートモジュールから URL ルールモジュールにアップグレードした場合は、アップグレード処理中に作成されて URL アーカイブに保管された URL リダイレクトによって動的マッピングが上書きされる場合があります。古い形式のリダイレクトを削除するには、SEO URL の URL アーカイブタブの使用を参照してください。

はじめに

マッピングルールを作成する前に、ホストエイリアスを定義します。SEO > エイリアスモジュールで、サイトのドメイン名の適切なリストを追加します。ユーザーが完全な B2C Commerce URL を入力しなくてもストアフロントにアクセスできるようにするには、シンプルなサイト URL (例: "www.store.com") をエイリアスリストに追加します。

ホスト名のエイリアスを参照してください。

ホスト名エイリアスの割り当てを参照してください。

Staging (ステージング)、Development (開発)、または Sandbox () インスタンスでマッピングルールを編集し、Production (本番) インスタンスにレプリケートします。

売れ筋の商品やカテゴリのマッピングルールを作成する

マッピングルールは、古いプラットフォーム上の古いサイトと B2C Commerce 上の新しいサイトで累積された SEO ランキングを維持するために作成します。Salesforce では、自社の売れ筋カテゴリと商品を Google で検索し、各検索の最初のページに表示されるリンクを、リダイレクトするリンクのリストとして使用することをお勧めします。リンクのリストができたら、ルールを適用するパターンを特定します。たとえば、同じカテゴリまたはサブカテゴリに多くのリンクがある場合、マッピングルールを使って、そのカテゴリ内の商品を古いサイトから新しいサイトにリダイレクトできます。

ホスト名のみの URL の代わりにマッピングルールを使用しないでください。シンプルなホスト名のみの URL で代用可能な場合は、B2C Commerce パイプラインを介してホームページに戻るイントラサイトのリンクの生成を避けます。

次の標準ルールがどのケースでも追加されます: 

/?** p,,,Default-Start,,{_querystring}

これにより、ホストのみとパラメーターのリクエストが Default-Start パイプラインに転送され、元の URL パラメーターが保持されます。このルールをカスタムルールで上書きまたは拡張します。

ホームページリンクの作成を参照してください。

マッピングルール構文

マッピングルールは、空白で区切った URL パターンと B2C Commerce URL テンプレートで構成されています。URL パターンは 受信 URL を特定し、URL テンプレートはリダイレクトに使用する B2C Commerce URL を生成します。また、パターンとテンプレートの間に特定のオプションを追加することもできます。

テンプレート内の番号パラメーター ({0}) を使用することで、ワイルドカード (*、**) に一致した受信 URL のどの部分でも、その URL 内での位置によって参照できます。ワイルドカードでは、URL に含まれるフォワードスラッシュの間の文字 (クエリ文字列ではないもの) が照合されます。

たとえば、古いサイトの Jewelry (ジュエリー) カテゴリに含まれる商品を、以前と同じ商品 ID とカテゴリ名を使用して新しいサイトにリダイレクトします。

受信 URL の例: 

http://www.oldsite.com/catalog/product/index.asp?ID=576416&Cat=Jewelry.html

B2C Commerce URL の例: 

http:///www.mystore.com/pendant/576416,default,pd.html?cgid=Jewelry

受信 URL のパターン

受信 URL のパターンには、URL の一部を置き換えるために使用するワイルドカードと、URL の一部または全部が含まれます。このパターンには、プロトコルとホスト名を含む絶対パターンか、または '/' で始まる、ホスト名を含まない相対パターンのどちらかを指定できます。

ワイルドカード

多くの URL を動的に表現するには、ワイルドカードを使用して元のレガシー URL の変数を解析します。ワイルドカードは以下の通りです:

ワイルドカード 意味
* スラッシュ"/"までの任意の文字にマッチします。クエリ文字列とパラメーターが一致しません。
** スラッシュ"/"を含む任意の文字に一致します。クエリ文字列とパラメーターが一致しません。** をキャッチオールとして使用すると、特定のマッピングよりも優先されます。

ホスト名エイリアスファイルが正しく設定されている場合は、パターンによって http および https プロトコルの両方を照合できます。

パターンの例: 

/**/images/**
 http://www.mystore.com/**/*.jpg    
/news/articles/**.html
 /catalog/special/*.*.*.html

URL エンコード

マッピングルールで URL がパラメーターとして渡される場合、その URL は元の URL エンコードを保持できるように処理されます。たとえば、元の URL に空白の置換としてプラス (+) またはダッシュ (-) が含まれている場合、その文字は保持され、テキストとしてエンコード (%2B または %2D) されません。

オプション

パターンの照合方法またはパターンパラメーターのエンコード方法を制御するいくつかのオプションを指定します。

オプション 説明
i (小文字の i) 大文字、小文字、および大文字と小文字が混在する一致を許可
I (大文字の I) URL テンプレートに置換する前に受信パラメーターを小文字に変換
ie UTF-8 以外で使用するエンコードを指定

B2C Commerce URL テンプレート

B2C Commerce URL テンプレートは、B2C Commerce URL を表します。

URL の生成は、静的 URL または動的パイプライン URL のいずれかの定義で構成されます。

静的 URL は次の形式です: 

 s,[<プロトコル>],[<ホスト>],[<ユニット>],[<地域情報>],<パス>

パイプライン URL は次の形式です: 

 p,[<プロトコル>],[<ホスト>],<パイプライン>[,<地域情報>][,<パラメーター名>,<パラメーター値>]*

<パラメーター名>または<パラメーター値>に空白が含まれている場合は、二重引用符 (" ") で囲みます。一重引用符 (' ') は使用しないでください。

動的パイプラインコールに設定するパラメーターは以下の通りです:

 <レガシー URL> [i] p,[<プロトコル>],[<ホスト>],<パイプライン>[,<地域情報>][,<パラメーター名>,<パラメーター値>]*

次の変数はパスで使用するか、パラメーター値として使用します:

変数 説明
{0}, {1}, ... パターンからの位置値。位置値は、ワイルドカードに一致した文字列で、パターンに含まれるワイルドカードの位置を示します。B2C Commerce URL へのリダイレクトで受信 URL の一部を使用する方法については、以下のセクションを参照してください。また、地域情報の判定には、抽出された URL セグメントも使用できます。
{_url} 元の URL 全体。
{_path} 元の URL のパス部分。
{_host} 使用されているホスト名。
{_querystring} 元の URL のクエリ文字列。
{<name>}

元の URL からのパラメーター。

{<name>} 値は、ワイルドカードに一致するいずれかのパラメーターで、[name]=[value] パターンを持っているものです。例: 

/product.asp?ProductID=12345 (legacy URL for mapping rule/product.asp?**)
{ProductID}

プレースホルダー ({0} など) とリテラルを混在させます。以下がその例です: 


                              literal1_{0}_literal2

例 1: B2C Commerce URL へのリダイレクトで受信 URL の一部を使用する

マッピングルールパターンでワイルドカードを使用して受信 URL の一部を一致させてから、テンプレートで位置値を使用し、リダイレクト先の B2C Commerce URL にその値を転送します。位置値とは、有効な URL マッピングで一致したワイルドカード文字列を、見つかった順番に並べたものです。空白文字列を管理するには、一重引用符で囲みます。

たとえば、以下のマッピングルールを使用します:

/**/images/** s,,,,,/{0}/{1}

この表は、位置値とマッピングルールの組み合わせが特定の受信 URL に対して機能する仕組みを表しています。

パターン //**/images/**
受信 URL http://www.oldshop.com/path/to/images/even/more/paths
テンプレート s,,,,,/{0}/{1}
B2C Commerce URL http://www.newshop.com/path/to/even/more/paths

このパターンで見つかる URL:

http://www.shop.com/path/to/images/even/more/paths
    {0} : path/to 
    {1} : even/more/paths
http://www.yourshop.com//images/
    {0} :
    {1} : 
    (どちらの位置値も空白！)
見つからなかった URL: 理由 
http://www.yourshop.com/images/even/more/paths
 URL の images の前にスラッシュが足りない 
http://www.yourshop.com/path/to/images
URL の images の後にスラッシュが足りない

この動的マッピングルールでは、ワイルドカードを使用せずに、空白を使用してブランド名または商品名のマッピングを作成する方法を示します。ワイルドカードではなく、引用符を使用して空白を管理すると、全体的なパフォーマンスの向上につながります。

eCDN ゾーンのホストヘッダー上書きルールの構成

複数のレルムで 1 つのホスト名をサポートするには、外部コンテンツ配信ネットワーク (CDN) を使用するサイトに対してホストヘッダー上書きルールを作成します。このルールは、一意のホスト名を共通のホスト名に置き換えて、単一のホスト名の設定を維持します。ホスト名を再利用すると、意図せずに別のレルムからトラフィックが提供される可能性があります。

プロキシゾーンはゾーン間で同じサブドメイン/ホスト名をサポートしていないため、各ゾーンごとに適切なカスタムホスト名と証明書を設定した一意のホスト名が必要です。

ホストヘッダーの上書きルールを作成する前に、独自のスタック CDN 構成があることを確認してください。CDN スタッキングは、地域情報または地域に基づいて適切な eCDN ゾーンにトラフィックを転送するための前提条件です。

各地域情報のホストヘッダールールを作成します。ホストヘッダーの上書きルールを作成するには、次の手順を実行します。

  1. Business Manager でアプリケーションランチャーをクリックし、管理 | サイト | 埋め込み CDN 設定の順に選択します。
  2. 構成するゾーンを見つけ、ドロップダウンメニューからゾーンの構成を選択します。
  3. 「ホストヘッダー上書きルールタブ」を選択し、新規ルールを選択します。このタブから別のゾーンに切り替えるには、[ゾーン]ドロップダウンメニューから別の名前を選択します。
  4. ホストヘッダー上書きルールの詳細を入力します。
    1. 視覚的なドロップダウンインターフェイスを使用してルール式を入力し、フィールド、演算子、値を選択します。この式は、トラフィックの行き先となる受信要求のホスト ヘッダーを指定します。たとえば、ホスト名が shop.alpine.net と等しいとします。
    2. (オプション) 保存時にルールをアクティブにする場合は、保存時にホストヘッダー上書きルールを有効化を選択します。ルールをアクティブ化する準備がまだ整っていない場合は、まずルールを作成します。準備ができたら、「ホストヘッダー上書きルール」タブに戻り、リストからルールを有効にします。
    3. ルール名は、ルールの詳細に基づいて自動的に入力されます。
    4. 保存をクリックします。保存時に、ルールのホストヘッダーが現在のゾーンと同じホスト名で終わっていることを確認します。
  5. 外部 CDN を変更して、各地域情報のプロキシゾーンにトラフィックをルーティングします。

eCDN ゾーンのレート制限ルールの作成

レート制限ルールを設定して、特定の式に一致するリクエストのレート制限を指定し、リクエストがそれらのレート制限に達したときにアクションを実行します。レート制限ルールは、ストアフロントの可用性を向上させ、特定のトラフィックパターンをターゲットにし、ボットなどの脅威に対抗します。

  1. Business Manager でアプリケーションランチャーをクリックし、管理 | サイト | 埋め込み CDN 設定の順に選択します。
  2. 構成するゾーンを見つけ、ドロップダウンメニューからゾーンの構成を選択します。
  3. 「セキュリティルール」タブで、新しいレート制限ルールをクリックします。このタブから別のゾーンに切り替えることもできます。ゾーンを切り替えるには、[ゾーン] ドロップダウンから別の名前を選択します。
  4. ルール名を入力します。たとえば、「user_agent_x からのリクエストのレート制限」などです。
  5. (オプション) 保存時にルールをアクティブにする場合は、保存時にルールを有効化を選択します。ルールを有効化する準備がまだ整っていない場合は、事前にルールを作成しておくことができます。準備ができたら、「セキュリティルール」タブに戻り、リストからルールを有効にします。
  6. ビジュアルドロップダウンインターフェイスを使用してルール式を入力し、フィールド、演算子、値を選択します。条件付きロジックを追加するには、「かつ」ボタンまたは「または」ボタンを使用します。式の編集をクリックして、式を手動で入力することもできます。
  7. レート制限を設定するには、期間あたりの要求数を指定します。
  8. (オプション) レート制限の対象とするリクエスト条件を定義するには、カスタムカウント式の使用を選択します。このパラメーターは、期間あたりのリクエスト数を追跡するレートカウンターをインクリメントするタイミングを定義します。レートカウンタが期間ごとに定義されたリクエスト制限を超えると、ルールはそのアクションを実行します。
    1. カウント式が指定されていない場合、カウント式はルール式と同じになります。
    2. カウント式では、HTTP 応答コードに基づいてレート制限するオプションがサポートされていますが、これはルール式のみを使用して行うことはできません。カスタムカウント式を使用する場合のその他の例については、「B2C Commerce API デベロッパーガイド」のレート制限ルールに関するよくある質問 (FAQ) を参照してください。
  9. 「一致特性」は、「IP」と「NAT サポート付き IP」をサポートします。この特性によって、受信リクエストのグループ化方法が決まります。定義された特性と同じ値をもつリクエストはグループ化され、レートカウンターを共有します。
    1. たとえば、ルールの特性として IP を使用するとします。単一の IP アドレスからのリクエストのレートが、定義された制限を超える場合、その IP アドレスからの以降のリクエストはレート制限されます。他の IP アドレスからのリクエストは、同じレートカウンターを共有しません。つまり、1 つの IP アドレスのリクエストレートは、他の IP アドレスのリクエストレートに影響を与えません。
  10. ルールのアクションを選択します。たとえば、ブロックまたはログ記録です。詳細については、「B2C Commerce API デベロッパーガイド」の「ルールのアクション」を参照してください。
  11. アクションの適用方法を定義するには、[ 選択した期間のアクション ] または[構成された最大レートを超える要求のスロットル ] を選択します。
    1. 選択した期間に対するアクション: レート制限の基準を満たしたら、期間で指定された期間、ルール式に一致する追加の要求にアクションを適用します。
    2. 構成された最大レート超過時のリクエスト制限: 構成した最大レートを超えるリクエストをスロットリングします。選択したアクションはこれらの超過要求に適用されますが、制限内の要求は引き続き許可されます。
  12. ルールで「選択した期間に対するアクション」を使用する場合は、ドロップダウンメニューから期間を選択します。
  13. ルールを保存します。

作成したルールは、「セキュリティルール」タブのレート制限ルールのリストに表示されます。このリストから、ルールのオンとオフを切り替えることができます (保存時にルールを有効化を選択した場合、ルールはデフォルトでオンになっています)。「レート制限ルール」リストには、過去 24 時間に各ルールに一致したリクエストの数も表示されます。この番号をクリックすると、詳細なトラフィック分析が表示されます。eCDN ゾーンの HTTP トラフィックとセキュリティトラフィックの分析を参照してください

プロビジョニングとセットアップ

新しい ODS インスタンスが作成されると、何が自動的にプロビジョニングされますか?

26.6 リリース以降、すべての新しい ODS インスタンスは、eCDN を経由するデフォルトドメインホスト名を自動的に受け取ります。DNS の変更や証明書の管理を手動で行う必要はありません。レルムごとに 2 つの共有 Cloudflare ゾーンがプロビジョニングされます (1 つはストアフロントトラフィック用、もう 1 つは Business Manager トラフィック用)。各 ODS インスタンスは、両方の共有ゾーンに登録されたカスタムホスト名を取得します。

ODSのホスト名形式は何ですか?

  • ストアフロント:<instance>.sbx.my.commercecloud.salesforce.com ( 例: bldp-001.sbx.my.commercecloud.salesforce.com )
  • Business Manager:<instance>.dx.commercecloud.salesforce.com、共有 BM ゾーン ( ccbm.< を介してプロキシされます。レルム>-sbx.cc-bm.net )

既存の ODS インスタンスは自動的に eCDN を取得しますか。

いいえ。既存の ODS インスタンスは遡及的に移行されません。eCDN を自動的に受信するように新しい ODS インスタンスをプロビジョニングします。

デフォルトゾーンは Business Manager のどこに表示されますか。

プロビジョニング後、デフォルトゾーンは、Business Manager管理 | サイト | 埋め込み CDN 設定のデフォルトゾーンの行 ( 例: zzpq.sbx.my.commercecloud.salesforce.com ) として表示されます。[ ゾーンの構成 ] ボタンを使用して、Web アプリケーション ファイアウォール (WAF) 規則、MRT ルーティング規則、キャッシュ設定、ホスト ヘッダーのオーバーライド、および PCI ポリシーを管理します。

共有ゾーン モデル

共有ゾーンモデルとは何ですか?

レルム内のすべての ODS インスタンスは、1 つのストアフロントゾーンと 1 つの Business Manager ゾーンを共有します。つまり、ゾーンで構成された WAF ルール、MRT ルーティング ルール、キャッシュ設定、ホスト ヘッダーのオーバーライド、および PCI ポリシーが、そのレルム内のすべての ODS インスタンスに適用されます。インスタンスごとの構成の分離は範囲外です。

共有ゾーンモデルは WAF ルールにどのように影響しますか。

WAF ルールのスコープは、インスタンスレベルではなく、ゾーンレベルです。追加または変更したルールは、レルム内のすべての ODS インスタンスに影響します。ルールの変更は慎重に計画し、インスタンス間で意図しない影響が発生しないようにします。

ODSゾーンにデフォルトの「すべてブロック」ファイアウォールルールはありますか?

いいえ。一部の PIG Production ゾーンとは異なり、ODS ゾーンにはデフォルトの Block All ファイアウォールルールがありません。ODS ゾーンはデフォルトで開いています。必要に応じて明示的なルールを追加し、アクセスを制限します。

運用環境との機能パリティ

すべての eCDN 機能は ODS で利用できますか。

はい、エッジキャッシュ、WAF (OWASP ルールセット、eCDN マネージドルールセット、カスタムルール)、ボット保護、DDoS 軽減、レート制限、リアルタイム分析、Log Center メトリクス (HTTP ステータスコード 502 から 530)、PCI 4.0/ページシールド、IP/ASN/geo ブロッキング、MRT ルーティングルール、イメージ最適化 (DIS)、ログエクスポート (LogPush) など、すべての標準 eCDN 機能を ODS デフォルトドメインゾーンで使用できます。

次の機能はまだ使用できないか、ODS の範囲外です。

  • バニティドメイン(カスタムホスト名):26.7 ODS リリースをターゲットとしています。
  • インスタンスごとの eCDN 構成の分離:範囲外です。レルム内のすべての ODS インスタンスは、同じ eCDN 構成を共有します。
  • ビデオの最適化:サポートされていません。外部 CMS またはパートナー ソリューションを使用します。

バニティ・ドメインの移行

私は dx.commercecloud.salesforce.com にCNAMEd ODSバニティホスト名を持っています。何をする必要がありますか?

26.4 のロールアウト前に対策を講じてください。適用可能なパスは、現在の設定によって異なります。

  • シナリオ 1 — 入力トランスポート層セキュリティ (TLS) ターミネーションを使用したバニティ ホスト名:暫定的な手動パスは 26.5 パイロットのお客様のみ利用可能で、eCDN チームの関与が必要です。Salesforce サポートに問い合わせてください。
  • シナリオ 2 — ODS 証明書なしで dx.commercecloud.salesforce.com に CNAMEd されたバニティ ホスト名:移行パスはまだ定義されておらず、スパイク評価が必要です。ロールアウト日の前に Salesforce アカウントチームと調整します。

詳細なガイダンスについては、B2C Commerce でのゾーンの作成を参照してください。

ODS でセルフサービスのバニティホスト名を完全にサポートできるようになるのはいつですか?

Salesforce では、26.7 リリースで ODS のセルフサービスバニティホスト名を完全にサポートする予定です。

証明書

ODS eCDN の証明書を管理するのは誰ですか。

Salesforce は、ODS デフォルトドメインゾーンのすべての証明書を管理します。*.sbx.my.commercecloud.salesforce.com (ストアフロント) と*.dx.commercecloud.salesforce.com (Business Manager) のワイルドカード証明書は自動的にプロビジョニングされ、更新されます。証明書を毎年更新する必要はありません。

eCDN プロキシゾーンに関するよくある質問 (FAQ)

eCDN プロキシゾーンに関する質問にお答えします。

プロキシゾーンとレガシーゾーン

CDN プロキシゾーンとは何ですか。

プロキシゾーンとは、eCDN で作成された新しいゾーンです。Business Manager によってプロキシゾーン名が変換されます。プロキシゾーン名は顧客には表示されません。プロキシゾーンは以下の特性をもちます。

  • cc-ecdn.net で終わる。
  • ゾーンの DNS CNAME が commcloud で始まる。
  • Business Manager または CDN-API からプロキシゾーンの構成にアクセスできる。

レガシーゾーンとは何ですか。

レガシーゾーンはルートゾーンとも呼ばれ、顧客のドメイン名を含むゾーンです。たとえば、brand.com などです。

ゾーンがルートゾーンかプロキシゾーンかは、どのように見極めることができますか。

Business Manager で、管理 | 埋め込み CDN 設定の順に選択して、ホスト名を見つけます。DNS の CNAME が commcloud で始まる場合、このゾーンはプロキシゾーンです。

eCDN プロキシゾーンではどのような問題を解決できますか。

  • レルムとインスタンスに固有の構成

    プロキシゾーンはインスタンスレベルで構成します。レガシーゾーンはドメイン名レベルで構成されます。複数のレルムがある場合、さまざまなホスト名をさまざまなレルムに割り当てることができます。たとえば、us.mystore.com と eu.mystore.com の eCDN 構成を別々に管理できます。

  • eCDN 管理証明書 (eCDN 自動証明書)

    すべてのプロキシゾーンでは証明書の自動更新がサポートされています。B2C Commerce マーチャントには、eCDN で管理される SSL 証明書を自動更新するオプションが提供されています。自動更新では、証明書が有効な状態に維持され、Development (開発)、Staging (ステージング)、および Production (本番) のインスタンスの eCDN の管理が簡単になります。

どの B2C Commerce インスタンスで、eCDN 管理証明書を構成できますか。

Development (開発)、Staging (ステージング)、Production (本番) の各インスタンスに対して eCDN で管理される証明書を構成します。

Business Manager を利用して、eCDN プロキシゾーンで eCDN 管理証明書を構成できますか。

はい。Business Manager は eCDN 管理証明書の構成をサポートしています。管理 SSL 証明書の追加を参照してください。

eCDN レガシーゾーンとプロキシゾーンはどのように連携しますか。

レガシーゾーンとプロキシゾーンは両方とも、異なるレルムと Cloudflare アカウントにのみ存在できます。たとえば、アカウント A に brand.com のレガシーゾーンがあり、アカウント B のホスト名でのプロキシゾーンも作成したとします。これらのゾーンは、同一のレルムおよび Cloudflare アカウント内に共存はできません。

トラフィックをホスト名にルーティングするには、レガシーゾーンとプロキシゾーンの両方に SSL 証明書が必要です。プロキシゾーンでは、証明書をアップロードするときにホスト名を指定する必要があります。レガシーゾーンでは、SSL 証明書はアップロードされた証明書内の SAN と一致するホスト名のみを提供します。

同じホスト名のレガシールートゾーンとプロキシゾーンがある場合はどうなりますか。

プロキシゾーンでトラフィックを処理するホスト名には SSL 証明書が必要です。ホスト名 (us.brand.com など) と、有効な SSL 証明書を使用してプロキシゾーンを構成します。

ホスト名 us.brand.com のトラフィックには、ルートゾーン (brand.com) と Salesforce Commerce Cloud (SFCC) の両方の eCDN プロキシゾーン (cc-ecdn.net で終わる) に、カスタムホスト名 us.brand.com を持つ有効な証明書が必要です。

  • ホスト名のトランスポート層セキュリティ (TLS) を終了するために使用されるルートゾーン (brand.com) 証明書 us.brand.com 有効期限が切れると、トラフィックを処理できなくなります。
  • プロキシゾーンにホスト名 us.brand.com がない場合、トラフィックを処理できません。

有効な SSL 証明書をアップロードするか、eCDN 管理の自動更新証明書を使用します。

ルートゾーンとプロキシゾーンにインストールされる証明書数に制限はありますか。

ルートゾーンまたはレガシーゾーン (domain.com) は、レルムごとに 4 つのカスタム証明書スロットに制限されており、Production (本番)、Development (開発)、Staging (ステージング) の間で共有されます。

プロキシゾーンは任意のサイトで、自己管理のカスタム SSL 証明書と eCDN で管理される自動更新 SSL 証明書の両方をサポートします。自己管理の SSL 証明書の制限はレルムごとに 5 つまでです。eCDN で管理される自動更新証明書の制限は、追加費用なしでゾーンごとに 500 通までです。

レガシーゾーンまたはプロキシゾーンの追加の証明書には、毎月のサブスクリプションコストがかかります。Salesforce は、次回の契約更新サイクル中に新しい条件についてお客様と話し合います。

プロキシゾーンで自己管理のカスタム SSL 証明書から eCDN 管理証明書に切り替えることはできますか。

認証局によって発行された自己管理のカスタム証明書がプロキシゾーンにある場合は、レルム内の任意のゾーンで SSL 証明書を自動更新するように構成できます。また、Development (開発)、Staging (ステージング)、Production (本番) の各インスタンスの SSL 証明書を引き続きアップロードすることもできます。

eCDN で管理される自動更新証明書または自己管理のカスタム SSL 証明書にいつでも切り替えられます。

認証局が発行した自己管理 SSL 証明書は、Business Manager または CDN-API で構成します。CDN-API でのみ管理される eCDN を構成します。

メモ eCDN で管理される自動更新証明書は、単一のカスタムホスト名証明書のみをサポートします。自己管理のカスタムワイルドカード証明書がある場合は、それらを引き続き使用するか、ホスト名用の eCDN で管理される証明書を使用して別のカスタムホスト名を作成します。

管理証明書を、eCDN の上にサードパーティの CDN をスタックして使用できますか。

はい。eCDN 上にスタックされたサードパーティ CDN で eCDN 管理証明書を使用するには、TXT レコードを 3 か月ごとに検証する必要があります。これは、自動証明書が 3 か月ごとにローテーションされるためです。ドメインコントロール検証 (DCV) の委任を行わない場合、2、3 か月ごとに TXT レコードの更新が必要になります。必要に応じて、サポートチームに連絡して、DNSレコードに含めるDCV委任の汎用一意識別子(UUID)を提供します。

eCDN 管理証明書を eCDN レガシーゾーンまたはルートゾーンで使用することはできますか。

いいえ。eCDN 管理証明書の機能は、eCDN プロキシゾーンでのみ使用できます。すべてのレガシーゾーン (brand.com など) で、カスタム証明書が必要です。Business Manager を使用して、有効期限が切れる前に証明書をアップロードして更新します。

リリースとタイムラインのスケジュール

Business Manager の eCDN プロキシゾーンは、いつ利用可能になりますか。

B2C Commerce 22.8 リリースの後に作成されたすべての新しいゾーンは、デフォルトでプロキシゾーンになります。

オンボーディングとアクティブ化

どのように Business Manager で eCDN プロキシゾーン機能をアクティブにできますか。

すべてのマーチャントは、eCDN プロキシゾーンを作成できます。この機能をアクティブ化または有効にするためにさらに必要な手順はありません。

eCDN プロキシゾーンを使用する資格を得るための要件はありますか。

eCDN プロキシゾーンを使用する資格を得るための要件はありません。

どのように eCDN プロキシゾーンを構成できますか。

埋め込み CDN

Salesforce B2C Commerce では、埋め込みのコンテンツ配信ネットワーク (CDN) が提供されています。コンシューマーへの応答時間を短縮するために、埋め込み CDN はコンシューマーに近い場所からコンテンツを提供し、サイトの拡張性を強化します。Salesforce サポートに連絡して、組織で埋め込み CDN を有効にしてください。

  • 埋め込み CDN の概要
    Salesforce B2C Commerce では、サイトの表示速度とコンテンツ配信を高速化する埋め込みコンテンツ配信ネットワーク (eCDN) をデジタル顧客に提供しています。eCDN は、プロキシサーバーを使用するコンシューマーに対して短い応答時間を提供します。プロキシサーバーを使用することによって、デジタルコンテンツを提供できます。
  • 埋め込み CDN の構成
    埋め込み CDN (eCDN) は、地理的に離れた場所にあるプロキシサーバーのネットワークです。eCDN を構成することで可用性とパフォーマンスが向上し、最終的にサイトの拡張性が向上します。
  • CDN Zones API を使用した eCDN 構成
    Development (開発)、Staging (ステージング)、Production (本番) のいずれかのゾーンを設定するには、開発チームが CDN Zones API を使用して顧客の証明書をアップロードして、Shopper Commerce API (SCAPI) の実装をテストし、eCDN の Development (開発)、Staging (ステージング)、Production (本番) の各インスタンスのバニティホスト名を構成します。
  • eCDN キャッシュのクリア
    B2C Commerce では、eCDN キャッシュまたは Web 層の静的コンテンツキャッシュに静的ストアフロントコンテンツが保存されます。
  • 外部 CDN またはサードパーティプロキシの構成
    自社独自のコンテンツ配信ネットワーク (CDN) と Salesforce B2C Commerce の埋め込み CDN を使用して、静的および動的のコンテンツを顧客に配信します。自社の CDN (またはリバースプロキシ) を B2C Commerce の前にデプロイすると、パフォーマンスとセキュリティを向上させ、自社の CDN を使用して追加機能を提供できます。
  • eCDN Web アプリケーションファイアウォール
    Embedded Content Delivery Network (eCDN) Web Application Firewall (WAF) は、レイヤー 7 による保護を使用してストアフロントの保護を支援します。
  • B2C Commerce での HSTS の管理
    サイトを保護するために、HTTP Strict Transport Security (HSTS) は HTTPS のみを使用してドメインにアクセスするように Web ブラウザーに指示します。このトピックは、B2C Commerce に該当します。

B2C Commerce での暗号化と暗号法

Salesforce B2C Commerce では、強力な暗号化トークンとセキュアなランダム識別子を安全に暗号化、署名、生成することを可能にする、Salesforce が維持する暗号化ライブラリを拡張しています。Salesforce では、Salesforce の Trust Compliance Web サイトの B2C Commerce ページに記載されているように、業界標準のコンプライアンスフレームワークを維持しています。

ベストプラクティスとして、機密データを保存、処理、または送信する際には、必ず暗号化を実装してください。カード名義人のデータ、特に主要口座番号 (PAN: Primary Account Number) の場合は、トークナイゼーションを使用します。B2C Commerce API で公開されている API を使用すると、コンプライアンスを維持しながらこれを実現できます。

以下に、dw.crypto API でもっとも一般的に使用されるクラスをあげます。

  • Cipher: さまざまなアルゴリズムを使用した、暗号化と復号化へのアクセスポイント
  • Encoding: 異なる文字のエンコードのためのサービス
  • Secure Random: 暗号論的に安全なランダムトークン生成器の実装

業界標準のコンプライアンスフレームワークを維持し、脆弱性を避けるために、カスタムの暗号化メソッドは実装しないでください。業界で受け入れられているテスト済みの暗号化メソッドを、強力な鍵とともに使用します。PCI とその他の機密情報を保護するために、B2C Commerce の dw.crypto は定期的に見直しを受けています。また、必要に応じて、Business Manager を通じて鍵のメンテナンスと保護を行うことができます。Salesforce の PCI データセキュリティ基準 (DSS) のコンプライアンス構成証明の暗号化要件を利用するには、B2C Commerce プラットフォームが提供する暗号化方法を使用してプライマリアカウント番号 (PAN またはクレジットカード番号) を保護する必要があります。

B2C Commerce での HTTPS の強制

HTTPS を使用する受信ページリクエストを HTTPS にリダイレクトするには、「HTTPS を強制する」設定を有効にします。サイトごと、またはインスタンスのすべてのサイトに対して設定を構成します。「HTTPS を強制する」をグローバルに有効にすると、サイトレベルで構成することはできなくなります。このグローバル環境設定を無効にすると、サイト固有の設定は元の値に戻ります。このトピックは、B2C Commerce に該当します。

グローバル環境設定として「HTTPS を強制する」を有効にすると、サイトに対して「HTTPS を強制する」を選択した場合にはアクティブにならないいくつかの動作も有効になります。

  • サーバーは Cookie の Secure フラグを設定できます。現在一部のブラウザーでは、特定のクロスサイト動作がリクエストされた場合、Cookie に Secure フラグが立てられていることが要求されます (SameSite Cookie 属性は None に設定)。Secure フラグはブラウザーに対し、暗号化されていない HTTP 接続で Cookie を送信しないように指示します。ブラウザーは HTTP チャネルを介して Cookie を送信することはありません。この動作の詳細については、Cookie 属性 SameSite=None の情報を検索してください。
  • ストアフロントは、誤った (誤検知の) セッションハイジャック検出を回避するために、セッション Cookie とセキュアトークンの組み合わせではなく、セキュアセッション Cookie を使用します。
  • Open Commerce API (OCAPI) のセッションブリッジへの HTTP リクエストは受け入れられません。
重要 グローバルの HTTPS 環境設定を有効にすると、クロスサイトリクエストとともにブラウザーが Cookie を送信できるようになります。グローバルの HTTPS 環境設定を有効にしないと、現在の一部のブラウザーではクロスサイトのシナリオが失敗します。

「HTTPS を強制する」をサイトに対して (グローバルに、またはサイトレベルで) 有効にした場合、そのサイトの URL 生成では常に HTTPS が使用されます。ハードコードされた URL と絶対 URL は影響を受けません。このため、以前にこの設定が無効にされたサイトに対してこの設定を有効にする場合は、HTML でハードコードされた URL と絶対 URL を適切に変更してください。URLUtils メソッドを変更する必要はありません。URLUtils.http では HTTPS プロトコルを使用する URL が生成されます。

「HTTPS を強制する」を有効にする利点

HTTPS は、侵入者が Web サイトとユーザー間の通信をパッシブにリッスンすることを防止します。HTTPS を強制するその他の理由には次のものがあります:

  • ユーザーがサイトを訪問する際には、プライベートで安全なオンライン体験を期待しています。
  • HTTP/2 などの一部のアップデートは、HTTPS を使用してのみ、一部のブラウザーでのみサポートされています。
  • Google は HTTPS をランキング信号として使用するため、HTTPS を使用するとサイトの検索ランキングが向上する可能性があります。
  • Google Analytics は HTTPs から HTTP へのリファラルデータをブロックします。

オンラインの影響

HTTPS を強制した直後は、オーガニック検索トラフィックが減少することがあります。Google によると、サイトに大幅な変更を行った場合、オーガニック検索トラフィックが変動する可能性があります。しかし、ページランク、またはリンクジュース には、HTTP から HTTPS へのリダイレクトによる悪影響はないはずです。Google によれば、HTTP から HTTPS への 301 または 302 リダイレクトでは、ページランクは失われません。

Google Analytics の検索キーワードは、HTTPS によって変わることはありません。Google Search Console で引き続き検索クエリを見ることができます。

Google がインデックスに登録した HTTPS ページの数を表示するには、Google Search Console で HTTP と HTTPS を別々に検証します。また、広い観点から見るためにインデックスステータスを使用したり、サイトマップ URL でインデックス付けされたサイトマップの数を確認したりできます。

Google インデックス内で HTTP から HTTPS に変更するタイミングは、サイトの規模とクロールの速度によって異なります。Google の検索インデックスにおける HTTP から HTTPS URL への移動は、URL ごとに行われます。Google は固定クロール頻度のデータを提供していません。

robots.txt ファイル

HTTPS サイトは robots.txt ファイルを使用するので、「HTTPS を強制する」を有効にする際には以下を確認してください。

  • robots.txt がアクセス可能であること、または、404 の結果コードを提供すること。
  • robots.txt ファイルが HTTPS URL をブロックしていないこと。
  • HTTP を使用した絶対 URL を使う XML サイトマップへの参照が robots.txt ファイルにないこと。

B2C Commerce の SEO 評価

インターネット上では、自分のサイトの SEO 対策がどれだけできているかを教えてくれる、使いやすくて低価格な (または無料の) ツールが多数あります。ただし、量と質はイコールではありません。結局のところ、SEO とはコンバージョンにつながる質のいいトラフィックを増やすためのものです。

  • SEO に関するベストプラクティスを理解します。
  • URL リクエスト分析機能を使用すると、ストアフロント URL リクエストの処理方法と、対応するページを開くために使用される構成を理解できます。
  • Google ウェブマスターツールを使用して、クロール情報や robot.txt 評価、トップ検索用語、予期される問題、侵害など、サイトのインデックス化とパフォーマンスがどのくらい Google で機能しているかを把握しましょう。
  • Xenu4 や OptiSpider5 などのツールを使用して、サイトが何ページあるか見積もりましょう。
  • 現時点でインデックス化されているページが何ページあるかチェックしましょう。これを実行するには、関連する検索エンジン上で site:(ドメイン) と入力します。(たとえば、site:demandware.com)。
  • Lynx6 などのテキストブラウザーを使用してスパイダートラップをチェックし、スパイダーが回収する情報を見てみましょう。
  • WebBug7 などのツールを使用して、サイトのリダイレクトをチェックしましょう。
  • Google の "link:" コマンドまたは Yahoo! Search Site Explorer8 を使用して、自分のサイトのバックリンクを誰が、何件作成したかをチェックしましょう。
  • 訪問を追跡します。
  • ページの追加をトラップします。

GMV 計算の例

多くの場合、Salesforce B2C Commerce の顧客は GMV (流通総額) レポートを実行して、B2C Commerce の請求書を再計算する必要があります。これらのレポートは自動化することができます。

必要なエディション

使用可能なソリューション: B2C Commerce

B2C Commerce では Production (本番) インスタンスで GMV データがキャプチャされますが、GMV の生成ジョブは Development (開発) と Sandbox (サンドボックス) のインスタンス上では無効になっています。

メモ 課税が購読料に与える影響を参照して、税金の計算が購読料支払いに著しく影響を与えることを理解してください。
メモ レガシーのレポートモジュールは、すべてのインスタンスタイプで使用することができます。ただし、このモジュールは、実際の収益を反映するために Production (本番) インスタンスで使用することを意図しています。自動生成レポートは、Production (本番) インスタンスでのみ生成されます。

以下に、このレポートを実行するために必要な手順を示します。

  1. アプリケーションランチャーをクリックし、管理 | オペレーション | GMV レポートの順に選択します。

  2. GMV レポートページの自動生成レポートセクションで、ダウンロードをクリックして、自動生成された GMV レポートをダウンロードします。
  3. エクスポートファイルの管理ページで、そのレポートを開いて .csv ファイルとして PC に保存します。
    レポートのファイル名をクリックしたときに、ファイルが Excel (または別のスプレッドシート) で自動的に開くように、PC を設定することもできます。
  4. Microsoft® Excel または別のスプレッドシートソフトウェアを開きます。
    1. Data (データ) タブをクリックします。
    2. From Text (テキストファイル) ボタンをクリックします。
    3. ダウンロードしたファイルを見つけて、Import (インポート) をクリックします。
    4. Text Import Wizard - Step 1 of 3 (テキストファイルウィザード - 手順 1/3) で、次の設定を保持します:Delimited (コンマやタブなどの区切り文字によってフィールドごとに区切られたデータ)、Start import at Row (取り込み開始行): 1、File origin (元のファイル): MS-DOS (PC-8)。
    5. 次へをクリックします。
    6. Text Import Wizard - Step 2 of 3 (テキストファイルウィザード - 手順 2/3) で、コンマを区切り文字の値として選択します (タブの選択を解除)。
    7. Text Import Wizard - Step 3 of 3 (テキストファイルのインポートウィザード - 手順 3/3) で、設定を変更せずに Finish (完了) をクリックします。
    8. 既存または新規のワークシートにデータを保存します。
    これらの手順は、Excel のバージョンや使用するスプレッドシートソフトウェアにより異なります。

フェールセーフ

フェールセーフとは、エラーが発生した場合にシステムを安全な状態にする決定ロジックを実装することを意味します。エラーを安全に処理することで、例外などのエラーパスによって、エラーが発生しなければ提供されることのない追加情報が公開されないようにします。攻撃者はこの追加情報を使用して、システムをどのように攻撃するかを学習することができます。

以下に、ベストプラクティスの一部をあげます。

  • Web サーバーの構成についての情報を公開するエラーメッセージは使用しないようにします。攻撃者が潜在的な脆弱性を特定する助けとなる場合があります。
  • ユーザーの列挙を防止するために、「ユーザー名が見つかりません」や「パスワードが正しくありません」ではなく、一般的な「ユーザー名またはパスフレーズが無効です」というメッセージを使用します。

B2C Commerce での機能スイッチ (トグル) の設定

Salesforce B2C Commerce では、デフォルトで無効に設定されている新機能を導入する場合があります。これは、既存のサイトに障害が発生する可能性があるからです。

必要なエディション

使用可能なソリューション: B2C Commerce

たとえば、新機能によって後方互換性なしに基本的なシステムの動作が変更されることがあります。この機能を有効にする前に、サイトで変更の準備をしていることを確認してください。機能スイッチでは、準備が整った時点で初めて新機能を有効にすることができます。

一般的に、まず 1 つまたは複数の SIG インスタンス (サンドボックス) で機能を有効にし、サイトの変更をテストします。変更が予想通りに機能することを確認した後に PIG インスタンスで機能を有効にします。

機能スイッチ (トグル) を有効にするには、次のステップを実行します。

  1. Business Manager で、アプリケーションランチャーをクリックし、次に管理 > グローバル環境設定 > 機能スイッチの順に選択します。
    機能トグルのページが開きます。このページには、機能が表示される場合と、表示されない場合があります。機能トグルがページに含まれていない場合は、次のメッセージが表示されます: 「現在表示されている機能トグルはありません。」
  2. 有効にしたい機能をチェックします。
    管理者はこのページに表示されているすべての機能トグルに対し、読み取り専用または読み取りと書き込みの許可をもつことができます。
  3. 適用をクリックします。

B2C Commerce のファイルフォーマット

B2C Commerce では、B2C Commerce スキーマファイルに準拠する XML インポートファイルのみを使用できます。B2C Commerce の旧バージョンでは、コンマ区切り値 (CSV) ファイルの事前処理が可能でしたが、B2C Commerce ではこの機能がサポートされなくなりました。

CSVFileReader クラスを使用して CSV を XML に変換するスクリプトを作成することもできますが、代わりにサードパーティのプログラムを使用して、.csvファイルを必要な XML 形式に処理します。処理に大量のメモリが割り当てられている .NET または Java プラットフォームを使用してファイルを変換する方が格段に高速かつ効率的です。

B2C Commerce で生成されるファイル形式

B2C Commerce ではファイルが常に XML 形式でエクスポートされます。例外はクーポンコードで、これは CSV 形式でエクスポートされます。

ファイル転送

ファイルをインポートする前に、マーチャントのシステムから B2C Commerce インスタンスにファイルを転送します。ファイルをエクスポートしたら、それを B2C Commerce インスタンスからバックエンドシステムに転送します。

WebDAV、FTP、HTTPS を使用してファイルを転送します。FTPS (FTP over SSL/TLS) は、外部システムと B2C Commerce の統合ではサポートされていません。

サイトのインポートとエクスポート - インポートのファイル形式

サイトのインポートとエクスポートを使用してインポート用に zip ファイルを作成したい場合は、まずフォルダーを作成します。

インポートしたい XML ファイルをそのフォルダーに追加します。XML ファイルに、そのタイプのオブジェクトをインポートするための標準名が指定されており、オブジェクトタイプのスキーマに準拠していることを確認します。

また、バージョン情報を含む以下の形式のテキストファイルを追加します: 

###########################################
# Generated file, do not edit.
# Copyright (c) 2022 by Salesforce, Inc.
###########################################
22.5.0

フォルダを圧縮し、そこに含まれるフォルダと同じ名前を付けます。

メモ Mac を使用している場合は、コマンドラインでフォルダーを圧縮し、右クリックメニューの「フォルダーの圧縮」機能は使用しないでください。B2C Commerce では、圧縮されたフォルダーは無効な形式として扱われます。

B2C Commerce でのデータの検証

Business Manager からファイルを手動でインポートした場合は、B2C Commerce スキーマに対する XML インポートファイルの検証は自動的に行われます。ファイルをインポートするカスタムパイプラインを作成する場合は、検証する XML インポートファイルの ValidateXML パイプレットを含めます。

大部分の B2C Commerce スキーマでは、スキーマ内のすべての要素が任意として指定されています。この方法を使用して、各フィードに必要な要素のみを含めます。ただし一部の例外を除き、要素の依存性を確認するためのデータ検証は行われません。

たとえば、商品とカテゴリの割り当てをインポートする場合に、割り当てで参照されるカテゴリが存在しないと、カテゴリの割り当ては無視され、ログにレポートされます。

最小権限の原則の適用

最小権限の原則は、ゼロトラストの中核をなす概念です。最小の権限を実装するとは、ユーザー、アプリケーション、システム、その他のコンポーネントに、それぞれのジョブを実行するために必要な最小限の権限レベルのみを付与することを意味します。

組織内で責任を分離できるように、アプリケーションに粒度を取り入れて設計するようにします。たとえば、分析をチェックすることのみを目的とするユーザーアカウントでは、マスターカタログを管理する許可は必要ありません。この場合、このユーザーアカウントは Business Manager の Analytics を確認する権利のみをもちます。カタログの管理などのその他の権限はブロックされます。

効率的に管理された役割ベースのアクセス管理 (RBAC: Role-Based Access Control) によって、これらの実装が可能になります。RBAC では許可のセットに基づいて役割を作成できます。ユーザーの許可の管理は、対応する役割にユーザーを割り当てるだけですむようになりました。

最小権限には次の利点があります。

  • 明示的な許可のない、高レベルの権限を必要とする操作を、ユーザーが誤って実行することがありません。
  • 悪意をもつ内部の人物が、必要以上の権限を付与されたアカウントを利用して、攻撃を進めることができません。
  • 攻撃者が不適切に付与された許可を利用して、簡単に攻撃を行うことができません。

たとえば、すべての Business Manager ユーザーと Open Commerce API (OCAPI) クライアントには、「デフォルトで拒否」の許可が設定されています。ジョブを実行するために必要な許可を各ユーザーに提供するのは、管理者の責任です。

また管理者は、すべてのユーザー、役割、許可が最新のもので、関連性をもっていることを確認します。アカウントを定期的に監査することが、このプロセスの助けとなります。

秘密鍵と公開鍵のペアの生成

DKIM 認証では、B2C Commerce の Business Manager で秘密鍵を指定する必要があります。これらのコマンドを使用して、端末で秘密鍵を生成します。

所有している Salesforce Commerce 製品

  1. 秘密鍵を生成するには、openssl genrsa -out private.pem 2048 を入力します。
  2. 秘密鍵を p12 形式に変換します。

    p12 (PKCS#12) ファイルは、秘密鍵、公開証明書、および中間 CA 証明書をパスワードで保護された 1 つのファイルに格納および転送するために使用される安全なバイナリ形式です。

    1. openssl req -new -key private.pem -out tmp.csr -subj "/CN=dkim01/O=customer" を入力します。
    2. openssl x509 -days 3650 -signkey private.pem -in tmp.csr -req -out "tmp_certificate.pem" を入力します
    3. openssl pkcs12 -export -inkey private.pem -in "tmp_certificate.pem" -out private_key.p12 -password pass:12345 を入力します
  3. DNS で公開する公開鍵をエクスポートします。openssl rsa -in private.pem -pubout -out public.pem を入力します

B2C Commerce の汎用マッピング

汎用マッピング機能を使用してキーを値にマッピングし、マッピングを高パフォーマンスのデータストアに格納します。汎用マッピングでは大規模なデータセットがサポートされており、高パフォーマンスで検索することができます。このトピックは、B2C Commerce に該当します。

たとえば、B2C Commerce スクリプトを使用して、バックエンドシステムの SKU を B2C Commerce の SKU にマッピングします。この手法により、バックエンドシステムとの相互作用が透過的に行われ、B2C Commerce SKU をサードパーティのシステムに追加する必要がありません。

汎用マッピングを使用するために、B2C Commerce の顧客は、データベース内の商品データを補完するインメモリのキーと値のペアにアクセスできます。

汎用マッピングの使用手順

一般的に、汎用マッピングを使用するには以下の手順に従います。

  1. マッピングを作成します。
  2. B2C Commerce サーバーにマッピングをアップロードします。
  3. ImportKeyValueMapping ジョブステップを作成します。
  4. B2C Commerce スクリプトを使用してマッピングから値を読み取ります。

マッピングの作成

.csv (コンマ区切り値) ファイルを作成してマッピングを保存します。以下のガイドラインに従います:

  • 各キーおよび関連する値を 1 つの行に配置します。
  • キーと値をコンマで区切ります。
  • マップにインポートする.csvファイルに、行ごとに一定数のエントリがあることを確認します。

.csv ファイルの各行の書式は以下のとおりです:

(<key>[,<key2>,…],<value1>[,<value2>,<value3>,...])

.csv ファイルの最初の行で、キー値エントリのプロパティ名を定義します。キー値エントリは 2 行目で始まります。汎用マッピングには、.csv ファイルの行数より 1 行少ない数のエントリが含まれます。MappingMgr.get(mapping, key) を呼び出すと、プロパティ名をキー値とする新しいマップが取得されます。

インポートで不正な形式のレコードが検出されると、インポートは失敗し、例外がログに記録されます。

マッピングをインポートする前に、アプリケーションサーバーからアクセス可能な場所にアップロードしてください。たとえば、Business Manager のアップロードページや FTP を使用します。各インスタンスでマッピングを明示的にインポートします。マッピングはグローバルです (サイト固有ではありません)。

マッピングファイルは 20 MB に制限されています。これは、各 20 バイトのレコードが 100 万件、および最高 20 個のマッピングに相当します。

B2C Commerce の HTTPS / TLS

HTTPS では、通信プロトコルはトランスポートレイヤーセキュリティ (TLS)、またはこの元になった SSL (Secure Sockets Layer) を使用して暗号化されます。またこのプロトコルはしばした HTTP over TLS (TLS を介した HTTP)、または HTTP over SSL (SSL を介した HTTP) とも呼ばれます。

常にHTTPSを使用して、ネットワークを通過するデータを保護します。HTTPS を使用しないと、データはクリアテキストとして送信され、攻撃者が機密情報を見ることができます。HTTPS の強制を設定して、HTTP を使用する受信ページを HTTPS にリダイレクトすることをお勧めします。サイトごと、またはインスタンスのすべてのサイトに対して設定を構成します。HTTPS をグローバルに強制すると、Salesforce B2C Commerce ではサイトレベルの設定が無視されます。ただし、このグローバル環境設定を無効にすると、サイト固有の設定は元の値に戻ります。TLS ではサーバー証明書が要求され、相互 TLS (MTLS) ではクライアント証明書が要求されるため、自分の証明書をサイトの鍵ストアにアップロードする必要があります。

また、B2C Commerce で HTTP Strict Transport Security (HSTS) を使用するように構成できます。これによって、HTTPS のみを使用してドメインにアクセスするように Web ブラウザーに指示できます。さらに HSTS は、攻撃者がサイトに対してダウングレード攻撃を使用できないようにします。セキュリティを高めるために、事前読み込み を有効にできます。これによって、サイトが初めてリクエストされた際に、Web ブラウザーがサイトを HTTPS で開くように強制されます。サイトに保護されていないコンテンツがあり、HSTS が有効の場合、このコンテンツは買い物客の Web ブラウザーには表示されず、サイトを表示することはできなくなります。HSTS を有効にする前に、サイトが完全に保護されていることを確認することが重要です。

HSTS を無効にすることもできますが、ビジネスの中断を防ぐために、以下の 2 つのステップによるプロセスを使用してください。

  1. 保護されていない接続を使用して買い物客がサイトにアクセスすることを許可します。
  2. サイトのヘッダーで HSTS の送信を中止します。
メモ TLS 1.1 はサポートされなくなりました。マーチャントは TLS 1.2 を使用する必要があります。TLS 1.2 はセキュリティとデータ整合性のためのベストプラクティスに従うために、B2C Commerce で使用される最低標準のセキュリティプロトコルです。

B2C Commerce Hyperforce に関するよくある質問 (FAQ)

Salesforce B2C Commerce インフラストラクチャは現在アップグレード中であり、Salesforce のファーストパーティデータセンターから、パブリッククラウドテクノロジーを活用した次世代型クラウドインフラストラクチャプラットフォーム、Salesforce Hyperforce へと移行しています。

Salesforce の他のほとんどのクラウドも Hyperforce に移行するため、この取り組みには数年かかります。Hyperforce への移行は、B2C Commerce 製品への当社の最大の投資の 1 つであり、今後何年にもわたってこの製品を維持していくという当社の取り組みを示すものです。

なぜレルムを移行するのですか?

Salesforce は、B2C Commerce の永続性と拡張性に取り組んでいます。当社は、プラットフォームが拡張可能で、成長し続ける組織のニーズを満たせるようにするため、プラットフォームへの投資を行っています。組織の継続的な成長に備えるために、お客様のレルムを新しく改善されたインフラストラクチャに移行することがあります。この変更により、インフラストラクチャのアップグレードとモダナイゼーションが可能になり、Salesforce B2C Commerce に期待されるレベルのパフォーマンスと信頼性を引き続き提供できます。

Hyperforce とは何ですか?

Hyperforce は、パブリッククラウドテクノロジーを活用した Salesforce の次世代型クラウドインフラストラクチャプラットフォームです。Hyperforce の概要と全般情報については、Hyperforce の紹介 - 全般情報とよくある質問 (FAQ) を参照してください。

Hyperforce のメリットにはどのようなものがありますか?

Hyperforce には、クラウドインフラストラクチャとして次のようなメリットがあります。

  • データレジデンシー: データレジデンシーとコンプライアンスの選択肢およびコントロールを強化しながら、世界中の従業員と顧客にサービスを提供できます。
  • 拡張性: ビジネスをより柔軟かつ持続的に成長させ、拡大することができます。リソースのスケールアップやハードウェアのリフレッシュが原因でレルムを移行する必要性がなくなります。
  • セキュリティ: Hyperforce は、最小特権の制御、ゼロトラスト原則、Infrafraction-as-Code (IaC) などの業界をリードする機能により、デフォルト設定でセキュリティが確保されています (セキュアバイデフォルト)。データは転送中も保存中も暗号化されます。
  • プライバシー: Hyperforce は、顧客データの透明性とコントロールを可能にする、包括的なプライバシー標準を提供します。

レルムはどの領域に移行しますか?

新しい Hyperforce レルムは、現在の POD の場所と同じ Salesforce リージョンにあります。

割り当てられた Hyperforce AWS リージョンの物理的な場所はどこですか?

  • us-east-2 — 米国東部 (オハイオ)
  • ap-northeast-1 — 東京、日本
  • eu-north-1 — ストックホルム、スウェーデン
  • ap-southeast-2 — オーストラリア、シドニー
  • ap-south-2 — インド、ハイデラバード

レルムを Hyperforce に移行するためのスケジュールは決まっていますか?

Salesforce は、2024 年の第 4 四半期から数年をかけて、既存のお客様を Hyperforce にアップグレードする予定です。アップグレード日が近づくと、移動予定日の 60 日から 90 日前に Salesforce から通知されます。

引っ越し日の少なくとも1か月前に、お客様には引っ越し前のチェックリストと指示書をお送りします。このチェックリストを利用して、レルムを Hyperforce インフラストラクチャに移行する準備ができていることを確認してください。移行日に、Salesforce エンジニアは証明書を含むすべてのレルムのデータを新しい Hyperforce の場所に移行します。移動中、ストアフロントはメンテナンスモードになります。移動が完了すると、通常の操作に復元されます。

既存のソース POD で現在許可リストに登録されている IP は、新しいサーバーに自動的に移行されますか?

はい。既存のすべてのファイアウォールルールは、ソース Pod から新しい Hyperforce 宛先にコピーされます。

顧客として、引っ越しの準備をするために何をすればよいですか?

レルムの移行日が確定すると、レルムを Hyperforce に移行するための準備を求められます。Salesforce は、サービスを構成してスムーズなアップグレードを確実に行うための重要な手順を説明するチェックリストと詳細な手順を提供します。

移行完了までにどのくらいの時間がかかりますか?

レルム移行は、所定のメンテナンス期間中に行われます。レルムのデータ移行 (メンテナンスページが表示されてからメンテナンスページが削除されるまでの期間で測定) には、通常 2～5 時間かかります。実際の移行時間は、移動するデータ量によって異なります。

その他の Salesforce クラウドも Hyperforce に移行しますか?

Salesforce の他のすべてのクラウドは Hyperforce にアップグレードされます。

新規顧客は Hyperforce でホストされますか?

Salesforce の B2C Commerce プラットフォームへの新規顧客は Hyperforce 上で実行しています。このプロセスは当社が Hyperforce の容量を拡大するにつれ、段階的に行われます。

ファーストパーティの POD 環境は廃止されますか?

すべてのお客様のレルムが Hyperforce インフラストラクチャに移行されると、現在のファーストパーティ POD 環境は廃止されます。

Marketing Cloud や Service Cloud など、他のクラウドとのインテグレーションがある場合、変更を加える必要がありますか?

すべての統合をチェックして、POD の移動後に機能していることを確認します。ほとんどのクロスクラウド統合では、ドメイン名を使用して接続しますが、これはPODの移動によって変更されることはありません。クロスクラウド統合では、直接 IP を使用して接続することはありません。ただし、Marketing Cloud Personalization などの一部のエンドポイントが影響を受ける可能性があります。ポッドの移行後に API 呼び出しが成功しなくなった場合は、新しい宛先の Hyperforce リージョン IP をファイアウォールルールの許可リストに追加します。Hyperforce 外部 IP リストは、https://ip-ranges.salesforce.com/ip-ranges.jsonで入手できます。

開発環境 (Sandbox) も Hyperforce に移行しますか?

上位語と下位語

上位語とは、商品のグループを表す広義の用語です。下位語とは、上位語が定義するグループに含まれる項目を表す用語です。上位語ではその上位語のすべての下位語の結果が返されますが、下位語で返されるのはその下位語の結果のみです。ネガティブ上位語を使用して特定の上位語を除外します。このトピックは、B2C Commerce に該当します。

検索するカテゴリが重複している場合、上位語の検索結果の合計数は、それぞれの下位語の検索結果を合計した数より少なくなることがあります。以下の例では、チュニック、シャツ、ブラウスを個別に検索すると、検索のヒット数の合計は 13 です。一方、チュニック、シャツ、ブラウスを下位語としてもつ上位語 "トップス" を検索すると、検索で返される語の数は 9 つだけになります。これは、一部の検索に一致する語が複数の下位語に該当するためです。個別の検索で返された重複結果は、上位語検索では削除されるため、ヒット数が少なくなります。

メモ 下位語と上位語は、それぞれ 4 個を超える単語で定義しないでください。複数語検索の用語には、一般的なフレーズ機能を使用してください。

たとえば、上位語がfootwearで、下位語が[shoes, boots, sandals, sneakers]である上位語ルールについて考えてみます。

買い物客の検索対象 実際の B2C Commerce クエリ
スニーカー スニーカーまたは履物
ブーツ ブーツまたは履物
フットウェア フットウェア

上位語のfootwearの場合、買い物客がfootwearを検索すると、footwear の検索結果のみが表示され、shoes、boots、sandals、sneakers の結果は表示されません。

ネガティブ上位語

'-' ネガティブ演算子が前に付いた上位語 (単一の語または複数語) を入力した場合、そのネガティブ上位語を含む商品は検索結果として返されません。

handbagがbag上位語の下位語である場合、「bag」を除外するユーザー検索は、「handbag」と「bag」の両方のキーワードを除外する検索に拡張されます。

画像管理

B2C Commerce の画像管理システムを使用して、各商品の画像のマトリックスを作成します。

ストアフロントで画像を使用することで、買い物客の購入体験を向上できます。画像管理システムでは、以下をサポートしています:

  • 各商品に複数の画像、また、バリエーション商品とバリエーション商品属性の個別の画像および画像下位セットへの多次元的アクセス
  • 代替テキストと画像タイトルによる画像注釈
  • B2C Commerce 内と B2C Commerce 外の両方に保存されている画像
メモ 商品画像管理では、画像を商品に明示的に割り当てることが必須です。パターンベースの画像検索はありません。

画像管理システムは、B2C Commerce および外部システムにある画像に、URL 参照によってアクセスします。画像の場所は、カタログとの関連で定義する必要があります。カタログでは、内部または外部の画像保存先を指定できます。デフォルトの場所 (保存先を指定していない場合) は、関連する内部カタログベースディレクトリを指します。

System URL アドレス
内部 システムでは URL の最初の部分 (サーバーアドレス、URL の他の部分) が認識されます。"/images/foo/" などのベース画像パスを指定します。
外部

URL の最初の部分を指定します。http URL または https URL (プロトコル、サーバーアドレス、URL のその他の部分) を指定します。

例:

http url = "http://www.yourimagelocation.com/foobar/"

https url = "https://yoursecureimagelocation.com/foo/bar/"

B2C Commerce では、画像の場所と画像の相対パスが別々に保存されます。

  • B2C Commerce では、画像の場所がカタログとともに保存されます。
  • B2C Commerce では、商品とともに画像の相対パスが保存されます (例: "bar/your_image.gif")。
メモ 商品画像 URL のパスは 1,800 文字以内で構成します。カタログの画像設定で構成するホストパスと合わせると、画像 URL は半角 2,056 文字以内で指定できます。これより長いパスを構成しようとすると、Business Manager に警告が表示され、その商品の画像設定を保存できなくなります。
メモ API クラス dw.content.MediaFile は、両方のパスに基づいて完全な URL を提供します。詳細については、B2C Commerce API のドキュメントを参照してください。

  • 表示タイプ
  • 画像バリアント
  • スウォッチ
  • 画像の注釈
  • 画像保存スペース
  • 画像変換サービス

Dynamic Imaging Service

B2C Commerce Dynamic Imaging Service では、ストアフロントの要件を満たすために異なるサイズの画像をアップロードする必要がなくなります。高解像度のソース画像をアップロードすると、Dynamic Imagingは、製品ページ、カタログページ、推奨製品、検索結果など、各画像アプリケーションに適したサイズをフォーマットします。パラメータを適用して、画像サイズ、切り抜き、オーバーレイ、フォーマット、背景色、および品質設定を制御します。

所有している Salesforce Commerce 製品

たとえば、ストアフロントに 100,000 点の商品カタログがあるとします。Web デザインは最大 150x150 ピクセルの画像をサポートし、顧客の検索結果の 1 行あたり 4 つの画像を表示します。Web デザイナーが別のレイアウトを作成し、商品検索に 1 行あたり 250 x 250 ピクセルのサイズの画像が 3 つだけ表示されるようになりました。サイズ変更された画像をアップロードする代わりに、Dynamic Imaging Service は既存の画像のサイズを変更します。

画像変換 URL の作成

URLUtilsクラスとMediaFileクラスは、1 つの高解像度画像から複数の画像リソースを動的に生成します。画像変換 URL は、キャッシュ可能なリソースを識別し、その変換方法を指定します。

これらのクラスを使用するのは、API が変換パラメーターを検証し、基本的な URL パターンが将来変更されるのを防ぐためです。URL をハードコードすると、パターンが変更されると機能しなくなる可能性があります。

JavaScript オブジェクトリテラルには、変換パラメーターが含まれています。各メソッドは、変換パラメーターから派生した URL を返します。パラメーターを Dynamic Imaging Service に渡さない場合、画像は元の構成で渡されます。

例: URL パラメーターcyが変換パラメーターcropYに置き換わります。

public URL absImage( String context, String contextID, String relPath, Object transform );
public URL httpImage( String path, Object transform );
public URL httpImage( String context, String contextID, String relPath, Object transform );

public URL httpsImage( String context, String contextID, String relPath, Object transform );

( oimg ) オーバーレイ値は、Dynamic Imaging Service ドメインによって提供される顧客所有のイメージを指す必要があります。

品質 品質 (q)

quality パラメーターは、JPG および JP2 画像の品質設定と、PNG 画像の圧縮レベルを指定します。

JPG および JP2 画像の場合、最高品質を得るには 1 から 100 までの値を設定します。既定値は 80 です。デフォルト値を維持するには、値を省略します。

PNG 画像の場合、圧縮は常に可逆圧縮であるため、画質設定は PNG の外観に影響しません。代わりに、品質設定を使用して、zlib 圧縮レベルとフィルタータイプを 2 桁の数値として設定します。最初の桁は zlib 圧縮レベル (1 から 9) を設定します。2 桁目はフィルターの種類を設定します。

PNG 設定が指定されていない場合、または 0 に設定されている場合、デフォルト値は 75 です。この設定を 100 (3 桁の数字) に設定すると、実際には品質設定の 90 と等しくなります。
メタデータ ストリップ

strip パラメータは、変換中に EXIF やカラープロファイルなどのメタデータを画像から削除するかどうかを指定します。

有効な値はtrueまたはfalseです。既定では、データが削除されます ( true )。
背景 Bgcolor

bgcolorパラメーターは、透明度をサポートするイメージ、または透明度をサポートする形式から変換された JPEG イメージの背景色を指定します。6 桁の 16 進数の RGB 値を入力します。PNG 画像の場合は、オプションの 2 文字のアルファ値も適用して透明度を指定します。

たとえば、FF0000 = Red;FF000077 = 透明度 50% の赤。

アルファ値を省略すると、結果の色は不透明になります。アルファ値として 00 を明示的に渡しても、同じ結果が得られます。アルファ値は、画像出力形式がPNGの場合にのみ有効です。

増分インデックス

商品またはカテゴリの割り当てが更新されたとき、またはスケジュールされているときに増分で再作成するように、B2C Commerce のインデックスを構成できます。インデックスに増分インデックスを有効にすると、インデックスの基礎となる商品、コンテンツ、または検索の構成に変更が行われるたびにインデックスが自動的に更新されます。インデックスへの変更はマーチャントが変更を行った 30 秒後に使用可能になります。増分インデックスは、各インスタンスの各インデックスタイプで有効または無効にできますが、インスタンスのすべての地域情報にも適用されます。

増分インデックス作成を使用すると、手動でインデックスを再構築したり、完全インデックスが再作成されるのを待ったりする必要がなくなるため、インデックスへの変更をすぐに確認できるため、開発に役立ちます。

インデックスに増分インデックスが無効になっている場合は、商品、コンテンツ、または検索の構成に変更が行われるたびにインデックスを手動で再作成する必要があります。インデックスがかなり断片化された場合、検索のパフォーマンスに影響が生じることがあるため、増分インデックスを有効にした場合も定期的にインデックスを再作成することが推奨されます。インデックスを毎日再作成することがベストプラクティスです。

メモ

入手可能性検索増分インデックスは自動です。有効または無効にすることはできません。

たとえばインポート中に、検索インデックスに関連するデータがロックされている場合、検索インデックスの増分更新はスキップされ、他のロック処理が完了するまで延期されます。これによって、大規模な操作中に多数のデータ変更が行われる場合に、不必要な増分更新が発生することを防ぐことができます。

完全インデックス再作成とは異なり、増分インデックスではすべての検索機能が更新されるわけではありません。インデックスが作成されたオブジェクトが変更、追加、または削除されたときに、B2C Commerce でインデックスが更新されます。

重要 増分インデックスが有効な場合も、断片化とパフォーマンスの劣化を防ぐために、インデックスを定期的に更新することを推奨します。

インデックスの作成

B2C Commerce の検索インデックスでは、商品、スペリング、コンテンツ、同義語、提案、入手可能性、アクティブデータの各インデックスに含まれるデータが使用されます。

商品インデックス

商品が検索結果に表示されるのは、商品が検索可能で、オンラインで、かつ少なくとも 1 つのオンラインカテゴリに割り当てられている場合のみです。商品がオンラインカテゴリとオフラインカテゴリの両方に割り当てられている場合でも、インデックスは作成されます。検索可能属性として構成された商品属性にのみインデックスが作成されます。

メモ バリエーションモデルの一般的な商品属性の継承モデルは次のようになります。
  • null 以外の値
  • バリエーショングループの値
  • マスター商品の値
ストアフロント検索の検索インデックスのドキュメントを作成する際には、(バリエーション商品が属性に null 以外の値を正しく定義している場合でも) バリエーション商品とマスター商品の属性値を考慮し、検索にはバリエーション商品とそのマスター商品からの値を使用します。

たとえば、main product.refinementColor=red かつ variation.refinementColor=blue の場合、商品は red と blue の検索で見つけることができます。

インデックス用語は、以下の処理ステップを経て商品データから抽出されます。

  • 同義語: 同義語は、いずれの用語もすべての用語の検索結果を返すように設定されます。たとえば、pants と trousers が同義語である場合、pants を検索すると pants と trousers が返され、trousers を検索すると pants と trousers が返されます。ドイツ語のウムラウトをもつ単語 (例: ‘küche’、‘kueche’) には同義語が追加されます。
  • 上位語: 上位語からは一連の下位語からのすべての結果が返されますが、下位語からはその下位語の結果のみが返されます。たとえば、winterwear が、hats、gloves、mittens の上位語である場合、 winterwear を検索すると、 hats、gloves、mittens が返されますが、 hats を検索すると、hats が返され、gloves を検索すると、gloves が返され、 mittens を検索すると mittens のみが返されます。
  • ストップワード: 検索エンジンが無視する単語です。たとえば、"an" や "the" です (英語で検索する場合)。これにより、インデックスが簡素化され、検索結果が返される速度が上がります。ストップワードはストップワード辞書に基づいて削除されます。
  • 複合語: マーチャントはフレーズとして、および単一の語として検索されるフレーズを指定します。たとえば、顧客が cheese cake を入力し、これが複合語である場合は、"cheese AND cake" と "cheesecake" の結果が返されます。複合語は複合語の辞書に基づいて、複数の部分に分割されます。
  • 一般的なフレーズ : マーチャントは、一緒に見つかった単語を検索ヒットとしてカウントするか、完全なフレーズまたはフレーズ内の最後の単語が見つかった場合に検索ヒットとしてカウントされる単語を指定します。
  • 語幹: 検索可能な商品属性に含まれるすべての単語は、各インデックスのタイプに設定された語幹規則に基いてステミングされます。語幹規則を使用することによって、顧客は単語の語幹に基いて商品を検索できるようになります。
  • 特殊記号: ! ( ) : [ ] { } + ~ ^ ? ' は削除されます。
  • 商品番号: 商品番号は、複数の部分に分割されます。
メモ インデックス作成中のサイトと同じ通貨をもつ価格表のみにインデックスが作成されます。たとえば、サイトの通貨が USD (米ドル) の場合、すべての EUR (ユーロ) 価格はサイトのインデックスに含まれません。

スペリングインデックス

顧客が用語を検索したが検索結果が何も見つからなかった場合、スペリング提案機能によって検索用語が分析され、スペルの間違いがチェックされて、商品セットに見つかった類似の用語が提示されます。たとえば、顧客が "telewision" を検索すると、 "television" でないかどうか尋ねられます。

スペリングインデックスはアルゴリズムを使用してコンパイルされるため、手動で設定する必要はありません。ただし、この機能は Business Manager の検索の環境設定ページで有効にしてください。スペリングインデックスは商品インデックスとコンテンツインデックスを使用するため、それらの後に再作成する必要があります。

コンテンツインデックス

コンテンツインデックスはコンテンツアセット、ライブラリフォルダー、ライブラリに基づいて作成されます。コンテンツアセットは、検索可能でオンラインの場合にのみ検索結果に表示されます。検索可能として設定されたコンテンツ属性のみにインデックスが作成されます。コンテンツインデックスでは、インデックス用語の抽出に商品インデックスと同じ処理ルールを使用します。

同義語インデックス

同義語インデックスは、特定の言語に定義された同義語/同義語グループに基づいて作成されます。すべての同義語は、設定されたステマーに基づいて語幹処理されます。

提案インデックス

提案インデックスは、Business Manager の検索の提案ページで追加または除外されたカテゴリ名、ブランド名、および用語に基づいて作成されます。

元の値に大文字が含まれている場合も、すべての提案は小文字に変換されて表示されます。提案は、提案に関連付けられた結果が少なくとも 1 つある場合にのみ表示されます。

検索結果カウントを判別するため、各提案について、インデックスの再作成中に現在の商品インデックスを使用して検索が実行されます。提案インデックスを作成する前に商品インデックスを作成して、正確なカウントを取得します。

入手可能性インデックス

在庫レコードに商品が存在しない場合も入手可能性インデックスには在庫データが含まれます。これにより、入手可能性の更新とデータのレプリケーションが分けられるため、相互に依存することがありません。新規商品の入手可能性インデックスを更新すると、新規商品が Staging (ステージング) から Production (本番) にレプリケートされると、検索結果にただちに表示されます。これは、関連する入手可能性データがすでに Production (本番) の入手可能性インデックスに含まれているためです。

次の特定のルールが適用されます:

  • 入手可能性インデックスは既存のすべてのサイト (および在庫リストの複数サイト) に含まれる商品の在庫レコードを処理します。
  • 入手可能性インデックスは在庫レコードに商品が存在しない場合、かつ、過去 5 日以内に在庫レコードが作成または変更された場合に、在庫レコードを処理します。
  • 入手可能性インデックスは在庫レコードに商品が存在しない場合、かつ、過去 5 日以内に在庫レコードが作成または変更されていない場合は、在庫レコードをスキップします。これは、使用されておらず古いと見なされる在庫レコードが処理されないようにするためです。
  • 新規商品がマスター商品または商品セットの場合、またはバリエーション商品または商品セットの一部である場合で、適用される並べ替えルールが SKUCoverage または TTOOS (Time to Out of Stock: 在庫切れまでの時間) などの集約入手可能性属性を使用していると、検索結果の並べ替えが正しく行われないことがあります。これは、検索インデックスが商品についての情報を何ももたない場合は、その複合商品のデータを集計できないためです。商品データがレプリケートされ、入手可能性インデックスが再作成され、ページキャッシュが更新されると、並べ替えが正しく行われるようになります。

入手可能性インデックスは、在庫ステータスによる検索結果を並べ替えてフィルターするために使用される、商品の入手可能性の情報に基づいて作成されます。このインデックスは、在庫量を更新するトランザクションに依存するため、定期的な再作成が必要です。同じ在庫リストに割り当てられた B2C Commerce サイトは、検索入手可能性インデックスを共有します。在庫リストごとに 1 つのインデックスのみが保守されます。

メモ ユーザーまたはカスタムジョブによる検索入手可能性インデックスの完全更新または増分更新は不要になりましたが、検索入手可能性インデックスの再作成がトリガーされます。ただしこれは、インデックスが同期していないなど予期しない事態が発生した場合のみです。

検索入手可能性インデックスは次の場合に自動的に増分更新されます:

  • インポートにより在庫レコードが更新されます
  • 在庫レコードが Business Manager で更新されたとき
  • 買い物客はストアフロントで注文を行います
メモ 共有検索入手可能性インデックスに変更が反映されるまでに、5 分以上かかることがあります。
メモ スクリプティング API パイプレット UpdateSearchIndexes が入手可能性 インデックスタイプに使用されても、処理は何も行われません。

入手可能性インデックスは、Staging (ステージング) システムから Production (本番) システムにレプリケートされません。代わりに、本番システムで作成されて更新されます。

アクティブデータインデックス

アクティブデータインデックスは、ストアフロントから収集されたアクティブデータ属性、バックエンドシステムからインポートされたアクティブデータ属性、または B2C Commerce で計算されたアクティブデータ属性を含めるために使用します。アクティブデータ属性は、並べ替えオプションを顧客に提示するときに使用されます。また、カテゴリ検索またはキーワード検索の並べ替えルールでも使用されます。

アクティブデータインデックスには、販売速度など商品のアクティブデータについての情報が含まれています。日次アクティブデータフィードによって、このインデックスは 1 日 1 回自動的に再作成されます。インデックスを手動で再作成するのは、カスタムフィードをインポートした後にしてください。

この拡張機能は、Google Chrome ブラウザーでのみ使用できます。Chrome ウェブストアで B2C Commerce Recommendation Validator 拡張機能を検索してインストールします。

  1. Chrome ブラウザーで Chrome ウェブストアに移動します。
  2. B2C Commerce Recommendation Validator 拡張機能を検索します。
    拡張機能は Chrome の拡張機能リスト表示に表示されます。
  3. Chrome に追加をクリックします。
    Chrome によって拡張機能が追加されます。
  4. インストールを確認するために、拡張機能を追加をクリックします。
    アドレスバーの右側に拡張機能のアイコンが表示されます。

Data 360 for B2C Commerce のアセット

Commerce データキットが Data 360 にインストールされると、すべての Data 360 アセットとデータマッピングが作成されます。Intelligence Analytics ダッシュボードをインストールすると、データ変換が実行され Data 360 データが取り込まれ、CRM Analytics ダッシュボードとコンポーネントが作成されます。

所有している Salesforce Commerce 製品

インストールが成功すると、アプリのアセットが [セットアップ] ページの [リソース] に表示されます。これには、Data 360 のデータ変換とデータモデルオブジェクト (DMO)、さらに CRM Analytics のダッシュボードとコンポーネントが含まれます。アセットを選択すると、それぞれのツールで開き、詳細な検査を行うことができます。
