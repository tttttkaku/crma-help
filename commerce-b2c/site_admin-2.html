B2C Commerce のサイトトラフィックの移行

eCDN にトラフィックを移動するために、トラフィック移行を構成します。

必要なエディション

使用可能なソリューション: B2C Commerce
  1. この作業を行うには、事前にホスト名を検証します。このステップは、次の条件に該当する場合に必要です。
    • eCDN にトラフィックを移動する際にダウンタイムを防止したい。
    • Akamai などのサードパーティーの CDN を eCDN の前にスタックしたい。
    各ホスト名について、TXT レコードを DNS プロバイダーに送信し、ドメインのコントロールを検証します。TXT レコード、ホスト名、およびターゲットは、検証されていないホスト名に対する GET certificates (証明書の取得) 呼び出しの応答にリストされています。getCertificates を参照してください。
    • TXT 検証レコードの例:
    _cf-custom-hostname.stg.mystore.com. IN TXT 3adc7a39-12d7-4baf-be1b-c5ea5295181b

    B2C Commerce Engineering が eCDN 構成を完了している場合は、TXT 検証レコードが提供されます。

    重要: 検証レコードはできるだけ早く送信してください。構成の作成後、自動検証チェックが 7 日間、最大 4 時間間隔で実行されます。検証を 7 日以内に完了しなかった場合は、B2C Commerce エンジニアリングに手動で検証チェックを再開するようにリクエストできます。

  2. トラフィックを eCDN に直接送信するには、DNS を CNAME 値に更新します。CNAME ターゲットでは commcloud.<ゾーン名> という書式が使用されます。
    CNAME レコードの例:

    stg.mystore.com. IN CNAME commcloud.stg-abcd-mystore-com.cc-ecdn.net.

    メモ ホスト名を事前検証しなかった場合は、トラフィックを eCDN に直接送ることで、検証が行われます。この方法では、DNS を更新してから次の検証チェックまでの間、ダウンタイムが発生します。
  3. (オプション) サードパーティーの eCDN をスタックします。このステップでは、検証済みのホスト名が必要です。
    eCDN への接続で SNI が使用されていることを確認します。eCDN 構成には SNI が必要です。
    • Akamai では、上流接続の SNI サポートはデフォルトで無効になっています。Akamai の起点サーバーの動作の構成に関するドキュメントを参照してください。SNI Transport Layer Security (TLS) 拡張を有効にします。
    • その他のすべての CDN では、デフォルトで有効になっていない場合、CDN プロバイダーと協力して SNI を有効にする方法を決定してください。Business Manager で推奨される設定については、外部 CDN またはサードパーティプロキシの構成を参照してください。提供された CNAME のターゲット値を起点サーバーとして使用します。
  4. (オプション) TXT 検証レコードを削除します。
    レコードを削除する前に、ホスト名が検証されていることと、トラフィックが eCDN に流れていることを確認します。

B2C Commerce の複数通貨のサイト

Salesforce B2C Commerce の複数通貨のサイト機能によって、複数の国や地域で商品を販売できます。この機能を利用することで、顧客が好みの通貨で商品の検索や注文手続きを行うことが可能になります。

1 つのサイトで、異なる通貨を使用して複数の国で販売することが可能です。複数通貨のサイトは同時に 150 種類の通貨をサポートできます。

以下の場合に、この機能の使用を検討してください。

  • 通貨によって商品の価格や配送方法、配送料、支払方法、およびプロモーションが異なる、複数通貨のサイトをもちたい。
  • サイトのロジックと設計、カタログとコンテンツ、検索とマーチャンダイジングルール、顧客、在庫、サードパーティの統合、および注文管理が全通貨を通して同じである。

複数通貨のサイトに対するサポートは、B2C Commerce の特定エリアに限られます。

セッション通貨

複数通貨のサイトはセッション通貨 に依存します。バージョン 14.2 のリリースまで、B2C Commerce はサイト通貨を使用して価格の検索、買い物カゴの計算、注文手続き操作、注文の確定、計算などの機能を実行してきました。バージョン 14.2 のリリースからは、セッション通貨を代わりに使用できます。

顧客が初めてストアフロントにアクセスする際、その顧客のセッション通貨は、サイトのデフォルト通貨で初期化されます。顧客が異なる通貨を選択するまで、B2C Commerce はデフォルト通貨をセッション通貨として使用します。顧客がこの機能を利用できるようにするには、カスタムビジネスロジックを使用します。

B2C Commerce はセッション通貨を常に記憶し、顧客がストアフロントに戻った際に適切に復元します。ただし、特定の顧客のセッション通貨は無効になることがあります。たとえば、許可されている通貨をサイト管理者が削除した場合です。このようなシナリオでは、この顧客がストアフロントに次回にアクセスした際に、B2C Commerce によってセッション通貨がデフォルトのサイト通貨にリセットされます。

セッション通貨は、構成されたサイトで使用できる通貨のいずれかである必要があります。顧客は、無効な通貨を使用して、注文手続きへ移動したり、注文を作成したりできません。

レポートとアナリティクス

収益金額をレポートする以下の機能では、複数通貨のサイトがサポートされています:

機能 コメント
A/B テスト A/B テストの文脈で注文を行った場合、A/B テスト統計には換算した金額が反映されます。
アクティブデータ 注文を確定する顧客のアクティブデータと注文商品のアクティブデータは、換算された通貨価値を反映して変更されます。
Reports & Dashboards レルムの通貨設定を変更して、すべてのサイトの集計レルムデータを、選択した通貨で表示できます。

これらの機能には、ストアフロントの購入データを使った収益メトリクスが用意されており、検索の並べ替えや顧客の区分けのために表示または使用できます。B2C Commerce が収益イベントを記録する場合、すべての通貨の価値は、サイトのデフォルト 通貨に換算されます。この換算では、その日に該当する為替レートが使用されます。

たとえば、サイトのデフォルト通貨は米ドル (USD) ですが、サイトは USD とユーロ (EUR) の両方をサポートしているとします。顧客が注文を行い、通貨として EUR を選択した場合、注文金額はその日の為替レートを使用して EUR から USD に換算されます。

B2C Commerceは、各通貨について個別のレポートを提供しません。為替レートサービスは B2C Commerce 内で行われるため、Business Manager には表示されず、B2C Commerce API でも利用できません。価格は定期的に更新される為替レートサービスに基づいているため、サブシステムによって提供されるメトリクスは複数通貨のシナリオにも適しています。

今後のリリースで対応する機能制限

複数通貨のサポートは、まだ B2C Commerce のすべてのエリアでは利用できません。特に Analytics では、購入レポートには、すべての通貨のすべての注文が含まれます。通貨によって区別されることはありません。

生成された SEO URL の上書き

URL ルールモジュールが有効な場合、ページ URL 属性を使って、URL ルールモジュールの構成によって生成される URL を上書きできます。この上書きで作成された URL に文字置換を適用できます。

必要なエディション

使用可能なソリューション: B2C Commerce
メモ このトピックでは、URL ルールモジュールが有効であり、廃止予定の SEO サポートモジュールを使用していないものと想定します。SEO サポートモジュールで生成された URL を上書きする方法はありません。ページ URL 属性をルール構文に含めて、エンドポイントをカスタマイズできるようにします。

ページ URL 属性を使って、生成された URL を Salesforce B2C Commerce で上書きできるように構成するには:

  1. アプリケーションランチャーの順にクリックし、マーチャントツール | サイト | SEO & 検出可能性 | URL ルールの順に選択します。
  2. 設定する URL のタイプに応じて、カタログ URL またはコンテンツ URL タブをクリックします。
  3. 適切な URL ルールセクションで、'pageURL' カテゴリ属性による上書きを有効にする (設定されている場合) にチェックを入れます。
  4. ページ URL 属性に適切な値をインポートするか、Business Manager で商品に移動し、ページ URL フィールドに値を追加します。
  5. SEO URL が再生成されるのを待ちます。URL ルールページの全般タブで、生成ジョブのステータスを監視します。

URL の戦略を練る際は、手動で ページ URL 属性値を作成し、テストすることをお勧めします。入力フィードを使用する代わりに、Business Manager に手動で入力します。

カテゴリ URL を手動で作成するには:

  1. アプリケーションランチャーをクリックし、次にマーチャントツール | サイト | 商品とカタログ | カタログの順に選択します。
  2. URL を作成したいカタログの編集をクリックします。
  3. カテゴリ属性タブをクリックし、Search Engine Optimization Support (検索エンジン最適化サポート) 属性にそれぞれの値を入力します。
  4. 適用をクリックして変更を適用します。

商品 URL を手動で作成するには:

  1. アプリケーションランチャーをクリックし、マーチャントツール | サイト | 商品とカタログ | 商品 | 商品の順に選択します。
  2. 情報を入力して、商品を検索します。ワイルドカードまたは特定の商品 ID を使用して検索します。
  3. 検索結果に含まれる商品をクリックして、商品を選択します。
  4. 全般タブで、Search Engine Optimization Support (検索エンジン最適化サポート) 属性にそれぞれの値を入力します。
  5. 適用をクリックして変更を適用します。

コンテンツ URL を手動で作成するには:

  1. アプリケーションランチャーをクリックし、次にマーチャントツール | サイト | コンテンツの順に選択します。
  2. 「ライブラリフォルダー」をクリックし、コンテンツ ID または名前をクリックするまで移動してページを選択します。
  3. 全般タブで、Search Engine Optimization Support (検索エンジン最適化サポート) 属性にそれぞれの値を入力します。
  4. 適用をクリックして変更を適用します。

Salesforce Payments の SiteGenesis ページのサンプル

SiteGenesis インスタンスに Salesforce Payments を追加する際に、注文手続き、買い物カゴ、ミニ買い物カゴ、および商品詳細ページのページレイアウトを編集します。ここでは、これらのレイアウトを編集するアプローチを説明します。

Salesforce Payments を使用した SiteGenesis の注文手続き

SiteGenesis での複数ステップチェックアウトの標準の支払は、買い物客が 3 つの支払ページにわたって 3 つのステップを行います。

  1. 配送情報の取り込み
  2. 支払情報の取り込み
  3. 注文の確定

1 つのページに配送情報を構成し、2 ページ目に請求先住所と複数ステップチェックアウトの支払ステップを組み合わせます。また、これら 3 つすべてを 1 つのページにまとめることもできます。

レイアウトの変更

CSS を使用して境界の色を SiteGenesis の色と一致させ、エラーを強調表示します。Salesforce Payments のレイアウトは SiteGenesis とは異なります。

  • SiteGenesis
    • 請求情報には、請求先住所のための要素 (グレーのカード) が含まれています。
    • レイアウトには、プロセスの前のステップに戻るための編集ボタンが含まれています。
  • Salesforce Payments
    • 請求データは最後のページで支払が確認されるまで不明であるため、請求先住所は表示されません。
    • レイアウトには編集ボタンはありません。プロセスで前のステップに戻ることはできません。
    • 支払の概要を表示する確認のページでは、クレジットカードタイプに Stripe のブランドと定数が使用されます。クレジットカードの種類をローカライズします。

注文手続きページで PayPal を提供する場合の注意事項

買い物客が支払方法として PayPal を選択すると、「注文の確定」ボタンが無効になり、PayPal 支払ウィンドウが表示されます。PayPal 支払オプションでは、一般的な PayPal 支払方法と、「Pay in 4」(4 回の分割払い) の方法が提供されます。

買い物客が PayPal による支払の入力を完了すると、SiteGenesis の注文手続きの確認ページが表示され、支払方法として PayPal が表示されます。支払方法のデータには、支払方法、請求先住所、および配送情報が含まれます。確認ページの支払の概要にツールチップを追加します。

PayPal エクスプレスチェックアウトを完了した後に、買い物客がサイトに戻ったことを通知する UX 要素を確認ページに設定します。

エラーメッセージの処理

エラーメッセージの表示をカスタマイズします。エラーメッセージは Stripe から送信され、イベントのカスタムコードに提供されます。要素やそのスタイル、配置は、カスタムコードで構成します。

Salesforce Payments を使用した SiteGenesis の買い物カゴ

SiteGenesis では買い物カゴページに 2 つの注文手続きボタンがあります。また SiteGenesis によって、2 つの注文手続きボタンの下にレガシーの Apple Pay ボタンを追加するコードが提供されています。また、SiteGenesis の買い物カゴに Salesforce エクスプレスチェックアウト機能 (たとえば PayPal など) を追加できます。

エクスプレスチェックアウトボタンを追加するには、支払リクエストを作成してコンテナにマウントします。この方法では、複数のエクスプレスチェックアウトボタンを追加できます。たとえば、2 つのエクスプレスチェックアウトボタンを追加するには、2 つの同じ支払リクエストを作成して、それぞれを異なるコンテナにマウントします。

  • 買い物カゴコントロールの追加: 買い物カゴコントロールでは、買い物客が商品の数量を調整したり、商品を削除したり、クーポンコードを適用したりできます。カスタム JS を使用して Salesforce Payments 用の SiteGenesis 買い物カゴコントロールを作成する。カスタム JS コードは、支払コードから独立したカスタムコントローラーを呼び出します。買い物カゴコンポーネントに最新のデータを提供するには、JS 呼び出しに応答を追加します。
  • エクスプレス支払タイプのメッセージ: Salesforce Payments では、買い物カゴページでの支払メッセージの追加がサポートされています。SiteGenesis の買い物カゴにメッセージを追加するには、DIV 要素に HTML 属性を追加します。
  • Salesforce Payments を使用した Site Genesis のミニ買い物カゴ: ミニ買い物カゴにエクスプレスチェックアウトや PayPal などのボタンを追加します。ボタンは垂直方法に位置を合わせることをお勧めします。ミニ買い物カゴと買い物カゴは「今すぐ支払う」のユースケースに対して <ispayment> を使用し、「PayPal で支払う」ボタンが表示されます。支払方法では既存の買い物客の買い物カゴが必要です。ミニ買い物カゴと買い物カゴのページでは同じアプローチが使用されます。
  • PayPal ボタンの配置: PayPal ボタンの配置は、PayPal で使用される特定の z インデックス値によって設定されます。z インデックス値を使用してミニ買い物カゴの CSS ルールを追加し、PayPal ボタンの配置順を変更します。
メモ PayPal ボタンの配置は、一部の SiteGenesis の実装で発生する可能性のある予測不能な問題の種類と複雑さの範囲を強調しています。

Salesforce Payment を使用した SiteGenesis 商品詳細ページ (PDP)

PDP と PDP のクイックビューページにエクスプレスチェックアウトボタンを追加できます。標準の SiteGenesis PDP の構成では、エクスプレスチェックアウトボタンまたは PayPal ボタンを「買い物カゴに追加」ボタンの右に配置することが適しています。この配置は CSS で行うことができ、複数の支払ボタンを垂直方向に並べることができます。ボタンでフローまたはラップを行うには、より複雑な CSS の使用が必要です。PDP は「今すぐ購入」のユースケースに <isbuynow> を使用し、「PayPal 今すぐ購入」ボタンが表示されます。このアプローチは、複数の買い物客に対して「今すぐ購入」を同じように表示するために、SiteGenesis PDP ページをキャッシュして再利用できることを意味します。買い物客が「今すぐ購入」をクリックすると、買い物客の買い物カゴが作成または更新されます。

  • PDP クイックビュー: PDP クイックビューページは、やや異なるテンプレートを使用した同じ SiteGenesis PDP コードを使用します。これらは同じコードを使用するため、PDP ページにエクスプレスチェックアウトボタンを追加すると、PDP クイックビューページにもエクスプレスチェックアウトボタンが追加されます。
  • PDP ミニ買い物カゴのアクセス: ミニ買い物カゴが PDP からトリガーされると、SiteGenesis の買い物カゴへの追加は応答に HTML を含む AJAX 呼び出しであるため、ミニ買い物カゴにエクスプレスチェックアウトボタンが表示されるように構成されていれば、ミニ買い物カゴにエクスプレスチェックアウトボタンが表示されます。HTML には、Salesforce Payments コンポーネントを表示するためにプラットフォームによって注入された <script> タグが含まれています。SiteGenesis によって、ミニ買い物カゴを表示する HTML を追加する際に、これらのスクリプトが正常に実行されます。この機能は jQuery によって提供されています。

B2C Commerce のサイトマップ属性のオプション

店舗のサイトマップには、検索エンジンがサイトをクロールする頻度、クロールの優先度、クロールに含めるコンテンツをコントロールする属性が含まれています。このトピックは、B2C Commerce に該当します。

Change Frequency (変更頻度) 属性

ページの変更頻度は、ページの変更可能な頻度を検索エンジンに知らせます。ただし、これによって、検索エンジンによるページのクロール頻度が決定されるわけではありません。Change Frequency (変更頻度) 属性は、以下のいずれかに設定できます:

  • always (常時): この値は、アクセスされるたびに変更する文書に使用します。
  • hourly (毎時)
  • daily (毎日)
  • weekly (毎週)
  • monthly (毎月)
  • yearly (毎年)
  • never (なし): この値は、アーカイブされた URL に使用します。
メモ コンテンツスロットを使用している場合は、コンテンツへの変更スケジュールの頻度とこの頻度が一致するようにします。

Change Frequency (変更頻度) およびPriority (優先度) の値の優先順位は以下のとおりです:

  1. 項目のページ専用の属性。
  2. 次に、商品の分類カテゴリ。
  3. 次に、商品の主要カテゴリ。
  4. いずれのカテゴリ属性も見つからなかった場合は、カタログフィードで構成されたデフォルトの設定が使用されます。

Priority (優先度) 属性

小数点以下 1 桁の [優先度] の値を 0.0 から 1.0 に設定します (例: 0.1、0.2)。検索エンジンはこれを使用して、どのページを先にクロールするかを判断します。この値が検索結果でのページのランクに与える影響はありませんが、この値を使用することで、重要なページが検索インデックスに表示される可能性が確実に高まります。値が指定されていない場合、検索エンジンはページのデフォルト優先度を .5 と見なします。値が高いページはより重要であると見なされ、値が低いページは、それほど重要でないと見なされます。

Included (含める) 属性

Included (含める) 属性は、デフォルトで「なし」に設定されています。

  • すべてのオブジェクトが「なし」に設定されている場合、システムのデフォルトではコンテンツが除外され、フォルダーの URL が含められます。また、含める Content オブジェクト、または除外する Folder オブジェクトで、sitemap-included-flag が false に設定されていることが必要です。
  • すべてのオブジェクトが「なし」に設定されている場合、システムのデフォルトで商品の URL が除外 されます。
  • すべてのオブジェクトが「なし」に設定されている場合、システムのデフォルトでカタログの URL が含められます。

Included属性を次のいずれかの値に設定します。

  • なし: 項目で未定義なため、以下に説明する優先順序に従って、割り当てられたカタログカテゴリを使用してフォールバックが発生します。
  • 1 (YES): 上位カテゴリの設定にかかわらず、常にサイトマップに含まれます。
  • 0 (NO): 常にサイトマップから除外されます。Salesforce では、フッターやヘッダーなどのコンテンツスニペットを「NO」に設定することをお勧めします。

Included (含める) の値の優先順位は以下のとおりです:

  1. 分類カテゴリが存在する場合は、このカテゴリ、またはルートカテゴリに向かう親カテゴリのいずれかから、値が取得されます。分類カテゴリがルートカテゴリの場合、この項目は含まれます。
  2. その後、商品が現在のストアフロントカタログに主要カテゴリをもつ場合は、このカテゴリ、またはルートカテゴリに向かう親カテゴリのいずれかから、値が取得されます。
  3. それ以外の場合は、この項目は除外されます。

B2C Commerce のサイトマップのトポロジー

Google はサイトを検索結果に含めるために、グーグルボットを使用してサイトをクロールします。Google は、提供されたサイトマップを使用して、サイト内のどのページが新しいかを判断します。Google がサイトマップをリクエストすると、アプリケーションの SiteMap パイプラインは、SendGoogleSiteMap パイプレットを使用して Google にサイトマップを提供します。このトピックは、B2C Commerce に該当します。

サイトマップは、インデックスファイル (sitemap_index.xml) 1 つと、1 つまたは複数の実際のサイトマップファイル (sitemap_0.xml, sitemap_1.xml, ...) で構成されます。

インデックスファイルは、検索エンジンに登録するファイルで、すべてのサイトマップファイルの場所が含められています。その唯一の目的は、実際のサイトマップをポイントすることです。サイトマップファイルの実際の数は、サイトマップあたりに構成可能な URL (たとえば、50,000)、またはサイトマップファイルの最大サイズ 10 MB のうち、最初に到達した条件によって決定されます。

メモ SendGoogleSiteMap パイプレットは、サイトマップに対する検索エンジンのリクエストに応えるために使用します。

グーグルボットはサイトをインデックス化して、各ページに含まれる情報を正確に Google に伝えます。グーグルボットは、robots.txt ファイルを使用して、サイトのどの部分をインデックス化するかを判断します。robots.txt ファイルで許可されていないサイトのコンテンツは、その URL がサイトマップに含まれている場合でも、グーグルボットによってインデックス化されません。

Google ウェブマスター ツールを使用して robots.txt ファイルを生成し、複数のサイトで使用できます。また、robots.txt ファイルは、Business Manager でも生成することができ、サイトごとにクローラーに提供できます。

SEO サポートから URL ルールへのアップグレード

このトピックでは、13.1 以前のバージョンを使用してサイトを実装したユーザー向けに、新しいモジュールへのアップグレードに必要な情報を提供しています。B2C Commerce ではバージョン 13.1 のリリースにおいて、URL ルールモジュールを追加しました。この URL ルールモジュールでは、ストアフロント URL をカスタマイズすることにより、検索エンジンの検索結果を最適化することができます。同機能の一部を提供する SEO サポート機能は、バージョン 13.1 で廃止予定となり、将来的には削除される予定です。ストアフロント URL のサイト環境設定で新しい URL ルールモジュールを有効にするまでは、URL ルールモジュールから SEO サポート機能にアクセスできます。

メモ 13.1 以降のバージョンを使用してサイトを実装した場合、SEO 機能は表示されないため、このトピックは適用されません。

URL ルールモジュールは、以下のような方法で、サイト URL の最適化に貢献します:

  • ページタイプインジケーターや独自の拡張機能 “sc.html” を URL に含めない
  • URL は短く有意なものにする
  • URL には “demandware“ を含まない
メモ SEO サポートモジュールは、URL ルールモジュールが有効になると同時に表示されなくなります。

Sandbox での URL ルールのテスト

新しい URL ルール機能を使用するには、この機能を有効にします。URL ルールモジュールが有効になるまでは、URL ルールモジュールに SEO サポートページが表示されます。URL ルールを無効にし、廃止予定の SEO サポート機能を再度有効化する場合、この移行は一方的なものとなり、リダイレクトは作成されません。Staging (ステージング) または Production (本番) で機能を有効化する前に、Sandbox (サンドボックス) で新しい構成をテストします。

URL の評価と解決方法

顧客がブラウザーのナビゲーションバーに URL を入力すると、B2C Commerce でその URL が評価され、以下の順に解決されます。

このトピックでは、URL ルールモジュールが有効であると想定します。レガシーの検索しやすい URL モジュールを使用している場合は、レガシーの検索しやすい URL における URL の評価と解決方法を参照してください。

メモ URL ルールモジュールが有効になっているかどうかを確認するには、マーチャントツール | サイトサイト | 環境設定 | ストアフロント URLの順に選択します。

URL ルールモジュールによって生成された同じ URL が 2 つある場合、競合レポートが作成されます。このレポートは、URL ルールページの全般タブで表示できます。

  1. 入力された URL がホストエイリアスファイルのホスト名と一致する場合、B2C Commerce サーバーはホスト名からサイトへのマッピングを処理します。
    メモ エイリアスファイルマッピングルールは、この時点では適用されません。

    1. 地域情報が解決されます。

      URL ルールモジュールが有効で、地域情報マッピングがパスに設定されている場合は、URL に含まれる最初の 2 つの要素が、地域情報の評価に使用されます。また、パスに含まれる 1 つまたは 2 つの要素を使用して、地域情報を作成することができます。以下がその例です: 

      http://mystore.com/s/SiteGenesis/en/mens
http://mystore.com/s/SiteGenesis/de/DE/mens

      地域情報マッピングの定義の詳細については、URL ルールページの設定タブも参照してください。

  2. URL が処理されます:
    1. 新しい URL は、正しいコンテンツアセット、商品、またはその他のオブジェクトに解決されます。
      1. パイプライン URL が解決されます。
      2. フォルダー URL が解決されます。
      3. 受信 URL の URL リダイレクトが検出された場合は、そのリダイレクトが実行されます。URL リダイレクトを参照してください。
    2. URL を解決できない場合:
      • URL がどのオブジェクトとも一致しない場合は、URL 内の大文字と小文字が間違っているか、エンコードされていない文字が原因である可能性があります。URL は、大文字と小文字を区別しない一致を使用して解決され、エンコードされていない次の文字セットに対してエンコードされた文字を代用します: 
        , @ ) !$ ' (~
      • URL アーカイブから URL を見つけ出し、対応するオブジェクトに解決することを試みます。まず、受信 URL から URL リダイレクトがあるかどうかチェックし、見つからない場合は、オブジェクトの短い新規 URL にリダイレクトします。
        メモ 古いバージョンの B2C Commerce からの移行中に URL ルール機能を有効にすると、B2C Commerce は、新しい URL を作成する前に、B2C Commerce にある既存 URL のリストを作成します。この古い URL のリストは、アーカイブと呼ばれます。
    3. URL アーカイブにない場合は、受信 URL の URL リダイレクトがあるかどうかチェックし、実行します。
    4. 見つからない場合は、マッピングルールにフォールバックします。URL の扱い (動的/静的) は、以前のバージョンから変更されていません。

B2C Commerce の URL の生成および競合の解決方法

B2C Commerce では、パイプライン、カテゴリ、フォルダー、検索絞り込みの URL が B2C Commerce のデータベースに保存されます。商品 URL とコンテンツ URL は動的に構築されるため、このディレクトリに含まれません。URL ディレクトリには、パイプラインのエイリアス、ストアフロントカタログのカテゴリ、各サイト地域情報のサイトライブラリにあるフォルダーの URL エンドポイントが含まれます。

URL の生成プロセスでは、地域情報のパイプライン、カテゴリ、およびフォルダー内の一意の URL が確保されます。

  • URL の生成プロセス中に重複するカテゴリ URL が検出された場合、URL にインデックス番号が付加されます。たとえば、カテゴリの表示名を使用するようにカテゴリ URL ルールが構成されており、2 つのカテゴリに「shoes」という同じ表示名が指定されている場合、最初のカテゴリでは URL に「shoes-1」が使用され、2つ目のカテゴリでは URL に「shoes-2」が使用されます。カテゴリ URL がパイプライン URL と競合する場合は、グローバル競合が表示されます。
    メモ カテゴリをスケジュールする場合、B2C Commerce ではスケジュール時に重複がチェックされます。スケジュールされたカテゴリがオンラインカテゴリと同じ名前をもつ場合、この 2 つのカテゴリが同時に実行するようにスケジュールされていない場合でも、競合が表示されます。
  • パイプラインのエイリアスは、他のパイプライン URLや、現在 URL ディレクトリに保管されているカテゴリまたはフォルダー URL と競合しない場合のみ保管できます。たとえば、「shipping」と呼ばれるフォルダーに「/shipping」が付く URL がある場合、「/shipping」が付く URL でパイプラインのエイリアスを作成することはできません。
  • Search-Show パイプライン: カテゴリ ID と検索の絞り込みなしに Search-Show パイプラインに対して作成された URL は、検索絞り込み URL でのみサポートされています。たとえば、search/abrand/blue などです。この機能は Search-ShowContent パイプラインでも使用できます。たとえば、searchcontent/history などです。

アカウント デフォルト パイプライン Account-Show
検索 デフォルト パイプライン Search-Show

バージョン情報 en_US フォルダー folder_about
バージョン情報 de_DE フォルダー folder_about

パイプライン URL、カテゴリ URL、およびフォルダー URL は、B2C Commerce のシステムジョブを使用して生成されます。ジョブは、次のいずれかの変更が行われた際に URL を生成します:

  • カテゴリ/フォルダーの削除
  • カテゴリ/フォルダーの追加
  • サイトの割り当ての変更
  • カテゴリ/フォルダー名または ID の変更
  • カテゴリ/フォルダーのページ URL、ページ説明、またはページキーワードの変更
  • カテゴリの階層の変更 (category-path (カテゴリパス) またはcategory-parent (上位カテゴリ) 変数で表示される名前)
  • 属性値の変更
  • 地域情報の変更
  • 任意の URL 設定の変更、URL マッピングのコントロール

これらのいずれかを変更すると、すべてのパイプライン URL、カテゴリ URL、およびフォルダー URL が完全に再生成されます。URL 生成ジョブは、Staging (ステージング) および Sandbox (サンドボックス) でのみ実行されます。このジョブが Production (本番) で実行されることはありません。代わりに、URL は、カタログやライブラリとともに Production (本番) にレプリケートされます。ジョブが 50,000 件のカテゴリ/フォルダーを処理するのには、約 3 分かかります。

商品 URL は、このジョブを使用して生成されません。各 URL に付加される商品/コンテンツ ID は、URL が '.html' で終わる場合のみ、商品の識別に使用されます。

検索絞り込み URL

URL パスに検索絞り込み情報を追加すると、URL クレンジング (文字の置換など) の後で絞り込み値に競合が発生する場合があります。B2C Commerce では、これらの競合が一意になります (カテゴリとフォルダーのマッピングと同様に、設定した区切り文字で区切られたインデックスが追加されます)。プラットフォームは、1,000 件の競合を検出すると、URL の競合の検出と解決を停止します。

検索絞り込み URL の競合のエリアには、次の場合に、現在の検索絞り込み URL 値におけるグローバルな競合が表示されます。

  • 異なる検索の絞り込みに複数使用されている値。たとえば、色とブランドの両方にレッドがある場合など。
  • 区切り文字としてダッシュ "-" やアンダースコア "_" を含む検索絞り込み値。

B2C Commerce の URL リダイレクトの処理および例

URL リダイレクトモジュールを使用して、既存の B2C Commerce URL から新しい B2C Commerce URL へのリダイレクトを作成します。

レガシープラットフォームから URL リダイレクトを作成するには、URL リダイレクトを参照して、ホストエイリアス、静的マッピング、またはマッピングルールを使用するかどうかを判断し、リダイレクトを作成します。

  • URL ルールの URL 構文: URL ルールモジュールを使用して最適化された URL について説明します。リリース 13.1 より後のバージョンで作成されたサイトのデフォルトです。

URL リダイレクト地域情報フォールバック検索

以下のように URI ソースタイプを使用して、異なる地域情報用に URL リダイレクトを 1 つだけ構成できます:

Source URI '/Home-Show?brand=brandname' Destination URL '/home/brandname'

これを行うために、リクエスト地域情報の有無にかかわらず、リクエスト URL は、構成されているマッピングと一致するかどうかチェックされます。たとえば、

リクエスト 'www.my-host.com/[...]/default/Home-Show?brand=brandname' と'www.my-host.com/[...]/en_US/Home-Show?brand=brandname'はwww.my-host.com/home/brandnameにリダイレクトされます。

一般的に、この検索方法はすべての URL に適用されます。また以下のように、有効な構成済みリダイレクトは、リダイレクト先 URL にリダイレクト元の URI が含まれていた場合に、URL パスに地域情報が含まれていないサイトで、リダイレクトループになります:

Source URI '/home' Destination URL '/new/home'

リクエスト URL www.my-host.com/home の例は、www.my-host.com/new/homeにリダイレクトされ、newは地域情報を表す ため、構成されたリダイレクトも適用されるため、ループを示しています。

ただし、B2C Commerce では、URL パスに地域情報が含まれていないサイト (たとえば、ストアフロント URL が有効になっていて、地域情報マッピングがなし に設定されているサイト) については地域情報フォールバック検索が行われません。

URL リダイレクトの処理

このセクションでは、B2C Commerce が、受信 URL に基づいて、使用するリダイレクトルールを選択する方法について説明します。このトピックでは、URL のドメイン名とクエリ文字列の間の部分を URI と呼びます。以下の例では、URL の URI 部分は、Sites-YourShopHere-Site の後です。

                    www.mystore.com/on/demandware.store/Sites-YourShopHere-Site/en_US/Search-Show?_ie=iso-8859-1&cgid=womens
                    www.mystore.com/on/demandware.store/Sites-YourShopHere-Site/Sony-PSP-Game-Console/sony-psp-console,default,pd.html
                    ?cgid=electronics-gaming
  1. リダイレクトにワイルドカードが含まれていますか?
    • はい - リダイレクトにワイルドカードが含まれている場合、ワイルドカードを含まないリダイレクトの後に処理されます。ワイルドカードを含むリダイレクトは優先度に基づいて処理されます。ワイルドカード URL の処理方法に関する詳細については、最後のステップを参照してください。
    • いいえ - 次のステップに進みます。ワイルドカードを含まない URL には、優先度が割り当てられません。
  2. 受信 URL の URI は、リダイレクトルールで入力した URI と完全に一致しますか?
    メモ 考慮される URI が完全に一致していることを確認してください。部分的な一致では無視されます。
    • はい - 一致するリダイレクトルールが 1 つだけの場合、そのルールが使用されます。完全一致の URI が複数のルールにある場合、それらのルールは候補として特定され、処理が継続されます。
    • いいえ - リダイレクトは実行されません。
  3. どのリダイレクトルールに、受信 URL と一致するパラメーターが一番多く含まれていますか?
    1. B2C Commerce はクエリ文字列パラメーターの数でリダイレクトルール候補を並べ替え、最もパラメーターの数が多いルールを最初に処理します。

      たとえば、/mens?cgid=hats&color=red は、/mens?cgid=hats よりも先に処理されます。

    2. B2C Commerce は、リダイレクトルールの各パラメーターを、受信 URL のパラメーターと一致させます。一致していると判断されるには、リダイレクトルールのパラメーターがすべて存在し、受信 URL のパラメーターと同じ値である必要があります。リダイレクトルールまたは受信 URL にリストされるパラメーターの順序は関係ありません。検索しやすい URL と標準の B2C Commerce URL は両方とも同様に処理されます。
      メモ 受信 URL にこの他のパラメーターがある場合、これらのパラメーターはリダイレクトの一致論理とは関係ありません。
  4. ワイルドカードを含む URL のリダイレクトに、配置が割り当てられていますか?
    • はい - リダイレクトは、優先度順に処理されます (数字が低いものから高いものへ)。最小値は 1 です。整数を指定します。
    • いいえ - 優先度が空白になっているリダイレクトは、優先度が割り当てられたリダイレクトの後に処理されます。処理がルールと一致しないように、処理される順番は定義されません。リダイレクトが処理される順序を制御するには、優先度を追加します。

B2C Commerce は、パラメーターが最も多いリダイレクトルール候補を最初に評価しますが、リダイレクトルールのパラメーターをすべて含んでいない受信 URL は一致と見なされません。以下の例では、受信 URL の URI と一致する 2 つのリダイレクトルール候補があります。リダイレクトルールは、パラメーターが多いものから少ないものの順に処理されます。ただし、受信 URL に、最初に処理されるリダイレクトルールのパラメーターがすべて含まれていないため、一致と見なされないことから、2 つ目のルールである /abc?a=1 がリダイレクトとして選択されます。

リダイレクトルール候補 受信 URL
/abc?a=1&b=2 www.mystore.com/on/demandware.store/Sites-MySite-Site /abc?a=1
/abc?a=1  

受信 URL に他のパラメーターが含まれているかどうかは関係ありません。以下の例では、すべての受信 URL が同じリダイレクトルール候補と一致しており、すべてが 2 つ目のルールである /abc?a=1 をリダイレクトとして選択しています。

リダイレクトルール候補 受信 URL
/abc?a=1&b=2 www.mystore.com/on/demandware.store/Sites-MySite-Site /abc?a=1 &c=1&d=1
/abc?a=1 www.mystore.com/on/demandware.store/Sites-MySite-Site /abc?a=1 &c=1
  www.mystore.com/on/demandware.store/Sites-MySite-Site /abc?a=1

B2C Commerce の URL リダイレクト

既存のサイトから新しい B2C Commerce 店舗へ移行する初期の段階では、古いサイトから新しいサイトへの 301 リダイレクトを作成することを考慮してください。時間をかけて、あるページや URL から別のページや URL へのリダイレクトを作成します。

エイリアス、マッピングルール、静的マッピング、および URL リダイレクトの各機能を使用するタイミング

  • マーチャントツール | サイト | SEO & Discoverability | URL Redirects を使用します。この機能は、B2C Commerce でホストされている古いページを B2C Commerce の現在のページにリダイレクトするために使用します。たとえば、カテゴリ名を変更する場合が考えられます。B2C Commerce URL のリダイレクトに使用できるのは、この機能のみです。B2C Commerce URL からのリダイレクトの作成を参照してください。この機能の詳細については、URL リダイレクトの処理および例を参照してください。

  • コンテンツページ、一意のページ、または通常と異なるページ - この場合は、マーチャントツール | サイト | SEO & 検出可能性 | 静的マッピングを使用します。この機能は、ランディングページか一般的なパターンに従わない検索かにかかわらず、特定のページに使用します。静的マッピングを参照してください。

  • 商品ページ、カテゴリページ、パターンに準拠するページの場合 - マーチャントツール | サイト | SEO & 検出可能性 | 動的マッピングを使用します。 - マッピングルールは受信 URL のパターンを識別し、B2C Commerce URL のパターンにマッピングします。マッピングルールをいくつか作成すると、レガシーサイトにある多数の URL を効率良く管理できるようになります。

レガシープラットフォーム URL のリダイレクトとサイトランキング

多くのマーチャントが、既存のサイトから B2C Commerce に移行します。既存のサイトでは通常、トラフィックを誘導するために、検索ランキングや、他のサイトから自社サイトへのリンクがすでに構築されています。B2C Commerce を使用して古いリンクと新しいページの間にマッピングを作成することで、他のサイトや検索エンジンからのトラフィックを失わないようにします。このようなマッピングを作成しないと、古いリンクは機能せず、SEO ランキングにに大きな影響を及ぼす場合があります。

このようなリンクのリダイレクトを作成するには、B2C Commerce ホスト名エイリアス、B2C Commerce サイト URL マッピングルール、およびサイト URL 静的マッピングの 3 つの方法を利用できます。レガシー URL 用の 301 リダイレクトの構成を参照してください。

商品をブックマークした顧客を失わないために、また、ランキングを維持するためにも、B2C Commerce のカテゴリ名を変更したために古くなってしまったリンクを永久リダイレクトする必要があります。

このようなリンクのリダイレクトを作成するには、URL リダイレクト機能を使用します。

B2C Commerce では、検索エンジンによるサイトのクローリングに使用される XML サイトマップのリダイレクトキーワードとして、sitemap*xml が保持されます。この文字列は、B2C Commerce URL リダイレクト機能のいずれかを使用してリダイレクトを作成する場合には使用できません。ただし、古いサイトの概要を表示していたレガシーのサイトマップページをリダイレクトする場合は、sitemap または SiteMap という文字列を使用してリダイレクトを設定できます。サイトマップの概要を参照してください。

廃止予定の SEO サポートモジュールの URL から URL ルールモジュールの URL への自動リダイレクト

13.1 以前のバージョンでストアフロントを作成し、URL の最適化を目的として SEO サポートモジュールを使用し、次に URL ルールモジュールへアップグレードすると、URL ルールモジュールを有効化した際に、古い URL から新しい URL への 301 リダイレクトが自動で作成されます。

ストアフロント URL を生成する際には、特定の文字を削除または置換します。このトピックは、B2C Commerce に該当します。

URL を生成中に、マッピングルールの左側の文字がマッピングルールの右側の文字に置き換えられます。

マッピングルール

検索文字の置換ルールを作成すると、次の特別なルールが適用されます:

  • マッピングルールの左側では、[a-z, A-Z, 0-9] ['-','_','.','~'] 以外の文字であれば、どの文字でも使用できます。
  • マッピングルールの右側では、文字の長さは 0 ～ 5 文字で、[a-z, A-Z, 0-9] ['-','_','.','~'] の中からどの文字でも使用できます。
  • 置換せずに文字を削除するには、マッピングルールの右側を空白にします。
  • 文字を ['-','_','.','~'] に置換する場合に、その文字の前後に空白があると (例: シャツ & サンダル)、その空白は削除されます (例: シャツ-サンダル)。
  • 文字を削除する場合に、その文字の前後に空白があると (例: シャツ & サンダル)、その文字と前後の空白は 1 つの空白に置換されます (例: シャツ サンダル)。

ローカライゼーション

マッピングルールはローカライズ済みです。たとえば、デフォルトの地域情報のウムラウトの置換 (ö -> o) を定義し、de_DE (ö -> oe) 地域情報のマッピングを上書きします。Salesforce B2C Commerce では、地域情報固有の URL の生成中に、現在の地域情報 (例: de_DE) に定義されているマッピングを使用します。次に、対応する言語の地域情報 (例: de) にフォールバックし、その次にデフォルトの地域情報にフォールバックします。

文字の置換管理 (作成/更新/削除) で選択できる地域情報は、アクティブなインスタンスの地域情報のみです。サイトでアクティブでない地域情報で定義されたルールによっても、URL がクリーンアップされます*。これにより、グローバル地域情報がサイト地域情報より広い場合に、より多くの地域情報を選択できるようになります。サイトでアクティブでない地域情報で文字の置換を作成して、複雑な文字置換戦略を策定する機能。たとえば、'en_US' > 'en' > 'default' というフォールバックスキームでは、どのフォールバック地域情報でもルールを拡張できます。たとえば、アクティブな地域情報が 'en_US' 1 つしかないサイトで可能な置換は 150 の文字の置換です。これは、'en' または 'default' の置換でルールを拡張できるためです (インスタンスで有効になっている場合)。

ヒント 文字の置換がユーザーの優先地域情報に保存されている場合、別の地域情報で構成された文字の置換を検索します。
メモ *URL をクリーンにすると、Web サイトや Web サービスの使いやすさとアクセス性が向上します。これらは、専門家以外のユーザーにとってすぐに意味があります (Wikipedia)。

    • ホスト名: 地域情報は、ホスト名の一部として表示されます。最上位レベルのホスト名エイリアスは、エイリアスファイルで作成します。ホスト名を指定し、地域情報を選択します。

      ホスト名エイリアスの割り当てを参照してください。

    • URL パラメーター: 地域情報は、URL パラメーターとして表示されます。パラメーターの名前と各地域情報の値の両方を設定します。

      結果として返される URL は以下のようになります:

      http://mystore.com/s/mysite/home?lang=en_US

      URL で使用される地域情報名と実際の地域情報 (例: en -> default) の間のマッピングを指定します。

    • パス: 地域情報は、URL パスの一部として表示されます。

      これにより、URL で使用されるように入力した地域情報名と、Salesforce B2C Commerce により認識される地域情報との間のマッピングを指定できるようになります。

      地域情報には、1 つまたは 2 つの値を定義できます。

      • 1 つの値を定義した場合、結果として返される URL は以下のようになります:

        http://mystore.com/s/SiteGenesis/en/mens

      • 2 つの値を定義する場合は、de/DE のように、最初の値を指定し、'/' を挟んで、次の値を指定することで、以下のような結果が返されます:

        http://mystore.com/s/SiteGenesis/de/DE/mens

        使用できるバックスラッシュは 1 つのみです。

        メモ 2 つの値を使用する場合、URL パラメーター タイプの地域情報マッピングには '/' を使用できません。

      マッピングルールは以下のとおりです:

      • マッピングは空白でも構いません。
      • マッピングセグメントでは 'a-z'、'A-Z'、'-'、および '_' を使用できます。
      • マッピングでは、両セグメントが空白でないことを条件に、'/' を 1 つだけ使用できます。

      受信 URL の地域情報は以下のように決定されます:

      1. B2C Commerce で、1 つ目と 2 つ目の URL 要素の地域情報マッピングが検索されます。
      2. マッピングが存在しない場合、1 つ目の URL 要素の地域情報マッピングのみが検索されます。
      3. マッピングが存在しない場合、1 つ目の URL 要素の地域情報 ID が検索されます。
      4. マッピングが存在しない場合、default が使用されます。
    メモ 地域情報 マッピングセクションを使用する前に、地域情報を設定しておく必要があります。地域情報は、サイト環境設定 | 地域情報モジュールで定義します。
  5. 検索絞り込み URL 設定セクションで、次の設定を使用して、検索絞り込みを URL にどのように表示するかを構成します (下の「カテゴリ URL と商品 URL の作成」セクションにある例を参照してください):

    /brand/blue|black/new-arrivals/shoes という例を使用すると:

    • 絞り込みセグメント区切り文字は、black と new の間の / です。
    • 絞り込み区切り文字は、brand と blue の間の / です。
    • 絞り込み値の区切り文字は、blue と black の間の | です。

    以下の設定を行います。

    • 位置： 絞り込みはカテゴリ/フォルダーマッピングの前または後に含められます。前 または 後 (デフォルト)。たとえば、前は /blue/shoes/、後は /shoes/blue/ です。
    • 絞り込みセグメント区切り文字: 絞り込みセグメントをどのようにカテゴリ/フォルダーセグメントから区切るかを定義します。/ (スラッシュ) (デフォルト)、_ (下線)、- (マイナス記号)
    • 絞り込み区切り文字: 複数の絞り込みをどのように区切るかを定義します。/ (スラッシュ)、_ (下線) (デフォルト)、- (マイナス記号)、ピリオド (.)、プラス記号 (+)
    • 絞り込み値区切り文字: 複数の絞り込み値をどのように区切るかを定義します。| (縦線) >、_ (下線) (デフォルト)、- (マイナス記号)、ピリオド (.)、プラス記号 (+)

      リリース 16.3 では、縦棒 "|" の検索絞り込み値区切り文字が URL パスにエンコードされます。URL パスにエンコードされた縦棒のない URL は、以前と同様に機能します。

    • 競合する絞り込み値区切り文字: 競合する値について値マッピングからインデックスを区別するために使用する区切り文字を定義します。(なし) (デフォルト)、_ (下線)、- (マイナス記号)
    • パイプラインのエイリアスを除外: カタログ (Search-Show) またはコンテンツ (Search-ShowContent) の検索絞り込み URL のパイプラインのエイリアスを除外する場合に指定します。無効 (デフォルト)、カタログ、またはコンテンツ。
    • 商品およびコンテンツ絞り込みの名前と値 URL パラメーター: 商品およびコンテンツの検索絞り込みの名前と値の URL パラメーターを入力します。SiteGenesis と Salesforce Reference Architecture (SFRA) では、デフォルト値は prefn、prefv、crefn、crefv です。値の構成の更新に加え、デフォルト設定を超えてパラメーターを使用するにはカスタムコードの変更が必要です。
    メモ ピリオド (.) とプラス記号 (+) の区切り文字はエンコードされません。このいずれかを区切り文字および空白の置換文字として使用した場合は、競合モニターに競合が表示されます。
  6. 上記の各セクションについて、適用をクリックして変更を保存します。

URL アーカイブタブの使用

URL アーカイブでは、Staging (ステージング) インスタンスと Production (本番) インスタンスの古くなった URL マッピングが現在の URL マッピング (カテゴリとフォルダーの URL ルールのセクションで定義) にリダイレクトされます。アーカイブによって開始された古いリダイレクトが不要になった場合 (たとえば、カテゴリが削除された場合や ID が変更された場合) は、URL アーカイブタブから削除します。URL パスまたはオブジェクト ID を検索します。

必要なエディション

使用可能なソリューション: B2C Commerce

Production (本番) インスタンスで URL マッピングをライブにするには:

  1. Staging (ステージング) インスタンスでルールを定義します。
  2. 準備ができたら、レプリケートします。
  3. すべてのマッピング (Production (本番) インスタンスでライブ) が Staging (ステージング) インスタンスでアーカイブに追加されます。

URL のレプリケートプロセスでは、URL アーカイブもレプリケートされます。

新しいマッピングを使用するその後の Production (本番) へのレプリケートでは、URL アーカイブには以前のレプリケートプロセスからのマッピングが含まれます。新しいマッピングがあるので、古くなったマッピングは自動的に新しい URL マッピングにリダイレクトされます。

このページを使用して、アーカイブされたカテゴリ、フォルダー、パイプラインの URL を検索し、必要な場合は削除できます。

また、有効なカテゴリ、フォルダー、パイプラインを参照していないマッピングや、無効になった地域情報で定義されているマッピングを、検索して削除できます。

メモ SEO サポートモジュールから URL ルールモジュールへアップグレードした場合、Salesforce B2C Commerce では、古い URL から新しい URL へのリダイレクトが自動で作成されます。これらの自動リダイレクトでは、手動による設定やマッピングは必要ありません (関連するマッピングは URL アーカイブに保存されません)。
  1. アプリケーションランチャーの順にクリックし、マーチャントツール | サイト | SEO & 検出可能性 | URL ルールの順に選択します。
    URL ルールページの全般タブではなく検索サポート環境設定ページが表示される場合は、サイト環境設定 | ストアフロント URLの順に移動して URL ルールモジュールを有効にします。
  2. URL アーカイブタブをクリックします。
  3. 簡易を選択した状態で、アーカイブされたカテゴリ、フォルダー、パイプラインの URL を検索します。
    B2C Commerce は、アーカイブされた URL を現在のオブジェクトの URL にリダイレクトします。
    1. オブジェクト ID または URL の一部を入力します。
      文字列を正確に入力してください。ワイルドカードはサポートされていません。フィールドを空白のままにすると、検索結果が表示されません。検索では大文字と小文字が区別され、間違っている場合は検索結果が表示されません。

      例 1: ipods を含む ID の検索

      検索フレーズ 検索結果
      ipods あり
      ipod なし
      Ipod なし

      例 2: electronics/ipods を含む URL の検索

      検索フレーズ 検索結果
      electronics/ipods あり
      **、electronics/*、*/ipods または */* なし
      ElectroniCs/IpodS いいえ
    2. URL のターゲットを、カテゴリ、フォルダー、パイプラインから選択します。
    3. 検索をクリックします。
      アーカイブ URL、リダイレクト URL、またはオブジェクト ID のいずれかのカテゴリで検索フレーズを検索した結果が表示されます。
    4. 削除するリダイレクトのボックスを選択して、削除をクリックします。
      リダイレクトの削除を確認するメッセージが表示されます。
    5. OK をクリックすると、リダイレクトが永久に削除されます。
  4. クリーンアップを選択した状態で、有効なカテゴリ、フォルダー、またはパイプラインを参照していないマッピングを検索して削除します。または、無効な地域情報で定義されている。
    1. オブジェクトタイプを、カテゴリ、フォルダー、パイプラインから選択します。
    2. 無効な項目の検索をクリックします。
    3. 結果から 1 つまたは複数のアーカイブされた URL を選択します。
    4. 削除をクリックします。

B2C Commerce のサイトプレビューツールを使用したサイトのプレビュー

サイトプレビューツールを使用すると、特定の日付や時刻にストアフロントがどのように表示されるかを確認できます。特定の顧客グループに対して、または特定のソースコードを使用して、ストアフロントがどのように表示されるかを選択します。ストアフロントで A/B テストをプレビューするには、A/B テストと A/B テストセグメントの値を入力します。

必要なエディション

使用可能なソリューション: B2C Commerce
  1. 表示するサイトを選択して、Toolkit をクリックします。
    ストアフロントを表示する新しいタブが開き、右上隅に Storefront Toolkit のアイコンが表示されます。
  2. プレビュー設定ツールアイコンをクリックします。
  3. (オプション) 日付と時刻を入力します。

    サイトプレビューツールでは、対応する地域設定の定義に基づいて、サイト地域情報の日付と時刻の形式が使用されます。サイトで複数の地域情報が許可されている場合は、現在の地域情報が使用されます。

    過去の日付を選択すると、ストアフロントに現在のコンテンツが表示されます。コンテンツアセットが削除された場合は、コンテンツは表示されません。

  4. (オプション) ソースコードまたは顧客グループを入力します。

    登録済みと未登録の両方を同時に選択することはできません。

    作成してから数分しか経過していないソースコードや顧客グループが選択肢として表示されない場合は、ページを更新するか、Storefront Toolkit を再度開いてみてください。

  5. A/B テストをプレビューするには:
    1. A/B テストを選択します。
    2. A/B テストのセグメントを選択します。
    3. A/B テストのスケジュール範囲内の日付を入力します。日付を入力しないと、プレビューツールではテストの有効日が使用されます。選択した日時にテストが非アクティブな場合は、エラーが表示されます。

    作成してから数分しか経過していない A/B テストやA/B テストセグメントが選択できない場合は、ページを更新するか、Storefront Toolkit を再度開いてみてください。

  6. プロモーションのテストツールを使用してプロモーションをテストするには、プロモーションの追跡を有効にするを選択し、リクエストログでプロモーションメッセージの追跡に使用するプロモーション追跡 ID を入力します。
    プロモーションの追跡の詳細については、B2C Commerce でのプロモーションの追跡ツールを使用したプロモーションのテストを参照してください。
  7. (オプション) 将来の日付の価格設定をプレビューするために、日付を設定します。
    1. ステップ 3 では、プレビューしたい将来の日付を入力します。
    2. 価格表のインポートまたは設定後に、商品インデックスを再作成したことを確認します。
      メモ Salesforce Reference Architecture (SFRA) の実装では、将来の価格設定は商品詳細ページにのみ表示されます。商品一覧ページには現在の価格設定のみが表示されます。将来の価格設定は表示されません。
  8. プレビューをクリックします。
    ブラウザータブ内の URL には、地域情報に固有の形式で日付と時刻が含まれます。ソースコードまたは顧客グループのプレビューでは、指定期間のコンテンツスロット、価格、およびその他のデータがストアフロントで表示されます。A/B テストのプレビューでは、A/B テストのスケジュール日時にかかわらず、A/B テストセグメントに関連付けられているプロモーションや割引、スロット、並べ替えルールが有効になります。

URL リクエスト分析機能の使用

URL リクエスト分析機能は、特定の URL リクエストに関する詳細な情報を提供します。このツールは、B2C Commerce がストアフロント URL リクエストをどのように処理するか、および対応するストアフロントページを開くためにどの構成を使用するかを理解する助けとなります。また、無効な URL、404 エラーページ、および、予想されたページが開かない URL の根本的な原因を特定する際に役立ちます。

必要なエディション

使用可能なソリューション: B2C Commerce

さらに、このツールを使用して、慎重に扱わなければならない構成が SEO に与える可能性のある影響をテストでき、ライブにする前に潜在的な問題を特定できます。

ストアフロントでパスワードによる保護を有効にした場合、一部のリダイレクト (たとえば、セキュアなプロトコルへのリダイレクト) またはイベント (たとえば、パスワードの入力) がアクセスを付与される前に発生します。URL をテストしている場合は、これらのイベントは高レベル情報として表示されます。

次のリクエストに対し、結果が提供され、可視化されます。

  • パスからのサイトマッピングや、エイリアスファイルと地域情報マッピングなどサイトと地域情報の識別
  • 商品とコンテンツのパスマッピング、(アーカイブ済み) カテゴリ/フォルダ/パイプライン (検索の絞り込みとサイトマップあり、またはなし)
  • パイプラインとコントローラーのリクエスト
  • サービスの対象 (Shop/Data API)
  • ホスト名などのリダイレクト、静的リダイレクト、動的リダイレクト、URL リダイレクトマッピング、検索リダイレクト、URL 検索絞り込み値、および古いマッピングの自動リダイレクト (つまり、SEO 向けの検索絞り込み URL)
  • カスタムコード (リダイレクトがカスタムパイプライン/コントローラー内で開始された場合)
  1. アプリケーションランチャーの順にクリックし、マーチャントツール | サイト | SEO & 検出可能性 | URL Request Analyzerの順に選択します。
  2. 分析する URL を URL フィールドに入力します。
    • 絶対 URL。プロトコルあり (例: https://www.my-host.com/mens/') またはプロトコルなし (HTTP プロトコルを使用、例: www.my-host.com/mens/)。
    • スラッシュで始まる相対 URL (HTTP プロトコルと現在のリクエストホスト名を使用、例: /us/mens/?param=aValue)。
  3. 結果を次のようにフィルターします。
    • なし (すべて)
    • ホストのみ: ホストの解決情報 (およびその他の基本的な解決情報) が表示されます。
    • リダイレクトのみ: リダイレクトの解決情報 (およびその他の基本的な解決情報) が表示されます。
  4. 追加をクリックします。

    URL に対し、プレビューリンクをもつエントリが作成されます。プレビューリンクには、情報の記録に必須である記録 ID が含まれています。情報は、このユーザーインターフェイスに対してのみ記録されます。

    サイトごとに最大で 5 つのリンクをもつことができます。エントリは x ボタンを使用して削除できます。各サイトは個別のリストを持ちます。

  5. エントリのプレビューアイコン をクリックすると、ストアフロントへのリクエストが処理されます。ストアフロントページが正常に表示されたら、次の操作を実行します。
    1. ストアフロントを表示しているブラウザーのタブを閉じます。
    2. Business Manager の URL リクエスト分析機能のページに戻ります。
    3. 更新をクリックするか、フィルターを変更して更新をクリックします。
  6. 追加された URL オブジェクトをクリックして開き、記録された情報を確認します。
    1. アイコンをクリックして、詳細を開きます。
    2. アイコンをクリックして、表示を折りたたみます。
    3. アイコンをクリックして、情報を表形式で完全に展開します。

    解決タイプは以下のとおりです。

    (http://system-a.system-b.dw.demandware.net/s/SiteGenesis/womens/clothing/?lang=en_US という URL を使って説明します。)

    • サイトマッピング: リクエスト URL がサイトを識別する方法。たとえば、リクエストサイトSiteGenesisはパス/s/SiteGenesisから解決されます。
    • 地域情報マッピング: パイプラインディクショナリーにおけるリクエストで使用可能な地域情報。たとえば、パラメーターから識別された地域情報 en_US。
    • パイプラインマッピング: 呼び出されるパイプラインリクエスト。リクエストパスから解決されます。たとえば、カテゴリ URL、womens/clothing は /Sites-SiteGenesis-Site/en_US/Search-Show?cgid=womens-clothing にマッピングおよび転送されます。
    • プロセスパイプライン/コントローラー: このリクエストに対して呼び出されるパイプライン/コントローラー。たとえば、OnRequest-Do、OnSession-Do、Search-Show。
    • リダイレクトマッピング: このリクエストで 1 つ以上のリダイレクトが発生した場合に使用されます。RedirectURL-Startパイプラインはリダイレクトを識別するか、パイプラインの実行前にリダイレクトします。
    • 色グループ: 解決情報セクションのオプションの色。あるマッピングタイプが同じように何回も発生した場合に使用される場合があります。同じ色は同じマッピングを示します。

    結果に複数の解決タイプがある場合、最初の反復を表示するか、すべての結果を表示するかを選択します。たとえば、結果に OnRequest-Do と Product-ShowInCategory の 2 つのパイプラインの処理の行がある場合、最初の行を表示するか、両方の行を表示するかを選択できます。

  7. 関連する構成を変更し、B2C Commerce の動作を確認する場合は、ステップ 5 と 6 を繰り返して、更新された情報を確認します。

SEO のための URL ルール

サイトのトラフィックを増やすには、Google や Yahoo などの外部検索エンジン向けにサイト URL を最適化します。サイトを作成する場合、URL ルールは自動的に有効になり、URL ルールモジュールへの許可があれば URL ルールを構成できます。Salesforce では、URL ルールを Staging (ステージング) にエクスポートして Production (本番) にレプリケートする前に Sandbox 上で構成およびテストすることをお勧めします。このトピックは、B2C Commerce に該当します。

メモ URL ルールを無効にすることで、廃止予定の SEO サポートを使用できます。ただし、Salesforce では URL ルールモジュールを使用することをお勧めします。URL ルールモジュールと (廃止予定の) SEO サポートモジュールを同時に有効にすることはできません。

ストアフロント URL の長さは 1800 文字までです。この長さを超える URL は短くされますが、有効性と一意性は保たれます。具体的に言うと、商品 URL やコンテンツ URL には商品 ID や コンテンツ ID が保持されます。

URI とクエリパラメーターのリクエストの最大長は 2002 文字です。リクエストがこの制限を超えると、ページは 404 エラーを返します。

すべての URL タイプに適用される設定がいくつかあります。これらには、ローカライゼーション、大文字と小文字の区別、および URL のスペースエンコーディングが含まれます。

サイト URL は以下のように最適化します:

  • ページタイプインジケーターや独自の拡張機能 “sc.html” を URL に含めない
  • URL を短く有意なものにする
  • URL に demandware を含めない

Business Manager での構成

SEO URL を有効にしたら、設定することができます。マーチャントツール | サイト | SEO と発見性 | URL ルールを選択します。対象は次のとおりです。

  • カテゴリ URL と商品 URL
  • フォルダー URL とコンテンツアセット URL
  • パイプライン URL
  • 検索絞り込み URL

また、競合を解決し、全般設定を構成し、アーカイブを確認します。

許可

URL ルールモジュールには、モジュール化された許可があります。これを設定すると、モジュールが Business Manager に表示されるようになります。ストアフロント URL 環境設定の構成を参照してください。

インポートとエクスポート

URL ルールは、サイトのインポート/エクスポートモジュールのサイト URL 項目の一部としてインポートおよびエクスポートします。SEO サポートモジュールからルールをエクスポートする場合、これらのルールはサイトのインポート/エクスポートモジュールのサイト環境設定項目からエクスポートされます。

既存のサイト URL ユニットの一部として URL ファイルをエクスポートします。

レプリケーション

以下のレプリケーションタスクを使用して、URL ルールをレプリケートします:

構成 レプリケーションタスク
カテゴリ URL サイト > カテゴリ URL
フォルダー URL サイト > フォルダー URL
パイプライン URL サイト > パイプライン URL
URL ルール サイト > サイト URL ルール (または既存 URL のレプリケーショングループの一部)

B2C Commerce での Google のサイト所有権の検証

Google は、サイトの所有者であることを検証するために、特定のメタタグをサイトに追加するよう、またはお使いの Web サーバーのルートディレクトリにファイルを特定の名前でデプロイするようリクエストします。このトピックでは Google を対象としていますが、他の検索エンジンでも同様のプロセスが行われます。
