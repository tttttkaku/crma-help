B2C Commerce のデベロッパーのためのセキュリティのベストプラクティス

B2C Commerce のデベロッパーは、これらのセキュリティのベストプラクティスを使用して安全なストアフロントを開発します。

  • B2C Commerce での暗号化と暗号法
    Salesforce B2C Commerce では、強力な暗号化トークンとセキュアなランダム識別子を安全に暗号化、署名、生成することを可能にする、Salesforce が維持する暗号化ライブラリを拡張しています。Salesforce では、Salesforce の Trust Compliance Web サイトの B2C Commerce ページに記載されているように、業界標準のコンプライアンスフレームワークを維持しています。
  • B2C Commerce でのクロスサイトスクリプティング
    クロスサイトスクリプティング (XSS) を使用すると、攻撃者は、ターゲットとなるユーザーが表示している Web ページにクライアント側の JavaScript を注入できます。コンテンツの操作による悪意をもった攻撃を防止するには、すべてのユーザーが提供するコンテンツを適切にエンコードする必要があります。
  • B2C Commerce における HTTP ヘッダーでの宣言によるセキュリティ
    宣言によるセキュリティコントロールを、クリックジャックなどのクライアントのブラウザーをベースとする攻撃に対する強力な防御手段として使用し、クロスサイトスクリプティング (XSS) に対するビルトインのブラウザー保護を提供できます。OWASP Secure Headers Project は、アプリケーションのセキュリティを向上するためにアプリケーションで使用することのできる HTTP 応答ヘッダーを記述しています。
  • コンテンツセキュリティポリシー(CSP)の設定
    コンテンツセキュリティポリシー (CSP) は、ストアフロントに対して構成するセキュリティ機能です。CSP を実装するときは、構成によって必要なスクリプトが意図したとおりに実行されることを確認する責任があります。
  • B2C Commerce でのコマーススクリプトインジェクション
    サーバースクリプトインジェクション、またはリモートコード実行は、攻撃クラスの 1 つで、許可を付与されたコード実行によって悪意をもって作成された入力が実行されます。このクラスの攻撃により、攻撃者はサーバー上で実行されるコードを制御することができます。
  • B2C Commerce でのクロスサイトリクエストフォージェリ (CSRF)
    各ストアフロントには、高レベルのセキュリティ保護を必要とする、保護されたリクエストがいくつかあります。通常これらのリクエストは、認証済みの買い物客がアカウントを変更する場合や、操作を完了するためにサーバーに個人データを送信する場合に実行されます。ユーザーは、これらのリクエストは自分がリクエストを開始した場合にのみ行われると考えています。
  • B2C Commerce での機密事項の保存
    機密事項の保存と使用は、買い物客の情報のセキュリティを万全にするために、デベロッパーが行うもっとも重要なアクションの 1 つです。機密事項には以下のものがあり、また、これには限られません。
  • B2C Commerce でのフックセキュリティの使用
    Salesforce B2C Commerce では、デフォルトの機能を拡張するパワフルなツールとしてフックを使用できます。ただし、他のすべてのパワフルなツールと同様に、フックは適切に使用しないと危険です。
  • B2C Commerce でのデータの検証
    ユーザー入力の検証は、アプリケーションセキュリティの基礎です。データの検証によって、データがアプリケーションで予想されている種類のものであることが確認されます。B2C Commerce では通常、無効なリクエストは完全に拒否され、ユーザーにエラーが返されます。データの検証を行う場所を選択しますが、ここではクライアント側とサーバー側の検証に重点を置きます。
  • B2C Commerce でのオープンリダイレクト攻撃
    Web アプリケーションがユーザー入力をリダイレクト先として信頼すると、攻撃者はこの入力を使用してユーザーを自分がコントロールする Web サイトにリダイレクトし、ユーザーの情報を盗むことができます。
  • B2C Commerce での認証と承認のベストプラクティス
    アクセスコントロールの脆弱性を利用するのは、攻撃者の中核となるスキルです。攻撃者に対する保護を行うために、アカウント管理、注文管理、購入などのビジネス機能に対するサーバー側アクセスのコントロールチェックを強制します。
  • B2C Commerce のサプライチェーンのセキュリティ
    アップロードと外部リンクを通じて含めた未検証のソフトウェアソースは、攻撃の潜在的な侵入経路となる可能性があります。
  • B2C Commerce のセキュアなログ
    Salesforce B2C Commerce のログは安全に保存されており、site_admin 役割または developer 役割のユーザーのみがアクセスできます。ログは Web インターフェイスまたは WebDAV を通じてアクセスできます。ログに記録する情報のタイプを決定する際には、これらを考慮してください。
  • B2C Commerce での安全なコーディングのための一般的なプラクティス
    Salesforce B2C Commerce が提供するすべてのセキュリティコントロールを使用しても、コーディングで適切なプラクティスを行わないと、これらの管理に悪影響を与え、脆弱性を導入する可能性があります。一般的な推奨事項については、OWASP Secure Coding Practices - Quick Reference Guide (OWASP セキュアコーディングプラクティス - クイックリファレンスガイド) を参照してください。

B2C Commerce でのセキュリティイベントの監査

Salesforce B2C Commerce は、セキュリティログを含むさまざまなログファイルを提供しています。セキュリティログには Business Manager ログインのログエントリが含まれます。

B2C Commerce サービスのプロビジョニングに使用するすべての Salesforce システム (ファイアウォール、ルーター、ネットワークスイッチ、オペレーティングシステムを含む) は、それぞれのシステムログ機能、または一元化されたログ収集サーバーに情報をログします。これにより、セキュリティのためのレビューと分析を行えます。セキュリティログでは、セキュリティの状態を認識できます。詐欺行為、乱用、その他の疑わしい行為などの、セキュリティ関連の問題が発生した場合に、より適切に調査して情報を共有するために、インスタンスで使用可能なログをダウンロードして収集します。セキュリティログ情報は、発生したサイバー攻撃の対象、内容、日時、方法を見極めるために役立ちます。

セキュリティログファイルはこちらにあります: https://<instance-name>/on/demandware.servlet/webdav/Sites/Securitylogs

セキュリティログエントリは以下のサンプルエントリのようになります。

[2015-10-28 02:23:19.139 GMT] [DW-SEC] (User: 'username' (Sites), IP: 100.100.10.100 [LOGIN] : logged in.)

セキュリティログには以下の情報も含まれています。

  • Business Manager ログインのログエントリへのセッション ID。
  • アイドル状態が続いたために Business Manager がパスワードを要求する場合は、再ログインのログエントリ。これらのログエントリは、古いセッション ID と新しいセッション ID を記録します。

セキュリティログファイルは 90 日後に自動的に削除されます。ユーザーとクライアントは、セキュリティログを削除したり、セキュリティログの記録をオフにしたりすることはできません。ログファイルを 90 日間を超えて保持するには、ファイルをダウンロードして、ローカルまたは専用のストレージに保存する必要があります。

WebDAV

B2C Commerce では、すべてのユーザーのセキュリティログに、WebDAV を介したファイルとフォルダーへのアクセスが記録されます。各ファイルとフォルダーへのアクセスログメッセージは同じ構造になっています。メッセージには、使用された WebDAV メソッドと、アクセス可能なディレクトリ構造内でアクセスまたはリクエストされたファイルやフォルダーのパスが含まれます。以下は WebDAV メソッドのメッセージの例です。

  • ディレクトリの作成 (MKCOL) 
    [DW-SEC] User: 'support' (Sites), IP: 100.100.10.100, [MKCOL] : /src/myfolder - starting (inIMPEX)
                     
[DW-SEC] User: 'support' (Sites), IP: 100.100.10.100, [MKCOL] : /src/myfolder - finished successfully (in IMPEX)
  • ファイルのアップロード (PUT) 
    [DW-SEC] User: 'support' (Sites), IP: 100.100.10.100, [PUT] : /src/myfolder/my-testfile.pdf - starting (in IMPEX)

[DW-SEC] User: 'support' (Sites), IP: 100.100.10.100, [PUT] : /src/myfolder/my-testfile.pdf - finished successfully (in IMPEX)
  • 別の場所にファイルを移動 (MOVE) 
    [DW-SEC] User: 'support' (Sites), IP: 100.100.10.100, [MOVE] : /src/myfolder/my-testfile.pdf --> /src/myfolder2/my-testfile.pdf - starting (in IMPEX)

[DW-SEC] User: 'support' (Sites), IP: 100.100.10.100, [MOVE] : /src/myfolder/my-testfile.pdf --> /src/myfolder2/my-testfile.pdf - finished successfully (in IMPEX)
  • ファイルのダウンロード (GET) 
    [DW-SEC] User: 'support' (Sites), IP: 100.100.10.100, [GET] : /src/myfolder2/my-testfile.pdf - starting (in IMPEX)

[DW-SEC] User: 'support' (Sites), IP: 100.100.10.100, [GET] : /src/myfolder2/my-testfile.pdf - finished successfully, downloaded 425 kb of 425 kb (in IMPEX)

各 WebDAV メソッドについて、開始と終了が記録されます。

フォルダーブラウザー

B2C Commerce では、すべてのユーザーのセキュリティログに、フォルダーブラウザーからのファイルアクセスが記録されます。フォルダーの参照は意図的に記録されません。ファイルのビューとダウンロードのログメッセージは同じです。

[DW-SEC] User: 'support' (Sites), IP: 100.100.10.100, [GET] : /src/myfolder2/my-testfile.pdf - starting (in IMPEX) 

[DW-SEC] User: 'support' (Sites), IP: 100.100.10.100, [GET] : /src/myfolder2/my-testfile.pdf - finished successfully, downloaded 425 kb of 425 kb (in IMPEX)

内部ユーザーアクセスの追跡

Salesforce の従業員が顧客のレルムで行うアクションに関する B2C Commerce セキュリティモデルには、すべての機密性の高い領域で透明性の高いログ記録が含まれています。機密性の高い領域で読み取りまたは書き込みのアクションが行われると、B2C Commerce では、Salesforce 従業員の Business Manager ユーザー名、領域、およびアクションが、顧客が利用できるセキュリティログに記録されます。このセキュリティコントロールの目的は、監視によって、またはレルム固有の顧客情報の変更を介して、Salesforce 従業員のアクションを明白にすることです。

  • この時点では、機密性の高い領域が Salesforce で定義されます。これには、セキュリティ設定、買い物客や注文データへのアクセス、キャンペーンやクーポンへのアクセスが含まれますが、これらに限定されるものではありません。
  • (読み取りまたは書き込みのアクションに関係なく) すべてのアクセスがログに記録されます。
  • ユーザーの役割と許可に対するすべての変更がログに記録されます。
  • マーチャントが Business Manager にインストールしているあらゆるカスタムモジュールへのすべてのアクセスがログに記録されます。
  • アクセスは、Business Manager のセキュリティログに記録および保存されます。
  • Salesforce 従業員の Business Manager ユーザー名 (Eメールアドレス) はログに記録されます。

以下はセキュリティログの対象外です。

  • フォルダーブラウザーによるフォルダーの参照
  • インポートとエクスポートによるファイルアクセス
  • スクリプト API によるファイルアクセス

以下に、ログに記録される機密性の高い領域の一部 (すべてではありません) を示します。

  • site-urls_aliases
  • site-prefs_apple-pay
  • orders_paymethods
  • orders_paymentmethods
  • marketing_coupons
  • marketing_giftcert
  • marketing_campaigns
  • customer_groups (API アクセス許可が制限されているため、事実上読み取り専用)
  • customers_gdpr
  • customers_batchprocs
  • customer_service_center_module
  • content_pages
  • content_impex
  • sourcecode

セキュリティログストリーミング

セキュリティログには、ログイン情報やクライアントのダウンロード情報などの機密情報が含まれています。

役割と許可

セキュリティログのストリーミングを設定するには、Log Center External Admin (外部管理者) の役割が必要です。Log Center External Admin の役割では、次のことができます。

  • セキュリティログのストリーミング構成の作成と更新
  • 編集許可リストへのユーザーの追加。この許可リストに含まれるユーザーは、セキュリティログのストリーミング構成を更新できます

ユーザーの役割が「Log Center 外部管理者」から「ユーザー」に変更されると、そのユーザーが設定したストリーミングセキュリティログはすべて無効になります。別の「Log Center 外部管理者」ユーザーが新しいストリームを設定する必要があります。ユーザーが編集許可リストに含まれていた場合でも、既存の構成を編集できます。

「Enable Security Logs」(セキュリティログの有効化) オプションは、Log Center External Admin の役割が割り当てられていないユーザーに対してはアクティブになりません。

その他の参照項目:

  • Account Manager で管理される役割
  • セキュリティログのストリーミング
    セキュリティログのストリーミングを設定するには、セキュリティログを有効にするオプションを設定します。

Salesforce が管理するセキュリティ

Salesforce では、B2C Commerce の開発においてセキュリティが焦点であることを保証し、安全な開発とプラットフォームレベルのセキュリティを提供しています。

セキュリティに焦点をあてた開発

Salesforce セキュア開発ライフサイクル (SSDL) は、開発プロセスの各段階でセキュリティを提供します。SSDL は教育、業界をリードするプロセス、およびツールを提供して、予測可能性、責任、透明性を確実にします。安全な開発のベストプラクティスには、多層防御、最小権限、安全なデフォルト、定期的な静的および動的な脆弱性分析などがあります。

Salesforce セキュア開発ライフサイクル:

  • Open Web Application Security Project (OWASP) のセキュアコーディング原則を適用します。
  • すべての商品と新しく開発した機能に対して、実装前に脅威のモデリングアクティビティを実行します。
  • 静的および動的な脆弱性スキャンを実行します。
  • 定期的にサードパーティのセキュリティの評価を行います。
  • 顧客が開始したセキュリティ評価をサポートします。
  • 質疑応答セッションとピアレビューで顧客をサポートします。

B2C Commerce プラットフォームレベルのセキュリティ

B2C Commerce では、本番環境を保護するために多層防御のアプローチをとっています。このアプローチには、アプリケーション、インフラストラクチャ、およびネットワークレベルでの複数のセキュリティ制御が含まれており、顧客データが安全に処理および保存されるようにします。

B2C Commerce を構成する複数のアプリケーションは、強力な認証メカニズムを提供しています。認証済みのユーザーに対し、ユーザーの役割に応じてアプリケーションのさまざまな部分へのアクセスを承認できます。SSDL によって、カスタマイズが可能となる一方、これらの機能でユーザーを保護するためのセキュリティコントロールが確実に提供されます。

インフラストラクチャレベルは複数のレイヤーの信頼性をもち、データベースレイヤーを含むシステムのすべてのレベルにファイアウォールとアクセスコントロールがあります。

  • データベースレイヤーでは、データがテナントを超えてアクセスされないようにするため、複数テナント制が強制されています。
  • 各テナントは独自のデータベースをもち、すべてのデータはテナントの Org ID と利用資格にリンクされています。
  • 暗号化は、転送中のデータを保護し、主要な場所とバックアップの場所の間で転送される際のオープンデータの漏洩の可能性を防ぎます。
  • また、セキュリティは当社のデータセンターの物理レイヤーにも広がっています。たとえば、当社のデータセンターのディスクが寿命に達した場合、データが復元できないように、ディスクは消去され、細断されます。

B2C Commerce プラットフォームのセキュリティに関する勧告は、Security Advisories サイトで顧客に通知されます。

Salesforce の従業員が顧客のレルムで行うアクションに関する B2C Commerce セキュリティモデルには、すべての機密性の高い領域の透明性の高いログ記録が含まれています。詳細については、B2C Commerce でのセキュリティイベントの監査を参照してください。

ユーザーアクセスの設定

Account Manager 管理者の認証情報をもつユーザーは、Reports & Dashboards ポータルへのアクセスをユーザーに付与できます。

必要なエディション

使用可能なソリューション: B2C Commerce

ユーザーアクセスを設定するには、管理者が Account Manager で Reports & Dashboards の役割を追加します。

  1. Account Manager に Administrator (管理者) としてログインします。
  2. 既存のユーザーに役割を追加します。
    1. 組織、役割、ステータスのフィルターを使用して、ユーザーをリストします。
    2. User's ID (ユーザーの ID) をクリックして、ステップ 5 に進みます。
  3. 新規ユーザーにこの役割を追加します。
    1. Account Manager | User (ユーザー)の順に移動し、Add User (ユーザーの追加) をクリックします。
    2. ユーザーアカウント情報と組織の割り当てを完了して、ステップ 5 に進みます。
  4. Roles (役割) セクションまでスクロールして、Add (追加) をクリックします。

B2C Commerce での買い物客の認証

買い物客はストアフロントで登録を行ってアカウントを作成するか、匿名のままでいることができます。たとえば、ストアフロントを閲覧するには、買い物客はアカウントにログインしたり、アカウントを作成したりする必要はありません。ただし、買い物客がアカウントを作成すると、請求先住所、クレジットカード、以前の注文などの情報を取得します。また、認証済みの買い物客は、ギフトレジストリやほしい物リストなど、匿名の買い物客は利用できない機能にアクセスできます。

アカウントを作成するには、買い物客はユーザー名とパスワードを入力します。登録後、買い物客はパスワードを変更できます。Business Manager を使用して、買い物客の認証のための主要なセキュリティコントロールとしてパスワードポリシーを設定します。セキュリティを向上するには、パスワードの長さをデフォルトの 8 文字から 10 文字に増やします。

Salesforce B2C Commerce では、買い物客を認証し、Google や Facebook などのサードパーティの OAuth プロバイダーから買い物客に関する情報を取得するために、OAuth2 がサポートされています。買い物客はこのアクセスを承認する必要があります。またこの機能では、買い物客がストアフロントでよりすばやく簡単に登録してログインできるようになります。個人情報を入力する代わりに、買い物客は Google アカウントなどの既存のアカウントを使用してログインできます。既存のアカウントを使用することで、そのアカウントから個人情報を取得する許可がストアフロントに与えられます。

これらの認証スキームは、ストアフロントが本番になる際に適用されます。ただし、ストアフロントが開発またはテストの段階にある場合、潜在的な消費者が検索エンジンを使用してそのストアフロントを見つけられないようにする必要があります。これを防止するには、Business Manager を使用して Development (開発)、Staging (ステージング)、Production (本番) インスタンスへのアクセスをマーチャントとプロジェクト関係者に制限します。

これを行うには、ストアフロントの保護モードを有効にし、共有のユーザー名とパスワードを構成します。この共有のユーザー名とパスワードは、開発やテストなどの、内部での使用のためのストアフロントアクセスに使用します。ストアフロントの保護モードはデフォルトで無効になっていますが、有効にするようにしてください。

メモ 買い物客の認証はマーチャントの責任です。

B2C Commerce のサプライチェーンのセキュリティ

アップロードと外部リンクを通じて含めた未検証のソフトウェアソースは、攻撃の潜在的な侵入経路となる可能性があります。

コードのアップロード

コードのアップロードは注意を要する操作です。信頼できないコードがアップロードされる危険性が少しでもあると、悪意をもった人物がレルムのデータや機能のほとんどにアクセスできる可能性が生じ、サイトや買い物客のデータの機密性、整合性、可用性に悪影響が及びます。

サードパーティのライブラリ

サードパーティのソフトウェアは、簡単に機能を追加し、製品を市場に導入するまでの時間を短縮するために、頻繁にカスタムコードに統合されています。これには、不要なライブラリや安全ではないライブラリがストアフロントのコードに含まれてしまうリスクが伴います。SiteGenesis と Salesforce Reference Architecture (SFRA) にも、いくつかのサードパーティライブラリが含まれています。これらのライブラリをカスタムコードに組み込んだ場合、潜在的な問題や脆弱性がないか、注意して監視する必要があります。

不要な、または脆弱性をもつ可能性のあるライブラリをストアフロントに含めないようにするには、以下のガイドラインに従います。

  • ストアフロントを適切に操作するために必要なライブラリのリストを維持します。
  • 必要でないライブラリをコードベースから破棄します。
  • サードパーティのソフトウェアは、信頼できる安全なソースから入手します。
  • 使用している各ライブラリの特定のバージョンを追跡します。
  • ライブラリに既知の弱点がないかを定期的に確認し、これらのライブラリを安全なサポートされているバージョンにアップグレードします。

リモートでホストされるリソース

現在 eコマースでは、サプライチェーン攻撃がより頻繁に発生するようになりました。たとえば、Magecart は多くの場合サードパーティのリモートでホストされているリソースをターゲットとして、Web ページで入力された機密情報をスキミングするドライブバイをインストールします。攻撃者は JavaScript のみを使用して暗号通貨を採掘し、マシンを DDoS ネットワークに従属するものとし、場合によってはさらにコントロールと被害を広げるためにクライアントマシンに直接マルウェアをインストールすることを試みます。

これを行うために、攻撃者はリモートでホストされているリソースを侵害し、かつては信頼されていた JavaScript リソースに悪意のあるコードを挿入します。その後、このスクリプトを含むすべての Web サイトには、この悪意をもつ JavaScript が含まれることになります。

最近、セキュリティ業界は、この種の攻撃を抑制するのに役立つ新しい制御を導入しました。これらのコントロールは、リモート リソースを含む HTML 要素に整合性ハッシュを挿入します。たとえば、フェッチするリソースをブラウザーが検証できるようにするセキュリティ機能である Subresource Integrity (SI) では、リモートリソースのコンテンツのハッシュをもつ HTML 要素に整合性値が必要です。攻撃者がリモートリソースを侵害した場合、ハッシュ値は事前構成された信頼されたハッシュ値とは一致せず、クライアントのブラウザーは悪意のあるスクリプトを読み込みません。

SFRA の実装では、addJs と addCss のヘルパーメソッドが整合性ハッシュをオプションの二次引数として受け入れます。サブリソース完全性の実装の例は、Mozilla Developer Network のドキュメントを参照してください。

DomainKeys Identified Mail (DKIM) 認証のサポート

Salesforce B2C Commerce では、顧客がメール要件に合わせて使用できる、すぐに使用可能なソリューションをファーストパーティの POD (Point of Deployment) で提供しています。このサービスは、DKIM および SPF 認証のサポートを提供します。DKIMは、送信メールに暗号化デジタル署名を追加するメール認証プロトコルです。DKIMを使用すると、受信者はドメイン所有者がメールを承認し、送信中に変更されていないことを確認できます。DKIMは、スパムメールやフィッシングメールを減らすのに役立ちます。

ポジティブセキュリティモデルの使用

ポジティブセキュリティモデルは、セーフリストアプローチとも呼ばれ、何を許可するかを定義し、それ以外はすべて拒否します。このアプローチを使用して、悪意をもつ可能性のある入力をすべて拒否する代わりに、既知の正規の入力のみを許可リストに追加できます。

また、以下の点に注意します。

  • ユーザーのデータ入力を検証する際には、悪意をもった入力をフィルターする代わりに、英数文字のセーフリストに対して入力を検証します。
  • アクセスコントロールエリアを構成する際には、すべてのアクセスを拒否し、特定の承認を受けたリソースや関数のみにアクセスを許可します。

B2C Commerce のユーザー認証

管理者は常に Salesforce B2C Commerce で統合認証を使用します。従来は常にローカルユーザー認証を使用していましたが、ローカルユーザーのローカルログインは、認証情報が作成された Business Manager インスタンスのみに限られていました。サイトが統合認証に移行した後は、サイトでは Account Manager での統合認証が要求され、ユーザーは自分の組織の任意の Business Manager インスタンスにグローバルにログインできます。

ローカル認証

ローカルユーザー認証では、管理者、または適切な許可をもつ既存のユーザーが Business Manager で新規ユーザーをプロビジョニングし、そのユーザーの認証情報をインスタンスに保存します。ユーザーが複数のインスタンスにログインできるようにするには、各インスタンスでユーザーのアカウントを作成する必要があります。主要なセキュリティコントロールは、ユーザーパスワードポリシーとログインロックアウトポリシーに関連します。これらの設定は適切なデフォルト値をもっていますが、自分のポリシーの要件に合わせて変更できます。

セキュリティを向上するには、パスワードの長さをデフォルトの 8 文字から 12 文字に増やします。リリース 17.5 より前に構成した顧客リストを更新します。

統合認証

統合ユーザー認証では、Account Manager がマルチサイト組織のすべての Business Manager ユーザーを管理します。ユーザーは Account Manager の認証情報を使用して Business Manager にログインする必要があります。Account Manager は、パスワードの変更やリセットなど、ユーザーに関連するすべてのアクションを処理します。これらのプロセスでは、対応する Business Manager の設定は無視されます。

主要なセキュリティコントロールは、ユーザーパスワード、ログイン、およびロックアウトポリシーです。自分のポリシーの要件に合わせてデフォルト値を変更できます。Business Manager とは異なり、Account Manager は 2 要素認証 (2FA) を使用します。攻撃者がアクセスするには、パスワードとユーザーの 2FA アプリケーションの両方にアクセスする必要があるため、セキュリティが大幅に向上します。

B2C Commerce でのユーザーの認証と承認

管理者は、Business Manager でセキュリティコントロールを構成します。Business Manager ユーザーが実際に名乗っている人物かどうかを判定するために認証を行う必要があります。また、ユーザーが実行しようとしている特定の操作を行う許可があるかどうかを判定するために承認を行います。

  • B2C Commerce のユーザー認証
    管理者は常に Salesforce B2C Commerce で統合認証を使用します。従来は常にローカルユーザー認証を使用していましたが、ローカルユーザーのローカルログインは、認証情報が作成された Business Manager インスタンスのみに限られていました。サイトが統合認証に移行した後は、サイトでは Account Manager での統合認証が要求され、ユーザーは自分の組織の任意の Business Manager インスタンスにグローバルにログインできます。
  • B2C Commerce でのユーザーの承認
    Salesforce B2C Commerce では役割ベースのアクセスコントロールを使用して承認を行います。ユーザーは 1 つまたは複数の役割に割り当てられます。各役割は一連の許可で構成されています。ユーザーの承認は、Business Manager でカスタムの役割と許可を使用して構成します。このプロセスは、ローカル認証と統合認証のどちらを使用する場合でも、基本的に同様に機能します。

WAF on On-Demand Sandboxes (ODS)

OWASP ルールセット、eCDN マネージドルールセット、カスタムファイアウォールルール、ボット保護、DDoS 軽減、レート制限など、すべての標準 WAF 機能は ODS デフォルトドメインゾーンで使用できます。これらは、Business Manager eCDN UI または CDN API を使用して構成します。

ODSは共有ゾーン・モデルを使用するため、ゾーンで構成されたWAFルールはレルム内のすべてのODSインスタンスに適用されます。ルールはインスタンスごとにスコープが設定されていません。ルールの変更は慎重に計画し、インスタンス間で意図しない影響が発生しないようにします。

必要なエディション

使用可能なソリューション: B2C Commerce

前提条件: WAF 設定を構成する前に、埋め込みコンテンツ配信ネットワーク (eCDN) にホスト名を追加し、ゾーンを作成します。

メモ WAF は、新しいプロキシゾーンを作成した場合、デフォルトで有効になっています。デフォルト設定では機密性モードが “低” で、アクションは “チャレンジ” です。

ECDN WAF 設定を変更するには:

  1. Business Manager で、アプリケーションランチャーをクリックし、管理 | サイト | 埋め込み CDN 設定の順に選択します。
  2. ゾーンを選択します。
  3. WAF タブで、WAF を有効にする (新しいプロキシゾーンのデフォルト) には、有効を選択 (チェック)します。ゾーンで WAF を無効にするには、有効の選択を解除 (チェックを外す) します。
  4. アクションドロップダウンリストから、アクションを選択します。
    • シミュレーション — Web リクエストのブロックやチャレンジは行われず、イベントがログに記録されます。
      メモ 初めて使用する場合は、このモードを少なくとも 1 週間使用して、受信トラフィックを分析することをお勧めします。その後、ログファイルを確認して、適切なアクションと機密性レベルを決定します。
    • チャレンジ - 受信した Web リクエストが疑わしい場合は、続行する前に、Completely Automated Public Turing test to tell Computers and Humans Apart (CAPTCHA) チャレンジ応答が必要です。
    • ブロック — リクエストがサーバーに到達するのを阻止します。
  5. 機密性ドロップダウンリストから、機密性レベルを選択します。
    機密性を高いレベルに設定すると、WAF による保護が厳重になり、より多くのリクエストがブロックされる可能性が高くなります。反対に、機密性を低いレベルに設定すると、WAF による保護が緩まり、より多くのトラフィックが通過する可能性が高くなります。一般的に、機密性は中から高に設定することを推奨します。ただし、ログの分析に基づいて、機密性レベルを上げたり下げたりできます。これらの調整により、WAF が不正なユーザーとして検出した実際の買い物客が多すぎる場合や、不正なユーザーが十分に検出されない場合に、管理を行うことができます。
    メモ オフのオプションを選択すると、OWASP ルールセットが無効になります。

    HTTP リクエスト

    • 低—脅威スコアが 60 以上
    • 中—脅威スコアが 40 以上
    • 高—脅威スコアが 25 以上

    Ajax リクエスト

    • 低—脅威スコアが 120 以上
    • 中—脅威スコアが 80 以上
    • 高—脅威スコアが 65 以上
  6. 1 つまたは複数の日付に対し時刻 (すべての時刻はローカルブラウザーの時刻に基づく) を選択し、リクエストログをクリックします。

    ログファイルのダウンロードの準備ができると、リンクを記載した Eメールが、Business Manager で使用している Eメールアカウントに送信されます。ログをダウンロードして、トラフィックを分析し、機密性を調整します。

  • JSON ログ出力
    すべての Open Commerce API (OCAPI) 呼び出しは、JavaScript Object Notation (JSON) ログ出力に表示されるすべてのフィールドを返します。
  • B2C Commerce のログフィールド情報
    JSON リクエスト形式は、ログ出力のカテゴリ、フィールド、および説明を提供します。

eCDN 管理ルールセット設定の変更

eCDN セキュリティチームによって作成されたこのルールセットは、迅速かつ効果的な保護をすべてのアプリケーションに提供します。eCDN セキュリティチームは、新しい脆弱性をカバーし、誤検知を減らすために、ルールセットを頻繁に更新します。ルールセットのデフォルト設定は有効になっています。

実行するアクションを選択します (デフォルトを推奨)。実行可能なアクションは次のとおりです。

  • ブロック (デフォルト)
  • 管理されたチャレンジ
  • JS チャレンジ
  • ログ記録
  • レガシー CAPTCHA

ルールセットのアクションを定義すると、各ルールに定義されているデフォルトのアクションが上書きされます。アクションの上書きを削除するには、ルールセットのアクションを「デフォルト」に設定します。

eCDN OWASP WAFv2 設定の変更

潜在的な Web アプリケーションの脅威に対応する場合、eCDN Web アプリケーションファイアウォール (WAF) は受信する各リクエストを確認し、リクエストに脅威スコアを割り当て、適切に対応します。受信リクエストが OWASP ルールをトリガーするたびに、全体的な脅威スコアが上昇します。一部のルールは他のルールよりもスコアに対する影響が大きくなります。

  • 異常スコアのしきい値の定義 - スコアのしきい値を定義します。利用可能なしきい値は次のとおりです。
    • 低 (60 以上)

    • 高 (25 以上)

Web アプリケーション ファイアウォール (WAF) とネットワーク トラフィック ログ

このログには、WAF によって識別されたトラフィックだけではなく、すべての eCDN ネットワークトラフィックが含まれています。IP 評価によってブロックされたトラフィックを追跡し、WAF 設定をトリガーしないトラフィックがどの程度あるかを分析します。

指定した時刻に最大 7 日間、ログファイルをリクエストします。ログをダウンロードするリンクを記載した Eメールが、Business Manager で使用している Eメールアドレスに送信されます。GDPR (General Data Protection Regulation: 一般データ保護規則) により、Salesforce はログファイルを 7 日後に削除します。このため、ログファイルはお客様自身のサーバーに保存することをお勧めします。

ログ項目は、60 分間隔によるストアフロントへのトラフィックリクエスト数です。60 分間隔のログファイルは、OCAPI (Open Commerce API) を通じてリクエストできます。OCAPI を使用する場合、API はログをダウンロードするための URL を API 応答で返します。ログのダウンロードに対するすべての API 呼び出しで Eメールが生成されないようにするには、一時トークンを使用し OCAPI を通じてログをダウンロードできます。

メモ CDN Logpush を使用して、より包括的なログのセットを取得することもできます。ログには、ファイアウォールのイベントと HTTP リクエストを S3 バケットに保存してログをすぐ確認できるようにする CDN-API が含まれています。この API は、CDN ログでの HTTP リクエストとファイアウォールイベントの表示をサポートします。

Web アプリケーション ファイアウォール (WAF) 保護

WAF は、プロキシゾーンの作成の際にデフォルトで有効になり、レイヤーを使用してセキュリティを提供し、攻撃を緩和するマルチレイヤーによる対策で非常に重要な要素です。

WAF は、発生する可能性のあるすべての攻撃に対して保護を提供するものではありませんが、Production (本番)、Staging (ステージング)、Development (開発) のストアフロントホスト名を特定のコードレベルの脆弱性から保護します。これらの脆弱性には以下が含まれる場合があります。

  • SQL インジェクション攻撃
  • クロスサイトスクリプティング
  • Open Web Application Security Project (OWASP) WAFv2 管理ルールセット - アプリケーション層を標的とする脅威を特定。CDN プロバイダーは、Open Web Application Security Project (OWASP) ModSecurity Core Rule Set をプラットフォームに統合します。定期的な監視により、WAF ルールセットが最新の状態に保たれ、公式コードリポジトリから入手できる最新バージョンの OWASP が維持されます。
    • CDN によって実装される OWASP WAFv2 管理ルールセットは、OWASP ModSecurity Core Rule Set (CRS) をミラーリングし、OWASP からの更新を定期的にモニタリングします。この更新により、ルールセットが最新の公式コードリポジトリバージョンと一致するようになります。
    • OWASP WAFv2 管理ルールセットは統合されたエンティティとして機能し、脅威スコアを計算し、このスコアに基づいて適切なアクションを決定します。リクエストがルールセット内のルールに一致すると、脅威スコアはルールのスコアに従って段階的に上がります。最終的な脅威スコアが構成されたしきい値を超えた場合、CDN はルールセットの最後のルールで指定されたアクションを実行します。
  • eCDN 管理ルールセット - これらは CDN セキュリティチームによって特定された脅威です。このルールセットは、迅速かつ効果的な保護をすべてのアプリケーションに提供します。このルールセットは、新しい脆弱性をカバーして誤検知を減らすために頻繁に更新されます。
  • eCDN 公開認証情報チェック管理ルールセット - 盗まれた認証情報に関する公開データベースに対して検索を実行する、広く知られたコンテンツ管理システム (CMS) アプリケーション用に事前設定された一連のルール。エンドユーザー認証エンドポイントに自動認証情報チェックを実装すると、WAF ルールセットを使用して、侵害された認証情報の公開データベースに対して認証情報ペアが検索されるようになります。

WAF を使用する際には、以下を念頭に置いてください。

  • WAF は、一般的なコードの脆弱性を悪用するボットによる攻撃の試みを止めることができます。ただし、総当りのクーポンコードの試行では、リクエストは正常な HTTP および Web フォームのリクエストであるため、WAF ではボットの試みが見逃されることがあります。

    該当する場合は、アカウントチームに連絡して、当社が推奨するボット専門のパートナーから管理ソリューションを取得してください。

  • OWASP ルールセットは「オン」または「オフ」にすることができます。WAF OWASP ルールセットでは、OWASP ルールセット内の個々のルールのカスタマイズはサポートされていません。
  • eCDN 管理ルールセットは「オン」またはオフにすることができます。eCDN 管理ルールセットでは、eCDN 管理ルールセット内の個々のルールのカスタマイズはサポートされていません。
  • CDN 公開認証情報チェックは「オン」または「オフ」にすることができます。eCDN 公開認証情報チェックでは、eCDN 公開認証情報チェック内の個々のルールのカスタマイズはサポートされていません。

WAF はインターネットトラフィックを監視し、ストアフロントに対して行われたすべての HTTP または HTTPS (フルサイト) と Ajax (小規模なデータスニペット) のリクエストを検討します。OWASP による最も一般的な Web アプリケーションの脆弱性を利用して、効果的なルールセットを決定します。ルールは、ユーザーエージェント、パス、国、クエリ文字列、IP アドレスなどの複数のリクエスト属性に基づくことができます。

ストアフロントの保護を支援するために、WAF は次の処理を行います。

  • Web サイトアドレスや URL を検査して、正常ではないものがないかを検出します。
  • アプリケーションの特定の脆弱性を標的とする、悪意のあるトラフィックをフィルターにかけます。
  • 悪意をもつユーザーによる、コードの脆弱性の悪用を防止します。

WAF のデフォルト設定では、機密性モードが低で、アクションはチャレンジになります。

Web アプリケーション ファイアウォール (WAF) の初めての使用

WAF を初めて使用する場合は、WAF を少なくとも 1 週間、ログモードまたはシミュレーションモードで実行することをお勧めします。

シミュレーションモードは、サイトのトラフィックに関する情報を収集して記録します。生成されたログを確認して、ファイアウォールのニーズに関してデータに基づいた決定を行い、ストアフロントのアクションと機密の設定方法をより適切に判断します。

ログを確認する際には、次の点を考慮します。

  • トリガーされているルールと頻度。
  • ルールをトリガーしている地域 (国)。これらの国に商品を販売しているかどうか。これらの国に配送を行っているかどうか。
  • 悪意をもつユーザーまたはトリガーされた WAF ルールに関連付けられている IP アドレス。問題のある IP アドレスで IP ルックアップを実行すると、どこで登録されているかを特定できる場合があります。
    IP アドレスの登録ソース アクセスの理由
    Google 検索エンジン (通常は悪意をもたないボット)。
    Amazon Web Services (AWS) 悪意をもたないアクセス (販売を向上させるためにインターネットで使用する情報を収集)
    悪意をもつアクセス (テキスト、画像、価格などの価値のあるコンテンツを特定するためにサイトをターゲットにしている在庫データ取得ボット)
    競合会社 インテリジェンスを収集するためにサイトをスキャンしている競合会社。

WAF のシミュレーションモードでの実行で多くの悪意をもつアクセスが見つかった場合は、WAF の機密性レベルを上げることができます。または、WAF が実際の買い物客でトリガーされている場合は、機密性を下げることができます。

B2C Commerce での WebDAV の認証と承認

WebDAV は、データやコードファイルのアップロードとダウンロードを可能にするプロトコルです。マーチャントは WebDAV リクエストをインスタンスの WebDAV サーバーに送信します。マーチャントの WebDAV クライアントは Business Manager ユーザー、またはマシン対マシンのインタラクションのための API クライアントとすることができます。

マーチャントの WebDAV クライアントが Cyberduck などの Business Manager ユーザーである場合、Salesforce B2C Commerce では基本認証 (ユーザー名とパスワード) を使用して認証が行われます。Business Manager で認証ルールを指定するには、役割モジュール (WebDAV の許可タブ) でフォルダーごとのルールを設定します。

マーチャントの WebDAV クライアントが API クライアントの場合は、B2C Commerce では Account Manager によって作成された認証トークンを使用して認証が行われます。認証トークンを取得するには、API クライアントは client-id と client-secret を Account Manager に示します。Business Manager で認証ルールを指定するには、WebDAV クライアントの許可モジュールでフォルダーごとのルールを構成します。

さらに、OAuth 2.0 Authorization Code Grant は WebDAV に使用できます。詳細については、インターネット技術標準化委員会 (IETF) 仕様の「Authorization Code Grant」セクションを参照してください。このシナリオでは、Account Managerのユーザーには OAuth のトークンを使用するインスタンスに一致するテナントフィルターとともに、Business Manager 管理者 または Business Manager User の役割が割り当てられている必要があります。
