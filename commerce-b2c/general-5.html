静的キャッシュの無効化

B2C Commerce サイトでの保護を強制するために、静的コンテンツキャッシュを無効にします。無効にしないと、配信済みの保護されていないコンテンツが期限切れになるまで有効のままになってしまいます。パスワードを変更した場合、新規パスワードの使用を強制するために静的コンテンツのキャッシュを無効にします。

必要なエディション

使用可能なソリューション: B2C Commerce
  1. 管理 | サイト | サイトの管理 | サイト名 | キャッシュの順に選択します。
  2. キャッシュタブで、インスタンスタイプを自分のインスタンスタイプに設定します。
  3. キャッシュの無効化セクションで、1 番上の無効にするボタンをクリックします。
    2 番目の「無効にする」ボタンをクリックすると、パイプラインページのキャッシュのみがクリアされ、保護されていないコンテンツは引き続き配信されます。
  4. 適用をクリックします。

B2C Commerce のアクセス設定の構成

IP アドレスに基づいてアクセスを制限します。許可リストまたはブロックリストを提供しない場合は、この機能はアクティブにはならず、これらの設定は効果をもちません。このトピックは、B2C Commerce に該当します。

必要なエディション

使用可能なソリューション: B2C Commerce

Business Manager の IP 許可リストとブロックリストは、不正な手段を使用して有効な認証情報を入手した攻撃者をブロックするために使用します。たとえば、元従業員が退社前に認証情報を入手した場合や、ソーシャルエンジニアリングを通じて従業員以外の人物が認証情報を入手した場合などです。これらのリストは、総当たり攻撃を阻止するためのものではありません。

統合認証を使用せずに Business Manager にログインする場合、これらのリストは Business Manager が認証情報を検証する前に適用されます。

統合認証を使用せずに WebDAV またはエージェントユーザーログイン処理を使用してログインする場合は、Business Manager が認証情報を検証した後にリストが適用されます。

統合認証を使用してログインする場合は、ログイン方法にかかわらず、これらのリストは Business Manager が認証情報を検証した後に適用されます。

  1. Business Manager で、アプリケーションランチャーをクリックし、管理 > グローバル環境設定 > セキュリティの順に選択します。
  2. アクセス制限タブで、Business Manager にアクセスを許可する許可リストの IP アドレスの範囲を入力します。
  3. Business Manager にアクセスを許可しないブロックリストの IP アドレスの範囲を入力します。
    IP アドレスがブロックリストと許可リストの両方に含まれている場合は、アクセスは拒否されます。
  4. 無効なログイン試行をエラーログに記録するかどうかを選択します。
  5. 無効なログイン試行が発生した際に Eメールを送信するには、1 つまたは複数の Eメールアドレスをセミコロンで区切って入力します。
    Eメールアドレスを指定しないと、Eメールは送信されません。
  6. 明確に許可リストに追加されていない IP アドレスのログインアクセスをブロックするかどうかを選択します。
    このオプションが選択されていない場合、明確に許可リストに追加されていない IP アドレスが Business Manager にアクセスできます。
  7. 無効なログイン試行を、ログインの失敗回数にカウントするかどうかを選択します。
    このオプションを選択すると、ユーザーがロックアウトされることがあります。
  8. 適用をクリックします。

B2C Commerce の HTML 属性内の JavaScript とオブジェクト

セキュリティ上の理由から、Account Manager の多要素認証などの強力な認証をもつ Business Manager ユーザーのみが、データベースオブジェクトの HTML 属性に JavaScript および iframe、object、applet、embed タグで埋め込まれているオブジェクトを含めることができます。このトピックは、B2C Commerce に該当します。

強力な認証をもつ Business Manager ユーザーは、強力な認証のないユーザーに対し、一時的に HTML 属性への JavaScript とオブジェクトの埋め込みを許可することができます。管理 | グローバル環境設定 | 属性内の JavaScript の順に移動し、有効にするをクリックします。強力な認証のないユーザーは 1 時間の間、HTML 属性に JavaScript とオブジェクトを埋め込むことができます。

Account Manager で多要素認証を使用してユーザーを認証するには、Business Manager で管理 | グローバル環境設定 | セキュリティの順に移動して、Account Manager での統合認証を有効にします。また Account Manager で、ユーザーのアカウントを多要素認証を必要とする役割に割り当てます。

重要 HTML 属性内の JavaScript と埋め込みオブジェクトの問題とは別に、Salesforce ではすべての Business Manager ユーザーに対して多要素認証を実装することを強くお勧めしています。

Tableau コネクタの起動

Tableau デスクトップアプリケーションからコネクターを Web データコネクタとして起動し、B2C Commerce データを Tableau に接続します。

  1. Web Data Connector をクリックします。
  2. ポップアップ画面で、データコネクタの URL https://ccac.analytics.commercecloud.salesforce.com/twdc/ を入力します。
  3. B2C Commerce Account Manager ログインで、Account Manager API のクライアント ID とパスワードを入力します。
  4. LOG IN (ログイン) をクリックします。
  5. データ領域を選択します。
    1. Tableau でアクセスしたいデータの領域のタイルをクリックします。
    2. B2C Commerce の実装に複数のレルムがある場合は、データを分析したいレルムを Realm (レルム) ドロップダウンから選択します。
      メモ コネクターは、選択したレルムに割り当てられたすべてのサイトからデータを取得します。
  6. 使用する属性とメトリクスを選択します。すべての属性を選択するには、Attributes (属性) を選択します。すべてのメトリクスを選択するには、Metrics (メトリクス) を選択します。すべての属性とすべてのメトリクスを選択するには、FIELDS (フィールド) を選択します。
    メモ クエリにかかる時間を最小にするには、クエリに必要な属性とメトリクスのみを選択します。
  7. 評価する日付の範囲を選択します。最大は 3 か月です。最大 3 か月までのデータがある過去のデータを表示します。
  8. Create Datasource (データソースの作成) をクリックします。
    Tableau によってデータがインポートされます。これで Tableau を使用してデータの視覚化を作成できるようになります。

プロキシゾーン設定の構成

レガシーゾーンの移行のためにプロキシゾーン設定を構成します。

必要なエディション

使用可能なソリューション: B2C Commerce

レガシーゾーンをプロキシゾーンに移行すると、ほとんどのゾーン設定が自動的に転送されます。ただし、一部の設定は、レガシーゾーンからプロキシゾーンに手動でコピーする必要があります。

  1. Business Manager で、アプリケーションランチャーをクリックし、管理 | サイト | 埋め込み CDN 設定の順に選択します。
  2. Logpush 設定をコピーします。
    1. 以前に移行したレガシーゾーンのウィンドウで、設定 | Logpush の順に選択します。
    2. logpush 設定を選択してコピーします。
    3. 新しいプロキシゾーンで、設定 | Logpush の順に選択します。
    4. logpush 設定を貼り付けます。
    5. CDN-API を使用してバケットの所有権を検証します。eCDN Logpush を参照してください
  3. API を使用したレート制限ルールをコピーします。
    1. レガシーゾーンで、設定 | API を使用したレート制限ルールの順に選択します。
    2. API を使用したレート制限ルールを選択してコピーします。
    3. 新しいプロキシゾーンで、設定 | API を使用したレート制限ルールの順に選択します。
    4. API を使用したレート制限ルールを貼り付けます。
    5. CDN-API を使用してバケットの所有権を検証します。eCDN レート制限ルールを参照してください

カスタム証明書を使用したカスタムホスト名の作成

レガシーゾーンをプロキシゾーンに移行すると、検証メソッドが「http」に設定された証明書が自動的に作成されます。別の検証メソッドが必要な場合は、生成された証明書を削除し、カスタムの証明書を追加します。Business Manager でカスタム証明書を作成するか、addCertificateForZone API を使用します。

必要なエディション

使用可能なソリューション: B2C Commerce
  1. Business Manager で、アプリケーションランチャーをクリックし、管理 | サイト | 埋め込み CDN 設定の順に選択します。
  2. ホスト名リストからプロキシゾーンを選択し、証明書をクリックします。
  3. 暗号化タブで、リストからゾーンを選択します。
  4. 更新したい証明書の設定アイコンをクリックします。
  5. 自己管理証明書を選択します。
  6. 証明書プロバイダーから受け取った証明書と秘密鍵を貼り付けます。
  7. 証明書を割り当てるホスト名を選択します。
  8. 証明書の更新をクリックします。

レガシーゾーンの削除

すべてのサブドメインをプロキシゾーンに移動した後、ゾーンの削除オプションを使用してレガシーゾーンを削除します。

必要なエディション

使用可能なソリューション: B2C Commerce

検証には 2 つのオプションがあります。

  1. Business Manager で、アプリケーションランチャーをクリックし、管理 | サイト | 埋め込み CDN 設定の順に選択します。
  2. 「暗号化」タブでレガシーゾーンを選択し、ゾーンの削除をクリックします。

    各インスタンス (Dev/Stg/Prod) で移行を実行し、すべてのインスタンスで正常に移行されたら、Production (本番) インスタンスからレガシーゾーンを削除します。

プロキシゾーンへの移行

セキュリティを強化し、負荷分散を改善し、規制要件に準拠するために、レガシーゾーンをプロキシゾーンに移行します。

必要なエディション

使用可能なソリューション: B2C Commerce

レガシー/Orange-to-Orange (O2O) の競合

完全修飾ドメイン名 (FQDN) (例: merchantsite.com) に対して (eCDN 経由で、または既存の Cloudflare 顧客/O2O として) アクティブなレガシーゾーンがすでにある場合は、レガシーゾーンがプロキシゾーンよりも優先されます。このシナリオでは、ワイルドカードのカスタムホスト名は機能しません。ホスト名の優先順位を参照してください。

メモ レガシーゾーンは、Development (開発)、Staging (ステージング)、Production (本番) の各インスタンスで共有されます。各インスタンス (Dev/Stg/Prod) で移行を実行し、すべてのインスタンスで正常に移行されたら、Production (本番) インスタンスからレガシーゾーンを削除します。
  1. Business Manager で、アプリケーションランチャーをクリックし、管理 | サイト | 埋め込み CDN 設定の順に選択します。
  2. 移行するレガシーゾーンを選択します。
  3. 「プロキシゾーンへの移行」をクリックします。
  4. プロキシゾーンのステータスに「検証済み」と表示され、新しいプロキシゾーンのホスト名が表示されるまで待ちます。

証明書をアップロードするか、新しいホスト名に自動証明書を使用します。

メモ ゾーンが現在 Apex/ルートドメインを指している場合は、B2C Commerce プラットフォームの eCDN を使用したルートドメインの構成、APEX/ルートドメインをサブドメインにリダイレクトしたくない場合はどうすればよいかを参照してください。

認証 DNS の更新

ストアフロントの DNS レコードを更新します。DNS CNAME レコードの値を取得するには、getZonesInfo 名前プロパティを使用します。

必要なエディション

使用可能なソリューション: B2C Commerce

開始する前に、ホスト名のステータスが「アクティブ」であることを確認します。 .

  1. DNS プロバイダーアカウントにログインします。
  2. ゾーンを検索し、リストから選択します。
  3. DNS タブで、マッピングするホスト名を見つけます。
  4. "is an alias of" (は次のエイリアス: ) の後のすべてのテキストを、Business Manager からの DNS CNAME に置き換えます。
  5. ステータス列のクラウドを、ツールヒント「DNS のみ」をもつグレーのクラウドとして表示されるまでクリックします。
    メモ この手順では、いくつかの可能性のうちの 1 つを例として示します。実際の結果は DNS プロバイダーによって異なります。

別のアカウントの DNS プロバイダーで同じルートドメインを使用している場合は、DNS を新しいゾーンにポイントします。新しいゾーンをポイントすると、トラフィックを標準ゾーンやルートゾーンではなく、新しいゾーンに送信することが示されます。

Page Designer の一括ローカライゼーションのためのローカライズ可能な要素のエクスポート

ローカライゼーションプロセスにかかる時間を短縮するために、2 つの API ジョブを使用して、ローカライゼーションのエクスポートとインポートを構成します。このトピックは、B2C Commerce に該当します。

まず始めに、エクスポートする PageID のリストを提供するカスタムジョブステップ (以下のドキュメントでは FindPages と呼ぶ) を作成します。このプロセスの詳細については、カスタムジョブステップの作成を参照してください。

以下のサンプルコードは参照用です。

FindPages.js

/**
* Sample logic for finding Page Designer pages for bulk translation
*
* @module cartridge/scripts/jobsteps/FindPages
*/

'use strict';

/**
* Find the pages main function
*
* @param {object}  parameters Job step parameters
* 
* @param {boolean} parameters.IsDisabled Mark the step as disabled - skips step execution and returns an OK status
* @param {string}  parameters.TranslationContentFolder The content folder for pages for translation
* @param {string}  parameters.OutputPageIDsFile File with list of IDs of pages found for translation, relative to the 'Impex/src' folder
* @param {boolean} parameters.OutputUnassignmentFile File with unassignments for the Page Designer pages from the translation folder, relative to the 'Impex/src' folder, not created if omitted
* @param {string}  parameters.NoDataFoundStatus No Data for translation found exit code
* 
* @param {dw.job.JobStepExecution} stepExecution Represents an execution of a step that belongs to a job
* 
*/
function DoFindPages(parameters, stepExecution) {
	var 
		Status = require("dw/system/Status"), 
		ContentMgr = require("dw/content/ContentMgr"),
		File = require("dw/io/File"),
		FileWriter = require("dw/io/FileWriter");
	
	var folder, foundContent, content, contentFolder, impexsrc, pageidsFile, pageidsWriter, unassign, unassignFile, unassignWriter;
	
	if (parameters.IsDisabled) {
	    return new Status(Status.OK, "SKIPPED", "The job step " + stepExecution.stepID + " was skipped");
	}
	
	folder = ContentMgr.getFolder(parameters.TranslationContentFolder); // get contents of translation folder
	foundContent = (folder != null) && (folder.content.length > 0);
	if (foundContent) {
		foundContent = false;
		impexsrc = new File('IMPEX/src');
		pageidsFile = new File(impexsrc, parameters.OutputPageIDsFile);
		pageidsWriter = new FileWriter(pageidsFile, "UTF-8");
		unassign = !!parameters.OutputUnassignmentFile;
		if (unassign) {
			unassignFile = new File(impexsrc, parameters.OutputUnassignmentFile);
			unassignWriter = new FileWriter(unassignFile, "UTF-8");
			unassignWriter.writeLine('<?xml version="1.0" encoding="UTF-8"?>');
			unassignWriter.writeLine('<library xmlns="http://www.demandware.com/xml/impex/library/2006-10-31" library-id="' + ContentMgr.siteLibrary.ID +'">');
		}
		for (var i=0; i<folder.content.length; i++) { // loop through the folder content
			content = folder.content[i];
			if (content.page) {
				foundContent = true;
				pageidsWriter.writeLine(content.ID); // write page ID to the result pages list file
				if (unassign) {
					unassignWriter.writeLine('  <content content-id="' + content.ID + '">'); // write content xml for unassigning the page from the translation folder
					unassignWriter.writeLine('    <folder-links>');

					for (var j=0; j<content.folders.length; j++) {
						contentFolder = content.folders[j];
						unassignWriter.write('      ');    
						if (contentFolder.ID == folder.ID) { // as it is not possible to just delete a folder assignment, all folders a listed without the translation one
							unassignWriter.write('<!-- ');   // an XML comment is used to not include the translation folder, but it is also possible to omit it in the content xml
				        }
						if (contentFolder.ID == content.classificationFolder.ID) {
							unassignWriter.write('<classification-link folder-id="'+contentFolder.ID+'"/>')
						} else {
							unassignWriter.write('<folder-link folder-id="'+contentFolder.ID+'"/>')
						}
						if (contentFolder.ID == folder.ID) {
							unassignWriter.write(' -->');
				        }
						unassignWriter.writeLine('');
					}
					unassignWriter.writeLine('    </folder-links>');
					unassignWriter.writeLine('  </content>');
				}
			}
		}
		pageidsWriter.flush();
		pageidsWriter.close();
		if (unassign) {
			unassignWriter.writeLine('</library>');
			unassignWriter.flush();
			unassignWriter.close();
		}
	}
	if (!foundContent) {
		return new Status(Status[parameters.NoDataFoundStatus], "NO_DATA_FOUND", "No pages were found for translation in folder " + parameters.TranslationContentFolder)
	}
}

Page Designer の一括ローカライゼーションのための要素のエクスポート

ローカライゼーションプロセスをスピードアップするには、カスタムジョブを使用して 1 つまたは複数のページのローカライズ可能な要素をエクスポートします。このトピックは、B2C Commerce に該当します。

必要なエディション

使用可能なソリューション: B2C Commerce

ローカライゼーションのために要素をエクスポートする前に、どのページをローカライズするかについて明確に定義する必要があります。

  1. Business Manager でジョブを作成するには、アプリケーションランチャーをクリックし、管理 | オペレーション | ジョブの順に選択した後、新規ジョブをクリックします。
  2. 新しく作成されたジョブをクリックして、スケジュールと履歴タブをクリックします。ジョブを実行するために必要な間隔を設定します。
  3. ジョブステップタブをクリックします。
    このジョブには 4 つのステップがあります。
    1. FindPages - ローカライゼーションのために作成した定義済みフォルダー内のすべてのページを見つけ、一括ローカライゼーションプロセスで使用される 2 つの出力ファイルを生成します。
    2. ExportPageLocalization - エクスポートページファイルを作成します。

      カスタムジョブステップで作成したファイルのファイル名を使用して、ExportPageLocalization エクスポートセットを構成します。

      Resource ファイルタイプを使用することをお勧めしますが、使用するファイルタイプについてローカライゼーションチームと調整を行ってください。

      メモ 地域情報を設定した場合は、エクスポートではその地域情報からのデータが使用されます。地域情報が設定されていない場合は、システムでデフォルトの地域情報が使用されます。
    3. ImportPageUnassignments - このジョブステップはコンテンツをインポートします。ImportMode をマージに設定します。
    4. FtpUpload - ローカライズするコンテンツをアップロードするカスタムジョブステップです。
  4. ジョブを手動で実行するには、ジョブの実行をクリックするか、マーチャンダイザーおよびローカライゼーションチームと調整してジョブの実行をスケジュールします。
    B2C Commerce は、各ページに対して 1 つのファイルを含む .zip ファイルとしてページをエクスポートします。
  5. 組織のローカライゼーションチームにコンテンツを提供します。このプロセスはカスタムジョブステップで自動化できます。
    ファイル内のテキストは、ページに表示される順番であるとは限らないことに注意してください。これらのファイルをハンドオフする際には、コンテキストを提供するために URL やスクリーンショットなどを添付することをお勧めします。
  6. 組織のローカライゼーションプロセスを使用して、コンテンツをローカライズします。

Page Designer ページのローカライズの管理

Page Designer でページを追加する場合は、基本言語 (通常はデフォルトの地域情報) で作成します。ページを作成すると、Page Designer によって、Business Manager で定義されているフォールバック階層に各地域情報のバリエーションが追加されます。次に、ページバリアントを使用し、必要に応じてコンポーネントを各地域情報用にローカライズします。このトピックは、B2C Commerce に該当します。

必要なエディション

使用可能なソリューション: B2C Commerce

Page Designer でコンテンツをローカライズする方法については、ビデオをご覧ください。

たとえば、デフォルト地域情報でページを作成し、カナダフランス語のフォールバック階層がデフォルトfr_CA > fr > 場合、fr_CA と fr のページバリアントも作成されます。これらの各ページバリアントについて、コンテンツをコンポーネントレベルでローカライズするか、またはフォールバック階層に従って表示されるようにコンポーネントをそのままにしておきます。カナダフランス語 (fr_CA) ページバリアントのコンポーネントにローカライズされたカナダフランス語のテキストまたは画像を提供すると、そのコンテンツはカナダフランス語ページに表示されます。カナダフランス語ページ用にローカライズしたテキストまたは画像がない場合、そのページでは、そのコンポーネントのコンテンツとして、フォールバック階層における次の地域情報 (この例では、フランス語 (fr) ページバリアント) のコンテンツが使用されます。フランス語ページでコンポーネントがローカライズされていない場合は、そのコンポーネントのコンテンツとして、フォールバック階層における次の地域情報 (この例では、デフォルト地域情報) のコンテンツが表示されます。コンポーネントにローカライズされたコンテンツを提供する場合は、フォールバックに戻すオプションを使用してローカライズされたコンポーネントを削除し、代わりにフォールバック階層のコンテンツを使用します。

最初にページを構成する場合、すべての地域情報ページのバリアントでは、ページ設定ウィンドウで SEO フィールドとローカライゼーションフィールドのページを設定した地域情報のテキストが使用されます。これらのフィールドでローカライズされたテキストを使用するには、地域情報ページのバリエーションに移動し、ローカライズされたテキストを入力します。ただし、SEO タブまたはローカライゼーションタブで変更を保存すると、両方のタブのすべてのテキストでフォールバックテキストへのリンクが解除されます。地域情報ページのバリアントの SEO フィールドとローカライゼーションフィールドではフォールバックに戻すオプションがありません。

  1. Business Manager で、Content | Page Designerに移動します。
  2. ビジュアルエディターを開いてコンテンツをローカライズするには、ページ ID を選択します。
  3. 上部にあるドロップダウンメニューから地域情報を選択します。
    ページバナーには、その地域情報のフォールバック階層が表示されます。ページ上の各コンポーネントにカーソルを合わせると、ローカライズされていないコンポーネントの周囲にピンクのボックスとフォールバックラベルが表示されます。
  4. ローカライズするコンポーネントを選択し、右側のペインでテキストまたは画像を変更して、「適用」をクリックします。このローカライズされたコンポーネントの周囲にはブルーのボックスが表示されるようになります。
  5. ローカライズされたコンポーネントを削除し、フォールバック階層のコンテンツを使用するには、右側のペインのドロップダウンメニューから [ フォールバックに戻す ] を選択します。
    フォールバックに戻すと、このコンポーネントのローカライズされたバージョンは永久的に削除されます。
  6. この地域情報のページを表示または非表示にするには、以下の手順に従います。
    1. この地域情報で表示、またはページ設定アイコンのいずれかを選択します。
    2. 「この地域情報でページを表示」の設定を「表示」または「非表示」にします。
    3. (オプション) この地域情報の名前または説明を変更します。
    4. 保存をクリックします。
    デフォルトでは、ページはサポートされているすべての地域情報で表示されます。

Log Center

Log Center は、システムおよびカスタムコードから生成されたレルムログメッセージを表示するために使用できるアプリケーションです。Log Center から、プライマリインスタンスグループ (PIG) とセカンダリインスタンスグループ (SIG) のすべてのテナントレルムログにアクセスできます。Log Center ダッシュボードの表示、ログの検索、ログストリーミングの設定、および Control Center 監査イベントの表示を行います。管理者権限を持っている場合は、ログレベルとボリュームを構成できます。

  • Log Center へのアクセス
    Log Center には、ブラウザーまたは Business Manager からアクセスします。
  • Log Center ダッシュボード
    ダッシュボードは、Account Manager のテナントフィルターとレルムの割り当てに基づいて設定されます。管理者およびサポートの役割を担うユーザーは、ダッシュボードを任意の会社レルムのデータを表示するように設定できます。ダッシュボードのデフォルト設定では、過去 10 日間の上位スタックトレースのヒストグラムが表示されます。正確な各スタックトレース数を表示するには、チャート内のバーにマウスオーバーします。
  • Account Manager 監査ログイベント
    Log Center は、ユーザー、API クライアント、組織への変更を含む、Account Manager の監査ログイベントを発行します。フィルターとキーワード検索を使用して、選択した期間内の特定のフィールドの変更またはアクションイベントを追跡します。
  • Log Center 検索
    Log Center を使用して、カスタム検索でログを検索できます。期間、メッセージの重大度、問題のタイプ、キーワード、特定のテキスト、その他の属性のカテゴリから、クエリフィルターを使用して検索を構成します。
  • Log Center の構成
    ビジネスニーズに合わせて Log Center の表示を変更します。また、Log Center の管理者はログレベルとログボリュームを構成できます。
  • 監視強化のためのログストリーミング
    Log Center は、サードパーティの監視ツールや分析ツールへのログストリーミングをサポートしています。また、汎用 HTTP 接続を使用してログをストリーミングすることもできます。これらのツールを使用すると、Log Center ユーザーはエンタープライズ規模の監視および自動化機能を利用できます。B2C Commerce の Log Center をご利用のすべてのお客様は、追加費用なしでログストリーミングを利用できます。
  • Log Center での異常検出
    パフォーマンスの低下、運用上の問題、不審なアクティビティを Log Center の異常なパターンから特定します。Log Center は受信したログデータを継続的に分析し、学習したベースライン動作と比較します。データがベースラインから逸脱し、しきい値に達すると、Log Center は異常にフラグを立てます。このトピックは、B2C Commerce に該当します。これらのガイドラインを使用して、誤検知を減らし、検出器の精度を向上させます。
  • Log Center での異常検出機能の設定
    異常なログパターンを特定し、必要に応じて、異常がアラートのしきい値に達したときにアラートを送信します。Log Center は受信したログデータを継続的に分析し、学習したベースライン動作と比較します。データがベースラインから逸脱し、しきい値に達すると、Log Center は異常にフラグを立てます。このトピックは、B2C Commerce に該当します。
  • メトリクスダッシュボード
    メトリクスダッシュボードを使用して B2C Commerce ストアフロントのパフォーマンス、セキュリティ、リソース活用を監視します。このダッシュボードを使えば、デベロッパーの生産性を高め、解決までの平均時間を短縮し、トラブルシューティングを効率化できます。モニターできるメトリクスには、アプリケーションのパフォーマンス、売上、埋め込みコンテンツ配信ネットワーク (eCDN)、B2C Commerce API (Shopper Commerce API (SCAPI)) と SCAPI フック、マネージドランタイムのメトリクスがあります。
  • B2C Commerce の Log Center アラート
    一元化されたインターフェイスから、すべての Log Center データソースのカスタムアラートを監視します。ユーザーに影響を与える前に、アプリケーションのパフォーマンス低下を特定するように通知を構成します。メール、Slack、PagerDutyを介してリアルタイムでアラートをルーティングし、チームが重要なシステムイベントに対応できるようにします。

監視強化のためのログストリーミング

Log Center は、サードパーティの監視ツールや分析ツールへのログストリーミングをサポートしています。また、汎用 HTTP 接続を使用してログをストリーミングすることもできます。これらのツールを使用すると、Log Center ユーザーはエンタープライズ規模の監視および自動化機能を利用できます。B2C Commerce の Log Center をご利用のすべてのお客様は、追加費用なしでログストリーミングを利用できます。

サポートされているツールは次のとおりです。

  • Splunk
  • Datadoc
  • New Relic
  • Grafana Loki
  • Sumo Logic
  • Dynatrace
  • AWS Elastic Cloud

ログ・ストリーミングに関するこの情報を確認し、構成します。

ログストリーミングの動作

  • Sandbox のログをストリーミングします。
  • ログが Log Center から生成されたことを確認するには、ログストリーミングの設定時にパラメータを指定します。ログをストリーミングする際、これらのパラメーターによって追加属性をメタデータとしてサードパーティベンダーに渡すことができます。これらのベンダーのほとんどは、Firehose の HTTP ヘッダー X-Amz-Firehose-Common-Attributes を解析でき、このメタデータを受け取ることができます。
  • ログストリーミングのオンとオフを切り替えるには、停止ボタンと再生ボタンを使用します。
    重要 ストリーミングを無効化してから再度有効化した場合、新しいログに対してのみストリーミングが再開されます。ログストリーミングがオフの場合、その期間のデータは失われます。

ログストリーミング構成のガイダンス

  • 同じレルムに対してログストリーミングを複数回構成すると、ログが重複する可能性があります。この状況を回避するために、本番ログと非本番ログ用に別々のログストリーミング構成を作成してください。構成を分けることで、ログは 1 回だけ送信され、データも整理しやすくなります。
  • ログストリームを構成した後にストリーミングされるのは新規ログのみです。既存のファイルはログストリームに含まれません。

ログストリーミングの頻度とパフォーマンス

  • ログはバッチでストリーミングされます。各メッセージ間の時間は、ログがキャッシュされてストリーミングされる速度に応じて、20 秒から 2 分になる場合があります。
  • ログストリーミングはリアルタイムサービスです。たとえば「5 分ごと」など、定期的にストリーミングするようにログを構成することはできません。また、過去の特定日数分のログをストリーミングすることもできません。
  • ログ量の上限はログストリーミングに影響しませんストリーミングは続行されます。

ログストリーミングのサポート

  • サードパーティツールのログとの統合に問題がある場合は、サポートチケットを作成してください。
  • ログストリーミングに使用する API トークンの有効期限が切れた場合、更新はユーザーの責任です。トークンの自動更新は行われません。

ログストリーミングに関するサードパーティのドキュメント

ログストリーミングは、基盤となるストリーミングサービスとして AWS Firehose を使用します。AWS Firehose 連携の詳細については、次のリソースを参照してください。

  • New Relic
  • 汎用 HTTP
  • Grafana Loki
  • Datadog
  • Splunk
  • Dynatrace
  • SumoLogic
  • AWS Elastic Cloud
  • サードパーティ監視ツールへのログストリーミングの設定
    エンタープライズ規模の監視と自動化のために、Splunk、Datadog、Grafana Loki、New Relic、Dynatrace、SumoLogic、AWS Elastic Cloudなどのサードパーティ分析プラットフォームにログをストリーミングします。また、汎用 HTTP 接続を使用して、ログを他のツールにストリーミングすることもできます。
  • ログストリーミング通知の設定

B2C Commerce でのログイン設定の構成

Business Manager では、ユーザーパスワードの制約とログインのロックアウトポリシーを構成することが重要です。

必要なエディション

使用可能なすべての値は、クレジットカード業界データセキュリティ基準 (PCI DSS) に準拠していることを確認します。統合認証の一部として、Account Manager がすべてのパスワードポリシーを管理します。詳細は、B2C Commerce での組織の編集を参照してください。

PCI DSS 標準に準拠するため、15 分間何も操作がないと、Business Manager はユーザーをログアウトします。このタイムアウトの値は変更できません。

  1. Business Manager で、アプリケーションランチャーをクリックし、次に管理 > グローバル環境設定 > セキュリティの順に選択します。
  2. ユーザー認証タブで、ユーザーがログインを間違えて入力できる回数と、B2C Commerce によってロックアウトされる期間を設定します。最大値とデフォルト値は両方とも 6 です。

  3. ユーザーにパスワードの変更を求めるまでの日数を設定します。デフォルトは 60 日です。
  4. B2C Commerce で未使用のアカウントが非アクティブになるまでの日数を設定します。デフォルトは 90 日です。
    ユーザーにはアカウントが無効になる 7 日前に Eメールが送られ、アカウントが無効にならないようにログインすることが指示されます。また、アカウントが無効になる 1 日前には 2 度目の Eメールがユーザーに送られます。
    非アクティブの期間を 10 日未満に変更した場合は、最初の Eメールはアカウントが無効になる 7 日前ではなく、3 日前に送信されます。
  5. パスワードを変更する場合に、ユーザーがセキュリティ用質問に答える必要があるかどうかを示します。
  6. 「パスワード履歴を強制」で、ユーザーのパスワード履歴から B2C Commerce に記憶されるパスワードの数を指定します。
    B2C Commerce では、新しいパスワードがこの履歴と照合され、ユーザーが固有のパスワードを使用しているかどうかが確認されます。デフォルトでは、4 個のパスワードが記憶されます。
    この値を設定するまで、パスワード履歴は保存されません。
  7. パスワードの文字の要件の設定を構成します。制限とデフォルトの値については、「Business Manager パスワードの保護」を参照してください。
  8. 適用をクリックします。

B2C Commerce での HSTS の管理

サイトを保護するために、HTTP Strict Transport Security (HSTS) は HTTPS のみを使用してドメインにアクセスするように Web ブラウザーに指示します。このトピックは、B2C Commerce に該当します。

  • B2C Commerce の HSTS の構成
    HTTP Strict Transport Security (HSTS) は、HTTPS のみを使用してドメインにアクセスするように Web ブラウザーに指示することでサイトを保護します。HSTS は、攻撃者がサイトに対してダウングレード攻撃を使用するのを阻止します。セキュリティを高めるために、事前読み込みを有効にします。これによって、サイトが初めてリクエストされた際に、Web ブラウザーがサイトを HTTPS で開くように強制されます。詳細については、HSTS のインターネット技術標準化委員会 (IETF) を参照してください。
  • B2C Commerce での HTTP Strict Transport Security (HSTS) の無効化
    HSTS の無効化は 2 つのステップによる処理です。まず買い物客に保護されていない接続を使用してサイトにアクセスさせ、次にサイトのヘッダーで HSTS の送信を中止します。

信頼できる IP アドレス一覧の作成と管理

信頼できる IP アドレスまたは CIDR 範囲の名前付きリストを作成して、信頼できるトラフィックのセキュリティチェックをバイパスするカスタムファイアウォールルールで使用します。

必要なエディション

使用可能なソリューション: B2C Commerce

管理対象 IP アドレスリストを作成または変更するには、Production (本番) インスタンスで eCDN 管理者の役割が必要です。本番以外のインスタンスでは、「Realm Security Rules」タブは読み取り専用です。

管理対象IPアドレス・リストは、IPアドレスまたはCIDR範囲の名前付きコレクションです。リストのスコープは、アカウント (レルム) レベルでレルム内のすべての適格ゾーンに適用するか、ゾーンレベルで 1 つのゾーンのみに適用するかのいずれかに設定できます。次の 2 つのリストタイプがサポートされています。

  • 許可リスト— セキュリティチェックをバイパスする IP アドレス。スキップアクションを含むカスタムファイアウォールルールとともに使用します。
  • ブロックリスト— 明示的にブロックする必要がある IP アドレス。ブロックアクションを含むカスタムファイアウォールルールとともに使用します。

リストを作成したら、そのリストを参照し、適切なアクションを指定するカスタム ファイアウォール ルールを作成します。「eCDN ゾーンのカスタムファイアウォールルールの作成」を参照してください。

重要 リスト名には、システムによって自動的にcustomer_が接頭辞として付きます。名前の部分のみを入力します。接頭辞は Business Manager では表示されませんが、内部的には必須です。たとえば、「trusted_ips」と入力すると、リストはcustomer_trusted_ipsとして保存されます。
  1. Business Manager でアプリケーションランチャーをクリックし、管理 | サイト | 埋め込み CDN 設定の順に選択します。
  2. 構成するゾーンを見つけ、ドロップダウンメニューから「ゾーンの構成」を選択します。
  3. 「セキュリティ・ルール」タブを選択し、「レルム・セキュリティ・ルール」サブタブを選択します。
  4. 「管理対象 IP アドレス・リスト」セクションで、「新規リスト」をクリックします。
  5. リストの範囲を選択します。
    範囲 説明
    アカウント このリストは、レルム内のすべての適格ゾーン (プロキシ、レガシー、およびデフォルトドメインゾーン) に適用されます。
    ゾーン このリストは、現在のゾーンにのみ適用されます。
  6. リストの名前を入力します。

    以下の命名要件に従います。

    • 小文字、数字、アンダースコアのみを使用します。
    • 入力する名前の最大文字数 41 文字 (システムによってcustomer_接頭辞が追加されるため、保存される名前の合計は最大 50 文字になります)。
    • ハイフンとスペースは使用できません。代わりにアンダースコアを使用します — たとえば、support-team-vpnの代わりに「support_team_vpn」と入力します。

    格納される名前の形式は、スコープとリストの種類によって異なります。

    範囲 リストの種類 格納される名前の形式
    Account 許可リスト customer_ name—たとえば、customer_trusted_ips
    Account ブロックリスト customer_blk_ name—たとえば、customer_blk_blocked_ips
    ゾーン 許可リスト customer_ zoneID _ name— ゾーン ID の最初の 8 文字が自動的に付加されますcustomer_81d5067d_trusted_ips
    ゾーン ブロックリスト customer_ zoneID _blk_ name—たとえば、customer_81d5067d_blk_blocked_ips

    ゾーンレベルのリスト名は、名前の競合を防ぐために、システムによってゾーン ID 接頭辞で自動的に名前空間化されます。同じレルム内の 2 つのゾーンは、競合することなく同じ名前のリストを持つことができます。

  7. 「IPアドレス」フィールドに、リストに含めるIPアドレスまたはCIDR範囲を入力します。

    1 行に 1 つのレコードを入力します。受け入れられるフォーマット:

    • 単一の IPv4 アドレス ( 例: 198.51.100.1 )
    • IPv4 CIDR 範囲 —198.51.100.0/24など
  8. 保存をクリックします。
    リストが [管理対象 IP アドレスリスト] セクションに表示されます。このリストを使用して信頼できるトラフィックのセキュリティチェックをバイパスするには、このリストを参照するカスタムファイアウォールルールを作成します。「eCDN ゾーンのカスタムファイアウォールルールの作成」を参照してください。

リストを編集するには、[管理対象 IP アドレス一覧] セクションからリストを選択し、IP アドレスを更新して、[ 保存 ] をクリックします。リストを削除するには、リストを選択して[削除 ] をクリックします。リストを削除すると、そのリストを参照しているカスタム ファイアウォール ルールもすべて削除されます。

B2C Commerce でのバックエンドシステムを介した属性の管理

属性データまたは新しい商品属性を定義するためにバックエンドカタログ管理システムを使用する場合は、カタログインポートを使用して新しい商品属性定義を B2C Commerce にインポートします。また、バックエンドシステムで管理される属性が Business Manager で編集できないようにします。

属性の管理に役立つ要素

catalog.xsd 内の product-attribute-definitions 要素では、complexType.AttributeDefinitions タイプが使用されます。このタイプには、次のような役に立つ要素が 2 つ含まれています:

  • externally-managed-flag - カスタム属性値が外部で管理されていて、Business Manager で編集できないことを示すために使用します。
  • externally-defined-flag - カスタム外部システムがカスタム属性定義を管理し、それをシステムにインポートするかどうかを示します。この要素は、マーチャントがカタログ管理システムを使用してカタログデータと商品メタデータを管理している場合を想定して用意されています。カタログ情報とともにインポートされる属性定義は、明示的に externally-defined とマークされます。externally-defined-flag を Business Manager で設定する方法はありません。
メモ ほとんどのメタデータ属性は、商品属性定義を作成する際に設定できますが、以下の属性は Business Manager からでないと設定できません:
  • order-required-flag
  • searchable

商品オブジェクトのカスタム属性定義

カタログインポートで作成されたカスタム商品属性定義は「searchable」または「order-required」にできません。ストアフロントに意図しない変更が加えられないようにするには、これらの属性設定はカタログインポート後に変更します。

メモ 新しい属性が買い物カゴ、注文手続き、または注文情報に影響するかどうかを慎重に検討してください。

B2C Commerce でのシーケンス番号の管理

Salesforce B2C Commerce では、自動的に生成されたオブジェクトインスタンスの固有識別子としてシーケンス番号を使用します。

必要なエディション

使用可能なソリューション: B2C Commerce

たとえば、注文を作成する際、B2C Commerce は注文を識別するために注文シーケンス番号を生成します。B2C Commerce を使用して、1 つのサイトおよび多数のサイトをもつ組織全体のシーケンス番号を構成します。注文番号は配送および請求書番号と関連付けられています。注文番号をサイト固有に構成すると、請求書および配送番号もデフォルトでサイト固有となります。

組織によっては、組織全体でシーケンス番号を管理することが非常に重要になります。外部のサードパーティによる組織全体のアプリケーションで顧客と注文のデータを管理する場合は特に重要です。

メモ 生成されたシーケンス番号は各オブジェクトタイプ内で一意であることが保証されていますが、連続した番号であることは保証されていません。生成された番号は、以前に作成した番号よりも大きい場合や、小さい場合があります。このため、生成されたシーケンス番号でオブジェクトを並べ替えた場合、作成された順序に並べ替えられるとは限りません。
  1. Business Managerで、アプリケーションランチャーをクリックし、管理 > グローバル環境設定 > シーケンス番号の順に選択します。次の項目用のグローバルシーケンス番号スキーム (組織) を指定します:
    • 注文番号
    • 請求書番号
    • 配送番号
    • 顧客ナンバー
    • ギフト券マーチャント ID
  2. アプリケーションランチャーをクリックし、マーチャントツール > サイト > サイト環境設定 > シーケンス番号の順に選択します。グローバルシーケンス番号スキームの代わりに使用するサイト固有のシーケンス番号スキームを指定します。
    1. 注文番号を次のように構成し、適用をクリックします:

      組織ごとに一意 (推奨): グローバル環境設定で番号スキームを管理します。

      サイトごとに一意: 次の項目についてサイト固有の番号スキームを指定します:

      • 注文番号
      • 請求書番号
      • 配送番号
      • ギフト券マーチャント ID
    2. ギフト券マーチャント ID を次のように構成し、適用をクリックします:

      組織ごとに一意 (推奨): グローバル環境設定で番号スキームを管理します。

      サイトごとに一意: ギフト券マーチャント ID のサイト固有の番号スキームを指定します。

  3. アプリケーションランチャーをクリックし、サイトの 管理 > サイト>顧客リスト > サイトの順に選択します。顧客リストレベルのシーケンス番号を指定します。
    シーケンス番号の動作を選択します:
    • 組織ごとに一意: (推奨) 顧客シーケンス番号は組織全体で一意で、構成を共有します。
    • 顧客リストごとに一意: 顧客ナンバーは、顧客リストごとに異なる書式で構成できます。これは、後で顧客リストを結合した場合に問題が発生する可能性があるため、お勧めしません。
  4. 3 つすべてのモジュールで、次のようにシーケンス番号を定義します:
    1. 開始点を定義します。
    2. すべてのシーケンス番号が適切な値から始まるように書式を設定します。
    3. 会社のニーズを反映した特別な書式を定義します。
    4. 以下の数式を使用して書式を変更します: 
      <prefix>{0,number,00000000}<suffix>

      各パラメーターの説明:

      パラメーター 説明
      <prefix> すべての注文番号が開始する静的文字列または番号。
      {0 自動生成される開始番号。書式パターンによって書式設定されます。
      number 数値を数値として書式設定するようにシステムに指示するキーワードとして解釈されます。
      00000000 番号に含める桁数を指定します。
      suffix すべての注文番号の末尾に追加する静的文字列または数字です。

      例:

      DW-{0,number,00000000}-05 は、DW-00000007-05 と変換されますが、この 00000007 は次に生成される注文番号です。

      XX-{0,number,00000000}-AA-{0,number,00000000}-ZZ の場合は、XX-00000001-AA-00000001-ZZなどの番号が生成されます。

古くなったデータの管理

古くなったデータとは、定義されている最新 の期間よりも古いデータのことです。最新の期間は各フィードごとに定義します。フィードがインポートされるたびに、そのフィードの商品の最新の期間がリセットされます。このトピックは、B2C Commerce に該当します。

フィードのデータが変動せず、各フィードでほとんど同じである場合は、最新の期間を問題なく設定できます。この期間は、インポートフィードがスケジュール通りにインポートされない場合に古いデータを保持するために使用します。ただし、フィードのデータが変動しやすく、正しくない可能性が高い場合は、古くなっているデータを異なる方法で処理するように最新の期間を設定することを検討してください。商品が特定フィードに含まれていない場合、その最新の期間はリセットされません。

未定義のデータや古くなったデータの処理は、そのデータを使用する検索並べ替えルール、プロモーションルール、および顧客セグメンテーションに固有です。

顧客セグメンテーションでは、ルール演算子を使用して、未定義の (または古くなった) 属性をもつ顧客を含めたり除外したりします。検索並べ替えルールでは、動的属性の値を計算するときに、古くなったデータや見つからないデータの代わりに使用するデフォルト値を定義します。

B2C Commerce での店舗の管理

Salesforce B2C Commerce ではBrick to Click (ブリックツークリック) のビジネスモデルがサポートされています。このトピックは、B2C Commerce に該当します。

多くのマーチャントはオンラインのストアフロントだけでなく、ブリックアンドモルタルと呼ばれる実店舗をもっています。この販売方法は Brick and Click (ブリックアンドクリック) ビジネスモデルと呼ばれ、は、マーチャントがオンラインとオフラインの両店舗をもっています。このモデルでは、顧客は従来どおり実店舗で購入することも、オンラインで商品を注文して商品を配送してもらうこともできます。このビジネスモデルは衣料店、小売店、電化製品店、および大型店舗で特に人気があります。

ブリックアンドクリックモデルにより、顧客にとって買い物の選択肢が広がります。マーチャントは、住所や電話番号、営業時間、セールイベントなどの実店舗情報を、オンラインの顧客が簡単にアクセスできるようにします。

Business Manager で店舗を作成し、店舗の位置情報ファイルを使用して、B2C Commerce 店舗検索機能に位置情報を提供します。

また、店舗で受け取り 機能をオンラインストアで提供することもできます。店舗で受け取り を設定するには、B2C Commerce API と Business Manager 設定を使用して、店舗を在庫リストに関連付けます。

新しいサイトへのアクティブデータの手動移行

古いソースサイトと新しいターゲットサイトが同じレルム内にある場合、アクティブデータを手動で移行できます。

必要なエディション

使用可能なソリューション: B2C Commerce

以下の手順は、古いソースサイトと新しいターゲットサイトが同じレルム内にある場合にのみ実行してください。そうでない場合は、新しいサイトがライブになるように設定されている 10 日前にカスタマーサポートに連絡し、新しいサイトがライブになる日にデータ移行を処理するように依頼してください。

警告 この手順中にエラーがあると、データが失われたり、アクティブデータが誤動作したりする可能性があります。プロセスについて質問がある場合や不明な点がある場合は、カスタマーサポートに連絡して、これがアクティブデータを移行するための正しい手順であることを確認してください。
  1. アクティブデータを移行する前に、次のことを行ってください。
    • 営業時間終了の少なくとも 2 時間前には新しいサイトがオンラインになるように設定します。
    • 古いサイトをオンラインからメンテナンスに変更した後に、少なくとも 90 分間待ちます。

    2. 新規ジョブをクリックし、ID と説明を入力します。
    3. 「ジョブステップ」タブからステップを構成し、UploadActiveDataToStorage を選択します。
    4. 必要な設定を完了し、割り当てるをクリックします。
    5. 範囲をサイトパラメーターに設定します。
    6. 「ジョブ」のメインページに戻り、ジョブを選択して、実行をクリックします。
      ジョブをただちに実行します。完了したら、生成されたジョブのログのストレージフォルダー名をメモします。
  3. アクティブデータを新しいサイトにダウンロードします。これらの手順は、同じ営業日内に完了します。
    1. 新しいサイトで、アプリケーションランチャーをクリックし、管理 | オペレーション | ジョブの順に選択します。
    2. 新規ジョブをクリックし、ID と説明を入力します。

    5. 新しいサイトの範囲をサイトパラメーター に設定します。
    6. 「ジョブ」のメインページに戻り、ジョブを選択して、実行をクリックします。
      ジョブをただちに実行します。

レガシーゾーンのプロキシゾーンへの移行

B2C Commerce Business Manager または CDN-API を使用して、レガシーゾーンをプロキシゾーンに移行します。プロキシゾーンでは、標準の eCDN 構成と最新のセキュリティ機能が採用され、一般的な階層割り当ての問題が防止されます。レガシーシステムをプロキシゾーンに移行するには、スムーズな移行を提供し、システムの整合性を維持するためのいくつかの重要な手順が含まれます。レガシーゾーンはサポートされていないため、この移行は Hyperforce への移行に不可欠です。

  • プロキシゾーンへの移行
    セキュリティを強化し、負荷分散を改善し、規制要件に準拠するために、レガシーゾーンをプロキシゾーンに移行します。
  • プロキシゾーン設定の構成
    レガシーゾーンの移行のためにプロキシゾーン設定を構成します。
  • カスタム証明書を使用したカスタムホスト名の作成
    レガシーゾーンをプロキシゾーンに移行すると、検証メソッドが「http」に設定された証明書が自動的に作成されます。別の検証メソッドが必要な場合は、生成された証明書を削除し、カスタムの証明書を追加します。Business Manager でカスタム証明書を作成するか、addCertificateForZone API を使用します。
  • 認証 DNS の更新
    ストアフロントの DNS レコードを更新します。DNS CNAME レコードの値を取得するには、getZonesInfo 名前プロパティを使用します。
  • レガシーゾーンからのサブドメインの削除
    レガシーゾーンからサブドメインを削除する場合は、古い証明書が Web サイトに表示されないようにします。
  • 新しい証明書の検証
    管理プロセスまたは自己管理プロセスを使用して、新しい証明書を検証します。
  • レガシーゾーンの削除
    すべてのサブドメインをプロキシゾーンに移動した後、ゾーンの削除オプションを使用してレガシーゾーンを削除します。

Web アプリケーションファイアウォール (WAF) カスタムルールへの信頼できる IP 移行について

Salesforce がレガシーの信頼できる IP 構成を WAF カスタムルールと管理 IP アドレスリストに自動的に移行する方法と、移行した構成を検証する方法を学習します。

変更点

従来の信頼できる IP 構成 (以前はゾーン設定スライダーの ファイアウォール タブで管理) は、新しいレルムセキュリティルール タブの 2 つのコンポーネントに置き換えられます。

  • 管理対象 IP アドレス一覧:アカウント (レルム) レベルまたはゾーンレベルでスコープが設定された、信頼できる IP アドレスまたは CIDR 範囲の名前付きリスト。
  • スキップアクションを含むカスタムファイアウォールルール:IP アドレスリストを参照し、信頼できるソースからのトラフィックに対してバイパスするセキュリティチェックを指定するルール。

この変更は、Business Manager の新しい LWC ベースのゾーンの構成インターフェイスへの eCDN ゾーン構成設定の広範な移行の一環です。

Salesforce が自動的に行うこと

Salesforce では、既存の信頼できる IP 構成が新しい形式に自動的に移行されます。信頼できる IP リストを手動で再作成する必要はありません。移行後:

  • 既存のアカウントレベルの信頼できる IP グループは、アカウントレベルの管理 IP アドレスリストになり、レルムセキュリティルールタブでカスタムファイアウォールルールが関連付けられます。
  • 既存のゾーンレベルの信頼できる IP グループは、関連するカスタム ファイアウォール ルールを持つゾーンレベルのマネージド IP アドレス リストになります。
  • リスト名は、レガシーアクセスルールのメモフィールドから派生します。システムは、ラベルを小文字のスラッグに変換し、英数字以外の文字をアンダースコアに置き換えて、customer_を前に付加します。以下がその例です:
    • TrustedVPNというラベルの付いたグループがcustomer_trustedvpnになります
    • Support-Team VPNというラベルの付いたグループがcustomer_support_team_vpnになります
    • ラベルのないグループは、接尾辞のないcustomer_になります
  • 移行はべき等です。移行プロセスが複数回実行される場合、既存の移行済みルールは検出され、重複は発生しません。二重移行を防ぐためのアクションを実行する必要はありません。
ヒント 移行後、リストとルールが Business Manager のレルムセキュリティルールタブに正しく表示されていることを確認します。eCDN ゾーンのレルムセキュリティルールを参照してください。

信頼できる IP アドレスからのトラフィックがブロックされないようにするという主な目的は保持されます。新しいモデルでは、それを実装するメカニズムがよりターゲットを絞っています。

攻撃面の最小化

安全な開発における全体的なリスクを軽減するには、潜在的な攻撃者にさらされる攻撃面を減らします。ポートを開くたびに、コードで外部ライブラリを使用するたびに、そしてユーザーにデータへのアクセスを付与するたびに、新しい攻撃面が作成されます。システムに対する全体的なリスクを軽減するには、攻撃面を最小限に抑えます。

次に例をいくつか示します。

  • FTP、SMB、Telnet などの不要なサービスをサーバーで実行すると、これらのリッスンサービスの脆弱性を利用する機会を攻撃者に与えることになります。
  • HTTPS のみで作成された Web API をサーバーで公開することで、攻撃可能なポートを最小限に抑え、傍受を防止できます。
  • 多くのサードパーティライブラリをコードで使用する機能には、不要なものもあり、これらのライブラリのいずれかに潜在的な問題があります。
