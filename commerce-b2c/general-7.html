B2C Commerce の静的マッピング

B2C Commerce で、既存のレガシー URL から新しい URL への静的マッピングを作成します。URL には、動的パイプライン呼び出しまたは静的リソースのいずれかを指定できますが、ソース URL がシステムにとって未知であることを確認してください。Staging (ステージング) インスタンスから Production (本番) インスタンスに静的マッピングをレプリケートします。Business Manager の構成のファイルサイズは 2MB に制限されています。この制限を超えた場合は、サイトのインポートとエクスポートの機能を使用して静的マッピングを更新します。

メモ 静的マッピングでは、まずマーチャントツール | サイト | SEO & 検出可能性 | エイリアスモジュールでホスト名エイリアスを構成する必要があります。ドメイン名を使用してください。

各行には、各部分を空白で区切ったマッピング定義が 1 つ含まれます。コメント行を追加するには、行の最初の空白以外の文字として ASCII の '#' または '!' を使用します。空白を含む URL は、空白を一重引用符で囲んでマッピングします。

ワイルドカードを使用したマッピングは、URL を前または後ろに付加する場合にのみ有効で、両方に付加することはできません。たとえば、**/a-sample-url** は無効なマッピングです。

この構文に続く動的パイプラインコール:

<legacy URL> [i] p,[<protocol>],[<host>],<pipeline>[,<locale>][,<parameter name>,<parameter value>]*

この構文に続く静的リソース:

<legacy URL> [i] s,[<protocol>],[<host>],[<unit>],[<locale>],<path>
パラメーター 注意事項
レガシー URL 相対 URL (ホスト名がなくパスのみ) または絶対 URL (ホスト名とパスが指定されている) のいずれかになります。'**' が接頭辞または接尾辞ワイルドカードとしてサポートされ、クエリ文字列ではワイルドカード '?**' が無視されます。
オプションの 'i' パラメーター 大文字と小文字を区別しない一致を示します。
<protocol> および <host> 指定されていない場合は、リクエストの各値が使用されます。
<pipeline> 動的パイプラインを示します。
<unit>

カタログ/ライブラリ/組織という構造でフォルダーに名前が付けられます。<unit> URL パラメーターは、ファイルシステムにある以下のいずれかのフォルダーを参照します。

  • カタログ (すべてのカテゴリおよび商品の画像)
  • コンテンツライブラリ (コンテンツアセットで使用しているすべての画像)
  • 組織 (プロモーション画像など、他のすべてのリソース)
<locale> 指定されていない場合は、デフォルトの地域情報が使用されます。
<parameter name>,<parameter value> 動的パイプラインコールとともに使用されます。<parameter name> または <parameter value> に空白が含まれている場合は、二重引用符 (" ") で囲みます。一重引用符 (' ') は使用しないでください。
<path> 静的リソースとともに使用されます。

次の変数はパスで使用するか、またはパラメーター値として使用します:

変数 説明
{_url} 元の URL 全体
{_path} 元の URL のパス部分
{_host} 使用されているホスト名
{_querystring} 元の URL のクエリ文字列
{<name>} 元の URL のパラメーター

空白を含む URL のマッピング

空白を含む URL をリダイレクトしたい場合は、空白を含む商品名またはブランド名を二重引用符で囲みます。

例 1: 空白を含む商品名のリダイレクト

リダイレクト先: http://www.mysite.com/Sites-MySiteID-Site/default/Product-Show?pid=MyProductID

例 2: 空白を含むブランド名のリダイレクト

静的マッピング: "/mapping with whitespaces" p,,,Search-Show,,prefn1,brand,prefv1,"Brand Name"

リダイレクト先: http://www.mysite.com/Sites-MySiteID-Site/default/Search-Show?prefn1=brand&prefv1=Hugo%20Boss

トラブルシューティング

SEO サポートモジュールから URL ルールモジュールへ移行した場合、URL アーカイブのリダイレクトによって静的マッピングが上書きされる場合があります。古い形式のリダイレクトをアーカイブから削除するには、SEO URL の URL アーカイブタブの使用を参照してください。

ステミング例外

ステミングを行うと単語が短い基本形になり、検索のヒット数が増加します。このトピックは、B2C Commerce に該当します。

たとえば、インデックス作成時にステミングを使用すると、locks、locker、locked などの単語はすべてステミングされ、lock になります。lock を検索すると、これらの派生形を含むドキュメントがすべて返されます。スペルミスが多い既知の用語について、デフォルトのステミングが自動的に上書きされるように B2C Commerce を構成します。たとえば、leggings と bedding の語幹はそれぞれ leg と bed ですが、どちらの場合も不適切で、顧客が商品を見つける助けにはなりません。例外リストを使用すれば、bedding というキーワードで検索したときには bedding を含む商品だけが見つかり、bed というキーワードで検索したときには bed を含む商品だけが見つかります。

複数形やその他の組み合わせを考慮するために、同じ語幹に複数の用語を指定します。たとえば、towel というキーワードの検索では towels と towel が含まれる商品が見つかり、towels というキーワードの検索の場合も同じになります。

このリストに最大 500 個の例外を作成します。

メモ 重複する例外の定義は作成しないでください。

ストップワード

ストップワードのインデックスは作成されないため、ストップワードをクエリに入力すると無視されます。ストップワードとは、冠詞や前置詞 (a、an、the、in、on、for) など、検索クエリの結果に影響を与えない単語です。これは、インデックスのサイズと検索結果の効率に大きく影響します。このトピックは、B2C Commerce に該当します。

一般的なストップワード (英語の場合): a、an、and、are、as、at、be、but、by、for、if、in、into、is、it、no、not、of、on、or、s、such、t、that、the、their、then、there、these、they、this、to、was、will、with、x

一般的なストップワードは検索の意味に大きな影響を与えることはありませんが、一部のマーチャンダイザーでは例外があることがあります。たとえば、映画のタイトルを検索する場合、「The Natural」と「A Natural」はそれぞれ異なる映画です。「安全に」インデックスが作成されないようにする単語は、慎重に検討してください。

ストップワードをインデックス定義ファイルの一部としてインポートおよびエクスポートします。

B2C Commerce での位置情報データの保存

Salesforce B2C Commerce には、テスト用の位置情報データベースが用意されています。このトピックは、B2C Commerce に該当します。

提供されている位置情報データベースは、米国とドイツのものです。これらの位置情報はデータベースレベルで事前にロードされており、SiteGenesisi アプリケーションの店舗検索機能で使用されます。お客様は各自の実装のために独自のデータベースの購入とアップロードを行うため、このデータは主にテストを目的としています。

インスタンスの設定の一環として、アプリケーションを拡張して外部データベースから郵便番号を含めることができます。このインスタンスの設定を使用して、データのロード後に基本的な検証を実行します。位置情報は時を経るにつれて精度が低くなるため、Salesforce では、定期的に最新の位置情報データをインポートすることをお勧めしています。

IP アドレスによる位置情報の検索機能に関する詳細については、ログイン位置情報に基づく顧客プロモーションの作成を参照してください。

メモ 位置情報モジュールは、管理者が、モジュールを適切な役割に割り当てた場合にのみ表示されます。

Staging (ステージング) インスタンスで位置情報を読み込み、テストしてから、通常のデータレプリケーション処理として、Production (本番) に移行させます。参照データの組織レベルのレプリケーションタスクは、店舗の位置情報をレプリケートします。

位置情報の検索

アプリケーションランチャーの順にクリックし、管理 | グローバル環境設定 | 店舗検索データの順に選択します。国の選択と郵便番号に基づいて、インポートした位置情報記録の簡単な検索を実行します。

結果は市区町村、州/都道府県、郵便番号、緯度、および経度となります。

また、IP アドレスの位置情報検索を実行して、間違った IP アドレスデータ問題の診断に役立つ診断情報を確認できます。

同義語

同義語とは、別の単語やフレーズとまったく同じ、またはほぼ同じ意味をもつ単語やフレーズです。複数の用語が同義語として定義されている場合、そのいずれかの用語を検索すると、すべての用語の結果が返されます。また、ネガティブ同義語を使用して特定の同義語を除外することもできます。ブランドの同義語は自動的に生成されます。このトピックは、B2C Commerce に該当します。

ただし、両方の用語に重複した検索結果がある場合、同義語の検索結果は、それらの用語が同義語でない場合の各用語の合計数より少なくなることがあります。

同義語は、商品とコンテンツインデックスに追加されたときにステミングされます。たとえば、「lock」を含む同義語を構成すると、顧客が「lock」を検索したときに検索結果に「locks」、「locker」、「locked」、およびそれらの同義語が返され、同義語もステミングされます。次の例では、複数形など同じ単語の語幹を含むすべての単語を含め、同義語グループに同じ結果セットが返されるのを確認できます。

構成されている同義語 顧客が検索する用語 B2C Commerce クエリ 返される結果
bag、purse、pocketbook bag bag OR purse OR pocketbook bag、bags、purse、purses、pocketbook、pocketbooks
  purse bag OR purse OR pocketbook bag、bags、purse、purses、pocketbook、pocketbooks
  pocketbook bag OR purse OR pocketbook bag、bags、purse、purses、pocketbook、pocketbooks

商品の検索可能フィールドに両方の用語が表示される場合、結果が重複することがあります。たとえば、"The Ice Cap is the perfect hat for..." という検索可能な長い説明が商品にある場合、hatまたはcapを検索すると、この説明が見つかります。多くの人は同義語を作成するときに、同義語の検索結果が個々の用語のすべての検索結果と等しくなければならないと予測します。しかし、同義語の検索では重複した結果が返されないので、重なった結果は一度だけ返されます。

入力された 1 つの検索フレーズで検索される同義語の長さは最大 4 語です。ユーザーが「big nice back packs」を検索すると、クエリエンコーダーは次の同義語の検索を試みます:

  • big nice back packs (最大 4 語)
  • big nice back または nice back packs (3 語の組み合わせ)
  • big nice または nice back または back packs (2 語の組み合わせ)
  • big または nice または back または packs (1 語のキーワード)。

このため、4 語を超える同義語を設定すると、その同義語は決して検索されません。たとえば、次のような 4 語を超える同義語フレーズは設定しないでください。結果は返されません:

backpacks, backpack, back pack back packs rucksack ruck sack

代わりに、このように設定します: 

backpacks, backpack, back pack, back packs, rucksack, ruck sack

    '-' ネガティブ同義語演算子が前に付いた同義語 (単一の語または複数語) を入力した場合、そのネガティブ同義語を含む商品は検索結果として返されません。
  • ブランド同義語
    B2C Commerce では、商品のシステムオブジェクトのブランド属性の値からブランド名の内部辞書が自動的に作成されます。辞書を作成するために、ブランド属性を検索可能としてマークする必要はありません。B2C Commerce は、検索クエリでスペルミスのあるブランド名を検出すると、内部辞書から正しいブランド名を同義語としてクエリに追加します。

ネガティブ同義語

'-' ネガティブ同義語演算子が前に付いた同義語 (単一の語または複数語) を入力した場合、そのネガティブ同義語を含む商品は検索結果として返されません。

例 1

jeans、-skirts などの同義語グループを設定して、顧客が jeans を探している場合に、検索結果として skirts の一種である jean skirts が返されないようにします。

同義語グループ 顧客の検索対象 実際の B2C Commerce クエリ
jeans、-skirts jeans jeans AND NOT skirts

例 2

car accessories , -household , -technologyのような同義語グループを設定して、顧客がcar accessoriesを検索した場合にネガティブ用語の-householdと-technologyがクエリに追加されるようにします。検索結果にはフロアマットが含まれますが、エアーフレッシュナーや携帯電話用のケーブルは含まれません。

ただし、顧客が household (または -household) を検索した場合、car accessories という単語は検索されません。これは、household が car accessories の同義語としては設定されておらず、ネガティブ語として設定されているためです。

同義語グループ 顧客の検索対象 実際のクエリ
car accessories, -household, -technology car accessories car accessories NOT household AND NOT technology
  household household

例 3

正規の同義語は、ネガティブクエリにも適用されます。"chukkas" と "boots" が同義語である場合、"chukkas" を含まない顧客の検索には "boots" も含まれません。

同義語グループ 顧客の検索対象 実際のクエリ
chukkas, boots -chukkas NOT chukkas AND NOT boots
  -boots NOT chukkas AND NOT boots

ブランド同義語

B2C Commerce では、商品のシステムオブジェクトのブランド属性の値からブランド名の内部辞書が自動的に作成されます。辞書を作成するために、ブランド属性を検索可能としてマークする必要はありません。B2C Commerce は、検索クエリでスペルミスのあるブランド名を検出すると、内部辞書から正しいブランド名を同義語としてクエリに追加します。

たとえば、サイトに Mitsubishi ブランドがあり、顧客が誤って Mitsushi と入力すると、クエリ解析がスペルの間違いを識別して Mitsushi OR Mitsubishi を検索します。

商品システムオブジェクトのブランド属性に値が何も含まれない場合、ブランド同義語は自動的に生成されず、クエリ処理でこのステップは使用されません。

メモ ブランド同義語機能を無効にするには、カスタマーサポートにお問い合わせください。

ジョブ実行中のシステムリソースのロック

テキスト関連性

顧客の検索結果を向上させるには、検索用語を含む属性の重要性を高めるようにします。このトピックは、B2C Commerce に該当します。

通常これらは、商品名やブランドなど顧客が検索しそうなフィールドに関連付けられた短めの属性です。また、カテゴリ名などカテゴリ属性の重要度もブーストできます。たとえば、顧客がノートブックを検索する場合、ノートブックカテゴリからの結果が最初に返され、タイトルまたは説明に「ノートブック」という語が含まれる紙製品は検索結果の最後に表示されます。

テキスト関連性の判定方法

顧客が検索用語を入力すると、各ドキュメントのスコアが計算されます。このスコアは、各検索可能属性に検索用語が見つかった回数、ブースト係数、およびその他のウェイト係数に基づきます。検索結果がテキスト関連性で並べ替えられる場合、結果セットでドキュメントが返される順序はドキュメントのスコアによって決まります。最高スコアは、検索に最も関連したドキュメントに与えられます。

テキスト関連性に影響を与えるもの:

  • ドキュメント内の各属性に用語が出現する回数。
  • 各検索可能属性のブースト係数。
  • すべてのドキュメントで用語が出現する回数。出現回数が少ない用語のスコアが高くなります。
  • 特定のドキュメントに用語が出現する回数。出現回数が多い用語のスコアが高くなります。
  • フィールドに含まれる用語の数。1 つのフィールドに多数の用語がある場合、用語の数が少ない場合よりもスコアが低くなります。これは、商品名など 1 つの属性に含まれる用語の数が少ない場合は、長い説明など 1 つの属性に含まれる用語の数が多い場合よりみ、用語が見つかったことの重要度が高まるためです。

ただし、属性のどの位置に検索用語が見つかるか、また、用語の長さは関係ありません。

テキスト関連性ブースト係数

ブースト係数を 1.0 に指定した場合、これはブースト係数のデフォルト値なので、スコアはまったく変わりません。テキスト関連性を計算するために指定するブースト係数は、特定のクエリから返された検索結果ではなく、インデックス全体と相対的です。ブースト係数を 1.0 未満に指定すると、特定のフィールドの関連性が低くなることを示します。フィールドの関連性を低くするには、1 未満の任意の小数 (.5、0.3) を使用しますが、負の値を使用することはできません。

1.0 より大きいブースト係数を指定すると、フィールドのテキスト関連性が高くなります。ブースト係数を 2.0 に指定すると、ドキュメントの他のすべてのフィールドと比較して、フィールドの関連性が元の 2 倍になります。

一般的には、商品名や短い説明など、商品に関連する情報のみを含む属性をブーストします。より一般的な情報をもつフィールドをブーストすると、検索結果の並べ替えは向上しません。たとえば、「カーゴパンツを追加して、このシャツのコーディネートを作成します」といった文を含む商品の長い説明をブーストする場合、商品をパンツの前にブーストして、パンツの検索でシャツの組み合わせが表示されるようにすることができます。

検索スコアは、現在の結果セットにある項目だけでなく、すべての項目のスコアに影響を与えることに留意してください。さまざまなクエリでフィールドのブーストの影響をテストして、ブーストが意図しない結果になっていないことを確認してください。

メモ ブースト係数は、検索用語と検索用語の同義語に適用されます。たとえば、顧客がノートブックを検索し、ノートブックとノートパソコンが同義語である場合、ノートパソコンの商品も検索リストの一番上に表示されます。

ブースト係数のテスト

属性ブーストをテストするときには他の検索並べ替えルールを無効にして、ブーストのみの効果を確認できるようにすることをお勧めします。Storefront Toolkit を使用して、作成したブーストの効果を確認します。

B2C Commerce での階層割引

割引を階層化して、買い物客が購入する商品または金額が増加するほど割引金額が増加するようにします。条件パラメーターに複数のしきい値レベルがあるプロモーションでは、割引がしきい値によって異なり、組み合わせることができない階層割引を構成します。

階層プロモーションを使用すると、買い物客は割引を併用できません。たとえば、$100 以上の買い物で $10 割引、$200 以上の買い物で $25 割引、$300 以上の買い物で $40 割引というプロモーションを実行するとします。

個別の割引ルールをもつ 3 つの異なるプロモーションを構成した場合、$320 使った買い物客は 3 つのプロモーション ($10+$25+$40=$75) すべてに該当することになり、$75 の割引を受けます。複数の割引ルールをもつ単一の注文プロモーションとしてプロモーションを構成した場合、同じ買い物客は $40 の割引を受けます。

「X の購入で Y をゲット」商品プロモーションと、条件なしの商品プロモーション (対象商品なし) は除きますが、商品、注文、配送のプロモーションタイプのすべてに階層割引を作成します。

割引タイプは、階層ごとに異なるものを使用しても構いません。以下がその例です:

  • 「ABC 商品」を $250 購入すると 2.5% 割引
  • 「ABC 商品」を $500 購入すると 5% 割引
  • 「ABC 商品」を $1,000 購入すると $100 割引

条件付き商品プロモーションに階層割引ルールを作成する場合は、対象商品と割引商品のルールが階層全体で同じでなければなりません。たとえば、ABC ブランドルールと価格ルールは同じでなければなりません。

  • $300 を超える ABC 製品を 1 点購入すると 10% 割引
  • $300 を超える ABC 製品を 2 点以上購入すると 15% 割引

異なるクラスのプロモーションを異なる階層として構成することはできません。たとえば、注文が $150 を超えると配送料が無料、$300 を超えると 25% 割引というプロモーションは実行できません。複数の階層で異なる限定子タイプを使用することもできません。たとえば、商品を 3 点注文すると配送料が半額になり、$200 を超えると配送料に無料になるというプロモーションは実行できません。

訪問の追跡

B2C Commerce では、B2C Commerce Analytics を使用して訪問を追跡することができます。

訪問とは?

特定の人間のユーザーまたはコンピューターから送信された 1 つまたは複数のリクエストの合計です。B2C Commerce では、ユーザーに割り当てられたセッション ID によってこれらのリクエストが区別されます。B2C Commerce は、継続する期間にこのセッション ID を共有するすべてのリクエストを訪問にグループ化します。

セッション ID とは、リクエストしたクライアントに対して B2C Commerce が渡す一意の識別子です。クライアントは、継続してサイトを閲覧するためには、この ID (多くの場合は Cookie) を返す必要があります。クライアントがこの ID に注意を払わない場合は、ログインや注文手続きなど、特定の機能が利用できなくなります。

クライアントが 30 分間リクエストを送信しないと、セッションは終了したものと見なされます。この時間を過ぎたリクエストは、新規訪問と見なされます。

コンピューターと人間を区別するために、リクエストのフィルターには、事前に定義された識別子と IP アドレスが使用されます。B2C Commerce では、ロボット/クローラー/スパイダーからの訪問が別々にリストされます。人間のユーザーによる訪問という判断に基づいて、すべてのビジネスが計算されます。定義は定期的に更新され、顧客からのリクエストにより更新される場合もあります。

シナリオと例外

Eメールクライアント: Eメールクライアントには、JavaScript の実行や、画像の追跡といった第三者コンテンツの読み込みを行わなくても、埋め込まれた HTML コンテンツやリンクされた HTML コンテンツのプレビューが表示されることがよくあります。B2C Commerce では、これらのプレビューが訪問としてカウントされます。

ブラウザーのバックグラウンド取得: 最近の一部のブラウザーでは、先読み技術が使用されています。ブラウジング体験の応答性を向上させるために、これらのブラウザーは明示的に要求される前に Web コンテンツを読み込みます。たとえば、Firefox は Google 検索結果で表示される最初のリンクをたどり、この web サイトがユーザーの関心を引くものであり、ユーザーがこのリンクをクリックできると想定して、この web サイトを取得します。B2C Commerce では、このようなバックグランドでの読み込みも訪問としてカウントされます。

短時間の訪問: B2C Commerce を基にした Web サイトへのリンクをたどり、最初のページを見ただけでブラウザーを閉じたユーザー、または読み込んだコンテンツに興味を示さずに、30 分間ブラウザーを開いたままの状態にしているユーザーを示します。つまり、他のページをリクエストしていないユーザーです。B2C Commerce、およびその他のほとんどのアナリティクスパッケージでも、こういった場合は訪問としてカウントされます。

中断された訪問: Web ページを訪れ、ページをリクエストし、ブラウザーを閉じることなくセッションを終えたユーザーを示します。ユーザーが 30 分間何も操作を行わなかった場合、B2C Commerce は訪問が終了したものと見なします。そのユーザーが後で買い物を再開した場合、B2C Commerce では新規訪問としてカウントされます。

無効化された Cookie: ユーザーエージェントが Cookie を許可しない場合、B2C Commerce は、すべての URL にセッション情報を含みます。したがって、こういったリクエストも 1 回の訪問としてカウントされます。B2C Commerce Analytics には JavaScript は必要なく、訪問は常に同じ方法でカウントされるため、JavaScript が無効になっていても、訪問数には影響しません。

メリットとデメリット

B2C Commerce のアプローチでは、トラッキング目的で画像や JavaScript を配信しているかどうかにかかわらず、無効化された JavaScript やブロックされたサードパーティのサイトとは無関係に、すべての訪問がカウントされます。一方、デメリットは、フィルター情報が更新されるまで、不明なロボットや新しいロボットが実際のユーザーと見なされる可能性があることです。また、すべてのクライアントエージェントが正しく識別されているわけではありません。中には、誤解を生むような動きをしたり、通常のブラウザーのふりをしているものもあります。これらのエージェントを検出するには、スパムトラフィックソースと呼ばれる特定の IP 範囲を除外します。

ランディングページの PPC キーワード

B2C Commerce には、ペイパークリック (PPC) URL を簡単に管理する方法が用意されています。Google またはその他の検索エンジンが作成した各クエリに対し、個別の URL を指定しなくても構いません。代わりに、Google によって生成されたクエリを、B2C Commerce の関連するランディングページに自動でマッピングできます。URL マッピング機能を使用して、Google クエリ内のキーワードを、クエリに基づく検索結果のあるページに顧客を転送する Search-Show パイプラインに渡します。また Search-Show パイプラインは、検索語に対する検索リダイレクトを作成した場合にそれを検出し、そのリダイレクトに関連するランディングページを表示します。

Google AdWords の例

この例では、Google の "ValueTrack" システムの一部である AdWords のキーワード挿入機能を使用して、Google で PPC URL を管理していると想定します。この例は Google に特化したものですが、Yahoo やその他の検索エンジンでも原則は同じです。つまり、keyword パラメーターを URL の一部として渡します。

AdWords での、パイプラインを使用する宛先 URL を使ったキーワードのトラッピング

Google AdWords キーワードパラメーターを使用してキーワードを挿入し、検索用語を含む宛先 URL を使用して AdWords PPC 広告を定義します。

たとえば、AdWords で、Google ユーザーが検索した検索用語と同じ用語のオンサイト検索に常に移動する宛先 URL を作成する場合、宛先 URL は次のようになります: 

www.domain.com/on/demandware.store/Sites-SiteGenesis-Site/en_GB/Search-Show?q={keyword}

B2C Commerce マッピングルールを使用したキーワードのトラッピング

B2C Commerce URL を AdWords の宛先 URL に指定する代わりに、B2C Commerce マッピングルールを使用して AdWords URL をより詳細に管理できます。特定のキーワードをトラップして、明示的なランディングページや一致しない検索用語のキャッチオールに転送するマッピングルールを指定します。

次の例では、顧客がSony Braviaを検索すると、sony braviaというキーワード検索の検索結果を表示する Search-Show パイプラインに転送されます。また、顧客が lcd を検索した場合、フラットスクリーンテレビのカテゴリページに転送されます。最後のマッピングルールは、特定のマッピングルールを持たない受信 AdWords URL を識別し、それを Search-Show パイプラインにリダイレクトして、顧客が入力した検索用語の検索結果を表示できるようにするキャッチオールです。

メモ ルールを作成した順番によって、適用する順番が決まります。一般的なルールの前に特定のルールを追加します。

Google AdWords の詳細については、以下を参照してください:

  • http://adwords.google.com/support/aw/bin/answer.py?hl=en&answer=74996
  • http://adwords.google.com/support/aw/bin/answer.py?hl=en&answer=178482.

在庫切れまでの時間

在庫切れまでの時間 (TTOOS) は、商品が在庫切れになるまでの推定時間です。このトピックは、B2C Commerce に該当します。

TTOOS (在庫切れまでの時間) は、商品が在庫切れになるまでの推定時間です。特に、これは、直近の日の販売可能数量 (ATS) 属性と販売速度属性値との比率です。バリエーション商品、商品セット、潜在的な商品バンドルには、特別なルールが適用されます。TTOOS は、在庫リストを共有するすべてのサイトで同じです。つまり、これはサイト固有の値です。

TTOOS は:

  • Salesforce B2C Commerce では、この値がリアルタイムで計算されます
  • インポートまたはエクスポートできません。
  • ステージングされていないため、値はインスタンスに固有です。

標準商品

商品 (p) は、在庫リストを使用するサイトの標準商品または商品バンドルです。

  • 在庫切れの場合は、TTOOS = 0.0
  • 無期限で入手可能の場合は、TTOOS(p) =1.0
  • 販売速度日(p) が利用不可の場合は、TTOOS(p) =0.0
  • 販売可能数量 (ATS)(p) が利用不可の場合は、TTOOS(p) = 0.0
  • それ以外の場合は、TTOOS(p) = 販売可能数量 (ATS)(p) / 販売速度日(p)

在庫リストを使用する通常商品またはバンドルの例

商品 1 - 在庫切れ

InStock (在庫あり): false

TTOOS は: 0.0

商品 2 - 無期限

IsPerpetual (無期限): true

TTOOS は: 1.0

商品 3 - 販売速度の情報なし

販売速度: n/a

TTOOS は: 0.0

商品 4 - 販売可能数量 (ATS) の情報なし

販売可能数量 (ATS): n/a

TTOOS は: 0.0

商品 5

販売可能数量 (ATS): 5000

販売速度: 10.5 (1 時間につき)

TTOOS は: 5000 / 10.5 = 476.19

マスター商品

  • mp がマスター商品
  • vpX がマスター商品のオンラインバリエーション

表示タイプ

表示タイプ を使用し、たとえば画像のサイズごとに、画像を用途に基いてグループ分けします。このトピックは、B2C Commerce に該当します。

まず、表示タイプのリストをカタログとの関連で定義します。(Business Manager またはインポートによって) 新規カタログを作成すると、カタログには以下のデフォルト表示タイプが自動的に含められます:

表示タイプ 説明
large (ラージ) ストアフロントの商品詳細ページに表示される大きな画像。
medium (ミディアム) ストアフロントの検索結果ページに表示される小さな画像。
small (スモール) カーソルを合わせたときに、関連する詳細画像を表示するために使用する非常に小さな画像。
swatch (スウォッチ) たとえばバリエーション属性 "カラー" に基いて、バリエーション商品を区別するために使用する画像 (スウォッチはバリエーション商品に基づきます)。

表示タイプ:

  • 表示タイプは文字列 ID で、任意に名前を指定できます。
  • 表示タイプは、カタログごとに一意である必要があります。
  • 画像を割り当てるには、表示タイプが少なくとも 1 つなければなりません。
  • 1 つの画像に複数の表示タイプを割り当てることができます。
  • 1 つの表示タイプに割り当てられた複数の画像がスタックを形成します。スタックの最初の画像には仮想インデックス番号 0、2 番目の画像には仮想インデックス番号 1 のように、番号が順に割り当てられます。
    • インデックス番号を明示的に設定することはできません。
    • 割り当てられていないインデックス番号をとばして次のインデックス番号を割り当てることはできません。

    異なる表示タイプ間の関係を確立するには、表示タイプの画像スタックを並べ替えます。このアプローチでは、関連する画像がスタック内で同じ位置 (インデックス番号) になります。たとえば、small (スモール) をホバーヘルプ用に、large (ラージ) を商品詳細ページ用に指定すると、同じ写真が異なるサイズで表示されます。

  • 各商品に必要な表示タイプのみを使用します。
  • 商品属性の組み合わせに画像を指定するには、セカンダリ画像バリエーション属性 (色など) を追加します。たとえば、赤の画像を表示タイプ「large」で表示します。 レザー。

B2C Commerce でのユーザーの承認

Salesforce B2C Commerce では役割ベースのアクセスコントロールを使用して承認を行います。ユーザーは 1 つまたは複数の役割に割り当てられます。各役割は一連の許可で構成されています。ユーザーの承認は、Business Manager でカスタムの役割と許可を使用して構成します。このプロセスは、ローカル認証と統合認証のどちらを使用する場合でも、基本的に同様に機能します。

Business Manager には、管理者役割をもつ管理ユーザーがあらかじめ設定されています。管理者は、セキュリティコントロールの設定を含め、任意の操作を実行する許可を提供します。管理者による他のユーザーへの許可の付与は、適切かつ慎重に行うことをお勧めします。実際、このすべての権限をもつ管理者アカウントは、絶対に必要な場合にのみ使用するようにします。ユーザーの認証情報が漏洩した場合、システム全体のセキュリティが危険にさらされます。

デフォルトでは、ユーザーが Business Manager または Account Manager で作成された場合、そのユーザーは許可をもちません。ユーザーがログインしても、Business Manager で表示や操作はできません。これは、ベストプラクティスである「デフォルトで拒否」に従うものです。ユーザーが特定の操作を実行できるようにするには、適切な許可をもつ既存のユーザーが 1 つまたは複数の役割を作成し、それぞれの役割に一連の許可を関連付けます。次にこのユーザーは、これらの役割の 1 つまたは複数を新しいユーザーに割り当てます。

ユーザーを役割に割り当てる際には、最小権限の原則に従います。複数のユーザーを作成し、各ユーザーには仕事を行うために必要な最小限の役割と許可を付与します。たとえば、分析をチェックすることのみを目的とするユーザーアカウントでは、マスターカタログを管理する許可は必要ありません。また、ユーザーがオブジェクトへの書き込みアクセスを必要とする場合以外は、読み取り専用の許可を付与します。たとえば、すべての役割にクーポンモジュールへの読み取り専用許可を付与し、書き込みアクセスはクーポンを作成または変更する役割のにみに割り当てるようにします。

入手可能性ランキング

アイテムの入手可能性に基づいて検索結果を並べ替えます。B2C Commerce では、入手可能性は在庫機能で設定します。

入手可能性ランキング機能を使用して、商品の入手可能性に基づいて検索結果を操作するには:

  • 入手可能性に基いて動的ランキングを有効または無効にする。
  • 商品を検索結果の最後または最初に配置するかどうかを決定する入手可能性しきい値を設定する。

並べ替えルールの入手可能性モデル属性を選択して、商品を入手可能性の順に並べます。通常これは、入手できない商品を検索結果の最後に移動するために使用されます。

SKU カバレッジが低い、つまりマスター商品の一部のバリエーションの入手可能性が下がっている状況を管理する方法については、SKU カバレッジ を参照してください。

顧客がストアフロントで注文を行ったとき、またはマーチャントが Business Manager またはフィードから在庫情報を変更したときには、これらの変更を反映するように入手可能性インデックスを更新します。増分インデックスを使用して約 30 秒ごとにインデックスを更新するか、スケジュール済みのインデックス更新を使用してそれより長い間隔でインデックスを再作成します。

入手可能性インデックス

B2C Commerce のストアフロント商品検索機能を使用すると、アプリケーションで検索結果を在庫データに基づいてフィルターして並べ替えることができます。在庫切れの商品や入手可能性が低いために検索結果で最初または最後に移動する商品は検索結果から除外します。在庫のフィルタリングと並べ替えに使用されるデータは、サイトまたは組織の入手可能性検索インデックスに含まれています。

各サイトには独自の入手可能性検索インデックスがあります。複数のサイトが在庫リストを共有する場合、それらのサイトは検索入手可能性インデックスも共有します。インデックスの増分再作成または完全再作成は、在庫回転率、ストアフロントカタログに含まれる複合商品 (バリエーション、バンドル、セット) の数、およびサイトで使用される並べ替えルールによっては、緊急を要しリソースが必要な重要処理です。入手可能性インデックスを再作成すると、増分自動的に作成されます。

入手可能性インデックス処理は、在庫リストレコードデータに完全に依存し、商品のオンラインステータスが無視されます。入手可能性検索インデックスでは、インデックス作成時の商品のオンラインステータスにかかわらず、商品の在庫がある場合は入手可能として示されます。

メモ Omnichannel Inventory を使用する場合は、入手可能性は Omnichannel Inventory からキャッシュされた入手可能性データに基づいて計算されます。

複合商品 (マスター商品、バンドル、セット) の入手可能性に基づく並べ替え属性 (Availability (入手可能性)、ATS (販売可能数量)、TimeToOutOfStock (在庫切れまでの時間)、SKUCoverage (SKU カバレッジ)) の集計値も検索実行時に計算されます。集計では、商品検索インデックスに含まれているすべてのサブ商品 (バリエーション商品、バンドル商品、セット商品) が考慮され、これらの商品が現在オフラインの場合 (つまり、商品が商品インデックスに含まれているが online-from の日付が明日になっている) も集計されます。

メモ B2C Commerce では、入手可能性属性に基づいて検索結果をフィルターして並べ替えるときに、商品の online-from と online-to の日付が考慮されます。オンラインステータスは入手可能性インデックス処理で考慮されないため、商品は online-from の日付になるとすぐに入手可能と見なされます。

B2C Commerce でのフックセキュリティの使用

Salesforce B2C Commerce では、デフォルトの機能を拡張するパワフルなツールとしてフックを使用できます。ただし、他のすべてのパワフルなツールと同様に、フックは適切に使用しないと危険です。

Open Commerce API (OCAPI) と Commerce Script のフックは、OCAPI とプラットフォームメソッドの呼び出しのプラットフォーム操作を機能的に変更できます。権限をもたないユーザーが、権限の指定されている OCAPI やメソッドを呼び出すことができるようになる可能性があるため、フックは注意して使用してください。また、OCAPI フックの設計上の配置のため、デベロッパーは API 呼び出しを誤って変更し、認証をまったく受け入れないか、予想される認証を完全にバイパスしてしまう可能性があります。プラットフォームで呼び出しを変更する際には、十分に注意してください。

シークレットヘッダーを使用したサードパーティリクエストの検証

検証済みのサードパーティサーバーのファイアウォール許可リストを管理する代わりに、シークレットヘッダーを使用します。シークレットヘッダーは、通常、CDN レベルで添付される追加の HTTP ヘッダーです。

たとえば、「

x-extra_header_name: extra_header_value」

です。

受信リクエストを検証するために、eCDN レイヤーはヘッダーの存在をチェックして検証します。eCDN カスタムルールはヘッダーをチェックし、ヘッダーを含まない悪意のあるトラフィックをブロックします。ヘッダーチェックに失敗したすべてのリクエストは、403 レスポンスコードを返します。eCDN カスタムルールを参照してください。

B2C Commerce の Web サービス

Salesforce B2C Commerce では、Web サービスへの呼び出しの管理とサービスのパフォーマンスの分析を支援する、Web サービスフレームワークを提供しています。Web サービスとのやり取りを行うには、カスタムコードが必要です。Web サービスタイプには、HTTPS、セキュアファイル転送プロトコル (SFTP)、Transport Layer Security (TLS) を介した Simple Object Access Protocol (SOAP) などの安全なプロトコルを使用することをお勧めします。また Web サービスでは、ユーザー名とパスワードなどのサービス認証情報を使用して、HTTP 基本認証を行うこともできます。

スウォッチ画像には通常、商品バリエーション属性との関連で、バリエーション商品間の主な違いが表示されます。このトピックは、B2C Commerce に該当します。

バリエーション商品にはスウォッチを設定できます。以下がその例です:

  • ファブリック バリエーション属性では、各ファブリックを大きく拡大した詳細画像が、商品の写真の下の行に表示されます。
  • カラー バリエーション属性では、小さなカラー画像が主要商品の写真の下に表示されます。顧客がスウォッチ (例: "赤") をクリックすると、"赤" のバリエーション商品の詳細ページが表示されます。

スウォッチは画像バリアントと共に特別な表示タイプとして表示され、マスター商品ごとに管理されます。一般的に、表示タイプとバリエーション商品の組み合わせ 1 つにつきスウォッチ画像は 1 つしかありません。スタックされたスウォッチ画像は使用できません。たとえば、同じカラーコードをもつ商品は、異なる色調をもつことができます。スウォッチは必ずしもカラーコードを表すわけではありません。たとえば、スウォッチはファブリックを大きく拡大した詳細画像を表わすこともあります。この場合、赤い T シャツ、赤いニットドレス、赤いシルクスカーフのスウォッチはそれぞれ異なります。スウォッチを表示タイプとして表すことで、すべてのカラーバリエーション商品に必要なスウォッチ画像を表示できます。

B2C Commerce 内からの XML ファイル生成

標準のエクスポートでは、B2C Commerce で定義された XML スキーマファイルが使用されます。B2C Commerce には、最も一般的なエクスポートファイルを作成するために使用できるスキーマファイルのセットが用意されています。

また、商品とコンテンツの画像を zip ファイルとしてインポートし、Analytics データを xls 形式でエクスポートすることもできます。

典型的な B2C Commerce の実装には、バックエンドシステムへのデータ転送のための XML ドキュメントの生成が含まれています。

システム内のデータから XML ドキュメントを作成する場合、一般的な慣行は B2C Commerce 内のデータを反復してこのデータを XML ファイルに出力するコードを作成することです。

カスタムのコードを作成する必要がある場合、メモリに読み込むオブジェクトの数または XML の量について検討します。また、トランザクションをコミットする前に読み込むオブジェクトの数、および標準フィードでは自動的に処理されるその他の制約について検討します。

たとえば、注文エクスポートの後処理でバックエンドシステムの専有 XML 形式に変換する場合は、B2C Commerce スクリプトを使用することが合理的であるかどうかを検討してください。処理に大量のメモリが割り当てられている真正の .NET または Java プラットフォームを使用してファイルを変換する方が格段に高速かつ効率的である場合があります。

ただし、B2C Commerce スクリプトを使用するには、XMLStreamReader および getXMLObject() メソッドを使用して、エクスポートファイル内の特定の注文を取得します。次に nextTag() を使用して注文内の要素を反復し、XMLStreamWriter を使用してその注文を新しいファイルに書き出します。

エクスポートファイル全体または注文全体をメモリに読み込んでから XMLStreamWriter を使用して書き出しを行うとメモリ不足エラーが生じる可能性があるため、これはお勧めできる方法ではありません。

B2C Commerce でのインポート/エクスポートの例

コードのインポートとエクスポートの例を用意しました。このトピックは、B2C Commerce に該当します。

以下のコードの例では、サイトで現在構成されている商品を反復し、XML ドキュメント (オブジェクト) を作成します。XML 文書は、別のシステムにデータを渡すために使用できます。

このコードは、以下の反復を実行します。

var it : SeekableIterator = ProductMgr.queryAllSiteProducts(); 
var rootXML : XML = new XML(<products></products>); 
var pXML : XML = new XML(<product></product>); 
while(it.hasNext()){ 
  var product : Product = it.next(); 
  pXML.brand = product.getBrand(); 
  pXML.name = product.getName(); 
  pXML.id = product.getID(); 
 rootXML.product+=pXML; 
}

以下のように処理を行います:

  1. XML ドキュメントに必要なすべての商品データを取得する商品イテレーターを作成します。
  2. XML ルート要素である products (オブジェクト) を作成します。
  3. ドキュメントに追加する XML 要素 (product) を作成します。この XML オブジェクトは 1 回だけ作成します。
  4. product オブジェクトを反復して作成し、product 要素に追加します。
  5. 完成した product 要素を、次の行を使用してルート要素に追加します:
	rootXML.product+=pXML

この行により、反復のたびにルート要素に product 要素が追加されます。

別の要素を XML に追加する場合は、次のコードを使用します:

var it : SeekableIterator = ProductMgr.queryAllSiteProducts(); 
var rootXML : XML = new XML(<products></products>); 
var pXML : XML = new XML(<product></product>); 
var paymentXML = new XML(<payment></payment>); 
while(it.hasNext()){ 
  var product : Product = it.next(); 
  pXML.brand = product.getBrand(); 
  pXML.name = product.getName(); 
  pXML.id = product.getID(); 
 paymentXML.allowed =product.custom.allowed; 
 paymentXML.bml = product.custom.bml 
 rootXML.product+=pXML; 
 rootXML.payment+= paymentXML; 
 }

前述のコードでは、payment オブジェクトは、独自の XML 要素に含まれている必要があるカスタム属性として機能します。

新しい要素の追加に加えて、次のコード例に示すように、ドキュメント要素で許可されるデータ要素の概要を説明することもできます。

var it : SeekableIterator = ProductMgr.queryAllSiteProducts(); 
var rootXML : XML = new XML(<products></products>); 
var pXML = <product> 
          <brand></brand> 
          <name></name>     
          <id></id> 
          </product> 
var paymentXML = new XML(<payment></payment>); 
while(it.hasNext()){ 
  var product : Product = it.next(); 
  pXML.brand = product.getBrand(); 
  pXML.name = product.getName(); 
  pXML.id = product.getID(); 
  paymentXML.allowed =product.custom.allowed; 
  paymentXML.bml = product.custom.bml 
 rootXML.product+=pXML; 
 rootXML.payment+= paymentXML; 
}

var nsg : Namespace = new Namespace("g","http://base.google.com/ns/1.0"); 
var it : SeekableIterator = ProductMgr.queryAllSiteProducts(); 
var rootXML : XML = new XML(<products></products>); 
var pXML = <product> 
          <brand></brand> 
          <name></name>     
          <id></id> 
          </product> 
var paymentXML = new XML(<payment></payment>); 
pXML.addNamespace(nsg); 
while(it.hasNext()){

Salesforce Order Management を使用した Omnichannel Inventory の継続的な注文キャプチャ

B2C Commerce の継続的な注文キャプチャでは、不完全なデータが Salesforce Order Management に届かないように、注文を予約が欠落している状態で保留します。Omnichannel Inventory サービスが復旧すると、システムによって在庫が自動的に調整され、この予約が欠落している状態がクリアされます。その後、予約が部分的または失敗したために販売超過のフラグが立てられた場合でも、すべての注文が Salesforce Order Management にプッシュされます。

Omnichannel Inventory のダウンタイム中にキャプチャされた注文を表示する

調整後の進捗状況を監視するには、Omnichannel Inventory オフラインモードでキャプチャされた B2C Commerce Continuous Order Capture 注文を表示および追跡します。

  1. Business Manager | 注文 | 注文の順に移動します。
  2. 「詳細検索」タブをクリックします。
  3. [Integration State (統合状態)] フィルターを[Reservation Missing (予約が見つからない )] に設定します。
  4. 履歴を表示するには、注文をクリックし、[ 履歴 ] タブをクリックします。

接頭辞が「継続的な注文キャプチャ」の注文は、オフライン、予約済み、部分的な注文、失敗した注文を示します。

B2C Commerce の継続的な注文キャプチャの有効化

ビジネス継続性を維持するため、Omnichannel Inventory サービスの中断中に注文を受け付けます。この機能を有効にすると販売が中断されることはなくなりますが、B2C Commerce の Omnichannel Inventory がオフラインの間は過剰販売のリスクを受け入れる必要があります。

この機能を有効にする前に、Salesforce 管理者権限を持っていることと、サイトが Omnichannel Inventory を使用するように構成されていることを確認してください。

  1. Business Manager で、アプリケーションランチャーをクリックし、管理 | グローバル | 環境設定 | 機能スイッチ の順に選択します。
  2. Omnichannel Inventory の Inventory の Continuous Order Capture で Read をクリックし、法的要件に同意します。
  3. 利用規約を読み、法的要件に同意する場合は、[ 同意する]をクリックします。
  4. 変更内容を保存します。

この機能は、サービスの中断を待つのではなく、通常の操作中にオンにすることをお勧めします。継続的な注文キャプチャ設定を構成することで、ストアフロントが保護され、中断が発生したときに注文をキャプチャする準備が整います。
