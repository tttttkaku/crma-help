B2C Commerce のログインのためのアクセスキーの作成

B2C Commerce で統合認証を使用している組織は、外部アプリケーション経由で Business Manager にログインする際に次の方法で認証を行えます。WebDAV ファイルアクセス、UX Studio エージェント、ユーザーログイン、Open Commerce API (OCAPI)、および保護されたストアフロントへのアクセス。これらのアクセスキーは、統合認証のパスワードの代わりとして機能します。アクセスキーは 1 年で有効期限が切れます。アクセスキーを 6 回誤って入力すると、そのアクセスキーまたはパスワードを使用して認証範囲にログインすることはできません。

必要なエディション

使用可能なソリューション: B2C Commerce
  1. Business Manager の右上で自分のユーザー名をクリックします。
  2. アクセスキーの管理をクリックします。
    ここで、アクセスキーを有効、無効、または削除します。アクセスキーの有効期限が切れた場合、またはアクセスキーが無効になっている場合は、そのアクセスキーまたはパスワードを使用してログインすることはできません。
  3. アクセスキーを生成します。
  4. キーの範囲を選択します。これにより、キーがログインできる対象が決まります。
  5. ダウンロードをクリックして、アクセスキーをコピーします。
    この画面を閉じると、その後このキーに再びアクセスすることはできません。これがコードをコピーする唯一の機会です。コードは将来使用するために安全な場所に保管することをお勧めします。

また、Manage_Users_Access_Key の許可をもつ Business Manager ユーザーは、Data API 呼び出しを通じて他のユーザーのアクセスキーを生成、削除、循環できます。この API は、主に店舗内アプリを使用して B2C プラットフォームにログインするユーザーのために、アクセスキーの生成と循環の自動化を行います。この API を使用すると、これらの Business Manager ユーザーは Business Manager にログインしてアクセスキーを手動で生成またはローテーションする必要がなくなります。

B2C Commerce での Account Manager の利用

Account Manager では、B2C Commerce アカウントの作成、保守、無効化を行えます。また、アカウントの認証情報に基づいて、選択されたアプリケーションへのアクセスを許可 (または拒否) することもできます。Account Manager では、アカウント管理者と、非管理者ユーザーの 2 種類のユーザーがサポートされます。アカウント管理者は、非管理者ユーザーが実行できないすべての操作を行えます。アカウント管理者は、アカウントの作成、無効化なども行えます。各組織に、少なくとも 1 名のアカウント管理者が割り当てられています。Account Manager を使用する前に、まずログインする必要があります。

所有している Salesforce Commerce 製品

  • B2C Commerce とシングルサインオンの統合
    接続の安全性を確保し、摩擦を減らすために、B2C Commerce Account Manager とその他の Salesforce アプリケーションを ID プロバイダーと統合します。
  • Account Manager と B2C Commerce での ID フェデレーションによるユーザー管理
    Account Manager ユーザーアカウントが自動的に作成、プロビジョニングされ、Salesforce 組織の Salesforce Identity にリンクされるように、組織の ID フェデレーション設定を構成できます (Salesforce Identity Management (SFIDM))。
  • Account Manager と B2C Commerce のジャストインタイムユーザープロビジョニング
    ジャストインタイムユーザープロビジョニングを使用すると、Account Manager でのユーザーアカウント作成が自動化されるため、管理者がユーザーを手動で追加する手間を省けます。また、このプロビジョニングによって、ユーザーアカウントはシングルサインオン (SSO) に使用される Salesforce Identity のアカウントにリンクされます。
  • Account Manager と B2C Commerce でのリンクされていないアカウントの自動リンク
    ジャストインタイムプロビジョニングを有効にしない場合でも、Account Manager でユーザーアカウントを作成すると、新規ユーザーアカウントの自動有効化とリンクを利用できます。
  • ID フェデレーションの強制によるログイン
    初めてログインする前に、ログインリンクが記載されたメールが届きます。このトピックは、Account Manager と B2C Commerce に該当します。
  • ID フェデレーションの許可によるログイン
    すでにアカウントをお持ちの場合は、アカウントをリンクする、または Account Manager の認証情報を使用してログインするオプションについての説明を記載した Eメールが届きます。このトピックは、Account Manager と B2C Commerce に該当します。
  • Eメール通知
    Eメール通知は、アカウントの作成方法と、Account Manager での組織の ID フェデレーション設定に基づいてユーザーに送信されます。このトピックは、Account Manager と B2C Commerce に該当します。
  • B2C Commerce での Account Manager へのログイン
    Account Manager では、シングルサインオン (SSO) 用のリンクまたはユーザー名でのログインという 2 つのログインオプションを用意しています。
  • B2C Commerce での多要素認証による本人確認
    多要素認証 (MFA) は、ログインセキュリティを向上させ、ユーザーアカウントをセキュリティの脅威から保護するための、シンプルで効率的なメカニズムです。MFA は B2C Commerce のログイン体験の一部で、オフにすることはできません。
  • B2C Commerce での多要素認証の検証メソッドの登録
    多要素認証 (MFA) は、単一のパスワードによる保護を超える追加の保護レイヤーです。
  • B2C Commerce での多要素認証の検証メソッドの削除
    多要素認証 (MFA) 検証メソッドを置き換える場合は、登録済みの検証メソッドを Account Manager アカウントから削除できます。
  • B2C Commerce での Account Manager アカウントの Salesforce Identity (SSO) へのリンク
    組織の設定によっては、Account Manager アカウントを Salesforce Identity で管理されている Salesforce アカウントにリンクできます。組織がこの機能を有効にすると、Account Manager にログインしたときに、Account Manager アカウントを Salesforce アカウントにリンクできます。アカウントのリンクを解除する場合は、アカウント管理者に問い合わせてください。
  • Account Manager で管理される役割
    この表は、B2C Commerce Account Manager の役​​割に関するガイドとしてご使用ください。
  • Account Manager での廃止予定のロールの削除
    B2C Commerce のユーザーに廃止予定のロールを割り当てることは避けてください。これらのロールは B2C サービスへのアクセスを提供しなくなり、Salesforce は Account Manager 3.9 (2026 年 6 月) 以降に削除する予定です。廃止予定のロールをユーザーから削除しても、機能やアクセスが失われることはありません。
  • B2C Commerce での B2C Commerce アカウントのアクティベート
    アカウントをアクティブにするには、まず、アカウント管理者がアカウントを作成する必要があります。管理者がアカウントを作成すると、Account Manager からユーザーの Eメールアドレスにメッセージが送信されます。この Eメールメッセージを使用して、アカウントのアクティベートを開始します。
  • B2C Commerce でのアカウントパスワードの変更
    パスワードは 90 日ごとに変更する必要があります。既存のパスワードの有効期限が切れている場合でも、新しいパスワードを定義します。パスワードの有効期限が切れた後は、新しいパスワードの設定を 6 回まで試みることができます。その後は、アカウントが一時的にロックされます。有効期限が切れているパスワードで正常にログインしたら、ただちにパスワードをリセットしてください。
  • B2C Commerce でのパスワードを忘れた場合のリセット
    パスワードを忘れてしまった場合はリセットできます。ただし、この手順は、アカウントを正常にアクティベートした場合にのみ使用できます。既存のパスワードの有効期限が切れている場合でも、新しいパスワードを定義します。パスワードの有効期限が切れた後は、新しいパスワードの設定を 6 回まで試みることができます。その後は、アカウントが一時的にロックされます。有効期限が切れているパスワードで正常にログインしたら、ただちにパスワードをリセットしてください。
  • B2C Commerce でのアカウント情報の変更
    Account Manager でアカウント情報を変更します。Eメールアドレスは変更できませんが、勤務先の電話番号など、他のアカウント情報を変更できます。また、組織の多要素認証 (MFA) の検証メソッド設定によっては、B2C Commerce アプリケーションにログインする際に ID を検証するメソッドを登録できます。
  • B2C Commerce でのユーザーアカウントの作成
    アカウントの作成は、アカウント管理者のみが行えます。各アカウントは 1 つ以上の組織に割り当てる必要があります。また、作成できるのは、アカウント管理者がメンバーになっている組織のアカウントのみです。
  • B2C Commerce でのユーザーアカウントの編集
    アカウント管理者は、自分が所属する組織のユーザーアカウントの詳細、アクセス許可、ステータスを編集できます。
  • B2C Commerce でのアカウントのロック解除
    アカウントへのログインを 6 回失敗すると、Account Manager によってアカウントが一時的に 30 分間ロックされます。アカウント管理者は、管理者の組織内でロックされたアカウントを明示的にロック解除できます。
  • B2C Commerce でのアカウントの組織への追加
    アカウント管理者は、ユーザーアカウントを組織に追加できます。
  • B2C Commerce でのパートナーアカウントのアクセスの管理
    アカウント管理者は、Account Manager を使用して、管理者の組織 (パートナーアカウントなど) に招待されたユーザーアカウントのアクセスを管理できます。招待されたアカウントがどの B2C Commerce アプリケーションにアクセスできるかを制御できます。
  • B2C Commerce でのユーザーアカウントのリセット
    アカウント管理者は、Account Manager を使用してユーザーのアカウントをリセットできます。この操作は、ユーザーがパスワードを忘れた場合や、Salesforce アカウントから Account Manager アカウントのリンクを解除する場合に有用です。ユーザーのアカウントをリセットすると、そのアカウントは最初に作成されたときと同じ状態になります。ユーザーはアカウントを再度アクティベートする必要があります。
  • B2C Commerce でのアカウントの削除
    アカウントを削除できるのはアカウント管理者のみであり、そのアカウントがアカウント管理者の組織に割り当てられている必要があります。アカウント管理者がアカウントを無効にすると、そのユーザーは自分の認証情報を使用してサービスにログインすることができなくなります。アカウントを削除しても、セキュリティ上の理由から、Account Manager は引き続きそのユーザーをデータベースに保存します。
  • B2C Commerce アカウントのパージ (完全な削除)
    アカウントをパージ (完全に削除) できるのはアカウント管理者のみです。なお、当該アカウントはアカウント管理者の組織に割り当てられている必要があります。アカウントをパージすると、そのユーザーレコードは Account Manager のデータベースから削除されます。
  • B2C Commerce でのアカウント削除の取り消し
    アカウントが削除されると、削除されたユーザーは、Account Manager 認証情報を必要とするいずれのシステムにもログインできなくなります。アカウントを間違って削除した場合、あるいはセキュリティ対策として削除した場合は、そのアカウントの削除を取り消すことができます。アカウントの削除の取り消しは、アカウント管理者のみが行えます。
  • B2C Commerce での API クライアントの追加
    アカウント管理者は、Account Manager を使用して API クライアントを作成できます。Salesforce Commerce API (Shopper Commerce API (SCAPI)) または Open Commerce API (OCAPI) にアクセスするには、API クライアントを使用する必要があります。これらの API へのアクセスに使用する URL に API クライアント ID を追加します。API クライアントは、On-Demand Sandbox API を使用する場合にも必要です。
  • B2C Commerce での API クライアント ID の有効化と無効化
    アカウント管理者は、Account Manager を使用して、API クライアントの有効/無効を切り替えることができます。Open Commerce API には、API クライアントからアクセスする必要があります。API クライアント ID は、Open Commerce API とのインタラクションを行うために使用する URL に付加します。API クライアントは、On-Demand Sandbox API を使用する場合にも必要です。
  • B2C Commerce API クライアントのパージ
    Account Manager 管理者は、Account Manager のパージ機能を使用して API クライアントをパージできます。
  • B2C Commerce での組織の編集
    アカウント管理者は、組織を編集してパスワードポリシーを指定したり、ユーザーが自分の Account Manager アカウントを Salesforce Platform の組織内の既存のアカウントにリンクできるようにしたり、ユーザーが B2C Commerce B2C アプリケーションにログインする際に ID を検証するために使用できる多要素認証 (MFA) 検証メソッドを指定したりできます。セキュリティを向上させ、不正なアクセスやアカウントへの被害を削減するために、MFA はすべての Account Manager ユーザーに対して必須になっています。
  • 監査ログイベント
    Account Manager B2C Commerce の監査ログイベントは Log Center で利用でき、ユーザー、API クライアント、組織に対する変更を可視化できます。
  • B2C Commerce での B2C Commerce アカウントについての FAQ
    B2C Commerce では、統一アカウント管理システムである Account Manager を使用します。このトピックでは、Account Manager を使用してアカウントを設定し、アクセスする際の一般的な質問に回答します。
  • Account Manager セキュリティ通知メールを受信する連絡先ユーザーの選択
    B2C Commerce Account Manager の変更に関するセキュリティ Eメールアラートを受信する連絡先ユーザーを最大 5 人選択します。

過去のレポートの設定

過去のレポートのアナリティクスを記録するために、特定のテンプレートをアプリケーションに追加できます。過去のアナリティクスレポートの統合を参照してください。

B2C Commerce では、セッション ID を使用して Web アクティビティが記録されます。このため、訪問数と訪問者数 (一意の訪問数) は区別されませんが、ユーザーが Cookie をブロックしたり JavaScript を許可していないためにカウントされないという問題を回避できます。また、B2C Commerce は Web ログを使用しており、データベースからより高速にデータを取得できます。Web ログは、消費者によって入力された注文など、すべてのストアフロントの Web アクティビティを表します。一方、注文のキャンセル、注文の変更、マーチャントがオフラインで行った返品などは表されません。

これらのレポートを使用する場合は、次の点に注意してください:

  • 使用されているテクノロジーの性質上、どのレポートも常に 100% 正確であるとは限りません。
  • 訪問は、必要に応じて 1 回の期間 (たとえば、1 日の最後) で終了しますが、次回のより長い期間 (たとえば次の日) へ継続されます。このため、レポートの日数の合計は必ずしも、その月内の日数とは一致しません。
  • レポートを実行するには、ストアフロントに インクルード をもつ必要があります。例については、SiteGenesis アプリケーションを参照してください。
警告

アナリティクスレポートでは、en_US 地域情報ですべてのアナリティクスがコンパイルされます。どんな理由があっても、レポートテンプレートの地域情報を変更しないでください。ご不明な点がございましたら、Salesforce サポートにお問い合わせください。

メモ 分析カレンダーウィジットでは、週数の計算に米国の標準が使用されます。つまり、週の最初の日は日曜日で、土曜日が週の最後になります。
メモ レポートのコンバージョンと割合の値の精度は、小さなコンバージョン率を表示できるように、小数点以下 2 桁となります。たとえば、250,000 件の訪問に対する 95 個の注文は、(小数点以下 1 桁で) 0.0% ではなく、0.04% とアナリティクスレポートに表示されます。

コンテンツブロックの概要

コンテンツブロックは、1 回定義し、複数のページやストアフロント領域で使用する 1 つまたは複数のコンポーネントで構成されるものです。これらは JSON ベースの形式を使用し、PWA Kit、Storefront Next、および Salesforce Reference Architecture (SFRA) ストアフロントでサポートされています。

コンテンツブロックとは、画像、テキスト、ボタンなどの 1 つまたは複数のコンテンツコンポーネントを、1 つのターゲット可能な単位にまとめたものです。コンテンツブロックは個々のページに関連付けられていないため、コンテンツブロックは 1 回作成すれば、複数のページで再利用できます。

利点

  • 信頼できる唯一の情報源 :コンテンツを 1 回定義し、複数のページに表示します。
  • インスタントアップデート :一度編集すれば、どこでも更新できます。
  • メンテナンスの軽減 :ページごとの更新を繰り返す必要がなくなります。
  • 一貫したブランディング :ストアフロント全体でプロモーションメッセージとデザイン要素の一貫性を保ちます。
  • ターゲット設定とスケジュール設定 :スケジュールルール、顧客グループフィルター、またはキャンペーンのターゲット設定を使用して、コンテンツを表示する日時とユーザーを制御します。

コンテンツブロックの仕組み

Page Designer のコンテンツブロックは、コンポーネントから作成します。コンポーネントには、すぐに使用できるタイプ (画像、テキスト、ボタンなど) や、デベロッパーが定義したカスタムコンポーネントタイプがあります。コンテンツブロックには、1 つのコンポーネント、またはレイアウト内に配置された複数のコンポーネントのコンポジションを含めることができます。

Page Designer で作成したコンテンツブロックは、Business Manager のコンテンツブロックモジュールに表示されます。このモジュールを使用して、ターゲティングルールの設定、フィルタリングと検索、一括操作の適用、使用状況の確認などのライフサイクルタスクを管理します。

Business Manager でのクロスサイトリクエストフォージェリ (CSRF) からの保護

CSRF 攻撃は、悪意をもつ攻撃者が使用する手法で、被害者が Business Manager に対して保護されたリクエストを行うように強制します。このようなリクエストは eコマースビジネスに大きな混乱を引き起こす可能性があります。このトピックは、B2C Commerce に該当します。

CSRF 攻撃

すべての Business Manager ページは、CSRF 攻撃に対して自動的に保護されます。Business Manager ページが B2C Commerce サーバーにリクエストを行うと、そのリクエストに特別な CSRF トークンが自動的に挿入されます。サーバーがリクエストを受信すると、リクエストが保護された (害となる可能性のある) アクションを実行しようとしているかどうかが判定されます。リクエストがこのようなアクションを実行しようとすると、挿入されたトークンがサーバーによって自動的に検証されます。トークンが検証されると、サーバーは保護されたアクションを完了し、予想されている応答を返します。検証されなかった場合は、SIG では 17.4 および PIG では 17.5 から、サーバーによって警告がログされ、場合によってはエラーページが返されます。

エラーページが表示された場合は、指示されたステップにしたがって、エラーが発生したページを再試行してください。再試行が成功した場合は、エラーは無視できます。しかし再試行が失敗してエラーが再度表示された場合は、CSRF 攻撃が行われている可能性が高く、また、同時にこの攻撃から保護されています。この場合は、セキュリティ部門に連絡してください。

CSRF に関連するエラーやログエントリがあっても、攻撃が実際に行われているとは限りません。Salesforce システム管理者は、CSRF ログエントリをトラブルシューティングして、根本的な原因を調査し、適切な対応を決定します。Business Manager のカスタム拡張機能を使用している場合は、CSRF トークンを適切に挿入するためにデベロッパーが拡張機能のカスタムコードを変更する必要があります。その他の場合は、特定のパイプラインやユーザーエージェントを許可リストに追加できます。

CSRF ログエントリのトラブルシューティング

CSRF ログエントリは次の形式を使用しています。

Pipeline CSRF Token not valid[reason]: pipeline: (token|no_token)::Referer/Origin: URL::UserAgent: agent

各パラメーターの説明:

  • reason は検証が失敗した理由を説明する文字列です。以下のような理由が考えられます。
    • Origin validation ― リクエストが Business Manager ページではない Web サイトから送信された。
    • No token ― リクエストに CSRF トークンが挿入されていない。
    • CSRF token validation ― トークンがこのユーザーに対して正しくない、または、タイムアウトしている (タイムアウトは 1 時間)。
    • Exception occurred ― 処理中に予想外の事態が発生した (このエラーはキャッチオールです)。
  • pipeline はリクエスト内のパイプラインの名前です。
  • token はサーバーが受信したトークンです (リクエストでトークンが送信された場合)。
  • no_tokenは、要求にトークンが見つからないことを示す文字列です。"CSRF Token doesn't exist." (CSRF トークンがありません。)
  • URL はリクエストの起点を示す URL です。
  • agent は、ユーザーエージェントの最初の 32 文字です。

ログファイルでこれらのエントリを見つけるには、「Pipeline CSRF Token」という文字列を検索します。

Log Center を参照してください。

サーバーは、有効な CSRF トークンを予想する際に、トークンが見つからないか、または無効なトークンが見つかった場合に、ログエントリを作成します。次のような状況では、ログエントリが発生する可能性があります。

状況 対応策
Business Manager ユーザーが攻撃を受けている場合。ユーザーが別のサイトを訪問した後にエラーページが表示された場合は、この別のサイトが Business Manager に対して保護されたリクエストを試み、フレームワークによって攻撃に対する適切な保護が行われています。 Business Manager ユーザーは、この攻撃をセキュリティ部門に報告します。

Business Manager ユーザーは攻撃を受けておらず、ログエントリにトークンが見つからなかったことが示されている場合。Business Manager のカスタム拡張機能でトークンの自動挿入が適切に行われなかった可能性があります。

B2C Commerce では、このような事態が発生する可能性がある場所として、次のような状況を特定しています。

  • URL が JavaScript 変数の内部に、JavaScript メソッドの引数として、または、onclick ハンドラとして形成されている。
  • URL が <meta> タグの内部、特に refresh に形成されている。
  • URL が <isset> の内部、またはカスタム定義のタグ内に形成されている。
  • URL がパイプライン、パイプラインディクショナリー、またはコードの内部に定義されている。

トークンを手動で追加するには、デベロッパーはdw.web.URL.appendCSRFTokenBM()メソッドを使用します。たとえば、次のコードを変更できます。

<meta http-equiv="refresh" 
content="0; URL=${dw.web.URLUtils.url('ViewAccount-Show').toString()}">

デベロッパーは次のように変更できます:

<meta http-equiv="refresh" 
content="0; URL=${dw.web.URLUtils.url('ViewAccount-Show').appendCSRFTokenBM().toString()}">
Business Manager ユーザーは攻撃を受けておらず、ログエントリにトークンが無効であることが示されている場合。トークンは 60 分後に無効になるため、ユーザーが古いブラウザーのタブに戻ってリクエストを行うと、検証に失敗することがあります。また、Business Manager 内の別のページにナビゲートしなくてもページ内に表示されるデータが更新されるいくつかのページでも、このような状態が発生することがあります。 Business Manager ユーザーがエラーの発生したページを更新できる。
Business Manager ユーザーは攻撃を受けていないが、Business Manager からサーバーにリクエストを行う代わりに、Eメール、ブックマーク、または別の Web サイトからユーザーがリクエストを行った場合。

ユーザーが Eメール、ブックマーク、別の Web サイトからリクエストできるようにするには、目的のページへの安全なリダイレクトとして機能する新しい開始ノードをパイプラインに作成することをお勧めします。このタスクはデベロッパーが実行します。

デベロッパーがこの作業を完了したら、管理者はこのリダイレクトパイプライン - 開始ノード (redirect pipeline-start node) の組み合わせを許可リストに追加できます。これによって、すべてのユーザーに対し、この開始ノードの CSRF 検証が無効になります。
Business Manager ユーザーは攻撃を受けていないが、リクエストを保護できないか、リクエストがまだ保護されていない場合。 管理者は CSRF 許可リストを使用して、パイプラインまたはパイプライン/開始ノードの組み合わせの検証を一時的に無効にできます。これは一般的に推奨されません。
自動スクリプトは、Business Manager インスタンスからデータを収集するか、自動テストのためにデータをインポートします。

管理者は CSRF 許可リストを使用して、スクリプトのユーザーエージェントを許可することができます。この方法を使用する場合は、ブラウザー以外のユーザー エージェント文字列を使用することを強くお勧めします。これによって、ユーザーエージェントが許可リストの値と完全に一致する場合、すべてのリクエストの検証ロジックが無効になります。

または、顧客が (B2C Commerce によってすべての Business Manager ページに埋め込まれている) CSRF トークンの自動スクリプトの知識を提供して、スクリプトベースのリクエストでトークンを使用することもできます。これによってブラウザーベースのナビゲーションの動作が模倣されます。これが推奨されるアプローチです。

エンゲージメントイベント統合リファレンス

エンゲージメントイベントは、B2C Commerce ストアフロントからの顧客とのやり取りをほぼリアルタイムでキャプチャし、そのデータを Data 360 データモデルオブジェクト (DMO) にマッピングします。

イベントファミリー

エンゲージメントイベントはイベントファミリーに分類されます。各ファミリーは、特定のタイプのインタラクションをキャプチャします。

  • Cart Management (買い物カゴ管理): 買い物カゴのインタラクション ( 買い物カゴへの追加、買い物カゴの削除、買い物カゴの更新 ) を追跡し、買い物カゴの放棄と購入意向の分析に役立てます。
  • Checkout Process (注文手続きプロセス): 注文手続きの進行状況 ( checkout-begin、checkout-step、checkout-contact-info (廃止予定)、checkout-user-register、checkout-submit ) を追跡し、注文手続きのコンバージョンの分析に役立てます。
  • Customer Profile Management (顧客プロフィール管理): アカウント登録とプロファイルの更新 ( user-register、update-user-profile ) を追跡して、ID 管理とクロスデバイス認識の分析に役立てます。
  • Order Processing (注文処理): 完了した注文 ( 注文承認済み ) を追跡して、収益の追跡と顧客ライフサイクルの分析に役立てます。
  • Product Discovery (商品発見): 商品の検索と閲覧 ( search、catalog-object-view-start、catalog-object-impression ) を追跡し、検索の最適化とマーチャンダイジング戦略の分析に役立てます。
  • Content Engagement (コンテンツエンゲージメント): ページビュー( page-view )を追跡して、コンテンツの最適化とユーザージャーニーマッピングの分析に役立てます。
  • Wishlist Management (ほしい物リスト管理): 後で使用するために保存された商品を追跡し( wish-list-add、wish-list-remove )、リマーケティング キャンペーンや在庫計画の分析に役立てます。

埋め込み CDN の概要

Salesforce B2C Commerce では、サイトの表示速度とコンテンツ配信を高速化する埋め込みコンテンツ配信ネットワーク (eCDN) をデジタル顧客に提供しています。eCDN は、プロキシサーバーを使用するコンシューマーに対して短い応答時間を提供します。プロキシサーバーを使用することによって、デジタルコンテンツを提供できます。

B2C Commerce の顧客は、常に成長を続ける拡張可能な国際コンテンツ配信ネットワークの一部です。買い物客とリテーラーの間の接続を効率化すると、買い物客がどんなデバイスを使用していても、すべての B2C Commerce サイトで高速かつ効率的にレンダリングができるようになります。

WAF を構成する際には、以下を念頭に置いてください。

  • 同じゾーンのサブドメインは、同じ B2C Commerce インスタンスで、または同じリテーラーの別のレルムの別のインスタンスで構成します。たとえば、www.shop.comは Production (本番) インスタンスで、test.shop.comは Development (開発) インスタンスで、eu.shop.comは EU レルムの Production (本番) インスタンスで構成できます。
  • 埋め込み CDN は、Business Manager の eCDN コンソールを含み、すべてのプライマリインスタンスグループ (PIG) インスタンスタイプで使用できます。Development (開発)、Staging (ステージング)、Production (本番) の 4 つの種類があります。埋め込み CDN は、On-Demand Sandboxes (ODS) を含むセカンダリインスタンスグループ (SIG) インスタンスでも使用できます。B2C Commerce にトラフィックをルーティングする前に、カスタムホスト名 (サブドメイン) の eCDN を構成する必要があります。
  • すべてのストアフロントで「HTTPS を強制する」が有効であることを確認します。
  • eCDN はさまざまな Cookie を使用して、ネットワークリソースを最大化し、トラフィックを管理し、サイトを悪意をもったトラフィックから保護します。これらの Cookie の詳細については、Understanding the Cloudflare Cookies (Cloudflare Cookie の理解) を参照してください。

また eCDN は Web Application Firewall (WAF) と HTTP Strict Transport Security (HSTS) をサポートしています。

B2C Commerce でのインポート/エクスポート処理の概要

一連の基本的な手順に従って、インポートとエクスポートを完了します。このトピックは、B2C Commerce に該当します。

インポートの基本的な手順:

まず、該当するタイプのシステムオブジェクト用の B2C Commerce スキーマに準拠する XML ファイルを作成します。すべての B2C Commerce オブジェクトとそのオブジェクトのインポートに使用されるスキーマファイルのリストについては、インポート/エクスポートオブジェクトのチートシートを参照してください。

次に、XML ファイルをマーチャントのバックエンドシステムから B2C Commerce インスタンスに転送します。Staging (ステージング) インスタンスまたは Production (本番) インスタンスでは、ファイル転送用のセキュアな接続も設定する必要があります。Sandbox (サンドボックス) ではセキュアな接続は必要ありません。

その次に、XML ファイルをインスタンスのデータベースにインポートします。このインポートは Business Manager から手動で行うか、カスタムパイプラインを作成します。B2C Commerce には、最も標準的なインポート用にインポートパイプレットが用意されています。Salesforce では、ビジネスオブジェクトが B2C Commerce に読み込まれるたびに、スクリプトまたはパイプレットによるカスタムロジックを実装するのではなく、標準のインポートパイプレットを使用することをお勧めします。標準のインポートパイプレットでは大量のデータセットを処理でき、高速で信頼性が高いうえ、システムリソースを効率的に使用することができます。

エクスポートの基本的な手順:

まず、データベースオブジェクトを XML ファイルにエクスポートします。エクスポートファイルでは、データベースオブジェクトのインポートに使用されるスキーマ定義と同じ定義が使用されます。このエクスポートは Business Manager から手動で行うか、カスタムパイプラインを作成します。データエクスポートを自動化するには、パイプラインを作成します。B2C Commerce には、ほとんどのエクスポートで使用できるエクスポートパイプレットが用意されています。場合によっては、エクスポートパイプレットで選択するオブジェクトの粒度が、Business Manager で許容されるよりも高いことがあります。

次に、ファイルをインスタンスからマーチャントのバックエンドシステムに転送します。必要に応じて、安全な接続を使用します。たとえば、PCI-Data Security Standard (DSS) 要件として、セキュアな接続を要求できます。別のバックエンドシステムでも、セキュアな接続を要求できます。

定期的にインポート/エクスポート処理を行う場合は、ファイル転送とインポート/エクスポートの両方でバッチジョブを構成します。パイプレットを使用して、プログラムでインポート/エクスポート処理を制御することもできます。

Staging (ステージング) および Production (本番) のためのインポート/エクスポート

バックエンドシステムからプライマリインスタンスグループのインスタンスにセキュア接続経由でデータを移動する際は通常、カスタムのパイプラインを使用します。

頻度の低いフィードは Staging (ステージング) インスタンスのみにインポートしてから Production (本番) インスタンスにレプリケートします。このアプローチを使用して、インポートされたデータに関する問題から Production (本番) インスタンスを保護します。Web のみの記述やその他の情報を手動で追加するには、一部のフィードで Business Manager の強化が必要です。強化の必要なフィードは、まず Staging (ステージング) インスタンスで強化を施し、次にデータを Production (本番) インスタンスにレプリケートします。

頻繁に変更されるデータをステージングしてレプリケートする方法は現実的ではありません。頻繁な変更は、フィードを使用して Production (本番) インスタンスに直接インポートします。頻繁なフィードはステージングおよび本番インスタンスに同時にインポートし、両インスタンスの同期が保たれるようにします。

バックエンドシステム用に B2C Commerce からファイルをエクスポートすることもできます。インポートフィードと同じ B2C Commerce スキーマファイルで定義されたフィードをエクスポートするか、カスタムパイプラインを使用してカスタムフィードを作成します。

開発中は、まず Business Manager 経由で手動でファイルをインポートします。ただし、その後はカスタムのインポートパイプラインを使用してファイルのインポートとエクスポートを自動化する方が効率的です。Production (本番) インスタンスは価格や在庫が頻繁 (たとえば 10 分ごと) に変更される可能性があるため、たいていは自動化が不可欠です。フィードのインポートとエクスポートは、カスタムパイプラインとスケジュール済みジョブを使用して自動化します。

カスタムパイプラインにビジネスロジックを追加して、インポートファイルに値を追加したり、検索インデックスを自動的に更新したり、インポートファイルをアーカイブしたりできるようにします。

Production (本番) インスタンスからサードパーティーまたはバックエンドシステムにデータをエクスポートします。カスタムパイプラインにビジネスロジックを追加して、エクスポートファイルの形式の変更、値の追加、その他のファイル処理を行えるようにします。

Development (開発) インスタンスのためのインポート/エクスポート

Development (開発) インスタンスは Production (本番) インスタンスのテスト環境であるため、通常インポートまたはエクスポートは使用されません。最初に、Staging (ステージング) インスタンスから Development (開発) インスタンスにサイトのインポート/エクスポートを行います。最初のインポート/エクスポート後は、データのレプリケーションを使用して Development (開発) インスタンスでデータとコードを更新します。

メモ  最初のサイトのインポートを実行するには、ImportSiteArchive ジョブステップを含むカスタムジョブを使用します。サイトのインポートは、Business Manager モジュールからは開始できません。

B2C Commerce の概念と用語

B2C Commerce では、eコマースサイトのためのリソースと処理を提供しています。サイトはレルム内で作成および構築します。

顧客のレルムにはプライマリインスタンスグループとセカンダリインスタンスグループが含まれています。

レルム

一般的に、顧客は 1 つのレルムをもちます。レルムにはインスタンスが含まれ、インスタンスでオンラインストアフロントの開発、テスト、デプロイを行います。B2C Commerce インスタンスは、アプリケーションインフラストラクチャです。これには、Web サーバー、アプリケーションサーバー、データベースサーバーが含まれています。通常は、6 つの B2C Commerce インスタンスがあります。コード開発のための Sandbox (サンドボックス) インスタンスが 3 つ以上、および、サイトのステージング、テスト、デプロイ用のインスタンスが 3 つです。マーチャントは、ストアフロントのオンラインマーチャンダイジング、構成、カスタム化のオプションを制御できます。マーチャントのインスタンス管理者は、レルム内のパスワード管理、ユーザー許可、インスタンスの停止と開始を直接制御できます。

  • Development (開発) インスタンス: サイトの構成、データ準備、およびデータインポートに使用します。
  • Staging (ステージング) インスタンス: デプロイ前にサイトをテストするために使用します。
  • Production (本番) インスタンス: 顧客が使用するライブサイトをホストします。

単一レルム構成と複数レルム構成

ほとんどの場合、単一のレルムで、ブランディングや地域情報が異なる複数のサイトを開発、ステージング、デプロイできます。ストアフロントサイトを管理する担当者は、異なる場所にいてもかまいません。サイト間でマスターカタログを共有することも、異なるカタログをもつこともできます。

複数の異なる業務を行っている場合や、グローバルチームがそれぞれ独自のプロセスやビジネスポリシーをもっている場合は、複数のレルムをもつことを検討します。また、明確に異なる組織でバックエンド統合やスケジュールが異なる場合、または各チームがサイトを個別に管理することに利点がある場合は、別々のレルムをもつことができます。同じレルム内のサイトは商品データのマスターカタログを共有できます。レルムの異なるサイトは、カタログ構造を使用してデータを共有することはできません。データを共有するには、別のレルムにデータをインポートします。

例: たとえば、ヨーロッパと環太平洋に別々のブランドをもつサイトがあるとします。この場合は、環太平洋のサイトを管理するチームのためにレルムを 1 つ、ヨーロッパのチームのために別のレルムを 1 つもつことができます。

プライマリインスタンスグループ

プライマリインスタンスグループ (PIG) は 3 つのインスタンスをもち、マーチャントはこれらのインスタンスを使用してデータの追加、コードのテスト、ライブサイトの実行を行います。PIG は 1 つのレルムに 1 つしか存在できません。

セカンダリインスタンスグループ

セカンダリインスタンスグループ (SIG) には Sandbox (サンドボックス) インスタンスが含まれます。SIG 内の Sandbox の最小数は 3、最大数は 47 です。

Cloud

クラウドは、Salesforce が管理するインスタンスとライブサイトを実行するために使用される基本リソースです。クラウドを直接操作することはありませんが、クラウドはサイトを支える基盤です。

B2C Commerce の検索とナビゲーション

B2C Commerce を使用して、サイト内や Google などの外部検索エンジンから顧客による商品の検索方法を制御できます。

  • B2C Commerce の検索チェックリスト
    検索チェックリストには、B2C Commerce での検索をカスタマイズするために実行できるタスクが含まれています。基本検索設定以外の設定はほとんどが任意ですが、設定することが推奨されます。
  • B2B Commerce のキーワード検索機能
    キーワード検索とは、購入したい商品を見つけるために大部分の顧客がストアフロントで使用する検索方法です。大規模で正確な検索インデックスを作成するには、検索可能な商品属性を指定し、検索辞書を使用して関係を構成します。商品の検索が実行された場合は、B2C Commerce によって検索処理が実行され、結果が収集され、それぞれの結果の表示方法を定義する並べ替えルールが適用されます。
  • B2C Commerce の検索辞書
    B2C Commerce の検索辞書モジュールを使用すると、すべての検索辞書を 1 か所で管理できます。検索辞書にはすべての検索可能な商品属性が含まれており、特定の条件によってグループ化され、整理されています。
  • B2C Commerce の検索インデックス
    B2C Commerce の検索インデックスは、ストアフロントで検索を実行するために使用されるデータを提供します。商品またはコンテンツのデータを更新するたびにインデックスを再作成して、インデックス内のデータができるだけ最新になるようにしてください。
  • B2C Commerce の検索結果
    検索結果とは、顧客がストアフロントで検索を行った際に返される項目です。
  • B2C Commerce の並べ替えルール
    B2C Commerce の並べ替えルールを使用して、検索結果が表示される順序を制御し、顧客が関心を持っている商品をすばやく見つけられるようにすることができます。
  • B2C Commerce の検索絞り込み
    B2C Commerce では、顧客が価格、プロモーション、カテゴリ、商品属性などの複数の属性を使用して検索を絞り込めるようにすることができます。たとえば、顧客が画面のサイズ、価格、メーカーに基づいてテレビを検索したり、ズーム倍率、価格、メーカーに基づいてレンズを検索できるようにします。これは、大規模なカタログがあり、どの顧客も具体的な商品のみを探している場合に役立ちます。たとえば、アパレルサイトでは、ほとんどの顧客は希望するサイズまたは色でない商品には関心がありません。

B2C Commerce の SEO & の見つけやすさ

検索エンジンの最適化 (SEO) は、検索エンジンで無料のサイトの結果を増やすことに焦点を当てたものです。創造的要素と技術的要素の両方を使用して、検索エンジンのランキングと認知度を向上させ、サイトにより多くのトラフィックを導くことを目指します。外部検索エンジン (Google など) では、関係のないキーワードや複数のディレクトリレイヤー、複数のパラメーターなどが含まれる長い URL には低いランキングが割り当てられます。このトピックは、B2C Commerce に該当します。

SEO Platform Adoption Playbook (SEO プラットフォーム導入プレイブック) を参照することをお勧めします。

外部検索エンジンでのオーガニック (無料の) 検索結果を最適化するために、サイトマップの作成前と後にいくつかのタスクを行う必要があります。

AI を活用した検索と発見可能性

従来の検索エンジンに加えて、AIを活用した検索および回答エンジン(ChatGPT、Perplexity、Google AI Overviewsなど)がコマースサイトをクロールして応答を強化するようになりました。この新しい分野は、Generative Engine Optimization (GEO) や Answer Engine Optimization (AEO) と呼ばれることもあります。従来のSEOを改善するのと同じプラクティスの多くは、クリーンなURL構造、整形式のサイトマップ、メタタグの適切な使用など、AIによる発見可能性も向上させます。

AI の検出可能性に関する主な考慮事項は次のとおりです。

  • AI クローラーのRobots.txt:GPTBot、ClaudeBot、PerplexityBot などの AI クローラーは、robots.txt ファイルをリクエストして、アクセスできるページを判断します。Business Manager の「カスタムrobots.txt定義」オプションを使用して、これらのクローラーのアクセスを制御します。B2C Commerce のRobots.txtファイルを参照してください。
  • サーバー側のレンダリング通常、AI クローラーは JavaScript を実行しません。クライアント側でのみレンダリングされるコンテンツは、これらのクローラーには表示されません。主要な商品情報 (名前、説明、価格) が最初の HTML 応答に含まれていることを確認します。Salesforce Reference Architecture (SFRA) とサーバーサイドレンダリングを備えた PWA Kit を使用する B2C Commerce ストアフロントは、この点に適しています。
  • 自然言語コンテンツ:AIモデルは、キーワードの多いテキストや仕様のみのテキストよりも、明確で説明的な自然言語で書かれたコンテンツを優先します。顧客からの一般的な質問に回答する商品説明を作成します。
  • 構造化された HTML 階層:見出しタグ ( h1、h2、h3 ) を使用して、論理的なコンテンツ階層を作成します。各ページには、主要な主題 (PDP の製品名など) に対して 1 つのh1があり、下位レベルの見出しを使用してサポート コンテンツを整理します。
  • 構造化データ:スキーママークアップ ( Product、Offer、AggregateRatingタイプの JSON-LD など) は、従来の検索エンジンと AI クローラーの両方がページコンテンツを正確に解釈するのに役立ちます。

B2C Commerce のサイトマップ

サイトマップは、クローラーによるインデックス化の効率が上がるように、Web サイトに関する情報を Google や Yahoo といった検索エンジンに提供する XML ファイルです。サイトマップには、インデックス可能なすべての URL のリストが含まれており、ページの最終更新日や更新頻度、ページの関連性などの追加情報を検索エンジンに提供することができます。検索エンジンは、この情報を使用してサイトへのリンクを構築し、検索結果のリンクのランキングを制御します。このトピックは、B2C Commerce に該当します。

サイトマップを利用する主な利点は、次のとおりです。

  • サイトのクロール範囲の改善。サイトマップを使用して、サイトの静的コンテンツによって参照されない動的コンテンツや、標準的なクロールプロセスで検出されない動的コンテンツを公開します。
  • 検索結果の改善。サイトマップを使用することで、検索インデックスのコンテンツを最新の情報に保つことができます。古いインデックス化されたコンテンツが検索結果に表示されるないようにするには、ページの変更頻度を検索エンジンに通知して、検索エンジンがそのページを再インデックス化するタイミングを認識できるようにします。
  • サイトに対する理解の改善。ページの可視性や、サイトへのトラフィックにつながった検索の統計、サイト内の異なるページをクローラーがインデックスする方法など、Google が提供するレポートを分析することができます。

Google は検索エンジンの例であり、SiteGenesis はサイトの例です。Google は、検索エンジン市場でほぼ半分のシェアを占めており、Google からのトラフィックを最適化できるよう尽力することは、ビジネスにおいて理に適っています。ただし、多くの検索エンジンが sitemap.org プロトコルを使用してサイトマップを定義しているため、Google 向けに生成したサイトマップが、Yahoo や MSN といった他の検索エンジンで登録、使用される場合もあります。

サイトマップのトポロジーを参照してください。

B2C Commerce でのサイトマップの構成

B2C Commerce では、Sitemaps.Org のサイトマッププロトコル 0.9 に準拠したサイトマップを生成できます。これは、Google の標準サイトマップ定義です。

B2C Commerce でサイトマップを使用するには:

  • Business Manager でフィードまたは手動で、対応するデータのサイトマップ属性を構成します。
  • Business Manager でサイトマップを生成します。サイトマップの生成を参照してください。
  • お好きな検索エンジンでアカウントを作成し、サイト所有権を確認します。検索エンジンへのサイトマップの通知を参照してください。

サイトマップのホームページリンク

B2C Commerce ストアフロントは、以下の形式で、店舗のホームページへのリンクを含むマップを生成します:

http://<alias>/on/demandware/Sites-<Sitename>-Site/default/Home-Show.

ただし、以下のようなルールを使用して、解決先がホームページとなるドメインエイリアスをサイトに設定した場合は:

"www.mysite.com" : [
{"pipeline":"Home-Show"} 
],

生成されるサイトマップには、以下のようなリンクが含まれます:

http://www.mysite.com/
メモ 各インスタンスタイプに、個別のサイトマップ設定を構成します。サイトマップのサイト環境設定を Staging (ステージング) から Production (本番) または Development (開発) にレプリケートすることはできません。各インスタンスにサイトマップを生成するには、設定とジョブを作成する必要があります。

複数サイト

複数のサイトがある場合、複数のサイトマップが必要になる場合があります。同じマスターカタログを複数のサイトで共有する場合は、地域情報が異なっていても、別々のサイトマップは必要ありません。

しかし、同じマスターカタログを複数のサイトで共有しない場合は、異なるサイトマップが必要になります。これらのサイトマップを別々に登録して生成します。
