拡張チャット向けのオムニチャネルルーティングの設定

オムニチャネルルーティングは、顧客メッセージを拡張チャットメッセージングチャネルを介して B2C 買い物客エージェントに転送し、エージェントが買い物客とエンゲージできるようにします。ルーティング構成を作成して、会話をメッセージングキューに割り当てる際の作業量と優先度を定義します。

  1. Salesforce 組織で、ページ上部のをクリックし、設定を選択します。
  2. 「クイック検索」ボックスで、オムニチャネル設定を有効化を見つけて選択し、オムニチャネルルーティングをオンにします。
  3. 「クイック検索」ボックスに、ルーティング構成と入力し、選択します。
  4. 次の設定でルーティング構成を作成します。
    1. ルーティング優先度 — 1
    2. ルーティングモデル — 最も利用可能
    3. キャパシティの単位 — 1.00
    4. キャパシティタイプ — 継承
  5. 構成を保存します。
  6. プライマリのオムニチャネルルーティングフロー用に、フォールバックのメッセージングキューを作成します。
    プライマリフローが使用できない場合、またはルーティングルールが失敗した場合、会話はフォールバックキューにルーティングされます。
    1. 「クイック検索」ボックスで、キューを見つけて選択します
    2. 新規をクリックします。
    3. 「ルーティング構成」で、先ほど作成した構成を選択します。
    4. 「サポートされるオブジェクト」で、メッセージングユーザーおよびメッセージングセッションを選択します。
    5. 「キューメンバー」で、EinsteinServiceAgent ユーザーとシステム管理者ユーザーを選択します。

このルーティング設定とフォールバックキューを使用するShopper Agent のオムニチャネルルーティングフローを作成します。

製品とサイトの FAQ データライブラリの前提条件の完了

買い物客エージェントが Agentforce データライブラリ (ADL) を使用するには、まずソースコンテンツでライブラリを設定します。買い物客エージェントは、アップロードされたファイルと Salesforce ナレッジ記事を含むデータライブラリを使用できます。

  1. ADL に Salesforce ナレッジを使用するには。
    1. Salesforce ナレッジを設定する。「Salesforce ナレッジを使用したナレッジベースの作成」を参照してください。
    2. データソースとして使用するために、Agentforce と Salesforce ナレッジ間の接続を確立します。
  2. データ ライブラリを作成します。
  3. ライブラリのデータソースを選択します。

    ファイルについては、「アップロードされたファイルを使用する」を参照してください。ファイルをアップロードするときは、[詳細設定] で [基本コンテンツ] を受け入れます。

    ナレッジ記事については、「Salesforce ナレッジの使用」を参照してください。

  4. 各ライブラリの API 参照名をメモします。API 名は、Shopper Agent FAQ サブエージェントの指示で指定します。

Storefront Next での Shopper Agent の起動

Shopper Agent を使用して、ショッパージャーニーで AI 支援のメリットを享受できます。Shopper Agent は、適切な商品を見つけ、おすすめ商品を取得するお手伝いをします。

Storefront Next で買い物客エージェントを以下のいずれかの方法で使用します。
  1. ストアフロントのヘッダーから Shopper Agent を起動し、チャットウィンドウを開きます。
  2. 検索フィールドに検索テキストを入力します。Storefront Next は、検索テキストをメッセージとして買い物客エージェントに送信します。

B2C ストアフロントの Shopper Agent のローカライズ

グローバル展開している店舗でエージェントを利用できるようにするには、エージェントが対応する言語を指定します。

Salesforce と Agentforce がサポートする任意の言語でストアフロントをローカライズします。Salesforce がサポートする言語および Agentforce がサポートする言語を参照してください。

  1. Salesforce 組織で、ページ上部のをクリックし、設定を選択します。
  2. 「クイック検索」ボックスに、「Agentforce エージェント」と入力し、選択します。
  3. 構成するエージェントを選択します。
  4. ビルダーで開くをクリックします。
  5. 「言語」タブで、サポートされている言語を「利用可能」列から「選択済み」列に移動します。
  6. 「会話プレビュー」で、エージェントを更新します。
  7. 目のアイコンをクリックしてプレビュー条件を編集し、ドロップダウンリストからエンドユーザーの言語を選択します。
  8. 変更を適用します。
  9. 「会話プレビュー」に戻り、エージェントを更新します。
  10. 更新したエージェントを有効化します。

PWA KIT ストアフロントに地域情報を追加する

Shopper Agent でまだサポートされていない地域情報と通貨を追加するには、地域情報と通貨と、関連するカスタムメッセージング設定を追加します。会話コンテキストを有効にすると、静的会話コンテキストピルに、ストアフロントのアクティブな地域情報に対応するローカライズされたラベルが表示されます。

  1. Business Manager で、サイト環境設定 | 地域情報の順に選択します。
  2. 新しい地域情報を構成し、エージェントでサポートする利用可能な地域情報のリストに追加します。
  3. 通貨で、新しい地域情報の通貨を選択します。
  4. PWA-Kit リポジトリに移動し、packages/template-retail-react-app/config/sites.js ディレクトリに移動します。
  5. sites.js を編集して、ストアフロントの新しい地域情報と通貨を追加します。
  6. 新しい地域情報をデフォルトのチャットメッセージに適用するには、デフォルトのメッセージをその地域情報の言語に更新します。
    1. PWA Kit リポジトリで、packages/template-retail-react-app/translations に移動します。
    2. 新しい翻訳を JSON ファイルに抽出するには、コマンドnpm run extract-default-translationsを実行します。
    3. 抽出した翻訳を、組織内の翻訳担当者に送信します。
    4. 翻訳チームから受け取ったファイルを packages/template-retail-react-app/translations フォルダーに配置します。
  7. npm run compile-translations を実行します。

拡張チャットの設定

買い物客は、モバイルアプリまたはデジタルストアフロントとのリアルタイムのチャットベースの会話を通じて、B2C Shopper Agent とエンゲージします。エージェントの拡張チャットを構成して、必要なメッセージングチャネルを設定します。

  • 拡張チャット向けのオムニチャネルルーティングの設定
    オムニチャネルルーティングは、顧客メッセージを拡張チャットメッセージングチャネルを介して B2C 買い物客エージェントに転送し、エージェントが買い物客とエンゲージできるようにします。ルーティング構成を作成して、会話をメッセージングキューに割り当てる際の作業量と優先度を定義します。
  • 買い物客エージェントのオムニチャネルルーティングフローの作成
    オムニチャネルフローは、買い物客に関するメッセージと情報を B2C 買い物客エージェントにルーティングします。フローを作成する前に、エージェントが有効になっていることを確認してください。
  • B2C Shopper Agent のメッセージングチャネルの構成
    チャットの開始前に顧客情報を B2C Shopper Agent に渡すための拡張チャットメッセージングチャネルを作成します。このチャネルに、買い物客に関するコンテキストを提供するカスタム変数を追加します。
  • 拡張チャットへのメッセージングコンポーネントの追加
    Commerce Messaging Components (CMC) は、チャットウィンドウ内の JSON 出力を変換して、買い物客とエージェント間のインタラクションを円滑にします。メッセージングバブルコンポーネントを追加するには、必要なコンポーネントを Salesforce 組織にアップロードします。
  • 拡張チャットのウェルカムメッセージのカスタマイズ
    買い物客が B2C 買い物客エージェントとのチャットを開始すると、まずウェルカムメッセージが表示されます。このメッセージをカスタマイズし、画像を追加します。

カテゴリ間で買い物客の嗜好を維持するようにエージェントを設定します

買い物客が B2C Shopper Agent を使用して商品を検索するときの好みを記憶します。買い物客が以前のカテゴリに戻ったり、新しいカテゴリに切り替えたりすると、エージェントは前回の検索で一致するファセットを識別します。一致するものが見つかった場合、買い物客エージェントは、これらのフィルターが新しい結果に適用されるかどうかを確認するために、コンテキストを明確にする質問を表示します。

この機能を有効にするには、Salesforce アカウントエグゼクティブにお問い合わせください。機能を有効にしたら、次の手順に従います。

  1. Salesforce 組織で、ページ上部のをクリックし、設定を選択します。
  2. 「クイック検索」ボックスに、「Agentforce エージェント」と入力し、選択します。
  3. B2C Shopper Agent を選択し、Builder で開くをクリックします。
  4. 「サブエージェント」タブで、「B2C Commerce Product Search Assistant」を選択します。
  5. 「Subagent 構成」タブで、下にスクロールし、「命令の追加」をクリックして、これらの指示を貼り付けます。 
    "category, attribute1:value1, attribute2:value2, ..." という形式の質問に対する回答から convContext を構築します。ここで、attributes は facetNames です。 確認の質問中に、買い物客が否定的な回答をした場合は、convContext をクリアし、NO_CONTEXTとして渡します。回答を投稿して B2CCommerceProductSearch を呼び出す
買い物客が新しい検索を開始したり、カテゴリ、性別、受信者、コア商品の意図を変更したりするときは、常に入力値 actionType を QUESTION に設定します。「いいえ」という単独の応答も、新しい検索として扱う必要があります。買い物客がコア商品の意図を変更せずに現在の検索を絞り込む絞り込みや追加のコンテキストを提供する場合 (買い物客が「はい」と言って詳細を追加する場合など) は、常に入力値 actionType を SEARCH に設定します。入力値 actionType は必須であり、常に含める必要があります。
  6. 変更内容を保存します。
  7. エージェントの会話をプレビューしてから、更新したエージェントをアクティブ化します。

買い物客エージェントのオムニチャネルルーティングフローの作成

オムニチャネルフローは、買い物客に関するメッセージと情報を B2C 買い物客エージェントにルーティングします。フローを作成する前に、エージェントが有効になっていることを確認してください。

  3. 「新規」をクリックし、オムニチャネルフローのテンプレートを選択します。
  4. フローに名前を付けます (例: Route to the Shopper Agent (買い物客エージェントへのルーティング)。
  5. 次の変数リソースを追加します。
    • Currency
    • DomainURL
    • IsCartMgmtSupported
    • OrganizationId
    • QueryFacets
    • recordid
    • RefreshToken
    • SiteId
    • UserLanguage
    • UserLocale
    • UsId
    • SfraAuthToken* (英語)
    • CsrfToken(英語)*
    *Salesforce Reference Architecture (SFRA) ストアでは必須です。
    1. 各変数について次の設定を構成します。
      • リソースタイプ — 変数
      • API 参照名: 名前を入力します。
      • データタイプ: テキスト
      • フロー外での使用可否: [ Available for input for all variables except QueryFacets] を選択します。

    2. 完了をクリックします。

    • SfraNamedCredential - 値を SFRA 指定ログイン情報の API 参照名に設定します。たとえば、SFRA_Guest_Named_Credential などです。「B2C API の名前付きログイン情報の作成」を参照してください。
    • BooleanTrue - True
    • BooleanFalse - いいえ
    1. 各変数について次の設定を構成します。
      • [リソース タイプ(Resource Type)]: [定数(Constant)]
      • API 名名前を入力します。
      • データタイプ: テキスト

      この文字列には、ファセット名 ("f")、ファセット定義 ("d")、およびファセット値 ("e") を含めます。英語以外の地域情報の場合は、ファセット名と説明は英語のままにしますが、ファセット値は地域情報の言語で入力します。

      "[{"f":"c_refinementColor","d":"this is the color of the product","e":"White, Blue, Purple, Red"},
{"f":"brand","d":"this is the brand","e":"Sony, Samsung"},
{"f":"cgid","d":"indicates the category of the product","e":""},

    オムニチャネルフローファセットの例。
  8. ファセットの後に、「レコードを更新」要素 (例: メッセージングセッションの更新) を追加し、メッセージングセッション ID を recordid に設定します。
  9. 事前チャット変数の値を設定します。
  10. メッセージングセッション要素の後に、「作業をルーティング」要素 (例: エージェントへのルーティング) を追加し、レコード ID を recordid に設定します。
  11. フローを保存します。
  12. フローをアクティブ化します。

エージェントに B2C Commerce Shopper API へのアクセス権を付与します

買い物客エージェントは、Shopper Login and API Access Service (SLAS) を介して B2C Commerce と通信します。SLAS への認可されたアクセスを取得するには、SLAS クライアントとシークレットを作成し、それらを使用して SLAS トークンを取得します。エージェントはこのトークンを使用して、SCAPI または OCAPI への認可済みの呼び出しを行います。

  • SLAS クライアントの作成
    B2C Commerce API にアクセスするための認可トークンをエージェントが取得できるように、SLAS クライアントとシークレットを作成します。
  • SLAS認証用の指定ログイン情報の作成
    SLAS は、ヘッドレス B2C Commerce API にアクセスするための Salesforce B2C Commerce の ID およびトークンサービスです。安全に保存されている SLAS クライアント ID とパスワードにアクセスするには、Salesforce が SLAS サービスに対して認証できるよう、指定ログイン情報を設定します。パブリックA PI にアクセスし、パブリックエンドポイントをテストするには、認証を必要としない指定ログイン情報も構成します。指定ログイン情報を構成する前に、まず関連付けられた外部ログイン情報を構成します。
  • B2C 買い物客エージェントのプリンシパルアクセスの割り当て
    プリンシパルアクセスを含むエージェント用の権限セットを作成します。このアクセス権により、Shopper Agent は SCAPI で認証を行い、作成した接続を使用できます。

B2C Commerce の税区分 ID 属性

B2C Commerce には、ストアフロントで商品の税率を管理するために、レガシーの taxClassId と localizedTaxClassId の 2 つのシステムオブジェクト属性があります。

taxClassId は、Salesforce Reference Architecture (SFRA) と SiteGenesis サイトのデフォルトです。localizedTaxClassId は Business Manager で有効にするフラグ設定です。taxClassId と localizedTaxClassId は並行して実行することはありません。両方の属性に値を指定しますが、アクティブな属性のみが使用されます。

taxClassId 属性

taxClassID は商品属性です。taxClassID 属性を使用して、サイトの商品 SKU に税区分を割り当てます。たとえば、商品の taxClassID を標準または除外に設定できます。特定の商品の taxClassId 属性設定は、サイトに含まれるすべての地域情報で同じになります。地域情報に別の税区分を割り当てるには、taxClassID を使用して必要な商品 SKU の税区分をマッピングします。

localizedTaxClassId 属性フラグがオフの場合は、taxClassId 属性が使用されます。taxClassId はサイトの実装に以下のような影響を与えます。

Business Manager – taxClassId フィールドは商品詳細ページに表示されます。ドロップダウンから値を変更できます。値のオプションは、税区分に対して定義されている値によって変わります。

マスターカタログのエクスポート – エクスポートによって localizedTaxClassId の属性値が渡される場合、その属性値がエクスポートファイルに表示されます。エクスポートによって存在する taxClassId の属性値も渡される場合は、その属性値もエクスポートファイルに表示されます。

注文処理 – 買い物カゴの注文手続き中に taxClassId が使用されます。

localizedTaxClassId 属性

localizedTaxClassId 属性を使用して、1 つのサイトを複数の地域情報で運営し、異なる地域情報で商品 SKU に異なる税区分 ID 値を割り当てることができます。たとえば、サイトの複数の地域情報で輸入品のチーズを販売するとします。サイトに含まれる地域情報は、輸入品のチーズに対して異なる税率をもっています。localizedTaxClassId を使用し、各地域情報に基づいてチーズの SKU に異なる税区分を設定します。

localizedTaxClassId は次の両方の税区分のシナリオをサポートするように設計されています。

  • 1 つのサイトで 1 つの商品に対して 1 つの税率
  • 1 つのサイトで 1 つの商品に対して複数の地域情報固有の税率

同じ商品に対して異なる税クラスをもつ複数の地域情報を含む新しいサイトでは、レガシーの taxClassId の代わりに localizedTaxClassId を使用することをお勧めします。

メモ レガシーの taxClassId を使用するサイトでは、localizedTaxClassId フラグを有効にすることができます。特定の地域情報の税処理のために taxClassId にマッピングされている商品 SKU がサイトにある場合は、商品が localizedTaxClassId にマッピングされるようにマッピングを変更します。

localizedTaxClass 属性フラグ

localizedTaxClassId 属性フラグは、Business Manager | グローバル環境設定 | 設定 | 商品で有効にすることができます。このフラグを有効にすると、サイトの実装で以下の処理が変更されます。

Business Manager – 商品詳細ページでレガシーの localizedTaxClassId フィールドが taxClassId フィールドを置き換えます。フィールドのデフォルト値は未定義に設定されます。ドロップダウンからこの値を変更できます。値のオプションは、税区分に対して定義されている値によって変わります。

マスターカタログのエクスポート – エクスポートによって taxClassId の属性値が渡される場合、その値がエクスポートファイルに表示されます。エクスポートによって localizedTaxClassId の属性値が渡される場合は、その値もエクスポートファイルに表示されます。

注文処理 – 買い物カゴの注文手続き中に localizedTaxClassId が使用されます。属性値は、ストアフロントからのリクエストの地域情報に基づきます。

B2C Commerce でのストアフロント URL の表示方法は、標準の B2C Commerce URL 構文、SEO URL 構文、または廃止予定の検索しやすい URL 構文の 3 種の URL 構文で定義します。使用する構文は、どの Business Manager モジュールが有効に設定されているかによって異なります。

  • URL 構文を指定しない場合は、標準の B2C Commerce URL 構文が使用されます。
  • URL ルールを有効にした場合、URL ルールモジュールで設定した構文が使用されます。ストアフロント URL 環境設定の構成を参照してください。
  • (URL ルールの環境設定の選択を解除して) 廃止予定の SEO サポートモジュールを有効にした場合、SEO サポートモジュールで構成した構文が使用されます。検索しやすい URL の有効化を参照してください。
メモ URL ルール と SEO サポート の両方を有効にすることはできません。Salesforce では、よりフレキシブルに構成できる URL ルールモジュールの使用をお勧めします。

このページでは、URL ルールの構文について、また、この構文が標準構文や SEO 標準とはどう違うのかを説明します。

サイト URL の形式

サイト URL の形式は以下のように定義されます: 

<hostname>/<endpoint>

これは、your.instance.hostname.example.com で終わるホスト名のための URL です。

例: yoursite.com/mens 

your.instance.hostname.com/s/<site-name>/<endpoint>

これは、your.instance.hostname.example.com または localhost で終わるホスト名のための URL です。

B2C Commerce 内で、URL のエンドポイントを構成およびカスタマイズします。

Production (本番) インスタンスの URL

Production (本番) インスタンスでは、B2C Commerce URL が以下のように表示されます:

タイプの例 URL
パイプライン URL 
www.SiteGenesis.com/cart
カテゴリ URL 
www.SiteGenesis.com/men
商品 URL 
www.SiteGenesis.com/shoes/sandals/red/water-sandal.html
カスタム URL 
www.SiteGenesis.com/entertain

Sandbox (サンドボックス)、Staging (ステージング)、および Development (開発) インスタンスの URL

Staging (ステージング)、Development (開発)、または Sandbox () インスタンスでエイリアス ( your.instance.hostname.example.com ) を定義します。URL は、ホスト名として your.instance.hostname.example.com 、次に接頭辞の /s、そしてサイト名が続きます。実際のエンドポイントは、Production (本番) インスタンスのエンドポイントと一致します。これにより、複数のサイトをもつ販売店は、各サイトに構成されたエンドポイントを確認することができます。

example.com などのカスタムのホスト名がエイリアスファイルで使用される場合、URL のパターンとしてパスの中で /s とサイト ID を使用する必要はなく、example.com/cart などの短い URL が作成されます。

タイプの例 URL
パイプライン URL 
your.instance.hostname.example.com/s/SiteGenesis/cart
カテゴリ URL 
your.instance.hostname.example.com/s/SiteGenesis/men
商品 URL 
your.instance.hostname.example.com/s/SiteGenesis/shoes/sandals/red/water-sandal.html
カスタム URL 
your.instance.hostname.example.com/s/SiteGenesis/entertain

一般的な構文のヒント

リクエスト URL の評価と解決方法を理解するには、URL の評価と解決方法を参照してください。

URL 内の大文字と小文字に違いがある場合でも、URL を解決することが可能です。

B2C Commerce で自動的にエンコードされるため、エンコードされていない次の文字が URL に含まれている場合でも、URL を解決することが可能です: 

, @ ) ! $ ' ( ~

URL 構文では、読みやすさを目的とした場合のみ空白を使用できます。ルール要素の前後で空白を使用しなくても、URL ルールの検証に影響はありません。ただし、要素を区切るためのコンマは重要です。コンマを使用しない場合は、ルールの検証に影響を与えます。

URL ルールを定義する場合、属性のソースを指定する際にコンテキストを考慮する必要があります。カテゴリルールの場合、ソースはカテゴリなので、以下のようなルールを使用します:

[ [ constant, const ], /, [ category-path, [ attribute, ID ], - ]]

このルールでは、各 URL で使用される定数とカテゴリパスを定義します。このルールの 属性 は、カテゴリ の属性、つまりカテゴリ ID となります。

ただし、商品ルールでは、ソースは商品であるため、以下のルールのように、カテゴリをカテゴリパスのソースとして宣言します:

[ [ constant, const ], /, [ category, [ category-path, [ attribute, ID ], - ] ]]

以下の商品ルールを定義する場合は、定数 const111 が適用され、カテゴリルールで指定した通りにカテゴリが適用されます。

[ [ constant, const111 ], /, [ category] ]

カテゴリの使用はいずれもカテゴリルールで定義された通りになるため、商品ルールを定義する際は注意が必要です。たとえば、カテゴリ ルールが /const222/electronics/ になるように指定した場合、[ [ constant, const111 ], /, [ category] ] を使用して商品ルールを定義します。その結果、以下の通りになります:

/const111/const222/electronics/008884303996.html

複数の値をもつ属性

SEO ルールを構成して、商品、コンテンツ、カテゴリ、フォルダーの URL を生成する場合は、単一値属性と同様の方法で、Enum-of-StringタイプとSet-of-Stringタイプを使用して、複数の値をもつ属性を指定します。以下の例では、color が Enum-of-String 商品属性です。

[ [ category, [ attribute, displayName ] ], /, [ attribute, custom.color], /, [ attribute, name ] ]

複数の値をもつ属性の値はすべて URL に含まれます。値は、空白、または空白の代わりに定義された文字 (‘-‘ など) で連結されます。表示値が定義されていない場合、Enum (列挙型) の値にはローカライズされた表示値が使用されますが、それ以外の場合は表示値が使用されます。

前述のルールに基づいて生成された URL の例は、次のとおりです。

/mens-shoes/black-yellow/spring-sneaker/12345.html

カテゴリ URL

URL ルールのサイト URL は、カテゴリページで有効にすることができ、マーチャントはカテゴリ URL のエンドポイントを URL ルールページのカタログ URL タブで構成できます。

すべての SEO モジュールが無効になっている場合、標準の B2C Commerce カテゴリ URL は次の形式になります: 

www.sitegenesis.com/on/demandware.store/Sites-SiteGenesis-Site/default/Search-Show?cgid=mens-clothing-shorts

廃止予定の SEO モジュールが有効になっている場合、カテゴリ URL は次の形式になります: 

www.sitegenesis.com/mens-clothing-shorts,default,sc.html

URL ルールモジュールが有効になっている場合、カテゴリ URL は次の形式になります: 

[ category-path, [ attribute, displayName ], - ]

このルールでは、カテゴリのカテゴリパスと表示名を、カテゴリ名の空白をダッシュ区切りで代用して表示します: 

www.sitegenesis.com/mens-clothing-shorts

カテゴリ URL のコンテンツを定義するには、複数の要素を組み合わせ、要素間の区切り文字を指定します。

[ [attribute_1], del , [attribute2], del , [attribute_3] ]

ルールには最大 5 つの要素を含めることができます。カテゴリ要素には、attribute (属性)、constant (定数)、category-path (カテゴリパス)、category-parent (上位カテゴリ) の 4 つのタイプがあります。 (各要素の仕様については以下を参照してください。)

例: 

[ [constant, shop], / , [category-path, [attribute, ID], -] ]
www.sitegenesis.com/shop/mens-clothing-shorts/

URL から特定のカテゴリやフォルダーを除外したい場合は、パス除外カテゴリ構文を使用します。

簡単な構文の例は次のとおりです: 

[ category-path, [attribute, displayName], /, [3,4]]

「Brand > sale > men > shoes > leather」のカテゴリツリーを作成し、URL を次のように表示します

www.sitegenesis.com/brand/sale/leather

この構文は、次の URL ルール属性の設定で使用できます。

  • category-path (カテゴリパス)
  • category-path-with-offline (オフラインのカテゴリパス)
  • folder-path (フォルダーパス)
  • folder-path-with-offline (オフラインのフォルダーパス)

カテゴリ URL の定義には、以下の構成オプションを利用できます:

オプション 定義
attribute (属性)

この要素は、ID、名前、カスタム属性など、カテゴリまたはフォルダーの属性を含めるために使用します。デフォルト値を定義することができ、属性または属性値がカテゴリに定義されていない場合に使用できます。デフォルト値が指定されていない場合、パラメーターは URL で省略されます。

[ attribute, custom.categoryURL ]
www.sitegenesis.com/mens-shorts
[ [category-path, -], / , [attribute, custom.url_param] ] 
www.sitegenesis.com/mens-clothing-shorts/custom
category-parent (上位カテゴリ)

この要素は、カテゴリとその直接の上位カテゴリの名前またはその他の属性を含めるために使用します。属性と区切り文字を指定します。

[ category-parent, [attribute, ID], - ]
www.sitegenesis.com/clothing-shorts
[ category-parent, [attribute, displayName], / ]
www.sitegenesis.com/clothing/shorts

www.sitegenesis.com/sale/clothing-shorts
[ category-parent-with-offline, [attribute, displayName], / ]
www.sitegenesis.com/sale/clothing/shorts

[ category-path, [attribute, ID], - ]
www.sitegenesis.com/mens-clothing-shorts
[ category-path, [attribute, displayName], / ]
www.sitegenesis.com/mens/clothing/shorts
[ category-path, [attribute, custom.customURLName], + ]

www.sitegenesis.com/mens/shorts

[ category-path-with-offline, [attribute, ID], - ]
www.sitegenesis.com/sale/mens-clothing-shorts
[ category-path-with-offline, [attribute, displayName], / ]

[ category-path-with-offline, [attribute, custom.customURLName], + ]
www.sitegenesis.com/sale/mens+clothing+shorts

この要素は任意のテキスト要素を含めるために使用されます。

[ folder-parent-with-offline, [ attribute, displayName ], / ]
folder-path (フォルダーパス)

この要素タイプは、フォルダーの名前またはその他の属性を含めるために使用します。属性と区切り文字を指定します。

[ folder-path, [ attribute, displayName ], / ]

[ folder-path, [ attribute, displayName ], /, [2]]

[ folder-path-with-offline, [ attribute, displayName ], / ]

[ folder-path-with-offline, [ attribute, displayName ], /,[2]]
www.sitegenesis.com/mens/shorts

URL ルールページのカタログ URL タブで、カテゴリ URL の最後に任意でスラッシュを付加できるよう設定できます。 

www.sitegenesis.com/mens-shorts (最後のスラッシュがオフの場合)
www.sitegenesis.com/mens-shorts/ (最後のスラッシュがオンの場合)

サイトがローカライズ済みの場合、各地域情報別に異なる URL が存在します。以下がその例です:

www.sitegenesis.com/en/mens-clothing-shorts
www.sitegenesis.com/de/herren-kleidung-shorts

URL ルールページの設定タブで、URL の地域情報を指定する方法を制御します。グローバル環境設定の地域情報ページで、サイトがローカライズ済みかどうかを設定します。

カテゴリパスを使用するルールの URL 生成の動作では、通常、オフラインカテゴリが省略され、実際には競合が発生していない場合でも、カテゴリに競合しているというフラグが付けられることがあります。これは、マーチャントがカテゴリを特定のイベントまでオフラインにしておく必要がある場合に発生する可能性があります。一般的には、各イベント関連のカテゴリ内では、サブカテゴリ名の標準の構造が使用されます。たとえば、MothersDay/sale (母の日/セール)、ValentinesDay/sale (バレンタインデー/セール)、Easter/sale (イースター/セール) などです。

例:

  • カテゴリ A (オフライン) にサブカテゴリ a-sale があり、表示名は SALE だとします。カテゴリ A がオンラインに変更されると、a-sale カテゴリは URL a/sale をもちます。
  • カテゴリ B (オフライン) にはサブカテゴリ b-sale があり、表示名は SALE だとします。カテゴリ B がオンラインに変更されると、b-sale カテゴリは URL b/sale をもちます。

A と B は両方ともオフラインであるため、a-sale と b-sale の URL saleは同じです。これによって URL の競合のログに混乱が起こり、誤って競合が発生していると判断され、実際の URL の競合を特定するのが困難になります。

次の例に示すように、オフラインのカテゴリ/フォルダーから情報を取得するルールを定義します。 

[ category-path-with-offline, [ attribute, displayName ], / ]
[ category-parent-with-offline, [ attribute, displayName ], / ]
[ folder-path-with-offline, [ attribute, displayName ], / ]
[ folder-parent-with-offline, [ attribute, displayName ], / ]

たとえば、sale カテゴリはオフラインで、カテゴリの分類は次のようになります。

host.com/sale/mens
host.com/mens

オフラインカテゴリが認識されると、競合とみなされることはなくなり、URL の競合を解決する必要はありません。

host.com/sale/mens
host.com/mens

オフラインカテゴリが認識されない と、競合が検出され、URL の競合の解決で対応することができます。 

host.com/mens-1
host.com/mens-2

B2C Commerce では、カテゴリ URL ルールに基いて、自動でカテゴリ URL が生成されます。また、カテゴリの URL エンドポイントを定義することもできます。

たとえば、

[ attribute, displayName ]

というルールでは、Mens | Clothing | Sales と Womens | Clothing | Sales の Sales カテゴリで競合が発生し、URL ジェネレーターによって生成された URL の後に自動的にインデックス番号が追加されます。生成されたMens | Clothing | SalesまたはWoens | Clothing | Salesの URL を上書きします。この場合、ルールによって生成されたエンドポイントではなく、カテゴリの PageURL 属性がエンドポイントとして使用されます。

  • Mens | Clothing | Sales の URL には、www.sitegenesis.com/sales-1 が生成されます
  • Womens | Clothing | Sales の URL には、www.sitegenesis.com/sales-2 が生成されます

例 1: メンズセール

Mens | Clothing | Sales の URL が、以下のように生成されると想定します: 

www.sitegenesis.com/sales-1

しかし、Mens | Clothing | Sales カテゴリの PageURL 属性を mens-sales に設定した場合、Mens | Clothing | Sales の実際の URL は以下のようになります: 

www.sitegenesis.com/mens-sales

例 2: レディースセール

Womens | Clothing | Sales の URL が、以下のように生成されると想定します: 

www.sitegenesis.com/sales-2

しかし、Womens | Clothing | Sales カテゴリの PageURL 属性を womens-sales に設定した場合、Womens | Clothing | Sales の実際の URL は以下のようになります: 

www.sitegenesis.com/womens-sales

商品 URL

商品ページの URL を有効に設定することができます。商品 URL のエンドポイントは、単純なルール構文に基づいて構成されます。

商品 URL は、Business Manager の環境設定で有効にし、URL ルールページのカタログ URL タブで構成します。以下の例では、商品 URL に、カテゴリ、名前、商品 ID が含まれています。商品 ID は必須であり、拡張子 .html とともに各商品 URL に付加されます。

URL ルール:

 [ [category], /, [ attribute, name ] ]

URL の例: 

www.sitegenesis.com/mens-clothing-shorts/straight-fit-shorts/8353682.html

商品 ID の前の区切り文字は、'/' または '-' に構成することができます。区切り文字が '-' に設定されているが、商品名にも '-' が含まれる場合は、この商品の URL には自動的に区切り文字 '/' が使用されます ( www.sitegenesis.com/crowne-shorts-brown-83536828.html ではなく、www.sitegenesis.com/crowne-shorts-brown/83536828.html)。

商品 URL のコンテンツを定義するには、複数の要素を組み合わせ、要素間の区切り文字を指定します。

[ [attribute_1], del , [attribute2], del , [attribute_3] ]

ルールには最大 5 つの要素を含めることができます。要素には、attribute (属性) と category (カテゴリ) の 2 種類があります。

商品 URL のエンドポイントの定義には、以下の構成オプションを利用できます:

オプション 定義
category (カテゴリ)

例 :

[ ]
www.sitegenesis.com/83536828.html

以下のルールでは、商品 ID セパレーターとして '/' の代わりに '-' を使用する ボックスにチェックを入れます。

[ [category], - , [attribute, name] ]
www.sitegenesis.com/shop/mens-clothing-shorts-beach-shorts-83536828.html

このボックスにチェックが入っていないと、以下のように表示されます。

www.sitegenesis.com/shop/mens-clothing-shorts-beach-shorts/83536828.html
attribute (属性)

この要素はカテゴリ情報を含めるために使用します。これは、カテゴリ URL ジェネレーターによって生成されたカテゴリ URL の例 (前セクションを参照) です。このルールは、URL がカテゴリのコンテキストで商品を表示する場合に使用する必要があります。

[category]
www.sitegenesis.com/mens+clothing+shorts/83536828.html

カテゴリの表示名です。

[ [category, [attribute, displayName]] ]
www.sitegenesis.com/shorts/83536828.html

カテゴリの URL 名とカテゴリの追加カスタム属性。

[ [category], / , [category, [attribute, customAttr] ]
www.sitegenesis.com/mens+clothing+shorts/custom-cat-value/83536828.html
constant (定数)

この要素は任意のテキスト要素を含めるために使用されます。

[ constant, cat ]
www.sitegenesis.com/cat/83536828.html

カテゴリと定数要素を一緒に使用することもできます。

[ [ constant, cat ], /, [category] ]
www.sitegenesis.com/cat/shorts/83536828.html

B2C Commerce では、以下のロジックを使用して URL のカテゴリが決定します:

  1. ストアフロントカタログ内のその商品の主要カテゴリを使用。

    商品に主要カテゴリが割り当てられていない場合、またはストアフロントカタログに主要カテゴリが存在しない場合は、次のステップに進みます。

  2. ストアフロントカタログ内のその商品の分類カテゴリを使用。

    商品に分類カテゴリが割り当てられていない場合、またはストアフロントカタログに分類カテゴリが存在しない場合は、次のステップに進みます。

  3. ストアフロントカタログ内のカテゴリのうち、1 番最初にその商品に割り当てられたカテゴリを使用。サイト内で商品を使用可能にするには、ストアフロントカタログ内の少なくとも 1 つのカテゴリに商品を割り当てる必要があります。

カテゴリ URL と同様、URL ジェネレーターによって生成された商品 URL を上書きするには、PageURL 属性を使用します。

生成された商品 URL : www.sitegenesis.com/sports-shoe-red/1234.html

商品の PageURL 属性: mckenzie-sports-shoe

コンテンツ URL およびフォルダー URL

フォルダーとコンテンツアセットの URL 定義や生成も、カテゴリや商品と同じように機能します。フォルダーおよびコンテンツ URL ルールの例については、Business Manager の URL ルールページのコンテンツ URL ページを参照してください。

メモ フォルダーは通常、ランディングページを持たず、ストアフロント内の他のページの一部としてレンダリングもされることもありません。ただし、URL 構文を指定した場合、生成される URL はカテゴリ URL と競合する可能性があります。たとえば、ギフトレジストリまたはセールの場合などです。このため、フォルダーの URL 構文を指定しない方がよい場合があります。これはコンテンツアセットには当てはまらないため、Salesforce では、コンテンツアセット URL を最適化することをお勧めします。

パイプラインのエイリアス

商品、カテゴリ、コンテンツページを除くページ URL にはすべて、パイプラインが表示されます。パイプラインページで/on/demandware.storeを含まない URL を作成するには、パイプライン名を Business Manager のエイリアスにマッピングします。パイプラインページの URL は以下のようになります: 

www.sitegenesis.com/on/demandware.store/Sites-SiteGenesis-Site/default/Account-Show www.sitegenesis.com/on/demandware.store/Sites-SiteGenesis-Site/default/Search-Show?q=shoes

Business Manager、パイプラインのマッピングを定義します。

URL パイプライン
アカウント Account-Show
検索 Search-Show
ほしい物リスト Wishlist-Show

新しい URL を有効にして、パイプラインにマッピングを定義すると、URL は以下の形式に変わります: 

www.sitegenesis.com/account
www.sitegenesis.com/search?q=shoes

地域情報

地域情報/言語の識別子をすべてのストアフロント URL で表示するかどうか、またどのように表示するかを制御するには、地域情報オプションを選択します。(なし、ホスト名、クエリ文字列、またはパス)。

なしオプションは、サイトの表示言語が 1 つだけの場合に使用します。受信 URL で言語識別子の検査が行われることはありません。すべてのページがサイトのデフォルト地域情報で配信されます。B2C Commerce では使用可能なサイトの地域情報数が 1 つだけであると想定していますが、複数ある場合はデフォルトの地域情報が使用されます。生成された URL には、地域情報識別子が含まれていません。

www.example.com/mens

ホスト名では、表示言語は受信 URL のホスト名を検査することにより判断されます。ホスト名とサイト地域情報の間のマッピングを構成します (例: de.example.com - de_DE、www.example.com - en_US、es.example.com - es_US)。1 つの地域情報に複数のホスト名をマッピングすることができます。ホスト名にマッピングが存在しない場合は、デフォルトのサイト地域情報でページが配信されます。

www.example.com/mens
de.example.com/mens

URL パラメーターでは、表示言語は受信 URL の標準 URL パラメーターを検査することにより判断されます。デフォルトのパラメーター名は "locale"、?locale=en-USで、システムでは "lang" などの別のクエリ文字列パラメーター名を指定できます。カスタム文字列の言語コードからサイトの地域情報へのマッピングを構成します (デフォルト <> en_US、es <> es_US など)。マッピングが存在しない場合は、地域情報 ID が指定されているものと見なされます。地域情報 ID が、使用可能なサイト地域情報と一致しない場合、デフォルトのサイト地域情報を使用してページが配信されます。生成された URL は、接頭辞が有効な場合に受信 URL と同じ URL パラメーターを含み、接頭辞が無効な場合は、デフォルトのサイト地域情報で定義された接頭辞を含みます。URL パラメーターの名前を定義します。

www.example.com/mens?locale=en-US
de.example.com/mens?lang=en
www.example.com/mens?lang=spanish

パスでは、表示言語は URL パス内の最初の要素を検査することにより判断されます。たとえば、default <> en_US、en <> en_US など、URL 言語コードのマッピングをサイト地域情報に構成できます。マッピングが存在しない場合は、URL に地域情報 ID が指定されているものと見なされます。地域情報 ID が、使用可能なサイト地域情報と一致しない場合、デフォルトのサイト地域情報を使用してページが配信されます。

www.example.com/de/mens
www.example.com/en/mens

二重パスの地域情報を定義するには、最初の値、'/' 文字、2 番目の値の順に指定します。たとえば、en/US または de/DE を指定すると、以下のようになります: 

www.example.com/en/US/mens
www.example.com/de/DE/mens
メモ 二重パスを使用する場合、URL パラメータータイプの地域情報マッピングに '/' を使用できません。SEO URL の設定タブの使用を参照してください。

B2C Commerce の URL 構文

Salesforce B2C Commerce でのストアフロント URL の表示方法を、3 種類の URL 構文で定義します。

以下を考慮します。

使用するモジュール 参照する手順 使用する構文
URL ルールモジュール SEO URL の構成 URL ルールの構文
廃止予定の SEO サポートモジュール (URL ルールの環境設定の選択を解除) 検索しやすい URL の構成 SEO サポートの URL 構文
URL 構文を指定しない   B2C Commerce の標準の URL 構文
メモ リリース 13.1 より前のバージョンでは、ストアフロント URL の設定には、SEO サポートモジュールが使用されていました。このモジュールは現時点でも互換性のために提供されていますが、廃止予定であるため新規顧客向けにはお勧めできません。

使用する構文は、どの Business Manager モジュールが有効に設定されているかによって異なります。URL ルール と SEO サポート の両方を有効にすることはできません。Salesforce では、よりフレキシブルに構成できる URL ルールモジュールの使用をお勧めします。

B2C Commerce 向け Adyen 支払の検証

B2C Commerce インスタンスのテストまたはライブの Adyen マーチャントアカウントで、テスト支払を設定して検証します。B2C Commerce インスタンスに関連付けられている Adyen マーチャントアカウントを使用して、テスト支払を作成します。

必要なエディション

  • テストマーチャントアカウント: 実際の承認やキャプチャを使用しません。テスト用のカードと銀行口座を使用します。
  • ライブマーチャントアカウント: クレジットカードと銀行口座に対して実際の承認とキャプチャを使用します。有効なクレジットカードと銀行口座のみを使用します。
使用可能なソリューション: B2C Commerce

Adyen マーチャントアカウントを B2C Commerce インスタンスに関連付けます。Adyen マーチャントアカウントの B2C Commerce への関連付けを参照してください。

  1. Business Manager からストアフロントに移動します。
  2. 買い物カゴに商品を追加します。
  3. 複数ステップチェックアウト、「今すぐ支払う」、または「今すぐ購入」(Chrome または Android では Google Pay、Safari または IOS では Apple Pay) を使用してチェックアウトします。

ストアフロントまたは Adyen Customer Area から注文を表示し、Salesforce Payments が Adyen 処理業者を使用して支払を処理したことを確認します。注文に Adyen 支払サービスプロバイダー (PSP) の参照が一覧表示されます。

B2C Commerce 向け Stripe 支払の検証

B2C Commerce インスタンスのテストまたはライブの Stripe マーチャントアカウントで、テスト支払を設定して検証します。B2C Commerce インスタンスに関連付けられている Stripe マーチャントアカウントを使用して、テスト支払を作成します。

必要なエディション

  • テストモード: 実際の承認やキャプチャを使用しません。テスト用のカードと銀行口座を使用します。
  • ライブモード: クレジットカードと銀行口座に対して実際の承認とキャプチャを使用します。有効なクレジットカードと銀行口座のみを使用します。
使用可能なソリューション: B2C Commerce

Stripe マーチャントアカウントを B2C Commerce インスタンスに関連付け、アカウントのオンボーディングを完了します。Stripe マーチャントアカウントの B2C Commerce への関連付けおよびB2C Commerce の Stripe マーチャントアカウントの設定を参照してください。

  1. Business Manager からストアフロントに移動します。
  2. 買い物カゴに商品を追加します。
  3. 複数ステップチェックアウト、「今すぐ支払う」、または「今すぐ購入」(Chrome または Android では Google Pay、Safari または IOS では Apple Pay) を使用してチェックアウトします。

ストアフロントまたは Stripe Dashboard から注文を表示し、Salesforce Payments が Stripe 処理業者を使用して支払を処理したことを確認します。注文に Stripe Payment Intent (支払意思) ID がリストされます。

B2C Commerce でのほしい物リストまたは注文ステータスオブジェクトのインポート/エクスポート

ほしい物リストオブジェクトや注文ステータスオブジェクトのインポートのサポートは組み込まれていません。ただし、独自の XML 形式を作成し、B2C Commerce スクリプトまたはパイプレットを使用してしてこれらのオブジェクトを更新できます。

ほしい物リストは商品リストとしてエクスポートできます。

B2C Commerce の Omnichannel Inventory の継続的な注文獲得

継続的な注文キャプチャをオンにすると、顧客の注文を受け付け、Omnichannel Inventory への接続が失われた場合でもビジネス継続性を維持できます。サービスが利用できない場合、Continuous Order Capture は自動的にオフライン モードに移行し、即時在庫の予約なしでトランザクションを受け入れます。この機能は、保留中の予約を個別に調整し、リアルタイムの復旧アラートを提供することで、過剰販売のリスクを最小限に抑えながら、ストアフロントをダウンタイムから保護します。

Continuous Order Capture は、Omnichannel Inventory サービスのリアルタイムモニタリングを提供します。中断が発生した場合、システムは次の手順で継続性を維持します。

  • 自動的にオフラインモードに切り替わり、最新の在庫データに基づいて注文を受け付けます。
  • 過剰販売を防ぐために、各注文後に注文可能数量 (ATO) の値を減らします。
  • 注文を予約欠落としてマークします。バックグラウンド ジョブでは、オフライン注文が処理され、在庫が予約され、過剰販売が報告され、成功すると予約が欠落している状態が削除されます。
  • Salesforce Order Management で構成されたシステムでは、Omnichannel Inventory が復旧して在庫が調整されるまで、B2C Commerce は注文が Salesforce Order Management に流れないように保留します。
