B2C Commerce の WebDAV ファイルへのアクセス

Business Manager のフォルダーブラウザーを使用すると、WebDAV ファイルを簡単に表示してダウンロードできます。また、サードパーティの WebDAV クライアントを使用して、WebDAV ファイルを表示、ダウンロード、アップロード、削除できます。

必要なエディション

使用可能なソリューション: B2C Commerce
  1. Business Managerm で、アプリケーションランチャーをクリックし、次に管理 | サイトの開発 | 開発セットアップの順に選択します。
  2. フォルダーブラウザータブをクリックします。
    WebDAV の許可をもつフォルダーがフォルダーブラウザーに表示されます。
    • フォルダーをフィルターするには、名前でフィルターテキストボックスにフォルダー名を入力し、フィルターをクリックします。フォルダー名では大文字と小文字は区別されません。アスタリスク (*) と疑問符 (?) をワイルドカードとして使用できます。
    • ファイルをダウンロードするには、操作の下でダウンロードアイコンをクリックします。
    • ディレクトリの URL をローカルマシンのクリップボードにコピーするには、WebDAV URL をコピーをクリックします。この URL を使用して、サードパーティの WebDAV クライアントでディレクトリにアクセスします。
  3. サードパーティの WebDAV クライアントを使用してディレクトリにアクセスするには、開発セットアップウィンドウで次のように操作します。
    1. WebDAV アクセスセクションまでスクロールダウンします。
    2. ディレクトリ名の横にあるリンクアイコンをクリックして、URL をローカルマシンのクリップボードにコピーします。WebDAV クライアントに URL を貼り付けます。
      WebDAV クライアントから WebDAV ファイルにアクセスするには、WebDAV の認証情報を入力します。
    フォルダーブラウザーを使用してディレクトリを表示するには、WebDAV アクセスセクションでディレクトリ名の横にあるフォルダーアイコンをクリックします。

グリッド表示での商品バリアント情報へのアクセス

マスター商品のバリアント表示を使用して、バリアント商品の在庫レベル、属性、および価格設定を確認できます。その後、グリッド表示と商品詳細リストを切り替えることなしに、戦略的にバリアント商品を配置して販売を促進できます。このトピックは、B2C Commerce に該当します。

必要なエディション

使用可能なソリューション: B2C Commerce
メモ バリアントの表示オプションは、マスター商品タイルでのみ使用できます。
  1. アプリケーションランチャーをクリックし、次にマーチャントツール | サイト | 商品とカタログ | カタログの順に選択します。
  2. 編集したいカタログカテゴリを選択します。
  3. 商品リストで、グリッド表示アイコンをクリックします。
  4. 目的のマスター商品タイルでドロップダウンをクリックし、バリアントの表示を選択します。
  5. マスター商品のバリアントの在庫レベル、属性、および価格設定を確認します。
  6. バリアントの表示ツールを使用して結果を絞り込みます。
    1. 特定の商品を見つけて表示するには、商品 ID を入力します。
    2. 在庫ありステータスと商品属性の組み合わせに基づいて商品バリアントを表示するには、テーブルフィルターを使用します。
    3. 販売可能在庫の降順または昇順で商品リストを並べ替えるには、販売可能数量 (ATS)列をクリックします。

eCDN ゾーンへの SSL 証明書の追加と DNS マッピングの構成

ゾーンのホスト名に SSL 証明書を追加し、B2C Commerce から DNS プロバイダーアカウントに DNS の値をマッピングします。eCDN 管理証明書と自己管理証明書を追加します。

エンドポイントをマッピングする際には、以下を念頭に置いてください。

  • DNS Request for Comments (RFC) では、ルートドメインを B2C Commerce に直接ポイントすることはできません。ルートドメインを eCDN CNAME エイリアスにダイレクトする場合は、外部サービスを使用してルートドメインからサブドメインにリダイレクトする必要があります。
  • リダイレクトを設定する際には、必ず HTTP と HTTPS の両方に設定します。
  • トラフィックをサブドメイン (www.yourcompany.com) ではなく永久にルートドメイン (yourcompany.com) から供給するには、DNS レベルのソリューションを使用して、ルートドメインを eCDN CNAME エイリアスにダイレクトします。
  • レガシーゾーンとプロキシゾーンには、有効な SSL 証明書が必要です。
  • 管理 SSL 証明書の追加
    ゾーンのホスト名に eCDN 管理 SSL 証明書を追加して、起点のエンドポイントをマッピングします。
  • 自己管理 SSL 証明書の追加

管理 SSL 証明書の追加

ゾーンのホスト名に eCDN 管理 SSL 証明書を追加して、起点のエンドポイントをマッピングします。

必要なエディション

使用可能なソリューション: B2C Commerce

管理 SSL 証明書をホスト名に追加し、B2C Commerce から DNS プロバイダーアカウントに DNS の値をマッピングするには、次のようにします。

エンドポイントをマッピングする際には、以下を念頭に置いてください。

  • DNS Request for Comments (RFC) では、ルートドメインを B2C Commerce に直接ポイントすることはできません。ルートドメインを eCDN CNAME エイリアスにダイレクトする場合は、外部サービスを使用してルートドメインからサブドメインにリダイレクトする必要があります。
  • リダイレクトを設定する際には、必ず HTTP と HTTPS の両方に設定してください。
  • トラフィックをサブドメイン (www.yourcompany.com) ではなく永久にルートドメイン (yourcompany.com) から供給するには、DNS レベルのソリューションを使用して、ルートドメインを eCDN CNAME エイリアスにダイレクトします。
  1. アプリケーションランチャーをクリックし、管理 | サイト | 埋め込み CDN 設定の順に選択します。
  2. 証明書を追加するゾーンの証明書または設定をクリックします。
  3. 暗号化タブで、リストからゾーンを選択します。
  4. 証明書の追加をクリックします。
  5. eCDN 管理証明書を選択します。

  6. 「SSL 認証局」ドロップダウンから、Lets Encrypt または Google (推奨) を選択します。
  7. 「SSL 証明書検証メソッド」ドロップダウンから、HTTP 検証または TXT 検証を選択します。
    • HTTP 検証
      • スタック構成の CDN を使用しない場合に、このオプションを使用します。
      • eCDN を使用してスタック構成を実装する場合、サードパーティーの CDN をスタックするときに HTTP 検証がブロックされないことに注意してください。検証プロセスを円滑に実行し続けるには、ACME (Automatic Certificate Management Environment) 準拠の認証局 (CA) のドメイン名の利用権確認 (DCV) HTTP パスを許可します。Let's Encryptのドキュメントによると、許可するHTTPパスは http://<YOUR_DOMAIN>/.well-known/acme-challenge/<TOKEN>です。
    • TXT 検証
      • スタック型 CDN と DCV デリゲーションを使用する場合に、このオプションを使用します。スタック型 CDN を使用する場合、DCV デリゲーションが必要です。
      • DCV の汎用一意識別子 (UUID) が必要な場合は、サポートチームに連絡して、DNS レコードに含める DCV 委任 UUID を取得してください。
      • DCV デリゲーションを使用しない場合:
        • 証明書の自動ローテーションにより、3 か月ごとに TXT レコードを検証します。
        • TXT 検証用に eCDN 管理証明書を構成した場合でも、証明書の更新中に HTTP 検証が試行されます。前の項目で説明した DCV 用 HTTP パスの検証を許可してください。
  8. SSL 証明書を割り当てたいホスト名を選択します。
  9. 証明書のアップロードをクリックします。
  10. (オプション) HTTP で検証します。
    1. 表示される検証テキストを自分の DNS ポータルにコピーします。

    2. ホスト名検証のステータスを確認するには、ホスト名の検証をクリックします。この検証には最大で 6 時間かかります。
    3. ホスト名がアクティブになったときに、SSL for SaaS V2 経由でトラフィックを新しいゾーンに導く CNAME レコードを作成します。
    4. ゾーン用に DNS マッピングを構成します。
      1. DNS プロバイダーアカウントにログインします。
      2. ゾーンを検索し、リストから選択します。
      3. DNS タブで、マッピングするホスト名を見つけます。
      4. “is an alias of” (は次のエイリアス: ) の後のすべてのテキストを、Business Manager からの DNS CNAME に置き換えます。
      5. ステータス列のクラウドを、ツールヒント「DNS のみ」をもつグレーのクラウドとして表示されるまでクリックします。
    5. 証明書検証のステータスを確認するには、eCDN 管理証明書の検証をクリックします。検証には最大で 6 時間かかります。
  11. (オプション) TXT で検証します。
    1. 表示される証明書とホスト名の検証テキストを自分の DNS ポータルにコピーします。

    2. ホスト名検証のステータスを確認するには、ホスト名の検証をクリックします。この検証には最大で 6 時間かかります。
    3. ホスト名がアクティブなときに、証明書検証のステータスを確認するには、「eCDN 管理証明書の検証」をクリックします。検証には最大で 6 時間かかります。
    4. ホスト名と証明書がアクティブになったときに、SSL for SaaS V2 経由でトラフィックを新しいゾーンに導く CNAME レコードを作成します。
    5. ゾーン用に DNS マッピングを構成します。
      1. DNS プロバイダーアカウントにログインします。
      2. ゾーンを検索し、リストから選択します。
      3. DNS タブで、マッピングするホスト名を見つけます。
      4. “is an alias of” (は次のエイリアス: ) の後のすべてのテキストを、Business Manager からの DNS CNAME に置き換えます。
      5. ステータス列のクラウドを、ツールヒント「DNS のみ」をもつグレーのクラウドとして表示されるまでクリックします。

使用可能なソリューション: B2C Commerce
重要 この方法は、すべての DDoS コンポーネントと WAF コンポーネントをバイパスするため、お勧めしません。特定のサードパーティアドレスの WAF、その他のカスタムルール、またはレート制限を選択的にスキップするには、eCDN カスタムルールを使用します。

  2. ゾーンで設定をクリックします。
  3. ファイアウォールタブで、信頼できる IP 許可リストを追加または編集して、サードパーティのプロキシ IP アドレスを含めます。

B2C Commerce の管理者の役割

管理者の役割は、組織の最上位の役割です。この役割は自動的に作成され、直接、またはインポートによって間接的に削除することはできません。このトピックは、B2C Commerce に該当します。

管理者の役割には、次のプロパティがあります:

  • 新しいインスタンスでは常に使用可能です。
  • B2C Commerce ツールやインポートを使用して削除できません。
  • 組織のすべての既知のサイトにあるすべての既知のシステムモジュールへのアクセス許可をもちます。
  • 新しく作成されたサイトのすべてのシステムモジュールへのアクセス許可を自動的に取得します。
  • (すべての組織とサイトについて) 新しいリリースをデプロイする場合、新しいモジュールへのアクセス許可を自動的に取得します。
  • 機能の許可を使用して拡張できます。
  • カスタムモジュールのアクセス許可を使用して拡張できます。
  • すべての役割に割り当てられたすべての地域情報への許可にアクセスできます。リリース 16.9 より後に作成した地域情報では、管理者は地域情報に特定の許可を関連する役割に明示的に付与する必要があります。

すべてのシステムモジュールへの管理者アクセスは、次のメカニズムで徹底されます:

  • 新しいサイトを作成すると、管理者の役割はすべてのサイトシステムモジュールへのアクセス許可を自動的に受け取ります。管理者の役割は、すべてのサイト内のすべてのモジュールへのフルアクセスを維持します。
  • サーバーの起動時には、組織レベルおよびサイトレベルの管理者の役割が、すべてのサイトのすべての既知のシステムモジュールへのアクセス許可をもっているかどうかがチェックされます。管理者の役割は、新しく導入されたシステムモジュールへのアクセス許可を自動的に取得します (たとえば、新規リリースをデプロイする場合)。

パスワードの回復

全インスタンスのパスワードに責任をもつ管理者を 1 人任命することをすべての顧客およびパートナーにお勧めします。この管理者は通常、各新規インスタンスに含まれるデフォルトの Admin ユーザーアカウントです。Admin ユーザーは、他のアカウントを作成して名前を付け、同様の管理者許可をもたせることができます。

デベロッパーは独自のアカウントを使用してインスタンスにアクセスし、グローバル管理者のパスワードを変更またはリセットすることはありません。dbinit を Sandox (サンドボックス) インスタンス上で実行した後、管理者は Sandox (サンドボックス) のパスワードをオリジナルのパスワードに戻す責任があります。

セキュリティ設定では、管理者が Business Manager のパスワードの動作を構成できます。パスワードを忘れた場合、管理者はパスワードを忘れましたか 機能を使用してパスワードを取得するか、リセットできます。

メモ Salesforce サポートでは、admin アカウントのメイン管理者パスワードのみがリセットされます。Admin ユーザーとしてログインしたユーザーのみが、管理者の許可をもつ他のアカウントをリセットできます。

インポートとエクスポート

管理者の役割を削除しようとすると (たとえば、削除モードのインポートを使用した場合)、インポートロジックによって拒否されます。システムモジュールのアクセス権限を変更しようとした場合 (たとえば、置換モードのインポートを使用) も、インポートロジックによって拒否されます。インポートログには、両方のケースが警告として記録されます。

Business Manager のモジュールの許可

モジュールの許可を使用して、特定の Business Manager モジュールへのアクセスを付与します。ログインしているユーザーが Business Manager モジュールへのアクセス許可を持っている場合、アプリケーションが左側のナビゲーションペインに表示されます。

特定のモジュールと環境設定に読み取り専用許可を付与します。読み取り専用許可をもつユーザーは、環境設定とモジュールを表示できますが、編集はできません。読み取り専用許可は、顧客、商品、商品セット、グローバルカスタム環境設定、コンテンツアセット、顧客、在庫リスト、ジョブ履歴、ライブラリ、ライブラリフォルダー、注文、価格表、商品、商品セット、サイト環境設定、およびバリエーション属性の各モジュールで使用できます。書き込みアクセスを有効にすると、読み取りアクセスも有効になります。

また、すべてのサイト固有の環境設定において、Business Manager モジュールへの読み取り専用許可を付与できます。これらの環境設定には、ロック、買い物カゴ、A/B テスト、地域情報、通貨、ソースコード、ギフト券、誘導検索、シーケンス番号、注文、クーポン、プロモーション、Storefront Toolkit、ストアフロント URL、システムオブジェクトの定義、およびカスタム環境設定が含まれます。

Business Manager モジュールにサイト固有の機能がある場合、許可の対象は、特定のサイトのコンテキスト内、または組織全体になります。たとえば、注文はサイトの中で管理されるため、注文モジュールの許可の対象はサイトになります。

Business Manager の地域情報の許可

Business Manager はビジネスオブジェクトのローカライゼーションをサポートしています。地域情報のデータにアクセスできるユーザーを指定します。

ユーザーに地域情報へのアクセスを付与するには、まず役割と許可のページの地域情報タブを使用して役割を作成します。この役割をユーザーに割り当てます。書き込みアクセスを有効にすると、読み取りアクセスも有効になります。各役割には、少なくともデフォルトの地域情報の読み取り許可が必要なので、読み取り許可は自動的に割り当てられます。

たとえば、書き込み許可をもつユーザーは、地域情報内の商品を編集できます。これらのユーザーは、説明や名前などのローカライズ可能なフィールドと、ブランドやマーチャンダイザーなどのローカライズ不可能なフィールドを編集できます。

選択した地域情報で読み取り許可のみをもつユーザーは、ローカライズ不可能なフィールドを含め、フィールドを編集することはできません。

B2C Commerce での認証と承認

認証と承認は、重要なセキュリティの概念です。セキュリティコントロールを構成するには、Business Manager にアクセスする必要があります。

  • B2C Commerce の役割の概要
    Business Manager では、認証を実行してユーザーが実際に名乗っている人物かどうかを判定できます。また、ユーザーが実行しようとしている特定の操作を行う許可があるかどうかを判定するために承認を行います。
  • B2C Commerce での買い物客の認証
    買い物客はストアフロントで登録を行ってアカウントを作成するか、匿名のままでいることができます。たとえば、ストアフロントを閲覧するには、買い物客はアカウントにログインしたり、アカウントを作成したりする必要はありません。ただし、買い物客がアカウントを作成すると、請求先住所、クレジットカード、以前の注文などの情報を取得します。また、認証済みの買い物客は、ギフトレジストリやほしい物リストなど、匿名の買い物客は利用できない機能にアクセスできます。
  • B2C Commerce でのユーザーの認証と承認
    管理者は、Business Manager でセキュリティコントロールを構成します。Business Manager ユーザーが実際に名乗っている人物かどうかを判定するために認証を行う必要があります。また、ユーザーが実行しようとしている特定の操作を行う許可があるかどうかを判定するために承認を行います。
  • B2C Commerce での OCAPI クライアントの認証と承認
    Open Commerce API (OCAPI) は、OCAPI クライアントが使用する RESTful インターフェイスを提供します (カスタムコード)。ここでは、OCAPI のクライアントの認証と承認を説明します。
  • B2C Commerce での WebDAV の認証と承認
    WebDAV は、データやコードファイルのアップロードとダウンロードを可能にするプロトコルです。マーチャントは WebDAV リクエストをインスタンスの WebDAV サーバーに送信します。マーチャントの WebDAV クライアントは Business Manager ユーザー、またはマシン対マシンのインタラクションのための API クライアントとすることができます。

B2C Commerce の秘密鍵と証明書

さまざまなシナリオで、サードパーティの証明書と秘密鍵をインスタンスの鍵ストアにインポートする必要が生じます。鍵ストアは複数のエントリを保存できます。各エントリはタイプ PrivateKeyEntry または TrustedCertificateEntry とすることができます。これは java.security.KeyStore で使用される用語と同様です。

メモ Salesforce B2C Commerce では、内部パスワードを使用してインスタンスの鍵ストアを暗号化します。
ヒント リリース 26.1 から 26.3 では、移行中および証明書の更新時に、証明書と秘密鍵のインポート日が誤ってリセットされていました。リリース 26.4 以降、インポート日が正しく表示されるようになりました。リリース 26.1 より前にインポートされた証明書と鍵には、元の正しいインポート日が表示されます。新しくインポートされたすべての証明書と鍵には、正確なインポート日が表示されます。

秘密鍵のエントリ

インスタンスの鍵ストアの各 PrivateKeyEntry は、秘密鍵とそれに対応する公開鍵を保持します。この鍵のセットは、外部 Web サービスと通信し、ファイルを自分のインスタンスの WebDAV クライアントから外部の WebDAV サーバーに転送するために使用されます。KeyRef または CertificateRef パラメーターを使用するカスタムコードは、データの暗号化または復号化の際にこれらの鍵を使用します。たとえば、データの暗号化や復号化に使用されるカスタムコードなどです。

メモ eCDN に必要な証明書を、インスタンスの鍵ストアではなく、eCDN の鍵ストアに個別にインポートします。

信頼できる証明書のエントリ

インスタンスの鍵ストアの各TrustedCertificateEntryは、アウトバウンド SSL 接続を確立するときにサーバー証明書を検証する公開鍵証明書を保持します。デフォルトでは、B2C Commerce は Oracle の Java プラットフォームとともに出荷されるルート CA のみを認識します。ただし、CA 証明書をインスタンスの鍵ストアにインポートできます。

証明書のローテーション

証明書とそれに対応する秘密鍵のローテーションは、有効期限の切れた証明書、無効にされた証明書、または秘密鍵の漏洩への対処など、さまざまな理由で重要です。証明書の有効期限が切れた場合、証明書のローテーションは通信を保護するために証明書を引き続き使用するために必要となります。証明書が無効になった場合や秘密鍵が漏洩した場合は、攻撃者が証明書を悪用するのを防ぐために証明書のローテーションが必要となります。

カスタムコードを使用して保管されているデータを保護するために証明書のローテーションを使用する場合は、以前の鍵で暗号化されたデータを扱わなければならないため、状況はより複雑になります。

このような状況に対応するには、次の手順に従います。

  1. 新しい鍵を生成します。
  2. 古い鍵で暗号化されたデータを特定します。
  3. 古い鍵を使用してデータを復号化します。
  4. 新しい鍵を使用してデータを再度暗号化します。
  5. 古い鍵と、古い鍵で暗号化されたデータを削除します。

古い鍵で暗号化されたデータをこのプロセスで特定できなかった場合は、古い鍵は維持しておきます。

eCDN ゾーンとホスト名の作成

Development (開発)、Staging (ステージング)、Produation (本番) のいずれかのインスタンス POD にカスタム SSL 証明書がインストールされていない場合、または POD にインストールされているカスタム SSL 証明書にホスト名が含まれていない場合は、eCDN ゾーンを作成し、各ドメイン名の証明書をアップロードします。

必要なエディション

使用可能なソリューション: B2C Commerce

1 つ以上のホスト名を含む Development (開発)、Staging (ステージング)、または Production (本番) のいずれかのゾーンを作成し、各ホスト名の証明書を作成してアップロードします。

メモ 複数の SAN 証明書またはワイルドカード証明書がサポートされており、作成するホスト名ごとに必要です。
  1. 各ドメイン名に対し、POST storefront-zones エンドポイントを使用して eCDN ゾーンを作成します。createStorefrontZone を参照してください。
    たとえば、ホスト名に対して 2 つのゾーンを作成するには、次のようにします。
    • staging1.example.com
    • staging2.example.com
    • staging.example.co.uk
    1. 各ゾーンに対し POST /storefront-zones エンドポイントを呼び出します。

      i. 以下の各ペイロードに対し POST storefront-zones エンドポイントを呼び出します。

      • {"domainName": "mystore.com"}
      • {"domainName": "mystore.co.uk"}

      応答にはバックエンドゾーン名とゾーン ID が含まれるので、これらを使用して各ホスト名を証明します。たとえば:

      • stg-abcd-mystore-com.cc-ecdn.net
      • stg-abcd-mystore-co-uk.cc-ecdn.net

      バックエンドゾーン名は以下の形式を使用します。

      • stg-<realm_id>-<dashed-domain-com>.cc-ecdn.net
    2. (オプション) GET /zones/info エンドポイントを使用して、ゾーンとゾーン ID をリストします。すべてのゾーンを表示するには、offset または limit のクエリパラメーターを使用できます。以下がその例です: getZonesInfo を参照してください。
  2. eCDN 管理証明書を使用する場合は、certificateType に automatic (自動) を使用し、各ホスト名の証明書を追加します。eCDN 管理証明書の場合、フォーマットは必要ありません。ステップ 4 に進みます。
  3. 証明書と鍵は PEM 形式で書式設定します。改行は \n 文字で表されます。
    証明書と鍵のファイルの改行をリテラルな \n で置換するには、オペレーションシステムの例に従ってください。

    Mac/Linux

    次のようなシェルコマンドを使用します。
    • cat cert.crt | perl -pe 's/\r?\n/\\n/g'

    Windows PowerShell

    • (Get-Content -path C:\path\to\cert-file.crt -Raw ) -replace ('\r?\n','\n')
    メモ このコマンドは、Windows (CF LF) または Unix (LF) の改行コードを処理します。

    Windows GUI

    Windows のデフォルトのメモ帳には、改行コード置換をプログラムする機能がありませんが、サードパーティ製の高機能テキストエディターを使用してこれを行うことが可能です。たとえば、Notepad++ を使用できます。
    1. Notepad++ を使用するには、それぞれの cert ファイルと key ファイルを Notepad++ で開き、改行コードを確認します。
    2. Search (検索) | Replace (置換)を選択します。
    3. Find what (検索) フィールドで次の操作を行います。
      • ファイルの改行コードが Unix (LF) の場合は、「\n」と入力します。
      • ファイルの改行コードが Windows (CR LF) の場合は、\r\n を入力します。
    4. Replace with (置換) フィールドに、「\\n」と入力します。
    5. Search Mode (検索モード) で、「Extended (\n,\r,\t,\o,\x...)」を選択します。
    6. Replace All (すべて置換) をクリックします。複数の cert/key フィールドが開いている場合は、Replace All in All Opened Documents (開いているすべてのドキュメントですべて置換) をクリックできます。
  4. 各ホスト名に対し、POST 証明書エンドポイントと、ホスト名、証明書、ペイロードのキーを使用して、証明書をアップロードします。addCertificateForZone を参照してください。

重要: 複数のホスト名が含まれている証明書およびワイルドカード証明書の場合は、各ホスト名に対し証明書をアップロードします。同じ証明書を繰り返しアップロードできます。

カスタムファイアウォールルールを構成し、指定したリクエストパラメーターに基づいて受信トラフィックを制御します。

  1. Business Manager でアプリケーションランチャーをクリックし、管理 | サイト | 埋め込み CDN 設定の順に選択します。

  4. ルール名を入力します。たとえば、「user_agent_x からのリクエストをブロックする」などです。
  5. (オプション) 保存時にルールをアクティブにする場合は、保存時にルールを有効化を選択します。ルールをアクティブ化する準備がまだ整っていない場合は、まずルールを作成します。準備ができたら、「セキュリティルール」タブに戻り、リストからルールを有効にします。
  6. 視覚的なドロップダウンインターフェイスを使用してルール式を入力し、フィールド、演算子、値を選択します。条件付きロジックを追加するには、「かつ」ボタンまたは「または」ボタンを使用します。また、エクスプレッションを手動で入力するには、「エクスプレッションの編集」をクリックします。

    1. [最初 ] を選択すると、既存のルールよりも先にルールが評価されます。

SiteGenesis アプリケーションには、管理者役割など、あらかじめ定義された便利な役割がいくつか用意されています。これらの役割をインポートおよびエクスポートできます。これらの役割はそのまま使用したり、自社のアプリケーションのニーズに見合うようにカスタマイズしたりすることができます。必要に応じて、役割を削除し、独自の役割のセットを作成します。少なくとも 1 人のユーザーに、必ず「役割 & 許可」モジュールへのアクセスを付与してください。

役割と許可を管理するには、役割 & 許可モジュールの許可が必要です。ユーザーを追加してユーザーログインと認証情報を管理するには、ユーザーモジュールの許可が必要です。役割をユーザーに割り当てる、または割り当てを解除するには、ユーザーモジュールと役割 & 許可モジュールの両方の許可が必要です。

「役割と許可」モジュールへのアクセスをもつユーザーがいない場合は、B2C Commerce サポートに連絡してこのモジュールへのアクセスを回復してください。

メモ 割り当てられた役割のリストは、ユーザ定義の役割ページにも表示されます。
  1. 管理 | 組織 | 役割 & 許可の順に選択します。
    黄色の三角形でマークされた役割は、セキュリティに影響する役割です。これらの役割には、ユーザーまたはアクセスの役割、あるいはその両方を管理する許可が与えられます。この役割を変更する場合は、間違ったユーザーにアクセス権限を与えないよう注意してください。
  2. 新規をクリックします。
  3. 全般タグで、全般情報を定義または編集して、適用をクリックします。

    役割の ID に使用できるのは次の文字のみです。

    • 文字 (ラテン文字以外の文字を含む)
    • 数字
    • 空白
    • 特殊文字: _ ! " & \ ' ( ) + - . , / : < > ? @ [ ]

    B2C Commerce では、許可されていない文字を含む ID は拒否されます。アクセスロールを作成またはインポートすることはできません。

  4. ユーザータブで、ユーザーを選択して割り当てるをクリックします。
    ユーザータブを使用してユーザーに役割を割り当てるには、ユーザーモジュールへのアクセス許可も必要です。

B2C Commerce における HTTP ヘッダーでの宣言によるセキュリティ

宣言によるセキュリティコントロールを、クリックジャックなどのクライアントのブラウザーをベースとする攻撃に対する強力な防御手段として使用し、クロスサイトスクリプティング (XSS) に対するビルトインのブラウザー保護を提供できます。OWASP Secure Headers Project は、アプリケーションのセキュリティを向上するためにアプリケーションで使用することのできる HTTP 応答ヘッダーを記述しています。

B2C Commerce API と Storefront Reference Architecture (SFRA) でこの機能を提供しています。Response オブジェクトに対してaddHttpHeader()メソッドを使用して、HTTP 応答に HTTP ヘッダーを設定します。ストアフロントまたはカートリッジが SFRA ベースの場合は、httpHeadersConf.json ファイルを使用してすべて の応答の HTTP 応答ヘッダーを自動的に設定できます。

HTTP ヘッダーでの宣言によるセキュリティコントロールと、その他のクライアントのブラウザーベースの保護は、クライアントのブラウザーがこの機能をサポートしている場合にのみ適用されます。ヘッダーに依存してすべてのサポートしているユーザー環境をカバーする前に、B2C Commerce のサポートされているブラウザーのリストを確認してください。

B2C Commerce での認証と承認のベストプラクティス

アクセスコントロールの脆弱性を利用するのは、攻撃者の中核となるスキルです。攻撃者に対する保護を行うために、アカウント管理、注文管理、購入などのビジネス機能に対するサーバー側アクセスのコントロールチェックを強制します。

機密オブジェクトへのアクセスをコントロールするには、認証と承認を使用します。機密オブジェクトの例を次に示します。

  • Order
  • Customer
  • CustomerPaymentInstrument
  • OrderPaymentInstrument
  • Basket

B2C Commerce では、オブジェクト識別子 (汎用一意識別子 (UUID)、ID、トークン) を使用して Script API オブジェクトが識別されます。識別子によって、機密オブジェクトへの読み取りや書き込みのアクセスを付与しないようにします。すべてのリクエストを処理する前に、ストアフロントで追加の認証と承認を常に行います。一部の Script API では、セキュアなメソッドとセキュアではないメソッドの両方が提供されています。セキュアでないメソッドはレガシーのユースケースに対応するものです。セキュアなメソッドを使用することを強くお勧めします。

たとえば、クラス OrderMgr はメソッド getOrder に 2 つの署名を提供します: 

static getOrder(orderNumber : String)
static getOrder(orderNumber : String, orderToken : String)

2 番目の署名がセキュアなメソッドです。詳細については、クラス OrderMgr を参照してください。

承認

ストアフロント処理を実装する場合には、自社のビジネスワークフローに合った承認チェックを行います。機密オブジェクトで管理操作を実行する場合は、そのオブジェクトに関するシークレットを使用してリクエストしているユーザーを認証します。たとえば、ゲストが注文手続きを完了した後にアカウントを作成し、B2C Commerce がそのゲストに注文を再割り当てした場合、その注文に関するシークレットを使用してユーザーを認証します。このアプローチを使用すると、リクエストを行っているユーザーがオブジェクトを作成したユーザーと同一人物であることに確信を持てます。

ゲスト買い物客

ゲスト (未登録の) 買い物客に適用される堅牢な認証と承認のスキームを実装することは、登録済み顧客よりも困難な課題です。不正利用のリスクを下げるために、自社のユースケースに合わせて、以下のオプションを考慮します。

    • レート制限
    • コンピュータと人間を区別するための完全自動公開チューリングテスト(CAPTCHA)

B2C Commerce の一般的なセキュリティのベストプラクティス

Salesforce では、データの機密性、整合性、可用性がビジネスに不可欠なものだと理解しています。当社ではお客様がセキュリティの脅威に対する最大の保護をサイトに実装することを推奨しています。また、Salesforce B2C Commerce 環境を設定する際には次の中核となるベストプラクティスに従うことをお勧めします。

  • 権限をもつすべてのアカウントで 2FA を使用
    2 要素認証 (2FA) は、1 つのパスワードによる保護を超えた、追加の保護レイヤーです。この追加の保護には、知識 (知っていること)、所有物 (持っているもの)、または生体認証 (身体的特徴など) を使用できます。携帯電話 (持っているもの) などの 2 つ目の認証要素を使用することで、アカウントの乗っ取り、詐欺行為、データの損失、悪意をもったコード、フィッシング攻撃などの、一般的なセキュリティの脅威に対する追加の保護を提供できます。
  • 最小権限の原則の適用
    最小権限の原則は、ゼロトラストの中核をなす概念です。最小の権限を実装するとは、ユーザー、アプリケーション、システム、その他のコンポーネントに、それぞれのジョブを実行するために必要な最小限の権限レベルのみを付与することを意味します。
  • 多層防御の適用
    多層防御とは、環境内で 1 つではなく複数の層のセキュリティを使用することを意味します。攻撃によって 1 つのセキュリティメカニズムが突破されても、システムを保護するために必要なセキュリティを他のメカニズムが提供できます。卵のようなセキュリティではなく、玉ねぎのようなセキュリティを作成することを考えてください。卵は落としてしまうと割れて飛び散ってしまいますが、玉ねぎにはいくつもの層があるため、少し傷がつくだけですみます。
  • ポジティブセキュリティモデルの使用
    ポジティブセキュリティモデルは、セーフリストアプローチとも呼ばれ、何を許可するかを定義し、それ以外はすべて拒否します。このアプローチを使用して、悪意をもつ可能性のある入力をすべて拒否する代わりに、既知の正規の入力のみを許可リストに追加できます。
  • フェールセーフ
    フェールセーフとは、エラーが発生した場合にシステムを安全な状態にする決定ロジックを実装することを意味します。エラーを安全に処理することで、例外などのエラーパスによって、エラーが発生しなければ提供されることのない追加情報が公開されないようにします。攻撃者はこの追加情報を使用して、システムをどのように攻撃するかを学習することができます。
  • セキュリティ機能の使い勝手の向上
    使用の難しいセキュリティ機能は、無効にされることが多くなります。セキュリティ機能は、ユーザーが理解しやすいように作成するようにします。ユーザーがセキュリティに関する決定を理解できるように、ユーザーがセキュリティ設定を可視化して制御できるようにします。
  • 安全なデフォルトの使用
    管理者は、ユーザー体験を安全なものにし、デフォルトのセキュリティ設定の数を減らしたいと考えています。セキュリティ設定は、ユーザーがオプトインするのではなく、デフォルトのセキュリティ設定からオプトアウトしなければならないように構成します。セキュリティ上のリスクがある場合は、API またはユーザーインターフェイスで安全ではない機能を明確にラベルして、使用しないように促します。
  • 攻撃面の最小化
    安全な開発における全体的なリスクを軽減するには、潜在的な攻撃者にさらされる攻撃面を減らします。ポートを開くたびに、コードで外部ライブラリを使用するたびに、そしてユーザーにデータへのアクセスを付与するたびに、新しい攻撃面が作成されます。システムに対する全体的なリスクを軽減するには、攻撃面を最小限に抑えます。
  • eコマースの不正行為の防止
    eコマースの不正行為は、増加しつつあるセキュリティ上の課題です。サイバー攻撃者は盗んだ認証情報のリストを使用して、ユーザーアカウントにアクセスし、承認されていないトランザクションを行うために総当たり攻撃を行います。
  • サードパーティアプリの安全な導入
    ストアフロント機能とオンラインでの販売は Salesforce B2C Commerce の専門です。その他の作業に関しては、サードパーティのアプリケーションがストアフロントプラットフォームに専門知識を提供します。たとえば、オンラインでの税金の処理、クレジットカードでの支払い、配送業者などです。特定のプロセスを専門とする人々によって作成されたサードパーティアプリの使用は、B2C Commerce を柔軟にする要素の 1 つです。

B2C Commerce でのネットワークアクセスの制限

ネットワークレベルは、アセットにアクセスしようとする攻撃者に対する最初の防御ラインです。Salesforce B2C Commerce では、ストアフロントと Business Manager に対して 1 つずつ、2 つのメカニズムを使用しています。

  • B2C Commerce でのストアフロントのネットワークアクセス
    ストアフロントへのネットワークアクセスを制限するために、B2C Commerce に付属の埋め込みコンテンツ配信ネットワーク (eCDN) を有効にします。組織で eCDN を有効にするには、Salesforce カスタマーサポートにお問い合わせください。
  • B2C Commerce での Business Manager のネットワークアクセス
    Business Manager へのネットワークアクセスを制限するには、セキュリティコントロールを構成して特定の IP アドレスや IP アドレスの範囲のアクセスを制限します。これらのネットワークアクセスの制限を設定する意図は、不法な手段で有効な認証情報を取得した攻撃者をロックアウトすることにあります。この機能を有効にするには、Business Managerへのアクセスを許可する許可リストの IP アドレスの範囲と、Business Managerへのアクセスを許可しないブロックリストの IP アドレスの範囲を指定します。IP アドレスがブロックリストと許可リストの両方に含まれている場合は、アクセスは拒否されます。

B2C Commerce での OCAPI クライアントの認証と承認

Open Commerce API (OCAPI) は、OCAPI クライアントが使用する RESTful インターフェイスを提供します (カスタムコード)。ここでは、OCAPI のクライアントの認証と承認を説明します。

OCAPI クライアントの認証

認証を行うには、Account Manager 管理者が Account Manager で新しいクライアントにクライアント認証情報をプロビジョニングします。ユーザー認証とは異なり、OCAPI クライアントのプロビジョニングは Account Manager でのみ実行できます。Account Manager によって、組織のすべての Business Manager インスタンスに対する認証が可能になります。

OCAPI クライアントの承認

グローバル認証とは異なり、OCAPI クライアントの承認ルールはローカルの Business Manager インスタンスで指定します。このインスタンスは独特の承認ルールをもつことができます。複数のインスタンスで同じ承認ルールを使用したい場合は、これを手動でプロビジョニングするか、最初のインスタンスからエクスポートして 2 番目のインスタンスにインポートします。ユーザーの承認と同様、Account Manager でクライアントを作成すると、そのクライアントには何も許可が与えられていません。認証を行っても、アクセスできる OCAPI エンドポイントはありません。これは、ベストプラクティスである「デフォルトで拒否」に従うものです。

ユーザーの承認とは異なり、OCAPI の承認は役割に基づくものではありません。代わりに、一連の承認ルールとして構成し、OCAPI Shop API と OCAPI Data API に対して別々に構成します。特定のサイト、またはインスタンスのすべてのサイトに対してルールを指定します。最小権限の原則に従うには、複数のクライアントを作成し、各クライアントには仕事に必要な承認ルールのみを付与します。

B2C Commerce のセキュリティ設定

Business Manager のセキュリティ設定を構成します。ログイン設定の構成は、統合認証に移行していないアカウントにのみ適用されます。統合認証は、すべての Business Manager インスタンスのログインを Account Manager ログインにリンクします。19.5 では、すべての新しいインスタンスは Account Manager ログインにリンクされます。

  • Account Manager 経由のユーザーの統合認証への移行
    ユーザーが Account Manager 経由でインスタンスにログインできるようにするには、ユーザーを統合認証に移行します。移行後、ユーザーは 1 つのログイン認証情報を管理するようになります。インスタンスのセキュリティを強化するには、Account Manager の 2 要素認証を使用します。このトピックは、B2C Commerce に該当します。
  • B2C Commerce でのログイン設定の構成
    Business Manager では、ユーザーパスワードの制約とログインのロックアウトポリシーを構成することが重要です。
  • B2C Commerce のアクセス設定の構成
    IP アドレスに基づいてアクセスを制限します。許可リストまたはブロックリストを提供しない場合は、この機能はアクティブにはならず、これらの設定は効果をもちません。このトピックは、B2C Commerce に該当します。
  • 「HTTPS を強制する」グローバル環境設定の構成
    インスタンスのすべてのサイトで HTTPS の使用を強制します。この設定が有効な場合、URL は HTTPS プロトコルを使用して生成され、HTTP を使用する受信ページリクエストは HTTPS にリダイレクトされます。Open Commerce API (OCAPI) のセッションブリッジへの HTTP リクエストは受け入れられません。また、セッション Cookie とセキュアトークンの組み合わせの代わりに、誤った (誤検知の) セッションハイジャック検出を防止するセキュアセッション Cookie が使用されます。「HTTPS を強制する」グローバル環境設定を有効にすると、クロスサイトコンテキストでブラウザーが Cookie を送信できるようになります。このトピックは、B2C Commerce に該当します。
  • グローバル環境設定での Business Manager に対する HSTS の設定
    HTTP Strict Transport Security (HSTS) を使用すると、Business Manager のセキュリティを大幅に向上できます。Business Manager を保護するため、HSTS は HTTPS のみを使用してドメインにアクセスするように Web ブラウザーに指示します。
  • B2C Commerce の Secure File Transfer Protocol (SFTP) の正常動作ホストのクリア
    Business Manager では、以前に SFTP に使用されたホストが記憶されます。これらの記憶された既知のホストをクリアします。
  • B2C Commerce でのシステム使用通知メッセージの追加
    ユーザーがログインしたときに表示されるシステム使用通知メッセージを作成します。また、ユーザーがログインする前に、このメッセージを確認しなければならないように設定できます。

B2C Commerce 管理者のためのセキュリティのベストプラクティス

Business Manager を使用してサイトを保護し、買い物客のために安全なオンラインショッピング環境を確保できます。また、こうすることで Business Manager が保護され、以前に構成したセキュリティコントロールが攻撃者によって削除されるのを防ぐことができます。

  • B2C Commerce での攻撃のブロック方法の決定
    Salesforce B2C Commerce ではセキュリティ保護を提供していますが、セキュリティコントロールの構成と、デフォルトで有効になっているセキュリティコントロールを維持することはお客様の責任です。お使いの B2C Commerce インスタンスのセキュリティを維持するために、次のすべての面を考慮する必要があります。
  • B2C Commerce でのネットワークアクセスの制限
    ネットワークレベルは、アセットにアクセスしようとする攻撃者に対する最初の防御ラインです。Salesforce B2C Commerce では、ストアフロントと Business Manager に対して 1 つずつ、2 つのメカニズムを使用しています。
  • B2C Commerce でのセキュアな接続
    セキュアな接続は、クレジットカード、個人を特定できる情報 (PII)、認証情報などの機密情報を攻撃者が読み取ったり、変更したりできないようにするために非常に重要です。Salesforce B2C Commerce では、以下の安全なプロトコルを使用してインタラクションを保護できます。
  • B2C Commerce のセキュアなストレージ
    Salesforce B2C Commerce は多くのタイプの機密情報を保存しており、もっとも重要なものとしてはクレジットカード情報があります。
  • B2C Commerce での認証と承認
    認証と承認は、重要なセキュリティの概念です。セキュリティコントロールを構成するには、Business Manager にアクセスする必要があります。
  • B2C Commerce でのセキュリティイベントの監査
    Salesforce B2C Commerce は、セキュリティログを含むさまざまなログファイルを提供しています。セキュリティログには Business Manager ログインのログエントリが含まれます。
  • B2C Commerce での Dos 攻撃に対する保護
    DoS 攻撃では、攻撃者がネットワークのユーザーに対してコンピューターリソースを拒否することを試みます。攻撃者は通常、ターゲットのコンピューターシステムのリソースに大量の未承認のリクエストを送信し、一般のユーザーがネットワークにアクセスできないようにします。
  • B2C Commerce でのデータプライバシーと保護
    Salesforce B2C Commerce のサービスは、耐久性の高いデータセキュリティとプライバシープログラムを装備しています。データのプライバシーと保護、および関連するトピックについては、紹介されているリソースを参照してください。
