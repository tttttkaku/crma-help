Data 360 を活用した Intelligence Analytics ダッシュボード

Intelligence Analytics ダッシュボードには、主要な店舗パフォーマンスメトリックが表示され、ビジネスの俊敏性のためにデータ主導の意思決定を行うのに役立ちます。店舗内で最もパフォーマンスの高いカテゴリと商品を包括的に把握し、ロケーションとロケーショングループ全体の在庫の健全性を常に把握できます。Shopper Intelligence ダッシュボードを探索して、顧客の初回購入とリピート購入の行動を把握し、ロイヤルティの向上と維持に役立てます。

所有している Salesforce Commerce 製品

  • 高度な概要ダッシュボード
    高度な概要ダッシュボードで、主要業績評価指標のリアルタイムの視覚化を表示します。これらのインサイトを使用して、B2C Commerce の店舗パフォーマンスを改善する方法について、十分な情報に基づいた意思決定を行います。
  • Shopper Intelligence Analytics ダッシュボード
    顧客の購買行動を理解します。アクティブな顧客、リスクのある顧客、解約された顧客に関するデータを確認します。
  • Product Intelligence Analytics ダッシュボード
    地域全体の商品パフォーマンスと売れ筋カテゴリに関するインサイトを取得します。売れ行きの良くない商品や商品検索に関するデータを表示し、どの商品が頻繁に同時購入されているかを確認できます。

Log Center ダッシュボード

ダッシュボードは、Account Manager のテナントフィルターとレルムの割り当てに基づいて設定されます。管理者およびサポートの役割を担うユーザーは、ダッシュボードを任意の会社レルムのデータを表示するように設定できます。ダッシュボードのデフォルト設定では、過去 10 日間の上位スタックトレースのヒストグラムが表示されます。正確な各スタックトレース数を表示するには、チャート内のバーにマウスオーバーします。

その他のダッシュボードのオプションには以下が含まれます。

  • 個々のスタックトレースの表示: 表示したいスタックトレースのヒストグラム内の水平ラベルをクリックします。
  • メッセージの検索: リストされたスタックトレースで、すべてのメッセージを検索をクリックします。検索ページには、スタックトレースのヒストグラムと検索結果が表示されます。
  • 時間フィルターの切り替え: ヒストグラムの下部にある色のついた日付をクリックします。選択した時間のスタックトレースがヒストグラムに表示されます。
  • スタックトレースのフィルター: レルム (管理者のみ) のインスタンスタイプおよびサービスで、選択するスタックトレースのフィルターを設定します。
  • 検索の開始: 現在のフィルター設定で検索を実行するには、フィルターされた結果を表示をクリックします。

地域を切り替えるには、ページの右上隅にあるドロップダウンリストを使用します。

B2C Commerce の A/B テストの管理

アクティブな A/B テストのセグメントの合計数が 12 を超えない限り、最大 12 の同時進行の A/B テストにテストセグメントを配布します。各 A/B テストには、一意のテストセグメントが最高 5 つあり、そのうちの 1 つは常に対照群 です。各テストセグメントでは、すべてのテスト参加者のうちの一部を対象にします。対照群の参加者には、A/B テストが存在しない場合と同じストアフロント体験が表示されます。他のいずれかのセグメントへの参加では、ストアフロント体験が部分的に変更されます。この体験は、対照群の体験に 1 つまたは複数の変更を加えた体験です。このトピックは、B2C Commerce に該当します。

メトリクスダッシュボード

メトリクスダッシュボードを使用して B2C Commerce ストアフロントのパフォーマンス、セキュリティ、リソース活用を監視します。このダッシュボードを使えば、デベロッパーの生産性を高め、解決までの平均時間を短縮し、トラブルシューティングを効率化できます。モニターできるメトリクスには、アプリケーションのパフォーマンス、売上、埋め込みコンテンツ配信ネットワーク (eCDN)、B2C Commerce API (Shopper Commerce API (SCAPI)) と SCAPI フック、マネージドランタイムのメトリクスがあります。

重要 免責事項: Log Center メトリクスは、システムが出力する集計レートで、ストアフロントをリアルタイムで可視化します。これらは、基になるデータストアの信頼できる情報ソースとなることを意図したものではありません。たとえば、Business Manager の検索ページで 1 分あたりの注文数と注文数を比較することはできません。

メトリクスダッシュボードにアクセスするには、アプリケーションランチャーをクリックし、Log Center を選択した後、Metrics (メトリクス) をクリックします。

メトリクスダッシュボードへのアクセス

すべての Log Center の役割 (ユーザーおよび外部管理者) は、アクセス権のあるレルムのメトリクスダッシュボードを表示できます。

メトリックデータの粒度

データ解像度の粒度は、すべてのメトリクスで 1 分です。

メトリクスダッシュボードのフィルター

ユーザーは、1 日、1 週間、2 週間、または最大 30 日間のメトリクスを表示できます。

メトリクス

メトリクスダッシュボードで使用可能なメトリクスを確認します。

  • 全体的なアプリケーションメトリクス
    すべてのユーザーは、リクエスト、セッション、システムワークロードなどのトラフィックとパフォーマンスのメトリクスを表示できます。これらのメトリックは、Web サイト管理者と DevOps がすべてのサイトのパフォーマンスを監視するのに役立ちます。
  • 売上メトリクス
    すべてのユーザーは、注文数や作成された買い物カゴの数などの、ライブの売上メトリクスを表示できます。
  • 埋め込みコンテンツ配信ネットワーク (eCDN) のメトリクス
    HTTP トラフィックメトリクスは、Web サイト管理者、DevOps チーム、セキュリティ担当者がパフォーマンス、セキュリティ、リソース使用率をモニタリングしたり最適化したりするのに役立ちます。これらの eCDN メトリクスは、Web サイトのパフォーマンス、セキュリティ、信頼性を最適化するために重要です。これらの指標を積極的にモニタリングすることで、Web サイト管理者は問題を早期に検出し、キャッシュ効率を高めることができ、コスト削減、ユーザーエクスペリエンスの向上にも役立ちます。
  • B2C Commerce API (Shopper Commerce API (SCAPI)) メトリクス
    SCAPI メトリクスは、Web サイト管理者と DevOps チームが API 呼び出しのパフォーマンスを監視および分析するのに役立ちます。また、実行時間の長い API 呼び出しや不正なキャッシュヒット率など、API の問題を特定するのに役立ちます。SCAPI メトリクスは、最大 10 分の遅延でメトリクスダッシュボードに表示されます。
  • B2C Commerce API (Shopper Commerce API (SCAPI)) フックメトリクス
    SCAPI フックメトリクスは、Web サイト管理者と DevOps チームが SCAPI フックのパフォーマンスを監視および分析するのに役立ちます。これらのメトリクスは、パフォーマンスの低下や SCAPI フックの失敗に関する問題を特定するのに役立ちます。SCAPI フックメトリクスは、最大 10 分の遅延でメトリクスダッシュボードに表示されます。
  • Managed Runtime メトリクス
    コンポーザブルストアフロントに基づいてエクスペリエンスを運用するチームの場合、Managed Runtime メトリクスは、Web サイト管理者、DevOps チーム、およびセキュリティ専門家がパフォーマンス、セキュリティ、およびリソース使用率をモニタリングし、最適化するのに役立ちます。これらの CDN とアプリケーションのメトリクスは、Web サイトのパフォーマンス、セキュリティ、信頼性を最適化するために重要です。これらのメトリクスを積極的にモニタリングすることで、Web サイト管理者は問題を早期に検出し、キャッシュの効率を高めることができ、コスト削減、ユーザーエクスペリエンスの向上にもつながります。

埋め込みコンテンツ配信ネットワーク (eCDN) のメトリクス

HTTP トラフィックメトリクスは、Web サイト管理者、DevOps チーム、セキュリティ担当者がパフォーマンス、セキュリティ、リソース使用率をモニタリングしたり最適化したりするのに役立ちます。これらの eCDN メトリクスは、Web サイトのパフォーマンス、セキュリティ、信頼性を最適化するために重要です。これらの指標を積極的にモニタリングすることで、Web サイト管理者は問題を早期に検出し、キャッシュ効率を高めることができ、コスト削減、ユーザーエクスペリエンスの向上にも役立ちます。

On-Demand Sandboxes の eCDN メトリクス (ODS)

Log Center には、本番環境と同様に、ODS ゾーンの eCDN レイヤーからの HTTP ステータスコード502から530が表示されます。これらのメトリクスを使用して、トラフィックをモニタリングし、異常を検出し、ODSインスタンスの問題のトラブルシューティングを行います。

ODSは共有ゾーン・モデルを使用するため、メトリクスはインスタンスごとのトラフィックではなく、レルム内のすべてのODSインスタンスの総トラフィックを反映します。結果を特定のインスタンスに絞り込むには、分析ダッシュボードでサイトコンテキストフィルターを適用すると、各エラータイプがサイトごとに表示されます。

成功とエラー

成功とエラーのメトリクスは、成功した HTTP リクエスト (2XXステータスコード) とエラーリクエスト (4XXと5XXステータスコード) の数を追跡します。

  • 2XX (成功):リクエストがオリジンまたは Cloudflare キャッシュによって正常に受信、認識、処理されたことを示します。
  • 4XX (クライアントエラー):不正なリクエスト、禁止、見つからないなど、クライアントリクエストに関する問題を示しています。
  • 5XX (サーバーエラー):内部サーバーエラー、不正なゲートウェイ、サービス利用不可応答など、配信元サーバーでの障害を示します。

使用事例:

  • Web サイトの信頼性を監視するには、成功したリクエストと失敗したリクエストの比率を追跡します。
  • 404エラーの原因となるリンク切れなど、クライアント側の問題を特定します。
  • オリジンのダウンタイムや設定ミスなど、アクションが必要なサーバー側の障害を検出します。
  • API の信頼性を向上させるには、API コンシューマーの5XXエラーを最小限に抑えます。

キャッシュヒット率

キャッシュヒット率メトリクスは、オリジンサーバーではなく eCDN キャッシュから直接処理されたリクエストの割合を測定します。割合が高いほどキャッシングが効果的であることを示し、配信元サーバーの負荷が軽減されます。

使用事例:

  • パフォーマンスを最適化するには、キャッシュヒット率を高め、配信元サーバーの負荷を軽減します。
  • eCDN キャッシュからコンテンツを提供すると、オリジンリクエストの繰り返しが回避されるため、帯域幅のコストを削減できます。
  • 静的ファイルなど、想定されるアセットが適切にキャッシュされていないキャッシュ構成の問題を特定します。
  • コンテンツ配信を改善するには、頻繁にアクセスされるコンテンツを eCDN キャッシュに残して、読み込み時間を短縮します。

合計リクエスト数

合計リクエスト数のメトリクスは、キャッシュのヒットとミスを含む、ドメインに対して eCDN が受信した HTTP(S) リクエストの合計数です。

ユースケース:

  • トラフィックの傾向をモニタリングして、Webサイトへのアクセス急増または減少を把握します。
  • DDoS の脅威を分析するには、リクエストの急増を検出します。
  • マーケティングキャンペーンの効果を評価するには、トラフィックの急増とキャンペーンを関連付けます。
  • API の使用状況をモニタリングするには、API エンドポイントのリクエスト数を追跡します。

合計帯域幅

合計帯域幅メトリクスは、キャッシュのヒットとミスを含む、すべてのリクエストで使用される帯域幅の合計量を測定します。このメトリクスは、ユーザーと eCDN 間、または eCDN とオリジン間で転送されるデータの量を追跡します。

使用事例:

  • 帯域幅のコストを最適化するには、キャッシュ ヒット率を高め、圧縮 (Brotli、Gzip) を使用します。
  • スクレイピングやボット攻撃など、不正使用を示す可能性のある異常なトラフィックパターンを検出します。
  • スケーラビリティを計画するには、時間の経過に伴う帯域幅消費の傾向を監視します。
  • 起点サーバーの負荷を軽減するには、eCDN のキャッシュと圧縮によってコンテンツ配信を最適化します。

合計ページビュー数

合計ページビュー数メトリクスは、受け取ったページビューの合計数を測定します。ページビューは、ユーザーがページを読み込むたびにカウントされます。

使用事例:

  • ユーザーエンゲージメントを分析するには、経時的に閲覧されたページ数を追跡します。
  • マーケティング活動と関連付けて、プロモーションやSEO戦略の成功を評価します。
  • 人以外のトラフィックからのページビューが異常に多い際は、ボットのアクティビティをモニタリングします。
  • ユニーク訪問者数と比較して、各訪問者が平均して閲覧したページ数を判断します。

ユニーク訪問者数

ユニーク訪問者指標は、特定の期間にWebサイトにアクセスした個別のユーザーの合計数を測定します。eCDN は通常、IP アドレスと Cookie を使用して一意の訪問者を識別します。

使用事例:

  • 実際のオーディエンスサイズを測定するには、個々のユーザーとリピート訪問を区別します。
  • 訪問者の維持率を分析するには、異なる期間のユニーク訪問者数を比較します。
  • ボットのアクティビティや新規訪問者の急激な増加など、トラフィックパターンの異常を検出。
  • ローカライゼーションとコンテンツターゲティング戦略のために、訪問者の地理的分布を把握。

Managed Runtime メトリクス

コンポーザブルストアフロントに基づいてエクスペリエンスを運用するチームの場合、Managed Runtime メトリクスは、Web サイト管理者、DevOps チーム、およびセキュリティ専門家がパフォーマンス、セキュリティ、およびリソース使用率をモニタリングし、最適化するのに役立ちます。これらの CDN とアプリケーションのメトリクスは、Web サイトのパフォーマンス、セキュリティ、信頼性を最適化するために重要です。これらのメトリクスを積極的にモニタリングすることで、Web サイト管理者は問題を早期に検出し、キャッシュの効率を高めることができ、コスト削減、ユーザーエクスペリエンスの向上にもつながります。

リクエスト数

リクエスト数メトリクスは、ページ、静的アセット、プロキシされた API リクエストのキャッシュされたレスポンスとキャッシュされていないレスポンスを含む、Managed Runtime CDN が処理した HTTP リクエストの全体的な数を追跡します。

警告 スタック eCDN またはサードパーティ CDN を使用しているお客様は、アップストリームでキャッシュされた応答は表示されないため、正確を期すためにスタックされた CDN からのリクエスト数に依存しています。

使用事例:

  • 買い物客のエンゲージメントを分析するには、リクエスト数を経時的に追跡します。
  • マーケティング活動と関連付けて、プロモーションやSEO戦略の成功を評価します。
  • 人以外のトラフィックからのリクエストが異常に多い場合に、ボットのアクティビティを監視します。

キャッシュのヒット数

キャッシュのヒット数メトリクスは、コンポーザブルストアフロントのアプリケーションでは CDN キャッシュから直接処理されたリクエストの数を測定します。カウントが大きいほど、キャッシュが効果的であることを示し、アプリケーションサーバーの負荷が軽減されます。

警告 スタック eCDN またはサードパーティ CDN を使用しているお客様は、アップストリームでキャッシュされた応答はカウントされないため、精度をスタックされた CDN からのキャッシュヒットメトリクスに依存しています。

使用事例:

  • パフォーマンスを最適化するには、キャッシュヒット率を高め、アプリケーションサーバーの負荷を軽減します。
  • CDN キャッシュからコンテンツを提供することで、アプリケーションサーバーリクエストの繰り返しが回避されるため、帯域幅のコストが削減されます。
  • 想定されるページ、アセット、API が適切にキャッシュされていないキャッシュ設定の問題を特定します。
  • コンテンツ配信を改善するには、頻繁にアクセスされるコンテンツを CDN キャッシュに残して、読み込み時間を短縮します。

エラー率

エラー率メトリクスは、コンポーザブルストアフロントのアプリケーションからのエラーリクエストの数を追跡します。

  • 401 (Unauthorized)認証を必要とする要求。
  • 403 (Forbidden)許可されていない要求。
  • 404 (Not Found)存在しないページ、静的アセット、その他のリソースへのアクセスを試みるリクエスト。
  • 502 (Bad Gateway):アプリケーションサーバーとの通信の障害。
  • 503 (Service Unavailable):アプリケーションサーバーは、サービスリクエストに使用できません。
  • 504 (Gateway Timeout):アプリケーションサーバーの応答に時間がかかりすぎました。通常、これは最大応答時間制限を超えたために起こります。

使用事例:

  • Web サイトの信頼性を監視するには、成功したリクエストと失敗したリクエストの傾向を追跡します。
  • 404エラーの原因となるリンク切れなど、クライアント側の問題を特定します。
  • アプリケーションのダウンタイムや構成の誤りなど、アクションを必要とする可能性のあるサーバー側の障害を検出します。

SSR 呼び出し

SSR 呼び出しメトリクスは、コンポーザブルストアフロントのアプリケーションからのサーバー側レンダリングリクエストの数を追跡します。

使用事例:

  • パフォーマンスを最適化するには、キャッシュされた CDN 応答と比較して、低速でコストの高いサーバー側レンダリング応答をモニターします。
  • 人以外のトラフィックからのアプリケーションリクエストが異常に多い場合に、ボットのアクティビティを監視します。

リクエスト時間

リクエスト時間のメトリクスは、コンポーザブルストアフロントアプリケーションからのサーバー側レンダリングリクエストへの応答にかかった時間をミリ秒単位で追跡します。

  • P50 - リクエストへの応答にかかった平均時間。
  • P95 - アプリケーションリクエストの 95 パーセンタイルが、この時間未満で応答しました。
  • P99 - アプリケーションリクエストの 99 パーセンタイルは、この時間未満で応答しました。

使用事例:

  • パフォーマンスを最適化するには、アプリケーションの応答時間が遅いかどうかを監視し、最適化の領域と外部 API 統合のレイテンシーに関する潜在的な問題を特定します

全体的なアプリケーションメトリクス

すべてのユーザーは、リクエスト、セッション、システムワークロードなどのトラフィックとパフォーマンスのメトリクスを表示できます。これらのメトリックは、Web サイト管理者と DevOps がすべてのサイトのパフォーマンスを監視するのに役立ちます。

トラフィック関連のメトリクスをご確認ください。

合計プラットフォームリクエスト

合計プラットフォームリクエストのメトリクスは、すべてのプラットフォームとストアフロントのリクエストの 1 分あたりの数です。

使用事例:

  • セールイベントやキャンペーンの開始中にリクエストのトラフィックを監視。リクエスト数の予期せぬ急増や減少を探す。
  • 変更管理を検証。コードやデータのレプリケーション、プロモーション、キャンペーンなど、デプロイまたは変更が成功したことを検証。変更後の予期せぬ要求の破棄を監視。
  • パフォーマンスと可用性を監視するには、トラフィック パターンを分析します。
  • リクエストメトリクスを他の Log Center メトリクスと関連付ける。リクエストメトリクスは初期の指標であり、他の Log Center メトリクス、ログ、イベントと組み合わせて表示する場合に最も役立ちます。たとえば、コードレプリケーションストアフロントの回帰は、これらのインジケーターが true の場合に発生します。
    • プラットフォームリクエストの合計が減少。
    • 売上注文率の減少。
    • システムワークロードが 100% に急増。

ストアフロントリクエスト

ストアフロントリクエストのメトリクスは、すべてのサイトでの 1 分間あたりに行われたメインページリクエストの数です。レポートでは、インクルードや Open Commerce API (OCAPI) のリクエストは追跡されません。ストアフロントリクエストのメトリクスは、プラットフォームリクエストの合計数とは若干異なり、メインページのリクエスト率のみを表示します。

使用事例:

  • プラットフォームへのリクエストの合計数が多いことで覆い隠されるかもしれない、リクエスト率の小さなスパイクまたはドロップを分析。

セッション

セッションメトリクスは、すべてのサイトでの 1 分間あたりのアクティブなセッションの数です。

使用事例:

  • セールイベントを監視するには、セッションの急増と減少を分析します。このパターンは、通常、リクエストメトリクスのパターンと一致しています。
  • セッションメトリクスを他の Log Center メトリクスと関連付けます。
    • ストアフロントリクエストとストアフロントセッション:アクティブなセッションとストアフロントリクエストの比率を監視して、ユーザーの行動と、ユーザーセッションあたりのリクエスト数を俯瞰的に把握できます。セッション/リクエストレートが 1:1 の場合は、ボットのトラフィックが多いか、コードの問題に関連しているかもしれない問題を示します。
    • システムワークロードとストアフロントセッション:システムワークロードが高い状態が続いていることと、ストアフロントセッション (すべてのトラフィック) の関係性をモニタリングします。

プラットフォーム関連のメトリクスをご覧ください。

応答時間

応答時間のメトリクスは、すべてのリクエストで平均された 1 分あたりの応答時間のレイテンシーで、ミリ秒単位で表示されます。

使用事例:

  • 応答時間を初期指標として使用します。Business Manager Code Profiler を使用して、他の Log Center メトリクスと関連付けて詳細を確認します。
  • Commerce Analytics Center (CCAC) テクニカルレポートを使用して、応答時間の過去の傾向を確認します。詳細については、Technical ダッシュボードを参照してください。

送信済みメール

送信済みメールのメトリクスは、プラットフォームを介して送信されたすべてのメールの分単位の数です。

使用事例:

  • 送信済みメールを全般的に可視化し、予想される増加または予想外の減少を監視。

システムワークロード

システムワークロードのメトリクスは、1 分あたりのレルムリソース使用率の割合です。システムワークロードは、プラットフォーム上のシステムリソース使用率の集計であり、最も重要なパフォーマンス指標メトリックです。

使用事例:

  • システムリソースの使用状況を監視。持続的なシステムワークロードレベルが 30% を超える場合は、コントローラーパイプラインのレイテンシを示す。
    • 検索、チェックアウト、製品のコントローラー時間が遅い場合、コンバージョン率に影響します。
    • 低速のコントローラーでは、トラフィック負荷が増加した場合には適切に拡張できません。
  • システムリソース使用率のスパイクを監視します。システムワークロードの急激な増加を調査するためのトラブルシューティングのヒントをいくつか紹介します。
    • 何が変更されたかを確認するには、これらの質問に対する答えを見つけてください。
      • コードのデプロイやデータのレプリケーションを行ないましたか?
      • 予期せぬトラフィックの急増が発生していませんか?
      • サーキットブレーカーやレート制限なしで速度が低下するサードパーティサービスはありますか?
    • 10 分以上で 70% を超える急増と、それに伴うトラフィックや注文の減少がある場合は、サポートケースを開いて問題の調査に役立ててください。
    • 短いスパイクや断続的なスパイクがある場合は、Log Center のイベント、ログ、および Code Profiler を使用してさらに調査し、根本原因を導き出してください。

売上メトリクス

すべてのユーザーは、注文数や作成された買い物カゴの数などの、ライブの売上メトリクスを表示できます。

注文数

注文数のメトリクスは、すべてのサイトで 1 分間あたりに作成された注文の数です。失敗した注文やキャンセルされた注文については、レポートは更新されません。

使用事例:

  • 通常の注文率パターンを理解して、不規則性がある場合に発見します。
  • セールイベントを監視するには、セールイベント中に注文率をリアルタイムで追跡します。
  • 売上メトリクスとパフォーマンスメトリクスを関連付けて、予期せぬ注文率の低下を把握します。

買い物カゴの作成回数

買い物カゴの作成回数メトリクスは、すべてのサイトで 1 分間あたりに作成された買い物カゴの数です。

使用事例:

  • セールイベントを監視するには、買い物カゴの作成をリアルタイムで追跡します。このメトリクスは、一般的なユーザーの行動を示し、コンバージョンの追跡に役立ちます。
  • 買い物カゴの作成をストアフロントのリクエストおよびセッション率と比較します。これらの測定値の間に 1 対 1 の関係がある場合は、多くの場合、リクエストまたはセッションごとに空の買い物カゴを作成するコードにバグがあることを意味します。

買い物カゴの更新

買い物カゴの更新メトリクスは、すべてのサイトで 1 分間あたりに行われる、商品の追加や削除を含む買い物カゴの更新数です。

使用事例:

  • セールイベントを監視するために、リアルタイムの買い物カゴの更新率を追跡します。このメトリクスは、一般的なユーザーの行動を示し、コンバージョンの追跡に役立ちます。
  • リクエストと買い物カゴのメトリクスを関連付けて、買い物カゴに商品を追加したユーザーの割合に関するインサイトを取得します。

B2C Commerce での A/B テストの停止

非常に短期のプロモーションを実行している間は、長期的なテストを数日間一時停止して、トラフィックに基づいてデータが歪められないようにします。

必要なエディション

使用可能なソリューション: B2C Commerce

Staging (ステージング) インスタンスでテストを一時停止できますが、そのテストを Production (本番) にレプリケートした場合にのみこの変更が反映されます。もっと迅速に変更を反映させるには、Production (本番) インスタンスで A/B テストを一時停止します。ただし、テストを Production (本番) で一時停止する場合は、その後のレプリケーションによって上書きされないように、Staging (ステージング) でも一時停止してください。

テストを一時停止しても、終了日が延長されることはありません。A/B テストを一時停止にすると、新規参加者を追加できなくなるか、参加の有効期限が切れる前にサイトを再訪問した過去の参加者を識別できなくなります。テストを一時停止した時点でストアフロント訪問中の参加者は、引き続き参加者になります。これらの参加者は、セッションの有効期限が切れるまでテストセグメントの体験を継続します。つまり、テストを一時停止した後も一部のメトリクスは引き続き収集されますが、これは一時停止前に訪問を開始した参加者に限定されます。セッションの有効期限が切れると、参加者がいなくなるかテストを再開するまで、アクティブな参加者の数は減少します。

テストを一時停止して再開しなかった場合は、そのテストは停止されたものとみなされます。

  1. アプリケーションランチャーをクリックし、マーチャントツール | サイト | オンラインマーケティング | A/B テストの順に選択します。
  2. A/B テストのリストページで、変更したい A/B テストをダブルクリックします。
  3. A/B テストの詳細ページで、一時停止ボタンをクリックします。

    再開ボタンが表示されます。

  4. テストを再開する場合は、再開ボタンをクリックします。

B2C Commerce での A/B テストのプレビュー

B2C Commerce で A/B テストのさまざまなテストセグメントをプレビューおよびテストするには、ストアフロントのサイトプレビューコントロールを使用します。

アプリケーションランチャーをクリックし、マーチャントツール | サイト | オンラインマーケティング | A/B テストの順に選択します。テストを開いてテストセグメントを表示します。プレビューしたいテストセグメントのプレビューアイコンをクリックします。ストアフロントが開いて、テストグループに参加できます。サイトプレビューコントロールウィンドウにはテストとテストセグメント名が読み込まれています。

Reports & Dashboards とは

B2C Commerce の Reports & Dashboards は、高度な分析とレポートの機能を提供します。Reports & Dashboards を使用すると、ビジネスユーザーは、使いやすいダッシュボードで、売上、売れ筋商品、プロモーションの収益性などに関する分析情報を入手できます。

Eコマースチームは次のことが可能です:

  • 選択した期間の収益を追跡し、1 日当たりの最高値と最低値を確認できます。
  • Einstein Recommendations のパフォーマンスを確認し、最適化が可能な部分を特定できます。
  • 売れ筋商品を SKU レベルまで掘り下げて確認し、同時購入されている商品の傾向を特定して、前の期間から販売が大幅に増加した商品などの、売上が増加した商品と話題の商品を特定できます。
  • プロモーションのパフォーマンスと収益性を追跡できます。
  • デジタルチャネル間でダッシュボードを確認し、カスタムの日付範囲を選択して、サイト、顧客タイプ、デバイスタイプなどで比較できます。
  • 1 つのサイト、またはレルム内の全サイトにわたって指定した期間の結果を表示できます。
  • コントローラーと Open Commerce API (OCAPI) のリクエストと応答時間のテクニカルメトリクスを表示します。
  • 選択したデータのリアルタイムの売上とパフォーマンスを表示できます。これらの情報は毎分更新されます。

Reports & Dashboards のメリット

Reports & Dashboards アプリは、信頼性の高いストアフロントのパフォーマンスデータを計算します。マーチャンダイザー、マーケター、および eコマースチームは、このデータを使用して、販売やプロモーション、商品に関してよりスマートで情報に基づいたビジネス上の決定を行うことができます。たとえば、ビジネスユーザーは顧客タイプ、サイト、地域情報、デバイスタイプなどで簡単にフィルターを行うことができます。Reports & Dashboards アプリは、サードパーティーのアナリティクスプロバイダーや以前の Business Manager の機能では不可能な、正確で粒度の高いインサイトを提供します。

データの収集方法 － Business Manager Analytics と Reports & Dashboards のデータ収集方法の違い

すべての過去のレポートのレポート作成は、Analytics レポート URL の呼び出しを含め、ストアフロントのテンプレートに依存しています。これらの呼び出しはログに記録され、Business Manager の Analytics レポートに入力されます。具体的な統合は、SiteGenesisとSalesforce リファレンスアプリケーション (Salesforce リファレンスアーキテクチャ (SFRA))では異なります。

Reports & Dashboards では、B2C Commerce アプリケーションでの注文の作成や、買い物カゴへの追加などのイベントによって、ほとんどのレポートでデータが自動的に収集されます。次に例外をいくつか示します。

  • Site Search (サイト検索) レポートの場合。オンサイト検索のパフォーマンスを向上させるために、一部の検索結果はキャッシュされ、アプリケーションへの呼び出しは行われません。すべての検索が確実にキャプチャされるようにするには、ストアフロントテンプレートが次の要件を満たしていることをデベロッパーに確認してもらいます。
    • <isobject view…> タグ – isobject 要素。
      • 検索結果で返された各商品を示すために、検索結果ページで <isobject view=”searchhit”> が使用されている。
      • 検索結果がないことを示すために、検索結果なしページで <isobject view=”none”> が使用されている。
    • 検索結果の最初と、検索結果なしページのテンプレートに <isactivedatahead> が含まれている – isactivedatahead タグを追加する。
    • 検索結果と検索結果なしページのテンプレートに <isanalyticsoff/> が含まれていない。このタグがある場合、検索は正しく追跡されません – isanalyticsoff 要素。
  • Traffic (トラフィック) レポートの場合。ユーザーの訪問とボットの訪問を分類するには、<isactivedataheadタグを使用します> トラフィックを追跡するには、このタグをすべてのページに含めます –isactivedatahead タグを追加します。
    • <isanalyticsoff/>分析を追跡するすべてのページで、このタグがないことを確認します。特定のページのトラッキングをオフにするには、このタグを使用してトラフィックのトラッキングを防止します –isanalyticsoff 要素。
  • Traffic (トラフィック)、Shopper Journey (ショッパージャーニー) ダッシュボードの場合。注文手続きの手順はサイトによって異なるので、自分のサイト用の注文手続きステップのレポートを設定します。注文手続きテンプレートの各ステップにタグを追加して、注文手続きプロセスの正しいステップ番号と名前を Reports & Dashboards に提供します。実装のガイダンスの Analytics レポート URL パターンドキュメントで注文手続きの URL パターンのセクションを参照します。
  • Einstein のレポートは、Einstein アクティビティ追跡に依存しています。デベロッパー QA ガイドラインを参照してください。

Reports & Dashboards のデータを Development (開発) インスタンスと Staging (ステージング) インスタンスで表示できますか。

リリース 26.1 以降、指定されたテストレルム (ライブトラフィックを提供しないレルム) で、On-Demand Sandbox (ODS)、Development (開発)、Staging (ステージング)、Production (本番) インスタンスなど、Production (本番) 以外のインスタンスの Reports & Dashboards データを表示できます。

非 Production (本番) インスタンスで Reports & Dashboards を使用するには、Reports & Dashboards のデータ追跡の有効化の機能スイッチをオンにします。手順については、B2C Commerce での機能スイッチ (トグル) の設定を参照してください。機能スイッチをオンにした後、プロビジョニングが完了するまで最大 2 時間待ちます。

非本番環境用の URL を使用して Reports & Dashboards にアクセスします: https://ccac.stg.analytics.commercecloud.salesforce.com

メモ 非 Production (本番) インスタンスでは、Real-Time Performance ダッシュボードと Einstein ダッシュボードは利用できません。

ボットやスパムの自動トラフィックフィルターなど、データ収集でフィルターが使用されていますか。

データの収集でフィルターは使用されていません。ただし、ロボットとロボット以外のリクエストでトラフィックレポートを特定および分類することはできます。

Traffic (トラフィック) の Top Robots (上位ロボット) レポートで、プラットフォームはどのようにしてボットを識別していますか。

Reports & Dashboards では、以下の条件のいずれかが満たされる場合にデータがロボットとしてフィルターされます。

  • ページ数がゼロで、注文が行われなかった場合
  • ユーザーエージェントクラスが空白で、注文が行われなかった場合
  • ユーザーエージェントクラスがクローラーで、注文が行われなかった場合
  • ユーザーエージェントクラスが認識不可で、注文が行われなかった場合

ページ数がゼロの最初のケースは、javascript コードが実行されなかったことを示します。javascript を読み込まなかったユーザーは、ロボットのセッションである可能性が高いといえます。クローラーのユーザーエージェントクラスのリストは、サードパーティのソースから入手されます。

レルムに複数のサイトがあります。最初にダッシュボードを開いた場合、すべてのサイトを集計したメトリクスが表示されますか。

はい。デフォルトでは、レルム内のすべてのサイトを集計したメトリクスが表示されます。より粒度の高い情報を表示するために、サイトや地域情報でフィルタリングします。

通貨はどのように集計され、表示されますか。

システムで処理されるすべての注文において、Reports & Dashboards は外部から提供された為替レートを使用して、注文で使用された現地通貨を換算します。Reports & Dashboards では、注文の合計金額が現地通貨からレルムとサイトで構成されている通貨に換算されます。レルムの通貨は、Reports & Dashboards の管理設定で構成します。サイトの通貨は Business Manager で構成します。Reports & Dashboards では、現地通貨も米ドル (USD) に換算されます。

レポートを表示する場合、異なる通貨をもつ複数のサイトを選択すると、すべての値はレルムの通貨で表示されます。同じ通貨をもつ複数のサイトを選択した場合は、すべての値はサイトの通貨で表示されます。

分析のレポート通貨を変更できますか。

はい。Reports & Dashboards の管理者がレポートの通貨を変更することができます。

メモ 通貨を変更しても、履歴データは変更されません。通貨の変更はプラットフォームレベルであり、ユーザーレベルではありません。サイトを設定する際に、正しいレルムの通貨を設定することをお勧めします。

個々のレポートをエクスポートする場合、サイトで USD を使用していないのにデータで USD が使用されるのはなぜですか。

エクスポートされたレポートでは、3 つの通貨による金額が含まれています。Reports & Dashboards では、必要に応じて、外部サービスから提供された為替レートに基づいて通貨が換算されます。

  • レルムの通貨 (prefix std_) は Reports & Dashboards で構成します。
  • サイトの通貨 (prefix ste_) は Business Manager で構成されるデフォルトのサイト通貨です。データは、レポート対象のすべてのサイトで同じサイト通貨が使用されている場合にのみ挿入されます。
  • USD (prefix usd_)

Reports & Dashboards ではどの時点で注文がカウントされますか。

注文は、注文が完了し、B2C Commerce プラットフォームデータベースに追加された時点でカウントされます。一般的に、注文は、注文の確認ページで注文が完了したことが表示された時点でカウントされます。注文がキャンセルされた場合など、注文が変更されても、Reports & Dashboards アプリは更新されません。

Sales (売上) ダッシュボードにデバイスの内訳が表示されます。「不明」のデバイスとは何ですか。

Reports & Dashboards は、ユーザーエージェント情報からデバイス情報を導き出します。「不明」とは、Reports & Dashboards がユーザーエージェント情報からデバイスタイプを特定できないことを示しています。

ストアフロント、Endless Aisle、Customer Service Center、コールセンター、およびマーケットプレイスのチャネルとは何ですか。

チャネルは通常、買い物カゴの作成中に設定されます。詳細については、「注文の発生源の属性」ドキュメントを参照してください。

Top Referrers Traffic (上位リファラートラフィック) レポートの直結型と内部のリファラーとは何ですか。

Reports & Dashboards では、リファラー情報がない場合、トラフィックは直結型として分類されます。Reports & Dashboards は、リファラー情報の最上位ドメインがストアフロントと同じである場合に、トラフィックを内部トラフィックとして分類します。

私の会社は、新しいレルム ID を生成し、既存のサイトを新しいレルムに移動 (レルムを分割) したいと考えています。新しいレルムに移動されない Reports & Dashboards の分析要素はどれですか。

  • 注文に関連付けられている支払手段は移動できません。支払手段は暗号化されており、シードを必要とします。
  • 新しいレルムでは、過去のレポートのデータは新たに開始されます。
  • [Reports & Dashboards] ドロップダウンから古いレルム ID を選択し、履歴データを見つけます。新しいレルムを確立した後、2 つのレルムからのデータは結合されません。

詳細については、レルム分割に関するよくある質問 (FAQ) を参照してください。

現在はできません。新機能のアイデアやリクエストをIdeaExchangeに投稿してください。

Sales ダッシュボード

B2C Commerce Sales ダッシュボードには売上メトリクスが表示され、分析のニーズに合わせてフィルターできます。Sales ダッシュボードには、特定の売上メトリクスの合計と平均を表示するダッシュボードのグループが含まれています。また、ダッシュボードには新規顧客とリピーター、登録済み顧客と未登録の顧客、サイト、デバイスのレポートが含まれます。

ダッシュボードには以下のメトリクスが含まれます。

  • 収益 - 売上からの合計収益と平均収益を表示します。たとえば、ホリデーセールの最初の週に、新規顧客をターゲットとしたマーケティングキャンペーンの結果の収益を確認できます。ダッシュボードメトリクスを使用して、キャンペーン期間に新規顧客によって生み出された収益と、リピーターによって生み出された収益を比較します。また、登録済み顧客と未登録の顧客を比較することもできます。
  • 注文—確定した注文数を表示します。たとえば、レポートをフィルターして、特定のサイトで先週注文されたユニット数の合計と平均を表示できます。
  • ユニット数 — ダッシュボードのフィルターを構成して、販売されたユニット数をサイト別、デバイスタイプ別、チャネル別、および顧客タイプ別に確認します。たとえば、先月の売上数をデバイスタイプ別に確認します。日付の範囲に先月を選択し、デバイスタイプに携帯電話を選択します。この結果、携帯電話で注文を行った顧客に販売されたユニット数が表示されます。
  • 平均注文金額—行われたすべての注文の平均金額を確認します。ダッシュボードのフィルターを使用して、概要と詳細な結果を確認します。たとえば、レルム全体の平均注文金額を確認したり、1 つのサイト、顧客タイプ、デバイスタイプでフィルターしたりできます。また、ショッピングエージェントのサポートの有無にかかわらず行われた注文を比較することもできます。
  • トランザクションあたりのユニット数 - 新規顧客とリピーターのトランザクションあたりのユニット数を比較します。たとえば、リピーターを対象に、ターゲットを絞った 1 個購入で 1 個もらえる (BOGO) 2 週間のマーケティングキャンペーンを実施したとします。別の 2 週間では、新規顧客をターゲットを設定して、「1 個購入で 1 個無料」のマーケティングキャンペーンを実施します。キャンペーンの売上を比較するために、トランザクションあたりのユニット数を表示するフィルターを設定します。
  • 税金 — ダッシュボードを使用して、日付範囲内の売上の納税義務を確認します。たとえば、サイトの 1 つで 1 か月間のプロモーションを終了した後に、売上に関連する納税義務を確認したいとします。ダッシュボードの日付範囲をプロモーション期間に設定し、適切なサイトを選択します。
  • 配送料 — Sales ダッシュボードを使用して、配送料の合計と平均を確認します。たとえば、無料配送のプロモーションを計画している場合に、配送料を推定したいとします。ダッシュボードのフィルターを使用して、前回の無料配送プロモーションに関連付けられている配送料を確認します。日付範囲とダッシュボードのフィルターを、前回の無料配送プロモーションに合わせて設定します。

Shopper Journey ダッシュボード

B2C Commerce Reports & Dashboards の Shopper Journey (ショッパージャーニー) ダッシュボードを使用して、買い物客がサイトの訪問から注文コンバージョンまでどのように移動するかを評価します。このダッシュボードは、Traffic Report (トラフィックレポート) タブの選択肢として提供されています。

ダッシュボードで、買い物客訪問数合計に対するコンバージョン率のデータを確認できます。また、ショッパージャーニーの買い物カゴ、注文手続き、注文コンバージョンの段階の割合と合計も表示されます。さらに、サイトに対して構成した注文手続き手順についてコンバージョンデータを確認することも可能です。

Shopper Journey ダッシュボードには、次のチャートとグラフでコンバージョンデータが表示されます。

ショッパージャーニーファネル

Shopper Journey Funnel (ショッパージャーニーファネル) は、買い物客がストアフロントでプロセスをどのように進み、注文を行う前にどの時点で処理を中止したかを示します。ジャーニーの各段階において、段階の訪問数と合計訪問数に対する割合がチャートに表示されます。Shopper Journey Funnel は、以下の買い物客の段階に関するデータを表示します。

  • Site Visits (サイト訪問数): 既知のロボットを除く、合計の買い物客のセッション数。
    メモ セッションは 30 分間非アクティブだった場合にタイムアウトします。
  • Cart Visits (買い物カゴ訪問数): 1 つ以上の買い物カゴアクションをともなうサイトの訪問数。たとえば、追加、更新、または表示などです。
  • Checkout Visits (注文手続き訪問数): 1 つ以上の注文手続きアクションをともなうサイトの訪問数。たとえば、項目数の編集、項目の追加、項目の削除などです。
    メモ 注文手続きアクションは、注文手続きコントローラーのアクションを呼び出す買い物客のアクションです。
  • Order Visits (注文訪問数): 1 つ以上の注文が行われたサイトの訪問数。
  • Percent drop between stages (段階間の割合の低下): 各段階間で低下した合計訪問数に対する割合です。

この段階のメトリクスを使用して、買い物客が訪問を中止し、買い物カゴを放棄することが多いコンバージョンプロセスのポイントを特定します。

ファネルギャップ

Shopper Journey Funnel において、ファネルギャップは 1 つの段階から次の段階に進まない買い物客の割合を示します。これらの割合を使用して、ストアフロントでのショッピングジャーニーの成功と失敗を評価します。割合のギャップが大きい場合は、ギャップのある段階で買い物客の体験を改善することが考えられます。たとえば、注文手続きがわかりにくい場合や、買い物客に過度のデータの入力を求めている場合などです。

1 つの段階から次の段階に進んだ買い物客の割合を使用します。ファネルギャップの変化の相関関係を示すトレンドを探します。次に、他のダッシュボードデータと比較して、上向きまたは下向きのトレンドに影響を与えるビジネスプロセスを特定します。

Shopper Journey Funnel レポートでは、買い物客が買い物カゴを操作するときに、ReportingEvent-Start コントローラーが呼び出される必要があります。詳細については、Analytics レポートの URL パターンを参照してください。

上位 10 の注文手続きのステップ

ダッシュボードには、ストアフロントで使用された上位 10 の注文手続きのステップが表示されます。たとえば、サイトで買い物客が住所のステップを完了した訪問の数を追跡できます。

注文手続きのデータをダッシュボードに挿入するには、適切な注文手続きステップのデータを挿入するために必要な実装ステップがサイトに含まれていることが必要です。Salesforce B2C Commerce の一般的な実装では、注文手続き URL パターンからの注文手続きステップのイベントデータがダッシュボードによって収集されます。Top 10 Checkout Steps (上位 10 の注文手続きのステップ) レポートでは、注文手続きプロセスの各ステップで ReportingEvent-Start コントローラーを呼び出す必要があります。Salesforce リファレンスアプリケーション (Salesforce Reference Architecture (SFRA)) と SiteGenesis JavaScript コントローラー (SGJC) の実装では、注文手続きステップは注文手続きイベントから収集されたデータを使用します。詳細については、Analytics レポートの URL パターンを参照してください。

サイトの注文手続きステップは、それぞれのストアフロントと事業に合わせた独自の構成であるため、一般的なステップとは異なる場合があります。

一般的な注文手続きのステップには以下のものがあります。

  • 注文手続き
  • 請求
  • 配送
  • 支払い
  • 注文サマリ
  • 確定した注文

テーブルには、各注文手続きステップに対して以下のメトリクスがリストされます。

  • Site (サイト): データが該当するサイト。ダッシュボードフィルターで特定のサイトまたは複数のサイトを設定します。
  • Step (ステップ): プロセスのステップ番号。たとえば、注文サマリの確認の場合、それがサイトで追跡される買い物プロセスの 3 番目のステップである場合、注文サマリはステップ 3 として表示されます。
  • Step Name (ステップ名): B2C Commerce 実装コードでのステップの名前。
  • Step Visits (ステップの訪問): リストされたステップを含むサイトの訪問数。

ショッパージャーニーのグラフ

ダッシュボードには一連の折れ線グラフが表示され、ジャーニー段階を通じたショッパージャーニーが、前回のショッパージャーニーとの関係で示されています。

Cart Visits / Visits (買い物カゴ訪問数 / 訪問数):

買い物カゴ訪問数をサイト訪問数の割合としてプロットします。割合が大きい場合は、サイトが買い物客のトラフィックを買い物カゴへの商品の追加にうまく導いていることを示しています。

Checkout Visits / Cart Visits (注文手続き訪問数 / 買い物カゴ訪問数):

注文手続き訪問数を買い物カゴ訪問数の割合としてプロットします。割合が小さい場合は、買い物客が買い物カゴに追加した商品が、注文手続きの訪問にコンバージョンしていないことを示しています。

Order Visits / Checkout Visits (注文訪問数 / 注文手続き訪問数):

注文訪問数を注文手続き訪問数の割合としてプロットします。割合が大きい場合は、買い物客が買い物カゴに追加した商品を維持し、注文のコンバージョンへと移動していることを示します。割合が小さい場合は、買い物客が買い物カゴを放棄しているか、注文を中止していることを示しています。注文訪問数の割合が低い場合は、注文手続きステップのメトリクスを確認して、買い物客が注文を中止しているステップを特定します。

Order Conversion Rate (注文コンバージョン率)

顧客が注文を行った合計訪問数の割合を計算します。注文手続き訪問数の割合とはやや割合が異なることは普通です。注文手続き訪問数の割合とは割合が大きく異なる場合は、買い物客が注文手続きの最後のステップで注文を放棄している可能性があります。

B2C Commerce での A/B テストの停止

たとえば、成果を出していないテストや、テストセグメントの効果が収益の減少となっているテストを停止します。

必要なエディション

使用可能なソリューション: B2C Commerce

A/B テストを停止するには、終了日を現在の日時に変更します。停止されているテストでは、新規参加者を追加できなくなり、サイトを再訪問した過去の参加者が除外されます。ただし、有効期限が切れるまでは、アクティブな参加者のセッションでメトリクスを収集し続けます。

Staging (ステージング) インスタンスでテストを停止できますが、そのテストを Production (本番) にレプリケートした場合にのみこの変更が反映されます。もっと迅速に変更を反映させるには、Production (本番) インスタンスで A/B テストを停止します。ただし、この変更を Production (本番) で実装する場合は、その後のレプリケーションによってこの変更が上書きされないように、同じ変更を Staging (ステージング) でも行う必要があります。

  3. A/B テスト詳細ページの全般セクションで、終了日を現在の日時より前に変更します。
  4. 適用をクリックして、A/B テストへの変更を保存します。
    テストが停止されます。

Technical ダッシュボード

B2C Commerce Reports & Dashboards の Technical Reports (テクニカルレポート) ダッシュボードは、パイプラインとコントローラーを含む、サイトのサーバー側の技術的運用データに関するインサイトを提供します。

Average Response Time (平均応答時間)

平均応答時間レポートは、リクエストあたりの平均応答時間のトレンドを表示します。応答時間の単位はミリ秒です。グラフには、選択した期間内の毎日の応答時間が点としてプロットされます。応答時間を表示するには、マウスをプロットラインに合わせます。コントローラーの応答時間を追跡して、トラブルシューティングを行い、リソースの最適化を特定します。

Cache Hit Ratio (キャッシュヒット率)

キャッシュヒット率レポートには、選択した期間におけるキャッシュヒット、キャッシュミスと保存、キャッシュミスの 3 つの率が表示されます。

  • キャッシュヒットレポートは、Web アダプターページキャッシュから取得された応答の割合です。
  • キャッシュミスと保存は、アプリケーションサーバーで作成されて、キャッシュ可能としてマークされ、Web アダプターページキャッシュに保存された応答の割合です。
  • キャッシュミスは、Web アダプターページキャッシュから取得されなかった応答の割合です。

Non200-Level Responses (200 レベル以外の応答)

200 レベル以外の応答レポートは、選択した期間中に 200 レベル以外の応答コードとなったリクエストの頻度のトレンドを合計に対するパーセントとしてプロットします。特定の日の 200 レベル以外の応答の数とタイプを表示するには、グラフの点をマウスでポイントします。

Response Time Distribution (応答時間の分布)

このレポートは、応答時間 500 ミリ秒の範囲ごとのリクエスト数を表示します。たとえば、ダッシュボードの期間中、サイトで 1000 万件のリクエストが受信されました。このうち、700 万件のリクエストは応答時間が 0 ~ 400 ミリ秒の範囲でした。また、300 万件のリクエストは応答時間が 500 ~ 999 ミリ秒の範囲でした。棒グラフには、各応答時間の範囲に該当するリクエスト数と、表されている応答の合計の割合が表示されます。システムとコントローラーのパフォーマンスを確認します。応答時間が長く、コントローラーリクエストの数が多くなっている場合は、コントローラーで問題が発生していることが考えられます。

Main Controller Requests (メインコントローラーリクエスト)

メインコントローラーリクエストレポートには、ダッシュボードの期間中のシステムコントローラーとパイプラインのパフォーマンスメトリクスが表示されます。このレポートのメトリクスを使用して、システムのパフォーマンスを評価し、コントローラーとパイプラインのパフォーマンスの問題を特定します。たとえば、インクルードの数が小さく、合計処理時間の長いコントローラーは、関連するインクルードの呼び出しに問題がある可能性があることを示しています。

Technical Details (テクニカル詳細)

このダッシュボードには、1 つのコントローラーまたはパイプラインのテクニカルレポートが表示されます。このダッシュボードにアクセスするには、メインコントローラーのリクエストレポートにリストされているコントローラーまたはパイプラインをクリックします。

Include Controller Request (インクルードコントローラーリクエスト)

テクニカル詳細レポートには、インクルードコントローラーレポートも含まれています。このレポートには、ダッシュボードに情報が表示されているコントローラーによって行われたインクルード 呼び出しのパフォーマンスメトリクスが表示されます。このレポートのメトリクスを使用して、各インクルード呼び出しのパフォーマンスを評価します。

Include Controller (インクルードコントローラー)

インクルードコントローラーレポートには、ダッシュボードの期間においてすべてのコントローラーとパイプラインのリクエストで行われたすべてのインクルード 呼び出しのメトリクスが表示されます。レポートを表示するには、インクルードコントローラータブをクリックします。このレポートを使用して、パフォーマンスを評価し、インクルード 呼び出しに関する問題を特定します。

Traffic ダッシュボード

B2C Commerce Reports & Dashboards の Traffic (トラフィック) ダッシュボードには、サイトの訪問者に関するデータが表示されます。

レポートを使用して、以下を確認します。

  • 訪問数
  • 平均訪問時間
  • サイトへのアクセスに使用されたデバイス
  • リファラーのソース
  • 上位 IP アドレス
  • 上位ユーザーエージェント
  • 上位ロボット

レポートは毎日更新されます。すべての時刻はグリニッジ標準時 (GMT) です。

Number of Visits (訪問数) と Visit Duration (訪問時間)

最上位レポートには、デフォルトで訪問数が表示されます。表示するグラフを変更するには、訪問時間または訪問当たりの収益をクリックします。これらの 3 つのレポートを使用して、合計訪問数と平均訪問時間、および特定の日における訪問あたりの合計収益を確認します。

Visits By Device (デバイスごとの訪問数)

このレポートは、レポート期間におけるデバイスごとの合計訪問数を示します。レポートされるデバイスは、デスクトップ、携帯電話、タブレット、および不明 (定義されているデバイスクラスに適合しないすべてのデバイス) です。

Top Referrers (上位リファラー)

上位リファラーレポートには、トラフィックをストアフロントに誘導した上位リファラーホストがリストされます。レポートにはリファラルのソースとオリジンが含まれます。たとえば、facebook.co.uk の顧客がサイトへのリンクをクリックした場合、facebook がソースで、facebook.co.uk がオリジンになります。リファラーレポートには、リファラーのタイプ (検索、ソーシャル、または Web 全般)、およびソースからのリクエスト数も含まれます。

Top IP Addresses (上位 IP アドレス)

上位 IP アドレスレポートには、IP アドレスからの訪問数の概要が表示されます。リストされた IP アドレスを匿名化するために、レポートは各 IP アドレスの最後のオクテットをマスクします。このレポートにはロボットとユーザークライアントが含まれ、結果は直近に使用された 10,000 個のエントリに制限されます。このレポートには、マスクされた IP アドレス、訪問されたサイト (ストアフロント)、およびレポート期間中における IP アドレスからの合計リクエスト数がリストされます。

Top User Agent (上位ユーザーエージェント)

このレポートは、エージェントクラス別に一意のエージェント (エージェントファミリー) をリストします。レポートには、各エージェントからの合計リクエストのカウント数が表示されます。すべてのブラウザーが含まれますが、既知のロボットは除外されます。また上位ユーザーエージェントには、合計数の割合が表示されます。

Top Robots (上位ロボット)

上位ロボットレポートには、一意のロボットの数 (既知のロボットのみを含む)、ロボットクラス、ロボットファミリー、およびロボットからのリクエストの合計数の概要が表示されます。このレポートは、ユーザーのストアフロントをクロールしているロボットの特定に役立ちます。このレポートには、直近に使用された 10,000 個のエントリのみが含まれます。

Real-Time Performance ダッシュボードの表示

すべてのユーザーは、B2C Commerce Reports & Dashboards の Real-Time Performance (リアルタイムパフォーマンス) ダッシュボードを使用して、注文数や作成された買い物カゴの数などの、ライブの売上メトリクスを表示できます。パフォーマンスメトリクスを表示するには、パフォーマンスユーザー、または顧客マネージャーの役割をもっていることが必要です。各メトリクスについて表示する期間を変更します。

必要なエディション

使用可能なソリューション: B2C Commerce
メモ Real-Time Performance ダッシュボードは、Production (本番) インスタンスでのみ使用できます。On-Demand Sandbox (ODS)、Development (開発) インスタンス、Staging (ステージング) インスタンスなどの非 Production (本番) インスタンスでは使用できません。
  1. Real-Time (リアルタイム) タブで、Sales (売上) または Performance (パフォーマンス) を選択します。
  2. メトリクスの表示を、1 日、3 日、1 週間、または 2 週間に設定します。
  3. 各メトリクスの日時と計測値を表示するには、グラフにマウスを合わせます。
  4. グラフの上でドラッグすると、特定の日時にズームインできます。
  5. 表示をリセットするには、グラフをダブルクリックします。
    メモ グラフの表示は、グラフが更新されるとリセットされます。

B2C Commerce の A/B テストの結果の表示

B2C Commerce で一度に実行できる A/B テストは 3 つまでです。複数のユーザー体験を伴う複数のセグメントをそれぞれのテストに設定できます。A/B テストからデータを収集したら、テストグループの体験の一部またはすべてをサイトにデプロイします。

必要なエディション

使用可能なソリューション: B2C Commerce

通常、最高の結果をもたらしたテストグループの体験をデプロイしますが、複数のグループの体験をデプロイしたい場合もあります。これらの体験を手動でデプロイするには、キャンペーンを作成するか、既存のキャンペーンに追加します。

  1. アプリケーションランチャーをクリックし、マーチャントツール | サイト | オンラインマーケティング | A/B テストの順に選択します。
  2. A/B テストのリストページで、テストの左側にあるツールアイコンをクリックして、メニューからテスト結果の表示を選択します。
  3. A/B テストを開いてから、テストの結果をクリックすることもできます。A/B テストをダブルクリックします。
  4. A/B テストの詳細ページで、テストの結果ボタンをクリックします。

    A/B テストの結果ページが開き、リスト最上部にキーメトリクスが表示されます。
