B2C Commerce でのレプリケーションのベストプラクティス

レプリケーション処理を定義および実行する場合は、次の推奨に従ってください。このトピックは、B2C Commerce に該当します。

  • Production (本番) にレプリケートする前に、Staging (ステージング) から Development (開発) に各レプリケーションを実行してテストします。Development (開発) システムで検索が機能していることと、データが正しいことを確認します。
  • Development (開発) へ適切にレプリケートされた場合でも、Production (本番) ですべてをテストします。
  • 複数のレプリケーション処理を同時に実行しないでください。
  • システムオブジェクトタイプを編集した場合は、同じタイプのオブジェクトをレプリケートする前にグローバルシステムオブジェクトタイプをレプリケートします。
  • 異なるデータレプリケーショングループ間の依存関係を識別して、これに従います。たとえば、ソースコードとクーポンを使用するキャンペーンがある場合、キャンペーンをレプリケートする前に、またはそれと同時に、ソースコードとクーポンをレプリケートします。この場合にキャンペーンを先にレプリケートすると、データが破損します。
  • Production (本番) インスタンスにレプリケートする場合、まずデータまたはコードを転送して、転送処理を検証します。データを公開、またはコードをアクティブ化する前に、ログを確認します。
  • レプリケートする前に、常に検索インデックスを再作成し、処理が完了していることを確認します。検索インデックスをレプリケートする際には、増分およびスケジュール済みインデックスを無効にし、他のジョブを停止します。インデックスの再作成中または変更中は、レプリケーションが失敗します。
  • レプリケーション処理は大量のリソースを必要とするため、サイトのパフォーマンスに影響が出る場合があります。レプリケーションは、深夜や早朝など、トラフィックが少ない時間帯に実行します。ストアフロントでのアクティビティが最小の時に、Production (本番) へのレプリケーションをスケジュールします。Salesforce B2C Commerce の標準メンテナンス期間中は、大規模なデータレプリケーションを行わないようにします。
  • データのレプリケーションを実行するユーザー権限を制限し、複数のユーザー役割間で責任を分割します。以下が例です:
    • 商品担当マネージャーがレプリケーション処理を定義するが、処理をスケジュールまたは実行する許可はもたない。
    • レプリケーション担当マネージャーがレプリケーション処理を管理して実行する。
  • 可能な限り、静的コンテンツファイルの編集や移動は避けます。これらの変更はレプリケートするのに長い時間がかかります。
  • 処理を最初から作成する代わりに、可能であれば既存のレプリケーション処理をコピーします。
  • レプリケーション処理によって自動的にページキャッシュがクリアされた場合は、手動で再度クリアしないでください。
  • Production (本番) インスタンスで直接カートリッジパスやコードを編集しないでください。直接編集すると、ページの複数のバージョンなど、予想外の動作が発生する場合があります。コードと環境設定は、常に Staging (ステージング) から Production (本番) にレプリケートします。
  • パフォーマンスを低下させないために、次のパスに作成されるディレクトリには 100,000 個を超えるオブジェクト (通常のファイルとディレクトリ) を保存しないことをお勧めします。/on/demandware.servlet/webdav/Sites/Catalogs/CatalogName/MyDirectoryWithNoMoreThan100kObjects/.

B2C Commerce での A/B テストオブジェクトのインポートとエクスポート

A/B テストのインポートとエクスポートには abtest.xsd スキーマを使用します。このトピックは、B2C Commerce に該当します。

abtest.xsd スキーマを使用している場合、異なるインポートモードをサポートできるように、すべての A/B テストの下位要素は任意です。A/B テストの特定の属性を更新し、テストの他の属性には影響しないようにするには、更新モードのインポートを実行します。または、削除する A/B テストの ID のみを指定する削除モードのインポートを実行します。どちらの場合も、ファイルから無関係な要素を省略できます。

<participation> 要素では、置換 セマンティックがサポートされます。更新モードまたはマージモードでは、A/B テストに関連する属性が変更されないように、この要素を省略します。要素を含める場合は、そのコンテンツ全体を指定します。たとえば、<participation>要素には、<trigger>要素と<expiration>要素も必要です。

テスト結果ページから A/B テスト結果を.csv形式でエクスポートし、後で分析できるようにします (通常はスプレッドシートアプリケーション内)。

B2C Commerce での Data 360 ゲスト買い物客セグメントの有効化

Salesforce Data 360 セグメントを使用して、プロモーションの対象ユーザーを決定し、セグメントのメンバーに提供する報酬の種類を決定します。Data 360で作成したゲスト買い物客セグメントは、B2C Commerce のゲスト買い物客キャンペーンで使用できます。

アプリケーションランチャーをクリックし、マーチャントツール | 顧客の順に選択して Business Manager の顧客関連機能にアクセスします。

ゲスト買い物客とは、ログインしたり、登録済みアカウントを使ったりせずにサイトにアクセスする買い物客のことです。ゲスト買い物客が注文すると、注文データが取得され、Data 360 と共有されます。Data 360 は注文データを複数のデータストリームに分割します。SalesOrderCustomer_bjmp_prd データストリームには、ゲスト顧客情報が保持されます。SalesOrderCustomer データストリームは 1 時間ごとに更新されます。SalesOrderCustomerデータストリームを使用して、ゲスト買い物客セグメントを作成します。

ゲスト買い物客の Data 360 セグメントを作成するには、Data 360 でのセグメントの作成を参照してください。データセグメントには、SalesOrderCustomer データストリームを使用します。SalesOrderCustomer データストリームで、Anonymous フラグが true である顧客を識別するルールを設定します。

アクティブデータ属性

B2C Commerce では、入手可能性、原価、商品の有効期間、SKU カバレッジ、TTOOS (在庫切れまでの時間) など、いくつかの属性が計算されるか、またはこれらの属性を使用して追加のメトリクスが計算されます。

収集された情報を表示するには、マーチャントツール | サイト | 商品とカタログ | 商品の順に選択します。

各標準属性には、特定の使用目的があります。Salesforce では、指定された使用目的以外に属性を使用しないことをお勧めします。たとえば、costPrice (原価) 属性を使用して原価以外のデータをインポートしないでください。インポートされた値はしばしば他のメトリクスの計算に使用されるため、属性にデータをインポートする場合や、インポートされた属性に情報を指定しない場合には、他の属性に影響を与える可能性があります。

メモ アクティブデータ属性を使用して、他のシステムにレプリケートする予定のデータをインポートしないでください。アクティブデータはレプリケートできません。

複数のシステムで、異なるインポート周期で属性データをフィードできます。たとえば、サードパーティのシステムでは商品レビューデータを毎日フィードし、バックエンドシステムでは返品率の情報を毎週フィードできます。

アクティブデータフィードには、次の表のタイプ列にインポート済みと示されている属性が含まれています。

フィードには、ProductActiveData および CustomActiveData ビジネスオブジェクトに追加したカスタム属性も含めることができます。

ニアタイム属性データは 1 日以内に更新されます。データは営業日中にリアルタイムで収集され、その日の夜間に集計され、翌日送信されます。リアルタイムの属性データは、ライブの B2C Commerce 本番サイトからオンデマンドで更新することができます。

メモ B2C Commerce では、年間および無期限の属性が毎日収集されます。

現在、次のフィールドが商品アクティブデータのエクスポートで利用可能であり、サポートされています: productID、revenueDay、unitsDay、ordersDay、impressionsDay、viewsDay、avgSalesPriceDay、conversionDay、revenueWeek、unitsWeek、ordersWeek、impressionsWeek、viewsWeek、avgSalesPriceWeek、conversionWeek、revenueMonth、unitsMonth、ordersMonth、impressionsMonth、viewsMonth、avgSalesPriceMonth、conversionMonth、revenueYear、unitsYear、ordersYear、impressionsYear、viewsYear、avgSalesPriceYear、conversionYear

B2C Commerce でのインポート/エクスポートのベストプラクティス

インポートとエクスポートでは、確立されているベストプラクティスに従うことをお勧めします。このトピックは、B2C Commerce に該当します。

可能であれば、カタログ以外のフィードでは、現在のフィードと前回のフィードの差異だけを含むインポートフィードを作成します。これらのフィードは、差分フィードと呼ばれます。このようなフィードはサイズが小さめで、インポートの速度が上がり、ネットワークの中断に対する脆弱性が下がります。

差分カタログフィードを作成する場合、グローバルインポートモードをフィールド固有インポートモードに置換するフィールドを含めることはできません。たとえば、バンドルされた商品用に差分フィードを作成することはできません。これは、bundled-products フィールドでは常に置換セマンティックが使用されるからです。

フィードをロールバックすることはできません。そのため、ベストプラクティスとして少なくとも前回のフィードをアーカイブし、新しいフィードを検証できない場合に古いバージョンを再インポートできるようにすることをお勧めします。ただし、B2C Commerce ではアーカイブが自動的に消去されないため、アーカイブファイルは自分で消去する必要があります。アーカイブファイルを空にするためのデモカートリッジについてサポートが必要な場合は、カスタマーサポートまでお問い合わせください。

  • B2C Commerce でのコードのレプリケーション処理の作成

B2C Commerce でのコードのレプリケーション処理

各コードレプリケーション処理では、コードのバージョンを転送するか、転送されたコードのバージョンをアクティブ化するか、コードのバージョンを転送してアクティブ化するか、前回のターゲットインスタンスでアクティブなコードのバージョンを元に戻します。このトピックは、B2C Commerce に該当します。

コードのレプリケーションは 2 つのステップによる処理です。まず、コードのバージョンが Staging (ステージング) からターゲットインスタンスに転送され、その後、ターゲットインスタンスでアクティブ化されます。両方のステップを 1 つのレプリケーション処理として実行するか、別々に実行します。別々に実行すると、エラーの原因の特定に役立ちます。

メモ すべてのレプリケーション処理は Staging (ステージング) インスタンスで実行します。これには、ターゲットインスタンスにのみ影響を与える、「コードのアクティブ化」と「元に戻す」を含みます。

コードのバージョンを転送すると、同じ名前のコードのバージョンがターゲットインスタンスに作成されます。この名前をもつコードのバージョンがターゲットに存在する場合、B2C Commerce によってタイムスタンプとインデックス番号が付加されます。たとえば、「version1」という名前のコードバージョンをレプリケートし、この名前のバージョンがターゲットインスタンスに存在する場合は、新しいバージョンの名前は「version1_05032018-1」などのようになります。

コードレプリケーション処理には 4 つのタイプがあります。

レプリケーションタイプ 説明
コードの転送 ソースインスタンスで選択したコードのバージョンはターゲットインスタンスに転送されますが、アクティブにはされません。ターゲットにある現在アクティブなバージョンが、引き続きアクティブになります。「コードのアクティブ化」のレプリケーション処理を実行すると、レプリケートしたバージョンがターゲットインスタンスでアクティブになります。
コードの転送 & アクティブ化 ソースインスタンスで選択したコードのバージョンがターゲットインスタンスに転送され、ターゲットでただちにアクティブなバージョンになります。
コードのアクティブ化 この処理は、「コードの転送」処理が正常に完了した後にのみ使用できます。アクティブ化では、転送したコードのバージョンがターゲットインスタンスでアクティブなバージョンになります。コードのバージョンがすでにアクティブな場合は、変化はありません。コードのバージョンがターゲットインスタンスに存在しない場合は、レプリケーション処理は失敗に終わります。
元に戻す この処理は、「コードの転送 & アクティブ化」、または「コードのアクティブ化」のレプリケーション処理が正常に完了した後にのみ使用できます。ターゲットインスタンスでアクティブなコードのバージョンが、前回のコードレプリケーション処理の前にアクティブだったバージョンに戻ります。元に戻すバージョンがアクティブでない場合は、変化はありません。コードのバージョンがターゲットインスタンスに存在しない場合、または以前にアクティブだったコードのバージョンがすでに存在しない場合は、レプリケーション処理は失敗に終わります。

Tableau の B2C Commerce データ

Tableau で B2C Commerce データを使用して、お客様固有のビジネスニーズに合わせたダッシュボードやデータ表示を作成します。Salesforce B2C Commerce Cloud Connector は、B2C Commerce の分析データを Tableau インスタンスにエクスポートします。Tableau のデータ視覚化機能を使用して、コードなしでデータを分析できます。

メモ Tableau には、データを視覚化するためのオプションやリソースが多数用意されています。Tableau ライセンスで利用可能なトレーニングリソースを利用して、Tableau でデータの視覚化を作成、調整、共有する方法について学習することをお勧めします。技術的な詳細とヘルプについては、Tableau のドキュメントを参照してください。

Salesforce B2C Commerce Cloud コネクター

Salesforce B2C Commerce Cloud Connector を使用して、コマースデータを実用的なインサイトに変換します。実用的なインサイトは、顧客体験を最適化し、収益成長を加速させるのに役立ちます。この Java Database Connectivity (JDBC) ベースのコネクターは、B2C Commerce に保存されている eコマースデータおよび顧客行動インサイトへのアクセスを提供します。コマースプラットフォームへの直接接続により、デジタルタッチポイント全体での販売実績、カスタマージャーニー、製品エンゲージメントの分析が可能になります。

Tableau Exchange から B2C Commerce Cloud コネクタをダウンロードして設定するには、Salesforce Commerce Cloud Intelligenceを参照してください。

一般的なデータ用語

Tableau で B2C Commerce データの使用を開始するには、B2C Commerce と Tableau で使用される一般的なデータ用語の一部を知っておく必要があります。

  • 役割 – Tableau のフィールドに割り当てられる一連のプロパティ。
    • ディメンション – データの詳細をセグメント化および表示するために使用される質的なフィールド。たとえば、GMV (流通総額) というメジャーを顧客タイプと日付のディメンションでグループ化できます。メジャーの値は、ディメンションのコンテキストに依存します。
    • メジャー – メトリクスまたは数値データを表示するために使用される量的フィールド。メジャーの意味は Tableau で選択されているディメンションに依存し、その値はディメンションのコンテキストに依存するため、メジャーは依存プロパティと見なされます。Tableau ではメジャーの意味を粒度と呼びます。

      B2C Commerce のメジャーは、完全加法メジャー、または準加法メジャーです。完全加法メジャーは、メジャーとともに使用されるディメンションに対し合計することができます。適用可能な集計関数の例としては、合計、カウント、平均などがあります。

      準加法メジャーは、算術的な計算や集計の結果です。これは合計可能ですが、合計は含まれるディメンションによって異なる場合があります。

  • 集計 - データを結合する方法を指定します。Tableau チャートにおけるデータ集計量が、データの評価方法と発見可能な内容に影響を与えます。準加法メジャーを集計すると、誤った結果が生成される可能性があります。

B2C Commerce のデータ集計

B2C Commerce Tableau Connector は、B2C Commerce データを領域別にグループ化する Web データコネクタです。各領域は、B2C Commerce の生データから抽出されたディメンションとメジャーで構成されています。

B2C Commerce データを Tableau にインポートする際に、Tableau でデータを表示するために適切な集計関数がコネクタによって適用されます。インポートしたディメンションを使用してメジャーをさらに集計することで、意味のあるデータ表示を作成できます。

データダッシュボードは、同じ基礎となる領域からのデータを読みやすいチャートや表に表示するための便利な方法です。各ダッシュボード要素は、さまざまなデータ集計によって異なります。

Account Manager 経由のユーザーの統合認証への移行

ユーザーが Account Manager 経由でインスタンスにログインできるようにするには、ユーザーを統合認証に移行します。移行後、ユーザーは 1 つのログイン認証情報を管理するようになります。インスタンスのセキュリティを強化するには、Account Manager の 2 要素認証を使用します。このトピックは、B2C Commerce に該当します。

必要なエディション

使用可能なソリューション: B2C Commerce

この移行には、ユーザーに徐々に変更を導入できるように、複数のステージが用意されています。移行を開始する前に、ユーザーデータのバックアップファイルをエクスポートすることをお勧めします。セキュリティモジュールで「許可リストに含まれるホスト名のみを許可」の設定を無効にしている場合でも、Business Manager に対して使用されるすべてのホスト名を許可リストに追加します。

最初のユーザーが統合認証への移行を完了したら、統合認証を無効にすることはできません。ローカル認証に戻すには、サポートに連絡してください。

  1. Business Manager で、アプリケーションランチャーをクリックし、次に管理 > グローバル環境設定 > セキュリティの順に選択した後、「ユーザー認証」タブを選択します。
  2. 組織で使用する移行段階を選択します。
    1. ユーザーの統合認証なし

      すべてのユーザーは、自分専用のインスタンスログイン認証情報を使用して、各自のインスタンスにログインします。

    2. ユーザーの統合認証をサポート

      パワーユーザーに、自分のインスタンスと Account Manager アカウントをリンクできるリンクを提供します。

    3. 統合認証を推奨

      ユーザーがインスタンスにログインすると、インスタンスのアカウントと Account Manager のアカウントをリンクするようにとの指示が表示されます。ユーザーは、引き続きアカウントをリンクせずにログインできます。

    4. 統合認証が必須

      ユーザーがインスタンスにログインすると、インスタンスのアカウントと Account Manager のアカウントをリンクするようにとの指示が表示されます。ユーザーは、アカウントをリンクしないとログインできません。

    5. 統合認証のみ

      ユーザーは、Account Manager のログイン経由でしかインスタンスにログインできません。この時点では、まだアカウントをリンクしていないユーザーに手動でリンクを提供する必要があります。

  3. 移行したすべてのユーザーに自動的に付与する役割を入力します。
  4. 統合ログインに移行済みのユーザーの数や割合など、移行ステータスを確認できます。
  5. 適用をクリックします。
  • 手動によるユーザーの統合認証への移動
    場合によっては、ユーザーが Business Manager と Account Manager のプロフィールを自分でリンクできないことがあります。2 つのアカウントで異なる Eメールアドレスを使用している場合、ユーザーは統合認証に移行できません。ただし、管理者が Business Manager から Account Manager にユーザーを手動で移行することができます。これは、手動でユーザーを統合認証に移行する管理者のためのものです。管理者が B2C Commerce の使用を 2019 年 10 月以降に開始した場合は、組織が自動的に統合認証を使用しているため、このトラブルシューティングは該当しません。
  • 統合認証からユーザーを元に戻す
    統合認証では、ユーザーは Account Manager を介して Business Manager にログインできます。統合認証ではログインプロセスが効率化され、ユーザーのログイン認証情報の数が減ります。Business Manager を使用して、移行済みのユーザーを Business Manager ログインに戻すことはできません。代わりに、影響を受けたユーザーを元に戻すには、ユーザーをエクスポートし、ファイルを変更して、ユーザーを再インポートします。これは、手動でユーザーを統合認証に移行する管理者のためのものです。B2C Commerce の使用を 2019 年 10 月以降に開始した場合は、組織が自動的に統合認証を使用しているため、このトラブルシューティングは該当しません。

B2C Commerce でのコードのレプリケーション処理の作成

コードレプリケーション処理を手動でトリガーするか、指定した時刻に実行するようにスケジュールするか、ジョブを作成して実行します。

必要なエディション

使用可能なソリューション: B2C Commerce
  1. アプリケーションランチャーをクリックし、管理 | レプリケーション | コードのレプリケーションの順に選択します。既存のコードレプリケーション処理のリストが表示されます。
  2. 新規をクリックします。
  3. システムによって処理 ID が生成されます。別の ID を入力します。
  4. ドロップダウンリストから、ターゲットインスタンスを選択します。
  5. (オプション) 説明を入力します。
  6. ドロップダウンリストから、アクティブ化のタイプを選択します。
    手動 処理は手動でトリガーした場合に実行されます。
    自動 処理は指定した日時に 1 回実行されます。このオプションを選択すると、日付と時刻のフィールドが表示されます。デフォルト値は翌日の午前 0 時です。
    ジョブステップ 処理をジョブの一部として実行できます。
  7. ドロップダウンリストから、通知 Eメールのトリガーを選択します。複数のターゲット Eメールアドレスをコンマで区切って入力します。
    - なし - Eメールは送信されません。
    処理終了時 成功か失敗かにかかわらず、処理が終了した際に指定したアドレスに Eメールを送信します。処理がハングした場合は、Eメールは送信されません。
    処理失敗時 処理が失敗した場合に、指定したアドレスに Eメールを送信します。処理が成功またはハングした場合は、Eメールは送信されません。
    定期的 間隔を分数で入力します。処理の実行中、処理が終了するまで指定したアドレスにこの間隔で Eメールが送信されます。処理が成功または失敗した際にも Eメールが送信されます。
  8. 次へをクリックします。
  9. ドロップダウンリストから、レプリケーションタイプを選択します。
  10. 次へをクリックして処理の詳細を確認します。処理を作成後に変更することはできません。
  11. 作成またはスケジュールをクリックして、処理を作成します。手動によるアクティブ化を選択した場合は、「開始」をクリックしてプロセスを作成し、すぐに実行します。

B2C Commerce でのデータレプリケーション処理の作成

データレプリケーション処理を手動でトリガーするか、指定した時刻に実行するように、または指定した間隔で繰り返して実行するようにスケジュールするか、ジョブを作成して実行します。

所有している Salesforce Commerce 製品

  1. アプリケーションランチャーをクリックし、管理 | レプリケーション | データのレプリケーションの順に選択します。既存のデータレプリケーション処理のリストが表示されます。
  2. 既存の処理をコピーするか、最初から処理を作成します。
    • 既存の処理をコピーするには、リストからコピーする処理を選択して、コピーをクリックします。複数の処理を選択し、一度にコピーします。生成されたプロセスを変更するには、プロセス ID をクリックして詳細ページを開き、編集をクリックします。
    • レプリケーション処理を最初から作成する場合は、新規をクリックして、手順に従って処理を構成します。
  3. システムによって処理 ID が生成されます。別の ID を入力します。
  4. ドロップダウンリストから、ターゲットインスタンスを選択します。
  5. (オプション) 説明を入力します。
  6. ドロップダウンリストから、ページキャッシュの無効化の戦略を選択します。
    • 無効にする: (デフォルト) レプリケーション処理の最後にターゲットインスタンスでページキャッシュが更新されます。
      メモ キャッシュをクリアすると、サイトのパフォーマンスが一時的に低下します。
    • 影響を受けるキャッシュパーティションを無効にする: 現在のレプリケーション処理で選択されているものと一致するレプリケーションタスクが割り当てられているページキャッシュパーティションはすべて無効になります。ストアフロントのページの残りの部分はキャッシュされます。は手つかずのままです。
    • 無効にしない: ページキャッシュは更新されません。このオプションは、トラフィックが多い時間帯に選択します。ただし、キャッシュを更新しないと、ストアフロントで顧客に古いコンテンツが表示される可能性があります。このオプションを使用する際には充分に注意してください。
  7. ドロップダウンリストから、アクティブ化のタイプを選択します。データは、処理を定義した時点ではなく、処理が実行される時点の状態でレプリケートされることに注意してください。
    手動 処理は手動でトリガーした場合に実行されます。
    自動 処理を実行する日時を 1 つスケジュールします。このオプションを選択すると、日付と時刻のフィールドが表示されます。デフォルト値は翌日の午前 0 時です。
    繰り返し 処理を繰り返し実行する時間をスケジュールします。このオプションを選択すると、間隔、日付、時刻のフィールドが表示されます。デフォルト値は毎日午前 0 時です。
    ジョブステップ 処理をジョブの一部として実行できます。
  8. ドロップダウンリストから、通知 Eメールのトリガーを選択します。受信者の Eメールアドレスを複数入力する場合は、コンマで区切ります。
    - なし - Eメールは送信されません。
    処理終了時 成功か失敗かにかかわらず、処理が終了した際に指定したアドレスに Eメールを送信します。処理がハングした場合は、Eメールは送信されません。
    処理失敗時 処理が失敗した場合にのみ、指定したアドレスに Eメールを送信します。処理が成功またはハングした場合は、Eメールは送信されません。
    定期的 間隔を分数で入力します。処理の実行中、処理が終了するまで指定したアドレスにこの間隔で Eメールが送信されます。処理が成功または失敗した際にも Eメールが送信されます。
    Eメールによる通知には、処理の開始時刻および終了時刻、ターゲットシステム、レプリケーションタイプ、および含まれるレプリケーションタスクが含まれます。エラーが発生した場合は、エラーコードも含められます。繰り返しの処理ごとに、独自の通知が送信されます。
  9. 次へをクリックします。
  10. ドロップダウンリストから、レプリケーションタイプを選択します。
  11. 含めるレプリケーションタスクを選択します。B2C Commerce でのデータレプリケーションタスクを参照してください。
    新しいサイトのサイトレベルのレプリケーションタスクは、グローバルレベルのサイトタスクを含むレプリケーションを正常に完了するまで無効になります。
  12. 次へをクリックして処理の詳細を確認します。
  13. 作成またはスケジュールをクリックして、処理を作成します。手動によるアクティブ化を選択した場合は、「開始」をクリックしてプロセスを作成し、すぐに実行します。
    データのレプリケーション処理の開始後は、削除することはできません。

ジョブパラメーターの作成

さまざまなジョブステップで使用するパラメーターを作成します。たとえば、ReplicationProcessID のパラメーターを作成し、特定のレプリケーション処理の ID に設定します。次に、このパラメーターを異なるジョブステップで使用します。別のレプリケーション処理を使用する必要がある場合は、このパラメーターの値を変更すると、そのパラメーターを含むすべてのステップが B2C Commerce によって更新されます。Open Commerce API (OCAPI) を使用してジョブを実行する場合は、ジョブパラメーターの値を上書きします。このトピックは、B2C Commerce に該当します。

必要なエディション

使用可能なソリューション: B2C Commerce

ジョブステップ内にジョブパラメーターを作成します。ジョブパラメーターは、このジョブパラメーターを設定した元のパラメーターと同じタイプのステップパラメーターにのみ使用してください。たとえば、true または false のブール値を必要とするステップパラメーターのジョブパラメーターを作成する場合は、このジョブパラメーターを使用してテキスト文字列のエントリを必要とする値を指定することはできません。

  1. ジョブステップを作成するか、既存のジョブステップを選択します。
  2. パラメーターの作成対象であるフィールドをクリックします。
  3. ジョブパラメーターをクリックします。
  4. ジョブパラメーターの追加をクリックします。
  5. パラメーターに一意の名前を入力します。
    パラメーターには SiteScope という名前は付けないでください。この名前は、範囲がサイトパラメーターのフローのために予約されています。
  6. パラメーターの値を入力します。
  7. 保存をクリックします。
  8. 割り当てるをクリックします。
  9. パラメーターを別のジョブステップで使用するには:
    1. パラメーターを使用するフィールドをクリックします。
    2. ジョブパラメーターをクリックします。
    3. 使用するパラメーターを選択します。
    4. 割り当てるをクリックします。

B2C Commerce のジョブの作成

ジョブを作成する際には、少なくとも 1 つのフローを構成し、各フローで実行するステップを選択します。コードを作成する必要なしに、すぐに使用可能なシステムジョブステップを使用できます。必要な処理を行うシステムジョブがない場合は、デベロッパーにカスタムジョブステップの作成を依頼します。また、ジョブを実行する日時のスケジュール設定、ジョブ実行中にロックするリソースの指定、Eメールによる通知やエラーハンドリングの構成を行うことができます。

必要なエディション

使用可能なソリューション: B2C Commerce
  1. アプリケーションランチャーをクリックし、次に管理 | オペレーション | ジョブの順に選択します。
  2. 新規ジョブをクリックします。
  3. ID と説明を入力します。
  4. 作成をクリックします。
  5. (オプション) 特定の日時に実行するジョブ、または定期的に実行するジョブをスケジュールします。
    Sandbox (サンドボックス) インスタンスでは、ジョブのスケジュールはサポートされていません。
    1. スケジュールと履歴をクリックします。
    2. 有効をクリックします。
    3. 「アクティブ」で 1 回限り実行または定期的な実行間隔を選択し、日付、または日付や時刻の範囲を指定します。
      メモ Business Manager のジョブスケジューラーは、分単位までの精度にのみ対応しています。インターフェースでは秒が表示され、編集もできますが、秒を変更しても実際のスケジュールには影響しません。

  6. (オプション) ジョブの処理中にリソースが変更されるのを防止するために、リソース、選択とクリックして、リソースのタイプと値を選択します。

    1. ジョブステップをクリックします。
    2. 同位フローのセットを追加するには、をクリックします。
    3. 同位フローの各セットに対し、並行処理または順次処理を指定します。
    4. 別の順次フローを追加するには、フローの下部にあるをクリックします。
    5. フローの範囲を選択します。
      • 組織: フローはインスタンスに対して実行されます。
      • すべてのストアフロントサイト: フローは、ジョブの実行時に使用可能なすべてのストアフロントサイトで実行されます。フローは、Business Manager サイト、またはステータスが削除対象となっているサイトでは実行されません。
      • 特定のサイト: フローは選択したストアフロントサイトでのみ実行されます。
      • サイトパラメーター: フローは、Open Commerce API (OCAPI) Data API を使用して渡すサイトで実行されます。ジョブは Business Manager から実行することはできず、ジョブを自動的に実行するようにスケジュールすることはできません。Business Manager で「ただちに実行」ボタンとスケジュールのオプションは無効になります。このオプションを選択すると、SiteScope パラメーターが空の値でジョブに追加されます。OCAPI Data API を使用して、SiteScope に 1 つまたは複数の特定のサイト、あるいはすべてのストアフロントサイトを指定します。
  8. フローにステップを追加します:
    CreateSitemap などの一部のジョブステップは、サイトのコンテキストでのみ実行できます。また、ExecuteDataReplication などのジョブステップは、組織のコンテキストでのみ実行できます。ステップでサポートされていない範囲をもつフローにジョブステップを割り当てようとすると、ステップにエラーが表示されます。
    1. ジョブステップタブで、ステップを追加するフローを選択します。
    2. ステップを設定をクリックして、ステップを選択します。
    3. ステップパラメーターを構成します。
      必須のパラメーターには赤いアスタリスクが付いています。一部のパラメーターでは、パラメーターの上にマウスを置くと、入力する内容に関する情報が表示されます。
    4. このジョブステップを、すでに完了した場合でもジョブをリスタートした場合に常に実行するかどうかを選択します。
    5. ジョブステップが終了する場合に適用されるルールを構成するには、終了ステータスのルールでルールの追加をクリックします。
      ジョブステップの終了ステータスコードは、ジョブステップが正常に実行されたかどうかを示します。通常、終了コードが ERROR の場合は、ジョブステップが失敗したことを示しています。終了コード OK は成功を示します。デフォルトでは、終了コード ERROR は「ジョブの停止」アクションにマッピングされます。その他のすべての終了コードは、デフォルトで「次のステップに進む」アクションにマッピングされます。
    6. 次の場合フィールドの各終了ステータスコードと * に対して操作を選択します。
      * は、ルールのない任意の終了ステータスコードを示すワイルドカードです。
      • ジョブの停止: それ以降のジョブステップは実行されません。ジョブ実行の全体が失敗しました。ステップが並列フローの一部で、失敗したステップと並行して他のステップがまだ実行中の場合は、並列ステップの実行が完了した時点でジョブの実行が失敗します。
      • フローの停止: 同じフローの後続のジョブステップはスキップされ、実行は次のフローに進みます。
      • 次のステップを続行: 同じフローに他のステップがある場合は、実行はフロー内の次のステップに進みます。同じフローに他のステップがない場合は、実行は次のフローの次のステップに進みます。
      • <ステップ> を続行: 同じフロー内の指定されたジョブステップにジャンプします。
    7. 割り当てるをクリックします。
  9. ジョブのエラーハンドリングを構成するには:
    1. エラー処理を選択します。
    2. 失敗ルールを選択します。失敗ルールは、ジョブが ERROR ステータスで終了した場合に呼び出されます。
      • スケジュール済みとして続行: ジョブは次回のスケジュールされている時刻に実行されます。
      • エラー時停止: ジョブスケジュールが無効になり、以降は実行されなくなります。
      • 再試行: エラー時にはジョブが最初からやり直されます。このオプションでは、再試行の回数と再試行の間隔を構成します。
  10. ジョブステータスについて Eメール通知を送信するには:
    1. 通知をクリックします。
    2. 通知をトリガーするイベントを少なくとも 1 つ選択します。
    3. 有効を選択します。
    4. Eメールの送信者と受信者の Eメールアドレスを入力します。
    5. (オプション) 延長ランタイム検知を選択して、実行時間を指定します。

レガシージョブの作成

レガシージョブでは、デベロッパーが Eclipse IDE への UX Studio プラグインを使用して作成するパイプラインが使用されます。この機能は廃止予定となりました。新しいジョブフレームワークを使用してジョブを作成することをお勧めします。

必要なエディション

使用可能なソリューション: B2C Commerce

この作業を行うには、以下を把握しておく必要があります:

  • ジョブのパイプラインと開始ノード。
  • パイプラインで必要なパラメーター。
  • ジョブの実行中に更新されるシステムオブジェクト。

  1. アプリケーションランチャーをクリックし、次に管理 | オペレーション | ジョブ (廃止予定)の順に選択します。

  3. 名前と説明を入力します。
  4. 実行範囲を指定します。
  5. パイプライン名と開始ノードを入力します。
  6. ジョブを 1 回実行する日付を入力するか、繰り返し実行する間隔を指定します。
  7. 適用をクリックします。
  8. 実行範囲がサイトのジョブでは、サイトをクリックして 1 つまたは複数のサイトを選択します。
    範囲が複数サイトのジョブはランタイム時に 1 つのサイトにつき 1 つのジョブに分割されます。分割されたジョブの 1 つが失敗した場合、そのジョブで再試行が行われ、失敗の通知が個別に行われます。分割されたジョブは、ジョブ履歴にも別々に表示されます。
  9. リソースをクリックします。
  10. ジョブで変更または更新するオブジェクトを選択し、割り当てるをクリックします。
    リソースをジョブに割り当てると、このジョブが処理されている間、別のジョブまたはユーザーがそのリソースを変更できなくなります。たとえば、ジョブによるカタログの更新中に、別のジョブやユーザーがカタログ、カテゴリ、商品を変更できないようにします。
  11. ジョブステータスについて Eメール通知を送受信するには、通知をクリックして、Eメールアドレスと通知設定を構成します。
  12. ジョブパイプラインでパラメーターが必要な場合は、パラメーターをクリックして、各パラメーターの名前と値を入力します。

B2C Commerce でのインポートのためのデータファイルの作成

データの構造と範囲を理解し文書化したら、既存のデータを B2C Commerce 形式に変換する方法をマッピングします。また、データを B2C Commerce 環境から顧客の環境にエクスポートして戻す方法もマッピングする必要があります。

以下のタスクを実行します。

  • B2C Commerce サイトを設定する
  • インポートファイルの仕様を作成する
  • ファイルの転送、作成、インポートのプロセスを定義する

インポートファイルの仕様

  • ファイルの仕様を構築するための開始点として B2C Commerce スキーマを使用します。
  • サンプルのエクスポートファイルを見るには、ファイルをリファレンスアプリケーションからエクスポートします。

転送とインポートのプロセス

必要なフィードの数を特定します。各データフィードについて、以下を決定します:

  • バックエンドシステムからのファイルの転送方法
    • ファイル転送メカニズム
    • 頻度 (ページキャッシングパフォーマンスへの影響を考慮する)
  • データのインポート先

    通常はデータをステージングにインポートしますが、小さいデータセットを頻繁にインポートする場合は、ステージングと本番の両方にインポートできます。

  • 使用しているバックエンドシステムと連動し、マーチャントの要求を満たせるインポートモデルはどれか (たとえば、完全、増分、更新、置換)

この処理が、ステージングやインデックス作成など他の処理にどのような影響を与え、これらの処理とどのように関連するかを検討します。目的は、マーチャントのデータファイルを B2C Commerce XML ファイル形式に変換するために使用できる、繰り返し可能な処理を構築することです。処理は、スケジュールを使用して、または Business Manager からオンデマンドで実行します。

フィードファイルの作成

最大 3 つの新しいフィード定義を作成します。フィールド定義は、インポートする属性で異なるインポート頻度 (毎日と毎週) が必要な場合、または属性が異なるバックエンドシステムからフィードされる場合に使用します。

  1. インポートしたいカスタムアクティブデータの属性を作成します。
  2. アプリケーションランチャーの順にクリックし、マーチャントツール | オンラインマーケティング | アクティブデータ | フィード定義の順に選択します。
  3. フィードの定義ページにある商品のアクティブデータセクションで、新規をクリックします。
  4. 新規商品のアクティブデータフィードのページで、フィードの属性および列を編集します。
  5. 適用をクリックします。
  6. フィードファイルをインポートします。

アクティブデータフィードの作成

サイトでアクティブデータが使用可能になっている場合、Business Manager のシステムオブジェクトによって定義されている特定のデータが Production (本番) インスタンスでキャプチャされます。これらのデータは、自動的に Production (本番) インスタンスと Staging (ステージング) インスタンスにインポートされます。

メモ アクティブデータフィードはレプリケートされますが、アクティブデータはレプリケートされません。

Sandbox (サンドボックス) インスタンスでこのデータを使用するには、Production (本番) インスタンスからこのデータ (.csv 形式) をダウンロードして、それを Sandbox (サンドボックス) インスタンスにインポートします。Production (本番) インスタンスの impex ディレクトリから WebDAV 経由で直接 csv ファイルを入手することもできます。

このデータを Salesforce B2C Commerce の外部で追加の分析やレポートに使用するには、データをエクスポートします。

キャプチャされたデータは、CustomerActiveData および ProductActiveData システムオブジェクトで定義します。これらのシステムオブジェクトのほとんどの属性は、B2C Commerce の Merchandising Analytics の処理によって、次の自動化フィードで使用されます:

  • B2C Commerce 商品のアクティブデータ
  • B2C Commerce 商品の週次アクティブデータ
  • B2C Commerce 顧客のアクティブデータ
  • B2C Commerce 顧客の週次アクティブデータ

B2C Commerce のサイトマップ属性のフィード

サイトマップ属性である変更頻度、優先度、および含める条件ステータスは、catalog.xsd および library.xsd のインポート/エクスポート XML スキーマに表示されます。

Salesforce では、各カテゴリや商品のサイトマップ属性値を手入力する手間を省くため、サイトマップ属性値の作成を自動化することをお勧めします。コンテンツ項目については、めったにインポートされることがないため、この属性値は手入力します。

B2C Commerce でのジョブの作成

Business Manager を使用してジョブを作成します。ジョブの作成には新しいジョブフレームワークを使用することをお勧めしますが、Business Manager ではレガシーの廃止予定の機能も使用できます。

  • B2C Commerce のジョブの作成
    ジョブを作成する際には、少なくとも 1 つのフローを構成し、各フローで実行するステップを選択します。コードを作成する必要なしに、すぐに使用可能なシステムジョブステップを使用できます。必要な処理を行うシステムジョブがない場合は、デベロッパーにカスタムジョブステップの作成を依頼します。また、ジョブを実行する日時のスケジュール設定、ジョブ実行中にロックするリソースの指定、Eメールによる通知やエラーハンドリングの構成を行うことができます。
  • ジョブパラメーターの作成
    さまざまなジョブステップで使用するパラメーターを作成します。たとえば、ReplicationProcessID のパラメーターを作成し、特定のレプリケーション処理の ID に設定します。次に、このパラメーターを異なるジョブステップで使用します。別のレプリケーション処理を使用する必要がある場合は、このパラメーターの値を変更すると、そのパラメーターを含むすべてのステップが B2C Commerce によって更新されます。Open Commerce API (OCAPI) を使用してジョブを実行する場合は、ジョブパラメーターの値を上書きします。このトピックは、B2C Commerce に該当します。
  • ジョブパラメーターの編集
    ジョブパラメーターの値を変更すると、そのパラメーターを含むすべてのステップが新しい値に更新されます。
  • ジョブ実行中のシステムリソースのロック
    ジョブを作成する場合は、そのジョブの実行中に別のジョブがシステムリソースを変更することを防止します。ジョブに割り当てるシステムリソースを知るには、どのリソースがどのエンティティに関連するかを理解します。たとえば、ジョブで顧客が変更される場合、顧客はプロフィールシステムリソースと関連するので、システムリソースプロフィールをジョブに割り当てます。ジョブの実行中に別のジョブがプロフィールシステムリソースを変更することはできず、ジョブの結果が予想外のものに変わることがありません。リソースロックは再入可能ロックです。つまり、ジョブがリソースをロックする場合、このジョブのジョブステップは同じリソースを再度ロックすることができます。商品インデックスの再作成タスクは、それ自体を除いてリソースロックを必要としません。ただし、商品インデックスの更新タスクには、商品、カタログ、およびカテゴリに対するリソースロックが必要です。このトピックは、B2C Commerce に該当します。
  • ジョブステップの使用
    ジョブフレームワークには、すぐに使用できるシステムステップが含まれています。ジョブフローでシステムステップを使用する場合、コーディングは必要ありませんが、ほとんどのジョブステップでは一部のパラメーターを構成する必要があります。目的の処理を行うシステムステップがない場合は、デベロッパーにカスタムジョブステップの作成を依頼します。このトピックは、B2C Commerce に該当します。
  • B2C ストアフロントのカスタムジョブのトラブルシューティング

イベントファミリーの DMO マッピング

各イベントファミリーは、Data 360 内の特定のデータモデルオブジェクト (DMO) にマッピングされます。B2C Commerce がエンゲージメントイベントをキャプチャすると、そのデータは Data 360 が処理可能な標準化された DMO フィールドに変換されます。各イベントファミリーには、顧客インタラクションの種類に基づく個別のマッピングがあります。

各ファミリーのマッピングリファレンスには、次の情報が含まれます。

  • B2C Commerce のソースフィールド
  • Data 360 のターゲット DMO フィールド
  • フィールド要件 (必須またはオプション)
  • マッピング時に適用されるデータ変換
  • 買い物カゴ管理ファミリーの DMO マッピング
    買い物カゴ管理のインタラクションは、顧客が商品を買い物カゴに追加したとき ( cart-add )、買い物カゴから商品を削除したとき ( cart-remove )、数量と商品オプションを変更したとき ( cart-update ) をキャプチャします。これらのインタラクションは、買い物カゴレベルのイベントには ShoppingCartEngagement、個々の商品品目には ShoppingCartProductEngagement という 2 つの DMO にマッピングされます。
  • 注文手続きプロセスファミリー
    チェックアウトプロセスのインタラクションでは、顧客がいつチェックアウトを開始したか ( checkout-begin )、チェックアウトステージの進行 ( checkout-step )、連絡先情報の提供 ( checkout-contact-info、廃止予定)、チェックアウト中にアカウントを作成するタイミング ( checkout-user-register )、最終注文を送信するタイミング ( checkout-submit ) がキャプチャされます。これらの対話は、チェックアウトイベントの WebsiteEngagement DMO にマッピングされ、あわせて顧客データ取得のために Individual、ContactPointEmail、ContactPointPhone、ContactPointAddress の各 DMO にもマッピングされます。
  • 顧客プロフィール管理ファミリー
    Customer Profile Management のインタラクションでは、新しい顧客アカウントの作成 ( user-register ) とプロファイルの変更 ( update-user-profile ) がキャプチャされます。これらのインタラクションは、顧客の基本となる識別情報を表す Individual、Eメールアドレス用の ContactPointEmail、電話番号用の ContactPointPhone、住所情報用の ContactPointAddress、システム間 ID 連携に使用される PartyIdentification の 5 つの DMO にマッピングされます。
  • 注文処理ファミリー
    注文処理インタラクションは、注文が正常に処理され、承認 ( order-accepted ) された時点をキャプチャします。このインタラクショは、注文完了イベント用の ProductOrderEngagement DMO にマッピングされ、Individual オブジェクトと ContactPoint オブジェクトを使用して顧客プロフィールデータを更新することもできます。
  • 商品発見ファミリー
    Product Discovery インタラクションは、顧客が商品検索 ( search )、商品詳細ページの表示 ( catalog-object-view-start )、商品のインプレッションの表示 ( catalog-object-impression ) を実行した時点をキャプチャします。これらのインタラクションは、検索アクティビティ用の WebSearchEngagement と、商品の表示と参照用の ProductBrowseEngagement の 2 つの DMO にマッピングされます。
  • コンテンツエンゲージメントファミリー
    コンテンツエンゲージメントインタラクションは、顧客がさまざまなサイトページ( ページビュー )にアクセスしたタイミングをキャプチャします。このインタラクションは、一般的なサイト操作用の WebsiteEngagement DMO にマッピングされます。
  • ほしい物リスト管理ファミリー
    ウィッシュリスト管理のインタラクションは、顧客が後で使用するために商品を保存するタイミング ( wish-list-add ) と、ウィッシュリストからアイテムを削除するタイミング ( wish-list-remove ) をキャプチャします。これらのインタラクションは、ほしい物リスト操作用の WebsiteEngagement DMO にマッピングされます。

Apache Iceberg File Federation コネクタを使用すると、すべての B2C Commerce ドメインデータをData 360に取り込むことができます。これには次のものが含まれます。

  • 製品 (商品製品、マスター製品、バンドル)
  • 製品カタログとカテゴリ
  • 販売注文および注文詳細
  • 顧客プロフィール
  • 商品と顧客プロフィールのカスタム属性

接続を設定したら、ソース オブジェクトをデータ モデル オブジェクト (DMO) に手動でマップする必要があります。使用可能なソースオブジェクトとそのマッピングの詳細については、「B2C Commerce ドメインデータマッピング」を参照してください。ソーステーブルスキーマの詳細については、「B2C Commerce レイクハウススキーマリファレンス」を参照してください。

  1. Data 360で[設定 ] をクリックし、[ Data Cloud 設定 ] を選択します。
  2. [外部統合] で [ その他のコネクタ]を選択します。
  3. 新規をクリックします。
  4. 「ソース」タブで、「Apache Iceberg ファイル・フェデレーション」を選択し、「次へ」をクリックします。
  5. 接続名と接続 API 参照名を入力します。
  6. 認証の詳細を入力します。

    B2C Commerce データストアのRESTカタログはストレージ認証情報の販売をサポートしているため、ストレージタイプとしてCATALOG_PROVIDEDを選択します。

    [RESTカタログ] の [ クライアントアクセストークン ] フィールドに、Base64 でエンコードされた値{tenant_id}:{account_manager_client_id}:{account_manager_client_secret}を入力します。

    これらの値を取得するには、次のようにします。

    • tenant_id :テナント ID は B2C Commerce の組織 ID の一部です。組織 ID の形式はf_ecom_{tenant_id}です。たとえば、組織 ID がf_ecom_zzzz_001の場合、テナント ID はzzzz_001です。
    • account_manager_client_id :Account Manager で API クライアントを作成したときに生成されるクライアント ID。
    • account_manager_client_secret :Account Manager で API クライアントを作成する際に設定したパスワード。

    Account Manager クライアントにはSalesforce Commerce APIロールが必要です。この役割を割り当てる際には、インスタンスフィルターを使用して本番 B2C Commerce インスタンスを検索して追加します。

    Account Manager API クライアントの作成については、B2C Commerce での API クライアントの追加を参照してください。このトピックのステップを実行して Iceberg コネクターの API クライアントを設定する場合は、ステップ 9 (インスタンスフィルターを使用した Salesforce Commerce API ロールの割り当て) を実行します (これは Iceberg コネクターで必須です)。手順 10 と 11 (既定のスコープと OpenID Connect 設定) は、このコネクタには適用されないため、実行しないでください。

  7. 接続の詳細を入力します。

    [カタログエンドポイント ] に、Apache Iceberg REST カタログの Data Cloud アクセス可能な HTTPS URL を入力します。

    • Production: https://iceberg-catalog.analytics.commercecloud.salesforce.com
    • 非生産:https://iceberg-catalog.stg.analytics.commercecloud.salesforce.com

    オプションの倉庫フィールドは空白のままにします。

  8. 構成を確認するには、「接続のテスト」をクリックします。
  9. 保存をクリックします。
    コネクタの詳細が受け入れられると、接続が作成され、[コネクタ] の下に一覧表示されます。これで、データストリームを作成し、B2C Commerce データを DMO にマッピングできます。

接続を設定したら、取り込みたい B2C Commerce オブジェクトのデータストリームを作成します。データ ストリームの作成とソース オブジェクトを DMO にマッピングする方法については、「Apache Iceberg ファイル フェデレーション データ ストリームの作成」を参照してください。

  • B2C Commerce ドメインデータマッピング
    Apache Iceberg コネクタを使用して B2C Commerce ドメインデータを取り込む場合、これらのソースオブジェクトをData 360のデータモデルオブジェクト (DMO) に手動でマッピングする必要があります。
  • B2C Commerce レイクハウススキーマリファレンス
    B2C Commerce データレイクハウスは、商品カタログ、顧客、および販売注文のデータを、ccdl_プレフィックスを使用するエンティティテーブルに格納します。

  • Apache Iceberg ファイルフェデレーション接続のセットアップ
  • Apache Iceberg ファイル フェデレーション データ ストリームの作成

データキットのインストール

データキットを使用すると、B2C Commerce から Data 360 でデータストリームを簡単に定義できます。また、正しいスキーマとマッピングを使用してコネクターを簡単に構成できます。

必要なエディション

使用可能なソリューション: B2C Commerce
  1. ブラウザーウィンドウを開き、このリンクをたどります。
  2. Salesforce (Data 360) 組織にログインします。
  3. すべてのユーザーのインストールを選択します。
  4. 承認を受け入れます。
  5. アップグレードをクリックします。
