B2C Commerce での支払方法の支払ゾーンへの追加

買い物客が購入を完了する方法を構成するには、国または通貨に基づいて各支払ゾーンの支払方法をカスタマイズします。

必要なエディション

使用可能なソリューション: B2C Commerce

ゾーンに支払方法を追加する前に、マーチャントアカウントで少なくとも 1 つのチェックアウトタイプが有効になっていることを確認してください。

  1. Business Manager でアプリケーションランチャーをクリックし、マーチャントツール | サイト | 注文 | Salesforce Paymentsの順に選択します。
  2. 支払ゾーンの割り当てをクリックします。
  3. 支払ゾーンを選択します。
  4. 支払ゾーンに対して 1 つまたは複数の支払方法を選択します。
  5. 保存をクリックします。

Salesforce Payments の SiteGenesis 構成

一部制限がありますが、Salesforce Payments を SiteGenesis に追加します。

SiteGenesis インスタンスに Salesforce Payments を追加するには:

  • SiteGenesis の注文手続きのページに Salesforce Payments 複数ステップチェックアウト機能を追加します。
  • SiteGenesis の注文手続きのページに Paypal エクスプレスチェックアウトを追加します。
  • SiteGenesis の買い物カゴに Salesforce Payments エクスプレスチェックアウトを追加します。
  • SiteGenesis のミニ買い物カゴに Paypal エクスプレスチェックアウトを追加します。

Salesforce Payments を SiteGenesis に統合するには、以下の B2C SiteGenesis インスタンスコンポーネントを編集します。

  • SiteGenesis カートリッジ
    カートリッジは、プログラムコードとデータをパッケージ化してデプロイするためのメカニズムです。カートリッジは、ビジネス機能を拡張するために、または外部システムと統合するために使用します。カートリッジでは、一般的な機能、またはアプリケーション固有の機能を提供できます。
  • SiteGenesis コントローラー
    コントローラーは、ストアフロントのリクエストを処理するサーバー側スクリプトです。コントローラーはアプリケーション内のデータフローを管理し、ViewModel を作成してルートとして各ストアフロントリクエストを処理し、適切な応答を生成します。たとえば、ストアフロントアプリケーションでカテゴリメニュー項目をクリックしたり、検索用語を入力すると、ページを表示するコントローラーがトリガーされます。
  • SiteGenesis のモデルとビュー
    コントローラーはモデルとビューに統合されます。すべてのスクリプトは CommonJS モジュールであり、グローバル名前空間の汚染を防ぐために、エクスポートが定義およびドキュメント化されています。
  • SiteGenesis のサーバー側スクリプト
    サーバー側スクリプトはクライアント側リクエストを処理します。すべてのスクリプトは CommonJA モジュールであり、エクスポートが定義されています。
  • SiteGenesis のクライアント側のスクリプト
    クライアント側の js は、サーバーからの情報を必要としない機能を実行します。
  • Salesforce Payments 用の SiteGenesis のテンプレート、フォーム、および CSS
    デベロッパーは、Internet Store Markup Language (ISML) テンプレート、CSS、および B2C Commerce フォームを使用して Salesforce B2C Commerce ストアフロントページを作成し、ブラウザーに表示される HTML を生成します。これらのテクノロジーを使用して、ストアフロントの外観や印象をカスタマイズします。

B2C Commerce のガイド付きショッピング

B2C Commerce の Shopper Agent は、実店舗とオンラインショッピングの長所を融合させます。生成 AI と高度な言語モデルを搭載したこのエージェントは、顧客の商品発見と購入プロセスをガイドします。顧客は、B2C Commerce ストア内および複数の会話型プラットフォームで、買い物客エージェントによるパーソナル化されたサポートを受けることができます。

所有している Salesforce Commerce 製品

  • B2C Shopper Agent の設定に関する考慮事項
    B2C Commerce の Shopper Agent を設定する前に、サポートされている機能、使用方法、制限と許容量、制限、およびその他の問題を検討してください。
  • B2C Shopper Agent に必要なライセンス
    B2C Shopper Agent を有効にする前に、これらの必要なライセンスを有効にします。
  • Einstein 生成 AI の有効化
    顧客が B2C ストアを訪れたときに最高のショッピング体験を提供するには、Salesforce 組織で生成 AI 機能を有効にします。
  • ガイド付きショッピング向け Agentforce の有効化
    B2C Commerce のガイド付きショッピングに Agentforce を有効にします。
  • エージェントに B2C Commerce Shopper API へのアクセス権を付与します
    買い物客エージェントは、Shopper Login and API Access Service (SLAS) を介して B2C Commerce と通信します。SLAS への認可されたアクセスを取得するには、SLAS クライアントとシークレットを作成し、それらを使用して SLAS トークンを取得します。エージェントはこのトークンを使用して、SCAPI または OCAPI への認可済みの呼び出しを行います。
  • 買い物客エージェントの作成と初期設定
    顧客エンゲージメントを強化するために、B2C Commerce の Shopper Agent はパーソナライズされたリアルタイムの支援を提供し、買い物客が必要な商品をより速く、より自信を持って見つけられるように支援し、最終的に購入の増加につなげます。
  • 拡張チャットの設定
    買い物客は、モバイルアプリまたはデジタルストアフロントとのリアルタイムのチャットベースの会話を通じて、B2C Shopper Agent とエンゲージします。エージェントの拡張チャットを構成して、必要なメッセージングチャネルを設定します。
  • Storefront Next の Shopper Agent の設定
    Shopper Agent を Storefront Next と連携させるには、Managed Runtime (MRT) を設定します。MRT は Storefront Next ストアフロントのインフラストラクチャを提供し、買い物客エージェントが Salesforce 組織の拡張チャットサービスと通信できるようにします。デプロイされたバンドルに対して、Managed Runtime で正しい環境変数を設定します。
  • PWA Kit ストアフロントの買い物客エージェントの設定
    買い物客エージェントが PWA Kit ストアフロントと連携できるようにするには、マネージドランタイム (MRT) を設定します。MRT は PWA Kit ストアフロントのインフラストラクチャを提供し、買い物客エージェントが Salesforce 組織の拡張チャットサービスと通信できるようにします。デプロイされたバンドルに対して、Managed Runtime で正しい環境変数を設定します。
  • SFRA ストアフロントの買い物客エージェントの設定
    B2C SFRA ストアフロント用に Shopper Agent を設定するには、plugin_shopper_agentカートリッジを取り付け、Shopper Agent 機能を構成します。これらのタスクは Git と B2C Commerce インスタンスの両方で行います。
  • 会話コンテキストに基づく検索結果のパーソナライズ
    買い物客との会話中にエージェントが収集した情報に基づいて、パーソナライズされた商品リストを買い物客に提供します。会話のコンテキストを設定してから、エージェントの商品検索アシスタントサブエージェントの指示を更新して、エージェントが買い物客に適切な商品を見つけるために尋ねることができる質問を含めます。会話型発見のための質問に優先順位を付け、買い物客が B2C Commerce の Shopper Agent を使用して商品を検索するときに、その買い物客のカテゴリの好みを記憶します。
  • クーポンを適用するための B2C Shopper Agent の構成
    買い物客がクーポンコードを買い物カゴに手動で適用できるようにすることで、お金やその他のインセンティブを節約して、全体的な購入満足度を高めることができます。B2C Commerce Coupon Management エージェントのサブエージェントは、クーポンコードを買い物客の買い物カゴに適用し、複雑で階層化された割引を自動的に分類します。
  • B2C ストアフロントの Shopper Agent のローカライズ
    グローバル展開している店舗でエージェントを利用できるようにするには、エージェントが対応する言語を指定します。
  • B2C Commerce 買い物客エージェントのテスト
    B2C Shopper Agent をアクティブにする前に、B2C Shopper Agent をテストして、構成が適切であることを確認します。エージェントの「会話プレビュー」ウィンドウでプレビュー条件を追加し、会話を試します。
  • B2C ストアフロントからの拡張チャットのテスト
    買い物客が B2C Shopper Agent とチャットしてサポートを依頼できることを確認します。B2C ストアフロントから拡張チャットをテストします。

B2C Commerce でのマーチャントアカウントへの支払ゾーンの割り当て

マーチャントアカウントに 1 つ以上の支払ゾーンを割り当てます。すべての通貨と国に設定されたデフォルトの支払ゾーンは、最初に作成したマーチャントアカウントに割り当てられます。マーチャントアカウントに追加の支払ゾーンを割り当てて、どの支払方法をどのゾーンで使用できるかをさらにカスタマイズできます。

必要なエディション

使用可能なソリューション: B2C Commerce
  1. 支払ゾーンページからマーチャントアカウントに支払ゾーンを割り当てるには:
    1. Business Manager でアプリケーションランチャーをクリックし、管理 | サイト | グローバル環境設定 | 支払ゾーン の順に選択します。
    2. 対象の支払ゾーンのアクションメニューから、マーチャントアカウントの管理を選択します。
    3. 支払ゲートウェイとマーチャントアカウントを選択します。
    4. (オプション) PayPal をセカンダリ支払ゲートウェイとして構成します。
    5. 保存をクリックします。
  2. Salesforce Payments ページからマーチャントアカウントに支払ゾーンを割り当てるには:
    1. Business Manager でアプリケーションランチャーをクリックし、管理 | サイト | グローバル環境設定 | Salesforce Payments の順に選択します。
    2. 支払ゾーンを割り当てるマーチャントアカウントをクリックします。
    3. 「支払ゾーン」セクションで、割り当てるをクリックします。
    4. 少なくとも 1 つの支払ゾーンを選択し、割り当てるをクリックします。
      支払ゾーンがない場合は、「新しい支払ゾーンの作成」をクリックして、B2C Commerce の支払ゾーンを作成しに従って支払ゾーンを作成し、アカウントに追加します。

B2C Commerce の後払い決済サービス

B2C Commerce の後払い決済 (Buy Now, Pay Later) の支払オプションを使用すると、買い物客はすべての価格帯の商品を便利に購入できるようになります。Salesforce Payments では、Klarna と AfterPay を通じて後払い決済サービスを提供しています。

  • B2C Commerce での Afterpay を使用した後払い決済 (BNPL)
    Afterpay は Stripe マーチャントアカウントを通じて Salesforce Payments で注文手続きの支払方法として使用できます。Afterpay では、買い物客は無利子の分割払いで支払を行います。この機能は、B2C Commerce で利用可能です。
  • B2C Commerce での Klarna を使用した後払い決済 (BNPL)
    Klarna は、注文手続きの支払方法として利用できます。Klarna では、買い物客は注文の支払を 3 回または 4 回の無利子の支払に分割することができます。Klara を利用できる国については、Stripe のドキュメントを参照してください。この機能は、B2C Commerce で利用可能です。

B2C Commerce の「今すぐ購入」と「今すぐ支払う」の注文手続き方法

Salesforce Payments にはエクスプレスチェックアウトの体験として、2 つの方法が用意されています。「今すぐ購入」と「今すぐ支払う」です。「今すぐ支払う」では現在の買い物客の買い物カゴが必要であるのに対し、「今すぐ購入」では現在の買い物カゴは無視されます。

互換性のある Salesforce Reference Architecture (SFRA) バージョンでplugin_commercepaymentsを使用する場合、「今すぐ購入」と「今すぐ支払う」の両方がサイトに含まれています。これらは互いに依存していないため、両方またはいずれかを追加できます。サイトの注文手続き方法をカスタマイズする場合は、それぞれが独自の要件をもちます。

「今すぐ購入」では、特定の商品を購入するためのボタンが買い物客に表示されます。このボタンをクリックすると、その商品のみを含む買い物カゴが準備されます。この買い物カゴは、Apple Pay や Google Pay などの買い物客のデバイスとブラウザーにあったブラウザーの支払アプリを使用して、注文手続きを完了します。

「今すぐ支払う」では、買い物客には、買い物カゴに入っているものをすべて購入するために、ブラウザーの支払アプリを使用してチェックアウトを完了するためのボタンが表示されます。

buyNowButton テンプレート以外のすべては、SFRA app_storefront_base カートリッジの一部です。plugin_commercepayments カートリッジは buyNowButtons を含んでおり、これを含めるために addToCartButtonExtension を上書きします。

buyNowButtons テンプレートは表示モデルのデータに依存します。データがない場合は、ボタンは予想通りに機能しません。addToCartButtonExtension テンプレートは、エクスプレスチェックアウトを通じて購入される商品の商品モデルオブジェクトに buynowproduct という名前のページ変数を設定します。buyNowButtons を直接含める場合は、まず buynowproduct で互換性のあるオブジェクトを設定する必要があります。

Product-Show (商品-表示) コントローラーは、データを表示モデルに追加します。SFRA ベースコントローラーは、商品の在庫と入手可能性に関する情報を追加し、その情報を使用して商品が購入可能であるかどうかを判断します。商品を注文できない場合は、「今すぐ購入」ボタンは非表示になります。plugin_commercepayments カートリッジでもこのコントローラーにコードが追加され、エクスプレスチェックアウトのコードを注入するために必要な構成とその他の情報を含む dw.extensions.payments.SalesforcePaymentRequest オブジェクトが追加されます。詳細については、テンプレート、コントローラー、API のドキュメントを参照してください。

「今すぐ購入」では買い物客の既存の買い物カゴが必要なく、買い物カゴが存在する場合は無視されるため、注文手続きを完了するためにブラウザーの支払アプリに渡されるすべてのデータは買い物カゴとは独立して計算される必要があります。商品詳細ページがキャッシュされている場合、データもキャッシュされます。データは商品の価格や、税金、配送、プロモーションなどのその他のサイトの構成と一致する必要があります。データが一致する場合、結果として買い物カゴは、買い物客に対して支払アプリで表示されるものと一致します。買い物客は B2C Digital プラットフォームやカスタムコードとさらにやり取りすることなしに購入を完了するので、金額は正しくなります。

plugin_commercepayments カートリッジは、paymentHelpers スクリプト関数 getBuyNowData を提供し、商品モデルオブジェクトのデータを計算します。さらに checkoutHelpers スクリプト関数 calculateBuyNowData を使用して、特定の SKU、価格、数量、およびオプションのデータを計算します。これらの関数は提供されている状態でそのままサイトで使用できます。サイトのニーズをサポートするために、特定の商品、価格、配送方法、プロモーション、税金の計算をカスタマイズできます。商品詳細ページがキャッシュされている場合は、カスタム計算の出力もキャッシュできることを確認してください。

買い物客が合計の品目、またはブラウザーの支払アプリに表示されるその他のデータに影響する変更を行った場合は、「今すぐ購入」ボタンを更新します。この目的は、買い物客がボタンを使用したときに、結果として生じる買い物カゴと一致するデータが支払アプリに表示されるようにすることです。plugin_commercepayments カートリッジによって、Product-Variation コントローラーに追加されたコードのデータが再計算されます。データは応答に含められ、Salesforce Payments のクライアント側の JS API を使用して「今すぐ購入」ボタンが更新されます。SFRA では、バリエーション属性が変更された場合と、数量や商品オプションなどが変更された場合に、このコントローラーが呼び出されます。サイトでこのようなユースケースを更新するには、このコントローラーを呼び出すか、同様のパターンに従います。

ストアフロントセッション間での買い物カゴの永続化

買い物客のセッションの永続化を制御する、サイト固有の買い物カゴ設定を構成します。これらの設定は、BasketMgr メソッドの動作に直接影響し、セッション間で買い物カゴの状態を維持するための Cookie の使用を定義します。

次の 2 つのキー識別子が買い物カゴの取得に影響します。

  • dwsid (セッション ID): 現在のブラウザーセッションを追跡する一時的な Cookie。dwsid が変更された場合 (たとえば、セッションの満了など)、システムは匿名 Cookie に依存して永続性を保ちます。
  • dwanonymous (匿名 ID Cookie): dwsid の変更の有無にかかわらず、未登録 (ゲスト) 買い物客を、複数の訪問にわたって一意の保存済み買い物カゴに関連付けるために使用される永続的な Cookie。この Cookie が存在するかどうかによって、ゲスト買い物客に対する永続化が決まります。

グローバル制約

設定にかかわらず、以下のルールが常に適用されます。

  • 未登録の買い物客が買い物カゴを作成すると、その関連付けは買い物客の一意の ID を保管するdwanonymous Cookie によって維持されます。この Cookie を使用すると、一時的なセッション ID (dwsid) が変更または期限切れになった場合でも、システムは買い物カゴを取得できます。
  • 顧客が買い物カゴを作成して、登録またはログインを行った場合、その買い物カゴはセッション中保持され、所有権は顧客に移ります。
  • 顧客がログアウトすると、現在の買い物カゴは保存された場合でもセッションからクリアされます。
  • 買い物カゴの有効期間が切れると、その買い物カゴにはアクセスできなくなり、再作成できなくなります。
  • 支払情報が更新されない状態が 7 日間続くと、支払情報は買い物カゴから自動的に削除されます。
  • 登録済み顧客に属さない買い物カゴは、買い物客が最後に買い物カゴを操作してから 365 日を超えて永続化されることはありません。

買い物カゴ永続化の設定

  • 買い物カゴの保持: 顧客が新しいセッションを開始したときに、BasketMgr.getCurrentBasket() を使用して、システムが保存済みバスケットを自動的に検索して復元する条件を定義します。この設定は、返される買い物カゴが、構成された買い物カゴの有効期間内である場合にのみ適用されます。この設定は Shopper Commerce API (SCAPI)/OCAPI には関係ありません。
  • 買い物カゴの有効期限: 保存された買い物カゴが BasketMgr.getCurrentBasket() で使用できなくなるまでのシステム内で使用可能な期間を定義します。

買い物カゴ保持の設定

ユーザーセッションの開始と終了時における買い物カゴの処理を構成するには、保持と有効期間の設定を使用します。

登録済み顧客と未登録 (ゲスト) 顧客に対して異なる有効期間を定義します。買い物カゴの有効期限には次のルールが適用されます。

  • 買い物カゴの有効期限は、最終の変更から起算されます。
  • 登録済み顧客のデフォルトの有効期限は 240 分 (4 時間) です。
  • 有効期限は、異なる期間を必要とする特定のユースケースがある場合を除き、20,160 分 (14 日) から 43,200 分 (30 日) の間にすることをお勧めします。登録済み顧客に対する有効期限には、Maximum Basket Lifetime (買い物カゴの最大有効期限) API のクォータである 525,600 分 (365 日) が適用されます。API クォータの詳細については、API ドキュメントを参照してください。
  • 未登録顧客に対する最大有効期限は、43,200 分 (30 日) または登録済み顧客に対する有効期間のうち、短い方になります。
  • 未登録顧客に対する有効期限を指定しないと、デフォルトは最大有効期限になります。

重複する商品を買い物カゴに追加する際の処理

商品を買い物カゴに追加するときの処理設定は、顧客がすでに買い物カゴに入っている商品と同じものを追加しようとしたときの動作をコントロールします。商品は次のルールを使用して比較されます。

  • 環境設定が「リピートを許可しない」または「数量追加」の場合、商品の SKU、商品リスト ID、および在庫リスト ID が同じ場合に、商品は重複するものとなります。この比較では、null のリスト ID は他の null リスト ID のみと一致します。たとえば、在庫リストにない商品は、在庫リストにない別の商品とのみ一致することができます。
  • 環境設定が「リピートを許可する」の場合は、商品を追加しても他の既存の商品品目には影響はありません。
  • オプション商品は、環境設定の内容にかかわらず、常に新しい商品品目に追加されます。
  • バリエーションマスターを含む商品バンドルは、環境設定の内容にかかわらず、常に新しい商品品目に追加されます。
  • 買い物カゴ内の商品で属性が変更された場合、システムでは重複のチェックは繰り返されません。
商品を買い物カゴに追加するときの処理 説明
リピートを許可しない リクエストを無視します。
数量追加 既存の商品品目の数量に追加します。この設定はデフォルトです。

買い物カゴごとの商品品目の最大数

買い物カゴ内で許可する商品品目の数を制限するには、商品品目の最大数フィールドに値を入力します。この制限を超えて商品品目を追加しようとすると、エラーが返されます。この制限で考慮されるのは品目の行数で、数量ではありません。デフォルト値は 50 です。

メモ 制限は独立商品にのみ適用されます。配送料、オプション、ボーナス品目など、単独で購入することのできない依存商品はカウントされません。
メモ 「買い物カゴごとの商品品目数」オブジェクトのクォータは、独立商品と依存商品の品目を含め、各買い物カゴの商品品目数を 200 に制限します。オブジェクトクォータの詳細については、API ドキュメントを参照してください。

一時的買い物カゴ

一時的買い物カゴ API を使用して、B2C Commerce システムに一時的買い物カゴを作成します。一時的買い物カゴは、価格設定、プロモーション、クーポン、在庫、配送方法、注文の作成、注文の再オープンを含め、Shopper Baskets Script API、Open Commerce API (OCAPI)、および SCAPI によって有効になります。一時的買い物カゴには、注文手続きの準備をするために必要なすべてのデータが設定されますが、次の点で通常の買い物客の買い物カゴと異なります。

  • 非アクティブ状態が15 分間続くと買い物カゴの有効期限が切れます。
  • 買い物客は最大 10 個 (デフォルトでは 4 個) の一時的買い物カゴをもつことができます。一時的買い物カゴの数を構成するには、Business Manager でアプリケーションランチャーの順にクリックし、マーチャントツール | サイト名 | 買い物カゴの環境設定の順に選択して、「顧客 1 人あたりの一時的買い物カゴ」の値を設定します。
  • ゲスト、登録済み、エージェントのユースケースを含むすべての買い物客が利用可能です。

一時的買い物カゴでは、正確な合計、品目、プロモーション、入手可能性などを生成するために必要なすべての計算が、買い物客の通常のストアフロント買い物カゴに影響を与えることなく実行されます。一時的買い物カゴの計算結果を使用して、一時的買い物カゴに追加された商品の購入情報を表示します。また、一時的買い物カゴの注文手続きにも同じ計算を使用します。

一時的買い物カゴは、特定のユースケースを目的としています。たとえば、

  • 買い物客は、通常の買い物カゴに入っていない商品を購入したいと考えています。
  • 買い物客は商品表示ページの Apple Pay ボタンをタップし、これとは無関係の購入のための商品が含まれる現在のストアフロント買い物カゴに影響を与えずに、即時購入を行えます。
  • 買い物客は注文履歴ページの「再注文」ボタンをタップし、これとは無関係の購入のための商品が含まれる現在のストアフロント買い物カゴに影響を与えずに、過去に購入した商品を再注文できます。
  • 買い物客はほしい物リストページの「注文」ボタンをタップし、これとは無関係の購入のための商品が含まれる現在のストアフロント買い物カゴに影響を与えずに、商品を 1 点または複数購入できます。
  • マーチャントは、ソーシャルチャネルを通じて、プロモーション商品用の一時的買い物カゴを生成するリンクを共有します。
  • カスタマーサポートエージェントは、事前セット商品を含む「今すぐ購入」リンクを送信し、買い物客は自分で注文手続きを行います (支払いの詳細がサポートに送信されることはありません)。

B2C Commerce 向け Salesforce Payments の Adyen 構成

既存の Adyen マーチャントアカウントを、B2C Commerce の Sandbox (サンドボックス)、Staging (ステージング)、Development (開発)、または Production (本番) インスタンスの Salesforce Payments に統合できます。任意の B2C Commerce インスタンスをテストまたはライブの Adyen マーチャントアカウントに接続します。

Adyen のテストマーチャントアカウントとライブマーチャントアカウントは、異なるインフラストラクチャを使用します。テストマーチャントアカウントとライブマーチャントアカウントを切り替えることはできません。B2C Commerce インスタンスで Adyen のテストマーチャントアカウントとライブマーチャントアカウントの両方を使用するには、Business Manager で各マーチャントアカウントとそれぞれの API 認証情報を個別に設定します。

Salesforce では、まず Staging (ステージング) インスタンスでテストマーチャントアカウントを作成することをお勧めします。その後、そのマーチャントアカウントを Development (開発) インスタンスと Production (本番) インスタンスにレプリケートできます。インスタンス間でマーチャントアカウントをレプリケートした後、インスタンスでテストマーチャントアカウントとライブマーチャントアカウントのどちらを使用するかを選択します。Staging (ステージング) インスタンスと Development (開発) インスタンスでテストトランザクションを実行し、Production (本番) インスタンスで実際のトランザクションを実行します。

インスタンス内でマーチャントアカウントを作成する場合でも、インスタンス間でマーチャントアカウントをレプリケートする場合でも、API キーを設定してください。セキュリティを維持するため、API キーはレプリケートされません。

  • B2C Commerce への Adyen マーチャントアカウントの関連付け
    Adyen で Salesforce Payments を使用するには、既存の Adyen マーチャントアカウントを B2C Commerce インスタンスに関連付けます。Adyen マーチャントアカウントをお持ちでない場合は、まず Adyen からアカウントを取得してください。Salesforce Payments から Adyen マーチャントアカウントを作成することはできません。
  • B2C Commerce の Adyen マーチャントアカウント認証情報のテスト
    Adyen マーチャントアカウントの支払ゲートウェイ認証情報を検証します。
  • B2C Commerce からの Adyen マーチャントアカウントの削除
    Adyen マーチャントアカウントと B2C Commerce インスタンス間の関連付けを削除します。Adyen マーチャントアカウントがデフォルトの支払ゾーンにリンクされている場合は、先にデフォルトの支払ゾーンを別のマーチャントアカウントに再割り当てします。マーチャントアカウントを削除すると、B2C Commerce によってそのアカウントからすべての支払ゾーンの割り当てが解除されます。

B2C Commerce での Payments の Customer オブジェクトのインポートとエクスポート

B2C Commerce の Payments では、Customer オブジェクト (customer.xsd) を使用して、支払顧客に関するサイト固有データをインポートおよびエクスポートします。Customer オブジェクトの詳細については、「Customer オブジェクトのインポートとエクスポート」を参照してください。

エクスポート

Customer オブジェクトのエクスポートには、以下の要素をマッピングする PaymentsCustomer コンプレックスタイプが含まれます。

  • アカウント ID ⁻ Stripe マーチャントアカウント ID
  • ライブ ⁻ アカウントがライブか Sandbox (サンドボックス) か
  • 顧客 ID ⁻ Stripe ID
  • 作成日 ⁻ レコードの作成日

このマッピングは、システムが支払データを検索する場所を判断するための顧客データです。マッピングは顧客の支払データではありません。PaymentsCustomer 情報がデータベースにある場合、Salesforce Payments の機能トグルのステータスにかかわらず、エクスポートされます。

インポート

顧客のインポートでは、標準のインポートモードに基づいて、PaymentsCustomer マッピングが処理されます。

  • マージ
    • 欠落している PaymentsCustomer レコードを追加し、既存の情報を更新します。
    • 結果
      • すべてのインポートされた PaymentsCustomer レコードを利用できます。
      • 以前に作成された PaymentsCustomer レコードを利用できます。
      • 欠落している情報は変更されません。
  • 更新
    • 既存の PaymentsCustomer レコードを更新します。欠落しているレコードは追加されません。
    • 結果
      • すべての既存の PaymentsCustomer レコードを利用できます。
      • 以前に作成された PaymentsCustomer レコードを利用できます。
      • 欠落している情報は変更されません。
  • 置換
    • 顧客のすべての PaymentsCustomer レコードを削除します。
    • インポートファイルからすべての PaymentsCustomer レコードを再作成します。
  • 削除
    • 顧客のすべての PaymentsCustomer レコードを削除します。
    • 顧客を削除します。

マーチャントアカウントを利用できない場合、インポートでは警告がログ記録されます。

B2C Commerce のエクスプレスチェックアウトの考慮事項

エクスプレスチェックアウトは、多くの場合、チェックアウトよりも高速で使いやすいですが、クーポン、ギフトラッピング、買い物客の商品のカスタマイズ、ギフトカードの使用などの機能は、エクスプレスチェックアウトに必ずしも適しているとは限りません。

Apple Pay や Google Pay などのエクスプレスチェックアウトオプションはストアフロントでのコンバージョンを向上させますが、エクスプレスチェックアウトが複雑すぎる場合は逆効果です。ストアフロントの買い物客が予想する場所にエクスプレスチェックアウトボタンを追加し、支払アプリの操作をシンプルに保ちます。

互換性と設定

エクスプレスチェックアウトのオプションは、デバイスやブラウザーによって異なります。Salesforce Payments は、ブラウザーで使用可能な API を使用して、特定の買い物客に表示するボタンを決定します。クライアント側のコードは変更しないことをお勧めします。

Apple Pay

Web上のApple Payの利用に関するガイドラインに従います。ストアフロントが許可される使用の条件を満たさない場合は、Apple Pay を使用しないことを検討してください。また Apple では、マーケティングガイドラインとヒューマンインターフェイスガイドラインを提供しています。これらのガイドラインは、ストアフロントでエクスプレスチェックアウトオプションの表示を変更する場合に重要です。エラーメッセージの一部のガイドラインは W3C Payment Request API 標準でサポートされておらず、Salesforce Payments では使用できません。

2016 年以降のすべての Apple デバイスとオペレーティングシステムで Apple Pay がサポートされています。Apple Pay を Web 上で使用するには、買い物客がこの機能を有効にし、Apple Wallet にカードを追加し、Safari ブラウザーを使用することが必要です。詳細については、Apple サポートの Web サイトを参照してください。買い物客がこれらの条件を満たしている場合、エクスプレスチェックアウトに Apple Pay ボタンが表示されます。

Stripe のテストカードを Apple Wallet に追加することはできません。ストアフロントでテストモードを使用する場合、Stripe によって実際のカードがテストカードに置き換えられます。Apple Wallet では任意の Apple ID を実際のクレジットカードまたはデビットカードとともに使用しますが、テストモードで支払を行った場合はカードへの課金は行われません。Salesforce Payments と Stripe でテストするには、個別のアカウントを作成するか、他のApple の Sandbox テスト手順に従う必要はありません。

Adyen のストアフロントでテストモードを使用する場合、Adyen は Apple Sandbox Tester アカウントの作成を要求します。詳細については、「代替支払方法のテスト資格情報」および「Sandbox テスト」を参照してください。

Apple Pay をサイトで利用するには、Apple のマーチャント設定手順と構成を完了します。Salesforce Payments を使用すると、ドメイン登録後にマーチャントの識別や支払情報の暗号化に使用される証明書など、多くの手順が Stripe と Adyen によって自動的に完了されます。

Google Pay

Google Pay ブランド ガイドラインとユーザーエクスペリエンスに関するおすすめの方法を遵守します。技術的な詳細の多くは Salesforce Payments で処理されますが、許可される買い物客データの収集や使用などのその他のガイドラインは組織によって異なります。

Google Pay は多くのブラウザーとデバイスで使用できますが、Stripe ではすべての組み合わせがサポートされているわけではありません。買い物客はこの機能を自分の Google アカウントで有効にし、支払方法を追加し、支払が有効になったブラウザーを使用する必要があります。Google サポートの Web サイトとStripe の paymentRequestButton のドキュメントを参照してください。買い物客がこれらの条件を満たすと、Stripe によって Salesforce Payments のエクスプレスチェックアウトに Google Pay ボタンが表示されます。

一部のブラウザーでは、以前に使用したことがない場合、Google Pay ボタンの表示が許可されないことがあります。Google アカウントで Google Pay の設定が完了したら、デモサイトを訪問してそこで Google Pay ボタンをクリックします。たとえば、このデモサイトでこの問題が解決することが知られています。この問題は Chrome の既知の問題です。

Google Pay をご利用いただくには、クイックスタートガイドの完了をお願いしています。Salesforce Payments を使用する場合は、Salesforce Payments によって以下の手順が自動的に実行されます。

ストアフロントでエクスプレスチェックアウトの支払方法を表示する場所のカスタマイズ

注文の検索

ストアフロントで注文が作成されたら、Business Manager で注文の詳細を表示します。簡易検索または詳細検索のパラメーターを使用して検索するか、複数の注文番号で検索します。B2C Commerce では、大文字と小文字を区別せずに全文検索が行われます。

必要なエディション

使用可能なソリューション: B2C Commerce

複数語検索では、語順は考慮されません。すべての可能な語順で検索が行われます。ワイルドカードは使用できません。

品目の課税基準

B2C Commerce API (LineItem.updateTax ()) と Business Manager を使用して、注文内の品目に対する代替の税計算を構成します。この機能は、バックエンドシステムでは商品レベルの割引しか処理できないが、注文全体に税金を比例配分する必要がある品目を処理する場合に便利です。

品目の課税基準 は丸めによるエラーと、1 円合わない 問題を排除します。また、たとえば返品処理などの機能のために、注文レベルの割引と 1 個購入で 1 個無料 (BOGO) の割引を品目間に配分します。

この機能を使用すると、比例配分された価格 または注文レベルの割引と BOGO 割引を比例配分した後の価格にしたがって、品目は課税されます。注文の計算は変化しません。変更されるのは税金の計算のみです。つまり、ネット価格、グロス価格、基本価格を含むすべての既存の品目属性は、元の値を維持します。これらの品目の価格調整は注文の合計金額に含められますが、税金の金額は 0.00 のまま維持されます。

この機能はデフォルトでは無効になっています。この機能を使用するには、割引の課税をプロモーションのサイト環境設定で構成してください。

次の表は、品目の課税基準が有効な場合と無効な場合における、税金の計算を説明しています:

サイトの課税方針 調整価格に基づいて商品および送料のみに課税 - 設定が有効 価格に基づいて商品、送料、割引に課税 (デフォルト) - 設定が無効
ネット 税金 = 課税基準額 * 税率 税金 = ネット価格 * 税率
グロス 税金 = 課税基準額 * (1 - (1 / (1 + 税率))) 税金 = グロス価格 * (1 - (1 / (1 + 税率)))

品目の課税基準額は Business Manager の注文モジュールに表示され、データは注文のエクスポートに含められます。

メモ 品目の課税基準が無効の場合、品目の課税基準額は価格と同じになります。

B2C Commerce の Salesforce Payments と Salesforce Order Management のリンク

既存の B2C Commerce マーチャントアカウントを Salesforce Order Management と統合するには、まず B2C マーチャントアカウントを、Core Salesforce プラットフォーム上にある Salesforce Payments のマーチャントアカウントと Payment Gateway (支払ゲートウェイ) のレコードにリンクします。B2C マーチャントアカウント用に設定したものと同じ Stripe または PayPal のアカウントが、Core プラットフォームの新しいレコードにリンクされます。

マーチャントアカウントが Stripe のアカウントにリンクされている場合、Order Management は支払いデータを収集し、払い戻しを行うことができます。マーチャントアカウントが PayPal のアカウントにリンクされている場合は、Order Management は払い戻しのみを行うことができます。

2 つの製品を統合するには、Payments ライセンスと Order Management ライセンスが必要です。Connected Commerce ライセンスを使用することもできます。

Payments (支払) と Order Management (注文管理) を統合する手順は以下のとおりです。

  1. 同じ Core Salesforce プラットフォームの Org で「Salesforce Payments」と「注文管理」を有効にします。
  2. Salesforce プラットフォームの「支払」アプリケーションから、マーチャントアカウントのガイド付き設定に沿って、既存の Stripe または PayPal アカウントに連携するマーチャントアカウントを追加します。この支払ゲートウェイのアカウントは、B2C Commerce マーチャントアカウント用に設定されたアカウントである必要があります。Stripe またはPayPal で新規のアカウントは作成しないでください。
    メモ マーチャントアカウントをリンクする Stripe または PayPal のアカウントは、Stripe/PayPal を通じて購入済みの標準アカウントではなく、Salesforce 用に設定されたアカウントである必要があります。

注文後に、Order Management は注文の作成から履行、配送までの購入後のプロセスを処理します。

B2C Commerce での注文の管理

注文の処理に別のシステムを使用する一方で、B2C Commerce で最初に注文を作成する場合や、注文に関連する処理を管理する場合に Business Manager を使用することもできます。

  • 注文の検索
    ストアフロントで注文が作成されたら、Business Manager で注文の詳細を表示します。簡易検索または詳細検索のパラメーターを使用して検索するか、複数の注文番号で検索します。B2C Commerce では、大文字と小文字を区別せずに全文検索が行われます。
  • 注文の更新
    注文を送信後に更新することができます。たとえば、顧客情報を修正したり、ステータスを変更できます。Salesforce Order Management (SOM) を使用する場合は、注文 が Order Management に送信された後に Order Management で管理を行います。このトピックは、B2C Commerce に該当します。
  • 注文のキャンセル
    ステータスが「新規」、「未処理」、または「完了」の注文をキャンセルすることができます。失敗した注文をキャンセルすることはできません。配送注文、返品、または譲歩などのアクティブな後処理オブジェクトに関連付けられている注文をキャンセルするには、オブジェクトをキャンセルする必要があります。B2C Commerce Order Management を使用する場合は、注文 が Order Management に送信された後に Order Management で管理を行います。このトピックは、B2C Commerce に該当します。
  • Order Management への注文の再送信
    B2C Commerce で Order Management への注文の送信が失敗した場合、または送信した注文で情報が欠落している場合は、手動で再送信できます。再送信できるのは、ステータスが送信中または承認済みで、まだ割り当てが行われていない注文のみです。
  • B2C 店舗の注文エクスポートの遅延
    注文に対する非同期アクションの結果を待つために、注文のエクスポートを遅らせることができます。
  • 変更の追跡: 配送注文、請求書、または返品
    自動注文ルーティングと支払処理機能を B2C Commerce に統合したら、これらのジョブによって配送注文、請求書、返品に加えられた変更を注文ごとに Business Manager 注文モジュールで追跡できます。注文詳細ページの配送注文、請求書、返品の各タブはそれぞれ、配送注文、請求、返品が注文に含まれている場合にのみ表示されます。タブに表示される情報は読み取り専用です。
  • 注文の削除
    注文ステータスが「作成済み」、「キャンセル済み」、「置き換え済み」、または「失敗」の注文、またはエクスポートステータスが「エクスポート済み」で、関連付けられている交換注文がない注文は削除できます。注文を削除しても、Salesforce Order Management やその他の外部注文管理システムに保存されているデータは削除されません。このトピックは、B2C Commerce に該当します。

    課税方針 サイト内で商品およびサービス価格をグロス価格で扱うか、ネット価格で扱うかを指定します。このポリシーは、サイトの作成時に構成されます。変更できるのは Salesforce サポートのみです。
    住所のマッピング先

    Salesforce B2C Commerce で、顧客の配送先住所を基に課税管轄区域が検索される方法を規定します。

    管轄区域 ID に設定すると、住所マッピング 1 で設定されている住所属性は、管轄区域の ID と一致するかどうかで検索されます。

    管轄区域マッピング に設定すると、住所マッピング 1 および 住所マッピング 2 で構成されている住所属性は、サイトに設定されている管轄区域マッピングと一致するかどうかで検索されます。
    住所マッピング 1

    課税管轄区域の判定に使用する住所属性を選択するために使用します。

    住所マッピング 1 では、国、州、または郵便番号を選択します。

    住所マッピング 2 では、国/州や国/郵便番号などの属性の組み合わせを定義します。
    住所マッピング 2 住所のマッピング先 が管轄区域 ID に設定されていると、B2C Commerce は、自動的に住所マッピング 2 を未使用 に設定します。
  3. 税区分タブでは:

    • サイトの税区分を作成できます。

    • 1 つの税区分をデフォルト税区分として設定できます。特定の税区分に割り当てられていない商品およびサービスについては、この税区分が使用されます。
    • 税区分を削除します。
  4. 課税管轄区域タブで、サイトの課税管轄区域を指定します。

    課税管轄区域が管轄区域マッピングに基づいて判断される場合、B2C Commerce は、住所マッピング属性 1 (例: 州) とマッピング属性 2 (例: 郵便番号) の組み合わせで管轄区域を検索しようと試みます。特定の管轄区域が見つからない場合、マッピング属性 1 (例: 州) のみで表される管轄区域に戻ります。このマッピングで管轄区域が見つからない場合は、デフォルトの管轄区域が返されます。

    • 課税管轄区域を作成します。

    • デフォルト税区分として課税管轄区域を設定します。
    • 1 つ以上の課税管轄区域を削除します。
  5. 税率タブで、サイトの税率を指定します。このページでは、税区分と課税管轄区域のどの組み合わせについても税率を定義できます。
    • 税区分/課税管轄区域の組み合わせの除外 税率を入力します。
    • 税区分/課税管轄区域の組み合わせの標準 税率を入力します。

B2C Commerce での注文オブジェクトのインポートとエクスポート

外部システムとの統合や、テストデータを使用した作業のために、B2C Commerce では注文データを XML としてエクスポートおよびインポートできます。

注文のインポート

Business Manager で注文をインポートするには、サイト名 | 注文 | インポート & エクスポート | 注文 (XML) | インポートの順にクリックします。注文は、Production (本番) インスタンス以外の任意のサイト、または Production (本番) インスタンスのライブではないサイトにインポートできます。Production (本番) インスタンスのライブサイトに存在しない注文をインポートするには、Salesforce サポートにお問い合わせください。

メモ Salesforce サポートでは、既存の注文を更新するデータはインポートされません。注文のインポートプロセスの際には、このデータは省略されます。

注文の XML のデータ形式の詳細については、order.xsd スキーマファイルを参照してください。

未登録の顧客の注文をインポートすると、重複する顧客ナンバーが発生する場合があります。この問題を避けるために、注文 XML の Customer 要素にブール値の guest 要素を含めます。

  • guest が true の場合、注文データの顧客ナンバーが、システムの顧客ナンバーに対してチェックされます。この顧客ナンバーが既存の顧客ナンバーのいずれとも一致しない場合は、インポートされます。それ以外の場合は、省略されます。
  • guest が false の場合は、注文データの顧客ナンバーが、システムの顧客ナンバーに対してチェックされます。この顧客ナンバーが既存の顧客ナンバーと一致する場合は、インポートされます。それ以外の場合は、省略されます。
  • (注文 XML バージョン 19.2 以降) guest がない場合は、エラーがログされ、注文は省略されます。他の注文には影響はありません。

顧客ナンバーのチェックを正確に行うために、注文をインポートする前に顧客データをインポートします。

メモ guest 要素は注文エクスポートデータスキーマのバージョン 18.5 で追加されましたが、必須なのはバージョン 19.2 からです。この要素が確実にチェックされるように、注文 XML でバージョン 19.2 以降を指定することをお勧めします。

注文のエクスポート

注文情報のエクスポートには、order.xsd スキーマファイルを使用します。

注文をエクスポートする際には、次の情報を考慮します。

  • Business Manager またはカスタムアプリケーション内での注文ステータス
  • クレジットカードデータの処理方法
  • 詳細検索を行った後に注文を .csv ファイルにエクスポートすると、最初の 10,000 件の注文のみがエクスポートされること

注文エクスポートバージョンの設定

Salesforce B2C Commerce では、XML ベースのエクスポートで簡易バージョン管理に対応しています。このバージョン管理によって、組織が注文 XML への変更を承認できない場合に、固定のバージョンを引き続き使用することができます。

バージョンを指定するには、サイト名 | マーチャントツール | サイト名 | サイト環境設定 | 注文 | 注文エクスポート形式を選択し、バージョンを選択して適用をクリックします。

エクスポートで無視される注文

注文のエクスポートでは、作成済みステータスと失敗ステータスの注文は無視されます。作成済みステータスは処理中でまだエクスポートできる状態になっていない注文を表し、失敗ステータスはエクスポートに適さない注文をマークします。

注文エクスポートと注文在庫

商品 X の 1 個の注文が送信されると、エクスポートの前であっても売上数量は 1 と表示されます。割り当てが更新されると、売上数量が 0 にリセットされ、販売過剰の状態になる可能性があります。

この状況を回避するには、注文在庫を有効に設定します。サイト名 | マーチャントツール | サイト名 | 商品とカタログ | 在庫リストの順に移動し、在庫リストの ID をクリックし、注文在庫の有効化オプションにチェックを入れて、適用をクリックします。

「注文在庫の有効化」にチェックが付いている場合、まだエクスポートされていない注文には注文中の金額が設定されます。商品は、注文がエクスポートされてから最終 とマークされます。この設定にチェックが付いていない場合、まだエクスポートされていない注文には注文中の金額が設定されません。商品は、注文がエクスポートされてから最終とマークされます。

Business Manager を使用して注文エクスポートのコピーを作成する場合は、ジョブステータスを変更せずにエクスポートジョブを実行できます。これは、この時点ではまだ注文がエクスポート用にクリアされていないからです。また、注文在庫の有効化にチェックが付いている場合、注文エクスポートステータスがエクスポート済みに変更されたときに、関連するすべての注文在庫トランザクションが最終在庫トランザクションに変わります。この設定を使用して、処理のこの部分を制御することができます。

メモ この設定は、ExportOrders パイプレットには影響しません。

クレジットカード番号を含めた注文のエクスポート

デフォルトでは、(Business Manager または ExportOrders パイプレットで) 注文をエクスポートするときには、マスクされたクレジットカードデータのみが含められます。以下に例を示します:

<credit-card> 
	<card-type>VISA</card-type> 
	<card-number>XXXX-XXXX-XXXX-1111</card-number>
	<card-holder>John Doe</card-holder> 
	<expiration-month>1</expiration-month> 
	<expiration-year>2010</expiration-year>
</credit-card>

クレジットカードデータを外部システムに送信しなければならない場合は、ExportOrders パイプレットを使用して暗号化されたクレジットカード番号をフィードに埋め込みます。これには、ExportOrders パイプレットを Studio で開き、次のパラメーターをパイプレットに追加します。

  • 暗号化鍵: X.509 書式の公開鍵を base64 でエンコードした文字列表記 (SubjectPublicKeyInfo 部分)
  • 暗号化メソッド: 暗号化で使用する暗号化アルゴリズムとパラメーターを指定する文字列

    現時点でサポートされているメソッドは 1 つだけ (RSA) で、パイプレット内で次の式を使用して指定できます:

    dw.order.PaymentInstrument.ENCRYPTION_METHOD_RSA

クレジットカード番号の暗号化には RSA 公開鍵を使用します。B2C Commerce 内部では、クレジットカード番号の暗号化に (秘密でない) 公開鍵を使用します。次にこのフィードは外部システムに送信され、そこで、秘密鍵を使用して復号化されます。注文のクレジットカード番号は、暗号化データの base64 表記としてエクスポートされます。通常、こうした表記はクレジットカード番号よりも長くなります (たとえば、2048 ビットの鍵を使用すると、16 桁のカード番号は 348 文字になります)。

メモ クレジットカード検証番号 (CVN) は注文エクスポートに含められません。

UTF-8 文字を含む注文のエクスポート

UTF-8 文字を正しくコーディングするには、管理 | グローバル環境設定 | インポート & エクスポートの順に移動し、「エクスポート中に無効な XML 文字をフィルタリングする」設定にチェックを付けて、エクスポートされたデータから無効な XML 文字を削除します。

置換モードと注文

空白の要素のエクスポート

スキーマに minOccurs="0" として定義されている空の要素または属性はエクスポートされません。要素にスペースやその他の文字が含まれている場合は、空と見なされません。

エクスポートステータス変更のコミットまたはロールバックの許可

注文エクスポート処理では、処理の進行にともない、注文が「エクスポート済み」 (Order.exportStatus == Order.EXPORT_STATUS_EXPORTED) とマークされます。エクスポートパイプレットを明示的なトランザクションに埋め込んで (パイプライン内の遷移で定義) すべてのエクスポートステータス変更をコミットまたはロールバックできます。

注文のエクスポートは、配送に割り当てられていないサービス品目 (品目グループ) を含む注文に使用できます。この場合、この品目のエクスポートファイルで <shipment_id> 要素は作成されません。注文に品目グループ (配送) が含まれていて、ドキュメント番号が空の場合は、注文のエクスポートは FullOrderExport でのみ成功します。この問題を修正するために、サービス品目がこのタイプの配送に割り当てられている場合、<shipment_id>invalid<shipment_id> 要素が作成されます。

メモ <shipment_id> 要素はサービス品目とギフト券品目では必須ではありません。注文のインポートファイルでは、これらの品目にこの要素が存在しない場合があります。ギフト券品目に <shipment_id> 要素がない場合、品目はデフォルトの注文の配送に割り当てられます。サービス品目に <shipment_id> 要素がない場合は、品目は配送に割り当てられません。

位置属性

注文エクスポート xml の各商品品目要素には、位置 属性が含まれています。この機能は、XML ファイルの解析を行う際に XML タグの順序を保証できないシステムのためのものです。位置属性は順序の判定に使用されます。

置換モードでカタログをインポートすると、内部識別子が変わります。ただし、商品品目とクーポン品目は、内部識別子ではなくセマンティック ID によって注文にリンクされます。このため、商品 SKU が変更されない限り、商品品目は注文に付随したままになります。どのリンクも固有の識別子ではなくセマンティック ID によって設定されるため、インポートされたときにこれらのリンクが解除されることはありません。

B2C Commerce の注文環境設定

Salesforce B2C Commerce での注文の処理方法を選択します。

必要なエディション

使用可能なソリューション: B2C Commerce

一部の注文環境設定は、インポートおよびエクスポートできます。

  1. Business Manager で、アプリケーションランチャーをクリックし、マーチャントツール | サイト | サイト環境設定 | 注文の順に選択します。
  2. 注文のエクスポート設定を構成します。
    これらの設定は、Salesforce Order Management またはレガシーの Order Management の統合には該当しません。
    1. 注文がエクスポート対象になるまでの待機時間 (分) を入力します。
      デフォルトは 30 分です。
    2. 注文を編集するために開いた場合にエクスポートを遅延するには、待機する時間 (分数) を入力します。
      デフォルトは 30 分です。
    3. 注文エクスポートに使用する XML スキーマ (order.xsd) のバージョンを入力します。
      B2C Commerce の最新バージョンを選択するか、必要に応じて特定のバージョンをそのまま使用します。
  3. 注文 IP ログを有効にして、注文作成中に顧客 IP アドレスを保存します。
    まず、この種の情報を保管することについて顧客に通知するよう法で定められているかどうかを確認します。
  4. 注文データの設定を構成します。
    1. 顧客の注文を B2C Commerce に保存する日数 (注文保持) を入力します。
      指定日数よりも古い注文は自動的に B2C Commerce から削除されます。注文を維持するには、この設定を空白にします。
    2. 未確定注文を B2C Commerce に保存する日数 (未確定注文保持) を入力します。
      指定日数よりも古い未確定注文は自動的に B2C Commerce から削除されます。未確定注文を維持するには、この設定を空白のままにします (注文保持環境設定が指定されている場合を除く)。
    3. まだエクスポートされていない注文を保持するかどうかを選択します (「エクスポートされていない注文を保持」)。
      「はい」に設定した場合、ステータスが「新規」、「未処理」、「完了」の注文が削除されます。ただし、注文が削除されるのは、削除ジョブが実行された際に注文エクスポートステータスが「エクスポート済み」である場合のみです。ステータスが「作成済み」、「失敗」、「キャンセル済み」、「置き換え済み」の注文は、エクスポートのステータスに関わらず削除されます。この設定は「注文保持」が有効の場合にのみ適用されます。
  5. 1 ～ 365 の日数を入力します。この日数が経過すると、B2C Commerce で注文支払情報がマスキングされます (支払情報保持)。
    指定日数よりも古い注文の支払手段は、自動的にマスキングされます。これらの支払手段をマスキングすると、元のクレジットカード番号と銀行口座番号は復元できなくなります。マスキングは永久的なもので、後から日数を変更しても元に戻すことはできません。
  6. (ジョブを通じて) 注文を自動的に未確定として扱うまでの、注文が確定されなかった分数を入力します。
    注文が自動的に未確定として扱われないようにするには、この設定を空白のままにします。
  7. ストアフロントからの注文へのアクセスを制限する場合に指定します。
  8. ストアフロントの注文検索をセッション顧客に対して検証するかどうかを指定します。この検証を無効にする理由が特にない限り、「はい」に設定します。
    「はい」または「いいえ」
  9. 未登録の顧客の注文に対して顧客ナンバーを生成するかどうかを指定します。
    「はい」に設定した場合、未登録購入者による注文に対して、Script API、Open Commerce API (OCAPI)、パイプレット (CreateOrder または CreateOrder2) などの注文の作成方法にかかわらず、顧客ナンバーが生成されます。「いいえ」に設定した場合は、Script API または OCAPI で注文が作成された際に顧客ナンバーは生成されません。パイプレットで注文が作成された場合 (CreateOrder または CreateOrder2)、ゲスト注文に対して顧客ナンバーを生成するかどうかは、対応するパイプレット構成パラメーターによって指定されます。
  10. 注文の計算の丸め方法を設定します。

    品目価格の丸め または品目レベルの丸め を選択します。この設定は、ネットおよびグロスのサイトと、B2C Commerce Script API および OCAPI に適用されます。

    また、プロモーションのサイト環境設定を有効にします。

  11. このサイトの注文を Order Management で管理するかどうかを指定します。Order Management インテグレーションを構成して有効にします。
    この設定は、Salesforce Order Management とレガシーの Order Management 製品の両方に適用されます。
  12. 在庫とクーポンの使用の処理方法を指定します。在庫を予約できない場合、またはクーポンを使用できない場合は、対応する注文履歴のエントリが書き込まれます。
    1. 予約する在庫がない場合でも、失敗した注文を有効な注文にする (過剰販売) かどうかを指定します。
    2. 予約する在庫がない場合でも、キャンセルした注文を有効な注文にする (過剰販売) かどうかを指定します。
    3. すべてのクーポンが使用可能でない場合でも、失敗した注文を有効な注文にするかどうかを指定します。クーポンの使用に失敗すると、クーポンが設定した回数よりも多く使用されることになります。
    4. すべてのクーポンが使用可能でない場合でも、キャンセルした注文を有効な注文にするかどうかを指定します。クーポンの使用に失敗すると、クーポンが設定した回数よりも多く使用されることになります。
  13. 適用をクリックします。
