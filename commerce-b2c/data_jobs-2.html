B2C Commerce レイクハウススキーマリファレンス

B2C Commerce データレイクハウスは、商品カタログ、顧客、および販売注文のデータを、ccdl_プレフィックスを使用するエンティティテーブルに格納します。

各テーブルは、特定のエンティティ型とその属性およびリレーションシップを表します。

データの制限

B2C Commerce データレイクハウスで使用可能なデータには、次の制限が適用されます。データの統合と分析を計画する際には、これらの制約を確認してください。

一般

  • データは、ライブの本番インスタンスからのみ自動的に使用可能になります。Production (本番) 以外のインスタンスについては、Data 360 での非本番 B2C Commerce 環境の使用を参照してください。
  • 通貨の値は現地通貨のみです。

受注データ

  • 販売注文データはリアルタイムではありません。
  • 過去の販売注文データは 2026 年 3 月 1 日に開始されます。
  • 買い物客が追跡をオプトアウト (Do Not Track) した注文は、販売注文テーブルから除外されます。

商品データ

  • 商品データでは、Einstein 商品カタログフィードを有効にする必要があります。
  • 商品データは Einstein データエクスポートスケジュールに従って更新されます (最大頻度は毎日)。
  • 商品レコードはストアフロントカタログから取得されます。
  • 商品データは、サイトのデフォルトの地域情報でのみ使用できます。
  • 商品データにはサイト固有の属性は含まれません。

顧客プロフィールデータ

  • 2026 年 3 月 1 日より前に変更された顧客プロフィールは、Business Manager で登録済みの買い物客プロフィールのエクスポートをすでに有効にしている場合でも利用できません。2026 年 3 月 1 日までさかのぼって顧客プロフィールをエクスポートするには、「登録済み買い物客プロフィールの Data Cloud への取り込みを有効にする」チェックボックスをオフにして、「適用」をクリックします。次に、チェックボックスを再度オンにし、「登録済み買い物客プロフィールの最終更新日」フィールドに希望の日付を入力して、「適用」をクリックします。登録済み買い物客プロフィールのエクスポートをData 360を参照してください。
  • 通貨の値は現地通貨のみです。

エンティティ テーブル

次のトピックでは、各エンティティ テーブルとその列について説明します。

  • ccdl_attribute_definition
    カスタム属性とそのデータ型を定義します。各レコードは、さまざまなエンティティの値を割り当てることができる属性定義を表します。
  • ccdl_attribute_value
    さまざまなエンティティの属性値を含みます。これは、異なるエンティティタイプ間でカスタム属性を格納するための一般化されたテーブルです。
  • ccdl_customer_profile
    連絡先の詳細、環境設定、アクティビティのタイムスタンプなど、顧客のプロフィール情報が含まれます。
  • ccdl_product
    商品と SKU に関する詳細情報が含まれています。各レコードは、コア属性、識別子、メタデータとともに商品を表します。
  • ccdl_product_catalog
    製品カタログに関する情報を格納します。各レコードは、カテゴリと商品のカタログコンテナを表します。
  • ccdl_product_category
    カタログ内のカテゴリ階層情報を含みます。各レコードは、その親リレーションシップとメタデータを持つカテゴリを表します。
  • ccdl_product_category_product
    商品をカタログ内のカテゴリにマッピングします。各レコードは、商品カテゴリの割り当てを表します。
  • ccdl_product_image
    商品画像のメタデータとパスを格納します。各レコードは、商品に関連付けられた画像を表します。
  • ccdl_product_option
    ギフトラッピングや保証などの商品オプションについて説明します。商品オプションは、商品間で共有することも、1 つの商品にローカルで共有することもできます。
  • ccdl_product_option_value
    商品オプションの個々の値を含みます。各レコードは、オプションの選択可能な値を表します。
  • ccdl_product_product_option
    商品を利用可能なオプションにマッピングします。各レコードは、商品とオプションの関係を表します。
  • ccdl_sales_order
    合計と価格設定を含む販売注文ヘッダー情報が含まれます。各レコードは、価格の内訳と顧客情報とともに、完了した注文を表します。
  • ccdl_sales_order_customer
    販売注文に関連付けられている顧客の詳細が含まれます。各レコードには、注文時の顧客プロフィール、デフォルトの住所、請求先住所の情報が取り込まれます。
  • ccdl_sales_order_product
    販売注文内の製品の品目詳細を含みます。各レコードは、価格、数量、割引情報とともに商品品目を表します。
  • ccdl_sales_order_product_option_value
    販売注文の品目の商品オプション値を含みます。各レコードは、注文内の商品に対して選択されたオプション値を表します。
  • ccdl_site
    サイトの構成と設定が含まれます。各レコードは、通貨、地域情報、カタログ、および顧客リストの割り当てを持つストアフロントサイトを表します。

ニアリアルタイムのセグメンテーション機能の構成

データキットをインストールし、ID 解決ルールセットを作成し、セグメントを作成し、データグラフを作成した後、特定の B2C Commerce サイトに対してほぼリアルタイムのセグメンテーション機能を構成します。

必要なエディション

使用可能なソリューション: B2C Commerce
  1. Business Manager で、アプリケーションランチャーをクリックし、次にマーチャントツール | サイト | サイト環境設定 | Salesforce Data Cloudの順に選択します。
  2. グローバル構成を選択し、Data 360 テナント ID を指定します。
    1. Salesforce (Data 360) 組織でテナント ID を取得するには、Data Cloud 設定に移動します。
    2. Data 360 設定のホームページで、テナントのエンドポイントの最初の部分 (.c360a.salesforce.com より前の部分) をコピーします。
    3. テナント ID をテナント ID フィールドに貼り付けます。
  3. 機能構成 | Data Cloud ニアリアルタイムのセグメンテーションの順に選択します。
  4. 「ニアリアルタイムのセグメンテーション」で、ニアリアルタイムの登録済み顧客のセグメンテーションの有効化またはニアリアルタイムの匿名/ゲスト顧客のセグメンテーションの有効化、あるいはその両方を選択します。
  5. データグラフ API 名を指定します。

    データグラフを作成したときにデータキットで使用した名前 B2C_Individual_Data_Graph を指定します。

  6. データスペース名を指定します。

    データグラフを作成したときに使用したデータスペース名を指定します。

  7. 適用をクリックします。

ニアリアルタイム接続アプリケーションのサービスログイン情報の構成

データキットをインストールして接続アプリケーションを作成したら、Business Manager でアプリケーションのサービス認証情報を設定します。

必要なエディション

使用可能なソリューション: B2C Commerce
  1. Business Manager で、アプリケーションランチャーをクリックし、次に管理 | オペレーション | サービス | 認証情報の順に選択します。
  2. 新規をクリックします。
  3. 名前で、Data Cloud 接続アプリケーションを指定します。
  4. URLには、Salesforce Org の Classic (Lightning ではない) インスタンスの URL を指定します。末尾にスラッシュは含めないでください。
  5. ユーザー と パスワードで、ニアリアルタイムのセグメンテーション用に作成した接続アプリケーションのコンシューマーキーとコンシューマーシークレットを指定します。
    1. アプリケーションのコンシューマーキーとコンシューマーシークレットを取得するには、Salesforce 組織にログインします。
    2. 設定の「クイック検索」ボックスに アプリケーションと入力し、アプリケーションマネージャーを選択します。
    3. 接続アプリケーションの表示をクリックします。
    4. コンシューマー情報を管理をクリックします。
    5. 本人確認を求められたら、指定されたメールアドレスに送信された確認コードを入力します。
  6. 適用をクリックします。

Data 360 によるニアリアルタイムの顧客セグメンテーション

B2C Commerce のストアフロントでは、Data 360 で作成された顧客セグメントをほぼリアルタイムで利用できるようになり、バッチを有効化する必要がなくなりました。最新の顧客セグメントを活用することで、ストアフロントはタイムリーかつパーソナライズされ、またターゲットを絞った買い物客体験を提供できます。

メモ このセクションのトピックでは、commerce-b2c-datakit データキットのインストールと使用が必要です。このデータキットは、ほぼリアルタイムのセグメンテーションのための完全なソリューションを提供し、Webおよびモバイルアプリコネクタを使用してエンゲージメントイベントデータをData 360に取り込み、ID解決ルールセット、セグメント、データグラフ用に事前設定されたテンプレートを提供します。データ キットは、このフローに必要なデータ レイク オブジェクト (DLO) からデータ モデル オブジェクト (DMO) へのマッピングも処理します。データ インジェストに他のコネクタ (Apache Iceberg コネクタなど) を使用する場合は、DLO から DMO へのマッピングを手動で構成します。標準マッピングの詳細については、「B2C Commerce ドメインデータマッピング」を参照してください。さらに、追加の近リアルタイムセグメンテーションマッピング (Data Kit を使用しない場合)で説明されているように、ID 解決のためにいくつかの追加のマッピングを構成する必要があります。
  • その他のほぼリアルタイムのセグメンテーションマッピング(データキットを使用しない場合)
    commerce-b2c-datakit データキットは、ほぼリアルタイムのセグメンテーションに必要なデータモデルオブジェクト (DMO) マッピングを自動的に構成します。内部的には、データ キットは Web および Mobile Apps コネクタを使用してエンゲージメント イベントを取り込みます。データの取り込みにデータキットを使用しない場合 (たとえば、Apache Iceberg コネクタを使用する場合)、ほぼリアルタイムのセグメンテーションが正しく機能するように、これらの追加のマッピングを手動で作成します。
  • ニアリアルタイムのセグメンテーションのための ID 解決ルールセットの作成
    データキットをインストールしたら、ID 解決ルールセットを作成します。
  • ニアリアルタイムのセグメンテーションのためのセグメントの作成
    データキットをインストールし、ID 解決ルールセットを作成したら、セグメントを作成します。
  • ニアリアルタイムのセグメンテーションのためのデータグラフの作成
    データキットをインストールし、ID 解決ルールセットを作成し、セグメントを作成したら、データグラフを作成します。
  • ニアリアルタイムのセグメンテーションのための接続アプリケーションの作成
    データキットをインストールし、ID 解決ルールセットを作成し、セグメントを作成し、データグラフを作成したら、接続アプリケーションを作成します。
  • ニアリアルタイム接続アプリケーションのサービスログイン情報の構成
    データキットをインストールして接続アプリケーションを作成したら、Business Manager でアプリケーションのサービス認証情報を設定します。
  • ニアリアルタイムのセグメンテーション機能の構成
    データキットをインストールし、ID 解決ルールセットを作成し、セグメントを作成し、データグラフを作成した後、特定の B2C Commerce サイトに対してほぼリアルタイムのセグメンテーション機能を構成します。
  • ほぼリアルタイムのセグメンテーションのための顧客グループの作成
    ほぼリアルタイムのセグメンテーション機能を構成したら、使用するData 360セグメントごとに B2C Commerce で顧客グループを作成します。

ニアリアルタイムのセグメンテーションのための接続アプリケーションの作成

データキットをインストールし、ID 解決ルールセットを作成し、セグメントを作成し、データグラフを作成したら、接続アプリケーションを作成します。

必要なエディション

使用可能なソリューション: B2C Commerce
  1. Salesforce 組織にログインします。
  2. [設定 ] から、[クイック検索] ボックスに、「外部クライアントアプリケーションマネージャ」と入力します。
  3. [New External Client App (新規外部クライアントアプリケーション )] をクリックします。
  4. アプリ名と連絡先のメールアドレスを指定します。
  5. [OAuth を有効にする ] を選択します。
    この設定を選択すると、OAuth 関連の追加設定が表示されます。
  6. コールバック URL をhttps://login.salesforce.com/services/oauth2/successとして入力します。
  7. 次の OAuth 範囲を選択した OAuth 範囲リストに追加します。
    • Data 360 プロフィールデータの管理 (cdp_profile_api)
    • API によるユーザーデータの管理 (api)
    • Data 360 データに対する ANSI SQL クエリの実行 (cdp_query_api)
    • リクエストをいつでも実行 (refresh_token、offline_access)
    • Data 360 データに対するセグメンテーションの実行 (cdp_segment_api)
  8. クライアントログイン情報フローを有効化を選択します。
  9. [ Enable Device Flow ] を選択します。
  10. Web サーバーフローの秘密が必要を選択します。
  11. 更新トークンフローの秘密が必要を選択します。
  12. サポートされる認証フローに Proof Key for Code Exchange (PKCE) 拡張を要求の選択を解除します。
  13. 保存をクリックします。
  14. External Client App Managerに移動し、アプリをクリックします。
  15. ポリシーを編集をクリックします。
  16. 「クライアントログイン情報フロー」で、ユーザーを検索して選択します。
    多要素認証 (MFA) (メールまたはプッシュ通知) にアクセスできる組織の任意のユーザーを選択できます。
  17. [Refresh Token policy] で、[ Refresh Token is valid until revoked ] を選択します。
  18. [IP 緩和] で、[ IP 制限を緩和 ] を選択します。
  19. 保存をクリックします。

  • OAuth 2.0 クライアントログイン情報フロー用の接続アプリケーションの構成
  • JDBC ドライバー: 接続アプリケーションの設定

ニアリアルタイムのセグメンテーションのためのセグメントの作成

データキットをインストールし、ID 解決ルールセットを作成したら、セグメントを作成します。

必要なエディション

買い物客が B2C Commerce のストアフロントを操作すると、買い物カゴへの商品の追加や注文手続きの開始などのエンゲージメントイベントが生成されます。このリアルタイムデータをData 360に取り込み、ハーモナイゼーション、インサイト、パーソナライゼーションに役立てます。

  • データキットのインストール
    データキットを使用すると、B2C Commerce から Data 360 でデータストリームを簡単に定義できます。また、正しいスキーマとマッピングを使用してコネクターを簡単に構成できます。
  • エンゲージメントイベント用のデータストリームとコネクタの構成
    データキットをインストールしたら、特定の B2C Commerce サイトのエンゲージメントイベントを取り込むようにデータストリームとコネクターを構成します。
  • エンゲージメントイベント機能の構成
    データキットをインストールし、データストリームとコネクターを構成したら、特定の B2C Commerce サイトに対してエンゲージメントイベント機能を構成できます。
  • エンゲージメントイベント統合リファレンス
    エンゲージメントイベントは、B2C Commerce ストアフロントからの顧客とのやり取りをほぼリアルタイムでキャプチャし、そのデータを Data 360 データモデルオブジェクト (DMO) にマッピングします。

B2C Commerce のアウトバウンド接続の許可リスト

B2C Commerce からプライベートインターネットを介した外部クラウドプロバイダーへの接続は、アウトバウンド接続と呼ばれます。B2C Commerce レルムのセキュリティと整合性を確保するために、Salesforce カスタマーサポートはすべてのアウトバウンド接続を承認します。データの送信先を制御するには、送信接続の許可リストに新しいエンドポイントを追加します。B2C Commerce から、Secure File Transfer Protocol (SFTP)、FTP、WebDAV、HTTP および HTTPS などのサードパーティプロバイダーを含む、許可リストにある任意のエンドポイントにデータを送信します。

アウトバウンド接続を許可するには、Salesforce カスタマーサポートにリクエストを送り、各 Point of Delivery (POD) のファイアウォールに新しいルールを追加してもらう必要があります。ファイアウォールにルールを追加する際には、以下の点に留意してください。

  • TCP ポート 22、80、443、および 587 は B2C Commerce ではデフォルトで開いており、個別のファイアウォールルールは必要ありません。
  • ファイアウォールルールで使用できるのは IP アドレスのみで、ドメイン名は使用できません。
  • 1024 から 65,536 までのポートにルールを追加できます。1024 未満のポートは、ポート 21 を除き、新しいルールの対象にはなりません。
  • レルムごとに 5 つ以下の IP:ポートのペアを使用することをお勧めします。ただし、ビジネス上のニーズがある場合は、レルムごとに最大 10 個の IP:ポートのペアをリクエストできます。
  • POD のメンテナンス中にファイアウォールの変更は行わないでください。
  • 予約済み IP アドレスを許可リストに追加するリクエストは Salesforce カスタマーサポートによって拒否されるため、行わないでください。予約済み IP アドレスには、これらの IP アドレス範囲が含まれますが、これらに限定されません。

B2C Commerce でのデータのレプリケーション処理

各データレプリケーション処理では、データやメタデータ、ファイルをコピーするか、前回のデータレプリケーションのコピーを元に戻します。このトピックは、B2C Commerce に該当します。

メモ レプリケーションを使用して、Staging (ステージング) からデベロッパーの Sandbox (サンドボックス) にデータをコピーすることはできません。デベロッパーの Sandbox (サンドボックス) にデータを挿入するには、Staging (ステージング) からデータをエクスポートしてから、Sandbox (サンドボックス) にインポートします。

データのレプリケーションは 2 つのレベルで機能します。

  • 1 つはグローバルレプリケーションで、組織全体に適用される構成情報とデータが含まれます。
  • もう 1 つはサイトレベルのレプリケーションで、1 つまたは複数の特定のサイトに属するデータ (商品やカタログのデータ、XML ベースのコンテンツコンポーネント、画像ファイルなど) が含まれます。

PIG を作成する場合は、サイトレプリケーションを実行する前に、各ターゲットインスタンスへの完全なグローバルレプリケーションを実行します。

その後のレプリケーション処理には、グローバルデータ、サイトレベルのデータ、またはデータの組み合わせを含めることができます。含めるデータを構成するには、特定のレプリケーションタスクを選択します。タスクをレビューして、異なるタイプのデータがレプリケーションされる粒度を理解します。たとえば、単一のカタログをレプリケートしますが、特定の商品のみをレプリケートすることはできません。部分的なデータのレプリケーションは、次のような場合に便利です。

  • 新しいプロモーションを準備した後に、新しいプロモーションの定義やテキスト、グラフィックス、クーポンなどをストアフロントにロールアウトする場合。
  • ストアフロントのホームページのデザインをシーズンごとに異なるメッセージで更新する場合。
  • 商品価格の変更により、新しい価格表を実装する場合。

データをレプリケートすると、選択したデータがターゲットインスタンスの対応するデータを置換します。たとえば、Staging (ステージング) インスタンスと Development (開発) インスタンスの両方にカタログ A、B、C が含まれているとします。Staging (ステージング) インスタンスでカタログ B を更新し、カタログ C を削除し、カタログ D を追加します。Staging (ステージング) から Development (開発) にカタログをレプリケートすると、Development (開発) インスタンスは次のように更新されます。

  • カタログ A は影響を受けません。
  • カタログ B は更新されます。
  • カタログ C は削除されます。
  • カタログ D は追加されます。
メモ ターゲットインスタンスで上書きされるのは、レプリケーションに選択したデータのみです。他のデータは影響を受けません。前の例を考えてみると、カタログ以外のデータをレプリケートすると、カタログ A、B、C には影響はなく、カタログ D は追加されません。

データレプリケーション処理のタイプ

データのレプリケーションは 2 つのステップによる処理です。まず、データが Staging (ステージング) からターゲットインスタンスに転送され、その後、ターゲットインスタンスで公開されます。両方のステップを 1 つのレプリケーション処理として実行するか、別々に実行します。別々に実行すると、エラーが発生した場合に、原因の特定に役立ちます。

B2C Commerce でのデータのアップロード

データのアップロードとは、外部システムから自分のインスタンスのファイルシステムにデータファイルを転送することを指します。インポートファイル、画像、スナップショットなどのデータを手動またはプログラムでアップロードします。データを手動で転送する場合は、Business Manager を使用します。いつものように、Business Manager とのやり取りはすべて HTTPS を使用して行われます。カスタムコードは、プログラムによってデータ転送を実行します。この場合は、いくつかのファイル転送プロトコルがサポートされていますが、安全なプロトコルのみを使用します。トランスポート層セキュリティ (TLS) (推奨)、HTTPS、またはセキュアファイル転送プロトコル (SFTP) を介した WebDAV。

B2C Commerce でのデータの検証

ユーザー入力の検証は、アプリケーションセキュリティの基礎です。データの検証によって、データがアプリケーションで予想されている種類のものであることが確認されます。B2C Commerce では通常、無効なリクエストは完全に拒否され、ユーザーにエラーが返されます。データの検証を行う場所を選択しますが、ここではクライアント側とサーバー側の検証に重点を置きます。

  • 通常クライアント側の検証は、スクリプティング言語によって実装され、データがサーバーに送信される前に、クライアントマシンでチェックされます。Salesforce B2C Commerce では、ユーザーのブラウザーで実行されてフォームデータを検証する JavaScript コードを作成します。ただし、クライアント側の検証は、セキュリティ管理としては信頼できません。

  • サーバー側の検証を実装するには、ビジネスフローに追加のステップを記述します。このステップは効果的なセキュリティ管理です。通常デベロッパーは、B2C Commerce API といくつかの基本的なサニティチェックを使用して、B2C Commerce スクリプトでサーバー側の検証を実行します、

クライアント側の検証を使用する基本的なデータのサニティチェックは、ストアフロントユーザーにただちにフィードバックを表示できます。一方、堅牢なサーバー側の検証は、悪意をもつリクエストを停止できます。

リクエストの送信後に、データを再度検証します。データが無効な場合は、B2C Commerce は処理を中止し、エラーメッセージを介してユーザーに通知します。その結果、クライアント側の検証では、誤って入力されたデータを正規のユーザーに報告し、サーバー側の検証では、悪意のあるユーザーがサーバーに直接リクエストを送信するのを阻止します。

インジェクション攻撃に対する保護

適切な検証によって、インジェクション攻撃から保護することができます。出力のエンコードとともに使用すると、インジェクション攻撃に対してさらに堅牢な防御が提供されます。以下に注意事項を示します。

  • クライアント側の検証における内部の機密データの公開:

データを検証する際には、クライアント側のチェックで内部ロジックをあまり使用しないようにします。これによって、クライアントのチェックで使用される、予想される値や有効なデータの候補のリストが公開される恐れがあります。貴重なデータが、脆弱性を探している悪意をもつ攻撃者を含むすべてのクライアントにさらされてしまいます。

  • セキュリティが万全であるという錯覚につながる、不正確な検証:

セキュリティでは、検証にあまり頼らないようにします。検証ステップは、複数の段階によるセキュリティチェックを推進する、より大規模な奥の深いセキュリティ管理の一部にすぎません。これは一般的な問題です。特に、徹底的に検証することの難しい正規表現で問題となります。

次の方法でユーザー入力を検証します。

ユーザーの検証方法 説明
許可リストへの追加

許可リストへの追加はもっとも厳格な検証戦略です。許容可能な入力を定義し、これ以外はすべて拒否します。たとえば、入力が曜日である場合は、予想される値は 7 つのみになります。

また、入力形式を許可リストに追加することもできます。たとえば、日付とソーシャルセキュリティナンバーには特定の形式があります。

B2C Commerce の差分エクスポート

特定のビジネスエンティティのデータを、完全なデータセットとしてではなく差分としてエクスポートします。このトピックは、B2C Commerce に該当します。

差分エクスポートは、Order Management にエクスポートしたカタログデータで使用できます。各差分エクスポートには、オブジェクトの削除を含め、B2C Commerce が前回のエクスポートデータファイルを生成してからのすべての変更が含まれます。エクスポート中に行われた変更は、次のエクスポートに含められます。複数のコンシューマーにデータをエクスポートするには、複数の WebDAV パスを指定します。

この機能を有効にするには、Salesforce サポートに連絡して機能スイッチをアクティブにしてください。

メモ 差分エクスポート機能では、変更ログ機能がアクティブであることが必要です。これによって、データベースパフォーマンスがやや低下する (5% 未満) 場合があります。このペナルティは、選択したタイプだけでなく、差分エクスポートで選択可能な任意のエンティティタイプにおけるトランザクションの更新および削除に影響を与えます。
メモ レプリケーションによって本番環境で発生した変更を含めるには、変更ログのレプリケーション機能も有効にします。Staging (ステージング) と Production (本番) で 3 つの機能スイッチをすべてアクティブにします。
メモ 差分エクスポートを、Order Management に送信されるカタログデータとともに使用します。差分カタログデータを受信するように Salesforce サポートがコネクタを構成します。

使用可能なビジネスエンティティのタイプ

差分エクスポートは、次のビジネスエンティティタイプでのみ使用できます：

  • 次のグローバルにステージング可能なタイプでは、特定のコンテナの差分をエクスポートします:
    • カタログ (カタログの差分エクスポートを受け入れるように Order Management を構成)
    • 共有ライブラリ
    • 価格表
    • グローバルメタデータ
  • 以下のサイト固有のステージング可能なタイプでは、特定のサイトの差分をエクスポートします:
    • 店舗
    • キャンペーンおよびプロモーション
    • クーポン
  • また、次のトランザクションタイプの差分もエクスポートします。
    • 顧客リスト
    • カスタムオブジェクト
    • 在庫リスト

制限事項

差分エクスポートには、次の制限があることに注意してください。

  • 差分エクスポートジョブの最初の実行には、変更ログをアクティブ化した後に行われた変更のみが含められます。これは完全なデータエクスポートではありません。
  • 差分エクスポートデータは、常に標準の B2C Commerce エクスポート形式です。B2C Commerce では、エクスポートされるデータファイルには xxxxxx.zip という名前が付けられます。ここで xxxxxx は、000001 から始まり、エクスポートジョブの実行が成功するたびに増加していく 6 桁の数字です。また、xxxxxx.meta という名前の対応するメタデータファイルも生成されます。メタデータファイルは必要ありません。
  • 差分エクスポートは、エンティティタイプとコンテナ (特定のカタログに属する商品など) に対してのみ構成できます。タイプのサブセット (例：特定の特徴をもつ商品) に対して構成することはできません。
  • レプリケーションによって Production (本番) に発生した変更は、「変更ログのレプリケーション」の機能スイッチがアクティブでなければ、追跡されることはありません。これを機能させるには、Staging (ステージング) と Production (本番) の両方で 3 つの機能スイッチをすべてアクティブにします。
  • 特定のコンテナに対して差分エクスポートを構成する場合、そのコンテナの削除は差分では考慮されません。たとえば、特定の価格表のコンテンツの差分をエクスポートする場合に、この価格表を削除すると、次回の差分エクスポートファイルにはこの価格表やそのコンテンツに関するデータは何も含まれません。差分エクスポートデータには、他のエンティティの削除が含まれます。
  • 差分エクスポートデータは、変更ログに依存しています。変更ログのデフォルトの保有期間は 7 日間であるため、差分エクスポートが少なくとも 7 日間に 1 回実行されるように構成します。差分エクスポートの間隔が 7 日以上経過すると、7 日以前に行われた変更は失われます。
  • システムでは、エクスポートされたデータの消費は追跡されません。データが読み取られたかどうかを確認するには、コンシューマー側に独自のチェックを実装します。

詳細なデータレプリケーション

詳細なレプリケーションは、既存のデータレプリケーションを補完および強化するためのものであり、既存のデータレプリケーションに取って代わるものではありません。

詳細なレプリケーション機能は、必要に応じて Production (本番) 環境の既存のコンテンツに小さな更新を加える必要性に対応します。次の 3 つのレプリケーション グループについて、きめ細かなデータ更新を行います。

  • 商品: 特定の商品を Staging (ステージング) から Production (本番) に更新します。
  • 価格表: 特定の価格テーブルエントリを Staging (ステージング) から Production (本番) に更新します。
  • コンテンツアセット: 特定のコンテンツアセットを Staging (ステージング) から Production (本番) に更新します。
  • B2C Commerce サイトでの詳細なレプリケーションの有効化
    Staging (ステージング) および Production (本番) の B2C Commerce インスタンスで粒度の細かいレプリケーションを有効にして、必要に応じて既存のコンテンツに小さな更新を加えます。
  • 詳細なレプリケーション許可の割り当て
    特定の商品を Staging (ステージング) から Production (本番) にレプリケートします。
  • 詳細なレプリケーションによる商品のレプリケーション
    Staging (ステージング) から Production (本番) に商品と商品画像をレプリケートします。
  • 詳細なレプリケーションによる価格のレプリケーション
    Staging (ステージング) から Production (本番) に特定の価格をレプリケートします。

    特定の価格表を Staging (ステージング) から Production (本番) にレプリケートします。
  • 詳細なレプリケーションによる特定の Page Designer ページの公開
    きめ細かなレプリケーションを有効にし、コンテンツライブラリアセットフォルダーにレプリケートする Page Designer ページを整理したら、完全なデータレプリケーションの費用と複雑さを伴わずに、小規模でターゲットを絞ったレプリケーションを 1 日に複数回実行します。このトピックは、B2C Commerce に該当します。
  • 詳細なレプリケーションステータスの確認
    「詳細なレプリケーション」テーブルを使用して、過去、進行中、および今後の詳細なレプリケーションジョブを確認します。

トラブルシューティングと移行

B2C Commerce Dynamic Imaging Service の画像 URL が失敗したり、タイムアウトしたり、正しく表示されない場合は、ソースファイル、完全な URL、および Dynamic Imaging Service のトピックに記載されている制限を確認してください。このトピックは、他のホスト名や Adobe Scene7(Dynamic Media)クエリ文字列からの移行にも役立ちます。

ファイルサイズ、タイムアウト、コンテンツ配信ネットワーク (CDN) と CDN 以外の動作、および 4xxまたは408応答については、「Dynamic Imaging Service の画像ガイドラインと Dynamic Imaging キャッシュ 」を参照してください。このトピックは、トラブルシューティングの手順に使用します。数値制限は、そのトピックにとどまります。

画像が壊れている、または欠落している

  • ブラウザーで、完全な imgsrc URL をコピーして、新しいタブで開きます。変換が予期されていて、パスに/dw/image/v2/が表示されない場合、テンプレートは静的ファイルまたは Dynamic Imaging Service を使用していないホストを指している可能性があります。「画像変換 URL の作成」のように、URLUtilsとMediaFileを使用します。
  • イメージリクエストの HTTP ステータスが4xxの場合は、画像変換 URL の構造、検証、および操作の順序、およびサポートされている変換の表のパラメータールールを再確認します。一般的な原因: クエリ文字列の?の重複、空のsw=またはsh=値、クロップまたはオーバーレイ パラメーターの不完全なセット、範囲外の値、またはメイン トピックの長さ、エンコード、またはホスト規則に不合格のOIMGです。
  • 表示タイプのソースファイルがない場合は、変換クエリだけでなく、Business Manager でコンテンツを更新します。

速度低下またはタイムアウト

  • 最初のコールドリクエストは遅くなる可能性があります。CDN キャッシュがウォーム状態になった後は、繰り返しの読み込みが速くなります。詳しくは、 Dynamic Imaging Caching を参照してください。
  • 大きすぎるファイルや重い変換(大きなアニメーションGIFのアップスケーリングなど)は、画像ガイドライン (ファイルサイズとタイムアウトを参照)のタイムアウトに達する可能性があり、ソースの複雑さを軽減するか、変換コストを先に削減します。
  • 非本番環境では、Firefox のトラッキング防止が一部の初回取得をブロックすることがあります。そのファイルの画像ガイドラインのブラウザノートを参照してください(ファイルサイズとタイムアウト付き)。

移行: レガシーホストとその他の CDN

過去のインフラストラクチャまたはベンダーの CDN ホスト名を置き換える場合は、プログラムから承認されたパターンがない限り、新しいエッジホストを手動で編集しないでください。URLUtilsとMediaFileを使用して、またはバニティストアフロントドメインのコミュニティヘルパーから、オプションのコミュニティ DIS 商品画像ラッパーのように、正しい URL を再生成します。

一般的な Scene7 スタイル 一般的な DIS 方向
wid=400 scaleWidth / sw=400を変換またはクエリに含めます。

B2C Commerce でのインポートとエクスポート

B2C Commerce アプリケーション環境はバックエンド統合を円滑に行えるよう設計されています。他のシステムから B2C Commerce 環境にデータをインポートしたり、バックエンドシステムに B2C Commerce データをエクスポートしたりできます。

B2C Commerce インスタンスと、在庫、注文、マーケティングなどのシステムとの間でデータを転送する場合は、データレプリケーションではなくインポートとエクスポートを使用します。インポートでは外部ファイルを処理し、そのデータを使用してデータベースに値を読み込みます。価格設定フィードのように頻繁に更新されるインポートフィードにインポートを使用することもあります。エクスポートを使用して B2C Commerce データベースからデータを抽出し、外部システム用のフィードとして使用できる XML ファイルを作成します。

サイトのインポートとエクスポートは、サイトの構成と設定の情報を 1 つのインスタンスから別のインスタンスに移動するためにも使用します。

データとコードのレプリケーション対インポートとエクスポート

サイトで使用するインスタンスのデータベースにデータを自動的に読み込むには、インポートとエクスポート機能およびデータレプリケーションの両方を使用します。ただし、インポートとエクスポートと、データレプリケーションは異なるメカニズムです。

レプリケーションでは、データは、B2C Commerce データベースの中にすでに入れられた後で、1 つのインスタンスから別のインスタンスに移動されます。インポートとエクスポートでは、外部システムとの間でデータをやり取りできます。

データのレプリケーションでは、元のインスタンスデータベースのデータのコピーが作成されます。コピーは、目的のインスタンスデータベース内の新しい場所に作成されます。元のデータは置き換えられません。データレプリケーションが完了したら、目的のシステムで既存のデータから新しいデータに切り替えます。サイトへの変更は徐々にではなく、瞬時に実行できます。

この場合:

N
処理された要素の個数
<type name>
商品やカタログなど、データタイプの名前

Processed N total elements

(合計 N 個の要素が処理されました)

処理エラー

処理エラーはインポートとエクスポートの処理中に発生することがあります。これには、欠落している、または正しくない処理パラメーター、ロックの取得中の問題、形式に誤りがある XML フィード、一般的なシステムエラーなどが含まれます。処理エラーが原因でインポートやエクスポート処理が開始しなかったり、実行中に突然中断したりすることがあります。

データエラー

フィードが原因でデータエラーや警告が発生することがあります。これらのエラーはインポート処理中にのみ発生します。このエラーは常にフィード内の要素に限定されます。データエラーまたは警告が発生しても、インポート処理は中断されません。代わりに、インポートプロセスでは無効な要素がスキップされます。このため、インポート処理は処理エラーはないがデータエラーが発生した状態で終了することがあります。データの問題は DATAERROR または DATAWARNING に分類されます。エラーや警告の場所と原因についての詳細は、ログファイルで確認できます。

エラータイプ 説明
DATAERROR

フィード内の要素 (カテゴリや商品など) をまったく処理できない場合に記録されます。たとえば、必須の ID 属性が要素にない場合などです。

インポートフィード内でログされる DATAERROR は 1 つの要素につき最大 1 つです。
DATAWARNING

要素の処理が一部分だけ行なわれたことを示します。たとえば、フィード要素にカスタム属性があるが、その属性がシステム内で定義されていない場合などです。この場合、そのカスタム属性は無視されます。

もうひとつの例は、存在しない分類カテゴリを商品が参照する場合です。この場合、商品には分類カテゴリが定義されません。

フィード内のインポート要素 1 つにつき DATAWARNING は複数ある場合もあります。

使用されなくなっている要素または下位要素が使用された場合は、DATAWARNING としてログされます

インポートパイプレットでは、ステータス オブジェクトを使用して DATAERROR および DATAWARNING の数に簡単にアクセスできます。

次の例では、スクリプトではステータスオブジェクトを使用してエラーがカウントされます。

var dataErrors : Number = status.details.DataErrorCount; var dataWarnings : Number = status.details.DataWarningCount;

以下のスクリプトコードに示すとおり、最初に処理エラーを、次に DATAERROR をチェックして自動インポート処理が成功したかどうかを判断することは、一般的に推奨される方法です。

var success : boolean = (status.code == 'IMPEX-0') && (status.details.DataErrorCount == 0);

コードでは DATAWARNING を予期せぬエラーとして処理するべきではありません。これは、現時点ではフィードが原因で DATAWARNING が発生していなくても、将来の B2C Commerce バージョンで DATAWARNING が発生する可能性があるからです (たとえば、要素が廃止予定となったり、ルールが更新された場合など)。

B2C Commerce でのインポートとエクスポートのトランザクション処理とフィードサイズ

B2C Commerce では、任意のサイズのフィードを処理できるように標準のインポートを設計しています。すべてのトランザクションシステムと同様に、トランザクションのサイズには制限があります。Business Manager からトリガーされ、インポートパイプレットの実行時にトリガーされるインポートの標準動作では、各オブジェクトの後にコミットが行われます。

インポートパイプレットのこの動作を変更します。インポートパイプレットが明示的なトランザクションに埋め込まれている場合 (トランザクション境界は遷移時にパイプラインで定義できます)、それを囲んでいるトランザクションによってすべての変更がコミットされます。

異なるオブジェクトタイプ (カタログデータやコンテンツデータなど) のインポートや、その他の変更点を 1 つのトランザクション内でグループ化します。B2C Commerce では、最大 1,000 個のビジネスオブジェクトのトランザクションサイズを処理できます。制限を超えていないことを確認してください。

なるべく標準の動作、つまり各オブジェクトの後でコミットする方法を使用するようお勧めします。本番以外の環境にインポートする際は、この方法を使用してください。インポートに失敗した (たとえば、一部のオブジェクトはインポートされたが、他のオブジェクトはインポートされなかった) 場合は、インポートを繰り返します。ただし Production (本番) 環境では、一貫性のない処理を回避する必要があります。Staging (ステージング) インスタンスにインポートしてから Production (本番) にレプリケートすることはできません。明示的なトランザクションで、インポートを Production (本番) に埋め込みます。

B2C Commerce でのファイルサイズと転送の制限

B2C Commerce にはファイルサイズと転送の制限があります。

アップロード制限

WebDAV で B2C Commerce インスタンスにプッシュする場合、アップロード制限は 500 MB です。ただし、実際のアップロード可能容量は、接続の速度と質によって変わります。ファイル転送に時間がかかり過ぎると、接続がタイムアウトになることがあります。ファイルは圧縮してからアップロードすることをお勧めします。500 MB 未満のファイルのアップロードがうまくいかない場合は、B2C Commerce カスタマーサポートまでご連絡ください。

ダウンロード制限

ファイルにダウンロードする場合は、FTP または WebDAV 用のファイルサイズを 200 MB 未満にしてください。文字列へのダウンロードでは、ファイルサイズは大幅に小さくなります。

FTPClient サイズ制限

dw.net.FTPClient でファイルフェッチのサイズ制限が施行されるようになりました。これらのサイズ制限は dw.net.FTPClient.get() の引数として渡すことができます。それ以外の場合はデフォルトが使用されます。

- 文字列を返す GET 操作のデフォルトサイズは dw.net.FTPClient.DEFAULT_GET_STRING_SIZE (2 Mb) です。

- ローカルファイルを作成する GET 操作のデフォルトは dw.net.FTPClient.DEFAULT_GET_FILE_SIZE (10 Mb) です。

- 最大ダウンロードサイズは、文字列では dw.net.FTPClient.MAX_GET_STRING_SIZE (10 Mb)、ファイルでは dw.net.FTPClient.MAX_GET_FILE_SIZE (200 Mb) です。

メモ このサイズ制限は、圧縮ファイルに対するものです。非圧縮ファイルはこれより大幅に大きくすることができます。

HTTPClient サイズ制限

HTTP クライアントにはファイルサイズ制限がありません。

外部 XML エンティティと DTD 宣言の制約

いずれの XML インポート (カタログ、顧客、在庫など) でも、外部の XML エンティティおよび DTD 宣言は使用できません。これらは、XML 外部エンティティ (XXE) 攻撃を防ぐために、(13.3.3 時点で) 非アクティブにされています。

<?xml version="1.0" encoding="UTF-8"?> <!DOCTYPE catalog [ <!ENTITY remote SYSTEM "http://remote.apt.vsecurity.org/"> ]>

圧縮フィード

XML ファイルサイズは圧縮によって大幅に縮小できます。フィードの圧縮は、アップロードサイズを制限内に収め、低速度のネットワークリンクでアップロードおよびダウンロードの時間を短縮するために役立つことがあります。

標準のインポートサポートファイルは、ネイティブの gzip アルゴリズムで圧縮されます。インスタンスで明示的に gunzip する必要はありません。catalog.xml.gz などのファイル名をインポートパイプレットに渡すか、または gzip ファイル (拡張子は .gz) を Business Manager で選択するだけです。

フィードは、Business Manager のインポートとエクスポートセクション内で、1 つのファイルごとに圧縮および解凍 (gzip 圧縮ではなく zip 圧縮) できます。また、Business Manager では、アップロード中にファイルが自動的に解凍されます。dw.io.File.zip および dw.io.File.unzip の API を使用して、ファイルの圧縮や解凍をプログラムで行えます。

静的ファイル

カタログおよびコンテンツライブラリ内の永続的オブジェクトは、静的ファイル (通常は商品画像) で補完されます。静的ファイルはインスタンスのファイルシステム内に保存されています。XML フィードにはデータベースオブジェクトしか含まれていません。静的ファイルをエクスポートおよびインポート、またはダウンロードおよびアップロードするには、WebDAV インターフェイスを使用します。B2C Commerce では、ダウンロードやアップロードの操作回数を減らすために、dw.io.File.zip および dw.io.File.unzip の API で圧縮や解凍を行うこともできます。

サイズとランタイムの制限

インポートとエクスポートは、フィード内のオブジェクトをいくつでも処理できるように設計されています。顧客によっては、数百メガバイトを含むフィードを使用することもあります。インポートとエクスポート処理では、現在処理中の項目のみをメモリに入れておくチャンキング技法を使用することによって、大きなデータセットに対応します。インポートとエクスポートファイルにはサイズ制限がありませんが、インスタンスへのアップロードにサイズ制限がある場合があります。

B2C Commerce インスタンスへのリクエストには、タイムアウトが課されます。アプリケーションサーバーが 5 分以内に応答しない場合、Web サーバーは接続を閉じます。ただし、大容量のインポートまたはエクスポートは、通常 5 分以上かかります。リクエストのタイムアウトを回避するには、インポート/エクスポートパイプレットをジョブパイプラインに挿入し、非同期的に実行します。ジョブパイプラインにはランタイム制限がありません。

B2C Commerce での WebDAV の使用

どの B2C Commerce インスタンスにも、埋め込み型 WebDAV サーバーと WebDAV クライアントの両方があります。

WebDAVClient クラスでは、マーチャントのリモートシステムに実装されたサーバーが使用されます。WebDAV では、HTTP 接続または HTTPS 接続が使用されます。WebDAV と HTTPS を使用している場合、ファイルを Staging (ステージング) インスタンスまたは Production (本番) インスタンスに転送する際に PCI に準拠していることになります。

WebDAV サーバーは、名前の変更、コピー、変更、または作成の操作のタイムスタンプを、ファイルとディレクトリのアップロード操作の日時にリセットします。

Sandbox (サンドボックス) インスタンスの場合は、ファイルを Windows コンピューターからコピーしてカートリッジに貼り付けます。Windows オペレーティングシステムに WebDAV クライアントが統合されていて、カートリッジには WebDAV サーバーが統合されています。

WebDAV COPY コマンドを使用してファイルのコンテンツをそれ自体にコピーすると、コピー先は除外されます。コピー先が除外される理由は、それがすでに存在するためです (以下の注意を参照)。このように除外することで、再帰的な無限コピーによってファイルシステムが一杯になってしまうことが防止されます。

たとえば、次の構造の無限コピーを実行しようとしたとします。


             folder/path/content
             folder/path/content/c1
             folder/path/content/c2
             
             cp folder/path/content --> folder/path/content/targetfolder

結果は次のようになります。


             folder/path/content
             folder/path/content/c1
             folder/path/content/c2
             folder/path/content/targetfolder/c1
             folder/path/content/targetfolder/c2

この例では、ターゲットフォルダーは宛先フォルダーに存在しません (再帰的なケースの場合と同様)。

メモ 宛先フォルダーと同じ名前のフォルダーがソースに存在する場合は、何もコピーされず、エラーは表示されません。この動作はhttps://datatracker.ietf.org/doc/html/rfc4918再帰的なコピーがソースシステムで可能な場合に実行される RFC (Request for Comments) 4918 webDAV 標準とは異なります。

B2C Commerce WebDAV サーバーと B2C Commerce WebDAV クライアントは通信しません

WebDAV がインストールされていれば、B2C Commerce インスタンスを除き、任意のコンピューターから WebDAV クライアントまたは WebDAV サーバーに接続します。B2C Commerce WebDAV クライアントは同じインスタンスまたは他のインスタンス内にある B2C Commerce WebDAV サーバーに接続できません。

WebDAV ディレクトリ

B2C Commerce では、WebDAV 経由で特定のファイルシステムの場所へセキュアな接続ができます。以下に例を示します:

カートリッジ https://<domain>/on/demandware.servlet/webdav/Sites/Cartridges

ログファイル https://<domain>/on/demandware.servlet/webdav/Sites/Logs

セキュリティログファイル https://<domain>/on/demandware.servlet/webdav/Sites/Securitylogs

インポート/エクスポート https://<domain>/on/demandware.servlet/webdav/Sites/Impex

トラブルシューティング

これらの場所にアクセスしようとしたときに "Access Denied" (アクセス拒否) エラーが表示されることがあります。これらの WebDAV の場所では、ファイルの転送がセキュアに行われるように SSL 接続が施行されています。ストアフロントコード (および注文や顧客のデータなどのインポートファイル) は、暗号化なしでオープンに転送しないでください。これらの場所に暗号化なし (http) で接続しようとすると、B2C Commerce アプリケーションではアクセスが拒否されます。ブラウザーから WebDAV の場所にアクセスしようとしている場合は、URL に HTTPS を使用してください。HTTPS では SSL が使用されていてセキュアです。Total Commander などの WebDAV クライアントで接続しようとしている場合は、接続を設定する際に SSL オプションを選択してください。

B2C Commerce での WebDAV タイムスタンプのリセット

WebDAV サーバーは、名前の変更、コピー、変更、または作成の操作のタイムスタンプを、ファイルとディレクトリのアップロード操作の日時にリセットします。このリセットは、リモート解凍操作にも適用されます。このトピックは、B2C Commerce に該当します。

画像マネージャーが画像をリクエストする際、利用できる最新の画像が常に取得されるため、タイムスタンプのリセットは非常に重要です。

B2C Commerce での FTP の使用

B2C Commerce スクリプトクラス FTPClient を使用して、インスタンス内に FTP クライアントを作成します。B2C Commerce は、機密情報を含むファイルの移動で推奨されるセキュア FTP (sFTP) にも対応しています。

FTP 接続は暗号化されていないため、FTP を使用したマーチャントシステムと B2C Commerce 間のデータ移動はセキュアではありません。Staging (ステージング) または Production (本番) のシステムでは、FTP の使用は推奨しません。転送の前後にデータを暗号化および復号化するカスタムコードを作成した場合を除き、この接続は PCI に準拠しません。

メモ デフォルトでは、FTPclient の GET メソッドでは "ISO-8859-1" エンコードが使用されます。ただし、メソッドのオーバーロードバージョンを使用して、代わりに UTF エンコードを指定します。

B2C Commerce での HTTPS の使用

有効な証明書が購入済みであり、本番システムまたはステージングシステムに正しくインストールされていることを確認します。このトピックは、B2C Commerce に該当します。

証明書が次の要件を満たしていることを確認します。

  • 正式な信頼センターから発行されている
  • 有効期限が将来の日付になっている
  • ドメイン名に割り当てられている

以下の 2 つのタイプの証明書を利用できます:

  • 認証局によって顧客用に明示的に作成された証明書 (顧客の DNS 名が証明書チェーンの第 2 レベルにある)。このタイプの証明書では、顧客の証明書ファイルのみがインストールされていることが要件になります。
  • 認証局の役割を果たす会社が所有する一般証明書の下位証明書として作成された証明書 (顧客の DNS 名が証明書チェーンの第 3 レベルにある)。このタイプの証明書では、顧客の証明書ファイルおよび第 2 レベルの一般証明書を表す証明書ファイルの両方がインストールされていることが要件になります。

バックエンドシステムでの B2C Commerce 証明書の使用

Stating (ステージング) では、顧客は B2C Commerce ワイルドカード、つまり自己署名証明書を使用できます。このアプローチは他のファイル転送方法より複雑なため、一般的にはお勧めしません。

B2C Commerce 自己署名証明書を使用するには:

まず、バックエンドシステムに証明書をインストールします。

次に、ホストファイルをバックエンドシステムの IP に変更します。

その次に、Java Framework を使用して Trust Manager を作成し、ホスト名ベリファイアを上書きします。

B2C Commerce でのローカライゼーションのインポート

B2C Commerce のすべてのインポートフィードで、すべてのローカライゼーション要素のxml:lang属性が同じ方法で処理されます。

xml:lang 属性では、デフォルトの地域情報を含むインスタンスに存在する地域情報を指定する必要があります。ただし、地域情報はアクティブまたは非アクティブとして構成できます。インスタンスに含まれない地域情報を xml:lang 属性で指定すると、要素はインポートされません。B2C Commerce はインポートログにデータエラーを記録します。

B2C Commerce のインポートモード

インポート処理では、インポートモードを指定して、フィード内でデータを解釈する方法を定義します。一部のオブジェクトタイプではサポートされていないモードがあります。インポート処理用に定義されるインポートモードは、フィード内のすべてのオブジェクトに適用されます。インポートモードは、B2C Commerce スキーマで定義されるすべてのインポートファイルに適用されます。

以下の表は、一般的なインポートモードの動作を説明するものです。ニュアンスと例外については、オブジェクトタイプ固有のインポートとエクスポートのトピックを参照してください。

モード 説明
マージ

マージモードでは、オブジェクトが存在しない場合にはオブジェクトが作成されてから更新されます (「更新」インポートモードを参照)。

オブジェクトを作成する場合、一部のオブジェクト属性にはデフォルトが事前に設定されていることがあります。
更新

更新モードでは、既存のオブジェクトに変更が加えられます。オブジェクトが存在しない場合は、作成されません。

  • フィードで渡されたオブジェクト属性は更新されます。
  • フィードで渡されなかったオブジェクト属性はそのままになります。
置換

置換モードでは、フィードで渡されたデータを使用してオブジェクトが再作成されます。オブジェクトが存在する必要はありません。インポートによって、フィードで提供されていない既存の属性が削除されます。

事実上、置換モードは、削除を行ってからマージを行うのと同じです。
削除 削除モードでは、データベースからオブジェクトが削除されます。フィードで必要なのはオブジェクト ID のみです。インポートでは、他のオブジェクト属性は無視されます。

削除モードでは、フィード内 のオブジェクトが削除されます。同様に、置換モードでは、フィード内 のオブジェクトが削除されてから、再作成されます。1 つのオブジェクトを変更するために置換モードのインポートを実行すると、オブジェクトセット全体が削除されます。

警告 アクティブデータのインポートでは、常に置換モードが使用されます。アクティブデータ CSV ファイルをインポートする場合、ファイルに含まれていない属性はすべて完全に削除されます。保持したいすべての属性が CSV ファイルに含まれていることを必ず確認してください。詳細については、アクティブデータ.csvファイルのインポートを参照してください。

一部のインポートでは、import 要素レベルで属性モードがサポートされます。この場合、サポートされる唯一のモードは削除です。一方で、処理のインポートモードでは、特定の要素を上書きできます。この機能は、変更された情報を B2C Commerce システムにフィードする際に役立ちます。この機能を使用すれば、1 回のインポート処理でオブジェクトを作成、更新、削除できます。

以下の例では、インポートによって product-id が PN-00001の特定の商品が削除されます:

<product product-id="PN00001" mode="delete"/>

Salesforce では、Production (本番) で差分フィードを使用することをお勧めします。差分フィードには、前回のフィードからの変更点のみが含まれます。差分フィードはアーカイブサイズが小さく、インポート速度が速いうえ、トラブルシューティングも簡単です。ただし、一部のスキーマでは、一部の要素がグローバルインポートモードを上書きして常に置換モードを使用します。これらの要素では、オブジェクトの完全なセットを各インポートフィードに含める必要があるため、差分フィードに含めることはできません。

List-Type 要素

XML ファイルのすべての list-type 要素の標準動作では、インポートモードがマージか置換かにかかわらず、ファイルに含まれるデータベースのリスト全体が置換されます。

インポートファイルにリスト要素が含まれていない場合:

  • マージモードではデータベースリストが残ります
  • 置換モードでは、インポートによってデータベースリストが削除されます

インポートモードの処理の例

インポートモードの処理の例を用意しました。

次の例は、選択したインポートモードでデータベース内のオブジェクトがどのように更新されるかを示しています。

フィードで表される値は以下のとおりです:

  • A+a- 新しい属性をもつオブジェクト
  • B-a - 削除される属性をもつオブジェクト
  • C - 変更のないオブジェクト
  • D - 新しいオブジェクト
  • FΔa - 変更される属性値をもつオブジェクト
メモ XML には、データベースに存在するオブジェクト (E) は含まれていません。
XML ファイルオブジェクト インポート前のデータベースオブジェクト インポートモード インポート後のデータベースオブジェクト
A+a、B-a、C、D、FΔa A、B、C、E、F マージ A+a、B、C、D、E、FΔa
    更新 A+a、B、C、E、FΔa
    置換 (価格表を除く) A+a、B-a、C、D、FΔa
    置換 (価格表) A+a、B-a、C、D、FΔa
    削除 (価格表を除く) E
    削除 (価格表)  

マージと更新では、フィードで指定されていない属性は削除されません。B-a ではなく B となっているのはこのためです。属性を削除するには、インポートモードを変更するのではなく、属性値を「なし」または空白に変更することが必要になる場合があります。指定する正しい値は属性によって異なります。特定の属性が処理される方法の詳細については、フレームワークセクションを参照してください。

更新では、オブジェクト D は作成されません。

オブジェクト "E" は、価格表の場合を除き、いずれのテーブルのシナリオでも削除されません。置換モードまたは削除モードで価格表をインポートすると、フィードで指定されていないデータも含め、価格表全体が置換または削除されます。その他のインポートでは、フィードに含まれていないオブジェクトを削除するモードはありません。古くなったオブジェクトを明示的に削除するための方法を決定します。

置換モードで在庫リストをインポートすると、インポートファイルにない在庫レコードはすべて削除されます。同じ在庫リストが同じファイルに複数回表示される場合は、以前にインポートされた要素も削除されます。
