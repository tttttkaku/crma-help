通話を処理するための代替通話フロー

テレフォニーパートナーが通話を人間のサービス担当者に転送する 3 番目の音声通話レコード (VC3) を作成する場合は、次の代替通話フローを使用します。たとえば、VC1 を営業担当に転送できない場合に 3 番目のレコードを作成できます。

黄色で強調表示されているセクションは、推奨通話フローと代替通話フローの違いを示しています。

次の図は、通話フローのこれらの手順を示しています。

  1. まず、テレフォニーシステムが着信電話を受信します。

  2. 設定されている場合、テレフォニーシステムは初期音声通話レコード (VC1) を作成します。

    ヒント Salesforce で音声通話レコードを作成するには、VoiceCalls Telephony Integration API を使用します。
  3. 設定されている場合、テレフォニーシステムは指定された通信プロトコル (PSTN または SIP) を使用して通話をエージェントに転送します。

    1. PSTN で転送が行われる場合:

      1. Salesforce によってエージェント音声通話レコード (VC2) が作成されます。
      2. Agentforce Voice で [関連通話を接続] オプションが有効になっている場合、Salesforce は VC1 レコードと VC2 レコードを自動的に接続します。このオプションが無効になっている場合、音声通話レコードは接続されません。

    2. SIP で転送が行われる場合:

      1. Salesforce によってエージェント音声通話レコード (VC2) が作成されます。
      2. VC1 音声通話レコードの ID が UUI ヘッダーの callid パラメータに渡されると、Salesforce は自動的に VC1 レコードと VC2 レコードを接続します。パラメーターが指定されていない場合、音声通話レコードは接続されません。

  4. 顧客が電話を切ると、VC1 および VC2 コールは終了します。

  5. エージェントが通話を人間のサービス担当者にエスカレーションする場合は、通話を担当者に転送して VC1 と VC2 を終了し、VC3 を作成します。 VC3 を VC1 または VC2 のいずれか都合の良い方に接続します。会話が完了すると、VC3 コールは終了します。

    ヒント パートナーが担当者音声通話 (VC3) の音声通話レコードを作成するときに以前の音声通話の設定をサポートしている場合は、以前の通話 ID として VC2 の ID を入力します。 パートナーがサポートしていない場合は、手動で設定します。詳細は、「Alternative Call Flow for Handling Calls (通話処理の代替通話フロー)」を参照してください。

従来のビルダーでのサブエージェントとアクションへのアクセスを制御する検索条件の作成

サブエージェントとアクションの検索条件を作成して、特定の条件を満たした場合にのみエージェントが会話で使用できるようにします。指定した変数に基づいてアクセスを制限できます。顧客チャネルのエージェントの場合、検索条件を使用して、ユーザーの ToDo を実行するサブエージェントとアクションに認証を要求することをお勧めします。

必要なエディション

使用可能なインターフェース: Lightning Experience
使用可能なエディション: Enterprise Edition、Performance Edition、Unlimited Edition、および Developer Edition。必要なアドオンライセンスはエージェント種別によって異なります。
必要なユーザー権限
検索条件を作成および管理する AIエージェントの管理とエージェントタイプの必要な権限

開始する前に、[コンテキスト] パネルから、検索条件で使用する変数をエージェントに追加します。

  • メッセージングコンテキスト変数
  • カスタム変数
  1. Agentforce エージェントの [設定] ページから、Agentforce Builder でエージェントを起動します。
  2. エージェントが有効な場合は、無効化します。
  3. サイドバーから、[コンテキスト] を選択します。
  4. [コンテキスト] パネルから、[条件] タブを選択し、[新規] をクリックします。
  5. 検索条件の名前、API 参照名、説明を入力します。
  6. この検索条件が適用されたサブエージェントまたはアクションをエージェントが使用するには、いずれかの条件を満たす必要があるのか、すべての条件を満たす必要があるのかを指定します。
  7. 条件を作成するには、変数、演算子、値を指定します。
    複数の条件を作成できます。コンテキスト変数、会話変数、カスタム変数がサポートされます。
  8. 変更内容を保存します。
  9. 検索条件を使用するには、1 つ以上のサブエージェントまたはアクションに適用します。
    1. [サブエージェント] パネルから、変更するサブエージェントの名前をクリックします。
    2. 検索条件をサブエージェントに追加するには、サブエージェントの詳細パネルで [] をクリックします。
    3. 検索条件をサブエージェントのアクションに追加するには、[このサブエージェントのアクション] タブを選択し、変更するアクションの名前をクリックします。アクションの詳細パネルで、[] をクリックします。
    4. 適用する検索条件を検索して選択し、変更を保存します。検索条件は、このエージェントのサブエージェントまたはアクションにのみ適用されます。

検索条件をテストするには、プレビュー会話を再開して変更を適用します。

サブエージェントまたはアクションに適用された検索条件を表示したり、検索条件を追加または削除したりするには、[サブエージェント] パネルから、そのアセットの詳細パネルを開きます。

フィルタを編集または削除するには、[コンテキスト] パネルから [フィルタ] タブを選択し、変更するフィルタを開きます。現在検索条件を使用しているすべてのアセットを表示することもできます。

キャンバスビューでのエージェントの作成

Agentforce Builder のキャンバスビューの機能について説明します。このビューは、エージェントスクリプトを使用して強力で信頼性の高いエージェントを作成するのに役立ちます。

必要なエディション

使用可能なインターフェース: Lightning Experience
使用可能なエディション: Enterprise Edition、Performance Edition、Unlimited Edition、および Developer Edition。必要なアドオンライセンスはエージェント種別によって異なります。

Agentforce Builder でエージェントを開くと、キャンバスビューで開きます。このビューでは、エージェントスクリプトをわかりやすいブロックにまとめることで、エージェントの設定が簡略化されます。また、一般的なタスクのショートカットも表示されます。

キャンバスビューとスクリプトビューのどちらを使用してエージェントを作成するかに関係なく、エージェントの設定と行った編集は両方のビューで一貫しています。

コンソールには、構文エラーや予期しない値など、エージェントのパフォーマンスを妨げる可能性があるエラーと警告のリストが表示されます。問題にすばやく対処するには、キャンバスビューまたはスクリプトビューのコンソールでエラーまたは警告をクリックします。ビルダーは、現在表示しているビューで問題のある要素または行を開きます。警告のあるエージェントは確定できますが、エラーのあるエージェントは確定できません。

変更を保存すると、Agentforce Builder は両方のビューで検証チェックを完了します。キャンバスビューではエラーに下線が表示されますが、スクリプトビューに切り替えると詳細を確認できます。スクリプトビューを変更して、キャンバスビューを使用不可にできます。キャンバスビューに戻すには、まずスクリプトビューのエラーを修正します。

AI アシスタンス

Agentforce は、質問への回答からサブエージェントおよびアクションの作成まで、エージェントの作成のあらゆる側面で役立ちます。Agentforce が役立つ方法をいくつか紹介します。

  • エージェントスクリプトを生成。自然言語を使用してエージェントに何を実行させたいかを説明すると、Agentforce は要求に基づいてエージェントスクリプトを生成できます。その変更を確認して承諾または拒否できます。
  • 指示を評価して改善および調整します。たとえば、Agentforce に依頼して、指示をより確定的にすることができます。

Agentforce に特定の指示行について支援を求めるには、指示行にマウスポインターを置いて [] をクリックします。または、既存の指示行に「/」と入力し、[インラインアクションから AI に質問] を選択します。一般的なヘルプを表示するには、Agentforce Builder の Agentforce パネルで Agentforce とチャットします。

リソース

リソースは、サブエージェント、アクション、変数への明示的な参照です。フローやプロンプトテンプレートのリソースと同様に、推論命令のリソースも差し込み項目のように解決されます。ほとんどの場合、リソースを使用して、より確実にエージェントの行動を誘導するために、推論手順のサブエージェント、アクション、変数を参照することをお勧めします。変数についての詳細を確認します。

キャンバス ビューで、@ 記号を使用してリソースにアクセスします。アクション出力に設定されたカスタム変数を作成することもできます。アクション出力の横にある [変数を選択] をクリックし、[変数を作成] を選択します。

この例では、推論命令で変数とアクションへの明示的な参照が自然言語命令と混在しています。member_name 変数と order_summary 変数は、エージェント応答で使用され、応答をパーソナライズして形式を制御します。lookup_order および create_return エージェントアクションは、考えられるさまざまなユーザー要求に基づいてエージェントが正しいアクションを実行するために使用されます。

インラインアクション

インラインアクションは、確定的ロジックをエージェントに追加するためのショートカットです。命令にインラインアクションを含めると、推論が実行される前に実行されます。エージェントがインラインアクションを使用する方法については、サブエージェントの手順を参照してください。

キャンバス ビューで、/ 記号を使用してインライン アクションにアクセスします。

条件ステートメント

条件ステートメントは、1 つ以上の変数の値に基づいてエージェントの動作を制御します。条件ステートメントは、エージェントの分岐と考えることができます。条件が満たされると、エージェントは 1 つのパスに従います。それ以外の場合、エージェントは別のエージェントをフォローします。条件ステートメントは、推論命令で使用できます。少なくとも 1 つの変数、1 つの演算子、1 つの値が含まれますが、より複雑な場合もあります。条件ステートメント内では、サブエージェントとアクションの参照、アクションの実行、変数の設定、他のサブエージェントへの遷移ができます。

メモ 条件ステートメントを作成する場合、変数のデータ型によって値に必要な形式が決まります。
  • Boolean: True、False
  • リスト: [項目 1、項目 2、項目 3]
  • 数値: 60
  • オブジェクト: {Contact}
  • 文字列: “example@salesforce.com”

条件ステートメントを使用して、エージェントが特定の命令を適用したり、アクションを実行したり、変数を設定したり、別のサブエージェントに移行したりするときを定義します。

この例では、推論手順内でエージェントがdays_since_order変数を評価し、顧客が過去 60 日以内に注文を行ったかどうかを判断します。値が 60 以下の場合、解決済みプロンプトは、create_return アクションを使用して返品を処理するようにエージェントに指示します。値が 60 より大きい場合、解決済みプロンプトは顧客の注文が返品期間外であることを説明するようにエージェントに指示します。

移行

トランジションでは、エージェントが別のサブエージェントに移動するタイミングを定義することで、サブエージェントのルーティングを制御できます。推論手順のいずれかの時点でエージェントが別のサブエージェントへの移行を実行すると、エージェントは手順が解決して推論が行われる前に会話をリダイレクトします。

推論に使用できるアクションでは、インラインアクションの代わりにユーティリティを使用して移行またはエスカレーションします。

この例では、理由の説明でエージェントがloyalty_tier変数の値を評価し、顧客が Platinum VIP メンバーの場合、Escalation サブエージェントを介して担当者に会話を直接転送します。それ以外の場合、エージェントは顧客との会話を続行します。

変数の設定

変数を値に設定します。変数の設定は、変数に基づいて条件を作成したり、別のサブエージェントのアクションへの入力として変数を使用したり、ユーザーへの応答で変数を使用したりするなど、何らかの方法で再利用する予定の値を保存する場合に役立ちます。新しいサブエージェントを入力するときに変数の値をクリアするように変数を設定することもできます。

メモ 変数を設定する場合、変数のデータ型によって値に必要な形式が決まります。
  • Boolean: True、False
  • リスト: [項目 1、項目 2、項目 3]
  • 数値: 60
  • オブジェクト: {Contact}
  • 文字列: “example@salesforce.com”

命令でアクションを実行する場合、推論が実行される前にアクションが実行されるため、入力と出力の変数を手動で設定する必要があります。このアクションでは、設定変数の値を入力として使用するか、出力値を設定変数に保存します。推論に使用できるアクションでアクションを実行する場合、変数の設定は省略可能ですが、エージェントがあるアクションの出力を別のアクションへの入力として使用する必要がある場合に便利です。多くの場合、エージェントはアクションに最適な入力を判断できます。推論に使用できるアクションでは、インラインアクションの代わりに変数を設定するユーティリティを使用します。

この例では、推論手順内で、エージェントはorder_summary変数が空の場合に lookup_current_order アクションを実行して変数を埋めます。order_summary変数はorder_summary出力に設定されるため、エージェントがアクションを実行すると、order_summary出力の値がorder_summary変数に保存されます。次の手順では、エージェントの最初の応答に顧客の注文概要を含めるために変数が参照されます。

アクションの実行

アクションを実行すると、エージェントアクションが確定的に実行されます。推論手順では、アクションを実行して前提条件タスクを実行するか、情報を収集してエージェントに必要なコンテキストを提供します。

メモ 命令でアクションを実行する場合、推論が実行される前にアクションが実行されるため、入力と出力の変数を手動で設定する必要があります。

推論に使用できるアクションでは、インラインアクションの代わりにフォローアップアクションを使用してアクションを実行します。

この例では、推論手順にアクションの実行が条件ステートメントに含まれています。order_summary変数に会話の前半の値がまだ含まれていない場合、エージェントは lookup_current_order アクションを使用して変数を入力します。この条件文を理由の説明に含めると、エージェントは理由を説明する前に常に注文概要にアクセスできます。

推論に使用できるアクションの機能

光熱費

ユーティリティ種別には、サブエージェントを設定するトランジション、担当者へのエスカレーション、変数の設定などがあります。ユーティリティを作成し、推論に使用できるアクションに追加して、エージェントが推論中にこの機能を選択できるようにします。推論に使用できるユーティリティをアクションに追加したら、リソースを使用してアクションとして参照し、推論手順の他のインラインアクションでユーティリティの使用方法をエージェントに指示できます。

キャンバスビューでのトランジションユーティリティは次のようになります。

エスカレーションユーティリティは、メッセージングまたは拡張チャット v2 接続を使用するエージェントのみが使用できます。エージェントは Agentforce Builder で会話をエスカレーションできません。エスカレーションをテストするには、エージェントをリリースし、接続されたチャネルでチャットします。

従来のエージェントアクションとは異なり、推論に使用できるアクションで追加したユーティリティは、[エクスプローラー] パネルのサブエージェントのアクションセクションに表示されません。

検索条件 (次の場合にこのアクションを使用できるようにします)

検索条件により、エージェントは 1 つ以上の条件を満たした場合にのみサブエージェントまたはアクションを使用できます。

この例では、推論に使用できるアクションで、create_return アクションにフィルタが適用されています。このアクションは、注文が返品期間内にある場合 (return_eligibility変数が True) にのみ使用できます。

顧客の注文が検索条件を満たしているかどうかを判断するために、エージェントは理由の説明でdays_since_order変数を評価し、顧客が過去 60 日以内に注文を実行したかどうかを判断します。値が 60 以下の場合、エージェントは return_eligibility 変数の値を True に設定します。これは、create_return アクションへのアクセスの検索条件を満たしています。その後、エージェントは返品の処理を提案できます。

フォローアップアクション (このアクションの実行後:)

フォローアップアクションでは、エージェントが推論プロセス中にアクションを選択して実行した後に実行するステップを定義します。フォローアップアクションには、出力を変数に保存したり、別のサブエージェントに移行したり、別のアクションを実行したりできます。

この例では、推論に使用できるアクションで、エージェントがエージェント推論の一部としてvalidate_user_readyアクションを実行すると、エージェントは常に現在のサブエージェントからanalyze_issueサブエージェントに移行します。

Agentforce Builder での接続の設定

チャネルへのエージェントのリリースを開始するには、接続を追加します。各接続には、エージェントが 1 つ以上のチャネルの推論と応答を行うのに役立つバックグラウンドの指示が含まれます。各接続には、エージェントが応答を構造化し、画像、ボタン、リンク、動画などのマルチメディアコンテンツを提供するのに役立つ適応型応答形式が含まれます。エージェントとの会話を転送するオムニチャネルフローなどの適応型応答形式やその他の設定は、接続設定にあります。

開始する前に、エージェントを作成し、チャネルに必要な機能を有効にします。

現在、新しい Agentforce Builder でメッセージング接続と拡張チャット v2 接続を Agentforce サービス エージェントに追加できます。

  1. アプリケーションランチャーから、「Agent」と入力し、Agentforce Studioアプリケーションを選択します。
  2. [エージェント] タブで、エージェントの名前をクリックします。
  3. [エクスプローラー] パネルで、[] をクリックします。次に、[接続を追加] を選択します。
  4. [接続を追加] ウィンドウで、1 つ以上の接続を選択します。次に、[エージェントに追加] をクリックします。
    エージェントが使用できる接続のみが表示されます。各接続の詳細については、『Standard Agent Connection Reference』を参照してください。
  5. 接続の設定を完了するには、[エクスプローラー] パネルでその名前を選択します。

接続の設定が完了したら、接続チャネルでエージェントとチャットしてテストできます。

  • 新しい Agentforce Builder で作成された Agentforce 従業員エージェントは、現在会話のおすすめをサポートしていません。

    • after_reasoning ブロックはエージェント スクリプト専用であり、キャンバス ビューではサポートされません。
    • カスタム Lightning タイプを使用したエージェント アクションの入力または出力のカスタマイズは、キャンバス ビューではサポートされていません。回避策として、アセットライブラリからカスタムアクションを作成し、Input Rendering または Output Rendering パラメータを編集して、Agentforce Builder でサブエージェントに追加します。

Agentforce コンテキストエンジニアリングガイド

コンテキストエンジニアリングは、AI エージェントが目標を達成するために適切な情報、ツール、指示を提供する技術であり科学です。

プロンプトエンジニアリングは直接指示に焦点を当て、RAG (Retrieval Augmented Generation) は適切なコンテンツの取得に焦点を当てていますが、コンテキストエンジニアリングはモデルで使用できるすべてのものの全容を把握します。

コンテキストコンポーネントのサンプル

コンテキストの主要なコンポーネントをいくつか強調表示しましょう。

  • プロンプトと指示: コンテキストには、各サブエージェントにある指示やユーザのプロンプトなど、エージェントへの指示が含まれます。
  • アクションとツール: エージェントが使用できる機能は、フローの実行、Apex アクションの呼び出し、プロンプトテンプレートの使用など、コンテキストにも影響します。
  • データ入力:コンテキストには、CRM データ、Data 360、Knowledge 記事、アップロードされたドキュメント、Slack、その他のデータソースなど、構造化されたソースと非構造化ソースからエージェントが取得する関連情報が含まれます。
  • メモリ: 短期 (現在の会話) メモリと長期 (過去のやりとり) メモリの両方をコンテキストに含めることができます。

コンテキストエンジニアリングの目標は、このコンテキストを最適化して調整し、モデルが問題を解決する可能性が最も高いようにすることです。コンテキストエンジニアリングを正しく理解することで、次のような一般的な AI エージェントの問題を回避できます。

  • コンテキストクラッシュ: 命令が競合すると、予期しないパフォーマンスになったり、エラーになったりする可能性があります。
  • コンテキストの混乱: 無関係なコンテンツや不要なツールが多すぎると、エージェントの動作が一貫性を失い、エージェントの遅延が長くなる可能性があります。
  • コンテキスト ポイズニング：誤った情報または古い情報。ユーザーの Trust とエージェントの採用に影響する可能性があります。

これらの問題により、エージェントの精度と有効性が低下する可能性があります。適切な回答を得るには、AI モデルに適切な情報を適切な方法で提供することが重要です。

次に、コンテキストエンジニアリングのベストプラクティスを使用して、信頼性と効果の高いAgentforceソリューションを構築する手順について説明します。

  1. Clear Objectives の定義。Agentforce エージェントが達成すべき内容を明確に示します。このステップは、プロセスの残りの部分での決定を強固なものにするのに役立ちます。
  2. サブエージェントの制限、フィルタリング、およびルーティングの効率向上サブエージェントとアクションを最適化して、エージェントに必要な基本的なジョブとツールに制限します。適切なサブエージェントのリストを作成したら、サブエージェント分類を効果的に使用して、エージェントが作業に適したサブエージェントに転送されるようにします。
    • サブエージェントの制限。最も重要なサブエージェントとアクションのみをエージェントに割り当てます。必要に応じてサブエージェントを徐々に追加します。
    • サブエージェントを絞り込みます。検索条件を使用して、サブエージェントへのアクセスを制御します（キャンバスビューのエージェント ルータまたはスクリプトビューのstart_agentサブエージェントを使用）。

      次のスクリーンショットは、キャンバスビューでのサブエージェントの絞り込みを示しています。この手順では、変数を使用して、適用できないサブエージェントを除外します。

      エージェントスクリプトでの同じ絞り込みは次のようになります。

      start_agent agent_router:
    description: "Welcome the user and determine the appropriate subagent based on user input"
    reasoning:
        instructions: |
            You are an agent router for this assistant. Welcome the guest
            and analyze their input to determine the most appropriate subagent 
            to handle their request.
        actions:
            go_to_identity: @utils.transition to @subagent.Identity_Verification
                description: "Verifies user identity"
                available when @variables.verified == False
            go_to_order: @utils.transition to @subagent.Order_Management
                description: "Handles order lookup, refunds, and order updates."
                available when @variables.verified == True
            go_to_faq: @utils.transition to @subagent.General_FAQ
                description: "Handles various frequently asked questions."
                available when @variables.verified == True
            go_to_escalation: @utils.transition to @subagent.Escalation
                description: "Handles escalation to a human rep."
                available when @variables.verified == True and @variables.is_business_hours == True

      「サブエージェント分類およびルーティング」を参照してください。

    • Route Subagent with Logic (ロジックを使用したサブエージェントのルーティング)。特定の条件下でサブエージェントを確定的に別のサブエージェントに転送するには、サブエージェントへの明示的な参照を使用します。

      この例は、ロジック命令を使用してサブエージェント間で戦略的に転送する方法を示しています。

      start_agent agent_router:
    reasoning:
        instructions:->
            if @variables.approval_required:
                transition to @subagent.approval_workflow
            else:
                transition to @subagent.management_workflow

      Salesforce ヘルプの「プロンプトを作成するためのサブエージェント命令の解決方法」および『エージェントスクリプト開発者ガイド』の「理由の説明」を参照してください。

  3. Review Your Actions (アクションの確認)。各サブエージェントに、作業を完了するための適切で効果的なアクションがあることを確認します。

    一部のアクション(フロー、Apexメソッド、API)は確定的ですが、AIモデルを使用するアクション(プロンプト テンプレート)は確率的です。「エージェントアクション」を参照してください。

    また、アクションを使用する方法とタイミングについても検討する必要があります。その方法のヒントについては、次のステップの「Balance Probabilistic and Deterministic Behavior (確率的動作と確定的動作のバランス)」を参照してください。

  4. Tune Your Subagent Instructions (サブエージェントの指示の調整)。キャンバスビューでエージェントを作成するか、エージェントスクリプトで直接エージェントを作成するかに関係なく、コンテキストを最適化する最も強力な方法の 1 つは、サブエージェントの推論手順です。この手順には、コンテキストにとって重要な側面がいくつかあります。
    • ランタイムフローを確認します。命令を過度に変更する前に、エージェントの実行時の動作を理解して、コンテキストに含まれる命令を把握してください。「How Agents Work and How Subagent Instructions are Resolved to Build a Prompt」を参照してください。開発者は、『Agent Script Developer Guide (エージェントスクリプト開発者ガイド)』の「Flow of Control (制御フロー)」を参照することもできます。
    • 変数を使用してデータを保存。関連データを変数に指定して、指示で直接使用できるようにします。

      次のスクリーンショットは、キャンバスビューの変数定義を示しています。

      次のコードサンプルは、スクリプトビューで同じ変数を示しています。

      user_name: mutable string = ""
    description: "The name of the user"
    label: "Name"
    visibility: "External"

      変数を効果的に使用してアクションを実行する方法はいくつかあります。この例では、変数を使用してアクションを絞り込む方法を示します。

      get_order_details: @actions.GetOrderByOrderNumber
    available when @variables.verified == True

      また、この例では、アクションの入力と出力に変数を使用する方法を示します。

      run @actions.GetOrderByOrderNumber
    with order_number = @variables.order_number
    set @variables.order_details = @outputs.orderDetails

      エージェント定義全体で変数を使用できます。「変数」を参照してください。

    • Balance Probabilistic Behavior and Deterministic Behavior (確率的動作と確定的動作のバランス)。サブエージェントの指示には、ロジックベースの指示とプロンプトベースの指示の両方が含まれます。重要なビジネスワークフローの手順のロジックを活用して、予測可能で確定的な動作を増やします。たとえば、プロンプトベースの手順を実行する前に、ユーザーのロイヤルティランクを確認したり、条件ロジックを使用してユーザーがゴールドランクメンバーであることに感謝するかどうかを判断したり、変数を使用してプロンプトをカスタマイズしたり、メールを送信するアクションを実行したりできます。これにより、不必要で予測不能なロジック命令でモデルのコンテキストをオーバーロードすることなく、AI モデルが最も得意とする内容に自然言語プロンプトを集中させることができます。

      このサンプルでは、ロジックベースの命令の使用方法を示しています。この手順では、変数をチェックして、顧客がホテルを予約する準備ができているかどうかを確認します。その場合、アクションの入力と出力の変数を使用して取引先情報を取得します。次に、ホテル情報を取得する別のアクションを実行します。

      if @variables.ready_to_book:
    run @actions.get_account_info
        with account_id = @variables.account_id
        set @variables.hotel_code = @outputs.hotel_code
run @actions.get_hotel_info
    with hotel_code = @variables.hotel_code
    set @variables.hotel_info = @outputs.hotel_info

      Salesforce ヘルプの「プロンプトを作成するためのサブエージェント命令の解決方法」および『エージェントスクリプト開発者ガイド』の「理由の説明」を参照してください。

    • Reference Resources Direct (直接参照リソース)。キャンバスビューとスクリプトビューのどちらでエージェントを作成しているかに関係なく、サブエージェント、アクション、変数を指示で直接参照できます。この機能は、リソースを具体的に「@メンション」できるため、指示のあいまいさを排除します。

      このサンプルは、命令でリソースを参照する方法をいくつか示しています。

      instructions: |
    Refer to the user by name @variables.member_name.
    Show their current order summary: @variables.order_summary 
    when conversation starts or if requested.
    If they want past order info, ask for Order ID or Restaurant Name 
    and use @actions.lookup_order.
    If they ask for a service agent or seem upset, use @actions.go_to_escalation.
    If they want to make a return, confirm Order ID and use @actions.create_return.
    If returns are not eligible, explain politely.

      「Building Agents in Canvas View」または「Get Started with Agent Script」を参照してください。

  5. Use Accurate, Relevant Data (正確な関連データの使用)。入力が最適な情報に基づいていることを確認します。
    • CRMデータ、Data 360データ、外部データ、その他のソースなどの構造化データは、適切で最新であり、当面の意思決定やタスクに関連している必要があります。Trailhead の「Strategies for Data Quality」を参照してください。
    • RAGで取得したデータ ライブラリやその他の入力などの非構造化データは、正確で、ユーザーの要求に直接関連している必要があります。RAG入力の成功は、正確かつ完全で、最新かつ整理された一貫性のある、厳選された高品質のコンテンツのKnowledge Storeから始まります。その他の考慮事項には、検索戦略(ハイブリッド検索またはベクトル検索)、コンテンツの解析と前処理、検索インデックス最適化、適切に調整されたチャンク戦略、Knowledge/RAG品質データと評価指標を使用した改善すべき領域の特定などがあります。
  6. 一貫性を確保します。プロンプト、サブエージェント、アクション、RAGデータ、命令、Salesforce設定間の矛盾を排除します。
  7. Test、Iterate、Refine。Agentforce Builder でエージェントをプレビューします。Agentforceテストセンターを使用してテストを作成し、分析を使用してエージェントを監視します。会話トランスクリプトからのフィードバックを使用してコンテキストを絞り込みます。モデルの更新など、ソリューションのあらゆる側面が変更されたら、必ずエージェントを再テストしてください。

エージェントのコンテキストを慎重に管理することで、Agentforceを使用して信頼性が高く効果的なAIソリューションを構築できます。

変数と検索条件を使用して、エージェントが一般的なトラブルシューティングの問い合わせを効果的に解決できるようにします。この例では、ログインの問題に関連するトラブルシューティング手順と、エージェントが使用できるアクションを制御する検索条件を保存する変数を作成します。エージェントは、すべてのトラブルシューティング手順を変数に保存します。次に、会話のコンテキストに基づいて最も関連性の高いステップを提供することで、トラブルシューティングプロセスを通じて顧客をガイドします。

カスタムエージェントアクションの作成

エージェントがトラブルシューティングステップを [トラブルシューティングステップ] 変数に保存し、関連するステップをエンドユーザーに送信するのに役立つ 2 つのカスタムエージェントアクションを作成します。

カスタムエージェントアクションについての詳細は、「カスタムエージェントアクションの作成」を参照してください。

  1. Agentforce アセットの「設定」ページで、「アクション」タブを選択します。次に、カスタムアクションを作成するには、[新規エージェントアクション] をクリックします。
  2. 最初のアクションで、次のプロパティを入力します。
    1. 参照アクション種別: Select Prompt Template (プロンプトテンプレートを選択)
    2. 参照アクション: [Get Troubleshooting Steps (トラブルシューティング手順の取得)] を選択します。
    3. エージェントアクションの手順: トラブルシューティングガイドのトラブルシューティング手順をすべて取得します
    4. Loading Details (詳細の読み込み): トラブルシューティング手順の検索
    5. AllTroubleshootingSteps 入力手順: すべてのトラブルシューティング手順の順序付きリスト。
  3. 2 番目のアクションでは、次のプロパティを入力します。
    1. 参照アクション種別: Select Prompt Template (プロンプトテンプレートを選択)
    2. 参照アクション: [ ステップバイステップでトラブルシューティング] を選択
    3. エージェントによるアクションの手順: 現在、お客様の問題を解決中です。問題を解決するには、TroubleshootingSteps の手順に従います。この一連のステップのうち、顧客からのこの質問に最も適した UserInput ステップは一度に 1 つしか指定できません。最適なステップでユーザーにのみ応答します。
    4. Loading Details (詳細の読み込み): Getting the next step (次のステップの取得)
    5. UserInput input instructions (UserInput 入力手順): 解決する必要のある質問または問題をユーザーが指定した文字列。[入力が必要] を選択します。
    6. TroubleshootingSteps 出力手順: 残りのトラブルシューティング手順の順序付きリストです。[会話に表示] を選択します。

カスタムエージェントサブエージェントの作成

エージェントが [Get Troubleshooting Steps (トラブルシューティングステップを取得)] アクションと [Troubleshoot Step By Step (ステップバイステップでトラブルシューティング)] アクションを使用してトラブルシューティングの問い合わせに対応できるようにするカスタムエージェントサブエージェントを作成します。

カスタムエージェントサブエージェントについての詳細は、「従来のビルダーでのカスタムサブエージェントの作成」を参照してください。

  1. Agentforce エージェントの [設定] ページから、Agentforce Builder でエージェントを開きます。
  2. [サブエージェント] タブで、次のプロパティを使用してカスタムエージェントサブエージェントを作成します。後で、サブエージェントの指示で言及される変数を作成します。
    1. 名前: Troubleshooting Inquiries
    2. 分類の説明: このサブエージェントは、顧客が技術的な問題、エラー、または修正が必要な問題について説明すると、段階的なトラブルシューティングプロセスを開始します。
    3. 範囲: 職務は、最初に完全な手順セットを取得してから、一度に 1 ステップずつユーザーに提供する、複数ステップのトラブルシューティングプロセスを実行することです。各ステップの後にユーザーからのフィードバックに基づいて、複数のターンにわたって会話を管理する必要があります。文書に記載されているトラブルシューティング手順以外の問題には対処しないでください。
    4. 手順:

      Get_Troubleshooting_Steps アクションを使用して、完全なトラブルシューティングガイドを取得し、TroubleshootingSteps 変数に入力します。このアクションは、会話の開始時に 1 回のみ使用します。

      Get_Troubleshooting_Steps アクションを使用したら、Troubleshoot_Step_By_Step アクションを使用して最初のステップを取得します。次に、ステップを実行して結果を報告するようにユーザーに指示します。例: 「では、最初のステップから始めましょう: [ここに最初のステップを挿入してください]」

      ユーザからの後続の返信ごとに、Troubleshooting_Steps 変数を参照してください。次のステップをユーザーに提示します。

      問題が解決されたことをユーザーが確認するか、Troubleshoot_Step_By_Step アクションでステップがなくなったことが示されるまでループを続行します。

    5. サブエージェントに [Get Troubleshooting Steps (トラブルシューティングステップを取得)] および [Troubleshoot Step By Step (ステップバイステップでトラブルシューティング)] エージェントアクションを含めます。

カスタム変数の作成

トラブルシューティング手順を保存するカスタム変数を作成します。変数を使用すると、エージェントは会話全体で特定の情報を保存して再利用できます。この例では、変数に [トラブルシューティングステップを取得] アクションの出力が保存されます。

カスタム変数についての詳細は、「従来のビルダーでのエージェントのカスタム変数の作成」を参照してください。

  1. Agentforce エージェントの [設定] ページから、Agentforce Builder でエージェントを開きます。
  2. [サブエージェント] パネルで、[Troubleshooting Inquiries (問い合わせのトラブルシューティング)] サブエージェントを選択し、[このサブエージェントのアクション] タブをクリックします。
  3. [Get Troubleshooting Steps (トラブルシューティングステップを取得)] アクションを選択します。次に、[応答を要求] アクションの出力を新しいカスタム変数に対応付けます。
  4. 変数の名前に「Troubleshooting Steps」と入力します。[Allow LLM to use value (LLM に値の使用を許可)] を選択し、変数を保存します。

API から変数を使用するには、「エージェント API を使用したエージェント変数の送信」を参照してください。

アクション検索条件の作成と追加

作成したアクションを使用するタイミングをエージェントに指示する 2 つの検索条件を作成します。サブエージェントやアクションの指示とは異なり、検索条件は確定的であり、エージェントの会話全体で一貫して適用されます。この例では、検索条件によって、トラブルシューティングステップ変数が指定された条件を満たす場合にのみアクションが実行されます。

フィルタについての詳細は、「従来のビルダーでのサブエージェントおよびアクションへのアクセスを制御するフィルタの作成」を参照してください。

  1. Agentforce エージェントの [設定] ページから、Agentforce Builder でエージェントを開きます。
  2. [コンテキスト] パネルで、[フィルタ] タブを選択します。フィルタを作成するには、［New］ をクリックします。
  3. 最初の検索条件に「No Steps」 (ステップなし) という名前を入力します。条件で、Troubleshooting Steps 変数が空であることを確認します。
  4. 2 番目の検索条件に、「Yes Steps」 (はいステップ) という名前を入力します。条件で、トラブルシューティングステップ変数が空でないことを確認します。
  5. [サブエージェント] パネルを選択します。[トラブルシューティング問い合わせ] サブエージェントの [このサブエージェントのアクション] タブで、[Get Troubleshooting Steps (トラブルシューティング手順の取得)] アクションを選択します。アクションの詳細パネルで、[] をクリックし、[ステップなし] 検索条件を選択します。
  6. [Troubleshooting Inquiries (トラブルシューティング問い合わせ)] サブエージェントの [This Subagent's Actions (このサブエージェントのアクション)] タブで、[Troubleshooting Step By Step (ステップバイステップのトラブルシューティング)] アクションを選択します。アクションの詳細パネルで、[] をクリックし、[Yes Steps (はいステップ)] 検索条件を選択します。

エージェントをテストするには、プレビューの会話を更新し、エージェントにトラブルシューティングの支援を依頼します。エージェントは変数と検索条件を使用して、最も関連性の高いトラブルシューティング手順のみを送信します。

Einstein Requestsは、生成AIの利用状況の評価指標です。本番環境またはSandbox環境で生成AI機能を使用すると、Einstein要求と場合によってはData 360クレジットを消費します。詳細は、「生成 AI の請求可能な利用状況の種別」を参照してください。

Agentforce (デフォルト) は、Einstein を使用し、Data 360 を使用してデータを保存および処理する消費ベースの製品です。Agentforce（デフォルト）は、機能の使用に基づいて請求に使用されるクレジットを消費します。

Agentforce（デフォルト）は、Lightning Experience、Slack、Salesforce Mobile アプリケーション、Field Service Mobile アプリケーション、Sales Cloud Everywhere の Agentforce パネルなどの従業員チャネルでサポートされています。

  • 会話履歴は現在のセッションにのみ適用されます。最大で直近 6 ターンまでのメッセージ (エージェントおよびユーザーメッセージを含む) がコンテキストとして使用されます。CRM の使用事例に焦点を絞ったコンテキストを維持するため、「こんにちは」などのメッセージは含まれていません。

  • Agentforce (デフォルト) では、プロアクティブな提案はできません。エージェントとの会話を開始するには、ユーザーが要求を入力するか、質問する必要があります。

    Agentforce サービスエージェントが送信するすべてのメールの構造を定義する Lightning メールテンプレートを作成します。Classic メールテンプレートはサポートされていません。
  • 電子メールでの Agentforce サービスエージェントの電子メール設定の作成
    電子メール設定は、電子メールテンプレートを Agentforce サービスエージェントに接続します。[設定] で作成し、1 つ以上のルーティングアドレスにリンクします。
  • 電子メールでの Agentforce サービスエージェントのルーティングロジックの更新
    ほぼすべてのパズルピースが揃っていますが、エージェントが顧客にメールを送信するためにメールテンプレートを使用するタイミングは Salesforce で把握する必要があります。Agentforce サービスエージェントとサービス担当者のどちらにケースを転送するかを制御するオムニチャネルフローを作成することをお勧めします。
  • 電子メールでの Agentforce サービスエージェントのテスト
    ルーティングにオムニチャネルフローを使用している場合、新しい未使用のルーティングアドレスを使用してフローをテストします。次に、準備が整ったら有効なルーティングアドレスに切り替えます。
  • Agentforce サービスエージェントから送信されたメールの監視
    AI エージェントが送信したメールを表示および監視するには、カスタムレポートを作成するか、特定のケースのケースフィードを確認します。
  • Agentforce サービスメールでのコンテキスト変数の使用
    Agentforce サービスエージェントは、ケース ID などの受信メールコンテキストをユーザ メッセージにバンドルするのではなく、コンテキスト変数に渡すようになりました。これらの変数をトピックやアクションの入力で参照することで、自動化の信頼性を高めることができます。

拡張チャット

拡張チャットは Salesforce のメッセージングチャネルです。Agentforce エージェントが Web サイトまたはモバイルアプリケーションから直接顧客とのやりとりを処理できます。現在、拡張チャットには拡張チャット v1 と拡張チャット v2 の 2 つのバージョンが用意されています。

拡張チャットの両方のバージョンで、次の主要な機能が共通しています。

  • 自律的な問題解決: Agentforce エージェントは、受信した要求を自律的に処理し、問い合わせを解決できます。顧客の要求 (請求に関する質問、予定の予約、注文状況の検索など) を最小限の待ち時間で解決します。
  • サービス担当者へのエスカレーション: 必要な場合、またはお客様から特に要求された場合に、Agentforce エージェントから人間のサービス担当者に会話をエスカレーションします。
  • インタラクティブコンテンツ: クリック可能なメッセージングコンポーネントを活用して、顧客が最新のメッセージングチャネルに期待するインタラクティブで視覚的なリッチな環境を提供します。

拡張チャット v2

拡張チャット v2 は、最新のインタラクション環境とエージェントの使用事例に合わせて最適化された最新のメッセージングインターフェースです。カスタムLightning種別を使用したカスタマイズがサポートされているため、リッチ・リンクのプレビューやクイック返信など、標準のメッセージング・コンポーネント以外のインタラクションを調整できます。

拡張チャット v2 には、次の主要な機能があります。

  • 最新のインタラクション エクスペリエンス:標準でモダンに設計された、更新されたAgentforceスタイルのブランド設定を採用します。
  • カスタムコンテンツ: 標準およびカスタム Lightning タイプを定義して表示し、チャット内でカスタム Lightning Web コンポーネントを紹介できるようにします。
  • エージェント機能: トークンストリーミングなど、エージェント向けの高度な機能をサポートします。
  • パフォーマンス: チャットウィンドウの読み込み時間が短縮されました。
  • コンテキストイベント API: 新しい API (utlAPI) でコンテキストイベントをサポートすることで、ユーザーセッションの詳細 (現在のページ URL や検索活動など) をエージェントに渡すことができます。

サービスエージェントを拡張チャット v2 に接続するには、「拡張チャット v2 へのサービスエージェントの接続」を参照してください。

拡張チャット v1

拡張チャット v1 (旧称メッセージングアプリ内および Web) は、高度な設定が可能で、大企業向けに調整された Web およびモバイルチャット環境をサポートします。

拡張チャット v1 には、次の主要な機能があります。

  • カスタマイズ: 高度な設定可能性を活用して、広範な UI ブランドオプションを設定します。
  • エージェントルーティング: 転送とルーティングの営業時間とエージェントの対応可能状況を設定します。予想待機時間と順番待ちの位置を顧客に表示します。
  • セキュリティと認証: ユーザー検証をサポートし、検証済みユーザーと未検証ユーザーの両方の認証トークンの有効期限を設定します。
  • 顧客アクション: 顧客がエージェントに添付ファイルを送信したり、会話トランスクリプトをダウンロードしたりできるようにします。

サービスエージェント実行コンテキストの詳細

Agentforce サービスエージェントは、顧客対応の使用事例を対象としており、認証済みおよび認証されていない外部ユーザーをサポートする拡張メッセージングチャネルに接続します。エージェントのデータアクセスと実行コンテキストは、チャネルと、ログイン情報ベースのユーザー検証が有効になっているかどうかによって異なります。

  • 通常、エージェントのデータアクセスおよび実行コンテキストはエージェントユーザーによって決まります。エージェントユーザーとは、エージェントが作業するために必要なすべての権限を持つエージェントの一意のユーザーレコードです。エージェントはエージェントユーザーのコンテキストで実行され、エージェントユーザーのプロファイル、権限、項目レベルセキュリティ、共有ルールに従います。
  • 拡張チャット v1 または拡張チャット v2 を使用してサービスエージェントを Experience Cloud サイトにリリースしている場合、ログイン情報ベース ユーザー検証を有効にできます。ログイン情報ベースのユーザー検証が有効になっている場合、エージェントはログインサイトユーザーのコンテキストで実行され、ユーザーのプロファイル、権限、項目レベルセキュリティ、共有ルールに従います。

サービスエージェントがエージェントユーザーのコンテキストで実行される場合、コンテキスト変数(MessagingSesson.ContactIdなど)はエージェントに顧客の ID を渡すために使用されますが、データアクセスを制御するものではありません。追加の設定なしで、顧客はエージェントユーザーがアクセスできるすべてのレコードにアクセスできます。データアクセスを積極的に制限する必要があります。

  • 検証済みの顧客 ID をカスタム VerifiedCustomerId 変数に渡します。

    エージェントでのユーザー検証に標準の Customer Verification または Service Customer Verification サブエージェントを使用する場合、ID が正常に検証された後にユーザーの ID を VerifiedCustomerId 変数に保存するようにアクションが設定されます。それ以外の場合は、カスタム エージェント アクションと Apex クラスまたはフローを作成して、検証済み ID をエージェントに渡して VerifiedCustomerId 変数に保存できます。

  • 標準およびカスタム・エージェント・アクションによってコールされるApexクラスおよびフローの範囲を顧客レコード（WHERE ContactId = VerifiedCustomerId）に明示的に指定します。

    一部の標準アクションでは、顧客の検証が標準でサポートされています。たとえば、Get Cases for Verified Contact アクションは、顧客の取引先責任者 ID を検索し、VerifiedCustomerId変数と照合して、検証済みの顧客 ID を使用してクエリの範囲を設定するフローをコールします。ただし、セキュリティニーズに合わせて各アクションを慎重にテストしてカスタマイズする必要があります。

  • フィルタ (VerifiedCustomerId is not None) を作成して、サブエージェントへのアクセスと検証済みの顧客へのアクションを制限します。

命令の遵守

指示の遵守は、エージェントが応答を生成するときにサブエージェントの指示をどの程度適切に解釈しているかを評価するエージェントガードレールです。

命令遵守スコア

指示の遵守では、エージェントの応答を評価し、エージェントがサブエージェントの指示をどの程度適切に解釈して従えているかに基づいてスコアを付けます。スコアカテゴリは 3 つあります。

スコア 説明
High (高) エージェントがサブエージェントの指示を解釈して完全に従い、重要事項に対処して必要な情報を提供していることを示します。
Low (低) エージェントがサブエージェントの指示を正確に解釈または従わないことを示します。少なくとも 1 つの命令に従うことに失敗し、誤った応答が返されます。
不確定 指示の遵守を確定的に判断できないことを示します。これは、あいまいな応答またはアクション、不完全な応答、またはサブエージェントの指示の解釈の競合が原因である可能性があります。

スコアと説明が Data 360 に記録され、エージェントイベントログに表示される

命令遵守スコアは、Data 360のEinstein生成AI監査およびフィードバック データ モデルに記録されます。これは、組織で有効にする必要があります(「Einstein生成AI監査およびフィードバックの設定」を参照)。スコアはエージェントイベントログに表示されます。[拡張エージェントイベントログ] を有効にします。

操作手順

Agentforce では、次の 3 つの主要な言語設定が使用されます。

  • エンドユーザー言語: この設定はユーザーの入力言語を表します。この値は、エージェントチャネル (またはクライアント) によって明示的に定義されます。この設定の入力方法は、使用しているエージェントチャネルの種別によって異なります。
    • Lightning Experience の Agentforce パネルに接続されたエージェント（Agentforce 従業員エージェントなど）の場合、エンドユーザ言語は組織の Salesforce ユーザの言語設定から設定されます。「Edit Your Language and Locale Settings (言語およびロケール設定の編集)」を参照してください。
    • 拡張チャット v1 に接続されているエージェント(Agentforce サービス エージェントなど)の場合、システム管理者は事前チャット フィールドを設定して、エンドユーザーの言語を決定します。「拡張チャット v1 の会話での追加言語の使用」を参照してください。
    • 他のチャネル(Agentforce Lead Nurturing など)に接続されているエージェントの場合、エージェント API を使用してエンドユーザー言語を設定できます。「エージェント API を使用したエージェント変数の送信」を参照してください。
  • エージェントデフォルト言語: これは、エージェントに指定する主言語または代替言語です。セッションの開始時に言語が検出されない場合、または検出された言語がサポートされていない場合、エージェントはデフォルト言語を使用します。「言語設定の更新」を参照してください。
  • エージェントが許可する言語: これは、言語検出に基づいてエージェントが切り替えることができる、サポートされる第 2 言語セットです。「言語設定の更新」を参照してください。

例: システムメッセージとエンドユーザー言語

エージェントを設定するときに、エージェントのシステム メッセージを定義します。これには、歓迎メッセージ、エラーメッセージ、および (サービスエージェント用の) エスカレーションメッセージが含まれます。これらのメッセージは 1 つの言語で記述されます。

チャット セッションの開始時に、Agentforce は 3 つの主要な言語設定に基づいてシステム メッセージを翻訳するかどうかを決定します。

  • エンドユーザー言語がエージェントのデフォルト言語と一致する場合、翻訳は行われず、システムメッセージは最初に記述されたとおりに出力されます。
  • 設定が一致しない場合、Agentforce はエンドユーザー言語がエージェント第 2 言語かどうかを確認します。存在する場合、Agentforce はシステムメッセージをエンドユーザー言語に変換します。
  • エンドユーザー言語がエージェントデフォルト言語でもエージェント第 2 言語でもない場合は、エージェントデフォルト言語が使用されます。翻訳は行われず、システムメッセージは最初に記述されたとおりに出力されます。

メモ 言語切り替えは、新規 Agentforce Builder で作成されたエージェントでのみサポートされます。

エージェントに複数の言語が設定されている場合、エージェントは会話内のユーザーの入力言語 (設定済みの言語のいずれか) が優先されます。たとえば、デフォルト言語として英語、追加言語としてポルトガル語とスペイン語が設定されているエージェントについて考えてみます。

  • セッションの開始時に、エンドユーザーの言語は英語に設定されます。
  • ユーザーがスペイン語で質問すると、エージェントはスペイン語で応答します。
  • その後、ユーザーが英語で (同じ会話で) 質問すると、エージェントは切り替えて、ユーザーのデフォルト言語がスペイン語であっても英語で応答します。
  • その後、ユーザーがポルトガル語で (同じ会話で) 質問すると、エージェントは再度切り替えてポルトガル語で応答します。
  • エージェントがアクションを実行すると、アクションの出力はセッション全体を通じてエンドユーザー言語 (英語) で表示されます。ただし、アクション出力をラップするエージェントの応答は動的です。「Asunto: Issues with Canvas (アスンート: キャンバスの問題)」のように 言語が混在する回答を表示することもでます

エージェントは、理解するように設定された言語に従います。エージェントが設定されていない言語でユーザーが質問をすると、エージェントはその言語で回答しないことがあります。代わりに、ユーザーの言語で応答できないことを説明します。たとえば、ユーザーがイタリア語で質問し、エージェントがイタリア語を使用するように設定されていない場合、エージェントはイタリア語で応答し、サポートされる言語を説明します。

この動作により、エージェントはユーザーのメッセージの即時言語に応答し、処理するように設定されていない言語の境界も維持されます。

MCP とは?

モデルコンテキストプロトコル (MCP) は、AI モデルが外部システム (ツールを含む) に接続する方法に関するオープン標準です。このプロトコルを開発した Anthropic は、USB-C ポートのような MCP について次のように考えています。「USB-C がデバイスをさまざまな周辺機器やアクセサリに接続する標準化された方法を提供するのと同じように、MCP は AI モデルをさまざまなデータソースやツールに接続する標準化された方法を提供します。」

MCP のしくみ

Agentforce エージェントが、Salesforce 取引先に関連付けられた取引先責任者のローンリスクスコアをサードパーティの銀行サービスから取得するとします。MCP を使用しない場合、2 つのシステムを手動で統合し、すべての API 接続、認証、データアクセス、コードを処理する必要があります。MCP はシステム間の翻訳者として機能するため、この複雑な手動作業は自動的に行われます。エージェントは Salesforce データを使用してサードパーティの銀行サービスでユーザーの詳細を検索し、ローンリスクスコアを使用して会話の次のステップを判断できます。

MCP プロトコルは、サーバ、クライアント、およびホストに依存します。

  • MCP サーバーは、Salesforce、MuleSoft、サードパーティサービスプロバイダーなどのサービスプロバイダーによって作成されます。サーバーには、ツール、プロンプト、リソースなど、外部システムで使用可能なすべてのアセットが含まれます。
    • ツールはエージェントアクションに似ています。LLM が外部システムでアクションを実行するためにコールできる実行可能な関数です。
    • プロンプトは、動作のガイドとなる、サーバーから LLM への自然言語の指示です。
    • リソースは、データフィード、ファイル、その他の情報など、サーバーがアクセスできるデータです。
  • MCP クライアントは 1 つ以上のサーバーに接続して、外部システムのツールとデータにアクセスします。クライアントは機能と情報の取得者と考えてください。
  • MCP ホストは、このプロセスを調整するアプリケーションです。ホストは、MCP サーバーのツールとデータを使用するためのインターフェースを提供し、MCP クライアントを管理します。

MCPクライアントはAgentforceに組み込まれているため、MCPサーバを簡単に登録して管理でき、エージェントはサーバツールに安全にアクセスして使用できます。

Agentforce のTrustと MCP

Salesforce では、Trust が最大の価値です。Agentforce はホストおよびクライアントであるため、Agentforce の MCP をTrustできます。

MCP for Agentforceは、Agentforce Trust Layerやゼロ データ保持ポリシーなど、Agentforceの他の製品と同じセキュリティおよびコンプライアンス管理によって保護されます。Salesforce データは Salesforce に残ります。

一般的なセキュリティ脅威に対する自動チェックが提供されます。

  • 非表示文字: 非表示文字は、悪意のある命令を非表示にするために使用できます。Agentforce レジストリに MCP サーバを登録すると、サーバおよびツールの名前と説明に目に見えない文字が含まれていないかどうかが確認され、登録を完了する前に警告が表示されます。
  • ラグプル: ラグプルは、以前に安全な MCP サーバーまたはツールが、サーバーが登録された後に悪意のある手順が含まれるようにパブリッシャーによって更新された場合に発生します。登録時およびツールの許可リスト登録時に、入力スキーマと出力スキーマを含むサーバーとツールの定義を取得します。これらは実行時データだけでなく安定した契約として処理されるため、各エージェントセッションの開始時やエージェントがサーバーツールをコールするたびに変更をスキャンできます。変更が検出されると、関連付けられた MCP ツールアクションがエージェントのロジックと推論から削除され、実行時に同期されていないサーバーまたはツールの使用が自動的にブロックされます。影響を受けるアクションのみがブロックされるため、エージェントが中断されることはありません。

Agentforce ゲートウェイは、もう 1 つの保護レイヤーを提供し、アクセスの制御、使用制限の設定、コンプライアンスの確保を可能にします。Agentforce Gateway では、特定のエージェントや MCP ツールのルールなど、MCP サーバの使用状況と動作を規定するポリシーを作成して適用できます。ポリシーは、手動またはルールで自動的に適用できます。

他のAgentforce機能と同様に、MCP for Agentforceは生成AIを搭載しています。生成 AI では、不正確な応答が生成される可能性があります。回答を慎重にテストして確認します。

MCP サーバーと登録

  • MCP for Agentforce は、Streamable HTTP Transport Protocol を使用するサーバをサポートします。HTTP+SSE およびその他のプロトコルはサポートされません。
  • MCP for Agentforce では、認証なしと OAuth 2.0 クライアント クレデンシャルのみがサポートされます。認証コード、CIMD、DCR、JWT ベアラー、PKCE など、他の OAuth フローはサポートされていません。OAuth 2.1 クライアントログイン情報など、一部の高度な認証パターンを追加の設定で使用できます。
  • ユーザーレベルの認証はサポートされていません。現在、個々のユーザー ID やパーソナライズされた応答を必要とする使用事例はサポートされていません。たとえば、MCP for Agentforceを使用して個々のユーザーに返金することはできませんが、顧客のすべての請求書を取得することはできます。
  • MCP for Agentforce では、サーバ ツールのみがサポートされます。MCP サーバーアプリケーション、プロンプト、リソースはサポートされません。
  • ツール名は最大 128 文字で、^a-zA-Z0-9./-{1,128}$ の文字がサポートされます。
  • MCP サーバーが同期されていない場合や、MCP サーバーが使用できない場合、登録リストビューとサーバーレコードページには現在、サーバーが接続済みとして表示されます。修正が進行中です。
  • サーバー登録またはサーバー自体を変更すると、エージェントで関連付けられた MCP ツールアクションが中断される場合があります。登録の削除などの変更を行う前に、エージェントから関連付けられたアクションを削除し、アセットライブラリから関連付けられたエージェントアクションを削除してから、サーバー登録を削除します。その後、サーバーを再登録して、新しい MCP ツールアクションをエージェントに追加できます。

パッケージ化とリリース

セキュリティを確保するため、Salesforce では MCP ツールアクションを含むエージェントのパッケージ化またはリリースをサポートしていますが、MCP サーバー登録メタデータはパッケージ化されていません。エージェントに追加された MCP ツールアクションは、標準では機能しません。

パッケージをリリースする前に、新しい環境で MCP サーバーを登録し、エージェントが使用するツールを許可リストに登録します。次に、リリース後にエージェントから既存の MCP ツールアクションを削除し、アセットライブラリの新しいアクションに置き換えます。

エージェントメタデータは、ドラフトエージェントまたは確定エージェント用にパッケージ化できます。エージェントが新しい環境でドラフト状態の場合、編集できます。エージェントがコミット状態の場合、新しいドラフトを作成して変更を加えます。

Agentforce プラットフォームおよびビルダーのサポート

  • MCP サーバーアクション (MCP ツールアクション) を参照するエージェントアクションの請求レートは他のエージェントアクションと同じです。使用状況に関するレポートは Digital Wallet で利用できます。「Agentforce および生成 AI の使用状況と請求」を参照してください。
  • Agentforce Builder のサポートは、プリミティブ値と項目アクセスが浅い場合に最適です。そのため、可能な場合は、構造化された JSON 応答がシンプルな MCP サーバ ツールを選択するか、応答を調整してください。最上位オブジェクト、最上位オブジェクトプロパティ、および最上位オブジェクトの配列がサポートされます。現在、ネストされたプロパティ、オブジェクトの配列、動的オブジェクトのペイロードなど、より複雑な形状はエンドツーエンドでサポートされていません。詳細はこちら。
  • Agentforce Builder は Lightning 種別を使用してアクションの入力と出力を表示します。すべての MCP ツールの入力スキーマと出力スキーマが Lightning タイプに対応付けられるわけではありません。MCP ツール アクションのデータを Lightning 種別に解決できない場合でも、エージェントでアクションを使用できますが、入力または出力を変数に保存することはできません。詳細はこちら。
  • MCP ツールアクションをエージェントに追加すると、次のようになります。
    • 一部のデータ型 (数値など) の入力表示ラベルと出力表示ラベルは、「文字列」の表示ラベルに置き換えられることがあります。これはエージェントのロジックや推論には影響しませんが、使いやすさを考慮して、表示ラベルをアセットライブラリの MCP ツールアクションまたは MCP ツールの入力スキーマまたは出力スキーマの元の値に置き換えることをお勧めします。修正が進行中です。
    • [参照アクション種別] 項目は空で表示されます。参照アクションが入力されるため、アクションは必須項目として識別されていても、参照アクション種別なしで実行できます。[参照アクション種別] 項目をクリックまたは変更すると、参照アクションはリセットされ、MCP ツールに手動でリセットすることはできません。この場合、エージェントからアクションを削除して、アセットライブラリから再追加します。修正が進行中です。
    • MCP サーバーおよびツールの場合、プロパティは 255 文字以下にする必要があります。255 文字を超えるプロパティは現在サポートされていません。
  • MCP サーバの応答には、次のタイムアウト期間が適用されます。可能な場合は、これらの制限に合わせて応答を調整します。
    • MCP クライアントのタイムアウト制限は 60 秒です。たとえば、サーバーが使用できない場合や、応答に 60 秒以上かかる場合などです。
    • Atlas 推論エンジンのタイムアウトは 120 秒です。たとえば、複数のサーバーがコールされ、その応答に合計で 120 秒以上かかった場合などです。
