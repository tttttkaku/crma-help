クエリを使用したインサイトの取得

クエリを使用して監査およびフィードバックデータを分析します。次の例は、GenAIGtwyObjRecord を sObject から GenAIGatewayRequest または GenAIFeedback にリンクする方法を示します。sObject が Case であるとします。このクエリでは、ケースで使用またはコールされた生成 AI 要求の数を取得できます。生成 AI を使用したケースと使用しないケースの解決時間を比較できます。GenAIFeedback テーブルをリンクして、生成 AI が役立ったかどうかを判断したり、特定のケースの生成 AI にフィードバックしたりすることもできます。

SELECT *
        FROM "GenAIGtwyObjRecord__dlm"
        JOIN "GenAIFeedback__dlm" ON "GenAIGtwyObjRecord__dlm"."parent__c" = "GenAIFeedback__dlm"."feedbackId__c"
        JOIN "GenAIGeneration__dlm" ON "GenAIFeedback__dlm"."generationId__c" = "GenAIGeneration__dlm"."generationId__c"
        JOIN "GenAIGatewayResponse__dlm" ON "GenAIGeneration__dlm"."generationResponseId__c" = "GenAIGatewayResponse__dlm"."generationResponseId__c"
        JOIN "GenAIGatewayRequest__dlm" ON "GenAIGatewayResponse__dlm"."generationRequestId__c" = "GenAIGatewayRequest__dlm"."gatewayRequestId__c"
        LIMIT 10

監査およびフィードバックオブジェクトのデータガバナンス権限の実装

監査およびフィードバックデータには、個人識別情報 (PII) など、未承認のユーザーには無効化または非表示にする機密情報が含まれている可能性があります。Data Cloud データガバナンスを使用して、動的データマスキングと項目固有のデータ除外ポリシーを設定し、機密データを保護します。アクセスポリシーに従って、影響を受ける Data 360 オブジェクトへのアクセス権を付与する必要があります。

アクセスポリシーオプション

属性ベースのアクセス制御 (ABAC) またはロールベースのアクセス制御 (RBAC) のいずれかを選択できます。これにより、データへのユーザーアクセスをより詳細に制御できます。「データアクセスの割り当て」の手順に従って、これらのオブジェクトを使用可能なポリシーに割り当てます。

影響を受けるData 360オブジェクトのリストは、「生成AI監査およびフィードバックのデータ モデル」を参照してください。

複数のデータスペースがある場合、各データスペースのオブジェクトへのアクセス権を付与する必要があります。デフォルト以外のデータスペースのオブジェクト名は、<DataSpace Prefix>_<Object Name>の規則に従います。

アクセスポリシーのテスト

権限を更新したら、収集した監査およびフィードバックデータへのユーザーアクセスを必ずテストしてください。

ベータモデル

ベータモデルは、Salesforce がベータテストを行っているモデルプロバイダーの新しいモデルです。通常、ベータモデルはレート制限が低く、一部の地域では使用できないことがあります。ベータモデルの名前には (ベータ) が付加されます。ベータモデルが有効になっていない場合、AI モデルには (無効) と表示されます。

メモ この機能はパイロットサービスまたはベータサービスで、Salesforce.com の契約に関するページのベータサービス条件、またはお客様が署名された Unified Pilot Agreement、および製品規約ディレクトリの該当する条件が適用されます。このパイロットまたはベータサービスは、お客様独自の裁量で使用するものとします。

ベータ生成AIモデルを有効にする前に、Data 360を有効にする必要があります。Data 360は、Data CloudライセンスがSalesforce組織に追加されるとすぐに自動的にプロビジョニングされます。「Data 360 の有効化」を参照してください。

ベータ生成AIモデルを有効にするには、Einstein設定に移動します。ベータモデルを有効にすると、AI モデルでベータモデルを確認し、Salesforce で管理されるモデルと同じように使用できます。

Sandbox または開発組織でのみベータモデルを有効にすることをお勧めします。

大規模言語モデルのデータマスキング

Einstein Trust Layer は、プロンプトで機密情報を識別してマスキングしてから、Large Language Model(LLM; 大規模言語モデル)に送信します。Einstein Trust Layerは、データ マスキングを使用して、PII(個人識別情報)などの機密データが外部LLMに公開されないように保護します。

必要なエディション

使用可能なエディション: Einstein for Sales、Einstein for Platform、Einstein for Service、Einstein 1 Service、または Einstein GPT Service アドオンが付属する Enterprise Edition、Performance Edition、および Unlimited Edition。アドオンを購入するには、Salesforce アカウントエグゼクティブにお問い合わせください。

Einstein Trust Layer では、2 種類のデータ マスキングが提供されます。データ型は、データ型を識別するために使用される方法に基づきます。

  • パターンベース: Einstein Trust Layerは、高度なパターンマッチングと機械学習技術を使用して、プロンプト内の機密データを検出します。
  • 項目ベース: Einstein Trust Layer は、セキュリティ対策のために分類またはタグ付けされた Salesforce CRM 項目をメタデータを使用して識別します。

データマスキングでは、機密データが表す内容に基づいてプレースホルダーテキストに置き換えられます。

Einstein Trust Layer の ［設定］ で、マスキングするデータを選択できます。

重要
  • Einstein Trust Layer を介したデータ マスキングはエージェントで無効になっています。「Agentforce でのデータマスキングの制限」を参照
  • LLM データマスキングは、すべての機能で常に使用できるわけではありません。詳細は、機能に関するドキュメントを参照してください。
  • パターンベースのデータマスキング: 内部テストで検出モデルの有効性が確認されていますが、どのモデルも 100% の精度を保証することはできません。また、地域間および複数国の使用事例は、特定のデータパターンを検出する機能に影響する可能性があります。Trustを優先事項として、モデルの継続的な評価と調整に取り組んでいます。
  • 項目ベースのマスキングでは、レコードの差し込み項目と関連リストで参照される差し込み項目のみがサポートされます。

パターンベースのマスキング

データの種別に応じて、特定のテキストパターンとコンテキストまたは機械学習モデルを使用して機密データを識別します。パターンマッチングモデルと機械学習モデルのしくみを説明するのに役立つ例をいくつか紹介します。

  • 社会保障番号 (SSN): SSN は桁数と形式に基づいて識別されます。「SSN」や「Social」などの語句が近いと、社会保障番号として識別しやすくなります。
  • 名前: 個人または会社の名前は多様で、特定のパターンはありません。名前を認識し、個人または会社の名前として分類するようにトレーニングされた機械学習モデルを使用します。

パターンベースのマスキングでサポートされるデータ型の完全なリストについては、「Einstein Trust Layer Region and Language Support」を参照してください。

項目ベースのマスキング

Einstein Trust Layer の項目ベースのマスキングでは、Salesforce 項目のメタデータを使用して、プレースホルダーで機密データを識別し、マスキングします。この種別のマスキングは、コンプライアンスカテゴリや機密レベルを含む、Platform Shield Encryption やデータ分類などの既存のセキュリティコントロールに基づいて構築されます。

フィールドベースのマスキングは、プロンプトビルダーや他の AI 機能でプロンプトテンプレートを使用して適用されます。プロンプト テンプレートの差し込み項目に Platform Shield Encryption またはデータ分類タグが含まれている場合、Einstein Trust Layer は応答生成のために LLM に送信する前にこれらの項目の情報をマスキングします。

マスク解除

LLM が応答を返すと、Einstein Trust Layer は最初にマスクされたデータをマスク解除します。表示される応答には実際のデータが含まれます。

Einstein Trust Layer の ［設定］ で、マスキングするデータを選択できます。

プロンプトビルダーでデータのマスキングを実際に確認できます。Data 360 に保存されている監査履歴を使用して、データのマスキングを追跡し、マスキングされたデータを表示することもできます。

モデルの非推奨と再ルーティングの準備

このドキュメントでは、モデルの非推奨および再ルーティング時の Salesforce AI 実装の再テストに関する指針を示します。廃止と再ルーティングは一時的とみなされます。モデルが次のいずれかの状態になっている場合は、新しいモデルに切り替えることを検討してください。

用語集
非推奨 AI 開発のコンテキストでは、「非推奨」は使用が推奨されなくなったモデルを表します。通常、Open AI などのモデルプロバイダーは、新しい改善されたモデルが使用可能になると古いモデルを廃止します。非推奨は、別のモデルに移行するようにユーザーに指示する正式なプロセスです。非推奨フェーズの間、非推奨モデルは設計どおりに動作します。
再ルーティング モデルの再ルーティングは、古いモデルから使用可能な代替モデルに要求をリダイレクトするプロセスです。再ルーティングは、モデルプロバイダーがモデルを廃止または廃止したときに発生する可能性があります。Salesforce は、サービスの継続性を確保するために要求を再転送します。 

廃止および再ルーティング情報

モデルの非推奨と再ルーティングに関する通知は、Einstein Platform リリースノートで公開されています。[Large Language Model Support (大言語モデルのサポート)] ページには、非推奨モデルと再ルーティングされたモデルのリストも表示されます。

モデルプロバイダーがモデルを廃止した場合、サービスの継続性を確保するために、Salesforce はそのモデルファミリーの最新バージョンに要求を転送できます。たとえば、OpenAI GPT 3.5 Turbo 16k は OpenAI GPT 3.5 Turbo へのルーティングを要求します。

実装の成功の定義

  1. エンドユーザーの成功の程度を定義します。さまざまな使用事例で、一意のテスト方法が必要です。
  2. 初期実装フェーズのテスト結果を保存します。予想される回答の例がある場合は、それらを使用して結果と比較します。新しいモデルで同じテストを使用して、大きな変動がないことを確認します。

モデル変更時のガイダンス

  1. メモ モデルビルダーでモデル設定を確認します。「Create a Model Configuration」を参照してください。
    AIモデル(旧Einstein Studio)モデルPlaygroundでモデルを設定する場合、非推奨モデルと再ルーティングされたモデルを選択することはできません。 代わりに、新しい基盤モデルを選択して、設定を引き続き使用できます。 
  2. [AI モデル] で、再ルーティングされたモデルと一致する新しい設定済みモデルを作成します (該当する場合)。以前のモデルと同じハイパーパラメーターを使用して設定を定義します。
  3. 設定を保存したら、プロンプトビルダーを開きます。 
  4. 新しいモデルを使用してプロンプトテンプレートを再テストします。プロンプトビルダーでのプロンプトと応答のテストは、AIモデルのモデルPlaygroundで直接実行できます。プロンプトテンプレートを目標に合わせて調整します。
  5. 実装にエージェントが含まれている場合は、Agentforce Builder でエージェントを開きます。Agentforce Builder では、サブエージェント、アクション、Knowledge をテストしてエージェントを設定できます。エージェントの動作を調整して、事前に定義された成功の定義と一致させます。
  6. 設定したモデル、プロンプトテンプレート、エージェントを個別に設定したら、AI 実装全体をエンドツーエンドでテストします。改善のためにユーザーフィードバックを継続的に取得することが重要です。

インテントは、特定のユーザー要求に対応するセッション内の一連のインタラクションを表します。インテントを使用して、ユーザーが何を尋ねているかとエージェントがどのように応答しているかを理解します。インテントの生成またはクラスタリングで問題が発生した場合は、「Troubleshoot Agent Optimization (エージェント最適化のトラブルシューティング)」を参照してください。

インテント分析とクラスタリング

エージェント最適化では、インテント生成およびクラスタリングパイプラインを使用してセッションデータを分析します。インテントパイプラインは、セッションを分析してインテントを識別および生成します。クラスタリングパイプラインでは、共有ユーザーの目的別にインテントがグループ化され、セマンティックおよびサイズのしきい値を満たすインテントにクラスタータグが割り当てられます。

インテント パイプラインは、クローズされたセッションからインテントを取得します。次に、クラスタリングパイプラインで類似するユーザー目標を表すインテントがグループ化されるため、未加工のインテントごとだけでなく、タグレベルでパターンを分析できます。

最小クラスタ サイズ: パイプラインは、少なくとも 10 個のインテントが十分に類似している場合にのみクラスタを形成します。類似するインテントの小さなグループはクラスターにならず、クラスタータグを受け取りません。

クラスタ化されていないインテント: 10 件以上のセマンティック一致のクラスタに配置されていないインテントは、タグを取得しません。クラスター化では、ほぼ最後の月のデータからインテントが評価されます。ジョブは約 1 週間に 1 回実行されるため、特定の実行でインテントがタグ付けされていない場合、後続の実行 (通常はさらに 1 週間に数回のパス) で再度評価できます。それらのパス後も対象クラスターに参加しない場合、cluster タグなしで残ります。

セッション トレースおよびタグなしインテント: セッション トレースには、タグ付きインテント インスタンス (クラスタに参加したインスタンス) のみが表示されます。タグなしインテント インスタンスは、セッションにインテントがあってもセッション トレースに表示されません。セッショントレースにインテントがない場合は、タグなしインスタンスである可能性があります。「Troubleshoot Agent Optimization」を参照してください。

インテントクラスタートリガー

インテントパイプラインでインテントが生成されたら、システムは 12 時間待機してからクラスタリングパイプラインをトリガーします。この遅延により、有意義なクラスター分析を行うために、生成されたインテントを含む十分なセッションが蓄積されます。クラスターには、意味的に類似するインテントが少なくとも 10 個必要です。そのようなクラスターに参加しないインテントはタグを受け取りません。

トリガー条件 説明
最初の成功したインテントパイプラインの実行 インテントパイプラインの最初の実行を完了し、インテントを生成する

クラスタリングパイプラインでは、複数のセッションで共有ユーザーの目的別にインテントがグループ化されます。パイプライン期間は最大 24 時間かかります。生成されたインテントが含まれるセッションを数えることで、データが十分にあるかどうかが評価されます。全体的な会話量が少ない場合、クラスター化パイプラインを効果的に実行するための十分なデータがまだない可能性があります。これは、クラスターごとのルールが適用される前の制限要因になることがよくあります。

クラスタリングの実行内では、実質的に類似するインテントが 10 つ以上モデルが検出した場合にのみ、クラスタ (とそのタグ) が存在します。一致するインテントが 10 個未満のグループはクラスタを形成しません。これらのインテントは、その結果に対してタグが付けられず、セッション トレースに表示されません。インテントの合計数が多い場合、類似する意味を持つセットにグループ化されていないと、クラスターは保証されません。

通常、クラスタリングでは、約 1 か月前のデータからのインテントが考慮されます。クラスタリング ジョブは約週に 1 回実行されるため、1 回の実行でタグ付けされていないインテントは、次の週に数回の実行で再検討できます。インテントが合格しても対象クラスターに含まれない場合、クラスタータグを受け取りません。

スコアラーとカスタムスコアラー (ベータ)

スコアラー (ベータ) は、エージェントセッションを分析し、Agentforce Optimization および Analytics のスコア、ディメンション、基準を生成する Agentforce Studio の評価コンポーネントです。Salesforce 標準スコアを KPI のカスタム評価と組み合わせ、次世代テストを使用してカスタムスコアラーを作成し、セッションに適用して、最適化と Analytics の出力を使用してエージェントの改善に優先順位を付けます。

必要なエディション

使用可能なエディション: Einstein for Sales、Einstein for Platform、Einstein for Service、Einstein 1 Service、または Einstein GPT Service アドオンが付属する Enterprise Edition、Performance Edition、および Unlimited Edition。アドオンを購入するには、Salesforce アカウントエグゼクティブにお問い合わせください。
メモ Salesforce 標準データモデルバージョン 1.130 以上が必要です。
メモ

スコアラーはベータサービスであり、Agreements - Salesforce.com のベータサービス条件、またはお客様が実行した場合は書面による統合パイロット契約、および製品条件ディレクトリの適用条件が適用されます。このベータサービスは、お客様独自の裁量で使用するものとします。

最適化と分析でのスコアラーの表示場所

  • 次世代テスト — 新規または既存のテストスイートの一部としてカスタムスコアラーを作成し、調整して公開します。
  • スコアラー ハブ(Agentforce Studio) — スコアラーの表示、有効化、および管理を一元的に行います。
  • Sessions and Intents テーブル — セッションにはスコアラーの結果が表示されます。カスタムスコアラーディメンションで絞り込んで分析します。
  • セッションページ — セッションには、関連付けられたスコアラーの表示ラベルとスコアが表示されます。
  • Analytics ダッシュボード: カスタムスコアラー基準がレポートの総計値として表示されます。

考慮事項と制限

  • エージェント最適化および分析が有効になっている Salesforce Foundations Edition または Agentforce 1 Edition が付属する Enterprise Edition、Performance Edition、および Unlimited Edition の Lightning Experience で使用できます。
  • カスタム スコアラーはベータであり、Agentforce以外の追加ライセンスは必要ありません。
  • ベータ期間中は、セッションレベルのスコアラーのみがサポートされます。
  • カスタム スコアラーは、Agentforce Employee Agent(AEA)エージェント タイプではサポートされません。
  • SDR エージェント種別はスコアラーハブに表示されますが、最適化 UI エージェントドロップダウンには表示されません。
  • 標準スコアラー (A&D、品質スコア) は、STDM がプロビジョニングされたときに作成されます。欠落している場合は、プロビジョニングの問題を確認してください。
  • 標準スコアラーを編集する前にコピーする必要があります。ベータ期間中は直接編集はサポートされません。
  • 式ベースのスコアラーには Boolean 出力種別が必要です。
  • LLM は非常に狭い数値範囲ではパフォーマンスが低いため、0 ～ 1 スケールの数値スコアラーはお勧めしません。
  • テストセンターセッションはカスタムスコアラーでスコアリングされません。テストセンターセッションには終了タイムスタンプが付与されないため、カスタムスコアラー評価をトリガーするデータアクションが起動されることはありません。

概要

スコアラーはエージェントセッションを評価し、スコア、ディメンション (テキスト値)、基準 (数値) を生成します。これらは、Agentforce Optimization and Observabilityの一部です。これらは設定可能なセッションの割合に対して自動的に実行され、最適化と Analytics で結果が表示されるため、システム管理者と開発者はエージェントのパフォーマンスを継続的に改善できます。

スコアラーには次の 2 種類があります。

  • 標準スコアラーは Salesforce によって標準で提供されます。
  • カスタムスコアラーは、ビジネス固有の条件を評価するために組織で定義されます。

標準スコアラー

標準スコアラーは、STDM プロビジョニングで自動的に作成される事前作成済みの評価です。エージェントセッションで実行され、追加の顧客設定は必要ありません。

現在の標準スコアラー

  • Abandonment Score — エージェントが問題を解決する前に顧客がセッションを途中で終了したかどうかを示します。
  • デフレクションスコア — エージェントがインタラクションを人のエスカレーションが必要ないように回避したかどうかを示します。
  • 品質スコア — 定義済みのSalesforce条件に基づいてセッション全体の品質を測定します。

標準スコアラーは、ユーザーインターフェースで予約された場所を使用し、カスタムスコアラーリストとは異なります。

重要

標準のスコアラーを直接編集することはできません。コピーして、ロジックを変更した新しいカスタムバージョンを作成します。

カスタムスコアラー

カスタムスコアラーを使用すると、評価ロジックを定義してセッションに適用できます。LLM-as-a-Judge アプローチ (プロンプトベースの評価) または式ベースのロジックを使用して、条件に対するセッションの表示ラベル付け、スコアリング、分類を行います。

メモ

カスタムスコアラーは Agentforce Studio の Next Gen Testing(NGT; 次世代テスト)で作成します。「Agentforce Studio でのテストの設定および実行 (ベータ)」を参照してください。詳細は、「Next Gen Testing on Slack」を参照してください。

カスタムスコアラーはセッションに対して実行され、Observability にカスタムスコアとディメンションが表示されます。

カスタムスコアラーのしくみ

カスタムスコアラーは、セッションの終了時に一括処理ジョブとして自動的に実行されるプロンプトテンプレートによってサポートされています。スコアラーがセッションで実行されると、セッションはそのスコアラーに関連付けられ、表示ラベルとスコアが最適化と Analytics に表示されます。

  • スコアラーは、設定可能なセッションの割合 (サンプルレート) で実行されるプロンプトテンプレートです。
  • スコアは、ライブ会話中ではなく、セッション終了時に適用されます。スコアリングデータアクションを起動するには、セッションで終了タイムスタンプを受信する必要があります。
  • 結果は [Observability (可観測性)] にカスタム基準として表示されます。
  • executeAgentforceScoresJob 呼び出し可能アクションを使用してスコアラーを手動でトリガーすることもできます。
  • スコアリングはセッションの終了後に実行されるため、ライブ会話中のエージェントの遅延やパフォーマンスにスコアラーが影響することはありません。

エージェント最適化の設定

Agent Optimization を設定して、Agentforce セッショントレーシングデータに基づいてエージェントセッションを分析し、Knowledge ギャップを特定し、未解決のインタラクションを探索します。

必要なエディション

使用可能なエディション: Einstein for Sales、Einstein for Platform、Einstein for Service、Einstein 1 Service、または Einstein GPT Service アドオンが付属する Enterprise Edition、Performance Edition、および Unlimited Edition。アドオンを購入するには、Salesforce アカウントエグゼクティブにお問い合わせください。
メモ エージェント最適化は、Salesforce Foundations Edition または Agentforce 1 Edition が付属する Salesforce Enterprise Edition、Performance Edition、および Unlimited Edition で使用できます。エージェント最適化は、Sandbox、DC1、Civilian Government Cloud 組織で使用できます。
エージェント最適化へのアクセスと表示 「アクセスエージェントの最適化」および「Data Cloud ユーザー」権限セットの割り当て
メモ
  • 要件: Salesforce 標準データモデルバージョン 1.130 以上。
  • エージェント最適化では、Agentforce(デフォルト)、Agentforce従業員エージェント、およびAgentforceサービスエージェントがサポートされます。
  • エージェント最適化では、すべての言語でエージェントセッションがサポートされます。ただし、分析とインサイトは英語で表示されます。
  • エージェント最適化では、音声エージェントがサポートされます。

Einstein Trust Layerサービス サポート:機能では、データ マスキング、データの制限と請求、プライバシー(PIIマスキング(個人識別情報))がサポートされます。エージェントの最適化は、クレジット消費に影響します。エージェント最適化データの保存とクエリでは、Data 360 クレジットが消費されます。

重要 デフォルトの LLM モデル、連動関係、地理対応ルーティング
  • ほとんどの組織では、OpenAIがエージェント最適化セッション分析のデフォルトのモデル プロバイダーです。
  • Civilian Government Cloud組織では、その環境でのバッチ コールでOpenAIがサポートされていないため、Anthropicがデフォルトです。
  • エージェント最適化は、OpenAI(またはCivilian Government Cloud組織ではAnthropic)に大きく依存します。Agentforce のモデル プロバイダーのイネーブル化およびディセーブル化は正式リリースされています。[Manage Model Provider Access (モデルプロバイダーアクセスの管理)] では、組織全体でモデルプロバイダーをオンまたはオフにできますが、OpenAI (Civilian Government Cloud 組織では Anthropic) を無効にすると、エージェントの最適化が中断されます。エージェント最適化を使用する場合は、OpenAI(または Civilian Government Cloud 組織では Anthropic)を有効にしておきます。
  • 商業組織では、デフォルトの最適化動作をOpenAIからAnthropicに変更するには、Salesforceサポートを介した特別なリクエストが必要です。
  • セッション分析は、エージェントのモデルの選択に従いません。エージェント最適化が有効になっている場合、セッションデータは割り当てられたプロバイダーに送信されます。この処理を停止するには、Einstein Audit， Analytics， and Monitoring Setup で Agentforce Session Tracing and Data Model を無効にします。
  • エージェント最適化では、地理認識ルーティングはサポートされません。LLM 要求が組織の地域外で処理される可能性があります。

標準環境のエージェント最適化の設定

Salesforce 組織でエージェント最適化を有効にして、エージェントセッションの分析とパフォーマンスの最適化を開始します。

  1. エージェント最適化を有効にする前に、組織で Data Cloud がプロビジョニングされて有効になっており、有効なエージェントがいることを確認します。
  2. Einstein生成AI(「Set Up Einstein Generative AI」を参照)とAgentforce(「Enable Agentforce」を参照)が組織で有効になっていることを確認します。
  3. 組織 (Sandbox または本番) に最新バージョンの Salesforce 標準データモデル (バージョン 1.130 以上) があることを確認します。[設定] から、[アプリケーション] -> [パッケージ] -> [インストール済みパッケージ] -> [Salesforce 標準データモデル] に移動します。必要なバージョンを取得するには、ここをクリックして指示に従います。
  4. [設定] の [クイック検索] ボックスに「Einstein Audit, Analytics, and Monitoring Setup」と入力し、[Einstein Audit, Analytics, and Monitoring Setup] を選択します。
  5. Agentforce セッション トレーシングを有効にします。「Set Up Agentforce Session Tracing」を参照してください。
    エージェント最適化は、セッション追跡を有効にすると自動的に有効になります。詳細については、「Agentforce セッション トレーシング」を参照してください。
  6. [設定] で、[ユーザー] を見つけます。
  7. ユーザーに「Access Agent Optimization」権限セットを割り当てます。
  8. 作業内容を保存します。

DC1 環境のエージェント最適化の設定

DC1 (Data Cloud One) のサポートとは、複数の Salesforce 組織が 1 つの Data 360 インスタンスを共有する設定のことです。この設定により、1 つの「ホーム組織」と複数の「コンパニオン組織」または「LOB (基幹業務) 組織」で、組織全体の効率的なデータ管理とコラボレーションが可能になります。

コンパニオン組織イネーブルメント: コンパニオン組織のエージェント最適化を有効にするには、まずホーム組織で Einstein 設定を有効にする必要があります。その後、各組織でエージェント最適化を有効にするプロセスは同じままです。コンパニオン組織からエージェント最適化を有効にすると、Data Cloud アセットがホーム組織にプロビジョニングされ、コンパニオン組織と共有されます。

ホーム組織とコンパニオン組織は独立して運営され、各組織には独自のエージェントの分析のみが表示されます。

エージェント最適化が有効になっている組織ごとに異なるデータスペースを選択できます。

重要 DC1 環境では、エージェント最適化によって生成された LLM コールはすべての組織 (自宅組織とコンパニオン組織) で集計され、個々の組織で区切られません。
制限

同じ API 参照名の複数のエージェントが複数の組織に存在し、組織がデータスペースを共有している場合、エージェントは同じビューに集約され、1 人のエージェントとして表示されます。

この制限を回避するには、次のいずれかを実行します。

  • 組織全体でエージェントに異なる API 参照名を作成します。
  • 組織ごとに異なるデータスペースを選択します。
  • データガバナンスルールを作成して、参照権限を持つデータグループを制御します。
  1. Einstein生成AI(「Einstein生成AIの設定」を参照)とAgentforce(「Agentforceの有効化」を参照)がホーム組織で有効になっていることを確認します。
  2. コンパニオン組織に Salesforce Foundations または Agentforce 1 があり、有効なコンパニオン接続があることを確認します。
  3. Data Cloud One がホーム組織に表示されていることを確認します。
  4. コンパニオン組織で必要な権限セット(Access Agent OptimizationとData Cloud One User)をユーザーに割り当てます。

Sandbox 環境のエージェント最適化の設定

テストおよび開発目的で、Sandbox 環境でエージェント最適化を有効にします。Sandbox のサポートでは、コネクタを再接続してデータストリームを有効化するための特定の設定手順が必要です。

  1. Sandbox 組織で Data Cloud をプロビジョニングします。
  2. Sandbox 組織に Salesforce 標準データモデルパッケージをインストールまたはバージョン 1.130 以上にアップグレードします。インストールが完了したら、[設定] の [インストール済みパッケージ] ページでバージョンを確認します。
  3. コネクタを再接続します。
    メモ 接続は Sandbox に複製されますが、認証データは複製されません。その結果、すべてのコネクタが「有効化が必要」状態になります。

    [設定] から、[Data Cloud 設定]> [取り込み API]> [AgentOpt] に移動して、[有効化] をクリックします。

  4. Agentforce セッション トレーシングの再切り替え。セッショントレーシングを有効にすると、エージェント最適化が自動的に有効になります。
    すべてのデータストリームは自動的に有効化されます。

インテントの生成とパイプラインの実行に関する一般的な問題

インテントが生成されないか、クラスター化が発生していない場合は、各フェーズが正常に完了し、データの十分な要件を満たしていることを確認します。

トラブル 考えられる原因 解決策
生成しないインテント セッションがクローズされていないか、クローズ済みとみなされています。スケジューラーによってインテントパイプラインがトリガーされていません。 セッションが明示的に終了するまで待つか、3 時間の無操作タイムアウトに達します。
クラスター化が発生していない インテントが含まれるセッションが不十分である (通常は 50 セッション、データによって異なる)、または 12 時間の待機期間が経過していない。 インテントの生成が完了するまで他のセッションを待機します。最初に成功したインテントパイプラインの実行から 12 時間の待機期間を経過したことを確認します。
セッションにインテントがあるが、セッショントレースに表示されない セッショントレースには、タグがあるインテントのみが表示されます。クラスター化では、類似するインテントをグループ化するときにタグが追加されます (少なくとも 10 個)。インテントがグループ化されていない場合、タグがなく、表示されません。多くの場合、類似するインテントがまだ十分ないか、クラスタリングが (毎週) 実行されていないか、要求がまれであることが原因です。 これは、クラスタリングでタグが割り当てられるまでは正常です。類似するトラフィックが増えるか、次の週次実行まで待機します。
処理時間の延長 データ量またはシステムリソースの制約が大きい。 パイプラインの完了には最大 24 時間かかります。システムリソースとデータ量を監視します。
インテントの生成に予想以上の時間がかかる 使用可能なセッションデータが制限されています。 通常、5 ～ 7 セッションで十分なデータが提供されますが、セッションによって異なります。最初の試行が失敗した場合は、より多くのセッションを累積できるようにします。
STDM と MessagingSession のセッション数が一致しない セッションの定義はシステムによって異なります。STDM は各エージェントの呼び出しのセッションを記録しますが、MessagingSession は認証済みユーザーを返すための永続的なコンテキストを保持します。 アクションは不要です。この違いは予想されます。

AI に関する会社のビジョンの作成

AI ビジョンステートメントは、会社の努力の焦点を絞るのに役立つ全体的な目標を明確にします。このビジョンステートメントでは、営業の生産性向上やオープンケースの目標達成率の短縮など、幅広いビジネス成果を定義できます。

  • エグゼクティブリーダーシップ
  • ビジネス部門リーダー
  • IT、データサイエンス、ビジネスインテリジェンスなどの技術チーム
  • 法務とセキュリティ

関係者は、チームが目指す目標を特定し、新しいビジネスユニットと連携するように成功した AI プロジェクトを修正するなど、プロジェクトの成功に合わせて拡張する方法を革新するのに役立ちます。以前のプロジェクトの成功を積み上げるたびに、AI ソリューションを正常に実装する組織の能力と業務量が増加します。

ビジネスプロセスでの AI の使用事例の特定

日常業務を検証し、AI ソリューションを実装することでメリットを得られるビジネスプロセスを特定します。

AI ソリューションがビジネスプロセスの詳細なレビューに役立つ領域を特定します。営業生産性の向上という目標を持つことは有益ですが、その目標を達成するのに役立つソリューションを実装するには、関連するプロセスを吟味し、AI ソリューションを実装することで得られる生産性を推定する必要があります。この分析により、主要な関係者が AI への投資による付加価値を理解することができます。

  1. プロセスの手順を書き留めます。結果を達成するために必要なタスクの順序は?承認は必要か?
  2. プロセスに関与するユーザーを特定します。特定の個人が必須か省略可能か?関係者に基づいてステップを統合できるか?
  3. 関連するシステムとデータを特定します。個人は ToDo を完了するときに複数のシステムにアクセスする必要がありますか?システムが停止している場合、バックアップシステムは整っていますか?このタスクを完了するためにアクセスする必要があるデータソースは?外部データソースを Salesforce に取り込むことで、プロセスはメリットを得られますか?
  4. 各ステップに通常かかる時間を推定します。チームにとって最適な指標 (営業日、時間、分など) を使用します。より大まかな時間の見積から始めて、関係者とこれらの数値を確認して、より正確な見積を策定すると役立つ場合があります。
  5. 関連する AI ソリューションを確認します。まず、Salesforce AI使用事例ライブラリから開始することをお勧めします。そのまま使用できるソリューションは?一部のカスタマイズで機能するのはどれですか?構築するものと類似するものは?
  6. AI で改善できるステップを特定し、メリットを定量化します。
    1. これらのステップを確認し、ステップあたりの時間を節約できる時間を推定します。元の推定を行った同僚にチェックインして、これらの時間の推定を確認します。
    2. 時間の節約に基づいて、AI を使用してこのビジネスプロセスで節約された金額を計算します。コスト削減と生産性向上が会社の AI ビジョンと一致しているかどうかを判断します。

Einstein 生成 AI プラットフォームでの地理対応 LLM 要求ルーティング

Einstein生成AIプラットフォームは、大規模言語モデル(LLM)要求を、Einstein生成AIプラットフォーム インスタンスが配置されている場所に最も近いサーバーにルーティングします。地理認識ルーティングには、Einstein 生成 AI プラットフォームを使用する Einstein 生成 AI 機能によって実行される LLM API 要求が含まれます。

必要なエディション

使用可能なエディション: Einstein for Sales、Einstein for Platform、Einstein for Service、Einstein 1 Service、または Einstein GPT Service アドオンが付属する Enterprise Edition、Performance Edition、および Unlimited Edition。アドオンを購入するには、Salesforce アカウントエグゼクティブにお問い合わせください。

サポート対象モデル

モデルが関連する地域で使用可能な場合、地理認識ルーティングをこれらのモデルで使用できます。

  • OpenAI モデル (GPT-4 Omni など)。これらの地理対応モデルでは、OpenAI または Azure OpenAI を使用して LLM 要求に対応します。OpenAI と Azure OpenAI で同じ基礎モデルが使用されます。「OpenAI および Azure OpenAI の地理認識ルーティング」を参照してください。
  • 人類学モデル (Amazon Bedrock でホスト)

使用可能なライセンス

地理認識ルーティングは、次の目的で使用できます。

  • AI エージェント
  • Einstein生成AIプラットフォームを介したOpenAIおよびAnthropicモデルを使用するSalesforceアプリケーションおよび機能
  • モデルAPIまたはプロンプトビルダーを使用してOpenAIおよびAnthropicモデルを使用しているお客様。

特定の Salesforce AI 機能で地理対応ルーティングが有効になっているかどうかを確認するには、そのドキュメントを参照するか、Salesforce アカウントエグゼクティブにお問い合わせください。

近接性とルーティング

最も近い LLM サーバへの近接性は、Einstein 生成 AI プラットフォーム インスタンスが配置されているリージョンによって決まります。2024年6月13日以降にEinstein生成AIプラットフォームを有効にした場合、Einstein生成AIプラットフォームのリージョンはData 360のリージョン(Data 360: Data Center Locations)と同じです。それ以外の場合は、Salesforce アカウントエグゼクティブに連絡してプロビジョニング場所を確認してください。

モデル API でのルーティング

Einstein生成AIプラットフォームをモデルAPIを介して直接使用する場合、地理対応モデルにはモデルのAPI名を使用することをお勧めします。

フィードバックと監査

LLM 要求の転送先を確認するには、「フィードバックおよび監査機能」を参照してください。

機能固有のサポート

Einstein 機能で地理対応 LLM 要求ルーティングがサポートされているかどうかを追跡するには、機能のマニュアルを参照してください。

  • OpenAI および Azure OpenAI の地理対応ルーティング
    GPT 4 Omni などの地理対応モデルでは、OpenAI または Azure OpenAI を使用して LLM 要求に対応します。OpenAI と Azure OpenAI で同じ基礎モデルが使用されます。
  • Anthropic の地理認識ルーティング
    Anthropic on AWS Bedrock の LLM 要求は、モデルエンドポイントを使用できる最も近い AWS データセンターに転送されます。
