Anthropic の地理認識ルーティング

Anthropic on AWS Bedrock の LLM 要求は、モデルエンドポイントを使用できる最も近い AWS データセンターに転送されます。

必要なエディション

使用可能なエディション: Einstein for Sales、Einstein for Platform、Einstein for Service、Einstein 1 Service、または Einstein GPT Service アドオンが付属する Enterprise Edition、Performance Edition、および Unlimited Edition。アドオンを購入するには、Salesforce アカウントエグゼクティブにお問い合わせください。

推測プロファイル

一部のモデルは、特定の AWS リージョンではクロスリージョン推測プロファイルとしてのみアクセスできます。クロスリージョン推測要求は、要求が発信された場所の一部である AWS リージョン内に保持されます。たとえば、クロード・ソネット 4 に対する米国内の要求は、米国の AWS リージョン内に保持されます。日本で行われた要求は、apac.anthropic.claude-sonnet-4-20250514-v1:0 推測プロファイルの任意の宛先から処理できます。

詳細は、Amazon Bedrock ドキュメントを参照してください。

OpenAI および Azure OpenAI の地理対応ルーティング

GPT 4 Omni などの地理対応モデルでは、OpenAI または Azure OpenAI を使用して LLM 要求に対応します。OpenAI と Azure OpenAI で同じ基礎モデルが使用されます。

必要なエディション

使用可能なエディション: Einstein for Sales、Einstein for Platform、Einstein for Service、Einstein 1 Service、または Einstein GPT Service アドオンが付属する Enterprise Edition、Performance Edition、および Unlimited Edition。アドオンを購入するには、Salesforce アカウントエグゼクティブにお問い合わせください。

米国での要求は、米国では OpenAI、場合によっては Azure OpenAI によって処理されます。米国以外の要求は、Einstein生成AIプラットフォーム インスタンスが配置されている場所に最も近いサポート対象Azure OpenAIエンドポイントに転送されます。

米国へのフォールバックの無効化

米国への最終フォールバックを無効にする前に、Data 360 を有効にする必要があります。Data 360は、Data CloudライセンスがSalesforce組織に追加されるとすぐに自動的にプロビジョニングされます。「Data 360 の有効化」を参照してください。

米国への最終フォールバックを無効にするには、Einstein の [設定] に移動して、[モデルプロバイダーリージョンフォールバックを無効化] を切り替えます。米国にフォールバックする代わりに、エラーが返されます。エラーが返される前に、要求は引き続きプライマリモデルエンドポイントとセカンダリモデルエンドポイントで試行されます。

一括処理

プロンプトテンプレートの大量の応答を非同期で生成するには、プロンプトテンプレートの一括処理を使用します。これらのモデルでは、Azure OpenAI によるネイティブバッチ処理のグローバルエンドポイントがサポートされています。

  • GPT 4 Omni
  • GPT 4 Omni Mini
  • GPT 4.1

グローバルエンドポイントを使用するこれらのモデルでは、バッチ以外の LLM 要求が特定のリージョン内 Azure エンドポイントに制限されていても、組織のリージョン外のリージョンでバッチ要求が処理される可能性があります。一括処理は地理対応ルーティングルールに従わず、地域での適用は行われません。

バッチ処理の詳細については、『 Agentforce Developer Guide 』の「 Prompt Template Batch Processing in Apex 」を参照してください。

エージェントプラットフォーム追跡

このトレース機能により、Agentforce Agent のアクションとパフォーマンスを包括的に把握し、さまざまなサービスの重要なテレメトリ・データを取得できます。Data 360 を活用することで、ユーザーはこのトレースデータをセッション情報と統合して、詳細なレポートを作成できます。これらのレポートは、重要業績評価指標 (KPI) の監視、パフォーマンスのボトルネックの特定、問題の原因の迅速な特定を行い、最終的にエージェント実装の信頼性と効率を向上させるために不可欠です。

必要なエディション

メモ エージェントプラットフォームトレーシングでは、Government Cloud はサポートされていません。
使用可能なインターフェース: Lightning Experience
使用可能なエディション: Foundations が付属する Enterprise Edition、Performance Edition、Unlimited Edition、および Developer Edition、または Agentforce 1 Edition または Einstein 1 Edition

エージェントプラットフォーム追跡の設定

セッションおよびプラットフォームトレースの Data 360 レポートを生成するには、ユーザーが最初に Data 360 とプラットフォームトレースを有効にする必要があります。

  1. [設定] で、[クイック検索] ボックスを使用して Einstein 生成 AI を検索します。
  2. Einstein生成AIで、[Einstein Audit, Analytics, and Monitoring Setup]をクリックします。
  3. Agentforce セッショントレーシングが有効になっていることを確認します。「Set Up Agentforce Session Tracing」を参照してください。
  4. [エージェントプラットフォーム追跡] 切り替えまでスクロールしてオンにします。

データモデルはわずか数分でプロビジョニングされます。その後、データ収集はすぐに開始され、5 分間隔で繰り返されます。データ収集を切り替えると、組織のクレジット消費率が増えます。

データ収集を一時停止すると、後で再開できるようにデータが保持されます。レポートには、無効にしてから再度有効にするまでのギャップが表示されます。

サービス担当者セッションとプラットフォーム追跡の Data 360 レポート

KPI とトレンドに関するインサイトを取得するには、エージェントセッショントレースとエンドツーエンドプラットフォームトレースの両方を統合する 1 つの Data 360 レポートを作成します。このレポートは、ほぼリアルタイムのデータに対して実行でき、レコードのグループ化、絞り込み、集計を行い、他のユーザーと共有できます。

エージェントトレーシングには、次のサービスからのスパンが含まれます。

  • Apex
  • フロー
  • プロンプトビルダー
  • 呼び出し可能なアクション
  • プランナー
  • AI ゲートウェイ
  • LLM ゲートウェイ
  • DC クエリ統合

Data 360 レポートの生成

テレメトリトレーススパンや AI エージェントインタラクションなど、特定のデータモデルオブジェクト (DMO) に関するレポートを作成して、統合データを分析および学習します。

  1. Salesforce の [レポート] タブに移動し、[新規レポート] をクリックします。[レポートタイプ] ページが表示されます。
  2. 検索バーに、レポートを作成するデータモデルオブジェクト (DMO) の名前を入力します。この場合、[テレメトリー追跡範囲] または [AI エージェントインタラクション] を選択します。
  3. 関連するデータモデルオブジェクト内に新しい項目リレーションを作成します。この場合、[Telemetry Trace Span - Telemetry Trace (テレメトリートレース範囲 - テレメトリートレース)] → [ManyToOne] → [AI Agent Interaction - Telemetry Trace (AI エージェントインタラクション - テレメトリートレース)] を選択できます。

    Data 360 では、キー項目を使用して「ソース DMO」から「対象 DMO」への接続を定義することで、DMO 間のリレーションが確立されます。最も頻繁なリレーションの種別は多対一で、ソース DMO の複数のレコードが対象 DMO の 1 つのレコードに対応します。詳細は、「データモデルオブジェクトリレーション」を参照してください。

  4. DMO の詳細ページには、[リレーション] タブがあります。このタブには、この DMO に存在するすべてのリレーションが視覚的に構造化されています。[リレーション] タブで新しい DMO リレーションを確認します。

    テレメトリトレース範囲の例

    AI エージェントのインタラクションの例

  5. カスタムレポートタイプを作成します。
  6. [設定] の [新規カスタムレポート] で [新規カスタムレポート] をクリックします。項目を入力して、新しいカスタムレポートタイプを作成します。この場合は、Session & Platform Traces レポートタイプを作成します。
  7. Data Cloud アプリケーションに移動し、[レポート] タブを選択します。
  8. Data 360 レポートを作成します。[新規レポート] をクリックし、目的のレポートタイプ ([Session Traces (セッショントレース)] と [Platform Traces (プラットフォームトレース)]) を選択します。
  9. [Start Report (レポートを開始)] をクリックします。

レポートを開始すると、各エージェントセッションの一部として記録された相関プラットフォームテレメトリ追跡期間を視覚化できます。

メモ Data 360 レポートでは、実行モードで最大 2,000 行が表示されます。最大 50,000 行をエクスポートできます。詳細は、「Data 360 のレポートとダッシュボード」および「Data Cloud のレポートとダッシュボード: 制限」を参照してください。

Einstein Data Prism

Einstein Data Prism は、Salesforce 内の生成 AI アプリケーションのグラウンディングソリューションであり、グラウンディング機能を使用する AI ソリューションの精度を向上させます。Einstein Data Prism を使用して、大規模言語モデル (LLM) を自動的にグラウンディングし、発言に対するより正確で関連性の高い応答を得られるようにします。Einstein Data Prism は、Einstein セグメント作成や Agentforce などの統合アプリケーションで自動的に有効になります。

必要なエディション

メモ Prism と Metadata Studio は Government Cloud Plus ではサポートされていません。Government Cloud Plus 組織ではこの機能を有効にしないでください。詳細は、Salesforce アカウントエグゼクティブにお問い合わせください。

Data Prism 製品の一部として、Metadata Studio アプリケーションを使用することもできます。Metadata Studio では、ユーザーが最新情報を常に確認できます。これにより、ユーザーはAIで生成されたメタデータ記述を検証し、ビジネスKnowledgeを提供することで、生成AIで生成された結果を改善できます。

構造化データのスマートグラウンディング

スマートグラウンディングにより、大規模言語モデル (LLM) にビジネスコンテキストが提供され、正確かつ最新のメタデータに基づいて関連する応答が作成されるため、ユーザーのインテントやコンテキストに合わせて出力が微調整されます。Data Prism は、自然言語の質問に関連する正確なデータエンティティを特定することで、結果の精度を高め、大規模な組織でカバー率を高めます。Data Prismを使用すると、Einsteinセグメント作成などの生成AIアプリケーションは、元のスキーマからグラウンディングされたデータセットを受信して、正確なデータが返されます。

Einstein Data Prismのしくみ

Data Prism が組織にプロビジョニングされると、すべてのメタデータ (スキーマ、リレーション、サンプル値、説明) がスキャンされます。欠落している説明はすべて自動的に生成され、ベクトルデータベースに保存されます。実行時にユーザーが Salesforce アプリケーションで自然言語の質問を行うと、生成 AI アプリケーションが Data Prism API をコールし、要求された自然言語の発言を送信します。Data Prism は、自然言語の発言に一致するテーブルと項目をフォーカスされたグラウンディングデータとしてアプリケーションに返します。そのため、アプリケーションではこのフォーカスされたグラウンディングデータを使用して、大規模言語モデル (LLM) からより正確な結果を得ることができます。

メモ プロビジョニングプロセスには最大 24 時間かかります。

Data Prism の結果を改善するには、メタデータスタジオを使用して LLM で生成された説明を強化します。生成された説明は、どのような場合でも使用されますが、結果が正確であることを確認するために検証および強化することを強くお勧めします。

取得拡張生成について

Data 360のRAG(取得拡張生成)がKnowledgeでAgentforceおよびEinstein生成AIソリューションを強化する方法について説明します。

RAG アクション

大規模言語モデル (LLM) プロンプトを送信すると、Data 360 で RAG を実行します。

  • 構造化コンテンツと非構造化コンテンツを含むKnowledgeから関連情報を取得する
  • この情報を元のプロンプトと組み合わせることで、プロンプトを増強します。
  • プロンプト応答を生成する

RAG In Data 360 の概要

RAG は、オフラインでの準備とオンラインでの使用の 2 つの主要な部分に分けて考えることをお勧めします。

オフライン準備のクイックスタート

RAGソリューションを最も迅速に設定するには、Agentforce Builderまたは[設定]でデータライブラリを作成します。Agentforce データライブラリを作成すると、正常に機能する RAG 機能を備えたソリューションに必要なすべての要素が自動的に作成されます。Salesforce では、ベクトルデータストア、検索インデックス、レトリーバー、プロンプトテンプレート、標準アクションのすべてのコンポーネントにデフォルト設定を使用します。必要に応じて、これらの要素をカスタマイズして、使用事例に合わせて RAG ソリューションを微調整できます。

オフライン準備の高度な設定

Data 360 に RAG を実装するには、まず RAG で使用する構造化データと非構造化データをグラウンディング LLM プロンプトに接続します。Data 360では、検索インデックスを使用して、構造化コンテンツと非構造化コンテンツを検索に最適化された方法で管理します。コンテンツは、さまざまなソースやファイル形式から取り込むことができます。RAGで使用される非構造化コンテンツの例として、サービス返信、ケース、RFP応答、Knowledge記事、FAQ、Eメール、ミーティングメモなどがあります。

オフライン準備の手順は次のとおりです。

  1. 非構造化データを接続します。
  2. コンテンツをチャンク化してベクトル化する検索インデックス設定を作成します。

    チャンクでは、元のコンテンツ (文章や段落など) の文章を反映して、テキストを小さな単位に分割します。ベクトル化では、チャンクがテキストの数値表現に変換され、セマンティックの類似性が取得されます。

  3. Data 360 で検索インデックスを保存および管理します。

詳細は、「Search for AI, Automation, and Analytics」を参照してください。

取得者は、検索インデックスとプロンプトテンプレート間のブリッジとして機能します。取得者は検索条件をさらに絞り込み、プロンプトの増強に使用される最も関連性の高い情報を取得します。さまざまな使用事例をサポートするために、AIモデル(旧称Einstein Studio)でカスタム リトリーバーを作成します。詳細は、「データの取得」を参照してください。

オンライン利用状況

RAG 実装のパズルの最後のピースは、プロンプトテンプレートで通話を取得者に追加することです。プロンプトデザイナーは、特定のプロンプトテンプレートで、取得クエリと結果の設定をカスタマイズして、プロンプトに最も関連性の高い情報を入力できます。詳細は、「Ground with Knowledge Using Retrieval Augmented Generation (取得拡張生成を使用したナレッジの活用)」を参照してください。

取得元を含むプロンプトテンプレートが実行されるたびに、次の順序になります。

  1. プロンプトテンプレートは、動的クエリを使用して取得者を呼び出します。
  2. クエリはベクトル化されます (数値表現に変換されます)。ベクトル化により、検索インデックスでセマンティック一致を検索できます (すでにベクトル化されています)。
  3. クエリは、検索インデックスのインデックス付けされたデータから関連するコンテキストを取得します。
  4. 元のプロンプトには、検索インデックスから取得した情報が入力されます。
  5. プロンプトが LLM に送信され、LLM がプロンプト応答を生成して返します。

多くの LLM は、静的なコンテンツと公開されているコンテンツについてインターネット全体で一般的にトレーニングを受けていました。RAGは、正確で最新であり、LLMのトレーニング済みKnowledgeの一部として使用できない情報をプロンプトに追加します。これは、最新かつ最適なバージョンの事実が含まれるKnowledge Storeから取得した関連情報を提供することでLLMの機能を補完するようなものです。RAG を使用すると、プロンプトテンプレートユーザーはモデルを再トレーニングして微調整することなく独自のデータを LLM に取り込むことができるため、各自のコンテキストや使用事例により関連性の高い応答が生成されます。

例: Advanced Data 360 を使用したエージェント型 RAG の設定

この例では、Data 360のRAG(Retrieval Augmented Generation)を使用してKnowledgeを基盤とするエージェントを実装するエンドツーエンドの手順を説明します。

必要なエディション

使用可能なエディション: Einstein for Sales、Einstein for Platform、Einstein for Service、Einstein 1 Service、または Einstein GPT Service アドオンが付属する Enterprise Edition、Performance Edition、および Unlimited Edition。アドオンを購入するには、Salesforce アカウントエグゼクティブにお問い合わせください。

Data 360、AIモデル(旧Einstein Studio)、Agentforceに関する予備知識は必要ありません。このシナリオは、Advanced RAG with Data 360とAgentforce Trailheadバッジを受講して、プレイグラウンド組織に実践的に実装してください。概要については、「About Retrieval Augmented Generation and Retrieval Augmented Generation: Quick Look in Trailhead (拡張生成の取得と Trailhead のクイックルックについて)」を参照してください。

RAG を駆使したエージェントを作成するためのアプローチ

RAG 機能を備えたエージェントを設定するには、主に 2 つの方法があります。

  • クイックスタート。このアプローチの利点は、エージェントが使用できるソリューションを導入し、内部的にすべてのコンポーネントを設定する必要がないことです。クイックスタートの方法は、Agentforce データライブラリを使用してデータライブラリを作成することです。データ ライブラリを作成するときは、検索するデータ ソース (HTML、PDF、Knowledge オブジェクト、アップロードされたファイル、Web 検索、またはカスタム取得) を選択して、エージェントに割り当てます。Agentforceデータライブラリは、基盤となるすべてのRAGソリューションコンポーネントを自動的に生成します。詳細については、Salesforce ヘルプの「Agentforce Data Library」および Trailhead の「Agentforce Data Library Basics」を参照してください。
  • 上級者向け。このアプローチの利点は、ビルダーツールを直接操作し、特定の使用事例に合わせて RAG ソリューションをカスタマイズするために使用できるすべての設定とオプションを利用できることです。

この例では、高度なアプローチについて説明します。各コンポーネントを個別に設定することで、その設定オプションと RAG ソリューションスタックへの適合方法をエンドツーエンドで直感的に理解できます。Salesforce 開発者組織の指示に従ってください。結果は異なる場合があります。

この例のシナリオ

RAG は、構造化データのドキュメント、Web サイト、自由形式のテキスト項目など、非構造化データから関連情報を抽出することを得意としています。このシナリオでは、Salesforce ケースオブジェクトに追加する自由形式のテキスト (件名と説明) を使用します。エージェントはこの情報を使用して、商品の問題に関する質問をユーザーに通知できます。その他のデータソース オプションについては、Salesforce ヘルプおよび Trailhead を参照してください。

エージェントが最近更新された情報で応答していない。

最近更新された最新情報ではなく、古い情報が表示されます。

  • 大規模なKnowledge Storeの場合、検索インデックスの作成に数時間かかることがあります。検索インデックスのジョブ ステータスとステータス状態を確認します（「 検索インデックス ステータスとプロセス履歴の表示 」を参照）。インデックス付けジョブの進行状況と完了結果 (成功または失敗) を積極的に監視します。コンテンツタイプまたはドメインで区切られた複数の検索インデックスを使用します。
  • ハイブリッド検索インデックスの場合、ランキング要素として [RECENCY] を選択し、データモデルオブジェクト (DMO) の LastModifiedDate 項目を選択します。「高度な設定を使用したハイブリッド検索インデックスの作成」を参照してください。
  • Salesforce で Knowledge Article の状況を確認します。アーカイブ済み記事には引き続きインデックスが付けられるため、情報が矛盾したり、重複したり、古くなったりする可能性があります。取得元に事前条件を追加して、有効な記事のみが返されるようにします。
  • インデックス付けログにエラーがないか確認します。データストリームが停止した場合は、インデックスを再構築します。

文書にインデックスがまったく付けられていない。

ドキュメントが検索インデックスに表示されません。

  • インデックスから欠落しているドキュメントを調査します。Salesforce オブジェクトの添付ファイルが取り込まれるように設定されているかどうか (ContentDocument がデータソースに含まれているかどうか) を確認します。データソースの設定と権限を確認し、設定の問題に対処します。
  • ドキュメントファイル形式を確認します。サポートされていない場合は、ドキュメントをサポートされているファイル形式に変換します。Data 360 の非構造化データのファイル制限を参照してください。
  • Salesforce オブジェクト権限を確認し、必要に応じて権限を変更します。エージェントユーザーが必要なオブジェクトとKnowledgeにアクセスできることを確認します。データカテゴリ検索条件を確認し、必要に応じて検索条件を調整します。
  • すべての DMO レコードにインデックスが付けられているかどうか、または検索インデックスの増分更新が失敗したかどうかを判断します。次の例のようなクエリを使用して、レコード件数の結果を比較します。 
    SELECT 'INDEX' AS Location, COUNT(DISTINCT rc.SourceRecordId__c) AS ArticleCount, now() AS Timestamp 
FROM
<chunk DMO of the Search Index> rc
UNION
SELECT 'DMO' AS Location, COUNT(DISTINCT  kav.Id__c)  AS ArticleCount, now() AS Timestamp 
FROM <DMO that was indexed, e.g. Knowledge Article Version> kav
ORDER BY Location;

テーブルデータが正しく抽出されていない。

抽出されたデータにエラーがあります。

  • 水平検出エラーと垂直検出エラーを回避するには、Doclingパーサーを使用したコンテンツの処理と抽出に切り替えます(ブログ「Turn Hidden Data into AI-Ready Insights: How the Docling Parser Harvests Value from Unstructured Information」(隠しデータをAI対応インサイトに: ドクロッシングパーサーが構造化されていない情報から値を取得する方法)を参照)。その他の解析オプションについては、「LLM ベースの解析と前処理」を参照してください。
  • チャンクを調べて、テーブル情報が無傷であるか、複数のチャンクに分散しているかを判断します。後者の場合は、チャンクサイズを増やすか、セクション対応チャンク戦略を実装します。

マルチ言語クエリは機能しません。

異なる言語で送信されたユーザークエリに対するエージェントの応答が低い。たとえば、Knowledge Store にスペイン語のコンテンツが含まれており、ユーザーのクエリがフランス語と英語であるとします。

  • 英語以外の言語を使用するRAGソリューションの場合、マルチ言語e5大規模埋め込みモデルを使用していることを確認します。この埋め込みモデルでは、言語間のセマンティック類似性が保持されます。フランス語のクエリでは、スペイン語で記述された関連記事を取得できます。最適な結果を得るには、Knowledge Storeのコンテンツに単一の言語を使用することを検討してください。
  • キーワード検索は、マルチ言語ソリューションでは効果が低くなります。キーワードがソースコンテンツとは異なる言語である場合、ベクトル検索のパフォーマンスがハイブリッド検索よりも優れているかどうかをテストします。検索戦略ごとに、AIモデルのRetriever Playgroundと個々の取得者を使用して、同じクエリへの応答をスコアリングし、比較します。
  • ユーザーは、ユーザーのクエリと同じ言語で応答することを想定しています。設定は応答に影響する可能性があります。たとえば、プロンプトテンプレートの手順では、特定の言語で応答を生成するように LLM に指定できます。マルチ言語ソリューションで結果を改善するには、エージェント、プロンプト テンプレート、Einstein Trust Layer でサポートされる言語と設定された言語を確認します。
  • LLM と LLM バージョンは、マルチ言語サポートで異なる場合があります。パフォーマンスが優れているものもあります。最良の結果を得るには、異なる LLM と LLM バージョンでプロンプトをテストします。

その他の考慮事項

  • RAG 機能を備えたソリューションをデバッグするには、拡張イベントログを有効にして会話の詳細を表示します。
  • RAG機能を備えたソリューションを本番にリリースする前に、AIモデルでRetriever Playgroundを使用して、重要なRAGの質問に回答します。適切なドキュメントが存在するか?最も関連性の高いチャンクが表示されましたか?ノーコードの個々の取得機能を使用して、回答の品質をテストおよび改善します。取得者の設定を調整し、中間出力を調べ、取得結果の品質をスコアリングし、取得の精度と関連性を高めるために調整します。
  • Knowledge/RAG品質データおよび評価指標を使用して、取得品質の問題とパターンを調査します。総計値は、回答の精度と関連性を最も高めることができる領域に焦点を絞る取り組みの指針となります。Context Precision スコアには取得の品質が反映されます。[忠実度] スコアと [回答の関連性] スコアには、生成された回答の正確性と関連性がそれぞれ反映されます。「About Knowledge/RAG Quality Data and Metrics」を参照してください。
  • ベクトル検索を使用している場合は、ハイブリッド検索を試して取得結果を比較します。検索戦略ごとに、コードなしのAIモデルでRetriever Playgroundを使用し、個々の取得者が同じクエリへの応答をスコアリングして比較します。
  • 検索条件では、最も関連性の高い情報に検索を絞り込むことができますが、関連するコンテンツを検索から除外することもできます。プロンプトテンプレートの事前検索条件設定と取得者の検索条件設定が、適切な量のコンテンツを取得するように最適化されていることを確認します。
  • 検索インデックスのチャンク設定を調整して、取得品質を最適化します。ヘルプの「チャンク戦略」、「Optimizing Search Indexes: Field Selection and Chunking (検索インデックスの最適化: 項目の選択とチャンク)」、および「Data 360 のコンテンツチャンクの強化されたインデックス付け」を参照してください。

ソリューションレイヤーのトラブルシューティング

RAGソリューションを調査するもう1つの方法は、ソリューションスタックの異なるレイヤーで検索結果と取得結果を確認することです。

ステップ 1: エージェントレイヤーの調査

エージェントレイヤーで問題を修正する場合、RAG コンポーネントのトラブルシューティングは不要です。Agentforce Builder または Agentforce テストセンターを使用して、推論プロセスを調査および診断します。

たとえば、Atlas 推論エンジンが適切なサブエージェント内で適切なアクションを実行しているかどうかを判断します。適切なサブエージェントが選択されていない場合、または適切なサブエージェントが選択されているが適切なアクションが実行されていない場合、問題はおそらくエージェントによる指示と分類の説明の設定で発生します。必要に応じて、サブエージェント手順とアクション手順を調査して対処します。

その他のエージェント関連の問題については、「エージェントのトラブルシューティング」を参照してください。

ステップ 2: データライブラリの調査

RAG機能を備えたソリューションにAgentforceデータ ライブラリが含まれている場合は、権限を確認し、データ ライブラリのステータスを確認します。「Agentforce Data Library Troubleshooting」を参照してください。

ステップ 3: 検索インデックスおよび取得レイヤーの調査

検索インデックスに期待するコンテンツが含まれているかどうかを確認します。

  • AIモデルのRetriever Playgroundをノーコードの個々の取得者と共に使用して、取得者をテストし、返されたチャンクを調査します。症状とパターンを特定し、それに応じて改善します。
  • プロンプトビルダーで、取得機能が組み込まれたプロンプトテンプレートを使用して、さまざまなプロンプトを試します。プレビューモードを使用して、取得者が返す内容を確認します。エラー、欠落、その他の異常のパターンを探します。
  • Data 360 クエリエディターで、インデックス DMO に対してクエリを実行します。必ず LIMIT 10 または同様のステートメントを使用してください。たとえば、このトピックの後半の「Data 360 クエリエディターを使用したチャンクのデバッグ」を参照してください。

ステップ 4: 生成レイヤーの調査

LLM がグラウンディング済みプロンプトのチャンクをどのように取得して回答を生成するかを調べます。

  • プロンプトビルダーで、プロンプトで取得されたチャンクと LLM の応答を比較します。回答に誤り、欠落、幻覚が見られるものは?引用を使用して、LLM が応答の生成に使用したソースを特定します。重要な取得済みチャンクのランク付けが低すぎますか?LLM プロンプトの指示を調整することを検討してください。
  • この記事の前半の「エージェントがKnowledge Storeに存在する情報を返していない」の推奨事項を参照してください。

Data 360 クエリエディターを使用したチャンクのデバッグ

クエリエディタを使用して、検索インデックス内のチャンクを直接検査およびトラブルシューティングします。

ソースレコードによるチャンクの検索

特定のソース(URLやKnowledge Articleなど)から作成されたすべてのチャンクを確認します。

    InternalOrganization__c, KQ_RecordId__c, KQ_SourceRecordId__c, 
    RecordId__c, SourceRecordId__c 
FROM <Your_Chunk_DMO>__dlm 
WHERE SourceRecordId__c = '<source_record_id>'

ベクトル検索クエリのテスト

特定のクエリで取得されたチャンクを確認します。

SELECT v.score__c AS Score, c.Chunk__c AS Chunk, 
        c.SourceRecordId__c AS SourceRecordId
FROM vector_search(
  TABLE(<Your_Index>__dlm), 
     'your search query here', 
     '', 
     10
     ) v 
INNER JOIN <Your_Chunk_DMO>__dlm c 
   ON c.RecordId__c = v.RecordId__c
   ORDER BY Score DESC 
LIMIT 10

ハイブリッド検索のテスト (ベクトル + キーワード) 


SELECT c.Chunk__c, h.hybrid_score__c, h.keyword_score__c, h.vector_score__c
FROM hybrid_search(
  TABLE(<Your_Index>__dlm),
      'your query here',
      '',
      100
      ) h
JOIN <Your_Chunk_DMO>__dlm c 
   ON h.SourceRecordId__c = c.RecordId__c
ORDER BY h.hybrid_score__c DESC            
LIMIT 10

デバッグチャンクの作成

チャンクが特定のコンテンツ用に作成されたかどうかを確認します。

SELECT COUNT(*), SourceRecordId__c
FROM <Your_Chunk_DMO>__dlm
GROUP BY SourceRecordId__c

重複するチャンクの検索 

SELECT COUNT(RecordId__c) AS duplicates, SourceRecordId__c, Chunk__c  
FROM <Your_Chunk_DMO>__dlm  
GROUP BY SourceRecordId__c, Chunk__c  HAVING COUNT(RecordId__c) > 1

Agentforce セッション トレーシングのデータ モデルは、エージェントの動作の詳細なセッション トレーシング ログが含まれる DLO(データ レイク オブジェクト)と DMO(データ モデル オブジェクト)のコレクションです。データモデルには、フィードバックデータまたはガードレール総計値との結合をサポートするために推論エンジンによって行われるすべての LLM コールへの参照も含まれます。データストリームは、データを Data 360 の DLO に転送します。 DMO は DLO にマッピングされます。

例: フラットリストでのセッションの関連レコードの取得

1 つのエージェントセッションには、関連オブジェクトの多くのレコードが含まれます。このクエリを使用して、セッションのすべてのレコードをタイムスタンプで並び替えたフラット化されたリストで表示します。<your sessionID> を sessionID に置き換えます。

WITH
            -- Keep session ID in temp table for easier reference
            params AS (
            SELECT
            '<your sessionID>' AS session_id
            ),
            -- Retrieve the agent interactions and agent interaction messages to see each turn and input/output messages per turn
            interactionsWithMessages AS (
            SELECT
            I.ssot__AiAgentInteractionType__c AS InteractionType,
            I.ssot__StartTimestamp__c AS InteractionStartTime,
            I.ssot__EndTimestamp__c AS InteractionEndTime,
            I.ssot__TopicApiName__c AS TopicName,
            M.ssot__MessageSentTimestamp__c AS MessageSentTime,
            M.ssot__ContentText__c AS ContextText,
            M.ssot__AiAgentInteractionMessageType__c AS InteractionMessageType
            FROM
            ssot__AiAgentSession__dlm AS S
            JOIN ssot__AiAgentInteraction__dlm AS I ON S.ssot__id__c = I.ssot__aiAgentSessionId__c
            JOIN ssot__AiAgentInteractionMessage__dlm AS M ON I.ssot__id__c = M.ssot__aiAgentInteractionId__c
            JOIN params AS p ON S.ssot__Id__c = p.session_id
            ),
            -- Retrieve the agent interactions and agent interaction steps performed on each turn by the agent to generate its output
            interactionsWithSteps AS (
            SELECT
            I.ssot__AiAgentInteractionType__c AS InteractionType,
            I.ssot__StartTimestamp__c AS InteractionStartTime,
            I.ssot__EndTimestamp__c AS InteractionEndTime,
            I.ssot__TopicApiName__c AS TopicName,
            St.ssot__AiAgentInteractionStepType__c AS InteractionStepType,
            St.ssot__Name__c AS Name,
            St.ssot__InputValueText__c AS InputValueText,
            St.ssot__OutputValueText__c AS OutputValueText,
            St.ssot__StartTimestamp__c AS InteractionStepStartTime,
            St.ssot__PreStepVariableText__c AS PreStepVariableText,
            St.ssot__PostStepVariableText__c AS PostStepVariableText
            FROM
            ssot__AiAgentSession__dlm AS S
            JOIN ssot__AiAgentInteraction__dlm AS I ON S.ssot__id__c = I.ssot__aiAgentSessionId__c
            JOIN ssot__AiAgentInteractionStep__dlm AS St ON I.ssot__id__c = St.ssot__aiAgentInteractionId__c
            JOIN params AS p ON S.ssot__Id__c = p.session_id
            ),
            -- Join both data sets
            interactionsWithMessagesAndSteps AS (
            SELECT
            *,
            CAST(NULL AS VARCHAR) AS InteractionStepType,
            CAST(NULL AS VARCHAR) AS Name,
            CAST(NULL AS VARCHAR) AS InputValueText,
            CAST(NULL AS VARCHAR) AS OutputValueText,
            CAST(NULL AS VARCHAR) AS PreStepVariableText,
            CAST(NULL AS VARCHAR) AS PostStepVariableText
            FROM
            interactionsWithMessages
            UNION ALL
            SELECT
            InteractionType,
            InteractionStartTime,
            InteractionEndTime,
            TopicName,
            -- Use InteractionStepStartTime as MessageSentTime to sort unified records
            InteractionStepStartTime AS MessageSentTime,
            CAST(NULL AS VARCHAR) AS ContextText,
            CAST(NULL AS VARCHAR) AS InteractionMessageType,
            InteractionStepType,
            Name,
            InputValueText,
            OutputValueText,
            PreStepVariableText,
            PostStepVariableText
            FROM
            interactionsWithSteps
            )
            -- Reorder fields and sort them by MessageSentTime 
            SELECT
            TopicName, InteractionType, InteractionStartTime, InteractionEndTime,
            MessageSentTime, InteractionMessageType, ContextText,
            InteractionStepType, Name, InputValueText, OutputValueText, PreStepVariableText, PostStepVariableText
            FROM interactionsWithMessagesAndSteps
            ORDER BY MessageSentTime ASC

Agentforceおよび生成AIの使用状況と請求

Salesforce には、AI 使用量の支払方法に関するいくつかのオプションがあります。

AI インタラクションの請求は、アクティビティが発生する環境やインタラクションの性質など、いくつかの要素によって異なります。

  • 価格設定モデルでは、価格設定ルールと測定ルールのフレームワークを決定します。
  • AI ライフサイクルフェーズでは、活動が開発のフェーズに基づいて測定されるかどうかを判断します。

価格設定モデル

Salesforce では、AI の使用に対して 3 つの価格設定モデルを提供しています。

  • 消費ベースの価格設定: プロンプト数やアクション数など、基本的な AI 評価指標に基づいて使用量に対して料金を支払う。
  • ハイブリッド価格設定 (ユーザーあたり/月あたりのライセンス数 + 消費): このモデルでは、固定ユーザーライセンスと使用量ベースの消費を組み合わせて、多くの AI シナリオでユーザーあたりの価格の確実性を提供します。
    • ユーザーごとのライセンス: 定義された範囲内の特定の機能に対して、測定されていない使用量を提供します。
    • ライセンス固有の測定: 特殊なライセンスでのみ使用可能な機能への測定されていないアクセス権を付与します。
    • 測定条件: ライセンス固有の条件が満たされない場合にのみ Flex Credit の消費がトリガーされます。「Metering for Agentforce and Generative AI Usage」を参照してください。
  • ビジネス評価指標ベースの価格設定: このモデルでは、技術的な直接的な消費ではなく、高レベルのビジネス成果に基づいて支払います。たとえば、Agentforce Voice Minutes や翻訳された文字などがあります。

AI 使用量の測定方法と消費したクレジット

AI の利用状況は、特定の消費単位を決定する 2 つの主要なカテゴリに分類されます。

  • エージェントの利用状況: エージェントの利用状況には、推論、複数ステップの ToDo の実行、および単独での行動が可能な自律エージェントが含まれます。この種別の消費単位は、トリガーされたアクションの数に基づきます。
  • プロンプトベースの (組み込み) AI 利用状況: これらの機能は、ユーザーが自律的に行動することなく、特定のタスク (サマリー生成やメールのドラフト作成など) を支援します。消費は、大規模言語モデル (LLM) への直接要求を含むプロンプト数に基づきます。

アクションやプロンプトなどの AI 利用状況は、Flex Credit に変換される前にネイティブ単位で記録されます。このプロセスは 3 つのステップに従います。

  • 使用量種別分類: これらの単位は、使用される特定の機能またはエージェントに基づいて特定の使用量種別に対応付けられます。
  • メジャメント: 使用量種別 (1 つのアクションや 1 つのプロンプトなど) に基づいて未加工の消費単位が計数されます。
  • クレジット計算:使用量タイプは、Agentforce レート カードで定義された単価または乗数を使用して Flex Credit に変換されます。この乗数により、さまざまな AI サービスが統合クレジットプールに対してさまざまなレートで請求できます。

利用状況の種別とその測定単位についての詳細は、次のトピックを参照してください。

  • Flex Credits
  • 会話
  • Einstein 要求

AI ライフサイクルの測定

AI インタラクションの請求可能性は、開発ライフサイクルのフェーズによっても異なります。

  • 設計および開発: エージェントを作成および構築するための Agentforce Builder 機能は測定されず、クレジットを消費しません。ただし、Salesforce では、チャットまたは音声でエージェントをプレビューするときに使用状況を測定します。
  • テストと検証: Agentforce Builder、Agentforce Grid、Testing Center、および Sandbox を使用したテストは、必要なコンピューティングリソースを考慮して測定されます。テストの種類には、音声テストとチャットテストのプレビューオプション、または一括テストの実行オプションが含まれます。
  • 本番: 消費モデル (自律エージェントワークフローとユーザートリガープロンプト) に基づく本番環境でのすべてのライブインタラクション。
メモ Agentforce Gridは一般的にテストに使用されますが、AIライフサイクルの3つのフェーズすべてに適用できます。重要なのは、Agentforce Gridの使用量は、AIライフサイクルのフェーズに関係なく測定されるということです。

データモデルの照会

DMO から関連情報を取り込むアドホッククエリを実行できます。Data 360 では、データを照会する方法が複数用意されています。詳細は、「Query Data in Data 360」を参照してください。

使用できるクエリの例を次に示します。

Billable Usage by Agent (エージェント別の請求可能使用量)

このクエリを使用して、最も高価なエージェントを特定します。エージェント開発者名と種別でグループ化され、合計使用量とイベント数が集計されます。

SELECT
    AgentDeveloperName__c,
    AgentTypeCode__c,
    SUM(UsageQuantity__c) AS TotalUsage,
    COUNT(*) AS EventCount
FROM AiAgentGenerativeAiUsage_std__dlm
WHERE IsBillableIndicator__c = true
    AND Timestamp__c >= CURRENT_DATE - 30
GROUP BY AgentDeveloperName__c, AgentTypeCode__c
ORDER BY TotalUsage DESC

モデル別のトークン消費

このクエリを使用して、最も多くのトークンを消費しているモデルを特定します。モデル ID、プロバイダー、クラス別に入力、完了、合計トークン、イベント数が集計されます。

SELECT
    GenAiGatewayModelName__c,
    ModelProviderName__c,
    ModelClassType__c,
    SUM(PromptInputTokenCount__c) AS TotalInputTokens,
    SUM(PromptCompletionTokenCount__c) AS TotalCompletionTokens,
    SUM(PromptTotalTokenCount__c) AS TotalTokens,
    COUNT(*) AS EventCount
FROM AiAgentGenerativeAiUsage_std__dlm
WHERE Timestamp__c >= CURRENT_DATE - 30
GROUP BY GenAiGatewayModelName__c, ModelProviderName__c, ModelClassType__c
ORDER BY TotalTokens DESC

Usage by Channel (チャネル別の利用状況)

次のクエリを使用して、音声チャネルとメッセージングチャネルの利用状況を比較します。生成 AI 使用状況テーブルとセッションテーブルを結合して、チャネル種別ごとに合計使用状況とトークンを集計します。

SELECT
    s.ssot__AiAgentChannelType__c         AS ChannelType,
    s.ssot__RelatedMessagingSessionId__c  AS MessagingSessionId,
    s.ssot__RelatedVoiceCallId__c         AS VoiceCallId,
    u.AgentDeveloperName__c,
    SUM(u.UsageQuantity__c)              AS TotalUsage,
    SUM(u.PromptTotalTokenCount__c)      AS TotalTokens
FROM AiAgentGenerativeAiUsage_std__dlm u
    JOIN ssot__AiAgentSession__dlm s
        ON u.AiAgentSessionId__c = s.ssot__Id__c
WHERE u.Timestamp__c >= CURRENT_DATE - 30
GROUP BY s.ssot__AiAgentChannelType__c,
    s.ssot__RelatedMessagingSessionId__c,
    s.ssot__RelatedVoiceCallId__c,
    u.AgentDeveloperName__c
ORDER BY TotalUsage DESC
LIMIT 20

Agentforce機能の生成AIの使用量は通常測定され、クレジットを消費します。場合によっては、必要な条件が満たされると、使用量が測定解除され、クレジットを消費しないことがあります。

使用量は、ユーザー種別、割り当てられた権限、実行コンテキストなどの特定の条件を満たす場合に測定されません。測定解除には 2 つのカテゴリがあります。

AIエージェント生成AI利用状況データモデルを使用して、利用状況の照会、表示、監視、監査を行います。使用状況データ モデルでは、未測定の使用状況、未測定の理由、トークンの使用状況など、すべての生成AIとAgentforceの使用状況を取得します。

  • Global Unmetering (グローバル測定): AI 使用状況が一般的な組織およびユーザーレベルの条件を満たしているかどうかに基づく、商品に依存しないロジック。

Agentforce アクションまたは AI 機能のグローバルな測定解除の主な条件

  • ユーザーには「測定されていないユーザーベースの AI」権限が必要です。
  • アクションまたは AI 機能の使用は、自動化プロセスユーザーまたはその他の ID ではなく、上記の測定されていない権限を持つ現在のユーザーとして実行する必要があります。
  • 非測定使用量は、ユーザーあたり 1 分あたり最大 30 LLM コールに制限されます。この制限は現在、製品で技術的に適用されていません。

Agentforce(デフォルト)から Agentforce 従業員エージェントへの移行方法

Agentforce(デフォルト)から Agentforce 従業員エージェントに数ステップで移行できます。すべての設定は新しいエージェントに自動的に継承されます。

Agentforce(デフォルト)から Agentforce 従業員エージェントに移行するには、必要なアドオン ライセンスとFlex Creditsがプロビジョニングされている必要があります。カスタムプロンプト、名前を変更したアクション、およびエージェントを使用できるユーザーを決定する権限セットやプロファイルなどの表示設定を新しいエージェントで再作成するように計画します。

  1. [設定] から、[クイック検索] ボックスに「エージェント」と入力し、[Agentforce Agents] を選択します。
  2. Agentforce(デフォルト)のドロップダウンメニューから、[従業員エージェントに移行(Migrate to an Employee Agent)] を選択します。
    [従業員エージェントに移行] アクションが表示されない場合は、Flex Credits がプロビジョニングされていることを確認します。Flex Credits を使用しない場合、移行ツールは使用できません。
  3. Agentforce 従業員エージェントの名前と API 参照名を入力します。
  4. [作成] をクリックします。
    移行には数分かかり、移行後、新しい Agentforce 従業員エージェントを使用する準備が整います。これを使用するには、ユーザーにアクセス権を付与してエージェントを有効化します。

Agentforce(デフォルト)から Agentforce 従業員エージェントへのサブエージェントとアクションの手動移行

この記事で説明されている Flex Credits の利用状況種別は、標準測定方法に基づいています。ただし、一部の機能には特定の制限や例外があります。これらの機能に固有の請求についての詳細は、機能のマニュアルを参照してください。

アクションの利用状況の種別

アクションは、AI エージェントが情報を取得したりタスクを実行したりするために使用する機能です。アクションには、標準とカスタムの 2 種類があります。

  • 標準エージェントアクションは、標準で使用できるアクションです。「標準アクションリファレンス」を参照してください。
  • カスタムアクションは、ユーザーが最初から作成するか、標準アクションを変更して作成するアクションです。顧客が作成したアクションについての詳細は、「カスタムアクションの作成」を参照してください。
重要 標準アクションとカスタムアクションの請求可能な使用量種別は、テキスト会話と音声会話のどちらで実行されるかによって異なります。

エージェントアクションは、確定的 (推論手順など) に実行されるか、LLM を使用してエージェントが推論するときに実行されるかに関係なく、実行時に請求されます。ユーティリティ (担当者へのエスカレーション、変数の設定、別のトピックへの移行) は、エージェントアクションとして請求されません。

請求カテゴリ 説明
標準アクション

使用量は、テキスト会話でエージェントがコールした標準アクションの数によって決まります。現在、エージェントがコールするすべての標準アクションは、処理されるトークンの数に関係なく、1 つの標準アクションとして測定されます。

標準エージェントアクションは、標準で使用できるアクションです。標準アクションのリストを確認するには、「標準アクションリファレンス」を参照してください。

メモ Agentforce for Sales アドオンや Agentforce for Service アドオンへの登録など、一部の標準エージェント アクションを使用するには、これらのアクションにアクセスするユーザごとに登録を購入する必要があります。このような標準アクションに必要な登録を判断するには、『標準アクションリファレンス』の「標準アクションリファレンス」を参照してください。この要件はまだ技術的には適用されていませんが、必要なアドオンライセンスを持たないユーザーは、要件が適用されるとライセンスを持たないアクションにアクセスできなくなります。
カスタムアクション

使用量は、テキスト会話でエージェントがコールしたカスタムアクションの数によって決まります。現在、エージェントがコールするすべてのカスタムアクションは、処理されるトークンの数に関係なく、1 つのカスタムアクションとして測定されます。
標準音声アクション

使用量は、エージェントが音声会話で実行する標準アクションの数によって決まります。

メモ Agentforce for Sales アドオンや Agentforce for Service アドオンへの登録など、一部の標準エージェント アクションを使用するには、これらのアクションにアクセスするユーザごとに登録を購入する必要があります。このような標準アクションに必要な登録を判断するには、『標準アクションリファレンス』の「標準アクションリファレンス」を参照してください。この要件はまだ技術的には適用されていませんが、必要なアドオンライセンスを持たないユーザーは、要件が適用されるとライセンスを持たないアクションにアクセスできなくなります。
カスタム音声アクション

使用量は、エージェントが音声会話でコールしたカスタムアクションの数によって決まります。

カスタムアクションは、ユーザーが作成したアクション、または標準アクションの変更によって発生するアクションです。顧客が作成したアクションの詳細については、「Create a Custom Agent Action (カスタムエージェントアクションの作成)」を参照してください。標準アクションがカスタムアクションになる方法についての詳細は、「標準エージェントアクションの参照アクションの編集」を参照してください。

Agentforce Voice Minutes 利用状況種別

Agentforce Voice Minutes 使用量タイプは、Voice Actions 使用量タイプの代替として Agentforce Voice ユーザ向けに設計されています。この使用量種別は、Agentforce Voice Minutes のサブスクリプションを購入した一部の対象顧客にのみ適用されます。Agentforce Voice Minutes の詳細については、アカウントエグゼクティブにお問い合わせください。

請求カテゴリ 説明
Agentforce Voice Minutes

使用量は、エンド ユーザと Agentforce Voice 間の音声通話の長さによって決まります。使用量は、次の丸 1 分に切り上げられます。つまり、1 分未満の端数は丸 1 分として処理されます。

たとえば、

  • 60 秒の通話は 1 分として請求されます。
  • 61 秒の通話は 2 分として請求されます。

組織で Agentforce 音声アクションと Agentforce Voice Minutes の両方が有効になっている場合、請求では Voice Minutes が優先されます。組織で Agentforce Voice Minutes を使用できる場合、Agentforce Voice Minutes のみが測定され、Voice Actions の使用量種別は同じアクティビティに適用されません。

プロンプト利用状況種別

プロンプトの使用種別は、大規模言語モデル (LLM) ゲートウェイへのコール数に基づいて計算され、使用される大規模言語モデルによって異なります。プロンプトの使用種別は、特定の ToDo に対して LLM への直接要求が含まれるサービス返信などの組み込みの生成 AI 機能に適用されます。

請求カテゴリ 説明
スタータープロンプト

使用量は、LLM ゲートウェイを介した LLM への直接要求の数と、ゲートウェイで Bring Your Own Large Language Model (BYOLLM) が使用されているかどうかの 2 つの要素に基づいて計算されます。

各スタータープロンプトには、最大 2,000 トークンの処理が含まれます。プロンプト使用量は、切り上げられた 2,000 トークンのチャンクで計数されます。この制限を超えるプロンプトは複数のプロンプトとして測定され、2,000 トークンのチャンクが追加されるたびに新しいプロンプトとして計数されます。たとえば、入力トークンと出力トークンの合計が 6500 のプロンプトは、4 つのプロンプトとして測定されます。

トークンは、AI モデルによって処理されるデータの単位です。

Speech Foundation の利用状況の種別

音声基盤は、AI プラットフォームの音声-to-テキスト、テキスト-to-スピーチ、翻訳サービスです。これらのサービスにより、システム管理者と開発者は音声機能をワークフロー (ボイスメールの文字起こしや音声アラートの生成など) に統合できます。請求に重複がないように、Speech Foundation の利用状況種別は他の利用状況種別とは独立して測定されます。機能のドキュメントを参照して、機能に適用される利用状況の種別を判断してください。

請求カテゴリ 説明
音声-to-テキスト 音声-to-テキストは、音声を書き込みテキストに変換します。このプロセスは、自動音声認識 (ASR) モデルによって実行されます。使用量は、文字起こしごとに処理された音声の長さ (秒単位) に基づいて計算されます。Digital Wallet では、この使用量が分単位で集計されて表示されます。
テキスト読み上げ

テキスト読み上げは、記述されたテキストを自然な音声に変換します。これは、自動音声合成モデルによって実行されるプロセスです。使用量は、音声生成で処理されたテキスト文字数で測定されます。Digital Wallet では、この使用量が 100 万文字単位で集計されて表示されます。

Digital Wallet で消費量がどのように表示されるかを理解するために、テキストから音声への変換用に 9,000 文字を処理するシナリオについて考えてみます。この使用量は 100 万文字単位であるため、実際の消費量は 0.009 単位 (9,000 を 1,000,000 で除算) になります。Digital Wallet では、この使用量は小数点以下 2 桁に丸められ、値は 0.01 単位として表示されます。
トランスレーション

翻訳では、人間の言語から別の言語のテキストに変換されます。これは、機械翻訳モデルによって実行されるプロセスです。翻訳の使用量は、翻訳で処理された文字数で測定されます。

Digital Wallet で消費量がどのように表示されるかを理解するために、翻訳用に 9,000 文字を処理するシナリオについて考えてみます。この使用量は 100 万文字単位であるため、実際の消費量は 0.009 単位 (9,000 を 1,000,000 で除算) になります。Digital Wallet では、この使用量は小数点以下 2 桁に丸められ、値は 0.01 単位として表示されます。
