MCP Server レコードページからのポリシーの手動適用

MCP サーバーにポリシーを適用して、アクセスを制御し、使用制限を設定し、コンプライアンスを確保します。手動で適用できる Agentforce ゲートウェイ ポリシーを追加できます。

必要なエディション

使用可能なインターフェース: Lightning Experience
使用可能なエディション: Enterprise Edition、Performance Edition、Unlimited Edition、および Developer Edition。必要なアドオンライセンスはエージェント種別によって異なります。
必要なユーザー権限
MCP サーバーの登録を管理する AIエージェントの管理とエージェントタイプの必要な権限
メモ ルールベースのポリシーは、指定した条件を満たす MCP サーバーとエージェントに自動的に適用されるため、MCP サーバーレコードページからは管理できません。ルールベースのポリシーを適用または削除するには、Policy Builder でポリシールールを編集します。
  1. [設定] から、[クイック検索] ボックスに「Agentforce」と入力し、[Agentforce レジストリ] を選択します。
  2. 編集するサーバの名前をクリックし、［Policies］ タブを選択します。サーバーに適用されるポリシーを追加した場合は、ここに表示されます。
  3. ポリシーを適用するには、［Apply Policy］ をクリックします。
    1. 手動で適用できる既存の MCP サーバ ポリシーを選択し、［Apply Policy］ をクリックします。
    2. 代わりに新しいポリシーを作成するには、［Create Policy］ をクリックして Policy Builder を起動します。

Agentforce Gateway の Policy Builder からポリシーを作成、適用、および削除できます。[設定] から、[クイック検索] ボックスに「Agentforce ゲートウェイ」と入力し、[ポリシー] を選択します。

MCP for Agentforce の要件

要件を確認して、Agentforce で MCP サーバを登録し、使用する準備が整っていることを確認します。

必要なエディション

使用可能なインターフェース: Lightning Experience
使用可能なエディション: Enterprise Edition、Performance Edition、Unlimited Edition、および Developer Edition。必要なアドオンライセンスはエージェント種別によって異なります。

MCP Server は次の要件を満たす必要があります。

  • 機能し、ネットワーク接続を介してアクセスできます。
  • ストリーム可能 HTTP 転送プロトコルを使用します。HTTP+SSE はサポートされません。
  • サーバーで認証プロトコルを使用している場合、OAuth 2.0 クライアントログイン情報を使用する必要があります。OAuth 2.1 クライアントログイン情報など、追加の設定が含まれる高度な認証パターンがいくつかサポートされています。

エージェントのパフォーマンスを安全にテストして互換性を確保できるように、新しいエージェントを使用して Sandbox 組織で開始することをお勧めします。次に、エージェントのパフォーマンスが信頼できることを確認したら、本番組織でエージェントを再作成します。

MCP for Agentforce を使用する前に、次の前提条件を完了してください。

  • Einstein生成AIを設定します。
  • Agentforce を有効にします。
  • Agentforce Studio の Agentforce Builder でエージェントを作成します。顧客または従業員の一般的な使用事例を処理する Agentforce サービスエージェントまたは Agentforce 従業員エージェントを作成します。
    メモ データ モデルと Atlas 推論エンジンが異なるため、従来の Agentforce Builder で作成されたエージェントでは Agentforce の MCP はサポートされません。

エージェントへの MCP ツールアクションの追加

MCP ツールを参照するエージェントアクションをアセットライブラリからエージェントに追加して、エージェントが会話でツールをコールできるようにします。

必要なエディション

使用可能なインターフェース: Lightning Experience
使用可能なエディション: Enterprise Edition、Performance Edition、Unlimited Edition、および Developer Edition。必要なアドオンライセンスはエージェント種別によって異なります。
必要なユーザー権限
エージェントアクションを管理する AIエージェントの管理とエージェントタイプの必要な権限

MCP Server をまだ登録していない場合は、エージェントで使用するツールを許可リストに登録します。

エージェントを変更するには、ドラフト状態である必要があります。確定したエージェントを変更する場合は、エージェントの新しいドラフトを作成します。

次の手順では、エージェントの既存のサブエージェントに MCP ツールアクションを追加する方法について説明します。MCP ツールで新しいサブエージェントを使用する場合は、「サブエージェントの管理」を参照してください。

  1. Agentforce Studio アプリケーションの [エージェント] リストから、アクションを追加するエージェントを開きます。
  2. [エクスプローラー] パネルで、アクションを追加するサブエージェントにマウスポインターを置いて、[] をクリックします。
  3. [アセットライブラリから追加] を選択します。
  4. サブエージェントに追加するアセットライブラリから 1 つ以上のアクションを選択し、変更を保存します。
    MCP ツールを参照するエージェントアクションは、命名パターン「Tool Name ServerName」に従い、 アイコンで示されます。
  5. MCP ツールアクションをサブエージェントに追加したら、アクションの使用方法をエージェントに指示する推論手順を追加します。
  6. 変更内容を保存します。
メモ

MCP ツールアクションをエージェントに追加すると、次のようになります。

  • 一部のデータ型 (数値など) の入力表示ラベルと出力表示ラベルは、「文字列」の表示ラベルに置き換えられることがあります。これはエージェントのロジックや推論には影響しませんが、使いやすさを考慮して、表示ラベルをアセットライブラリの MCP ツールアクションまたは MCP ツールの入力スキーマまたは出力スキーマの元の値に置き換えることをお勧めします。修正が進行中です。
  • [参照アクション種別] 項目は空で表示されます。参照アクションが入力されるため、アクションは必須項目として識別されていても、参照アクション種別なしで実行できます。[参照アクション種別] 項目をクリックまたは変更すると、参照アクションはリセットされ、MCP ツールに手動でリセットすることはできません。この場合、エージェントからアクションを削除して、アセットライブラリから再追加します。修正が進行中です。

エージェントを確定して有効化する前に、エージェントを慎重にテストして MCP ツールアクションが期待どおりに動作することを確認します。結果に基づいて推論手順を調整します。

  • MCP ツールの応答スキーマとエージェント設計
    MCP サーバーツールは、サーバーツールを参照するエージェントアクション (MCP ツールアクション) としてエージェントに追加され、他のエージェントアクションと同様に使用できます。ただし、Agentforce Builder では、すべての有効な MCP 応答スキーマが完全にサポートされるわけではありません。エージェントを作成するときに、変数の対応付け、アクションチェーン、入力と出力の表示の違いについて計画します。複雑な応答では、よりシンプルなエージェント設計パターンが必要になる場合があります。
  • エージェントからの MCP ツールアクションの削除
    MCP ツールを参照するエージェントアクションを削除して、エージェントのアクセス権を削除します。
  • アセットライブラリからの MCP ツールアクションの削除
    MCP ツールを参照するエージェントアクションをアセットライブラリから削除して、どのエージェントにも追加できないようにします。アセットライブラリからエージェントアクションを削除しても、そのアクションは、すでに追加しているすべてのサブエージェントおよびエージェントで引き続き使用できます。アセットライブラリから削除する前に、エージェントからアクションを削除することをお勧めします。

サポートされる JSON 応答

Agentforce Builder のサポートは、プリミティブ値と項目アクセスが浅い場合に最適です。そのため、シンプルな構造化 JSON 応答を使用する MCP サーバ ツールを選択するか、可能な場合は重要な値をプリミティブ フィールドまたはシンプルな最上位フィールドとして公開するように応答を調整します。サポートされる JSON 応答には、最上位のオブジェクト、最上位のオブジェクトプロパティ、オブジェクトの最上位の配列が含まれます。現在、ネストされたプロパティ、オブジェクトの配列、動的オブジェクトのペイロードなど、より複雑な形状はエンドツーエンドでサポートされていません。

Lightning 種別

すべてのエージェント アクションで Lightning 種別を使用して、入力と出力でデータの構造を定義、検証、表示します。MCP ツールの入力スキーマと出力スキーマは、Lightning タイプに常に対応付けられるとは限りません。これは、データ タイプがサーバによって定義され、プロトコルで幅広いデータ タイプがサポートされるためです。たとえば、データ型に any/or などの演算子が含まれている場合です。標準 Lightning タイプと、エージェント アクションで Lightning タイプを使用する方法について説明します。

データを Lightning タイプに解決できない場合、Agentforce レジストリの MCP サーバのレコード ページでツールの入力スキーマと出力スキーマを表示できます。ただし、アセットライブラリとエージェントでは、関連付けられた MCP ツールアクションの入力または出力は空で表示されます。

エージェントで MCP ツールアクションを使用することはできますが、入力または出力を変数に保存したり、下流のロジックや命令で使用したりすることはできません。

  • アクションを確定的に別のアクションにチェーニングすることはできません。ただし、推論では、エージェントは関連する入力と出力を選択できます。
  • 各入力と出力を変数に対応付ける必要があるため、アクションは推論命令で確定的に実行できません。
  • Lightning タイプに解決されない出力は、条件文またはフィルタで使用できません。

最良の結果を得るには、エージェント設計で確定的動作に関するエージェントの推論を計画し、簡単な自然言語サブエージェントの指示を設定します。

マルチエージェントソリューション

Agentforce のマルチエージェントオーケストレーションは、エージェントの機能を拡張するために使用できる相互運用性フレームワークです。このフレームワークでは、オーケストレーターエージェントがユーザーと通信します。サブエージェント分類を使用して、接続済みサブエージェントの説明とエージェントルーターの指示に基づいて、(会話ではなく) 要求を接続済みサブエージェントに転送します。ハンドオフ全体でコンテキストが保持され、ユーザーに到達する前に接続済みサブエージェントの応答が合成されます。マルチエージェントオーケストレーションを使用すると、企業は顧客との円滑なやりとりなしで、共通のコンテキストを使用してチャネル全体に 1 人のエージェントをリリースできます。

優れたカスタマーサービスエージェントを構築して、チームがフィールドサービスの使用事例を追加したいと考えているとします。または、異なるビジネスユニットで 3 人のエージェントをすでに実行していて、ビジネスでエージェントが相互に話をする必要があるとします。または、6 つの異なるドメインをカバーするほどに膨れ上がった Instructions ブロックを眺めていて、ルーティングが中断され続けている理由がわからないとします。トリガーが何であれ 同じ問題に行き着いたある時点で、1 人のエージェントでは不十分です。

Orchestrator エージェントと接続済みサブエージェント

エージェントが ToDo を管理し、他の接続済みサブエージェントに委任する場合、オーケストレーターエージェントと呼ばれます。オーケストレーターエージェントは、業務を遂行するために会話を任意の組み合わせのサブエージェントと接続済みサブエージェントに転送できます。オーケストレーターエージェントは、ユーザーとやりとりする 1 つの「フロントドア」と考えることができます。また、バックグラウンドで作業を調整し、さまざまな「バックドア」接続済みサブエージェントに作業を委任して、結果をユーザーに返します。

接続済みサブエージェントは、オーケストレーターエージェントがサブエージェントのように使用できる Salesforce 組織内の完全に独立したエージェントです。アセットライブラリから追加された標準サブエージェントと接続済みサブエージェントの違いを理解することが重要です。

  • サブエージェントは、プライマリエージェントが使用できる命令 (ロジックと推論を制御する) とアクション (ツール) のみを含むローカライズされたコンポーネントです。
  • 接続済みサブエージェントは、独自の専門知識と ID を持つ完全な独立エージェントを表します。接続済みサブエージェントには、1 つ以上のサブエージェントが含まれます。接続済みサブエージェントはモジュール式で、独自のドメインを表し、多くのマルチエージェントソリューションで再利用するのに適しています。

オーケストレーターに割り当てられた内部サブエージェントと外部接続サブエージェントの組み合わせによって、エージェントが処理できる機能の完全な拡張性が定義されます。

オーケストレーターエージェントのコンテキストでは、参照エージェントは、接続済みサブエージェントの基盤となるエージェントです。接続済みサブエージェントを追加すると、参照エージェントの設定 (説明など) が含まれ、上書きして動作をカスタマイズできます。

エージェント間ソリューションの計画

次に、Agentforce のマルチエージェントオーケストレーションで使用するエージェントの設計を開始するためのヒントをいくつか示します。

  • 確定性と一貫した動作を実現するために、接続済みサブエージェントは一意のエージェントに基づきます。たとえば、返品の承認、配送表示ラベルの送信、購入の返金は、さまざまな接続済みサブエージェントが実行できる 3 つの個別のアクションを表します。
  • モジュール化と再利用を考えます。専門エージェントは、共通の目標を達成するために組織の境界を越えてやりとりする必要があるさまざまなビジネスドメイン (営業、人事、財務など) を表すことができます。再利用できるように設計した場合、専門のエージェントが複数のマルチエージェントソリューションで作業を行うことができます。
  • 接続済みサブエージェントに使用する説明 (命令) を作成します。オーケストレーターエージェントとエージェントルーターは、説明に基づいて、接続されたサブエージェントに転送するタイミングを決定します。説明が曖昧であったり、他のサブエージェントや接続済みサブエージェントと重複したりすると、動作が一貫しなくなる可能性があります。
  • オーケストレーターエージェントから接続する前に、エージェントを個別にテストします。その手順と理由アクション、および接続済みサブエージェントに含まれるエージェントアクション (基盤となるフロー、プロンプトテンプレート、その他の参照アクションを含む) を確認します。単体テストは、問題を個別に見つけて解決するのに役立つため、他のソリューションコンポーネントと組み合わせてテストするときに信頼性が高まります。

接続と適応応答形式

接続には、エージェントが応答を構造化し、画像、ボタン、リンク、動画などのマルチメディアコンテンツを配信するのに役立つ適応型応答形式が含まれます。また、エージェントとの会話の転送に役立つ設定とオムニチャネルフローも含まれます。

接続を使用すると、エージェントを一度作成すれば Agentforce Builder で複数のチャネルに簡単に追加できるため、エージェント開発を拡張し、反復的な設定を減らすことができます。また、エージェントは顧客と従業員のエクスペリエンスをより動的でチャネル固有、一貫したものにすることができます。つながりを考える方法の 1 つは、人々がさまざまな状況でどのように行動するかを考慮することです。ユーザーは、各設定の独自のルール、エチケット、制約に合わせてコミュニケーション方法を適応させます。たとえば、Slack ではテキストとカジュアルトーンを使用し、通話では音声とフォーマルトーンを使用します。各エージェントテンプレートは特定の接続をサポートしており、その接続に関連付けられたチャネルにエージェントを接続できます。

ユーザーが接続済みチャネルでエージェントとやりとりすると、エージェントはエクスペリエンスに関連付けられた接続を識別します。エージェントは、接続に関連付けられているバックグラウンドの指示に基づいて推論を調整し、ユーザーの発言を最も関連性の高いサブエージェントに分類して、1 つ以上のアクションを起動します。応答を送信する前に、エージェントは応答を構造化する適応型応答形式を決定します (ある場合)。適応型応答形式を選択するために、エージェントは使用可能な形式、アクションの出力、および付随するエージェントメッセージを考慮します。接続で使用できる適応型応答形式と、付随するメッセージを含むアクション出力が考慮されます。

たとえば、顧客が拡張Facebook MessengerチャネルでASA(Agenforceサービスエージェント)にメッセージを送信したとします。ASA にはメッセージング接続があり、これはすべての拡張メッセージングチャネルに関連付けられており、メッセージングコンポーネントに対応付けられる適応型応答形式が含まれています。メッセージング接続では、拡張 Facebook Messenger チャネルで ASA の理由付けと応答に役立つ指示が推論エンジンに送信されます。エージェントがユーザーの発言をサブエージェントに分類し、アクションを起動します。次に、リッチリンク応答適応応答形式で応答を構成し、Facebook Messenger で応答を送信します。

詳細は、「従来のビルダーでの接続の設定」を参照してください。

チャネル

チャネルは、エージェントをリリースできるメッセージングプラットフォーム、アプリケーション、およびインターフェースです。チャネルには、Lightning Experience の Agentforce パネル、Salesforce モバイル アプリケーション、Slack、メッセージング プラットフォーム、電子メールなどがあります。チャネルのサポートはエージェント種別によって異なります。一部のエージェント種別とテンプレートは従業員が使用でき、他の種別とテンプレートを顧客対応チャネルに追加できます。

オムニチャネルフロー

オムニチャネルフローを使用すると、エージェントの会話を簡単に転送できます。これらのフローでは、[作業を転送] アクションを使用して、会話とそれに関連付けられたレコード (メッセージングセッションやメールレコードなど) を転送します。メッセージングまたはメールに接続するエージェントには、少なくとも 1 つの受信および送信オムニチャネルフローがあります。

顧客がチャネルでエージェントとやりとりすると、会話に関連付けられたレコードが作成されます。次に、受信オムニチャネルフローによって、レコードが顧客チャネルからエージェントに転送されます。たとえば、顧客が WhatsApp でメッセージを送信すると、受信オムニチャネル フローによって会話が WhatsApp から Agentforce サービスエージェントに転送されます。エージェントは複数の受信フローに接続できますが、各受信フローは 1 つのエージェントにのみ接続できます。

エージェントは、送信オムニチャネルフローを使用して会話を別の送信先 (サービス担当者、キュー、別のエージェントなど) に転送します。ビジネスニーズに合わせて送信オムニチャネルフローをカスタマイズできます。たとえば、異なる使用事例でそれぞれが得意とする複数の目的地がある場合、会話を最も関連性の高い目的地に転送する決定要素をフローに追加できます。エージェントは複数の送信フローに接続でき、各送信フローは複数の送信先に接続できます。

オムニチャネルフローについての詳細は、「オムニチャネルを使用した作業の転送」を参照してください。

参照アクションの設計に関する考慮事項

エージェントアクションの基礎となる参照アクションの設計に取り組むときに考慮すべきいくつかの要素を次に示します。

確定的またはプロンプトベース

エージェントアクションの基礎となるプラットフォーム機能を開発する場合、まず使用事例に関連するビジネスプロセスと ToDo を確認します。次に、プロセスまたは ToDo を決定論的にするかプロンプトベースにするかを決定します。

  • 確定的: 呼び出し可能または REST Apex クラスまたは自動起動フローを使用して出力を生成します。フローまたは Apex に基づくアクションは確定的であり、ビジネス ロジックとルールを使用して一貫した結果を生成します。
  • プロンプトベース: 1 つ以上のプロンプトテンプレートを使用して出力を生成します。プロンプトベースのアクションでは、応答の記述方法を制御したり、LLM の推論および生成機能を使用したりできます。たとえば、概要を生成したりセンチメント分析を実行したりするには、プロンプトテンプレートを参照アクションとして使用する必要があります。プロンプト テンプレートは、Knowledge や外部システム データなどのデータをエージェントにグラウンディングするためにも使用されます。

アクションでは、確定的アプローチとプロンプトベースのアプローチの両方を組み合わせることができます。たとえば、予定管理サブエージェントには、予定をキャンセルするアクションが含まれる場合があります。ユーザーが予定のキャンセルを要求すると、フローベースのアクションがトリガーされてキャンセルが完了します。このフローの途中で、エージェントはユーザーのキャンセル理由をまとめたプロンプトテンプレートを起動することもできます。

原子または複合

参照アクションがアトミックか複合かを考慮するもう 1 つの要素です。

  • アトミック: 小さな単独の ToDo。モジュール方式により、エージェントはより高度な目標を達成するためにさまざまな方法でアクションを自由に組み合わせることができます。また、さまざまなサブエージェントでアクションを再利用する機会も増える傾向にあります。
  • 複合: 複数のサブタスクで構成される複雑な ToDo。複合アクションの利点は、エージェントが ToDo を完了するために実行するステップの正確な順序を制御できることです。

入力と出力

Agentforce では、各エージェント アクションに少なくとも 1 つの入力が必要です。つまり、基礎となるフロー、Apex、またはプロンプト テンプレートにも少なくとも 1 つの入力が必要です。たとえば、ホテルの予約を検索する場合、入力はゲストのメールアドレスまたは予約番号になります。会話中に、AI エージェントは情報を収集し、アクションをトリガーして入力を渡すために必要なすべての詳細があるかどうかを判断する自律性があります。

また、各アクションには少なくとも 1 つの出力が必要です。アクションの作成方法によって、出力の内容、使用方法、および会話でのユーザーへの表示の有無と方法が決まります。完全には実装されていないテストアクションを恐れずに実験してください。テストアクションは、アイデアが実行でどのように機能するかを確認するための優れた方法です。

アクションの作成方法を決定したら、Best Practices for Agent Action Instructions (エージェントアクション手順のベストプラクティス) を確認します。

ルーティングとエスカレーション

AI エージェントは、会話をライブ担当者にエスカレーションする必要がある場合があります。担当者にエスカレーションする理由には、会社のポリシー、ブランド要件、セキュリティ対策、リスク管理、規制へのコンプライアンスなどがあります。

計画プロセス中に、AI エージェントの作業中に人間の意思決定と監視が発生するすべての方法を定義します。担当者が介入するタイミングと方法に関する明確なガイドラインがあれば、エージェントのプロトタイピングを開始するときに、組織で適切なガードレールを簡単に設定できます。

セキュリティコントロール

  • 管理者アクセス: SalesforceでAIエージェントを作成および管理するには、「AIエージェントの管理」ユーザー権限とエージェント タイプに必要な権限、または「アプリケーションのカスタマイズ」ユーザー権限が必要です。
  • 従業員アクセス: 従業員が Salesforce で AI エージェントを操作する場合、エージェントは現在ログインしている Salesforce ユーザーのコンテキストで実行されます。「Trust and Agents」を参照してください。
  • 顧客アクセス: エージェントが Web サイトなどの外部チャネルにリリースされている場合、検証されない限り、AI エージェントが顧客の代わりに実行したくないアクションがある可能性があります。Agentforce用の認証ソリューションの設計方法は、特定の使用事例のセキュリティおよび識別要件によって異なります。「Agentforce アクションによる信頼の維持」を参照してください。
  • エージェントアクセス: サービスエージェントなどの一部の AI エージェントはエージェントユーザーとして動作し、エージェントユーザーは Salesforce で専用のユーザープロファイルとロールを持っています。AI エージェントが実行できるアクションは、割り当てられた権限によって異なります。AIエージェントがアクセスできるデータを制御する方法については、「Best Practices for Agent User Permissions(エージェントユーザー権限のベストプラクティス)」を参照してください。

シミュレーションモードは、エージェントが正しく設定されていることを確認するのに役立ちます。エージェントの設定が正しく、目的どおりに動作することを確認します。このモードでは、エージェントのユーザー検証やアクションの実行などは確認されず、Salesforce データは変更されません。

ライブテストモードは、エージェントに必要なツールが正しく設定されていることをテストする場合に最適です。アクションと、それを正常に実行するエージェントの能力がテストされます。この種類のテストでは、Salesforce データが変更されます。

  • Agentforce Builder でのエージェントのテスト (ベータ)
    Agentforce Builder でエージェントを手動でテストすると、エージェントのインタラクションとプロセスの詳細なステップバイステップのトレースが提供されます。[プレビュー] パネルを使用してエージェントとチャットし、[インタラクションの概要] パネルでサブエージェントの選択、アクションの実行、推論を確認します。Agentforce Assistant と会話することで、どの手順についても詳細を取得できます。

ステップ 1: ユーザーがメッセージを送信する

エージェントが会話型インターフェースを使用している場合、ユーザーが質問または要求を入力するとプロセスが開始されます。

バックグラウンドで操作するエージェントの動作は異なります。

  • Agentforce SDRエージェント:エージェントが、リードの割り当て、スケジュール、および設定したその他のエンゲージメント ルールに基づいて見込み客との連絡を開始したときにプロセスが開始されます。
  • Agents called from a Apex class or flow：設定した条件に基づいてエージェントが起動されると、プロセスが開始されます。Apex クラスまたはフローを設定するときに、サンプルのユーザ メッセージを指定してエージェントの ToDo を定義します。エージェントは同じユーザーメッセージを使用して、チャットウィンドウでユーザーが質問や要求を行った場合と同じように、割り当てられたサブエージェントとアクションを検索します。

ステップ 2: エージェントがユーザーのメッセージをサブエージェントに分類する

エージェントは、ユーザーの希望とエージェントが実行できるジョブに基づいて、最も一致するサブエージェントを選択します。そのために、推論エンジンでは、ユーザーの最新のメッセージを含む最近の会話履歴と、エージェントが使用できるすべてのサブエージェントの名前および分類の説明が比較されます。検索条件が適用されたサブエージェントは、検索条件が満たされた場合にのみ含まれます。

サブエージェントが選択されると、推論エンジンはエージェントが次のステップを決定するために必要なすべての情報を収集します。

  • 最近のユーザーメッセージ (会話の過去 6 ターンの平均) を含む最近の会話履歴。
  • サブエージェントの名前、範囲、指示。
  • サブエージェントに含まれるアクションの名前と命令 (入力および出力命令を含む)。検索条件が適用されたアクションは、検索条件が満たされた場合にのみ含まれます。

その後、エージェントは推論プロセスに進みます。

推論エンジンで適切なサブエージェントが見つからない場合、エージェントはトピック外システムサブエージェントに移動し、会話を割り当て済みのサブエージェントに戻そうとします。

ステップ 3: エージェントが推論プロセスを開始し、アクションを実行する

エージェントはサブエージェントを選択すると、使用可能な情報を分析して次のステップを決定します。

  • エージェントアクションの実行

    エージェントが情報を取得または更新する必要がある場合、1 つ以上のエージェント アクションを使用して、Apex クラス、フロー、プロンプト テンプレートなどの Salesforce サービスをコールできます。エージェントアクションの詳細を確認します。

    また、エージェントはアクションを使用して、信頼できるビジネス データと他のソース (Knowledge 記事や外部 Web サイトなど) に応答をグラウンディングします。データのグラウンディング エージェントについての詳細を確認します。

  • ユーザーに詳細情報を求める

    エージェントが会話履歴外の情報を必要とする場合、エージェントはユーザーに直接質問できます。

  • ユーザーに明確な質問をする

    エージェントはフォローアップの質問をして、使用可能なオプションを明確にすることができます。

  • ユーザーの質問または要求に直接回答する

    ユーザーの質問や要求をエージェントがすでにアクセスできる情報で解決できる場合、エージェントは追加アクションを実行せずに応答できます。

エージェントの意思決定は、サブエージェントの指示に大きく影響されます。たとえば、サブエージェントの指示で、商品関連の質問に回答する前に必ずモデル番号を尋ねるように指定されている場合、エージェントは次のステップに進む前にその情報を要求します。または、サブエージェントの指示で、エージェントが取引先情報を提供する前に顧客の ID を検証する必要があると指定されている場合、エージェントはユーザーの要求を満たす前に顧客検証サブエージェントに移動します。サブエージェントの手順について説明します。

エージェントはアクションを実行するときに、推論ループで結果を確認し、ユーザーに応答する前に適切な情報が含まれていることを確認します。エージェントは、会話に関する既存の情報にアクション出力を追加します。次に、別のアクションを実行するか、ユーザーにさらに質問するか、最終応答を送信するかを決定します。このプロセスは最大 7 個の推論ループを続行します。

ステップ 4: エージェントが最終応答検証を実行する (Agentforce サービスエージェントのみ)

Agentforce サービスエージェントは応答を送信する前に、応答がデータソースに基づいているかどうか、サブエージェントの範囲と手順に準拠しているかどうか、幻覚、未検証の情報、または潜在的なプロンプトインジェクションリスクが含まれていないかどうかを確認します。提案された応答がこの検証に失敗した場合、エージェントは新しい応答を生成します。

メモ エージェントは応答を受信すると会話で LLM 応答をストリーミングします。応答検証がエージェントの最終応答に適用されます。応答のストリーミングが開始された後に提案された応答がこの検証に失敗した場合、応答が削除され、新しい応答が生成されます。

エージェントが検証に合格する応答を生成できない場合、質問や要求に対応できないことをユーザーに通知します。

ステップ 5: エージェントがユーザーに応答を送信する

エージェントは、推論ループを完了すると、ユーザーにメッセージを送信します。ユーザーはフォローアップの質問をしたり、件名を変更したりして会話を続行でき、エージェントが適切に応答します。バックグラウンドでは、ユーザーの応答によってジャーニーが再開されますが、ユーザーにとっては会話が順番に行われているように見えます。

通話処理の推奨通話フロー

推奨される通話フローでは、音声通話レコードの数を最小限に抑え、関連レコードを接続します。可能な場合は、このフローを使用して通話のさまざまなレッグを処理します。

次の図は、通話フローのこれらの手順を示しています。

  1. まず、テレフォニーシステムが着信電話を受信します。
  2. 設定されている場合、テレフォニーシステムは初期音声通話レコード (VC1) を作成します。
    ヒント Salesforce で音声通話レコードを作成するには、VoiceCalls Telephony Integration API を使用します。
  3. 設定されている場合、テレフォニーシステムは指定された通信プロトコル (PSTN または SIP) を使用して通話をエージェントに転送します。
    • PSTN で転送が行われる場合:

      • Salesforce によってエージェント音声通話レコード (VC2) が作成されます。

      • Agentforce Voice で [関連通話を接続] オプションが有効になっている場合、Salesforce は VC1 レコードと VC2 レコードを自動的に接続します。このオプションが無効になっている場合、音声通話レコードは接続されません。

    • SIP で転送が行われる場合:

      • Salesforce によってエージェント音声通話レコード (VC2) が作成されます。

      • VC1 音声通話レコードの ID が UUI ヘッダーの callid パラメータに渡されると、Salesforce は自動的に VC1 レコードと VC2 レコードを接続します。パラメーターが指定されていない場合、音声通話レコードは接続されません。

  4. 顧客が電話を切ると、VC1 および VC2 コールは終了します。

  5. 通話がエージェントから人間のサービス担当者にエスカレーションされると、VC2 通話が終了し、VC1 通話を使用するテレフォニープロバイダーに通話制御が返されます。コールが完了すると、VC1 コールは終了します。

    1. データ型: レコード。[複数の値を許可 (コレクション)] を選択します。

    3. Availability Outside the Flow (フロー外の可用性): 出力で使用可能
  4. 次のプロパティを使用して recordId リソースを作成します。
    1. データ型: Text
    2. フロー外部での可用性: 入力で使用可能
  5. 次のプロパティを使用して menuRecordId リソースを作成します。
    1. データ型: Text
    2. Availability Outside the Flow (フロー外の可用性): 出力で使用可能
  6. 次のプロパティを使用して menuURL リソースを作成します。
    1. データ型: Text
    2. Availability Outside the Flow (フロー外の可用性): 出力で使用可能
  7. [開始] 要素の後に [] をクリックし、次のプロパティを持つ [レコードを取得] 要素を追加します。
    1. 表示ラベル: Get Menu Details (メニューの詳細を取得)
    2. Get Records of This Object (このオブジェクトのレコードを取得): Salesforce Object データソースを選択します。[オブジェクト] ドロップダウンから、作成したメニューオブジェクトを選択します。
    3. Filter Product Menu Records (商品メニューレコードの絞り込み): [なし – すべてのメニューレコードを取得] 条件要件を選択します。
    4. 保存するレコード数: すべてのレコード
    5. How to Store Record Data (レコードデータの保存方法): 項目を選択して変数を割り当てます (詳細)。
    6. [商品メニューレコードを保存する変数]: 作成した menuList リソースを選択します。
    7. 変数に保存するメニュー項目の選択: Name、ImageMimeType__c、Menu__c、MenuURL__c、DescriptionText__c
  8. フローを保存して有効化します。

エージェントユーザーに「フローを実行」権限があることを確認します。

カスタムエージェントアクションの作成

[メニューの詳細を取得] フローを参照アクションとして使用するカスタムエージェントアクションを作成します。

  1. 参照アクション種別: フロー
  2. 参照アクション: メニューの詳細を取得
  3. エージェントアクションの手順: メニューから詳細を検索して取得します。各メニューの名前、画像、MIME タイプ、URL を取得します。このアクションは、ユーザーがメニューの表示を要求したときに使用します。
  4. 読み込み中の詳細: メニューを取得
  5. recordId input instructions (recordId 入力手順): メニュー名を含む Salesforce レコードの単一 ID。
  6. menuList 出力手順: メニュー URL のリスト。[会話に表示] を選択します。
  7. menuURL output instructions: メニューの URL。[会話に表示] を選択します。
  8. menuRecordId 出力手順: Salesforce レコードの 1 つの ID とメニュー名。[会話に表示] を選択します。

カスタムサブエージェントの作成

[メニューの詳細を取得] アクションを含むカスタムサブエージェントを作成します。

  1. Agentforce Builder で Agentforce サービスエージェントを開きます。
  2. 次のプロパティを使用してカスタムサブエージェントを作成します。
    1. 分類の説明: このサブエージェントは、メニュー情報に関する顧客の要求を処理します。
    2. 範囲: ジョブは、使用可能なメニューのリストを提供し、名前、画像、URL など、選択したメニューの詳細を表示することのみです。範囲外の ToDo をユーザーから要求された場合、支援できず、メニュー情報のみを提供できることを に指示する必要があります。
    3. 手順:
      Get_Menu_Details アクションを使用して、特定のメニューのメニューの詳細を取得します。
      ユーザーが「メニューをください」と言ったら、常に使用可能なメニューのリストを提供します。
    4. [メニューの詳細を取得] エージェントアクションをサブエージェントに含めます。

エージェントをテストするには、有効化してから、接続済みチャネルでチャットします。
