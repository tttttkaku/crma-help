Einstein Trust Layer サービスのサポート

Agentforce サービスエージェントは、次の Trust Layer サービスをサポートしています。

サービス 説明
Zero Data Retention Policy (ゼロデータ保持ポリシー)

データはサードパーティ LLM によって保持されません。OpenAI などのすべての外部モデルプロバイダーと提携して、ゼロデータ保持ポリシーを適用します。

  • サードパーティ LLM による LLM モデルのトレーニングや製品の改善にデータは使用されません。
  • サードパーティ LLM によってデータは保持されません。
  • サードパーティプロバイダーのユーザーは、LLM に送信されたデータを参照しません。
安全なデータ取得を使用した動的グラウンディング
  • Salesforce レコードの関連情報がプロンプトとマージされ、コンテキストが提供されます。
  • プロンプトを実行するユーザーの権限に基づいて、プロンプトをグラウンディングするための Salesforce データの安全なデータ取得を行います。
  • 安全なデータ取得では、CRM インスタンスまたは Data 360 からグラウンディングデータをマージするときに、ユーザー権限と項目レベルセキュリティに関するすべての標準の Salesforce ロールベースの制御が保持されます。
プロンプトの防御 (システムポリシーとプロンプトの挿入検出)
  • システムポリシーは、幻覚を制限し、LLM が意図しない出力や有害な出力を行う可能性を減らすのに役立ちます。
  • システムポリシーは、生成 AI の機能と使用事例によって異なります。
有害検出 潜在的な有害な LLM 応答が検出され、フラグが付けられます。
監査とフィードバック
  • プロンプト、応答、Trust シグナルが記録され、Data 360 に保存されます。
  • フィードバックは、プロンプトテンプレートの改善に使用できます。
  • 分析用の事前作成済みレポートとダッシュボードを提供します。

Einstein Trust Layer を介したデータ マスキングは、エージェントのパフォーマンスと精度を高めるために無効になっています。組織で有効になっており、サービスエージェントで使用可能な Einstein Trust Layer サービスについては、システム管理者にお問い合わせください。

データサービス バッチデータパイプライン 使用量は、すべてのコネクタの Data 360 データストリームで処理されるバッチデータの量に基づいて計算されます。  
データサービス データクエリ

使用量は、処理されたレコードの数に基づいて計算されます。

処理されるレコード数は、クエリの構造のほか、クエリ対象オブジェクトのレコード総数などの他の関連要素によって異なります。

  
データサービス 処理される非構造化データ

使用量は、AI によるコンテンツの処理と抽出を使用せずに処理される非構造化データの量に基づいて計算されます。たとえば、検索インデックスでそれぞれ 1 MB の PDF ドキュメント 100 件を処理する場合、使用量は 100 MB として計算されます。検索インデックスでそれぞれ平均 100 MB の 5 つのオーディオ/ビデオ ファイルが処理される場合、使用量は 500 MB として計算されます。

Data 360 では、埋め込みモデルを使用して非構造化データをチャンク化してベクトル化できます。使用量は、これらの両方の活動で 1 回のみ計算されます。たとえば、100 MB の PDF ドキュメントが 1 つにチャンクされてベクトル化されている場合、使用量は 200 MB ではなく 100 MB として計算されます。

データモデルオブジェクト (DMO) をデータソースとして使用する検索インデックスを作成し、DMO からテキストデータ型項目を選択すると、それらの項目のすべての文字列にインデックスが作成され、処理されたすべてのバイトの合計が [非構造化データ処理済み] として報告されます。

  
データストレージ 割り当てを超えるストレージ 使用量は、割り当てられた量を超えて使用されたストレージ量に基づいて計算されます。 ストレージとは、Data 360 に保存されているデータ量のことです。Salesforce Lightning Platformに保存されているデータなど、Data 360以外で使用されるストレージは、この制限に含まれません。Agentforce サービスエージェント向け Data 360 の会話に取り込んだデータは、ストレージ割り当てに含まれます。割り当てより多くのデータを使用すると、使用量が課金されます。

サービスエージェントの制限

  • 顧客の受信メッセージがメッセージングチャネルの文字制限を超えた場合、メッセージは配信されず、応答も生成されません。文字制限はメッセージングチャネルごとに異なります。
    • Facebook では、最大 2,000 文字を使用できます。
    • LINE では、最大 5,000 文字を使用できます。
    • SMS では最大 912 文字を使用できますが、メッセージに特殊文字が含まれている場合、この制限は 396 文字に減少します。
    • WhatsApp では、最大 4,096 文字を使用できます。
    • Apple Messages for Business では、最大 50,000 文字を使用できます。
  • Agenforce サービスエージェントセッションは、会話の開始から 24 時間後、2 時間無操作状態になってから、またはユーザが明示的に会話を終了したときに終了します。詳細については、「Agentforce および生成 AI の使用状況と請求」を参照してください。

ASA および Agentforce Builder に関する考慮事項

  • 現在、Agentforce サービスエージェントは次の標準サブエージェントをサポートしていません。
    • 一般的な CRM
    • 単一レコード概要
  • 現在、Agentforce サービスエージェントは次の標準アクションをサポートしていません。
    • 名前でオブジェクトを識別
    • 名前でレコードを識別
    • レコードを照会
    • 集計を使用したレコードのクエリ
    • レコードの要約
    • メールのドラフト作成または修正
    • レコード項目の更新
    • ユーザー入力からの項目と値の抽出
  • Agentforce Builder のプレビュー会話では、エージェントのメッセージがプレーンテキストで表示されます。ビルダープレビューのメッセージ形式は、メッセージングチャネル環境と同じとは限りません。エージェントをメッセージングチャネルに追加する前に、テストチャネルでエージェントとチャットしてください。

その他の考慮事項

  • エージェントが無効化され、有効な拡張チャットリリースに接続されている場合、チャットウィンドウは表示されますが、エージェントは会話に参加しません。

電子メールでの Agentforce サービスエージェントに関する考慮事項

一部の機能は、メール上の Agentforce サービスエージェントではサポートされていません。このツールに関する考慮事項と制限事項を確認してください。

  • サービスエージェントは、メールの件名と本文のテキストのみを処理して応答し、画像や添付ファイルには応答しません。エージェントがメールの件名を応答のコンテキストとして使用するには、メール接続が確立されている必要があります。
  • 会話に介入する場合は、AI エージェントから自分自身にケースを再割り当てします。
  • 自動ケースユーザーは、システムユーザーまたは「アプリケーションのカスタマイズ」権限を持つユーザーとして設定する必要があります。
  • サービスエージェントが電子メールチャネルを使用している場合、MessagingSession レコードは使用できません。
  • Agentforce は、会話の終了時にケースを自動的にクローズしません。選択した条件に基づいて古いケースをクローズするスケジュール済みフローを作成できます。
  • 署名を元のメッセージの見積の前または後のどちらに表示するかを制御する組織設定「メールスレッドの前にユーザー署名を配置」は、[メールの設定] ページで定義されたユーザー署名にのみ適用されます。Agentforce サービスエージェントをメールに設定したときに作成した署名には適用されません。
  • サービスエージェントがケース割り当てルールを使用するには、エージェントのユーザーレコードに「ケースの参照」権限を付与する必要があります。また、サービスエージェントがケースを更新するには、エージェントのユーザーレコードに「ケースの参照」権限と「ケースの更新」権限の両方を付与する必要があります。最小権限の原則に留意し、サービスエージェントが職務を行う必要がない権限を割り当てないでください。
  • ランタイムエラーの場合、エラーの詳細を含むケースコメントが作成され、ケースは組織のデフォルトのケース所有者に再割り当てされます。
  • Welcome および Error システム メッセージは、メールで Agentforce サービスエージェントによって使用されません。
  • サービスメール接続が有効になっていない従来の Agentforce Builder で構築されたエージェントの場合、すべてのメールで新しいセッションが作成されます。エージェントアクションによって設定されたコンテキスト変数は、セッション間で管理されません。
  • サービスエージェントが送信するメール応答は非同期であり、応答時間は異なる場合があります。
  • サービスエージェントが処理する受信メールは、Agentforce for Service on Email の 1 日のトランザクション制限 (デフォルトでは 5,000) に含まれます。制限の引き上げを要求するには、本番でトランザクション制限まで正常に使用された一貫した履歴があることを確認し、Salesforce カスタマーサポートにお問い合わせください。
  • メール設定で [全員に返信] を選択した場合、返信の受信者は [宛先] 項目と [CC] 項目の間で 20 人に制限されます。
  • 1 つの受信メールが複数のルーティングアドレスに送信され、スレッドのケースがまだ存在しない場合、ルーティングアドレスごとにケースが作成されます。サービスエージェントは 1 つのケースに対応し、他のケースにコメントを追加して、実際の応答が含まれるケースを示します。
  • 同じケースで複数の受信メールが連続して受信された場合、サービスエージェントは各メールに個別に返信できない場合があります。代わりに、エージェントは最新のメールに 1 回の返信ですべてのメールメッセージに返信できます。
  • Agentforce はエンドユーザの言語で応答を試み、エンドユーザの言語がサポートされていない場合は英語に戻ります。
  • Salesforce for Outlook のメール-to-ケースルーティングアドレスはサポートされていません。
  • 自動レスポンス ループを防止するために、Agentforce for Service on Email は、ヘッダーに自動レスポンスの一般的な表示が含まれる受信メール (不在通知など) には応答しません。推奨転送設定を確認し、受信メールに自動レスポンスヘッダーが含まれていないことを確認します。

Agentforce Builder での拡張チャット v2 へのサービスエージェントの接続

新しい Agentforce Builder でサービスエージェントを拡張チャット v2 に接続するには、拡張チャット v2 接続を追加します。Agentforce Builder によってチャネルとリリースが作成されます。

  1. アプリケーションランチャーから「Agent」と入力し、Agentforce Studioアプリケーションを選択します。[エージェント] タブで、エージェントの名前をクリックします。
  2. [エクスプローラー] パネルの [接続] で、[接続を追加] をクリックします。[接続を追加] ウィンドウで、[拡張チャット v2] を選択し、[エージェントに追加] をクリックします。エージェントのバージョンを有効化して確定してください。
  3. [接続] から、[拡張チャット v2] を展開し、[ルーティング] をクリックします。
  4. 人間のサービス担当者へのエスカレーションを有効にするには、エージェントのエスカレーションフローとエスカレーションメッセージを指定します。
  5. [拡張チャットチャネル] セクションで、[新規チャネル] をクリックします。
  6. [新規チャネル] ウィンドウで、次の項目値を指定します。
    • 名前: チャネルの名前
    • Developer Name (開発者名): Developer name は一意で、80 文字以下にする必要があります。この項目はチャネル名に基づいて自動的に入力されますが、選択すれば編集できます。
    • ドメイン: リリースをホストする Web サイト。
    • 代替キュー: 対応可能なエージェントがいない場合や、エージェントが接続できない場合に転送先のキューを選択します。キューでメッセージングセッションオブジェクトが選択されている必要があります。
  7. 契約条件を確認して同意し、[チャネルを作成] をクリックします。契約条件は、組織で初めてチャットチャネルを作成するときにのみ表示されます。
  8. これで、拡張チャット v2 接続のメッセージングチャネルとリリースが作成されます。このプロセスの完了には最大 10 分かかります。
  9. 新しいチャネルを表示するには、[キャンバス] ビューに移動して、拡張チャット v2 接続ページにリストされている新しいチャネルを見つけます。新しいチャネルが表示されない場合は、ページを更新します。
  10. チャネルセクションで、チャネル名をクリックしてチャネルの設定ページを開きます。リリース名をクリックして組み込みサービスリリースページに移動し、リリース設定を表示および編集します。
  11. [組み込みサービスリリース設定] ページで、[拡張 Web チャットをテスト] をクリックして、ブランド設定と設定をプレビューおよび確認します。
  12. 準備ができたら、サイトを公開します。
  13. 拡張チャット v2 を外部 Web サイトまたは Salesforce サイトに追加します。

従来のビルダーでのサービスエージェントへのメッセージの直接転送

  1. 拡張チャット v1 メッセージングチャネルを作成します。[チャネルルーティング] ウィンドウで、次の項目値を入力します。
    • ルーティング タイプ：Agentforce サービスエージェント
    • Agentforce サービスエージェント: エージェントの名前を選択します。エージェント名が表示されない場合は、エージェントを有効化してもう一度お試しください。
    • 代替キュー: 対応可能なエージェントがいない場合に転送先のメッセージングキューを選択します。
  2. 作成したリリースの [組み込みサービスリリース設定] ページで、[Switch to v2] をクリックします。
  3. [Switch & Publish (切り替え & 公開)] をクリックします。
  4. [組み込みサービスリリース設定] ページで、[拡張 Web チャットをテスト] をクリックして、ブランド設定と設定をプレビューおよび確認します。
  5. 拡張チャット v2 に接続されているエージェントは、エスカレーションサブエージェントと送信オムニチャネルフローを使用して会話を転送します。エージェントがエスカレーションをサポートできるようにアウトバウンドルーティングを設定します。
  6. 準備ができたら、サイトを公開します。
  7. 拡張チャット v2 を外部 Web サイトまたは Salesforce サイトに追加します。

オムニチャネルフローを使用してメッセージをサービスエージェントに転送します。

  1. メッセージをエージェントに転送する受信オムニチャネルフローを作成します。
  2. 受信オムニチャネルフローの [作業を転送] アクションで、次の項目値を入力します。
    • レコード ID: ステップ 1 でオムニチャネルフローに値を保存するために作成したレコード ID 変数。
    • サービスチャネル: メッセージング
    • ［ルート先］：Agentforce サービスエージェント種別を選択し、エージェントの名前を選択します。エージェント種別とエージェント名が表示されない場合は、エージェントを有効化して Flow Builder を更新し、もう一度お試しください。
    • メッセージングキュー。受信オムニチャネルフローで会話をエージェントに転送できない場合、このキューに会話が送信されます。メッセージングセッションオブジェクトをサポートするように設定されているメッセージングキューを選択します。
  3. 拡張チャット v1 メッセージングチャネルを作成します。受信フローをチャネルに追加し、チャネルを有効化します。エージェントは複数の受信チャネルに接続できますが、受信チャネルは 1 つのエージェントにのみ接続できます。
  4. Agentforce Builder でエージェントを開きます。[接続] パネルで、受信オムニチャネルフローが拡張チャット v2 接続の [受信ルーティング] セクションに表示されていることを確認します。フローが表示されない場合は、フローを有効化してビルダーを更新します。
    ヒント 拡張チャット v2 接続が表示されない場合は、[接続] タブで新しい [接続] パネル環境を有効にします。
  5. 作成したリリースの [組み込みサービスリリース設定] ページで、[Switch to v2] をクリックします。
  6. [Switch & Publish (切り替え & 公開)] をクリックします。
  7. [組み込みサービスリリース設定] ページで、[拡張 Web チャットをテスト] をクリックして、ブランド設定と設定をプレビューおよび確認します。
  8. 拡張チャット v2 に接続されているエージェントは、エスカレーションサブエージェントと送信オムニチャネルフローを使用して会話を転送します。エージェントがエスカレーションをサポートできるようにアウトバウンドルーティングを設定します。
  9. 準備ができたら、サイトを公開します。
  10. 拡張チャット v2 を外部 Web サイトまたは Salesforce サイトに追加します。

オムニフローの作成

[作業を転送] アクションを使用して、ケースをエージェントコンテキストユーザーに転送するようにオムニチャネルフローを設定します。これは、ケースをエージェントに接続する受信フローです。エージェントが回答できない場合にケースをサービス担当者にエスカレーションする追加の送信フローを作成できます。

  1. ケースとルーティング設定のサービスチャネルを含む、オムニチャネルの設定を完了します。
  2. 受信オムニチャネルフローを作成するときに、ケースをエージェントに転送するオプションを選択し、[エージェントユーザー] を選択します。正しい値を判断するには、Agentforce Agents 設定ページからエージェントを選択し、[エージェントユーザー] 項目を確認します。
  3. [作業を転送] アクションで [必須エージェント] を選択し、recordId 入力パラメーターを作成します。フローに input_record 変数がある場合、そのオブジェクト種別がケースであることを確認します。ケースでない場合、フローは機能しません。同じフローを複数のチャネルで使用する場合は、recordId 入力変数のみを含めて、input_record オブジェクト種別およびチャネルとの不一致を避けることをお勧めします。

ルーティングアドレスへのフローのリンク

フローを作成したら、ルーティングアドレスにリンクします。

  1. [設定] から、[クイック検索] ボックスに「メール-to-ケース」と入力し、[メール-to-ケース] を選択します。
  2. [ルーティングアドレス] セクションで、先ほど表示したルーティングアドレスの横にある [編集] をクリックします。
  3. [フローの設定]で、Agentforceサービスエージェントへのルーティングを含むオムニチャネルフローを選択し、フローを使用できない場合はケースを受信する代替キューを選択します。注意: スキルベースのルーティングとエージェントへの直接転送は、[設定] のオムニチャネル設定ページで有効にする必要があります。
  4. 変更内容を保存します。

オムニチャネルフローの代わりに、ルーティングアドレスの [ケース所有者] を [エージェント設定] の [エージェントの詳細] タブにリストされているエージェントのコンテキストユーザーに設定するか、またはケース割り当てルールを作成して同様の操作を実行できます。これはすぐに使用できる方法ですが、フローと同じレベルのきめ細かな制御は提供されません。

ケースの保存操作中にケース所有者を割り当てる必要があります。Agentforce への割り当てが遅延または非同期の場合、受信メールが処理されるときにケースが Agentforce によって所有される必要があるため、顧客が再度メールを送信するまで、システムから自動応答が送信されません。

エスカレーションサブエージェントの設定

エスカレーションサブエージェントを使用して、顧客がストレスを感じているときに作業をサービス担当者に転送します。これは、設定プロセスで作成する 2 番目のフローです。

  • Agentforce サービスエージェントは、エンドユーザーがインタラクションに不満を持っているときに通知し、エスカレーションサブエージェントを使用して受信メールをサービス担当者に転送できます。エスカレーションサブエージェントとその設定方法について説明します。
  • ケースがエスカレーションされると、送信フローがトリガーされ、ケース所有者がAIサービスエージェントからサービス担当者に変更されます。
  • エスカレーションサブエージェントを削除した場合、またはエスカレーション用のルーティングフローを設定しない場合、エスカレーションフローは機能しません。
  • メールに接続されたAgentforceサービスエージェントは、エージェントに定義されたエスカレーションメッセージを使用しません。メールに接続された Agentforce サービスエージェントが会話をエスカレーションしても、応答は送信されず、エージェントはこれ以上自動メールを送信しません。
  • 同じフローを使用して複数の種別のレコードを転送する場合、フローで input_record 変数を使用しないでください。この変数は 1 つの種別のレコードにのみリンクする必要があり、フローは他の種別のレコードでは機能しません。

  • カスタマイズされたエスカレーション環境を反映するようにエスカレーションメッセージを更新します。たとえば、「対応可能なサービス担当者がいるかどうかを確認します。
  • 転送が完了していないときにエージェントを誘導するようにエスカレーションサブエージェントをカスタマイズします。たとえば、[ケース管理] サブエージェントで [拡張データでケースを作成] アクションを使用してケースを作成するようにエージェントに指示する命令を追加します。拡張 Web チャットに接続されている従業員エージェントは、エスカレーションが完了していない場合、ケースの作成をサポートしません。

Lightning Experience、Salesforce モバイルアプリケーション、Slack などの従業員チャネルに接続されているエージェントは、デフォルトでエンドユーザーのコンテキストに基づいてサブエージェントとアクションへのアクセスを制限します。拡張メッセージングチャネルや拡張チャットなどの顧客チャネルに接続されている Agentforce サービスエージェントは、安全なアクセスを確保するために追加の設定が必要です。エージェントを設定するときには、使用事例のセキュリティ要件と識別要件を熟考し、顧客に代わって自律的に完了できるタスクを完了するために必要なアクションとアクセス権のみをエージェントに付与することが重要です。機密アクションの場合、顧客検証をアクションのフローに直接組み込むことをお勧めします。

エージェントが実行できるアクションを完全に制御できるため、ニーズに合わせてカスタマーエクスペリエンスをカスタマイズできます。セキュリティを強化し、定義された境界内でエージェントが動作するようにするには、次のようにすることをお勧めします。

  • 顧客チャネルに接続するエージェントに、作業に必要な最小限のユーザー権限を割り当てる。
  • 機密性の高いアクションのフローに ID 確認とアクセス制御を直接組み込む。

リスク許容度とセキュリティ基準は会社ごとに異なり、ID 検証をエージェントの実装に組み込む方法は 1 つではありません。たとえば、会社のポリシーによっては、Agentforce サービスエージェントが会話形式で注文 ID を受け入れ、それ以降に正式な ID 検証を行うことなく注文状況を提供することを許可できます。一方、機密性の高い材料や規制対象の材料を配送する必要がある場合は、顧客の代わりに注文情報を検索する前に顧客が自身を認証することが必要となる可能性があります。エージェントを設定する前に、会社のリスク許容度とセキュリティ標準を考慮してください。エージェントが意図した範囲外でデータを共有できないようにするには、認証と承認を念頭に置いて設定します。

Agentforce のアクションおよびセキュリティ

エージェントが顧客チャネルに接続されている場合は、エージェントアクションを公開または非公開と考えてください。Salesforce にはアクションを公開または非公開として指定する特定の設定はありませんが、このフレームワークは会社のセキュリティ標準の概念化と実装に役立ちます。

公開アクション
公開アクションは、認証なしで、ID に関係なく、誰にでも代わって会社が実行することに抵抗のないアクションです。たとえば、通常、[ナレッジを使用して質問に回答] アクションは、特に返品ポリシーなどの公開情報に基づいている場合、公開アクションとみなされます。要求者の ID をしっかりと確認しなくても問題がない場合は、注文の検索を公開アクションにすることもできます。このような場合、注文 ID やメールアドレスなど、特定の注文を識別するために必要な情報を会話形式で渡すことができます。
非公開アクション
非公開アクションでは、会社のコンフォートレベルに応じて、認証やメッセージングセッションでの識別情報の共有などを通じて要求者の ID を確認する必要があります。通常、サポート契約での個人の予定情報の更新、購入、サービスの要求は非公開アクションの例であり、公開することはお勧めしません。Agentforce サービスエージェントが非公開アクションを完了するには、アクションをトリガーするユーザーがそのアクションへのアクセスを承認されており、そのユーザーの ID を確実に確認する必要があります。

非公開アクションのセキュアな実装に関するガイドライン

顧客チャネルに接続されているエージェントのセキュリティを強化するには、エージェントが代理で非公開アクションを実行する前に、やりとりするユーザーの ID を確認するように要求することをお勧めします。

機密性が特に高いアクションの場合、会話の範囲外で認証プロセスを処理する 2 要素認証などの技術を使用して ID を確認することをお勧めします。チャット内で識別情報を共有することは安全な検証方法ではありませんが、選択する方法はリスク許容度とセキュリティ標準によって異なります。

顧客の ID が確認されたら、関連付けられた MessagingSession レコードにその識別情報を保存できます。非公開アクションを完了する前に、エージェントは MessagingSession レコードを参照して、やりとりするユーザーの ID と権限を確認できます。このプロセスは、非公開アクションのフローに直接組み込むことができます。

顧客チャネルに接続し、非公開アクションを実行できるエージェントを作成する場合、リスクを軽減する方法を考慮することが重要です。ユースケースは多様ですが、次のガイドラインに留意してください。

ガイドライン 詳細
最小権限の原則に従う。
  • アクセス制限: エージェントに必要な最小限の権限のみを付与します。
  • 定期的な権限の確認: 権限が適切であることを確認するには、定期的な確認を実施します。
堅牢なアクセス制御を実装する。
  • 強力な認証を適用: 2要素認証などの強力な認証メカニズムを実装して、エージェントとやりとりするユーザーのIDを検証します。
  • アクセス ログの監視:疑わしいアクティビティを特定するには、アクセス ログを定期的に確認します。
セキュアなアクションを設計する。
  • 範囲の制限: 特定の境界内で動作するアクションを設計し、機密データへの不正アクセスを防止します。ユーザーの ID と権限の確認を各非公開アクションに直接組み込みます。
  • 入力の検証: 悪意のある入力や潜在的なセキュリティの脆弱性を防ぐために、入力の検証を実装します。
  • エラー処理: 情報の開示とシステムの不安定さを回避するには、堅牢なエラー処理を実装します。
重要

組織の共有設定 (OWD) によって、所有していないレコードへのユーザーのアクセス権が決まります。認証済みユーザーを使用するエージェントセッションでは、セッションはエンドユーザーのコンテキストで実行され、OWD はユーザーが外部か内部かによって異なります。認証されていないユーザを含むエージェント セッションでは、セッションはエージェント ユーザのコンテキストで実行され、内部ユーザの OWD が適用されます。

OWD、エージェントユーザーの権限、およびエージェント設定を慎重に確認し、エンドユーザーとビジネスに適したレコードアクセス権があることを確認します。

  • エージェントのユーザーレコードを使用するすべてのエージェントで、検索条件と変数を使用して、サブエージェントおよびアクションレベルでレコードアクセスを制限することをお勧めします。この戦略により、OWD に関係なく機密データが保護されます。
  • 内部ユーザーの OWD を制限して、すべての内部ユーザーのレコードアクセスを制限できます。その後、必要に応じて Einstein エージェントユーザーを除外して、アクセス権を選択的に付与する共有ルールを作成できます。

セキュアな Agentforce サービスエージェントの実装例

セキュアな Agentforce サービスエージェントの実装の詳細は、エージェントがリリースされる場所や、関連するユーザー認証ポリシーによって異なります。基本パターンを理解するために、例を見てみましょう。

必要なエディション

使用可能なインターフェース: Lightning Experience
使用可能なエディション: Enterprise Edition、Performance Edition、Unlimited Edition、および Developer Edition。必要なアドオンライセンスはエージェント種別によって異なります。

Agentforce サービスエージェントがエクスペリエンスサイトにリリースされる場合、エージェントとやり取りするユーザーの再認証が必要になる場合があります。そのような場合、セッション内の認証を呼び出すことができます。

パラメーター化された URL を会話内で提供してユーザーを認証できます。パラメーター化された URL は、Experience Cloud ポータルのセキュアなメソッドを参照する必要があります。パラメーター化された URL を送信する前に外部認証の準備として、次のカスタム項目を使用して MessagingSession オブジェクトが設定されます。

項目 初期値 定義
AuthSessionId NULL この MessagingSession に現在リンクされている AuthSession があるかを識別します。これは、メッセージングセッションが認証されているかどうかを示します。
AuthRequestTime DateTime.Now() 認証が要求されたときに保存されます。これにより、指示された期間外で MessagingSession に ID が割り当てられないように制限し、外部認証が許可される期間を制御できます。
AccountId NULL 認証されたセッションにリンクされた取引先が Experience Cloud ポータルで認証された取引先責任者に相対的に割り当てられるようにします。
ContactId NULL 認証されたセッションにリンクされた取引先責任者が Experience Cloud ポータルで認証された取引先責任者に相対的に割り当てられるようにします。

パラメーター化された URL を処理する Apex メソッドでは、MessagingSession.SessionKey 項目を使用できます。このグローバル一意識別子 (GUID) は、Status = “Active” である MessagingSession レコードにおいて一意です。このメソッドは、次のクエリを使用して関連する MessagingSession レコードを検索します。

SELECT Id, Conversation.ConversationIdentifier, Status, FROM MessagingSession 
WHERE SessionKey = '1db8a0ab-aae4-4ed9-b6d5-3e7fe85b9574' AND Status = 'Active' 
AND AuthSessionId__c = NULL

このクエリでレコードが返された場合、そのレコードはユーザーが認証された Agentforce サービスエージェントとの会話を表します。その後、返されたレコードを更新して、Experience Cloud ポータルの現在の AuthSession との関係を表すことができます。たとえば、MessagingSession が ms として定義されているとします。

ms.AuthSessionId__c = SessionManagment.GetCurrentSession().get('SessionId');
User authUser = [SELECT Id, ContactId, AccountId from User WHERE Id = :UserInfo.getUserId()];
ms.AccountId__c = authUser.AccountId;
ms.ContactId__c = authUser.ContactId;
ms.commit();

これで、Agentforce サービスエージェントが非公開アクションを実行するときにユーザーの ID を確認するために必要な情報を取得できました。AuthSession の ID も含まれており、対応するポータルセッションの会話が終了した直後に解除できます。

この例では、ユーザーはポータルページに転送され、そこで認証されます。これにより、Agentforce セッションの MessagingSession レコードがユーザーの ID で更新されます。ただし、Agentforce セッションではイベントは生成されないため、認証が完了したら Agentforce で会話を続行するユーザーに依存します。

Agentforce アクションへのユーザー ID の追加

非公開アクションを安全に実行できるように顧客チャネルに接続するエージェントを設定する場合、会社の基準に従ってやりとりするユーザーの ID を確認してもらいます。

必要なエディション

使用可能なインターフェース: Lightning Experience
使用可能なエディション: Enterprise Edition、Performance Edition、Unlimited Edition、および Developer Edition。必要なアドオンライセンスはエージェント種別によって異なります。

Agentforce サービスエージェントは、複数のメッセージング設定でリリースできます。

  • 認証済みユーザーに制限されたエクスペリエンスサイトにリリースされた拡張チャットチャネル。
  • Salesforce の外部で独自の認証メカニズムを持つカスタムサイトまたはアプリケーションにリリースされた拡張チャットチャネル。
  • Apple Messages for Business などの拡張サードパーティメッセージングチャネル。

各設定で、エージェントが実行するアクションを完全に制御できます。定義したパラメーター内でエージェントが操作できるように、エージェントアクションの管理方法と制限方法を慎重に検討してください。会社のポリシーによっては、エージェントがすべてのアクションまたは非公開アクションを実行するときに true 認証を要求しないことがあります。

エクスペリエンスサイトユーザーの認証 (拡張チャット)

Agentforce サービスエージェントが認証済みユーザに制限されたエクスペリエンスサイトにリリースされると、各 Agentforce メッセージングセッションには、有効で認証済みの AuthSession が自動的に付属します。ユーザーの取引先 ID と取引先責任者 ID はわかっているため、MessagingSession レコードの各項目にこれらの値を割り当てるのは比較的簡単です。

各非公開アクションは、アクションを完了する前に、これらの値が割り当てられ、識別された AuthSession がまだ有効であることを確認するように設定する必要があります。

外部サイトまたはアプリケーションからのユーザーの認証 (拡張チャット)

Agentforce サービスエージェントを Salesforce の外部に独自の認証メカニズムを持つカスタムサイトまたはアプリケーションにリリースする場合は、Agentforce メッセージングセッションを MessagingSession レコードに対応付けます。

ユーザー検証機能を使用すると、カスタムサイトまたはアプリケーションでユーザー識別子を安全に渡すことができ、ユーザー識別子は MessagingEndUser レコードに保存されます。たとえば、メールアドレスを識別子として使用している場合、ユーザーの ID の確認として MessagingEndUser レコードのメールアドレスを解析するように非公開アクションを設定できます。

この認証管理方法では、認証済み AuthSession が自動的に追跡されないため、認証した後にすぐに無効にする方法はありません。認証は、トークンに埋め込まれた有効期限に達するまで有効です。会社の標準に従って有効期限を定義します。

サードパーティメッセージングチャネルでのユーザーの識別

Agentforce サービスエージェントを Apple Messages for Business などの拡張サードパーティメッセージングチャネルにリリースする場合は、Agentforce サービスエージェントが非公開アクションを実行するための認証をインタラクションのフローに組み込みます。

認証メソッド 詳細
チャネル識別子を使用してユーザーを認証する。

会社のポリシーに応じて、チャネル固有の識別子を認証に使用できます。この方法にはリスクがまったくないわけではありません。認証目的でチャネル固有の識別子を使用すると、認証がチャネルプロバイダーに委任されます。実装する前に認証要件を慎重に検討する必要があります。

認証をチャネルプロバイダーに委任する場合は、チャネルオブジェクトリンクを実装して、取引先責任者を関連するメッセージングセッションに自動的に関連付けます。次に、完了する前にこの情報を参照する非公開アクションを設定します。
サイドチャネルを介してユーザーを認証する。

認証にチャネル固有の識別子を使用できない場合は、サイドチャネルを介してユーザーを認証するように Agentforce サービスエージェントを設定します。チャネルプロバイダーの識別子に依存しなくなりますが、会話は引き続きそのプロバイダーによって保護されます。悪意のあるユーザーがそのチャネルでなりすましやその他の方法で他のユーザーの ID を装うことができる場合、サイドチャネルでセッションが認証された後に同様のことを行う可能性があります。

サイドチャネルを介したユーザーの認証は、既存の Web 認証メカニズムに認証を委任するという点でエクスペリエンスサイトユーザーの認証のバリエーションです。これを実装するには、必要な認証を実装するサイトにクエリパラメーターを介して MessagingSessionId を渡します。その後、そのサイトのサーバーがその MessagingSessionId の認証済み要求を受信すると、Salesforce API を使用して認証メカニズムから取得した識別子で MessagingSession レコードを更新するように設定する必要があります。
メッセージングコンポーネントを使用して認証する。 Apple Messages for Business などの拡張サードパーティメッセージングチャネルでは、Agentforce サービスエージェントは認証メッセージングコンポーネントをメッセージングエンドユーザー (MEU) に送信できます。このプロセスでは、MEU はデバイスで認証プロンプトを受信し、Facebook や Google などの標準認証プロバイダーを使用して認証を完了できます。また、カスタム認証プロバイダーを設定することもできます。

非公開アクションの範囲の制限

ユーザーの ID を確認したら、非公開アクションはセッション ID を使用して、関連付けられた取引先 ID と取引先責任者 ID に基づいて非公開アクションの範囲を適用できます。 セッション ID を使用すると、アクションが意図したとおりに制限されます。

たとえば、[Get Order By Order Number (注文番号で注文を取得)] アクションは、注文情報を検索する前に MessagingSession レコードから取引先責任者 ID を取得するように設定できます。

//Get Contact from Session
SELECT Id, contactId__c FROM MessagingSession 
WHERE sessionId =: SessionId

//Get orders based on Contact from Session
SELECT Id, Status FROM Order 
WHERE ContactId =: ms.contactId__c AND orderNumber =: orderNumber

他の非公開アクションも同様に設定して、Agentforce サービスエージェントが認証済みユーザーに独自のデータのみを提供するようにできます。

サービスエージェントテンプレートからのエージェントの作成

開始する前に、Einstein生成AIを設定し、Agentforceを有効にします。

  1. アプリケーションランチャーから、「Agent」と入力し、Agentforce Studioアプリケーションを選択します。
  2. [エージェント] タブで、[新規エージェント] をクリックします。
  3. Agentforce サービスエージェントテンプレートを選択します。[エージェントの詳細] で、このエージェントのエージェントユーザーレコードを選択または作成します。データに安全にアクセスしてアクションを実行するために、サービスエージェントはエージェントユーザー、またはエージェントが作業するために必要なすべての権限を持つ Salesforce インテグレーションユーザーとして動作します。「エージェントユーザー権限のベストプラクティス」を参照してください。
  4. エージェントの名前を入力し、[Let's Go] をクリックします。
  5. [設定(Settings)] セクションで、システム メッセージや言語設定など、会話でのエージェントの動作を決定する設定を定義します。
  6. [サブエージェント] セクションで、エージェントのサブエージェントとアクションを管理およびカスタマイズします。
  7. [データ] セクションで、データライブラリを選択します。[Answer Questions with Knowledge (ナレッジを使用して質問に回答)] アクションは、エージェントの回答をこのアクションでグラウンディングします。データライブラリを作成または管理するには、「データライブラリの設定」を参照してください。
  8. [プレビュー] をクリックしてエージェントをテストし、期待どおりに動作し、セキュリティ標準を満たしていることを確認します。実際のデータや組織を変更するリスクを冒すことなく、疑似データを使用してエージェントの動作をシミュレーションできます。トレースを使用してエージェントが実行したステップを詳しく調べ、任意のステップでのエージェントの動作を理解するために Agentforce に依頼します。詳細については、「Preview and Test in Agentforce Builder」を参照してください。
  9. エージェントをサービスチャネルに接続して、エージェントの会話を転送します。メッセージングチャネルへのエージェントのリリースの詳細については、「メッセージングへのエージェントの接続」を参照してください。
  10. ビルダーの外部でエージェントを使用する準備ができたら、[バージョンを確定] をクリックします。エージェントバージョンを有効化する前に確定する必要があります。コミットされたバージョンは編集できません。確定後も変更を続行するには、[新しいバージョン] をクリックして新しいバージョンを作成します。詳細は、「エージェントのバージョン設定と編集」を参照してください。
  11. 準備ができたら、エージェントを有効化します。

  10. ビルダーに戻り、サブエージェント、アクション、およびその他のエージェントアセットを使用してエージェントを設定します
  11. Agentforce Builder でエージェントをテストし、エージェントのパフォーマンスが期待どおりで、セキュリティ標準に準拠していることを確認します。
    サービスエージェントは、メッセージングチャネルでリリースされた場合と同じエージェントユーザーコンテキストで操作されるため、設計時テストでは、リリースされたときのサービスエージェントの動作が反映されます。
  12. サービスエージェントをチャネルに接続し、エージェントの会話を転送するようにエスカレーションサブエージェントを設定します。

検証サブエージェントのしくみ

未検証のユーザーがユーザー検証を要求するように設定したサブエージェントまたはアクションをトリガーすると、エージェントは検証サブエージェントを起動します。

サブエージェントには、2 つのフローベースのエージェントアクションが含まれます。最初のアクション [確認コードを使用してメールを送信] では、ユーザー名またはメールの入力をユーザーに求め、Salesforce ユーザーレコードと取引先責任者レコードと照合します。次に、5 分間有効なワンタイムパスコード (OTP) が記載されたメールが no-reply@salesforce.com から送信されます。次に、メールを確認してコードを入力するようにユーザーに促します。

ユーザーがコードを入力すると、2 番目のエージェントアクション [顧客を検証] がトリガーされます。このアクションは、ユーザーが指定したコードが有効な期間内に生成された確認コードと一致するかどうかを確認します。コードが一致すると、[検証済み] 出力が true に設定され、[顧客 ID] 出力に検証済みのユーザーまたは取引先責任者 ID が含まれます。 エージェントは確認メッセージを送信し、ユーザーの質問または要求の処理を再開します。

コードが一致しない場合、エージェントはユーザーにコードの再入力を促します。3 回失敗すると、エージェントはユーザーにユーザー名またはメールの入力を求めることで検証プロセスを再開します。

エージェントへの検証サブエージェントの追加

まず、検証標準サブエージェントを顧客チャネルに接続されたエージェントに追加します。

一部のエージェントテンプレートでは、エージェントに標準で検証サブエージェントが含まれています。テンプレートに当てはまる場合は、このステップをスキップできます。

  1. Agentforce エージェントの [設定] ページから、Agentforce Builder でエージェントを開きます。
  2. エージェントが有効な場合は、無効化します。
  3. サイドバーから、[サブエージェント] を選択します。
  4. [サブエージェント] パネルで、[新規] をクリックし、[アセットライブラリから追加] を選択します。
  5. [Customer Verification (顧客検証)] サブエージェントまたは [Service Customer Verification (サービス顧客検証)] サブエージェントを選択し、[完了] をクリックします。

[顧客を検証] の入力への [確認コードを含むメールを送信] の出力の割り当て

次に、シームレスに連携するように検証サブエージェントのアクションを設定します。

一部のエージェントテンプレートでは、[メール確認コードを送信] アクションの出力がすでに変数に対応付けられ、[顧客を検証] アクションの入力に割り当てられています。テンプレートに当てはまる場合は、このステップをスキップできます。

  1. [確認コードを使用してメールを送信] アクションの出力の値を保存します。
    1. [このサブエージェントのアクション] タブで、[Send Email with Verification Code (確認コードを含むメールを送信)] アクションを選択します。
    2. [Customer Type (顧客種別)] 出力の [Map to Variable (変数に対応付け)] ドロップダウンから、[New Custom Variable (新規カスタム変数)] を選択します。
    3. 変数の詳細を入力します。
    4. [API による値の設定を許可] 設定と [LLM による値の使用を許可] 設定は無効のままにします。
      検証やその他のセキュリティ機能に使用するすべての変数で、これらの設定を無効にしておくことをお勧めします。
    5. 変更内容を保存します。
    6. 顧客 ID と認証キーの出力に対してこのプロセスを繰り返します。
      [顧客 ID] の出力を [検証済み顧客 ID] システム変数に保存しないでください。代わりに、カスタム変数を作成します。[検証済み顧客 ID] は、検証プロセスが完了した後にのみ使用されることを目的としています。
  2. [顧客を検証] アクションの対応する入力に新しい変数を割り当てます。
    1. [このサブエージェント] のアクションのタブで、[顧客を検証] アクションを選択します。
    2. [顧客種別] 入力の [変数を割り当て] ドロップダウンから、[確認コードを使用してメールを送信] アクションから [顧客種別] 出力を保存するために作成した変数を選択します。
    3. 変更内容を保存します。
    4. [確認コードを使用してメールを送信] アクションからの対応する出力を保存するために作成した変数を使用して、顧客 ID と認証キーの入力に対してこのプロセスを繰り返します。

変数への [顧客アクションを検証] の出力の対応付け

[検証済み] および [顧客 ID] 出力の値を変数に保存します。これにより、検索条件で使用し、検証済みユーザーの代わりにエージェントが実行するアクションの入力としてのみ使用できます。

  1. [このサブエージェントのアクション] タブで、[顧客を検証] アクションを選択します。
  2. [検証済み] 出力の [変数にマッピング] ドロップダウンから、[新規カスタム変数] を選択します。
  3. 変数に「Is Verified」 (検証済み) という名前を付け、変数の詳細を入力します。
  4. [API による値の設定を許可] 設定と [LLM による値の使用を許可] 設定は無効のままにします。
    検証やその他のセキュリティ機能に使用するすべての変数で、これらの設定を無効にしておくことをお勧めします。
  5. 変更内容を保存します。
  6. [Customer ID (顧客 ID)] 出力の [Map to Variable (変数に対応付け)] ドロップダウンから、[Verified Customer ID (検証済み顧客 ID)] を選択します。
    一部のエージェントテンプレートでは、[検証済み顧客 ID] をシステム変数として標準で使用できます。テンプレートの検証済み顧客 ID 変数が存在しない場合は、カスタム変数として作成します。[API による値の設定を許可] 設定と [LLM による値の使用を許可] 設定は無効のままにします。
  7. 変更内容を保存します。

サブエージェントの検索条件の作成と適用

Is Verified 変数と Verified Customer ID 変数を使用して検索条件を作成し、非公開アクションを含むサブエージェントを検証済みユーザーのみが使用できるようにします。

  1. サイドバーから、[コンテキスト] を選択します。
  2. [コンテキスト] パネルから、[条件] タブを選択し、[新規] をクリックします。
  3. 検索条件の名前、API 参照名、説明を入力します。
  4. [アセットを使用する条件] で、この検索条件が適用されたサブエージェントまたはアクションをエージェントが使用するには、すべての条件を満たす必要があります。
  5. 次の条件を作成します。
    • 検証済み顧客 ID が Null と等しくない
    • 検証済み 次の文字列と一致する True
  6. 変更内容を保存します。
  7. 検索条件を使用するには、検証が必要なサブエージェントに適用します。[サブエージェント] パネルから、変更するサブエージェントの名前をクリックします。
  8. サブエージェントの詳細パネルで、[] をクリックします。
  9. 適用する検索条件を検索して選択し、変更を保存します。検索条件は、このエージェントのサブエージェントまたはアクションにのみ適用されます。

[このサブエージェントのアクション] タブから、非公開アクションに検索条件を追加することもできます。フィルタについての詳細は、「サブエージェントおよびアクションへのアクセスを制御するフィルタの作成」を参照してください。

非公開アクション入力への検証済み顧客 ID 変数の割り当て

セキュリティを強化するために、検証済みユーザーの代わりにエージェントが実行するアクションのみの入力として検証済み顧客 ID 変数を追加します。エージェントは、[検証済み顧客 ID] 変数が入力されている場合にのみアクションを実行できます。アクションのロジックで [検証済み顧客 ID] の値を使用することもできます。

  1. サイドバーから、[サブエージェント] を選択します。次に、変更するアクションが含まれるサブエージェントを選択します。
  2. [このサブエージェントのアクション] タブで、アクションを選択します。ID 入力で、[Assign a Variable] ドロップダウンから、[Verified Customer ID] 変数を選択します。
  3. 変更内容を保存します。

検証済みの顧客 ID を要求するアクションごとにこのプロセスを繰り返します。

変更のテスト

プレビュー会話とプレビュー条件を使用して、Agentforce Builder で変更を確認します。エージェントは、メッセージングチャネルでリリースされたときと同じエージェントユーザーコンテキストでプレビュー会話で操作します。

  1. 会話のプレビューパネルで、プレビュー条件を指定するためにクリックします。
  2. 特定のエンドユーザー ID を指定し、変更を保存します。
  3. 変更を適用するには、プレビュー会話を再開します。
  4. 顧客検証サブエージェントと連携するように設定したサブエージェントまたはアクションをトリガーすることが想定される会話を開始します。たとえば、エージェントに返金を依頼します。
  5. エージェントからメールアドレスの入力を求められたら、入力します。テストを完了するためにこのメールを確認する必要はありません。
  6. エージェントがメールを送信したら、プランキャンバスを確認して OTP をコピーします。次に、エージェントに送信します。

検証が成功した場合、エージェントは検証されたことを確認するメッセージを送信します。その後、トリガーした元のサブエージェントを引き続き実行します。

エージェントのパフォーマンスが期待どおりでない場合は、作成した変数と検索条件、およびそれらを適用したサブエージェントとアクションを確認します。エージェントが顧客検証サブエージェントを使用する状況を理解できるように、サブエージェントの指示を調整する必要がある場合があります。

結果に満足したら、エージェントを有効化します。

その他のカスタマイズ

検証サブエージェントを変更して、ビジネスの使用事例とセキュリティ要件を満たしていることを確認します。

デフォルトでは、検証サブエージェントはユーザー ID または顧客 ID とメールを使用します。ただし、いずれかのアクションに関連付けられた基礎となるフローを編集して、必要な ID や OTP の送信方法を変更できます。エージェントアクションを変更するには、同じフローに基づいてカスタムアクションを作成します。

検証サブエージェントにアクションを追加できます。検証に使用するアクションの範囲を制限して、各アクションがプロセスのモジュール化されたステップを完了できるようにします。出力が空のエージェントアクションは、プロセスが完了する前に出力の入力を試みるため、エラーが発生する可能性があります。
