テスト結果の使用

テストの実行が完了すると、テストスイートの全体的な総計値と各テストの評価スコアが表示されます。この結果を使用して、失敗した発言やスコアの低い発言を特定し、Agentforce Builder で手動で再テストします。サブエージェントとアクション内の手順を絞り込み、回答に満足するまで繰り返します。この結果は、ガイダンスの不明瞭さ、Knowledgeの欠如、設定の問題など、根本的な問題を明らかにするのに役立つ可能性があるため、繰り返し発生する障害には細心の注意を払ってください。結果を解釈するには、各評価がエージェントのパフォーマンスの測定にどのように役立つかを確認します。

デフォルトの評価のスコアは 1、合格、または 0、不合格です。

評価 テストの意義 推奨
回答評価

スコア 3 ～ 5 は、エージェントが一般的に目標を達成したことを示します。スコア 5 は、無関係なコンテンツを含まない、正確で完全、かつブランドに沿った回答を反映します。

スコア 3 ～ 4 では、明確さと完全性のレベルが低下しています。コアインテントがまだ解決されていない間に、若干の欠落や部分的な理解が生じてあいまいになることがあります。

スコアが 1 ～ 2 の場合、エージェントは目標達成に苦労したと考えられます。回答が不明確であったり、重要な要素が欠落していたり、無関係な情報が含まれていたりします。また、CRM から取得すべきであった情報をユーザーに要求する場合もあります。

スコア 0 は、ユーザーのクエリの解決に完全に失敗したことを示します。応答は汎用的で、ユーザーのインテントには対応しません。

サブエージェントアサーション

スコア 1 は、エージェントが発言に対応する適切なサブエージェントを正しく識別したことを示します。

スコア 0 は、エージェントが発言に対応するために予期しないサブエージェントを選択したことを示します。

 Agentforce Builder で失敗した発言を手動で再テストし、計画キャンバスでエージェントの推論を確認します。予期されるアクションとサブエージェント自体の両方の手順を調整して、エージェントが正しい選択肢に向かって明確に誘導し、誤ったアクションの使用を制限します。
アクションアサーション

スコア 1 は、発言に対処するためにエージェントがサブエージェント内の適切なアクションをすべて正しく識別したことを示します。

0 のスコアは、エージェントが誤ったアクションを選択したか、発言に対応するために必要なすべてのアクションをサブエージェント内で選択できなかったことを示します。

回答品質の評価は主に 0 ～ 5 で評価され、3 以上が合格を示します。ただし、[指示遵守] は [高]、[低]、または [不確実] として一意に評価されます。各スコアの理由は、LLM 審査員が情報バブルを介して提供します。

LLM-as-judge とは何ですか?

裁判官としての LLM は、ある大規模言語モデル (LLM) が別の LLM の出力を評価することで、集計のスコアリングや回答のランク付けなどのタスクの拡張性が高く、自動化された客観的な評価ツールとして機能します。「判断」LLM は、実際の正確性、関連性、一貫性、ソースへの忠実度などのタスクと評価条件を含むプロンプトを受信します。これらのリソースとガイドラインを使用して、LLM 審査員は予想される応答を判断し、エージェント応答と比較してから、スコア、ランキング、またはテキストフィードバックを生成します。LLM-as-Judge プロンプトは、最も正確で有益なテスト結果を提供するために慎重に設計されています。

評価 テストの意義
完全性

スコア 5 は、重要な漏れのない完全で正確な回答を示します。4 と 3 のスコアは、理解に若干影響する軽微なギャップから中程度のギャップを除き、完了度の低下を反映しています。

スコア 1 または 2 は、生成された回答が著しく不完全であり、いくつかの情報または最も重要な情報が欠落しているため、混乱が生じたり、部分的に誤解を招く結果になったりすることを示します。

スコア 0 は、評価が完全に失敗したことを示します。つまり、回答に重要な情報がすべて含まれていないため、非常に混乱したり、誤解を招く可能性があります。
一貫性

3 ～ 5 のスコアは、エージェントが基礎となる情報を適切な文章と文法構造で会話言語に正しく変換でき、会話が円滑に流れてユーザーにわかりやすくなることを示します。

0 ～ 2 のスコアは、情報が Salesforce オブジェクトから取得され、JSON 構造やダイレクト項目コンテンツなどの未加工データとして配信されたことを示します。
簡潔性

3 ～ 5 のスコアは、エージェントの反応が短いが正確で、目的のコンテンツの本質を正常に把握していることを示します。

0 ～ 2 のスコアは、回答が長かったり、反復的であったり、重要でない点が含まれていたり、無関係な内容が含まれていたりするため、生成された回答が簡潔でないことを意味します。
遅延 テスト発言で高い遅延または異常な遅延が発生している場合は、発言自体または一部の基盤インフラストラクチャに問題があると考えられます。エージェントによる調整で問題が解決しない場合は、Salesforce サポートに連絡してインフラストラクチャの問題を確認してください。
命令の遵守

高: エージェントはサブエージェントの指示を解釈して完全に従い、重要事項に対処して必要な情報を提供します。

低: エージェントがサブエージェントの指示を正確に解釈または従いません。少なくとも 1 つの命令に従うことに失敗し、誤った応答が返されます。これにより、命令を絞り込み、より明確な制約を設定する必要が生じます。

Uncertain (不確実): 応答やアクションがあいまいである、応答が不完全である、またはサブエージェントの指示の解釈が競合しているために、指示の遵守を確定的に判断できません。

デフォルトの評価は、期待結果と実際の結果を比較してスコアリングされますが、品質評価は固定条件に基づいて審査員 LLM によって評価されます。回答のスコアが低い場合、その回答が本当に期待を満たしていないかどうかを慎重に確認します。たとえば、審査員 LLM は簡潔性スコアが低いスコアを割り当てますが、追加のコンテキストの方が顧客にとって有益であると感じたり、ブランドの姿勢と一致したりする可能性があります。それ以外の場合は、追加の指示やガードレールを追加して、エージェントを目標に合わせて調整できます。スコアを解釈するときは、常に具体的な目標と使用事例を考慮してください。品質評価は指針となりますが、エージェントの成功または失敗の絶対的な基準ではありません。

サブエージェント

サブエージェントはエージェントが実行できるジョブです。サブエージェントの各部分と、それらを使用してエージェントのロジック、推論、会話機能を定義する方法について説明します。

必要なエディション

使用可能なインターフェース: Lightning Experience
使用可能なエディション: Enterprise Edition、Performance Edition、Unlimited Edition、および Developer Edition。必要なアドオンライセンスはエージェント種別によって異なります。
メモ 2026 年 4 月以降、エージェントトピックはサブエージェントと呼ばれるようになりました。機能に変更はありません。この移行中、ドキュメントで新しい用語と以前の用語が混在している場合があります。

サブエージェントは、エージェントが実行できる特定のジョブであると考えてください。エージェントに割り当てられたサブエージェントによって、エージェントが処理できる機能が定義されます。サブエージェントには、エージェントのロジックを制御してエージェントの推論を誘導する命令と、エージェントが使用できるツールであるアクションが含まれます。

サブエージェントの部分には、名前、説明、推論手順、推論アクション、エージェントアクションが含まれます。

サブエージェント項目 説明 使用方法
名前と説明

名前はサブエージェントの API 参照名です。通常、サブエージェントが行う作業を平易な言葉で説明するには 2 ～ 3 語です。

説明は、サブエージェントの機能と、このサブエージェントに分類する必要があるユーザー要求の種別を説明する 1 ～ 3 文です。つまり、この説明では、このサブエージェントをトリガーするユーザーメッセージについて説明します。

デフォルトでは、これらの項目は特別なサブエージェントであるエージェントルーターと共に使用され、会話でサブエージェントを使用するタイミングを決定します。ルーティング動作はカスタマイズできます。「サブエージェント分類およびルーティング」を参照してください。

エージェントは、エージェントに割り当てられたすべてのサブエージェントの名前と説明をユーザーの質問または要求、最近の会話履歴と比較します。そのコンテキストとエージェントルーターの指示に基づいて、エージェントは最適な一致を選択します。
説明 指示 (推論指示と呼ばれることもあります) は、サブエージェント、ビジネスケース、および会話全般のコンテキストで会話を処理する方法をエージェントに指示するガイドラインです。命令には、プログラムロジック (エージェントスクリプトで記述) と自然言語プロンプトの組み合わせが含まれます。ロジックでは、エージェントのワークフローとビジネスルールを厳密に定義します。プロンプトはエージェントの会話スキルをより柔軟にガイドします。

LLM に送信するプロンプトを作成するには、推論命令を使用します。

エージェントがサブエージェントに移動すると、順序どおりに推論手順の解決が開始され、エージェントがより正確に確実に推論できるようにロジックが実行されます。「How Subagent Instructions are Resolved to Build a Prompt」を参照してください。

エージェントがロジックの最後に達すると、自然言語の指示を含む解決済みプロンプトを LLM に送信して、推論プロセスを開始します。
推論に使用できるアクション (推論アクション)

推論に使用できるアクション (推論アクションとも呼ばれる) は、LLM を使用した推論中にエージェントが実行できるアクションです。これには、「Answer Questions with Knowledge」などの従来のエージェントアクションへの参照が含まれます。ただし、別のサブエージェントへの移行、変数の設定、担当者へのエスカレーションなどのユーティリティを含めることもできます。

推論アクションでは、アクションを使用できるタイミングを制御する検索条件を定義できます。アクションの後にロジックを追加して、アクションを順番に連結することもできます。

理由アクションは、理由の説明から作成されたプロンプトと共に LLM に送信されます。LLM は、ユーザーのメッセージ、最近の会話履歴、解決済みの推論手順、および推論アクションで定義されたロジックに基づいて、実行するアクションとユーティリティを選択します。

アクションをサブエージェントに追加すると、デフォルトでアクションがサブエージェントの推論アクションに追加されます。
アクション定義 バックグラウンドで、サブエージェントにはサブエージェントに割り当てられたすべてのエージェントアクションのリストが含まれます。これは、アクションの名前と説明、入力と出力のリスト、エージェントアクションが情報を取得したり ToDo を実行したりするためにコールする Salesforce 機能 (フローやプロンプトテンプレートなど) への参照など、サブエージェントの使用事例に関連するすべてのアクションのリストと考えることができます。アクション定義により、サブエージェント内でアクションを参照および使用できるようになります。アクション定義はキャンバスビューには表示されませんが、スクリプトビューでは確認できます。

アクションをサブエージェントに追加すると、デフォルトでアクションがサブエージェントのアクション定義とその推論アクションに追加されます。アクションをサブエージェントの推論アクションから削除して、エージェントが推論中に実行できないようにし、引き続きサブエージェント内で使用できます。

  • アクションを確定的に実行するには、推論を実行する前にアクションをサブエージェントの推論手順に追加します。
  • LLM が推論中にアクションを選択できるようにするには、アクションをサブエージェントの推論アクションに追加します。

サブエージェントからアクションを完全に削除するには、[エクスプローラー] パネルから削除します。または、エージェントのスクリプトでアクション定義とアクションへの参照を削除します。
  • サブエージェントの分類とルーティング
    エージェントルーターの詳細と、会話でエージェントがサブエージェントを選択する方法を制御するためにエージェントルーターをカスタマイズする方法について説明します。
  • プロンプトを作成するためのサブエージェントの指示の解決方法
    エージェントがサブエージェントの推論手順でプログラム式を実行して推論の準備をする方法について説明します。
  • サブエージェントの管理
    エージェントにサブエージェントを追加および削除します。カスタムサブエージェントを作成します。アセットライブラリでサブエージェントを管理します。

エージェントを変更するには、ドラフト状態である必要があります。コミットされたエージェントを変更する場合は、新しいドラフトを作成します。

  1. Agentforce Studio アプリケーションの [エージェント] リストから、サブエージェントを追加するエージェントを開きます。
  2. [Explorer (エクスプローラー)] パネルで、[Subagents (サブエージェント)] にマウスポインターを置いて [] をクリックします。
  3. [アセットライブラリから追加] を選択します。
  4. エージェントに追加する 1 つ以上のサブエージェントを選択します。
  5. [エージェントに追加] をクリックします。

選択した各サブエージェントのコピーがエージェントに追加され、そのコピーを編集できます。サブエージェントに加えた変更は、このエージェントバージョンにのみ適用され、アセットライブラリの他のエージェントやサブエージェントには影響しません。

エージェントルーターを使用してサブエージェントのルーティングと分類を制御する場合、エージェントに追加する各サブエージェントは、エージェントルーターの推論アクションに自動的に追加されます。

エージェントにサブエージェントを追加する場合、ビジネスニーズに合わせてサブエージェントをカスタマイズします。

  • サブエージェントの指示と推論アクションを確認してカスタマイズします。
  • サブエージェントに含まれるエージェントアクション (基盤となるフロー、プロンプトテンプレート、その他の参照アクションなど) を確認してカスタマイズします。
  • エージェントルーターを使用する場合、会話をサブエージェントに転送するロジックまたは手順を指定します。

エージェントを変更するには、ドラフト状態である必要があります。コミットされたエージェントを変更する場合は、新しいドラフトを作成します。

メモ

次の手順では、キャンバス ビューでサブエージェントを作成する方法について説明しますが、Agentforce Builder でサブエージェントを作成する方法はいくつかあります。

  • Agentforce にサブエージェントの作成を依頼します。エージェントが実行できる作業の詳細を入力すると、Agentforce によってサブエージェントとアクションが生成されます。変更を受け入れるか拒否できます。
  • スクリプトビューでサブエージェントを作成します。
  1. Agentforce Studio アプリケーションの [エージェント] リストから、サブエージェントを追加するエージェントを開きます。
  2. [Explorer (エクスプローラー)] パネルで、[Subagents (サブエージェント)] にマウスポインターを置いて [] をクリックします。
  3. [Create new subagent] を選択します。
  4. サブエージェントに名前を付け、[作成して開く] をクリックします。
    カスタムサブエージェントがエージェントに追加されます。エージェントルーターを使用してサブエージェントのルーティングと分類を制御する場合、推論に使用できるエージェントルーターのアクションにサブエージェントが追加されます。
  5. 説明、推論の手順、および推論に使用できるアクションを編集します。変更を保存します。
    サブエージェントの各部分について説明します。
  6. 必要に応じて、サブエージェントにアクションを追加します。
    1. [Explorer (エクスプローラー)] パネルで、サブエージェントにマウスポインターを置いて [] をクリックします。
    2. アセットライブラリから 1 つ以上のアクションを追加するか、カスタムアクションを作成します。
      アセットライブラリからアクションを追加するときは、基盤となるフロー、プロンプトテンプレート、その他の参照アクションを含め、常にアクションを確認してビジネスニーズに合わせてカスタマイズしてください。
    3. サブエージェントの推論手順、推論に使用できるアクション、またはその両方でアクションを参照します。
      アクションは、推論に使用できるアクションに自動的に追加されます。

サブエージェントはこのエージェントバージョンでのみ使用でき、アセットライブラリでは使用できません。サブエージェントに加えた変更は、このエージェントバージョンにのみ適用され、他のエージェントには影響しません。サブエージェントの名前を変更する場合は、エージェントルーターまたは他のサブエージェントでサブエージェントへの参照を手動で更新します。

プロンプトを作成するためのサブエージェントの指示の解決方法

エージェントがサブエージェントの推論手順でプログラム式を実行して推論の準備をする方法について説明します。

必要なエディション

使用可能なインターフェース: Lightning Experience
使用可能なエディション: Enterprise Edition、Performance Edition、Unlimited Edition、および Developer Edition。必要なアドオンライセンスはエージェント種別によって異なります。
メモ 2026 年 4 月以降、エージェントトピックはサブエージェントと呼ばれるようになりました。機能に変更はありません。この移行中、ドキュメントで新しい用語と以前の用語が混在している場合があります。

推論手順は、サブエージェント、ビジネスケース、および会話全般のコンテキストで会話を処理する方法をエージェントに指示するガイドラインです。プログラムロジックと自然言語プロンプトの組み合わせが含まれ、ロジックでエージェントの一般的なワークフローとビジネスルールを確実に処理し、プロンプトでエージェントの会話スキルをより柔軟にガイドします。推論手順のロジックは、エージェントが推論の前に実行する必要があること、自然言語プロンプトは、エージェントが推論中に考慮する必要があることと考えることができます。

エージェントがサブエージェントに移動すると、記述された順序でサブエージェントの推論手順が上から下へ解決されます。このプロセスには次のものが含まれます。

  • リソース (変数やアクションなど) への参照を実際の値に置き換える (値の手動設定を含む)
  • インラインアクションを実行し、結果を命令に挿入する
  • 条件ステートメントの評価と適用

サブエージェントの実行のこの段階では、推論は実行されないため、エージェントはまだ LLM に依存しません。推論命令のすべての論理式は、記述どおりに実行され、記述された順序で実行されます。

推論手順のいずれかの時点でエージェントが別のサブエージェントへの移行を実行すると、エージェントは手順が解決して推論が行われる前に会話をリダイレクトします。それ以外の場合、エージェントが推論手順の最後に達すると、解決された推論手順をプロンプトに挿入して LLM に送信し、推論プロセスを開始します。プロンプトには次の内容が含まれます。

  • すべてのエージェント操作に適用されるエージェントレベルの手順
  • ユーザーの最新のメッセージを含む最近の会話履歴
  • 解決済みサブエージェントの推論手順
  • サブエージェントに関連付けられた推論アクション。これは、エージェントが推論プロセス中に実行できるアクション (エージェントアクションを含む) です。

エージェントは LLM を使用して、プロンプトで使用可能な情報を分析し、次のステップを決定します。

例

エージェントが配送を期待する顧客とチャットしている。顧客の注文 ID が 1234、配送予定日が 2026 年 2 月 10 日で、配送予定期間外である。

顧客のメッセージに基づいて、エージェントは次の推論手順を含むサブエージェントを選択します。

reasoning:
  instructions:->
    If @variables.updated_delivery_date == None
      run @actions.get_delivery_date 
        with order_ID=@variables.order_ID
        set @variables.updated_delivery_date=@outputs.delivery_date

      | Tell the user that the expected delivery date for order number {!@variables.order_ID} is {!@variables.updated_delivery_date}. 

    If @variables.is_late == None
      run @actions.check_if_late
        with order_ID=@variables.order_ID
        with delivery_date=@variables.updated_delivery_date
        set @variables.is_late = @outputs.is_late

    if @variables.is_late == "true":
      | Apologize to the customer for the delay in receiving their order.

プロンプトを作成するために、Agentforce は次の手順で 1 行ずつ理由の説明を解決します。

  1. アクションget_delivery_dateを実行して配送予定日を取得します。
  2. 変数updated_delivery_dateを、アクションによって返された outputs.delivery_date の値に設定します。この場合、値は February 10, 2026 に設定されます。
  3. プロンプトに命令 Tell the user that the expected delivery date for order number 1234 is February 10, 2026. を追加します。
  4. action check_if_lateを実行します。
  5. このvariable is_lateを、アクションによって返された outputs.is_late の値に設定します。この場合、変数は "True" に設定されます。
  6. if @variables.is_late == "True" の値をチェックして、注文が遅延しているかどうかを判断します。
  7. 注文が遅れているため、プロンプトに次の命令を追加します。 Apologize to the customer for the delay in receiving their order.

プロンプトに追加された解決済みの理由の説明を次に示します。

Tell the user that the expected delivery date for the order number 1234 is February 10, 2026. 
Apologize to the customer for the delay in receiving their order.

プロンプトが LLM に送信され、エージェントの次のステップが判断されて応答が生成されます。

ただし、代わりに別のサブエージェントを開始サブエージェントとして定義できます。会話の後半でエージェントルーターを使用してサブエージェント分類に移動することも、サブエージェントルーティングを異なる方法で制御する場合はエージェントからエージェントルーターを完全に削除することもできます。

2026 年 4 月以降、新しい Agentforce Builder で Agentforce 従業員エージェントと Agentforce サービスエージェントのデフォルト テンプレートを使用して作成されたエージェントは、Salesforce が所有する HyperClassifier モデルをサブエージェント分類に使用します。HyperClassifier モデルは、特に複雑な命令に従ったり、否定的な命令に従ったりする場合に、標準的な LLM よりも速度と精度で優れています。

エージェントスクリプトの次のstart_agentブロックは、サブエージェント分類の HyperClassifier を設定します。

start_agent agent_router:
    description: "Welcome the user and determine the appropriate topic/subagent based on user input"
    model_config:
       model: "model://sfdc_ai__DefaultEinsteinHyperClassifier"

model_configを削除すると、エージェントはデフォルトでサブエージェント分類に [設定] の Agentforce のモデル オプションを選択します。

詳細については、『Agentforce 開発者ガイド』の「Configure Models in Agent Script」を参照してください。

Agentforce のデータマスキングの制限事項

Einstein Trust Layer では、大規模言語モデル（LLM）のパターンベースおよび項目ベースのデータ マスキングはエージェントで無効になっています。

必要なエディション

使用可能なインターフェース: Lightning Experience
使用可能なエディション: Enterprise Edition、Performance Edition、Unlimited Edition、および Developer Edition。必要なアドオンライセンスはエージェント種別によって異なります。

マスキングは、機密情報や個人識別情報を LLM に公開しないように保護できますが、場合によっては、応答に必要なコンテキストがマスキングされるため、エージェントの応答の精度や関連性に影響する可能性があります。たとえば、ユーザーがエージェントに類似する取引先のリストの作成を依頼した場合、参照取引先の詳細は重要なコンテキスト情報になります。参照取引先を LLM に送信する前にプロンプトからマスクした場合、類似する特性を持つ取引先を識別するために必要なコンテキスト情報がありません。

Einstein Trust Layerには、機密データをデータのマスキング以外の悪用や漏洩から保護するのに役立ついくつかのポリシーと機能が含まれています。

Salesforce Trust境界外のLLMに送信されるすべての情報は、LLMプロバイダーとのゼロ データ保持契約の対象になります。LLM に送信された情報は、生成された応答が Salesforce に返送された後は、プロバイダーによって保持、参照、またはトレーニングに使用されません。

プロンプト テンプレート、Apex、またはモデル API に基づくカスタム アクションは、Salesforce Trust Boundary 内でホストされている LLM (Anthropic Claude モデルなど) を含め、Salesforce が管理する LLM を参照できます。Salesforce Trust 境界内でホストされる LLM を使用する場合、データは Salesforce Trust 境界から離れません。この場合、エージェントのデータ マスキングは無効のままですが、データはSalesforce Trustの境界内に留まり、ゼロ データ保持ポリシーは引き続き適用されます。

メモ プロンプトテンプレートは、Salesforce アプリケーションで直接、またはエージェントアクションを介して使用できます。エージェントアクションを介してプロンプトテンプレートがコールされると、データマスキングが無効になります。プロンプト テンプレートが直接使用される場合（サービス返信など）、データ マスキングは Einstein Trust Layer の設定に基づいて適用されます。

エージェントユーザー権限のベストプラクティス

エージェントユーザーの考慮事項

重要

組織の共有設定 (OWD) によって、所有していないレコードへのユーザーのアクセス権が決まります。認証済みユーザーを使用するエージェントセッションでは、セッションはエンドユーザーのコンテキストで実行され、OWD はユーザーが外部か内部かによって異なります。認証されていないユーザーのエージェントセッションでは、セッションはエージェントユーザーのコンテキストで実行され、内部ユーザーの OWD が適用されます。

OWD、エージェントユーザーの権限、およびエージェント設定を慎重に確認し、エンドユーザーとビジネスに適したレコードアクセス権があることを確認します。

  • エージェントのユーザーレコードを使用するすべてのエージェントで、検索条件と変数を使用して、サブエージェントおよびアクションレベルでレコードアクセスを制限することをお勧めします。この戦略により、OWD に関係なく機密データが保護されます。
  • 内部ユーザーの OWD を制限して、すべての内部ユーザーのレコードアクセスを制限できます。その後、必要に応じて Einstein エージェントユーザーを除外して、アクセス権を選択的に付与する共有ルールを作成できます。
  • エージェントに適切なアクセス権があることを確認するには、リリースする前に Sandbox でエージェントをテストします。
  • 管理者権限を持つ Salesforce ユーザーのみがエージェントユーザーを表示または編集できます。
  • エージェントユーザーログイン情報を使用して Salesforce にログインすることはできません。
  • エージェントユーザーが Salesforce で作業している場合、そのユーザー名はレコードの [作成者]、[最終更新者]、または [所有者] 項目や Salesforce の監査項目に表示される可能性があります。
  • エージェントユーザーを区別するには、各ユーザーの名を、関連付けられているエージェントの名前に更新することを検討してください。
  • [ユーザー] 設定ページですべてのエージェントユーザーを簡単に見つけるには、Einstein エージェントユーザープロファイルで絞り込むリストビューを作成することを検討してください。

必要なエディション

使用可能なインターフェース: Lightning Experience
使用可能なエディション: Enterprise Edition、Performance Edition、Unlimited Edition、および Developer Edition。必要なアドオンライセンスはエージェント種別によって異なります。

コンテキスト変数はオブジェクト項目に対応付けられます。エージェントが顧客チャネルに接続できる場合、カスタム項目を含め、メッセージングセッションオブジェクト項目から対応付けられたコンテキスト変数が含まれます。コンテキスト変数には $Context のプレフィックスが付き、通常は参照のみです。エンドユーザー言語コンテキスト変数は編集可能です。

会話変数はエージェントに固有であり、会話セッション中にのみ値が保持されます。

カスタム会話変数には、アクションの出力値が保存されます。カスタム会話変数は、検索条件で、またはアクションの入力として使用できます。この変数は Boolean、Number、または Text データ型にできます。

変数を使用する方法をいくつか紹介します。

  • コンテキスト変数またはカスタム会話変数をアクション入力に割り当てます。アクション入力に変数を割り当てると、エージェントは割り当てられた変数のみを使用して入力の値を入力できます。アクション入力は、Boolean、Number、Text のいずれかのデータ型である必要があります。
  • アクション出力を変数に対応付けます。出力値は検索条件と命令で使用できます。アクション出力は、Boolean、Number、Text のいずれかのデータ型である必要があります。
  • 検索条件で変数を使用します。検索条件により、エージェントは変数が検索条件を満たした場合にのみサブエージェントまたはアクションを使用できます。
  • エージェント API で変数値を指定し、サブエージェントの指示で変数にメンションします。

コンテキスト変数の場合は、{!$Context.VariableAPIName} の形式を使用します。会話変数の場合は、{!VariableAPIName} の形式を使用します。

  • 従来のビルダーでのエージェントのカスタム変数の作成
    アクション出力をカスタム変数に対応付けて、エージェントがサブエージェントとアクションを使用する方法を制御します。たとえば、アクション入力に変数を割り当てると、エージェントは割り当てられた変数のみを使用して入力の値を入力できます。

エージェントのバージョン管理と編集

ドラフト状態や確定済み状態、エージェントのバージョン管理方法など、エージェントの作成と反復を行うときのエージェントのさまざまな状態について説明します。

エージェントを作成するときに、変更を加えて保存します。変更を保存するたびに、現在のエージェントバージョンへの変更が保存され、引き続き編集できます。

この時点で、エージェントはドラフト状態になります。多くの変更や 1 つ以上の大きな変更を行っているため、変更をすばやく実行してテストする必要があります。

[プレビュー] パネルで、模擬データを使用してエージェントの動作をシミュレーションするか、組織の実際のデータを使用してエージェントの動作をライブテストします。エージェントをプレビューすると、エージェントのやりとりとプロセスの詳細なステップごとの追跡を確認できます。また、詳細なトレースとデバッグでさらに詳しく調べることができるため、情報に基づいた正確な修正を行うことができます。

エージェントがドラフト状態の場合、エージェントを有効化することはできません。

3. エージェントを確定して有効化する

エージェントの設計とパフォーマンスに満足したら、エージェントを確定します。準備ができたら、顧客または従業員のエージェントを有効化します。

Git に精通している場合、エージェントバージョンの確定は変更の確定に似ています。エージェントバージョンをコミットすると、エージェントバージョンのスナップショットがメタデータに保存されます。これにより、有効化できるようになります。

エージェントバージョンを確定すると、そのエージェントバージョンは変更できなくなります。

バージョンを確定した後にエージェントに対して反復処理を実行するには、ドラフトを作成します。ドラフトを作成すると、新しい編集可能なバージョンのエージェントが作成されます。ドラフトは確定するまで編集できます。

エージェントに対して反復処理を行う場合、多くのエージェントバージョンを作成するのが一般的です。Agentforce Builder では、ヘッダーのドロップダウンメニューからバージョンを切り替えることができます。

API 接続への手動でのポリシーの適用

Policy Builder の [手動選択] タブを使用して、特定の API 接続にポリシーを割り当てます。

  1. [設定] から、[クイック検索] ボックスに「ポリシー」と入力し、[ポリシー] を選択します。
  2. Agentforce Gateway Policies ページで、API タブを選択し、ポリシーを選択します。
  3. ポリシーの詳細ページで、[ビルダーで開く] を選択します。
  4. Policy Builder で、サイドバーから [Target Entities ] を選択します。
  5. [Target APIs (対象 API)] ページで、[Manual Selection (手動選択)] タブを選択します。
  6. [手動選択] で、[接続を追加] を選択します。
  7. [接続を追加] ダイアログの [API で接続を選択] で、ポリシーを適用する API を選択します。
    • API のすべての接続にポリシーを適用するには、API 名の横にあるチェックボックスをオンにします。API の [接続] 列が [現在のすべての接続] に更新されます。
    • ポリシーを特定の接続に適用するには、[接続] 列のリンクをクリックし、各接続の横にあるチェックボックスをオンにして、[API で接続を選択] ウィンドウに戻ります。[接続] 列のリンクが更新され、選択した接続数が表示されます (例: 2 接続)。
  8. [接続を追加] を選択します。
    [接続] 列に [現在のすべての接続] リンクがある選択した API の場合、ポリシーはすべての接続に適用されます。選択した API の [接続] 列に多数の接続が表示されている場合、ポリシーは事前選択された接続にのみ適用されます。

MCP Server 接続への手動でのポリシーの適用

Policy Builder の [手動選択] タブを使用して、特定の MCP サーバーにポリシーを割り当てます。

MCP サーバーを登録するときに手動でポリシーを適用することもできます。これらのポリシーは手動で適用するため、新しいサーバー登録には自動的に適用されません。

  1. [設定] から、[クイック検索] ボックスに「ポリシー」と入力し、[ポリシー] を選択します。
  2. Agentforce Gateway Policies ページで、MCP Servers タブを選択し、ポリシーを選択します。
  3. ポリシーの詳細ページで、[Open in Policy Builder] を選択します。
  4. Policy Builder で、サイドバーから [Target Entities ] を選択します。
  5. [Target MCP Servers (対象 MCP サーバ)] ページで、[Manual Selection (手動選択)] タブを選択します。
  6. [Manual Selection (手動選択)] で、[Add MCP Servers (MCP サーバを追加)] を選択します。
  7. 1 つ以上の MCP サーバを選択し、[サーバを追加] をクリックします。

ポリシーを自動的に適用するための一致条件の定義

1 つのポリシーを複数の MCP サーバーまたは API 接続に自動的に適用するための一致条件を定義します。ポリシーは、条件に一致する既存および将来の登録を保護します。

一致条件により、サーバー保護を自動的に拡張できます。

  1. [設定] から、[クイック検索] ボックスに「ポリシー」と入力し、[ポリシー] を選択します。
  2. Agentforce ゲートウェイの [ポリシー] ページで、ポリシー タイプに応じて [APIs] タブまたは [MCP Servers] タブを選択し、ポリシーを選択します。
  3. ポリシーの詳細ページで、[Open in Policy Builder] を選択します。
  4. Policy Builder で、［Matching Criteria］ タブを選択します。
  5. 一致条件を設定します。
    • 適用先:
      • API 接続の場合、ポリシーをすべての条件を満たす接続またはすべての条件を満たす接続に適用します。
      • MCP サーバ接続の場合、ポリシーをすべての条件を満たす MCP サーバまたはMCP サーバに適用します。
    • 変数:
      • API 接続の場合、API ソースまたは API 参照名で絞り込みます。
      • MCP サーバの場合は、MCP Server Source または MCP Server Name で絞り込みます。
    • 演算子: 条件演算子を選択します。
    • 値: 絞り込む値を選択します。この値は大文字と小文字が区別されます。
  6. 条件を追加するには、[条件を追加] をクリックします。
  7. 複数のルール間で AND 条件を作成するには、［Add Group］ をクリックします。
  8. [ポリシーを保存(Save Policy)] をクリックします。
    ポリシーは、指定した条件に一致する現在および将来のすべての MCP サーバーまたは API 接続に自動的に適用されます。
メモ 一致条件を作成または編集したり、MCP サーバーまたは API を作成または編集したり、接続を追加したりすると、保護する接続が変更される可能性があります。同期は 15 分間隔で自動的に実行されます。更新をすぐに適用するには、「Sync Policy Matching Criteria Immediately」を参照してください。

ポリシー一致条件をすぐに同期

API、接続、一致条件、または MCP サーバーの設定後、保護には最大 15 分かかります。

  1. ポリシーの詳細ページで、[Open in Policy Builder] の横にあるドロップダウンをクリックします。
  2. [Sync Criteria-Based Policies] を選択します。

このアクションにより、自動更新を待たずに接続と保護対象間ですべてのポリシー一致条件が同期されます。

Agentforce ゲートウェイ ポリシー テンプレート

ポリシーを作成するには、テンプレートから開始します。使用可能なテンプレートは、API と MCP のどちらのサーバー接続を保護しているかによって異なります。

API 接続のテンプレート

発信通話量を制限し、特定の HTTP メソッドまたはパスへのアクセスを制限することで、API トラフィックとセキュリティを管理します。リソースの枯渇を防ぎ、エージェントがセキュリティ要件に従って承認されたエンドポイントのみを操作できるようにします。

目標管理ポリシーテンプレート

目標管理ポリシーテンプレートは、API 接続と MCP サーバー接続の両方で使用できます。指定された期間中にエージェントが送信できる要求の数を制限することで、発信通話を選択された接続に制限します。次の設定を行うことができます。

  • Call Limit:指定した期間内でポリシーで許可されるコールの最大数。
  • Time Interval:指定したコール制限が適用される期間。
  • Quota Type by API Operation (API 操作別の目標種別): API 操作間で目標がどのように配分されるか。
    • 共有: すべての操作で共有される 1 つの目標。たとえば、1 秒あたり 100 件のコールを複数の操作で共有する場合、操作 A で 50 件を使用すると、残りの操作は合計で 50 件になります。
    • API 操作ごと: 各操作の個別の制限。たとえば、制限が 1 秒あたり 100 コールの場合、各操作では 1 秒あたり 100 コールが許可されます。
  • Quota Type by Agent (エージェント別の目標種別): 目標エージェント間の配分方法:
    • 共有:AA の単一割り当てがすべてのエージェントで共有されます。たとえば、1 秒あたり 100 件の通話があり、エージェント A が 50 件を使用した場合、エージェント B と C を合わせて 50 件残っています。
    • エージェントごと: 各エージェントの個別の制限。たとえば、エージェントごとに 1 秒あたり 100 件の通話がある場合、エージェント A、B、C はそれぞれ独立して 1 秒あたり 100 件の通話を行うことができます。

制限付きアクセスポリシーテンプレート

[アクセス制限] ポリシーテンプレートは API 接続にのみ適用されます。Flex Gateway で許可される HTTP パスとメソッドが制限されます。次の設定を行うことができます。

  • Methods: 制限する HTTP メソッド。
  • パス: 制限するパス。このフィールドでは文字列パスがサポートされ、ワイルドカード*は任意のセグメントに一致します。たとえば、/users/*/details は /users/123/details または /users/john/details と一致します。デフォルトでは、* はすべてのパスを意味します。
メモ API 接続の場合、ポリシーに API 接続がないと無効になります。一致条件が設定されている場合に有効になります。

MCP Server 接続のテンプレート

目標管理ポリシーテンプレート

目標管理ポリシーテンプレートは、API 接続と MCP サーバー接続の両方で使用できます。指定された期間中にエージェントが送信できる要求の数を制限することで、発信通話を選択された接続に制限します。次の設定を行うことができます。

  • Call Limit:指定した期間内でポリシーで許可されるコールの最大数。
  • Time Interval:指定したコール制限が適用される期間。
  • Quota Type by Tool (ツール別の目標種別): MCP ツール間で目標がどのように配分されるか:
    • 共有: すべてのツールで共有される個々の目標。たとえば、1 秒あたり 100 件の通話をツールで共有する場合、ツール A で 50 件を使用すると、残りのツールは合計で 50 件残ります。
    • ツールごと: 各ツールの個別の制限。たとえば、制限が 1 秒あたり 100 コールの場合、各ツールでは 1 秒あたり 100 コールが許可されます。
  • Quota Type by Agent (エージェント別の目標種別): 目標エージェント間の配分方法:
    • 共有: すべてのエージェントが 1 つの制限を共有します。たとえば、1 秒あたり 100 件の通話があり、エージェント A が 50 件を使用した場合、エージェント B と C を合わせて 50 件残っています。
    • エージェントごと: 各エージェントの個別の制限。たとえば、エージェントごとに 1 秒あたり 100 件の通話がある場合、エージェント A、B、C はそれぞれ独立して 1 秒あたり 100 件の通話を行うことができます。

グリッドワークシートを作成および変更する Agentforce グリッドの管理
  1. アプリケーションランチャーで、[Agentforce Grid]を見つけて選択します。
  2. [Create Grid (グリッドを作成)] をクリックします。
  3. 名前を入力します。必要に応じて、[ホーム] タブのグリッドのリストに表示される説明を追加します。
  4. [作成] をクリックします。
  5. 最初の列の入力に使用する内容を選択します。
    • Salesforce は CRM レコードを照会します。
    • Data Cloud は Data 360 レコードを照会します。
    • AI は LLM を使用してデータを生成します。
    • エージェントが Agentforce エージェントを実行します。
    • CSV ファイルから独自のデータをアップロードすることもできます。
  6. データの準備ができたら、データの追加と実験を開始できます。
    • さらに列を作成するには、[+列を追加] をクリックします。
    • ある列のデータを参照し、別の列の入力として使用するには、別の列で @メンションします。
    • 列の詳細を表示したり、データを並び替えたり、編集または削除したりするには、列ヘッダーをクリックします。
    • ワークシートをエクスポートまたは削除したり、CSV ファイルをアップロードしたりするには、オプションアイコンをクリックします。
    • 新しいワークシートタブをグリッドに追加するには、[+] をクリックします。
    • ワークシートの名前を変更するには、タブ名をダブルクリックします。
    • セルを変更するには、ダブルクリックしてテキストを変更します。
    • 列でデータを実行するには、列パネルで [保存 & 実行(Save and Run)] を保存するか、列メニューで [この列のすべてのセルを更新(Update All Cells in this Column)] をクリックします。
    • セルでデータを実行するには、実行ボタンをクリックします。
    • 行のデータを実行するには、行を選択して [実行] をクリックします。
    • ワークシート全体のデータを実行するには、すべての行を選択して、[実行] をクリックします。

必要なエディション

使用可能なインターフェース: Lightning Experience

必要なユーザー権限
権限セットを割り当てる 「権限セットの割り当て」
  1. [設定] から、[クイック検索] ボックスに「Einstein 設定」と入力し、[Einstein 設定] を選択します。
  2. Einstein を有効にします。
  3. [設定] の [クイック検索] ボックスに「権限セット」と入力し、[権限セット] を選択します。
  4. [新規] をクリックします。
  5. 権限セット情報を入力します。
  6. 権限セットのユーザー種別を選択します。特定のユーザーまたは権限セットライセンスを選択します。または、異なるライセンスを持つユーザーを権限セットに割り当てる場合は、[なし] を選択します。
  7. 「Agentforce グリッドの管理」権限を追加します。
  8. 権限セットをユーザーに割り当てます。
