第1章Salesforce Security Basics

公式: https://help.salesforce.com/s/articleView?id=xcloud.overview_security.htm&type=5 ↗

Salesforce のセキュリティは「Salesforce 側」と「顧客側」の共有責任モデルで成り立ちます。 Salesforce はインフラ・プラットフォーム・物理セキュリティ・暗号化基盤を提供し、 顧客はユーザー認証・権限設計・共有設定・監査といった「組織の中の使い方」を設計します。

本ガイドの全体像は次の4層に整理できます:

  1. 認証 (Authenticate) — 誰がログインできるか (MFA / SSO / セッション)
  2. 認可 (Give Access) — ログインした人が何をしてよいか (プロファイル / 権限セット)
  3. 共有 (Share) — どのレコードを見られるか (OWD / ロール階層 / 共有ルール)
  4. 監査 (Audit & Monitor) — 何が起きたかを記録・検知する (ログ / Health Check / Real-Time EM)

1.1Phishing and Malware 公式 ↗

フィッシングとマルウェア対策: trust.salesforce.com で稼働状況を公開し、 ユーザー側は不審なメール/ファイルを開かない、MFA を有効化する、ブラウザを最新に保つ等の基本対策が前提。 Salesforce は顧客に対しパスワードや個人情報をメールで尋ねることはない。

1.2Security Health Check 公式 ↗

Security Health Check: 設定 → セキュリティ → ヘルスチェックで開く。 パスワード方針・セッション設定・証明書管理など 50 以上の設定項目を、Salesforce 推奨ベースラインと照合してスコア化する。 カスタムベースラインで自社基準に合わせた評価も可能。四半期ごとにスコアを確認するのが基本運用。

1.3Auditing 公式 ↗

監査: 「誰がいつ何をしたか」を残す機能群。代表的なログ:

  • ログイン履歴 (過去 6 か月): 成功/失敗、IP、認証方式
  • 設定監査証跡 (過去 180 日 / Shield で 365 日): 管理者の設定変更
  • 項目履歴管理: 個別レコード項目の変更追跡 (オブジェクトあたり最大 20 項目)
  • Event Monitoring (Shield): API コール・レポート出力など 50+ イベント

1.4Salesforce Shield 公式 ↗

Salesforce Shield: 高度セキュリティが必要な業界 (金融・医療等) 向けの追加製品。3 機能セット:

  1. Platform Encryption: 暗号化キーを顧客が管理しつつ、項目/添付/検索インデックスまで暗号化
  2. Event Monitoring: 詳細イベントログ + Threat Detection (リアルタイム異常検知)
  3. Field Audit Trail: 項目履歴を最大 10 年保持
標準機能の延長ではなく 有償アドオン。コンプライアンス要件 (PCI/HIPAA/GDPR 等) で購入を検討する。

第2章Authenticate Users

公式: https://help.salesforce.com/s/articleView?id=xcloud.security_sharing_setup.htm&type=5 ↗

認証は「本人確認」のレイヤー。Salesforce は ID/パスワードに加え、 MFA・SSO・OAuth・セッション制御を組み合わせて多層防御を実現する。 2022 年以降、Salesforce は全顧客に MFA を契約上義務化しており、未導入の組織は自動的に有効化される運用となっている。

2.1Multi-Factor Authentication 公式 ↗

多要素認証 (MFA): 「知っているもの (PW)」+「持っているもの (Authenticator/物理キー)」の2つを要求。 推奨方式は Salesforce Authenticator アプリ、TOTP アプリ、WebAuthn (FIDO2 物理キー)。 SMS や音声通話は非推奨。MFA は契約義務であり、未対応の組織には自動有効化が段階的に適用される。

2.2Single Sign-On 公式 ↗

シングルサインオン (SSO): 外部 IdP (Azure AD / Okta / Google / 自社 ADFS) を信頼し、 Salesforce ログイン画面で ID/PW を入力せずに通過する。プロトコルは SAML 2.0 または OpenID Connect。 SSO 経由でも MFA は IdP 側で実装されていれば「MFA 義務」を満たす。

2.3Custom Login Flows 公式 ↗

ログインフロー: ログイン直後に Flow を差し込み、利用規約同意・追加質問・条件付き MFA 等を実行できる。 プロファイルごとに割り当て可能。

2.4Connected Apps 公式 ↗

接続アプリ (Connected App): 外部アプリ (モバイルアプリ・iPaaS・社内ツール) が Salesforce API を呼ぶための入口。 OAuth 2.0 で認可し、スコープ・IP 制限・セッション期限・許可するプロファイルを細かく制御できる。 管理者は「使用済み接続アプリ」画面で利用状況を監視し、不要なアプリのアクセスを失効させる。

2.5Manage User Passwords 公式 ↗

パスワード管理: パスワード方針 (長さ・複雑度・有効期限・履歴) はプロファイル単位で設定。 パスワードリセットメール、強制ロック解除、初回ログイン URL 発行などは管理者が個別に実行可能。 SSO 環境では Salesforce 側のパスワードは「フォールバック用」となるが、流出経路となるため強度は維持する。

2.6Device Activation 公式 ↗

デバイス有効化: 未知のブラウザ/IP からログインがあった際に追加確認 (メールコード等) を要求する仕組み。 信頼済みデバイスとして登録すれば次回以降スキップ。MFA とは別レイヤーの緩い保護であり、MFA 導入後も併用される。

2.7Session Security 公式 ↗

セッションセキュリティ: タイムアウト時間、IP ロック (セッションを発行 IP に固定)、 HTTPS 強制、High Assurance セッション (重要操作だけ MFA 再要求) などを制御。 Lightning Experience では既定で安全側の設定が適用される。

第3章Give Users Access to Data

公式: https://help.salesforce.com/s/articleView?id=xcloud.security_feature_setup.htm&type=5 ↗

認可は「ログインした人が何をしてよいか」を決めるレイヤー。Salesforce では伝統的に プロファイルと権限セットの2系統で表現される。 近年は「プロファイルは最小限に、機能ごとの追加権限は権限セット (権限セットグループ)」が推奨設計。

3.1Control Who Sees What 公式 ↗

Control Who Sees What: Salesforce のアクセス制御は3軸で考える。

  1. オブジェクトレベル: 「Account を見られるか」 (プロファイル/権限セット)
  2. 項目レベル: 「Account の Revenue 項目を見られるか」 (Field-Level Security)
  3. レコードレベル: 「この特定の Account レコードを見られるか」 (共有設定 — 第4章)
3つは AND で重なる: オブジェクト Read 不可なら、項目や共有を緩めても見えない。

3.2User Permissions 公式 ↗

ユーザー権限: 「Modify All Data」「View All Data」「API Enabled」など、 組織全体に効く特殊権限。誤付与すると共有設定をすべて貫通するので、付与対象は最小に。

    • 第7章Security Guidelines for Apex and Visualforce Development

    公式: https://help.salesforce.com/s/articleView?id=xcloud.review_and_certification.htm&type=5 ↗

    Apex / Visualforce / LWC で開発するときに開発者が踏みやすい脆弱性パターンと対策。 Salesforce のセキュリティレビュー (AppExchange 出品時) でも厳しくチェックされる項目。

    開発者が必ず守る基本:

    1. SOQL/SOSL インジェクション対策: 動的 SOQL を組むときは String.escapeSingleQuotes() または bind 変数を使う。文字列連結は厳禁。
    2. XSS 対策: Visualforce では {!value} でなく HTMLENCODE/JSENCODE 関数を経由。LWC は標準で自動エスケープされるが lwc:dom="manual" は要注意。
    3. CRUD/FLS 適用: Apex は既定で共有・FLS を「無視」する。with sharing 宣言、Schema.sObjectType.X.isAccessible() 確認、または WITH SECURITY_ENFORCED / Security.stripInaccessible() を使う。
    4. 機密情報のハードコード禁止: API キー・パスワードは Named Credential / Protected Custom Metadata / Protected Custom Setting に格納。
    5. CSRF 対策: Visualforce は apex:form でトークン自動付与。GET でのデータ変更は禁止。
    6. オープンリダイレクト対策: retURL / startURL パラメータを Apex で取り出す場合、ホワイトリスト検証必須。
    さらに本番反映前に Checkmarx や Salesforce Code Analyzer (PMD) で静的解析することが推奨される。

    第8章API End-of-Life Policy

    公式: https://help.salesforce.com/s/articleView?id=xcloud.api_rest_eol.htm&type=5 ↗

    古い API バージョンの段階的廃止ポリシー。 リリースから 3 年経過すると EOL (廃止) 候補となり、その後段階的に無効化される。

    API End-of-Life ポリシー: SOAP/REST/Bulk/Streaming API は約 3 年経過後に廃止対象となる。 廃止対象バージョンを呼び出すと最初は警告ヘッダ、最終的に HTTP 410。 影響を受けるかは Event Monitoring の ApiTotalUsage イベントまたは Setup → API Usage Notifications で確認。 本番では常に最新の3バージョン以内を使う運用が安全。
