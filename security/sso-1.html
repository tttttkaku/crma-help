SAML が有効なアプリケーションとしてのサービスプロバイダーの統合

Salesforce を ID プロバイダーとして SAML シングルサインオン (SSO) を設定するには、外部クライアントアプリケーションフレームワークまたは接続アプリケーションフレームワークを使用してサービスプロバイダーを統合します。この SSO 設定では、ユーザーは Salesforce 組織または Experience Cloud サイトにログインするときと同じログイン情報を使用してサービスプロバイダーにログインします。サービスプロバイダーの詳細を変更するには、アプリケーションを編集します。プロファイルと権限セットを管理して、アプリケーションにアクセスできるユーザーを制御します。

必要なエディション

使用可能なインターフェース: Salesforce Classic および Lightning Experience の両方
使用可能なエディション: Developer Edition、Enterprise Edition、Performance Edition、Unlimited Edition、および Database.com Edition
必要なユーザー権限
ID プロバイダーとサービスプロバイダーの定義と変更 「アプリケーションのカスタマイズ」

外部クライアントアプリケーションフレームワークは、新世代の接続アプリケーションフレームワークです。接続アプリケーションフレームワークの多くの欠点を解決します。「接続アプリケーション機能と外部クライアントアプリケーション機能の比較」を参照してください。

メモ SAML の場合、外部クライアントアプリケーションフレームワークで現在サポートされているのは、メタデータ API 設定のみです。

外部クライアントアプリケーションとしてのサービスプロバイダーの統合

SAML が有効な外部クライアントアプリケーションは、親の ExternalClientApplication コンポーネント、ExtlClntAppConfigurablePolicies コンポーネント、および ExtlClntAppSamlConfigurablePolicies コンポーネントという 3 つの主要なメタデータコンポーネントで構成されます。

このコンポーネントを作成および編集する手順は、「外部クライアントアプリケーションとしての SAML SSO サービスプロバイダーの統合」を参照してください。

接続アプリケーションとしてのサービスプロバイダーの統合

SAML 設定を作成するには、「SAML 2.0 を使用した接続アプリケーションとしてサービスプロバイダーを統合」を参照してください。

サービスプロバイダーの詳細を確認および編集するには、次のリソースを参照してください。

  • 接続アプリケーションを再設定する。
  • ユーザーアクセスを信頼できる IP 範囲に制限する。
  • カスタム属性を追加する。
  • 接続アプリケーションを削除する。

プロファイルと権限セットを管理するには、「接続アプリケーションへのアクセスの管理」を参照してください。

OpenID Connect ID プロバイダーとしての Salesforce

SAML シングルサインオン (SSO) とは異なり、サービスプロバイダーを OpenID Connect と統合する場合、または証明書利用者を統合する場合、Salesforce を ID プロバイダーとして有効にしません。OpenID Connect を使用して、サービスプロバイダーを接続アプリケーションとして統合できます。そうすることで、組織はユーザーを認証できるようになり、ユーザーは証明書利用者にログインできます。

SAML サービスプロバイダーへの Salesforce ユーザーの対応付け

Salesforce ユーザーがシングルサインオン (SSO) でログインするときに SAML サービスプロバイダーが Salesforce ユーザーを認識できるようにするには、Salesforce でユーザー情報を更新します。サービスプロバイダーが認識するユーザー ID を提供します。

必要なエディション

使用可能なインターフェース: Salesforce Classic および Lightning Experience の両方
使用可能なエディション: Developer Edition、Enterprise Edition、Performance Edition、Unlimited Edition、および Database.com Edition
必要なユーザー権限
ID プロバイダーとサービスプロバイダーの定義と変更 「アプリケーションのカスタマイズ」

開始する前に、次のステップを実行します。

  • ID プロバイダーとして Salesforce を有効化します。
  • サービスプロバイダーを統合するための前提条件を完了します。
  • サービスプロバイダーを SAML 対応アプリケーションとして統合します。

使用する ID は、サービスプロバイダーが SAML アサーションで想定する件名種別によって決まります。たとえば、[件名種別] が [ユーザー名] である場合は、サービスプロバイダーは、SAML アサーションの件名にユーザーの Salesforce ユーザー名が含まれていると想定します。Salesforce が SAML アサーションにユーザー名を含めて送信することで、サービスプロバイダーは、ユーザー名を認識してユーザーを識別します。件名種別は、サービスプロバイダーを SAML 対応アプリケーションとして統合するときに指定します。

[件名種別] が [統合 ID] である場合は、ユーザーの Salesforce 設定で統合 ID を指定する必要があります。統合 ID を更新することで、Salesforce が SAML アサーションを送信したときにサービスプロバイダーはユーザーを認識できます。

同時に複数のユーザーを対応付けるには、SOAP API を使用します。詳細は、『SOAP API 開発者ガイド』を参照してください。

組織内の個別ユーザーをサービスプロバイダーに対応付けるには、以下の手順を実行します。

  1. [設定] から、[クイック検索] ボックスに「ユーザー」と入力し、[ユーザー] を選択します。
  2. ユーザーを見つけて、ユーザー名の横にある [編集] をクリックします。
  3. [統合 ID] の [シングルサインオン情報] に、サービスプロバイダーが認識できる ID を入力します。たとえば、サービスプロバイダーへのログインに使用するユーザー名を入力します。
  4. 変更内容を保存します。

SAML サービスプロバイダー統合の前提条件の完了

サービスプロバイダーを Salesforce に統合する前に、組織を ID プロバイダーとして有効化して、SAML シングルサインオン (SSO) 情報をサービスプロバイダーと交換します。

必要なエディション

使用可能なインターフェース: Salesforce Classic および Lightning Experience の両方
使用可能なエディション: Developer Edition、Enterprise Edition、Performance Edition、Unlimited Edition、および Database.com Edition
必要なユーザー権限
ID プロバイダーとサービスプロバイダーの定義と変更 「アプリケーションのカスタマイズ」

開始する前に、SalesforceをIDプロバイダーとして有効化します。

  1. Salesforce の ID プロバイダーとしての設定に関するサービスプロバイダー情報を指定します。この情報は、サービスプロバイダーがサポートする形式により、XML ファイルのメタデータ、または証明書として共有できます。この情報にアクセスするには、次の手順を実行します。
    1. [設定] の [クイック検索] ボックスに「ID プロバイダー」と入力し、[ID プロバイダー] を選択します。
    2. サービスプロバイダーがメタデータをサポートしている場合は [メタデータのダウンロード] をクリックします。サービスプロバイダーが証明書をサポートしている場合は [証明書のダウンロード] をクリックします。
    メモ Salesforce では、サービスプロバイダーに送信される SAML アサーションの存続期間も定義します。Salesforce ID プロバイダーによって送信された SAML アサーションは、発行から 5 分間有効であり、クロックスキューに対応する 30 秒のバッファがあります。たとえば、アサーションが 12:00:00 GMT に発行された場合、11:59:30 GMT から 12:05:00 GMT の間有効になります。通常、サービスプロバイダーは、この期間以外に SAML 応答を受信してもアサーションを拒否します。この要件に適合するようにサービスプロバイダーと協力します。
  2. サービスプロバイダーから次の設定情報を取得します。
    • アサーションコンシューマーサービス (ACS) URL — ID プロバイダーが SAML 応答を送信する URL。
    • エンティティ ID — サービスプロバイダーの一意の識別子。
    • 件名種別 — サービスプロバイダーが想定する、Salesforce がユーザー ID 情報を送信する SAML アサーション内の場所を指定。Salesforce は、アサーションの件名またはカスタム属性でユーザー情報を送信できます。
    • セキュリティ証明書 — サービスプロバイダーが Salesforce 経由でログインを開始し、SAML 要求に署名する場合に必要になります。
  3. 機密性の高いリソースの保護を強化するには、サービスプロバイダーで強制認証を設定します。強制認証では、すでに Salesforce にログインしているユーザーでも、サービスプロバイダーにアクセスしようとするときにログイン情報を再入力する必要があります。

    強制認証を設定するには、サービスプロバイダーと協力して ForceAuthn パラメーターを SAML 要求に追加します。次の強制認証 SAML 要求の例を共有できます。SSO 中にサービスプロバイダーはこのパラメーターを使用して、ユーザーの再認証が必要であることを Salesforce に通知します。組織で追加設定を行う必要はありません。Salesforce が ID プロバイダーとして機能する場合、強制認証は自動的にサポートされます。

    Salesforce が強制認証で受け入れる SAML 要求の例を次に示します。

    <?xml version="1.0" encoding="UTF-8"?>
<samlp:AuthnRequest 
  AssertionConsumerServiceURL="ACS_URL" 
  Destination="IDP_INIT_LOGIN_URL" 
  Version="2.0" 
  IssueInstant="2011-05-20T13:01:00.000Z'
  ProviderName="https://saml.salesforce.com"
  ProtocolBinding="urn:oasis:names:tc:SAML:2.0:bindings:HTTP-POST"
  xmlns:samlp="urn:oasis:names:tc:SAML:2.0:protocol"
  ForceAuthn = "true">
  <saml:Issuer xmlns:saml="urn:oasis:names:tc:SAML:2.0:assertion">ENTITY_ID</saml:Issuer>
</samlp:AuthnRequest>

これらの前提条件を完了したら、次の手順を実行します。

  • サービスプロバイダーを SAML 対応アプリケーションとして統合します。
  • Salesforce ユーザーをサービスプロバイダーに対応付けます。

シングルログアウト

シングルログアウト (SLO) を使用すると、ユーザーは ID プロバイダーまたはサービスプロバイダーのいずれかからログアウトすることで、両方からログアウトできます。Salesforce がサービスプロバイダーか ID プロバイダーかに関係なく、SAML または OpenID Connect を使用して SLO を有効化できます。SLO は、個々のアプリケーションすべてから手動ログアウトを削除することで、セキュリティを強化し、ユーザーの時間を節約できます。

SLO は、サービスプロバイダーまたは ID プロバイダーのいずれかから開始できます。たとえば、Salesforce が ID プロバイダーである場合、ユーザーはシングルサインオン (SSO) を使用して、Salesforce からログアウトしてサービスプロバイダーから自動的にログアウトできます。また、ユーザーはサービスプロバイダーからログアウトして、Salesforce からログアウトすることもできます。

SLO を使用するには、SSO が使用できるように ID プロバイダーおよびサービスプロバイダーを設定し、SLO に登録する必要があります。

現在、Salesforce では、フロントチャネル SLO のみがサポートされています。つまり、SLO リダイレクトは、同じブラウザーで実行する必要があります。異なるブラウザー全体での SLO はサポートされていません。ユーザーは、ブラウザーを介して外部クライアントアプリケーションまたは接続アプリケーションから明示的にログアウトする場合にのみ、登録済みアプリケーションからログアウトされます。ブラウザーセッションが期限切れになっても、SLO に登録されている他のアプリケーションからはログアウトされません。

Salesforce では、次のプロトコルがサポートされています。

  • SAML SLO (ID プロバイダーまたはサービスプロバイダーとして)
  • OpenID Connect SLO (ID プロバイダーまたは証明書利用者として)
  • SAML シングルログアウトの設定 (Salesforce がサービスプロバイダーの場合)
    SAML ID プロバイダーのシングルログアウト (SLO) を設定します。SAML SLO を使用すると、ユーザーは Salesforce または ID プロバイダーのいずれかからログアウトすることで両方からログアウトできます。
  • OpenID Connect シングルログアウトの設定 (Salesforce が証明書利用者の場合)
    OpenID Connect プロバイダーとして機能する認証プロバイダーのシングルログアウト (SLO) を設定します。OpenID Connect SLO を使用すると、ユーザーは Salesforce または OpenID Connect プロバイダーのいずれかからログアウトすることで両方からログアウトできます。
  • SAML シングルログアウトの設定 (Salesforce が ID プロバイダーの場合)
    SAML サービスプロバイダーのシングルログアウト (SLO) を設定します。SAML SLO を使用すると、ユーザーは Salesforce またはサービスプロバイダーのいずれかからログアウトすることで両方からログアウトできます。
  • OpenID Connect シングルログアウトの設定 (Salesforce が OpenID Connect プロバイダーの場合)
    OpenID Connect 証明書利用者として機能する既存の接続アプリケーションのシングルログアウト (SLO) を設定します。OpenID Connect SLO を使用すると、ユーザーは Salesforce または証明書利用者のいずれかからログアウトすることで両方からログアウトできます。
  • SAML セッションインデックスのサポート
    Salesforce では、SAML シングルログアウト (SLO) の要求と応答でセッションインデックスパラメーターがサポートされます。SAML SLO 用に登録された接続アプリケーションからユーザーがログアウトする場合は、終了するユーザーセッションを識別するためにセッションインデックスパラメーターが必要です。

SAML セッションインデックスのサポート

Salesforce では、SAML シングルログアウト (SLO) の要求と応答でセッションインデックスパラメーターがサポートされます。SAML SLO 用に登録された接続アプリケーションからユーザーがログアウトする場合は、終了するユーザーセッションを識別するためにセッションインデックスパラメーターが必要です。

Salesforce が ID プロバイダーの場合、SAML シングルサインオン (SSO) 時に Salesforce がセッションインデックスパラメーターを生成してサービスプロバイダーに送信します。SLO を開始するアプリケーションに応じて、次のプロセスのいずれかが発生します。

  • Salesforce が SLO を開始した場合、Salesforce は同じセッションインデックスパラメーターをログアウト要求と共にサービスプロバイダーに送信します。
  • サービスプロバイダーが SLO を開始した場合、Salesforce は、現在のセッションに参加している他のサービスプロバイダーに SAML SLO 要求を送信します。他のサービスプロバイダーはログアウト応答を Salesforce に投稿します。その後、Salesforce はログアウト応答を開始サービスプロバイダーに返します。

Salesforce がサービスプロバイダーの場合、Salesforce は SSO 時に ID プロバイダーから送信されたセッションインデックスパラメーターを受信して保存します。ID プロバイダーが SLO を開始した場合、Salesforce はログアウト応答を送信します。Salesforce が SLO を開始した場合、Salesforce はログアウト要求と同じセッションインデックスパラメーターを ID プロバイダーに送信します。

メモ ID プロバイダーが複数のセッションインデックスパラメーターを送信した場合は、Salesforce は最初に受信したもののみを保存します。セッションインデックスパラメーターは、512 文字を超えることはできません。

シングルサインオン

シングルサインオン (SSO) は、ユーザーが 1 回のログインと 1 セットのログイン情報で複数のアプリケーションにアクセスできるようにする認証方法です。たとえば、ユーザーが組織にログインすると、自動的にアプリケーションランチャーからすべてのアプリケーションにアクセスできます。ユーザーを認証するためにサードパーティ ID プロバイダーを信頼するように Salesforce 組織を設定できます。または、組織を使用して認証するようにサードパーティアプリケーションを設定することもできます。

SSO を設定する場合、ユーザーの認証で 1 つのシステムが別のシステムを信頼するように設定するため、ユーザーは各システムに個別にログインする必要がなくなります。ユーザーを認証するシステムは、ID プロバイダーと呼ばれます。認証で ID プロバイダーを信頼するシステムは、サービスプロバイダーと呼ばれます。

たとえば、組織にアクセスするユーザーを認証する ID プロバイダーとして Google を設定できます。そのため、ユーザーは Google ログイン情報を使用して組織にログインします。この例では、組織はサービスプロバイダーとして機能し、ユーザーの正確な認証について Google を信頼します。

Salesforce 組織を ID プロバイダー、サービスプロバイダー、またはその両方として設定できます。これらの各使用事例で、使用する認証プロトコルを選択します。Salesforce は、SAML および OpenID Connect を使用した SSO をサポートしています。Salesforce には、Facebook などの独自の認証プロトコルがあるシステムで SSO を有効にするために使用できる、事前設定された認証プロバイダーも用意されています。詳細は、「シングルサインオン使用事例」を参照してください。Salesforce が ID プロバイダーになっている SAML SSO の実装を確認するには、この動画をご覧ください。

複数のサービスプロバイダーのユーザーを認証するように 1 つの ID プロバイダーを設定することもできます。たとえば、組織を ID プロバイダーとして有効にし、Workday と Office 365 をサービスプロバイダーとして設定できます。その場合、ユーザーは 1 回のログインで組織、Workday、および Office 365 にアクセスできます。

SSO を設定したら、ユーザーがサービスプロバイダーと ID プロバイダーから同時にログアウトできるようにシングルログアウトを設定します。

  • シングルログアウト
    シングルログアウト (SLO) を使用すると、ユーザーは ID プロバイダーまたはサービスプロバイダーのいずれかからログアウトすることで、両方からログアウトできます。Salesforce がサービスプロバイダーか ID プロバイダーかに関係なく、SAML または OpenID Connect を使用して SLO を有効化できます。SLO は、個々のアプリケーションすべてから手動ログアウトを削除することで、セキュリティを強化し、ユーザーの時間を節約できます。
  • 代理認証
    代理認証はシングルサインオン (SSO) に似ていますが、ユーザーの操作が若干異なります。代理認証では、システムが別のシステムを使用してユーザーのログイン情報を検証します。たとえば、Lightweight Directory Access Protocol (LDAP) サーバーを使用してログイン情報を検証するように Salesforce 組織を設定できます。SSO と代理認証の両方とも、ユーザーは 1 セットのログイン情報で複数のアプリケーションにログインできます。ただし代理認証では、ユーザーが各アプリケーションに個別にログインする必要があります。

シングルサインオン認証と承認フロー

ほとんどの認証プロバイダーには 2 つの目的があります。SSO でのユーザー認証に加えて、ユーザーデータへのアクセス権の提供です。SSO でログインした後、このサードパーティデータへのアクセス権を使用して、ユーザーの Salesforce プロファイルを追加の情報で強化できます。

たとえば、あるユーザーが Facebook ログイン情報を使用して Salesforce にログインした場合、そのユーザーは Facebook データへのアクセスを承認できます。Facebook データへのアクセスが承認された場合、Facebook は Salesforce にアクセストークンを送信します。このアクセストークンを使用して Facebook プロファイルデータにアクセスすることで、ユーザーの Salesforce ユーザープロファイルにデータを追加できます。

認証プロバイダーの設定

認証プロバイダーの設定には、次の概要手順が含まれます。

  • 登録ハンドラーを作成します。登録ハンドラーは実装の重要な部分です。SSO 中にユーザーの作成と更新を行う面倒な作業を処理します。Apex または Flow Builder を使用して登録ハンドラを設定できます。
  • 認証プロバイダーを定義します。このステップには、ID プロバイダーでのアプリケーションの作成、[設定] での認証プロバイダーの作成、登録ハンドラーを使用するようにプロバイダーの設定が含まれます。
  • 組織または Experience Cloud サイトのログインページにプロバイダーを追加します。
  • 必要に応じて、要求パラメーターを使用して認証プロバイダーに機能を追加します。
  • 認証プロバイダー登録ハンドラーの作成
    認証プロバイダーを使用してシングルサインオン (SSO) を設定するには、登録ハンドラーを設定する必要があります。登録ハンドラーは、ID プロバイダーによる認証後に Salesforce ユーザーを作成および更新します。登録ハンドラを設定するには、Flow Builder または Apex を使用できます。
  • 認証プロバイダーの定義
    シングルサインオン (SSO) に認証プロバイダーを使用するには、[設定] でサードパーティ ID プロバイダーの設定情報を使用して認証プロバイダーを定義します。セキュリティ設定を制御し、エラー URL とログアウト URL を使用して SSO 環境をカスタマイズし、登録ハンドラー設定を定義します。GitHub、Microsoft Access Control Service、X (旧 Twitter) を除き、ほとんどの認証プロバイダーはシングルサインオン (SSO) とサードパーティデータアクセスをサポートしています。
  • 組織のログインページへの認証プロバイダーの追加
    認証プロバイダーを設定したら、組織のログインページに追加して、従業員が簡単に使用できるようにします。
  • Experience Cloud サイトのログインページへの認証プロバイダーの追加

Salesforce ID プロバイダーの設定

組織またはサイトを認証ハブとして機能する ID プロバイダーとして設定します。サイトを ID プロバイダーとして有効化するには、サイトが設定されている組織で次の手順を実行します。

  1. [設定] の [クイック検索] ボックスに「ID プロバイダー」と入力し、[ID プロバイダー] を選択します。[ID プロバイダーを有効化] をクリックします。
  2. ID プロバイダーとサービスプロバイダーが互いに信頼するために使用できる証明書を選択します。組織を ID プロバイダーとして有効にすると、Salesforce で自己署名証明書が自動的に作成されます。独自の証明書を作成するには、[新規証明書の作成] を選択します。
  3. 証明書を保存します。証明書を変更した場合は、[OK] をクリックして警告メッセージを受け入れます。
  4. [ID プロバイダー] ページで [証明書のダウンロード] をクリックします。これは、サービスプロバイダーを設定するときに使用します。
  5. サービスプロバイダーと共有する SAML メタデータを取得します。このメタデータは、サービスプロバイダーで SAML 設定を行うときに使用します。このステップは、組織とサイトで異なります。
    • ID プロバイダーが組織の場合、[メタデータのダウンロード] をクリックして、XML ファイルでメタデータを取得します。XML メタデータファイルを参照する URL を取得するには、[SAML のメタデータ検出エンドポイント] にリストされている Salesforce の ID URL をコピーします。
    • ID プロバイダーがサイトである場合は、[SAML のメタデータ検出エンドポイント] にある Experience Cloud サイトの ID URL をコピーします。

Salesforce サービスプロバイダーの設定

サービスプロバイダー組織またはサイト (認証ハブに依存するスポーク) を設定します。サービスプロバイダー組織、またはサービスプロバイダーサイトが有効になっている組織で、次の手順を実行します。

  1. [設定] から [クイック検索] ボックスに「シングルサインオン設定」と入力し、[シングルサインオン設定] を選択します。
  2. [編集] をクリックします。SAML SSO 設定を表示するには、[SAML を有効化] を選択します。変更内容を保存します。
  3. [SAML シングルサインオン設定] で、適切なボタンをクリックして設定を作成します。
    1. ID プロバイダーから XML メタデータファイルをダウンロードした場合は、[メタデータファイルから新規作成] をクリックします。保存したメタデータファイルをアップロードして、[作成] をクリックします。このオプションでは、XML ファイルのメタデータを使用して SSO 設定を完了します。
    2. Salesforce または Experience Cloud サイトの ID URL を ID プロバイダーからコピーした場合は、[メタデータ URL から新規作成] をクリックします。URL 入力を貼り付けて、[作成] をクリックします。このオプションでは、Salesforce の ID URL にある XML ファイルを読み取り、その内容を使用して SSO 設定を完了します。
    メタデータオプションでは、[発行者]、[エンティティ ID]、[ID プロバイダーのログイン URL] 項目を含め、必須の SAML 設定を入力します。
  4. [ID プロバイダーの証明書] では、以前に ID プロバイダーからダウンロードした証明書をアップロードします。
  5. [SAML ID 種別] で、[アサーションには、ユーザーオブジェクトの統合 ID が含まれます] を選択します。
  6. 設定を保存します。次に、[シングルサインオン設定] ページから、エンティティ ID をコピーして保存します。 接続アプリケーションの作成時に、この値を ID プロバイダーと共有します。
  7. 同じページから、ID プロバイダーと共有する SAML ログインエンドポイントを取得します。このステップは、組織とサイトで異なります。
    1. 組織をサービスプロバイダーとして設定するには、[組織] の下にあるログイン URL をコピーします。
    2. サイトをサービスプロバイダーとして設定するには、[コミュニティ用] の横にあるドロップダウン矢印をクリックします。サイトの SAML エンドポイントが表示されます。サイトのログイン URL をコピーします。
  8. サービスプロバイダーで、認証サービスとして ID プロバイダーを追加します。
    1. [設定] から、[クイック検索] ボックスに「私のドメイン」と入力し、[私のドメイン] を選択します。
    2. [認証設定] で [編集] をクリックします。
    3. ID プロバイダーの認証サービスを選択します。

      ユーザーがサービスプロバイダーに直接ログインできないようにするには、[ログインフォーム] をオフにします。ユーザーは、サービスプロバイダーのログイン URL にアクセスすると、ID プロバイダーにリダイレクトされてログインします。

      サービスプロバイダーに直接ログインするオプションをユーザーに提供するには、[ログインフォーム] と [私の Salesforce ID プロバイダー] をオンにします。これらの両方のオプションがオンになっている場合、ID プロバイダーがサービスプロバイダーのログインページのログインオプションとして表示されます。ユーザーは、サービスプロバイダーに直接ログインするか、SSO を使用してログインするかを決定できます。

  9. サービスプロバイダーとして他の組織を定義するには、これらの手順を繰り返します。ID プロバイダーの SAML メタデータを使用して、サービスプロバイダーの SSO 設定を完了します。

接続アプリケーションとしてのサービスプロバイダーの統合

ID プロバイダーに対してサービスプロバイダーを定義するには、ID プロバイダーで接続アプリケーションを作成します。

  1. ID プロバイダーの [設定] から、[クイック検索] ボックスに「外部クライアントアプリケーション」と入力し、[外部クライアントアプリケーション] セクションの [設定] を選択します。
  2. [Allow create of connected apps (接続アプリケーションの作成を許可)] をオンにします (オフの場合)。
  3. [新規接続アプリケーション] をクリックします。
  4. 接続アプリケーションの基本情報を入力します。
  5. [Web アプリケーション設定] で、[SAML の有効化] を選択します。サービスプロバイダーを設定したときに保存したエンティティ ID とログイン URL の値を覚えていますか?これらの値を使用して接続アプリケーションの設定を完了する必要があります。
    1. [エンティティ ID] に、サービスプロバイダーのエンティティ ID を貼り付けます。
    2. [ACS URL] に、組織またはサイトのログイン URL を貼り付けます。
    3. [件名種別] で、[統合 ID] を選択します。
  6. 設定を保存します。
  7. ユーザーにこのサービスプロバイダーへのアクセス権を付与するには、[接続アプリケーション] ページで [管理] をクリックします。[プロファイルを管理する] または [権限セットの管理] を選択し、サービスプロバイダーにアクセスするプロファイルまたは権限セットを追加します。プロファイルと権限セットについての詳細は、「データアクセスの管理」および「接続アプリケーションの他のアクセス設定の管理」を参照してください。
  8. ID プロバイダーでは、各サービスプロバイダーの独自の接続アプリケーションが必要です。他のサービスプロバイダーを定義するには、これらの手順を繰り返します。

SSO 接続のテスト

ID プロバイダーからサービスプロバイダーにテストユーザーを対応付け、テストユーザーが SSO を使用してログインできることを確認します。

  1. ID プロバイダーで、テストユーザーを作成します。
    1. [設定] から、[クイック検索] ボックスに「ユーザー」と入力し、[ユーザー] を選択します。
    2. [新規ユーザー] をクリックします。
    3. テストユーザーの基本情報を入力し、サービスプロバイダーにアクセスできるプロファイルをユーザーに割り当てます。
    4. [シングルサインオン情報] で、一意の統合 ID を入力します。 統合 ID には任意の値を指定できます。ユーザーの識別および対応付けについての詳細は、「SAML サービスプロバイダーへの Salesforce ユーザーの対応付け」を参照してください。
    5. 設定を保存します。
  2. サービスプロバイダーで、同じテストユーザーを作成します。ユーザーをバインドするには、ID プロバイダーでテストユーザー用に入力した統合 ID を使用します。
  3. シークレットブラウザーで、ID プロバイダーの [私のドメイン] の URL を入力します。
  4. テストユーザーとして ID プロバイダーにログインします。
  5. 新しいシークレットブラウザータブで、サービスプロバイダーの [私のドメイン] の URL を入力します。

SSO が成功すると、ID プロバイダーにリダイレクトされます。すでに認証されているため、その後に再びサービスプロバイダーにリダイレクトされてログインします。

ID プロバイダーチェーンの作成

Salesforce 組織とサードパーティクライアントアプリケーションでユーザーを同時に認証するには、ID プロバイダーチェーンを作成します。この SSO 設定では、サードパーティが Salesforce のユーザーを認証し、Salesforce がクライアントアプリケーションのユーザーを認証します。ユーザーは、サードパーティにログインして、Salesforce およびクライアントアプリケーションにすぐにアクセスできます。ID プロバイダーは、SAML または OpenID Connect と排他的に連結できます。または、2 つの異なる認証プロトコルを実装するチェーンを作成できます。

使用可能なインターフェース: Salesforce Classic および Lightning Experience の両方

統合認証を使用可能なエディション: すべてのエディション

代理認証を使用可能なエディション: Professional Edition、Enterprise Edition、Performance Edition、Unlimited Edition、Developer Edition、および Database.com Edition

認証プロバイダーを使用可能なエディション: Professional Edition、Enterprise Edition、Performance Edition、Unlimited Edition、および Developer Edition

SAML 専用チェーンの作成

SAML 専用チェーンは、Salesforce とクライアントアプリケーションの両方がサービスプロバイダーの起動による SAML SSO 用に設定されている場合には特に効果的です。SAML を使用して ID プロバイダーチェーンを作成する手順は、次のとおりです。

  1. サードパーティ ID プロバイダーのサービスプロバイダーとして Salesforce を使用した SAML SSO。
  2. クライアントアプリケーションの SAML ID プロバイダーとしての Salesforce。

SAML ID プロバイダーチェーンを設定したら、ユーザーはサードパーティ ID プロバイダーから Salesforce にログインし、クライアントアプリケーションにすぐにアクセスできます。サードパーティ ID プロバイダーは Salesforce のユーザーを認証し、Salesforce はクライアントアプリケーションのユーザーを認証します。

たとえば、ユーザーが Google にログインして、Salesforce とモバイルカスタマーサービスアプリケーションに直接アクセスできるようにするとします。SAML 専用チェーンを作成するには、組織を SAML サービスプロバイダー、Google を ID プロバイダーとして定義します。次に、サービスプロバイダーとして機能するモバイルカスタマーサービスアプリケーションの SAML ID プロバイダーとして Salesforce を設定します。

OpenID Connect 専用チェーンの作成

OpenID Connect を使用する場合は、Salesforce のユーザーを認証するサードパーティ認証プロバイダーを設定できます。認証プロバイダーは、ユーザーを認証して Salesforce にログインできるようにするだけでなく、Salesforce による保護されているサードパーティデータへのアクセスも承認します。OpenID Connect を使用して ID プロバイダーチェーンを作成する手順は、次のとおりです。

  1. サードパーティ OpenID Connect プロバイダーの OpenID Connect を使用した認証プロバイダーを設定します。認証プロバイダーは、ユーザーがサードパーティのログイン情報で Salesforce にログインできるようにします。
  2. クライアント アプリケーションのOpenID Connectを使用して、サービスプロバイダーを接続アプリケーションとして統合します。OpenID Connect を使用する場合は、Salesforce を ID プロバイダーとして有効化する必要はありません。

OpenID Connect ID プロバイダーチェーンを設定したら、ユーザーはサードパーティ認証プロバイダーから Salesforce にログインし、クライアントアプリケーションにすぐにアクセスできます。サードパーティ認証プロバイダーは Salesforce のユーザーを認証し、Salesforce はクライアントアプリケーションのユーザーを認証します。

たとえば、ユーザーが Amazon のログイン情報で組織にログインしてから、カスタムモバイルアプリケーションにログインできるようにするとします。このチェーンを作成するには、Amazon の OpenID Connect 認証プロバイダーを設定することで、ユーザーが Amazon から組織にログインできるようにします。その後、組織を ID プロバイダーとして有効化して、カスタムモバイルアプリケーションを OpenID Connect 接続アプリケーションとして統合します。

2 つのプロトコルを実装するチェーンの作成

異なるプロトコルを実装している 2 つのアプリケーションがある場合は、Salesforce を使用してそれらをリンクできます。SAML と OpenID Connect を実装する ID プロバイダーチェーンを作成できます。また、カスタム認証プロトコルを実装するサードパーティを使用してチェーンを設定することもできます。

たとえば、ユーザーが Facebook のログイン情報で Salesforce にログインして、Workday に直接アクセスできるようにするとします。Facebook は独自のカスタム認証プロトコルを実装しており、Workday は SAML を使用しています。ユーザーが Facebook から Salesforce、Workday に簡単に移動できるように SSO を設定する方法を次に示します。

  1. Facebook 認証プロバイダーを設定し、Facebook が Salesforce のユーザーを認証できるようにします。
  2. Workday のユーザーを認証する SAML ID プロバイダーとしての Salesforce。

Salesforce は、カスタムプロトコルを実装するサードパーティ向けに定義済み認証プロバイダーをいくつか提供しています。Apex を使用してカスタム認証プロバイダーを作成することもできます。詳細は、「認証プロバイダー SSO」を参照してください。

認証プロバイダー登録ハンドラーの作成

認証プロバイダーを使用してシングルサインオン (SSO) を設定するには、登録ハンドラーを設定する必要があります。登録ハンドラーは、ID プロバイダーによる認証後に Salesforce ユーザーを作成および更新します。登録ハンドラを設定するには、Flow Builder または Apex を使用できます。

必要なエディション

使用可能なインターフェース: Lightning Experience および Salesforce Classic
使用可能なエディション: Enterprise Edition、Performance Edition、Unlimited Edition、および Developer Edition

登録ハンドラーの役割

SSO 中の登録ハンドラーのロールを理解するために、SSO が認証プロバイダーフレームワークでどのように機能するかを簡単に説明します。

  • (1) エンドユーザーが Salesforce に移動して、Google などの ID プロバイダーを使用してログインするボタンをクリックします。
  • (2) Salesforce がユーザーのブラウザーを ID プロバイダーのログインページにリダイレクトします。
  • (3) ID プロバイダーのログインページで、ユーザーはログイン情報を入力します。
  • (4) ID プロバイダーがユーザーを認証し、ID トークンを含むトークンを Salesforce に返します。
  • (5) ID プロバイダーがユーザー情報エンドポイントをサポートしている場合、Salesforce はトークンを使用してユーザー情報応答を要求します。
  • (6) ID プロバイダーがサポートしている場合、ユーザー情報応答を返します。
  • (7) ID プロバイダーから返された情報を使用して、Salesforce はユーザーを表す Apex Auth.UserDataオブジェクトを作成します。
  • (8) Salesforce で、登録ハンドラーが ID プロバイダーから情報を取得し、次のアクションを実行します。
    • 登録ハンドラーは、ID プロバイダーから返された情報と一致する情報を持つ Salesforce ユーザーを検索します。
    • 一致するユーザーがいない場合、登録ハンドラーはユーザーレコードを作成します。
    • 一致するユーザーがいる場合、登録ハンドラーは ID プロバイダーからの情報でユーザーレコードを更新します。
  • (9) 作成または更新されたユーザーが Salesforce にログインし、Salesforce データにアクセスできる。

登録ハンドラー種別の選択

登録ハンドラー種別を選択する前に、登録ハンドラーの基本設計を考慮してください。その設計を把握しておくと、使用事例にフローと Apex のどちらが適しているかを判断しやすくなります。少なくとも、登録ハンドラーは次のタスクを実行する必要があります。

  • ID プロバイダーから情報を取得し、Salesforce で一致するユーザーレコードを探します。ID プロバイダーによっては、このステップで複雑な JSON 構造の解析が必要になる場合があります。
  • ユーザーを作成するか、既存のユーザーを更新するかを決定します。
  • ID プロバイダーからの情報に基づいて完全なユーザーレコードを作成します。
  • ID プロバイダーからの情報で既存のユーザーを更新します。

使用する登録ハンドラーの種別に関する明確なルールはありません。これらの考慮事項を確認するときに、登録ハンドラーに何を実行させ、どのようなリソースを使用できるかを検討します。

代理認証

代理認証はシングルサインオン (SSO) に似ていますが、ユーザーの操作が若干異なります。代理認証では、システムが別のシステムを使用してユーザーのログイン情報を検証します。たとえば、Lightweight Directory Access Protocol (LDAP) サーバーを使用してログイン情報を検証するように Salesforce 組織を設定できます。SSO と代理認証の両方とも、ユーザーは 1 セットのログイン情報で複数のアプリケーションにログインできます。ただし代理認証では、ユーザーが各アプリケーションに個別にログインする必要があります。

必要なエディション

使用可能なインターフェース: Salesforce Classic と Lightning Experience の両方
使用可能なエディション: Professional Edition、Enterprise Edition、Performance Edition、Unlimited Edition、Developer Edition、および Database.com Edition

代理認証を設定し、ユーザーが Web サービスにラップされた外部認証方法で管理されるログイン情報を使用して、Salesforce 組織にログインできるようにします。ユーザーが組織にログインしようとすると、Salesforce はこの Web サービスをコールしてユーザーのログイン情報を検証します。代理認証では、Salesforce は組織へのログインに使用されるパスワードを制御できません。代わりに、外部認証方法でユーザーパスワードおよび関連ポリシーを制御します。

Salesforce が使用できる Web サービスでラップしていれば、任意の認証方法を使用できます。たとえば、認証方法として Lightweight Directory Access Protocol (LDAP) サーバーを使用し、SOAP ベースの Web サービスでラップできます。認証バックエンドを Salesforce と統合したら、Salesforce の権限を使用して、Salesforce ログイン情報ではなく代理認証を使用してログインするユーザーを制御できます。

たとえば、会社が従業員用に LDAP サーバーを使用しているとします。LDAP サーバーを使用して、Salesforce へのユーザー認証を行いたいと考えています。また、ユーザープロファイルの権限を使用して、ユーザーが LDAP と Salesforce のどちらで認証するかも決定したいと考えています。具体的には、標準プロファイルを持つユーザーは LDAP サーバーで管理されるパスワードでログインし、システム管理者プロファイルは Salesforce パスワードを使用するようにします。そのため、LDAP サーバーを SOAP ベースの Web サービスでラップすることで、組織を LDAP サーバーと統合します。標準プロファイルを持つユーザーのみが代理認証を使用するようにする権限を作成します。これで、標準プロファイルを持つユーザーは Salesforce のユーザー名を入力し、パスワードは LDAP サーバーが処理します。システム管理者プロファイルを持つユーザーは、Salesforce のユーザー名とパスワードを入力します。

ユーザーパスワードの制御を外部認証方法に渡すため、「シングルサインオンの有効」ユーザー権限を有効にします。Salesforce は、ユーザーパスワードのポリシー (パスワードの有効期限や必要な最小限の長さなど) を管理しなくなります。代わりに、代理認証エンドポイントのサービスがパスワードポリシーを適用します (存在する場合)。

Salesforce で代理認証を使用してユーザーを認証するプロセスは次のとおりです。

メモ 代理認証を使用すると、ログイン時にユーザーアカウントが組織で使用可能になるまでわずかな遅れを感じることがあります。
  1. ユーザーが、オンラインまたは API の使用のいずれかでログインしようとすると、Salesforce はユーザー名を確認し、そのユーザーの権限とアクセス設定をチェックします。
  2. 「シングルサインオンの有効」ユーザー権限が有効になっている場合、Salesforce は SOAP ベースの SSO Web サービスをコールし、ユーザー名とパスワードを確認します。
    メモ Salesforce はパスワードを保存、記録、表示することなく、すぐに破棄します。
  3. Web サービスコールは、ユーザー名、パスワード、アクセス元 IP を SSO Web サービスの実装に渡し、Salesforce サーバーがそれらにアクセスします。アクセス元 IP は、ログイン要求を出した IP アドレスです。
  4. SSO Web サービスの実装では、渡された情報を確認し、true または false を返します。
  5. 応答が true ならば、ログイン処理を続行して、ユーザーが組織にログインします。false の場合、ユーザーにはユーザー名とパスワードの組み合わせが無効であることを示すエラーメッセージが表示されます。

  1. Salesforce で、代理認証 Web サービス記述言語 (WSDL) ファイルをダウンロードします。
    1. [設定] から、[クイック検索] ボックスに「API」と入力し、[API] を選択します。
    2. [代理認証 WSDL をダウンロード] をクリックします。

    WSDL ファイルには代理認証 Web サービスが記述されています。WSDL ファイルを使用して、代理認証実装を追加するサーバー側スタブを生成します。たとえば、Apache Axis から入手できる WSDL2Java ツールでは、--server-side スイッチを使用します。.NET wsdl.exe ツールでは、/server スイッチを使用します。

  2. 企業イントラネットまたはその他の内部サイトへのリンクを追加します。このリンクは、確認されたユーザーのログイン情報を取得し、それを HTTP POST 経由で Salesforce ログインページに渡します。

    Salesforce はパスワード項目のみを使用し、それを企業に戻します。企業のパスワードを Salesforce との間で受け渡ししないようにするには、代わりに Kerberos チケットなどの別の認証トークンを渡します。

    Salesforce サーバーから Authenticate メッセージでログイン情報が戻されたら、それを確認します。その後、ユーザーは組織にアクセスできるようになります。

  1. [設定] から [クイック検索] ボックスに「シングルサインオン」と入力し、[シングルサインオン設定] を選択します。
  2. [編集] をクリックします。
  3. [代理ゲートウェイ URL] に URL を入力します。

セキュリティ上の理由から、Salesforce では、送信投稿を次のうちいずれかに制限します。

  • 80: HTTP 接続のみを受け付けます。
  • 443: HTTPS 接続のみを受け付けます。
  • 1024 ～ 66535: HTTP 接続または HTTPS 接続を受け付けます。

  1. [設定] から [クイック検索] ボックスに「シングルサインオン」と入力し、[シングルサインオン設定] を選択します。

認証プロバイダーのユーザー登録にフローを使用する場合、フローの実行時にのみ明らかになるエラーがいくつかあります。実行エラーに基づいてフローを更新する方法について説明します。

ユーザー登録のフローを設定したら、必ずフローを詳細にテストして、ユーザーが正常に作成および更新されることを確認してください。フローをテストするには、新規ユーザーおよび既存のユーザーとしてログインします。ID プロバイダーで認証すると、Salesforce によってブラウザーがリダイレクトされます。フローの実行エラーがある場合、UI にエラーメッセージが表示されます。エラーメッセージは URL でも確認できます。

フローの起動方法

フローは開始要素で始まります。このフロー種別では、フローが認証プロバイダー定義で登録ハンドラーとして設定されている場合、SSO 中にフローが自動的に起動されます。ID プロバイダーはユーザーを認証すると、ユーザー情報を Salesforce に返します。Salesforce はこの情報を使用してAuth.UserDataオブジェクトを作成します。この時点で、フローが開始されます。

ID プロバイダーからの情報の取得

フローは最初に ID プロバイダーから情報を取得します。SalesforceはAuth.UserDataオブジェクトを作成するときに、IDプロバイダーのユーザー情報応答とIDトークンを公開します(返された場合)。これらの応答から特定の情報を取得するには、[JSON 文字列からユーザーデータを取得] アクションを使用できます。

メモ このステップは、ID プロバイダーがユーザー情報応答または ID トークンを返し、特定の情報を取得する場合にのみ必要です。

このアクションは 2 つの入力パラメーターを取ります。最初の入力パラメーターは JSON オブジェクト文字列です。このパラメーターでは、ユーザー情報応答または ID トークンを指定します。ユーザー情報応答または ID トークンを指定するには、Auth.UserDataオブジェクトの項目を参照します。

  • 完全なユーザー情報応答は userInfoJSONString フィールドに保存されます。
  • ID トークンの復号化された JSON Web トークン（JWT）ペイロードは、idTokenJSONString フィールドに保存されます。

テンプレートには、Auth.UserData オブジェクトを保存する Apex で定義された変数 authUserData が含まれています。この変数を使用して、{!authUserData.userInfoJSONString} などの入力パラメータとして authUserData のuserInfoJSONString項目またはidTokenJSONString項目を参照します。

2 番目の入力パラメーターは JSON 属性キーです。このパラメーターでは、取得する特定の属性の JSON 変数パスを指定します。たとえば、ネストされた属性を持つ JSON 文字列があるとします。

{"location": [ { "type": "office", "city": "San Francisco"}, {"type": "home", "city":"New York"}]}

最初の場所の type 属性の値を取得するには、次の JSON 変数パスを使用します: $.location[0].type。

このアクションは、属性の値を返し、その値を JsonValueOutput Apex クラスのインスタンスに保存します。フローの後半で簡単に使用するには、手動で変数に割り当てます。たとえば、テンプレートでは、このアクションでユーザー ID 値を取得して federationIdentifier 変数に保存します。Toolbox に移動して federationIdentifier をクリックすると、この Apex で定義された変数で JsonValueOutput クラスが使用されていることがわかります。

ユーザーを作成するか更新するかの決定

フローでユーザー情報を取得したら、フローの最初の決定 (ユーザーを作成するか既存のユーザーを更新するか) を行います。この複数要素にわたる意思決定を行うには、Salesforce がユーザーを ID プロバイダーにリンクする方法を理解することが重要です。

ユーザーが認証プロバイダーフレームワークを使用して ID プロバイダー経由で Salesforce にログインすると、Salesforce によって ThirdPartyAccountLink レコードが作成されます。フローでこのレコードを使用して、特定のユーザーがこの ID プロバイダーで以前に認証したかどうかを判断できます。

このプロセスを容易にするために、Salesforce ではフローに existingUserIdFromTpal 変数を含めています。この変数は入力可能としてマークされます。つまり、値はフロー外から取得されます。テンプレートでは、フローの実行時に Salesforce によってこの値が自動的に設定されます。値を設定するために、Salesforce は ID プロバイダーのサードパーティ識別子を使用して、一致する remoteIdentifier 値を持つ ThirdPartyAccountLink を検索します。ThirdPartyAccountLink が見つかった場合、Salesforce はその UserId の値を existingUserIdFromTpal 変数に保存します。

ユーザーが以前に ID プロバイダーで認証されている場合、ユーザーは Salesforce に存在し、フローでユーザーの更新を続行できます。テンプレートでは、ThirdPartyAccountLink を持つユーザーをリンク済みユーザーと呼びます。

ユーザーが ID プロバイダーで認証していない場合、そのユーザーが Salesforce に存在するかどうかはわかりません。ユーザーが Salesforce に存在するが、この ID プロバイダーを以前に使用していない可能性があります。ユーザーが存在するかどうかを判断するために、フローでは Auth.UserData オブジェクトで返された ID プロバイダーからの情報が使用されます。Auth.UserData オブジェクトの値と一致する属性値を持つユーザーレコードを検索します。

一致するユーザーが見つかった場合、フローは ID プロバイダーからのユーザー情報を更新します。テンプレートでは、存在するが ThirdPartyAccountLink を既存のユーザーとして持っていないユーザーを参照します。一致するユーザーがフローで見つからない場合は、ユーザーを作成します。

ユーザーの作成と権限セットの管理

フローで新規ユーザーのプロファイル、取引先、および取引先責任者の割り当てが処理されると、最終的にユーザーレコードが作成され、権限セットが割り当てられます。フローのこのセクションでは、次の手順を次の順序で実行することが重要です。

  • (1) ユーザーレコードを作成します。
  • (2) 新しいユーザー ID を userIdOutput 変数に割り当てます。Salesforce はバックグラウンドでこの変数を使用して権限セットの割り当てを完了します。
  • (3) 作成したユーザーに権限セットを割り当てます。

SAML 用のジャストインタイムプロビジョニング

ジャストインタイム (JIT) プロビジョニングを使用して、ユーザーが SAML ID プロバイダーで初めてログインしたときに、Salesforce 組織にユーザーアカウントを自動的に作成します。JIT プロビジョニングはユーザーをプロビジョニングしたりユーザーアカウントを事前に作成したりする必要がないため、作業負荷を軽減して時間を節約できます。

必要なエディション

使用可能なインターフェース: Salesforce Classic および Lightning Experience の両方
使用可能なエディション: すべてのエディション

JIT プロビジョニングでは、ID プロバイダーが SAML 2.0 アサーションでユーザー情報を Salesforce に渡します。これは、Apex JIT ハンドラークラスによって処理されます。JIT ハンドラーは、面倒な作業 (ユーザーアカウントの作成と更新) を実行します。JIT ハンドラーを Salesforce で管理できるようにするには、標準 JIT プロビジョニングを設定します。より詳細に制御する必要がある場合は、カスタムハンドラーを使用して JIT プロビジョニングを設定します。カスタム Apex ハンドラーについての詳細は、『Apex リファレンスガイド』の「SamlJitHandler インターフェース」を参照してください。

メモ ユーザーが JIT プロビジョニングで作成される場合、メールアドレスは自動的に検証されません。Spring '24 以降、シングルサインオン (SSO) ユーザーは検証済みのメールアドレスがない限り、Salesforce からメールを送信できません。JIT プロビジョニング対象ユーザーにメール送信機能が必要な場合は、メールアドレスを手動で検証します。方法については、「ユーザーメール検証」を参照してください。

SAML シングルサインオン設定

Salesforce をサービスプロバイダーとして使用して SAML シングルサインオン (SSO) を設定し、JIT プロビジョニングを有効にします。必要に応じて値を設定し、JIT プロビジョニングのサイトに固有の次の値を含めます。

  • [ユーザープロビジョニングの有効化] をオンにします。
    • ジャストインタイムプロビジョニングでは、ユーザー種別の統合 ID が必要です。[SAML のユーザー ID 種別] で、[アサーションには、ユーザーオブジェクトの統合 ID が含まれます] を選択します。
    • ID プロバイダーが Salesforce ユーザー名を以前使用していた場合は、統合 ID を使用する必要があることを ID プロバイダーに通知してください。
  • [エンティティ ID] は組織全体で一意であり、https で始まる必要があります。1 つの組織に [エンティティ ID] が同じ 2 つの SAML 設定を使用することはできません。[エンティティ ID] に基本ドメイン (https://saml.salesforce.com) を使用するか、サイト URL (https://acme.my.site.com/customers) を使用するかを指定します。この情報は、ID プロバイダーと共有します。
    ヒント 通常、エンティティ ID としてサイト URL を使用します。 Salesforce to Salesforce サービスを提供する場合、サイト URL を指定する必要があります。

    拡張ドメインを使用していない場合、組織の Experience Cloud サイトの URL は異なります。詳細は、Salesforce ヘルプの「[私のドメイン] の URL の形式」を参照してください。

  • [SAML のユーザー ID 種別] で、[アサーションには、ユーザーオブジェクトの統合 ID が含まれます] を選択します。ID プロバイダーが Salesforce ユーザー名を以前使用していた場合は、統合 ID を使用する必要があることを ID プロバイダーに通知してください。

受信 URL

SAML アサーションには Recipient URL が必要です。この URL は、SAML シングルサインオン設定詳細ページからのサイトログイン URL です。URL は次の形式を使用します。 

https://domainName/login?so=orgID

たとえば、acme.my.site.com/customers がサイトのホームページ、00DD0000000JsCM が組織 ID であるRecipient="https://acme.my.site.com/customers/login?so=00DD0000000JsCM"です。

アサーション復号化証明書が組織の SAML シングルサインオン設定にアップロードされている場合、sc パラメーターを使用して URL に証明書 ID を含めます。たとえば、0LE000000Dp が証明書 ID であるRecipient="https://acme.my.site.com/customers/login?so=00DD0000000JsCM&sc=0LE000000Dp"です。

統合 ID

Salesforce で、SAML アサーションの件名内の [統合 ID] を既存のユーザーレコードの User.FederationIdentifier 項目と照合すること。SAML シングルサインオン設定での SAML ID の場所の定義方法によっては、Salesforce は属性要素を使用して照合することもできます。

一致するユーザーレコードが見つかった場合は、SAML アサーションの属性を使用して指定された項目を更新します。一致するユーザーレコードを持つユーザーが見つからない場合、Salesforce は取引先責任者 ID (User.Contact) またはメール (Contact.Email) に基づいて、一致する取引先責任者を検索します。User.Contact を指定しない場合、Contact.Email と Contact.LastName は両方とも必須プロパティですが、一致は両方のプロパティが存在する場合のContact.Emailのみに基づきます。

一致する取引先責任者レコードが見つかった場合は、SAML アサーションの属性を使用して指定された取引先責任者項目を更新してから、新しいユーザーレコードを挿入します。一致する取引先責任者レコードが見つからない場合、Salesforce は SAML アサーションで指定されたContact.AccountまたはAccount.AccountNumberに基づいて取引先を検索します。Contact.Account を指定しない場合、Account.AccountNumber と Account.Name は必須プロパティですが、一致は両方のプロパティが存在する場合のAccount.AccountNumberのみに基づきます。

一致する取引先レコードが見つかった場合は、新しいユーザーレコードを挿入し、SAML アサーションで指定された属性に基づいて取引先レコードを更新します。一致する取引先レコードが見つからなかった場合は、Salesforce は、SAML アサーションで指定された属性に基づいて、新しい取引先、取引先責任者、ユーザーのレコードを挿入します。

ユーザーアカウントが無効な場合、ユーザーアカウントは更新されますが、JIT アサーションの User.IsActive が true に設定されていない限り、無効なままです。その [統合 ID] のユーザーアカウントが存在しない場合、ユーザーが作成されます。

プロファイル名と ID

サイト SAML アサーションでサポートされる項目

Salesforce に作成するオブジェクトを正しく識別するために、プレフィックスを使用する必要があります。SAML アサーションでは、取引先スキーマのすべての項目に Account プレフィックス (たとえば、Account.AccountId) を使用します。また、取引先責任者スキーマのすべての項目に Contact プレフィックスを使用します。次の例では、Email 項目名に Contact プレフィックスが追加されています。

<saml:Attribute 
   Name="Contact.Email" 
   NameFormat="urn:oasis:names:tc:SAML:2.0:attrname-format:unspecified">
      <saml:AttributeValue xsi:type="xs:anyType">testuser@123.org</saml:AttributeValue>
</saml:Attribute>
メモ Salesforce では、SAML アサーション内のユーザーオブジェクトのカスタム項目もサポートされています。User で始まるアサーションの属性は、カスタム項目として解析されます。たとえば、アサーションの属性 User.NumberOfProductsBought__c は、プロビジョニングされるユーザーの NumberOfProductsBought 項目に配置されます。取引先と取引先責任者ではカスタム項目はサポートされていません。

ポータルのジャストインタイム SAML アサーション項目

ポータルのジャストインタイム (JIT) プロビジョニングを使用すると、SAML アサーションを使用して、カスタマーおよびパートナーポータルユーザーが ID プロバイダーから初めてログインするときに、それらのユーザーを作成できます。Summer '13 以降、新しい Salesforce 組織ではカスタマーポータルとパートナーポータルを使用できません。 代わりに、Experience Cloud で JIT プロビジョニングを使用してください。

ポータルユーザーの作成

SAML アサーションの一部として [ポータル ID] と [組織 ID] を指定する必要があります。これらのパラメーターは、Salesforce 組織またはポータルの会社情報ページにあります。通常のユーザーもプロビジョンできるため、[ポータル ID] は、通常の要求とポータル JIT プロビジョニング要求を区別するために使用されます。[ポータル ID] が指定されていない場合、要求は通常プラットフォームユーザーの JIT 要求として扱われます。

ポータルユーザーの作成の要件は、次のとおりです。

  • SAML アサーションで [統合 ID] を指定します。ID が既存のユーザーアカウントに属する場合、そのユーザーアカウントは更新されます。ユーザーアカウントが無効な場合、ユーザーアカウントは更新されますが、JIT アサーションの User.IsActive が true に設定されていない限り、無効なままです。その [統合 ID] のユーザーアカウントが存在しない場合、ユーザーが作成されます。
  • ポータルでセルフ登録が有効になっておらず、デフォルトの新規ユーザープロファイルとロールが指定されていない場合、User.ProfileId 項目には有効なプロファイル名または ID が含まれている必要があります。さらに、User.PortalRole 項目には有効なポータルロール名または ID が含まれている必要があります。 すべてのポータルユーザーに対して Worker を使用します。
    メモ User.Role は null である必要があります。

取引先の作成と変更

有効な [取引先 ID] または Account.AccountNumber と Account.Name の両方を指定して、取引先を作成または変更します。取引先は次の条件に従って作成または変更されます。

  • 一致は Account.AccountNumber に基づきます。複数の取引先が見つかった場合、エラーが表示されます。そうでない場合は、その取引先が更新されます。
  • 一致する取引先が見つからない場合、新しい取引先が作成されます。
  • SAML アサーションに Account.Owner を指定し、この所有者のプロファイルの Account.AccountNumber 項目の項目レベルセキュリティが表示されるように設定されている必要があります。

取引先責任者の作成と変更

有効な User.Contact の取引先責任者 ID または Contact.Email と Contact.LastName の両方を指定して、取引先責任者を作成または変更します。取引先責任者は次の条件に従って作成または変更されます。

  • 一致は Contact.Email に基づきます。複数の取引先責任者が見つかった場合、エラーが表示されます。そうでない場合は、その取引先責任者が更新されます。
  • 一致する取引先責任者が見つからない場合、新しい取引先責任者が作成されます。

<saml:Attribute Name="ProvisionVersion" NameFormat=

      <saml:AttributeValue xsi:type="xs:anyType">1.0</saml:AttributeValue>

SAML アサーションの項目

標準の JIT プロビジョニングが有効になっている組織にユーザーがログインすると、Salesforce は ID プロバイダーからユーザーデータを取得し、それを新しい User オブジェクトに保存します。このオブジェクトを作成するように Salesforce に指示するには、SAML アサーションのすべての User オブジェクト項目に User. プレフィックスを使用する必要があります。次の例では、Username 項目名に User. プレフィックスが追加されています。

<saml:Attribute 
   Name="User.Username" 
   NameFormat="urn:oasis:names:tc:SAML:2.0:attrname-format:unspecified">
      <saml:AttributeValue xsi:type="xs:anyType">testuser@123.org</saml:AttributeValue>
</saml:Attribute>

各 User オブジェクト項目についての詳細は、『オブジェクトリファレンス』の「User」を参照してください。

アサーションの例は、「サンプル SAML アサーション」の「ジャストインタイムプロビジョニングのサンプル SAML アサーション」セクションを参照してください。

Salesforce は以下のクライアント設定 URL を生成します。

  • テスト専用初期化 URL — この URL を使用して、サードパーティが正しく設定されているかどうかをテストします。この URL を開いて、サードパーティにログインします。その後、属性の対応付けと共に Salesforce にリダイレクトされます。
  • シングルサインオン初期化 URL — この URL を使用して、サードパーティから組織への SSO を実行するようにユーザーをリダイレクトします。ユーザーは、この URL を開いて、サードパーティにログインします。サードパーティは、ユーザーアカウントを作成または更新して、そのアカウントでユーザーを Salesforce にログインさせます。
  • 既存のユーザーをリンクする URL — この URL を使用して、組織のユーザーをサードパーティの既存のアカウントにリンクします。このユーザーはこの URL を開いてサードパーティにログインし、Salesforce にログインして、アカウント間のリンクを作成します。
  • OAuth 専用初期化 URL — この URL を使用して、ユーザーの認証後に OAuth アクセストークンを取得します。このフローは、サードパーティデータアクセスには対応していますが、SSO には対応していません。
  • コールバック URL — 他の各クライアント設定 URL について、認証プロバイダーはコールバック URL に情報を送信します。

クライアント設定 URL には、必要に応じて要求パラメーターを追加します。たとえば、組織のユーザーをそれぞれの既存 Facebook アカウントにリンクして、Facebook からプロファイルへのアクセスを要求できるようにしたいとします。この場合は、[既存ユーザーをリンクする URL] に scope パラメーターを追加します。ユーザーがこの URL にアクセスすると、ユーザーは Facebook と組織にログインし、Facebook が自分の Salesforce プロファイル情報にアクセスするための要求を受け取ります。

メモ Janrain プロバイダーの場合は、適切なコールバック URL に要求パラメーターを追加します。
  • (Salesforce 認証プロバイダーのみ) 認証エンドポイント — ユーザーを認証用の特定の認証エンドポイントに転送します。
  • Experience Cloud — 認証後にユーザーを特定のサイトに転送します。
  • expid — 異なるユーザー環境を提供します。たとえば、expid パラメーターを使用して、ユーザーが使用している言語ごとに異なる登録プロセスを提供します。
  • prompt — 認証サーバーがユーザーに再認証および再承認を促す方法を指定します。たとえば、アカウントの作成後に、ユーザーにログインを促します。
  • scope — サードパーティがユーザーに要求できる情報をカスタマイズします。たとえば、、サードパーティがユーザーのプロファイル情報へのアクセスを要求できるようにします。
  • site — 認証プロバイダーをサイトで使用できるようにします。
  • 保護された URL リダイレクトパラメーター — ユーザーが認証された後、もしくはユーザーが [戻る]、[保存]、[キャンセル] ボタンをクリックした後で、ユーザーを指定された場所に転送します。

設定のヘルプ

  • 認証プロバイダーへの機能の動的追加
    認証プロバイダー機能を最大限柔軟にするには、独自の URL パラメーター転送許可リストを作成します。許可リストを使用すると、許可リストに登録されたパラメーターを実行時にクライアント設定 URL に動的に追加し、サードパーティプロバイダーに転送できます。たとえば、ユーザーの言語設定をサードパーティプロバイダーに転送して、プロバイダーのログインページがユーザーの希望する言語で表示されるようにします。
  • 承認のためのユーザー送信場所の制御
    Salesforce 認証プロバイダーを設定する場合に、認証エンドポイントホスト要求パラメーターを使用することで、認証要求を承認するためのページにユーザーを転送できます。このパラメーターは、Salesforce 認証プロバイダーにのみ使用できます。Salesforce ドメイン外の認証ページにユーザーを転送するために使用することはできません。
  • 認証後の Experience Cloud サイトへのユーザーの転送
    認証プロバイダーを使用してシングルサインオン (SSO) を設定する場合は、Experience Cloud サイト URL 要求パラメーターを使用して、ユーザーを認証後に特定のサイトに転送します。サイトパラメーターを使用することで、ユーザーを Salesforce 組織または Experience Cloud サイトのどちらにログインさせるかを指定できます。このパラメーターでは、登録ハンドラーが作成するユーザーの種別も変更できます。
  • 認証プロバイダーのユーザーエクスペリエンスの制御
    認証プロバイダーを使用して Salesforce Experience Cloud サイトのシングルサインオン (SSO) を設定する場合に、expid 要求パラメーターを使用することで、異なるユーザー環境を提供できます。
  • ユーザーに再認証と再承認を求める
    認証プロバイダーを使用して Salesforce コミュニティのシングルサインオン (SSO) を設定する場合は、必要に応じて prompt URL 要求パラメーターをクライアント設定 URL に追加できます。このパラメーターは、認証サーバーがユーザーに対して再ログインとデータアクセスの再承認を促す方法を指定します。たとえば、ユーザーがアカウントにサインアップした後で再ログインを促すことができます。
  • 証明書利用者データ要求のカスタマイズ
    認証プロバイダーを使用してシングルサインオン (SSO) を設定する場合に、scope パラメーターを使用することで、サードパーティ (Facebook など) のデータへの要求をカスタマイズできます。たとえば、ユーザーの Facebook プロファイルに記載されているメールアドレスへのアクセスを要求できます。このパラメーターは、Janrain 以外のすべての認証プロバイダーで使用できます。
  • 認証プロバイダー向けの Salesforce サイトのサポート
    認証プロバイダーを使用してシングルサインオン (SSO) を設定する場合は、site URL 要求パラメーターを使用して、ユーザーを特定のサイトにログインさせます。サイトユーザーにリンクすることもできます。
  • ユーザーを安全な URL にリダイレクト
    認証プロバイダーを使用してシングルサインオン (SSO) を設定する場合に、保護された URL リダイレクトパラメーターを使用することで、ユーザーを *.force.com ページに転送して、悪意のあるリダイレクトを防止できます。

認証プロバイダーシングルサインオン (SSO) フローでは、証明書利用者がユーザーを認証エンドポイントに転送することによって認証を開始します。カスタムドメイン ([私のドメイン] など) の認証エンドポイントにユーザーを転送するには、認証エンドポイントホストパラメーターを Salesforce クライアント設定 URL に追加します。

たとえば、Salesforce 認証プロバイダーを設定して、カスタム Your Benefits (従業員福利厚生) アプリケーションで SSO を設定します。認証エンドポイントホスト要求パラメーターを SSO クライアント設定 URL に追加することで、特定の Salesforce ドメインにユーザーを認証用に転送します。ユーザーが Your Benefits (従業員福利厚生) アプリケーションに移動してログインすると、認証エンドポイントにリダイレクトされ、そこで Salesforce ログイン情報を入力します。このエンドポイントでは、Your Benefits (従業員福利厚生) アプリケーションのデータへのアクセスを承認するかどうかが尋ねられます。

ユーザーを特定の Salesforce 認証エンドポイントに転送するには、有効な HTTPS ホストを指定した provAuthorizeEndpointHost 要求パラメーターをクライアント設定 URL に追加します。ホスト URL に追加されたクエリ文字列は無視されます。ただし、サイトパスは指定できます。

例

次に、ユーザーを [私のドメイン] に転送して認証するために [シングルサインオン初期化 URL] に追加された provAuthorizeEndpointHost パラメーターの例を示します。ここで、

https://login.salesforce.com/services/auth/sso/orgID/
URLsuffix?provAuthorizeEndpointHost=https://MyDomainName.my.salesforce.com
  • orgID は、Salesforce 認証プロバイダー ID です。
  • URLsuffix は、Salesforce 認証プロバイダーを設定したときに指定した値です。

以下に、サイト URL にユーザーを転送して認証するための provAuthorizeEndpointHost パラメーターの例を示します。

https://login.salesforce.com/services/auth/sso/orgID/
URLsuffix?provAuthorizeEndpointHost=https://MyDomainName.my.site.com%2Fbilling

認証エンドポイントが指定されていない場合、Salesforce は Salesforce 認証プロバイダーのデフォルトの認証エンドポイントを使用します。認証プロバイダーにデフォルトが設定されていない場合、Salesforce では login.salesforce.com のエンドポイントが使用されます。

認証エンドポイントを変更しても、トークンエンドポイントには影響しません。トークンエンドポイントは、設定されたホストまたはデフォルトのホストのままになります。Sandbox インスタンスと本番インスタンスでは、認証エンドポイントとトークンエンドポイントが一致することが重要です。

たとえば、本番トークンエンドポイントを使用するようにプロバイダーが設定されているとします。認証エンドポイントを Sandbox インスタンスに設定すると、Sandbox インスタンスのみが認証を許可されているため、フローは失敗します。このエラーを修復するには、認証エンドポイントを本番インスタンスに変更して、トークンエンドポイントと一致させます。

たとえば、Google 認証プロバイダーを設定し、自分の Salesforce 組織を証明書利用者として SSO を設定するとします。そして、ユーザーが Google アカウントを作成したら、新しい Google ログイン情報でログインするように促します。このプロンプトを設定するには、prompt パラメーターを SSO クライアント設定 URL に追加して、Google でサポートされる値を使用します。

Salesforce 認証プロバイダーは、prompt パラメーターで次の値をサポートします。

  • login — 認証サーバーはユーザーに再認証を求めて、再ログインを強制します。

例 この例では Salesforce でサポートされている値を使用しています。値を login に設定した prompt パラメーターを [シングルサインオン初期化 URL] に追加する例を示します。 
https://login.salesforce.com/services/auth/sso/00Di0000000hqQ8EAI/FB?prompt=login

認証プロバイダー SSO フローでは、scope パラメーターで指定する範囲によって、証明書利用者が要求できるデータの種別を定義します。ユーザーがログインすると、証明書利用者は認証要求を送信します。サードパーティは、ユーザーを検証し、範囲が指定されたアクセストークンを返します。ユーザーが範囲で定義されるデータへのアクセスを承認すると、証明書利用者は要求したサードパーティデータにアクセスできるようになります。

たとえば、Google 認証プロバイダーを設定し、自分の Salesforce 組織を証明書利用者として SSO を設定するとします。そして、ユーザーが自分の Google ドライブのデータを Salesforce 組織で表示できるようにします。そのため、scope パラメーターを SSO クライアント設定 URL に追加し、要求した範囲が指定されたアクセストークンを取得するための Auth.AuthToken メソッドを実装します。ユーザーが組織にログインすると、Google にリダイレクトされて認証され、Salesforce から Google ドライブへのアクセスを承認します。その後、ユーザーの Google ドライブデータを Salesforce で表示できるようになります。

メモ 一部のサードパーティでは、要求するデータの範囲を事前に登録する必要があります。

ユーザーが指定する範囲に加えて、認証プロバイダーにはデフォルトの範囲も用意されています。デフォルトの範囲はサードパーティによって異なりますが、一般に、基本的なユーザー情報へのアクセスは制限されています。たとえば、Salesforce のデフォルト範囲は id であり、ユーザーの ID へのアクセスを許可します。デフォルトの範囲を上書きするには、範囲をスペースで区切って指定した文字列をサードパーティに送信します。

  1. scope パラメーターをクライアント設定 URL に追加します。
  2. Apex Auth.AuthToken メソッドを使用してアクセストークンを取得します。詳細は、『Apex リファレンスガイド』の「AuthToken クラス」を参照してください。

登録ハンドラーの設定

シングルサインオンに認証プロバイダーを使用するには、登録ハンドラーを作成する必要があります。登録ハンドラーがユーザーを作成し、ID プロバイダーを介して Salesforce にアクセスする既存のユーザーを更新します。Apex または Flow Builder を使用して登録ハンドラを設定できます。詳細は、「Create an Authentication Provider Registration Handler (認証プロバイダー登録ハンドラーの作成)」を参照してください。

Amazon アプリケーションの設定

Amazon アプリケーションにより、ユーザーが Amazon ログイン情報を使用して Salesforce 組織にログインできます。

  1. https://login.amazon.com/manageApps に移動して、Amazon 開発者アカウントにログインします。
  2. [Register new application (新規アプリケーションを登録)] をクリックします。
  3. アプリケーション情報を入力して保存します。
  4. [Web Settings (Web 設定)] を展開します。
  5. クライアント ID とクライアントの秘密をコピーします。
  6. [Allowed Return URLs (許可された戻り URL)] は空白のままにします。この項目には後で Salesforce コールバック URL を入力します。この URL は、ログイン時に組織が Amazon 承認サービスへの応答に使用するアドレスです。

Salesforce での Amazon 認証プロバイダーの作成

Amazon を外部認証プロバイダーとして認識するように Salesforce 組織を設定します。この手順では、ログイン時に Amazon ログイン情報を使用するよう組織に指示します。

  1. [設定] から、[クイック検索] ボックスに「認証プロバイダー」と入力し、[認証プロバイダー] | [新規] を選択します。
  2. プロバイダータイプには [Open ID Connect] を選択します。
  3. 認証プロバイダーの名前を入力します (例: 「MyAmazon」)。Salesforce がこの名前をコールバック URL の URL 接尾辞に設定し、アプリケーションが Salesforce の認証要求に応答できるようにします。たとえば、名前とサフィックスの組み合わせが MyAmazon の場合、SSO URL は https://mydomain_login_url または site_url/services/auth/sso/MyAmazon のようになります。
  4. [コンシューマー鍵] には、先ほどコピーしたクライアント ID を入力します。
  5. [コンシューマーの秘密] には、クライアントの秘密を入力します。
  6. Amazon のエンドポイントを入力します。
    • 承認エンドポイント URL — https://www.amazon.com/ap/oa
    • トークンエンドポイント URL — https://api.amazon.com/auth/o2/token
    • ユーザー情報エンドポイント URL — https://api.amazon.com/user/profile
    • デフォルトの範囲 — 「プロファイル」

    エンドポイントについての詳細は、「認証エンドポイントパラメーターの使用」を参照してください。

  7. Apex 登録ハンドラを使用するには、次の手順を実行します。
    1. [登録ハンドラ種別] で、[Apex] を選択します。
    2. [登録ハンドラ] で、Auth.RegistrationHandler インタフェースを実装する既存の Apex クラスを選択します。または、登録ハンドラのテンプレートを作成するには、[登録ハンドラテンプレートを自動的に作成] をクリックします。このクラスを後で編集してデフォルトのコンテンツを変更してから使用します。
  8. 登録ハンドラーにフローを使用するには、次の手順を実行します。
    1. [登録ハンドラ種別] で、[フロー] を選択します。
    2. [登録ハンドラー] で、[ID ユーザー登録] フロー種別の既存のフローを選択します。
    3. デフォルトプロファイルを選択します。登録ハンドラーを実行するには、デフォルトプロファイルが必要です。ここでデフォルトプロファイルを指定しない場合、フロー自体でデフォルトプロファイルを設定します。

      認証プロバイダーユーザー登録フローテンプレートを使用する場合、ここで設定したプロファイルは defaultProfileId 変数に自動的に保存されます。

    4. デフォルトの取引先を選択します。Experience Cloud サイトで認証プロバイダーを使用している場合、このアカウントには新しい内部ユーザーが保存されます。

      「認証プロバイダーのユーザー登録」フローテンプレートを使用する場合、ここで設定したプロファイルは自動的に defaultAccountId 変数に保存されます。

  9. [Execute Registration As (登録の実行ユーザー)] で、Apex クラスまたはフローを実行する実行ユーザーを選択します。このユーザーは「ユーザーの管理」権限を持っている必要があります。

    [他のアカウントで登録を実行] では、登録ハンドラーが動作するコンテキストが提供されます。本番環境では、通常、[他のアカウントで登録を実行] ユーザー用にシステムユーザーを作成します。このように、ハンドラーによって実行される操作は、その登録プロセスが簡単に特定されます。たとえば取引先責任者が作成される場合、システムユーザーがそれを作成します。

  10. 設定を保存します。

Amazon アプリケーションの Salesforce コールバック URL の更新

  1. Salesforce の Amazon 用の [認証プロバイダー] ページで、コールバック URL をコピーします。
  2. Amazon アプリケーションページで、[Web Settings (Web 設定)] にある [Edit (編集)] をクリックします。[Allowed Return URLs (許可された戻り URL)] に、Salesforce コールバック URL を入力します。設定を保存します。

SSO 接続のテスト

Salesforce の [認証プロバイダー] ページに、[テスト専用初期化 URL] が示されます。この URL を使用すれば、Salesforce 組織にログインしなくても、設定が正しく行われているかどうかを確認できます。ブラウザーでこの URL を開いて Amazon にサインインすると、一連のユーザー属性によって Salesforce にリダイレクトされます。

  1. Salesforce で、Amazon 認証プロバイダーの詳細ページに移動します。
  2. テスト専用初期化 URL をコピーします。
  3. ブラウザーを開いてテスト URL を入力します。Amazon にリダイレクトされます。
  4. アカウントを選択してログインし、Amazon アプリケーションへのアクセスを承認します。
  5. [OK] をクリックします。ログインに成功すると、Amazon に登録されているコールバックにリダイレクトされます。Amazon がユーザーおよびアプリケーションに関する情報を返します。

次はいよいよ、登録ハンドラー、認証プロセス、Salesforce 組織へのログインなど、エンドツーエンドの SSO 設定をテストします。

  1. Salesforce 組織への SSO をテストします。

    2. Amazon 認証サービスを選択して、設定を保存します。

    4. Amazon 認証サービスを選択して、Amazon ログイン情報を入力します。
  2. Salesforce Experience Cloud サイトへの SSO をテストします。
    1. まだ Amazon 認証サービスアカウントを作成していない場合は作成します。
    2. サイトユーザー用の十分なライセンスがあることを確認します。
    3. [設定] から、[クイック検索] ボックスに「デジタルエクスペリエンス」と入力し、[すべてのサイト] を選択します。
    4. 編集するサイトの横にある [ワークスペース] をクリックします。
    5. エクスペリエンスワークスペースのメニューから、[管理] を選択し、[ログイン & 登録] を選択します。
    6. [ログイン] で、Amazon 認証プロバイダーを表示するオプションを選択し、設定を保存します。
    7. ログアウトして、サイトのログインページに移動します。
    8. Amazon 認証サービスを選択し、Amazon ログイン情報を使用してログインします。

      「認証プロバイダーのユーザー登録」フローテンプレートを使用する場合、ここで設定したプロファイルは自動的に defaultAccountId 変数に保存されます。

  15. [Execute Registration As (登録の実行ユーザー)] で、Apex クラスまたはフローを実行する実行ユーザーを選択します。このユーザーは「ユーザーの管理」権限を持っている必要があります。

    [他のアカウントで登録を実行] では、登録ハンドラーが動作するコンテキストが提供されます。本番環境では、通常、[他のアカウントで登録を実行] ユーザー用にシステムユーザーを作成します。このように、ハンドラーによって実行される操作は、その登録プロセスが簡単に特定されます。たとえば取引先責任者が作成される場合、システムユーザーがそれを作成します。

  16. プロバイダーでポータルを使用するには、[ポータル] ドロップダウンからポータルを選択します。
  17. [アイコン URL] で、[いずれかのサンプルアイコンを選択] を選択して、使用可能なアイコンのリストを開きます。Apple アイコンを選択して URL をコピーし、[アイコン URL] に入力します。
    このアイコンはサイトのログインページに表示されます。ユーザーはこのアイコンをクリックして Apple ID を使用してログインします。
  18. ID プロバイダーの MFA サービスではなく、Salesforce 多要素認証 (MFA) 機能を使用するには、[この SSO プロバイダーで Salesforce MFA を使用] を選択します。この設定は、MFA が直接適用されているユーザーの MFA のみをトリガーします。詳細は、「SSO (Salesforce 組織) での Salesforce MFA の使用」を参照してください。
  19. 変更内容を保存します。

Salesforce で [認証プロバイダー] 詳細ページが表示され、Apple 認証プロバイダーの作成後に生成されたクライアント設定 URL がリストされます。

  • テスト専用初期化 URL — この URL を使用して、サードパーティプロバイダーが正しく設定されていることを確認します。システム管理者がブラウザーでこの URL を開き、Apple にサインインすると、属性の対応付けにより Salesforce にリダイレクトされます。
  • シングルサインオン初期化 URL — この URL を使用して、Apple ログイン情報で Apple から Salesforce へのシングルサインオン (SSO) を実行します。ユーザーは、ブラウザーでこの URL を開いて、サードパーティにサインインします。Apple は、ユーザーを作成するか既存のユーザーを更新します。次に Apple は、ユーザーを Salesforce にそのユーザーとしてサインインします。
  • 既存ユーザーをリンクする URL — この URL を使用して、既存の Salesforce ユーザーを Apple アカウントにリンクします。このユーザーはブラウザーでこの URL を開いて Apple にサインインし、Salesforce にログインしてリンクを承認します。
  • OAuth 専用初期化 URL — この URL を使用して、Apple の OAuth アクセストークンを取得します。Apple サービスがトークンを取得するには、ユーザーが Salesforce で認証する必要があります。このフローでは、以降の SSO 機能は提供されません。
  • コールバック URL — Apple でサインインサービスが Salesforce にコールバックするために使用するエンドポイントにこの URL を使用します。Apple は、各クライアント設定 URL の情報と共に、コールバック URL にリダイレクトします。

コールバック URL を使用した Apple 設定の更新

Salesforce で Apple 認証プロバイダーを作成したら、Apple のサービス ID の設定ページに戻ります。Salesforce で生成された Apple 認証プロバイダーからコールバック URL を使用するには、戻り URL を更新します。

SSO 接続のテスト

ブラウザーの認証プロバイダーの詳細ページで [テスト専用初期化 URL] を開きます。ユーザーは Apple にリダイレクトされ、サインインするよう求められます。そしてサインイン時に、アプリケーションを認証するよう求められます。認証後、ユーザーは Salesforce にリダイレクトされます。

Apple ID を使用したシングルサインオンのテスト

次はいよいよ、SSO 設定をテストして Salesforce にログインします。

  1. Salesforce への SSO をテストします。
    1. [設定] から、[クイック検索] ボックスに「ドメイン」と入力し、[私のドメイン] を選択します。
    2. [認証設定] で [編集] をクリックします。
    3. Apple を認証サービスとして選択して、設定を保存します。
    4. ログアウトして、サブドメインの Salesforce ログインページに移動します。
    5. Apple 認証サービスを選択して、Apple ログイン情報を入力します。
  2. Experience Cloud サイトへの SSO をテストします。
    1. まだ Apple 認証サービスアカウントを作成していない場合は作成します。
    2. サイトユーザー用の十分なライセンスがあることを確認します。
    3. [設定] から、[クイック検索] ボックスに「デジタルエクスペリエンス」と入力し、[すべてのサイト] をクリックします。サイトの横にある [ワークスペース] を選択します。
    4. [管理] を選択してから、[ログイン & 登録] を選択します。
    5. [ログイン] で、Apple 認証プロバイダーを表示するオプションを選択し、設定を保存します。
    6. ログアウトして、サイトのログインページを開きます。
    7. Apple アイコンをクリックし、Apple ログイン情報を使用してログインします。

Apple 認証プロバイダーと非公開鍵の管理

Apple 認証プロバイダーを作成したら、編集して、設定を変更したり新しい Apple 鍵をアップロードしたりできます。たとえば、鍵が侵害されたと思われる場合は新しい Apple 鍵をアップロードします。新しい Apple 鍵をアップロードしたら、古い鍵を取り消します。

新しい Apple 鍵をアップロードするには、Apple からコンピューターに新しい鍵をダウンロードします。鍵は末尾が .p8 のテキストファイルに含まれています。

  1. Apple で、Apple ヘルプの「サービスにアクセスするための秘密鍵を作成する」に従って Apple 鍵を作成します。

  3. Apple 認証プロバイダーの横にある [編集] をクリックします。
  4. [キーをアップロード] をクリックし、Apple からダウンロードした .p8 ファイルを選択します。
  5. 新しい鍵をアップロードしたら、Apple ヘルプの「鍵を無効化、編集、ダウンロードする」に従って古い鍵を取り消します。
